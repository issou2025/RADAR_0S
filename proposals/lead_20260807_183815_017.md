**SIGSEGV in QApplicationPrivate::setFocusWidget shortly after closing a task dialog (macOS)**

## Problem description

`TaskView::removeDialog()` in `src/Gui/TaskView/TaskView.cpp` deletes the
task dialog's `ActiveCtrl` (the standard OK/Cancel/Apply button bar) and
`taskPanel` with a raw `delete` instead of `deleteLater()`. Both are
`QWidget`s, and `ActiveCtrl` in particular is very likely to hold keyboard
focus at the exact moment this runs (it's the button bar the user just
clicked to close the dialog). A raw `delete` doesn't give Qt a chance to
clear its internal per-window "last focused widget" bookkeeping first, so
the pointer goes stale. The next time that window is reactivated by a
mouse click, Qt tries to restore focus into the freed widget and segfaults
inside `QApplicationPrivate::setFocusWidget`.

We captured 3 crashes sharing this identical stack over about a week of
normal use (out of 5 total crash reports collected; the other 2 are
unrelated). The user-visible symptom is confusing: FreeCAD just dies
shortly after a click in the 3D view, with no apparent connection to the
task dialog that had been closed earlier.

This is the same crash *shape* as #15157 (VarSet dialog segfaulting inside
Qt's focus-widget code because FreeCAD deleted a widget Qt's focus
subsystem could still reference), fixed there with the same kind of change.

Core (App, Gui,...)

## Steps to reproduce

1. Open any task dialog that uses the standard control bar — e.g. select an
   object and run **Edit > Placement** (`Std_TransformManip`).
2. Close the dialog (OK or Cancel) — ideally with a real mouse click on the
   button, see note below.
3. Click somewhere in the FreeCAD window (e.g. the 3D view background).

**Note on reproduction:** this is intermittent, not on-demand — 3 crashes
over a week, not a guaranteed repro every cycle. We tried to force a live
repro via automation (both on the build with this fix and, for comparison,
on an unpatched build) using `Gui.runCommand('Std_TransformManip')` +
`Gui.Control.closeDialog()` followed by simulated window reactivation, and
could not trigger the crash on either build. Looking at the crash log
below, the real chain runs through
`-[NSWindow(NSEventRouting) _handleMouseDownEvent:isDelayedEvent:]` on the
way to `becomeKeyWindow` — i.e. a genuine OS mouse-down, not just window
activation in the abstract — which our automation (window activation via
macOS Accessibility, and even explicitly priming Qt's focus record with
`QWidget.setFocus()` on the button beforehand) didn't reach; a true
synthetic click was blocked by Accessibility permissions in our test
environment. So this report is based on the 3 captured real-world crash
logs plus the source-level defect, not a fresh on-demand repro — a human
physically clicking OK then clicking the 3D view a few times is more likely
to reproduce it than what we automated.

### Root cause

`src/Gui/TaskView/TaskView.cpp`, `TaskView::removeDialog(std::vector<TaskInfo>::iterator)`:

```cpp
if (remove) {
    remove->ActiveDialog->closed();
    remove->ActiveDialog->emitDestructionSignal();
    delete remove->ActiveCtrl;
    delete remove->ActiveDialog;
    delete remove->taskPanel;
}
```

`ActiveCtrl` (`TaskEditControl : TaskWidget : QWidget`) and `taskPanel`
(`TaskPanel : QWidget`) are real widgets that can still be referenced by
Qt's focus-restore bookkeeping. This same file already handles the
equivalent situation correctly elsewhere — `TaskView::removeContextualPanel()`
uses `panel->deleteLater()` for the same kind of widget — so the fix below
just makes `removeDialog()` consistent with that existing pattern.

### Suggested fix

```diff
     if (remove) {
         remove->ActiveDialog->closed();
         remove->ActiveDialog->emitDestructionSignal();
-        delete remove->ActiveCtrl;
+        remove->ActiveCtrl->deleteLater();
         delete remove->ActiveDialog;
-        delete remove->taskPanel;
+        remove->taskPanel->deleteLater();
     }
```

(`ActiveDialog` is a `QObject`, not a `QWidget`, so it isn't part of Qt's
focus chain and doesn't need the same treatment.)

We've applied this locally, rebuilt cleanly, and run it through repeated
open-dialog/close-dialog/reactivate cycles without incident — reassurance,
not proof, given we couldn't force the original crash on demand either (see
note above). The fix itself is a minimal, low-risk `delete` → `deleteLater()`
swap matching an already-correct pattern in the same file, so we're
confident in it on code-review grounds independent of that testing gap.
Happy to open a PR with it, or leave it to a maintainer.
