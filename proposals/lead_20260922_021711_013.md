## Problem

The repository-specific review guide should let a reviewer decide ownership before a detailed technical audit. Reusable extension content has sometimes included host, runtime, profile, or Canvas machinery that belongs in another repository.

Generic support for an early scope outcome and maintainer handoff is tracked in #640.

## Acceptance criteria

- The repository review guide starts with a concise ownership/scope gate.
- It identifies extensions-owned work: reusable skills, automations, MCP integrations, and extension content built on public host/runtime capabilities.
- It identifies common work owned elsewhere:
  - runtime, agent-server, and client contracts in OpenHands/software-agent-sdk;
  - generic automation scheduling, state, dispatch, and profile-selection machinery in OpenHands/automation;
  - Canvas product UI and app integration in OpenHands/OpenHands.
- It recognizes legitimate coordinated cross-repository stacks and evaluates whether this PR contains only reusable extension content.
- Wrong-repository, unresolved architecture, obsolete/duplicate, and contrary-to-direction outcomes stop before exhaustive code review and request a maintainer decision.
- Clearly in-scope changes continue through the existing packaging, installation, portability, permissions, prompt-quality, and test criteria.
- The guidance uses stable categories, not lists of PR numbers, and is concise enough to apply consistently.

### Desired Behavior
A reviewer opening the repository review guide meets an ownership/scope gate first, ahead of every executable-instruction, credential, sources-of-truth, documentation-claims, dependency, and evidence checkpoint. The gate states what this repository owns (reusable skills, plugins, automation bundles, integrations, and extension content built only on public host/runtime capabilities) and what belongs elsewhere (`OpenHands/software-agent-sdk` for runtime, agent-server, and client contracts; `OpenHands/automation` for generic automation scheduling, state, dispatch, and profile selection; `OpenHands/OpenHands` for Canvas product UI and app integration). A PR that is in the wrong repository, whose product/architecture direction is unresolved, that is obsolete or duplicated, or that runs contrary to the current direction stops at the gate and requests a maintainer decision instead of continuing into exhaustive code review. Coordinated cross-repository stacks remain legitimate when this PR's own diff contains only reusable extension content, and clearly in-scope changes continue through the guide's existing downstream criteria unchanged.

### Acceptance Criteria
- [ ] In `.agents/skills/custom-codereview-guide.md`, the ownership/scope gate appears before the executable-instruction/runtime-parity, untrusted-trigger/credential, sources-of-truth, documentation-claims, dependency/supply-chain, and evidence-discipline checkpoints, so a reviewer reads scope before a technical audit.
- [ ] The gate names extensions-owned work: reusable skills, plugins, automation bundles, integrations, and extension content that builds only on public host/runtime capabilities.
- [ ] The gate names the out-of-scope ownership areas together with their owning repositories: runtime, agent-server, and client contracts -> `OpenHands/software-agent-sdk`; generic automation scheduling, state, dispatch, and profile selection -> `OpenHands/automation`; Canvas product UI and app integration -> `OpenHands/OpenHands`.
- [ ] The gate states that a coordinated cross-repository stack is legitimate and gives a decision rule for it: judge whether this PR's own diff contains only reusable extension content, rather than treating cross-repository references as automatically out of scope.
- [ ] The gate defines the four stop outcomes - wrong repository, unresolved product/architecture decision, obsolete/duplicate, and contrary to current direction - as maintainer-decision outcomes that stop before exhaustive code review and that neither approve the PR nor enable auto-merge.
- [ ] The gate states that a clearly in-scope change proceeds unchanged through the guide's existing packaging, installation, portability, permissions, prompt-quality, and test criteria.
- [ ] For a wrong-repository outcome the gate directs the reviewer to name the likely owning repository when the evidence supports it, and to omit the name when it does not.
- [ ] The scope gate uses stable categories only: it contains no list of individual PR numbers and no enumerated case history.
- [ ] The guide's existing downstream checkpoints, evidence discipline, and repository conventions (plain hyphens, no em dashes) remain intact, and no new reference file or parallel guidance document is added.
- [ ] The repository's documented test command `uv sync --group test` followed by `uv run pytest -q` passes on the change.
- [ ] A reviewer applying only the gate can classify a PR whose diff is host/runtime, automation scheduling/dispatch, or Canvas UI machinery as out of scope, state which of the four reasons applies, and reach a maintainer-decision outcome that does not approve the PR.
