# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**The CLI command names came from a sketch, not a design**

*Project description:*
These command names were never designed. They come from a rough example — a
sketch written to illustrate what a pipeline would roughly look like, using
whatever words made the sentence readable at the time. That sketch got
implemented literally, and the words became an API.

So the names are not wrong because someone chose badly. They are wrong because
nobody chose at all, and an illustration was promoted to a specification by
being built.

It is worth fixing before the bundle package lands, because that work fixes the
shape in place: once generated output has a home and commands write to it, every
name here is one more thing a project depends on.

## What ships today

```
good create
good generate            Write lib/good.generated/ from the assets the pubspec declares.
good assets compact      Convert source art into the one canonical format per kind.
good assets pack         Chunk, compress and encrypt the assets a build ships.
good build <platform>    windows | linux | android | ios
```

Four problems, in rising order of how much they cost.

**`generate` does not say what it generates.** It writes typed asset keys. The
name would fit code generation of any kind, and there is going to be more than
one kind.

**`compact` is not compaction.** It converts jpg-beside-png-beside-webp into one
format per kind, so the runtime carries one decoder instead of six. That is
normalisation. "Compact" reads as size reduction, which is `pack`'s job.

**`pack` does three things**, and one of them belongs to a different phase.
Compress, encrypt, chunk. Encryption is a release concern that has nothing to do
with chunking, and the code already knows it — `pack` takes `--encryption` with
an `aes` default and a debug mode that skips compression and encryption
entirely. So the coupling is already conditional; the name just does not admit
it.

**Nothing says which order to run them in.** The real order is compact, pack,
generate, build. Nothing in the help text implies it.

## Not a proposal — a second sketch

```
# ILLUSTRATION ONLY. No name below is decided. Do not implement this block.
good create
good assets pack         # source art -> bundle package assets
good assets <verb>       # write the typed asset keys
good build <platform>    # compile, encrypt, package
```

This is where the previous names came from too, so it is worth saying plainly:
**the block above is the same kind of artifact that caused this issue.** It
exists to make the shape of the discussion visible, not to be built. The design
below it is about the *phases* and what belongs in each; the words are
placeholders until the phase model is settled, and then the names follow from
it.

What is genuinely being argued, independent of any name:

**Encryption belongs in the build phase.** Three things fall out of it, and they
are the argument:

- **A key never has to sit anywhere a repo can see it.** Encryption at pack time
  means the key is present whenever assets are packed, which is every iteration.
  At build time it is needed once, by the thing that already handles signing.
- **Development stops paying for it.** Re-chunking after an art change currently
  re-encrypts. The debug mode exists precisely to avoid that, which is the
  design telling us where the seam belongs.
- **Chunks in the bundle package become inspectable.** A developer can look at
  what was packed. Today the release path produces opaque bytes at the one point
  someone might want to check them.

The cost is a build-order constraint: the chunks the bundle package declares
must be encrypted **before** the Flutter build bundles them, so `good build` has
to rewrite them in place and then invoke the platform build. That ordering has
to be explicit, because getting it wrong ships plaintext assets and nothing
fails.

**Normalisation and chunking may be one step or two.** They are always run in
sequence today and neither is independently useful, which argues for one.

The counter-argument is iteration speed: normalisation is ffmpeg over every
texture and is slow, chunking is fast, and folding them means paying for ffmpeg
whenever you want to re-chunk. So folding needs the normalisation step to be
cached on content hash, or it makes the common case worse. If that cache is not
worth building yet, the two stay separate and only get renamed.

## "key" is already taken, and this is the trap

`good assets key generate` reads well until you notice the codebase already has
`good_cli/lib/src/assets/key_material.dart`, and `pack` takes an encryption key.

So `good assets key` would mean two different things depending on who is
reading: the typed Dart identifiers that name assets, or the AES key material
that encrypts them. Those are different objects with different lifetimes and
different secrecy, and one of them is about to become `good build`'s
responsibility.

Options, none chosen:

- **`good assets bind`** — writes the bindings. Leaves "key" free for encryption.
- **`good assets keys`** (plural, no sub-verb) — shorter, still collides.
- **`good generate keys`** — keeps generation as the verb and asset keys as the
  object, at the cost of splitting asset work across two top-level commands.

Whatever it becomes, **the encryption key and the asset keys must not share a
noun in the command tree.**

## Also open

- **Does `good build` still take a platform subcommand**, or a `--target` flag?
  Four subcommands that differ only in target is a lot of surface for one axis.
- **Should any of this run automatically?** The bundle package work already
  established that `good generate` has to run `flutter pub get` itself, because
  every off-path state fails silently. The same question applies to whether
  `good build` should pack first rather than trusting that someone did.
- **What `good create` scaffolds** changes with the answer, since it writes the
  first version of every generated artifact.

## Done when

The tree describes what each step does, the encryption phase is stated rather
than implied by a flag default, and no two commands share a noun that means
different things.
