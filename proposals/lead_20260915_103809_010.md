# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[Impeller][Vulkan][Android] Virtual Display platform view renders as sheared, repeating garbage on Mali-G72 (MediaTek MT8788, Android 13)**

*Project description:*
### Steps to reproduce

Up front, so nobody wastes time: **this is a production field report, not a locally reproduced bug.** I do not own the affected hardware and have not been able to reproduce it on any device I have. I am filing it because the corruption pattern is specific enough to point at a concrete code path, and because `IsKnownBadDriver()` has no Mali handling at all (details under Actual results).

What the affected user did:

1. Launch the app on a **wheatek WP36_A16_EEA (WP36)**, `Build.HARDWARE = mt8788`, **Android 13**. The MT8788 ships an **Arm Mali-G72 MP3**.
2. Open a screen whose body is a native map rendered through an Android platform view.
3. The platform view is hosted in **Virtual Display** mode — `PlatformViewsService.initAndroidView` via the `AndroidView` widget — and the native `MapView` inside it is configured to use a `TextureView` rather than a `SurfaceView`.
4. Observe the platform view region.

Relevant configuration:

- Flutter **3.41.6**, framework `db50e20168`, engine `425cfb54d0`.
- Impeller enabled (default). The app's `AndroidManifest.xml` sets no `io.flutter.embedding.android.EnableImpeller` and no `io.flutter.embedding.android.ImpellerBackend`, so the engine picks its own backend.
- The rest of the Flutter UI on the same screen is ordinary widgets composited on top of the platform view.

### Expected results

The platform view region displays the content the native view drew into it, correctly.

### Actual results

The platform view region is filled with corrupt pixels. Every Flutter-drawn widget on the same screen — app bar, scale bar, icon buttons, a rounded label pill, the FAB, the bottom navigation bar — renders **pixel-perfect**. Only the platform view is destroyed.

The corruption is not random noise. Zoomed in 8x (second and third attachments) it is clearly **periodic and sheared**:

- A small motif repeats horizontally at a fixed period.
- Each successive scanline is offset by a constant amount, producing diagonal banding.
- One band is a perfectly regular dot grid at a fixed pitch.

That is the signature of a buffer being sampled with an **incorrect row stride / tiling layout** rather than corrupt source content. The pixels are present and structured, the layout is misinterpreted. Genuinely corrupt source imagery would still show recognisable structure aligned to its own boundaries, and a driver producing random garbage would not produce a constant per-row shear.

In Virtual Display mode the native view draws into a `VirtualDisplay`-backed `SurfaceTexture`, which the engine imports as an external texture for Impeller to sample. On the Vulkan backend that is the SurfaceTexture trampoline path. A stride/tiling mismatch when importing that buffer into a Vulkan image would produce exactly this artifact, and would leave normal Flutter rendering untouched, which matches what is observed.

### Why I think this is worth a denylist look regardless

In `engine/src/flutter/impeller/renderer/backend/vulkan/driver_info_vk.cc` on `master`, the engine already parses and stores the Mali generation, including G72:

```cpp
// line 76
const std::unordered_map<std::string_view, MaliGPU> kMaliVersions = {
    ...
    {"G76", MaliGPU::kG76},
    {"G72", MaliGPU::kG72},
    {"G52", MaliGPU::kG52},
    ...
```

```cpp
// line 300-306
      adreno_gpu_ = GetAdrenoVersion(driver_name_);
      ...
      mali_gpu_ = GetMaliVersion(driver_name_);
      ...
      powervr_gpu_ = GetPowerVRVersion(driver_name_);
```

But `IsKnownBadDriver()` consults `adreno_gpu_` and `powervr_gpu_` and never consults `mali_gpu_`:

```cpp
// line 398
  if (adreno_gpu_ && *adreno_gpu_ <= AdrenoGPU::kAdreno650) {
    return true;
  }
  ...
// line 425
  if (powervr_gpu_.has_value() && powervr_gpu_.value() < PowerVRGPU::kCXT) {
    return true;
  }
  return false;
```

The only other reference to `mali_gpu_` in the file is the getter at line 432 (`return mali_gpu_;`). So `MaliGPU` is tracked but is not, today, an input to the Vulkan fallback decision, while Adreno, PowerVR, Huawei and Samsung Xclipse all are. A 2018 Bifrost part like G72 MP3 on a low-end MediaTek board is the kind of driver that has needed workarounds elsewhere.
