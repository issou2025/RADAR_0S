## Confirmed state
**Backend: push-token endpoints exist; delivery is not live.** In Postman, Account → "Notifications & push":
- `POST /me/push-tokens` with `{"token": "<fcm token>", "platform": "android"}`;
- `DELETE /me/push-tokens` with `{"token": "<fcm token>"}`.

Both work for any signed-in account (student or teacher). Their response bodies and status codes are **not verified**. The folder note says **"Push delivery starts once FCM is configured."** The admin `POST /admin/notifications` note says **"In-app only until FCM is set."** As documented, **the backend does not send push yet**.

**App: no push setup at all.**
- No `firebase_core` or `firebase_messaging` (or local-notifications) dependency in `pubspec.yaml`.
- No `android/app/google-services.json` and no `ios/Runner/GoogleService-Info.plist`.
- No iOS entitlements file (no `aps-environment`), and no `UIBackgroundModes` / `remote-notification` in `Info.plist`.
- No `POST_NOTIFICATIONS` permission in `AndroidManifest.xml` (needed on Android 13+), and no Gradle Google Services plugin.
- No code calls `/me/push-tokens`.
- App IDs: Android `com.aiacademyasia.aia_mobile`, iOS `com.aiacademyasia.aiaMobile`. They differ, so Firebase must register both.

## Blockers
1. **Backend FCM configuration.** Push delivery is off until FCM is set server-side (Postman notes). Needs: the Firebase project, the backend service account, and confirmation that delivery is live.
2. **Firebase project and app config files.** `google-services.json` and `GoogleService-Info.plist` for the two app IDs above, from the Firebase project owner.
3. **APNs.** An APNs auth key uploaded to Firebase, and the Push Notifications capability on the iOS App ID (Apple Developer account owner).
4. **Protected iOS files.** Enabling push on iOS needs the Push Notifications and Background Modes capabilities. That changes `ios/Runner.xcodeproj/project.pbxproj` and adds a `Runner.entitlements`, and `ios/Runner/AppDelegate.swift` may need delegate setup. These files are protected under the repository rules, so a human must make or approve these changes.
5. **New dependencies.** `firebase_core` and `firebase_messaging` (and likely `flutter_local_notifications` for foreground display). The rules require an explicit task approving dependencies.
6. **Payload contract (`BACKEND GAP`).** Which `notification`/`data` keys a push carries (for example the in-app notification `id`, `kind`, `data.assignment_id`) is undocumented. Without it, tap navigation can't be built.

## Backend dependencies (questions)

- [ ] The push payload schema (`data` keys), and whether each push matches an in-app notification `id`.

## Proposed app work (after the blockers clear)
1. Add the Firebase setup (deps, config files, Gradle plugin, iOS capabilities: human-approved for the protected files).
2. **Permission:** ask at a defined moment (`PRODUCT DECISION`: when). Android 13+ needs `POST_NOTIFICATIONS`, and iOS needs the authorization prompt. Handle denial gracefully; in-app notifications still work.
3. **Token lifecycle, per account** (matching the per-account isolation of #286):
   - register after sign-in (`POST /me/push-tokens`);
   - re-register on `onTokenRefresh`;
   - remove on sign-out **before** the session is cleared (`DELETE /me/push-tokens`), so the next account on the device never receives the previous one's pushes.
4. **App states:**
   - **foreground:** show an in-app banner or local notification, and refresh `NotificationCenter` (unread badge);
   - **background or terminated:** the OS shows the notification;
   - **on tap** (`onMessageOpenedApp` / `getInitialMessage`): open the Notification Center or detail. Deeper targets wait on the payload contract.
5. **Release configuration:** APNs production vs sandbox, Android release signing, and Play / App Store declarations.

## Acceptance criteria
- [ ] A signed-in student and teacher, on a **real** Android and iOS device, receive a push for a backend-sent notification with the app in foreground, background and terminated states.
- [ ] Tapping a push opens the matching in-app notification (or the Notification Center if no target is defined), including from a terminated launch.
- [ ] Denying permission leaves the app fully working, and in-app notifications still appear.
- [ ] After sign-out, the previous account's device token is removed: no push for account A after account B signs in.
- [ ] Token refresh re-registers. Release builds are verified on real devices; simulators don't count.
- [ ] Protected iOS files change only with explicit human approval, in a reviewable commit.
