# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Track which platform features each host plugin supports, and why each gap exists**

*Project description:*
## The problem

There is no one place that says, for each platform feature a bundle can carry, what each host plugin does with it. Unreal and Revit have diverged, and they diverge for three different reasons that today look identical from the outside:

1. **Lag** — one host simply has not built it yet (Unreal lands tree points as a data table and places no foliage; Revit places them as Planting families).
2. **The host does it differently, on purpose** — the same feature becomes a different host construct (a painted landscape layer in Unreal, a toposolid subdivision in Revit), or a different frame (`HPS-54`: Unreal is a fixed-frame host, Revit an order-frame host).
3. **The host declines it, on purpose** — [ADR 0006](https://github.com/mantleplace/mantleplace-dcc/blob/main/docs/adr/0006-unreal-declines-elevation-bounds-target-crs.md) records one such asymmetry as the contract rather than a disagreement. Some features have no sensible home in a host at all (a hazard plan is a Revit sheet idea; a World Partition data layer is an Unreal one).

Planning needs those three told apart. "Revit does X and Unreal doesn't" means very different things depending on which of the three it is, and a future host (`host:rhino`, `host:blender`, `host:max`) will need to start from the same list.

## What exists today, and why it is not this

I searched the repo and the tracker before filing. The pieces exist, but scattered, and none of them is a per-feature, per-host view:

- `tools/manifest-conformance/verified-against.json` — per host, which **manifest version** it is verified against. Version-level, not feature-level.
- The conformance corpus groups ([`spec/conformance.md`](https://github.com/mantleplace/mantleplace-dcc/blob/main/spec/conformance.md)) — what a reader claims to *parse*, not what the host *does* with the result.
- `revit/README.md` and `unreal/README.md` ▸ "What it does today" — accurate, but prose, per host, and not comparable side by side.
- `docs/host-plugin-standard.md` — says what a host *must* do, not what each host *currently* does.
- Per-host ADRs (0006, 0008, 0012–0014) — the reasoning behind individual divergences, with no index across them.
- #147 was a feature plan for Revit alone and is closed; #43, #75, #76, #196, #234, #241 and #255 are each one row of what this tracker would hold.

## What I'm proposing

A single public support matrix: one row per platform feature, one column per host, and a status in every cell drawn from a small fixed vocabulary, something like:

| Status | Meaning |
| --- | --- |
| supported | imported and placed, verified in the host |
| partial | imported, with a named gap (link the issue) |
| planned | not yet; link the issue that will do it |
| declined | will not be done in this host; link the ADR or say why |
| not applicable | the feature has no meaning in this host |

Every cell other than `supported` links the issue or ADR that explains it, so the matrix is an index into the reasoning rather than a second copy of it.

## Open questions for triage

1. **Where does it live?** A tracked file (for example under `docs/`) gets review, history and the docs-integrity gate; a pinned issue or a GitHub Project is easier to edit but unreviewed. A file seems right for a public, normative-adjacent artifact — but it is the maintainer's call.
2. **What is a row?** A manifest layer, a published field, or a user-facing capability (the vault, notices, sign-in, streaming)? `spec/` deliberately never restates a field or an enum, so rows named after schema fields may collide with that doctrine; rows named after capabilities avoid it.
3. **Can any of it be checked?** A structured file (JSON or a Markdown table with a fixed shape) could be cross-checked in CI against `verified-against.json` and the corpus groups each host claims, so a `supported` cell cannot outlive the evidence for it. Worth deciding before the format is chosen.
4. **Who keeps it current?** Per-key ownership, as `verified-against.json` already does — a Revit PR edits the Revit column only — would let the hosts keep moving at their own pace.

## Done when

- The matrix exists in the agreed place, with a row for every feature either host handles today and a status for both hosts on each row.
- Every non-`supported` cell links an issue or an ADR.
- Root `CLAUDE.md` ▸ "Where knowledge lives" points to it, so it is found before a fact is written somewhere else.
