# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**RFC: Android and iOS apps — a remote-control client (PWA push first, then a Capacitor shell)**

*Project description:*
## Summary

Owner question: how should we build Android and iOS apps? Recommendation: keep the phone a **remote-control client** for a kernel that stays on the desktop or in the cloud. Make the phone page a solid installable PWA with Web Push first, then ship a **Capacitor shell** that bundles the same `desktop/frontend-next` build to both stores. Do not put the kernel on the phone and do not rewrite the UI natively.

Facts below are from `origin/studio` and vendor documents read 2026-10-10/11. Anything marked *unverified* is inference or second-hand.

## What exists today

- **LAN phone page**: `DeviceShare` opens a second listener on a private address (Tailscale's CGNAT range is recognised). A one-time pairing code (5 min, digest only) is traded at `/pair` for an HttpOnly, SameSite=Strict cookie (30 days). `NewDeviceGate` checks Host and Origin (anti-rebinding); a paired device gets no window-only routes (`device.host_only`).
- **Persistence**: #12440 keeps paired phones across restarts (`remember_paired_devices`, default off, digests only).
- **Cloud relay**: `internal/platform/remotecloud` keeps a signed-in Studio reachable via `wss://remote.reasonix.io`; X25519 session keys between controller and Studio, the relay sees routing identities, capability scopes and ciphertext only. The web entry is `reasonix.io/remote/?device=...`.
- **UI**: the same frontend-next runs on phones (LAYOUT.md "Phones": 680px fold, drawer-as-route, `dvh`, hover-free controls).
- **PWA**: #12591 (open) adds manifest and icons, deliberately no service worker. The second half of #12515 (reopen the last host without scanning) waits on the device-enrollment design in #11878.
- **Missing**: push or any background delivery; reopening a paired host from the home-screen icon; a stable device identity (cloud controllers are numbered per connection); offline shell; in-app QR scanning; store packages. The original ask (#4294) wanted progress, send, approve, diff, and notifications.

## Connection architecture

- **LAN direct** (exists): fine at home; plain HTTP, gone when you leave.
- **Tailscale/WireGuard** (works today): strong, but asks users to install it; a poor fit for most of our users.
- **Own relay** (exists): the main path off-LAN. Keep it as the only Internet path.
- **WebRTC**: still needs TURN for symmetric NAT; more moving parts than the relay. Not now.
- **Cloudflare Tunnel to serve**: gives plaintext to a third party, inconsistent with the relay model. Not recommended.

Threats: a lost phone (add biometric lock, Keychain/Keystore, per-device revocation); phishing of the pairing QR (an in-app scanner should show the host name before trusting); relay visibility (code says ciphertext only; we did not audit it); push payloads transit APNs/FCM, so they must carry no commands, paths or code.

## Distribution

- Apple Developer Program: USD 99/year; organisations need a D-U-N-S number ([Apple](https://developer.apple.com/support/enrollment/)). Review time and TestFlight limits: *unverified*.
- Google Play: personal accounts created after 2023-11-13 need a closed test with 12 testers opted in for 14 days before production ([Google](https://support.google.com/googleplay/android-developer/answer/14151465)). Start early; it is calendar time.
- Mainland China: iOS needs an ICP filing number for new apps since 2023-09-29 (second-hand: https://appleinsider.com/articles/23/10/03/apple-bows-to-china-starts-enforcing-app-store-rules; *unverified* against Apple). The Interim Measures on Generative AI Services took effect 2023-08-15 with filing duties for providers; whether a bring-your-own-key client is a "provider" has no official answer we found: *unverified*. Domestic Android market requirements: *unverified*. A PWA and direct download avoid store filing entirely.

## Recommendation

Route A now, then B; no C/D/E/F. Bundle the web build in the shell (no remote-loaded pages) so review sees an app with native features, and so cleartext LAN pages are not the app itself.

## Phases

Day counts are estimates for one full-time person.

0. **Finish what is in flight (3-5 days)**: land #12591 and #12440; implement #11878 enrolment so the home-screen icon reopens the last host. *Accept*: kill the PWA, tap the icon, no re-scan; revocation takes effect at once. *Not*: a caching service worker.
1. **PWA push (8-12 days)**: service worker for push and notification clicks only; VAPID subscriptions stored in the device registry and dropped on revoke; send on "approval needed" and "turn finished" with a minimal payload. *Accept*: a locked phone shows the approval within about 10 s and the tap lands on it; payload has no command or path. *Not*: offline editing, background sockets.
2. **Capacitor shell (12-20 days plus store calendar time)**: bundled frontend-next, configurable host address, native push, secure credential storage, in-app QR scan with host confirmation, biometric unlock; TestFlight and a 12-tester Play closed test. *Accept*: pair, send, approve, receive push on both platforms; one iOS review passed. *Not*: kernel on phone, native UI rewrite, code editing or a terminal on the phone.
3. **Only if data supports it**: offline session cache, China Android markets, organisation accounts.

## Open questions (no mature precedent or majority practice)

1. **Who sends push?** Everyone compared has a vendor server. We have none for this. Should the cloud relay or the platform worker send APNs/FCM/Web Push (holding device tokens), and are LAN-only users simply without push?
2. **Legal entity and regions**: individual or organisation Apple account, and do we list on the China storefront at all, given the ICP requirement (unverified) and the Chinese-speaking majority?
3. **Generative-AI filing**: does a bring-your-own-key client count as a provider under the Chinese rules? This needs legal advice, not engineering.
4. **Shell loading policy**: bundled frontend (needs a frontend-kernel version-compatibility window) or loading the host's page (review and cleartext-HTTP problems). We lean bundled.

## Update 2026-10-11: native-first, performance-first, on-device

### Summary
Under the new constraints (performance first, native UI preferred, on-device interpreted two ways) we revise round one: the phone client should be a **native remote client** (Compose on Android, SwiftUI on iOS; KMP is an alternative), not a Capacitor shell. The PWA stays only as the stopgap already in flight (#12591). An **on-device kernel mode** is feasible only as a restricted subset (no bash, no stdio MCP, no LSP; iOS foreground only). **Operating the phone itself** (computer-use style) is blocked on both stores. All dates are retrieval dates, 2026-10-10. "Unverified" means no first-party source was read. Day counts are estimates.

### What changed in the constraints
Round one optimised for one-person sustainability and reuse of frontend-next, which favoured PWA then Capacitor. Now performance and native feel outrank reuse. Round one's other findings (phone as remote, kernel not the main thing on the phone) were re-checked and hold.

### Performance findings
- No first-party measurement exists for streamed markdown, long transcripts, highlighting and diffs in WebView vs native. "Native is faster" is inference. A 3-day spike (mid-range Android, 2000 messages, 50k streamed tokens, 1000-line diff) would settle it for our app (estimate).
- WKWebView runs content in a separate process that the system can terminate under memory pressure, leaving a blank view that must be reloaded ([Apple forums](https://developer.apple.com/forums/thread/119550), search summary, secondary). Chrome reports 48% fewer janky scrolls on Android 2023-2026 ([Google blog](https://blog.google/chromium/smoother-scrolling-how-we-halved-scroll-jank-in-chrome-on-android/)), so old "WebView lists are slow" forum posts are not evidence.
- frontend-next ships react, react-markdown, rehype-highlight and the full CodeMirror 6 set (package.json, origin/studio); a native read-only diff/code view needs none of it.
- Peers: OpenAI's ChatGPT Android role requires Kotlin and Jetpack Compose, "deeply native" ([OpenAI careers](https://openai.com/careers/android-engineer-chatgpt-library-team-seattle/)); Anthropic's Claude Android role is native (search summary, secondary). Happy uses Expo. Codex and Cursor mobile stacks: unverified. Compose Multiplatform for iOS is stable since 1.8.0, 2025-05 ([JetBrains](https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/)).
- Go kernel as a library: gomobile builds AAR/xcframework ([Go wiki](https://go.dev/wiki/Mobile)); artifact size is a known open issue ([golang/go#40348](https://golang.org/issue/40348)). Android 15+ updates need 16 KB page support since 2025-11-01 ([Android docs](https://developer.android.com/16kb-page-size)). Tailscale ships Go inside native iOS shells but had to cut memory to fit a 15 MB extension limit ([Tailscale](https://tailscale.com/blog/go-linker)). Our kernel's real size, startup and memory are unmeasured; it uses cgo tree-sitter and modernc sqlite (go.mod).

### On-device feasibility matrix
| Tool | Android | iOS |
|---|---|---|
| bash / arbitrary commands | Restricted: no execve from app-writable dirs for targetSdk 29+ ([Android 10 changes](https://developer.android.com/about/versions/10/behavior-changes-10)); the system-linker workaround is called a Play-policy violation by Termux's own maintainer ([termux#4000](https://github.com/termux/termux-app/discussions/4000)) | Not feasible: no fork/exec ([golang/go#58323](https://golang.org/issue/58323)); guideline 2.5.2 ([Apple](https://developer.apple.com/app-store/review/guidelines/)) |
| files | Feasible in app dir; user folders via SAF (unverified) | Feasible in container; outside via document picker/bookmarks (unverified) |
| git / grep / glob / edit | Feasible, pure Go; little value without a repo | Same ([Working Copy](https://apps.apple.com/app/id896694807) is the precedent for git) |
| LSP, MCP stdio | Restricted (subprocess) | Not feasible |
| MCP HTTP, web fetch, in-app browser | Feasible | Feasible (guideline 4.7.2: no native API exposure) |
| Sandbox (Seatbelt/bwrap) | No equivalent; app sandbox only | Same |
| Background | Foreground service with declared type; dataSync not startable from boot on Android 15 ([docs](https://developer.android.com/develop/background-work/services/fgs/service-types)) | About 30 s after backgrounding; minutes only for BGProcessing on charger (secondary) |

Subset that works: cloud-model chat plus file read/write/search/edit in an app or imported folder, MCP over HTTP, browsing. This is a notes/research agent, not a coding agent. No store precedent exists for an arbitrary-command agent on a phone; a-Shell uses WASM/prebuilt commands ([App Store](https://apps.apple.com/app/id1473805438)), Termux's Play build is unofficial.

### Operating the phone itself
- Play policy: autonomous use of the Accessibility API is "strictly prohibited"; only verified accessibility tools may; deterministic rule scripts are allowed ([Play policy](https://support.google.com/googleplay/android-developer/answer/10964491)). Effective date as quoted by search summaries: 2026-01-28; confirm on the page.
- Google's own path: Gemini screen automation, Android 16 QPR3 permission ([9to5google, 2026-01-15](https://9to5google.com/2026/01/15/android-16-qpr3-screen-automation/), secondary). AppFunctions (Android 16+, apps as on-device MCP servers) is a private preview with a limited caller set ([Android docs](https://developer.android.com/ai/appfunctions)).
- iOS: App Intents expose our actions to Siri/Shortcuts; MCP traces in iOS 26.1 beta ([9to5mac](https://9to5mac.com/2025/09/22/macos-tahoe-26-1-beta-1-mcp-integration/), secondary); no API lets a third party drive other apps' UI. Chinese vendor phone agents' store policy: unverified.
- Research prototypes (AppAgent, Mobile-Agent) use ADB/vision ([arXiv 2401.16158](https://arxiv.org/abs/2401.16158)).

### Architecture: one native UI, two modes
- Mode = an `Endpoint{url, auth}`. Remote: LAN or the E2E cloud relay. Local: gomobile-embedded kernel served over loopback HTTP/SSE with a per-launch token and Host/Origin checks (as device_gate does). Same client code, same wire events. In-process calls would need a second transport and an extra frontend-parity edge; not recommended unless loopback is measured to be a bottleneck.
- Capabilities, not UI branches: the kernel declares its tool set at start; the UI hides what is absent.
- Wire models: TS types are hand-mirrored and gated by `wire-parity` (tools/repolint/wireparity.go); no schema exists. We need a Go-driven generator for a Kotlin/Swift subset (about 15-25 types, estimate) plus a new lint gate. 6-10 days (estimate).
- REASONIX.md: behaviour stays in the controller; each mobile frontend needs a declared port subset in frontendparity.go (a deliberate, recorded exception); local mode must not claim sandbox protection.

### Options compared
| | Round 1: PWA, then Capacitor | Native remote client | Native + local kernel |
|---|---|---|---|
| Performance | WebView limits, JS payload | Native lists/text | Same, plus Go runtime memory |
| Effort (est.) | 12-20 d shell | 56-90 d two apps + 6-10 d contract | +20-35 d |
| Reuse | about 95% of UI | protocol only | kernel reused |
| Review risk | 4.2 "repackaged website" | Low | Medium (exec/FGS rules) |
| Maintenance | One UI | Three UIs | Three UIs + AAR/xcframework builds |

### Recommendation
Native remote client first (Android first), Capacitor dropped, PWA kept as stopgap. Local mode as a later restricted subset, Android first. Phone-control not shipped on stores. It differs from round one only on the UI technology, because the objective changed from reuse to performance; the "phone is a remote" conclusion is unchanged because store rules did not change.
