*Project description:*
## Objective

Implement the project-approved factory-learning follow-up from the CI-control adversarial findings in the #23 workstream and its continuing learning rounds:

1. Mechanically reject forbidden raw control bytes in tracked files before the semantic review stage.
2. Require every new or changed guard/checker to ship a known-bad-input table and executable assertions that each bad input is rejected by the intended behavior.
3. Keep adversarial review focused on semantic bypasses and unenumerated paths after lint and negative-input evidence have been verified.
4. For every adversarial blocking finding, explain whether the class can be prevented mechanically; if it can, land the appropriate lint/rule/negative-test template or record a concrete follow-up Issue. If it cannot, explain why.

These are factory/evidence controls, not new game features, canonical Tasks or graph edges.

## Scope

### A. Raw-control-byte lint for tracked files

- Extend the existing bounded public-hygiene checker (`scripts/check_public_hygiene.py`) rather than building a parallel security framework.
- Enumerate actual tracked/index files safely with Git. Apply the deterministic content check to C0 bytes `0x00..0x1F` except TAB (`0x09`), LF (`0x0A`) and CR (`0x0D`), and to DEL (`0x7F`). This includes U+0008, but is not limited to it. Check the actual bytes before UTF-8/text normalization so that control bytes cannot disappear through decoding or line splitting.
- Do not add exemptions based on file extension or readability. Preserve the existing privacy-first behavior: protected private inputs must still be rejected without reading or echoing their contents. Existing artifact rules remain intact. The raw-byte diagnostics must give a safe filename/line-or-byte locator and an escaped byte value; never echo offending file contents or secret-shaped values. Keep existing public-hygiene heuristics and their documented boundaries.
- Ensure this lint executes in the controls workflow on **every pull request and every push to main**, not only when one of the previous four control paths changes. Retain `workflow_dispatch`, immutable action pins, read-only permissions and bounded jobs. The fast controls job should not become an unbounded main-build replacement.
- Retain the existing Rust workflow's real guards and all existing checks; do not remove the Plan validation commands or other process checks.

### B. Required negative-input evidence

- Add a clearly accessible known-bad-input table (or equivalent indexed/parameterized case collection) with executable rejection checks for every guard/checker implemented or changed. Each case must reach the real guard/test harness as appropriate and assert rejection, including the relevant semantic class or property where an unrelated nonzero/error would not prove that the intended guard fired. A dead table or an assertion over the existence of table entries alone is not evidence.
- This requirement applies to guards such as CI validators, schema/Amount parsing, command legality, persistence validation and resource gates. Existing valid cases may be reused rather than duplicated. A missing or non-executable table for an applicable guard is a blocking first-review finding.
- Keep semantic review distinct from the purely mechanical lint gate. Once the linter and negative-input tests have verified known input shapes, adversarial review focuses on semantic bypasses, unlisted forms, execution path defects and false acceptance rather than rerunning known cases as if they were new audit evidence.
- Convert the currently accepted direct and ordinary-command-prefix canary-output regressions into the project's explicit reusable negative-test table/template, while preserving their exact process-output meaning and valid comment/document-only cases. Do not replace narrow guards with a universal shell parser or general eval security claim.
- Update `AGENTS.md` with the short author/reviewer obligations and `requirements/testing.md` with the evidence and automation-learning contract. Note the approved raw-byte definition and executable-negative-input rules without duplicating canonical gameplay or renaming Tasks.

### C. Recurring learning loop

- An adversarial blocking finding includes: category, real reproduction, applicable acceptance/invariant, and its automation candidate: lint/rule, executable negative-input case/template, or another concrete known-bad-input guard. Give the target file/test route and whether it lands in the current Issue or a separately linked follow-up.
- Every such finding must be acted upon for the class, not just patched once. If automatic interception is not feasible, record the reason and the remaining review obligation; do not invent a false save/checkmark.
- Actual FAIL reports and subsequent fixes remain part of the evidence record. Reports are not replaced by happy-path CI, clean source trees, self-assertions, or stale-head reviews.

### D. Persistent regression fixtures and review scaffolding

Reuse the *mechanically learned* attack cases across rounds without turning fresh adversarial review into a re-run or a transcript replay.

- **Fixture library:** Establish `fixtures/ci-controls/` (or the equivalent clearly named repository fixture directory) with a small catalog/manifest, safe fixture inputs, and a one-line provenance per case (for example `R1` for the literal-word-boundary/control-byte failures, `R2` for ordinary command-prefixed echo/printf canary output, and `R3` for ordinary command option/end-of-options spellings). Include the verified `command -- echo` and `command -p printf` cases from R3 as well as the confirmed R1/R2 cases. Add R4 provenance for backslash-newline continuation that turns a benign-looking test comparison into echo output; retain the exact two-line static fixture, require continuation-aware code/data role evaluation (or a deliberately bounded safety refusal), and preserve actual non-output safe forms. Add R5 provenance for ordinary adjacent-shell-word reconstruction recognized by shlex but missed by raw-substring filtering. Preserve its reconstructed-token negative cases for adjacent-quoted printf and command echo plus the legitimate reconstructed bare-call and non-output comparison controls. Add R6 provenance for attached-# inside ordinary unquoted shell words: Python shlex incorrectly starts a comment where Bash keeps emitting. Preserve the test-comparison and bare-capture attached-# emit cases through the real CLI. Also preserve true whitespace-started comments, quoted hash and non-emission data controls. Mechanical guards and safe positive forms govern all of them. Give each case a stable fixture ID, target checker/guard, input/injection kind and expected rejection class. These are test-fixture IDs, not canonical feature IDs.
- Preserve the concrete attacks from the two FAILs as durable regressions. Full safe document snippets/TEMPLATES may be committed and applied to the current healthy workflow, rather than trusting stale opaque copies. Every fixture must be machine-consumed by the appropriate self-test or fixture runner on every PR/main controls run, with expected-versus-actual evidence. No dead, documentation-only case table.
- For literal U+0008 / other forbidden raw-byte cases affecting the three earlier guard paths, construct the mutated checker/input in an isolated temporary directory from escaped numeric byte values, and run both the intended rejection path and the semantic regression path as applicable. Do NOT place forbidden raw bytes into a tracked file, in a YAML/document string, code comment, report, or other public fixture. Bad control-byte fixtures are generated, never committed.
- If a full document fixture contains invoked-looking shell text, it is data for a static checker only; never run the mutated workflow shell. Project guard cases still need separate real benign process behavior evidence rather than substituting a mutated fixture for normal runtime safety.
- When later adversarial FAILs produce a new confirmed class, add the corresponding fixture/table entry in the fixing PR or the explicitly linked follow-up and give its round/provenance. Non-reusable human judgment questions must give a reason; do not force every semantic bug into an unrelated hardcoded guarantee.

Reusable review scaffolding (`scripts/`):

- Provide a reviewed project CLI (suggested `scripts/review_fixture_harness.py`, with normal conventional Python-invocation usage; no unrelated framework) for **detached exact-worktree preparation**, private evidence-directory creation, fixture-running, bounded stdout/stderr/log capture, SHA256 recording, exit-status/timing records and a basic evidence manifest.
- Worktree setup must accept and validate an exact candidate commit (and expected tree when supplied), never overwrite or reset someone else's working tree, use a detached review worktree by default, and never delete a branch or force-update refs. It may prepare new evidence/worktree paths under a caller-selected private task directory. It must not accidentally read `.env`, credentials, cookies or private source captures. Prefer small typed operations over a generic arbitrary-command shell runner. The target CLI for the checked fixtures must be a real project invocation, not a synthetic return value.
- Capture the real project command argv, actual exit code, duration and safe output separately. Provide hash and source/artifact provenance metadata without copying private absolute paths into public repository material. The script's own setup/schema/guard behaviors also need their applicable negative test cases; it does not get an exemption from this policy.
- CI must actually execute the persistent regression library automatically, rather than merely creating reusable directories during interactive reviews. A new reviewer can reuse the same scaffolding instead of reimplementing logging, hashing and document synthesis, but this helper must not perform peer approval or merge a PR.

Report and evidence contract in `requirements/testing.md`:

1. Exact candidate HEAD/tree/base and live-PR identity, clean/review-workspace provenance, independent fresh status and real current model selection in the private report.
2. Actual commands/checker log paths and hashes, real CI run/job IDs/head SHA/event/step results; distinguish PR merge-checkout CI from post-merge MAIN CI. Report measured case counts and times, not an assumed maximum step number.
3. A summary of known-regression fixture execution versus genuinely new probing. Previously stored cases are useful as the mechanical gate, not as evidence of new independent reasoning.
4. Each blocker includes category, concrete reproduction, invariant/criterion and automation_followup (lint/rule, negative test/template, target/test owner and placement in this fix or a linked Issue), or a specific explanation why it cannot be automated.
5. Report nonblocking and bounded deferrals, and an exact-HEAD verdict without converting a missing local report into approval.

Freshness convention for future adversarial rounds (this does NOT change the active R3 mandate):

- Fresh reviewers receive the candidate, current contract/invariants and negative-input mandate, plus the reusable fixture library and its real passing evidence. They DO NOT receive earlier reviewers' narrative analysis, speculative hypotheses or complete finding walkthroughs merely to direct their next attack. Existing source/test code and known input catalogs remain shared controls, not substitutes for fresh reasoning.
- New semantics and unenumerated-path testing must be conceived and performed by the fresh reviewer. The reusable layer removes boilerplate and already-covered mechanical regressions; it does not remove the need for independent adversarial thought or reduce an all-green existing fixture run to a current-HEAD semantic PASS.
