# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**context filter: silently drops distinct values, over-compresses digests, and can fail the wrapped command**

*Project description:*
## Symptom

The Bash context filter degraded an agent's view of its own tool output three distinct ways in one session (2026-09-11, the standing chief session, ~12:45–19:15). Each is separately reproducible-looking, and each is a *silent* degradation — the agent has no way to know from the result that it is reading less than the command produced.

### 1. It can kill the command outright (exit 124)

```
Background command "...context_filter_cli.py run --tool Bash --mode rewrite --encoded ..."
failed with exit code 124
```

The wrapped command was trivial (a 6-line `python -c` reading a small JSON file, chained to a shell script). The filter CLI timed out and the **whole Bash call failed**, so the work simply did not happen. In this case the casualty was a re-armed monitoring poll — the chief lost a 10-minute tick and only noticed because it re-armed a second one defensively.

### 2. It can compress a result down to nothing useful

```
[fleet-context-filter: raw_tokens=482 compressed_tokens=40 reduction=91.7%]
job Claude Code Insights: failed
  job Cleanup Fleet (all buckets): failed
  ...
```

That was a monitoring digest whose *point* was the lines it dropped — live session ids and states, the worktree list, open PR numbers. What survived was the five least informative lines (static job statuses, unchanged for hours). Read at face value, it says "nothing is happening" about a tick in which several lanes had in fact progressed. The agent caught this only by re-reading the raw file with the Read tool and comparing.

### 3. It collapses adjacent similar lines, losing data

A worktree listing rendered as:

```
[x2]      1	/e/automation/app-launcher-wt-885
```

Two distinct paths — `app-launcher-wt-885` and `local-llm-hub-wt-561` — were collapsed into one line with an `[x2]` marker. **A count is not a substitute for the values when the values are the payload.** This survived even after the command was changed to `ls -d ... | cat -n` specifically to make the lines distinguishable; only reformatting to a single space-joined line stopped it.

## Why this is worse than ordinary lossiness

The filter's failure mode is **indistinguishable from a true negative**. An agent reading case 2 concludes "no change this tick"; reading case 3 concludes "one worktree exists"; in case 1 the command's absence is the only evidence. None of those look like errors. This is the same shape as the fleet rule the hooks themselves are held to — *a check that cannot establish a fact must report that as its own state, never fold it into the passing one* — and three separate bugs fixed elsewhere in the fleet today (`local-llm-hub` #576/#577, `app-launcher` #902's motivating case) were instances of exactly that pattern.

It is sharpest for **monitoring and orchestration output**, where near-identical lines across ticks are the normal shape and small differences between them are the entire signal.

## Proposed approach

Not prescribing the fix. Directions worth weighing:

- **Fail open, loudly.** A filter that times out should let the unfiltered output through with a visible note, never fail the wrapped command. A timeout is the filter's problem; the command already ran.
- **Cap the reduction, or refuse to summarise below a floor.** A 91.7% reduction that leaves 40 tokens is not compression, it is replacement. If the filter cannot summarise faithfully, returning the raw output truncated at a byte limit is strictly more honest.
- **Never collapse distinct values.** Dedupe identical lines if useful, but `[xN]` over lines that differ discards the payload. At minimum, collapsing should be off when the differing part is a path, an id, or a number.
- **Make the degradation legible in the result**, so an agent can tell "this was filtered heavily" from "there was nothing there" without re-reading the file.

## Acceptance criteria

- [ ] A filter timeout never fails the wrapped Bash command; the command's own exit code is what propagates.
- [ ] Lines that differ are never merged into a single `[xN]` line.
- [ ] There is a floor below which the filter returns raw (or byte-truncated) output instead of a summary.
- [ ] The result makes heavy filtering distinguishable from an empty result.
- [ ] `E:/automation/fleet-config/.venv/Scripts/python.exe tests/run_acceptance.py` green, with coverage for the timeout path and the collapse path, proven to fail against pre-fix code.

## Workaround in the meantime

Read background-task output files with the Read tool rather than `cat` through Bash — Read is not filtered. The chief session switched to this mid-session after case 2 and it is the only reason cases 2 and 3 were caught at all.
