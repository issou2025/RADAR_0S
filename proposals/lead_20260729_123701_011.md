# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat(auth): optional TOTP second factor — per-browser tokens that expire and refresh every X days (Google Authenticator compatible)**

*Project description:*
Today a broker is guarded by exactly one static shared secret (#142: *"a token is required on every surface, on every interface, always"*). Whoever holds it has a shell on the machine — no second step, no expiry, no way to notice it leaked, and no way to cut off one browser without rotating the secret for all of them.

Add an **optional core component**, off unless enabled: with it on, a browser trades the shared token plus a 6-digit TOTP code for its **own** token, which expires after a configurable number of days. When it expires that browser — and only that browser — is challenged again. RFC 6238 defaults (HMAC-SHA1, 30 s step, 6 digits) so Google Authenticator, Authy, 1Password and friends all work unmodified.

Two properties are the point, and they drive the whole design:

1. **Time-boxed access.** A leaked credential dies on its own within `totp_days` instead of living until someone notices.
2. **Per-browser, independently.** The laptop, the phone and the desktop each hold a separate token with a separate expiry, minted at different times and refreshed at different times. Revoking one does not touch the others.

## Vocabulary (there is a collision to avoid)

`auth.py` currently calls `auth_token` *"the live browser token"*. That name is about to be wrong. In this issue:

- **shared token** — today's `app.ctx.auth_token`. Unchanged, still minted into `webterm_token.json`, still what you type into the auth overlay.
- **browser token** — new, per-browser, expiring, minted only after a TOTP challenge.

Rename the docstring while implementing, or the next reader will conflate them.

## Not a mod — a core component, shaped like `/mcp/config`

Mods are page-realm and load *after* the page is authenticated (`86_js_mod_loader.js`, booted by `90_js_mod_boot.js`), so a gate a mod enforces is a gate an attacker skips by not being the mod. This belongs in `auth.py` + `app.py`.

The MCP surface is the precedent to copy verbatim — it is already an optional core component with an `enabled` flag, its own token realm, its own sidecar and a Control Panel section:

- `app.ctx.totp_cfg` / `app.ctx.totp_state_path` / `app.ctx.totp_lock`, mirroring `mcp_cfg` / `mcp_state_path` / `mcp_lock`.
- `GET`/`POST /auth/totp/config` mirroring `_mcp_config_get` / `_mcp_config_post` (`app.py:4607`): validate everything **before** the lock/write so a bad field changes nothing, persist an **explicit** schema rather than the whole dict, and run the write inside `_shielded_region(app.ctx.totp_lock, …)` + `_write_state_atomic` so a cancelled request can never leave disk ahead of memory. That last one is #160's lesson and it matters more here than it did for MCP: disk ahead of memory on an auth config means a restart adopts a policy nobody chose.
- The public config projection never includes the secret — the same way `_mcp_cfg_public` hand-picks its fields.

UI lands in the **host** pane of the Control Panel (`#set-pane-host`, `40_body.html:51`, wired in `79_js_settings_modal.js`) next to the existing MCP block, not the browser pane: this is per-broker server config, and the host pane is already per-host, so the same UI administers a remote broker's second factor from its own tab exactly as #157 did for mods.

## Config

| key | default | meaning |
| --- | --- | --- |
| `enabled` | `false` | the whole component. Off ⇒ behaviour is byte-identical to today |
| `totp_days` | `30` | lifetime of a browser token, in days |
| `max_browsers` | `32` | cap on remembered browsers (LRU-evicted), so the sidecar cannot grow forever |

**Absolute expiry from the last successful challenge**, not sliding-on-activity. "Required every X days" is what was asked for, and a sliding window means a browser left open in a tab never re-authenticates — which is precisely the browser most likely to be the unattended one.

## Server state

Sidecar `webterm_totp.json`, beside `webterm_token.json`, `0o600`, written through `_write_state_atomic`:

```
{ "enabled": true, "totp_days": 30, "secret": "<base32>",
  "recovery": ["<sha256>", …],
  "browsers": [ {"id", "hash", "created", "expires", "last_seen", "label"} ] }
```

- **Not** `webterm_state.json` — `/state` is readable by any token holder (`_gated_auth_error(request, "/state")`), which would hand the seed to the exact holder the factor exists to challenge.
- **Not** `/mod-store` — it keeps a 50-deep revision ring (`MODSTORE_MAX_REVISIONS`), so a rotated secret would linger in history until someone remembered `purgeRevisions`.
- Store the **hash** of each browser token, never the token. The sidecar already holds the shared token so the marginal gain is small, but it costs one `hashlib` call and it means a backup of the state dir does not carry live sessions.
- **Sessions must survive a restart.** They are on disk for that reason: a broker restart that silently logged every browser out would train the operator to expect spurious challenges, which is exactly how a real phishing prompt gets clicked through. Windows has no POSIX mode — the state dir's own ACL is the actual control (`docs/SETUP.md`).

## Wire

- `POST /auth/totp` — `{code, label?}`, gated by the **shared** token. On success mints a browser token, records it, returns `{token, expires, id}`. On failure counts toward the lockout.
- `POST /auth/totp/refresh` — same challenge, on an expired-or-expiring browser token, replacing that one record. The browser keeps its identity and its place in the list.
- `POST /auth/totp/enroll` — mints a 20-byte base32 secret and returns `otpauth://totp/Browserland:<broker_id>?secret=…&issuer=Browserland`. **Commit only after the operator echoes back one valid code**, or a half-finished enrollment locks the broker with a secret nobody holds. The enrolling browser is granted its browser token in the same response — it just proved possession, and making it re-challenge immediately is the kind of papercut that gets a feature disabled.
- `DELETE /auth/totp/browsers/<id>` — revoke one. Plus revoke-all-others. This is the feature that a shared static token structurally cannot offer, so it should be visible in the UI, not just an API.
- `GET /info` grows `totp: true|false` (and nothing else — no secret, no browser list).

**`/info` must stay satisfied by the shared token alone.** It carries no session-derived data and the client needs it to *discover* that a broker wants a second factor. It also has to be `/info` rather than a new route: that handler already documents why, from #157 — a new path is invisible to an older peer, whose preflight 404s and surfaces as an opaque network error indistinguishable from "that machine is asleep."

## What the shared token still buys once this is on

Decide this before writing a line, because getting it wrong makes the whole feature theatre. If the shared token keeps satisfying browser-realm routes, an attacker who has it simply never asks for a challenge. But headless clients genuinely cannot answer one: `/browserland` producers, the `/ws` and `/control` sockets, and another broker's browser dialling this one directly.

- **(a) Realm split.** Browser realm requires a browser token; automation moves to a separate `automation_token`, the way `/mcp/*` already has its own (`WEB_TERMINAL_MCP_TOKEN`, `auth.resolve_mcp_token`). Strongest, most work, breaks existing headless integrations until re-pointed.
- **(b) Enabled ⇒ shared token is challenge-only.** With `enabled: true` the shared token satisfies only `/info`, `/auth/totp*` and the public `GET /`; everything else — HTTP and sockets — needs a live browser token.
- **(c) Gate only `GET /`.** Worthless; the page is public by design and every route is reachable without it. Named so nobody proposes it in review.

**Recommend (b)**, with (a)'s automation token as a follow-up rather than a prerequisite.

## Client

- `hostFetch` sends `host.token` as `Authorization: Bearer` (`63_js_clipboard_auth.js:566`). The browser token goes in a **separate** field (`host.browserToken`) because the shared token must survive in order to answer the next challenge without re-prompting for the password. Send the browser token when there is one, fall back to the shared token otherwise.
- The challenge reuses the existing auth overlay (`#auth-overlay` / `#auth-token`, `40_body.html:318`, driven from `63_js_clipboard_auth.js:656`) with a second step, rather than a new dialog.
- **`host-registry` must not publish it.** #65's opt-in *Include passwords (tokens)* projects host records into the broker's shared store; a browser token is per-browser and expiring, and copying it to another browser defeats the entire point. Exclude it explicitly and add a test — it will otherwise ride along the day someone adds a field to that projection.
- A 401 carrying `{error: "totp_required"}` is what triggers the challenge, distinct from a plain bad-token 401, so the overlay knows which step to show. `promptFileHostAuth` (`77_js_context_menu.js:352`) force-pops, so a background repaint must never be what raises a re-challenge — the #161 lesson.

## Multiple browsers, concurrently

- Sessions are **not** the single-active-client lease. A passive browser holds a perfectly valid browser token and keeps polling `/state`; being non-active makes it read-only for *writes*, not unauthenticated. Say this in a comment where someone will look for it, because "one active browser" and "one authenticated browser" are easy to conflate.
- Two browsers refreshing at the same moment both write the sidecar. All writes go through `app.ctx.totp_lock` + `_write_state_atomic`; a refresh replaces one record and must not rewrite the whole list from a stale read — that is exactly the silent-clobber shape #158 hit with `putHostState`'s 409 retry re-PUTing a stale blob.
- Same code, two browsers: the replay rule below means the second one is refused. That is correct but confusing at 9 a.m. when two devices are being set up together, so the 401 body should say *"code already used — wait for the next one"* rather than *"invalid code"*.
- Expiry mid-use: enforce at every HTTP request and at socket **connect**. Leave an already-established socket alone; it re-authenticates naturally on its next reconnect, and that avoids inventing socket-expiry plumbing for no security gain. A session-less upgrade closes **4401** through the existing path, never an opaque 1006.

## TOTP details

- `hmac` and `secrets` are already imported in `auth.py`; `hashlib` is stdlib. **No new dependency.**
- Accept ±1 step of drift (`t-1`, `t`, `t+1`) and no more. The server's clock is the reference, so the browser's clock is irrelevant — the one genuine advantage a server-side factor has over a client-side generator.
- **Replay.** A code is valid across the whole window. Record the last accepted step and refuse to accept it twice, or a code read off the screen stays good for another 60 s.
- **Brute force.** Six digits across a ±1-step window is 10⁶ with ~90 s of validity — trivially grindable at HTTP speed. Hard lockout with growing backoff, counted **per broker, not per IP**: `tailscale serve` makes every request arrive from loopback, which is the reasoning #142 used to *delete* `is_loopback_request` rather than merely stop calling it.
- Compare with `hmac.compare_digest`, as `token_matches` already does.

## Multi-host is where this gets expensive

`prefs._hosts` holds one record per broker and the browser talks to each broker **directly** — the registry mod's own description says the broker never proxies. So:

- Adding broker B, and every expiry afterwards, needs a challenge *for B*, raised from A's page.
- Each broker has its own secret, its own enrollment and its own `totp_days`. **There is no SSO here** — document it before someone enrolls once and expects a fleet.
- A browser therefore holds one browser token *per host*, expiring on its own schedule. `host.browserToken` living on the host record gets this for free; a single global slot would not.

## Locking yourself out is the real failure mode

This broker runs live terminal sessions; a lost phone must not cost the machine.

- **Recovery codes** — N single-use codes shown once at enrollment, stored hashed.
- **Local escape hatch** — `--disable-totp` on `python -m webterm.broker`, a sibling of `--print-token` (which already runs without starting a server), plus the documented delete-the-sidecar path. Anyone who can run either already owns the box, so it costs nothing in security and buys everything in recoverability.
- **Never on by default.** Absent `enabled`, behaviour must be byte-identical to today — the auth.py docstring's promise that a fresh install stays one-command usable is not negotiable.

## Acceptance

- Disabled: no new prompt, no new required field, no behaviour change anywhere; `/info` reports `totp: false`.
- Enabled: the shared token alone reaches the challenge and nothing else; token + valid code returns a browser token that unlocks the browser realm; the *same* code is refused the second time with a distinguishable error; a wrong code counts toward a lockout that actually locks.
- Three browsers enroll at different times, hold three tokens with three different expiries, and one expiring or being revoked leaves the other two working.
- A browser token survives a broker restart; revoking it does not.
- After `totp_days`, that browser is challenged and refreshes in place — same list entry, new expiry, no duplicate row.
- Multi-host: A's page completes B's challenge, the token is stored per-host, and `host-registry`'s include-passwords publish does not carry it.
- A recovery code works exactly once; `--disable-totp` restores access with the broker stopped.

## Tests and docs

- New `tests/test_auth_totp.py`: check against **RFC 6238's published test vectors** first — an HMAC that is wrong but self-consistent passes every round-trip test you would otherwise write. Then drift window, replay refusal, lockout/backoff, expiry, refresh-in-place, revocation, the LRU cap, sidecar mode, restart persistence, and the disabled no-op path.
- Multi-browser paths need `ReusableClient`, not `test_client` — the latter drains app state between requests, which is what #108/#109 hit with upload sessions.
- `tests/test_ui_assets.py`: the Control Panel additions are core fragments, so they belong in the existing host-pane assertions — and the new settings keys must stay **out** of the mod settings model, which that suite already polices.
- Docs: `docs/SETUP.md` (enabling, enrollment, escape hatch, the Windows ACL note), `docs/TECHNICAL.md` (the two token kinds, alongside the `?token=` deep-link discussion already there), `wiki/Hosts-and-Multi-Browser.md` (per-broker enrollment, per-host expiry, no SSO), `wiki/Getting-Started.md`. Regenerate the corpus with `python -m webterm.broker.help_corpus` — the drift test is byte-exact.

## Out of scope

- **QR rendering.** Nothing in the repo draws one, `vendor/` is xterm + CodeMirror only, and the page CSP is `script-src 'sha256-…' 'self' https://esm.sh`. Ship manual key entry — which Google Authenticator supports — plus the `otpauth://` URI as copyable text. A vendored pure-JS QR encoder is a follow-up.
- **WebAuthn / passkeys.** The better long-term answer and a different issue; TOTP is the one that works from any phone with no registration ceremony.
- **A client-side authenticator window** — a Browserland app that *generates* codes for your other accounts. Different feature, shares no code with this one, and it could not use `crypto.subtle` at all: the broker is commonly served on plain `http://<LAN-IP>:4445` and SubtleCrypto is secure-context only (see the comment at the top of `63_js_clipboard_auth.js`).
- **Per-user accounts.** There is one operator; a second factor does not change that.
- **`/mcp/*`.** Already its own token realm.
