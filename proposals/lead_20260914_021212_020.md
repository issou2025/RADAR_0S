# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat(cli): comment on a task with task comment add, list, edit and delete across every plugin**

*Project description:*
## What

Add a **comment** capability to the plan store: a comment on a task, readable and writable through
the CLI, implemented for `github-projects` (GitHub issue comments), `local-md` (a trailing section
of the task's Markdown file), `in-memory` and `linear` (Linear issue comments), carried over the
stdio plugin protocol, rendered by `task show`, and exposed by both SDKs. Nothing a copy does
changes: comments are written only through this verb.

This is contract **C1** and **C2** of the plan (the project record states them; they are restated
here in full because this node is their producer). The consumer is the orchestration harness at
`github.com/nickderobertis/ai-orchestrator`, whose follow-up agent drives this verb through the
installed `onetaskgraph` binary after this repository releases it; it reads only the CLI surface
and the `--json` shapes below, never the Rust types.

### C1 — the CLI surface (fixed)

```
onetaskgraph task comment add    <ID> [--body-file PATH] [--author NAME]
onetaskgraph task comment list   <ID>
onetaskgraph task comment edit   <ID> <COMMENT-ID> [--body-file PATH]
onetaskgraph task comment delete <ID> <COMMENT-ID>
```

- `<ID>` is a qualified task id, `<source>:<native-id>`, on the same terms as `task show`.
  `<COMMENT-ID>` is the comment's own id exactly as `list` or `add` reported it.
- The body of `add` and `edit` is read from `--body-file PATH`, or from **stdin** when that flag is
  absent; it is never a command-line word (a body quoting a command must not reach a shell). The
  body is stored and returned **byte-for-byte** (a trailing newline included). An empty body is
  refused.
- `--author NAME` is optional on `add`. A source that records the author itself (GitHub and
  Linear each record the authenticated user) refuses a `--author` rather than dropping it, naming why; `local-md`
  records it.
- Every verb takes the global flags every verb takes (`--output json` / `--json`, `--set`, …).
- Machine output (`--json`), one JSON document per invocation:
  - `add`, `edit` → one **Comment** object.
  - `list` → `{"comments": [Comment, …]}` in creation order, oldest first; an empty list when the
    task has none.
  - `delete` → `{"deleted": "<COMMENT-ID>"}`.
  - **Comment** = `{"id": string, "author": string|null, "created_at": RFC 3339 string|null,
    "updated_at": RFC 3339 string|null, "body": string, "url": string|null}`. `null` means the
    source did not give that field; `id` and `body` are always present.
- `task show <ID>` renders the task's comments after its content in the human rendering, and its
  `--json` output carries `"comments": [Comment, …]` (same order) for a source that has comments.
  For a source declaring none, the human rendering says nothing about comments and the machine
  output omits the key — absent rather than an empty list, because an empty list reads as a
  source that has comments and holds none.
- Failure and recovery follow the repository's existing exit-code table and diagnostic style
  (problem and a next action on stderr): an unknown task id, an unknown comment id, a source that
  cannot hold comments (refused before anything is read, naming the source and its plugin), a
  source with comments but no write side for them, and a `github-projects` item that is a draft
  issue (which GitHub gives no comments) are each refused, never answered with an empty result.
- `task copy`, `project copy` and `document copy` neither read nor write comments, at either end.

### The plugin contract behind it

Comments are a capability a source declares at the handshake, the way `writes` is, and four
`TaskSource` methods defaulted to a refusal so every existing plugin compiles and keeps working
unchanged: list a task's comments, add one, edit one, delete one. Where the new types and the
capability live follows this repository's own rule: a type a trait signature names goes in
`onetaskgraph-plugin-api` (update the inventory in `AGENTS.md` that
`scripts/check-contract-inventory.sh` reconciles), everything else in `onetaskgraph-core`. Naming
the Rust items is yours; the CLI surface and JSON shapes above are not. Add the four methods and the
capability to the stdio plugin protocol and `docs/plugin-protocol.md`, so a subprocess-wrapped
source is proven by the same journeys.

### Per plugin

- **`github-projects`**: a task's comments are its issue's comments — read through the issue, added
  with GitHub's add-comment mutation, edited and deleted through the issue-comment mutations; the
  comment id is GitHub's node id for the comment. Every document you add stays inside the node-count
  bound this plugin already gates offline, and is added to the document inventory that gate reads.
  Prove it against the loopback board `tests/plugin.rs` already drives, with fixtures pinned the way
  every other operation there is pinned.
- **`local-md`**: contract C2 below.
- **`in-memory`**: a full implementation, so the shared journey table covers the capability in the
  same process as every other row.
- **`linear`**: a full implementation. A task's comments are its Linear issue's comments: read
  through the issue's `comments` connection, added with `commentCreate`, edited with
  `commentUpdate` and deleted with `commentDelete`; the comment id is Linear's comment id. Linear
  records the authenticated user as the author, so `--author` is refused there as on GitHub. Extend
  the documentation-derived schema subset `crates/onetaskgraph-linear/tests/fixtures/schema.graphql`
  with exactly the comment types, inputs, payloads and mutations the plugin sends, pinned from
  Linear's published schema the way that file records its other pins. Prove it against the loopback
  server `crates/onetaskgraph-linear/tests/plugin.rs` already drives, with fixtures pinned the way
  every other Linear operation there is pinned. The credentialed live lane is not this node's bar.
  The manager ruled that Linear is implemented, not deferred: no plugin declares comments
  `Unsupported`, so no `docs/follow-ups.md` entry is written for this capability.

### C2 — the `local-md` comments section (fixed)

A task's comments are an **optional trailing section of the task's own file**, after the body,
human-readable, at full fidelity, never JSON:

  ```markdown
  ---
  title: Ship the release
  status: todo
  ---
  Long-form task content.

  ## Comments

  <!-- onetaskgraph:comment id="20260913T151107Z-1" author="ada" created_at="2026-09-13T15:11:07Z" updated_at="2026-09-13T15:11:07Z" -->
  ### ada — 2026-09-13T15:11:07Z

  The body, byte-for-byte: any Markdown, including its own `##` headings.

  <!-- /onetaskgraph:comment -->
  ```

- The section is the heading line `## Comments` followed by one or more comment blocks separated by
  blank lines, and nothing else to the end of the file. A `## Comments` heading anywhere else, or
  one followed by anything that is not a comment block, is ordinary task content. A task with no
  comments has no section at all — deleting the last comment removes the heading.
- A block opens with the marker line `<!-- onetaskgraph:comment ... -->` carrying `id`,
  `created_at`, `updated_at`, and `author` when one was given (attribute values double-quoted, with
  `&`, `"`, `<` and `>` escaped as the four XML entities). A human heading line follows —
  `### <author> — <created_at>`, or `### comment — <created_at>` without an author — then a blank
  line, the body verbatim, a blank line, and the closing line `<!-- /onetaskgraph:comment -->`. The
  marker line is the source of truth; the heading is for a person and is regenerated on every write.
- The body is stored verbatim; a body containing a line that is exactly the closing marker is
  refused on `add` and `edit`, naming why, rather than escaped.
- A comment id is minted as `<created_at in UTC as YYYYMMDDTHHMMSSZ>-<n>`, `n` the smallest positive
  integer not already an id in that file; ids are never renumbered.
- The section is **not** part of the task's `content`: `task show` and every query report content as
  the body above the section, the way `github-projects` takes its metadata slot off the body.
  `search --in content` does not match comment text.
- Writing the task through `write_task` (a copy into `local-md`) **keeps the file's existing
  section byte-for-byte**; nothing a copy does adds, changes or removes a comment.
- `docs/local-md.md` documents the section; `onetaskgraph-local-md/src/lib.rs` is its single
  executable source, and the boundary tests exercise every rule above.

## Why

In the user's words, follow-ups today are "reported upwards from workers" — and nothing a
manager reads ever receives them: the judge's `assessment` list is retained in a report no view
opens, a worker's `proposal` surface is briefed to nobody, and managers have been hand-collecting
`scratch/FOLLOW-UP-*.md` files and dispatching ad-hoc triage runs from them. The user wants "a
more structured system where we have a follow-ups project through onetaskgraph and the agents are
logging things there with local md because they're unverified", then "one follow-up agent that
runs at the end of the entire graph after the DAG is completed to go through all the draft
follow-ups and verify each one and group them by root cause", copying the verified tickets "to a
single follow-ups project in GHP so that multiple sessions will accumulate their follow-ups into
the same project" — commenting on an open issue for the same root cause rather than duplicating
it.

This node is the part of that system that belongs to the plan store. The user decided that comments
go "through a new `onetaskgraph` comment verb, not through `gh` directly", and that on `local-md` "a
comment is a special optional section at the end of the file, human readable, full fidelity". The
follow-up agent needs it for two things only a comment can do: add its session's evidence to an
open issue another session created — without touching that session's content — and, when re-run
with the user's feedback, edit or remove a comment its own session posted. Edit and delete are in
scope because the user ruled that a re-dispatched agent "may delete, create or edit its own content
from the session".

## Acceptance criteria

- `onetaskgraph task comment add|list|edit|delete` exist with exactly the arguments C1 states. The body
  of `add` and `edit` comes from `--body-file` or stdin, is stored and returned unchanged, and an empty
  body is refused. `--author` and every `--json` shape behave as C1 states. `task show` renders comments
  and carries `comments` in its machine output for a source with comments, and omits the key for one
  without.
- For `local-md`, `github-projects`, `in-memory` and `linear`, and for a source served over the stdio
  plugin protocol, a comment added through the CLI is listed with its body unchanged. An edit changes only that
  comment's body and `updated_at`, and a delete removes only that comment. Each is proven by a journey
  that drives the compiled binary as a subprocess against that source kind through the shared fixture
  table, and each is also proven at the plugin boundary for `linear` by the loopback tests with pinned
  fixtures.
- `linear` implements all four operations through Linear's issue `comments` connection and its
  `commentCreate`, `commentUpdate` and `commentDelete` mutations. The pinned schema subset
  `crates/onetaskgraph-linear/tests/fixtures/schema.graphql` carries every comment type, input, payload
  and mutation the plugin sends. Each is taken from Linear's published schema, with no placeholder, and
  its pin is recorded in that file as its other pins are. That content is later compared against Linear's
  real API by the repository's credentialed Linear live lane, which its merge path runs on a change to
  the Linear plugin. That comparison's result is not this node's bar. No
  plugin declares comments `Unsupported`, and `docs/follow-ups.md` gains no entry for the capability,
  unless the manager recorded an operation Linear cannot carry as a plan exception. A journey shows
  that a comment verb against a source that does not declare comments, such as a stdio plugin whose
  handshake omits the capability, is refused before anything is read, naming the source and its plugin.
- Each refusal C1 lists exits non-zero with the problem and a next action on stderr, and each is proven
  by a journey. The refusals are an unknown task id, an unknown comment id, a source without comments, a
  `github-projects` draft issue, `--author` on a source that records authors itself, and an empty body.
- A `local-md` task file carries its comments in exactly the C2 section shape. Every C2 rule is exercised
  by a test at the plugin boundary or by a journey:
  - the section is recognised only as the trailing run of comment blocks;
  - there is no heading when there are no comments;
  - bodies, including their own headings, are kept unchanged;
  - a body containing the closing marker is refused;
  - comment ids are minted as C2 states;
  - the section is excluded from `content` and from content search;
  - a copy into the file keeps its existing section unchanged, and no comment of the copy's source
    enters it.

  Beyond `local-md`, `task copy`, `project copy` and `document copy` each neither read nor write
  comments at either end. A journey for each of the three shows the copy making no comment call at its
  source or its destination. Where both ends hold tasks with comments, it also shows the destination's
  comments unchanged and no source comment reaching the destination.

  `docs/local-md.md` describes the section.
- The `github-projects` comment operations are covered by the loopback-board tests with pinned fixtures.
  Every document they add is inside the node-count bound the offline gate enforces.
- `docs/plugin-protocol.md` documents the new capability and the four methods. The contract inventory in
  `AGENTS.md` names every new api-crate export, and `scripts/check-contract-inventory.sh` passes. The
  journey inventory in `AGENTS.md` lists the new journeys.
- `SCHEMA_BUNDLE_VERSION` and `PUBLISHED_BUNDLES` record the changed emitted document. Both SDKs are
  regenerated from it and expose the four operations, and each SDK's tests exercise them against the real
  binary.
- The tests and checks over the projects this change touches pass over the finished tree: the
  affected-project deterministic tier, the capability-verdict and contract-inventory checks, and both
  SDKs' tests.
- The judged lint over this branch's diff against its base leaves no finding unanswered. The completion
  report lists, each with its site and reason, every suppression directive the diff writes (added, moved
  or rewritten) and every site-scoped directive already standing over a line the diff changes. A
  file-scoped directive the diff does not itself write is outside that list.
- The behaviour this node adds is proven end to end by journeys that drive the real binary, not by
  inspection. Every claim the dispatch makes about the finished work, including what it verified and the
  evidence for it, is true of the tree as it finally stands.

## Additional info

### Operational notes for this host

**Run only the checks that exercise what you changed.** The tests that cover the code
you touched, the lint that reads your diff — and nothing wider. The repository's own
automation runs the full bar downstream on the change this work becomes: a `pre-push`
hook where that repository publishes locally, the host's required checks where it
publishes remotely. Neither is waiting for you to have run it first, so running it here
spends twenty to forty minutes of this dispatch learning what the merge path reports
anyway. That is measured rather than estimated: one node in this workstream spent about
84 minutes on three rounds of everything its repository could run, to reach lint findings
a diff-scoped run reports in two.

**Pick those checks from your change, and take the narrowest scope each one supports.**
One test module over the whole suite; the lint over your diff over the lint over the
tree. A repository's own fast deterministic tier is a fine choice when it is what
exercises your change — its `just --list` says which recipe that is — and a poor one when
you reached for it because it was the widest thing available. When a check you ran
reports something, fix that and run **that check** again; nothing here asks you to re-run
its neighbours to confirm, and a wider tier cannot re-check a finding it never made.

**A dispatch that changed nothing tracked owes none of them.** When your deliverable is a
document, a report, or an answer, there is no changed code for those checks to exercise
and you are complete without them — decide that from what the repository shows, never
because running them is slow or inconvenient. `git status` reporting nothing to commit is
then a correct and complete outcome, not a problem to solve by writing a file nobody
asked for.

**Never signal a process you did not identify by PID, and a PID you got from a pattern is
still a pattern kill.** Several managers share this host, and their dispatches, drivers,
publications and test servers run under the same few binary names — `just`, `node`,
`python`, `onepipeline-api` — so a kill by name knows nothing about *whose* work it
matched. The distinction is the tool rather than the pattern: `pgrep` and `ps` **read**,
and either spelling of them is fine, `pgrep -x` included; `pkill` **signals**, and it is
never the answer here, in any spelling. `-x` is the trap, because it reads as the careful
one — `pkill -f 'just gate'` at least needs a narrowing pattern, while `pkill -x just`
takes every `just` on the machine. Reading the table first and piping the pids into `kill`
is no way around it: that is the same pattern kill with more steps.

Two workers reached that place from different directions on 2026-08-24, while another
manager's dispatch had been live over an hour. One ran `pkill -TERM -x just`. The other
ran `ps -eo pid,args | grep 'onepipeline-api serve' | awk '{print $1}' | while read pid;
do kill "$pid"; done` — which obeys the letter of every paragraph below and does the same
damage, because `just dag-ui` and the e2e suites both spawn that server and a pytest run's
were alive at that moment.

**The one process you may signal is one you started yourself, so capture its PID as you
start it:**

    cmd & MYPID=$!
    kill "$MYPID"

Anything you did not start belongs to somebody. Read what it is, report what you found,
and leave it running.

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or
`publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

That has wedged four workers here, and then two more workers and the manager itself in one
night: seven instances of one defect. A crozier corpus audit waited in `until ! pgrep -f
'scripts/fetch-corpus.sh'` with no fetch running at all — the only two matches were its own
polling shell and the manager's diagnostic shell — and waited until it was interrupted. A
`check-plan-bar-conflict` dispatch waited on `! pgrep -f "llmlint-judge.sh"`, whose negation
could never become true, and was cancelled and killed; its replacement then reached for
`pkill -f` against three patterns, which is not a wait at all but the same self-match with a
signal attached, and is refused above. And the manager, an hour after instructing a worker
about this, guarded a launch with `pgrep -f "publish-branch" && echo ABORT || launch`, whose
pattern was a literal substring of the launching shell's own command line: it aborted
unconditionally and then reported a publish as RUNNING that did not exist. That last one is
the evidence that matters most — a rule its own author reproduces an hour after issuing it
is a rule whose wording is the problem rather than its reader.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.

**To ask whether a process is running at all, match the executable, not the command line.**
`pgrep -x onepipeline` matches process *names* exactly — the binary, not its arguments — so
the shell doing the asking, whose own name is `bash`, cannot match it however the pattern
is spelled. Where the binary name is not distinctive enough to identify what you mean
(`just`, `node` and `python` run everything), read the process table instead and drop the
one self-match that form has:

    ps -eo pid,args | grep -v grep | grep 'lint-llm-diff'

Both of those are **reads**, which is what makes `-x` safe here and forbidden the moment
the tool signals. The replacement for the worker wedged above reached for `pkill -f "just
gate"`, `pkill -f "just check"` and `pkill -f "nx run"` while another manager's run was
live. Read to learn what is running, report what you found, and signal nothing you did not
start.

**One sentinel and one log per invocation, and look before you launch one.** That pair is a
shape rather than two literal paths. Several dispatches run on this host at once and they
share `/tmp`, so a second worker writing `/tmp/check.log` writes into the first one's — and
`until [ -f /tmp/check.exit ]` returns immediately on somebody else's exit file, reporting
their result as yours. Name both after the invocation (`/tmp/check.$$.log`, or the node
id), and, before starting it, check whether its sentinel path is already in use by another
invocation; if so, choose a different invocation-specific pair. This path-ownership check
does not prohibit concurrent checks or judged tiers. Three workers collided on shared names
today and not one of the three failures read as what it was: two
deterministic-tier runs deadlocked against the same cargo target-directory lock, so both
logs sat unchanged and neither progressed — about fifteen minutes lost and three
interruptions to a live turn; two whole-e2e runs wrote to one log, and stopping the
duplicate left four `SIGTERM` entries in it that read exactly like real test failures; two
judged-tier runs raced and wasted a roll, which was harmless only by luck. Read a log that
has stopped growing as two commands blocking each other before you read it as one command
working.
