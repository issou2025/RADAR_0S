# `pull_request_rules` in `.mergify.yml` is not loaded — Mergify has never evaluated it

## The finding

Mergify's own evaluation of the configuration reports:

```
The new Mergify configuration is valid, but some sections will not be used:
- `pull_request_rules`
  The product Workflow Automation needs to be activated to enable this feature.
The rest of this new configuration will be used for the next pull requests once
it is merged.
```

Surfaced by the PR #5424 `Configuration changed` check (app `mergify`), verified on head `8e443c754`. The same warning appears on #5384 and on #5065, the PR that added the file.

So **every rule under `pull_request_rules` in this repo's `.mergify.yml` is inert.** The section is parsed and schema-valid, and Mergify never acts on it. A reader — or an agent — writing a rule there gets silence, not an error.

## Why this matters more than a tidy-up

The file contains exactly one rule, and it is the mechanism that was *supposed* to queue finished PRs:

```yaml
pull_request_rules:
  - name: queue ready PRs onto main
    conditions: [base=main, -draft]
    actions:
      queue:
        name: main
```

**It has never run.** This is the second, independent reason nothing auto-queued:

1. the intended rule above is not loaded (this issue); and
2. `autoqueue` / `auto_merge_conditions` was never set (#5150).

Only reason 2 was previously known. That matters because reason 1 means a *correct-looking* configuration produced no behaviour — the same defect family this repo keeps hitting: **a mechanism that appears to be wired and is not.** It also means the diagnosis in #5150 was incomplete: setting `auto_merge_conditions` fixes the observed symptom, but anyone who later reads the file and reasons "the queue rule is here, so PRs queue" will be wrong for the *other* reason.

## Why it was invisible

- Mergify treats it as a **warning**, on a check whose default conclusion is not failure.
- The config is **schema-valid** — Mergify's published schema accepts `pull_request_rules` (the file validates with 0 errors).
- The warning text lives in a check-run **output summary**, which nothing reads unless it is deliberately fetched.

## Options

**A — Activate Workflow Automation** for the repo. Then `pull_request_rules` loads and the rule starts working. This introduces a second queueing mechanism alongside `auto_merge_conditions`, which would then need reconciling (they overlap almost entirely).

**B — Delete the `pull_request_rules` section** from the file, since `auto_merge_conditions` under `merge_protections_settings` is loaded and is doing the job. The file then contains no dead config, and no reader has to know which product is activated to interpret it.

**C — Leave the section and rely on the comment** added in #5424 warning that it is not loaded. Cheapest; keeps a schema-valid but inert block whose only effect is to mislead.

## Recommendation

**B**, once #5424 lands and the queue is confirmed draining. It removes the trap rather than documenting it, and there is no behaviour to lose — the section has never executed.
