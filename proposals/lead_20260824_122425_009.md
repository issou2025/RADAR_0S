# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**flutter (cratestack_cbor ios) flakes on unrelated PRs — marker missed, app SIGTERM'd before it prints**

*Project description:*
### Type

Bug

### Summary

`flutter (cratestack_cbor ios — real build, xcframework + round-trip proof)` fails intermittently on
PRs that touch no Dart, Flutter, or iOS code, and passes on re-run of the same commit. Observed twice
in ~100 minutes on 2026-08-23. The app builds, installs and launches successfully; the round-trip
marker simply never reaches either capture channel before the process is terminated.

This is the **third** variant of this failure mode. The recipe's own comments document two previous
fixes for it, both of which are still in place and working — so the usual remedy (narrow the log
capture further) is likely not the answer here.

### Source of truth (links)

- Occurrence 1 — PR #701 (`fix: correct protobuf/gRPC removal version wording`), job `97184681860`,
  started 2026-08-23T11:06:14Z. That PR changed Rust error strings, code comments, docs and a
  changelog entry. No Dart, Flutter or iOS code.
- Occurrence 2 — PR #703 (`fix(cratestack-client-rust): remove obsolete null-strip`), job
  `97195124783`, started ~12:46Z. That PR changed `cratestack-client-rust` and added a
  `cratestack-pg` test. No Dart, Flutter or iOS code.
- Both passed on re-run of the identical commit, no code change in between.
- The recipe: `justfile`, `cbor-example-verify-ios`.

### Current Behavior

Byte-identical failure signature both times:

```
=== installing + launching dev.cratestack.examples.cratestackCborExample ===
FAIL: built iOS simulator app did not print the expected round-trip marker.
--- device state ---
    iPhone 17 Pro (…) (Booted)
--- is the app installed? ---
    …/Bundle/Application/…/Runner.app
--- console-pty capture (     160 bytes) ---
… Runner[30243:93502] Warning: Unable to create restoration in progress marker file
dev.cratestack.examples.cratestackCborExample: 30243
--- unified log capture (     147 bytes), last 50 lines ---
getpwuid_r did not find a match for uid 501
Filtering the log data using "process == "Runner""
Child process terminated with signal 15: Terminated
error: recipe `cbor-example-verify-ios` failed with exit code 1
```

So: simulator booted, app installed, app launched with a real PID, log stream attached and filtering
correctly — and then `signal 15` (SIGTERM) with the marker absent from **both** channels.

**What rules out the two known causes.** The recipe's comments record them:

1. *"The first CI run of this recipe failed with a COMPLETELY EMPTY capture from `--console-pty`"* —
   which is why there are now two independent capture channels. Not this: both channels captured
   content (160 and 147 bytes), just not the marker.
2. *"produced 63 MB of log in 90 seconds … the poll loop below then re-greps that growing file once a
   second, so the marker race is lost on a slow runner — which is exactly how this failed,
   intermittently, while passing on other runs."* Fixed by the exact `process == "Runner"` predicate,
   taking capture from 63,727,376 bytes to 283. Not this either: our captures are 160/147 bytes, so
   the firehose is genuinely gone.

The remaining hypothesis is that the app is being SIGTERM'd by the recipe's own timeout before Flutter
reaches the `print` that emits the marker — i.e. a startup-latency race rather than a log-volume race.
The recipe's comment already notes the runner is *"comfortably slower than the desktop jobs this
timeout was copied from."* That would make the timeout, not the capture, the thing to look at.

### Expected Behavior

- The job passes deterministically on any commit that does not touch the iOS/Flutter/CBOR surface.
- If the app genuinely fails the round trip, the job fails for that reason and says so.
- A failure distinguishes "app never printed the marker" from "app was killed before it could."

### Acceptance Criteria

- [ ] The job passes on repeated runs of an unrelated commit — say 5 consecutive runs, since a flake
      that reproduces one time in three will look fixed after a single green.
- [ ] On timeout, the diagnostic states explicitly that the process was terminated by the harness and
      after how long, so the next reader is not left inferring it from `signal 15`.
- [ ] A genuine round-trip failure still fails the job — verify by deliberately breaking the marker
      string and confirming a red run. Without this, "fixing" the flake by widening a timeout could
      equally be achieved by making the assertion unreachable.
- [ ] Existing behavior is not broken.
- [ ] Verification evidence is provided.

### Out of Scope

- The two already-fixed variants (empty capture, log firehose). Both remain fixed; do not undo them.
- The macOS/Android/Windows/Linux/web legs, which have not been observed failing this way.

### Technical Context

`justfile`'s `cbor-example-verify-ios` boots a simulator, attaches
`xcrun simctl spawn … log stream --level=debug --style=compact` with a `process == "Runner"`
predicate, `sleep 2`, launches via `xcrun simctl launch --console-pty`, then polls both capture files
once a second for `CRATESTACK_CBOR_EXAMPLE_RESULT:` until a timeout.

Note `--level=debug` is load-bearing and documented as such — Flutter's `print` reaches the unified
log at DEBUG level (`Df Runner[…] (Flutter) flutter: CRATESTACK_CBOR_EXAMPLE_…`). An earlier attempt
dropped it and broke detection. Do not remove it while chasing this.

### Risks

- **Widening the timeout is the obvious fix and the easy way to paper over a real regression.** If the
  app is genuinely getting slower to start, a longer timeout hides that. Worth capturing how long the
  marker actually takes on a passing run before choosing a number.
- This job has **no `main` baseline** — it does not appear in `main`'s CI runs, so when it fails there
  is nothing to compare against. That is what made the diagnosis slower here than it needed to be, and
  is arguably worth fixing independently.
- macOS runners are a constrained resource; more retries or longer timeouts have a real cost.

### Test Plan

1. Instrument a passing run to record the interval between `simctl launch` and the marker appearing.
2. Compare against the current timeout. If the margin is thin, that is the bug.
3. Apply the fix, then run the job ≥5 times on an unrelated commit and confirm all green.
4. Break the marker string deliberately; confirm the job still fails red.

### Verification evidence

Not yet implemented. Evidence for the diagnosis is above: two job IDs with identical signatures, both
on PRs touching no iOS code, both green on re-run of the same commit, and the recipe's own comments
ruling out the two previously-fixed causes.
