## What happened

While checking the meaning of “require approval every time”, we reproduced two identical concurrent static tool calls executing after one approval with `remember_minutes=0`.

This was reproduced **offline**, using the real FastMCP server, PolicyMiddleware and approval queue, with a fake terminal action that only appends to a Python list. No Home Assistant connection, household device operation or live Settings UI approval was used. This report was prepared by Hermes at the owner's request from executed tests; it is not a claim of a household incident or unauthenticated access.

## Version and scope

- Reproduced against unchanged **v8.4.3**, commit `eac7a3aa7063432e9af17e7d7726040e909c7b8f`.
- Test environment: Python 3.13.15, upstream dependency environment; network denied during the recorded tests.
- Both direct `ha_call_service` and nested `ha_call_write_tool` routes reproduce it.
- An unconditional rule with `remember_minutes=0`; no argument-condition matching ambiguity.

## Reproduction

1. Register a synthetic write tool behind the real policy middleware with zero remembered reuse.
2. Start two identical calls through two in-process MCP clients.
3. Wait until both clients report “Awaiting user approval”. Confirm one pending row and no terminal dispatch.
4. Approve that row once through the queue's public approval method.
5. Observe the terminal dispatch list.

**Observed on v8.4.3:** both calls dispatch the fake action. The one-execution assertion fails for both routes.

**Expected from a zero-reuse setting:** one call dispatches; the other requires a new approval. If sharing among already-waiting identical static calls is intentional, please clarify that contract—the distinction from remembered reuse is important to operators.

"""Approval cardinality at the MCP call/progress and public approval seams.

Real FastMCP and PolicyMiddleware; only the terminal action is synthetic.
No HA connection, queue internals, clock patching, or race-by-sleep assertions.

from __future__ import annotations

import asyncio
from collections.abc import Awaitable, Callable
from typing import Any

import pytest
from fastmcp import Client, Context, FastMCP
from fastmcp.client.client import CallToolResult
from mcp.types import TextContent

from ha_mcp.policy.approval_queue import ApprovalQueue
from ha_mcp.policy.middleware import PolicyMiddleware
from ha_mcp.policy.model import Policy, Rule
from ha_mcp.transforms.categorized_search import CategorizedSearchTransform

ARGS = {"domain": "light", "service": "turn_on", "entity_id": "light.synthetic"}
MUTATED = {"domain": "light", "service": "turn_on", "entity_id": "light.other"}
SELECTOR = {
    "selector": {"domain": "light", "area_ids": ["synthetic_area"]},
    "action": "turn_on",
}


def policy_server(
    queue: ApprovalQueue, *, remember_minutes: int = 0, wait_seconds: int = 5
) -> tuple[FastMCP, list[dict[str, Any]]]:
    server = FastMCP("single-use-approval-test")
    dispatched: list[dict[str, Any]] = []

    @server.tool(name="ha_call_service", annotations={"readOnlyHint": False})
    async def action(domain: str, service: str, entity_id: str) -> dict[str, bool]:
        dispatched.append(
            {"domain": domain, "service": service, "entity_id": entity_id}
        )
        return {"fake_dispatch": True}

    @server.tool(name="ha_bulk_control", annotations={"readOnlyHint": False})
    async def bulk(selector: dict[str, Any], action: str) -> dict[str, bool]:
        dispatched.append({"selector": selector, "action": action})
        return {"fake_dispatch": True}

    policy = Policy(rules=[Rule(tool_name="*", remember_minutes=remember_minutes)])
    server.add_middleware(
        PolicyMiddleware(
            policy_provider=lambda: policy, queue=queue, wait_seconds=wait_seconds
        )
    )
    server.add_transform(CategorizedSearchTransform())
    return server, dispatched


def envelope(route: str, args: dict[str, Any] = ARGS) -> tuple[str, dict[str, Any]]:
    if route == "direct":
        return "ha_call_service", dict(args)
    return "ha_call_write_tool", {"name": "ha_call_service", "arguments": dict(args)}


def assert_approval_required(result: CallToolResult) -> None:
    assert result.is_error
    assert isinstance(result.content[0], TextContent)
    assert '"USER_APPROVAL_REQUIRED"' in result.content[0].text


def assert_denied(result: CallToolResult) -> None:
    assert result.is_error
    assert isinstance(result.content[0], TextContent)
    assert '"USER_DENIED"' in result.content[0].text


async def wait_for_approval_progress(
    *events: asyncio.Event,
) -> None:
    await asyncio.gather(*(event.wait() for event in events))


def progress_setter(
    event: asyncio.Event,
) -> Callable[[float, float | None, str | None], Awaitable[None]]:
    async def handler(
        progress: float, total: float | None, message: str | None
    ) -> None:
        assert message and "Awaiting user approval" in message
        event.set()

    return handler


@pytest.mark.parametrize("route", ["direct", "write-proxy"])
async def test_one_approval_dispatches_only_one_overlapping_static_call(
    route: str,
) -> None:
    queue = ApprovalQueue()
    server, dispatched = policy_server(queue)
    ready = [asyncio.Event(), asyncio.Event()]
    name, arguments = envelope(route)
    async with asyncio.timeout(10), Client(server) as first, Client(server) as second:
        async with asyncio.TaskGroup() as tasks:
            calls = [
                tasks.create_task(
                    first.call_tool(
                        name,
                        arguments,
                        progress_handler=progress_setter(ready[0]),
                        raise_on_error=False,
                    )
                ),
                tasks.create_task(
                    second.call_tool(
                        name,
                        arguments,
                        progress_handler=progress_setter(ready[1]),
                        raise_on_error=False,
                    )
                ),
            ]
            await wait_for_approval_progress(*ready)
            pending = queue.list_pending()
            assert len(pending) == 1
            assert dispatched == []
            assert queue.approve(pending[0].token)
        results = [call.result() for call in calls]

    assert dispatched == [ARGS], "one approval must authorize only one execution"
    assert sum(not result.is_error for result in results) == 1
    assert_approval_required(next(result for result in results if result.is_error))
    assert len(queue.list_pending()) == 1
    assert queue.list_pending()[0].token != pending[0].token

## Source observation / possible correction

`ApprovalQueue.find_or_create` shares a pending entry for matching static arguments. Waiters can retain the same approved entry; removing its token does not by itself require every dispatcher to successfully claim that token before continuing.

A local candidate makes zero-reuse consumption exclusive and checks the claim in both middleware dispatch paths. Other waiters receive a new pending approval. It preserves timeout → approval → identical re-call and explicitly positive remembered reuse, including per-approved-waiter refresh.

The candidate passed **12 regression/compatibility cases** and **504 selected offline tests**, plus scoped Ruff/format/mypy checks. Those are local candidate results, not the full upstream collection or installed-app verification. A compatibility regression found during review was corrected before the final run. The candidate is not installed or submitted as a PR.

Related: #2246 addresses dynamic selectors; this reproduction uses static arguments. #2369 is a tool-concurrency limit, which is distinct from consuming an approval once. #1990 describes missing/inconsistent gating; here the gate is present and waits, but one approval releases multiple calls.

Could you confirm the intended zero-reuse behavior and whether an exclusive-consumption correction would be welcome? We are reporting this as a non-blocking known limitation for our use, not requesting a private deployment or making a universal security claim.

`ha_report_issue` was not run because the evidence is an isolated source regression rather than a live HA failure; household logs and connection details are not needed for this reproduction.
