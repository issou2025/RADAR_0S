*Project description:*
### Bug Description

`ifcopenshell.util.unit.calculate_unit_scale(model, unit_type)` applies the SI prefix
**linearly**, ignoring that for `SQUARE_METRE` / `CUBIC_METRE` the prefix attaches to the
*metre* and is therefore raised to the power of the dimension.

For `IFCSIUNIT(*,.VOLUMEUNIT.,.DECI.,.CUBIC_METRE.);` — a cubic decimetre, i.e. a **litre**,
which real-world MEP exports declare as the project volume unit — it returns `0.1` instead of
`0.1**3 = 0.001`, so every volume read through this scale factor is inflated **×100**.
`AREAUNIT` is affected the same way (the error factor is 1/prefix: ×10 for DECI, ×100 for CENTI).

In SI, a prefix attached to a unit symbol forms a new inseparable symbol which is raised to
the power as a whole: dm³ means (dm)³ = 10⁻³ m³, not 0.1 m³. There is no SI construct meaning
"0.1 m³", so the linear interpretation maps `DECI CUBIC_METRE` to a unit that does not exist.

The rest of `util/unit.py` already follows the exponent interpretation, so the module is
internally inconsistent:

- `named_dimensions["VOLUMEUNIT"] == (3, 0, 0, 0, 0, 0, 0)` ([unit.py#L178](https://github.com/IfcOpenShell/IfcOpenShell/blob/048242783eafe097eb9733eee9c99a4ded235682/src/ifcopenshell-python/ifcopenshell/util/unit.py#L178))
- `convert()` multiplies the prefix multiplier twice for `SQUARE` and three times for `CUBIC`
  unit names ([unit.py#L666-L684](https://github.com/IfcOpenShell/IfcOpenShell/blob/048242783eafe097eb9733eee9c99a4ded235682/src/ifcopenshell-python/ifcopenshell/util/unit.py#L666-L684))
- `get_unit_symbol()` renders this exact unit as `dm3` ([unit.py#L624](https://github.com/IfcOpenShell/IfcOpenShell/blob/048242783eafe097eb9733eee9c99a4ded235682/src/ifcopenshell-python/ifcopenshell/util/unit.py#L624))

i.e. the library *displays* the unit as dm³ (one litre) but *scales* it as 0.1 m³ (100 litres).

### Expected vs actual (ifcopenshell 0.8.5)

| unit_type  | declaration       | meaning     | expected scale     | actual scale | error |
| ---------- | ----------------- | ----------- | ------------------ | ------------ | ----- |
| LENGTHUNIT | MILLI METRE       | mm          | 1e-3               | 1e-3         | OK    |
| AREAUNIT   | DECI SQUARE_METRE | dm²         | (1e-1)² = **1e-2** | 1e-1         | ×10   |
| VOLUMEUNIT | DECI CUBIC_METRE  | dm³ = litre | (1e-1)³ = **1e-3** | 1e-1         | ×100  |

### Root cause

[`calculate_unit_scale`, unit.py#L723 on current master](https://github.com/IfcOpenShell/IfcOpenShell/blob/048242783eafe097eb9733eee9c99a4ded235682/src/ifcopenshell-python/ifcopenshell/util/unit.py#L723)
(line 718 in the 0.8.5 wheel):

```python
if unit.is_a("IfcSIUnit"):
    unit_scale *= get_prefix_multiplier(unit.Prefix)
```

The prefix multiplier is applied to the first power regardless of `unit_type` / unit name.
(The `IfcConversionBasedUnit` part of the chain is fine — the conversion factor carries the
full multiplier; a prefixed SI unit terminating the chain hits the same line above.)

### Suggested fix

Mirror the logic `convert()` in the same module already uses:

```python
if unit.is_a("IfcSIUnit"):
    multiplier = get_prefix_multiplier(unit.Prefix)  # 1 when Prefix is None
    if "CUBIC" in unit.Name:
        multiplier **= 3
    elif "SQUARE" in unit.Name:
        multiplier **= 2
    unit_scale *= multiplier
```

Keying on the unit *Name* (rather than on `named_dimensions[unit_type]`) keeps prefixed
derived units such as KILO PASCAL or MEGA NEWTON linear, which is correct — there the prefix
attaches to the derived unit itself, not to the metre.

### Real-world impact

IFC4 MEP exports (e.g. MagiCAD for Revit) declare
`IFCSIUNIT(*,.VOLUMEUNIT.,.DECI.,.CUBIC_METRE.);` with quantity values in litres. Reading any
`IfcQuantityVolume` through `calculate_unit_scale(model, "VOLUMEUNIT")` then inflates every
volume ×100 (confirmed on production files; caught by cross-validating quantities against an
independent source).
