## Context

`docs/parity.csv` row `native-formats` — «Собственные форматы коммерческих программ», status `open`, release `unresolved`, verification «Документировать разрешённый формат и корпус совместимости», no evidence. Every other open row has a 1.0 plan; this one blocks closing the matrix because it has no decision.

Current state of exchange: IFC2X3 import, IFC4 / IFC4.3 import and export (`docs/ifc-support.md`, `docs/help/model-import.md`), DXF export (DWG via acadrust in [1.0 #9]), DSTV NC, BVBS, CSV, PDF. `docs/help/model-import.md` already explains to users: native formats of commercial programs are closed, their structure is not published and reading them is allowed only by the vendors' own tools, so the path is «save as IFC in the source program → import in Open BIM».

## Proposal

1. **Scope for 1.0: IFC only.** Native/proprietary formats of commercial programs (model databases and project files of commercial BIM/detailing tools) are **out of scope for 1.0**. Exchange with them goes through IFC (ISO 16739), plus DXF/DWG for drawings, DSTV for NC and BVBS for rebar.
2. Reasons: formats are undocumented or licensed only through vendor SDKs whose terms are incompatible with Apache-2.0 distribution; reverse engineering creates legal and maintenance risk; IFC4.3 import/export already covers the model exchange with verified results.
3. **Change to the matrix after approval:** row `native-formats` → `status=verified`, `release=1.0`, verification «Документировать разрешённый формат и корпус совместимости» satisfied by: a short `docs/native-formats.md` stating the decision and the allowed formats (IFC2X3/IFC4/IFC4.3, DXF/DWG, DSTV, BVBS, CSV, PDF), and a compatibility corpus = the existing IFC import corpus (`tests/fixtures/ifc/`, `crates/ifc/tests/foreign.rs`) listed with the source program of each file. Alternatively mark the row `release=out-of-scope` if the owner prefers it not to count as "verified".
4. Revisit after 1.0 only if a vendor publishes an open specification or an Apache-compatible SDK.
