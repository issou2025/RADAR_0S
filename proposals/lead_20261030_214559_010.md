# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Plan: Unified OptiScaler manager with OptiPatcher data, recipes and advanced options**

*Project description:*
## Objective

Turn OptiScaler Backup into a Windows game-mod manager combining **our recoverable backup/package engine**, **OptiClick's game/GPU recipes**, and **OptiScaler Client's compatibility data, component/version selectors, profiles and advanced controls**.

Keep our application, CLI, WPF UI, launcher discovery, readable snapshots and existing package history. Add automatic installation and configuration above that foundation. Do not fork either upstream application wholesale or replace our storage engine.

Make ongoing upkeep data-driven: automatically refresh read-only upstream information, propose recipe/schema updates in one weekly maintenance PR, and publish approved data packs independently of application releases. New execution behavior remains application code.

**This issue is a detailed implementation roadmap only. No application code was changed, dependencies installed, builds run or game files touched during this investigation.**

## 1. Compatibility and OptiPatcher data

### Sources and model

Add independently versioned CompatibilityCatalog and GameRecommendation services:

- Primary OptiPatcher source: official GameSupport.md at the **selected release tag's resolved commit**. Parse DLSS and DLSS-FG separately into Supported / Unsupported / NotApplicable / Unknown; preserve notes and source links. Show main-branch additions separately as potentially unreleased.
- Secondary context: official OptiScaler Compatibility-List main and Luma tables. Preserve overall compatibility, upscaler inputs, OS constraints, OptiPatcher indicator, mod context, notes and individual-page link.
- Fetch per-game pages lazily. Extract only structured fields: tested OptiScaler version, proxy filename, inputs, FG settings and known-issue count. Keep remaining prose readable and link to the original page.
- Each observation records source URL, revision or response hash, fetch time, parser schema and relevant component version. Do not collapse contradictory observations into a single Boolean.
- Blank wiki OptiPatcher cells mean **unknown/unlisted**, not "not required." A supported marker does not establish FG support. Newer notes describing DRM/version failures override an optimistic badge for automatic recommendations until reviewed.
- Official component documentation takes precedence over historical OptiClick data. Curated executable/platform/version-specific corrections can constrain a recommendation but must cite their evidence. Conflicts are displayed and prevent automatic selection of the disputed feature.

### Matching, refresh and offline behavior

- Resolve by known launcher ID plus curated executable/platform aliases first, then unique exact normalized title. Fuzzy matches are suggestions requiring a saved user association; never auto-apply another game's recipe.
- Keep remakes, editions, demos, launcher variants and separate executables distinct. Do not infer every Unreal title supports OptiPatcher.
- Background refresh at most daily, explicit Refresh bypasses cooldown; conditional HTTP requests, bounded responses, retry/backoff and rate-limit reporting.
- Store last-known-good raw and normalized data atomically. Validate expected table headers and reject empty/truncated/invalid refreshes without replacing good data.
- Missing/unknown symbols stay unknown. Preserve unknown prose; never turn free-text instructions into executable actions.
- Show source age, stale/offline state and match confidence. Offline backup/restore/local packages remain usable; cached exact component versions can install offline.
- Automatic OptiPatcher selection requires a positive match for the **chosen released version**. Stale data alone cannot establish newly added support.

### OptiPatcher installation

- Selector: Auto, None, or concrete release; resolve Auto to an exact asset before preview. Auto is a policy value, never a release string sent to GitHub.
- Download official optiscaler/OptiPatcher assets only; rename the selected release asset to OptiPatcher.asi at its resolved destination.
- Use the selected package's actual layout and configured OptiDllPath / Plugins.Path. Support legacy root/plugins and newer OptiScaler/plugins; validate custom plugin paths against explicitly approved roots.
- Stage plugin bytes and the section-aware Plugins.LoadAsiPlugins=true edit together. Missing/ambiguous INI locations require resolution before commit.
- Display DLSS unlock and DLSS-FG unlock as separate capabilities, relevant game-version notes, and required user steps.
- Do not mark runtime patch success merely because the plugin exists. Show Installed; offer upstream's overlay/log verification guidance separately.
- Do not blanket-disable spoofing: derive recommendations from the selected FG route and version. Include the documented Windows Nukem exception in validated recipe rules rather than copying an unconditional toggle.

## 2. Component catalog, downloads and recipes

Introduce ComponentCatalog, ReleaseProvider, ArtifactCache, GameAnalyzer, GpuProvider and RecipePlanner boundaries. Core planning remains UI-independent; Windows supplies process/GPU/file-version/registry adapters.

### Components and sources

- Core sources: official OptiScaler stable/nightly, OptiPatcher, fakenvapi, Nukem9/dlssg-to-fsr3, NVIDIA Streamline, praydog REFramework, official Ultimate ASI Loader/Special K projects and the referenced UE fix project.
- Beta, extras, FP8/INT8 and experimental repositories are separate, visibly identified community providers; do not present Client-hosted mirrors as official OptiScaler releases.
- Every descriptor records component ID/version/channel, repository/release/asset identity, architecture, digest/trust provenance, archive type, layout, dependencies, conflicts and supported configuration-schema family.
- Support raw DLL/ASI, ZIP and bounded 7z extraction. Keep existing ZIP mapping/import behavior. Isolate 7z behind an archive-reader interface; use a pinned managed reader such as SharpCompress after dependency/license/security review, without invoking packaged setup scripts.
- Apply our existing entry-count/expanded-byte limits to all formats; reject links, traversal, device paths, case collisions, encrypted/multipart archives and conflicting destinations. Stage outside game directories; clean incomplete downloads/extractions.
- Use HTTPS, exact asset matching and expected SHA-256 from GitHub asset metadata or a reviewed pinned manifest. Reverify cached bytes before use. A locally computed hash alone is labeled as such, not independent publisher verification.
- If no trusted expected digest is available, offer explicit reviewed local import; do not silently promote unverified bytes into automatic installs.
- Cache exact artifacts and extracted payloads. Pins remain reproducible even when "latest" moves. Catalog refresh never silently upgrades installed games.

### Recipes

- Convert useful historical OptiClick recipes into reviewed declarative records: executable match, launcher variant, GPU/API conditions, destination mapping, exclusion list, component requirements, typed configuration edits, prerequisites and source/version evidence.
- Initial recipes are file-only. No arbitrary shell, PowerShell, batch, installer or script execution.
- Analysis distinguishes selected runtime executable, launcher executable and game library root; handles nested UE shipping/WinGDK layouts and multiple candidate binaries through explicit selection.
- Show installed DLSS/FSR/XeSS/FG versions with evidence. Preserve raw file versions alongside friendly mappings; mappings do not prove capability.
- Preferred GPU is explicitly persisted and visible. Ambiguous API/GPU detection remains unknown; feature availability comes from an explainable capability matrix, not vendor-name guessing.
- Resolve proxy conflicts with ReShade/Special K/other mods without replacing an unidentified existing DLL. Offer validated alternative names or explicit reviewed conflict resolution; installation ownership comes from our manifest, not filename alone.
- OptiClick's remote V2 authentication, device registration and unpublished backend are not dependencies. No hosted service, API keys or local secrets are needed.

## 3. One plan and one recoverable execution path

Do not call upstream installers directly and surround them with a broad backup. They modify files/settings outside a complete known target set.

### Public interfaces

Add shared UI/CLI interfaces:

- BuildPlan(game, selections, evidence) -> immutable OperationPlan.
- Preview(plan) -> additions/replacements/removals, key/value edits, component resolutions, sources, warnings, preconditions and conflicts.
- ExecutePlan(plan), ReviseInstallation(id, plan), RollbackRevision(id, revision), and UninstallBundle(id).
- OperationPlan contains exact resolved artifacts, selected executable/GPU, recipe/schema revisions, desired targets, pre-state fingerprints and typed side effects. No network resolution or mutable "latest" remains at execution time.

### File and bundle behavior

- Download and transform everything in staging. Generate complete final INI/JSON/XML bytes before taking affected-target snapshots. Resolve all required components before the first game mutation; a required component failure fails the whole bundle.
- Merge shared paths once. Permit component overrides only when declared by the selected recipe; unresolved output collisions block preview.
- Recheck destination hashes and analysis preconditions immediately before commit. Changed inputs invalidate the preview.
- Reuse Store/Engine integrity, approved-root, process, access, free-space and exclusive-lock protections. Journal must be durable before any file, attribute or registry change.
- Cancellation before commit changes no game files; cancellation/failure after writes starts recovery. Report whether rollback succeeded or remains pending.
- A managed bundle owns its component files and generated configs as one installation. Uninstall restores originals, including removal of files originally absent; unrelated files remain untouched.
- Config-only changes revise that bundle's expected post-state without reinstalling DLLs. Preserve the first pre-install baseline; retain immutable revisions and recovery snapshots. Rollback revision restores the previous desired state; uninstall restores the original baseline.
- On an upgrade, retain baseline bytes for existing owned targets, capture newly owned targets once, and restore targets no longer needed. External edits require review and a recovery snapshot; newer overlapping independent layers block revision/uninstall.
- Keep manually imported packages and their existing overlap semantics intact. A pre-existing manual/upstream installation is Unmanaged until explicitly adopted; capture its actual state without labeling it pristine Original.
- Reopening CLI/UI always completes pending recovery before allowing new work. Network access is never needed for rollback.

### Storage/migration

- Introduce catalog/journal schema 3 for bundle revisions, component provenance and typed reversible side effects. Keep snapshot folder layout and existing bytes unchanged.
- Retain original schema-2 catalog metadata; convert atomically under the exclusive lock. Existing snapshot/package/installation IDs, labels, Original flags and relationships survive unchanged.
- Preserve schema 1 -> 2 conversion, then 2 -> 3; explicitly accept legacy journal schemas 1 and 2 for recovery. Resolve old pending transactions before publishing upgraded metadata.
- Add optional recorded file-attribute state for new operations, especially Engine.ini read-only recipes; absence in historical snapshots means legacy behavior, not invented metadata.
- Old executables must reject schema 3 instead of dropping new fields. Coordinate minimum app-version/update checks with #8; its implementation remains a separate issue.

## 4. Profiles and additional options

### Profile editor and precedence

- Create/import/export/clone/rename profiles; choose a default and save per-game overrides.
- Easy editor: output upscaler, quality ratio, FG, spoofing, sharpness, overlays, FPS/menu shortcut, ASI/ReShade/Special K loading.
- Advanced searchable editor: all supported sections/settings of the selected release's actual INI template, with typed values, ranges, descriptions and reset/inherit controls.
- Use Client's schema-driven editor approach and version maps as references. Section+key is the identity: repeated names such as Enabled, Path or DebugView must never collide.
- Schema families cover legacy stable and newer/nightly formats. Unknown/custom releases keep raw INI editing/import and explicit review; disable unsupported convenience controls instead of writing guessed keys.
- Compose in this order: selected release template -> validated game recipe -> default profile -> selected per-game profile -> explicit per-game controls. Mandatory component/schema constraints validate the final result and report conflicts; never silently override a user's explicit choice.
- Distinguish Inherit, OptiScaler Auto, Disabled/None and explicit values. Preserve comments, unknown keys, encoding and line endings where possible; show exact edits. Ambiguous duplicate keys require resolution.
- Live settings changes offer config-only preview/apply and restart guidance. All writes use the same transaction path and update expected installation hashes.

### Rendering and FG controls

- Output: Default, FSR2, FSR3, FSR4, XeSS, DLSS where supported. Do not label an auto FSR fallback as guaranteed FSR4.
- Quality: Game controlled, Native AA, Ultra Quality, Quality, Balanced, Performance, Ultra Performance, custom ratio; show render ratio separately from output scaling and validate using the chosen schema.
- Spoofing: Auto/On/Off plus advanced per-channel controls; coordinated DXGI/Streamline/Vulkan keys only where supported.
- FG route/input: Disabled, Auto, native DLSSG/Streamline, native FSR3/3.1, Nukem, OptiFG and newer native XeFG/Nvngx routes supported by the package schema.
- FG output/provider: Auto, FSR FG, XeFG, DLSSG; advanced Nvngx replacement options when supported.
- MFG: Auto, x2-x6 and dynamic-target settings only when the exact provider/GPU/schema combination supports them. Explain dependency requirements, experimental status and unavailable choices; never universally expose x6 as working.
- Plan Streamline/Nvngx/Nukem/plugin dependencies alongside settings. Keep controls synchronized between Quick, Manage, profiles and bulk planning through one resolver.
- Surface DX12/Vulkan, borderless/HDR, HUDless/HUD-fix, Reflex/latency, game-version and mod conflicts from validated rules. Detection of files alone is not proof of runtime support.

### FSR DLL swaps

- Separate "OptiScaler installation" and "FSR DLL swap only" modes.
- INT8/FP8 selection, custom imported versions, per-effect Upscaler/Loader/FrameGeneration/Denoiser/RadianceCache choices.
- Recognize legacy amd_fidelityfx_upscaler_dx12.dll, amdxcffx64.dll, monolithic amd_fidelityfx_dx12.dll and split SDK layouts. Show source-to-target mappings.
- Validate loader/companion dependencies and renamed targets. Do not install OptiPatcher/Fakenvapi/Nukem implicitly during swap-only mode.
- Every replacement is an owned, reversible package operation.

## 5. External settings and experimental modules

Implement after the main file pipeline:

- File-based game/RTSS profiles use explicitly approved external roots, exact path previews and snapshots.
- Extend typed transaction targets for allowed per-user registry values: hive/view/key/value name, value kind/data and explicit prior absence. Journal before/after states; restore only owned values, never delete entire keys. Machine-wide/elevated recipes remain manual instructions.
- Record/restore explicitly changed read-only attributes. Do not change ACLs or permissions to force installation.
- Anti-cheat detection and incompatible-game status are preflight evidence: disable automated injection by default and show source-specific guidance. Do not automatically disable anti-cheat, create Defender exclusions, change drivers or run elevated installers.
- Experimental feature switch defaults off and gates both UI visibility and execution/default selection. Turning it off prevents hidden defaults from installing experimental components.
- RenoDX: per-game upstream Mods data and addon selection; explicit ReShade dependency/conflict handling.
- DLSS Enabler: official download instructions and reviewed local import by default; clearly identify optional community providers. Do not inherit an unofficial mirror as a silent default.
- XeFGUnlock: separate provider/plugin and validated MFG capability rules, installed through the same ASI path/config plan.
- AMD neural rendering + AMD-NR-bridge: support file-based reviewed payloads and version pairing; upstream workflows requiring external GUI installers/elevation remain guided/manual until every side effect can be represented and recovered. No auto-run installer.
- RTX 20/30 DLSSG: pinned commit/files, SHA-256 and expected signer verification where supplied, GPU constraints and collision-aware proxy selection; never a general compatibility guarantee.
- Experimental dependencies must fail before mutation; never leave a reported-success base install with silently failed selected addons.

## 7. Low-effort upstream maintenance

### Goal and boundaries

Keep compatibility, release metadata, recipes and configuration definitions current without repeatedly rebuilding the application. Automate discovery, validation and update proposals; reserve engineering for new capabilities or changed execution semantics.

Maintain three distinct update paths:

| Update class | Mechanism | Initial approval policy |
| --- | --- | --- |
| Compatibility observations and available release versions | At-most-daily app refresh from official sources with last-known-good caching | Automatic read-only refresh; never authorizes new game-file actions by itself |
| Executable aliases, recipes, dependencies, destination/layout rules, settings schemas and version maps | Independently versioned data packs published by our repository | One reviewed maintenance PR before publication |
| Application behavior, new controls, new operation types or upstream feature ideas | Weekly source/release comparison and a concise proposal | Normal implementation PR and application release |

Refreshing data must not change installed mods, saved user choices, active bundle revisions or an already reviewed operation plan. Application self-update remains #8; per-game component update remains an explicit preview/apply operation.

### Data-driven extension boundary

- Represent recipes, component descriptors, aliases, capability constraints, settings schemas, version maps and supported editor control definitions as declarative data with documented schemas. Existing application primitives should handle a newly supported game, known option or known layout through a data change alone.
- Keep execution primitives, path validation, trust policy, registry/file semantics and the journal engine in application code. Data packs cannot contain scripts, assemblies, arbitrary expressions or new executable operation types.
- Use a small allowlisted condition language for GPU/API/version/platform matching; validate it in application code. Unsupported operators, controls, schema families or action types make that pack ineligible instead of being ignored during installation.
- The UI and CLI consume the same loaded pack and resolver. Showing an existing supported INI setting can be a data change; a new interactive control or installation method still needs application code.
- Pin the data-pack revision/hash, provider/source revisions, component releases and generated outputs into each OperationPlan and installation revision. Preserve the manifest/evidence needed to explain and undo historical installs independently of current feeds.

### Publication and app consumption

- Publish immutable data-pack assets and a small stable-channel manifest through this repository's GitHub Releases. Use a separate data release/tag namespace; ensure application updater #8 filters by application assets/tags so data releases never appear as executable updates.
- Pack manifest records format/schema version, data version, minimum app version, supported operation/schema capabilities, source revisions, creation time and payload hashes. Publish notes distinguishing metadata, recipe and schema changes.
- Repository CI validates packs from reviewed source records. Clients accept only the configured project feed over HTTPS, verify expected asset digests, size bounds and supported schemas, and atomically activate the complete pack. Digests establish integrity against fetched metadata, not an independent guarantee against a compromised publishing account.
- Ship an initial validated pack with the app. Keep the current and previous validated packs plus referenced historical manifests locally; retain last-known-good data on offline, invalid, incomplete or incompatible refreshes.
- Display active data version, source age, last successful check and available update details; provide Refresh, pause automatic data updates, and restore previous validated pack. Restoring a pack changes future recommendations only.
- Fetch compatibility/wiki observations directly as described in section 1, but keep **displayed observations** separate from **approved executable recipes**. Fresh wiki prose cannot silently become a destination mapping or an automatic config change.
- Refresh at most daily without blocking startup or backup/restore. Apply compatible packs only when no operation is being planned/applied; a pending reviewed plan continues using its pinned data. New known incompatibility or withdrawal requires a new preview before applying that plan, without silently changing its selections.
- Existing installs and rollback stay usable if the feed disappears. Recipe withdrawals stop new automatic installs and explain why; they do not delete local artifacts, rewrite installations or prevent recovery/uninstall.
- Publish a rollback as a new data release containing the previous validated rules, with release notes and provenance. Keep app and data release channels independent; stable is the default for both.

### Weekly consolidated maintenance workflow

- Add a scheduled weekly GitHub workflow and manual trigger. Track exact last-reviewed revisions in a checked-in source registry; use commit/release IDs and response hashes, not mutable branch names as baselines.
- Monitor official OptiScaler/OptiPatcher releases and support docs, component providers, Client source/release notes/settings schemas/version maps, and available OptiClick source/data/docs.
- Fetch upstream content as input data only; never execute upstream workflows/scripts or automatically merge upstream application code.
- Compare normalized records and settings definitions. Produce one consolidated PR with categorized additions/removals, source/version evidence, digest changes, prerequisites and expected user impact. Update an existing maintenance PR rather than creating one per upstream change.
- Feature/code changes become a short "candidate improvements" section with source links and a proposed follow-up; do not pretend they can be imported automatically. Record the reviewed revision even when no change is adopted, so the same suggestion is not repeated weekly.
- Distinguish "observed" from "reviewed/adopted" source checkpoints. Failed parsing/validation must not advance the adopted checkpoint or discard a pending change.
- Include an explicit source-health report. OptiClick's currently unavailable latest code is a monitoring limitation, not a reason to scrape private services or claim current feature parity. Historical forks stay pinned reference sources unless new public source is verified.
- Use repository-native scheduling and workflow authentication. No hosted backend, new local credentials or paid agent API is required; deterministic diffs are sufficient initially. An optional agent can help summarize a PR later without being required for correctness.
- Workflow permissions stay read-only for source inspection; grant write permission only to the PR/publication job that needs it. No component/game installation is run by the monitoring workflow.

### Validation and staged automation

- All changes initially go through a reviewed PR. On approval, a publication workflow emits the immutable pack and manifest; no application build is required for a data-only release.
- Require schema/allowed-operation validation, source provenance and license inventory, artifact digest checks, release-tag-versus-main support checks, parser regression fixtures, and deterministic plan/config previews for affected known game/GPU/layout combinations.
- Flag unexplained table shrinkage, support-status reversals, changed hashes for existing artifact identities, altered destinations, new providers, changed dependency/conflict rules and newly exposed options for manual review. Do not infer improved compatibility merely from a larger upstream list.
- Add feed tests for partial publication, corrupt/incompatible packs, unknown operations, minimum-app mismatch, interrupted activation, rollback to the previous pack, independent data/app update selection, and pinned plans surviving refresh. Existing installs must retain exact rollback behavior after a pack update.
- Add source-monitor tests for changed upstream formats, missing source/history, rate limiting, duplicate PR suppression, baseline advancement and release-only support attribution.
- Establish four consecutive successful reviewed weekly cycles before enabling any unattended publication. Later opt-in automation is limited to display-only release listings/source timestamps whose artifacts have verified identity/digests and whose layout/schema assumptions have not changed.
- Recipes, executable matches, compatibility gains, dependency changes, file destinations, FG/GPU rules, schemas/new settings, source trust and application code **always require a reviewed PR**. Unattended publication must never expand the set of game-file actions the app may recommend automatically.
- One maintainable source registry, documented parser fixtures and one weekly PR are the intended routine maintenance workload; no promise of zero maintenance or automatic inheritance of unpublished/new functionality.

- **Data:** parser fixtures captured from pinned real upstream documents, main/Luma and escaped-pipe tables, unknown/blank symbols, N/A vs unsupported, renamed games, edition collisions, non-working notes, wiki field aliases, malformed/truncated responses, stale cache, 404/rate limit/offline, and released-vs-main support differences.
