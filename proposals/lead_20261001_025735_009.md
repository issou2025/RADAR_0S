# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Run stages as configurable task chains with deterministic exit gates**

*Project description:*
## Summary

Rebuild how Conveyor runs a stage around **small, named, testable tasks** chained by configuration, so that every stage has one concrete job and one deterministic exit gate. The engine becomes a thin runner: it executes a stage's task lists, saves a shared context, waits when a task says "not yet", and routes the item when a task says "no". Providers (items, code, CI), agent harnesses and the MCP server all plug into the same task shape.

Goals, in order:

1. **Hands-off.** An item moves from refinement to merged (and deployed) without a person unless a genuine product question or a missing permission needs one, and when it stops the reason is explicit.
2. **Reliable.** Gates are code, not AI judgement; the same state always gives the same answer, and every failure says exactly what is missing.
3. **Extensible.** A new issue tracker, code host, CI system or agent harness is a package that registers tasks and providers; the engine core does not change. Conveyor is open source, so this must be easy for contributors.
4. **Simple.** Stages have one job each; configuration is declarative and readable.

This issue records the full design discussion and decisions (2026-09-30). It is a **roll-up parent**: the work is split into the child issues listed under "Breakdown". Refinement should create those children with their own acceptance criteria.

---

## Why: what went wrong on 2026-09-30

Observed on the live board (midgame #155, #157, #161, #193–#195 and this repo's #8–#17):

- **Agents could not see or start CI but criteria demanded hosted CI evidence.** Items blocked with "no successful run for the current SHA" and waited for a person. (Partly fixed since by the engine-owned CI gate, PRs #2–#7 and #16.)
- **`delivery.get_state` was a start-of-run snapshot**, stale as soon as the agent pushed. (Fixed in PR #2: served live over MCP.)
- **AI verifiers (Mitra) judged free-form instructions at every boundary.** Results were non-deterministic, expensive, and failed items for reasons nobody could act on (e.g. "delivery state still reports PR open" right after a merge).
- **Checks ran twice** (review exit and merge entry re-verified the same things) and stages mixed several jobs (the CI stage synced git, pushed, created the PR, triggered workflows and waited).
- **Local environment failures became item failures**: emulator port clashes, tmpfs quota, a read-only SDK cache. (Mitigated by moving full suites to CI.)
- **Missing repository facts went unnoticed**: this repository had no CI at all, so every "passes in PR checks" criterion was unmeetable and the CI gate passed with "no checks". (Fixed by PR #15.)
- **Tool bug**: `source.set_dependencies` is not idempotent — re-adding an existing GitHub dependency fails (HTTP 422, surfaced as 500), which blocked the refinement of #17. See child C0.

## Decisions

### D1 — Providers by role, generic names
- Three provider roles, each chosen per repository by configuration: **items** (issue tracker), **code** (branches, change requests, merge), and **ci**. GitHub is the only implementation for now, but the seams must be real.
- Agent **harnesses** (Codex today; Claude Code, OpenCode, … later) are the same kind of pluggable piece.
- The generic word is **item**, not issue. Repository names in configuration drop the `-v2` suffix; addresses and folders are unchanged.

### D2 — A stage is `actions` followed by an `exit-gate`
- Every stage has exactly two task lists: **`actions`** (do the stage's job) and a non-empty **`exit-gate`** (prove that job is done). Script stages use `script.run` followed by `script.succeeded`; action success is not itself the gate.
- No entrance gates. Conditions required by the next stage belong to the previous exit gate. A direct human relabel may skip that gate, so acts must still validate their own safety preconditions.
- Exit gate open → advance. Exit gate `fail` → run the stage's actions again with `run.feedback`, unless `onFail` routes elsewhere. Exit gate `pending` → park and later re-evaluate the whole gate with fresh loads; actions are not repeated.
- If an **action** returns `pending` (for example an agent asks a question), the durable cursor stays on that task. Completed earlier actions are not repeated. C4 extends the neutral harness contract with an optional `sessionResume` capability and opaque `resumeSessionId` input. After wake-up the engine uses that input only when the selected harness advertises the capability; otherwise the task starts a fresh attempt with the original question and answer in context. Correctness never depends on session resume.

### D3 — Tasks and task instances
- A stage task is `run({ context, config, deps })`; an MCP tool additionally receives validated `input` and `actor`. `context` is shared state, `config` is that task instance's `with` value, and `deps` contains providers, git, clock, store and other injected dependencies.
- Four kinds:
  - **load** — the sole writer of its provider snapshot (`item`, `workspace`, `change`, `ci`); safe to re-run.
  - **check** — a pure function of context returning `pass`, `pending(message, { after? })`, or `fail(message, { details? })`; it performs no I/O and writes no context.
  - **act** — reconciles external state toward a desired result, declares which snapshots it invalidates, and is safe to resume after a crash.
  - **tool** — callable only through an agent's scoped MCP grant and not allowed in stage lists.
- Every configured occurrence has a stable **task-instance ID**. `id` defaults to the task name when that name occurs once in the list and is required for duplicates. Overrides, execution records, script results and idempotency keys address the instance ID, not an array index or task name.
- Before an act mutates anything, the engine persists a `planned` execution record containing `{ item, stage, stageEpoch, attempt, taskInstance, idempotencyKey }`. The act first observes external state, performs only missing work, and reconciles again when the same key is resumed. The journal then records `completed`. This handles a crash between an external side effect and the local commit; a key alone is not considered sufficient idempotency.
- `script.run` must declare `recovery: replay-safe | reconcile`. `replay-safe` is valid only for side-effect-free checks and observations. `reconcile` passes the stable idempotency key to the JSON process and gives it an `observe` phase before `apply`; the process must report `already-applied`, `not-applied`, or `indeterminate`. Recovery records `already-applied` as complete, applies only after `not-applied`, and stops as `needs-intervention` on `indeterminate` instead of blindly repeating an external effect. Deploy scripts with external effects use `reconcile`; local checks, read-only verification and side-effect-free no-op deploys use `replay-safe`. The compiler rejects a `script.run` without this declaration.
- Mutating tools use the same journal/reconciliation contract with an MCP call ID, so a disconnected or retried tool call cannot duplicate a comment, relationship or push.
- Every task declares `reads`, `writes` (loads and engine-captured outputs only), and `invalidates` (acts). The config compiler validates task kinds, dataflow on every conditional path, unique instance IDs and valid routes. It emits the expanded execution plan—including implicit loads—for `check-config` and debugging.
- Tasks do not sleep or poll. Infrastructure exceptions are distinct from domain `fail` results and use the existing bounded infrastructure/usage-limit retry policy.
- Names are `group.camelCase`; implementation and tests live under `src/tasks/<group>.ts` and `tests/tasks/<group>.test.ts` until a group needs a directory.

### D4 — Context, ownership and checkpoints
- One latest context is materialized per item and persisted after every completed task. An append-only execution/event history keeps every stage attempt, task result, transition and context version for debugging. Large logs remain artifacts and only bounded summaries/links enter context.
- Provider snapshots have one writer: their load task. Acts never patch those snapshots; they invalidate them, and the engine reloads before the next reader. `agent` and `script` are engine-captured task outputs. `checkpoints` is engine-owned.
- Context carries `schemaVersion` and `configHash`. A parked item whose schema or compiled plan changes must be migrated or restarted explicitly; it is never resumed against an incompatible plan.
- `run` is rewritten per task and contains a monotonically increasing `stageEpoch`. Every external completion is fenced by that epoch so a late task cannot mutate or advance an item after a pause, relabel or return.
- Load tasks remain implicit. Before a task runs, the engine refreshes each invalid or not-yet-loaded key it reads. The expanded plan makes these loads visible even though YAML does not repeat them.
- When required CI passes, the engine records `checkpoints.ciPassed`. When the complete review gate passes, it atomically records `checkpoints.reviewPassed`. Merge verifies the current head against `reviewPassed.sha` and, when CI is required, `ciPassed.sha`.

### D5 — Engine owns execution, waiting, timing and routing
- The durable cursor records the current list and task instance as `planned`, `running`, `pending` or `completed`. Pending identity, first-pending time, next wake-up and deadline are persisted, so restarts neither reset timeouts nor rerun completed actions.
- `pending` releases runner permits and updates the board status. Provider webhooks may wake it early; otherwise the engine wakes it after `poll`.
- `wait: { timeout, poll }` is common task configuration and can be overridden per repository by task-instance ID. Dependency waiting has no timeout by default; operators may configure one.
- `onFail`: `retry` (exit-gate default, bounded by stage `retries`), `return: <stage>`, or `stop: <state>`. Action failure defaults to `stop: blocked` unless explicitly configured. `settings.maxReturns` bounds cross-stage loops.
- Stage execution posts conversation messages only for failures, routing and stops. The one-time CI start announcement and one final advisory-CI result are explicit engine-owned exceptions. Repeated pending polls update one board status line.

### D6 — MCP is another task transport
- Agent-callable `tool` tasks and read-only getters are exposed by task name. The task registry owns schema, implementation and description; there is no parallel MCP implementation layer.
- `agents.<id>.tasks` is the exact grant. The MCP server and task dispatcher both enforce it and also validate issue, stage, actor and head-SHA preconditions.
- Current snake_case tool names remain aliases during migration. New configuration and documentation use camelCase names.
- Agents receive no GitHub or other source-provider credentials, and outbound network is restricted by each repository's `agentEgress` block to the run-scoped loopback MCP endpoint plus exact HTTPS package-host names needed to build and test. `allowLoopbackMcp` permits only the injected MCP address and port, not arbitrary loopback listeners. DNS results and every redirect are checked against the same list; wildcards, arbitrary CIDRs and provider APIs such as `api.github.com` are forbidden. A missing package host fails closed and is added through reviewed configuration rather than opened dynamically. The allowlist governs the agent's sandbox, meaning every command the agent runs and its child processes. The harness's own connection to its model API (e.g. Codex to OpenAI) is harness configuration, runs outside that sandbox, and is never reachable from agent commands. C9 verifies credential removal, sandbox egress enforcement and this control-plane/data-plane split: a fake harness reaches its model endpoint while a command inside every agent access level cannot reach that same endpoint.

### D7 — CI has explicit operating modes
- Repository CI mode is **`required`**, **`advisory`**, or **`disabled`**—not a boolean:
  - `required`: start CI, require the provider to find an applicable CI definition, and gate on all reported checks for the current head except `ignoreChecks`.
  - `advisory`: start CI and advance immediately after setup, while an engine-owned durable watch reports its eventual result without changing the item's stage or state.
  - `disabled`: omit CI tasks and require no CI provider.
- An advisory watch is keyed by repository, item and full head SHA, persists its original settle/timeout deadline, holds no runner or stage permit, survives restart, and is woken by CI events or polling. It posts the normal start announcement at most once and exactly one final pass, failure or timeout message with available run links and focused logs. A newer head marks the old watch `superseded` and suppresses its final message. Starting the same head again reuses the existing watch. Advisory results are evidence only and never route, stop or reopen the item.
- `ci.defined` is a separate deterministic check. In `required` mode, no applicable workflow/check definition is a configuration/repository failure and stops as `blocked`; it never silently passes. This prevents an accidentally deleted workflow from weakening the gate.
- `ci.passed` handles registration settling, queued/running checks and failures. A red run returns implementation with focused logs. Cancelled-run reruns and label-triggered starts remain provider behavior.
- Provider discovery may inspect workflows, branch/path applicability, Actions availability and configured external checks. Where a provider cannot prove applicability, required mode fails explicitly rather than guessing that CI is absent.

### D8 — Review evidence is SHA-bound; the PR is its projection
- `change.ensure` renders the item's criteria as a managed checklist, but Markdown checkboxes are **not authoritative state**.
- `change.checkCriterion` records `{ criterionId, reviewer, headSha, checkedAt }` in Conveyor and then updates the checklist projection. A new head invalidates prior approvals. `change.criteriaChecked` requires every non-manual criterion to be approved for the current head.
- A review finding is a provider-neutral record. GitHub maps it to an inline review thread when a valid diff position exists and otherwise to a managed PR comment. Every finding has an ID, stable provider key when imported, author, source, head SHA, state and URL.
- `change.load` imports native human review threads and changes-requested reviews into those records. Provider artifact IDs are the deduplication keys; edits update the same record, resolved threads resolve it, and an author-deleted artifact becomes an audited `withdrawn` record rather than disappearing. Ordinary PR conversation comments are not findings. A changes-requested review without an inline thread becomes one top-level finding linked to the review, so human blocking feedback cannot be lost.
- Unresolved human findings block by default. An authorized operator may explicitly dismiss one with a recorded reason; login allowlists do not silently discard review feedback.
- `change.dismissFinding` is not an agent grant. The dashboard/operator API invokes the same task dispatcher with an authenticated human actor, and the dispatcher requires an allowed operator login plus a non-empty reason.
- The reviewer must express every requested change as a finding. A `changes-requested` result with no finding is an invalid agent result and stops the review for correction rather than allowing the gate to pass.
- The complete review gate requires resolved findings, current-head criterion approvals, unchanged required-CI head and mergeability. Passing it records `checkpoints.reviewPassed`; `change.merge` squashes only `reviewPassed.sha`.

### D9 — No AI verifier
- Mitra and `agent.verify` are removed. Deterministic code checks own every gate; judgement remains in the refiner, implementer and reviewer, with its evidence visible as criteria approvals and findings.
- `agent.run` returning `done` never opens a gate by itself. `needs-input` parks the current action and, on the answer, uses C4's optional harness resume input when supported or starts a fresh attempt with the original question and answer; `blocked`/`rejected` stop with the agent's reason; an invalid structured result is an actionable failure.

### D10 — Configuration stays declarative and versioned
- Task entries support `id`, `task`, `with`, `wait`, `onFail`, and `when`. Stages support `id`, `concurrency`, `retries`, `actions`, and `exit-gate`. Repository overrides address `overrides.stages.<stage>.<list>.<task-instance-id>`. Each repository also declares `agentEgress.allowLoopbackMcp` and an exact `agentEgress.httpsHosts` list; these are security inputs, not task expressions.
- Guards are a small validated vocabulary such as `ci.enabled` and `ci.required`, not arbitrary expressions. There are no loops, variables or message templates.
- The reference configuration and agent instructions live in this repository. The live service imports and pins a repository version while retaining machine-local paths/secrets in `~/.config/conveyor-v2`; it does not maintain a copied pipeline.
- Existing configurations continue to load through a compatibility compiler until the canary rollout completes. The compiler translates current `enterCheck`, `exitCheck`, `afterSuccess`, `run.*`, `pullRequest.*`, `ci.await` and top-level labels into a task plan, with golden equivalence tests. It never guesses that an existing process script is replay-safe: legacy process stages stay behind the legacy adapter until C4 gives each reference script an explicit recovery mode and any required `observe` implementation; C8 refuses native-plan migration while one remains unclassified.

### Rejected alternatives (and why)
- **Entrance gates** — duplicate the previous exit gate on the normal path; acts still enforce safety after manual stage changes.
- **A separate CI stage** — waiting for required CI is the last part of implementation.
- **A polling task** — would retain a process and lose timing state on restart.
- **A task idempotency key without reconciliation** — cannot close the crash window after a remote side effect.
- **Untyped shared mutable context** — hides coupling; provider snapshots have load owners and acts invalidate them.
- **PR checkboxes as the approval database** — edits and new commits can make them stale.
- **“No CI found” as success in required mode** — silently weakens delivery when CI is deleted or misconfigured.
- **AI judgement as a stage gate** — non-deterministic and expensive; judgement is recorded by working agents and gates verify structured evidence.

## Review decisions

1. **Implicit loads stay**, and `check-config` displays them in the compiled execution plan.
2. **History is append-only per attempt** while one bounded latest context is materialized for fast reads.
3. A reviewer returning `changes-requested` **without a structured finding is invalid**, not a passing review.
4. **All unresolved human findings block by default**; an authorized operator can dismiss one only with a recorded reason.
5. CI keeps the proposed 3 h default (8 h for midgame) and mergeability keeps 30 m. **Dependency waits have no default timeout**; repositories may set one.
6. Reference configuration and instructions are **versioned in this repository and imported/pinned by live configuration**; local paths and secrets remain machine-local.
7. **Scripts with external effects reconcile before apply**; an indeterminate observation stops rather than risking a duplicate effect.
8. **Advisory CI retains a durable background watch** and reports once without controlling delivery.

## Acceptance criteria (roll-up)

- [ ] Children C0–C9 exist with their own acceptance criteria and dependencies as above.
- [ ] Every stage compiles to `actions` plus a non-empty `exit-gate`; no stage uses an AI verifier.
- [ ] A crash before an act, after its remote side effect, during pending, and after completion resumes without duplicate mutation, lost timeout or stale-stage advancement; deploy-script recovery observes before apply and stops safely when the outcome is indeterminate.
- [ ] Provider snapshots have one load owner; acts invalidate them; checks are pure; `check-config` rejects invalid dataflow and duplicate task-instance IDs.
- [ ] Required CI blocks when no applicable CI is defined; advisory CI advances without gating but its durable watch survives restart, suppresses stale heads and posts exactly one final result; disabled CI performs no CI work.
- [ ] Criterion approvals and review completion are tied to the current head SHA, native human review findings are imported without duplication or silent deletion, and merge refuses any SHA other than `checkpoints.reviewPassed.sha`.
- [ ] A parked agent action resumes only through an advertised harness capability; a harness without it receives a fresh attempt containing the original question and answer, and both paths produce the same durable task outcome.
- [ ] Every agent-callable task is exposed by the registry with server-side grant/context enforcement; agent sandboxes have no source-provider credentials and reach only the run-scoped loopback MCP endpoint and exact HTTPS hosts in their repository's `agentEgress` block (never provider APIs); an isolation test proves the harness can reach its model endpoint outside the sandbox while agent commands cannot reach that endpoint, and repository restore tests start with empty task-scoped package caches.
- [ ] Legacy and task plans pass golden equivalence tests, then one repository completes a shadow/canary delivery before the remaining four migrate.
- [ ] A CI failure, review finding and unresolved human finding each produce an explicit, actionable route; pending polls do not spam the conversation.
- [ ] `docs/tasks.md`, imported reference configuration, agent instructions and rollback documentation match the code.
