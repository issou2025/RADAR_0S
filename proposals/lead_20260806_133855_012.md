## Problem

A working session left `core.bare = true` in the repository's shared `.git/config`. A bare repository cannot have work trees, so this broke the main worktree and three of five linked worktrees at once. Every affected worktree failed every git command that needs a work tree:

```
fatal: this operation must be run in a work tree
```

`git status`, `git diff`, and `git rev-parse --show-toplevel` all failed. Repairing it was a single command, `git config core.bare false`, after which all six worktrees returned to normal immediately.

## Why it is worth a gate rather than a shrug

The failure does not present as a git problem. It presents as several unrelated test and gate failures at once, each of which invites its own wrong diagnosis. In this session it surfaced as four separate symptoms:

- Two pre-PR gate checks failing, "Documented Interpreter Portability" and "Skill Markdown Portability", which look like portability defects.
- A lefthook integration test failing, which looks like a test-isolation defect. I filed an issue for that and had to close it as invalid.
- `git diff` failing inside a worktree, which looks like a corrupt worktree.

Three separate diagnoses were attempted before the shared cause was found. The generalizable lesson is that when several unrelated checks fail simultaneously, a shared substrate is a better first hypothesis than several independent causes, but the tooling gives no signal pointing there.

## Likely mechanism

The repository has `extensions.worktreeConfig = true`:

```
[extensions]
	worktreeConfig = true
```

When that extension is enabled, `core.bare` is worktree-specific and belongs in the main worktree's `config.worktree` file, not in the shared config. A `core.bare` written to the shared config is inherited by every linked worktree, which is exactly the observed blast radius. Any code path that runs `git config core.bare true` without an explicit repository target, while the current directory resolves to this repository, produces this state.

I could not identify the specific writer. No source file in this repository sets `core.bare` directly, so the likely candidates are a test that creates a bare fixture repository and runs a `git config` or `git init --bare` with the wrong target directory, or a tool invoked during a gate.

## Second problem in the same file

`.git/config` is 44648 bytes across 1268 lines, with 422 sections, of which 416 are `[branch ...]` entries. Four are leftover test branches named `wt/t_<hex>` and `wt/push-batch`. Ordinary repository config is a few hundred bytes. Branch sections accumulate and nothing prunes them, so the file grows without bound as worktrees and branches are created by automation.

This is not merely untidy. Every git invocation parses this file, and it is the same file the corruption above landed in, so a large hand-edited-looking config makes such corruption harder to spot by inspection.

## Proposed fix

1. Add a fast repository health check that fails loudly when the repository is in a self-inconsistent state, at minimum `core.bare = true` on a repository that has a work tree or any linked worktree. This is a sub-second check and it would have converted three wrong diagnoses into one correct message.
2. Run it early, before other gates, so its message precedes the confusing downstream failures rather than following them.
3. Find and fix the writer. A test that creates bare fixture repositories should be verified to always target a temporary directory, never an inherited working directory. This repository already has prior work on isolating tests from inherited `GIT_` environment variables; the same isolation reasoning applies to the target of `git config` and `git init` calls.
4. Prune stale `[branch ...]` sections for branches that no longer exist, and remove the `wt/` test leftovers.

## Acceptance criteria

- A check detects `core.bare = true` alongside a present work tree and fails with a message naming the repair command.
- A test asserts the check fires for that state and passes for a healthy repository.
- Fixture-creating tests are shown to write bare repositories only under a temporary path.
- `.git/config` branch-section growth is bounded, or a maintenance path prunes sections for deleted branches.
