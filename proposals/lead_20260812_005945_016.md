# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**739: a PR with unresolved review findings is invisible next to a PR waiting on a human**

*Project description:*
## The gap

739's `readyWaiting` metric (#900, repaired in #1183) names PRs that are **green, clean and stuck in draft** — work that a human has to move. It cannot name the neighbouring population: a PR carrying **unresolved review findings**. Those two look identical in the weekly report, and only one of them is waiting on a human.

Measured on 2026-08-11 (run 149): **#1183 sat with three unresolved `copilot-pull-request-reviewer` threads for ~2.5 hours**, and one of them was a real defect — a transient `pulls.get` failure returned as a definite negative, the same silent-false-negative class the PR itself was written to fix. Nothing in any report said so. The Conductor's run-148 END comment recorded step 3 as *"No CI failures on any open agentic-os PR. No fix issues needed"*, which was true about **checks** and silent about **findings**.

The merge queue does refuse a PR with unresolved threads, so the damage is bounded at merge time. The cost lands earlier: a run that reads only `statusCheckRollup` concludes supervision is finished, and the findings wait for whoever next happens to look.

## Why the existing field cannot answer it

`mergeStateStatus` / `mergeable_state` **conflate the two causes**: a draft reads `BLOCKED` because it is a draft, whether or not anything is unresolved. #1183 read `BLOCKED` with three open threads and `CLEAN` seconds after `gh pr ready` with those same threads resolved — the field moved for the draft reason, not the review reason. So the state that matters is only available from the GraphQL `reviewThreads` connection, which is also the only way to read it at all (`gh pr view --json reviewThreads` is not a field — L?/`CLAUDE.md` § _Review threads are GraphQL-only_).

## Scope — one PR

Extend the existing metric step; do not add a new workflow.

**Files**

- `.github/workflows/739-process-health-metrics.yml` — the `report` job's `github-script` step, `Gather, compute, and post the weekly report`. `getPrWithMergeability` and the `agenticPrs` loop are the neighbourhood to work in.
- `scripts/process-health-metrics-lib.js` — `computeMetrics` / `renderReport`, where the metric object and its Markdown row are built.
- `tests/workflow-logic/test_739_process_health.py` — the module already slices JS out of the workflow YAML and drives it under `node`; follow `_drive_resolver`'s pattern for anything new.

**Behaviour**

1. For each open `agentic-os` PR, read `reviewThreads(first: 50)` and count `isResolved == false`. Paginate or say so — do not let `first: 50` become a silent cap (L173's denominator rule).
2. Add a metric alongside `readyWaiting`, e.g. `unresolvedFindings: { count, prs: [{ number, threads }] }`, and render it as its own row so it cannot be read as part of the backlog number.
3. A PR that is **both** a clean parked draft and carrying unresolved threads must appear in the findings row, not only the parked row — the reader's next action differs.
4. Failure to read threads for a PR must **warn and be excluded explicitly**, matching what #1183 established for unresolvable mergeability: the count is a floor, not a total.

- [ ] A PR whose threads cannot be read emits a `core.warning` naming it and is stated as excluded; the printed count is described as a floor.
