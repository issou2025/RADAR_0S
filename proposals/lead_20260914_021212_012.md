# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**feat(server)!: require the documented API credential on every request**

*Project description:*
## What

Make the API credential that printobserver's reference documentation already promises true of
the server. Today `docs/reference/api-and-clients.md`, `command-surface.md` and
`common-operations.md` say every request to a versioned operation carries the credential the
server was configured with. The CLI (`crates/printobserver/src/config.rs`, `transport.rs`), the
Rust SDK (`crates/printobserver-sdk/src/transport.rs`) and the Python and Node clients already
send one as `Authorization: Bearer <credential>`. But `crates/printobserver-server` requires none
on any route, and `write_client_config` in `crates/printobserver-server/src/server.rs` writes the
generated client configuration with the address alone. The README's real-printer setup
walkthrough (step 5, as PR #31 wrote it) currently reports that disagreement as a gap.

This node owns the following contract, and restates it nowhere else. The three nodes of this
plan build against it as written here: `print-discovery` runs its journeys against this
authenticated server, and the supervision turn that `agent-sign-in` configures reads its
credential out of the client configuration below.

1. **Where the credential comes from.**
   - `config.toml` gains an optional `[api]` table with one key, `credential` (a string). It is
     declared as a new `ConfigField` spelled `api.credential` and added to `ConfigField::ALL`, so
     the server crate's configuration walk covers it.
     - A value that is empty or only whitespace is refused at startup, naming `api.credential`.
     - The value is held in a type whose `Display` and `Debug` both render `<redacted>`, the way
       `SharedSecret` already does.
     - The value is compared in constant time.
   - When `api.credential` is absent, the server uses the file `<state_dir>/api-credential`:
     - If the file does not exist, the server generates a credential before it starts listening.
       The credential is at least 32 bytes from the operating system's cryptographically secure
       random source, encoded as unpadded URL-safe base64 text. The file is created with mode
       `0600`.
     - A later start reuses the file's contents unchanged.
     - A file that exists but is empty, only whitespace or unreadable refuses the start, naming the
       path and never the contents.
   - When `api.credential` is present, it is the credential in force and the file is neither read
     nor written.
   - The file name is one public constant in `printobserver-server`, next to `CLIENT_CONFIG_FILE`.
2. **What the generated client configuration carries.** `<state_dir>/client.toml` is written with
   mode `0600` as a `[client]` table carrying:
   - `server = "http://<the bound address>"`, as today;
   - `credential = "<the credential in force>"`.

   The CLI's existing `config::load` reads exactly those two keys. So the context command a
   supervision turn runs, and an operator using `--config <state_dir>/client.toml`, both
   authenticate without anyone copying a secret by hand.
3. **What the server enforces.**
   - Every request beneath `/v1` whose `Authorization` header is not exactly
     `Bearer <the credential in force>` is answered HTTP `401` before any handler runs.
     - The answer carries the existing `ErrorAnswer` JSON body, under the operations' media type,
       with a `WWW-Authenticate: Bearer` header.
     - Nothing about the credential appears in the answer.
     - No store read or write happens, no printer port is called, and no action is recorded.
   - The Obico ingress (`/obico/webhook`) is unchanged. It is authenticated by
     `ingress.shared_secret` alone. The API credential does not admit a post there, and the shared
     secret does not admit a versioned operation.
4. **What a refused client reports.**
   - The CLI reports a `401` under its existing `Unconfigured` exit status (`4`). Its message names
     where the credential is read from — the `[client]` table's `credential` in the configuration
     file, or `PRINTOBSERVER_CREDENTIAL` — and prints no credential.
   - The Rust, Python and Node clients surface a `401` through the error each already raises for an
     unsuccessful answer.
   - Their own source statements that "this server requires none of its API callers" (for example
     `python/printobserver-sdk/src/printobserver_sdk/_client.py` and
     `npm/printobserver-sdk/src/client.ts`) are corrected.

**Where each fact lives.**
- The configured key is declared once, in `ConfigField`.
- The state-directory file name is one constant, and the server and every test import it.
- The client configuration's keys are the ones `crates/printobserver/src/config.rs` already reads.
  A journey in which the real CLI reads the `client.toml` the real server wrote reconciles the
  writer and the reader.

**The operator on their own user account** can read neither `/etc/printobserver/config.toml` nor
`/var/lib/printobserver`: both belong to the service user and are private. So the documented route
for them is:
1. Read the credential once as root — `/var/lib/printobserver/api-credential`, or the value they
   set as `api.credential`.
2. Supply it together with the address, either through `PRINTOBSERVER_SERVER` and
   `PRINTOBSERVER_CREDENTIAL`, or through a `[client]` table in a file only they can read, named
   with `--config`.

One snag to resolve and prove rather than document around: `config::load` currently treats an
unreadable default configuration file as an error. It skips only a missing one. So a command run
by such a user may be refused before the environment is ever read. Whatever the fix is, the route
the README documents is the route a test drives.

The installer's configuration template (`scripts/install-service.sh`) documents the optional
`[api] credential` in a comment and carries no value. The systemd unit text carries no credential.

Update everything that describes this behaviour:
- `docs/reference/api-and-clients.md` ("How a request is authenticated"), `command-surface.md` and
  `common-operations.md`. Regenerate whatever `just docs-generate` writes rather than editing it by
  hand.
- The README's step 5. It no longer reports the disagreement; it describes the credential in force,
  where it is, and how an operator on their own user account authenticates.
- Where step 7's first read and "Using it" mention configuration, they say that the address and the
  credential are read from configuration or from those two variables.
- Removing the README paragraph that reports the gap also removes its `llmlint: ignore` directive
  and that directive's `suppressions.toml` entry.

Every journey that starts a real server — the CLI's journeys and integration tier, the SDK
integration suites of all three clients, `crates/printobserver/tests/service.rs`, and the
documented-example generator behind `common-operations.md` — authenticates through the routes
above. None of them does so through a test-only switch.

## Why

In the user's words, after reading the rewritten README: "1 is fine but we actually need to
resolve 2-4 to make this usable". The point of printobserver is an AI agent supervising a real
print under bounded control. Today the docs promise an authenticated API that the server does not
enforce, so anything that can reach `listen` can command the printer. The first read a person is
told to make needs an ID nothing tells them. And the agent the whole tool exists to run has no way
to authenticate on the machine beside the printer. The README is now honest about all three, and
honest documentation of an unusable path is not the goal. This node closes the first of those
gaps: a supervisor that commands a physical machine must refuse a caller who cannot prove it was
given access.

## Acceptance criteria

- A server built from the finished tree answers every versioned operation beneath `/v1` with HTTP
  `401`, carrying the `ErrorAnswer` body and a `WWW-Authenticate: Bearer` header, when the request
  has no `Authorization` header, a malformed one, or a wrong credential. Such a request reads or
  writes nothing in the store, calls no printer port, and records no action.
- A request carrying `Authorization: Bearer <credential in force>` is served exactly as it was
  before this change.
- No configuration value, environment variable or build feature lets a server built from the tree
  serve a versioned operation without the credential.
- The Obico ingress admits a post by `ingress.shared_secret` alone. The API credential does not
  admit a post there, and the shared secret does not admit a versioned operation.
- `api.credential` is a declared configuration field:
  - covered by the server crate's configuration walk;
  - refused at startup, naming the field, when it is empty or consists only of whitespace, or
    contains a control character or a byte outside printable ASCII;
  - when present, it is the credential in force: the server neither reads nor writes
    `<state_dir>/api-credential` in that case, and a test proves a stale file there is ignored and
    left untouched;
  - the server compares a presented credential to the one in force with a constant-time comparison
    (a `subtle`-style `ct_eq` over the bytes, after a length check that itself leaks nothing but
    the length), and no other comparison of the credential exists in the server crate;
  - the value is absent from every rendering the server produces of its configuration or state —
    its startup line, its startup refusals, its `Debug`/`Display` implementations, and its error
    bodies — with the one bounded exception of `<state_dir>/client.toml`, which exists to carry it
    and is written at mode `0600`.
- With no `api.credential` configured, a first start writes `<state_dir>/api-credential` with mode
  `0600` before listening, holding at least 32 bytes drawn from the operating system's
  cryptographically secure random source (`getrandom` / `rand::rngs::OsRng` or equivalent — never a
  seeded or non-cryptographic generator) encoded as unpadded URL-safe base64. A second start over
  the same state directory uses the same credential and rewrites nothing. A file that is present
  but empty, whitespace-only, or not valid under the character rule above, or that cannot be read,
  refuses the start naming the path and never its contents, and is never replaced or overwritten by
  the server. Each of those states is driven by a test through a real server start.
- `<state_dir>/client.toml` is written with mode `0600`. Its `[client]` table carries both the
  bound address and the credential in force.
- In `crates/printobserver/tests/service.rs`, a server started by the installed unit's own start
  command is read successfully by the real `printobserver` binary given only
  `--config <state_dir>/client.toml`.
- The CLI reports a `401` under its `Unconfigured` exit status, with a message naming the
  configuration file's `[client] credential` and `PRINTOBSERVER_CREDENTIAL` as where the credential
  is read from.
- An operator on their own user account authenticates by the route the README documents, and a
  test drives the real binary through exactly that route. That route never reads the service's
  configuration file or state directory, and an unreadable default configuration file does not
  stop it.
- The credential in force is never disclosed by the server or the CLI: the full credential string
  does not appear in the server's standard output or standard error (its startup line and every
  startup refusal included), in any CLI output, in the systemd unit or configuration template the
  installer writes, or in any committed file. The CLI's existing redaction journey
  (`crates/printobserver/tests/journeys/redaction.rs`) is extended to the server command under a
  generated credential of the shipped length and alphabet, and to the CLI under a configured
  credential the test chooses so that it cannot occur in ordinary output, and proves the full
  string is absent from every stream and file above while the messages those streams are required
  to carry are still present.
- Every behaviour above is proven end to end, by tests that start a real server and drive it
  through a real client — the `printobserver` binary, and each of the Rust, Python and Node
  clients' integration journeys — with nothing in place of the server's HTTP boundary.
- These are all green over the finished tree:
  - the test suites of every crate and client this change touches;
  - the repository's own deterministic repository checks, which cover the generated reference documents, the install-path and
    service-install rules, and the suppressions ledger.
- The installer still enables and starts nothing, and the systemd unit it writes carries no
  credential.
- These documents are true of the finished tree:
  - `docs/reference/api-and-clients.md`, `docs/reference/command-surface.md` and
    `docs/reference/common-operations.md`;
  - the README's setup step 5, which describes the working credential path — where the credential
    comes from, where it is written, and how an operator on the host and one on their own user
    account authenticate — and no longer states that the server requires no credential or
    disagrees with the reference pages;
  - every other README statement about how a client finds and authenticates to the server.
- Every site-scoped suppression directive this change writes has its `suppressions.toml` entry —
  rule, file, site and a non-empty reason — in the same change. Every directive this change removes
  has its entry removed with it.
- Every finding of the judged lint over this change's own diff (run against the change's base) is either fixed, or answered by a site-scoped suppression carrying a substantive
  reason and its ledger entry.
- Nothing in the change selects the real-printer smoke test or the scheduled Obico tier from any
  ordinary test or gate target.
- Every claim the dispatch makes about the finished work — what it verified, and the evidence

you touched, the lint that reads your diff — and nothing wider. The repository's own
automation runs the full bar downstream on the change this work becomes: a `pre-push`
hook where that repository publishes locally, the host's required checks where it

anyway. That is measured rather than estimated: one node in this workstream spent about

**Pick those checks from your change, and take the narrowest scope each one supports.**
One test module over the whole suite; the lint over your diff over the lint over the
tree. A repository's own fast deterministic tier is a fine choice when it is what
exercises your change — its `just --list` says which recipe that is — and a poor one when
you reached for it because it was the widest thing available. When a check you ran
reports something, fix that and run **that check** again; nothing here asks you to re-run
its neighbours to confirm, and a wider tier cannot re-check a finding it never made.

**A dispatch that changed nothing tracked owes none of them.** When your deliverable is a
document, a report, or an answer, there is no changed code for those checks to exercise
and you are complete without them — decide that from what the repository shows, never
because running them is slow or inconvenient. `git status` reporting nothing to commit is
then a correct and complete outcome, not a problem to solve by writing a file nobody
asked for.

**Never signal a process you did not identify by PID, and a PID you got from a pattern is
still a pattern kill.** Several managers share this host, and their dispatches, drivers,
publications and test servers run under the same few binary names — `just`, `node`,
`python`, `onepipeline-api` — so a kill by name knows nothing about *whose* work it
matched. The distinction is the tool rather than the pattern: `pgrep` and `ps` **read**,
and either spelling of them is fine, `pgrep -x` included; `pkill` **signals**, and it is
never the answer here, in any spelling. `-x` is the trap, because it reads as the careful
one — `pkill -f 'just gate'` at least needs a narrowing pattern, while `pkill -x just`
takes every `just` on the machine. Reading the table first and piping the pids into `kill`
is no way around it: that is the same pattern kill with more steps.

Two workers reached that place from different directions on 2026-08-24, while another
manager's dispatch had been live over an hour. One ran `pkill -TERM -x just`. The other
ran `ps -eo pid,args | grep 'onepipeline-api serve' | awk '{print $1}' | while read pid;
do kill "$pid"; done` — which obeys the letter of every paragraph below and does the same
damage, because `just dag-ui` and the e2e suites both spawn that server and a pytest run's
were alive at that moment.

**The one process you may signal is one you started yourself, so capture its PID as you
start it:**

    cmd & MYPID=$!
    kill "$MYPID"

Anything you did not start belongs to somebody. Read what it is, report what you found,
and leave it running.

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or
`publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

That has wedged four workers here, and then two more workers and the manager itself in one
night: seven instances of one defect. A crozier corpus audit waited in `until ! pgrep -f
'scripts/fetch-corpus.sh'` with no fetch running at all — the only two matches were its own
polling shell and the manager's diagnostic shell — and waited until it was interrupted. A
`check-plan-bar-conflict` dispatch waited on `! pgrep -f "llmlint-judge.sh"`, whose negation
could never become true, and was cancelled and killed; its replacement then reached for
`pkill -f` against three patterns, which is not a wait at all but the same self-match with a
signal attached, and is refused above. And the manager, an hour after instructing a worker
about this, guarded a launch with `pgrep -f "publish-branch" && echo ABORT || launch`, whose
pattern was a literal substring of the launching shell's own command line: it aborted
unconditionally and then reported a publish as RUNNING that did not exist. That last one is
the evidence that matters most — a rule its own author reproduces an hour after issuing it
is a rule whose wording is the problem rather than its reader.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.

**To ask whether a process is running at all, match the executable, not the command line.**
`pgrep -x onepipeline` matches process *names* exactly — the binary, not its arguments — so
the shell doing the asking, whose own name is `bash`, cannot match it however the pattern
is spelled. Where the binary name is not distinctive enough to identify what you mean
(`just`, `node` and `python` run everything), read the process table instead and drop the
one self-match that form has:

    ps -eo pid,args | grep -v grep | grep 'lint-llm-diff'

Both of those are **reads**, which is what makes `-x` safe here and forbidden the moment
the tool signals. The replacement for the worker wedged above reached for `pkill -f "just
gate"`, `pkill -f "just check"` and `pkill -f "nx run"` while another manager's run was
live. Read to learn what is running, report what you found, and signal nothing you did not
start.

**One sentinel and one log per invocation, and look before you launch one.** That pair is a
shape rather than two literal paths. Several dispatches run on this host at once and they
share `/tmp`, so a second worker writing `/tmp/check.log` writes into the first one's — and
`until [ -f /tmp/check.exit ]` returns immediately on somebody else's exit file, reporting
their result as yours. Name both after the invocation (`/tmp/check.$$.log`, or the node
id), and, before starting it, check whether its sentinel path is already in use by another
invocation; if so, choose a different invocation-specific pair. This path-ownership check
does not prohibit concurrent checks or judged tiers. Three workers collided on shared names
today and not one of the three failures read as what it was: two
deterministic-tier runs deadlocked against the same cargo target-directory lock, so both
logs sat unchanged and neither progressed — about fifteen minutes lost and three
interruptions to a live turn; two whole-e2e runs wrote to one log, and stopping the
duplicate left four `SIGTERM` entries in it that read exactly like real test failures; two
judged-tier runs raced and wasted a roll, which was harmless only by luck. Read a log that
has stopped growing as two commands blocking each other before you read it as one command
working.
