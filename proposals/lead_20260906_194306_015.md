## Summary

`issue-to-prd`'s stage-00 automation guard enforces owner opt-out **by label only**. It is blind to
an opt-out written in the issue **body** — which is exactly where owners write. Proven live today
on [fellowship-dev/pylot#3403](https://github.com/fellowship-dev/pylot/issues/3403).

## Evidence

`skills/ops/issue-to-prd/stages/00-automation-guard/CONTEXT.md:34` fetches **state and labels only**:

```bash
GUARD=$(gh issue view {number} --repo {repo} --json state,labels \
  -q '"\(.state) \([.labels[].name]|sort|join(","))"')
```

and line 39 instructs: *"do not run stages 01-07, **do not read the body**, do not write anything."*
The three abort conditions are `no-automation`, `epic`, and not-open. There is no body check.

**Live miss (pylot#3403):** owner-filed 2026-09-06T17:47:02Z with `bug` + `P1` and this line in the
body:

> `**OWNER-OWNED: do not dispatch.** Fix PR is being produced directly by the owner session (Max/Fry, 2026-09-06).`

The guard saw `bug,P1`, returned `proceed`, and `challenge-new-issue` spent a mission **51 seconds
after filing** (job `1788716825-…-3403-…-098bee`). The refusal that stopped it was an operator
reading the body by hand — not the guard.

**Counterfactual cost.** Per `SKILL.md`, the PRD path rewrites the issue body and applies
`prd-ready` (+ `ready-to-work`). #3403 already carries `P1`. Completing the skill would have:

1. **deleted the OWNER-OWNED directive** and the issue's cited evidence, by body rewrite — the
   literal #2834 failure this guard was built to stop, reached through a different door; and
2. produced `prd-ready` + `ready-to-work` + `P1` — the exact dispatchable triple — so the next
   auto-pylot cycle (every 2h, ~$11-15) would have dispatched a competing mission against a fix the
   owner was hand-writing.

**The convention has zero enforcement surface.** `OWNER-OWNED` appears in exactly **one** issue in
`fellowship-dev/pylot` — #3403 itself. No skill, guard, or automation reads the token. Prose in a
body is not a mechanism.

## Why this is the same bug as the issue that exposed it

pylot#3403 is about `report_integrity`: a truth detector shipped in #3076 that **has never fired in

## Deliverable

**An owner opt-out stops the machinery regardless of how it was expressed.** Both halves, because
either alone still leaves a dark path:

- **Guard (backstop):** add `body` to the stage-00 fetch and abort on an owner opt-out token. The
  guard already runs `gh issue view`; this is one field and one match. Reading the body read-only
  costs nothing — the harm stage 00 prevents is *writing*, and the current "do not read the body"
  wording is what forecloses the check. Canonicalize the token (`no-automation` in prose form is
  ambiguous; pick one spelling) and document it in the pylot playbook's *Issue-filing conventions*
  alongside the existing `no-automation` / `epic` rules.
- **Filer (root cause):** whatever emits an OWNER-OWNED directive must apply the `no-automation`
  label in the same call. A directive that is only prose is decoration.

## Acceptance criteria

- [ ] Stage 00 aborts with `status=success` on a body-level owner opt-out, with no GH writes.
- [ ] A test that makes the guard **FIRE**: a fixture issue carrying the opt-out token in the body
      and no guard label asserts verdict `abort` — mirroring #3403's own "shipped-but-dark is the
      failure mode this issue exists to kill" bar. A test that only asserts the existing
      label-path abort does not close this.
- [ ] The token's canonical spelling is documented in the pylot playbook's Issue-filing conventions.
- [ ] The filing path applies `no-automation` when it emits an owner-opt-out directive.
