A controlled convention beta needs self-service account access, onboarding, and convention participation.

A new player can access an account, complete a TailTag profile, join a convention, and return later without developer assistance.
Include email, Google, Apple, and passkeys on capable devices across Android and iOS.

## Account access

### Shared rules

The account screen offers email, Google, Apple, and passkey access.
Successful access requires a complete, active Clerk session.
A provider callback, verified email, or dismissed native sheet alone does not prove success.

Clerk remains the authentication authority and owns identity linking.
TailTag never links accounts from matching email text, merges accounts, or invents a second identity mapping.
Provider paths that require further verification must complete the Clerk-supported flow before the app enters TailTag.
The app must preserve the same TailTag identity when Clerk resolves different access methods to the same Clerk account.

The app supports one account-access attempt at a time.
Cancellation returns to the account screen without a failure banner or a TailTag write.
Network and provider failures offer a clear retry action.
Provider refusals and incomplete challenges never trigger automatic account creation through another method.

The app uses the existing native SDK boundary, token transport, and secure session storage.
Product features receive no Clerk types, OAuth tokens, credential secrets, or platform channel types.
An OAuth flow is a provider-controlled sign-in exchange.
The capability issue must freeze its supported callbacks and cancellation behavior before implementation.

### Email

Players explicitly choose sign-in or account creation.
The flow collects an email address, sends a verification code, and accepts the code.
Players can resend a code or change their email while no request is pending.
Sending and submitting controls prevent duplicate concurrent requests.
Resending requires an explicit tap and respects provider limits.

Incorrect or expired codes keep the email and allow another attempt.
The app never stores email codes after the attempt ends.
Mailbox access provides recovery for the email-code path. This milestone adds no password reset flow.
An existing account during registration leads to a safe sign-in choice through the supported Clerk flow.

### Google and Apple

Both providers must support account creation and returning sign-in on both target platforms.
The native SDK owns provider exchange, callback processing, and session activation.
The app handles user cancellation, unavailable provider services, and incomplete verification without entering the game.

Apple's private relay email must not become a separate TailTag account-linking rule.
The app does not require another email address merely because Apple hides the player's address.
Missing display-name data leads to TailTag onboarding rather than blocking account access.

### Passkeys

A passkey is an account credential managed by the platform.
Passkeys must support returning sign-in and authenticated enrollment on supported devices.
The minimal account-access screen lets signed-in players list and remove their own passkeys.
It does not expose general provider linking, account deletion, or other profile editing.

The player can skip passkey enrollment and continue to convention participation.
Passkey setup requires a fresh, supported Clerk authorization step when the provider requires one.
Cancellation leaves the existing session and credential list unchanged.
After adding or removing a passkey, the app reads the current credential list from Clerk.
It reports success only after the provider acknowledges the operation.

The app must retain another usable, verified access method before allowing removal of the last passkey.
Verified email-code access or a linked Google or Apple method can qualify when Clerk establishes that it is usable.
The rule does not require a separate email-code method for every player.
The implementation must prove this condition through provider state rather than infer it from a displayed email address.
TailTag keeps Android API 26+ and iOS 17+ as its minimum OS versions.
The same app build enables passkey creation and sign-in on capable devices.
The app uses supported capability detection and handles platform refusal safely.
If passkeys are unavailable, the app explains the limitation and offers email, Google, and Apple access.
Unsupported native SDK capability blocks the passkey issue until the owner approves a supported approach.
The implementation must not silently omit Android passkeys, add a web credential implementation, or raise a platform floor.

### Capability gate

Current official documentation describes email registration, native Google access, and native Apple access on iOS.
It also describes hosted browser access on Android and passkey flows on both platforms.
These examples do not prove the exact APIs in TailTag's pinned versions.

The [October 29 passkey announcement](https://clerk.com/changelog/2026-10-29-passkey-second-factor) gives SDK minimums for second-factor support only.
It does not establish enrollment or primary passkey sign-in at the current pins.
The [Android passkey guide](https://clerk.com/docs/reference/android/passkeys) requires Android API 28 or later.
TailTag retains API 26 support, so API 26 and 27 need another account-access method.

The [iOS Apple guide](https://clerk.com/docs/ios/guides/configure/auth-strategies/sign-in-with-apple) describes native Apple access.
The [Android hosted-auth guide](https://clerk.com/docs/android/guides/account-portal/hosted-auth) describes browser return to the native SDK.
The prerequisite issue must make sure that this route meets the accepted native-auth architecture before selecting it for Android Apple access.
It must not assume that hosted browser access and the existing headless bridge are interchangeable.

Use the [Google guide](https://clerk.com/docs/android/guides/configure/auth-strategies/sign-in-with-google) for Android provider setup.
Use Clerk's [account-linking rules](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking) for identity challenges.
These sources establish research inputs, not completed integration or permission to change provider configuration.

Before auth implementation, record supported behavior for each method on each pinned native SDK.
Record required dashboard configuration, callback URLs, app identifiers, signing entitlements, and domain association files.
Record any required SDK upgrade with its compatibility and rollback implications.
Unknown provider support is a blocker, not an implementation assumption.

The prerequisite issue must freeze TailTag-owned method contracts and sanitized failure categories for tests and implementation.
Only named categories needed by these flows can extend `AuthFailure`.
Native error messages, email addresses, codes, and credential data must not enter logs or bridge error details.

## Application entry and routing

The app owns one entry coordinator, which selects the current route from authoritative session and product state.
The coordinator uses Riverpod and `go_router` through the existing composition pattern.

| State | Visible result | Allowed actions |
| --- | --- | --- |
| SDK restoring | Loading state | Wait. No protected content. |
| Native SDK failed to start or lost its state stream | Auth-recovery state | Retry session loading through the auth boundary. No protected content. |
| Signed out | Account-access screen | Sign in or create an account. |
| Signed in, identity or profile loading | Loading state | Sign out. |
| Identity or profile read failed | Error state | Retry the read or sign out. |
| Profile disabled | Account-unavailable state | Refresh status or sign out. |
| Profile incomplete and enabled | Onboarding form | Submit handle and display name, or sign out. |
| Profile complete, convention state loading | Loading state | Sign out. |
| No selected convention | Convention picker | Join or select a convention. |
| Selected convention active | Convention home | Refresh, change convention, manage passkeys, or sign out. |
| Selected convention paused, completed, cancelled, or otherwise inactive | Convention home with unavailable status | Refresh or choose another convention. |

`AuthFailed` is distinct from signed out and from a TailTag API failure.
Its recovery uses the approved auth boundary rather than concrete SDK calls from the screen.
Retry must not erase secure session storage or report a new session before restoration succeeds.
Unsupported platforms show their limitation instead of an endless retry.

The account-access controls are an auth-only route available from every signed-in entry screen.
This includes onboarding, the picker, home, product-read errors, and the disabled-profile screen.
The route requires an active Clerk session but no completed profile or convention selection.
It never grants product participation or bypasses server eligibility.
Closing the route recomputes the correct entry stage rather than restoring a stale protected screen.

Route names and exact copy are implementation details unless this spec quotes a required action label.
Back navigation cannot expose protected routes while signed out, disabled, or incomplete.
Route transitions replace entry stages so Back cannot reopen a completed onboarding form.
The app never selects a convention automatically because only one option exists.

On foreground return, the app reloads profile eligibility and the selected convention before treating participation state as current.
This milestone adds no polling timer or background refresh worker.

When sign-out starts, the app hides protected content, cancels pending work, and invalidates player-scoped state.
If sign-out fails, the app offers retry. Returning to protected content requires a fresh bootstrap of the still-active session.
After successful sign-out, Back cannot restore the old player's content.
Late responses from a previous session cannot populate a new session or change its route.
Unsaved forms and account-access attempts remain in memory only and clear when their session ends.

## TailTag profile onboarding

After Clerk access, the app calls `GET /api/me/` and then `GET /api/profile/`.
`/api/me/` supplies the TailTag identity. It does not supply profile or onboarding state.
The app uses `onboarding_complete` and `is_enabled` from the profile response.

The form contains Handle and Display name fields and one continue action.
It submits both values through `PUT /api/profile/`.
The backend owns normalization, uniqueness, reserved handles, eligibility, and onboarding completion.
The client can reject empty fields but must not invent stricter name or handle rules.

The app displays server field errors next to the matching field.
It retains the entered values after validation or connectivity failures in the current session.
It does not report completion or enable convention writes until the server reports `onboarding_complete: true`.
An existing completed profile skips onboarding without another `PUT`.

If a profile write times out, Retry first reads the current profile.
If onboarding is complete, the app accepts the saved server state.
If onboarding is incomplete, the player can resubmit the retained fields.
This avoids replacing a completed profile from another device with a stale local form.

Avatar state remains untouched. The player does not need a camera permission or a photo library permission.

## Convention participation and home

The picker reads available conventions, the player's enrollments, and the selected convention.
Available conventions come from `GET /api/conventions/`, which currently returns an array of active conventions.
The app preserves server ordering and treats start and end dates as calendar dates.
It does not apply timezone conversion to those dates.

The app combines convention IDs with owner-scoped enrollments to distinguish new, joined, and selected entries.
It does not infer enrollment from a convention listing.
If no conventions are available, the picker shows an empty state with Refresh and Sign out.

For a new enrollment, the explicit action label is "Join and enter".
The app sends `POST /api/conventions/enrollments/` with `convention_id` and `set_active: true`.
Both `201` and the retry-safe `200` mean successful enrollment.
For an existing enrollment, "Enter convention" sends `PUT /api/conventions/active/` with `convention_id`.
Enrollment and selection require the player to be enabled and onboarded.

Successful entry shows a home containing the convention name, dates, current status, and change-convention action.
The home also provides account-access controls for passkeys and sign-out.
It shows no fabricated catch count and no inactive scan, collection, or fursuit buttons.
Later milestones add those capabilities when they work.

Changing convention returns to the picker and leaves the current selection intact until another selection succeeds.
Switching conventions preserves earlier enrollments.
This milestone adds no unenroll or clear-selection action.

Convention lifecycle changes do not erase enrollment or active selection on the server.
If the selected convention becomes inactive, the app shows its real status and offers another selection.
It does not silently clear the selection, select another convention, or claim that the convention remains playable.

## API surface

| Operation | Request or response contract |
| --- | --- |
| `GET /api/me/` | TailTag-owned user ID. |
| `GET /api/profile/` | `handle`, `display_name`, `avatar_url`, `onboarding_complete`, `is_enabled`. |
| `PUT /api/profile/` | Both `handle` and `display_name`. Returns the complete profile. |
| `GET /api/conventions/` | Array of currently active conventions. No pagination envelope. |
| `GET /api/conventions/enrollments/` | Array of the current player's durable enrollments. |
| `POST /api/conventions/enrollments/` | `{convention_id, set_active: true}`. Returns an enrollment. |
| `GET /api/conventions/active/` | `{enrollment: ...}` or `{enrollment: null}`. |
| `PUT /api/conventions/active/` | `{convention_id}`. Returns `{enrollment: ...}`. |

The existing [OpenAPI snapshot](https://github.com/TailTag-Game/tailtag/blob/main/services/api/openapi/schema.yaml) defines exact wire shapes.
No TailTag backend migration or product API change is expected.
Clerk account and credential operations stay inside the auth boundary.

## Failure and recovery contract

| Condition | Required behavior |
| --- | --- |
| Connectivity failure, timeout, or server failure on a read | Distinguish failure from an empty result. Offer an explicit retry. |
| Profile `400` | Show matching field errors. Preserve the form. Do not navigate forward. |
| Convention `400` or `404` | Explain that entry failed. Refresh convention state and keep the previous confirmed selection. |
| Any product `403` | Reload profile eligibility. Distinguish disabled, incomplete, and otherwise denied state. Never assume every `403` means disabled. |
| Product `401` while Clerk appears signed in | Recheck the native session once. If still active, show an API-access error with Retry and Sign out. |
| Native session ended | Clear player state and return to account access. |
| Mutation response lost | Show an unknown outcome. Retry reads authoritative state before another write. |
| Enrollment or selection read proves the target selected | Accept that state and enter its home without another write. |
| Read after an ambiguous enrollment proves enrollment but not selection | Offer explicit entry through the selection operation. Do not report full success. |
| Read cannot resolve an ambiguous write | Keep the outcome unknown. Do not display success or silently repeat the write. |
| User taps a pending action twice | Send one in-flight operation for that action. |
| Account changes during a request | Cancel and ignore stale work. Never show the previous player's data. |

The app never automatically retries authentication or product mutations.
Cancellation during navigation does not show a generic failure banner.
Error UI uses existing shared feedback patterns and contains no raw provider details or token data.
