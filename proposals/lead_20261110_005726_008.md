### Project Summary

zec_wallet lets any Flutter app send and receive shielded ZEC as an ordinary package dependency, with the keys kept in a Rust core built on librustzcash, and it shipped NU7 support before mainnet activated the upgrade. An optional drop-in wallet UI, native screen protection and Tor come with it, all published on pub.dev and crates.io.

### Project Description

Before this work, a Flutter developer who wanted shielded ZEC in their app had nothing to depend on. The Flutter Zcash wallets that exist are apps, not libraries, so the next team starts from zero (discussed in the [forum thread](https://forum.zcashcommunity.com/t/a-flutter-sdk-for-zcash-ffi-over-librustzcash-with-a-drop-in-shielded-wallet-ui/56639)). zec_wallet closes that gap. A shop app, a messenger or a game can add one dependency and take or send private payments without becoming a wallet team.

What is published, under the verified pub.dev publisher relim.io:

- **zec_wallet**: the SDK. Create or restore a wallet (BIP39), sync over lightwalletd/Zaino, shielded send and receive (Orchard and Sapling), ZIP-321 payment URIs, ZIP-302 memos, ZIP-320 (TEX) two-step sends, an offline send queue, shielding of transparent funds, history, watch-only wallets through UFVK export and import (ZIP-316; asked for in the forum thread and shipped), swaps behind a pluggable provider port (NEAR Intents as the reference), and a C contract through which a host plugs in its own transport. Releases: 0.0.1 and 0.0.2 (8 October), 0.0.4 (23 October, a security release of the TLS stack), 0.0.5 (31 October, NU7) and 0.0.6 (1 November, Android builds on Gradle 9, which Flutter 3.44 sets up for new apps).
- **zec_wallet_ui** (0.0.1, 0.0.3, 0.0.4): a complete wallet UI that mounts under the host's router: onboarding, backup and restore, send, receive, history, shielding and swaps, themed by the host, in 16 languages.
- **zec_wallet_ui_platform** (0.0.1, 0.0.3): native screen protection for that UI (Android FLAG_SECURE, the iOS app-switcher cover and backup exclusion), with no native code in the host app.
- **zec_wallet_tor** (0.0.1, 0.0.3, 0.0.4, 0.0.5): optional Tor. An app that does not add it carries no Tor code.

And on crates.io, **dialer-tor** (0.1.0 on 3 October, 0.1.1 on 8 October, 0.1.3 on 23 October): the Tor client on its own, usable by any Rust app. Since 0.1.1 each Tor client gets a runtime of its own and shuts down within a budget, so switching Tor off really stops it.

NU7 was the largest piece after the first release. 0.0.5 shipped on 31 October, six days before mainnet activated NU7 at block 3,543,405. It builds the new version 6 transactions and follows ZIP 218's limits. It pauses sending in the last 20 blocks before an activation, so no payment is signed for the wrong branch. It reports payments the upgrade cancelled, returns their funds, and counts confirmations for the faster blocks. On 9 November a funded wallet on an Android phone sent itself a payment on NU7's branch; it confirmed within 2 minutes and arrived.

The status is stated plainly in the READMEs: pre-release and not yet externally audited; the Rust core compiles from source, so a Rust toolchain is needed; wallets run on Android, iOS and macOS. One known issue, a light server lowering recorded subtree heights after a rewind, is tracked publicly as [issue #1](https://github.com/alvorado-lab/zec-wallet/issues/1): the server cannot take funds, and until it is fixed the README advises small amounts and a trusted server.

### Technical Approach (how you did it)

- **Audited code used as-is.** The core is Rust over `zcash_client_backend` and `zcash_client_sqlite`, with `sapling-crypto` and `orchard` unchanged, so consensus and proof code is never reimplemented. Dart talks to it through flutter_rust_bridge; Cargokit builds the native library inside `flutter build`.
- **Keys never enter Dart.** Seeds and spending keys stay in Rust; Dart sees addresses, balances, statuses and typed errors with stable codes. CI policy tests enforce the two allowed crossings (the recovery words for backup and restore, and the viewing key for watch-only).
- **Custody.** The seed is sealed with XChaCha20-Poly1305 under a key held by the OS key store (Android Keystore/StrongBox, iOS Secure Enclave); the wallet database is SQLCipher.
- **Transport.** The wallet dials its server through a host-supplied transport or the optional Tor plugin, and the UI reports the real transport state.
- **Network upgrades.** The SDK checks the branch the server reports before it signs, so a build that does not know an upgrade refuses instead of signing transactions the network would reject. Confirmation depth follows NU7's 25-second blocks from the activation height; a few time estimates still assume 75 seconds and can read up to three times too long, as the changelog says.
- **Process.** Spec first, then code; every money-path change reviewed from several angles; guard tests checked against deliberately planted bugs; money paths proven on mainnet with real ZEC on Android and iOS devices before release; advisories checked against a freshly fetched RustSec database before each publish.

- The public CI is green on the current release; on the 0.0.6 release commit it ran 2,622 Rust tests and 2,420 Dart tests.
- NU7 support was on pub.dev six days before NU7 activated; after the activation, a mainnet payment made with it confirmed within 2 minutes.
- Mainnet proof with real ZEC on Android and iOS: shielded sends including ZIP-320 two-step sends, a force-kill in the middle of a send that recovered to exactly one transaction pair on chain, the offline queue, a recovery sweep of funds sent to already-used ephemeral addresses, and an in-place upgrade of a funded wallet from 0.0.4 to 0.0.5 that kept its balance and history. Total losses: transaction fees.
- Two consumers today: the Relim messenger it grew out of, whose tester builds run on 0.0.5 and 0.0.6, and the reference example app. The Relim app also adopted dialer-tor 0.1.1 independently: its probe counted 0 Tor connection attempts after switching Tor off, against 6 to 16 without the fix.
