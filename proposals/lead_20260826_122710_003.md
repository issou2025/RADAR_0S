# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**SkipGenerated/SkipType don't protect <PrivateImplementationDetails> at all — container and nested types both renamed (2.2.50)**

*Project description:*
## Expected behavior

Tell us what you expected to happen.

I expected this: with `SkipGenerated="true"` set (and, redundantly, an explicit `<SkipType rx="^&lt;PrivateImplementationDetails&gt;(/.*)?$" skipStringHiding="true" />` targeting the exact same hierarchy), Obfuscar should not rename the compiler-generated `<PrivateImplementationDetails>` type or any of its nested `__StaticArrayInitTypeSize=N` array-literal-blob helper structs.

## Actual behavior

Tell us what you see!

But a bug happened like this: `<PrivateImplementationDetails>` — the **container type itself**, not just a nested member — is renamed anyway, along with its nested `__StaticArrayInitTypeSize=N` struct, with **no** "skipped" annotation at all in `Mapping.txt` for either of them:

```
[ObfuscarRepro]<PrivateImplementationDetails> -> [ObfuscarRepro]A.A
	<PrivateImplementationDetails>/__StaticArrayInitTypeSize=700 [ObfuscarRepro]<PrivateImplementationDetails>/__StaticArrayInitTypeSize=700 <PrivateImplementationDetails>::22FB108E29D76950119863C325E356566EF8B2C8FCC47A3FD2321058CC0099E2 -> A
[ObfuscarRepro]<PrivateImplementationDetails>/__StaticArrayInitTypeSize=700 -> [ObfuscarRepro]A.A/A
```

Neither `SkipGenerated="true"` alone, nor adding an explicit `<SkipType rx="...">` (or a plain `name="&lt;PrivateImplementationDetails&gt;/*"` wildcard, or explicit per-size `name="&lt;PrivateImplementationDetails&gt;/__StaticArrayInitTypeSize=700"` entries) changes the result — `Mapping.txt` is identical across every configuration tried. **This is a regression relative to the 3.0.0-beta.x line**, where the same `SkipGenerated="true"` setting *does* at least correctly protect the container type (see the companion issue for the 3.x line filed alongside this one) — only its nested array-literal struct escapes protection there. On 2.2.50, neither is protected at all.

This is not just a theoretical/cosmetic issue: renaming this type breaks any downstream consumer that needs to resolve it by name/identity. We found this while building for Unity's IL2CPP target. Unlike the 3.x line (where `UnityLinker` fails outright on this rename), on 2.2.50 the build gets further — `UnityLinker` doesn't crash — but IL2CPP's C++ code generation then fails instead, on the same file/line across repeated runs:

```
error: no matching function for call to 'RuntimeHelpers_InitializeArray_...'
note: candidate function not viable: no known conversion from
'RuntimeFieldHandle_t...' to 'intptr_t' (aka 'long') for 2nd argument
```

(Those specific errors are Unity/IL2CPP-specific and not something this report asks Obfuscar to fix directly — included only as evidence of real-world impact. The underlying defect — the skip rule not applying to this type at all — is fully reproducible and observable purely via `Mapping.txt`, with no Unity involvement at all; see the minimal repro below.)

## Detailed steps

Detailed steps to reproduce the problem.

The steps are: a minimal, from-scratch repro project (not derived from any real codebase) is available at <link to `.examples/obfuscar-repro/` in this repo, or attach `Data.cs` + `ObfuscarRepro.csproj` + `run-22x/Obfuscar.xml` from that folder>. Summarized:

1. Create a plain .NET 8 console project with one file containing a `public static readonly byte[]` field initialized with a literal of ~700 elements (large enough that Roslyn backs it with a `<PrivateImplementationDetails>/__StaticArrayInitTypeSize=N` helper rather than per-element IL assignments — the exact values don't matter, only the count).
2. `dotnet build -c Release`.
3. Run Obfuscar 2.2.50 against the built DLL with this config:
   ```xml
   <?xml version="1.0"?>
   <Obfuscator>
     <Var name="InPath" value="<bin/Release/net8.0 dir>" />
     <Var name="OutPath" value="<some out dir>" />
     <Var name="KeepPublicApi" value="true" />
     <Var name="RenameFields" value="true" />
     <Var name="RenameProperties" value="true" />
     <Var name="RenameEvents" value="true" />
     <Var name="HidePrivateApi" value="true" />
     <Var name="SkipGenerated" value="true" />
     <SkipType rx="^&lt;PrivateImplementationDetails&gt;(/.*)?$" skipStringHiding="true" />
     <Module file="<path to the built .dll>" />
   </Obfuscator>
   ```
4. Inspect the resulting `Mapping.txt` — both `<PrivateImplementationDetails>` and its nested `__StaticArrayInitTypeSize=N` type will show as renamed, with no "skipped" annotation for either.

Also confirmed the same result using a plain wildcard (`<SkipType name="&lt;PrivateImplementationDetails&gt;/*" skipStringHiding="true" />`) instead of `rx`, and using per-size hand-listed entries instead of a wildcard/regex — all forms produce the identical outcome, and running with `SkipGenerated="true"` alone (no explicit `SkipType` at all) also produces the identical result.

## Related issues (searched before filing)

None of these are duplicates of this report (different trigger/symptom in each case), but they're the closest prior art found searching this repo's issue tracker, and may be useful context for whoever triages this:

- **#201** — Unity IL2CPP build failure involving `<PrivateImplementationDetails>`, closed 2019 after the reporter worked around it with `HideStrings="false"`. **We tried that exact workaround against this repro and it does not fix this issue** — `Mapping.txt` is unchanged with `HideStrings="false"` set, since this repro's `<PrivateImplementationDetails>` usage comes from an array literal, not from Obfuscar's own string-hiding feature.
- **#583** — "ExceptionHandlers table stripped... `SkipType` with `skipMethods="true"` → does NOT fix it" (ILRepack + Obfuscar, tested on Obfuscar 3.0.0.0). Same general shape as this report (a documented `SkipType` rule not actually preventing the described breakage) but for a different trigger (ILRepack-merged assemblies) and a different symptom (stripped exception handler tables, not a rename). Closed without a technical resolution recorded in the thread.
- **#340** — a different `<PrivateImplementationDetails>`-related failure (method-count overflow from `HideStrings` generating too many string-decoder methods on a large assembly). Root cause and trigger are unrelated to this report's array-literal-blob scenario.
- **#400** — another `<PrivateImplementationDetails>`-related crash ("declared in another module and needs to be imported"), triggered by a different codepath than this report.
- **#467**, **#191**, **#154** — the same general pattern ("still obfuscated/broken despite a skip configuration option") reported for *anonymous types* (`SkipAnonymous`) rather than compiler-generated array-literal helpers. #467 was closed as "not_planned" for lack of a clear repro; the other two describe anonymous-type properties being stripped under `HidePrivateApi`.
- **#613** — a separate, confirmed v2-vs-v3 regression report (unrelated symptom — a Revit API reference failing only on `3.0.0-beta.18`), included here only as evidence that cross-version behavior differences between the 2.2.x and 3.x lines are a known, recurring category of report for this project — directly relevant here, since **this specific report documents 2.2.50 behaving worse than 3.x** for this exact type (see the companion issue for the 3.x line).
