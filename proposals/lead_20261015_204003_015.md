# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Bot-traffic watcher: flag new bot user agents from ingress logs and file a block issue**

*Project description:*
## Problem

We find new bad bots after they've done damage. Each of these was spotted by hand in the ingress logs:

- **ShapBot** (Oct 13): about 87k requests to sanrafael.gov, driving about $3.9k/day of Translation spend (pc-dev-issues#391).
- **KeenableBot**: an AI search crawler hitting translated pages.
- **`Chrome/145.0.7632.6`** (Oct 15): a headless-browser crawler with 300k+ requests across the fleet in a few hours. It ran page JavaScript, so it burned Google Maps loads toward the daily cap.
- **`node`** (Aug): a sitemap scraper that crashed every montgomeryoh pod by running them out of memory.

All of them had a user agent we could have blocked right away in `www/bots.csv`, if something had flagged it.

## Proposal

Add a **bot-traffic watcher** alongside the existing watchers in `proudcity-kubernetes/migration-watcher/` (migration drift, cron health, filetoweb queue). Use the same image (alpine + kubectl + gh + jq), the same CronJob/ServiceAccount/RBAC pattern, and the same one-rolling-issue-with-fingerprint behaviour.

### Data
- [ ] Every **15 minutes**, read the last ~20 minutes of logs from the `nginx-ingress-controller` pods in `default` (`kubectl logs --since=20m`). Container log rotation keeps about 1h, so a 20m window is safe.
- [ ] RBAC: `get`/`list` on `pods` and `pods/log` in `default` only. No `pods/exec`.
- [ ] Parse each line for user agent, backend (`[prod-<tenant>-80]`), status and path.

### Detection (per user agent, per window)
- [ ] **Bots that name themselves:** UA matches `bot|crawl|spider|scrape|fetch|http-?client|python|go-http|java/|node|curl|wget|headless|scrapy` and isn't already matched by `bots.csv`. ShapBot and KeenableBot would have been flagged.
- [ ] **Automation clues:**
  - a full Chrome build number (`Chrome/\d+\.0\.[1-9]\d*\.`), since real Chrome sends `Chrome/NNN.0.0.0`
  - `HeadlessChrome`
  - very old Chrome versions above a volume threshold

  `Chrome/145.0.7632.6` would have been flagged.
- [ ] **Volume:** one UA with more than N requests in the window, hitting M or more distinct tenants, or taking more than X% of one tenant's traffic. Tune N/M/X against about 1–2 weeks of history.
- [ ] **Skip:**
  - UAs already matched by the live `www/bots.csv`. Fetch it from the repo with `gh api` each run so it never drifts.
  - A `bin/check-bots.allow` file of known-good UAs, each with a reason, like `check-migrations.exclude`: Googlebot, UptimeRobot, Kubernetes probes, cities' own monitors, and so on.

### Output: one rolling `bot-traffic` issue in wp-proudcity
- [ ] For each suspect: the UA string, which rule matched, requests and the share that got 2xx, top tenants, sample paths, first and last seen, and **a ready-to-paste `bots.csv` line** with a suggested comment.
- [ ] Behaviour (matches the migration watcher):
  - New suspect, no open issue: create it on board 3, Status **To-do**.
  - Same suspect set: **do nothing**, so quiet runs make no noise.
  - Set changed: rewrite the body and add one comment saying what's new or gone.
  - No suspects: close with a comment.
- [ ] Optionally @-mention curtis when a suspect passes a high volume, for example over 50k requests in a window, or more than 20 tenants.
- [ ] **Never block automatically.** Some rules can match real people (old browsers, city monitoring tools), so a human adds the line to `bots.csv` and it ships with the next build.

### Deploy
- [ ] `bin/check-bots.sh` (the audit, human or `--json` output) and `bin/check-bots-report.sh` (the issue handling).
- [ ] `migration-watcher/bot-traffic-cronjob.yml`, reusing the `migration-watcher-github` token and the token-expiry handling.
- [ ] Add it to the README's table of pieces.

## Limits
