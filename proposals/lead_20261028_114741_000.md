## Context

The contract already defines typed performance properties (`FireProperty`, `AcousticProperty`, `ThermalProperty`, …) with canonical keys, e.g. `FirePropertyKey.resistance_rating`. The IFC mapping does not use them yet: values such as `Pset_WallCommon.FireRating` land as free text in `metadata` (`{Pset}.{Property}`).

Rule checks (SHACL) need a stable path and a normalized value. With free text, `"EI 90"`, `"EI90"` and `"EI 90-RF1"` are different values, and every rule has to know the Pset name.

## Goal

Map rule-relevant Pset values into `performance_properties` with canonical keys and normalized values, in the declarative mapping.

## Scope

- Mapping entries from IFC Psets to `performance_properties`, at least:
  - `Pset_*Common.FireRating` → `FireProperty` / `resistance_rating`
  - `Pset_*Common.AcousticRating` → `AcousticProperty` / `rating_db`
  - `Pset_*Common.ThermalTransmittance` → `ThermalProperty`
  - `IsExternal`, `LoadBearing` where not yet typed
- Tool-specific fallbacks (Revit, ArchiCAD, Vectorworks) in `_pset_fallbacks.yaml`, same pattern as `code_or_number`.
- Value normalization rules, declared in the mapping (e.g. fire rating: remove spaces, upper case, keep suffixes such as `-RF1` separately).
- Keep the raw value in `metadata` for traceability.

## Acceptance criteria

- [ ] `Pset_WallCommon.FireRating = "EI 90"` produces a `FireProperty` with key `resistance_rating` and value `EI90`, and the raw value stays in `metadata`.
- [ ] Normalization is covered by tests with the value variants found in the sample models.
- [ ] `merge_ifc_mapping.py --check` passes.
- [ ] Mapping README documents the promoted properties and normalization rules.
