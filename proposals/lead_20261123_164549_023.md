# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[change] Standardize and reuse CI dependencies for on-demand AI reviews**

*Project description:*
**Is your feature request related to a problem? Please describe.**

The AI reviewer can run focused tests, but it often lacks dependencies that normal CI already sets up. In [Controller #1490](https://github.com/openwisp/openwisp-controller/pull/1490#pullrequestreview-5992163074), missing project dependencies blocked a focused Django test. In [netjsongraph.js #660](https://github.com/openwisp/netjsongraph.js/pull/660#pullrequestreview-6012849067), the reviewer worked around Yarn setup problems but couldn’t start ChromeDriver. A separate setup for AI review would duplicate maintenance and could drift from CI.

**Describe the solution you'd like**

Give the AI reviewer the tools a maintainer uses to investigate and verify findings. Standardize the main CI workflow and dependency setup across OpenWISP repositories so normal CI and on-demand AI reviews can reuse the same installer and caches.

- **Standardize CI’s internal structure.** Use `.github/workflows/ci.yml` in every repo. Give each workflow a distinct, repo-specific display name and keep job display names descriptive. Standardize the identifiers that automation uses: job IDs, step IDs, inputs, outputs, and matrix keys that serve the same purpose. Keep equivalent steps in the same order where practical. When changing identifiers that existing checks or automation rely on, update those references as part of the migration.
- **Use `./install-ci-deps.sh` as the standard entry point.** Normal CI and the reusable AI review workflow call the same repo-owned script. Move existing install commands into it or have it call an existing installer. Keep service startup, tests, builds, and publishing separate from dependency installation.
- **Add a brief, mandatory rule to `AGENTS.md` in every repo as it adopts the standard.** Document the full convention in `openwisp-actions`. Suggested wording: “Add CI dependencies to `./install-ci-deps.sh` and cache them. Keep cache inputs in sync with the installer and dependency files. Follow the shared structure and internal naming in `.github/workflows/ci.yml` so OpenWISP automation works across repositories.”
- **Standardize the test entry point.** Provide an executable `./runtests` at the repository root that invokes the repository’s test runner, forwards supported arguments, and returns its exit status. Whitelist this entry point with arguments in the AI reviewer’s OpenCode command policy so it can run focused tests without maintaining separate commands for each repository. Make sure the whitelist matches the intended entry point. Keep dependency installation separate from test execution. Make sure `./runtests` cannot be abused to do anything other than run tests.
- **Test the shared behavior.** Use focused tests for matrix selection.
- **Select the environment deterministically.** Mark one valid row in the existing CI matrix as `review_default`. A script selects it before looking up caches. Allow an explicit override for another valid row when a finding is specific to it. Repos without a matrix use their normal CI configuration. For the initial Django pilot, choose one valid Python/Django pair from its current matrix. Use `dev` for `netjsongraph.js`.
- **Let normal CI warm the caches.** Use the same cache keys and paths in both workflows. Cache each distinct dependency setup and share caches across rows with matching inputs. Include the relevant OS, architecture, runtime versions, dependency files, and installer inputs in the keys. If a cache misses, install for the selected row. Restore an installed environment only when its runtime and paths match.
- **Explain the goal in the shared AI review context prompt.** Update `.github/actions/bot-ai-review/prompts/shared/context.md` so every review stage uses existing CI results for routine checks rather than repeating them. Do not rerun the full suite, QA checks, or builds just to get another pass. Run a targeted check when it answers a specific question that CI results do not answer.
- **Support maintainer-style experiments.** In a temporary copy, the reviewer can run the application, try a scenario, edit code or tests, and write a minimal failing test to demonstrate a bug. For a regression test, temporarily remove the fix and check that the test fails for the expected reason with a clear error message. When practical, also check that it passes with the fix. Share a useful failing test or other reproducer, how to run it, and the observed result with the finding.
- **Keep experiments isolated.** Use trusted base-branch code for privileged setup. Execute PR code in isolation, without bot credentials or write access to shared caches.

| **Python/Django** (`openwisp-controller`, `openwisp-monitoring`, `openwisp-users`) | Install requirements for the selected Python/Django pair and system packages such as GDAL or SpatiaLite when required. | APT `.deb` archives across compatible rows; Python dependencies keyed by the selected pair. Start Redis or other services fresh and use disposable test databases. | One Django test or test class. |
| **Node.js and frontend** (`netjsongraph.js`, `openwisp-wifi-login-pages`, `downloads.openwisp.io`) | Use the CI Node version and npm or Yarn lockfile. Prepare browser tooling when the selected test needs it. | Package downloads or `node_modules` keyed by the lockfile, runtime, package manager, and platform. Match browser and driver versions. Rebuild bundles and start dev servers from the current checkout. | One unit or browser test, or the affected build or QA check. |
| **OpenWrt packages and Lua** (`openwisp-config`, `openwrt-openwisp-monitoring`) | Reuse `install-dev.sh` where present for host tests. Prepare the OpenWrt SDK, toolchain, and feeds only for package builds. | Host dependencies separately from SDKs, toolchains, and source downloads. Key the build cache by OpenWrt version, target, and feed revisions. | A focused Lua or shell test, or an unsigned build of the affected package. |
| **Ansible roles** (`ansible-openwisp2`, `ansible-openwisp-wifi-login-pages`) | Install the repo’s Ansible, lint, and Molecule dependencies and the Galaxy roles or collections CI uses. | Python dependencies and Galaxy roles or collections keyed by their requirements and tool versions. Create a fresh test instance for the selected distro. | A syntax or lint check, or one Molecule scenario where available. |
| **Docker Compose** (`docker-openwisp`) | Install host QA tools and Python test dependencies. Use the existing Compose and Make targets for integration setup. | Python dependencies and, where supported, Docker build layers keyed by build inputs. Start containers and volumes fresh in an isolated CI job. | A Compose config check, an affected image build, or a focused integration test. |
| **Sphinx docs and themes** (`openwisp-docs`, `openwisp-sphinx-theme`) | Install Sphinx, extensions, and theme dependencies, plus render or formatting tools where CI uses them. | Python dependencies and applicable system package archives. Build rendered output from the current checkout. | A local docs build, theme preview, or docs QA check. |
| **Pelican website** (`OpenWISP-Website`) | Install both Python requirements and Yarn dependencies using the versions selected by CI. | Separate Python and Yarn caches. Regenerate frontend assets and site output from the current checkout. | The site build or QA check, without deploying. |
| **Tooling and configuration** (shell tooling, workflow-only repos, shared config) | Install only the linters, validators, or test dependencies the repo already uses. | Cache downloads where useful. No cache is needed for repos without external dependencies. | The relevant linter, config validator, or small test suite. |

**Describe alternatives you've considered**

[PR #20](https://github.com/openwisp/openwisp-actions/pull/20) proposed separate package and service lists for the review workflow. That would duplicate CI setup. Prebuilt images can save more installation time, but they require a build and publishing process. Start with the shared entry point and existing caches, then measure what still takes time.

**Additional context**

**Pilot repositories**

Start with these three repositories to keep iterations fast:

- [openvpn-status-reader](https://github.com/openwisp/openvpn-status-reader) (pure Python)
- [django-minify-compress-staticfiles](https://github.com/openwisp/django-minify-compress-staticfiles) (Django package with a version matrix)
- [netjsongraph.js](https://github.com/openwisp/netjsongraph.js) (Node.js and browser tests)

Then expand to:

- [openwisp-config](https://github.com/openwisp/openwisp-config) (OpenWrt packages and Lua)
- [ansible-openwisp2](https://github.com/openwisp/ansible-openwisp2) (Ansible role with a Molecule distro matrix)
- [docker-openwisp](https://github.com/openwisp/docker-openwisp) (Docker Compose and integration tests)
- [openwisp-docs](https://github.com/openwisp/openwisp-docs) (Sphinx documentation)
- [OpenWISP-Website](https://github.com/openwisp/OpenWISP-Website) (Pelican website with Python and Yarn dependencies)

Verify that CI and AI review call the same installer, select the intended matrix row, and run a focused test with both cold and warm caches. Record setup times before expanding to other repository types.

[#38](https://github.com/openwisp/openwisp-actions/issues/38) tracks waiting for CI to finish and can ship independently.
