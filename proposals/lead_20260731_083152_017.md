# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Request a review automatically when the required CI suite passes on a same-repo PR**

*Project description:*
## Problem Statement

Since issue #936 withheld the automatic pull-request-triggered review tier, the only way a PR
gets a DevFlow review is a collaborator typing `/prflow:review` into a PR comment. That is a
manual step on the one gate that matters most before merge, and it is the step most easily
forgotten — a PR can sit green and unreviewed indefinitely. The maintainer of this repo hits
this on every PR; a consumer maintainer who installed DevFlow after #936 hits it on every PR
too, with no automatic path available at all.

The withheld tier is not the answer to restore as-is. Its defect (#937) was structural: it ran
on `pull_request_target` with `secrets: inherit` and checked out the pull request head, so fork
code executed inside a secrets-bearing job.

## Current Behavior

`.github/workflows/ci.yml` runs the test shards and the aggregating required check on every
pull request, and it stops there. Nothing observes that the suite passed. `devflow.yml` listens
for `issue_comment` and will run the review engine, but only a human ever produces the comment
that starts it.

## Desired Behavior

A new `review_trigger` job in `.github/workflows/ci.yml` posts one PR comment containing the
`/prflow:review` command when the PR is opened (or marked ready for review), the aggregating
required check and the lint job have both concluded success, the pull request head branch lives
in this repository, and the DevFlow App is configured. `devflow.yml`'s existing `issue_comment`
path picks that comment up and runs the review, exactly as it does for a human-authored command.

The job runs no fork code and receives no secrets on a fork run, because the head-repo clause
excludes every pull request whose head branch lives outside this repository. Within a same-repo
pull request the author already holds write access and already controls the workflow file that
defines this job, so pinning the helper checkout to the base ref would buy no isolation while
guaranteeing the job breaks on the very pull request that introduces the helpers. The checkout is
therefore the event's default ref, sparse and with the credential not persisted into the
repository config.

## User Impact

This repo's maintainer stops hand-typing the review command on ready PRs. Consumer maintainers
gain a documented, copy-pasteable path back to automatic reviews — one that never grants a fork
access to secrets, because the head-repo clause excludes every pull request whose head branch
lives outside the repository before any credential is minted. The `pull_request` event is a
necessary condition for that, not the defense on its own, which is why the snippet's hard
precondition below is stated where a reader cannot miss it.

### Architecture Alignment

The notifier is a producer of the same `issue_comment` trigger a collaborator produces, so it
adds no new entry point to the review engine and no new allowlist grant. The extraction of its
branch-selection and message-composition into `scripts/*.sh` follows the reference pattern
`scripts/describe-denial-count.sh` established by PR #367. Issue #402's trusted-source rule is
deliberately **not** applied here: that rule exists because the review job checks out the PR head
while acting on a floor the PR author must not control, whereas this job's authorization boundary
is the head-repo clause and its output is a fixed-shape comment, so a base-ref pin would add no
guarantee and would break the introducing pull request.

### Dependencies

`actions/create-github-app-token@v3` (already used across this repo's workflows) and
`actions/checkout@v6`. No new dependency.

### Data/Schema Considerations

None. The mechanism reads no configuration file — deliberately, since the `devflow.allowed_bots`
value that authorizes the resulting comment is resolved by `devflow.yml` from the default branch
at trigger time, so a read of the checked-out tree would answer about a different value than the
one used — and it writes no persistent state. Its only durable artifact is the posted comment and
the HTML marker inside it, which is also its dedupe key.

### Cross-layer Impact

CI workflow, two new shell helpers, the suite module that drives them, and two documentation
pages. No skill, agent, or capability-profile surface is touched — but the job's own conclusion
becomes an input to every review prompt through the engine-ground-truth block, which is a
reviewer-facing surface and is covered by its own acceptance criterion.

### Cost

The mechanism adds at most one standalone review-engine run per pull request, on the first of
`opened` or `ready_for_review` to find both jobs green, and no run at all on `synchronize`, on a
fork pull request, on a draft, or on a Dependabot pull request. The population it taxes hardest is
this repository's own bot pull requests: the implement flow opens a draft and then calls
`gh pr ready`, so every DevFlow-authored pull request buys one standalone engine run **in addition
to** the inline review pass its implement run already performed. That added spend is accepted, and
it is the reason the request is not fired on `synchronize`. The merge-gating judge's roster
economics are untouched — no `agent_overrides` value, model, or effort setting is read or changed
by this mechanism, which only produces the comment that starts an ordinary review.

## Implementation Notes

### Approach

Add one job to `.github/workflows/ci.yml`. It depends on `test` and `lint`. GitHub applies an
implicit `success()` to a job that declares `needs:` and whose `if:` carries no status function,
which would make the job **skip silently** over a red `lint` — this repository's own aggregator
carries `if: always()` for exactly that reason. The job therefore carries an explicit
`!cancelled()` and inspects the two dependency results itself, so a withheld request is announced
rather than invisible, and the body it does post is true because it is emitted only on the
both-succeeded arm.

The job checks out the event's default ref sparsely and without persisting the credential,
mints an App token scoped to pull-requests write, reads the pull request's full comment list
with that token using `gh api --paginate --slurp`, pipes the list into
`scripts/decide-ci-review-request.sh`, and on `post=true` pipes
`scripts/compose-ci-review-request.sh`'s output into a REST `POST` to
`repos/$GITHUB_REPOSITORY/issues/<pr>/comments`.

The checkout is deliberately **not** pinned to the base ref. A base-ref pin was the first design,
and it is wrong twice: the helpers this change adds do not exist in the base tree, so the job
would fail on its own pull request and on every pull request opened before the merge; and the
isolation it appears to buy is illusory, because on `pull_request` the workflow *definition*
already comes from the head, and the head-repo clause has already excluded every author without
write access. The security property is the head-repo clause, not the checkout ref, and the
`persist-credentials: false` setting is secondary hardening rather than a credential-free run.

The pagination flags are load-bearing rather than defensive, and there are two of them. The
issue-comments endpoint returns its first page in ascending creation order, and a matching marker
can sit at any position in the list — it is the newest comment only at the instant it is posted,
and any later human comment displaces it — so the helper must see the whole list, which is what
`--paginate` buys. `--slurp` is the second half and is not optional: `--paginate` alone emits one
JSON array per page, concatenated, which is not a single JSON document. Without it the helper's
stdin shape on a multi-page pull request differs from its shape on a single-page one, a
hand-authored single-array fixture would test a shape production never produces, and the
fail-closed arm would then suppress the request on exactly the busy pull requests the mechanism
is most useful on — a silent stop indistinguishable from correct dedupe.

Parsing the comment list is `jq` work, and this repository bans a bare `jq` invocation in a
`scripts/` helper: the decision helper sources `lib/resolve-jq.sh` and invokes `"$DEVFLOW_JQ"`,
so the suite's resolver pin stays green and a malformed payload surfaces as that invocation's
non-zero exit rather than an empty string the helper would misread as "no matching comment".

The author-login comparand is the operand most likely to be wired wrong, because a GitHub App's
comment author login carries a `[bot]` suffix the token-minting step's own slug output does not.
`scripts/authorize-actor.sh` already solves this by comparing both forms, and the decision helper
mirrors that rather than inventing a second convention.

`gh api` stays in the workflow file. Moving it into either helper would place it inside
`lib/test/lint-gh-api-repo-path.py`'s audited population, where `$GITHUB_REPOSITORY` addressing
is a violation, while the `{owner}/{repo}` placeholders it would demand cannot resolve in a
job with no git remote configured. Keeping the call in the workflow keeps it inside that lint's
`.github/workflows/` exemption, whose docstring gives exactly this reason.

The two helpers are split so each has one job: the decision helper never composes a message, and
the composition helper never decides. Their fail directions are deliberately opposite. The
decision helper fails **closed** — an unreadable comment list yields `post=false` — because
nobody asked for this review, a duplicate is unrecoverable engine spend, and a missed automatic
review is recoverable by a human typing the command. This is the inverse of `review_dedupe`'s
posture in `devflow.yml`, which fails open because suppressing a human's explicit command is
worse than a duplicate; the two are different cost profiles, not an inconsistency, and the
helper's header records the contrast. The composition helper fails **closed** in the other
sense: it refuses rather than emit a body whose marker carries an empty SHA, since such a marker
would match every future SHA and permanently suppress the mechanism.

The request fires on `opened` and `ready_for_review` only. `ci.yml` also runs on `synchronize`,
and requesting a review on every green push would buy one engine run per push on an iterating
pull request. `opened` and `ready_for_review` are the two events that carry an explicit
ready-for-eyes declaration, and `ready_for_review` is the event this repo's own bot pull requests
reach after `gh pr ready`. Re-review after a fix push is a human typing the command. The SHA-keyed
dedupe still runs, because a pull request can be toggled back to draft and ready again and
because a workflow run can be re-run by hand.

The trigger threshold is the two jobs' success conclusion, and it is a decided threshold rather
than an accident of what the gate happens to check. A run that passes while reporting a nonempty
skip tally still requests a review: issue #456's rule governs reading a suite run as
*verification evidence*, and the reviewer performs that reading for itself. The posted body says
so, so a reader is never told a skipping run was clean.

### Testing Strategy

Both helpers are pure stdin/argv/stdout units with exit codes, so an automated boundary exists at
the unit level for each, plus an integration-level assertion that composes and detects. The plan
adds one registered module under `lib/test/modules/` driven by the suite, with its entry in
`lib/test/modules/coverage-map.json`.

`governing conventions consulted: CLAUDE.md, CONTRIBUTING.md, docs/DEVFLOW_SYSTEM_OVERVIEW.md`

The decision helper reads agent- and human-mutable structured input (a GitHub comment list), so
its case matrix is the malformed-shape matrix for an external structured format rather than the
six-shape config-JSON matrix; the narrowing is deliberate and stated here.

**Named assertions — decision helper** (each fails first because the helper does not exist):

1. A comment list with no marker yields `post=true`. (Maps to the marker/author AC.)
2. A list containing the complete marker for the current head SHA, authored by the expected bot
   login, yields `post=false`. (Maps to the marker/author AC.)
3. A list containing that same marker text authored by any other login yields `post=true` — the
   planted-defect positive control for the quoting-suppression hazard. (Maps to the
   marker/author AC.)
4. A list containing the marker for a different SHA yields `post=true`. (Maps to the
   marker/author AC.)
5. Empty stdin yields `post=false` with a distinct reason token. (Maps to the fail-closed AC.)
6. Malformed JSON on stdin yields `post=false` with a distinct reason token. (Maps to the
   fail-closed AC.)
7. Well-formed JSON whose entries lack the author or body field yields `post=false` with a
   distinct reason token. (Maps to the fail-closed AC.)
8. A production-realistic captured comment list from this repository, with the marker absent,
   yields `post=true`. (Maps to the fail-closed AC; this is the required realistic fixture.)
9. Every one of the above exits 0 and emits exactly the two contract lines. (Maps to the
   contract AC.)
9a. A comment list spanning more than one page, with the marker present only in the entries
    beyond the first page, yields `post=false` — the paginated-read regression, which fails
    first by exhibiting the duplicate-post behavior on today's unpaginated read. (Maps to the
    pagination AC.)
9b. A marker comment whose author login carries the `[bot]` suffix while the supplied comparand
    is the bare slug still yields `post=false`, and the mirrored case yields the same. (Maps to

9c. With `DEVFLOW_JQ` pointed at a stub that exits non-zero, the helper yields `post=false` with

11. A valid 40-hex SHA produces a body whose marker embeds that SHA. (Maps to the composed-body
    ACs.)
12. An empty SHA argument exits non-zero with empty stdout. (Maps to the compose fail-closed AC.)
13. A SHA containing a non-hexadecimal character exits non-zero with empty stdout. (Maps to the
    compose fail-closed AC.)
14. A 39-character and a 41-character SHA each exit non-zero with empty stdout. (Maps to the
    compose fail-closed AC.)

**Named integration assertions:**

15. The composed body, piped into the real `scripts/detect-standalone-command.sh`, yields

    holds against the actual detector rather than against a reading of it. (Maps to the
    composed-body command AC.)
16. The composed body contains no `@claude` substring and no implement-command token in either

17. The composed body with only its marker line retained, piped into the detector, yields an
    empty `command=` — the marker alone triggers nothing. (Maps to the composed-body command AC.)
18. The composed body, supplied to `scripts/resolve-command-trigger.sh` through its `TRIGGER_TEXT`
    environment input (that resolver reads no stdin) together with a `CONTEXT_NUMBER` and an

    marker environment left at its defaults, yields the stdout line `should_run=true`. The bot
    arm is chosen so the assertion stays network-free and auth-free. (Maps to the composed-body
    command AC.)

19. The snippet block extracted from `docs/workflow-triggers.md` and the `review_trigger` job
    region extracted from `.github/workflows/ci.yml` agree on the compared element set. (Maps to
    the copy-agreement AC.)
20. Mutating one compared element on one side only turns assertion 19 RED — the planted-defect
    positive control that proves the guard fires rather than agreeing vacuously. (Maps to the
    copy-agreement AC.)
21. Each of these extractor input shapes turns assertion 19 RED rather than passing — complete by
    construction: the snippet block absent; the snippet block present but empty; two candidate
    snippet blocks in the page; the snippet block unfenced; the `review_trigger` job region

Nothing is mocked in the integration assertions: they run the real detector and the real
resolver, never a stand-in for either. The `jq`-stub assertion mocks the resolver's *output
binary* only, which is the documented `DEVFLOW_JQ` test-stub contract, never the unit under
test.

The workflow job itself has no unit-test boundary. Its reproducible verification is a numbered
checklist: (a) open a draft pull request and confirm no comment is posted; (b) mark it ready,
confirm CI runs, and confirm exactly one comment appears once both jobs are green; (c) confirm a
review starts; (d) re-run the CI workflow at the same head SHA and confirm no second comment
appears; (e) push a further commit, confirm CI runs green, and confirm no comment appears for the
`synchronize` event. Because the checkout is the event's default ref, the helpers are present on
the introducing pull request itself, so items (a) through (e) are executable **in that pull
request** rather than deferred to a post-merge window.

### Potential Gotchas

- On the `pull_request` event `github.sha` is the merge commit, not the head commit. A marker
  keyed on it would never match the SHA a reader sees on the pull request.
- The App-token mint is load-bearing twice over, and neither reason is least-privilege: a
  `GITHUB_TOKEN`-authored comment fires no `issue_comment` event at all, and
  `github-actions[bot]` is absent from `devflow.allowed_bots`, so such a comment would also fail
  authorization. Replacing the mint with the default token disables the mechanism silently.
- No job in this repository declares `permissions: {}` today, so `contents: read` on this job is
  the narrowest form with an in-repo precedent.
- No existing App-token mint step in this repository uses `continue-on-error`, so a configured
  App whose credentials fail turns the job red rather than skipping it. This is why the
  Dependabot exclusion must be an explicit actor clause.
- `install.sh`'s workflow copy loop is parsed by the suite to derive the shipped-workflow set, so
  a change there is machine-observed. This issue adds nothing to it.
- Re-running an old CI workflow run replays that run's event payload, so
  `github.event.pull_request.head.sha` is the SHA that run gated, which can be behind the pull
  request's current head. The marker keys on that SHA and the body attributes its claim to it, so
  the comment stays truthful; the review the engine then performs is of the current head, which
  is the intended behavior and not a defect to work around here.
- A pull request closed between the suite passing and the comment posting makes the POST fail.
  That is the best-effort warning path, not a job failure.
- The mechanism's success condition — that a review actually starts — is observable only in the
  other workflow's run. The posted body carrying the required `allowed_bots` entry is the
  compensating control, and it is deliberately on the pull request rather than only in a log.
- `grep -rn 'sparse' .github/` returns nothing, so there is no in-repo sparse-checkout precedent
  to inherit a correct cone from; the cone is specified from the helpers' transitive needs
  instead, and asserted.
- `docs/` is excluded from `lib/test/lint-gh-api-repo-path.py`, so the snippet's `gh api` line in
  the documentation page is outside that lint. The live job's copy is inside the
  `.github/workflows/` exemption. Neither copy is audited by it, which is why the ACs pin the
  addressing form directly rather than relying on that lint to catch a regression.
- The consumer snippet and the live `review_trigger` job are the same text in two places. A
  consumer cannot copy-paste a pointer, so the copy is unavoidable — but `CLAUDE.md`'s
  single-source-of-truth default scopes the coupled-invariant discipline to copies that already
  exist and calls that population backlog rather than a licence to extend it. This change
  therefore ships the copy **with a machine check** that the two agree, so the new pair enters the
  tree guarded rather than as an unchecked addition to that backlog.
- The `review-trigger-helpers` module already exists in `lib/test/modules/` and covers the
  *command-trigger* helpers, not this mechanism. Folding these assertions into it would break its
  pinned assertion floor and misattribute ownership in the coverage map.

## Open questions for the implementing run

These were surfaced by the final audit round and are deliberately left for the implementing run to
resolve rather than answered here. None of them blocks starting the work.

- **The zero-comment input shape.** The mechanism fires on `opened` and `ready_for_review`, so the
  modal production stdin is a well-formed comment list with **no entries**. That shape sits on the
  boundary between the decision helper's fail-closed `empty` arm and its ordinary no-marker arm. It
  must resolve to `post=true`, and the fail-closed AC's `empty` token must be read as *empty
  stdin* only. Add the acceptance criterion and the named assertion; an implementer who conflates
  the two ships a mechanism that never posts on a freshly opened pull request and fails silently,
  because `post=false` is a normal outcome.
- **The single-page `--slurp` shape.** See the flagged premise above.
- **The cost bound's exact form.** The Cost section states at most one standalone engine run per
  pull request. The dedupe key is the head SHA, not the pull request, so a
  draft-to-ready-to-draft-push-to-ready cycle buys a second run at a new SHA. Restate the bound as
  per head SHA, per `opened` or `ready_for_review`.
- **What the end-to-end assertion should assert.** `devflow.yml` routes the reviewer identity and
  token on `startsWith(needs.gate.outputs.command, '/prflow:review ')` — a trailing-space-sensitive
  prefix test on the resolver's `command` output, not on `should_run`. The integration assertion
  should pin the exact emitted `command=` line, so a value that resolves but fails that prefix test
  — and would therefore run under the write-capable token rather than the downscoped read-only
  reviewer token — cannot pass unnoticed.
- **`lib/test/modules/coverage-map.json` is generated, not hand-registered.** It declares its own
  producer and a repair command, `python3 lib/test/coverage_map_guard.py . --fix`. Regenerate it
  rather than hand-editing, and confirm both halves resolve: a `files` entry for each of the two
  new helpers, and `run_sh_blocks` labels for the new assertions.
- **Reconciling `pipefail` with the green-job outcome.** The acceptance criteria require both
  `set -o pipefail` on the `gh api` pipeline and a green job with a `::warning::` on failure. Under
  this repository's prevailing `set -euo pipefail` idiom those conflict, so the pipeline's exit
  status must be captured (an `if ! out=$(… | helper); then` shape) rather than allowed to abort
  the step. `.github/workflows/ci.yml` carries no `set -euo pipefail` today, so this is a
  convention-pull hazard rather than an in-file contradiction.
- **Any vestigial fragment carried over from the original design sketch.** The sketch this issue
  supersedes contained a partial `if ! existing=…` dedupe line that no longer has a place in the
  extracted-helper design; nothing of it should survive into the implementation.
