## Consider adding a validation step to verify the "Files Affected" section contains only paths that exist in the repository

### What

Add a validation step in `.github/scripts/create_followup_issues.py` that checks each file path listed in the "Files Affected" section of AI-generated issues against the repository's actual file tree. The validation should run after the LLM generates the issue body and before the issue is created.

### Why

The current template instructs the LLM to "Use only paths you can confirm from the review text above," but this is a soft constraint. LLMs can still hallucinate plausible-looking paths that don't exist in the repository. Invalid paths in issues create confusion for maintainers, break automation that consumes these paths (e.g., CI triggers, cross-referencing tools), and reduce trust in AI-generated issues. This is a correctness and maintainability risk that grows as more issues are auto-generated.

### How

1. In `.github/scripts/create_followup_issues.py`, after the LLM response is parsed and the issue body is assembled, extract the "Files Affected" section content.
2. Parse the section into a list of file paths (one per line, trimming whitespace and ignoring the "Unknown" sentinel).
3. For each path, check existence against the repository root (e.g., using `os.path.exists()` or `Path.is_file()` relative to the repo root).
4. If any path is invalid, either:
   - **Option A (strict):** Reject the issue and retry the LLM call with a corrective prompt, or
   - **Option B (lenient):** Replace the invalid path with "Unknown" and log a warning.
5. Add a unit test with a fixture repository containing known files to verify the validation logic.

### Files Affected

- `.github/scripts/create_followup_issues.py`

### Constraints

- Must not break the existing issue-generation flow when all paths are valid.
- Must not alter the prompt template or renumber sections (out of scope).
- Must handle the "Unknown" sentinel gracefully (it should pass validation).
- Must not introduce new dependencies beyond Python's standard library (or justify any addition).
- The `.aider.conf.yml` auto-testing remains disabled; tests should be run manually or via CI.

### LLM tier

**Sonnet** — This requires moderate design judgment (choosing between strict/lenient handling, parsing the section robustly, and adding test coverage with fixture data). It's a single-file change but involves non-trivial heuristics.

### Success looks like

- A PR that adds the validation logic to `.github/scripts/create_followup_issues.py`.
- Unit tests covering: valid paths pass, invalid paths are handled per the chosen option, "Unknown" passes, and empty section passes.
- Manual verification that a generated issue with a deliberately fake path is either rejected or corrected.
- No regression in the existing issue-generation flow for valid inputs.

### Failure looks like

- Validation is too strict and rejects valid paths due to parsing errors (e.g., trailing slashes, relative vs. absolute paths).
- Validation is too lenient and lets obviously fake paths through.
- The change breaks the existing issue-generation pipeline (e.g., crashes on malformed LLM output).
- Tests are missing or don't cover edge cases (empty section, "Unknown", multiple paths).
