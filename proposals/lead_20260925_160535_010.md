# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Spec: Contact discovery — find contacts on Convoze, start a chat, invite**

*Project description:*
Part of #1 · Settles the "user discovery / contacts" gap listed under *Not yet specified* on #1, and replaces the "search by username/email" half of feature 13 in `docs/features.md`, which can't work in a phone-only app (ADR 0003: the phone number is the sole identifier). It builds on the auth spec #20 and the messaging spec #38 (`POST /conversations/direct`, the chat screen). Glossary: `CONTEXT.md` (**Device**); this spec adds **Contact match**.

**Depends on:** #38 (Messaging).

## Problem Statement

Once messaging exists (#38), a Convoze user still has no way to start a chat. There are no usernames or emails to search for, and the phone number is the only identifier. So the user can only talk to someone who happens to have messaged them first. They can't see which of the people they already know are on Convoze. They can't reach someone whose number they have but haven't saved. And they can't invite a friend who isn't on Convoze yet.

## Solution

The conversation list gets a **New chat** button, which opens a screen that:
- **lists the user's phone contacts who are on Convoze**, with their Convoze name and avatar, found by matching the phone's address book against registered users;
- lets the user **type any phone number** and open a chat with it if that number is on Convoze;
- lists the user's **other contacts** with an **Invite** button, which opens the system share sheet with an invite message.

Tapping a person opens the existing direct chat with them, or starts a new one (#38's `POST /conversations/direct`).

To match, the phone reads the address book (only after the user grants permission), normalises every number to E.164, hashes it with SHA-256, and sends only the hashes. The server compares them with the hashes of registered numbers, returns the matches, and **stores nothing** about the upload. Typing a number uses the same path with a single hash.

## User Stories

1. As a user, I want a "New chat" button on my conversation list, so that I can start talking to someone.
2. As a user, I want to see which of my phone contacts are on Convoze, so that I can message people I already know without asking for their details.
3. As a user, I want matched contacts to show their name from my address book alongside their Convoze name and avatar, so that I recognise them.
4. As a user, I want the list sorted alphabetically and searchable by name, so that I can find someone quickly in a long address book.
5. As a user, I want tapping a contact to open our existing chat if we already have one, so that I never end up with two chats with the same person.
6. As a user, I want tapping a contact I've never messaged to open a new, empty chat with them, so that I can write the first message.
7. As a user, I want to be asked for contacts permission only when I first open New chat, with a short explanation of why, so that the request makes sense.
8. As a user, I want the app to explain that only scrambled (hashed) numbers are sent and nothing is kept on the server, so that I can decide to allow access.
9. As a user who denies contacts permission, I want New chat to still work by typing a number, so that the app stays usable.
10. As a user who denied permission earlier, I want a button that opens the system settings, so that I can change my mind.
11. As a user, I want to type or paste a phone number in my usual local format, so that I don't have to know international formatting.
12. As a user, I want a clear message when the number I typed isn't on Convoze, with an option to invite them, so that I know what to do next.
13. As a user, I want a clear error when the number I typed isn't a valid phone number, so that I can fix a typo.
14. As a user, I want to invite contacts who aren't on Convoze through my usual share options (SMS, WhatsApp, etc.), so that I can bring friends over.
15. As a user, I want the matched list to refresh by itself when I open New chat after a day or more, and when I pull to refresh, so that new sign-ups among my contacts show up.
16. As a user, I want the previously matched list to show instantly while a refresh runs, so that New chat opens fast.
17. As a user, I don't want to see myself in the list, so that I don't accidentally message myself.
18. As a user offline, I want New chat to show my last matched list and explain that starting a chat needs a connection, so that I'm not confused by a spinner.
19. As a user, I want numbers in my address book stored without a country code to be matched correctly, so that contacts saved in local format aren't missed.
20. As a user, I want my contacts' names never to leave my phone, so that my address book stays private.
21. As the product owner, I want the server to never store or log uploaded contact hashes, so that we don't hold a copy of users' address books.
22. As the product owner, I want the matching endpoint rate-limited per user, so that it can't be used to scan the whole number space to find out who is registered.
23. As a backend developer, I want one matching endpoint used for both address-book sync and typed-number lookup, so that there is one set of validation and limits.
24. As a Flutter developer, I want the address-book reader behind one provider, so that the e2e tests can supply a fixed contact list.

## Implementation Decisions

### Backend

- **Schema:** add `User.phoneNumberHash`: the lowercase hex SHA-256 of the E.164 `phoneNumber`. It's unique and indexed, set whenever a User is created (the #20 verify path, and the e2e seeders), and backfilled by the migration. As part of implementation, update ADR 0004's `User` block.
- **Hash module:** one function `hashPhoneNumber(e164)` used by user creation and the tests. It's plain SHA-256, **deliberately unsalted and unpeppered**, because the client has to compute the same value (see Further Notes for what this does and doesn't protect).
- **`POST /contacts/match`** (auth middleware from #20):
  - **Request:** `{ hashes: string[] }`, with 1–1000 entries, each 64 lowercase hex chars. Duplicates are ignored.
  - **Response:** `{ matches: [{ hash, user: { id, displayName, avatarUrl } }] }`. The caller is never included.
  - **Deliberately left out of the response:** the phone number (the client already has it) and anything about non-matches.
  - **Rate limit:** in-memory, per user, **at most 20,000 distinct hashes per rolling 24 h** (single instance, as ADR 0008 states). Over the limit it returns `429 rate_limited` with `retryAfterSeconds`, using #20's error shape.
  - Validation failures return `400 invalid_request`.
- **Nothing is persisted or logged.** The request body is not stored, and no request-body logging is added for this route. The only state is the rate limiter's per-user counter.
- **Blocked users:** the blocking spec may choose to hide people who blocked the caller. This spec returns every match; the hook is simply "filter `matches` before responding".

### Flutter client

- **New dependencies:**
  - `flutter_contacts` (read the address book and request permission);
  - `phone_numbers_parser` (pure Dart E.164 normalisation);
  - `crypto` (SHA-256);
  - `share_plus` (the invite sheet);
  - `permission_handler` (only to open app settings, if `flutter_contacts` doesn't cover it).
- **Platform config:** iOS `NSContactsUsageDescription`; Android `READ_CONTACTS`.
- **`DeviceContactsSource`** (a provider, overridden in e2e):
  - `permissionStatus()`, `requestPermission()`, and `read()`, which returns `[{ displayName, phoneNumbers[] }]`.
  - This is the only place that talks to the OS address book.
- **`ContactsRepository`** (`features/contacts/data`):
  - **Normalise:** parse each number with the **signed-in user's own country** as the default region (derived from their `phoneNumber`), keep the valid mobile/fixed numbers, and convert them to E.164.
  - **Hash:** SHA-256, the same as the server.
  - **Match:** send in chunks of 1000 to `/contacts/match`.
  - **Store** the result in a Local replica table `contact_matches(hash, userId, deviceContactName, e164)`, together with a `lastMatchedAt`.
    - It is wiped by the #38 wipe path like every other rebuildable table.
    - Contact names are stored **only** on the device.
  - **Refresh policy:** refresh on opening New chat when `lastMatchedAt` is more than 24 h old, and on pull-to-refresh. Otherwise, show the stored matches.
  - **`lookup(typedNumber)`:** normalise, then hash, then match a single hash. It returns `found(user)`, `notOnConvoze(e164)` or `invalidNumber`.
  - Unmatched contacts (for Invite) are computed on the device, from the address book minus the matches. They are never sent anywhere.
  - A `429` shows "Too many lookups, try again later" and keeps the stored list.
- **New chat screen** (`/new-chat`, reached from #38's conversation list button and its empty state):

  | Screen state | What the user sees |
  |---|---|
  | Permission not yet asked | An explainer card: "Convoze checks which of your contacts use it. Numbers are scrambled before they leave your phone and are never stored." A **Continue** button then triggers the OS prompt. |
  | Permission granted | A search field; then **On Convoze** (address-book name, Convoze name and avatar, alphabetical); then **Invite to Convoze** (contacts not matched, each with an Invite button). |
  | Permission denied | A short note and an **Open settings** button. |

  - In every state, an **"Enter a phone number"** row is shown at the top. It opens a field with a country prefix picker, defaulting to the user's own country, and on submit runs `lookup`:
    - `found`: open the chat;
    - `notOnConvoze`: "Not on Convoze yet", with an Invite button;
    - `invalidNumber`: an inline error.
  - Tapping a matched person calls #38's `ConversationsRepository.openDirect(userId)` and navigates to `/chat/:id`. While not `connected`, it shows "Starting a chat needs a connection" instead.
- **Invite:** `share_plus` shares "Let's chat on Convoze: <inviteUrl>". The link comes from a new `AppConfig.inviteUrl` `--dart-define`, per ADR 0001's config approach. This is a plain share with no referral tracking.

## Testing Decisions

**What makes a good test here:** it asserts on what the endpoint returns, or what the New chat screen shows and where tapping leads. It never asserts on hashing internals beyond "the client's hash matches the server's for the same number", or on the table layout.

**Backend: one seam, HTTP** (the #20 app factory, a real Postgres test DB, the fake clock).
- Hashes of registered users match, with id, name and avatar. Unregistered hashes are simply absent.
- The caller's own hash is excluded. Duplicates in the request are ignored.
- Validation: no hashes, 1001 hashes, bad hex, or unauthenticated is rejected.
- Rate limit: 20,000 distinct hashes pass, the next request is `429`, and it passes again after the clock moves 24 h.
- A user created through the real OTP flow gets a hash that the same function reproduces, and the migration backfill covers pre-existing users.
- Nothing is written: after a match, no table other than those touched by auth has new rows.
- **Prior art:** #20's HTTP tests (the OTP rate-limit tests especially).

**Flutter: the end-to-end suite** (the #20/#21/#38 harness).
- **The one client override:** `DeviceContactsSource` is swapped for a fixed in-memory address book with a scripted permission state. The OS address book and permission dialog can't be driven reliably from `integration_test`. Everything else is real: normalisation, hashing, the HTTP match against the real backend, the local table, and navigation.
- **Cases:**
  - **Permission granted:**
    - An address book of registered users (seeded through the other-device helper) and strangers, with numbers in both local and international formats.
    - Registered users appear under "On Convoze"; the rest appear under "Invite"; the signed-in user doesn't appear.
  - **Opening a chat:**
    - Tapping a match with no chat yet opens an empty chat, and after sending, the other user receives it.
    - Tapping someone with an existing chat opens that same chat.
  - **Permission denied:** the note and the settings button show, and "Enter a phone number" still works.
  - **Typed number:** a registered number opens the chat, an unregistered one shows the invite option, and an invalid one shows the error.
  - **Refresh:** a contact who signs up after the first match appears after pull-to-refresh.
  - **Offline:** with the transport dropped, the stored list shows, and tapping shows the connection message.
  - **Rate limit:** use an e2e-mode control endpoint that lowers the match limit (in the same style as the #20 token-TTL endpoint); the "Too many lookups" message shows and the list is kept.
- **Not covered by automation:** the real OS permission prompt and the share sheet. Check both by hand once on each platform.

## Out of Scope

- A server-side contact graph, "X joined Convoze" notifications, and suggested contacts. Nothing about the upload is kept.
- Showing address-book names instead of Convoze names in the conversation list and chat header. Here they're used only on the New chat screen.
- Searching users by display name.
- Referral or invite tracking, and deep links from the invite that open the app on a particular chat.
- Hiding people who blocked you from matches: that belongs to the blocking spec, through the filter hook.
- Group creation from contacts: the groups spec reuses this screen's matched list as its member picker.
- Syncing when the address book changes in the background. Refreshing happens only on open or pull.

## Further Notes

- **Decisions made while writing this spec** (flag them if you disagree before implementing):
  - The hashes are **unsalted SHA-256**, chosen by the user (upload hashed numbers, store nothing). Phone numbers are a small space, so anyone holding a hash can recover the number by brute force. The hashing keeps numbers out of logs and traffic dumps, but it is not strong privacy. **The real protection is the per-user rate limit plus not storing uploads**; the explainer copy says "scrambled", never "anonymous" or "encrypted". Signal's answer (SGX-based private contact discovery) is far beyond this project's scope.
  - The user chose the typed-number and invite options. Both reuse the single matching endpoint and the system share sheet.
  - Normalisation defaults to the signed-in user's own country.
  - The limit is 20,000 hashes per user per 24 h (enough for a large address book plus refreshes, and far too few to scan a country's numbers).
  - Matching refreshes when older than 24 h, or on pull.
- **Library behaviour to verify while implementing:** whether `flutter_contacts` can open app settings after a permanent denial on both platforms, or `permission_handler` is needed for that. Also Android 14's partial contacts access, which should behave like "granted" with fewer contacts.
- **`CONTEXT.md` addition** (during implementation): **Contact match**: a registered User found by comparing the hash of a number in a Device's address book with the hash of that User's phone number. It is computed on request and never stored on the server. _Avoid_: friend, connection (Convoze has no follow or friend relationship).
