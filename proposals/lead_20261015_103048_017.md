# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**coordination: build a real-time SI-agent chat bridge with GitHub provenance**

*Project description:*
## Problem

The shared SI research log at [Issue #5](https://github.com/miahpenn/0-Cosmos-engine/issues/5) already has more than 1,400 comments and remains durable, but GitHub comments do not guarantee push delivery. Agents can miss rapid state changes, reuse stale main/head/check snapshots, or duplicate expensive tests. The docs protocol is being tightened in [draft PR #221](https://github.com/miahpenn/0-Cosmos-engine/pull/221), but it does not create a live chat transport.

## Proposed MVP

Build an opt-in chat bridge around one team-selected messaging service. Slack is one candidate, not an assumed team choice. Keep GitHub as the system of record and use chat for rapid coordination and notifications.

### Required behavior

1. Provide a dedicated SI-agent coordination channel with structured `[CLAIM]`, `[RUNNING]`, `[RESULT]`, `[CORRECTION]`, `[BLOCKER]`, and `[HANDOFF]` messages.
2. Attach UTC timestamp, lane/owner, live `main` SHA, branch/PR head and base SHAs, relevant input/config/dependency pins, links to evidence/artifacts and the next gate.
3. Notify on relevant ownership/state transitions, PR head changes, and CI completion/failure. De-duplicate webhook retries and link back to the authoritative GitHub issue, PR, workflow or artifact.
4. Mark operational snapshots older than 5 minutes stale. Before any costly action, require a fresh source/status preflight no older than 2 minutes. If relevant refs move or provenance is missing, say `UNKNOWN—REVALIDATION REQUIRED` and do not launch automatically.
5. Mirror decision-critical claims/results/corrections back to Issue #5 (or their established task thread), so search, provenance and audit history survive outside chat.
6. Treat expired claims as unknown ownership, never as permission to duplicate an experiment. Chat messages alone must not authorize production merges, alter physics/configuration, or trigger an unbounded campaign.
7. Use least-privilege service credentials, secret storage, signed/verified inbound events, replay/idempotency protection, rate limits, and safe rendering of untrusted message bodies. Never put tokens or private credentials in GitHub comments or chat.
8. Include fixture-based tests for stale/fresh messages, source-head mismatch, duplicate/replayed events, missing provenance, corrections/supersession, provider failures, and message-to-GitHub linkage.

## Decisions / dependencies

- **Owner decision required before enabling:** which service the team actually uses (Slack, Microsoft Teams, or another supported platform), and who can authorize the workspace/channel and credentials.
- The current ChatGPT Slack connector, if connected, is not by itself a backend for autonomous repository agents; the repository bridge needs its own least-privilege app/credentials and deployment path.
- Do not add real credentials, provider-specific dependencies, or a live production webhook until the provider and deployment owner are selected.

## Acceptance

- A controlled end-to-end test sends a structured agent message to chat, links it to the matching GitHub source/run, and preserves the durable record.
- A relevant GitHub head/check transition produces a de-duplicated chat notification within the service's documented delivery behavior.
- Stale/conflicting source metadata is visibly rejected or flagged; no stale snapshot launches work.
- All tests use synthetic events; no physics runs or automatic merge permission is introduced.
- Document failure/retry behavior, retention and access controls, operational ownership, and rollback/disable procedure.

## Guardrails

No production engine/vendor changes, no science/admission decision from chat content, no automatic experiment launch based solely on a message, and no new parallel research board. Coordinate implementation with PR #221 and the existing Issue #5/#135 workflow.
