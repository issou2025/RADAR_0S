## Project Understanding

*Project description:*
## Goal

Make the app and the website easy for AI agents to use, and keep both on current web standards. Three projects were proposed as the way to get there:

- [A2UI](https://a2ui.org/)
- [UI SDK](https://ui-sdk.dev/)
- [Modern Web Guidance](https://developer.chrome.com/docs/modern-web-guidance)

This issue records what each one is, what Talyx already has, what we really need from each, and the work that follows. It is a proposal to review. Nothing here is decided until the open questions at the end are answered.

## Summary

| Project | What it is | What we need from it | Verdict |
|---|---|---|---|
| Modern Web Guidance 1.0 | Skills for coding agents: web platform practice and browser compatibility data | All of it, as a development tool | Adopt. No code change |
| A2UI v1.0 | A format a bot uses to show real UI (buttons, forms, tables) built from the app's own components | The format and a React renderer, in the chat | Adopt as a new feature, after a spike |
| UI SDK (beta) | A behaviour and component library, an agent bridge, and a skill for coding agents | Nothing today | Do not adopt. Talyx already has a stronger answer for each part |

The largest gain is not in any of the three. Talyx already lets agents operate it through its MCP server, and that server does not yet cover every feature. Closing those gaps is the most direct way to make the app agent friendly.

## What Talyx already has

All of this was checked in the code on `main`.

**Agents operate Talyx through its MCP server** (`src/shared/mcp.ts`, `src/renderer/src/features/bots/mcp.ts`, shipped in #48).

- 22 tools over the roster, folders, pins, rooms, routines and bot details.
- Each tool runs the same use case the screen runs, so the rules stay in one place.
- It listens on the loopback interface only, needs a bearer token, and refuses any request a browser page sent.
- Every bot has it already. An outside agent adds it from Settings, Agents, "Copy the add line".
- Tools that lose data or cost money ask the user in Talyx first: delete a bot, folder, room or routine, add or resume a routine, replace a SOUL, switch to a costlier model.

**Bots already show interactive cards in the chat** (`widgets/chat/ApprovalCard.tsx`, `widgets/chat/ClarifyCard.tsx`). An approval card offers the engine's answers. A clarify card shows a question with choice pills or a text box, over one or more pages. Both are fixed shapes the engine defines.

**The screens are already built for role and name.** `control-talyx` drives the app by ARIA role and accessible name, and the feature map records those names. A dry run of `eslint-plugin-jsx-a11y` (recommended rules) over the renderer and the website found 24 findings in 17 of 147 files. Read one by one:

- 9 are `autoFocus` in dialogs and the composer, which is intended.
- 12 are deliberate patterns: the sidebar's resize separator, the scrollable install log, search results as a listbox driven from the search field, Escape handling on the roster, and `aria-description` on roster rows (the plugin does not know the attribute).
- 3 are `href="#"` on the website's `/design` page, which shows sample buttons and is `noindex`.

No finding is a real defect in the app.

**The website is already readable without JavaScript.** Every route is prerendered (`website/scripts/prerender.mjs`). The home page serves about 6,100 characters of text and 3 JSON-LD blocks to a reader that runs no scripts. The build writes `robots.txt` and `sitemap.xml`. The only missing file is `llms.txt`: that address returns the home page.

## The three projects in detail

### Modern Web Guidance: adopt

It is a set of skills a coding agent loads while it writes code. It changes nothing at run time. It fits both the app and the website. The app targets one browser engine (Electron 44), so the compatibility data matters most on the website.

Install for Claude Code:

```
claude plugin marketplace add GoogleChrome/modern-web-guidance
claude plugin install modern-web-guidance@googlechrome
```

### A2UI: adopt as a chat feature

A2UI lets a bot send a declarative description of a small interface. The app draws it from a fixed catalog of its own components, and no code from the bot ever runs. That is the general form of what the approval and clarify cards do today.

What was checked:

- The engine has no A2UI support in its own source.
- A tool call in the chat carries a name and a label, not a payload (`features/chat/types.ts`), so the gateway cannot deliver a surface to the chat.
- A call to Talyx's MCP server does reach the page, and the page can hold it for up to 10 minutes while the user decides. Approvals already work this way.
- An MCP call carries no bot identity (`McpCall` is `id`, `tool`, `args`), so the page cannot tell which chat should show the surface.
- The engine's plugin API (as installed on the development machine) lets a Talyx-owned plugin register a tool, read the calling bot's profile, and call an MCP server the user allowed. Talyx's two plugins today (`talyx-usage`, `talyx-rooms`) only register CLI commands.

Proposed shape:

1. A new MCP tool, `show_ui`, takes an A2UI surface and the bot it comes from.
2. The chat draws the surface in that bot's transcript with `@a2ui/react`, from a small catalog of Talyx components (text, button, choice, text field, table to start).
3. The user's answer returns to the bot as the tool's result. No answer before the deadline counts as declined.
4. If bots cannot name themselves reliably, a Talyx-owned engine plugin (`talyx-ui`) registers `show_ui` on the engine side, attaches the bot's profile itself, and forwards the call to the MCP server. The engine stays stock.

Rules the feature keeps: the catalog is fixed, a surface is data only, remote images stay blocked as they are in bot messages, and a surface has a size limit.

### UI SDK: do not adopt

It has four parts. Each was weighed against what Talyx has.

| Part | What it offers | Why not |
|---|---|---|
| Behaviours (`@ui-sdk/core`) | Focus, selection, drag and drop, popups, lists | Radix already covers what Talyx uses. A single behaviour can be taken later when a feature needs one |
| Components (`@ui-sdk/react`) | About 55 unstyled components | Swapping the 11 files that import `radix-ui` gives the user nothing new, on a beta API that may still change |
| Agent bridge | `snapshot`, `act`, `query` over the page's components | Talyx's MCP server is the better design: typed arguments, validation, approvals, and no tie to a UI library |
| Skill and `checkPattern` tests | Teach a coding agent the library, check ARIA patterns | Only useful after the components are adopted |

Revisit if shadcn/ui offers UI SDK as a base, or when it leaves beta. Its WebMCP support (a browser's built-in agent using a page's components) may then be worth a look for the website.

## Proposed work

### 1. Development tooling

- [ ] Add Modern Web Guidance to the coding-agent setup for this repo.

### 2. Close the MCP server's gaps

Each row is a use case that exists in the app and has no MCP tool.

| Feature | Use case in code | Note |
|---|---|---|
| Hide a bot | `rosterActions.hide` | `list_roster` reports `hidden`, but no tool sets it |
| Memory and skills | `features/bots/memory.ts` | Read, edit, turn a skill on or off. Deleting asks the user first |
| Usage | `features/providers/usage.ts` | Read only |
| Chat with one bot | `chatActions.send`, `open`, `interrupt` | Bots already reach each other through the engine. The gap is for outside agents only |
| Routines: edit, run now, past runs | `saveRoutine`, `runRoutine`, `listRoutineRuns` | Left out on purpose in #48. Running a routine spends tokens, so it asks the user first |
| Providers, Theme, Modules | `features/providers`, `features/settings`, `features/modules` | Providers hold keys. Proposed: keep out |

- [ ] Add the tools chosen in the open questions, each through its existing use case, with tests that drive the tool.

### 3. A2UI in the chat

- [ ] Spike: `show_ui` as an MCP tool with one catalog component, drawn in the right chat, with the answer returned to the bot. Record whether bots name themselves reliably and how a bot with several chats is told apart.
- [ ] Design, from the spike's findings: the catalog, the plugin or no plugin, the deadline, the limits.
- [ ] Build, with `control-talyx` evidence for the chat screen.

### 4. Website

- [ ] Generate `llms.txt` in `website/scripts/prerender.mjs`, beside `robots.txt`: what Talyx is, the download links, the feature pages, the repository.

### Not planned

- Adopting UI SDK.
- An accessibility lint rule. The dry run found no defect, and the rule would add only exceptions. Revisit if a review ever finds a control an agent cannot reach by role and name.
- Changes to `robots.txt` or `sitemap.xml`. Both exist.
