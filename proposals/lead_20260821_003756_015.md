# Owner direction that is already decided

The study should evaluate implementation details, naming and migration, but the following strategic direction is owner-decided and should be treated as an input constraint rather than something to argue back to the old model.

## 1. SDP must no longer behave like a one-time waterfall implementation plan

Historically, SDP often looked approximately like:

```text
Mandate
  -> Study
  -> Requirements
  -> Architecture
  -> Design Analysis
  -> Design
  -> Implementation plan
  -> Sprints / Iterations / Slices implementing the initial design
```

That was useful for establishing a complete project skeleton, but it tends to make later development feel like it must remain inside the original implementation decomposition.

The desired model is more evolutionary:

```text
Initial project foundation
  Mandate
    -> Studies
    -> Requirements
    -> Architecture
    -> Design Analysis
    -> Initial Design

The initial design establishes the horizontal skeleton:
  responsibilities
  domain boundaries
  major layers
  interfaces/contracts
  persistence/integration boundaries
  cross-cutting constraints

Then product development grows through bounded work:

  Feature
    -> required local study / requirement refinement / design refinement
    -> vertical Slice(s) through the necessary horizontal layers
    -> verification / review / merge

  Refactor
    -> bounded structural objective
    -> Slice(s)
    -> verification / review / merge
```

The initial architecture/design pass should therefore establish enough horizontal structure to prevent accidental architecture, while later **Features** are allowed to introduce new requirements, studies and design decisions without pretending they were all known during the original design phase.

## 2. All implementation work should belong to a Feature or Refactor

The future canonical model should make **Feature** and **Refactor** explicit first-class work types for implementation.

A small Fix may remain useful for genuine corrections, but a new capability should not appear as an unanchored Sprint/Slice merely because the initial project design has already completed.

The study must determine the cleanest hierarchy, for example whether the canonical relationship should become something like:

```text
Project
├── Feature
│   ├── optional bounded Study / requirements / design refinement
│   └── Sprint or execution track
│       └── Iteration
│           └── vertical Slice
├── Refactor
│   └── Iteration / Slice(s)
└── Fix
```

or another evidence-backed structure.

Do not preserve Sprint as the conceptual owner of a capability merely because older SDP versions did so.

## 3. GitHub Issues should become the operational assignment boundary

Recent work has increasingly used GitHub Issues as the durable work request / steering boundary.

The target operating pattern is roughly:

```text
Human owner
  -> ChatGPT Steering Group
      -> creates / refines a GitHub Issue
          -> issue is assigned to a Codex worker/session acting as SDP Master
              -> Master reads repository SDP
              -> creates branch + draft PR
              -> delegates bounded Worker / Architect / Verifier / Reviewer work
              -> updates issue / SDP traceability / PR evidence
              -> returns completion summary
      -> Steering Group inspects actual repository/PR/CI/review evidence
      -> accepts, rejects, or creates the next bounded assignment
```

The study must determine how GitHub Issue identity should relate to:

- Feature IDs;
- Refactor IDs;
- Sprint / Iteration / Slice IDs;
- branch identity;
- draft PR identity;
- `CurrentAssignment` / steering state;
- traceability relations and Ledger events;
- verification and review records;
- handoff.

A Codex session assigned an issue may act as **Master for that bounded issue**, rather than requiring one permanent long-lived Master process for the whole repository.

## 4. ChatGPT Steering Group is now part of the practical operating model

We now use an online ChatGPT session as a repository Steering Group above Codex.

A reusable `steering-group` skill has been designed so a conversation can conceptually boot with a command such as:

```text
/steering-group Hans-Einar/weight_app_flutter
```

The Steering Group should:

- inspect repository evidence;
- understand current SDP state;
- decide the next bounded work item;
- create standalone prompts for Codex;
- inspect Codex summaries against GitHub state;
- inspect PRs, CI and independent review;
- coordinate cross-repository findings;
- stop at meaningful decision boundaries.

The study must determine how this role belongs in canonical SDP terminology and documentation without making ChatGPT itself a repository source of truth.

Repository records remain authoritative.

The study should also recommend whether SDP should have a separate reusable **ChatGPT `sdp` skill** in addition to the Steering Group skill, and what responsibilities should belong to each.

# Cross-repository questions to answer

The synthesis must answer at least the following.

## A. What is a Feature in canonical SDP?

Determine:

- stable Feature ID format;
- Feature folder/location;
- whether one GitHub Issue normally maps 1:1 to a Feature;
- whether a Feature may have multiple issues;
- relationship to Requirements and Design;
- relationship to Sprint / Iteration / Slice;
- how feature completion is verified;
- how a feature is reopened or extended;
- how feature release inclusion is represented.

## B. What is a Refactor?

Clarify when work is a Refactor rather than Feature or Fix, and whether it should use the same issue-driven execution mechanics.

## C. What role should Sprint have now?

Evaluate whether Sprint should remain:

- a first-class persistent hierarchy owner;
- a temporary execution/timebox inside Feature/Refactor;
- optional grouping only;
- or be replaced by another concept.

Do not preserve terminology solely for backwards compatibility.

## D. What exactly is a Slice?

Retain the useful concept of a small **vertical end-to-end capability** through the horizontal architecture.

Clarify:

- entry criteria;
- required contract;
- allowed requirement/design refinement;
- completion evidence;
- relation to PR commits;
- whether one issue may contain several sequential Slices;
- whether a Slice ever deserves its own GitHub Issue.

## E. How should initial project design work?

Formalize the distinction between:

1. initial horizontal architecture/design skeleton;
2. later feature-local refinement;
3. architectural change requiring explicit architecture revision;
4. implementation detail local to a Slice.

The goal is to avoid both extremes:

- waterfall design of the entire future product before implementation;
- architecture-by-accident feature coding with no stable system skeleton.

## F. GitHub Issue contract

Define what a high-quality SDP implementation issue should contain.

At minimum study whether it should include:

- goal;
- why now;
- Feature/Refactor identity;
- authoritative repository baseline;
- scope / non-goals;
- requirements / architecture references;
- expected files/areas;
- invariants;
- safety boundaries;
- verification;
- independent review;
- branch and draft PR expectations;
- stop condition;
- reporting contract.

Determine which fields should live only in the issue and which should be mirrored into a repository `Steering/CurrentAssignment` record for durable machine-readable state.

## G. Codex Master-per-issue model

Define the canonical expectation for an issue assigned to Codex:

- the Codex session acts as Master for the bounded assignment;
- it reads authoritative repository state first;
- it may delegate Workers / Architect / Verifier / Reviewer;
- Workers do not silently expand scope;
- review uses fresh context and exact head identity;
- the Master records evidence rather than trusting chat memory;
- the Master stops at the issue boundary.

Study how this differs from the older assumption of one Master owning an entire project lifecycle.

## H. Steering Group role

Define the Steering Group as a supervisory role above Codex without making it repository-authoritative.

Clarify responsibilities for:

- issue creation;
- architecture/product decisions;
- accepting Codex results;
- inspecting PR/CI/review evidence;
- opening follow-up work;
- cross-repository coordination;
- release readiness.

Determine what should be codified in:

- SDP docs;
- an SDP skill;
- the ChatGPT `steering-group` skill;
- project-local `AGENTS-project.md`.

## I. Studies

Compare the old single-study phase with ActionCam's independent bounded studies.

Determine when SDP should support:

- one broad Study;
- multiple parallel independent Studies;
- convergence gates;
- claim/evidence levels;
- physical validation pending states;
- Feature-local studies long after initial architecture.

## J. Traceability simplification

Assess which relationships truly need stable IDs and machine-readable relations.

The future method should retain truthful traceability without turning every trivial action into bureaucracy.

Identify fields that can be generated automatically by `gh-sdp`, GitHub data or SDP-Analyzer rather than manually duplicated.
