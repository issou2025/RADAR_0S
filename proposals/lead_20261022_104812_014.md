# Autonomous Engineering Implementation Prompt: Complete 3D Character Rigging & Skeletal Animation System

## Repository

**Target:** https://github.com/CompleteDotTech/hatch-pet

**Mission:** Implement a complete, production-grade 3D Character Rigging and Skeletal Animation subsystem that transforms genuine generated or imported 3D character models into reusable, editable, controllable, animation-ready characters.

**Execution mode:** Full engineering implementation, integration, testing, demonstration, documentation, and verification.

**Completion standard:** Working software and verifiable 3D artifacts—not architectural proposals, metadata-only rigs, placeholder implementations, or simulated demonstrations.

---

# 1. Primary Objective

Extend Hatch Pet into a character production system capable of accepting a real 3D character mesh and producing a complete rig with:

- Hierarchical skeletal structures.
- Automatic and manual rigging.
- Bone placement and semantic labeling.
- Skin binding and normalized vertex weights.
- Functional mesh deformation.
- Forward and inverse kinematics.
- Joint constraints and anatomical movement limits.
- Humanoid, quadruped, creature, robotic, and custom rig architectures.
- Facial expressions, facial bones, blendshapes, and morph targets.
- Eye movement, gaze, blinking, hands, fingers, tails, wings, and accessories.
- Retargetable skeletons and animation clips.
- Character proportion correction and scale adaptation.
- Automatic rig validation and motion-range testing.
- Foot planting, grasping, contacts, and attachment points.
- Animation blending, reusable poses, and controllable movements.
- Integration with the existing 416-state character animation catalog.
- Blender-compatible editable rig projects.
- Standards-compliant animated GLB/glTF exports.
- Human-editable corrections when automatic rigging is uncertain.
- Versioning, provenance, review, diagnostics, and repair.
- Automated regression tests and reproducible demonstrations.

The final system must let a user take a character such as a humanoid mascot, dog, winged creature, or robot, rig it, animate it through multiple distinct poses, inspect the resulting deformations, adjust the rig, and export a reusable 3D character.

**A skeletal hierarchy alone does not constitute a finished rig.** Completion requires actual bone influence on real mesh vertices, functional pose evaluation, visible geometry deformation or rigid articulated movement, validated animation playback, and independently loadable exported assets.

# 3. Engineering Principles

The implementation must follow these rules throughout.

### 3.1 Real geometry and real functionality

A successful rig must reference genuine 3D geometry.

Actual vertex positions must change when deform bones move. Rigid mechanical pieces must move through real spatial transforms around correct pivots.

Do not accept:

- Static meshes accompanied only by bone names.
- JSON containing imaginary skin weights.
- 2D images made to appear three-dimensional.
- Rendered pose images without a corresponding animated 3D asset.
- A skeleton that is not bound to the character geometry.
- Animation metadata that cannot be evaluated.
- Hardcoded demo screenshots unrelated to generated artifacts.
- Dummy Blender files without functioning armatures.
- GLB files containing only static geometry while claiming rig support.
- Provider success messages without independently validated outputs.

### 3.2 Deterministic core

Implement a functional local processing baseline.

External AI models may improve landmark identification, segmentation, rigging, or animation generation, but core rig evaluation, skinning, basic IK, validation, Blender processing, and export must work without paid services.

Provider unavailability must not disable import, manual rigging, deterministic automatic template fitting, or local testing.

### 3.3 Recoverability

Preserve original models and rig versions. Support bounded, resumable jobs and selective reprocessing.

A failed skinning operation must not destroy the approved skeleton. A failed export must not invalidate an otherwise valid rig.

### 3.4 Honest uncertainty

Automatic anatomical inference is not always reliable.

When geometry, landmarks, joints, hidden anatomy, proportions, or semantic labels cannot be determined confidently, record the uncertainty and offer an editable correction.

Never silently invent invisible limbs or describe guessed anatomy as measured geometry.

### 3.5 Compatibility

All 3D additions must be additive. Existing 2D functionality must continue to work without changing its established behavior.

Make each layer independently testable.

Expose stable Python APIs between layers. Avoid coupling the rig solver directly to browser controls, Blender's runtime, or any particular model provider.

# 5. Canonical 3D Coordinate and Transform Contracts

Define one canonical internal coordinate system:

- Right-handed coordinates.
- Positive X = character's right.
- Positive Y = up.
- Positive Z = forward.
- Lengths in meters.
- Angles in radians internally.
- Unit quaternions in XYZW order.
- Explicit local and world transforms.
- One consistent matrix multiplication convention.
- Explicit conversion at Blender, glTF, and 2D production boundaries.

Use a documented neutral rest pose. Support different rest poses such as T-pose, A-pose, and anatomically appropriate quadruped or creature stances.

Each bone must expose:

- Stable bone ID.
- Semantic anatomical role.
- Parent bone ID.
- Local rest transform.
- Evaluated world rest transform.
- Local pose transform.
- Evaluated world pose transform.
- Bone head and tail positions.
- Bone length and roll/orientation.
- Deform/control classification.
- Optional mirror partner.
- Rotation/translation restrictions.
- Optional joint constraints.
- Optional IK relationships.
- Confidence and source evidence where inferred.

Ensure local/world transform composition is mathematically correct.

Reject cycles, duplicate IDs, invalid parent links, non-finite values, singular required transforms, invalid quaternions, and inconsistent inverse bind matrices.

Implement tests against independently calculated transformations, not only comparisons between two functions sharing the same implementation.

# 7. Model Import and Geometry Preflight

Support real 3D input from:

- Imported `.glb`.
- Imported `.gltf` with safely resolved local dependencies.
- Existing Blender scenes through a Blender processing adapter.
- OBJ mesh import where geometry and materials are supported.
- Existing generated 3D assets from Hatch Pet's current or future 3D generation subsystem.
- Multi-part and semantically segmented 3D characters.

OBJ is a geometry interchange format and must not be advertised as preserving skeletal rigs, skin weights, or animations.

## 7.1 Import requirements

On import:

1. Verify source origin, format, size, and content.
2. Preserve the exact original source bytes.
3. Decode actual geometry.
4. Identify meshes, primitives, submeshes, and scene instances.
5. Identify materials, textures, UVs, normals, tangents, and morph targets when present.
6. Detect existing armatures, skins, and animations.
7. Preserve compatible existing rig data rather than replacing it automatically.
8. Normalize transforms through documented conversions without silently rewriting approved source geometry.
9. Inspect topology and component connectivity.
10. Compute bounding boxes, surface area, center of mass estimates, and geometric landmarks where applicable.
11. Detect scale ambiguity.
12. Identify potential symmetry planes and anatomical directions.
13. Record unsupported features and source uncertainty.
14. Produce a deterministic preflight report.

Handle multiple mesh primitives and multiple materials.

Support geometrically connected and disconnected pieces, including clothing, armor, eyes, accessories, shells, wings, and segmented mechanical parts.

Do not require watertight geometry for all valid characters. Report non-manifold surfaces, boundary edges, inverted normals, degenerate triangles, and disconnected islands appropriately.

## 7.2 Import preservation

Avoid silently:

- Applying destructive mesh decimation.
- Changing character proportions.
- Merging semantically separate components.
- Flattening existing morph targets.
- Removing source materials.
- Discarding existing animations.
- Converting articulated robot parts into deforming soft tissue.
- Mirroring asymmetric markings or accessories.
- Rescaling without a recorded conversion.

If import is incompatible with a required downstream operation, return actionable diagnostics and offer a bounded repair workflow.

# 11. Skin Binding, Vertex Weights, and Deformation

Use a consistent convention for skin transforms and verify its implementation against the glTF specification.

Support multi-mesh and multi-primitive characters.

## 11.2 Automatic skin weighting

Implement automatic initial weight assignment based on geometry and bone proximity, with improved surface/volume-aware methods where appropriate.

Provide:

- Bone-region initialization.

- Smooth blending across joints.
- Segmentation-aware weighting.
- Heat/diffusion-based weighting where numerically appropriate.
- Weight smoothing.
- Boundary protection.
- Influence pruning.
- Weight normalization.
- Symmetry-aware transfer when permitted.
- Locked/manual weights.
- Unassigned-vertex detection.

A geometry-aware primary approach and a deterministic fallback must both be implemented. If a selected algorithm cannot operate on a particular topology, return a meaningful fallback explanation.

## 11.3 Weight correctness

- Finite values.
- Normalized effective weights.
- No unintentionally unweighted vertices.
- Configurable influence limits.
- Consistent joint indexing.

- Proper handling of disconnected components.

# 22. GLB/glTF Interoperability

Use the Khronos glTF 2.0 specification as the authoritative interchange contract.

Reference:

https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html

## 22.1 Required exports

- Rigged GLB.
- Rigged glTF with associated local buffers/textures.
- Multiple named animations.
- Skin objects.
- Joint hierarchies.
- Inverse bind matrices.
- Bone animation channels.
- Morph targets.
- Morph-weight animation.
- Materials and textures.
- Deterministic coordinate conversion.
- Versioned export manifests.

## 22.2 Correct glTF semantics

Validate:

- `skins`.
- `skins[].joints`.
- `skins[].inverseBindMatrices`.
- Appropriate `skeleton` relationships.
- Skinned mesh references.
- `JOINTS_0` / `WEIGHTS_0`.
- Additional supported influence sets.
- Bone node transforms.
- Animation samplers.
- Animation channels.
- Translation, rotation, scale, and morph-weight targets.
- Buffer/accessor validity.
- Scene hierarchy.
- Finite animation data.

Ensure inverse bind matrix ordering corresponds exactly to the skin's joint ordering.

Use the official glTF Validator, or an equivalently rigorous standards-based validator, as an additional acceptance gate.

## 22.3 Control-rig limitations

glTF is not a universal interchange format for Blender's procedural constraints, IK controllers, drivers, or authoring interface.

Therefore:

- Preserve rich authoring controls in the Blender/native rig representation.
- Bake evaluated motion to standard joint and morph animation channels for GLB/glTF.
- Export available runtime metadata only through documented compatible mechanisms.
- Never claim an arbitrary Blender constraint survives an ordinary GLB export.

Validate the **evaluated animation**, not merely the presence of animation channel names.

## 22.4 Independent reimport

After export, load each GLB using an independent glTF parser or runtime.

Verify:

- Mesh vertices exist.
- Skeleton hierarchy exists.
- Skin weights exist.
- Joint transforms animate.
- Actual evaluated mesh positions change.
- Morph animation works where included.
- Multiple clips are independently selectable.
- Character identity and materials are preserved within documented tolerances.

An exporter reporting success is not sufficient.

## 29.2 Geometry tests

Compare computed vertex positions to independently derived expectations.

At least one test must prove that moving a deform bone changes the bound mesh geometry.

At least one separate test must prove that removing weights, removing the skin, or removing animation channels causes the acceptance test to fail.
