# PRD: Flutter Desktop Frontend V1 — Batch Inspect & Clean (Windows)

## Problem Statement

Users who own content (manuscripts, images, PDFs, office docs, audio/video) need to strip AI provenance marks (Layer A invisible Unicode, C2PA/EXIF/XMP/doc-props, ISOBMFF boxes) before sharing, but the current `watermarks-remover` is CLI/Python-service only (`service/scripts/server.py` on `127.0.0.1:8765`, `service/scripts/clean_file.py`, `inspect_file.py`). Non-technical users on Windows have no drag-and-drop GUI: they must install Python 3.10+, run `make serve` or `python service/scripts/server.py`, and craft `curl` with base64 JSON. Discovery of `suspicious` (unicode/C2PA/stylometry), batch handling (up to 50 files), per-file errors (`kind=unknown`, `looks_binary` guard), and report interpretation (how many `reserved_ignorable`, `has_c2pa`) is manual. Heavy pixel backends (CtrlRegen, Diffusion, SynthID scorer) and Layer B statistical rewrites are intentionally hidden but their absence is not communicated. A desktop app that wraps the existing stdlib HTTP service without reimplementing Python logic would remove this adoption barrier.

## Solution

A Flutter desktop app (Windows first) in `frontend/` as a thin HTTP client over the existing Python service. The app auto-detects service health (`GET /health`), auto-spawns `python service/scripts/server.py --host 127.0.0.1 --port 8765` as a managed subprocess when offline (with onboarding if Python not found), and otherwise connects to an existing endpoint. Core flow: drag-and-drop or file picker for 1–50 files → auto `POST /inspect/batch` (fallback per-file) → list with kind/status chips + detail pane (human-readable Layer A/C2PA/container report, not raw JSON) → `[Clean All → choose output folder]` via `POST /clean/batch` → write cleaned bytes (base64 decode) to chosen folder → per-file success/error + report summary. Options `keep_non_ai_metadata` (default strip all) and `also_layer_a_text` (default true) hide under Advanced. V1 is file-based batch only; no Layer B rewrite, no pixel removal, no text-paste editor — these are V2. Distribution is a zipped `build/windows/x64/runner/Release` bundle released as GitHub Release artifact; no MSIX/Inno installer in V1.

## User Stories

1. As a Windows author, I want to drag-and-drop a `.md`/`.txt` manuscript and see immediately whether it contains suspicious Unicode (Layer A: ZWSP, bidi, `reserved_ignorable` U+2065/U+FFF0 etc.), so that I can clean before publishing.
2. As a non-technical user, I want the app to tell me whether the background Python service is online (`GET /health`) with a green/red dot and one-click [Start Service], so that I don't need to open a terminal.
3. As a user without Python, I want onboarding that explains "Install Python 3.10+" with a link and Retry button when auto-spawn fails, so that I can fix the prerequisite.
4. As a photographer, I want to drop multiple images (PNG/JPEG/WebP/AVIF/HEIC/BMP/GIF/TIFF/SVG) and see per-file kind `image` and whether `has_c2pa`/`has_ai_metadata` was found, so that I can batch-strip metadata.
5. As a compliance officer, I want to drop PDFs/DOCX/XLSX/PPTX/EPUB/ODT/HTML/MD and see container inspection (docProps/customXml, `jumb`/`uuid` boxes, OPF meta) in a detail pane, so that I can audit file provenance.
6. As a podcaster, I want to drop MP4/MOV/M4A/WAV/MP3 and see `kind=av` inspection (`moov/udta`, `LIST INFO`, `id3 `) and clean them, so that AV files are covered.
7. As a batch user, I want to select 1–50 files via picker or drag-drop (desktop_drop) and see a table (filename | kind | status | actions), so that I can manage many files at once.
8. As a batch user, I want auto `POST /inspect/batch` on drop with progress (3/50) and per-file `ok:false` rows shown in red with the service error string (e.g. "unrecognized format; use notes.txt"), with Retry single file, so that one bad file doesn't abort the batch.
9. As a user who drops an unknown extension (e.g. `.xyz` → `kind=unknown`), I want pre-validation in Flutter before sending, showing an inline error and allowing Remove, so that I don't waste a round-trip.
10. As a user who drops a file larger than `MAX_INPUT_BYTES` (256 MiB default, `service/scripts/common.py:16`) or that would exceed `MAX_BODY_BYTES`, I want immediate inline validation without calling the service.
11. As a user protected by the `looks_binary` guard (`service/scripts/server.py:647`), I want a clear message when trying to inspect binary-as-text (e.g. DOCX via text path), directing me to the file route.
12. As a user, I want the detail pane for the selected file to show a human-readable report (unicode counts by kind `reserved_ignorable`/bidi/tag, c2pa actions, container props dropped) instead of raw JSON, so that I can understand what was found.
13. As a user, I want a chip `suspicious` vs `clean` derived from `report.suspicious_total`/`has_c2pa`/`stylometry>=0.65`/`text_detectors.is_watermarked` (server.py suspicious logic), so that I can triage quickly.
14. As a user, I want to expand Advanced settings to toggle `keep_non_ai_metadata` (default false = strip all) and `also_layer_a_text` (default true), and persist them via `shared_preferences`.
15. As a user ready to clean, I want `[Clean All]` to prompt for an output folder (via `file_picker`/`path_provider`), then call `POST /clean/batch` with chosen options, show progress, and write each `cleaned` base64 payload to `output/filename` via `dart:io`.
16. As a user saving cleaned files, I want the app to handle `Permission denied` with a snackbar ("Choose another folder or run as admin") rather than crashing.
17. As a user who prefers safety, I want cleaned files always written to the chosen output folder (never overwrite in place in V1), with original filenames preserved.
18. As a user, I want `[Clear All]` to reset the batch without touching output files, so that I can process a new batch.
19. As a user, I want single-file actions (Inspect again, Clean single, Remove from list) per row, so that I can handle outliers.
20. As a system tray-aware user, I want the app window 1100×700 resizable, Material 3 light/dark following system, with a header showing service version (`GET /capabilities`) and tools availability (`c2patool`/`exiftool`/`qpdf` usability).
21. As an offline user, I want a 5s timeout on `GET /health` with non-infinite retry (manual Retry/Relaunch), so that the UI stays responsive when the service is down.
22. As a release consumer, I want a zipped Windows bundle (`frontend/build/windows/x64/runner/Release` with `watermarks_remover.exe` + `flutter_windows.dll` + `data/`) downloadable from GitHub Releases, with a README noting Python 3.10+ prerequisite.
23. As a CI maintainer, I want a new workflow `frontend-ci.yml` that runs `flutter analyze && flutter test && flutter build windows` on Windows runner, so that frontend regressions are caught.
24. As a developer, I want settings (service URL `http://127.0.0.1:8765` by default, Advanced toggles) persisted and editable in a Settings dialog, so that custom ports/hosts work.
25. As a future V2 user, I want the UI to show a disabled tooltip "Pixel watermark removal (CtrlRegen/Diffusion) coming soon" when hovering advanced pixel options, so that roadmap is discoverable without exposing heavy backends in V1.
26. As a future V2 user, I want a note that Layer B statistical rewrite (Ollama/openai-compatible, `WATERMARKS_REWRITE_*`) is out of scope for V1 and will appear as a Text Paste tab later.

## Implementation Decisions

- **Monorepo layout:** `frontend/` is the Flutter project root (contains `pubspec.yaml`, `lib/`, `windows/`). Add `!/frontend/` and `!/frontend/**` allow-list entries to the deny-by-default `.gitignore` (`/*` plus `!/AGENTS.md` already patched). No separate repo. `flutter create .` inside `frontend/` on Flutter 3.44.7 / Dart 3.12.2.
- **Platform scope V1:** Windows only. `linux`/`macos`/`web`/`mobile` not enabled in V1. Build output is the standard `build/windows/x64/runner/Release` directory, not a single exe.
- **Backend coupling — managed subprocess (hybrid):** Flutter is an HTTP client, not a Python reimplementation. On startup, call `GET /health` (5s timeout). If reachable, use it. If not, attempt to spawn `python` (fallback `python3`, then `py -3` on Windows) executing `service/scripts/server.py --host 127.0.0.1 --port 8765` as a `dart:io Process`, capture stdout/stderr for diagnostics, kill on app exit. If no Python found, show onboarding screen with Python 3.10+ download link and Retry. No bundling of Python runtime or heavy venvs (MarkLLM/MarkDiffusion/CtrlRegen/SynthID ~10GB) in V1.
- **HTTP contract — reuse existing service:** All file operations use the JSON base64 envelope already served by `server.py`. Primary endpoints: `GET /health`, `GET /capabilities`, `GET /openapi.json`, `POST /inspect/batch`, `POST /clean/batch` with `MAX_BATCH_FILES=50` and `MAX_BODY_BYTES` caps. Single-file fallback (`POST /inspect`, `POST /clean`) for retry. Options map `ALLOWED_CLEAN_OPTIONS` (`nfkc`, `aggressive_homoglyphs`, `keep_non_ai_metadata`, `also_layer_a_text`, `remove_pixel`, `strip_all_metadata`, `detect_before/after`) — V1 only exposes `keep_non_ai_metadata` and `also_layer_a_text` in Advanced; `remove_pixel`/`detect_before/after` remain disabled/hidden.
- **UX — single-window 2-panel:** No router. Header: service status dot + version + Settings. Center: DropZone (desktop_drop) with "Drop files here or click to browse" (file_picker) that collapses into a List/Table after files added. Table columns: filename, kind (`text`/`image`/`container`/`av`/`unknown` from `classify_bytes`), status chip (pending/inspected/suspicious/cleaned/error), row actions. Detail pane (right/bottom) for selected file: human-readable report sections (Layer A counts, C2PA/container actions, AV boxes, stylometry if present). Bottom bar: `[Clear All]` and `[Clean All → choose output folder]` with linear progress. Window 1100×700 minimum, resizable, Material 3.
- **State — Riverpod:** `flutter_riverpod ^2.6` with `StateNotifier`/`Notifier` for `AppState` (serviceStatus, isCleaning, files[] as `FileEntry` with fields name, bytes, kind, report, suspicious, error, cleanedBytes). No `bloc` in V1. Service URL and Advanced toggles persisted via `shared_preferences`.
- **Dependencies (V1):** `http ^1.2` (no `dio`), `desktop_drop ^0.6` + `file_picker ^10` + `path_provider`, `flutter_riverpod`, `shared_preferences`, `path`. No `msix`/`updater` in V1.
- **File I/O — base64 in memory:** Read file bytes via `dart:io File.readAsBytes`, validate size vs `MAX_INPUT_BYTES` (256 MiB) and estimated base64 envelope vs `MAX_BODY_BYTES` before sending. Encode `dart:convert base64Encode` for request, `base64Decode` for response `cleaned`. No streaming in V1; cap at 50 files guards memory.
- **Error model — fail-soft per file:** UI mirrors service batch semantics: one entry with `ok:false` and `error` string does not abort the batch. Row turns red, shows `error`, offers Retry. Unknown `kind` and oversized files are pre-validated client-side with inline messages; `looks_binary` guard message is surfaced verbatim.
- **Security — loopback only:** Default `http://127.0.0.1:8765`; if `WATERMARKS_SERVER_API_KEY` set, attach `Authorization: Bearer` header from stored setting. Warn if host not loopback.
- **Distribution — zip bundle:** `flutter build windows` zip uploaded as `watermarks-remover-frontend-windows.zip` via GitHub Releases. No installer signing in V1. Unzip and run `watermarks_remover.exe`.
- **CI:** Add `.github/workflows/frontend-ci.yml` (windows-latest, `flutter analyze`, `flutter test`, `flutter build windows`). No change to existing `ci.yml` for Python.
- **Architecture seams:** Ideal seam count = one. Highest seam is the HTTP service boundary (`WatermarksServiceClient` wrapping `/inspect/batch`/`/clean/batch`/`/health`/`/capabilities`). Existing seam (`server.py` HTTP; tested by `tests/test_http_server.py`, `tests/test_detect_endpoint.py`) is reused; new seam is the Dart `WatermarksServiceClient`. Prefer this seam over lower seams (file drop, base64 codec) for tests.

## Testing Decisions

- **What makes a good test:** Test external behavior at the highest seam, not implementation details. Widget/integration tests should assert: dropping files triggers inspect and renders chips/reports; Clean All writes files; service offline shows dot+onboarding; per-file error rows show `error` and allow retry. Do not test internal notifier fields, private codec helpers, or exact JSON key order.
- **Modules to test:**
  - `WatermarksServiceClient` (Dart) — unit tests with `http/testing` MockClient for `inspect/batch`, `clean/batch`, `health`, `capabilities`, `detect` opt-in, error mapping (`unknown`, `looks_binary`, 413, 401, timeout), base64 round-trip, option filtering.
  - App state (`AppStateNotifier` Riverpod) — unit tests for transitions: add files → pending, inspect success → suspicious/clean, clean success → cleaned, error → per-file error, clear.
  - Widget tests (`WidgetTester`) — DropZone, FileList, DetailPane, Header status, Settings dialog, save flow with mocked `FilePicker`/`PathProvider` and `WatermarksServiceClient` fake.
  - Integration (optional, not blocking V1): run against a real Python service (`python service/scripts/server.py` on ephemeral port) with fixture files from `tests/fixtures/` (text with `reserved_ignorable`, PNG with C2PA, PDF, DOCX) to verify e2e batch.
- **Prior art:** Python service tests in `tests/test_http_server.py` (batch, caps, auth), `tests/test_inspect_file.py`, `tests/test_clean_text.py`, `tests/test_binary_guard.py`, `tests/test_security_hardening.py` establish expected HTTP semantics and size guards to mirror in Dart. Frontend will have `frontend/test/` with `api_client_test.dart` and `widget_test.dart` following `flutter test` conventions; coverage not enforced in V1 but `flutter analyze` must pass.

## Out of Scope

- Layer B statistical watermark rewrite (any `rewrite_text.py` flow, Ollama/openai-compatible backends, `WATERMARKS_REWRITE_*` envs, MarkLLM/Gumbel evaluators) — V1 is deterministic clean only.
- Pixel-domain watermark removal (`--remove-pixel ctrlregen/diffusion`) and Scoring (`REVERSE_SYNTHID_DIR`, `WATERMARKS_SYNTHID_SCORER_URL`, `wr-synthid-score` sidecar) — heavy backends requiring torch/CUDA/~10GB remain Docker-only and hidden in V1 (tooltip only).
- Text-paste editor tab (manual text input → Layer A inspect/clean inline, copy button) — planned V2 #1.
- Before/After diff viewer (split hex/metadata report comparison) — planned V2 #2.
- MSIX / Inno Setup installer, code signing, auto-updater — zip bundle only in V1.
- Linux, macOS, Web, Mobile targets — Windows-only in V1.
- Overwrite-in-place file saves — V1 always writes to a chosen output folder.
- Full offline Python bundling (PyInstaller, embedded interpreter) — requires Python on host in V1.
- Multi-window navigation / go_router / deep links — single window in V1.
- Authentication beyond optional bearer passthrough — no login UI.
