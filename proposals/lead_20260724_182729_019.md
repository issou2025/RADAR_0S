# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Integrate graphify into the wt/worktree + ~/projects setup for agent navigation**

*Project description:*
## Goal

Make the local dev setup genuinely AI/agent-friendly (pi, Claude, Cursor) by combining three pieces that each do one job well, instead of overloading directory structure to do semantic classification (see discussion: numbered pipeline-stage folders under `~/projects/hellofresh/0N-*` are lossy, single-axis, and already leak into a `misc/` bucket).

| Component | Job | Not its job |
|---|---|---|
| **worktrunk (`wt`)** | Workspace lifecycle: create/switch/remove isolated per-branch checkouts, run env-setup hooks, centralize storage | Understanding code, tracking ownership |
| **`~/projects/<owner>/<repo>`** (flat) | Where source repos physically live | Encoding relationships/purpose via folder nesting |
| **graphify** | Semantic layer: turn each repo (and the whole corpus) into a queryable, navigable knowledge graph for agents | Workspace/branch management |
| **TRE API + each repo's own README** | Ownership (squad/tribe/alliance) + purpose truth | Duplicating either into folder names or a hand-maintained registry |

## Why graphify fits

- Pass 1 (tree-sitter, 25 languages incl. SQL with table/JOIN/FK extraction) is **local and free** — no LLM calls for code-only corpora. tardis-community is dbt/SQL/Terraform-heavy, so most of it extracts for $0.
- Pass 3 (Claude subagents) only runs over docs/PDFs/images — this is where cross-repo *relationships* actually get surfaced (e.g. the "tardis family" link between tardis-community/tardis-library/tardis-infrastructure that a folder can never express, since a repo can only live in one folder but can be *referenced* by many).
- Every edge is confidence-tagged (`EXTRACTED` vs `INFERRED` vs `AMBIGUOUS`), so the graph is auditable, not a black box.
- Outputs (`graph.json`, `wiki/` with `index.md`, `obsidian/`) are exactly what an agent (or the user's existing Obsidian vault) wants: a compact, persistent, incrementally-cached structure that doesn't require re-reading raw files every session.
- Ships a `--platform pi` install target, a git commit hook (auto-rebuild, no daemon), and an MCP server (`query_graph`, `get_neighbors`, `shortest_path`, `list_prs`, `get_pr_impact`, `triage_prs`) — all designed for exactly this agent-navigation use case.
- `graphify prs`/`graphify prs --conflicts` gives PR + worktree mapping and merge-order risk (communities shared across open PRs) — a natural complement to `wtclean`'s existing open-PR skip logic.

## Architecture

```
~/projects/<owner>/<repo>/                 flat source checkout (main branch)
  graphify-out/                             per-repo graph (ignored via .gitignore or
    graph.json, cache/, wiki/, GRAPH_REPORT.md   .git/info/exclude for repos we don't own)
  .git/  <- graphify commit hook: rebuilds graph.json after every commit (AST-only, free)

~/worktrees/<owner>/<repo>/<branch>/       ephemeral wt-managed checkout
  graphify-out/  <- seeded from the repo's graph via `wt step copy-ignored` (cache reused),
                    then a cheap `graphify . --update` post-start step brings it current
  .venv          <- symlinked (existing hook)

~/projects/graphify-out/                   NEW: merged, cross-repo master graph
  graph.json      <- `graphify merge-graphs <repo1>/graph.json <repo2>/graph.json ...`
  wiki/index.md   <- single cross-repo navigation entry point

MCP: `python -m graphify.serve ~/projects/graphify-out/graph.json`
  registered in ~/.pi/agent/mcp.json (stdio) -> query_graph / get_neighbors / shortest_path / list_prs
```

## Lifecycle

1. **New repo cloned** -> lands flat under `~/projects/<owner>/<repo>`. One-time: `graphify install --platform pi` (writes agent instructions) + `graphify hook install` (git commit hook).
2. **`wtnew` creates a worktree** -> existing post-start hooks run (venv symlink, `copy-ignored`, VS Code, registry) + NEW: `graphify . --update --no-viz`, cheap because `copy-ignored` already seeded the cache from the base branch.
3. **Committing** -> graphify's own commit hook rebuilds that worktree's `graph.json` automatically. No daemon, no `--watch` process to babysit.
4. **Opening a PR** (the part of the workflow that matters most day to day) -> `graphify prs` / `graphify prs --conflicts` for review-queue triage and merge-order risk.
5. **`wtclean` removes a stale worktree** -> its local `graphify-out/` goes with it; nothing else to reconcile, it's fully regenerable.
6. **Cross-repo view** -> a scheduled job (cron/launchd, or an on-demand `graphify-sync` zsh function) merges every repo's `graph.json` into `~/projects/graphify-out/graph.json`. This is what the standing MCP server actually serves.
7. **Agent use** -> pi/Claude/Cursor query the graph instead of blind grep/read when exploring an unfamiliar repo or asking "how does X relate to Y."

## Open decisions

- `graphify-out/` exclusion for repos we don't control (tardis-community etc.): use a personal `.git/info/exclude` entry per clone rather than touching the shared `.gitignore`.
- Merge cadence: nightly (or on-demand), not per-commit — per-repo graphs already update on every commit; the merge step is for the "big picture" view only.
