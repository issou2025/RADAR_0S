# PRD: Sensor store resilience and silent-failure elimination (iOS SDK)

## Problem Statement

An app integrating the Sahha iOS SDK upgraded from native 1.3.7 to 1.3.9 in production. After the upgrade, the SDK performed exactly one ~30-day historical HealthKit backfill and then stopped collecting HealthKit data permanently. Non-HealthKit device logs kept flowing, the sensor-status callback returned a normal-looking `pending` with no error (which wrapper SDKs surface identically to success), the dashboard showed no sensor state at all, and not a single SDK error was logged — locally or to the API. Re-running the full auth + enable flow, force-quitting, and adding manual Health data all failed to recover collection. The only field remediation available today is deleting and reinstalling the app.

Root cause (confirmed by code audit and empirical decode tests):

1. 43 `SahhaSensor` raw values were renamed between 1.3.7 and 1.3.9 (39 nutrition, 4 reproductive). The enabled-sensor set is persisted as JSON-encoded raw-value strings under an unversioned key in the host app's standard UserDefaults suite, with no migration. 1.3.7 persisted the *expanded* granular set, so any install that enabled nutrition or reproductive sensors has old names on disk. On 1.3.9 (including every 1.3.9 beta), decoding throws for the entire set — one stale name takes down `steps`, `sleep`, and `heart_rate` too. Installs on ≤1.3.6 are unaffected (the renamed values did not exist before 1.3.7).
2. `enableSensors` reads the store inside a do/catch whose empty catch swallows the throw AND skips the store write that would have repaired it. Permissions and collection still start off the in-memory parameter — so backfill succeeds once, and every store-dependent path afterward (launch-time resume, health-check, probe, manual post, status query, diagnostic report) fails silently forever. The status query converts the store failure into `pending`, indistinguishable from a legitimately pending permission request.
3. Independently, the anchored-query timeout (present in **two** byte-identical copies — the data-log coordinator and the tag coordinator, the latter carrying all reproductive and symptom sensors) races a sleeper against a query that supports no cancellation. On timeout the sensor's task slot is wedged for the process lifetime and the HealthKit observer completion handler is never invoked, so iOS suspends background delivery for that type. Large syncs — an initial backfill, or a recovery after weeks of darkness — are exactly where the timeout lands.
4. At least ten distinct code sites swallow these failures without posting to the error API — the SDK's observability was blind to the exact failure class it needed to see. One of them (a swallowed anchor-save failure that does not advance the anchor) can additionally spin an infinite re-query loop. Another (a swallowed keychain read at token-store init) leaves the SDK's synchronous auth snapshot unpopulated, making auth-gated calls — including `deauthenticate` itself — wrongly reject an authenticated user.

## Solution

Make the sensor store impossible to poison, make `enableSensors` incapable of silently skipping its persistence step, make query timeouts non-wedging in both coordinators, and make every previously-silent failure observable — such that:

- Installs upgrading from 1.3.7/1.3.9 self-heal on the first launch of the fixed version that runs with a valid or refreshable auth session, with the user's enabled sensor set preserved (renamed values mapped, not dropped), with no app-side code change and no re-auth required.
- Already-poisoned installs in the field recover automatically when the app ships the fixed SDK.
- Recovery is forward-looking: ongoing collection resumes fully; historical backfill of the dark window is bounded by the SDK's 30-day query horizon, which is intentional product behavior (the SDK never collects data ending more than 30 days back).
- Any similar future fault surfaces in the error dashboard within one session instead of being invisible for weeks.

## User Stories

1. As an app developer, I want SDK version upgrades to never invalidate previously persisted SDK state, so that my users' data collection continues uninterrupted across releases.
2. As an app developer, I want sensor status responses to reflect reality (a broken store must never masquerade as a pending permission), so that I can trust what the SDK reports.
3. As an app developer, I want the SDK to self-heal from corrupted or legacy persisted state on launch, so that affected users recover by simply updating my app rather than deleting and reinstalling it.
4. As an app developer, I want the sensor set my users enabled on an old SDK version preserved across renames, so that users do not silently lose nutrition or reproductive tracking they opted into.
5. As an end user, I want my health data to keep syncing after an app update, so that my scores and biomarkers stay current without me noticing anything happened.
6. As an end user, I want background HealthKit delivery to survive slow or very large syncs, so that a big first import or a post-outage catch-up doesn't permanently break ongoing collection.
7. As an end user, I want manual entries I add in Apple Health to be picked up while the app is open, so that my record is complete.
8. As a Sahha support engineer, I want every sensor-pipeline failure posted to the error API with its throw site, so that I can diagnose a "data stopped" report from the dashboard without requesting device logs.
9. As a Sahha support engineer, I want the diagnostic report to be built and uploaded reliably on cold launch and to carry real per-sensor statuses, so that the dashboard's sensor panel reflects the device's actual state.
10. As a Sahha SDK engineer, I want repeated identical errors deduplicated and capped per process, so that a persistent fault posts a bounded number of error logs rather than flooding on every trigger.
11. As a Sahha SDK engineer, I want the persisted sensor-set decoding to tolerate unknown values and to distinguish foreign (non-SDK-shaped) data from SDK data, so that renames, host-app key collisions, and partial writes can never re-create this failure class — and so that the SDK never overwrites data it does not own.
12. As a Sahha SDK engineer, I want a regression test that replays a real 1.3.7-era persisted blob through the current store, so that this exact incident can never ship again.
13. As a Sahha release owner, I want the fix shipped in a single stable release that unpinned integrators resolve automatically, so that remediation reaches the fleet without manual pin edits.
14. As an app developer, I want a query timeout to abandon cleanly and re-arm on the next trigger, so that one slow HealthKit page fetch doesn't take a sensor offline for the whole session.
15. As a Sahha support engineer, I want recovered installs to resume incrementally from their existing anchors, so that recovery doesn't trigger duplicate uploads or a redundant 30-day re-backfill.
16. As an app developer whose app launches offline, I want the SDK to retry its authenticated bring-up when connectivity returns, so that a transient launch-time token refresh failure doesn't cost a whole session of collection.
17. As a Sahha support engineer, I want deauthentication's effect on the enabled-sensor set documented, so that I can tell integrators exactly which flows require calling enableSensors again.
18. As an app developer, I want `deauthenticate()` to succeed and fully clear SDK state no matter what the SDK currently believes about authentication, so that my logout flow is reliable and support can use "deauth, re-auth, re-enable" as a dependable clean-slate remediation.

## Implementation Decisions

Decisions are numbered for review traceability; each was validated (and in several cases corrected) by three independent codebase reviews.

- **D1 — Single release vehicle: the next stable release (1.4.0).** The install docs steer SPM users to an up-to-next-major range and CocoaPods users to the latest version, so unpinned integrators resolve the highest *stable* automatically — a 1.3.10 hotfix would have effectively no audience once 1.4.0 exists, would omit later reliability fixes (the enable-sensors callback-hang fix), and is not a clean cherry-pick (the timeout utility and the throw-site error provenance do not exist at the 1.3.9 tag, and the enable-sensors region diverged). A bespoke 1.3.x build remains available on request for a named integrator who cannot absorb 1.4.0, but it is not published as a supported line. The wrapper SDKs (which pin native versions exactly, in lockstep with Android) follow with their own stable releases.
- **D2 — Lenient decoding, not a one-shot stamped migration.** The sensor store decodes the persisted set as raw strings and maps them tolerantly on every read; unknown values can never make decoding throw. This is effectively a migration keyed on data *shape* rather than a version stamp — strictly better, because a stamp cannot detect foreign writes to the store's unnamespaced key in the host app's shared UserDefaults suite, and shape-keyed repair has no "did the migration run yet?" ordering state. (Note: this does not protect *downgrades* — older SDKs still decode strictly; that is accepted and documented.) Three subtleties are part of this decision: the membership check (`hasSensor`) must route through the same lenient read rather than its current cache-only path (which silently reports every sensor absent after a failed init, breaking demographics and device-lock gating even after repair); a value under the key that is not SDK-shaped data (e.g. a host-app write of a non-Data plist type) is reported as an anomaly but **never rewritten or deleted** — the SDK must not clobber data it does not own; and read + map + rewrite happen as one actor-isolated operation so a concurrent enable cannot interleave. On a healthy store the lenient path is a pass-through and the canonical rewrite is a no-op.
- **D2a — Prerequisite: make the storage seam real.** The storage protocol's data/object read-write conveniences are currently extension-only members hardcoded to the standard UserDefaults suite, so injected test doubles are silently bypassed on exactly the paths this PRD changes. They become protocol requirements with default implementations routed through the protocol's primitive get/set, which also makes the existing in-memory storage mocks in the test suite actually intercept reads. This is a prerequisite for nearly every test in this PRD.
- **D3 — Renames are mapped, unknowns are dropped.** A static, explicitly-enumerated 43-entry rename table (39 nutrition, 4 reproductive — verified injective, no collisions with current or other old names, and no mechanical derivation rule exists) maps old raw values to their current names so users keep the sensors they enabled. Strings with no mapping are dropped from the decoded set. Mixed old+new contents are handled by union-with-dedup (safe given injectivity). Both anomaly kinds (mapped renames, dropped unknowns) are reported through the error logger with the anomalous values and counts — never the full decoded set — and the store immediately rewrites itself in canonical form so the lenient path fires once per anomaly. *Rejected alternative — preserve unknowns for forward compatibility: actively harmful; a preserved unknown is exactly what makes an older binary throw on downgrade, and the wrapper boundary already drops unrecognized names on the next enable anyway.*
- **D4 — `enableSensors` write-always ordering with guards.** The persistence write of the newly requested set is unconditional: the previous set is captured first via the lenient read (a failed read is treated as empty), the new set is written, and teardown of removed sensors follows as best-effort with each stop call independently caught and reported. Two guards: an empty expanded set is rejected before any write or teardown (today it persists an empty set, tears everything down, and *then* throws); and a new set containing zero HealthKit-backed sensors while the previous set had some persists the new set but skips HealthKit teardown and posts an error (preventing the silent total-teardown cliff that the recent non-HealthKit-sensor fix made reachable). Legitimate narrowing between HealthKit-backed sets is untouched. Stated consequence: if teardown partially fails, removed sensors may keep collecting for the process lifetime (fail-open); the health check does not reap extras.
- **D5 — No silent failures in the sensor pipeline.** Ten sites are made observable: the enable-sensors store phase; launch resume; the sensor query path; the health-check listener; the probe listener; the diagnostic report builder (which needs the error logger added to its dependencies — it currently has none); the status query (which must stop converting a store failure into `pending` — with the lenient store this path can no longer throw, and status reflects the repaired truth); the store's own init-time decode (handled structurally by D2's lenient read plus deferred anomaly report); the swallowed anchor-save failure in both coordinators — which today not only hides the error but fails to advance the anchor, re-querying the identical page in an infinite loop; a save failure must break the query loop and post; and the token store's init-time keychain read, whose swallowed failure leaves the synchronous auth snapshot unpopulated so auth-gated calls wrongly reject an authenticated user (the token store already has the logger injected). To make this safe fleet-wide, the error logger gains an in-process dedup: a synchronous, lock-guarded gate placed before the posting task is spawned, keyed on the *resolved* error origin (the throw site captured by the error type, not the forwarding call site), with a hard cap on distinct signatures per process so per-sensor error families cannot flood. Scope note: the dedup set lives per logger instance (reset on deauthentication) — acceptable. Existing behavior note: the error logger's circuit-breaker gate is currently dead code (the breaker is never registered in DI), which means error posts always reach the network; do not "fix" that registration as a side effect of this work without deciding the drop-behavior deliberately.
- **D6 — Timeout without wedging, in both coordinators, shipping in the same release as D2.** Cancellation is the load-bearing fix: the anchored-query service gains cooperative cancellation whose handler both stops the underlying HealthKit query *and* resumes the pending continuation with a cancellation error behind a single-claim gate (stopping alone never fires the query's handler and would leak the continuation forever); the query object is held in a lock-protected box since it is created inside the continuation closure. The task-group race is replaced with the existing abandoning-timeout utility as the belt-and-braces wrapper, in **both** the data-log coordinator and the tag coordinator (the tag copy carries all reproductive and symptom sensors — including four of the 43 renamed values — so fixing only one lets the recovery path re-wedge). On timeout: the caller returns, the per-sensor task slot is released, the observer completion handler runs (its existing defer becomes reachable), and the timeout is posted with the sensor name. The observer's error path already invokes the completion handler; it gains logging only. Sequencing constraint, stated explicitly: a recovered install's first sync is a large multi-page query — precisely the wedge trigger — so D6 must ship with D2, never after it.
- **D7 — Anchor continuity via read-time alias, not a key migration.** Anchor loads already try a legacy key prefix before giving up; the same pattern extends with a rename-table lookup (old-name key, and the legacy-prefixed old-name key) so recovered sensors resume incrementally, and the next save naturally writes the canonical new-name key. No one-shot migrator, no idempotency state, no clobber risk. Justification: re-backfills are only *mostly* idempotent — log IDs derive from local-wall-clock timestamp formatting with no fixed timezone, so re-normalization across a timezone or DST change yields genuinely different IDs (and server-side upsert-by-ID is an unverified inference), making avoided re-uploads a correctness matter, not a bandwidth nicety. The anchor-date key family is excluded: its only consumer is the structurally dead activity-summary upload (separate ticket).
- **D8 — Deterministic probe-then-report, not listener ordering.** The sensor probe is extracted from its lifecycle listener into a service the diagnostic pipeline can await directly: when the report builder finds no in-memory statuses, it runs the probe first, then builds. Additionally, the diagnostic build-and-upload is invoked explicitly once at the tail of the SDK's authenticated bring-up, because on cold launch the resume lifecycle event can fire before listener registration completes and be lost entirely — today the report may simply never be built in the session that matters most. The probe gains a bound (per-sensor timeout and an overall cap) since recovered installs can carry 100+ expanded sensors, and probe results merge into (rather than replace) existing statuses. *Rejected alternative — reordering listener registration: the lifecycle dispatcher spawns one unstructured task per listener with no ordering guarantee, and the probe's event doesn't fire on cold launch at all; ordering by registration cannot work.*
- **D9 — Overwrite semantics stay, and get documented.** `enableSensors` keeps its declarative overwrite behavior, including narrowing — but that behavior is currently documented nowhere, so the README gains an explicit statement of it (call it with the full desired set; the store is replaced, removed sensors stop). The D4 guards handle the destructive edge cases; the diagnostic report (post-D2 always carrying the real effective set) makes accidental narrowing visible to support. Support-facing note: the report carries the *expanded* granular set, so a caller's single umbrella sensor appears as its expansion.
- **D10 — Authenticated bring-up survives offline launches.** Recovery (and all lifecycle listener registration) is currently gated on a launch-time profile-token validation that performs a network refresh when the JWT is expired; a cold launch offline means no resume, no listeners, and no retry for the entire process. When stored tokens exist but the refresh fails transiently, the SDK retries the authenticated bring-up on the next app-resume/foreground rather than staying dark all session. (Genuinely unauthenticated installs are unaffected.)
- **D11 — Health-check re-registration is bounded to missing sensors.** The health check currently responds to any missing observer by re-registering *all* sensors, and re-registration overwrites the observer store entry without stopping the previous query — a leak that only becomes reachable once this fix un-breaks the health check, on sets of 100+ sensors. Re-registration is limited to the sensors actually missing.
- **D12 — Deauthentication's effect is documented, not changed.** Deauth disposes the sensor store by design (the enabled set is cleared with the account); after re-authentication the app must call `enableSensors` again. The self-heal acceptance criterion explicitly does not cover installs that deauthenticated while poisoned — for them the store is already empty and clean, and the normal enable flow applies.
- **D13 — Deauthentication becomes idempotent, with a deterministic purge.** The auth-required gate on `deauthenticate` is removed: logout is a convergent operation that must succeed whether or not the SDK currently believes it is authenticated. Today the gate checks a synchronous auth snapshot that is populated only when the token store happens to have been resolved and its keychain read succeeded — so calling deauth early after configure, or after a failed keychain read, wrongly rejects an authenticated user, cleans nothing, and hands the wrapper an error that fire-and-forget app code never sees (a plausible contributor to the incident's failed recovery attempt). Removing the gate alone is not sufficient: the container-reset purge currently disposes only services that happened to be *resolved* in that container instance, so state can survive deauth on a session where the authenticated bring-up never ran. The purge therefore becomes deterministic — an explicitly enumerated clear of all SDK-owned persisted state (sensor set, anchors, tokens, queues) that does not depend on resolution order. Deauth still requires `configure` (it re-configures afterward), and it performs no server call, so no authentication is genuinely needed. Changelog notes the behavior change: deauth on an unauthenticated SDK now succeeds as a no-op-plus-purge instead of erroring.

## Testing Decisions

Good tests assert **external behavior at module boundaries** — what is persisted, what is posted, what status is returned, whether collection restarts — never internal call sequences. All tests run via the iOS-simulator suite (the package is iOS-only; `swift test` does not work; there is no CI test gate, so the suite must pass locally before push). D2a is the prerequisite that makes the store and anchor seams actually mockable — several existing in-memory storage mocks are silently bypassed today.

- **Rename table completeness** (the single test that prevents recurrence): a fixture embedding the 43 exact 1.3.7 raw values; assert every one maps to a current sensor, the mapping is injective, and no old name equals any current raw value. Plus the incident repro: a real store seeded with a 1.3.7-era JSON blob returns the mapped set, rewrites canonically, and reports once.
- **Store edge cases**: absent key; non-Data value under the key (reported distinctly, not rewritten, not deleted); mixed old+new contents (union-dedup); healthy store (pass-through, no rewrite); membership check consistent with the lenient read.
- **`enableSensors` ordering**: a throwing store read still persists the new set and starts both coordinators; a teardown failure doesn't block the write; empty-set and zero-HealthKit-backed guards behave as specified; failures posted. Prior art: the non-HealthKit-sensor-permissions tests' manager harness (in-memory sensor store + stub coordinators + stub logger).
- **Timeout/wedge regression, both coordinators**: a never-completing anchored query returns via timeout, releases the sensor's task slot (a second trigger issues a fresh query — the direct proxy for the observer completion handler firing), stops the underlying query, and posts with the sensor name. A failing anchor save breaks the loop instead of spinning. Prior art: the date-cutoff tests' scripted anchor-query service and coordinator factory, extended with a never-returns mode; the tag coordinator gets a mirror test.
- **Status truthfulness**: after a lenient read of a poisoned blob, the status query returns enabled (not pending) once permissions are granted.
- **Anchor alias**: loads resolve through new-name, old-name, and legacy-prefixed keys in order; the next save writes canonical; fresh installs unaffected.
- **Error-logger dedup**: identical resolved-origin signatures post once per logger instance; distinct signatures post independently; the distinct-signature cap holds; forwarded errors dedup on throw site, not forwarding call site. (The existing mock logging service needs a count/drain accessor for negative assertions.)
- **Launch recovery, end-to-end (two halves, simulator-safe, no HealthKit entitlements)**: store half — real store seeded with the poisoned blob, real manager with recording coordinators; resume delivers the migrated set and canonicalizes storage. Arming half — real observer service over the mock health store (extended with background-delivery overrides); one executed query per sensor.
- **Deauth population**: after deauth + re-auth, the store is empty, resume is a no-op, and a fresh enable works — pinning D12's documented behavior.
- **Deauth idempotency (D13)**: deauth on an unauthenticated SDK succeeds and clears all enumerated persisted state; deauth called immediately after configure (before bring-up completes) succeeds and purges; the purge clears state even when the authenticated services were never started in that session (the resolution-order gap).

## Out of Scope

- Changing the 30-day query horizon: it is intentional product behavior that the SDK never collects data ending more than 30 days back, so recovery backfilling at most 30 days of a dark window is by design, not a limitation to fix. (No separate ticket.)
- Log-ID timestamp formatting being timezone-dependent (the root of the duplicate risk D7 works around) and verification of server-side upsert-by-ID — separate ticket.
- The structurally dead activity-summary upload (`postInsights`) — separate ticket; it also settles which anchor key family D7 can ignore.
- Flutter/React Native wrapper changes (configure error propagation; surfacing `pending` distinctly; the wrapper's silent downgrade of unknown native statuses) — separate repos. Note: with this PRD, the native status becomes truthful, so wrapper work is additive, not blocking.
- Namespacing the SDK's UserDefaults keys — deferred safely *because* D2 treats non-SDK-shaped values as untouchable.
- Persisting per-sensor probe statuses across launches (D8 covers cold-launch behavior without it).
- The equivalent rename/persistence audit for the Android SDK — separate repo, flagged for triage.

## Further Notes

- **Population matrix** (who recovers, verified against the code): fresh installs and healthy 1.3.9/1.4.0 installs — unaffected (lenient path is a pass-through). 1.3.7-or-1.3.9-poisoned installs upgrading to the fixed release — recover on first launch with a valid/refreshable session, keeping their enabled set and anchors. Installs that deauthenticated while poisoned — store is already clean; they follow the normal enable flow (D12). Installs dark for >30 days — ongoing collection resumes fully; history beyond the 30-day horizon is not backfilled (intentional product behavior).
- **Sequencing**: D2a → D2/D3/D4/D5 and D6 are one release unit; D6 shipping later than D2 would let recovery syncs wedge. D7, D8, D10, D11, D13 belong in the same release but are independently mergeable. README work (D9, D12) accompanies the release notes.
- **Rejected alternatives** (recorded so review doesn't re-litigate): delete-the-poisoned-key one-liner — invalid, because apps are not instructed to call `enableSensors` every launch and the store would stay legitimately empty forever; preserve-unknown-values — harmful on downgrade and defeated at the wrapper boundary; version-stamped migration — cannot detect foreign writes and adds ordering state; 1.3.10 as the published remediation vehicle — no resolvable audience and a dirty cherry-pick; listener registration reordering for D8 — the dispatcher provides no ordering.
- **Field remediation before release**: delete + reinstall the app (clears the poisoned store). Integrators mid-rollout of 1.3.9/1.4.0-beta should hold for the fixed release.
- **Backend follow-ups** (separate systems): confirm which endpoint feeds the dashboard's sensor panel; after this fix, an empty enabled-sensor set in diagnostics becomes a meaningful alert signal (today it conflates "poisoned store" with "nothing enabled").
