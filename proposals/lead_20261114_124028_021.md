## Classification / scope

**Research / security preflight / P2 — feasibility only, NOT a request to embed a second security scanner in 007.**

Question: before `o7 run` lets a coding agent interact with a **new/untrusted repository**, can a lightweight, static-only intake step identify repository-controlled execution surfaces and stop the run from silently crossing the trust boundary?

Why here: 007's [README](https://github.com/PhysShell/007#readme) documents a disposable `git worktree` and autonomous agent execution with a deny-list; a worktree isolates changes to tracked files, **not** credentials, network egress, host processes or malicious tool instructions. Generic VM/sandbox discussions alone do not inventory what the repo is asking the agent/toolchain to execute.

**Scope separation:**
- [#74](https://github.com/PhysShell/007/issues/74): universal change admission / proof-carrying change, broader architecture.
- [#53](https://github.com/PhysShell/007/issues/53): external sidecar + sandbox process boundary.
- [#44](https://github.com/PhysShell/007/issues/44): 007 should **invoke evidence adapters**, not own supply-chain detection logic.
- ScenarioBox (concept only; **no verified project repository**) is a possible future caller of the same independent intake adapter for one-click manual test environments; this issue does **not** authorize building ScenarioBox or stretching 007 into a VM product.

## Real-world motivation and evidence

- [tayvano/lazarus-bluenoroff-research](https://github.com/tayvano/lazarus-bluenoroff-research) aggregates incident reports and examples of malicious developer projects; specifically [VS Code task cases](https://github.com/tayvano/lazarus-bluenoroff-research/blob/main/hacks-and-thefts/vscode-hacks.md) and [fake job coding tests](https://github.com/tayvano/lazarus-bluenoroff-research/blob/main/hacks-and-thefts/braintrust_job_dev_scam.md).
- [VS Code Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust) disables automatic task execution in Restricted Mode, but this is an IDE boundary, **not** a protection offered by Git worktrees or by generic CLI agents.
- The tayvano repository also contains **live malicious sample archives**. **Do not clone/sample-execute them** for this experiment, fetch them via a tool-enabled agent, or put them in the 007 repo/CI. Use public **textual incident descriptions** to derive harmless inert fixtures only; attribution to DPRK is not assumed for every report.

## Candidate preflight threat model

A repo can be readable but dangerous to *build, install, run, trust in an IDE or grant to an agent*. Candidate execution surfaces to inventory (not exhaustive):
- `.vscode/tasks.json` auto-run (`runOn: folderOpen`), debug/launch configurations and IDE extension recommendations.
- `package.json` lifecycle scripts (`preinstall`/`install`/`postinstall`, etc.) and transitive package scripts; `npm ci` is **not** a read-only operation.
- Python build backends/legacy `setup.py`, Makefile/npm scripts; `dotnet` MSBuild custom tasks/targets; CI/actions/workflows and custom runner hooks.
- Shell command chains, network downloads piped to interpreters, secrets/SSH/cloud-credentials access, filesystem writes, persistence and process spawning.
- Repo-owned `AGENTS.md`/agent settings/prompts or MCP/tool manifests that might trick an autonomous agent into treating untrusted instructions as authority.
- Opaque/transitive execution and unsupported languages must produce `UNKNOWN`, **not** a claim that the repo is safe.

**Critical distinction:** this is a *static, opt-in risk inventory*. A warning is not evidence that a project is malicious; lack of a warning is not proof of harmlessness. No automatic execution during inspection.

## Gate 0: overlap and baseline before implementation

1. Inspect the exact current 007 run setup, existing permission/sandbox boundaries and extension/gate APIs; distinguish stated design from enforced restrictions.
2. Compare at least [DataDog/guarddog](https://github.com/DataDog/guarddog), [safedep/vet](https://github.com/safedep/vet), and existing repository-intake scanners (e.g. [preflight](https://github.com/howardhsieh/preflight)) on their **actual supported inputs**. Package scanners are not automatically complete repository/IDE/agent scanners.
3. Choose whether the right home is an **external read-only adapter** called before agent launch, an OwnAudit profile, or a ScenarioBox security hook. Do not introduce a new scanner library into 007 if an existing check suffices.
4. Predeclare STOP/GO thresholds and legal access constraints. No network scanning or reputation claims beyond permitted public evidence.

## Minimal reproducible spike (safe fixtures only)

- Prepare **6–10 inert, hand-audited fixtures** covering: malicious-looking autostart (inert command), legitimate task, package install hook, nested/transitive configuration, agent-instruction injection as data, network/effect chaining, missing/unsupported config.
- Source linkage: case type → public textual incident report → synthetic fixture → expected **execution path** → scan report.
- Detect **entry point → trigger → command/tool → potential effect** (host filesystem/network/credential read), including whether executing it requires explicit user trust/approval.
- Use `Risk / Needs review / Not observed / Unknown` with evidence anchors and completeness limits. Never emit `SAFE` for missing coverage.
- Compare the adapter with baseline(s) for **unique true detections, false positives, missing coverage, scan time and analyst effort**; preserve negatives and unverifiable cases.
- If justified, integrate via an explicit **pre-run optional gate** with `STOP/DEFER` when inspection cannot complete, independent of agent output. Do not make it mandatory until compatibility and fail-closed semantics are proven. Agent must not override preflight verdict.
