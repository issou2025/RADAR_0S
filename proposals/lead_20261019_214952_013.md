## Project Understanding
You need assistance with: 
**Question about provenance: shipped kexts use com.nullmoth.* identifiers, and NVRMAGDC.kext is byte-identical to nullmoth-nvidia-2.3.7**

*Project description:*
I inspected the released `Tauri_Silicon_Driver.dmg` (v2.0.0, 290,651,574 B, `sha256 9c789ccb…bfcbd3`) read-only, without running the installer, and compared it against the public `nullmoth-nvidia-2.3.7.tar.gz`. Several things do not match the README's description of this project as an independent rewrite that is "not affiliated with, maintained by, or connected to the authors of the previous/legacy driver". I would like to ask for clarification before drawing any conclusion.

All of the checks below are reproducible from the two public artifacts alone; commands are at the end.

---

### 1. The shipped kernel extensions identify themselves as NullMoth

`payload/Extensions/*/Contents/Info.plist` in the DMG:

```
com.nullmoth.NVRM
com.nullmoth.NVRMFB
com.nullmoth.NVAccel
com.nullmoth.NVRMAGDC
```

and `CFBundleShortVersionString` is `0.1`.

The `NVRM` binary in the DMG contains this string:

```
nvidia id: NVIDIA UNIX Open Kernel Module for x86_64 610.57.04 Release Build (NullMoth Systems)
```

The DMG's own `src/tauri-watchdog.sh` checks `kextstat -b com.nullmoth.NVRM`.

Could you explain why a project described as an independent rewrite ships extensions under another project's bundle identifiers and version line?

### 3. Symbol tables overlap 99.84 %

Parsing the Mach-O symbol tables of the two `NVRM` binaries (DMG vs. the 2.3.7 release):

| | unique symbols |
|---|---|
| DMG `NVRM` (16,781,168 B) | 33,737 |
| NullMoth 2.3.7 `NVRM` (16,810,832 B) | 33,754 |
| **shared** | **33,682 (99.84 %)** |
| DMG-only | 55 (all `__ZL*` internal statics, e.g. `nv_pv_ring`, `nv_pv_head`) |
| 2.3.7-only | 72 (almost all external imports, e.g. `IOMallocAligned`, `SHA1Init`) |

A 99.84 % symbol overlap with differences confined to internal statics and external imports is what you get from the same source tree built with a different configuration — not from an independent implementation.

Note that the DMG's build is also *older* than 2.3.7: its `NVRM` looks for firmware at `/Users/Shared/nvfw/nvidia/610.57.04/`, while NullMoth moved that to `/Library/NullMoth/nvfw/…` in commit `ef9f11f` (2026-10-18 04:13, `v2.3.7~15`).

```

Building NVRM.kext...
```

Three `Info.plist` files, no executables. `kext/Makefile` contains no compiler invocation — the rule body is `cp $@/Info.plist`.

The published sources also declare `com.taurisilicon.driver.*` v2.0.0, while the shipped kexts are `com.nullmoth.*` v0.1. So the README statement that "the complete C++ IOKit kernel extension source tree is provided directly in the `kext/` directory … can be audited and built" does not describe the artifact users actually install. Whatever one audits there is not what one runs.

### 5. `tauri-smi` does not read any sensor

`src/tauri-smi`, lines 62–67:

```python
# Approximate die temperature and load profile
usage_factor = min(max(vram_used / float(max(vram_total, 1)), 0.05), 1.0)
gpu_util = int(usage_factor * 35) + 6
temp_c   = 38 + int(gpu_util * 0.22)
fan_pct  = 35 + int(gpu_util * 0.20)
power_w  = 26 + int(gpu_util * 0.45)
```

There is no sensor read anywhere in the script. Yet the README presents this output as a "live terminal dashboard of your graphics card (temperatures, clocks, VRAM usage …)" and includes a sample panel showing `39C`, `28W / 125W`, `36%` fan. Those numbers are generated by the formulas above.

### 6. Benchmark claims contradict each other

`README.md`: *"we deliberately do not publish synthetic or simulated benchmark numbers"*.

`docs/architecture.md`, line 5: *"1830.3 GFLOPS FP32 Compute (+42% к стоку) | 164 FPS в Minecraft"*.

Which is the project's position?

### 7. Licensing

NullMoth's `LICENSE` is **PolyForm Noncommercial License 1.0.0**. Its `## Notices` section requires that *"anyone who gets a copy of any part of the software from you also gets a copy of these terms or the URL for them above"*.

This repository is MIT-licensed (`Copyright (c) 2026 susanya27 & gllevnP`), and the DMG contains no PolyForm terms or URL. If the shipped binaries are built from NullMoth's source, on what basis are they redistributed under a different license? Note that PolyForm NC also does not permit sublicensing, so MIT redistribution would not be available regardless of whether the distribution itself is commercial.

### 8. The installer rewrites every ESP on the machine

`src/patch_opencore.py`:

- `mount_efi_partitions()` walks `diskutil list` and mounts **all** EFI system partitions
- then iterates `/Volumes/*/EFI/OC/config.plist` and rewrites each one with `plistlib.load` / `plistlib.dump`
- adding `nvfb=1 nvaccel=1 nvfbheads=4 -nvkmsnosmooth amfi=0x80 amfi_get_out_of_my_way=0x1 ipc_control_port_options=0`
- and setting `csr-active-config = <430a0000>`

By contrast, NullMoth's own `package/install.sh` deliberately does not touch OpenCore — it prints `NOTE: boot-args lack 'nvfb=1' — add it in your OpenCore config.plist (README: Install — by hand)` and leaves the decision to the user. It also validates the result with a `kmutil create` rehearsal and `kmutil inspect` before committing, and keeps a rollback path.

Two concerns here:

1. On a machine with a second, known-good EFI on a USB stick (a common rescue setup), this silently modifies the rescue copy too — the one thing a user relies on when a boot experiment goes wrong.
2. `plistlib.dump` rewrites the whole plist, which reorders keys and loses formatting. For `config.plist` that makes a later diff unreadable, and this project is installed into a boot path where diffing against a known-good config is the primary debugging tool.

Would you consider requiring an explicit `--config <path>` instead of enumerating `/Volumes/*`, and keeping the original formatting?

---

### Not a claim I am making

I did not find any network access, persistence beyond the documented `com.taurisilicon.watchdog` LaunchDaemon, or credential access in the shipped binaries. The string-set difference between the two `NVRM` builds contains no URLs, socket calls, `base64`, `LaunchDaemon` paths, or keychain references. So this is a question about provenance, licensing and installer behaviour — not an accusation of malware.

I also want to be precise about what *does* hold up in the README: the bundled GSP firmware is genuine (`gsp_ga10x.bin` 84,310,168 B and `gsp_tu10x.bin` 29,381,504 B are real ELF/RISC-V blobs), and the bundled Mesa NVK / NVMTLDriver payload is real. The engineering in the payload is not the issue. The provenance claim is.
