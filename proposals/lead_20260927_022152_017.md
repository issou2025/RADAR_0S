# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Add MSP-based explicit Muse session continuation with truthful continuity reporting**

*Project description:*
## Objective

Continue an explicitly identified Muse Code session through MSP without substituting a fresh session or interactive terminal state. Preserve the caller-requested execution mode and Auto-Coder's repository/Git-state safety boundary on every turn.

## Context

PR #5402 in `kitamura-tetsuo/outliner` exposed a concrete capability gap in the Muse reviewer path. Muse Spark returned an invalid `dynamic_check_requested` value; Adversarial Validator correctly entered its bounded target-correction flow, but the correction requires an explicit provider session. The current `MuseClient` runs `muse exec` as a one-shot subprocess, does not expose a provider session ID, and does not implement `continue_session()`, so the correction terminated with `Reviewer target correction could not continue without an explicit session`.

The generic client and backend-manager contracts already exist: `LLMClientBase.continue_session(session_id, prompt, is_noedit=...)` is provider-owned, `BackendManager.continue_session()` records whether the exact requested session was actually resumed through `_last_continue_session_resumed`, and adversarial review managers disable global automatic session resume in favor of their PR-scoped reviewer-session lifecycle. This Issue should fill the Muse adapter capability gap rather than redesign those authorities.

Muse Code's published Muse Session Protocol (MSP) provides the missing provider boundary. `session/start` creates a durable session and returns its canonical `sessionId`; `session/resume` loads exactly a stored session and returns its session metadata, history mode, pending requests, and a new view cursor; a new `muse serve` host can resume a session created by a previous host process. The official Python SDK exposes the same lifecycle through `MuseClient.start_session()`, `resume_session()`, and `Session.send_user_turn()`.

Current Muse behavior that must remain protected includes command-execution-CWD binding, timeout/usage-limit classification, configured alias/model/API-key handling, no-edit enforcement, Git lifecycle/index ownership by Auto-Coder, and the existing repository-state snapshot/recovery checks. Migrating transport must not silently weaken those properties.

## Requirements

REQ-001: A successful fresh production `MuseClient` invocation must establish a new root Muse session through MSP in the operation-bound execution workspace, submit the rendered Auto-Coder task as exactly one user turn, and expose the canonical opaque `sessionId` established by that invocation through `get_last_session_id()`; the ID must come from MSP session identity, not from assistant text, timestamps, session listings, locally generated guesses, or a previous invocation, and a failed or identity-inconsistent invocation must not expose stale prior identity as its own result.
REQ-002: `MuseClient.continue_session(session_id, prompt, is_noedit=...)` must perform one finite non-interactive continuation of exactly the nonempty session ID supplied by the caller by using MSP `session/resume` (or the official SDK operation with the same semantics) followed by exactly one new user turn; it must not use an interactive TUI/PTY, implicit last-session selection, session forking, a replacement session, or a fresh duplicate task as a substitute for the requested continuation.
REQ-003: A Muse continuation is successful only when MSP resumes the exact requested session, the resumed session is compatible with the caller-bound workspace and selected backend/model/provider identity, the submitted continuation turn reaches an unambiguous successful terminal outcome, and the returned Auto-Coder result is the final assistant text attributable to that new turn rather than replayed history, tool output, reasoning, protocol envelopes, or an earlier answer; missing or contradictory identity, pending or ambiguous terminal state, protocol failure, host death, or incompatible resume state must fail rather than be promoted as a continued answer.
REQ-004: At the production `BackendManager` boundary, `_last_continue_session_resumed` must be true only for a Muse continuation satisfying REQ-002 and REQ-003, must be reset for every attempt, and must remain false after failed resume or manager-level fallback to a fresh Muse session, another alias/provider/model, or another backend even when the fallback returns a plausible answer; adapter-local failure handling must not make a fresh session look continuous.
REQ-005: The `is_noedit` argument is authoritative for every Muse turn, including continuation regardless of the session's historical mode: no-edit must preserve the existing Muse read-only contract by preventing model-requested write and shell execution before their effects, preventing approval handling from weakening that restriction, and retaining Auto-Coder's repository/Git-state invariant checks; if the required no-edit policy cannot be established for the MSP turn, the invocation must fail before task submission rather than resume in an editable or more permissive mode.
REQ-006: Muse MSP start/resume must remain bound to Auto-Coder's current operation execution directory; if a requested session is stored for a different, removed, or otherwise incompatible workspace, continuation must fail explicitly and allow the existing manager-level non-continuous fallback policy to decide what happens next, rather than executing tools against the old workspace, recreating it, rebinding silently, or treating historical session content as current filesystem authority.
REQ-007: Existing Muse backend selection semantics that materially affect execution—including configured alias, selected model, provider credentials/environment, timeout, reasoning effort when configured, and edit/no-edit permission intent—must either be represented equivalently at the MSP host/session/turn boundary or be rejected with an actionable error before the turn is submitted; migration to MSP must not silently drop or reinterpret such configuration, and prompt-source/session-selection options must not override Auto-Coder's owned session and prompt transport.
REQ-008: Each Muse MSP invocation must have bounded lifecycle ownership: the owned MSP connection and `muse serve` process must be closed or terminated on success, handled failure, cancellation, and timeout, with no normal handled path leaving an orphan host or a continuation waiting indefinitely for an approval/user-input request Auto-Coder cannot satisfy; timeout and usage-limit/provider failures must retain their existing Auto-Coder error classifications where applicable.
REQ-009: An unsupported MSP host, failed MSP initialization, protocol/schema incompatibility, or SDK/host compatibility failure must fail explicitly before a turn is accepted and must leave continuation false; Muse continuation must not silently fall back inside `MuseClient` to legacy `muse exec`, a TUI/PTY session, or another undocumented continuation mechanism, while a `BackendManager` fallback performed after that explicit failure remains governed by the existing non-continuity semantics in REQ-004.

## Acceptance Scenarios

AC-001 — Fresh session to exact continuation (REQ-001–REQ-004): Build the production Muse backend manager from backend configuration and drive it through an executable MSP fixture that performs the real initialize/session/turn protocol. The first prompt must establish a host-chosen opaque session ID and return only its completed answer. Continuing that exact ID with a second prompt must issue `session/resume` for that ID, submit exactly one second turn, return only the second turn's final assistant text, and leave `_last_continue_session_resumed` true.

AC-002 — Continuation survives host replacement (REQ-001–REQ-003, REQ-008): Complete a fresh Muse turn, close the first `muse serve` host, start a distinct second host process over the same Muse session state, and continue using only the stored session ID. The continuation must resume the same durable session and succeed without dependence on an in-memory Python client, PTY, or still-running first host. A fake implementation that stores a local conversation object or generated ID must not satisfy this scenario.

AC-003 — Wrong identity or workspace is not continuity (REQ-002–REQ-004, REQ-006): Have `session/resume` return a different session ID, a different effective model/provider, or a workspace rooted outside the current operation-bound worktree, including a session whose original worktree has been removed. No continuation turn may be accepted as continuous; the client must fail, and if `BackendManager` then returns a valid-looking fresh fallback answer, `_last_continue_session_resumed` must still be false and the old workspace must remain absent.

AC-004 — PR #5402 target correction uses the same Muse session (REQ-001–REQ-004): Exercise the production adversarial-validation path with Muse as the reviewer. The initial review must return an otherwise parseable result whose `dynamic_check_requested` is rejected as prose. Auto-Coder must obtain the initial Muse session ID, send `pr.adversarial_validation_target_correction` through explicit continuation of that same session, accept a valid corrected target from the continuation, and proceed without the `could not continue without an explicit session` error. Constructing reviewer state directly in the test without traversing the production Muse invocation does not establish this oracle.

AC-005 — No-edit is reapplied, not inherited (REQ-005, REQ-008): Create or obtain a Muse session under an editable turn, then explicitly continue it with `is_noedit=True`. A controlled Muse host/model must attempt both a repository write and a shell command with an externally observable sentinel; neither effect may occur, the repository/Git snapshots must remain unchanged, and the invocation must not auto-approve or hang waiting for permission. Restoring repository files only after an actually executed shell/write does not satisfy this scenario.

AC-006 — Configuration is not silently lost in MSP migration (REQ-007, REQ-009): Configure a named Muse alias with an explicit model plus supported execution settings and credentials, then invoke fresh and continuation paths through the production manager. Assert that the effective MSP session/turn observes the selected model and supported settings. For an intentionally incompatible option, assert failure before a task-submission sentinel rather than silent omission or reinterpretation.

AC-007 — Terminal and transport failures are bounded (REQ-003, REQ-008–REQ-009): Cover host exit during a turn, timeout, MSP initialization failure, an SDK/host mismatch when the SDK path is used, and a resumed session that exposes a pending approval/user-input state that cannot be satisfied under the requested non-interactive policy. Each case must terminate/close the owned host, return the correct failure class or explicit backend error, leave continuity false, and perform no hidden legacy/TUI continuation.

AC-008 — Ordinary fresh calls do not gain adapter-local implicit resume (REQ-001–REQ-004): After a successful session-bearing Muse call, invoke the client's ordinary fresh execution path directly with stale `_last_session_id` state and verify that the adapter starts a new session rather than implicitly resuming the previous one. Separately, verify that `BackendManager` may still request explicit continuation when its existing `automatic_session_resume` policy authorizes it; provider capability must not redefine that manager policy.

## Non-goals

- Redesigning `BackendManager` session ownership, automatic-session-resume policy, or reviewer-session registry semantics.
- Changing Adversarial Validator's target-correction policy, dynamic-check target grammar, or whether a particular follow-up semantically requires same-session continuity.
- Adding PTY/TUI automation for Muse.
- Session forking, implicit last-session heuristics, distributed exactly-once turn execution, or automatic replay after an ambiguous accepted turn.
- Replacing the existing Muse repository/Git ownership model with a new global sandbox architecture.
- Broad refactoring of other backends or their continuation contracts.

## Implementation Notes

The official Python packages are `muse-code-sdk` and `muse-code-msp`, and Auto-Coder already requires Python 3.12, which satisfies their documented Python requirement. Using the official SDK is preferred over implementing an ad-hoc MSP parser, but the behavioral contract above is authoritative.

If the Python SDK is added as a dependency, account for its documented strict host/schema compatibility behavior and keep the Muse host and SDK pairing explicit in packaging/runtime setup. A version mismatch is an initialization failure, not model output and not a usage-limit event.

Reuse the current `MuseClient` repository snapshot, Git trace, timeout, usage-limit, environment, execution-CWD, and option-sanitization responsibilities where they still apply. Existing code is evidence of these responsibilities, not permission to weaken REQ-005 through REQ-008.

The MSP protocol is the authoritative session boundary. In particular, resume success is not defined merely by receiving a reply: validate the resumed session identity/state before submitting or accepting the continuation turn, and do not treat persisted history as current workspace evidence.
