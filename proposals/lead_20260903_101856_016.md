### What changed at the vendor — re-fetched and re-verified for this mint

`https://code.kimi.com/install.sh` (redirecting to `https://cdn.kimi.com/binaries/kimi-cli/install.sh`)
is now a deprecation shim. Fetched and read 2026-09-03, **never executed**: 134 lines,
sha256 `32a458064f8399def9513f052b44687cf3be3a5c53cd77580b546be8b16158ae`, header
`# Legacy kimi-cli (Python) installer - DEPRECATED.` Its main block gates on one variable:

| condition | what the shim does |
|---|---|
| controlling terminal openable — `(: < /dev/tty)`, its line 87 | deprecation banner, then `read -t 30`. **Enter, or simply waiting out the 30s, installs Kimi Code — a different CLI — and `exit 0`.** Only `o`/`O` keeps the legacy `kimi-cli`; `n`/`N` or Ctrl-D aborts `exit 1` |
| no controlling terminal | four warning lines on stderr, then the legacy install — behaviour unchanged |
| `KIMI_CLI_FORCE_OLD` non-empty | the whole block is skipped |

`KIMI_CLI_FORCE_OLD` is the vendor's **own documented automation switch**, named in the
script's header (`KIMI_CLI_FORCE_OLD   Non-empty: skip the prompt and install legacy
kimi-cli (intended for CI / automation).`) and repeated in the banner it prints
(`CI/automation: set KIMI_CLI_FORCE_OLD=1 to skip this prompt.`).

### Why this definition is safe today — and why that is not the whole answer

The gate is **whether a controlling terminal is openable**, not whether stdin is a tty. So
*"we pipe into bash, so we are non-interactive"* is **not** the reason this is safe, and an
operator running `rig bootstrap kimi-box` from their own SSH session does have one.

The reason is line 12's `runuser -l`, which puts its child in a new session with no
controlling terminal even when the caller has one. Measured in #25 on Debian 13 trixie /
util-linux 2.41-5 (`SID == PID`, `TT` is `?`): the definition takes the non-interactive
branch, the legacy `kimi-cli` installs as it always did, and the only new thing a fresh
mint sees is four lines of deprecation warning on stderr.

**That measurement covers one util-linux.** 2.39.3 (Ubuntu 24.04, the other supported
host) was not measured, and session semantics have moved in util-linux before. *"No host in
the supported set reaches the prompt"* is **unproven**, and this issue does not assume it.

### The second guard, which holds whatever util-linux does

If the interactive branch were reached anywhere and its 30-second default fired, Kimi Code
installs to `$HOME/.kimi-code/bin/kimi` — verified 2026-09-03 at
`https://code.kimi.com/kimi-code/install.sh`: `KIMI_INSTALL_DIR="${KIMI_INSTALL_DIR:-$HOME/.kimi-code}"`.
This definition declares `CLI_SRC="~/.local/bin/kimi"`, and rig asserts it —
[`commands/bootstrap-tenant.sh:442`](https://github.com/heavy-duty/rig/blob/main/commands/bootstrap-tenant.sh#L442):

```
[ -e "$CLI_SRC" ] || die "the ${CLI} installer produced no ${CLI_SRC} — upstream layout changed?"
```

**A mint that drifted onto Kimi Code aborts, loudly, and hands over no box.** The
`n`/Ctrl-D path is loud too: `exit 1` under this file's `set -euo pipefail` surfaces as
rig's `kimi-box's install.sh failed`. This is worth stating plainly because the report that
reached rig predicted the opposite — *"a box that quietly measures nothing"*. **The exposure
is a failed mint, not a silent one**, plus Kimi Code residue in the tenant home after it.

## The spec

**Set the vendor's switch on line 12, on the `bash` that reads the pipe.** The obvious
placement is wrong and is the one thing a reviewer must not wave through:

```bash
# WRONG — sets it for curl, not for the bash that reads the pipe
runuser -l "$TENANT_USER" -c 'KIMI_CLI_FORCE_OLD=1 curl -LsSf https://code.kimi.com/install.sh | bash'

# right
runuser -l "$TENANT_USER" -c 'curl -LsSf https://code.kimi.com/install.sh | KIMI_CLI_FORCE_OLD=1 bash'
```

The decisions, so none of them survives into the build as a question:

- **Set it.** It costs one variable and changes behaviour on no host that is already
  correct. It buys: the outcome stops depending on util-linux's session semantics, on how
  the operator invoked the bootstrap, and on the unmeasured half of the measurement above;
  and it silences four stderr lines on every fresh `kimi-box` mint.
- **The value is `=1`**, matching the vendor's documentation. The shim tests non-emptiness,
  so any non-empty value works; the documented one is the one a reader recognises.
- **The placement is on the interpreter**, per the block above.
- **The header comment gains a paragraph** recording that the vendor URL is now a
  deprecation shim, what the switch pins, and that the migration is a separate decision.
  `install.sh` diffs here are the highest-trust review surface in the org
  ([CONTRIBUTING.md](https://github.com/heavy-duty/rig-templates/blob/b6141c96a055117f0b7df7b9e2ca340b4b8a8b58/CONTRIBUTING.md#L53-L71)),
  so a bare environment variable with no stated reason is the wrong shape for this file —
  the next reader would read it as noise and the reader after that would tidy it away.
- **No other definition changes.** `claude-box`, `codex-box` and `grok-box` fetch different
  vendors and are untouched, and `kimi-box/template.env` is untouched: `CLI_SRC` is already
  right, and it is what makes the drift loud.
- **What this deliberately does not decide: whether the fleet migrates to Kimi Code.**
  Setting the switch *pins* the fleet to a CLI its vendor calls unmaintained — which is the
  argument **for** it, since it turns the migration into a dated decision somebody makes
  rather than a 30-second timeout nobody watched. See Dependencies.

  shell string and must not disturb the schema.

- **Must fail:** the wrong placement. `KIMI_CLI_FORCE_OLD=1 curl … | bash` sets the variable
  for `curl`'s environment; the shim never sees it, the banner returns, and this issue buys
  nothing. Prove the distinction rather than asserting it — e.g.
  `sh -c 'true | KIMI_CLI_FORCE_OLD=1 sh -c "echo \${KIMI_CLI_FORCE_OLD:-unset}"'` against
  the same construct with the assignment moved in front of the left-hand command.
- **Must fail:** dropping `runuser -l`. The tenant install must not become root's — a
  root-owned install under a `0700` home is a CLI that exists and cannot run, which is the
  scar the header comment already records for `grok-box`.
- **Must fail:** changing `CLI_SRC`, or any edit that makes a Kimi Code drift *quiet*.
  rig's `die` at `bootstrap-tenant.sh:442` is the guard that turns a wrong CLI into a failed
  mint instead of a working-looking box, and it stays load-bearing after this change.
- **Must fail:** a change under `commands/` in rig to make this work. This is a data-and-hook
  fix in the registry; if rig needs an edit, the deliverable is misplaced.
