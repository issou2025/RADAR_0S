## A. Low-friction intake and non-destructive capture
1. Ask only for phone model, Android/Lineage build, exact release filename/link or version, and whether it closes before any screen, after a particular screen, or after a permission prompt. Ask whether GMS/microG is present as context, not a diagnosis. No car, VIN, account, purchase or technical checksum calculation is needed for the first report; maintainer enriches artifact identity.
2. Provide an external capture route because the app may never open. Reuse/extend the privacy and explicit-device behavior of #53; do not wait for the full field-runner project to provide a manual recipe. No root, ROM flashing, installing GApps/microG, disabling OS protections, app-data clearing or uninstall is required by the diagnosis.
3. For a helper, proposed `tool/startup_probe/`: require explicit authorized device selection, private output directory, bounded time/bytes and a dry-run that touches no device. Start capture before the user reproduces the launch. Preserve full relevant exception/caused-by/backtrace context from main/system/crash as available. Do not depend solely on pidof after the process has died, or a single stale PID across restarts. Do not clear global logcat buffers or kill unrelated processes. Any launch/force-stop/install action is a separate explicit opt-in, not a side effect of collecting logs.
4. Logs may include data from other apps or identifiers; retain raw locally with a warning, no automatic GitHub upload. Produce a reviewed, minimal app-specific excerpt/summary separately. A full bugreport/tombstone is an optional later diagnostic, not public mandatory intake. ApplicationExitInfo can complement logs on supported Android versions if accessible after a later successful start; its absence is unknown, not evidence of no crash.

## B. Reproduce before selecting a fix
5. Compare the exact reported community release against a pinned candidate on an isolated clean AOSP image without Google services and, when available, the affected Lineage build/device. Add a stock/GMS baseline as a distinct row. Different ROMs/devices change more than GMS; do not claim a controlled causal experiment from those rows. A Google-APIs image with services disabled is not automatically equivalent to a clean no-GMS environment.
6. Inspect packaged ABI/native libraries, merged manifest, resolved release runtime dependencies and plugin registration. Separate install/signature/ABI rejection, native-loader or graphics abort, Java/Kotlin exception, Dart pre-runApp failure, hung startup/ANR and deliberate recovery blocking. Test the actual release configuration; a debug or synthetic-rig pass does not qualify the community field APK. Never overwrite an existing Play-signed installation with a different-signature APK.
7. Add bounded, non-identifying startup stage markers around the implicated boundary and reproduce the failure. If logs implicate graphics/Impeller, perform a version-supported, isolated renderer comparison with all other relevant inputs recorded. Do not disable the renderer globally or label GMS as the cause without evidence. If a plugin/service is implicated, fix its real capability check and lazy initialization rather than catching every exception and pretending startup succeeded.
8. Recover from a genuinely optional capability failure without blocking language selection, offline Demo or local data unnecessarily. Required preference/storage integrity failures must not silently replace user state with empty writable defaults, delete recordings or bypass existing startup ownership gates. A recovery screen must accurately distinguish unavailable, retryable and restart-required states. Native process faults cannot be solved merely by a Dart exception wrapper.

## C. Regression and closure
Proposed tests: `test/startup_compatibility/` and an explicitly defined native/device startup journey. These paths and capture tooling are deliverables to create, not existing or executed tests.
- [ ] A symptom/source/artifact record distinguishes reported, reproduced, root-caused and fixed. No attribution to GMS merely because the user lacks it.
- [ ] Helper tests with fake adb prove pre-launch capture, process restart/death handling, timeout/size limits, nonzero exits, explicit device selection, no clear/uninstall and zero device effects in dry-run. Raw identifiers do not enter default public summaries.
- [ ] For the reproduced fault, independent regression fails before the patch and passes after. Exact release/candidate variant and backend differences are recorded.
- [ ] Cold launch, offline launch, both UI languages, denied Bluetooth permission, Demo and local-record reopening work on the declared no-GMS test environment. No scan/OBD request is sent merely by launching or viewing language/help.
- [ ] Same-signature upgrade with preserved settings/records and clean install are separate tests; fault injection covers implicated preference/platform startup failures without silent data reset.
- [ ] Run `flutter analyze`, relevant startup/localization/recovery tests, full suite and the actual release-startup journey. Publish exact head/artifact, original exits and untested environments. Emulator success does not establish physical Lineage GPU/radio compatibility.
- [ ] Link the affected user's retest when obtained. If their environment remains unavailable, retain that limitation or transfer it explicitly to an open qualification follow-up; do not close a no-reproduction case as fixed just because one AOSP device launched.

Triage is the immediate priority; a reproduced launch regression blocks the affected candidate/platform claim. Unknown scope must not freeze unrelated correctness patches or require every volunteer to install a new ROM. No app/device experiment, log capture or fix was performed in this planning review.
