## Summary

We track [gfx-rs/wgpu#2869](https://github.com/gfx-rs/wgpu/issues/2869) for it, and the first cut agreed there is now an open PR: [gfx-rs/wgpu#10152](https://github.com/gfx-rs/wgpu/pull/10152) *Add damage-aware presentation via `Queue::present_with_damage`*.

This issue records **what the PR actually gives us**, **everything Frust has to change when it ships**, and **how we test it on our own device matrix before and after it lands** — the author has only tested Linux/Vulkan.

Status as of `main` @ 0c941464 (2026-10-18). Every claim below was checked against the PR head (`167e7687`), the v30.0.1 tag, the Vulkan spec source, and this tree on that date.

## What the PR is

- `Queue::present_with_damage(surface_texture, &[wgpu::Rect<u32>])`. Rects are pixels, top-left origin, clipped to the surface by wgpu-core; an empty slice is a plain `present`. `Queue::present` becomes a call to it with `&[]`.
- **It is a hint to the compositor, nothing more.** The PR's own doc: *"The texture must still contain the whole frame, since the compositor may use any part of it."* Frust keeps rendering every pixel. Our GPU and CPU time per frame does not change by adopting it.
- Implemented for **Vulkan** (`VK_KHR_incremental_present`) and **EGL** (`eglSwapBuffersWithDamage{KHR,EXT}`, untested on hardware). **Ignored** on DX12, Metal, WGL and WebGPU. DX12 is out because wgpu-hal creates the swapchain with `DXGI_SWAP_EFFECT_FLIP_DISCARD` (`wgpu-hal/src/dx12/mod.rs:1538` @ v30.0.1), and Microsoft's docs say that swap effect "cannot be used with multisampling and partial presentation".
- `hal::Queue::present` gains a `damage_rects` parameter. That breaks only out-of-tree `Api` implementations; Frust has none (`frust-gpu` uses `as_hal::<Vulkan>()` for the `AHardwareBuffer` import and `open_with_callback` only).
- Review state: changes requested by the maintainer on 2026-09-27, author re-pushed on 2026-10-17 (generic `Rect` moved to `wgpu-types`, clipping moved into wgpu-core, DX12 dropped). No milestone. v30.0.1 (2026-08-22) is still the latest release and does not have it; trunk is 628 commits past our pin. The `v31` milestone is fully closed (due 2026-10-09) but no release exists yet. ⚠️ #2869 still proposes a bigger `PresentationDescriptor` API later, so this first-cut shape may change.

### What the rects mean (Vulkan spec, `VK_KHR_surface/wsi.adoc`)

- `VkPresentRegionKHR::pRectangles`: *"a rectangle of the given image that has changed since the last image was presented to the given swapchain"*. So damage is relative to the **previous presented frame**, not to the previous use of the same swapchain image, and there is no buffer-age concept to track.
- *"The rectangles must be specified relative to `VkSurfaceCapabilitiesKHR::currentTransform`, regardless of the swapchain's `preTransform`"*. On a rotated Android surface (landscape) the rects live in the pre-rotated space. Whether wgpu-hal transforms them is unverified — the Android landscape leg has to prove it.
- Zero rectangles means "nothing changed" in the extension, but wgpu maps the empty slice to a full present. Frust already skips idle frames in the frame gate, so nothing is lost.

## How this relates to the partial-repaint NO-GO

We built partial repaint once (spike `d1d54658`: damage from pod dirtiness + engine frame scissor + persistent accumulator + copy to the swapchain, behind `FRUST_PARTIAL_REPAINT`), measured it on the T400 and stripped it (`28c4459b`). It paid only at ≤10 % damage, cost ~+0.2 ms GPU per frame above ~50–60 % (our S1/S2/S6 scenarios damage 85–100 % of the surface), left CPU encode unchanged, added ~20.7 MB, and tile GPUs still load/store every tile. That verdict is about **Frust rendering less**. The PR is about **the compositor compositing less**. The two are independent: adopting the hint does not bring the accumulator back, and nothing here re-opens the NO-GO.

The spike also recorded four blind spots in dirtiness-derived damage: a container whose own drawing changes in the same pass as a dirty descendant, ink outside a pod's bounds (shadows, overflow), a culled pod's vacated area, and one union rect per frame. For a *hint* path those are not lost savings — they are **visible stale pixels**. Any damage source we ship has to close them.

## What Frust needs to do when it lands

1. **Pin bump** to the wgpu release that carries it (31.x presumably). Version pins are LAW: the full engine gate suite in `docs/RENDER_DEVELOPMENT.md` (Pixel 5 Vulkan matrix, iPhone SE + Simulator Metal gates, macOS window smoke, Windows DX12 smoke on the Dell, browser WebGL gate) plus the 29→30-style CHANGELOG-driven API migration. #21 (HarmonyOS Vulkan) waits on the same bump.
2. **A damage source** — proposed: a **scene diff** in `frust-scene`, not pod dirtiness. `SceneDamage::between(last_presented, next)`: prefix/suffix match of the `Command` lists, union of the bounds of both changed ranges (the scene is already in device space — shell scale and ancestor transforms applied). It closes all four blind spots (a removed command's bounds cover the vacated area, a shadow is a command, a container's own change is a differing command), needs no `frust-core` change, and the previous scene already lives in `SurfaceRenderer::engine_scene`. Cost is O(n) command compares per frame — microseconds against the ~0.93 ms encode floor. Forced-full rules: first frame or new swapchain, `Outdated`/`Suboptimal`, resize, scale or translucency change, base colour change, any scene that draws a caller-bound texture, texture-bus/video texture or shader quad (pixels change with no scene change). Alternative: the spike's `PaintDamage` plus a new own-paint-changed bit in `frust-core` — more invasive, and still blind to ink outside pod bounds.
3. **Plumbing in `frust-render`**: `DeferredPresent` carries the rects and calls `present_with_damage`; the direct present in `submit_segmented` does the same for the main surface; overlay surfaces present full in v1. Diff against the last **presented** scene so a dropped latest-wins frame folds its damage forward. Behind `FRUST_PRESENT_DAMAGE` (same compile-time-or-runtime shape as the other knobs), default off until the device evidence says otherwise; a `perf-trace` `frust-perf damage` line (full/rect frames, rect count, covered area). Goldens stay byte-identical with the knob off and on (the hint changes no pixels).
4. **Shells**: nothing — every shell only calls `frame.present()`. The Android landscape leg checks the `currentTransform` question above.
5. **Docs**: `partial-repaint-outcome` keeps its verdict but its "trigger for removal" text changes; a new LIMITATIONS entry (hint only; Vulkan/EGL only; full frame still rendered; overlays full); `RENDER_ARCHITECTURE.md` present section; `RENDER_DEVELOPMENT.md` pin row + knob row; `docs/learning/17-render-model-vs-flutter.md` and the README gap line.

## How we test it — before it lands

**A. Pure-wgpu probe (no pin change, no Frust code).** A standalone workspace `testing/damage-probe` (same shape as `testing/hotpatch-canary`, excluded from the root graph) that depends on the PR head by git rev, opens a winit window and animates a small square, with `--damage none|exact|under`. `under` deliberately reports a rect smaller than what changed: a compositor that honours damage shows stale pixels (visible proof the hint is consumed), a backend that ignores it shows a correct frame. Legs: this rig — NVIDIA X11 via the linux-native container and Intel Wayland; the Dell — DX12 (expect no-op, no error) and `WGPU_BACKEND=vulkan`; a MacBook — Metal no-op. On Wayland `WAYLAND_DEBUG=1 … | grep damage_buffer` shows the rects reaching the compositor. Winit on iOS/Android is not worth the host-app setup; the mobile legs come from B.

**B. Frust spike branch (never merged).** `frust-rs/wgpu` fork branch = `v30.0.1` + the PR's three commits cherry-picked, version kept at 30.0.1 so `[patch.crates-io]` rows for `wgpu`, `wgpu-core`, `wgpu-hal`, `wgpu-types` apply in the root, `benchmarks/frust_bench` and `examples/playground` workspaces. Items 2 and 3 above land on that branch behind the knob. Legs with the existing shells and harness:
- Pixel 5 / OnePlus 9 / Xiaomi 12, portrait **and landscape** (the `currentTransform` question).
- iPhone SE + iOS Simulator, MacBook: Metal no-op regression (the engine gate, the Simulator gate, zero uncaptured wgpu errors).
- Dell: DX12 no-op and `WGPU_BACKEND=vulkan`.
- Linux rig: X11 NVIDIA, Intel Wayland.

**Metrics.** Correctness: a screen capture after a damaged present must equal a full-present capture on the same frame (`adb screencap`, `grim`, Windows screenshot) over the playground pages — any difference is an under-reported rect. Benefit: compositor-side, not Frust-side — Android Perfetto `gfx` + `power` (SurfaceFlinger composition time, power rails where the device exposes them) and `dumpsys SurfaceFlinger`; Linux compositor GPU utilisation (`nvidia-smi dmon`, `intel_gpu_top`) with the knob off vs on; thermal/charging gate via `benchmarks/harness/device_state.sh`. The scenario has to be **small-damage idle animation** (a 2 Hz caret plus a small spinner on a static page) — S1/S2/S6 damage 85–100 % and are the negative controls. `benchmarks/` stays read-only; the scenario lives in the playground on the spike branch.

**C. Feed upstream.** Post the matrix (Windows Vulkan, Android, Metal/DX12 no-op) on gfx-rs/wgpu#10152 — that is what the PR is missing.

## Risks / open questions

- The API shape may change before release (#2869's `PresentationDescriptor`). Mitigation: one call site (`DeferredPresent::present`).
- The v31 bump is the expensive part (five gate arms), and its timing is upstream's.
- Compositors may ignore the hint (X11, some Wayland compositors), and SurfaceFlinger may still compose the full buffer — then default-on buys nothing. That is what Phase 1 measures.
- Under-reported damage = visible stale pixels. The forced-full rules and the screen-capture test are the guard.
- Pre-rotation coordinate space on Android.
- Multi-surface processes (overlay surfaces, several desktop windows) each need their own diff; v1 presents overlays full.
