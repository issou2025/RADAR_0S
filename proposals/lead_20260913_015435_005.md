## Summary

The `tekla` agent manifest (`20-agents/aeco/engineering/tekla/manifest.yaml`, agent v0.1.4, main @ `d2552931b`) declares **24 commands**; the `aware-tekla` bridge dispatches **7**. The other **19** are declared as ordinary runnable commands — none carries the per-command `status: planned` that #199 added — so `aware app compile` accepts an app that uses them and the run fails at the bridge with `unknown verb`. This is #176 (`watch` declared, not implemented) again, at 19× the surface. Verified on CLI v0.135.0 with the installed bridge.

## Expected / proposal

Two acceptable end states, in order of cost:

1. **Mark, today.** Add `status: planned` to each of the 19 commands so the existing gate (`E_APP_COMMAND_UNAVAILABLE`, #199) refuses them at validate/install with a clear message. Also declare `list-instances` and `close`, which are implemented but undocumented. This is a manifest-only change.
2. **Implement, staged.** Wire the verbs the substrate already has the pieces for. The 8 `scope: selected` list/report verbs are one family (a `ModelObjectSelector.GetSelectedObjects()` / `GetAllObjects()` enumeration plus report-property reads — the pattern `exec` users hand-write today); `insert` is a `ConnectionPart` insert with a transaction, which `commands/insert.md` already specifies in full. Keep each family its own PR; flip its `status` as it lands.

Either way the manifest must not advertise a command the bridge cannot dispatch. A test that diffs the manifest's `commands:` against the `switch (verb)` cases would keep it that way (the reverse of the drift #176 was).

## Why it matters

- An app author (or the terminal AI composing a `.flo`) reads `manifest.yaml` and `commands/*.md` as the contract. Today that contract lists a native connection insert, UDA get/set, NC/IFC export, drawing issue and clash check that do not exist, and the first signal is a run failure — after compile and the Run gate said yes.
- The `scope: selected` family is the substrate half of "act on what the user selected in the host"; its absence is why every selection-driven workflow on AWARE is hand-written C# in `exec` today.
- The `E_APP_COMMAND_UNAVAILABLE` gate exists precisely for this; it is unused on the agent that needs it most.
