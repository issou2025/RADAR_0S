## Required audit method

This is not a grep-only audit.

For each file/function/major shell routine reviewed, record:
- file and function/routine name or line range
- intended contract inferred from docs/tests/callers
- actual implementation behavior
- caller/callee chain interactions where relevant
- edge cases and failure modes
- existing fixture coverage
- missing fixture coverage
- verdict: pass / suspicious / defect / follow-up needed

The audit must include sequence checks, not just isolated functions:
- CLI entrypoint -> parser -> helper -> scanner/hook decision -> exit code
- hook wrapper -> called script -> resolver/scanner/tooling -> mutation decision
- build/sync script -> generated artifact -> workspace deployment -> drift check
- tests -> fixtures -> asserted behavior -> untested behavior

## Persona / hostile frame

Assume the frame of a skeptical Scala/JVM engineer reviewing Python/Bash automation:
- distrust dynamic typing, implicit globals, regex parsers, Bash word splitting, and silent fail-open behavior
- look for stale docs, mismatched tests, parser/quoting bugs, hidden platform dependencies, and false-positive/false-negative scanner paths
- require executable evidence; context-free grep is discovery only, not proof
- call out lazy AI-generated code patterns directly, but keep findings actionable

## Output requirements

The worker must write durable audit results back to this epic in comments or linked child issues.

For defects, create child issues or comments with:
- reproduction command or executable fixture sketch
- expected vs actual behavior
- impacted functions/chains
- proposed fix shape
- priority and whether implementation should be split

For non-defect passes, summarize reviewed surface and why it passed.
