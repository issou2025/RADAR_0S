### backend-design-15 (minor) — `src_C/Vpc/Automation/EvalGate.cs:104`
- Problem: The K2 rule that a newer failed gate drops live to dry_run cannot happen in production. PostAsync returns 400 EVAL_GATE_FAILED and inserts nothing when a report fails (:104-116), so the newest row is always a passed one. If the owner re-runs the gate after a model or author change and it fails, live stays enabled on the older passed gate. Add an allowlist AutomationGateModels = ["global.openai.gpt-5.5"], or at minimum reject models containing 'anthropic' or 'claude', and fail 'reviewer.model' otherwise. Test through the POST route, not SQL.
- Evidence: EvalGate.cs:105-116 returns res.Raw(400 ...) before the insert at :135-140; :211 `Fail(string.IsNullOrWhiteSpace(r.Model), "reviewer.model")`; AutomationModeTests.cs:238 `failed = await InsertGateAsync(passed: false, revoked: false)`; A00 §15.4 step 4 records only passing reports.

### automation-13 (minor) — `src_C/Vpc/Automation/EvalGate.cs:104`

The insert hard-codes passed = true (:135-140). K2's 'a newer failed gate drops live to dry_run' can therefore never happen through the API; the test that covers it inserts a failed row directly (AutomationModeTests.cs:238). The newest failed row then blocks live, as K2 intends. Reject with 409 EVAL_GATE_REPORT_REVOKED a report whose sha256 equals that of a revoked row. Test: PostGate_FailingReport_IsRecordedAndBlocksLive and PostGate_RevokedReportAgain_Returns409.
- Evidence: EvalGate.cs:104-116 (early 400 return), :135-140 (`values ($1, $2, $3, true, ...)`); AutomationModeTests.cs:228-246 (InsertGateAsync(passed: false) directly); automation-operations.md:16-18.

Migration 034 has no uniqueness or revoked check on report_sha256 (034_automation.sql:170-184), so re-posting a revoked report silently re-enables live.
