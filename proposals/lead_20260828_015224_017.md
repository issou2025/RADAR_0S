# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**V7.1 board sold as Eight Relays matches 8relind-rpi's remap, not this repo's**

*Project description:*
### Summary

On a **V 7.1** card, `relayChRemap` maps channels 6, 7 and 8 to relays **7, 8 and 6**. Channels 1–5 are correct. The same table is in the C tool (`relay.c:37`) and the Python library (`python/8relay/lib8relay/__init__.py:13-14`), so both are affected.

The README says this repo targets Ver. 3, so I assume the board was re-laid at some point and the table did not follow.

### Measured

Board silkscreen: `SEQUENT MICROSYSTEMS 8-RELAY HAT`, `V 7.1`, `ALL RELAYS 120VAC/30VDC`. Raspberry Pi 4B, Raspberry Pi OS (kernel 6.18), single card, stack level 0, detected at `0x27`.

| `8relay 0 write N on` | Bit set in reg `0x01` | LED/terminal that actually closes |
|---|---|---|
| 1 | 0 | REL1 |
| 2 | 2 | REL2 |
| 3 | 1 | REL3 |
| 4 | 3 | REL4 |
| 5 | 6 | REL5 |
| **6** | 4 | **REL7** |
| **7** | 5 | **REL8** |
| **8** | 7 | **REL6** |

Method: energise one channel at a time, read the output latch back with `i2cget -y 1 0x27 0x01` to confirm which bit the driver set, then read the silkscreen label beside the lit LED. The bit read-back always agrees with `relayChRemap`, so it confirms only that the driver does what its own table says — the mismatch is between that table and the board, and is visible only by looking at the card.

### Why it matters

Writing the channel a user believes is spare closes a different relay. In my case `8relay 0 write 8 on` closes REL6, which my design assigns to a 30 A contactor for a 7.3 A blower motor. Nothing is wired yet and the card was bare throughout testing — but on a card sold for automation, this is the kind of mismatch that gets found by a motor starting.

### Not a case of using the wrong repo

Purchased as *Eight RELAYS 8-Layer Stackable HAT for Raspberry Pi* (Amazon B07KRKS67G), so this repo is the intended driver. I also checked the sibling repos in case one of them already carries the V7.x routing — none does:

| Repo | `relayChRemap` |
|---|---|
| `8relay-rpi` | `0, 2, 1, 3, 6, 4, 5, 7` |
| `8relind-rpi` | `0, 2, 6, 4, 5, 7, 3, 1` |
| `8relayhv-rpi` | `6, 4, 5, 3, 7, 2, 1, …` |
| **measured, V 7.1** | **`0, 2, 1, 3, 6, 7, 4, 5`** |

### Suggested fix

For V7.1 the table appears to be:

```c
const u8 relayMaskRemap[8] = {0x01, 0x04, 0x02, 0x08, 0x40, 0x80, 0x10, 0x20};
const int relayChRemap[8]  = {0,    2,    1,    3,    6,    7,    4,    5};
```

i.e. the last three entries rotate from `4, 5, 7` to `7, 4, 5`.

There is a complication: the card presents a single I/O expander and no microcontroller, so software cannot ask it which revision it is. Detecting this at runtime does not look possible — it probably needs a build flag, a separate branch, or at minimum a note in the README saying which hardware revisions the current table is correct for.

### Caveat

This is one board. I cannot rule out a mis-assembled unit from a single sample, though a clean three-way rotation with the other five channels correct looks more like a layout change than an assembly fault. If you can confirm the V7.x routing I am happy to open a PR with the corrected table and a README note.
