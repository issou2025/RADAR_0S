# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[epic] Adopt Hive practices **

*Project description:*
Worked for 37s

Yes. After looking at both repos, I think TunaOS should borrow Hive’s operating model more than its literal workflows.

The interesting thing is that tuna-os/tunaOS has already independently developed one of Hive’s strongest ideas: an explicit definition of what “green” means. TunaOS’s .github/green-criteria.yml says that a result that was skipped, never tested, or is stale cannot count as green, and distinguishes blocking, advisory, and unimplemented criteria.  That is exactly the sort of discipline that makes Hive’s automation safe.

So I would build on that rather than replacing it.

Internal engineering practices

1. Turn green-criteria.yml into the equivalent of Hive's test contract

TunaOS currently has a very good declarative specification:

image builds

desktop exists

QEMU boot works

ISO boots

installation completes

update/rebase/rollback

package parity

no silent omissions

rebuildability

architecture honesty


And crucially, TunaOS already records which criteria are blocking versus advisory.

I would go one step further and make CI prove that every criterion has an executing implementation.

Hive has learned the hard lesson that:

> a test existing in the repository is not the same as a test being run.



For TunaOS, introduce something like:

tests/test_ci_contract.py

It would parse green-criteria.yml and assert:

criterion asserted_by exists
workflow exists
job exists
job is reachable
workflow has an active trigger
blocking criteria cannot use continue-on-error
blocking criteria cannot be conditionally skipped without an explicit scope exemption
scheduled/advisory criteria have a freshness SLA

That closes an entire class of CI regressions.

You already explicitly identify this failure mode in the green criteria comments: people believing something is checked when nothing actually blocks on it.

This should become a required PR check.


---

2. Make testing two-speed like Hive

Hive separates predictable PR checks from more aggressive scheduled testing.

I'd do the same.

PR / deterministic

lint
schema/config validation
unit tests
green-contract validation
changed-variant build tests
desktop static contract
package omission contract
security/static analysis

Post-merge / scheduled

full build matrix
QEMU boot matrix
installer E2E
LUKS install
bootc upgrade/rebase/rollback
package parity
architecture/repository availability
reproducibility
fault injection
randomized execution/order testing

TunaOS already has much of the second category. Its lifecycle criterion, for example, tests upgrade, rebase, alias resolution, and rollback, while the ISO/install distinction correctly separates “installer UI exists” from “installation actually succeeds.”

What Hive adds is systematic scheduling and independent revalidation.


---

3. Add randomized/shuffled tests

This is one Hive practice I'd copy nearly verbatim in spirit.

TunaOS has lots of scripts and Python tests whose behavior can inadvertently depend upon:

filesystem ordering

YAML ordering

matrix ordering

previous build artifacts

cache state

network timing

registry timing

variant ordering


Add a nightly chaos-test workflow that deliberately randomizes things.

For Python:

pytest --random-order

or pytest-randomly.

Then randomize:

variant iteration
flavor iteration
architecture iteration
package-list ordering
parallel worker assignment
temporary-directory names
cache presence/absence

Record the random seed as an artifact.

A failure should say something like:

TUNAOS_TEST_SEED=83923598

and be locally reproducible.


---

4. Add failure injection

This is probably the biggest area where TunaOS can go beyond normal distro CI.

You should intentionally break the factory.

Tests I'd add:

registry temporarily unavailable
package repo returns 404
package repo returns 503
one requested package missing
base OCI manifest lacks arm64
cosign/Rekor temporarily fails
GHCR push fails midway
artifact download corrupted
QEMU boot timeout
installer crashes
network disappears during install
bootc upgrade downloads but reboot fails
new deployment fails to boot
rollback required
expired repository metadata
full disk
stale build artifact

Then assert TunaOS:

1. fails correctly;


2. says why;


3. does not call the cell green;


4. does not promote it;


5. preserves enough evidence to diagnose it.



This is particularly relevant because TunaOS already has explicit historical examples of upstream image garbage collection and repository/architecture failures in its green criteria.

Turn those historic incidents into regression tests.


---

5. Every production incident becomes a regression test

This is another Hive-style cultural practice worth adopting formally.

Something like:

tunaOS issue #858
    ↓
regression test
    ↓
test_issue_858_missing_desktop.py

Your green criteria actually mentions #858 as the reason an image merely building isn't enough: marlin:kde could ship without a Wayland session.

Make that convention explicit:

> A bug that allowed an unusable or incorrectly promoted image should not be considered fixed until a test proves the old failure mode cannot silently recur.



For TunaOS, that's exceptionally valuable.


---

6. Evidence artifacts for every important gate

Hive's backend smoke testing preserves evidence.

TunaOS should make that universal.

For every matrix cell, generate a small standardized bundle:

evidence/
  metadata.json
  image.json
  packages.txt
  omissions.json
  desktop-contract.json
  boot.log
  boot-journal.txt
  installer.log
  screenshot.png
  install-result.json
  lifecycle.json
  sbom.spdx.json
  provenance.json
  signature.json

Then the green verdict points at that bundle.

That transforms:

> yellowfin:gnome is green



into:

> yellowfin:gnome is green because here is the machine-readable evidence.



This also makes debugging agents dramatically more effective.


---

7. Add an explicit test coverage matrix—not code coverage

Ordinary statement coverage is relatively uninteresting for TunaOS compared with Hive's Go code.

Your real coverage unit is:

variant × flavor × architecture × lifecycle operation

For example:

Cell	Build	Static contract	Boot	ISO	Install	Upgrade	Rollback	Signature

bonito/gnome/x86_64	✅	✅	✅	✅	✅	✅	✅	✅
bonito/kde/x86_64	✅	✅	✅	❌	✅	✅	✅	✅
marlin/gnome/arm64	✅	✅	⬜	⬜	⬜	✅	✅	✅


And define:

✅ tested and current
❌ tested and failed
⬜ never tested / stale
➖ explicitly out of scope

Never turn ⬜ into ✅.

TunaOS is already conceptually doing this. Its documentation calls the lifecycle gate machine-enforced across variant/flavor/platform cells, and MATRIX-STATUS.md tracks several E2E axes.

I'd make that the primary project health metric.


---

8. Graduate advisory checks automatically

This could improve on both projects.

You already have:

enforcement: advisory

and comments such as lifecycle becoming blocking after sufficient healthy sweeps.

Formalize it.

For example:

promotion:
  required_consecutive_passes: 3
  required_coverage: 0.95
  maximum_flake_rate: 0.01

CI then opens an issue:

> bootc-lifecycle has met blocking-gate graduation criteria for three consecutive sweeps.



Human still approves the policy change.

This prevents advisory checks from becoming permanent dashboard wallpaper.


---

9. Canary before full promotion

I'd also borrow the safety philosophy behind Hive's autonomous changes.

For an OS image factory:

build
  ↓
test
  ↓
canary tag
  ↓
deep E2E
  ↓
stable tag

Never have successful podman build be sufficient to move a production tag.

For example:

ghcr.io/tuna-os/bonito:pr-1234
ghcr.io/tuna-os/bonito:candidate-20260902
ghcr.io/tuna-os/bonito:stable

The candidate gets installer/lifecycle testing before stable moves.

External / community-facing practices

This is where Hive has several inexpensive ideas that TunaOS should steal.

10. Centralize org automation

Hive's add-help-wanted.yml is tiny because the actual implementation lives in kubestellar/infra as a reusable workflow pinned to a commit.

Do the same across TunaOS.

Create or expand something like:

tuna-os/.github

or

tuna-os/infra

with:

reusable-lint.yml
reusable-security.yml
reusable-renovate-policy.yml
reusable-scorecard.yml
reusable-docs.yml
reusable-release.yml
reusable-pr-hygiene.yml
reusable-first-contributor.yml
reusable-test-contract.yml

Then repositories consume thin wrappers.

That would fit very nicely with the conventions work you've already been doing across the TunaOS organization.


---

11. Adopt Hive's contributor nudges

Hive's changelog workflow is a particularly good example.

It deliberately distinguishes:

policy worth reminding about
≠
policy worth blocking a merge over

It notices a code PR that doesn't touch the changelog and gives an advisory reminder, but always succeeds. It also explicitly handles fork permissions so external contributors aren't rewarded with a mysterious red CI check.

TunaOS should use this model for:

CHANGELOG entry?
docs affected?
screenshot affected?
new variant needs matrix docs?
new flavor needs testing declaration?
user-facing behavior needs release note?
breaking change needs migration note?

Soft reminders, not hard checks unless correctness requires it.


---

12. Make issue gardening automatic

Hive has automation around contributor-facing labels such as help wanted.

TunaOS already has a strong contributor starting point: CONTRIBUTING.md directs newcomers to an org-wide good first issue search.

Build on that.

An issue lifecycle could be:

triage/new
    ↓
needs-reproducer
needs-design
ready
    ↓
good first issue
help wanted
expert needed
    ↓
in progress
blocked
needs review
    ↓
done

Bots can:

mark inactive assignments;

detect issues missing reproductions;

automatically add help wanted when maintainers mark ready;

surface stale blocked issues;

link regressions to their test;

suggest duplicates;

welcome first-time contributors.


This makes a small maintainer team appear much more responsive without pretending automation is a maintainer.


---

13. Treat external contributions as a first-class CI environment

Hive's changelog workflow contains an unusually good lesson: they had an advisory workflow fail on forks because GITHUB_TOKEN was read-only, which turned a friendly reminder into a red check. They added an explicit regression test for the 403 case.

TunaOS should have a fork simulation test for every PR workflow.

Verify:

no secrets
read-only GITHUB_TOKEN
untrusted checkout
Dependabot
Renovate
first-time external contributor
same-repo contributor

And assert the correct jobs still work.

That's an excellent external-project practice to adopt.


---

14. Contributor environment contract

Hive benefits from making its test/development environment reproducible.

TunaOS already has .devcontainer.json and repository automation infrastructure visible in the tree.

I'd formalize:

just setup
just lint
just test
just test-fast
just test-cell bonito gnome amd64
just test-e2e bonito gnome
just ci

and guarantee:

> just ci locally approximates the PR gate.



A contributor shouldn't need to reverse engineer 40 GitHub Actions workflows.

Instead of a generic:

than a GitHub Actions badge does.

17. Apply the same model org-wide

The bigger lesson from Hive isn't really:

> “Hive has good GitHub workflows.”



It's:

> Policy is executable.



For TunaOS I'd establish an org-wide hierarchy:

tuna-os/infra
      │
      ├── shared CI/security/community policy
      │
tuna-os/tunaOS
      │
      ├── image-factory correctness contract
      │
tuna-os/tunaos-packages
      │
      ├── package build/reproducibility contract
      │
tuna-os/fisherman
      │
      ├── installer API/E2E contract
      │
tuna-os/bootc-migrate
      │
      ├── migration contract
      │
tuna-os/bootsahi
      │
      └── hardware/install contract

Each project defines what green means, while the org repo supplies reusable machinery.

That is where I think the Hive approach becomes particularly powerful for TunaOS.

Priority

I'd implement these in roughly this order:

1. CI meta-test — prove all declared gates actually execute.


2. Evidence bundles for every image cell.


3. Fork/external-contributor CI tests.


4. Randomized/nightly test lane.


5. Failure-injection suite.


6. Incident → regression-test policy.


7. Central reusable TunaOS org workflows.


8. Advisory PR nudges for changelogs/docs/etc.


9. Automated issue gardening.


10. Public factory health dashboard/release quality report.


11. Automatic advisory→blocking graduation recommendations.


12. Eventually, controlled autonomous maintenance/merge-on-green, but only where all the above establishes enough evidence.



The notable conclusion from comparing the two is that TunaOS isn't starting behind Hive. Its green-criteria.yml, matrix-oriented definition of correctness, lifecycle testing, and distinction between static desktop verification, runtime booting, ISO UX and actual installation are already unusually sophisticated. Hive mainly provides a good blueprint for making those guarantees self-auditing, contributor-friendly, failure-resistant, and safe enough for more automation.
