# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Enhancement: Allow `WindowController` to own the primary Desktop window**

*Project description:*
### Use case

## Summary

The experimental Flutter Windowing API allows desktop applications to create and configure windows from Dart using `WindowController` and `Window`.

However, when using this API as the application's entry point, the standard desktop runner may also create its own initial native window. This can result in an additional top-level window alongside the window explicitly created and configured through Dart.

I would like to propose an API or runner integration that allows a Dart-created window to serve as the application's **sole primary window**, without requiring developers to manually modify platform-specific runner code.

## Motivation

My intended use case is a conventional single-window desktop application, with the possibility of adding secondary windows later.

Ideally, I would be able to configure the primary window from Dart:

```dart
void main() {
  WidgetsFlutterBinding.ensureInitialized();

  runWidget(
    Window(
      controller: WindowController(
        title: 'My Application',
        size: const Size(800, 600),
      ),
      child: const MainApp(),
    ),
  );
}
```

The window created through this API should be the application's initial and primary window, rather than an additional window alongside one created independently by the default desktop runner.

I understand that Flutter still needs to initialize its engine and platform-specific infrastructure. I am not necessarily proposing that this infrastructure be removed, but rather that the initial native window's creation and ownership be coordinated with the Windowing API.

## Clarification of the Intended Behaviour

This request concerns **primary-window ownership and startup integration**, not embedding a native window as a child of another native window.

My goal is for the Dart-defined window to be the application's sole native top-level window at startup, with its title, dimensions, and other supported window properties managed through `WindowController`.

I am not requesting a mechanism for embedding one native window inside another, nor am I assuming that Flutter should reproduce Electron-like internal architecture. Rather, I would like Flutter's desktop startup process and Windowing API to cooperate so that applications can use a Dart-defined window as their primary window without creating a redundant top-level window.

## Proposed Behaviour

It would be useful if desktop applications could:

- Use `WindowController` to define the initial primary window's title, dimensions, and other supported window properties.
- Avoid creating a redundant top-level window through the default runner startup path.
- Continue using the existing `runApp` workflow for conventional applications that do not opt into the Windowing API.
- Create additional top-level windows through the Windowing API when needed.
- Rely on a documented startup and lifecycle model that explains how the primary window relates to the Flutter engine and platform-specific runner.

Ideally, this behaviour would be available consistently across supported desktop platforms, even if the underlying implementation differs between Windows, macOS, and Linux.

## Questions

1. Is the current requirement to create a separate window through `WindowController` intentional, or is there already a supported way to make it manage the initial runner window?
2. Could the Windowing API provide an opt-in startup mode in which the Dart-defined window becomes the application's primary native window?
3. Could the default desktop runner delegate primary-window creation to the Windowing API when this mode is enabled, while retaining the existing startup behaviour for conventional applications?
4. If this is already covered by ongoing multi-view or runner integration work, could the relevant issue or design discussion be linked here?

## Environment

- Platform: Windows desktop
- Flutter channel: `main`
- Feature: experimental Windowing API (`--enable-windowing`)

I would appreciate clarification on the intended architecture and whether this behaviour could be supported without requiring application developers to maintain custom native runner modifications.
