# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Feature request: target a specific Revit instance when several Revits of the same year are open**

*Project description:*
### Summary

We run several Revit 2026 sessions side by side, each with a different model, and want one MCP client (one AI agent) per session, working in parallel. Today rvt-mcp routes by year only. With several same-year Revits, only the most recently started one is discoverable, and an agent can't tell which instance it is connected to. Judging from the source, a reconnect can also silently move an agent to a different model. The plugin side is already per-instance (pipe `RvtMcp-<pid>`), so the change could stay additive and mostly within discovery and targeting.

### Environment

- rvt-mcp 0.8.1 (`0.8.1+2b38f12`), plugin R26 from the same release. We haven't re-run this on 1.0.1, but the logic below is the same on master `2a56356` (v1.0.1) and the links point there. Only the discovery/log folder moved, from `%LOCALAPPDATA%\RvtMcp\` to `%LOCALAPPDATA%\Bimwright\rvt-mcp\`.
- Revit 2026.5, several instances open at once, Windows 11
- MCP client: Claude Code, several sessions (each spawns its own stdio `rvt-mcp.exe`)

### What we see

1. **Only the most recent listener is discoverable.** Every Revit 2026 writes the same `revit-2026.json` (last writer wins), so `revit_list_available_targets` shows a single 2026 entry no matter how many are running.
2. **Closing any Revit 2026 removes discovery for all of them.** Closing or stopping MCP in *any* Revit 2026 deletes `revit-2026.json`, even when a different, still-running Revit 2026 wrote it. New sessions then can't connect until some listener restarts. We hit this when an unrelated Revit 2026 was closed.
3. **No way to pick or verify an instance.** `--target`, `BIMWRIGHT_TARGET` and `revit_switch_target(version)` accept only a year. `revit_get_current_target` reports only years (`pinned_target`, `currently_connected_year`), and `revit_list_available_targets` sets `is_currently_connected` by year only. The targeting tools therefore give an agent no way to confirm which instance/model it is talking to, short of `send_code_to_revit`.
4. **Reconnect can land on another model (inferred from the source, not yet observed).** Once a connection drops (pipe error, rate limit, `switch_target`), the next call re-reads `revit-<year>.json` and may attach to a *different* Revit of the same year. With production models open, a write to the wrong model is the risk we most want to rule out.
5. **Smaller, separate (happy to file it as its own issue if you prefer):** restarting a listener in the same Revit while the previous client is still attached produces a tight `Listen error: All pipe instances are busy.` / `Client disconnected` loop with no back-off. For us that was ~130k log lines over 5 bursts.

What works today: because each server keeps its pipe and token after the first call that reaches Revit, we can get parallel sessions by staggering them:

1. Start MCP (Add-Ins → RvtMcp) in Revit A.
2. Make agent A's first Revit call. It has to be one that actually reaches Revit, e.g. `revit_get_current_view_info`. `revit_list_available_targets` and `revit_get_current_target` don't open a connection.
3. Then start MCP in Revit B and do the same for agent B.

It works, but it is fragile because of (2) and (4).

### Proposal (additive, backward compatible)

1. **Per-instance discovery files.** The plugin writes `revit-<year>-<pid>.json`, optionally still writing `revit-<year>.json` for older servers. The JSON already carries `pid`. Optionally adding the active document title (bumping to `schema_version: 3`) would let agents pick by model. It would need refreshing when the active document changes, since the file is otherwise written only at listener start.
2. **Delete only your own file.** With per-PID file names this comes for free. If the legacy `revit-<year>.json` is still written, delete it only when its `pid` matches the current process.
3. **List every instance.** `ListAvailable` enumerates the per-instance files `revit-*-*.json`, or `revit-*.json` de-duplicated by `pid` so that the legacy file doesn't list the same instance twice. The existing `TryParseDiscovery` / `IsOwnerAlive` already handle per-file parsing and dead-PID cleanup. `is_currently_connected` would compare PID instead of year.
4. **Pin to an instance.** For example `--target-pid <pid>` / `BIMWRIGHT_TARGET_PID`, plus an optional `pid` (or `document`) argument on `revit_switch_target`. When pinned to a PID, a reconnect goes back to that PID only, or fails clearly. It never falls back to another instance.
5. **Report it.** `revit_get_current_target` adds `currently_connected_pid`, plus the document title if available.
6. **Listener back-off.** A short, capped back-off in the `ListenLoop` catch, and/or have `Stop()` release the active client pipe before a restart reuses the same pipe name.

Existing clients and year-based targeting keep working as today. With several same-year instances, year-only targeting would still pick the most recently started one. Pinning (4) and the extra fields (5) are opt-in. Items 1–3 and 6 do change internals by default: one discovery file per instance, a plugin deletes only its own file, and `revit_list_available_targets` returns one entry per instance instead of one per year. The token/ACL model stays the same.

If you're open to it, one more idea: even when unpinned, reconnecting to the same PID (instead of whichever Revit wrote the file last) would make the default safer. Happy to leave that to your judgement.

Glad to test a build on Revit 2026 with several instances open. Thanks for rvt-mcp, it's been very useful.
