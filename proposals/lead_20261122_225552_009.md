*Project description:*
## Goal

Bring TrailBuddy to iPhone while preserving offline-first behaviour, shared domain code, map and planner performance, and a high proportion of repeatable desk tests. The operator has an iPhone 8 (iOS 16) for initial device testing. First investigate and measure the tooling and architecture, then choose implementations; do not assume that a rewrite or an extra rendering engine is needed.

Environment: ☁️ architecture, Dart tests and implementation · 💻 Xcode, iOS simulator and profiling · 📱 iPhone, actual sensors, background behaviour and Garmin · 👤 Apple account, distribution and product decisions.

## Findings to verify first

- There is no `ios/` project on the inspected main snapshot. Flutter, the repositories, map facade, Dart routing engine and much of the business logic are shared already; audit `!kIsWeb` branches, as some assume Android. `rideRecordingAvailableProvider` and `sensorLogAvailableProvider` must not promise iOS support until proved.
- MapLibre 0.3.7+1 already resolves `maplibre_ios`; the existing facade selects it for non-web. This does **not** prove that our integration, MBTiles/PMTiles, offline layers, or performance work on iOS. The web uses flutter_map; the Android fallback is also flutter_map. Keep the facade, shared hit-testing and existing line-cache benefits in the comparison.
- Android recording uses `flutter_foreground_task` and an Android foreground service. The plugin's documented generic iOS background task is periodic, not a continuous Android-like service. Evaluate Core Location background modes and the separate background-location example; verify actual lifecycle semantics rather than promising continuation after force-quit. Local `tb_voice`, `tb_ambient` and Garmin platform bridges have Android implementations; inspect all MethodChannels and dependencies for support and graceful degradation.
- Existing web Safari location report #633 is related but independently reproducible; do not silently assume the native work fixes it.

## Initial tooling probe (2026-11-22)

- Tested an isolated export of main at `d8fb95d6` on Flutter 3.47.5 / Dart 3.13.4, Xcode 27.0 (iOS SDK 27.0), CocoaPods 1.16.2. Installed simulator runtimes: iOS 26.2 and 27.0. No iOS 16 simulator or iPhone 8 was tested.
- `flutter create` updated dependencies in its throwaway copy; discard that resolution. Restoring main's `pubspec.lock` and running `flutter pub get --enforce-lockfile` provided the baseline. The generated project targets iOS 15.0.
- Plugin manifests on that baseline: Firebase Core 4.15.2 and Messaging 16.7.1 require iOS 15; MapLibre iOS 0.3.7+1 declares iOS 12; geolocator_apple 2.3.14 iOS 11; inspected remaining native Flutter plugins declare iOS 13 or 15. These declarations do not establish the minimum of every transitive native dependency or prove iOS 16 device support. `path_provider_foundation` 2.6.0 is a Dart plugin, not a missing native plugin.
- Swift Package Manager resolution did not complete during two attempts; cause remains open. In a disposable project, CocoaPods resolved MapLibre Native 6.30.0 and Firebase 12.19.3. The unmodified MapLibre iOS 0.3.7+1 pod failed the simulator build with `Use of undeclared identifier MapLibrePlugin`: its bundled generated `MapLibreIos.h` shares the Swift-generated header's include guard. Renaming the guard alone exposed duplicate declarations. Excluding that bundled header from the podspec in a temporary plugin copy allowed the iOS simulator debug build to succeed. This is a diagnostic workaround, not a selected product fix or proof of map/offline functionality. Do not publish a temporary local override.
- Still open: complete the transitive native dependency and licensing inventory, investigate SPM resolution, reproduce/verify on iOS 16 hardware, compare map alternatives, test startup and offline behaviour, and measure before choosing an architecture.

### Simulator smoke and map comparison — initial evidence

- With the diagnostic CocoaPods header exclusion above, a Debug build started on an iPhone 17 simulator with iOS 26.2 and displayed the login screen; the process remained running. This establishes neither successful login nor map, offline, sensors, iOS 16 compatibility or device performance.
- The [0.4 migration guide](https://maplibre.org/flutter-maplibre/docs/migrate/upgrade-from-v0.3.x/) describes iOS 15, Swift Package Manager only and API changes. The [0.4 setup guide](https://github.com/josxha/flutter-maplibre/blob/834fc237fb52ad7d3fc5759c1c3f489ae4f387b8/website/docs/getting-started/setup.md) specifies Flutter 3.47 and Dart 3.13. Installed tool versions meet those stated minimums; 0.4's new native backend and the app's existing offline integration still need an actual build and feature/performance comparison.
- The distinct [maplibre_gl package](https://maplibre.org/flutter-maplibre-gl/) documents native offline regions, and its [iOS offline guidance](https://maplibre.org/flutter-maplibre-gl/advanced/offline-regions/) warns that the OS can clear Library/Caches. This is a candidate-specific warning, not evidence of the storage location of our 0.3 integration.
- `flutter_map` has separately documented local vector providers for [PMTiles](https://github.com/josxha/flutter_map_plugins/blob/main/vector_map_tiles_pmtiles/README.md) and [MBTiles](https://github.com/josxha/flutter_map_plugins/blob/main/vector_map_tiles_mbtiles/README.md). Provider existence does not establish parity with TrailBuddy's saved areas, style or performance.
- Independent throwaway `maplibre: 0.4.0` prototype (resolved `maplibre_native_ffi: 0.202611.0`): `flutter build ios --simulator --debug` failed because the native-assets hook requested an unavailable iOS simulator x64 archive. `flutter run` targeting the Apple-Silicon iPhone 17 simulator built and displayed the public online demo map. This does not validate TrailBuddy integration, saved areas, offline map data, iOS 16, performance or Intel simulator CI. The 0.4 prototype did not include Firebase, so it does not resolve the full app Swift Package Manager investigation.
- No architecture choice has been made. Version-specific maintenance, licensing, implementation costs and equivalent real-device benchmarks remain open.
