# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Android sideload release: mobile_release.yml android job builds the APK for v* tags**

*Project description:*
## Problem

HappyNotes has shipped no Android build since 1.1.4 (GitHub Release, 2025-06-25). `android_release.yml` fires only on bare `X.Y.Z` tags, but releases have been tagged `vX.Y.Z` since #58 (latest `v2.0.1`), so no APK is built. The workflow also `cat`s `android/key.properties` into the job log (GitHub masks the secret values, but the step has no purpose) and uses the deprecated `::set-output`.

The Play Store slice #59, which was to replace this workflow, is parked: there is no Play developer account. Sideloaded APKs from GitHub Releases are the only Android channel for now.

## Approach

1. Add `.github/workflows/mobile_release.yml`, triggered by `workflow_dispatch` with inputs `tag` (required; must match `^v[0-9]+\.[0-9]+\.[0-9]+$` and exist) and `release_notes` (optional, plain text). Keep this file name: its `run_number` is the build-number source (`RELEASING.md`, "Mobile build numbers").
2. The `android` job checks out `tag`. It prepares `.env` from `.env.production` with the existing `VERSION`/`SEQ_API_KEY` substitutions, and writes `android/key.jks` and `android/key.properties` from the existing secrets (`KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`) without printing them.
3. It runs `flutter build apk --release --build-name=<tag without v> --build-number=$((github.run_number + 100))`.
4. It creates or updates the GitHub Release for `tag` with the APK attached. The body holds the `CHANGELOG.md` sections after the previous `v*`-tagged GitHub Release, up to `tag` (all `v*` sections up to `tag` when no such Release exists), followed by `release_notes`.
5. Delete `android_release.yml`. Update `CI_WORKFLOW.md` and `RELEASING.md`.

## Acceptance criteria

- [ ] Dispatching `mobile_release.yml` with `tag=v2.0.1` (or the latest `v*` tag at delivery) publishes a GitHub Release for that tag with an APK attached. `aapt dump badging` (or `apkanalyzer manifest`) on the APK shows `versionName` `X.Y.Z` and `versionCode` = that run's `run_number + 100`. Paste the run URL and the output.
- [ ] Re-dispatching the same tag leaves exactly one Release for it, updated in place: `gh release list` shows the tag once.
- [ ] A malformed `tag` (e.g. `2.0.1`) or a non-existent tag fails in the first step, before any Flutter step runs. Paste both run URLs.
- [ ] The APK is signed with the existing release keystore, so 1.1.4 (`versionCode` 1) installs upgrade in place: the `apksigner verify --print-certs` SHA-256 digest equals that of the 1.1.4 Release APK.
- [ ] `grep -rnE 'cat .*key\.properties|::set-output' .github/workflows/` returns nothing. `android_release.yml` is deleted. `CI_WORKFLOW.md` and `RELEASING.md` describe `mobile_release.yml`.
