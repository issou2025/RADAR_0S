Move Kent's primary development environment from the MacBook Pro to **office4**, a new
developer-class Linux Mint workstation, while retaining full development capability on the

Full plan: `~/Documents/office4/office4-migration-plan.md` (local, not in-repo).

**Symptom:** the entire development environment — 20 repos, four agent config trees, all
credentials, and every dotfile — exists on exactly one machine, a laptop. There is no second
machine capable of doing this work, and office4 (32 threads, 125 GiB RAM, 1.8 TB) sits
near-idle with only `git`, `python3`, `docker`, `tailscale`, and `rsync` installed.

**Observer:** Kent, 2026-08-28, opening the migration topic.

**Cost of doing nothing:** a single point of failure for all development capability;
office4's capacity stays unused; and the work that office4 is intended to enable (Jenkins for
issue-queue maintenance and agent dispatch, larger agent fleets, local inference) cannot
start.

## Target architecture

> **office4 joins as a second *Mac-class* node, not a second *office2-class* node.**

| | MacBook Pro | office4 | office2 |
|---|---|---|---|
| Class | unmanaged peer | **unmanaged peer** | managed host |
| Role | mobile dev | primary dev + compute | always-on hub |
| Registered in | `network-topology.devices` | `network-topology.devices` | `hardware-inventory` + `service-inventory` |
| Unix users | kgale | **kgale only** | kgale / claude / codex |
| Deploy path | none | **none** | felix-deployer manifests |
| Runs Felix? | no | **no** | yes |

### Governing principle

> **office2 is unattended. office4 is attended.**

office4 **is** always-on, so uptime is not the axis. The axis is whether a human is in the
loop. office2 must survive with nobody looking. office4 is a physical workstation that is sat
at, where a reboot for a kernel or GPU-driver update is a normal Tuesday.

**Test before moving anything:** *"If this is down for ten minutes while nobody is watching,
is the cost annoyance or data loss?"* Annoyance → office4. Data loss → office2.

### Why office4 is NOT a managed host in pass one

Felix's operational substrate is single-host **in code**, not by convention:

- `deploys/schema/manifest-v1.schema.json` has no `host`/`target` field
- `scripts/deploy/lib/deploylock.py:41` — lock path is literally `office2-checkout.lock`
- `scripts/deploy/felix-deployer/_tick.py:59` — `DEFAULT_REPO_ROOT` is a module constant
- `scripts/deploy/felix-deployer/rebaseline.py:49` — strips `ssh office2-claude` prefixes
  because it assumes it *is* office2
- `scripts/deploy/lib/tier.py:73` — hardcodes `ssh office2-kgale`
- `restic forget` runs with **no `--group-by`** — a second host in the same repo would strand
  existing snapshots from pruning
- `self-pull`: "merging to `main` **is** the deploy"

Making office4 managed is a design change across five subsystems. Nothing in this migration
requires it.

**office4 must not hold a `kg-automation` checkout at any path felix-deployer would
recognise.**

### On `claude` / `codex` Unix users for office4

The office2 `claude` user exists because **the agent is a remote actor on a host it does not
live on** — attribution plus blast radius, which is why it is non-sudo. office4 inverts that:
the agent **lives there** and needs Kent's repos, git identity, `gh` token, and `~/.claude`
tree. A separate Unix user would firewall it from exactly what it needs.

- **R1 — Workstation** → `kgale`, no new users. **This pass.**
- **R2 — Remote-operated service host** → the office2 pattern. **Deferred** until office4
  hosts managed services.
- **R3 — Service runtime** (Jenkins etc.) → per-service system accounts, never a generic
  agent user. Per-service, as each lands.

### The spec-kitty-qa pipeline is NOT part of this migration (revised 2026-08-28)

spec-kitty has signed up with **exe.dev** (root Linux VMs, SSH, HTTPS, persistent disk) and
has free instances. An intern starting in September owns moving the QA pipeline there. The
pipeline was only ever going to sit on office4 briefly, for prototyping.

**Recommendation: skip office4 entirely for the production QA pipeline.** office2 → exe.dev,
one migration, done by the person whose job it is. Routing it through office4 first would:

- stand up a **new public ingress on personal hardware** (a second Funnel, or office4 exposed
  directly)
- keep the work/personal boundary blur alive rather than resolving it — merely relocated
- produce migration work that is thrown away within weeks

exe.dev resolves the public-ingress problem *properly*: a real HTTPS endpoint on work-owned
infrastructure, no Tailscale Funnel, no Certificate Transparency entry on a personal hostname.

**What office4 legitimately offers instead:** a **local, non-public dev instance** of the QA
pipeline for the intern to develop and break — no public ingress, no production data, no
boundary problem because it serves no real traffic. The webhook's `env/` directory already
carries a `local-docker.json` config alongside `linear-qa.json`, so this mode exists.

Net effect on this epic: **none of the QA pipeline work is a child of this epic.** It is
tracked on #887, which needs re-scoping from "the dev-class machine" to exe.dev.
