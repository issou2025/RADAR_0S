# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[DevEx] Add an offline developer preview with seeded data and controllable loading states**

*Project description:*
## Summary

Add a **self-contained, Flutter-native developer preview mode** to TouchIn so developers can run and browse the application **without a real account, backend, database, credentials, or `.env` files**.

The goal is to make it easy to develop and visually verify UI features—especially skeletons, server-startup waiting screens, loading transitions, errors, empty states, and populated pages—using deterministic fake data and adjustable simulated latency.

**This must be a development-only simulation, not an authentication bypass in the real application.**

## Existing architecture / implementation context

- `frontend/lib/main.dart`: `MyApp` already accepts injected `TouchInApi?` and `TokenStorage?`. Startup currently restores a persisted session and checks `getAuthContext()` before entering protected workspace routes.
- `frontend/lib/core/network/touchin_api.dart`: central API abstraction, with authentication and feature-specific requests.
- `frontend/lib/core/navigation/workspace_router.dart`: authenticated route and session lifecycle.
- `frontend/test/widget_test.dart`: test-only fake API/token storage, including asynchronous auth-context control and coverage for the **“Aguardando o servidor”** splash.
- `frontend/pubspec.yaml`: Flutter/Dart project—no Node/npm or environment-file system is needed for this feature.

Prefer extending these existing seams rather than adding an unrelated mock server, complex infrastructure, or a second application UI.

## Desired developer experience

1. Run TouchIn locally with the standard **Flutter debug workflow**, without configuring environment files, secrets, a database or an API.
2. Present an obvious **“Enter developer preview”** option in debug builds (or an equivalent explicit developer-only entry point). No real username, password, pre-existing account or login request required.
3. Browse existing pages and deep links with a clearly marked **synthetic local identity** and coherent seed data.
4. Use a small **developer controls panel** to change the simulation without editing code or restarting the app:
   - Data state: **populated / empty / error**.
   - Request timing: **instant / configurable delay / unresolved pending** (with a way to cancel or reset pending simulations).
   - Server readiness: **ready / delayed startup / unavailable / retry then success**.
   - Optional predefined scenarios for specific screens or features.
   - **Reset fixtures/scenario** to their deterministic defaults.
5. Watch actual application **loading widgets and skeletons** render through the normal presentation paths, not static mockups or screenshot overlays. Simulate both cold startup and ordinary page-level data fetching independently.

The preview controls should be visibly identified as developer-only, easy to dismiss, and should not interfere with normal screen layout when hidden.

## Seeded data and functionality

- Provide **deterministic, realistic but entirely fictional fixtures** for the features needed to navigate the workspace: company/user/roles, employees, projects/tasks, Kanban/Backlog, time tracking, audit views and other currently supported pages.
- Reuse the app's existing data contracts, parsers, widgets and navigation; include linked stable IDs, plausible dates and statuses, different list sizes, and representative long/short text to reveal layout defects.
- Support more than one **mock authorization persona/role** where useful for checking role-aware UI; **never** confer real backend privileges.
- Keep fixture references coherent across pages (e.g. projects, columns, cards, users and tasks must relate consistently).
- Make common UI interactions locally testable when practical—updates, reordering, filters, pagination, and other visible actions should modify only **in-memory fake state**, never a live backend. Explicitly identify controls that are not simulated.
- Distinguish simulated errors from the real application's error handling; use the same visible UI components and retry flows.
- Seed data must be reproducible across runs by default, with a reset action. Persist only non-sensitive developer preferences if necessary; no fabricated real credentials or production-like tokens in secure session storage.

## Security and isolation (non-negotiable)

- **Debug builds only:** compile-time gate the feature (e.g. `kDebugMode`) and require explicit entry into developer preview. Do not make it available in profile/release/production builds. Hostname or query-string checks alone are **not** sufficient security boundaries.
- Preview must use an **isolated fake API/data adapter**. It must **never call real authenticated endpoints**, create real sessions, issue backend tokens, or perform network writes, even when a previously used production session exists on the device.
- Keep the production authentication flow, permission checks, token persistence, session expiry/revocation, and backend authorization **unchanged**. Avoid a generic `skipAuth` check scattered throughout production routes or API clients.
- Clearly differentiate synthetic preview identity/state from authenticated production state; do not persist or reuse preview identity as a valid real session.
- Production/release builds must not expose the entry point, developer panel, mock authentication behavior, or an alternate way to access protected pages. Add explicit tests proving that preview activation is impossible in release configuration.
- Do not introduce external services, remote fixture downloads, secret values, broad dependencies, or new backend development endpoints just to support the preview.

## Implementation guidance

- Design a small, centralized **preview configuration + deterministic fixture factory + fake API implementation**, injected at the application boundary using the existing testable API seam where feasible.
- For navigation, use a **preview-specific session/context** without weakening the normal authenticated router's guarantees.
- Inject delays and failures at the fake request/bootstrapping boundary so **existing real loading components** appear naturally; avoid unnecessary production code branching.
- Support explicit fake server-boot scenarios independent of page-level request delays; provide a recovery/reset path so a deliberately never-resolving request cannot strand the developer.
- Clean up timers, pending futures/controllers and scenario listeners on route changes, reset, and disposal. Prevent stale mock responses from overwriting a newer scenario.
- Keep runtime overhead negligible outside developer preview. No backend or deployment changes are needed.

## Acceptance criteria

- [ ] A developer can start Flutter locally and open a populated workspace **without any account, backend, secrets or `.env` files**.
- [ ] Preview entry and controls are available only in debug builds; release/profile behavior remains the normal authenticated app.
- [ ] The preview never contacts real APIs or writes real data, including on existing browsers with previously stored sessions.
- [ ] Seed fixtures cover the principal screens, remain coherent and deterministic, and can be reset without restarting the app.
- [ ] Developer controls can independently simulate startup/server loading and per-screen data loading with instant, delayed and pending states.
- [ ] Existing skeletons, progress indicators, error/retry screens and empty states appear through their actual widget paths.
- [ ] A developer can test **cold-start wait → ready**, **server unavailable → retry → ready**, **page skeleton → populated**, **page skeleton → empty**, and **page skeleton → error → retry**.
- [ ] In-flight simulations can be reset or cancelled safely; no orphan timers, stale responses or retained listeners.
- [ ] Desktop and narrow/mobile viewport workflows remain usable; the debug controls do not obstruct normal content.
- [ ] Automated tests cover dev-only gating, zero real API activity, session isolation, fixture consistency, scenario changes, retries and lifecycle cleanup; run available Flutter checks and report verified results.
- [ ] A short developer README describes **how to start preview mode**, switch scenarios, reset seed data and exit to normal login—with **no environment setup**.
- [ ] Implementation and validation stay local. **Do not deploy or publish.**
