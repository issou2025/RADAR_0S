# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Architecture Re-baseline v3: AR-0 delta audit and staged 10/10 convergence**

*Project description:*
## Purpose

Establish a new forward-looking architecture authority for the repository without rewriting accepted history or performing a greenfield reset.

This program starts from exact accepted `main` `5be54c2989dbfa22822d3692e22156f23d2a4602` and preserves accepted R1–R9 and completed Pre-2J A/B/C/D repository results as immutable history/evidence. It remaps only future/unaccepted work into a stricter Architecture Re-baseline v3.

## First bounded unit — AR-0

AR-0 is read-only/governance-first. It must:

- inventory the actual current repository, not assumptions from earlier plans;
- classify every v3 target as `PRESENT`, `PARTIAL`, `MISSING`, `CONFLICT`, or `SUPERSEDED`;
- classify runtime/infrastructure components `KEEP`, `SIMPLIFY`, `DEFER`, or `DELETE`;
- identify current single-authority and dual-authority risks;
- map the active Pre-2J roadmap into the new sequence without erasing accepted provenance;
- explicitly preserve the Windows updater program rather than losing Batch E;
- define the cutover rule for existing Python operational orchestration to a project-specific Rust `opsctl` without creating dual operational authority;
- record whether the current D3 topology may proceed unchanged or must be adjusted before irreversible production provisioning.

No production code, Cloudflare resource mutation, D1 mutation, secret mutation, external provider mutation, staging/production deployment, `openapi/v1/**` mutation, or `production_ready=true` claim is allowed in AR-0.

## Program target

The target architecture is:

`Domain -> Application/Ports -> Adapters -> Composition Roots`

with independent operational lifecycles for application release, persistent infrastructure, database evolution, credentials, encryption keys, recovery, and Windows delivery.

Wrangler remains the Worker configuration authority. A future Rust `opsctl` may own project-specific inventory/plan/doctor/provision/migration/recovery orchestration only after parity/cutover proof; it must not become generic IaC or coexist as a second mutable authority.

## Required governance outcome

A dedicated repository plan must define:

- authority hierarchy and supersession semantics;
- capability ownership map;
- dependency and composition-root rules;
- Cloudflare topology ownership;
- environment model (`staging`, `production`, `rehearsal`);
- secrets/credential/key lifecycle;
- D1 compatibility windows and migration authority;
- immutable release/promotion model;
- recovery/rotation rehearsals;
- Windows release/update architecture;
- developer-readability acceptance test;
- whole-project final P0/P1 audit.

## Binding production sequencing

Architecture convergence and production rollout are separate authorities, but they are **not parallel execution tracks**.

The mandatory sequence is:

1. complete Architecture Re-baseline v3 through the final AR closeout against the latest accepted `main`;
2. prove the target architecture, ownership/composition rules, environment/secrets/release/recovery model, operational tooling boundaries and developer-readability DoD;
3. complete the whole-project final P0/P1 audit with no unresolved production-blocking architecture finding;
4. only then permit a `Production Core v1` release gate;
5. after `Production Core v1` is accepted, activate later product capabilities (Mailbox Administration, Mailbox Jobs/Automation, Outbound Mail, etc.) through separately gated capability releases.

Therefore `Production Core v1` is **blocked by the complete architecture-refactor program**, not merely by selected AR slices. `production_ready=false` remains mandatory until the final AR closeout explicitly authorizes the Production Core gate.

The first production scope is intentionally narrower than the repository source tree: users/authentication, clients, browser profiles/Camoufox, bulk browser-profile operations and client↔browser-profile bindings may be production-enabled while mailbox code remains present in the same `main` but production-disabled by server-side capability authority. No long-lived reduced production branch or mailbox fork is allowed.

## Required pre-production machine authorities

Before `Production Core v1`, the architecture program must establish and mechanically validate:

- a machine-readable **Production Capability / Release Profile** defining capability identity, dependencies, environment activation, release-set compatibility and fail-closed server-side production enablement;
- a complete **Python → opsctl disposition inventory** covering every repository-owned Python executable with owner, callers, LOC, role, remote-mutation status and one explicit disposition: `KEEP_PYTHON`, `MOVE_OPSCTL_READ`, `MOVE_OPSCTL_MUTATION_LATER`, `MERGE`, `RETIRE`, or `DELETE`;
- a single-authority rule: GitHub remains approval/orchestration authority, `opsctl` owns typed project operational semantics after bounded cutover, Wrangler remains the allowed Cloudflare Worker mutation executor, and Python remains valid for deterministic repository/CI validation where that is the cleanest implementation;
- no dual mutable authority for the same operational concern.

These machine authorities are architecture/refactor deliverables and may be implemented during the AR program, but they do not authorize production rollout by themselves. Production remains blocked until final AR closeout.

## Acceptance discipline

Each implementation unit after AR-0 must start from latest accepted `main`, use one bounded architectural reason per PR/PR chain, include permanent positive/negative fitness tests, preserve exact-head CI discipline, remain `behind_by=0` at acceptance, and use guarded squash merge. Historical accepted plans are never rewritten to pretend the new program existed earlier.

Phase 2J remains blocked and `production_ready=false` remains mandatory until the new final closeout proves the required repository-owned and external gates.
