**Why it still matters.** #162 is fragile in a specific way. If `RevitAPIMockCodeGenerator` ever references another BHoM assembly, every consumer must seed that too, and the failure mode is a soft-skip that silently degrades coverage rather than an error. Committing the generated sources makes the mock repo buildable with no BHoM closure at all, which is the property a validation fixture should have.

**One further consequence, relevant to a separate question.** Committing the sources severs the generator from the build path, so the mock repo would no longer need a populated `ProgramData` to produce its own artefacts. That makes it substantially easier to relocate, publish or package, and it adds no information to the repo that is not already committed: `ApiTypes.cs` is a mechanical transform of the JSON type lists already tracked there.

## The problem

`RevitAPIMockCodeGenerator/Program.cs` calls `BH.Engine.Adapters.File.Compute.ReadFromJsonFile`, resolved through `<HintPath>$(ProgramData)\BHoM\Assemblies\File_Engine.dll</HintPath>`.

All five proxy projects carry a solution-level `ProjectDependencies` edge on the generator (`{89C86588-0FF7-4ADE-A68A-0C8363319DAE}`), and **zero `.cs` files are tracked in any proxy project** (`Generated Files/` is gitignored). The generator's `PostBuild` target runs itself and writes `ApiTypes.cs` into each proxy directory.

So the generator must compile for the proxies to build, and the generator needs a BHoM install. A consumer without `File_Toolkit` in its closure gets:

```
error CS0234: The type or namespace name 'Adapters' does not exist in the namespace 'BH.Engine'
```

and the whole solution build fails.

**Verified by A/B on a clean clone, 2026-08-10:**

| Leg | `File_Engine.dll` in `ProgramData\BHoM\Assemblies` | Result |
|---|---|---|
| A | absent | `1 Error(s)`, `Build FAILED`, `error CS0234` |
| B | present | `0 Error(s)`, `Build succeeded`, all five assemblies at expected sizes |

## Why "just build the five proxy projects" does not work

Measured on a clean clone: building only the proxies produces `RevitAPI.dll` at **4,608 bytes** against a real **187,392**, with the correct assembly identity and **zero `Autodesk.Revit.DB` types**. That is worse than no mocks at all: the identity resolves so nothing soft-skips, while every type reference still fails and the failures look genuine.

## The fix

Commit the generated proxy sources so the proxies build without the generator running.

**Verified previously:** clean clone, committed sources, generator not built, `ProgramData` pointed at a directory with zero files, and all five proxies build at sizes identical to the real ones (187392 / 18944 / 13312 / 27136 / 10752). Not byte-identical, as MVIDs vary with build path.

## Impact if not done

*(Superseded by #162, retained for the record.)* `BHoM/Revit_Toolkit` reported **805 methods as unverified rather than verified** on every versioning run, all 805 attributable to the missing mocks (443 blocked on `RevitAPI`, 329 on `Autodesk.Revit.DB.*` types, 33 on `RevitAPI`). The old BHoMBot pipeline verified this surface because it built the entire installer set before versioning, so `File_Engine.dll` was always present; the new per-repo CI had no such guarantee.

This was never causing failures. The check reported `Warning` and exited 0. It was a coverage gap, not an outage.

## Note

Item 1 is the one that matters; the rest support it. The workaround now exists entirely on our side (#162, seeding `File_Toolkit` into the mock build's closure), so this is not blocking us. Committing the sources is the better architecture, because a validation fixture should not depend on the fleet it validates.

There is also a **trap for anyone experimenting locally**: the proxy csprojs' `PostBuild` `xcopy` writes to `C:\ProgramData\BHoM\Assemblies` unconditionally, so building them overwrites whatever mocks are already installed.

## Constraint to be aware of before proposing this upstream

`BHoMBot` builds the mock solution itself, from a hardcoded location: `Installer_Engine/Compute/RevitVersioningTypes.cs:19` clones `BuroHappoldEngineering/RevitAPIMock` and `:25` runs `BuildSolution`. Committing the sources does not break that path, since a solution build with sources present simply skips the generation step. But it means any change here should be checked against BHoMBot's build while BHoMBot is still live.
