*Project description:*
## Problem

`frontend-web/` (PR #4) has no tests of any kind:

- `app.js` — opens the WebSocket, renders readings, surfaces faults
- `index.html` — the page structure the renderer writes into
- `style.css` — including the severity colours that `describe()` drives

Nothing verifies that a `type: "dtc"` message renders its fault, that a `critical` severity gets the right colour, or that the page survives a dropped connection. All of it is checked by opening a browser and looking.

That is genuinely fine at 64 lines of vanilla JS. It stops being fine when the message shape changes — and the message shape is owned by the backend, which has three future clients (this dashboard, React Native, Android Auto).

## What this fixes

A change to what `/ws` emits fails a test instead of silently rendering an empty gauge.

## How

Deliberately **not** a browser automation suite — Playwright for three static files is more machinery than the code it tests.

The cheap version first: a contract test on the **message shape**, shared with #17. If the backend guarantees `{code, description, severity, zone, deferrable}` and the frontend asserts against the same fixture, a divergence fails in Python without a browser.

Escalate only if the frontend grows past vanilla JS. If DASH-1 becomes React (as `DEVELOPMENT_PLAN.md` intends, so components are shared with React Native), the calculus changes and component tests become worth it.

## Done when

- [ ] the message shape the frontend depends on is asserted somewhere automated
- [ ] a decision is recorded on whether browser-level tests are worth it *yet*

## Not this

Browser automation, visual regression, cross-browser. All premature for three files with no build step.
