# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: Offer store-compliant app ratings**

*Project description:*
## Problem Statement
Slove has no way for someone to rate it on the App Store or Google Play. Engaged users cannot find a voluntary rating link, and the app never asks for a review at an appropriate point. A custom ratings form or indiscriminate prompt would undermine trust and may violate store guidance.

## Solution
Use each platform's OS-managed in-app review flow after meaningful, score-neutral engagement at the end of a game round. Also provide a persistent Romanian 'Evaluează aplicația' action in the Home footer that opens the corresponding public store listing for a user-initiated review. The app itself does not collect stars, review text, identifiers, or analytics; the stores own submitted ratings and control whether an automatic dialog appears.

## User Stories
1. As a player who has completed several rounds, I can be invited to rate Slove at a natural pause rather than during a question, so my game is not interrupted.
2. As a player with any score, I have the same opportunity to review the app, so an invitation does not depend on giving positive feedback.
3. As a player who dismisses a native prompt, I can continue playing without penalty or a repeated immediate interruption.
4. As a player who wants to rate on my own terms, I can find a rating action on Home and open the correct store listing.
5. As a player whose device or installation is ineligible for native in-app review, I can still use the manual store action where a valid listing exists.
6. As a player on an unsupported platform or with an unavailable store listing, I do not see a dead-end rating action.
7. As a privacy-conscious player, my exercises and progress remain local and the app does not send my rating or track whether I submitted one.

## Implementation Decisions
- Treat this as one cohesive spec, not an epic. Support iOS App Store and Android Google Play; no custom stars, sentiment survey, incentives, or routing based on score.
- Invoke the platform-native in-app review API after the completed-round UI has settled, never directly from a rating button, on first launch, while answering, or immediately after an error. A completed round of any score counts; all four games participate. The API may silently decline to display anything; do not promise display or assume its completion means a review was submitted. Do not block navigation or gameplay if unavailable or failing.
- First eligible automatic attempt is after three completed rounds across games; cap to one attempt per app session, wait at least 90 days between attempts, and at most three attempts per rolling 365 days. Persist completed-round count and attempt timestamps locally across launches; record an attempted native request, not a purported review. The OS/store's stricter undisclosed quota still controls actual display. Manual store navigation is always available and is not subject to the automatic quota; after a manual navigation, suppress automatic attempts for 365 days to avoid nagging without claiming a rating was submitted. Handle corrupted/missing local state by safely resetting gating without affecting game progress.
- Add a small injectable rating coordinator/platform gateway and local state storage so the policy is independent of the widget tree and review/store actions can be faked in tests. Use a maintained Flutter native-review integration only if needed for the platform APIs (justified exception to the dependency constraint); reuse the existing url_launcher for the manual outbound link. Verify package/platform compatibility and pin a suitable version when implementing.
- The Home footer gains a Romanian, accessible 'Evaluează aplicația' link beside the existing 'Confidențialitate' link. Preserve the privacy link and all existing game-summary actions ('Joacă din nou', 'Înapoi la jocuri') unchanged; do not insert a new summary button or replace existing game feedback. Use existing design tokens/components and relative imports.
- Manual iOS action opens the public App Store review/listing URL using the actual numeric Apple app ID; Android opens the public Google Play listing for the confirmed application ID, with HTTPS fallback if an app-store URI cannot launch. Do not invent an Apple ID or publish a placeholder. Before release, obtain and validate the Apple ID and listing URLs on real devices/store installations. Hide or disable the link with an intelligible outcome if a valid listing is unavailable; never leave a dead button.
- Update in-app privacy wording and store-listing/privacy disclosures as necessary to mention the optional store outbound link while retaining accurate 'no app-collected user data' claims. Review notes should mention the in-app review flow. Do not silently change the unrelated conflicting public privacy-policy URL; raise its reconciliation through the existing listing work (#14).
- Follow the existing release process: implement against the configured development branch, then verify via TestFlight and Play internal testing before production. No branch or product code is created by this spec.

## Testing Decisions
- Test the concrete public coordinator seam (a new ReviewPromptCoordinator interface receiving completion events, persistent state, clock/session boundary and injectable platform gateway): first/third completions, score independence and cross-game accumulation, restart persistence, 90-day cooldown, rolling yearly cap, one-per-session behavior, manual-navigation suppression, unavailable/failed native request, and corrupted state. Do not assert that a native dialog actually appeared or a review was submitted.
- Exercise the existing HomeScreen injection seam with a fake rating gateway/coordinator in widget tests: Romanian footer action, correct platform URL/fallback, unsupported/unconfigured behavior, privacy link preserved, accessibility label and navigation not blocked.
- Use the existing injectable game-screen exercises/progress seams and shared LexioGameSummary behavior to verify each of the four game completions produces exactly one completion event without changing replay/back actions; avoid coupling tests to private widget structure.
- Run flutter analyze and flutter test; manually check real iOS and Play-installed Android builds because review-dialog display is OS-controlled and development/TestFlight/internal-testing behavior differs. Check both outbound store links on devices after store IDs exist.

## Out of Scope
- Collecting ratings/reviews inside Slove, sending rating data to a backend, analytics, asking sentiment before native review, offering incentives, showing custom star widgets, ratings on non-iOS/Android platforms, or automatically detecting whether a user actually reviewed. Publishing or fixing the public privacy-policy URL itself remains in listing work.

## Auto-decided
- One spec, not an epic (grade 0.2; one cohesive outcome).
- Three completed rounds before first attempt; 90-day spacing, three attempts/365 days, one/session (grade 0.5; conservative defaults aligned with both stores' rate limits).
- No pre-rating survey, score gating, tracking, or assumed review result (grade 0; platform guidance and project privacy constraints).
- Local persistence and injectable gateway; existing url_launcher for store navigation and justified native-review bridge (grade 0.4; repository architecture and dependency constraints).
- Missing Apple numeric ID is a release prerequisite, not a made-up constant; unsupported/unconfigured targets must fail safely (grade 0.4; identifier not present in repository).
- Preserve existing summary and privacy affordances; update outbound-link disclosure without changing unrelated privacy-policy URLs (grade 0.3; current UX and listing workflow).

## Further Notes
- Agreed choices: both native automatic and manual rating flows (grade 0.9; user preference); post-round after several completions (grade 0.8; interruption trade-off); manual link in Home footer (grade 0.65; discoverability/clutter trade-off). User confirmed this shared understanding before publication.
- Store guidance: https://developer.apple.com/design/human-interface-guidelines/ratings-and-reviews and https://developer.android.com/guide/playcore/in-app-review . Native requests are subject to store-controlled quotas and may not present UI; a user-triggered action should navigate to the store, not call the native request API.
- Related existing listing preparation: #14. Apple numeric listing ID is not recorded in this repo at definition time; verify it before shipping the iOS manual path.
