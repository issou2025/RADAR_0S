## Investigation done

### Source code scan

I grep'd the entire `apps/hermes-agent/` source tree for unguarded `.model_dump(` calls. Findings:

\`\`\`
agent/api_request_hooks.py:104:  if hasattr(value, "model_dump"):
agent/relay_tools.py:80:        model_dump = getattr(value, "model_dump", None)
agent/chat_completion_helpers.py:1571: def _dump_if_model(value):
agent/anthropic_message_convert.py:219: dumped = value.model_dump(warnings=False)
\`\`\`

These all have proper guards (`hasattr`, `getattr`, `_dump_if_model` wrapper). So the source code is correct **at these sites**.

### Suspect: deep Pydantic v2 transition

The error suggests an object is being passed where a Pydantic model is expected, but the object is a plain `dict`. Likely caused by one of:
- A v0.17→v0.21 migration path that converted some Pydantic models to dicts somewhere
- A third-party plugin (car-evolution, skill-trigger-map) returning dicts where v0.21 expects Pydantic models
- The `jobs.json` config schema changed but migration kept old format

### No full traceback available

`hermes cron incidents list` and `hermes cron runs <job_id>` only show the final `RuntimeError` line, not the full Python traceback. So I can't pinpoint the exact call site from the user side.

## Workaround (what I did)

I ran `hermes cron pause <job_id>` on all 11 failing jobs. They are now `[paused]` and don't dispatch. This stops the error spam and prevents wasted scheduler wakes, but obviously defeats the purpose of scheduled jobs.

I'd like to keep these jobs active. Could you:
1. **Reproduce locally** with any agent-mode cron job, and capture the full Python traceback?

3. **Ship a patch** — even if it's a one-line guard change in the right place.
