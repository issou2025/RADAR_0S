# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Measure the client's own rendering performance (frame build and raster)**

*Project description:*
We have no picture of the client's own rendering cost: how long frames take to build, how long they take to rasterise, and which surfaces are expensive. That is the performance question worth answering, and it is separate from backend latency, which belongs to the services that own it.

Open-ended on purpose. What to measure, how, and whether any of it should become standing tooling is @ggurdin's call.

Some context from a first pass, mostly so the same walls don't get hit twice:

- **Build and raster are separate costs with separate causes.** Build is UI-thread widget work; raster is GPU-thread work (shaders, blurs, `saveLayer`, large images). A surface can be fine on one and bad on the other, so a single "frame time" hides which.
- **Profile builds only.** Debug carries assertion and unoptimised-code overhead that makes build times several times worse than anything that ships.
- **Staging is not a valid place to measure.** It is built `--profile` (37.1MB bundle vs prod's 12.8MB) *and* its `/.env` sets `ENABLE_SEMANTICS=true`, which `main.dart` itself notes has a frame cost. Production has neither, so staging is inflated on both counts.
- **Verify GPU acceleration before trusting any raster number.** A headless browser may be software-rasterising, which would inflate raster times to the point of being meaningless.
- An embedded/hidden browser pane produces no frames at all, so nothing can be measured through one.

I did get numbers from a local profile build driven through Playwright, but **did not confirm the browser had a real GPU, so treat the raster figures as possibly artefactual**. Recording them only as a starting hypothesis, not a finding: build p50 was mostly healthy (2-20ms) while raster p50 sat at 31-83ms across every surface, and idle-while-logged-in produced expensive frames (build p50 20.6ms, max 199.6ms) which is odd for a still screen. If the GPU check invalidates the raster half, the idle-build observation stands on its own and may be the more interesting one.

Prior client perf work (#8393, #8416, #8418, #8420, #8431) all targeted compute and is closed; nothing measures whether it held.
