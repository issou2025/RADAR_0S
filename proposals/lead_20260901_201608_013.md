## Problem Statement

Gil can't currently see what MARVIN's automation is actually doing, or trust that it's running
reliably. Two coupled gaps: (1) once a ticket is claimed, its progress is invisible until a PR
shows up — no visibility into whether it's planning, executing, or stuck; (2) the pipeline
currently runs primarily on his laptop, which sleeps/closes between naps, silently breaking
continuity with no visible signal that it happened.

## Solution

Two coupled changes:

1. Relocate the pipeline's own entrypoints (`ticket_pipeline.py`'s launchd cron, `dashboard-webhook`)
   to run primarily on mac-mini (already always-on, already hosting several other MARVIN launchd
   jobs), with macbook-pro remaining an opportunistic worker `task_dispatch.py` can still route
   ticket execution to whenever it's up — no change to `task_dispatch.py`'s own machine-selection
   logic, which is already machine-agnostic ("self" vs. "remote" falls out of which machine's own
   launchd job invokes it).
2. Add a new "Activity" tab to the dashboard (already anticipated in CONTEXT.md's "Dashboard
   hosting, revised" note) showing a per-device board: each known machine (mac-mini, macbook-pro,
   future nodes) as a column with its live status (idle / current ticket + stage / unreachable),
   plus a shared backlog list of unclaimed `ready-for-agent` tickets underneath. The dashboard GUI
   itself keeps running wherever Gil is sitting; its data sources (webhook/refresh URLs) point at
   mac-mini's Tailscale hostname instead of `localhost` for the pieces that now live there.

## User Stories

1. As Gil, I want to see which machine (if any) is currently executing a ticket, so that I know the automation is actually alive without checking terminal logs.
2. As Gil, I want to see which ticket a machine is working on and roughly what stage it's in (planning / implementing / verifying), so that a stuck or slow run is visible instead of silent.
3. As Gil, I want to see the backlog of unclaimed ready-for-agent tickets in the dashboard, so that I don't have to run `gh issue list` to know what's queued.
4. As Gil, I want the automation to keep running even when my laptop is closed, so that I don't lose progress between naps.
5. As Gil, I want the dashboard to work the same whether I'm looking at it on my laptop or on mac-mini, so that I don't need to change my workflow based on which machine I happen to be using.
6. As Gil, I want to know if a machine has gone offline or unreachable, so that I don't mistake "can't reach it" for "it's idle."
7. As Gil, I want a PR's dashboard entry to show which machine produced it, so that I can tell where a given implementation actually ran.
8. As Gil, I want the per-machine status to update without me needing to manually refresh, so that the board reflects reality.
9. As Gil, I want the board to degrade gracefully if a machine is unreachable (SSH/Tailscale down) rather than hang the whole dashboard, so that one offline machine doesn't break visibility into the other.
10. As Gil, I want the primary-host migration to not require me to manually babysit two sets of cron jobs, so that I'm not the one keeping mac-mini and macbook-pro in sync by hand.
11. As Gil, I want a machine's "idle" status to be unambiguous from "unreachable," so red/gray/green-type states don't get confused.
12. As Gil, I want the existing single-machine status badge (built earlier this session) to become the mac-mini column in the new board rather than being thrown away, so prior work isn't wasted.

## Implementation Decisions

- **Primary-host relocation** (ops, not new code): install `com.marvin.ticket-pipeline.plist` and
  `com.marvin.dashboard-webhook.plist` on mac-mini (already has the repo/venv via existing
  cross-machine code-sync). Decide whether macbook-pro's copies are removed or kept-but-disabled as
  a manual fallback. `task_dispatch.py`'s `select_machine()` needs no code changes. Document this as
  its own ADR (which machine is authoritative for which job is an architecture decision, not just a
  deploy step), matching this repo's existing practice (ADR 0013, 0026) for this class of decision.
- **Webhook/refresh URL configuration**: the already-overridable env vars
  (`MARVIN_MR_WEBHOOK_URL`, `MARVIN_MR_DENY_WEBHOOK_URL`, `MARVIN_DASHBOARD_REFRESH_URL`,
  `MARVIN_DASHBOARD_REFRESH_PORT`) get pointed at mac-mini's Tailscale hostname (`gils-mac-mini`)
  instead of `localhost` when the GUI runs on macbook-pro; they stay `localhost` when it runs on
  mac-mini itself. Requires a Node-side way to tell which machine the app is currently running on
  (Python side already has `machine_profile.registry_id()`; needs an equivalent, or a simpler
  hostname-based check, on the Electron side).
- **Cross-machine dispatch-status reader** (new module, Node, tested): extends
  `dispatch_status.js`'s existing local-file read with a remote counterpart — SSHes to the other
  known device's `dispatch-state.json` over Tailscale, mirroring `task_dispatch.py`'s already-proven
  `_read_remote_dispatch_state()` pattern (same SSH options, same timeout-bounded behavior).
  Distinguishes three states per machine: idle, busy (with task), unreachable — unreachable must
  never collapse into idle (user story 11).
- **Per-ticket progress-stage module** (new instrumentation, Python, tested): `execute_ticket`
  (or `run_ticket.py` wrapping it) writes a small structured file per in-flight ticket (e.g.
  `~/.claude/ticket-progress/<issue_number>.json`: `{stage, iteration, max_iterations, subsystem,
  updated_at}`) at each real phase transition (claimed → planning → executing iteration N →
  verifying → raised/failed), removed on completion. This is the concrete instrumentation GitHub
  #82 itself flagged as missing ("no running process to poll/subscribe to for real-time state") —
  now buildable since the autonomous trigger (#95, already shipped) exists. Stages come directly
  from `execute_ticket`'s actual loop, not invented.
- **Activity tab** (new UI, not unit-tested per this codebase's existing convention): third
  dashboard tab. One column per known device from `marvin-network.json`'s registry — each shows
  reachability (idle / busy+stage / unreachable) — plus a shared backlog section listing unclaimed
  `ready-for-agent` tickets (plain `gh issue list`, mirrors `mr_review.js`'s existing `listOpenPrs`
  pattern, no new mechanism). The existing single-machine status badge (`DispatchStatusBadge.jsx`,
  built this session) becomes this tab's "self" column rather than being replaced.
- **MR-origin display**: each PR row already knows its ticket number; resolving which *machine*
  produced it needs either (a) stamping the device id into the PR body/branch name at raise time,
  or (b) inferring it from the `claimed:<machine>` label history. Left as an open decision for
  whichever implementation issue picks this up, not resolved here.

## Testing Decisions

- Only test external behavior, not implementation details, matching this session's established
  convention (`mr_seen.js`, `dispatch_status.js`, `merge.js`'s real-git-fixture tests).
- **Cross-machine status reader**: injected `exec` function (same DI pattern as `merge.js`/
  `mr_review.js`), asserting the idle/busy/unreachable three-state contract. Prior art:
  `dashboard/test/dispatch_status.test.js`.
- **Per-ticket progress file**: pure read/write logic tested via tmp files, same pattern as
  `dashboard/test/mr_seen.test.js` / `lib/tests/test_ticket_coordination.py`; a stage-transition
  test using a fake executor, same pattern as `lib/tests/test_sandbox_orchestration.py`'s existing
  `_noop_executor` fixture.
- **Activity tab UI**: no tests — consistent with the rest of this dashboard's components (App.jsx,
  MrReview.jsx, MrDetail.jsx have none either). Confirmed explicitly for this PRD.
- **Primary-host relocation**: not code, no automated tests — verified by observation (mac-mini's
  launchd job actually claims and completes a real ticket end-to-end), same verification style
  already used for #95's live-fire testing.

## Out of Scope

- Fan-out+merge or exo-scheduled dispatch modes (ADR 0013 already deferred these).
- A non-macOS node (e.g. the deferred Kali/Hackintosh third node) — registry/board design shouldn't
  preclude it, but no Linux-specific launchd-equivalent handling is being built now.
- Automatic failover if mac-mini itself goes down (e.g. auto-promoting macbook-pro back to
  primary) — a human re-pointing things by hand is acceptable for now.
- Historical/timeline view of past ticket runs — this is live "what's happening now," not an audit
  log. CONTEXT.md's note that the Activity tab may grow into a "general health-check monitor over
  time" is a future direction, not this pass.
- Device-targeted approve (choosing which machine executes a merge/build action) — separable from
  MR-origin display per #74's own text ("may split on its own PRD"); this PRD covers origin display
  only, not device-targeted routing.

## Further Notes
