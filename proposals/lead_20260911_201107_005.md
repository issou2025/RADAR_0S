<!--StartFragment--><h2 dir="ltr">Summary</h2>

<p dir="ltr">React Native build times (both debug and release, on Android and iOS) are substantially higher than equivalent Flutter and fully native (Kotlin/Swift) builds of comparable complexity. This issue proposes a discussion and roadmap around identifying the core bottlenecks and reducing build times, since this directly impacts developer iteration speed and CI costs.</p>

<h2 dir="ltr">Problem Statement</h2>

<p dir="ltr">For apps of similar size and dependency count, build time comparisons typically look like this:</p>

<div dir="ltr">
Build Type | Clean Build (approx.) | Incremental Build (approx.)

- Native Android (Kotlin) | 1–2 min | 5–15 sec
- Native iOS (Swift) | 1–3 min | 5–20 sec
- Flutter (Android/iOS) | 2–4 min | 10–30 sec
- React Native (Android) | 5–10+ min | 30–90 sec
- React Native (iOS) | 6–12+ min | 30–90 sec

</div>

<p dir="ltr" style=""><em>(Numbers vary by project, but the relative gap is consistently large and reproducible across teams.)</em></p>

<h2 dir="ltr" style="">Suspected Root Causes</h2>

<ol dir="ltr" style="">
<li><strong>Dual build pipeline</strong> — Native compilation (Gradle/Xcode) runs <em>in addition to</em> JS bundling, Metro transforms, and Hermes bytecode compilation, rather than in a unified pipeline.</li>
<li><strong>Autolinking overhead</strong> — Every native module generates and compiles native glue code at build time, even for modules with no native customization needed.</li>
<li><strong>CocoaPods resolution (iOS)</strong> — <code>pod install</code> and per-pod Xcode target compilation scale poorly as dependency count grows, unlike Flutter's more unified plugin registration.</li>
<li><strong>Gradle multi-module structure (Android)</strong> — Each autolinked library builds as a separate Gradle module rather than being precompiled/cached centrally.</li>
<li><strong>Lack of built-in incremental Hermes bytecode caching</strong> compared to Flutter's AOT snapshot caching strategy.</li>
<li><strong>No first-party unified build cache</strong> equivalent to Flutter's engine + AOT caching or native toolchains' incremental compilation state.</li>
</ol>

<h2 dir="ltr" style="">Why Flutter Is Faster (for comparison)</h2>

<ul dir="ltr" style="">
<li>Single, unified build pipeline (Dart AOT compiler + Flutter engine) instead of separate JS/native pipelines.</li>
<li>Plugins register through a single generated registrant file, avoiding heavy per-plugin native module compilation overhead.</li>
<li>Skia/Impeller rendering engine is precompiled and cached, not rebuilt per project.</li>
<li>Hot reload/hot restart operate on a single VM rather than crossing a JS-to-native bridge.</li>
</ul>

<h2 dir="ltr" style="">Ask / Discussion Points</h2>

<ul dir="ltr" style="">
<li>Is there an official benchmark/tracking effort for RN build time vs. previous versions and vs. Flutter/Native?</li>
<li>Can autolinking generate build artifacts incrementally, only rebuilding native glue for changed modules?</li>
<li>Can Hermes bytecode compilation be cached more aggressively across incremental builds (similar to Flutter's snapshot caching)?</li>
<li>Is there a roadmap item for reducing CocoaPods overhead (e.g., via Swift Package Manager migration)?</li>
<li>Would a unified build orchestrator (single command/pipeline coordinating Metro + native compile steps in parallel rather than sequentially) be feasible?</li>
</ul>

<h2 dir="ltr" style="">Additional Context</h2>

<ul dir="ltr" style="">
<li>New Architecture (Fabric/TurboModules) is expected to help incremental builds — is there build-time benchmarking data available comparing Old vs New Architecture?</li>
<li>Would be happy to contribute benchmarking scripts/data across sample apps if that would help prioritize this.</li>
</ul>
