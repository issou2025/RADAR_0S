# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[EPIC] WallMock 2.0 — Phone Case + Wallpaper Product Rendering Engine & Static Storefront Catalog**

*Project description:*
# WallMock 2.0 Implementation Plan

> **For agentic workers:** This is an EPIC. Implement it incrementally, phase by phase, with small reviewable commits/PRs. Do **not** attempt to rewrite the whole repository in one pass. Preserve all existing wallpaper functionality while adding the phone-case product rendering pipeline.

## Goal

Upgrade WallMock from a wallpaper mockup generator into a **product visual rendering engine for coordinated wallpaper + phone-case products**.

The system must support a workflow where we receive a design/artwork from a supplier or internal designer, map that artwork onto multiple supported phone-case templates, generate high-quality pre-rendered product images for exact phone models, optionally pair the matching wallpaper on the phone screen, and export a static/CDN-friendly catalog that the storefront can consume instantly when the customer switches phone models.

The key product requirement is:

> One design in -> many device-specific case visuals + coordinated wallpaper/case bundle visuals out.

The storefront should **not render cases on every customer request**. Rendering happens ahead of time. The storefront should only switch between already-generated assets.

# 1. Architectural decision

## 1.1 Runtime strategy

Use **pre-rendered 2D / 2.5D product assets** for storefront delivery.

Correct architecture:

```
Design source
     |
     +--------------------+
     |                    |
Wallpaper artwork      Case artwork
     |                    |
Screen Renderer       Case Renderer
     |                    |
     +---------+----------+
               |
        Composition Engine
               |
      +--------+---------+----------------+
      |                  |                |
PDP product images   Bundle images   Social creatives
      |                  |                |
      +--------+---------+----------------+
               |
        Catalog Builder
               |
       static asset bundle
               |
    Storefront / CDN / Next.js
```

The storefront must **not** start Blender, Pillow, Flask rendering, WebGL, or any other expensive renderer during normal product browsing.

When a customer changes:

```
iPhone 17 -> iPhone 17e
```

the expected storefront behavior is essentially:

```
/catalog/blue-hydrangea/iphone-17/hard/front.webp
                         ->
/catalog/blue-hydrangea/iphone-17e/hard/front.webp
```

This gives deterministic output, fast CDN delivery, predictable quality, and easy caching.

## 1.2 Blender / 3D policy

Blender is **not part of the storefront runtime**.

3D may be added later as an asset-authoring tool that produces reusable device/case views. For example, a Blender model may eventually export:

- flat rear view
- 20-30 degree angle view
- 45 degree hero view
- close-up camera view

Those renders then become reusable WallMock case templates.

Do not block the MVP on Blender.

## 1.3 Input strategy

Support two conceptual input paths, but prioritize only the first one initially.

### Primary path — source artwork available

Examples:

- PNG
- JPG
- seamless pattern
- print-ready artwork
- internally generated case design

This is the production MVP path.

### Secondary path — only supplier product photo available

Possible future pipeline:

```
supplier product photo
  -> case segmentation
  -> perspective rectification
  -> camera-hole masking
  -> approximate texture extraction
  -> manual review/correction
  -> reusable source artwork
```

This is inherently less reliable. Do **not** make it a Phase-1 dependency.

Build interfaces so it can be added later.

# 3. Core domain model

Create a clean domain model instead of encoding device/case logic directly into rendering functions.

## 3.1 Device

A Device is an exact sellable phone model.

Example canonical IDs:

```
iphone-17e
iphone-17
iphone-17-pro
iphone-17-pro-max
```

The registry must be data-driven. Do not bake model names into Python conditionals.

Suggested shape:

```json
{
  "id": "iphone-17e",
  "brand": "apple",
  "family": "iphone",
  "display_name": "iPhone 17e",
  "aliases": [],
  "active": true
}
```

Only add phone models for which we have verified template assets. The architecture must support expanding across iPhone 15-17 families without code changes.

## 3.2 Case type

A case type is separate from the phone model.

Examples:

```
hard
tough
magsafe
transparent
soft
```

Phase 1 can implement one neutral generic case type first, for example:

```
hard
```

but all schemas and rendering paths must already include `case_type`.

## 3.3 Case template

A case template represents:

```
device x case_type x view
```

Example:

```
iphone-17e x hard x rear
```

A template is reusable across unlimited designs.

## 3.4 Design

A Design is the aesthetic/product design, independent of phone model.

Suggested manifest:

```json
{
  "id": "blue-hydrangea",
  "display_name": "Blue Hydrangea",
  "case_artwork": "designs/blue-hydrangea/case.png",
  "wallpaper_artwork": "designs/blue-hydrangea/wallpaper.png",
  "case_fit_mode": "cover",
  "focal_point": [0.5, 0.5],
  "tags": ["blue", "floral"],
  "active": true
}
```

A design may have:

- case artwork only
- wallpaper only
- both

The system must not assume both are always present.

## 3.5 Inventory / availability

Rendering capability is **not inventory availability**.

Create a catalog/availability layer that can express:

```
design x device x case_type -> available / unavailable
```

Suggested shape:

```json
{
  "variant_id": "blue-hydrangea__iphone-17e__hard",
  "design_id": "blue-hydrangea",
  "device_id": "iphone-17e",
  "case_type": "hard",
  "available": true,
  "supplier_sku": null,
  "supplier_id": null
}
```

Do not publish a variant just because WallMock can render it.

This layer will later be connected to supplier/US-warehouse availability.

# 4. Asset/template format

Introduce a new first-class directory:

```
assets/
  case_templates/
    index.json
    apple/
      iphone-17e/
        hard/
          rear/
            template.json
            base.png
            print_mask.png
            overlay.png
            highlight.png
            shadow.png
          angle/
            ...
```

Do not force every layer to exist.

## 4.1 Layer roles

Recommended semantics:

- `base.png`
  - neutral phone/case body underneath artwork
- `print_mask.png`
  - alpha mask identifying printable/artwork region
- `overlay.png`
  - camera rings, edges, buttons, rim, non-print areas above artwork
- `highlight.png`
  - optional glossy/material lighting layer
- `shadow.png`
  - optional precomputed transparent shadow
- `template.json`
  - dimensions, print placement, transform mode, layer order, material hints

The renderer must tolerate optional layers gracefully.

## 4.2 Template JSON

Create and validate a schema similar to:

```json
{
  "schema_version": 1,
  "id": "iphone-17e__hard__rear",
  "device_id": "iphone-17e",
  "case_type": "hard",
  "view": "rear",
  "canvas": {
    "width": 1600,
    "height": 2000
  },
  "print_region": {
    "mode": "mask",
    "x": 200,
    "y": 150,
    "width": 1200,
    "height": 1700,
    "fit": "cover",
    "mask": "print_mask.png"
  },
  "layers": [
    {"type": "base", "file": "base.png"},
    {"type": "artwork", "blend": "normal"},
    {"type": "highlight", "file": "highlight.png", "opacity": 1.0},
    {"type": "overlay", "file": "overlay.png"},
    {"type": "shadow", "file": "shadow.png"}
  ]
}
```

Phase 1 requires `mode=mask`.

The schema should be designed so Phase 2 can add:

```
mode=quad
```

or another perspective transform without breaking existing templates.

# 5. Rendering pipeline

Create a separate case renderer. Do not overload `core/device_renderer.py`.

Recommended flow:

```
load source design
  -> normalize RGBA / color mode
  -> fit artwork to print region
  -> apply focal point / zoom / offset
  -> transform if required
  -> mask printable area
  -> composite onto base
  -> apply material/highlight
  -> apply overlay/camera geometry
  -> apply shadow
  -> export master RGBA
```

Required fit modes:

- `cover`
- `contain`
- `tile`

For `tile`, support seamless repeated patterns.

Required adjustment parameters:

- zoom
- offset_x
- offset_y
- focal_point_x
- focal_point_y

Use deterministic rendering. Same inputs + same template + same options must generate the same output.

# 12. Phase P5 — Batch pre-render catalog builder

This is a key production feature.

Create `core/catalog_builder.py`.

Input:

- design manifests
- available variants
- case templates
- output profile

Output example:

```
dist/
  catalog/
    blue-hydrangea/
      iphone-17e/
        hard/
          rear-800.webp
          rear-1200.webp
          rear-1600.webp
      iphone-17/
        hard/
          rear-800.webp
          rear-1200.webp
          rear-1600.webp
    catalog.json
```

## Rules

Only generate variants that are both:

1. renderable
2. marked available

If inventory/availability says false, do not publish that variant.

## Incremental build

Avoid re-rendering the entire catalog every time.

Use a deterministic content hash containing at least:

- design source hash
- template hash
- rendering options
- renderer schema/version

If unchanged, skip render.

Write a build report:

```
generated: N
skipped_unchanged: N
skipped_unavailable: N
failed: N
```

Failures for one variant must not silently corrupt the entire catalog.

## Output optimization

Support:

- WebP storefront assets
- PNG lossless master/debug output when requested

Suggested storefront widths:

- 800
- 1200
- 1600

Keep this configurable.

Avoid forcing AVIF in the MVP unless the environment already has a stable encoder.

Acceptance:

- A second identical build performs no unnecessary rendering.
- Changing one design rerenders only affected variants.
- Disabling one availability entry removes it from the published manifest.
- Output paths are deterministic.

Suggested commits:

```

feat: add incremental content-hash rendering
```

# 24. Performance / resource constraints

The render engine should be CPU-friendly and batch-oriented.

Do not require GPU for the main pipeline.

Expected optimization order:

1. avoid unnecessary rerenders with hashing
2. reuse loaded template layers where appropriate
3. resize only when required
4. build responsive outputs from a high-quality master
5. parallelize at catalog-build level only after correctness is stable

Avoid premature multiprocessing complexity.

# 31. First action for the implementation agent

Do **not** begin by building all iPhone templates.

Start with this sequence:

1. run and document the existing tests;
2. inspect the current rendering architecture;
3. implement the domain models/schema;
4. create one legally clean reusable case template;
5. render one sample design;
6. attach the result to this Issue;
7. verify camera/mask/edges visually;
8. only then expand to additional devices.

The immediate success metric is not "number of supported phones."

The immediate success metric is:

> **Can one reusable template produce a commercially acceptable phone-case product image from arbitrary source artwork without manual Photoshop work?**

Once that is true, scaling to more designs and devices becomes a repeatable asset-production problem rather than a new engineering problem each time.
