## In plain terms

`polygres-wizard` already automates one part of setting up Polygres: installing the CLI/SDK and logging you in, so you don't do that by hand. `analyze` is the next automation layer this roadmap builds — it's meant to do the *database and retrieval-config* work a developer would otherwise do manually through the Polygres CLI and docs: looking at your schema, figuring out which tables need graph search (relationships), semantic/vector search, or keyword search, and turning that into real Polygres configuration — plus, eventually, the application code that uses it.

If the wizard writes code that uses the Polygres SDK, your project needs to actually list that SDK as a dependency (like adding a line to `requirements.txt`) — otherwise the generated code works on your machine and silently breaks for a teammate or in CI. This issue is what edits your project's dependency file to add it — intentionally blocked until we've decided exactly how (see R1 below).

## Summary

🔒 **Gated on #30 (R1) — do not start this issue until R1 is resolved.**

The SDK manifest writer: detects the target repo's Python dependency manifest format and adds `polygres-sdk` to it, per whatever answers R1 settles on for hook point, version-pin policy, Poetry/lockfile handling, and approval shape. This closes the gap tracked in `docs/design/sdk-manifest-dependency.md`, where the wizard currently installs `polygres-sdk` into a Python environment but never records it as a dependency of the target repo — meaning generated code that imports it (Stage 8) works on the machine that ran the wizard and breaks for anyone else (a teammate, CI, a fresh clone).
