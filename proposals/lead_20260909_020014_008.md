## Context

Clue's own platform-sync surface is small: **write period days + flow level to Apple Health, one-way, opt-in, forward-only from grant** — nothing else. Only data tracked *after* permission is granted transfers; import from Apple Health into Clue is not possible; Clue's "heavy" and "super heavy" both map to Apple's `heavy`. On Android, Clue support states it cannot export or sync to other apps at all. Everything beyond this exact scope (read/import, fertility types, symptoms, etc. — #217 (HS-6) through #238 (HS-10)) is deliberate surplus over Clue, tracked separately so parity can ship in one small unit. (Source: A3-35)

lunarlog's data model: `lib/data/db/tables.dart:18` defines `FlowLevel { none, spotting, light, medium, heavy }`. `lib/domain/episodes/episodes.dart` already derives period-episode boundaries, i.e. it already knows which day is a cycle start.

Apple's relevant HealthKit types:
- `HKCategoryTypeIdentifier.menstrualFlow` with `HKMetadataKeyMenstrualCycleStart` metadata — **required** on every `menstrualFlow` sample (iOS 9.0+): `true` on the first day of a cycle, `false` otherwise (https://developer.apple.com/documentation/healthkit/hkmetadatakeymenstrualcyclestart). (Source: A3-2)
- iOS 18.0+ **deprecates** `HKCategoryValueMenstrualFlow` in favor of `HKCategoryValueVaginalBleeding` (`unspecified`, `none`, `light`, `medium`, `heavy`) — the raw values are identical, so writing against `HKCategoryValueVaginalBleeding` from day one requires no runtime branch, only the correct Swift symbol. iOS 26 also adds `bleedingDuringPregnancy`/`bleedingAfterPregnancy` (out of scope here). (Source: A3-14)
- `HKCategoryTypeIdentifier.intermenstrualBleeding` is a **separate** category type from `menstrualFlow`, carrying `HKCategoryValueNotApplicable` (no intensity) — this is where lunarlog's `spotting` flow value needs a semantic decision, since `menstrualFlow`/`HKCategoryValueVaginalBleeding` has no "spotting" case. (Source: A3-4)
- Full flow-enum mapping table needed both directions (Source: A3-41):

  | lunarlog `FlowLevel` | HealthKit write target |
  |---|---|
  | `none` | no sample written (or `none` on iOS only) |
  | `spotting` (inside a period episode) | `menstrualFlow`/`HKCategoryValueVaginalBleeding` = `light` |
  | `spotting` (outside a period episode) | `intermenstrualBleeding` (`HKCategoryValueNotApplicable`) |
  | `light` | `light` |
  | `medium` | `medium` |
  | `heavy` | `heavy` |

  On import (read direction, see #217 (HS-6)): `unspecified`/`FLOW_UNKNOWN` must map to something explicit — recommend `light` plus a note, or skip entirely; never guess silently. Document the collapse in Settings copy the way Clue documents its own "heavy"/"super heavy" collapse.

## Proposed change

1. Write one `HKCategorySample` per logged day for `HKCategoryTypeIdentifier.menstrualFlow` (using the `HKCategoryValueVaginalBleeding` raw values per A3-14), sourcing `HKMetadataKeyMenstrualCycleStart` from the episode boundary computed by `lib/domain/episodes/episodes.dart`.
2. Save each sample with `start`/`end` covering the profile's local day, converted via the #180 (HS-12) timezone contract (`observed_at`/`local_date`/`tz`).
3. Implement the spotting decision from A3-4: spotting *inside* a period episode → `menstrualFlow` with `light`; spotting *outside* an episode → `intermenstrualBleeding` (no intensity value). Pin this rule with a test — it is called out as the single most lossy point in the whole mapping.
4. Implement the full flow-enum mapping table above as a pure, unit-tested function in the adapter (`lib/data/health/`), independent of the native write call, so the mapping logic itself has full `flutter test` coverage even though the native call sites are excluded per #173 (HS-4).
5. Gate every write through the #153 (HS-1) guard (profile↔device-owner, owner-not-guardian) before calling into the native HealthKit adapter (#173 (HS-4)).
6. This issue defines "Clue parity" for the whole epic precisely as this one write-only, opt-in, forward-only surface (A3-35) — everything else (read/import #217 (HS-6), fertility #228 (HS-8), symptoms #238 (HS-10), sexual activity #210 (HS-9), interval/menopause #246 (HS-13)) is explicitly out of scope for *this* issue and tracked separately.

## Acceptance criteria

- [ ] A pure mapping function converts `FlowLevel` → `HKCategoryValueVaginalBleeding` raw value per the table above, with `spotting` branching on episode membership.
- [ ] `HKMetadataKeyMenstrualCycleStart` is set `true` on the first day of a cycle (per `episodes.dart`) and `false` otherwise, on every written `menstrualFlow` sample.
- [ ] Spotting outside a period episode is written as `intermenstrualBleeding` (`HKCategoryValueNotApplicable`), never as `menstrualFlow`.
- [ ] Sample `start`/`end` are computed via the #180 (HS-12) local-midnight-to-midnight conversion, not the device's current zone.
- [ ] Every write path calls the #153 (HS-1) guard first and refuses to write if the guard fails.
- [ ] Settings copy documents the flow-collapse behavior (mirroring Clue's own documented "heavy"/"super heavy" → `heavy` collapse) for whichever collapse applies here.
- [ ] Sync is opt-in (off by default), one-way (write only — no read in this issue), and forward-only from the moment permission is granted (no backfill of pre-existing entries, matching Clue's own behavior).
- [ ] Unit tests cover: cycle-start day gets `true` metadata; non-start days get `false`; spotting-in-episode vs spotting-outside-episode branch correctly; `none` produces no written sample (or an explicit `none` sample per the documented decision).
