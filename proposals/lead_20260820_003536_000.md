## Project Understanding

**M3: preview coverage under a sharded parse — first pixels are hostage to file layout**

*Project description:*
Sub-issue of #394. This is the one that moves the **conversion** metric rather than the total-time metric, and the first browser measurements (#541) turned it from a hunch into the main thread of work.

## The business framing, because it changes the priority order

Share acquires users from search ads. A visitor opens their model or leaves — so **first load is the only load that matters commercially**, and within first load, *time until they see their building* matters more than Total. Second-and-later loads are already fast via the GLB artifact, which is why the index-sidecar path (#541's caching half) is explicitly **not** the lever here.

Observed today on a real first load:

- **PSB**: first pixels arrive early in Parse — columns populate — then a long pause, then the rest fills in over ~10 s.
- **Many other models**: nothing at all for a long pause, then the building fills in at once.

Same code, wildly different felt experience. The difference is the **file's layout**.

## Mechanism, already documented in this repo

`store_preview_channel.ts:50`:

> `deferDanglingPlacements` (Share#1744) defers any product whose placement records the prefix does not hold yet, and **Revit writes per-product placements toward the file tail** — so early ticks meet long runs of products that cannot extract.

So it is not "geometry is at the end". It is **placements** at the end. The preview channel works off a growing **prefix** (`FIRST_GENERATION_MIN_RECORDS = 1024`, doubling by `GENERATION_GROWTH_FACTOR`), and a product is only previewable when its whole closure — including the `IfcLocalPlacement` chain — falls inside that prefix. On a Revit-authored file the chain lives near the tail, so every early tick walks products that all defer.

It is not even free to fail: each deferred attempt still pages source through the windowed provider, which is why `TICK_MAX_ATTEMPTS = 32` exists to cap the run.

## Progress — branch `claude/github-issue-394-3i7229` (`42d0e8ef`)

### Step 2 done: the layout statistic exists and is exact

`scripts/layout_report.mjs`, no engine involved. The statistic is the **prefix resolvability curve**: with the first p% of the file scanned, what fraction of records seen so far have all their `#refs` also inside that prefix? Backward-pointing references track the diagonal; deferred placements fall below it, and **the gap is the preview deficit**. It also names the furthest-reaching record types.

Scanning is hand-rolled rather than regex deliberately — a STEP string literal or a `/* */` comment can contain `;` and `#`, so a naive split mis-slices exactly the files with the most interesting content.

### Step 3 done: the controlled experiment works

`--emit-tail-placements` rewrites a file with every placement record moved to the end. STEP is reference-ordered, not position-ordered, so the result is **semantically identical** and only the layout differs — one model, two layouts, one variable.

`data/index.ifc` (ArchiCAD, well-ordered) against its own tail-placement variant:

| | forward refs | peak prefix deficit |
|---|---|---|
| as authored | 6.1 % | 3.9 % |
| placements at tail | **12.9 %** | **12.9 %** |

and `IFCBUILDINGELEMENTPROXY` — the products themselves — enters the top forward-reaching types, which is the mechanism directly.

Verified semantics-preserving: both files load to 7 meshes with **byte-identical placements**.

### Step 1 partly done — and the instrumentation is NOT yet validated

`DanglingPlacementError` tags the throw from `extractPlacementStrict_` so a preview tick catching it can attribute the deferral; `StorePreviewChannel` counts emitted / deferred / deferred-on-placement and reports them from `stop()` (the channel is a local of the open call, so a counter not reported there is one nobody can read).

**It has never been observed to fire.** Every fixture available locally is too small: `index.ifc` has 280 records against a 1024-record first generation, and a 3 360-record replica still parses faster than a tick, so the prefix is always the whole file and nothing can defer. That is precisely the trap `scripts/debug/README.md` warns about — *"a probe that never fires looks exactly like a clean model"* — so it is recorded rather than assumed working.

Validating it needs a model whose parse takes seconds (PSB, or any Revit file). The corpus keeps those in Git LFS, which the sandbox cannot fetch.

**Next action:** run a PSB first load and read the `[preview] emitted N of M attempted; deferred D (P waiting on placements = X%)` line. If X is near 100, the premise holds and steps 4–5 are worth building. If it is not, sharding will not fix those models and this issue needs re-aiming before any pipeline work.

## Remaining plan

**4. Head+tail two-way probe.** Before committing to N-way sharding plus a coverage-shaped preview channel: one scanner from the head, one from the tail. If layout-hostile models start streaming previews, the premise holds.

**5. The redesign**: coverage-set generations (the prefix `[0, k)` model becomes a set of scanned ranges — `deferDanglingPlacements` survives unchanged since it asks "resolvable?" not "before k?"), and shard ordering biased so the regions that unblock previews are scanned first.
