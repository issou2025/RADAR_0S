## Product success — what must be demonstrated

**Product success is not a build, green CI, or a model returning fluent text.** The existing `EXECUTION_CONTRACT.md` and proposed ADR-004 set the governing comparison: personalized humanization must beat a matched generic rewrite on authentic voice/user effort while preserving hard requirements. Before any scored product test, freeze the test set, held-out split, exact model/prompt/profile/retrieval versions, baseline, metric formulas, sample size, analysis, and pass thresholds. Do not invent thresholds after seeing results.

Use these gates:

1. **Fidelity and trust:** no accepted result violates supported hard meaning/fact/constraint/context checks; unsupported or subjective checks remain `unknown`/human-review, never false PASS. No cross-context evidence leakage or unauthorized learning.
2. **Personalization value:** on genuinely user-authored, held-out writing separated by writer and context, compare personalized against generic output. Measure normalized user edit effort, accept-without-edit rate, and blinded human voice-resemblance judgments. AI-detector scores are not a success metric.
3. **Usability:** first-time users can choose Academic/Professional/Everyday, supply/import a draft, understand mode and verification, and review/edit/accept/export without engine IDs or raw constraint syntax. Measure task completion, errors/help needed, and time-on-task; do not claim usability from developer-only tests.
4. **Reliability:** supported flows complete within declared resource/time bounds; failures are actionable; resumable document work preserves valid checkpoints; export/read-back is verified on the actual Windows path.
5. **Honest product claims:** distinguish generic from personalized, verification from voice resemblance, and implemented controls from design proposals. Never promise detector evasion or unsupported rubric automation.

No numeric quality/usability pass thresholds are frozen yet. PR #14 explicitly leaves benchmark thresholds as an owner decision. Define and approve them before V04/product scoring, using a pilot only to estimate variance and feasibility; do not score the final set during threshold selection.
