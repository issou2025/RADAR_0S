## Why

The README explains *what* each rule checks but not *which real, recurring failures* it answers. Developers arrive from a rejection email or an upstream issue thread; a "Problems this solves" section that maps those threads to rules is both the best onboarding and the best discovery path (search engines index issue titles verbatim, e.g. "ITMS-90683", "ITMS-91061"). A short, honest comparison with adjacent tools also answers "why not X?" before it is asked.

## What

1. README section **"Problems this solves"**: a table — upstream issue (linked), status, the store error it produces, the rule that catches it (today, or "planned: #N").
2. README section **"How it compares"**: one row per adjacent tool, stating what it does well and where this tool differs (no build needed, policy-aware, cross-checks rather than generates). Neutral wording; link each tool.
3. Add the ITMS codes and Play policy names to `pubspec.yaml` `description`/topics only where accurate (topics limit: 5).
