# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**compat: enforce Termux-first Android ARM64 Control Plane contract**

*Project description:*
## Goal
Make YasinHub the first-class Termux/Android Control Plane defined by the ecosystem-wide `TERMUX_FIRST_COMPATIBILITY_CONTRACT_V1.md`.

## Current evidence
- YasinHub already runs successfully on the A70 reference environment and serves the PWA/API on Termux.
- Real service lifecycle has been verified: Start, PID creation, Stop, PID disappearance, Start again, and Restart for managed services.
- The PWA control surface sends real POST requests to `/api/control/<service>/<action>` and refreshes authoritative status afterward.
- `pyproject.toml` currently supports Python 3.9+ and has no desktop-only runtime dependency. 

## Gaps to close
- Explicitly document Termux/Android ARM64 + Python 3.14 + Android API 30 as the reference runtime.
- Add environment/bootstrap validation for Python version, Android/Termux, architecture, and required runtime directories.
- Verify native/runtime dependencies on Android rather than relying only on package installation.
- Make the Control Plane service definitions Termux-safe and automation-safe, including non-interactive service commands.
- Verify clean-session startup behavior so closing/reopening Termux does not leave the PWA looking healthy while the Hub API is actually dead.
- Ensure service lifecycle status is based on real process state, not stale/cached state.
- Add an end-to-end Termux smoke test covering Hub API → service lifecycle → PID verification → status refresh.
- Keep PWA offline behavior clearly separated from live Control Plane availability.

## Acceptance criteria
- [ ] Termux/Android ARM64 is documented as a first-class YasinHub target.
- [ ] Python 3.14 and Android API 30 are included in the reference compatibility matrix.
- [ ] A diagnostic command reports runtime/platform/architecture and required paths.
- [ ] A clean Termux session can start YasinHub reproducibly.
- [ ] `/api/health`, `/api/services`, and `/api/status` reflect the live backend.
- [ ] PWA Start/Stop/Restart performs real process lifecycle changes and verifies them.
- [ ] Closing the Hub process makes live API health fail rather than being represented as healthy by cached UI state.
- [ ] Reopening the Hub restores live status and controls.
- [ ] Managed service commands do not require interactive TTY input.
- [ ] CI covers the compatibility-sensitive logic without introducing Linux desktop/systemd assumptions.

## Non-goals
- No PWA visual redesign in this issue.
- No replacement of the existing service manager.
- No rewrite of the execution Control API.
