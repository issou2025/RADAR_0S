# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**The exhaustive self-battery: every family constructor × shape × release, every instrument, in one run**

*Project description:*
`Refs #765` (S-2026-09-04-a, obligation 2). The owner's words were *"you should be able to test every possible item possible and debug and make it right"*, and this is that, as a thing that runs rather than a thing we say.

## Why now, and why it was not possible before

Two prerequisites landed or are landing:

1. **Builds are reproducible** (#168 / PR #793). Until a `.rfa` stopped changing on every run, "build the same thing twice and compare" — the core move of a battery — was not available, and neither was any single-variable comparison. I did not notice this dependency until working on #168.
2. **The bundled genesis bases are tracked**, so a fresh clone with no `samples/` can build and instrument real files. This issue is therefore **fresh-clone safe** and does not need the owner's machine.

Today each constructor is exercised by its own test file at its own depth. Nothing runs the *product* of constructor × shape × release and puts every instrument on each result, which means a failure that only appears at (say) `cable_tray` × `2024` × `place=True` is found by a user, not by us.

## DONE

1. A driver — `tools/self_battery.py` — that enumerates the matrix from what the engine **declares**, never a hand-written list: every `make_family.py` constructor, every archetype in the #591 registry, every `add_generic_part` shape, × every release in `KNOWN_RELEASES` for which a base is present. Adding a constructor or an archetype must add its cases with no edit here (#685: breadth is data, not code).
2. Every instrument on every result, each pass/fail recorded per case: `verify_family_rfa`, `rvt_validate` (0 errors required), `provenance` (all checks, `identity_is_ours` included), `constraint_law.check_file`, `conformance`, and the **determinism** check from #168 — same spec built twice into different directories, sha256 compared.
3. One machine-readable report (`out/self-battery.json`) plus a short text summary: total cases, pass/fail per instrument, and **every failure named with its case tuple** — no aggregate "N passed" without the failing tuples, which is what makes a battery actionable instead of decorative.
4. **Honest refusals are not failures.** `conduit` on 2024 stops at `Missing2024: ArcElemCell has no 2024 twin` (#786) — a named refusal from the port layer, not a crash. The report must have a third state (`refused`, with the message) between pass and fail, or the first run drowns in known-good refusals and nobody reads the second.
5. A `--quick` mode small enough for the CI shard (one release, the archetype set) and a full mode that is not in the shard, since the full product is minutes. Drop-in `tests/ci_shard.d/`.
6. Record in `docs/inbox/self-battery.md`: the matrix size, the first full run's numbers, and every failure it found, each either fixed in a follow-up issue or explained.

## Territory

`tools/self_battery.py` (new), `tests/test_self_battery_<n>.py` + shard drop-in, `docs/inbox/self-battery.md`. Read-only on `src/` — **anything this finds is filed as its own issue and fixed in its own PR**, because a battery that also changes the engine is a battery whose results nobody can trust.

## Evidence

The first full run's report, with the failure tuples listed rather than summarised. Per hard rule 4, none of it is a certification claim: every instrument here is ours, and "0 errors" is a fact about our bytes, never evidence that Revit opens them.
