# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**refactor(ci): share GitHub REST client across release automation**

*Project description:*
### Problem

The release-automation scripts currently use two different GitHub integration mechanisms:

- `scripts/merge_gate.py` contains a standard-library REST client (`RestGitHubApi`) for PR, commit, check-run and Actions evidence queries.
- `scripts/promote_devel.py` and `scripts/sync_main_to_devel.py` invoke `gh pr list`, `gh pr view` and `gh pr create` through `subprocess`, then parse CLI-specific JSON.

This duplicates authentication, PR identity handling, response validation, and error-handling responsibilities. The new REST client introduced by #396 makes it possible to consolidate those boundaries and reduce dependence on the GitHub CLI in repository-owned Python automation.

Repeated native Git execution code also has inconsistent timeout and error-handling policies across release automation and HIL tooling. A secondary maintenance objective is to share that narrow execution boundary while retaining real Git semantics.

This is a **behavior-preserving CI/CD and repository-tooling refactor**, not a new integration feature, a confirmed bug, or a release blocker. Related: #211, #396 and the Python automation policy introduced by #397.

### Proposed behavior

Implement this in a separate PR targeting `devel`, **after #396 is merged**, using the actual merged implementation as the baseline. Do not expand #396 or couple this refactor to the release schedule.

#### 1. Shared REST boundary

- Extract the existing REST transport and GitHub operations from `scripts/merge_gate.py` into a small, cohesive module such as `scripts/github_api.py`. Reuse existing code rather than writing a second REST client. Keep workflow-specific policy in its existing modules.
- Use Python's standard library and the existing token/environment contracts (explicitly normalize the current `GITHUB_TOKEN` / `GH_TOKEN` inputs if needed). Do not introduce PyGithub, requests, a new package manager, PAT, additional secrets, or new permissions.
- Centralize repository scoping, authorization headers, JSON encoding/decoding, pagination, request timeouts, and actionable error handling. Validate response shapes at the boundary; distinguish an absent PR from an API failure. Do not log credentials, silently suppress errors, or retry ambiguous writes blindly.
- Keep the Merge gate read-only in both its permissions and its exposed API contract. PR creation is only used by the authorized promotion/sync entry points. No generic write service or unnecessary abstraction.

#### 2. Replace only GitHub CLI subprocess calls

| Existing operation | REST replacement |
| --- | --- |
| `gh pr list` | `GET /repos/{owner}/{repo}/pulls`, with open-state/base/head filtering and pagination |
| `gh pr view` | `GET /repos/{owner}/{repo}/pulls/{number}` |
| `gh pr create` | `POST /repos/{owner}/{repo}/pulls`, including explicit base/head/title/body/draft as appropriate |

Use the actual REST response contract, not CLI field names translated mechanically. In particular, validate `base.ref`, `head.ref`, both repository identities, `base.sha`, `head.sha`, `draft`, `html_url`, and applicable mergeability fields. Handle temporarily unknown mergeability as an incomplete observation, not proof of a clean merge. Preserve handling of conflicts and concurrent creation. After an ambiguous create failure, reconcile by looking for the exact intended open same-repository PR before deciding whether another write is appropriate.

Retain the current command-line entry points, output keys, PR titles/templates, workflow triggers, concurrency, and token permissions. Update workflow wiring or repository validation only where necessary for the shared client. Do not change the behavior of bot-created PR events or introduce a new authentication mechanism to make CI trigger; deployment/live validation remains governed by #211.

#### 3. Keep native Git operations

**Architectural decision: invoking the native Git executable through Python's standard-library `subprocess` is the preferred and supported approach for this repository.** The presence of `subprocess` is not a defect or a reason to refactor by itself. Git provides documented plumbing commands and machine-readable output formats for programmatic use ([Git command reference](https://git-scm.com/docs/git#_low_level_commands_plumbing), [git status porcelain format](https://git-scm.com/docs/git-status#_porcelain_format_version_1)).

Retain native Git for fetch, ancestry, exact tree comparison, commit history, diffs, local immutable object access, and existing metadata preflight. This preserves the installed Git implementation's semantics, configuration and credential handling, including real local repositories and worktrees. These operations are infrequent; there is no demonstrated performance or portability requirement that justifies replacing Git with a library. Keep the temporary real-Git tests.

Do not introduce GitPython, pygit2/libgit2, Dulwich or another Git dependency merely to eliminate subprocess calls. GitPython still relies on the Git executable for many operations; alternative Git implementations or bindings would introduce dependencies and require additional compatibility validation. Do not replace native Git history traversal with GitHub REST comparisons. GitHub API operations and native Git operations are separate concerns: use REST for remote GitHub PR/API operations, and native Git for repository operations. The purpose of section 5 is to make existing Git subprocess usage safer and more consistent, not to reduce its call count.

#### 4. Preserve observable behavior and safety invariants

- Promotion still prepares/reuses a draft same-repository devel-to-main PR and enforces the existing ancestry, protected-file, version and metadata policy.
- Return sync still prepares/reuses one reviewed same-repository main-to-devel PR; no PR is created when main is already included in devel.
- Ref movement, conflicts, identical trees with divergent ancestry, duplicate/concurrent creation and ambiguous API results retain safe outcomes and useful diagnostics. Do not merge, approve, update a PR branch, force-push, mutate permanent branch refs, publish a release or edit release-managed files.
- The Merge gate continues to validate the exact tested PR revision, workflow/job identity and latest attempt, including the regressions delivered by #396. Extraction of the client must not weaken its evidence, polling, timeout, title, fork or optional HIL policies.
- Keep existing local and hosted validation contracts; no BLE/HA runtime, protocol, HIL qualification, release metadata, branch-protection or deployment policy changes.

#### 5. Secondary objective — shared native Git subprocess boundary

Consolidate repeated native Git execution boilerplate into a small standard-library module such as `scripts/git.py`, implemented directly with `subprocess.run` (argument list, `shell=False`). The helper should preserve Git's semantics rather than emulate its behavior. Use documented plumbing commands and machine-readable formats such as `--porcelain` and `-z` where appropriate, rather than parsing human-oriented output. This complements the shared GitHub REST client; it is not a replacement for native Git, a universal subprocess framework, or a new Git domain model.

Inventory at the reviewed devel baseline `a489487` and PR #396 head `acb748e` (recheck after rebasing):

| Caller | Git operations |
| --- | --- |
| `scripts/promote_devel.py` | fetch, ls-remote, cat-file, merge-base, rev-parse, log, diff |
| `scripts/sync_main_to_devel.py` | fetch, rev-parse, merge-base, log |
| `scripts/promotion_metadata.py` | show, diff |
| `scripts/hil/cli.py` | branch, status, rev-parse |
| `scripts/hil/environment.py` | rev-parse, ls-files, status |
| `scripts/validate_ha_candidate.py` | status |

- Provide a focused typed execution helper with an explicit working directory or repository path, argument-list invocation without a shell, captured output, finite timeout, and a consistent way to report missing executables, nonzero exit, timeout, and decoding errors. Keep Git argument construction and domain-specific decisions in the callers. Do not create a generic command dispatcher.
- Preserve raw bytes and NUL-delimited output where callers require them, including filenames containing whitespace or non-ASCII characters. Do not strip or split output indiscriminately. Use explicit decoding only where appropriate. Keep the distinction between `merge-base --is-ancestor` returning 0 (ancestor), 1 (not ancestor), and other exit codes (execution failure).
- Preserve the existing short HIL deadlines (2–3 seconds) and fail-closed behavior: unavailable checkout identity remains unknown; a checkout that cannot be inspected is not treated as clean or safe. Set explicit, documented and suitably longer bounded timeouts for network Git operations such as fetch and ls-remote; do not impose the HIL timeout on them. Preserve the current working-directory, credential, and remote semantics. Do not introduce automatic retries that could conceal errors or change side effects.
- Reuse this boundary in the listed scripts only where there is a genuine common execution need. Keep HIL standalone installation and invocation working without Home Assistant, test-only packages or third-party Git bindings. Retain the optional local `gh auth status` diagnostic and the intentionally isolated pytest subprocess in `scripts/hil/transaction_safety.py`; neither belongs in the Git helper.
- Keep real temporary Git repository tests, including worktree/dirty-checkout scenarios. Share test fixture helpers only when this genuinely removes duplication; do not mock away actual Git semantics. Do not touch `custom_components/`, physical qualification logic, or unrelated test organization.
- Implement and validate the REST migration first, then the Git helper as a separate cohesive commit or reviewable change under this same issue. If the secondary scope proves substantially larger than expected, report the concrete obstacle before expanding it.

#### 6. Small CI scheduling improvement — run Merge gate behavior tests in parallel

Move the standalone `Merge gate behavior tests` step (`pytest tests/test_merge_gate.py`) in `.github/workflows/ci.yml` into the existing parallel validation phase of the `quality` job, after dependency setup, pre-commit (which may modify files), and the initial repository validation. Recheck the actual merged #396 baseline before editing.

- At PR #396 head `55edb498`, the existing parallel group already contains ten steps, the documented limit recorded in the workflow. Do not add an eleventh. If the group remains full, combine the short, read-only Ruff format and lint checks into one parallel branch, running both commands sequentially within that branch, to free a slot for the dedicated Merge gate tests. Preserve failure propagation and useful diagnostics for both checks.
- Give the focused pytest invocation its own temporary directory and cache directory (for example, `--basetemp=.pytest-tmp-merge-gate -o cache_dir=.pytest_cache-merge-gate`) and set `USE_REAL_HOMEASSISTANT: "0"` consistently with the unit suite. Check for shared mutable files, coverage outputs and cleanup races; update existing cleanup rules if needed.
- Keep the focused gate suite and the full unit/coverage suite intact. Do not remove tests, weaken validation, add a required job, alter the existing required check name or change the Merge gate evidence contract. The parallel phase must finish successfully before the subsequent repository checks, cleanup, and release archive steps.
- Verify the workflow structure and hosted execution at the final head, including failure propagation. Report observed CI wall-clock timing if available; do not promise a speedup without measurements.

### Alternatives considered

- Retain `gh`: technically valid and acceptable until this maintenance work is scheduled, but retains two integration mechanisms and CLI-specific response parsing.
- Use a third-party GitHub client: unnecessary for the small existing API surface and would increase dependencies.
- Introduce GitPython, pygit2 or Dulwich instead of invoking native Git: rejected for this scope. Native Git already satisfies the requirements; replacing it would add dependencies and compatibility work without a demonstrated benefit.
- Replace native Git operations with GitHub REST comparisons: outside scope; it would reduce the value of local Git tests and can introduce pagination/comparison limitations.
- Fold the change into #396: rejected to keep the already-reviewed functional change separate from a behavior-preserving refactor.
