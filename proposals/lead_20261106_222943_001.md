# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Run several Revit sessions attached to different pyRevit clones at the same time**

*Project description:*
## Is your feature request related to a problem? Please describe

Only one pyRevit clone can be attached to a given Revit year at a time. `pyrevit attach` writes a single `pyRevit.addin` per year under `%APPDATA%\Autodesk\Revit\Addins\<year>\`, and that file names one clone and one engine. A second Revit of the same year loads whatever that file says.

Developers or agents working in parallel (PR reviews, bisecting, a feature branch next to `develop`) can't use live Revit without changing each other's attachment. Seen in practice: four review and PR sessions on one machine with Revit 2024 and 2026 installed. Revit 2026 ran with its manifest pointing at one review worktree, 2024 was claimed by another session, and a third session with a built worktree had to stop. Rewriting a manifest while another session may restart Revit (for example for an IronPython 3 pass) silently loads the wrong code in that session.

Where the single slot comes from (read from the code, not measured in Revit):

| Shared state | Where | Effect |
|---|---|---|
| Manifest per year | `RevitAddons.GetRevitAddonsFolder` / `CreateManifestFile` | One clone and engine per Revit year per user |
| `pyrevit attach <clone> <engine> --installed` | CLI | Rewrites every installed year, including one another session is using |
| One fixed add-in id | `PyRevitConsts.AddinId` | Two pyRevit manifests for one year can't coexist; which one Revit loads is unknown |
| User data | `PyRevitLabsConsts.PyRevitPath` (`%APPDATA%\pyRevit`) | `pyRevit_config.ini`, `agent\instances`, `agent\runs`, `agent\captures` and logs are shared. `PYREVIT_PATH_OVERRIDE` exists but nothing sets it per launch |
| Agent instance records | `AgentInstance` in `PyRevitAgentClient.cs` | Only `pid`, `revit_version`, `revit_build`, `started`. A client can't tell which clone or engine a Revit runs, and `ambiguous_revit` only offers year or pid |

Worktrees themselves are already isolated: each has its own `bin\` and build.

## Describe the solution you'd like

Start Revit with a per-launch manifest so the shared `Addins\<year>\pyRevit.addin` is not touched.

`pyrevit launch <clone> <engine> <year> [model]`:

- Writes the manifest to a per-launch directory (for example `%TEMP%\pyrevit\launch\<guid>\`).
- Optionally sets `PYREVIT_PATH_OVERRIDE` for the child process (`--isolated`), so config, instance records, runs and captures are per session.
- Prints the Revit pid and the clone, engine and root it runs.
- Cleans up the launch directory when Revit exits.

The repo already does this for `pyrevit run`: `PyRevitRunnerExecEnv` writes `PyRevitRunner.addin` to a temporary working directory via `CreateManifestFile(..., addinPath: WorkingDirectory)` (with its own add-in id) and starts Revit with a journal file in that directory. The mechanism could be reused.

Also add `clone` name, clone `path`, `engine` (and version), `branch` or commit and `config_root` to the agent instance record and `list_revit_instances`, and let the `revit` selector match a clone name. With two Revit 2026 sessions, "pass the year" can't choose between them.

Acceptance criteria:

1. Two Revit 2026 processes run at once, one on clone X with IronPython 2.7.12 and one on clone Y with IronPython 3.4.2, and each reports its own clone and engine in `get_context` / `list_revit_instances`.
2. Launching a session never changes `%APPDATA%\Autodesk\Revit\Addins\<year>\pyRevit.addin`, or restores it before returning.
3. Closing one session leaves the other running and unaffected, including its attachment on its next restart.
4. `--isolated` sessions don't share `pyRevit_config.ini`, `agent\instances`, `agent\runs` or `agent\captures`.
5. Documented in `docs/dev-guide.md` and `docs/agent-runtime.md`, including the "Testing agent skills and library changes through MCP" steps and the `ambiguous_revit` guidance.

## Describe alternatives you've considered

- **Locked, short-lived attach.** If Revit only reads manifests during startup, `launch` could take a machine-wide mutex, attach, start Revit, wait until the agent instance record or loader signals readiness, restore the previous manifest and release the mutex. Concurrent launches take turns and running sessions keep what they loaded. This is the fallback if per-launch manifests don't work, and it needs the same "startup only" assumption below.
- **A shim loader that picks the clone from an environment variable.** It would need a stable assembly outside any clone and loading another clone's loader into the same process. That is a larger change than the options above for the same result, so it is not proposed.

## Additional context

Not checked yet. Each is a quick experiment:

1. Does Revit read `.addin` files only at startup? Attach, start Revit, rewrite the manifest, and check that the running session keeps its code.
2. Does a manifest beside a journal replace or add to the standard-folder manifest? If it adds to it, a second pyRevit loads next to the first (see the add-in id point above), and these launches would need a different add-in id.
3. What does Revit do with two manifests that use the same add-in id in one year?
4. Does Revit offer a documented way to add an add-in search folder (command line, `Revit.ini` or registry)? None is used in this repo today.
5. Revit 2027+ moved all-users manifests (`Program Files\Autodesk\Revit\Addins\<year>`). Check that per-launch manifests behave the same there.
