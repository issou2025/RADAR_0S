## 9. P0 findings

### P0-01: OCPI TIME prices are overstated when billing steps differ from an hour

**Evidence:** `api.py:_unique_time_price` computes `gross_price * 60 / step_size`. OCPI defines `TIME.price` per hour, while `step_size` expresses a billing block in seconds, not the unit of that rate. `tests/test_api.py:test_tariff_prices_remain_decimal` currently expects the wrong result for a 60-second block.

An offline call to the real `_parse_tariff` with `TIME.price=3.00 EUR/hour`, VAT `21`, and `step_size=60` returns **3.6300 EUR/minute**; correct is **0.0605**. With `step_size=3600` it returns 0.0605. Billing granularity must not change the normalized rate. The result reaches sensor tariff attributes through `_tariff_attributes` / `_tariff_record_attributes`.

**Change:** normalize the gross hourly rate to a per-minute rate independently of block size; continue validating billing-step metadata, retaining Decimal precision and unknown/VAT/zero/currency safety. No billing/session calculator is requested.

**Tests:** multiple positive block sizes (60/300/3600), nonzero/zero price, explicit tax-included versus added VAT, missing VAT under the existing conservative policy, invalid steps, conflicting components, and the exposed sensor attribute. Correct the wrong expectation, not merely add coverage around it.

### P0-02: Connector-group sensors publish setup-time values after successful refreshes

**Evidence:** `sensor.py:ConnectorGroupSensor` captures frozen `self._connector`; both `native_value` and attributes use that object instead of the latest station connector. An offline update changing the current same-ID connector from total/available **2/1 to 4/0** still reads **2/1**. `entity.py:setup_dynamic_station_entities` only creates groups when a station first appears; new groups on an existing station are not reconciled.

**Change:** resolve live group values by existing stable connector ID; reconcile added/disappearing groups for existing stations without stale current-looking values. Reuse coordinator data only, preserve compatible IDs and the disabled-by-default policy, and make missing-group behavior explicit without deleting customizations casually.

**Tests:** same-ID count/availability updates, newly added group, temporarily missing/returning group, no extra provider calls, enabled/disabled registry state and custom names, stable IDs, unload/removal cleanup.

### P0-03: Location reconfiguration changes entry-level entity identity

**Evidence:** `config_flow.py:_async_save_reconfigured_location` replaces `ConfigEntry.unique_id` with a new location/radius hash. Best Nearby, Top Nearby, selectors, and nearby aggregate sensors derive their IDs from that mutable hash in `sensor.py`. Offline construction with the **same `entry_id`** but reconfigured `unique_id` creates different aggregate keys. `test_loaded_reconfigure_reloads_entry_once` checks reload count, not entity registry continuity.

**Change:** decouple persistent aggregate identity from the mutable duplicate-search key. Use immutable entry identity with compatible in-place registry migration/reconciliation, preserving public entity IDs, names, device links, automations, and favorites. Keep duplicate-search prevention. Do not delete/recreate entities or blanket-rename existing IDs. If saved data changes, version and test that migration.

**Tests:** actual loaded Home/Manual/Entity reconfiguration, repeated reconfiguration/reload, existing v1/v2 entries, existing customized entity IDs/names, stable device references and all aggregate families, no orphan/duplicate registry entries, canceled/failed flow leaves identity intact.

### P0-04: Overlapping same-provider searches collide; cleanup is not entry-owned

**Evidence:** `CurbChargeStationEntity` builds regular IDs as `{provider}_{station_id}_{key}`, without entry scope. Two different coordinators containing the same provider/station produce identical IDs. HA's entity platform ignores a duplicate registered unique ID. The existing same-country test uses **different stations**, so does not exercise overlap. `entity.py:remove_stations` also removes all same-platform registry entries for a device without filtering `config_entry_id`, risking another entry's entity/favorite rows when the physical device is shared.

**Change:** implement compatible identity/ownership for overlapping entry-scoped data and safe registry/device detach/cleanup. Physical station/device identifiers may remain provider-scoped, but one entry must not suppress or remove another entry's data. Preserve existing installations through in-place migration/registry compatibility, not a global rename. Avoid a speculative global runtime manager.

**Tests:** same station returned to two entries with different distances/options/favorites; both load in either order; independent update/failure/unload/reload; one expires the station while the other retains it; surviving custom names/devices/entities unchanged; unload/re-add and legacy registry compatibility. Run across supported HA registry APIs.

**Verification limit:** unique-ID collision and cleanup scope are confirmed from real classes/source. A new full overlapping-registry HA scenario could not run locally because pytest is blocked; add it to Linux CI before implementing the fix.

### P0-05: Administrators can bypass required main-branch validation

**Evidence:** live branch protection has `test`, `hassfest`, `hacs`, and `strict=true`, but `enforce_admins=false`; no repository ruleset supplies equivalent enforcement. This program explicitly treats bypassable required validation as P0. There is no claim that the currently green main bypassed a failing check.

**Change:** enforce status checks for maintainers/admins via branch protection or an active checks-only ruleset without blanket bypass. Address the single-maintainer review-policy tradeoff explicitly: enforcing an unfulfillable self-review requirement is not a usable solution, but review logistics must not bypass automated validation. Do not invent a new approver or weaken required contexts.

**Validation:** read back effective protection/rulesets and verify a maintainer cannot normally merge/push an unvalidated change under the intended policy. Do not test by pushing a bad commit to main. Repository administrators can always edit settings; protect ordinary contribution/release paths, not claim protection against the repository owner changing policy.
