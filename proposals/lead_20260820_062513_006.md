# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Packing only protects a build that went through good build**

*Project description:*
Asset packing exists so a release does not carry legible copies of its assets. Today that guarantee depends on **which command the developer typed**, and nothing says so.

## What ships

`flutter: assets:` lists `assets/` and `assets/packed/` (`generate/scaffold.dart:97-99`), so Flutter bundles the files in both.

`good build` calls `_stripLoose` (`commands/build/build_sub_command.dart:278`) immediately before handing off to Flutter, and it removes **only the compaction outputs named by the plan**. `assets/strip.dart`'s own doc says why it cannot do more:

> *Anything else there is an original: a file placed by hand… Emptying the directory instead would destroy work that cannot be rebuilt.*

| what | ships loose? |
|---|---|
| compaction output (`assets_src/` → webp) | stripped **by `good build` only** |
| hand-placed files in `assets/` | **never stripped** — loose *and* in a chunk (#107) |
| `.good_compact.json` | **ships** — filenames + SHA-256 of every original, plaintext (#107) |

## The gap

**`_stripLoose` is a step inside `good build`.** Run `flutter build windows` directly — or `flutter run`, which the scaffold's own next-steps message tells the user to run — and nothing is stripped. Every compacted asset ships loose and unencrypted, beside the encrypted chunks holding the same bytes.

Nothing warns. Nothing detects it afterwards. A team that wires CI with `flutter build`, which is the obvious thing to do, has an unencrypted release and no signal that packing did nothing.

So packing is not a property of the project. It is a property of the command, and the other command is the one Flutter documents.

## Second cost

`stripLoose` **deletes files out of the developer's own asset directory as a side effect of building**. That is deliberate and reasoned, but it is why *"assets vanished from assets/"* needed a troubleshooting entry (`docs/exporting/troubleshooting.md:86-95`).

## Why patching this is the wrong fix

The obvious repairs — warn when `flutter build` was used, strip harder, filter the journal — all defend a design that puts plaintext in a declared directory and then tries to remove it in time.

**#108's layout removes the class.** With `assets/` as the user's source tree and never declared, and `generated_assets/` containing only `chunk_*.dat`:

- there is nothing unencrypted in a declared directory, so `stripLoose` deletes entirely;
- no build command can ship plaintext, because plaintext is never bundled;
- hand-placed originals cannot double-ship;
- and nothing is deleted from the developer's directory at build time.

The guarantee stops depending on a step that one command performs.

## Until then

If the layout is months away, the cheap interim is for `good build` to record that it packed, and for the runtime or a check to notice a release bundle that carries both a chunk and a loose copy of the same logical asset. That converts a silent unencrypted release into a detectable one. It is worth doing **only** if #108 is not near — it is throwaway work that the layout deletes.

**Done when** a release cannot ship a legible copy of a packed asset, regardless of which build command produced it.
