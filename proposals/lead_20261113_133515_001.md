# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Level-1 learning: evidence-driven skill evolution with verification and rollback**

*Project description:*
## Goal

Introduce **`level-1/learning`**, a cross-cutting, evidence-driven method for deepening existing agent skills through actual use: **apply → observe → generalize → refine → verify → correct / rollback / accept**. The skill must help produce better methods, diagnostic branches, examples, boundary conditions, and reusable tools—not an ever-growing list of generic rules.

Level-1 activation means **continuous awareness of learning opportunities**, not mandatory analysis, file creation, or mutation after every task. A concrete learning cycle starts only when significant new evidence or a demonstrated gap warrants it, and proceeds within the current task's permissions.

## Result boundary

- A navigable, operation-oriented `level-1/learning/` exists and is discoverable through the normal Level-1 contract; the root is short and supporting material is loaded selectively.
- The method distinguishes **execution errors**, **context/access gaps**, **navigation gaps**, **project-specific facts**, and **genuine reusable method gaps** before proposing a change.
- One adequately evidenced exceptional case can justify a candidate; mere recurrence, user silence, model confidence, or textual plausibility cannot establish generality or acceptance.
- Learning can end with **no change**, a **proposed change without write authority**, a **tested candidate**, or a **deferred candidate**. Observations do not automatically rewrite canonical skills.
- A substantive candidate has a stated hypothesis, applicability boundary, protected behavior, planned evidence, and a proportional verification route. Decision outcomes are **correct, rollback, accept, defer**; readiness must not silently become user acceptance.
- Verification tests the **behavior produced by the skill**, not only prose or link validity. Original case, transfer/boundary cases, and relevant regressions are distinguished; actual runtime evidence is never inferred from static inspection.
- Accepted knowledge is integrated at its canonical owner. Transient candidates and evidence live in the existing task surface; do not create an indiscriminate central observation archive or duplicate existing Issue summaries.
- Test with representative positive and negative cases, including a case that must not change a skill; document verified outcomes and limitations. Update relevant Skills inventory, adoption/navigation, and internal links without changing downstream repositories.

## Scope

- Core learning process, evidence/transfer criteria, precise placement of method improvements, verification, correction, rollback, and final consolidation.
- Proposed structure (adjust only where evidence supports a better boundary):

```text
level-1/learning/
├── SKILL.md
├── operations/
│   ├── observe.md
│   ├── generalize.md
│   ├── refine.md
│   ├── verify.md
│   └── consolidate.md
├── references/
│   ├── evidence-and-scope.md
│   ├── placement.md
│   └── evaluation.md
├── templates/
│   ├── improvement.template.md
│   └── scenario.template.md
└── tests/
    └── scenarios.md
```

- **Observe:** capture meaningful user corrections, successful uncommon solutions, failure patterns, and missing branches as compact evidence; skip uneventful successful usage and avoid per-tool-call logging.
- **Generalize:** diagnose the cause and correct scope; identify reproducible method and exclusions. One exceptional validated case may reveal a real gap; frequency alone does not justify promotion.
- **Refine:** prepare the smallest coherent, owned improvement in an operation/reference/example/tool/test rather than defaulting to root `SKILL.md`. Define expected gain, limits, protected behaviors, and check plan **before** modifying it.
- **Verify:** minimal gate (original case + boundary/transfer + affected regressions) and optional expanded version comparison for broad changes. Keep static, mechanical, model-based, and target-runtime evidence distinct. No invented confidence, pass rates, or automated execution claims.
- **Consolidate:** correct and recheck, rollback only the candidate's changes while preserving unrelated work, accept through existing authorized process, or defer with named evidence gaps. Preserve outcome/provenance in existing durable owners.
- Pilot scenarios including a technical skill improvement, a methodological improvement, a no-change finding, a project-local finding, a rollback case, and an unavailable-runtime case.
- Integration into Level-1 navigation and Skills repository knowledge/adoption guidance.

## Out of scope

- Mandatory post-task self-reflection, always-on transcript harvesting, surveillance hooks, background agents, persistent services, an unconditional `instincts` database, or automatic skill mutation/promotion.
- A separate Eval Harness skill or new evaluation platform. Verification is a **selectively loaded part of learning**, proportionate to the candidate.
- Replacing context/workflow/delegation/arbitration, duplicating their authority, imposing a global fixed agent sequence, or changing the user-selected model workflow.
- Editing downstream project repositories, starting live pilots that modify them, installing tools, changing user-wide settings, or sending private content to third parties without separately established authorization.
- Creating new branches, PRs, other Issues, or accepting passes/closing this Issue without the applicable explicit instruction.

## Pass B — Observation, generalization, and refinement

**Status:** planned

### Purpose

Deliver the operational path from a meaningful observed episode to a correctly located, actionable candidate improvement.

### Planned decomposition

- B.1 — Implement `observe` and `generalize`: evidence sources, causal diagnosis, transfer limits, and stopping conditions.
- B.2 — Implement `refine` and `placement`: select the canonical owner and resource kind; protect the concise root and existing adaptations.

## Pass C — Verification and consolidation

**Status:** planned

### Purpose

Make evidence-based **refine → verify → correct / rollback / accept / defer** a complete method without introducing a mandatory stand-alone evaluation platform.

### Planned decomposition

- C.1 — Minimal check: original trigger, boundary/transfer, and affected regression behavior; distinguish source/static checks and verified runtime behavior.
- C.2 — Expanded evaluation for material changes: fixed baseline/candidate, comparable scenarios, reproducible checks, independent or human review when justified; avoid meaningless pass@k claims from insufficient trials.
- C.3 — Implement `consolidate`: local correction/retest, candidate-only rollback, acceptance via existing authority, and explicit deferral when evidence or environment is unavailable.

### Initial boundary

May change: `verify`, `consolidate`, `evaluation`, scenario format and bounded test fixtures.

Must not change: Issue acceptance/dispatch rules, model routing, unrelated committed material, or user-wide evaluator/tool configuration.

### Acceptance target

Proven passing, failing, and unverifiable candidates follow distinct outcomes. A known regression blocks acceptance; correction is rechecked; rollback retains unrelated work; a missing Revit/browser/other runtime check remains an explicit limitation.

## Pass D — Pilots, integration, and regression review

**Status:** planned

### Purpose

Prove the workflow on bounded representative work, integrate it in the shared Skills catalog, and ensure it adds useful depth without increasing agent overhead on ordinary tasks.

### Planned decomposition

- D.1 — Run pilots against existing technical and methodological skills using bounded fixtures/authorized scope: genuine method gap, useful positive experience, unsupported generalization, and no-change case.
- D.2 — Test broad-change comparison, boundary counterexample, failed candidate rollback, and unavailable-runtime reporting; record revisions, inputs, observed results, and unresolved gaps.
- D.3 — Update README, context/navigation and adoption guidance; review all changed references and Level-1 interactions. Avoid altering downstream repositories.
- D.4 — Independent final review for unnecessary rule growth, duplicated authority, mandatory background work, inappropriate source promotion and preservation of existing behavior.

### Initial boundary

May change: the new skill and its test fixtures, relevant shared navigation and narrowly scoped existing skill improvements required by an expressly authorized pilot within this Issue.

Must not change: other project repositories, unconnected user files, unrelated Level-0/Level-1 contracts, or existing methods merely to manufacture a successful demonstration.

### Acceptance target

The complete **use → improve → verify → correct/rollback/accept** route is demonstrated with reproducible evidence, at least one justified skill deepening, at least one justified no-change outcome, and a real correction/rollback scenario. The new root loads without requiring the full evaluation system for everyday tasks; all results distinguish tested behavior from inference.
