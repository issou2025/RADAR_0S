# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Generated families carry a user-supplied shared-parameter library (the owner's eVolve set): extract from their own .rfa, apply at build**

*Project description:*
## Why
Steer #865: "pull in the parameters from the eVolve library". This is the study of the owner's private 421-family pack; counts and format facts only, with no eVolve names, GUIDs or values in this public repo.

- **Parameters.** Every parameter in all 421 families is **shared** (`ParamElemExternal`): 6,523 in total. They resolve to **340 distinct shared-parameter GUIDs**, each with exactly one name across the library; only 2 GUIDs carry two datatypes. So the library runs on one master shared-parameter file.
  - 7 parameters appear in ≥ 90% of families (the library's core); the rest are per product line; 104 appear in one family only.
  - Definitions: `ParamDefValue` 119, `ParamDefString` 103, `ParamDefYesNo` 103, `ParamDefInt` 6, `ParamDefMaterialBrowse` 5, `ParamDefURL` 2, and one each of `ParamDefTextBrowseEdit` and `ParamDefNoOfPoles`.
- **The "entity".** Every file carries the add-in's extensible-storage entities: 3,006 `DataStorage` elements across 17 vendor-`EVOLVE` schemas, 6 of them in all 421 files. Each is **one `TCHAR` field holding an XML document**. They decode cleanly with `rvt.estorage` (0 errors on 421 files). They are the add-in's **document settings** (tags, macros, PowerShell, hash utility, integrations, parameter sync), stamped on save and nearly identical across the library (1–6 distinct payloads per schema). They are not per-family definitions, so carrying them is not needed for a family to hold the library's parameters.

## DONE
1. **`tools/shared_params_from_rfa.py` (new, generic, content-free).**
   - Given user-supplied `.rfa` files of any release (read inside `enter_own_release`), it writes a Revit shared-parameter TXT: GUID, name, DATATYPE, group, visibility, description, user-modifiable, hide-when-no-value.
   - It also writes a **parameter profile** JSON: for each source family, which parameters it carries, instance or type, and the palette group.
   - Output goes where the user says, never into the repo. Tests use synthetic families only.
2. **Build-time application.** `make_family` / `route run` take `--shared-params FILE --param-profile PROFILE[:KEY]`. Every profile parameter the family does not already author is **added** as a shared parameter at its GUID, with its group and instance/type. Values stay blank unless known (S-2026-08-11-a).
   - The writer covers every datatype the pack uses. Yes/No, Integer, Material and URL shared definitions are added if missing; a kind the writer cannot author yet is named in `notes` and skipped, never guessed.
3. Validator 0 errors, provenance clean and `doc.roundtrip()` failed 0 on a family carrying a 60-parameter synthetic profile, for 2024, 2025 and 2026.
4. `rvt.estorage.schemas()` accepts an `.rfa` path (today it only accepts `.rvt`).
5. **Owner's run (private):** extract from the pack, apply to each generated kind, record which parameters matched and which were skipped (counts only here), and STAGE a desktop batch. Only a desktop verdict says the family works with the owner's eVolve content (hard rule 4).
