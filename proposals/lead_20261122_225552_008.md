# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: first release pipeline (Windows and Linux) and app rename**

*Project description:*
## Problem Statement

There is no way to publish Agentic Hive. The repository has CI that only builds debug binaries, no tags, no release workflow and no packaging. A plain release build of the Flutter app would not work: the app looks for the backend beside its own executable, the backend cannot be built with `dart compile exe` (the `sqlite3` build hook needs `dart build cli`), and the MCP proxy must sit beside the backend. The desktop app is also still named `frontend` (`frontend.exe`, window title, bundle identifiers), which is not a name users should see.

## Solution

A tag-driven release pipeline for **Windows and Linux** (macOS stays CI-only, ADR 0012). Pushing a tag `vX.Y.Z` on `master` builds, on each OS, the Flutter app and the backend with `dart build cli`, assembles one **Bundle** (the whole backend bundle inside a `backend/` folder next to the app executable), smoke-tests the assembled Bundle, and publishes a GitHub pre-release with a `.zip` (Windows), a `.tar.gz` (Linux) and `SHA256SUMS`. Nothing is published unless both OS builds pass. The app is renamed to `agentic_hive` (executable) and "Agentic Hive" (display name), with identifier `agentic-hive`, on Windows, Linux and macOS.

## User Stories

1. As a user on Windows, I want to download one `.zip` from GitHub Releases, so that I can run Agentic Hive without building it.
2. As a user on Linux, I want to download one `.tar.gz` from GitHub Releases, so that I can run Agentic Hive without building it.
3. As a user, I want the archive to extract into a single `agentic-hive-<version>/` folder, so that files are not scattered into my current folder.
4. As a user, I want the executable to be called `agentic_hive` (`agentic_hive.exe` on Windows), so that the file name matches the product.
5. As a user, I want the window title, file properties and app name to read "Agentic Hive", so that the product looks finished.
6. As a user, I want the app to start the bundled backend by itself on first launch, so that I never run the backend by hand (ADR 0016).
7. As a user, I want the backend to find its bundled SQLite library, so that the database opens without installing anything.
8. As a user, I want harnesses to find the bundled `hive-mcp` proxy next to the backend, so that `report_result` and `ask_human` work (ADR 0015).
9. As a user, I want a `SHA256SUMS` file in every release, so that I can verify my download.
10. As a user, I want the release notes to say the build is unsigned and that Windows SmartScreen may warn me, so that the warning does not surprise me.
11. As a user, I want the release marked as a pre-release while the product is `0.x`, so that I know it can change incompatibly.
12. As a maintainer, I want to push a `vX.Y.Z` tag on `master` and get a release, so that publishing is one action.
13. As a maintainer, I want the workflow to fail when the tag does not match the frontend `pubspec.yaml` version, so that tag and binary never diverge.
14. As a maintainer, I want the three packages (`frontend`, `backend`, `shared`) aligned at `0.1.0`, so that there is one product version.
15. As a maintainer, I want a manual `workflow_dispatch` dry run that builds and uploads artifacts without publishing, so that I can debug the pipeline without burning the `v0.1.0` tag.
16. As a maintainer, I want the publish job to run only if both OS builds pass, so that a release never ships for one OS only.
17. As a maintainer, I want a smoke test on the assembled Bundle, so that a missing SQLite library, a wrong name or a wrong layout fails the release instead of the user.
18. As a maintainer, I want the smoke test to start the bundled backend with a temporary data folder and check `GET /health` over the Unix socket, so that I know the shipped backend actually runs.
19. As a maintainer, I want the smoke test to fail clearly when `server`, `hive_mcp` or the SQLite library is missing, so that I know which file to fix.
20. As a maintainer, I want release notes generated from merged PRs, so that I do not maintain a changelog by hand.
21. As a maintainer, I want an ADR for the release pipeline, so that future contributors know why `dart build cli` and the `backend/` subfolder were chosen.
22. As a maintainer, I want the glossary to define **Release** and **Bundle**, so that code, docs and workflows use the same words.
23. As a maintainer, I want the backend README to describe the real release build, so that it no longer says release builds "will do this later".
24. As a developer, I want the CI to keep building the macOS app after the rename, so that the rename cannot silently break macOS.
25. As a developer, I want the release launcher to resolve the backend from `backend/bin/server(.exe)` next to the app, so that development overrides (`AGENTIC_HIVE_BACKEND_BIN`, debug `dart run`) keep working unchanged.
26. As a developer, I want a clear `NotFoundFailure` when the bundled backend is missing, so that a broken install is diagnosable.

## Implementation Decisions

- **Platforms:** Windows and Linux are released. macOS is only built in CI (not released). No installer, no code signing, no auto-update, no hand-written `CHANGELOG.md` in v0.1.0; these are recorded as pending.
- **Rename (all three OSes):** the executable becomes `agentic_hive` (Windows `BINARY_NAME`, Linux `BINARY_NAME`, macOS `PRODUCT_NAME`). The Dart package name `agentic_hive_frontend` does not change. Display name is "Agentic Hive": window title on Windows and Linux, Windows version-resource strings (product, description, internal and original file name), and `CFBundleDisplayName` on macOS (needed because `PRODUCT_NAME` is the underscore form). The application/bundle identifier becomes `dev.othavioh.agentic-hive` on Linux and macOS (hyphen, because Apple rejects underscores); the macOS RunnerTests identifier and every reference to `frontend.app` (project file, scheme, test host) follow. Identifiers are changed now because they are costly to change after a published release.
- **Bundle layout:** `dart build cli` is run in the backend package; its whole output (`bin/` with `server` and `hive_mcp`, `lib/` with the SQLite library) is copied as-is into a `backend/` folder next to the Flutter executable. The `dart compile exe` path is never used (documented in the backend README).
- **Launcher contract:** the release `BackendLauncher` of each OS resolves `backend/bin/server(.exe)` relative to the app executable instead of a sibling `agentic_hive_backend`. Override environment variables and debug-mode fallback are unchanged. OS differences stay in the existing per-OS implementations (no inline platform branching, ADR 0012). The MCP companion lookup next to the backend binary must still resolve `hive_mcp` from the new layout; verify and adjust the OS naming candidates if needed.
- **Versioning:** one version for the product, aligned at `0.1.0` in the three packages; the frontend `pubspec.yaml` is the source of truth. Tags are `vX.Y.Z`. A release workflow step fails if the tag version differs from it.
- **Flow:** PR `development` -> `master` with green CI, then tag on `master`. Direct pushes are blocked by the ruleset.
- **Release workflow:** triggered by pushing a `v*` tag and by `workflow_dispatch` (dry run: build and upload artifacts, no publish). One build job per OS (`windows-latest`, `ubuntu-latest`) runs: version guard, codegen, backend `dart build cli`, frontend `flutter build ... --release`, Bundle assembly, smoke test, artifact upload. Linux installs the same GTK and build dependencies as the CI. A final publish job needs both builds, creates `SHA256SUMS` and publishes a GitHub **pre-release** with generated notes and a note about the missing signature.
- **Artifacts:** `agentic-hive-<version>-windows-x64.zip`, `agentic-hive-<version>-linux-x64.tar.gz`, `SHA256SUMS`. Each archive has a single root folder `agentic-hive-<version>/` containing the Bundle.
- **Smoke test tool:** a Dart script run by the workflow on both OSes against the assembled Bundle. It checks that `backend/bin/server`, `backend/bin/hive_mcp` and the SQLite library exist, starts the bundled server with a temporary data folder, waits for `server.json`, calls `GET /health` over the socket and stops the process (exit code 0 only on success, readable message otherwise). It does not open the app window.
- **Docs:** a new ADR (next free number after 0022, so `0023`) records the bundle layout, `dart build cli`, versioning and tag flow, and the pending items (signing, installer, auto-update); it cites ADRs 0012, 0015 and 0016 and supersedes none. `GLOSSARY.md` gains **Release** and **Bundle**. The backend README release section is updated and its "CI release builds will do this later" note removed. All in English.
- **Latest versions rule:** before adding or pinning any GitHub Action or tool version in the new workflow, check the current stable version and docs (Context7); existing CI action versions are the reference, not a source of truth.

## Testing Decisions

- A good test checks external behavior only: which executable the launcher resolves for a given layout, and whether the assembled Bundle can start its backend. No test asserts private structure or string contents of workflow files.
- **Seam 1 (existing):** `resolveLaunchTarget` of the `BackendLauncher`, with injected `fileExists`, `resolvedExecutable` and OS. Prior art: the existing backend launcher test in the frontend lifecycle tests. New cases: Windows resolves `backend/bin/server.exe`, Linux resolves `backend/bin/server`, the old sibling `agentic_hive_backend` is no longer used, a missing file returns `NotFoundFailure`, the environment override still wins, debug fallback still works.
- **Seam 2 (new):** the smoke test script against an assembled Bundle, run on Windows and Linux. The script's own pure logic (layout check, failure messages) gets unit tests where it can be tested without spawning a process.
- Not separately automated, on purpose: the native rename (validated by the existing three-OS CI builds, including macOS) and the release workflow (validated by the `workflow_dispatch` dry run before the real tag).
- Work is done only when `dart analyze --fatal-infos`, `dart format --output=none --set-exit-if-changed .` and `dart fix --dry-run` report nothing (ADR 0014).

## Out of Scope

- macOS release artifacts, Windows installer (Inno Setup/MSIX), Linux AppImage/`.deb`.
- Code signing and notarization.
- Auto-update.
- A hand-maintained `CHANGELOG.md`.
- Opening the app window in the smoke test (needs a virtual display on Linux).
- PATH or symlink installation of the backend command described in the backend README (belongs to a future installer).

## Further Notes

- It is not yet verified that one `dart build cli` run produces both `server` and `hive_mcp` (the backend package declares both executables). The implementer must check this first; if only one is produced, the pipeline builds the missing one explicitly and the ADR records it.
- The macOS build keeps running in CI after the rename; a broken rename there blocks the PR.
- The first real release is `v0.1.0`, made only after a successful dry run.
