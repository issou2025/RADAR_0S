### 🐞 Describe the bug

Follow-up to #3334 / PR #3337. The escape-doubling itself is fixed and I can confirm it no longer grows — thank you. This is about the **repair path** shipped alongside it: `heal_bloated_telemetry_fields()` only resets a field when it exceeds `TELEMETRY_FIELD_MAX_LEN = 8192` characters, so configs corrupted by the original bug are left corrupted unless they happened to reach the extreme size from the original report.

`pyrevitlib/pyrevit/versionmgr/upgrade.py`:

```python
TELEMETRY_FIELD_MAX_LEN = 8192
...
if len(raw_value) > TELEMETRY_FIELD_MAX_LEN:
    bloated.append((field_name, len(raw_value)))
```

Because the growth is doubling, a value spends almost its entire life *well under* that threshold — #3334 needed ~22 reload cycles to reach 8 MB. Anyone who upgraded before hitting that many cycles keeps a permanently malformed value, and the heal never fires.

### 🔎 What I actually found

Real values from a machine running `6.5.3.26176+2017` (which includes the #3337 fix), taken from the config as-found:

```ini
[telemetry]
telemetry_file_dir = "\"\\\"\\\"\""
telemetry_server_url = "\"\\\"\\\"/\"/"
apptelemetry_server_url = "\"\\\"\\\"/\"/"
```

| field | length | `> 8192`? | healed? |
|---|---|---|---|
| `telemetry_file_dir` | 14 | no | **no** |
| `telemetry_server_url` | 16 | no | **no** |
| `apptelemetry_server_url` | 16 | no | **no** |

These are all *conceptually empty* values that were never configured — they should be `""`. Instead each is a non-empty garbage string, so the telemetry paths/URLs read back as configured-but-nonsense rather than unset. (Note the URL fields also picked up a stray `/` per cycle, presumably from a trailing-slash normalization on the write path, so they are not purely quote-escapes.)

The doubling has stopped, so these are now frozen in this state indefinitely.

### 💡 Suggested fix

Detect the corruption by **shape** rather than by size. Any of these would catch it:

1. A value that round-trips to a shorter string — i.e. decoding it yields something different from the stored form — is bloated regardless of length.
2. A value matching an escaped-empty pattern (`^"(\\+")*\\*"*$` and friends) is a corrupted empty and should reset to `""`.
3. Simplest and probably sufficient: for these three fields specifically, if the decoded value is not a valid path / not a valid absolute URL and is not empty, reset it to `""` — none of the three has a legitimate value that looks like `"\"\\\"\\\"\""`.

Lowering the threshold alone wouldn't be enough, since a corrupted-empty is only ~14 characters and a legitimate URL can easily be longer than that.

I'd be glad to send a PR if you'd like — happy to follow whichever of the above you prefer.
