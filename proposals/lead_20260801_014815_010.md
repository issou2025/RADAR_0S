# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**ci: open the main -> dev back-merge pull request automatically**

*Project description:*
## Summary

Anything merged directly into `main` — a hotfix, a docs fix, a release bump — leaves `dev` behind until a human remembers to back-merge. Nothing on the GitHub side notices. The drift is silent from the moment it happens until the next release cut trips over it, which can be days later and is diagnosed by whoever happens to be cutting rather than by whoever caused it.

Add a workflow that watches for the divergence and opens the back-merge pull request itself, so the reconciliation is waiting for review instead of waiting to be remembered.

## Why the existing issues do not cover this

Two open issues already address the release path, and this one deliberately does not overlap with either:

- **#528** makes `release-pr` fail when `origin/main` has commits absent from `origin/dev`. That is a gate at the *next release*, so the drift still persists for however long passes before someone cuts one.
- **#532** makes `publish` close the loop for the drift *the release itself creates* (the version bump and the stamped `CHANGELOG` section).

Neither sees a commit that reaches `main` outside the release flow. That is the case here, and it is the more common one: #455 (`rc-main/fix/marketplace-version-lockstep`) and #457 (`docs/beginner-onboarding`) both merged straight into `main` without touching the version, so #528's guard would not have fired and #532's post-`publish` hook would never have run. #530 was the manual cleanup after a release cut, and it is a good picture of the pull request this workflow should be producing on its own.

## Constraints to design against

- **A pull request is mandatory on both branches.** The repository ruleset (`Push Ruleset`, active on `~DEFAULT_BRANCH` and `refs/heads/dev`) requires a pull request with one approving review, and blocks deletion and non-fast-forward pushes. The workflow cannot push to `dev` directly, and it cannot merge its own pull request. That is fine and intended — a human approval is the point. The workflow's job is to make sure the pull request *exists*.
- **A pull request opened with `GITHUB_TOKEN` does not trigger `on: pull_request` workflows.** Left as-is, the back-merge pull request would show zero checks, and CI (`.github/workflows/ci.yml`) is exactly what should be validating the merge result. Resolve this with a GitHub App token or a PAT, or state in the pull request body that checks must be re-run manually. Whichever is chosen, say so explicitly in the workflow comments — a green-looking pull request with no checks is worse than an obviously unchecked one.
- **`Allow GitHub Actions to create and approve pull requests`** must be enabled at the repository or organization level. Confirm before building; if it is off, the workflow needs a token that is not `GITHUB_TOKEN` anyway.
- **`CHANGELOG.md` conflicts are the normal case for release drift**, not the exception: `main` carries the stamped `## [X.Y.Z]` heading while `dev` still has those entries under `## [Unreleased]`. The workflow must handle a conflicting merge as a first-class outcome, not an error path bolted on afterwards.

## Proposed change

One new workflow, `.github/workflows/backmerge.yml`, with two behaviours driven by the same check.

### Triggers

```yaml
on:
  push:
    branches: [main]
  schedule:
    - cron: "0 9 * * *"   # catches drift the push event missed
  workflow_dispatch:
```

The `push` trigger reacts immediately. The schedule is the backstop for anything the push event missed (a workflow failure, a merge that happened while Actions was degraded) and for re-checking a divergence that is still unresolved. `workflow_dispatch` makes it testable without pushing to `main`.

### The check

```bash
git fetch --quiet origin main dev
behind=$(git rev-list --count origin/dev..origin/main)
```

`behind == 0` → nothing to do. Close the tracking issue if one is open, then exit successfully.

### The back-merge attempt

When `behind > 0`, branch off `origin/dev` and merge `origin/main` in. The direction matters: the head branch must contain `dev` plus `main` so the pull request's base can be `dev`. Follow the existing branch convention (`rc-dev/...`, as in #530) and make the name deterministic per `main` head so re-runs are idempotent:

```
rc-dev/chore/back-merge-main-<short-sha-of-origin/main>
```

- **Merge succeeds** → push the branch and open a pull request into `dev`. Title along the lines of `chore: back-merge main into dev (N commit(s))`. The body should list the commits being carried over and name why they are on `main`.
- **Merge conflicts** → abort the merge, push nothing, and fall through to the tracking issue.

If the branch or its pull request already exists for that `main` head, the workflow should leave them alone rather than pushing again — the ruleset forbids non-fast-forward pushes, and rewriting a branch under an open pull request destroys the incremental diff a reviewer is working through.

### The tracking issue

A single issue, found by a stable label (`back-merge` is suggested; it needs creating) rather than by title so the title can carry the live count:

- opened when `behind > 0` and no such issue is open
- updated with a comment when the count changes or a new conflict appears
- closed automatically when `behind` returns to `0`

For the conflict case it should carry copy-pasteable commands and the list of conflicting paths, so resolving it is mechanical:

```bash
git fetch origin main dev
git checkout -b rc-dev/chore/back-merge-main-<sha> origin/dev
git merge origin/main
# resolve, then:
git push -u origin rc-dev/chore/back-merge-main-<sha>
gh pr create --base dev --head rc-dev/chore/back-merge-main-<sha> --title "chore: back-merge main into dev"
```

For a `CHANGELOG.md` conflict specifically, the resolution is stable enough to state once in the issue body: keep `main`'s stamped `## [X.Y.Z]` heading and reopen an empty `## [Unreleased]` above it.

## Explicitly out of scope

- **A `backmerge` subcommand in `scripts/release.py`.** That is #532. This workflow is the net for drift that arrives outside the release flow; #532 removes the recurring source inside it. Both are worth having, and landing only this one means every release still generates a conflicting back-merge pull request that a human resolves by hand.
- **Pushing to `dev` directly, or auto-merging the pull request.** The ruleset forbids the first and requires an approval for the second. Neither should be worked around.
- **Resolving conflicts automatically** (`-X ours`, `-X theirs`, or similar). Both directions silently discard real work. A conflict is a human decision.
- **A local git hook.** The merge happens on GitHub's servers; a client-side hook never sees it and only exists on machines that installed it.

## Done when

- a commit reaching `origin/main` that is absent from `origin/dev` produces, without human action, either a back-merge pull request into `dev` or a tracking issue explaining why one could not be opened
- a clean back-merge opens exactly one pull request, based on `dev`, containing the `main`-only commits
- a conflicting back-merge pushes nothing and opens or updates the tracking issue with the conflicting paths and the commands to resolve them
- re-running the workflow against an unchanged `main` head does not open a second pull request, push over an existing branch, or file a duplicate issue
- the tracking issue closes on its own once `origin/main` and `origin/dev` are back in sync
- the back-merge pull request either carries CI results or says plainly in its body that it does not
- `RELEASE.md` describes the automation and what an operator is expected to do when the tracking issue appears

## Notes for whoever picks this up

- The scheduled run and the push run are the same job with the same logic — resist splitting them.
- Test the conflict path deliberately. The easiest reproduction is a `CHANGELOG.md` edit on both branches touching the `## [Unreleased]` section; that is the shape the real conflicts take.
- If any non-trivial logic lands in Python rather than shell, `.github/workflows/scripts/` is where workflow-owned scripts live (see `lint_skill_refs.py`), and `tests/test_release.py` shows the established pattern for testing git-touching code without shelling out (`_forbid_subprocess`, plus `monkeypatch` on `run`/`capture`).
- The version-shaped guard this complements is at `scripts/release.py:432`, with `_target_ahead_of_main` at `scripts/release.py:326`. The line numbers quoted in #528's body predate later edits; trust the symbol names over the numbers.
