# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Spec: Google Play release (Android)**

*Project description:*
Spec for the first Google Play release of Humspan on Android, step by step from no developer account to a live production listing. It follows PLAN.md Phase 2 ("First Mobile Release ... Ship it") and the brand commitments in `PRODUCT.md`. Terms follow `GLOSSARY.md`.

Most of the steps happen in Play Console and only the **owner** can do them. Those are marked **[owner]**. Steps an agent can do in the repo are marked **[agent]**. Play policy changes often, so check each limit quoted here against Play Console on the day you do the step.

## Problem Statement

Humspan works on the owner's Android phone: lock-screen controls, headphone unplug, call duck and a full `1h 37m` session all pass. But nobody else can install it. The release build is still signed with the debug key. There is no upload key, no Play developer account, no store listing, no privacy policy and no screenshots. Google's policy declarations (Data safety, content rating, target audience, the foreground-service declaration for `mediaPlayback`) have not been filled in. The owner has not submitted an app to Google Play before. They need the whole path in one place, in order, including the steps that take weeks to clear, such as the closed-test requirement for new personal accounts.

## Solution

One ordered walkthrough in eight phases. Each phase ends in a state you can check before starting the next.

### Phase 0: Before spending money [owner]

1. **Confirm the name.** Search Google Play for "Humspan" and for close spellings. Run a USPTO trademark search (Class 9, software) as `PRODUCT.md` asks. If either search turns up a conflict, stop and rename before anything is public. The application id `dev.humspan.app` is permanent once uploaded.
2. **Confirm the application id.** It must stay `dev.humspan.app`. Play never lets an app change its package name. Owning the `humspan.dev` domain isn't required, but it makes the id defensible and gives the privacy policy and support pages a home.
3. **Choose an account type.** A **personal** account is cheaper and faster to verify. New personal accounts must run a closed test with at least 12 opted-in testers for 14 days in a row before they can apply for production (Phase 6), so budget about 3 weeks for that. An **organization** account skips the closed-test rule but needs a D-U-N-S number and a registered business. Recommendation: personal, unless a business entity already exists.
4. **Set up a support address.** Play shows a contact email publicly on the listing. Use a dedicated address, such as a new mailbox or an alias on the domain, not a personal inbox.

### Phase 1: Developer account [owner]

5. Sign up at Play Console with the Google account that will own the app long term. Pay the one-time registration fee (US$25 at the time of writing).
6. Complete identity verification: legal name, address, phone, and government ID for a personal account. Verification can take a few days, and nothing can be published until it clears.
7. Verify the contact email and phone in Play Console.
8. Turn on 2-step verification for the Google account. Losing this account means losing the app.
9. Optional: under Users and permissions, invite a second Google account as admin as a recovery path.

### Phase 2: Release signing in the repo [agent, with owner for the secrets]

10. **[owner]** Generate an **upload key** on the Mac with `keytool`: RSA 2048 or larger, validity of 25+ years, alias `upload`. Store the keystore file outside the repo. Store both passwords in a password manager and keep an offline backup of the keystore. If this key is lost, Google can reset it, but only through a support request.
11. **[owner]** Create the signing properties file next to the Android project. It holds the store path, the store password, the key alias and the key password, and git already ignores it. Never commit the keystore or this file.
12. **[agent]** Change the release build type so it signs with the upload key when the signing properties file is present. When the file is missing, the build must **fail** with a clear message. It must not fall back to the debug key. Debug and profile builds stay on the debug key so `flutter run` keeps working.
13. **[agent]** Set the version. The `version:` line in `pubspec.yaml` is the only source: the part before `+` is the versionName shown to users, and the number after `+` is the versionCode. The first upload is `1.0.0+1`. Every later upload must raise the number after `+`, and Play rejects a versionCode it has already seen, even from a deleted draft.
14. **[agent]** Check the native libraries against Google's **16 KB page-size** requirement (apps targeting Android 15+ must support it). The engine and the player are built with the NDK through CMake, so their shared libraries must use 16 KB ELF alignment. Recent NDKs do this by default. Confirm the NDK version Flutter uses and add the linker flag if needed.
15. **[agent]** Confirm the target SDK meets Play's current minimum target level. The merged manifest has targetSdk 36 and minSdk 24, which is fine for now. Don't change minSdk.
16. **[agent]** Add the **release bundle check** (see Testing Decisions) and a CI job that builds the release AAB and runs it. The CI build signs with a throwaway key it generates itself, so CI never holds the real upload key. The check accepts any non-debug key in CI and is strict locally.
17. **[owner]** Build the bundle: `flutter build appbundle --release` from the app directory. Then run the release bundle check on the result. Install the bundle on the phone with `bundletool` (build-apks with `--connected-device`, then install-apks) and repeat the phone pass: lock screen, headphone unplug, call duck, a short timed session that fades to silence. The release build is the one that ships, so the debug-build pass doesn't count.

### Phase 3: Store assets [agent drafts, owner approves]

18. **App name** (30 characters max): `Humspan: Brown Noise & Binaural` is 31 characters, so it needs trimming. Candidates: `Humspan: Noise & Binaural` (25) or `Humspan – Brown Noise` (21). The name must not use words like "sleep", "best" or "#1", and must make no health claim.
19. **Short description** (80 characters max): plain and factual, no claims. Example direction: "Colored noise, binaural beats and a slow boom, generated live for any length."
20. **Full description** (4,000 characters max): what plays (White/Pink/Brown noise, a 2–10 Hz binaural beat, an alternating boom); that the sound is generated live and never loops; exact lengths up to Until I stop, with a fade over the final minute; lock-screen controls; headphone unplug pauses and never moves sound to the speaker; no account, no ads, no data collected. No sleep, health, brainwave or entrainment wording anywhere, per `PRODUCT.md`.
21. **App icon**: a 512×512 32-bit PNG, rendered from the same artwork as the adaptive launcher icon, with no rounded corners or shadow added (Play applies the mask).
22. **Feature graphic**: 1024×500 PNG or JPEG, using the session screen's dark palette from `DESIGN.md`. Keep text off it or minimal. It must not claim anything.
23. **Phone screenshots**: 2–8 images (aim for 4) from the release build on the phone or the `humspan_phone` emulator, at 9:16 or 16:9, with each side between 320 and 3,840 px. Suggested set: stopped with a length chosen; playing with the clock running; layers mixed with level sliders; the lock-screen media notification. No device frames with fake notifications, and no text overlays making claims.
24. **Tablet screenshots** (optional): the wide layout at 900 px and up. Without them the app still lists on tablets, but ranks lower there.
25. **Category**: Music & Audio. Not Health & Fitness, because that category invites health-claim review and the product makes no claims.
26. **Tags**: up to five from Play's list that describe the sound, such as white noise or ambient.

### Phase 4: Privacy policy [agent drafts, owner hosts]

27. **[agent]** Write a short privacy policy. Humspan collects no personal data, has no account, makes no network requests, stores its last-session settings only on the device, and contains no ads or analytics SDKs. Name the support address from step 4. Have a person confirm these statements against the merged manifest and the dependency list before they are published.
28. **[owner]** Host the policy at a public HTTPS URL that anyone can open without signing in: a web page, not a PDF and not an editable doc. GitHub Pages or the `humspan.dev` domain both work.

### Phase 5: Create the app and complete App content [owner]

29. In Play Console choose **Create app**: name, default language English (United States), type **App**, **Free**. Accept the declarations. Free can never be changed to paid later.
30. Under **App content**, complete every declaration:
    - **Privacy policy**: the URL from step 28.
    - **App access**: all functionality is available without special access.
    - **Ads**: No.
    - **Content rating**: the IARC questionnaire, with category Utility/Productivity/Communication/Other and no violence, sexual content, gambling, user interaction or data sharing. Expect the lowest rating everywhere.
    - **Target audience and content**: 18 and over (or 13+ as well). Don't include under-13 age groups, because that brings in the Families policy and its extra review.
    - **News app**: No.
    - **Data safety**: no data collected, no data shared. Check that this is true for the dependencies (`flutter_media_session`, `shared_preferences`). The `ACCESS_NETWORK_STATE` permission comes from a dependency and doesn't transmit anything, so it doesn't change the answer.
    - **Foreground service permissions**: declare `FOREGROUND_SERVICE_MEDIA_PLAYBACK` as Media playback. Describe the use case ("plays the listener's chosen sound while the screen is locked, with lock-screen controls"). Link a short screen recording, unlisted on YouTube or a public file link, that shows Play, locking the phone, the sound continuing and the notification controls.
    - **Health apps**: declare no health features. Humspan is an ambient-sound player, not a sleep or health tracker.
    - **Government apps, Financial features**: No.
31. Under **Store settings**: category Music & Audio, contact email (step 4), and optionally the website.
32. Under **Main store listing**: paste the assets from Phase 3.

### Phase 6: Testing tracks [owner]

33. **Internal testing** first. Create a release, upload the AAB from step 17, add release notes, and add the owner's own account as a tester. Opt in through the tester link and install from Play. The Play-installed build is signed by Google with the **app signing key**, so test it again: same phone pass as step 17.
34. **Play App Signing**: on the first upload, accept the Google-generated app signing key. The local key from step 10 stays the upload key.
35. Read the **pre-launch report** (Play runs the app on test devices automatically). Fix crashes or accessibility warnings that apply to the session screen, such as touch targets and labels.
36. **Closed testing** (required for a new personal account). Create a closed track, upload the same or a newer build, and add **at least 12 testers** by email list or Google Group. Every tester has to opt in and keep the app installed for **14 days in a row**. Recruit a few more than 12 to cover drop-outs. Collect their feedback.
37. After the 14 days, apply for **production access** from the Dashboard. The questionnaire asks how testers were recruited, what feedback came in, and what changed. Answer honestly and specifically. Review of the application takes up to about a week.

### Phase 7: Production release [owner]

38. **Countries/regions**: start with all of them, or with the English-speaking ones if non-English listings won't be ready.
39. Create the production release from the tested build, or promote it from closed testing. Release name `1.0.0`. Release notes in plain wording: "First release."
40. Choose a **staged rollout** (for example 20%) and send it for review. The first production review can take several days.
41. Once it's approved, install from the public listing on the phone and check the listing text, the icon and the screenshots.
42. Watch **Android vitals** (ANRs, crashes) and reviews for the first week, then move the rollout to 100%.

### Phase 8: Every later update [agent + owner]

43. Raise the versionCode in `pubspec.yaml`, build, run the release bundle check, and upload to internal testing. Do the phone pass, then promote to production. You only need the closed-testing requirement once per account.
44. Keep the Data safety form and the foreground-service declaration in sync whenever a dependency or permission changes. The release bundle check's permission allowlist flags those changes.

## Implementation Decisions

- **The application id stays `dev.humspan.app`.** It is permanent on Play. The namespace already matches.
- **Release signing comes from an untracked properties file** next to the Android project. It names the keystore path, the store password, the key alias and the key password. The Android app's Gradle build reads it only for the release build type.
- **No silent fallback.** A release build without the signing file fails with a message saying what to create. This replaces the template's "sign release with the debug key" placeholder. Debug and profile keep the debug key.
- **The upload key is separate from the app signing key.** The app uses Play App Signing with a Google-generated app signing key. The local keystore is only the upload key, so a lost upload key can be reset through Google support.
- **There is one version source**, the `version:` line in `pubspec.yaml` (`name+code`). The first release is `1.0.0+1`. Nothing else in the Android project hardcodes a version.
- **The AAB is the artifact.** Play takes only Android App Bundles for new apps. The universal APK stays a local testing convenience.
- **16 KB page alignment.** The CMake-built shared libraries of the engine and the player are linked with 16 KB max page size. If Flutter's NDK version doesn't already default to that, it is set explicitly in the native build.
- **Shrinking stays as Flutter configures it.** The existing release minification is kept. If R8 strips anything the media-session plugin needs, add a keep rule. Play takes the mapping and native debug symbols from the bundle.
- **Permission allowlist.** The release manifest may declare exactly: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `POST_NOTIFICATIONS`, `WAKE_LOCK`, `ACCESS_NETWORK_STATE`, and the app's own `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. `INTERNET` is explicitly forbidden. Adding a permission means updating the allowlist, the Data safety form and the privacy policy in the same change. `WAKE_LOCK` comes from a dependency. The app itself holds no wake lock (`PRODUCT.md`), and the listing must not claim otherwise.
- **The release bundle check** is one script that takes a path to an `.aab` and, optionally, the last uploaded versionCode. It uses `bundletool` and the SDK build tools already installed with the Android SDK. It fails on:
  - signed with the Android debug certificate (the CN "Android Debug" subject), only in strict mode;
  - versionCode not greater than the given last versionCode;
  - any declared permission outside the allowlist, or `INTERNET` present;
  - any native `.so` in the bundle with an ELF LOAD segment aligned below 16 KB;
  - targetSdk below a minimum constant kept in the script and raised when Play raises its rule.
  It prints the versionName, the versionCode, the signer and the permissions so the owner can check them before upload.
- **CI** gains one Android job: set up Flutter, generate a throwaway keystore and signing file in the job, build the release AAB, and run the check in non-strict mode (signer must not be the debug key, the other rules apply in full). The existing C++ matrix is unchanged.
- **The store listing text** is kept in the repo as plain text, next to the privacy policy source, so changes to it are reviewed like code and the no-claims rule is enforced in review. The listing assets (icon, feature graphic, screenshots) go next to it.
- **The category is Music & Audio.** The target audience is 18+ (13+ optional). No ads. Free.
- **The Data safety answer is "no data collected or shared."** It is valid only while the allowlist forbids `INTERNET` and no analytics or crash-reporting SDK is added.

## Testing Decisions

- **Good tests here check the shipped artifact, not the Gradle code.** The release bundle check reads the `.aab` that will be uploaded and asserts only things Play or a listener would see: who signed it, its version, its permissions, its target SDK and the alignment of its native code. It doesn't inspect Gradle files or the merged-manifest intermediates.
- **This spec adds one seam, the release bundle check.** It runs on the owner's Mac before every upload (strict) and in CI on every push and pull request (non-strict signer rule).
- **Give the check's own rules a small self-test.** Run it against a deliberately bad bundle (debug-signed, or with an extra permission) and expect a non-zero exit. That test lives in the same CI job.
- **Behaviour is still tested on the device by hand.** The phone pass from the session-screen work (lock-screen controls, headphone unplug, call duck, a timed session ending in silence) is repeated on the signed release build and again on the Play-installed build. No automated device tests are added.
- **Prior art.** The existing CI workflow's build-then-test jobs, and the C++ engine tests' style of one plain executable that fails loudly. The Flutter unit and widget tests in the app are unchanged and keep running.
- **The engine rules stay covered by the existing C++ tests.** Real-time safety and `testRenderDoesNotAllocate` don't change, because nothing in this spec touches the render path.

## Out of Scope

- The iOS App Store submission (a separate spec; it shares the name check and the privacy policy).
- In-app purchases, subscriptions, ads, analytics and crash reporting. Each would change the Data safety answer and need its own spec.
- Automated upload to Play from CI (service accounts, the Play Developer API, fastlane). The owner uploads by hand for now.
- Localised store listings and translated app text.
- Wear OS, Android TV, Android Auto and Chromebook-specific listings.
- Feature changes to the session screen. The release ships the screen as specified in #9 and #14.
- Paid pricing or regional pricing.

## Further Notes

- **Calendar.** Identity verification (days) plus the closed test (14 days of opted-in testers) plus the production-access review (up to about a week) plus the first production review (days) comes to roughly 3–5 weeks of elapsed time from the first step to a live listing, for about a day of hands-on work. Start recruiting closed testers in Phase 1, not Phase 6.
- **Limits drift.** Character limits, the tester count, target-API deadlines and the declarations list are as Google published them at the time of writing. Check each one in Play Console on the day.
- **Wording review.** The no-claims rule in `PRODUCT.md` applies to every Play surface: the name, the descriptions, the screenshots, release notes, the production-access questionnaire and replies to reviews.
- **Name length.** The subtitle form in `PRODUCT.md`, "Humspan: Brown Noise & Binaural", is one character over Play's 30-character app-name limit, so the owner needs to pick the final string in Phase 3.
