## Summary

`compliance-compiler`'s `PostToolUse` validator only fires for plan files that satisfy **both** of two hardcoded conditions. Any repo that uses a different plan layout gets a hook that silently never runs — no error, no log line, just no validation.

I hit this while trying to wire `compliance-compiler` as the plan gate in a [GSD](https://www.npmjs.com/package/get-shit-done-cc)-driven repo. GSD writes plans to `.planning/phases/<phase>/NN-NN-PLAN.md`. Both conditions fail, so out of 14 plan files, zero were ever checked.

This isn't a request to "make a path configurable" in the abstract — it's a concrete integration case. For anyone running GSD, that's *every* repo, and `compliance-compiler` is otherwise the best-fitting piece of the harness for a compliance-heavy project.

## Where it's wired

`engines/compliance-compiler/payload/scripts/config.py:36`

```python
# PRP plan files the validator hook checks (relative to the REPO root, which is
# ROOT_DIR.parent for a top-level catalog dir).
PLANS_SUBPATH = ".claude/PRPs/plans"
```

It's a module-level constant, not part of `DEFAULT_CFG` (`config.py:45-52`), so `<catalog_dir>/config.json` cannot override it. `load_cfg()` merges the file over `DEFAULT_CFG` only.

`engines/compliance-compiler/payload/scripts/precheck.py:19`

```python
def is_plan_path(path_str: str, repo_root: Path | str) -> bool:
    """True iff ``path_str`` is a live PRP plan file (not an archived one)."""
    if not path_str:
        return False
    p = Path(path_str)
    if not p.name.endswith(".plan.md"):        # ← condition 1
        return False
    ...
    plans = tuple(PLANS_SUBPATH.split("/"))
    parts = rel.parts
    if parts[: len(plans)] != plans:           # ← condition 2
        return False
    return "completed" not in parts[len(plans):]
```

Called from `engines/compliance-compiler/payload/hooks/co-post-tooluse.py:74`. When it returns `False`, the hook exits quietly — which is correct behaviour for a `PostToolUse` hook, but it also means a misconfigured layout is indistinguishable from a working one until you go looking.

## Why the obvious workaround is a trap

Editing `PLANS_SUBPATH` in the *installed* engine copy works until the next re-install: ADOPT refreshes the engine files and silently discards the change. So the workaround degrades over time in a way that looks exactly like the original bug.

The remaining escape hatch is calling `/neurawork-cc-harness:co-validate <path>` by hand, which gives up the automation that makes the `PostToolUse` hook worth having.

## Suggested fix

Move both conditions into `DEFAULT_CFG` so `<catalog_dir>/config.json` can override them:

```python
DEFAULT_CFG = {
    ...
    "plans_subpath": ".claude/PRPs/plans",
    "plan_suffix": ".plan.md",
}
```

and have `is_plan_path()` take them from `cfg` instead of importing the module constant. Defaults unchanged, so existing installs are unaffected.

Two details worth deciding explicitly:

- **Multiple roots.** A list (`["\.claude/PRPs/plans", ".planning/phases"]`) would cover repos that run both conventions during a migration. A single string is enough for my case; a list is strictly more useful and not much more code.
- **The `completed` convention.** `is_plan_path` treats a `completed` path segment as "archived". That's a PRP-specific convention and probably deserves its own key (or at least a note in the docs) once the subpath is no longer fixed — otherwise a foreign layout inherits a filtering rule it never opted into.

`engines/compliance-compiler/tests/test_shards_precheck.py:123-136` already covers the current behaviour and would extend naturally to a configured path.

I'm happy to send a PR for this if the shape above sounds right to you — say which variant you'd prefer (single string vs. list) and I'll follow the existing config conventions.
