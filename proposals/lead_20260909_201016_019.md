## 1. `relevance_filter` does not cover `status_phrases_present` — the detector escalates on out-of-scope content

**Severity: this fired in production and re-fired for five consecutive days.**

`extract_signals` scopes three of its four signal fields to the filtered heading set, but computes the fourth over the entire page:

```python
def extract_signals(text: str, headings: list[str], relevance: list[str] | None = None) -> dict:
    lowered = text.lower()
    filtered = apply_relevance_filter(headings, relevance)
    return {
        "headings": filtered,
        "preview_qualified_headings": sorted(h for h in filtered if PREVIEW_QUALIFIER.search(h)),
        "status_phrases_present": sorted(p for p in STATUS_PHRASES if p in lowered),  # <-- whole page
        "heading_count": len(filtered),
        "relevance_filtered": bool(relevance),
    }
```

`apply_relevance_filter` is not the defect — it does what its signature says. The defect is the **mixed-scope fingerprint** assembled here, plus that function's own docstring claim that *"Filtering is applied to the \*watched signal\*"*: `status_phrases_present` is part of the watched signal and is unfiltered.

**Measured on `defender-release-notes` (2026-09-09):** 86 total markdown headings, **2** surviving the AI relevance filter, **84 out of scope**. Every word inside those 84 still drives the fingerprint.

**What it did.** On **2026-09-05** the phrase `retired` entered the signal set from this entry:

> ### Classic Defender for SQL APIs retirement
> The classic Defender for SQL APIs for Vulnerability Assessment and Advanced Threat Protection will be **retired on August 16, 2027**.

SQL, not AI. That section correctly fails the filter — `\bAI\b` does not match "APIs", since the following `P` is a word character and there is no right-hand boundary — so it never reaches `headings`, yet its body moved the fingerprint anyway. The daily `Source watch` re-reported it on 2026-09-05, 06, 07, 08 and 09, each run routing to "Adjudication deferred to a local run". Row 4's two in-scope AI headings were byte-identical to baseline throughout, both still `(Preview)`.

**It contradicts the documented behaviour.** `docs/agent-cadence.md` states:

> The Defender for Cloud release notes carry seventy-five headings for products outside this repository's scope; the `relevance_filter` in `sources.json` reduces that to the AI-related entries, **so the detector does not escalate for Kubernetes and SQL notes that cannot affect any row.**

The consequence clause is false as written. Only the heading-count reduction is accurate.

**Two aggravating properties:**

- **The hole is symmetric.** It fires equally when an out-of-scope phrase *disappears*, so a future escalation may have no visible cause at all.
- **The `[changed]` line carries no scope attribution.** `status phrase appeared: 'retired'` gives a reader no way to tell an in-scope trigger from an out-of-scope one without re-fetching and re-reading the page. That is the cost that matters: a detector which cries wolf trains its maintainer to stop looking.

**Suggested fix.** Compute `status_phrases_present` over the relevance-scoped text rather than the whole page — for `markdown` sources, the concatenation of the sections whose headings survive the filter; for `html`, the equivalent slice. Where scoping is genuinely impossible, emit the phrase signal with the heading it was found under so the escalation is attributable. Either way, add a test with a fixture whose only change is an out-of-scope retirement notice and assert **no** change is reported.

## 2. Three stale numbers in `docs/agent-cadence.md`

Measured from the registry and the matrix on 2026-09-09:

| Claim in the doc | Actual | Location |
|---|---|---|
| "the complete watch surface is **fifteen pinned sources**" | **22** watched sources + **11** `human_only_sources` | line 16 |
| "worth its complexity even at **nine rows**" | **13** rows | line 66 |
| "carry **seventy-five headings** for products outside this repository's scope" | **84** (of 86) | line 81 |

The same sentence at line 16 also says the surface covers *"every matrix row"*. **Rows 12 and 13 refute that** — both are backed only by `human_only_sources`, so nothing watches them.

Worth noting how this was caught: the line-16 sentence carries its own instruction to *"Re-derive that count from the registry rather than trusting this sentence"*, and records that it had already been stale in exactly this way once before ("it described four sources for a release and a half after there were more"). The instruction works; the number still drifts. Consider deriving these counts at lint time instead of asserting them in prose — `validate-matrix.yml` already lints workflow definitions, so it is the natural home for a "doc numbers match the registry" check.

The `seventy-five` → `84` case is arguably not a defect: a live page's heading count drifts continuously and the figure was presumably right when written. That is the argument for not hard-coding it in prose at all.

## 3. `human_only_sources` entries carry no row mapping, and `registry_problems()` cannot see them

No entry in `human_only_sources` carries `matrix_rows` or any framework-row key — checked across all 11. Coverage is declared only in prose inside each entry's `reason` field. Consequences:

- Matrix rows **12** and **13** and the **NIST** and **CSA** cross-walk rows have **no machine-readable link to a source**. Mapping them requires matching cite URLs against row text, which is what the 2026-09 refresh had to do.
- `registry_problems()` (`scripts/watch_sources.py`) validates only `registry["sources"]`. It therefore cannot catch a malformed human-only entry, a mis-join, or — more importantly — **a matrix row with no source of any kind**.
- **Four of eighteen dated items can never be advanced by any agent run** (rows 12, 13, NIST, CSA). That invariant is load-bearing for reading the staleness output correctly, and it is stated nowhere in the repository.

`.github/watch-state/` *is* inside the refresh write allowlist, so a schema addition here is closer to hand than findings 1 or 2 — but adding keys is a design decision, not a refresh edit, which is why it is filed rather than done.

**Suggested fix.** Give human-only entries the same `matrix_rows` / `crosswalk_rows` keys the watched entries use, extend `registry_problems()` to validate both arrays, and add an assertion that every matrix row appears in at least one of them. That last check is the one that would have made "rows 12 and 13 are unwatched" visible without a human deriving it.

## 4. There is no discovery modality — the cadence cannot find a new row

`README.md` and `matrix/capability-status-matrix.md` both commit the refresh to *"Microsoft Learn 'What's new' pages and the Message Center"*. The registry contains **exactly one** such page — `defender-release-notes`, plus its archive. There is no Purview, Defender XDR, Defender for Cloud Apps, Entra or Sentinel "what's new" or release-notes source. Every other watched source is a per-capability page, which can only report drift on a row that **already exists**.

So the monthly refresh is **structurally incapable of finding a capability that should become row 14**. This is the same failure class that let the OWASP LLM Top 10 2026 edition land unnoticed — the registry claimed a coverage shape it did not have — and it is the half of the README's cadence promise that has never run. The matrix's *Planned rows* section was also not reviewed in the 2026-09 cycle and still reads "None currently."

**Suggested fix.** Either register a "what's new" source per product family and accept that discovery escalations need human triage, or amend the README's cadence sentence to state honestly that the automated half covers drift on existing rows and that discovery is a human step. The second is cheaper and still fixes the mismatch; the first is what the sentence currently promises.
