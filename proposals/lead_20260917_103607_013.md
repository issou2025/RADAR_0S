## Work-first rule

Every worker follows this priority:

```text
active PRs -> bugs/regressions -> integration/collision work -> tests/review -> backlog health -> ARADR research -> evidence-backed new issue/design
```

Do not start speculative feature implementation while useful active work is waiting.

All nontrivial new design uses ARADR:

```text
ANALYZE -> RESEARCH -> DESIGN -> ADVERSARIAL REVIEW -> DECISION
```

Use current primary/vendor sources for fast-moving claims. Record alternatives, failure modes, security/authority implications, lifecycle/restart/cancellation behavior, resource costs, migration/compatibility, and falsifiable acceptance fixtures.

## Pod-level feature freeze

Each pod may independently propose `FEATURE_FREEZE` when its active candidate set is coherent enough to stabilize.

A freeze ballot is recorded by the five workers in that pod as `FREEZE_YES`, `FREEZE_NO`, or `ABSTAIN`. The proposal author does not count as an independent vote on their own proposal. Freeze passes with at least **3 independent YES**, YES > NO, no unresolved security/authority blocker, and exact-current backlog evidence.

Effects of a passed freeze:
- no unrelated new feature implementation in that pod for the target release;
- bug fixes, regressions, tests, docs, packaging and release blockers remain allowed;
- newly discovered P0/security/data-loss defects automatically reopen scope;
- deferred features are explicitly recorded as excluded/experimental rather than silently dragged into the release.

## Version/release vote

The Release Lifecycle pod owns the final release candidate and version vote. It consumes the frozen state from all pods and chooses a coherent version scope.

Required record:

```text
RELEASE_CANDIDATE
version: <semver>
source_sha: <exact integrated sha>
included: <issues/prs/outcomes>
excluded: <explicit exclusions>
experimental: <explicit experiments>
required_gates: <checks/evidence>
votes: <five release-pod ballots>
```

Normal publication requires at least **3/5 YES** from the Release pod, YES > NO, and no unresolved security/authority/data-loss blocker. Voting never overrides failed/missing/pending required tests or repository protections.

The Release pod may choose not to release when the integrated candidate is incoherent, even if individual PRs are green. Conversely it should cut a new version when a coherent frozen candidate is fully green rather than letting `main` accumulate indefinitely.

## Continuous release lifecycle

After a release:
1. record shipped source/artifacts/checksums/signer/test evidence;
2. reopen feature intake for the next version;
3. each pod selects the next bounded release goal;
4. work existing PRs first;
5. when the bounded goal is coherent, each pod may freeze again;
6. Release pod votes/version-cuts again.
