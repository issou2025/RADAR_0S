# Project Proposal — Structural Drawings

*Project description:*
## Overview & Background

An analysis of a 90-step ATIF trajectory trace (`session_id: d6b1d63f9c`, model: `Qwen3.6-35B-A3B-Thinking`, LibrAgent v0.9.23) revealed several systemic bottlenecks in LibrAgent's built-in MCP tool layer and execution environment. 

During the session, the agent attempted to inspect an attachment, resulting in 86 tool calls with **37 failures (43.0% failure rate)** and ~4.4M prompt tokens consumed without recovering. While the user's document was an encrypted PDF, the tool failures were purely infrastructural and apply broadly across many agent workflows.

---

## 1. `attachments` Server: Misleading "0 lines" Error & Missing Local File Path

### Problem
When an attachment cannot be text-extracted during ingest (e.g., binary files, encrypted PDFs, OCR failures), `storage.read_content` returns:
```text
✗ Read attachment failed: Error: Requested range [1-0] exceeds file length.
File has 0 lines. Valid range: [1-0].
Use list to verify file size before reading.
```
- `[1-0]` is an invalid range that misleads the agent into believing the file is 0 bytes or corrupted.
- The attachment tool provides no `local_path` or metadata for fallback inspection, forcing the agent to hallucinate or scan arbitrary download directories.

### Proposed Improvement
- Return structured status when `chunks.is_empty()` or line count is 0:
  ```json
  {
    "status": "binary_or_unparsed",
    "mime_type": "application/pdf",
    "size_bytes": 158495,
    "local_path": "C:/path/to/original/file.pdf",
    "guidance": "Text extraction yielded 0 lines (file may be encrypted or scanned). Use workspace tools to inspect the file directly at local_path."
  }
  ```
- Expose `local_path` (or session attachment directory path) in `attachments__listAttachments` / `readAttachment`.

## 2. Tool Environment: Windows App Execution Alias Stub Trap (Exit Code 9009)

### Problem
On Windows, `%LOCALAPPDATA%\Microsoft\WindowsApps` contains 0-byte reparse points (`python.exe`, `python3.exe`). 
- When an agent checks for python via `Get-Command python3`, PowerShell confirms existence.
- Running it yields `exit code: 9009` (*"Python was not found; run without arguments to install from the Microsoft Store..."*).
- The agent assumed Python was installed elsewhere and spent 11 consecutive steps traversing `C:\Python*`, `C:\Program Files`, and `AppData\Roaming` looking for an interpreter.

### Proposed Improvement
- **Sanitize PATH**: Strip `%LOCALAPPDATA%\Microsoft\WindowsApps` from the spawned shell PATH if the executables are Microsoft Store stubs, or prioritize actual installed runtimes.
- **Error Guidance**: When exit code 9009 with Microsoft Store text is detected, inject targeted guidance:
  > *"⚠️ Microsoft Store execution alias stub detected. Python is NOT installed. Do not search the filesystem; switch to Node.js or native fallback tools."*
- **Preflight Host Info**: Inject available system runtimes (e.g. `node: 24.19.0`, `python: none`, `git: available`) into the session environment context so the agent doesn't waste steps discovering tool availability.

## 3. `workspace` Shell: Missing `cwd` Support & Stateless CWD Confusion

### Problem
`workspace__runPowerShell` runs statelessly from the workspace root (`workspaces/<session_id>`). 
- When the agent executed `cd $env:TEMP; npm install pdf-parse`, the next command `node -e "require('pdf-parse')"` reverted to the workspace root, failing with `Cannot find module`.
- The agent spent over 20 steps struggling with `$env:NODE_PATH`, relative path traversal (`./node_modules`, `../node_modules`), and package reinstallation.

### Proposed Improvement
- Add an optional `cwd?: string` parameter to `workspace__runPowerShell` (and other terminal tools).
- In the tool description or error guidance, explicitly remind the agent that directory changes (`cd`) do not persist across tool calls.

---

## 4. Process Lifecycle: Immediate Crash Detection on Background Handoff & Idempotent Stop

### Problem
- When `workspace__runPowerShell` hit the 5s timeout handoff, it returned `✓ Sync timeout handoff: command was still running after 5 seconds, so it continues in background. Process ID: <id>`.
- In reality, the process crashed immediately (e.g., Node server failed with `ENOENT` on startup). The agent assumed it was running and attempted browser connections (`ERR_CONNECTION_REFUSED`).
- Later, calling `workspace__stopProcess` on the dead process returned an error: `✗ Process <id> has already terminated with status: Failed`.

### Proposed Improvement
- **Grace Period / Early Exit Check**: Before handing off to background, verify whether the process exited with an error status within a brief initial window. If it already crashed, return the error output immediately instead of a success handoff.
- **Idempotent `stopProcess`**: If a process has already terminated, return success (`✓ Process <id> has already terminated (status: Failed)`) rather than an error (✗) to avoid triggering agent panic loops.

---

## 5. `browser` Server: Unhandled JS Promise Hanging & Unsupported Scheme Crashes

### Problem
- In `browser__evaluateJS`, returning an unresolved Promise (e.g. an infinite `setTimeout` loop) blocked the browser sidecar for 30,000ms until timeout, causing the active browser session to be dropped (`Browser session not found`).
- Calling `browser__fetchUrl` with `file:///` caused Chromium automation to exit with status `ExitStatus(21)`.

### Proposed Improvement
- Enforce an internal evaluation timeout on `browser__evaluateJS` so long-running promises do not freeze the sidecar IPC channel.
- Validate URL schemes at the MCP command boundary (`browser__fetchUrl`) and return a friendly error rather than forwarding unsupported schemes to Chromium.
