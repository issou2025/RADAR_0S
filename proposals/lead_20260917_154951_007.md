# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**2.0.0: Rust desktop app replacing the Flutter desktop targets**

*Project description:*
## Problem Statement

The desktop builds of cat(a)log are the phone layout on a big screen: one column, floating action buttons, bottom sheets, no menu bar, no right-click, hardly any keyboard. A keeper who sits at a desk with a Catalog open, a shared folder syncing and a printer next to the screen gets a stretched phone. On top of that the Flutter desktop targets are the least reliable builds the project ships, and the maintainer has no confidence left in Dart as a desktop platform.

## Solution

cat(a)log 2.0.0 ships a new desktop application written in Rust, in this repository, that replaces the Flutter desktop targets completely. It speaks the same shared-folder and bundle format as the 1.x phones, so a keeper's phone and desk stay one Catalog. It carries every feature of the phone app that makes sense at a desk, laid out as a desktop program: a menu bar, panes side by side, right-click where the phone has a hold, keyboard navigation, system file and print dialogs, remembered window state. It installs through the existing Homebrew tap and Scoop bucket. Nothing is published until the whole thing is done.

## Implementation Decisions

- **Placement.** A Cargo workspace in a `desktop/` directory of this repository, with two crates: `catlog-core` (Catalog store, entries, signing, folder sync, bundles, photos, PDFs, Flier reading) and `catlog-gui` (the egui application). The Flutter app stays at the repository root. The Flutter desktop targets (`linux/`, `windows/`, `macos/`) are deleted in the step that swaps the release pipeline, not before.
- **Compatibility contract.** The shared folder layout (one `.jsonl2` log per device, one keys file per device, photo blobs) and the `.catsync` bundle (format 2 with its marker, entries file, keys file and photos) are the contract with the phones. The Rust app writes exactly what 1.3.4 writes; key order aside, byte-compatible. Any change to the format is a separate later decision with its own reader-skip rule. Ed25519 signing, trust on first use and the verified state are part of the contract. The local storage schema is not.
- **Transports.** Shared folder and bundle only. LAN, hotspot and in-person sessions are not built for desktop.
- **Core shape.** The core exposes a plain synchronous Rust API over owned data: open a Catalog directory, apply a folder round, import and export a bundle, write entries, query state, record and return to Moments, dump state for comparison. No GUI types, no global async runtime, so an FFI bridge for the phones remains possible without rework. The phones keep the Dart core for now.
- **Storage.** SQLite through rusqlite with the bundled feature; no system SQLite. Schema owned by the Rust core. Photos as files on disk, addressed by hash as today.
- **Data directory.** The platform data directory under the existing app id, resolved with the directories crate, with a fresh sub-layout that never collides with the Flutter desktop files. No migration of Flutter desktop data; existing desks resync from the folder or a bundle.
- **Toolkit.** egui and eframe 0.35, as in dedup-rs. Light theme only, no dark mode, plain egui look with cat(a)log colours, no LCARS styling. Tables through egui_extras. Window state through the window bounds saved as a local setting, as on the phone build.
- **Desktop layout.** Master-detail panes on wide windows (list left, record right), a menu bar with File, Edit, View, Catalog and Help, right-click menus wherever the phone has a hold, keyboard navigation through every list, system file dialogs for import, export and photos, system print dialog for PDFs. The UI laws still apply where they are not phone-specific: one primary action per page, dialogs with one question and at most two actions, destructive actions confirm once with the verb in the error colour, wording of people and cats and homes, never devices and entries and hashes.
- **Feature set.** Every desktop-natural feature of the phone app: Catalogs, Clowders, Cats, Strays, Fields of every type, histories and graphs, timeline, chores and agenda, Appointments and Vet Runs, reminders as desktop notifications, ICS export, map with cached tiles and the Possible Stray Area, photos from files with crop and Mark and metadata stripping, Card as PDF and image, vet report PDF, missing poster PDF with the QR code phones read, Flier reading from image files, ID Fields with QR and barcode display and registry links, duplicates and match candidates, Merge, conflicts, import summary, folder watch line with the merge switch, Moments and going back, automatic backups and restore, Transfer, Private and Hidden, Ban and Hard Delete with the moderation page, archive, Deceased, Pet Mode, Species, unit values, achievements with sounds, intro and tips, help on every page, settings, about, crash screen with mailed report, `.catsync` file association. Phone-hardware features are replaced by their file equivalents: camera capture becomes file import or drag and drop, QR scanning becomes typing or an image file, Stray Cam is out.
- **Translations.** The ARB files under the Flutter app's localization directory are the single source. A build-time generator in the desktop workspace turns them into Rust string tables with typed placeholder functions and an ICU subset for plurals and select. Right-to-left languages render as text only; layout stays left-to-right.
- **PDFs and codes.** PDFs generated in Rust with embedded fonts, fetching the Greek, Cyrillic, Arabic, Hebrew, Farsi, Japanese and Chinese fonts once when first needed, as the phone does. QR codes on the poster and Card carry the same payload the phone writes so a phone reads them.
- **Coverage.** cargo-llvm-cov, line coverage, 80% gated per crate in CI, the binary entry point and generated code excluded.
- **Release.** The existing release workflow keeps its gate, Android, F-Droid, GitHub release and channel jobs. The three Flutter desktop build jobs are replaced by Rust jobs modelled on dedup-rs: Linux tar.gz, AppImage and .deb per architecture, Windows zip, macOS app bundle in a dmg per architecture. The gate checks that the tag, the pubspec version and the Cargo crate versions agree and runs clippy with warnings as errors and the coverage floor. The channel job renders the Homebrew cask from the dmg, the Homebrew formula from the Linux tarball and the Scoop manifest from the Windows zip, and pushes to the existing tap and bucket with the existing token. Templates and packaging scripts (desktop file, MIME registration, icon installer, app bundle, AppImage, deb) live under the desktop workspace.
- **No releases before done.** No tag, no pre-release, no nightly, no channel push until the done checklist below is complete. The workflow may run on the branch through manual dispatch with the release and channel steps skipped, producing artifacts for inspection only.
- **Order of work.** First the scenario list and the fixture generator with the corpus committed; second the core until every fixture passes in both directions; third the GUI screen by screen with its tests; fourth the pipeline swap and the deletion of the Flutter desktop targets; fifth the tag.
- **Done checklist.** Every fixture scenario green both ways; both crates at or above 80%; every screen of the feature set present with at least one harness test; clippy clean; the release workflow run on the branch with publishing skipped and every artifact produced; Flutter desktop targets deleted; CHANGELOG section for 2.0.0 written; versions matching; and one manual round by the maintainer with a real 1.3.4 phone through one shared folder and one bundle in each direction.

## Testing Decisions

A good test drives the system at its outermost seam and asserts what a keeper or a partner device observes: the state of a Catalog after an import, the files written to a folder, the pixels and rects of a rendered page. It does not reach into store internals, private functions or the SQLite schema.

- **Fixture corpus (the core's specification).** A Dart script in the core package's tool directory writes a corpus of scenarios into a fixtures directory under the desktop workspace: for each scenario a shared folder or a bundle produced by the Dart core, and an expected-state JSON dumped by the Dart core after importing it. Scenarios cover: a fresh Catalog with Clowders and Cats; Field definitions of every type; histories with reverts; Moves and Adoption; Strays and Flier Positions; Merge of Cats, Clowders and Fields; Private values with and without the share switch and the withheld trace; Hidden as a non-traveller; signed entries, unsigned pre-1.2 entries, a bad signature, trust on first use; a `.jsonl` next to a `.jsonl2` from an old device; photos present, missing and arriving later; Moments and going back; Transfer re-stamping; Ban and Hard Delete; chores, ticks, Appointments and Vet Runs; Pet Mode, Species, unit values; conflicts from two writers. The corpus regenerates deterministically. Rust tests import each scenario into a fresh Catalog and compare the dumped state. A CI job runs the reverse: Rust writes folders and bundles for the same scenarios, a Dart test imports them and compares. Prior art: the Dart core's folder sync, bundle, signing and merge tests, which build the same situations in code today.
- **GUI harness.** Tests in the GUI crate build the real application over a temporary Catalog seeded from a fixture, render it headless with egui_kittest at a desktop size, drive menus, clicks, right-clicks and keys, and assert on rects and labels, rendering wherever layout matters. Ignored render tests write PNGs for the maintainer and the screenshot set. Prior art: the dedup-rs GUI crate's inline kittest modules and its ignored screenshot tests.
- **Translation generator.** One test runs the generator over a small ARB with placeholders, a plural and a select and checks the generated table; the GUI harness runs in two locales.
- **Coverage.** cargo-llvm-cov per crate, gated at 80% in CI.
- **Pipeline.** Not automated beyond the dispatch dry run; the manual phone round is part of done.

## Out of Scope

- The vet practice set (issue #100): visits, invoices, medicine records, documents, vaccination lines, templates.
- LAN, hotspot and in-person sync on the desktop.
- Phone-hardware features: Stray Cam, video frame picker, camera OCR, QR scanning from a camera, device calendar mirroring, share intents.
- Dark mode and right-to-left layout.
- Migration of data from the Flutter desktop build.
- Any change to the sync or bundle format, and any FFI bridge from the phones to the Rust core.
- Pre-releases, nightlies or channel pushes before the done checklist is complete.
- Changes to the phone app beyond the fixture generator and the reverse-direction test.
