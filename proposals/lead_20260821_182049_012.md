# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**prd: observability — one pane of glass across Buzz, queryable by humans and agents**

*Project description:*
Converted from ADR [#83](https://github.com/launchpad-26/buzz/issues/83). That issue typed this as a decision, on the instruction of #42's criterion 6. It is not one: collectors, instrumentation, a stack and a retention policy all ship when this closes, and it decomposes into children. Feature-level work, so a PRD.

This PRD sets **scope**. It deliberately makes no design or tooling decisions beyond the direction below; those are its children.

### Problem

Buzz is opaque to the people operating it.

An error appears in the desktop app and disappears. It cannot be read in time, cannot be copied, and there is nowhere to go afterwards to retrieve it. So a fault that a human actually witnessed cannot be turned into a bug report with reproduction steps, an exact error, and a statement of whether the log was even correct.

Worse are the faults only one person has. One member cannot join a huddle while everyone else can. Nothing in the current setup can explain that, because explaining it requires comparing what happened on *that* client against what happened on the others and on the relay at the same moment. There is no vantage point today from which that comparison is possible.

The consequence is that diagnosis is guesswork, bugs get filed thin or not at all, and the cohort cannot answer basic questions about what the platform it operates is actually doing.

### Evidence

Verified in this repository on 2026-08-21:

- **OpenTelemetry is already a workspace dependency.** The root `Cargo.toml` declares `tracing-opentelemetry 0.33`, `opentelemetry 0.32`, `opentelemetry_sdk` and `opentelemetry-otlp` (grpc-tonic, tls-ring). `buzz-relay` already depends on `tracing-opentelemetry`.
- **The relay already has a telemetry module.** `crates/buzz-relay/src/telemetry.rs` builds an OTLP span exporter and sets a global tracer provider.
- **It is already configurable and already off.** `.env.example` documents `OTEL_EXPORTER_OTLP_ENDPOINT` — *"optional — leave unset to disable"* — and a separate `BUZZ_OTEL_FILTER`. Nothing sets them.
- **Structured events already exist to export.** 14 of 28 crates use `tracing` macros, across 89 files.
- **Relay metrics are already exposed and unscraped.** Prometheus on `:9102`.

So the relay side is closer to configuration than to construction. How much closer is a question this PRD's first child answers rather than assumes.

### Success criteria

1. **One place to look.** Telemetry from the relay, the web client and every participating desktop client is queryable together, in one pane of glass.
2. **An error a human saw is still there afterwards** — retrievable, readable, copyable, with enough surrounding context to write reproduction steps against.
3. **A single-user fault can be explained.** The huddle case is the acceptance test: given one member who cannot join and several who can, the telemetry supports a statement of what differed.
4. **An agent can do the diagnosis.** It queries the backend directly, and produces a bug report in `launchpad-26/buzz` carrying reproduction steps, the exact error, the supporting telemetry, and an assessment of whether the log itself was correct.
5. **Alerting is the trigger, not a notification.** An alert condition firing is what causes work to be raised: the alert starts an investigation and an issue is opened in `launchpad-26/buzz` automatically, with the telemetry that fired it attached. The recipient is the pipeline, not a person on a rota — which is what makes alerting useful here rather than noise.
6. **Collection is deliberate.** A stated policy of what is and is not stored, so telemetry is not generated for its own sake — and so that what is *not* being collected is known rather than discovered during an incident.
7. **Self-hosted, no per-seat or overage cost.** Direction set: a Docker Compose Grafana stack with Grafana Alloy on each participating machine pointed at it.
8. **Portable by design.** It runs on a maintainer's machine first and moves to a second host later without being redesigned.

### Non-goals

- **No hosted SaaS backend.** Rejected on cost — overage pricing against fleet-wide agent and client telemetry.
- **No design decisions here.** Which signals, which retention, which components of the stack, how the desktop app emits — all children of this PRD.
- **Mobile is out of scope for the time being.** Ruled out deliberately rather than deferred by omission: how a Flutter client would emit into this stack is an open question nobody has answered, and it is not worth the cost within this project. If that changes it needs its own decision.

  The web client **is** in scope — it is part of Buzz's feature surface and should be instrumented alongside the relay and the desktop app.

### Security implications

**Telemetry is an exfiltration path, and this PRD widens it deliberately.** Logs and spans are where hostnames, connection strings, auth tokens, private keys and environment dumps escape. Two consequences follow, and both belong to children of this PRD rather than being solved here: the filtering policy in criterion 6 is a security control and not only a cost control, and any configuration committed for this work lands in a **public** repository.

**The collector becomes the most valuable single target the cohort runs.** It holds a correlated picture of the relay plus every participating member's client. It is worth more to an attacker than any one machine it collects from, which is an argument about where it eventually lives and how it is reached, not a reason to avoid building it.

**Alloy runs on contributors' personal machines.** Accepted by the cohort as a condition of participation.

**The agent's query path is a credential.** Whatever the agent uses to query the backend is read access to the cohort's full telemetry picture, held by an automated process.
