# Project Proposal — Pdf To Revit

## Project Understanding
You need assistance with: 
**Installation drawing set: render datum-dimensioned floor/elevation/RCP vector sheets instead of only orthographic point data**

*Project description:*
## Summary

Deep installation-handoff review of HTDT `main@6ad227fafc88c6f19e0bdda927114326e2d5a081` found a gap between the existing InstallationOutput authority and a field-usable installation drawing.

Current `report.py` defines:

```text
InstallationDimensionSheet
- view: top/front/side
- horizontal/vertical axes
- view bounds
- points[]
```

and `_dimension_sheets()` projects each installation entity origin into top/front/side 2D point coordinates.

The class explicitly says:

> Canonical data for a dimensioned orthographic view; rendering is downstream.

#453 correctly plans native installation preview/export, but the current canonical sheet data does not yet define:
- dimension lines;
- datum/baseline references;
- object outlines/apertures;
- leader/callout layout;
- dimension-chain policy;
- reflected-ceiling plan;
- page/scale/title-block semantics;
- overlap/readability rules;
- vector/PDF drawing output.

A coordinate table and point cloud are useful, but they do not fully eliminate field transcription.

## Product goal

Add a deterministic **Installation Drawing Set** renderer/specification over exact InstallationOutput and project authorities.

The result should be practical for:
- marking speaker positions;
- projector/screen installation;
- display mounting;
- ceiling speakers/lights;
- treatment placement;
- rack/cable handoff;
- as-built verification.

Do not turn HTDT into a general-purpose BIM/CAD drafting suite.

## 1. Keep InstallationOutput as engineering authority

Installation drawings are a deterministic presentation/output of exact stored authority.

Do not make SVG/PDF geometry the canonical design truth.

Conceptually:

```text
InstallationOutput
+ DrawingSetSpec
-> InstallationDrawingSet
-> SVG/PDF/print
```

Bind the exact InstallationOutput semantic hash.

## 2. DrawingSetSpec

Create a versioned rendering/request spec containing only presentation/drafting choices such as:
- included sheets;
- page size;
- orientation;
- drawing scale or fit policy;
- unit display preference materialized for output;
- dimension datum policy;
- label density;
- optional layers;
- renderer/version.

Changing paper size should not change engineering authority.

## 3. Core sheets

Initial drawing set should support:

### Floor / top plan
- room outline;
- doors/openings where available;
- seats;
- speakers/subs;
- screen/display footprint/reference;
- projector;
- furniture/infrastructure when selected;
- dimension callouts.

### Front elevation
- screen/display;
- L/C/R / subs;
- speaker acoustic/reference points where relevant;
- treatment;
- wall/opening geometry;
- mounting heights.

### Side elevation
- projector lens;
- screen/image plane;
- rows/risers;
- speaker heights;
- sightline-critical geometry when selected.

### Reflected ceiling plan
- ceiling speakers;
- projector mount;
- ceiling treatment;
- lighting fixtures/zones (#640) when physical placement exists;
- ceiling cable/penetration references where modeled.

Do not fabricate ceiling-plane objects from non-spatial workflow records.

## 4. Real object geometry, not only origins

Where exact body geometry/envelope exists (#464), render:
- object outline/projection;
- visible aperture;
- mounting plate/reference if modeled;
- collision/service clearance optionally.

Use a point symbol only when body geometry is unavailable or intentionally simplified.

Clearly distinguish:
- physical envelope;
- acoustic reference;
- lens center;
- image/display center;
- measurement/reference target.

Do not plot all of them as the same dot.

## 5. Datum-based dimensions

Compose with #537 InstallationDatum.

Installation dimensions should prefer explicit field datums such as:
- finished floor;
- front-wall plane;
- room centerline;
- screen/display centerline;
- known side wall;
- user-defined datum.

Example:

```text
Center speaker acoustic reference
  +0.000 m from screen centerline
  +0.720 m above finished floor
  0.180 m forward of front-wall datum
```

Do not require installers to reconstruct coordinates from an opaque global XYZ origin.

## 6. Coordinate vs construction dimension

Keep distinction:
- global HTDT coordinate;
- datum-relative installation dimension;
- physical body edge/center;
- acoustic/reference point.

Drawings may show datum-relative values while advanced metadata preserves exact global coordinates.

## 7. Dimension chains

Support explicit dimension types:
- baseline/ordinate dimensions from datum;
- chained dimensions;
- center-to-center spacing;
- edge clearances;
- mounting height;
- screen/display aperture width/height;
- riser height/depth;
- cable/run length only as a schedule unless geometry is appropriate.

Do not automatically create every pairwise dimension.

## 8. Speaker-specific callouts

Useful callout fields:
- logical role from #505;
- physical model/instance when resolved;
- acoustic reference position;
- cabinet mounting position;
- aim/yaw/pitch when installation-relevant;
- mounting context #540;
- height datum.

Do not use legacy `speaker_role` string as the sole identity after #505 exists.

## 9. Ceiling speaker layout

Ceiling layouts are especially difficult from raw XYZ.

RCP should support:
- room/ceiling boundary;
- ceiling speaker cutout/center;
- centerline/front-wall dimensions;
- orientation/aim;
- exclusion/clearance zones where modeled;
- fixture conflicts.

Do not infer a cutout diameter from generic cabinet size unless exact mounting data exists.

## 10. Screen / projector / direct-view video

Projection sheets may include:
- physical screen frame;
- active presentation aperture (#565);
- screen center datum;
- projector body;
- lens reference point;
- throw distance;
- required lens shift/zoom state;
- mount point if modeled.

Direct-view #637 sheets include:
- chassis/body;
- active image aperture;
- wall-mount reference;
- display center/height/tilt.

Do not print projector-specific dimensions for direct-view installations.

## 11. Treatment

Treatment placement sheets should show:
- host surface;
- exact panel dimensions;
- center/edge offsets;
- air gap/depth where install-relevant;
- quantity/type tag.

Use #451 canonical placement authority.

Do not turn treatment material assumptions into construction dimensions.

## 12. Wiring / infrastructure

#538 CableRun may optionally render a separate layer/sheet:
- visible/planned route;
- endpoints;
- wall plates;
- rack;
- conduit zones;
- run IDs.

Hidden/unobserved in-wall route remains dashed/unknown according to authority.

Do not draw a guessed straight line as an as-built cable route.

## 13. BOM callouts

#639 may provide item/tag IDs used in the drawing.

Example:

```text
SPK-HL-01
MOUNT-04
CABLE-SUR-L
```

Drawing tag links to BOM/install schedule.

Do not duplicate mutable procurement status into the geometric drawing identity unless intentionally requested.

## 14. Layer model

Suggested deterministic layers:
- room/construction;
- equipment;
- speakers;
- seating/risers;
- video;
- treatment;
- infrastructure/wiring;
- dimensions;
- datums;
- callouts;
- proposed/current/as-built styling.

Layer visibility is drawing presentation state, not Scene truth.

## 15. Lifecycle styling

Drawings must clearly distinguish:
- current/as-built;
- proposed;
- measured deviation where requested;
- reference/planned target.

Do not print a proposed variant in the same line style as verified installed state without legend.

## 16. Collision/readability layout

Implement deterministic label/dimension placement with bounded overlap avoidance.

Requirements:
- labels should not cover critical object geometry;
- leaders when displaced;
- predictable ordering;
- same authority/spec -> same vector output;
- if layout cannot avoid collisions, flag drawing as needing review rather than silently omitting labels.

Do not require an AI layout engine.

## 17. Scale / paper

Support practical page modes:
- fit-to-page;
- fixed scale when room/page permits;
- common paper sizes including A4/A3 at minimum;
- portrait/landscape.

Every printed/vector sheet shows:
- scale or `NTS` (not to scale);
- units;
- project/room;
- authority/checkpoint identity;
- generated timestamp separated from semantic design identity;
- sheet title.

Never label a fit-to-page non-scale rendering as 1:50.

## 18. Vector-first export

Prefer deterministic vector output:
- SVG for native preview/internal pipeline;
- PDF via a defined renderer/print path.

Raster screenshots should not be the primary construction drawing format.

Text/dimensions must remain sharp/printable.

## 19. PDF semantics

PDF is presentation/export, not a second canonical authority.

Bind metadata to:
- InstallationOutput hash;
- DrawingSetSpec hash;
- renderer version.

A regenerated PDF under the same exact inputs should be deterministic where the PDF backend allows; otherwise preserve deterministic SVG/source payload and document PDF metadata variability.

## 20. Native preview

#453 preview should show the actual sheet, not only coordinate tables.

Features:
- zoom/pan;
- sheet selector;
- layer toggles;
- click callout -> Room entity;
- problem badges for UNKNOWN/overlap/stale data.

## 21. Field usability

Normal printed sheet should not expose:
- SHA-256 strings;
- internal UUIDs;
- raw enum tokens.

Use human tags/names.

Advanced/audit appendix can contain exact IDs/hashes.

## 22. As-built comparison

#520 can produce optional deviation overlay:
- planned center;
- observed center;
- delta vector/value;
- tolerance status where exact policy exists.

Do not rewrite the original installation drawing.

Generate an as-built verification sheet bound to both authorities.

## 23. Checkpoints

#619 ProjectDesignCheckpoint is a natural source for:
> Issue this drawing set from Final layout before installation.

Drawings should bind exact checkpoint/authority refs, not whatever is current when reopened.

## 24. Project portability

#488 need not preserve generated PDFs if they are reproducible, but should preserve:
- InstallationOutput;
- DrawingSetSpec if saved;
- required source authorities/assets.

User-exported reports remain normal external files.

## 25. Non-goals

Initial implementation does not need:
- DWG authoring;
- Revit/BIM round-trip;
- full architectural annotation suite;
- structural engineering;
- electrical code plans;
- arbitrary CAD paper-space editing.

The goal is deterministic theater installation sheets.
