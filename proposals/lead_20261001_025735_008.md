# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**Research: all-in-one payment terminals (Stripe S710, Clover, PAX, Sunmi, Adyen…) — can the POS run ON the device, ranked easiest to hardest**

*Project description:*
## Question

Which of the popular **all-in-one payment terminals** — a card reader and a touchscreen in one device, usually Android underneath — could run the WCPOS app *on the device itself*, so the terminal **is** the till rather than a reader beside it? Survey each candidate against primary sources (vendor developer docs, SDK repos, program terms), judge whether there is a real path to putting our POS on it, and **rank them from easiest to hardest**.

This is a different question from the terminal work already landed or in flight. #173 drives Stripe's S700/S710 as a server-mode reader from a separate phone, tablet or browser; #231 is the epic for readers *beside* the till. Here the ask is the reverse: a merchant wants to buy one device, and the POS lives on it.

## Why now

- A user has asked about running the POS (the Android app) on a **Stripe Reader S710**. Stripe's *Apps on Devices* program exists for exactly this, and it has a React Native SDK, so it is the obvious first candidate to size properly.
- Roadmap #25 (Star mPOP) is the other "all-in-one" people have asked for. Note for the researcher: the **mPOP is a receipt printer plus cash drawer with a tablet stand — it has no screen and no CPU we could target**, so it belongs to the peripherals work in #25, not to this survey. If Star sells a screen-and-reader terminal in some market, include it; otherwise say so and move on.

## Candidates (seed list — extend it, and say explicitly when one is dropped and why)

- **Stripe Reader S700 / S710** — Apps on Devices (Android 10, Android and React Native SDKs, a DevKit unit, Stripe app review and a sales-gated eligibility check). S710 adds cellular.
- **Verifone V660p** (also in Stripe's Apps on Devices) and Verifone's wider Android family (T650p and friends) under other acquirers.
- **Adyen** Android terminals (S1E2 / S1F2 / AMS1, Castles hardware) — Adyen's custom-app program on its Android terminals.
- **Clover** Flex / Mini / Station Duo — Clover Android SDK and App Market; per-processor and per-country lock-in.
- **PAX** A920 / A920 Pro / A3700 / A35 — PAXSTORE distribution, but payments come from whichever acquirer ships the unit. Mollie Terminal is a PAX A920 Pro; check whether Mollie permits third-party apps on it.
- **Sunmi** P2 / V2s / V3 Mix / T2s — open Android, payments usually via an acquirer's SDK or a paired reader.
- **Viva.com** (Viva Wallet) Android terminals and their terminal-apps program.
- **Ingenico / Worldline Axium** DX8000 and family — Android, developer program.
- **SumUp** Solo, 3G+, Kiosk — likely closed; confirm.
- **Square Terminal / Square Register** — Terminal API only, no third-party apps on the device; confirm and place at the bottom.
- **PayPal Zettle Terminal**, **Toast Go**, **Lightspeed**, **Shopify POS Go** — closed ecosystems; a one-line verdict each is enough.
- Generic Android POS stations with a bundled reader (**Elo PayPoint**, **imin**, similar) if any have a supported payments path rather than "bring your own reader".

## What to establish for each device

1. **Runtime**: OS and version, third-party APK support, kiosk / launcher mode, min Android our Expo build needs vs what the device runs.
2. **Distribution path**: vendor dashboard or store, sideload, MDM, or nothing. Who approves, how long, what it costs, which countries.
3. **Payments from inside the device**: is there a local handoff SDK the app calls to take the payment on the same unit, or does the device still expect a server-driven flow (in which case our existing server-mode providers in #231 may already cover it)?
4. **Fit with our stack**: Expo / React Native, Hermes, expo-sqlite, the web bundle; would the current dev client run as-is, and what would need to change (screen size and orientation, no Play Services, restricted networking, printer and scanner APIs).
5. **Developer cost**: DevKit price and availability, an emulator or simulated device, sandbox account.
6. **Business gating**: vendor contracts, revenue share, processing exclusivity, review terms that would constrain a general-purpose POS.
7. **Demand signal**: who has asked (link the support threads), and which regions the device actually sells in.

## Output

A matrix (device × the seven points above) plus a per-device note with citations, then a **ranked list, easiest to hardest**, with a one-paragraph justification each and a recommended first target. Separate "not possible" from "possible but not worth it". Facts only; where a vendor program is sales-gated or undocumented, say what is unknown rather than guessing. This is a research ticket, not a commitment to build anything.

Refs #231 (terminals epic), #173 (Stripe smart readers as a server-mode provider), #114 (card-present SDK survey), #25 (Star mPOP), #97 (payments map).
