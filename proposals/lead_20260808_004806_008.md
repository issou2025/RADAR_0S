### What happened?

On Apple platforms the plugin never observes `AVCaptureSessionWasInterrupted`. When iOS interrupts a capture session that has already started, `start()` has *already returned successfully*, so the controller settles into `isInitialized: true, isRunning: true, error: null` — and stays there forever while no frame is ever delivered.

For the user this is a **permanently blank viewfinder with no error, no message and no way out**, because `MobileScanner` only consults `value.error` *after* `isInitialized` is true, and nothing ever sets it:

https://github.com/juliansteenbakker/mobile_scanner/blob/main/lib/src/mobile_scanner.dart#L313-L316

The session is genuinely dead — `captureSession.isRunning` is `false` natively — but Dart has no way to know. Note also that `startRunning()` returning with `isRunning == false` does not stop `start()` from resolving and building a `MobileScannerViewAttributes` for a session that never started.

**Expected:** an interrupted or failed session surfaces as an error on the controller, so the app can tell the user what happened and what to do about it.

**Why this matters regardless of the underlying Apple bug:** the interruption itself is Apple's fault and the plugin cannot prevent it. But the plugin decides *whether the app can react to it*, and today it silently swallows the condition. Diagnosing this cost us the better part of a day and required a hand-instrumented build of the plugin, precisely because every layer reported success. An app cannot show a "reboot your device" message for a condition it is never told about.

**Suggested fix:**

1. Observe `AVCaptureSessionWasInterrupted` / `AVCaptureSessionInterruptionEnded` / `AVCaptureSessionRuntimeError` in `MobileScannerPlugin` and forward them on the existing event channel, so `MobileScannerController` can set `value.error`. A `MobileScannerErrorCode.interrupted` carrying the reason would let apps distinguish "went to background" from "the system refuses the camera".
2. Independently: check `captureSession.isRunning` after `startRunning()` and fail `start()` when it is `false`.

Point 2 alone would have turned this into a visible error.

**Workaround for other apps** — observe the notifications yourself; `NotificationCenter` delivers them for every session in the process when observing with `object: nil`, so no fork is needed:

```swift
NotificationCenter.default.addObserver(
  forName: .AVCaptureSessionWasInterrupted, object: nil, queue: .main
) { note in
  let reason = note.userInfo?[AVCaptureSessionInterruptionReasonKey] as? Int
  // forward to Dart over your own EventChannel
}
```

### Steps to reproduce

The bug is the *silent swallowing*, so reproducing it needs any interruption while the scanner is open.

**Deterministic (any iPhone):**

1. Open a `MobileScanner` screen and confirm the preview is live.
2. Trigger an interruption by taking the camera away — e.g. start a FaceTime video call, or otherwise cause another client to claim the device (`videoDeviceInUseByAnotherClient`, reason 3).
3. Return to the scanner.

**Observed:** the viewfinder is blank forever. `controller.value` is `isInitialized: true, isRunning: true, error: null`, so `errorBuilder` is never called and no barcode is ever detected.
**Expected:** `errorBuilder` is called with an interruption error.

**How we hit it in production**, for context: `videoDeviceNotAvailableWithMultipleForegroundApps` (reason 4) on an iPhone 16 Pro Max / iOS 26.6. It persisted across app reinstalls and was only cleared by rebooting the device. Apple documents that reason as iPad-only (Split View / Slide Over / Picture in Picture), but it is [widely](https://developer.apple.com/forums/thread/791671) [reported](https://developer.apple.com/forums/thread/769996) on iPhone. In that state the app was **fullscreen, active, single-scene, with nothing capturing the screen** — we verified all of it.

We ruled out, each with direct evidence: camera permission (authorized), `Info.plist` keys, plugin registration, pixel format (BGRA chosen and available), selected device (`Back Triple Camera`, built-in), the output connection (`active=true enabled=true`), our own overlay widgets, screen recording/mirroring, the scene manifest, and our entire app (a build stripped to nothing but `MobileScanner` failed identically).
