## Deep review: `cl1-aws-s3`

Authoritative, code-level audit of the repository at commit `9df4685`. Single-file

### L1 Code correctness

**High — `check_logging` always reports "Disabled" (wrong XML element).**
`check_logging` looks for `.//s3:Enabled` and requires its text to be `"true"`
(s3_scanner.py:209-213). The S3 `GET /?logging` response does not contain an
`<Enabled>` element; the enabled state is the presence of a `<LoggingEnabled>`
element in `<BucketLoggingStatus>` (`https://s3.amazonaws.com/?logging`). The
element lookup therefore never matches, so `logging_enabled` is always `False`,
regardless of real bucket state. This corrupts the verdict printed in
`scan_bucket` (s3_scanner.py:276-278) and inflates the risk score by a constant
5 points (s3_scanner.py:287).
Remediation: replace the tag lookup with
`root.find(".//s3:LoggingEnabled", ns) is not None`.

**Med — dead `if False` ternary in `list_contents`.**
s3_scanner.py:235 is `self._request_unsigned(url) if False else self._request("GET", url)`
— a leftover debug branch. The intended fallback (signed fails, then unsigned,
s3_scanner.py:236-238) already exists below it, so the ternary is dead code that
should be deleted.

**Med — region-redirect statuses misread as "not found" in enumeration.**
`enum_from_wordlist` treats only `200` and `403` as "bucket exists"
(s3_scanner.py:130-135). Buckets in regions other than `self.region` and
non-US-east-1 default-flag buckets respond `301 PermanentRedirect` / `400` via a
virtual-hosted `*.s3.<region>.amazonaws.com` request; those buckets are silently
reported as absent (`status == 301`/`400` falls through). Resolve the redirect and
report `actualBucketLocation` as existence, or consider the requests-list approach.

**Low — public-score cutoffs ignore versioning state and use inconsistent parity.**
`public_score` (s3_scanner.py:284-289) rates only anonymous list/write + logging +
encryption; contributions are hard-coded and the label uses `public_score` while
`risk_score` uses `min(public_score, 100)` (same value today, but the split
suggests drift). No points for disabled versioning despite versioning being
reported, and ACL/public-access-block findings are not reflected in the live score
(see L5).

### L2 Security

**High — state-modifying write probe with no consent flag and unreliable cleanup.**
`check_write_policy` anonymously PUTs an object `probe-write-test` to the target
bucket (s3_scanner.py:163-180) and, if writable, issues a signed DELETE. In
`--bucket` mode no credentials exist (`--access-key` defaults to empty,
s3_scanner.py:575), so the cleanup `_request("DELETE", ...)` signs with an empty
key, gets `SignatureDoesNotMatch`, and abandons the object permanently on the
target bucket — exactly the behavior the README prohibits
(README.md:121 "Uploading or deleting data on unauthorized buckets"). There is no
`--dry-run`/`--no-probe-write` flag. The probe object name is also fixed, so a
pre-existing `probe-write-test` key can be overwritten. Remediation: gate the
write probe behind an explicit flag (e.g. `--probe-write`), verify delete
authority before deciding `writable=true`, and use a unique UUID object key only
when the flag is set.

**Med — credentials accepted as CLI argv / shell-history plaintext.**
`--access-key`/`--secret-key` are parsed by argparse (s3_scanner.py:575-576) and
documented as a supported live path (README.md:50). Credentials then appear in the
process list (`ps`) and shell history. Remediation: prefer
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` environment variables or an interactive
prompt; keep argv support only for explicitly-local automation.

**Low — wordlist enumeration probes arbitrary third-party namespaces.**
`s3_scanner.py:124-136` and `--enum` (s3_scanner.py:579) send unauthenticated GETs
to `https://<name>.s3.<region>.amazonaws.com/`. This is inherent to an S3 scanner
and the repo has good scope gates (SCOPE.md, ETHICS.md, README legal section), but
the tool itself performs no in-tool scope bound (e.g. suffix filter to owned
domains). A `--suffix`/ownership assertion flag would make the documented
authorization requirement enforceable in code.

### L3 Error handling & resilience

**High — network errors are converted into secure-looking "negative" verdicts.**
`_request`/`_request_unsigned` collapse every exception (DNS failure, timeout,
TLS, HTTP 5xx) into `(0, str(exc))` (s3_scanner.py:97-100, 107-110). Callers then
read status `0` as "not public / not writable":
`check_anonymous_list` sets `anonymous_list: False` (s3_scanner.py:144-150),
`check_anonymous_read_object` sets `anonymous_read: False`
(s3_scanner.py:155-161), `check_write_policy` sets `anonymous_write: False`
(s3_scanner.py:170-180). A network blip during a scan therefore produces a
false-clean security report with no error surfaced to the user beyond a score. At
minimum, distinguish `0` as `"error"` in results and fail loudly; add a
`--strict` mode that aborts the scan on any transport error.

**Med — no retries, backoff, or rate limiting on live probes.**
`enum_from_wordlist` fans out one request per name immediately and sequentially
(s3_scanner.py:126-136) with no sleep, and `scan_bucket` fires 5+ sequential
requests (s3_scanner.py:254-282). Throttling (`SlowDown`, `503`) returns status 0
via the swallow above and is reported as "not found". Add per-bucket/global rate
limiting and retry-once-with-backoff for 5xx/`RequestTimeTooSkewed`.

**Low — no logging facility and errors to stdout only.**
s3_scanner.py relies on `print()` for both diagnostics and findings; results of
failed sub-checks are invisible in `--output` JSON (`results` only carries
non-200 as `status`, see e.g. s3_scanner.py:186-189). Route diagnostics to
`logging` and include warning/error entries in the JSON report.

### L4 Performance & scale

**Med — sequential probing, no concurrency.**
`enum_from_wordlist` is O(n) sequential HTTPS requests over a thread pool-free
loop (s3_scanner.py:126-136) and owned-bucket scans repeat the full `scan_bucket`
sequence per bucket (s3_scanner.py:650-656). For 100-word wordlists or large
accounts this is minutes of wall time. The requests are independent; a
`ThreadPoolExecutor` (or, better, `asyncio`) with bounded concurrency fits the
existing per-name/per-bucket structure.

**Low — whole-response buffering.**
`_request`/`_request_unsigned` read the entire response body into memory
(`resp.read()`, s3_scanner.py:96, 106) and `_parse_list_objects` parses the whole
document (s3_scanner.py:299-314). A bucket with very large listings (or
`--prefix ""`) inflates memory linearly. Stream/paginate instead (see L5).

### L5 Data & correctness

**Med — `list_contents` never paginates; inventories truncated at 1000 keys.**
`list_contents` requests `max-keys={max_keys}` once (s3_scanner.py:229-242) with
no `marker`/`continuation-token` loop, so buckets with more than
`max_keys` objects (default 1000) are silently reported incomplete, and
`scan_bucket`"s "Objects found: N" (s3_scanner.py:258-259) and object listing
(s3_scanner.py:631-637) under-report. Add a pagination loop driven by
`IsTruncated`/`NextMarker`/`NextContinuationToken`.

**Med — live risk score ignores public ACL grants and public-access-block, while
the offline auditor flags them CRITICAL/HIGH.**
`_audit_acl` rates a public `WRITE` ACL grant CRITICAL and `READ` MEDIUM
(s3_scanner.py:377-383, 426-445), and `_audit_config` flags a missing public
access block HIGH (s3_scanner.py:507-520) — yet the live `scan_bucket` risk score
(s3_scanner.py:284-290) accounts for none of these, and the live checker has no
`?publicAccessBlock` probe at all. The same bucket can score `LOW` live and
`CRITICAL` offline. Align the live path with the (correct) offline rule set.

**Low — `_parse_list_objects` can raise on malformed size.**
`int(size.text)` (s3_scanner.py:310) throws `ValueError` if `<Size>` is absent or
non-numeric, and `list_buckets` calls `.find("s3:Name").text` guarded in a list
comprehension (s3_scanner.py:122). Wrap object parsing in per-object try/except so
one bad entry does not abort the whole list.

### L6 Test coverage

Tests exist and pass (12 `unittest` cases, tests/test_s3_scanner.py) and cover the
XML parsers, ACL normalisation, severity map, the full offline audit rule set, and
signing-key derivation. Critical gaps — untested paths:

1. **XML sub-resource parsers for versioning/logging/encryption.** No test feeds
   real S3-shaped `BucketLoggingStatus` / `VersioningConfiguration` /
   `ServerSideEncryptionConfiguration` documents. A test asserting
   `check_logging` returns `True` for a `LoggingEnabled` response would have
   caught the L1 bug above (also `ParseResult` vs error payloads).
2. **Transport/error paths.** No tests exercise `_request`/`_request_unsigned`
   with HTTP 301/403/503/timeout via `http.server` or mocked `urlopen`; today any
   stub returns "not found". Tests must assert that status `0` is surfaced as an
   error, not as a secure verdict.
3. **`scan_bucket` risk scoring.** No assertions on `risk_score`, the `50/40/5/5`
   weights, or the label cutoffs (s3_scanner.py:284-292).
4. **`check_write_policy` cleanup semantics.** No test for the "writable but
   delete fails → artifact left" path, and no test that the probe is not sent
   without an opt-in flag.
5. **`list_contents` pagination** — assert that a truncated response yields
   `IsTruncated`-driven continuation (once implemented).

### L7 Build / CI-CD

There is no `.github/` directory, no workflow, no lint/type-check/coverage gate,
no dependency manifest (none needed — stdlib only), no dependabot, no secret
scanning, and no CodeQL. A pure `print`-based, network-facing security tool has
zero automated regression protection; the L1/L2/L3 findings above reached HEAD
undetected. Three concrete improvements:

1. Add `.github/workflows/ci.yml`: run `python -m unittest discover -s tests -v`
   on 3.11–3.13; add `ruff check .` (or `flake8`) + `python -m compileall .`;
   add a `coverage` step with a threshold (e.g. 70%) so untested parser/network
   paths fail the build.
2. Add a smoke job that runs the supported CLI surface:
   `python s3_scanner.py --demo` (exit 0), `--demo --output` (report JSON exists,
   `finding_count>0`), and `--demo --exit-code-on-findings` (exit 2) — these are
   documented in README.md:62-70 but never executed by any automation.
3. Enable GitHub secret scanning + Dependabot (`github-actions`), and add a
   `CodeQL` workflow to catch the injection/XSS-class and XML-billion-laughs risks
   in the probe/parse paths.

### L8 Features (fit existing architecture, each tied to code)

1. **`--probe-write` opt-in gating the write probe** — `check_write_policy`
   (s3_scanner.py:163-180) is currently always-on in live scans; making it
   explicit converts an ethics bug into an auditable consent flag.
2. **Live `?publicAccessBlock` probe** — the offline rule CL1-CFG-004
   (s3_scanner.py:507-520) has no live counterpart; add
   `check_public_access_block` alongside `check_acl`/`check_versioning`
   (s3_scanner.py:182-225) so live and offline parity (L5) is restored.
3. **Pagination + `--max-keys`/inventory summary** — extend `list_contents`
   (s3_scanner.py:229-242) with continuation-token looping and a per-prefix
   Top-N/size summary; the parser already emits the required fields
   (`size`, `storage_class`, `last_modified`, s3_scanner.py:308-313).
4. **Concurrent enumeration with rate limit** — wrap the independent
   `enum_from_wordlist` requests (s3_scanner.py:126-136) in a bounded thread pool
   with per-second cap and 5xx retry/backoff (L3), preserving current
   `status`-based classification.
5. **`--scope <domain>` ownership filter** — enforcement hook for the
   SCOPE.md/README authorization contract (s3_scanner.py:128 URL construction)
   that only classifies/examines buckets whose names match the caller-supplied
   suffix, making authorized-only probing an in-tool invariant.
6. **Markdown/CSV report exporter** — offline mode already builds a `summary`
   map by severity and a findings list (s3_scanner.py:609-619); a
   `--format markdown|csv` on `write_report` (s3_scanner.py:671-677) would let CI
   dashboards consume the audit without post-processing JSON.

### Summary

- **High/Critical:** 3 (logging verdict bug; error→false-clean verdicts;
  uncontrolled write probe with unreliable cleanup)
- **Med:** 5 · **Low:** 3
- Layers with findings: L1–L8 · Tests: 12 pass but miss the network/Oracle paths
- CI: none — no workflows, no lint/type/coverage gates

The offline audit rule set (fixtures + `S3OfflineAuditor`) is well-built and
well-tested; the live SigV4/`urllib` path carries the correctness, safety, and
resilience defects above. A fix-PR should prioritise: `check_logging` element
lookup, error-verdict separation, and the `--probe-write` gate (all small,
localised changes with low blast radius).
