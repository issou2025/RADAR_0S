*Project description:*
Coverage counts the numerator and the denominator over different file sets, so
it reports a percentage above 100.

## What happens

On a workspace with a `WORKSPACE.md` at the root, `aiwg index stats` reports:

```
"coverage": { "indexed": 130, "totalFiles": 128, "percentage": 102 }
```

`indexed` counts the entries in the project graph, which deliberately include
the root context-graph files. `totalFiles` counts only files under the graph's
`scanDirs`, which cannot see them.

The two extra entries are exactly the context files:

```
$ python -c "
import json
m = json.load(open('.aiwg/.index/project/metadata.json', encoding='utf-8'))
out = [p for p in m['entries'] if not p.replace(chr(92),'/').startswith('.aiwg/')]
print(len(m['entries']), 'entries;', len(out), 'outside the scan dir:', out)"
130 entries; 2 outside the scan dir: ['WORKSPACE.md', 'AIWG.md']
```

It is not a stale-entry problem. Every indexed entry exists on disk:

```
$ python -c "
import json, os
m = json.load(open('.aiwg/.index/project/metadata.json', encoding='utf-8'))
print(len([p for p in m['entries'] if not os.path.exists(p)]), 'entries whose file is gone')"
0 entries whose file is gone
```

## Steps to reproduce

In any project with a `WORKSPACE.md` at the root and artifacts under `.aiwg/`:

```
$ aiwg index build --force
Artifact index built in 45ms
  Indexed 130 new, updated 0, unchanged 0
  Total: 130 artifacts

$ aiwg index stats --json
{
  "project": {
    ...
    "totalArtifacts": 130,
    "coverage": { "indexed": 130, "totalFiles": 128, "percentage": 102 }
  }
}
```

## Root cause

Two functions counting different sets. Neither is wrong on its own.

**The numerator.** `dist/src/artifacts/index-builder.js` walks the graph's
`scanDirs` and then deliberately adds the context graph from outside them:

```js
// WORKSPACE.md is the root of the project context graph. Index it and its
// local Markdown-linked nodes without copying them into provider trees.
if (!scope && (!graph || graph === 'project')) {
    const workspacePath = path.join(cwd, 'WORKSPACE.md');
    const contextFiles = [
        ...(fs.existsSync(workspacePath) ? [workspacePath] : []),
        ...await workspaceLinkedFiles(cwd),
    ];
    ...
}
```

`AIWG.md` arrives through `workspaceLinkedFiles`, so the number of extra entries
is however many Markdown-linked context nodes a project has, not always two.

**The denominator.** `dist/src/artifacts/stats.js:17` walks `scanDirs` only,
with no equivalent block:

```js
function countArtifactFiles(cwd, graphType) {
    const config = graphType ? GRAPH_CONFIGS[graphType] : undefined;
    const scanDirs = config
        ? config.scanDirs.map(d => resolveGraphScanDir(cwd, d))
        : [resolveGraphScanDir(cwd, '.aiwg')];
    ...
}
```

`GRAPH_CONFIGS.project.scanDirs` is `['.aiwg']`, so the root context files are
structurally invisible to it.

## Why it is worth fixing

The percentage above 100 is cosmetic. The offset behind it is not: it masks
undercoverage of exactly its own size.

Coverage exists so that a file present and unindexed becomes visible. With the
numerator ahead by `n`, `n` files under `.aiwg/` can stop being indexed and the
metric still reads 100%, which is the reading that stops anybody looking. On
this workspace that is two documents.

`aiwg index stats --json` is also the surface the `artifact-discovery` rule
directs agents to. That rule says "Agents MUST use `--json` flag when invoking
index commands" and "When assessing project state, use `aiwg index stats --json`
instead of manual file counting", so the wrong number is on the path an agent is
instructed to take.

## Suggested fix

The narrow fix is for `countArtifactFiles` to include the same context-graph
files when the graph is `project`.

The fix that cannot drift again is for the builder to record the file set it
actually indexed and for stats to count that, so the two stop being two lists
that have to agree.

## Acceptance

- [ ] A project with `WORKSPACE.md` and every `.aiwg/` artifact indexed reports

- [ ] The table output and `--json` carry the same corrected pair
- [ ] A regression test covers the `project` graph specifically, since the
      defect appears only where the builder indexes outside `scanDirs`

## Note on how this was found

The number was first read from `aiwg index stats --json | tail -20`. That shows
the tail of a multi-graph JSON document, which on this project is the `codebase`
graph, empty because its built-in `scanDirs` are `src`/`test`/`tools` with
TypeScript extensions and the project is Python. That produced a first
conclusion of "the index holds nothing", which was wrong: the project graph
holds 130 artifacts. The real defect appeared only on the full output.

The empty `codebase` graph is not part of this report. Its scope is declared,
this project does not match it, and an empty result is the honest answer. It is
mentioned only so the numbers above are not read as contradicting it.
