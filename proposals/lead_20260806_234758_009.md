# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Distribution channels: Homebrew, Snap, winget, Microsoft Store, Mac App Store**

*Project description:*
One place to decide how the app reaches users, because the five channels differ far more than
"publish a package" suggests and two of them constrain decisions that are otherwise irreversible.

## Where each one stands

**Snap and winget already have a workflow.** #283 added `.github/workflows/publish-stores.yml`,
triggered on release publication so it cannot break a release. Both build and attach their artifact
when credentials are absent and publish when they are present. Neither is switched on.

**Homebrew, the Microsoft Store and the Mac App Store have nothing yet.**

## The identifier problem, which gates three of them

#298 moves the project to `github.com/simetrixch` and #299 renames it to `gitopset`. A published
package identifier is effectively permanent in every one of these channels: `winget-pkgs` has no
rename, a Homebrew cask name is the install command users type, a Snap name carries Canonical’s
confinement grant, and store listings carry ratings and install bases that do not transfer.

So the sequencing is not a preference. Publishing under `flutter-gitui` / `kartalbas` before those
two issues land means every early user silently stops receiving upgrades when the rename happens,
and the abandoned manifests point at installer URLs that die with the old repository.

**Recommendation: land #298 and #299 first, then switch the channels on.** The work can be built
now; only the credentials need withholding.

## What each channel actually requires

**Homebrew (macOS, and the natural fit for this project).** A cask in a tap — either
`homebrew/cask` or an own tap, which is the pragmatic start since an own tap needs no review. The
cask points at the release archive and its SHA-256, both of which the release already publishes in
`latest-macos.json`… except that manifest is deliberately withheld today (#155). A cask also expects
the app to be openable, so it interacts directly with the signing question in #66 and #365: an
unsigned cask install lands the user in the same Gatekeeper dialog, just after a command instead of
a download.

**Snap.** Ready. Needs `SNAPCRAFT_STORE_CREDENTIALS`, a registered name, and Canonical’s approval
for classic confinement — the app reaches arbitrary paths on the filesystem and runs `git`, so strict
confinement is not an option. That approval is per name, which is another reason to settle #299
first.

**winget.** Ready. Needs `WINGET_TOKEN`. Manifests are generated from the published Windows archive.

**Microsoft Store.** Substantially more work than winget: an MSIX package, a Partner Center account
with its one-off fee, identity and capability declarations, and certification. Worth deciding
whether the audience justifies it at all, given winget covers the command-line install and a plain
download covers the rest.

**Mac App Store.** The most constrained. It requires the App Sandbox, which is a genuine functional
question for this app rather than a packaging one: a sandboxed app cannot freely read arbitrary
repository paths or execute the system `git`, both of which are the whole point. **This probably
cannot ship to the Mac App Store without redesigning how it reaches the filesystem and git.** That
assessment should be confirmed before any effort goes into it, and if it holds, the issue should
record the decision not to pursue it rather than leaving it open forever.

Note that Developer ID plus notarisation — what #66 built — is *not* the App Store. It is the
direct-download path, and it is what makes Homebrew and a plain download work.

## What is needed here

Decide the order and the scope: which channels are worth supporting, in what sequence relative to
#298/#299, and whether the Mac App Store is achievable at all given the sandbox. Then split the
actual work into per-channel issues; this one is the decision record, not an implementation ticket.
