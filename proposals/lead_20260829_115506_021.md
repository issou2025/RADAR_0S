# Project Proposal — Structural Drawings

## Project Understanding

**Fresh spec-kitty install is broken: unbounded typer>=0.24.1 resolves 0.27.2, which removed the private typer._click.exceptions.Abort it depends on**

*Project description:*
## Summary

A fresh `spec-kitty` install on office4 is **unusable** — every invocation aborts before any
command runs. Root cause is an unbounded `typer` dependency combined with spec-kitty reaching
into typer's private `_click` module.

**Symptom:** `spec-kitty --version` (and every other subcommand) exits with a traceback:

```
File ".../specify_cli/orchestrator_api/commands.py", line 73, in <module>
  _CLICK_ABORTS: tuple[type, ...] = (click.Abort, _typer_click_module.exceptions.Abort)
AttributeError: module 'typer._click.exceptions' has no attribute 'Abort'
```

**Observer:** Claude Code session, 2026-08-28, installing the toolchain on office4 (#910/#914)
en route to running missions there.

**Cost of doing nothing:** office4 cannot run spec-kitty at all, which blocks the entire point
of the migration — running missions on the faster machine. More broadly, **any fresh spec-kitty
install today is broken**; this is not office4-specific. Existing installs keep working only
because their resolved `typer` predates the break, so the failure is invisible until someone
installs on a new machine.

## Root cause

| | typer | spec-kitty |
|---|---|---|
| MacBook (works) | **0.27.1** | 3.2.6rc2 |
| office4 (broken) | **0.27.2** | 3.2.6rc2 |

`spec_kitty_cli-3.2.6rc2` declares `Requires-Dist: typer>=0.24.1` — **no upper bound**. A fresh
resolve picks up 0.27.2, in which `typer._click.exceptions` no longer exposes `Abort`.

`specify_cli/orchestrator_api/commands.py:73` depends on that **private** attribute. Private API
+ unbounded range = breakage on any upstream patch release.

## Upstream: predicted and closed

**Priivacy-ai/spec-kitty#1401** — *"typer 0.26+ compatibility path is unexercised (locked at
0.24.2)"*, **CLOSED 2026-05-31**, priority:P1. It said:

> "ADR `2026-05-28-1` and PR #1395 cite typer>=0.26 behaviour (click vendored as `typer._click`),
> but `pyproject.toml` floor is `typer>=0.24.1` and `uv.lock` resolves `0.24.2`. The compatibility
> shim + JSON-envelope smoke test run on 0.24.2; **the 0.26-specific failure mode is never
> installed/tested.**"
>
> "Suggested: add a CI matrix leg (or constraint test) that installs typer>=0.26 to actually
> exercise the shim, or reword the claim as forward-looking."

The predicted failure has now materialised in the wild.

## Note the pattern

This is the **same structural defect class as #920**, filed earlier the same day: *CI does not
exercise the version that actually runs.* There it is Python 3.11 in CI versus 3.12 on office2;
here it is typer 0.24.2 in the lock versus 0.27.x on a fresh resolve. Both produce green
evidence about a configuration nobody actually uses.

## Status

Per the spec-kitty workflow-fault detour protocol: diagnosis complete, local record filed
(this issue). Upstream #1401 is CLOSED, so the protocol calls for a recurrence comment plus a
maintainer safety-check mention — **pending Kent's copy approval before posting.**

No workaround applied. Pinning `typer==0.27.1` to match the working Mac is the obvious candidate
and is verifiable, but it is **improvised, not a documented known workaround**, so it is a
stop-and-decide point rather than something to apply silently.

## Options

**A. Pin `typer==0.27.1` on office4** — reproduces the Mac's working configuration exactly, which
version parity wants anyway. Unblocks missions on office4 immediately. Needs recording as a
deliberate pin so it is not mistaken for a clean install.

**B. Wait for an upstream fix** — leaves office4 unable to run spec-kitty, blocking the
migration's main purpose.
