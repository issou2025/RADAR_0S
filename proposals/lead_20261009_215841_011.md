*Project description:*
## Goal
When enabled, the consumer updater (`.github/workflows/update_workflows.yml`) verifies the attested release manifest before any consumer mutation and stops the whole run if verification fails. The flag defaults to off, so the PR changes nothing for consumers until it is turned on. It depends on the release workflows publishing the attested manifest and on `scripts/verify_release_manifest.py`.

## Scope
- New flag (provisional repo var / env `UPDATER_VERIFY_RELEASE_MANIFEST`, default `false`, read as `${{ vars.UPDATER_VERIFY_RELEASE_MANIFEST || 'false' }}` and defaulted again inside the step shell). Use the plan's name if it names one.
- In `update_workflows.yml`, add a step with a new id right after "Fetch latest workflow templates from coding-workflows@stable" (`steps.fetch.outputs.upstream_sha`) and before "Prepare immutable workflow wrappers" and every other step that writes into the consumer checkout. When the flag is on:
  1. Download the release asset (provisional `release-manifest.v1.json`) for the release whose tag peels to `UPSTREAM_SHA`, using `GH_PAT`. One release lookup plus one asset download (§14).
  2. Run `gh attestation verify <manifest> --repo shubhodeep1/coding-workflows` with the signer-workflow / source-ref constraints the plan specifies (at least: signed by this repo's release workflow). Verification uses the runner's `gh`, not code from the release checkout.
  3. Make sure the sparse upstream checkout contains every path the later steps read (extend the `git sparse-checkout set` call if needed), then run `verify_release_manifest.py verify` from the release checkout, whose own bytes the attested manifest covers. Pass `--expected-sha "${UPSTREAM_SHA}"` and a `--paths-file` listing the files the later steps read.
  4. On any failure: `::error::` with the `UPDATER_MANIFEST_VERIFY` line, set an output such as `verified=false`, and exit non-zero, so that no later step mutates the consumer checkout and "Commit and push updates" never runs. Keep the existing failure summary / Telegram behaviour.
  When the flag is off, log one line (`UPDATER_MANIFEST_VERIFY outcome=skip reason=disabled`) and continue exactly as today.
- Route every `${{ }}` value through `env:`. Do not rename existing steps, ids or outputs. The existing guardrail contract `tests/test_update_workflows_guardrails.py` (e.g. `test_fail_fast_validation_precedes_any_copy_mutation`) must keep passing; do not edit it (it is outside this issue's scope).
- New `tests/test_update_workflows_manifest_verify.py`: the verify step sits between fetch and the first mutating step; it is gated on the flag with default `false`; it calls `gh attestation verify` before the hash verifier; failure exits non-zero; no `${{ }}` is interpolated into `run:`. Register it in `.github/workflows/ci.yml`.

## Acceptance criteria
- With the flag unset, the updater behaves exactly as before (contract-tested).
- With the flag on, a missing asset, failed attestation or hash mismatch stops the run before any consumer file changes.
