# LONG-TERM ROADMAP — TRANSPORT V2 / INTERNAL-B-FIRST

## Owner direction

This roadmap supersedes the earlier assumption that Transport v1 is the final business model. It does **not** invalidate already-proven v1 behavior by itself; changes must be additive/migrated through reviewable tranches.

Current business model to optimize first:

- **A = shipper / factory / cargo owner**. A may have its own fleet. If A cannot cover demand, an A-side contact may send work to B and B may pay a commission/referral amount.
- **B = transport company using Nexagnet Transport**. **B is the only organization we control in the current stage.**
- **C = another tractor-trailer transport company**. C may run on behalf of B, or B may run on behalf of C, and C may also act as a referral/source of work.

### Stage policy

**INTERNAL B FIRST.**

For now:

- A and C have no portal/login/API requirement;
- A/C data and settlements may be entered manually by B staff;
- do not build inter-company network semantics before B's internal operational truth is stable;
- design A/C as counterparties with multiple roles so future integration does not require rewriting B;
- later stages may add organization identity, contracts, portal/API/webhooks and cross-company handoff.

# 0. Architecture principles

1. PostgreSQL remains **business truth**.
2. Hatchet may orchestrate durable async work/retries, but is not business truth.
3. AI may extract/classify/suggest; **AI does not authorize money, debt, payroll or fraud conclusions**.
4. Files/proofs must use the shared File Platform from #223; do not create a Transport-only blob subsystem.
5. Portable deployment work #224 remains independent; no Transport feature may require GCP.
6. Current hotfix/customer UAT work (#222/#92/#196) has priority over conflicting UI changes.
7. Avoid one-customer branches; this remains a reusable Transport vertical.
8. Build provider ports for external integrations: maps/tiles, device attestation, vision/OCR, telematics, fuel statement, toll/ETC, future A/C connectivity.
9. No claim that GPS fraud can be made impossible. The target is **multi-signal evidence + risk detection + audit**, not magical anti-spoofing.
10. Preserve historical financial immutability: correction/reversal/allocation, not destructive overwrite.

# 1. Target domain model — separate commercial work from vehicle movement

The current `Trip = origin + destination` model is insufficient for return legs, empty running and multi-order vehicle cycles.

Target concepts (exact names may change after R0 research):

```text
Counterparty / Organization
  roles: CUSTOMER | CARRIER | REFERRER | FUEL_SUPPLIER | OTHER

TransportOrder        = commercial obligation / who owes whom / freight price
VehicleRun            = one operational vehicle run/cycle
RunLeg                 = one movement segment
  loaded | empty/deadhead
  origin → destination
  driver/vehicle assignment history
  operational proofs
```

Examples:

```text
Run #R1
├─ Leg 1 HN → HP, loaded, linked to Order A-001
└─ Leg 2 HP → HN, empty/deadhead
```

or:

```text
Run #R2
├─ Leg 1 HN → HP, Order from A
└─ Leg 2 HP → HN, Order sourced from C
```

Required future metrics:

- total km;
- loaded km;
- empty/deadhead km;
- empty-km ratio;
- revenue and direct margin by order;
- direct operating cost by leg/run;
- margin by full vehicle cycle/run.

Do not migrate current Trip blindly. R0 must map every existing Trip/Fuel/Expense/Settlement relationship and design additive compatibility.

# 2. Operational Proof Platform — start/delivery become evidence, not buttons

Long-term target:

```text
StartProof
DeliveryProof
FuelProof
ExpenseProof
```

A proof should be able to contain:

- authenticated actor;
- trip/order/run/leg reference;
- server challenge/nonce;
- client capture time + server receive time;
- latitude/longitude;
- accuracy/speed/bearing where available;
- device/app integrity verdict;
- app version/device installation identity;
- image/file IDs from File Platform;
- content hash/integrity;
- geofence/risk evaluation;
- append-only audit event.

### Start / delivery UX target

Driver should not simply press `Bắt đầu` / `Đã giao` with no context.

At minimum the system eventually captures:

```text
START
→ location proof
→ optional/required photo depending tenant policy
→ server validation/risk signals
→ transition

DELIVERY
→ current location
→ delivery photo(s)
→ recipient/note where required
→ geofence/risk signals
→ transition
```

Risk flags do not automatically accuse/fine the driver. They create reviewable anomalies.

# 3. Geospatial technology direction

## Server

Preferred candidate: **PostGIS on the existing PostgreSQL** rather than introducing a separate spatial database.

Use cases to research/prove:

- station/pickup/delivery geofences;
- `ST_DWithin` radius checks;
- impossible-travel / distance calculations;
- route/path storage and query;
- loaded/empty leg spatial reporting;
- location indexes and retention strategy.

R0 must benchmark data volume before choosing sampling frequency.

## Maps

Preferred rendering direction: **MapLibre** (web + native-capable) with tile/geocoding provider behind configuration.

Do not hardwire Google Maps into the domain. Tile/geocoder/routing providers remain adapters/config.

## Location retention

Do not store 1 Hz GPS forever by default. Research:

- event-only capture (start/fuel/delivery);
- distance/time adaptive sampling during active run;
- high-resolution short retention + simplified long-term route;
- PostGIS LineString/point storage trade-offs;
- privacy/access/retention policy.

# 10. Negative Driver Fund balance = reimbursement payable, not salary

Business interpretation:

If Driver Fund is negative after approved expenses, the driver has spent personal money for the company.

Example:

```text
company advances      +5m
authorized expenses   -7m
balance                -2m
```

The 2m means **company owes driver 2m**.

Model it separately from wage:

```text
Wage accrual                 15m
Driver reimbursement payable 2m
Total cash disbursement       17m
```

UI/payment may combine them into one bank/cash payment, but accounting provenance must remain separate.

---

# 11. Payroll v2 — accrual is separate from payment

B may allow drivers to accumulate salary for several months and receive one large payment later.

Therefore separate:

```text
PayrollAccrual / Payslip
≠
Disbursement / Payment
```

Target concepts:

- monthly/period payroll accrual remains immutable when posted;
- unpaid balances carry forward;
- one payment may allocate across several payslips;
- same payment may include driver reimbursement, but allocation/provenance stays separate;
- partial payment is possible if business confirms;
- driver can see `earned`, `paid`, `remaining`, and reimbursement separately.

Do not relabel reimbursements as salary.
