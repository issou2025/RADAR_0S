### automation-37 (major) — `src_C/Vpc/Automation/AutomationTick.cs:690`
- Problem: An alive runner that cannot work raises no exception, so the whole authoring pipeline can stall with no email. RunnerHealthAsync alerts only when no runner exists (:666-683), when a heartbeat is stale (:690-700) or when the login is expiring (:701-709). The runner, on author_config_error, sends an `error` heartbeat and exits without claiming (tools/author-runner/src/runner.ts:319-323). It does this every hour, so its heartbeat is never stale, and the server stores state='error' with last_error (RunnerRoutes.cs heartbeat upsert) but never acts on it. No run is created, so no complete, runner_unavailable or batch-summary email can fire either. Round F makes this path more likely at exactly the next operation. F03 adds a new refusal, a tool surface without a matching bundleSha256 (authorConfig.ts:108-110), and the runner README says every pull now needs both tools rebuilt (README.md:114-128). An owner who rebuilds only the runner, or whose rebuild of tools/mcp-server fails, gets a silently idle runner. The only surface is the console Overview's runner row (OverviewTab.tsx:251, 266). The weekly digest's runner line shows only heartbeat and login times (EmailTemplates.cs:479), so it reads as healthy.
- Suggested fix: In RunnerHealthAsync, also select `state`, `last_error` and `last_run_at`. When a runner's heartbeat is fresh, state = 'error', last_error does not start with 'RUNNER_UNAVAILABLE' (usage-limit and hold states already sent a runner_unavailable email), and due queued items exist with no run started by that runner in the last 2 h, raise runner_stalled under a new dedupe key `exception:runner_stalled:{runnerId}:error:{date}`. Give its template variant a summary built from last_error, e.g. 'runner X is running but cannot work: author config: … (rebuild tools/mcp-server)'. Reusing the subkind means no migration. Add state and lastError to the digest's runner line. Add an AutomationTickTests case (an error heartbeat 1 minute ago plus a queued item gives one email, and a RUNNER_UNAVAILABLE last_error gives none), and add a runbook line under runner_stalled.
- Evidence: src_C/Vpc/Automation/AutomationTick.cs:646-711 (only stale / no runners / login_expiring); tools/author-runner/src/runner.ts:275-281 (bestEffortError sends heartbeat 'error'), :308-323 (author_config_error → error heartbeat, EXIT_FAILURE, no claim); tools/author-runner/src/authorConfig.ts:94, 108-110, 130-138 (the refusals); tools/author-runner/README.md:38-41, 114-128; frontend/src/features/automation/OverviewTab.tsx:251, 266 (console-only visibility); src_C/Vpc/Automation/EmailTemplates.cs:479 (the digest shows no runner state); grep over docs/runbooks/automation-operations.md finds no author_config_error.
- Verifier: Checked in code. RunnerHealthAsync (AutomationTick.cs:646-711) raises an alert in only three cases: no runner registered (:666-683), a stale heartbeat (:690-700) and an expiring login (:701-709).
