# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Reference sample views: one sample per type, drawn with that type, label = name**

*Project description:*
## Context

After the naming-standards renames (#93), the user wanted one reference ("sample") view per rule section in a workshared project model: line styles, text types, dimension types, filled region types (#77) and fill patterns. The views are named by rule section number. No `am-*` skill covers this, so the agent wrote every query and change by hand. The legend view for families is filed separately in #98.

The user's rule, in their words for each category: every type in use has one sample, the sample is drawn **with** that type, and the label next to it **equals** the type name.

## What happened

1. **Labels were fixed, but samples were wrong.** The first job only rewrote labels to the new names. The user then saw that many line style samples were drawn with `<Thin Lines>`, while the label named another style. 17 labels named styles that did not exist in the model at all. A label check alone cannot find this. The fix needed a check of the sample itself: its style or type must be the one the label names.
2. **Coverage was found by the user, one category at a time.** The user had to send a screenshot of the Line Styles dialog, then of the text type list, to show that many types had no sample. A coverage check per category (types in the model vs samples in the view) found the gaps at once when it was finally run: 4 text types, 4 dimension types and about 40 line styles had no sample.
3. **Some types cannot have a sample in a drafting view.** Spot elevation and slope types need model geometry. `<Area Boundary>`, `<Sketch>` and `<Invisible lines>` cannot be set on a detail line. White and mask line styles draw white, so their samples are hard to see. 23 fill patterns had no filled region type; the user chose "list them as text, create no new types".
4. **Scale breaks readability.** In the text sample view, a 2" title sample (one word, no spaces, so Revit cannot wrap it) made the view about 2 ft wide. At full-view zoom the 3/32" samples were about 6 pixels tall, so the user reported them as "not showing". A re-layout could not fix this. The agent explained it and gave the sheet scale that prints every sample at true size.
5. **Layout faults from scripts.**
   - A row pitch was smaller than the height of a text box at the view scale (at 1/4" = 1'-0", a 3/32" note box is about 1.25 ft tall), so labels overlapped.
   - A script that re-ran moved rows up onto the column headers and added one more header on each run. Two more runs were needed to repair it. The script was not idempotent: it measured from fixed offsets, not from the existing header.
6. **Live data vs a static view.** The agent planned sample views for families and view templates too. The user stopped this: "those are live content" that a schedule and the View Templates dialog already show, and a static view goes out of date. For parameters, the user accepted a table view only as a **dated snapshot** that is rebuilt by re-running the audit. The rule note now says which sections have no sample view and where to read them instead.

## Proposed change

A reference-view recipe (in the naming-standards skill proposed in #93, or with the swatch sync in #77), for every category:

- **Coverage check (read only):** types in the model vs samples in the view. Report types with no sample, samples of deleted types, duplicates, and samples whose own type or style differs from the label.
- **Fix samples first, then labels:** set the sample's type or style to what the label names (mapped through the rename table), then set the label to the current name. List labels that name a type that does not exist; never set such a sample to a default style.
- **Known "no sample" cases:** spot types, built-in line styles, patterns with no fill type, white styles. List them as text rows.
- **Layout guard:** compute row pitch from the real text box height at the view scale; place new rows relative to the existing headers; make each script safe to run twice; check overlaps inside the dry run.
- **Readability note:** when one view mixes very large and very small samples, warn the user and give the sheet scale.
- **Live vs snapshot:** do not build static views for data that Revit already lists live (families, view templates). When a static table is the only option (parameters), put the snapshot date in the view.

## Acceptance ideas

- On a view where a line style sample uses `<Thin Lines>` but the label names another style, the coverage check reports it.
- After the recipe runs, every type in use has exactly one sample of its own type, and every label equals its sample's name.
- Running the layout script twice gives the same result as running it once.

## Not verified

- Whether a tag or a legend view would be a better label source than text notes.
- The text size threshold at which a mixed-size view stops being readable.
