# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**audit_issue: agent-authored ledgers drift to an unparseable marker**

*Project description:*
## Symptom

An agent-authored `audit-meta` ledger can carry a marker form `audit_issue.py` cannot parse. When that happens the step-2 gate returns `decision=AUDIT, reason="unparseable-ledger"` — indistinguishable in the sweep output from a genuine above-threshold change — so the repo pays for a **full `hard`-tier (Opus) whole-repo audit every single week**, forever, while reporting as legitimately changed.

Found in three repos during the 2026-08-06 supervised run:

- **minecraft-bedrock-bot** — would have been `SKIP_SELF_FIX` (all 5 commits since `55a84fa` only closed its own audit issues). Repaired during the run.
- **local-llm-hub** — today's audit was a full re-audit that should have been a skip. Self-repaired when its own audit upserted the ledger at the end of the run.
- **gitlab-to-github-migrator** — **ledger issue #6 was created by this very run and was already drifted.** Repaired manually after the run.

That third case is the important one: it rules out legacy data as the explanation. The bug is in the **write** path, and it reproduces on a fresh first-ever ledger.

## Root cause

`skills/_lib/audit_issue.py:96` defines:

```python
_LEDGER_MARKER = "<!-- audit-ledger -->"
```

The parser expects a **closed** marker followed by plain-text `key: value` lines:

```
<!-- audit-ledger -->
last-audited-sha: 7e31411…
last-audited-at: 2026-08-06
rubric-sha: 6e6ea0b…
```

An agent hand-authoring a fresh ledger instead writes the far more natural-looking **open-comment block**, with the data *inside* the comment so it stays hidden in rendered markdown:

```
<!-- audit-ledger
last-audited-sha: 7e31411…
last-audited-at: 2026-08-06
rubric-sha: 6e6ea0b…
-->
```

That is what `gitlab-to-github-migrator#6` contained verbatim. Both forms hide the data from a human reader, and the wrong one arguably looks *more* correct — nothing at authoring time distinguishes them, and nothing at read time reports the mismatch as a mismatch.

## Why this is the same defect class as #560

The gate **fails open, expensively, and silently**. It cannot establish "has this repo changed?", and instead of reporting `unknown` it resolves to the most costly answer and labels it with the same `AUDIT` decision a real change produces. Per `global-CLAUDE.md`: *"Any check … that can fail to establish a fact must report that as its own state — `unknown` / `not confirmed` — never folded into the passing state."* An unparseable ledger is currently folded into "changed".

The 2026-08-06 digest catalogued five independent instances of this class in one run. This is one of them.

## Proposed approach

**Primary — the tool should own the marker, not the prose.** `audit_issue.py upsert --kind ledger` should construct the marker block itself from `--last-audited-sha` / `--last-audited-at` / `--rubric-sha` arguments (or a small JSON payload), so no agent ever hand-writes the delimiter. This is the same "enforce it in the tool, not in agent prose" conclusion `project-scaffolding#202` already reached for the fanout mandate, and which this run's `project-scaffolding#209` independently re-nominated as a fleet convention. A prose instruction that has now failed on three repos is not going to start working.

**Secondary — read defensively.** Accept the open-comment block form on parse and normalize it on the next write, so existing drifted ledgers self-heal rather than needing a manual sweep.

**Required regardless — never fail open silently.** `evaluate_repo` should surface `unparseable-ledger` distinctly from a genuine `audit` decision in the sweep JSON, and `fleet_audit_scan.py`'s plan line should name it. A full Opus audit triggered by a parse failure must be visible as a parse failure, not indistinguishable from real organic change.

## Acceptance criteria

- [ ] A ledger written through `audit_issue.py upsert` always parses back, without the caller supplying the delimiter.
- [ ] A ledger in the open-comment block form parses correctly and is normalized on next write.
- [ ] `unparseable-ledger` is reported as its own state in the sweep JSON and in the printed plan line, never merged into `to_audit` unannotated.
- [ ] A fleet-wide scan of every `audit-meta` ledger reports zero drifted markers.
