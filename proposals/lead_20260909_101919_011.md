# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[Feature]: Canvas Extensions for user-invoked workspace tools with AI handoff**

*Project description:*
### Problem or Motivation

Many useful developer workflows start with deterministic project inspection rather than AI reasoning.

Examples include discovering reusable UI components, listing API endpoints, inspecting dependencies, surfacing test coverage, or finding security issues.

Today, users can ask the OpenHands agent to discover this information, but that often requires the agent to explore the repository, read multiple files, infer project structure, consume tokens, and potentially repeat the same discovery in later conversations.

For tasks that can be implemented deterministically, a script or command can often produce the same information faster, more reliably, and without requiring an LLM.

What is currently missing is a user-facing bridge between these deterministic workspace capabilities and the OpenHands agent.

A useful workflow would be:

```text
User runs a workspace action
        ↓
Extension executes a deterministic script
        ↓
Structured results are shown in Canvas
        ↓
User selects a relevant result
        ↓
Open file or continue with AI
```

For example, a Flutter extension could discover reusable UI components and show:

```text
PrimaryButton
lib/shared/widgets/primary_button.dart
14 usages

[Open File] [Ask AI]
```

If the user chooses `Ask AI`, that exact component can be passed to the OpenHands agent as context for a task such as:

> Add a loading state while keeping existing usages backward-compatible.

The goal is not to introduce Flutter-specific behavior into OpenHands core. Instead, Canvas Extensions could provide a generic way for extensions to expose **user-invoked workspace actions backed by deterministic scripts**, with an optional handoff to the agent when reasoning or code modification is needed.

In short:

> **Let deterministic tools discover, let users choose, and let agents act.**


### Desired Behavior

Canvas Extensions should be able to expose **user-invoked workspace actions** inside Agent Canvas.

A workspace action should allow an extension to:

* Define a visible action for the active workspace.
* Execute a deterministic script or command against that workspace.
* Receive structured output from the execution.
* Render that output inside the extension UI.
* Associate individual results with workspace files or other relevant metadata.
* Let the user open a referenced file directly from the result.
* Let the user pass a selected result to the current or a new OpenHands conversation as context.

A typical interaction could look like:

```text
Project Tools
└── UI Components
      ↓
    [Run]
      ↓
Deterministic script executes
      ↓
Structured results
      ↓
PrimaryButton
lib/shared/widgets/primary_button.dart
14 usages

[Open File] [Ask AI]
```

If the user selects `Ask AI`, the selected result should be handed off to the agent with its relevant metadata preserved, for example:

```text
Selected workspace entity:

Type: UI Component
Name: PrimaryButton
File: lib/shared/widgets/primary_button.dart
Usages: 14
```

The user can then continue with a normal OpenHands task such as:

> Add a loading state while keeping existing usages backward-compatible.

The extension should own the domain-specific discovery logic. OpenHands core should remain framework-agnostic and only provide the generic capabilities needed for:

```text
User invocation
    ↓
Workspace execution
    ↓
Structured result
    ↓
Canvas interaction
    ↓
Optional AI handoff
```

The exact manifest schema, execution API, and rendering model can follow the existing Canvas Extensions and Agent Server architecture.


### Acceptance Criteria

* [ ] A Canvas Extension can expose at least one **user-invoked workspace action** for the active workspace.
* [ ] The action can execute a deterministic script or command without requiring the user to start an agent conversation first.
* [ ] The command executes within the current workspace and respects existing workspace/sandbox permissions and isolation.
* [ ] The extension can observe execution states such as running, success, and failure.
* [ ] Execution failures are surfaced to the user with a clear error message.
* [ ] The action can return structured output using a documented format.
* [ ] The Canvas Extension can render the structured results in its UI.
* [ ] An individual result can include a reference to a file in the current workspace.
* [ ] The user can open a referenced workspace file directly from the result.
* [ ] The user can select an individual result and send it to an OpenHands conversation as context.
* [ ] Relevant metadata from the selected result is preserved during the AI handoff.
* [ ] The agent can continue a normal OpenHands task using that selected result as its starting context.
* [ ] Domain-specific logic, such as Flutter component discovery, remains inside the extension rather than OpenHands core.
* [ ] Existing Agent Canvas behavior remains unchanged when no extension exposes workspace actions.
* [ ] At least one end-to-end example demonstrates the full flow: **run workspace action → display structured results → select result → open file or continue with AI**.

### Additional Context

This proposal is intended to build on the existing **Canvas Extensions** direction rather than introduce a separate plugin UI system.

The main use case that motivated the idea is a Flutter project where an extension can deterministically discover reusable UI components and expose them inside Agent Canvas. A user could then select a component and continue working on it with the OpenHands agent.

However, the capability is intentionally framework-agnostic. The same pattern could support:

* API endpoint discovery
* Dependency inspection
* Test coverage
* Static-analysis findings
* Security findings
* Architecture inspection
* Organization-specific developer tools

The proposed flow is:

```text id="0qm8kr"
Canvas Extension
      ↓
User-invoked workspace action
      ↓
Deterministic script / command
      ↓
Structured project result
      ↓
User selects an item
      ↓
Open file / Ask AI
```

I am intentionally not prescribing whether this should be implemented as:

* a new Canvas Extension API,
* a convention built on existing workspace/Agent Server APIs, or
* an extension of an existing tool mechanism.

The main question is whether this **user-driven deterministic discovery → AI handoff** workflow fits the intended direction of Canvas Extensions.

A small proof of concept using reusable UI component discovery could be used to validate the interaction model before introducing a more generalized API.
