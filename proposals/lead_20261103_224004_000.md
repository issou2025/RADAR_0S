# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Audit tables: dated snapshot vs live schedule, and a saved refresh script set**

*Project description:*
## Context

During a standards cleanup in a workshared project model, the user asked for audit tables inside the model: one for parameters and one for materials. Each table is a drafting view built from aligned text notes and thin detail lines, with a date ("snapshot, rerun to refresh"). Later the user said (paraphrase) that a full material snapshot was not needed, because an audit material takeoff schedule shows everything live. Then the user changed the decision again: keep the snapshot and rerun it often as part of the audit, because the table can say things a normal schedule cannot, such as action flags and comments. No `am-*` skill says when a snapshot table is right and when a live schedule is right, or how to refresh a snapshot.

## What happened

1. **The live schedule could not replace the snapshot.** The agent built a multi-category Material Takeoff (name, description, category, family and type, count, area, volume, as paint). The read-back showed only 3 materials, of about 200 in the model. Limits that the agent found:
   - a takeoff lists only materials that element geometry or paint uses; unused materials never appear;
   - materials used only through category or import-layer styles do not appear; materials used only inside nested families may not appear;
   - `Material: Class` is not a schedulable field;
   - "unused", "duplicate look" and "suggested action" columns cannot come from a schedule.
2. **A snapshot goes stale, so it needs a refresh path.** The first snapshot was written by one-off scripts. The user asked for a rerun as part of every audit. The agent saved the scripts as a set with a README:
   - `1_scan.py` (read-only `run_query`), about 5 minutes on a large model;
   - `2_build_rows.py` (CPython; builds the rows and a CSV; lists new names that no rule class covers);
   - `3_write_table.py` (`run_modify`; finds the view by name and rewrites it in place; dry run first).
   The rerun reproduced the earlier rows (one grammar change only), so the set is repeatable.
3. **Schedule placement.** The project browser groups views by two shared parameters that are bound to views and sheets, not to schedules. So the new schedule could not go next to the other audit views. The agent did not change the bindings.
4. **No picture of a schedule.** `capture_view` does not support schedules. The agent checked the schedule by reading its cells.

## Proposed change

Add a short "audit output: snapshot or live schedule" section (in `am-param-qa`, `am-material-audit`, or `am-revit-api-docs`):

- Use a **live schedule** when the answer is a count or a value that elements carry (quantities, which elements use X).
- Use a **dated snapshot table** when the answer needs things a schedule cannot hold: unused items, flags, duplicates, comments, suggested actions.
- Often keep both. The snapshot names the live schedule in its "How to read" note.
- Every snapshot ships with a saved scan / build / write script set, so the next audit refreshes the same view in place. The audit step list includes the refresh.
- State the limits of a takeoff before offering it as a replacement for a list.

## Acceptance ideas

- A request for "all materials with flags" gets a snapshot, not only a takeoff.
- A second audit run refreshes the existing snapshot view, with the same columns and a new date, from the saved scripts.

## Not verified

- Whether a schedule of the Materials category itself (not a takeoff) can list unused materials. The agent did not try it.
