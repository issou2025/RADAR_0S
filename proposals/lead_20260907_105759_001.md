# Agent-driven simplified modeling: rux MCP gateway + headless rendering + Blender (blender-mcp) workflow

## Goal

Evaluate and prototype an **agent-driven alternative to the geometric reconstruction pipeline**: an LLM agent with full access to ReUseX project data (via a new **rux MCP gateway**) drives Blender (via **blender-mcp**) to construct a simplified building model and a tagged component inventory — as an alternative/complement to the current planes → rooms → CellComplex/MIP → windows pipeline, whose results have so far been underwhelming.

Inspiration: OpenAI's [architectural visualization with Astra](https://developers.openai.com/blog/architectural-visualization-with-astra) — but note the reality check below: that workflow is an agentic `bpy`-code loop, not native 3D generation, which means the pattern is **model-agnostic and reproducible** with any strong agentic model. What we must build is the *harness*: data access, agent "eyes", and the Blender bridge.

## Research findings (2026-09, verified unless flagged)

### What Astra actually does
- GPT-6 Astra (2026-09-04) is a text+image → text agentic model. **No native 3D input/output** — no point clouds, no meshes.
- Its architectural showcase = Astra in a Codex environment writing Blender Python (`bpy`) in an iterative render-inspect-refine loop; export to UE5. Inputs were a text brief + reference images.
- Its 95.9% "BenchCAD" score is a *CAD code generation* benchmark (⚠️ not independently audited).
- Implication: the differentiator is not the model, it's the **loop**: structured scene evidence in → code actions out → rendered feedback in. We can build that loop around Claude (or any model) today.

### State of the art: agents building 3D scenes
- All successful systems (SceneCraft, 3D-GPT, Holodeck 2.0, BIMgent) use **iterative loops with visual feedback**; one-shot generation fails for architecture.
- **Multi-view renders are the proven interface for agent spatial grounding** (SPAZER 2506.21924, S-Agent 2606.20515, SpatialAct, Think3D): render 3–6 viewpoints → vision model reasons → acts → re-render.
- **No published system does LLM-agent scan-to-simplified-BIM end-to-end.** BIMgent (2506.07217) drives Revit's GUI from floor plans at 32% task success. Scan-to-BIM in industry remains DL-segmentation + parametric fitting + human QA (A-Scan2BIM: "assistive, not autonomous").
- **Our position is unusually strong for a hybrid**: ReUseX already extracts planes (normals/centroids), rooms (visibility graph + Leiden), instances, and component candidates geometrically. The agent doesn't interpret raw scans — it works from *structured geometric evidence* plus renders, and applies judgment where the MIP/heuristics currently fail (topology decisions, component classification, simplification choices).

### blender-mcp landscape
- **ahujasid/blender-mcp** (community standard, Blender 3.0+): scene inspection, object create/modify, materials, asset libraries, and — critically — **arbitrary `bpy` Python execution** (the escape hatch that makes everything else possible). Geometry import: FBX/OBJ/GLB/STL/PLY. No point-cloud tools (fine — see architecture: Blender never holds the raw scan).
- **Official Blender Foundation ↔ Anthropic connector** (2026-04, "Claude for Creative Work", Blender 4.2+/5.1+ — ⚠️ min version inconsistent across sources, verify): full `bpy` API access via Claude Desktop.
- Notable fork: **PatrykIti/blender-ai-mcp** — vision-assisted feedback loops, deterministic verification, layout macros; most relevant to architectural use.
- Known limits: no parametric constraint solver (exact wall layouts need explicit Python), boolean ops make messy topology, per-object round-trips get slow on complex scenes.
- Tagging: custom properties (`obj["guid"] = …`) via the Python escape hatch — sufficient for a tagged inventory.

### Exposing large 3D data to agents (MCP patterns)
- Reference architecture for MCP-over-BIM (arXiv 2601.00809): **progressive disclosure** — lightweight summaries as resources, queries as tools, geometry fetched on demand, *never raw point clouds in context*.
- Survey of existing MCP servers (Speckle, Revit ×4 incl. official Autodesk, Rhino/Grasshopper, QGIS): all expose metadata/queries/operations; **none expose raw point clouds** — server-side abstraction is universal.
- **No MCP server for point-cloud data exists off the shelf** — this gateway is novel but follows established patterns.
- C++ MCP SDK status: **no official SDK** (TS + Python only); community C++ options exist but lag the spec. The proven pattern for wrapping an existing native app (pyRevit precedent): **thin Python FastMCP server shelling out to the CLI.**

**Gaps:**
1. **No headless rendering.** `rux view` requires a display; no `--screenshot`/offscreen mode exists. This is the critical missing piece — the agent's "eyes".
2. **No MCP surface** anywhere in the repo.
3. Bindings expose component *counts/names* only — not full component geometry (`building_component` singular is C++-only today).
4. No write-back path for agent results (tagged model → ProjectDB `building_components`).

### Lessons from the Blender addon test (maintainer feedback, 2026-09)
The existing `apps/blender/` addon was a test and **not successful**: loading each sensor frame as an individual object makes Blender slow, and the desired editing controls could not be built into Blender's UI. Consequences for this design:
- **Blender holds only the simplified model being constructed** — never raw scan data, never per-frame objects. The agent sees the scan via server-side renders from the MCP gateway, not by importing clouds into Blender.
- At most ONE decimated reference cloud (or a GLB of detected plane patches) is imported for visual alignment, and only if the workflow proves to need it.
- Interactive *human* editing controls are out of scope for Blender — that belongs to the GUI workstream (#265). Blender is the **agent's modeling tool**, not the user's editor.

## Proposed architecture

```
┌────────────────────────── agent (Claude / any agentic model) ──────────────────────────┐
│   iterative loop: query evidence → view renders → model in Blender → verify → refine   │
└──────────┬─────────────────────────────────────────────────────┬───────────────────────┘
           │ MCP                                                 │ MCP
┌──────────┴──────────────────────────┐            ┌─────────────┴────────────────┐
│  rux MCP gateway (NEW)              │            │  blender-mcp (existing OSS)  │
│  thin Python FastMCP server         │            │  scene ops + bpy escape      │
│  wraps `rux` CLI (+ pybind11 later) │            │  hatch; custom-property      │
│  ── resources ──                    │            │  tagging; GLB import         │
│  project summary, label defs,       │            └─────────────┬────────────────┘
│  coordinate system, inventory       │                          │
│  ── tools ──                        │                 ┌────────┴────────┐
│  query_planes/rooms/components      │                 │  Blender        │
│  get_frame(color|depth|pose)        │                 │  simplified     │
│  render_views(cloud, viewpoints[])  │◀── NEW rux      │  model + tags   │
│  export_geometry(→ GLB)             │    render       └────────┬────────┘
│  analyze_quality / compare          │    subcommand            │ export GLB/IFC +
│  save_components(tagged inventory)  │◀─────────────────────────┘ inventory JSON
└──────────┬──────────────────────────┘   write-back
           │ subprocess / bindings
     ProjectDB (.rux)
```

**Design rules:**
1. **Progressive disclosure**: summaries → queries → renders → geometry exports. Raw clouds never enter agent context.
2. **The gateway is a thin adapter** over existing `rux` capabilities (`get`, `info --json`, `analyze`, `export`, new `render`). New capability goes into `rux`/`libs/reusex` first, gateway second — consistent with the library-first rule and the #265 contract philosophy.
3. **Agent evidence package** per session: plane inventory (normal/centroid/extent/label), room graph, instance/component candidates with bboxes + confidence, floor-plan-style top-down render, elevation renders, quality metrics. This is "as much data as possible" in *useful* form.
4. **Round-trip validation**: after the agent builds the simplified model, export it and compare against the point cloud (`analyze accuracy`-style distance metrics) — gives the loop an objective error signal, not just visual judgment.
5. **Output contract**: simplified model (GLB/IFC + Blender file) + tagged inventory written back to `building_components` (guid-linked, `confidence` field marks agent-generated entries) so downstream export (Rhino/Speckle/CSV/materialepas) works unchanged.

## Phases

- **Phase 0 — Spike (manual, no new code)**: hand-run the loop once. Export data with existing commands (`rux info --json`, `rux get components`, `rux export ply` + decimation, screenshots from `rux view`), drive Blender manually via blender-mcp with Claude, build one room's simplified model with tagged components. **Deliverable: a written assessment — does agent judgment actually beat the MIP pipeline on a real scan?** Kill or continue based on this.
- **Phase 1 — Agent eyes**: `rux render` subcommand — headless multi-view rendering (offscreen VTK/EGL, or a minimal custom rasterizer if VTK offscreen fights Nix) of clouds/meshes/labels to PNG: top-down orthographic ("floor plan"), 4 elevations, N perspective views; camera params CLI-controllable. Also useful independently (CI artifacts, docs, GUI thumbnails).
- **Phase 2 — rux MCP gateway**: Python FastMCP server (new `tools/rux-mcp/` or `bindings/mcp/`), wrapping `rux` subprocess calls; resources + tools per the diagram; Nix-packaged. Enable/extend pybind11 bindings where subprocess overhead hurts (bulk queries, full component geometry).
- **Phase 3 — Blender bridge + workflow**: evaluate community blender-mcp vs. official connector vs. blender-ai-mcp fork; GLB hand-off of detected plane patches / reference geometry; custom-property tagging convention (`reusex_guid`, `reusex_type`, `reusex_material_guid`); scripted scene-setup template (units, coordinate system matching ReUseX).
- **Phase 4 — Closed loop + write-back**: `save_components` write-back tool (schema: agent-generated components with provenance flag); round-trip validation metric; document the full agent playbook (prompt template + evidence package) so any agent session can run it.
- **Phase 5 — Evaluation**: same scans through (a) existing geometric pipeline, (b) agent workflow; compare component inventory precision/recall vs. manual ground truth, geometric accuracy, wall-clock and token cost. Decide the roles: replacement, fallback, or QA layer.

## Open decisions
- Gateway placement & packaging: `tools/rux-mcp/` Python package vs. under `bindings/`; stdio vs. HTTP transport (stdio first — local single-user, matches Claude Desktop/Code).
- Rendering backend: PCL/VTK offscreen (dep already present; EGL headaches on Nix possible) vs. minimal custom point rasterizer (more work, fully controlled) — spike in Phase 1.
- Blender connector choice (community/official/fork) — Phase 3 evaluation.
- Whether Astra specifically is worth testing as the modeling agent (API access, $10/$50 per M tokens) vs. Claude via Claude Code + MCP — Phase 5 comparison candidate.
- Relationship to ruxd: none for now (stays headless per #265); if the gateway ever needs remote operation, it becomes another client of the #265 API contract.
