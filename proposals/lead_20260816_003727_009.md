# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Testing layer 3: multi-instance scenario tests over the in-app MCP surface**

*Project description:*
Layer 3 of #217. Layer 1 (client↔server, headless) landed in #219.

## What

Drive **two real app instances** against one server and assert on both sides of an interaction.

Voice, presence, and typing are the features where the interesting bugs are inherently multi-process: who hears whom, who sees the speaking indicator, what happens when one side drops. A single test process can't see them, and layers 1–2 don't either.

## The control surface already exists

`lib/features/developer/services/mcp_tools.dart` (~996 lines) exposes ~40 tools over a loopback JSON-RPC/MCP server (`mcp_server_io.dart`, `HttpServer.bind`), enabled from developer settings: `navigate`, `open_dm`, `open_settings`, `open_voice_view`, `join_voice_channel`, `leave_voice`, `send`/`edit_message`, `delete_message`, `add_reaction`, `list_messages`, `list_members`, `get_current_state`, plus role/ban/kick/moderation tools.

This is the Flutter equivalent of the Godot client's `client_test_api.gd`, and it means no synthetic input is needed — no xdotool, no fake clicks. A test harness launches two app instances on different MCP ports and speaks JSON-RPC to both.

## Scope

- A launcher that starts N app instances with developer mode + MCP enabled on distinct ports, pointed at one server-fixture instance.
- A thin Dart client for the MCP surface.
- First scenarios: A joins a voice channel, B sees A in it; A mutes, B sees the mute; A types, B sees the indicator; A goes offline, B's presence updates; A sends a DM, B's DM list surfaces it.

## Notes

- Prior art: #45 (merged, Godot-era, GDScript) did multi-instance app testing with login and input simulation. The approach carries over; the code doesn't.
- Voice scenarios need either a real LiveKit (`docker-compose.yml` runs one in dev mode) or `ACCORD_TEST_MODE=1`, which relaxes the SFU requirement for the signalling paths.
- Heaviest of the three layers — worth doing after layer 2 proves the fixture holds up under a real app process.
