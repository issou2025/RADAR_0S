# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[FEATURE REQUEST]  Jam: collaborative local-network listening sessions (shared queue, host-authoritative)**

*Project description:*
## Summary

Add **Jam**: a local-network collaborative listening session. One Namida instance
is the host and stays the only real player; other devices join over Wi-Fi (QR or
join code, mDNS discovery optional), see now playing and the queue, search the
host's library, and add or reorder tracks according to permissions the host sets.

The key point: this is a **remote-control and shared-state feature, not a new
player**. Every guest command goes through the existing `Player` API, so the
notification, media session, Android Auto, history and statistics keep working
unchanged. No new audio engine, no second queue, no cloud service.

Multi-phone synchronized audio (several phones playing the same audio at the same
acoustic time) is deliberately **not** part of this request. It is a separate
real-time audio problem and is filed separately as #1134.

I researched this against current `main` (`6.4.2-beta+260802156`) before writing.
Everything below is a suggestion for the maintainer to accept, change or reject,
not a demand for a specific implementation.

---

## Is your feature request related to a problem? Please describe.

When several people are in the same room, one phone plays and everybody else has
to ask the person holding it to queue something. Spotify solved this with Jam;
there is no equivalent for a local library player. Namida already has everything
needed except the session layer: a real queue, a search index, remote servers,
and a single clean playback authority.

Namida already uses the phrase "Party Mode" for the mini player visual effect, so
this feature needs a different name (Jam, Group Session, Listening Party) or an
explicit rename of the visual one.

## Describe the solution you'd like

### MVP scope

Host:
* start a Jam, show QR / join code
* optional LAN discovery
* see participants, remove a participant
* choose the guest policy (what guests are allowed to do)

Guest:
* discover or scan, join
* see now playing and the queue
* search the **host's** library
* add a track
* leave

Deliberately excluded from a first version: internet relay, guest-local file
uploads, automatic host transfer, speaker sync, CRDTs, accounts, chat.

### Architecture that fits the current code

```
network
  -> JamTransport
  -> JamSessionController   (authorization, revision check)
  -> JamPlaybackCommandAdapter
  -> Player
  -> existing Namida playback stack
```

and back out through a `JamPlaybackStateProjector` that observes canonical state
and broadcasts it, so changes made from the notification, headset, Android Auto
or the host's own UI reach guests too.

Suggested module layout, following the existing feature-specific controller
subdirectory precedent:

```
lib/controller/jam/{model,protocol,playback,catalog,transport,discovery,security}/
lib/controller/platform/jam_discovery/{base,android,windows,linux,ios}
lib/ui/pages/jam_page.dart   (RouteType.PAGE_jam)
test/jam/
```

### The three problems that actually need design decisions

**1. Media identity.** `Track.key` is the file path, and a path must never go on
the wire: it may not exist on the guest, differs across platforms, leaks storage
layout, can encode server credentials, and does not distinguish repeated queue
entries. Issue #1122 (closed as a duplicate of #621) is the same path-centric
identity problem seen from another angle.

Proposal: source-scoped IDs, resolved host-side only.

* YouTube: `youtube:<videoId>`, portable
* host local files and remote-server items: `hostmedia:<opaque session token>`,
  mapped to the real `Playable` inside the host process only

Guests browse the host catalog, so they never need a portable fingerprint. The
existing `MusicWebServer` resolver stays the credential boundary: the protocol
carries a `JamMediaDescriptor` (title, artists, duration, artwork token), never a
Jellyfin/Subsonic/WebDAV URL or auth header.

**2. Queue mutation on an index-based queue.** The queue is a list of `Playable`
with duplicates allowed and index-oriented operations. A remote client cannot
safely say "remove index 7". Proposal: host-authoritative state with a session
revision; every mutating command carries `expectedRevision` and a stable
`JamQueueEntryId`; the host validates, calls the normal `Player` queue API, takes
the result as canonical, bumps the revision and broadcasts. Entry IDs live in a
Jam-only sidecar (`JamQueueMirror`), never as new fields on `Track` or the
persisted `Queue`. If a local mutation makes ID reconciliation ambiguous, the
host regenerates affected IDs and sends a full snapshot. Explicit queue mutation
events from the handler or `QueueManager` would make this exact rather than
diff-based, if such hooks exist or can be exposed.

`beforeQueueAddOrInsert()` and the `mixedQueue` local/YouTube separation must be
preserved: a remote add is just an add, so the existing rules apply unchanged.
Jam state must stay out of `QueueController`, which is about persisted and
restored queues; when the session ends its metadata should vanish unless the user
explicitly saves the queue.

**3. Security.** "Same Wi-Fi" is not authentication. Minimum: high-entropy
ephemeral session secret, explicit join approval, authenticated channel, no
secrets or paths in discovery packets, frame size limits, rate limits, schema
validation, message IDs for idempotency. The pairing secret or public-key
fingerprint travels in the QR, not in the mDNS TXT record. Crypto behind a
`JamSecureChannel` interface rather than hand-rolled inside business logic. The
current `network_security_config.xml` only allows cleartext for `127.0.0.1`, and
that should not be widened to the whole LAN.

### Platform notes

* Android discovery: native `NsdManager` / DNS-SD, service type `_namida-jam._tcp`,
  TXT limited to protocol version, short session id, optional display name,
  capabilities. QR and a manual code as fallbacks, because mDNS fails on
  AP-isolated, guest and enterprise Wi-Fi.
* Android 17 local network permission: at `targetSdk <= 36` LAN access is still
  implicit via `INTERNET`, so nothing needs declaring today, but at 37+ broad
  access needs `ACCESS_LOCAL_NETWORK`, and there is a privacy-preserving NSD
  service picker for user-selected services. Worth hiding behind something like
  `ensureLocalNetworkAccess(mode)` now rather than sprinkling SDK checks later.
  Never trigger it at app startup.
  https://developer.android.com/privacy-and-security/local-network-permission
* iOS, if ever: `NSLocalNetworkUsageDescription` plus `NSBonjourServices`, and
  Apple explicitly recommends prompting on a user-understood action.
* Kotlin side: keep the NSD bridge in its own class, not in `NamidaMainActivity`,
  which is already broad.
* Startup: do not advertise a host session until `Player.initializePlayer()` has
  run and the latest queue is restored, otherwise guests see a false empty queue.
* Lifecycle: the session lives while the app lives. Do not abuse the media
  playback foreground service to keep an idle LAN server alive. If the host dies,
  the session ends; no automatic host election, since a replacement host may not
  have the media or the server credentials.
* Permission revocation, Wi-Fi change and Jam failure in general must never break
  normal local playback.

### Guardrails I would suggest for any PR

`Player` stays the playback authority. No Jam logic in widgets. No Jam fields on
`Track` or the persisted `Queue`. Transport never decides queue policy. Native
code provides primitives, not session state. All mutating commands revision
gated. No raw paths or credentials on the wire. `audio_handler.dart` is ~2.9k
lines already, so it should get at most a canonical-queue-mutation hook, not a
session controller.

### Suggested PR sequence

Not one large patch:

1. protocol and domain models plus tests, no networking
2. Player adapter, state projector, in-memory host, fake transport
3. real transport (reliable stream, reconnect, heartbeat, limits)
4. pairing and security
5. Android NSD and permission handling
6. UI

The protocol deserves a `docs/jam_protocol_v1.md` so it is reviewable without
reading Flutter code, and it should carry a version from day one with capability
negotiation, since mixed beta versions will meet each other.

## Describe alternatives you've considered

* **A second player mirroring `Player` on each guest.** Rejected: it duplicates
  queue semantics, breaks the media session and notification, splits history and
  listening stats, and doubles maintenance.
* **A network queue that periodically overwrites Namida's queue.** Rejected: it
  fights `beforeQueueAddOrInsert()` and the mixed-queue rules and races with
  local edits.
* **CRDTs.** Unnecessary: a listening session has a natural authority, the device
  that is actually playing.
* **Reusing Namida Sync's model** (UDP multicast, plain local HTTP, fixed port
  53317). Good precedent that LAN discovery is accepted in this ecosystem, but
  file transfer and a live session have very different security and lifecycle
  requirements.
* **Building this on top of casting (#914)** or on cross-device sync (#621).
  Different problems: #621 is data replication between a user's own devices,
  #914 is protocol-level casting to a renderer. Jam should not be entangled with
  either.

## Additional context

Related existing issues: #621 (cross-device sync), #1122 (closed duplicate,
shows the path-centric identity pain), #914 (casting).

Questions where I would rather have your answer than guess:

1. Would a Jam feature be accepted in principle?
2. Preferred user-facing name, given the existing Party Mode?
3. Android first, or all currently supported platforms?
4. Is a dedicated `lib/controller/jam/` subtree acceptable?
5. Can `basic_audio_handler` be changed if stable queue mutation events turn out
   to be needed, or should this stay diff-based in app code?
6. Should guest search expose remote-server tracks and YouTube items by default,
   and how should `mixedQueue` policy be presented to guests?
7. Should guest-requested tracks count in the host's history? (I would say yes.)
8. LAN only for the foreseeable future?

I am happy to do the work in the sequence above if the direction is acceptable,
starting with protocol plus tests so the architecture can be reviewed before
anything touches playback. The public `test/` directory currently holds only the
default widget smoke test; a distributed protocol should not ship without
deterministic tests, so I would bring those with it.

## Apps

* **Spotify Jam** (https://support.spotify.com/uk/article/jam/): host and guest
  model, shared queue, host review and removal of guests, optional guest control.
  The session semantics are worth copying; the shared cloud catalog is exactly
  the part Namida cannot assume, hence host-catalog browsing.
* **SoundSeeder** and **AmpMe**: same product space, but their focus is the
  synchronized audio half, which is the separate request.
