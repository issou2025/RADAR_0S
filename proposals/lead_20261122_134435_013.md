## Project Understanding
You need assistance with: 
**Release step for apps: deploy ledger, rollback line, changelog draft**

*Project description:*
## Pain

There is no release step for apps. `bin/release.sh` only serves ai-kit itself. In the apps surveyed, nothing records what is live, so the rollback target and the suspect commit are guesswork. No app has a written rollback line, and most changelogs are missing or stale.

Source: user feedback on the kit-workflow page, 2026-11-22. Survey and research: see the comments (release survey across apps, external research and wider survey).

## Proposed delivery

Three parts, in order. Build them in one app first, per the harvest-only-proven rule.

1. Deploy ledger. Each deploy records the SHA, the date and the smoke result, as a `deploy/<date>-<sha>` tag or a REVISION or ledger file.
2. One written rollback line per app.
3. Changelog draft. Trial `git cliff --unreleased` in one Laravel app and one Astro app, then rewrite the output for humans. The user-facing rewrite prompt in ComposioHQ's `changelog-generator` is worth borrowing. the SaaS app's `create-release-notes` skill is prior art.

Pilot app: the Laravel app (decided 2026-11-22). Ledger is an app issue, changelog step is an app issue. Start by asking the system lead session how system releases today. Use a real system deploy as the first worked example. Then run /ai:harvest to move the result into the kit.

Any deploy keeps waiting for the user's explicit go (deployment-on-demand rule). A per-app standing mandate is tracked separately in #310.

## Why-not (now)

- Customer announcements and visuals stay out for now. Optional for a solo dev.
- No semver for web apps. Local, deliberate deploys are fine as they are.
- Skip release-please, semantic-release and changesets unless semver is adopted. They need CI and are semver or npm centred.
- The work needs its own grill and plan before building.
