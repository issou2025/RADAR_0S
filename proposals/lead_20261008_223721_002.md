# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**AWARE CLI upgrade changes the signed reader identity under a locked model-reference-reader (lock 0.8.0 → packages signed 0.8.1/bridge 0.5.4 in v0.156.1)**

*Project description:*
## What happened

A FloLess app locked to `model-reference-reader@0.8.0` started emitting packages signed as **reader 0.8.1 / bridge `aware-connection-reader@0.5.4`** the moment the machine's AWARE CLI moved to v0.156.1. The lock didn't change, and the run did execute the 0.8.0 agent bundle. Every released FloLess (≤ 0.151.0) verifies the packager generation against the readers it has tested (0.7.3, 0.8.0), so **every Revit import on every released client with AWARE 0.156.1 now fails** after a full cloud conversion. That is a production outage, seen 2026-10-08.

## Evidence (real run, not a repro by reasoning)

- `~/.aware/apps/revit-model/revit-model.lock` (compiler 0.156.1) pins `model-reference-reader: 0.8.0` @ `sha256:536e2c40…bc99ad3`. `agent-store-control/refs/model-reference-reader/536e2c40….last-needed` was touched by the run, so the 0.8.0 bundle is what ran.
- The run's `node-output` (`~/.aware/logs/revit-model/default/7392db0c-905d-4339-ae88-b010bf4abb57.jsonl`) carries:
  `packagePreimage.packager = {"agent":"model-reference-reader","version":"0.8.1","bridgeBuildId":"aware-connection-reader@0.5.4",…}`
- `~/.aware/bridges/aware-connection-reader.version` = `0.156.1`, refreshed at the CLI upgrade.
- Cause in source: `cli-connection-reader/model-snapshot.mjs` stamps `version: packageManifest.modelReferenceReaderVersion` and `bridgeBuildId: ${name}@${version}` from the **bridge's own** `package.json`. #656 (`86944df04`, first released in v0.156.1) bumped that file to `0.5.4` / `0.8.1`.

## Why it is AWARE's

The lock is AWARE's determinism promise ("build once, run forever"). The bridge is global to the CLI and unpinned by the lock, so a CLI upgrade silently changes both the code that produces a locked app's output and the provenance it signs. Here the provenance also names a reader version (0.8.1) the lock never selected. A consumer that verifies what it reads can only follow by shipping a release first, and released clients cannot.

## Expected

A lock that pins `model-reference-reader@X` keeps producing reader-X packages (same packager identity, same bridge behaviour) across CLI upgrades. If that is impossible, AWARE should refuse to run the lock and name the drift, not sign a different identity.

## Options (owner's call)

1. Version the connection-reader bridge with the agent bundle: the lock pins the bridge build, and old builds stay side by side like `agent-store-v2`.
2. Have the bridge stamp the identity of the locked agent it serves, and keep that generation's behaviour behind it (frozen per reader version).
3. Release gate: an AWARE release that changes `cli-connection-reader/package.json` `version`/`modelReferenceReaderVersion` does not publish until the latest released consumer (`@floless/app@latest` on npm) accepts that identity.

Consumer side: floless.app#2098 accepts 0.8.1/0.5.4 on master, but not in any release yet. Tracking: pawellisowski/floless.app#2124.
