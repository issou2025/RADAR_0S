## Product contract — REQUIRED

### 1. New restaurant / branch / website onboarding
- Creating a new restaurant/branch provisions the required backend web-order channel, eligible order-inbox/dispatch configuration and defaults automatically. Once the restaurant completes normal storefront publishing, menu and pickup/channel setup, its website ordering works immediately **without a developer manually executing SQL, editing secrets, adding restaurant slugs/IDs, deploying Edge functions, editing an allowlist, or obtaining a pilot slot**.
- Ordering, background alerting (for opted-in authorized POS devices), and normal order handling are standard features of the platform, not feature flags switched on one restaurant at a time. Keep practical admin toggles per restaurant/branch for intentional **pause/unpause ordering**, sound preferences, printer setup and emergency disable. Defaults should be ready for service upon completed setup.
- No `mapsburger` hardcoding in general-purpose web-order submission, order status, eligibility, notification registration, dispatcher, site, printer routing or POS inbox. Replace restaurant-specific logic with tenant/branch scoped configuration and data-driven policies. Where legacy Maps Burger special routes must remain, preserve compatibility during migration.
- If a merchant has not published a menu/site or does not have an operational printer, the system should guide setup without silently pretending those prerequisites exist. A missing printer must not drop a web order, and must not trigger duplicate printing when one is added later.

### 2. Newly paired POS devices — ZERO additional rollout steps
- After a new legitimate POS is created/paired with a restaurant+branch and the employee signs in (valid device/PIN session), it automatically becomes eligible to see and accept that branch's website orders and participate in the normal notification/printing workflow. No static UUID allowlist or manual SQL needed, and no reliance on the CURRENT five Maps Burger UUIDs.
- Keep device lifecycle/tenant/branch/account authorization: unpaired/revoked/expired/other-tenant POS do NOT receive private orders, push tokens, print leases or acceptance power. Dynamic eligibility comes from currently valid pairing, device/session/role and branch scope, not caller-supplied IDs.
- All eligible online POS devices see synchronized request state; one acceptance wins atomically, other POS refresh, and only ONE kitchen print/claim is created and delivered through the restaurant's configured print/KDS route. Never broadcast the same print job to every tablet.
- Installing a current signed POS build and granting Android notification permission can require **one-time user/device action**. This is standard onboarding, not a developer-operated policy rollout. Honor per-device opt-in/OS permission and allow user to disable notifications. Upon valid onboarding, registering or renewing its FCM token should need no manual Supabase SQL, secret toggles, pilot UTC values or calls to the developer.

### 3. Permanent background alerts for all restaurants
- Build a normal **always-on** FCM notification path (new pickup order; terminal accepted/rejected/expired and safe cancellation where supported), per tenant/branch with strict isolation. One production-wide initialized service and independent emergency kill switch, not a 30-minute pilot mode. The current max-30-min gate must not block standard production; retain an optional bounded pilot mode if useful, but do NOT require pilots to operate every shop or day.
- Refactor ALL Maps Burger + HOME-specific alert gates including the `salehtab`-only `app.pos_order_alert_registrations` CHECK and registration function. Eligibility must be scoped dynamically by authenticated context and existing tenant/branch membership, preserving RLS, privileged function ACL, FCM token ownership, generations, opt-in, revocation, expiry and registrations/deliveries history.
- Add reliable, authenticated Cron/queue fallback for best-effort post-commit instant wake failures, with bounded retry/expiry, leases/idempotency, duplicate suppression and sane global/tenant quotas. Do not use stale deployment env or recurring 30-minute secret workarounds. A client/site submission succeeds even if FCM is unavailable.
- Current MAX-8-hour / PIN expiry requirement is incompatible with 'leave it running all day' if not refreshed: design an easy legitimate shift/session renewal/foreground re-registration UX, without forging or bypassing employee authorization.

### 4. Order acceptance + kitchen printer/KDS
- Generalize legacy Maps Burger `app.mapsburger_web_order_rollouts`, `app.pos_accept_web_order`, printer target-only lease and kitchen-print containment integration into **per-tenant/branch dynamic routing**. A fresh valid web order should be accepted by any currently authorized POS for the branch and printed/surfaced exactly once by its configured workflow; do not require a per-device rollout revision.
- Preserve existing kitchen safety semantics: deterministic single-winner acceptance, exact print target, no replay after expiry, immutable closures/holds, safety when two tablets race, and ordinary POS/KDS operations unaffected. Do NOT unlock or replay any legacy blocked dispatches by broadening the allowlist.
- If more than one eligible POS is online, they should receive order notifications, but physical printing occurs once according to the restaurant's configured printer/print-owner or kitchen workflow. Offline POS sync must not reprint the job.

### 5. Default behavior and operation
- No more manual per-restaurant `POS_ALERT_PILOT_START_UTC/END_UTC`, `POS_ORDER_ALERTS_ENABLED`, manual device UUID lists, or repeated 15-minute tests in normal production operation. Production-level kill switch remains possible for emergencies and merchant admin can pause their own ordering when closed.
- All relevant POS devices join automatically when paired; not every untrusted device on the internet. Do not weaken auth, RLS or cross-restaurant data isolation under the banner of convenience.
- Do not confuse 'website operational by default' with credit-card acquiring/payment integration; payments remain an independent feature requiring merchant setup and compliance.
- Ensure new restaurant published site, store data, dashboard availability, online inbox and intended KDS/printer workflow are wired and tested end to end.
