# Project Proposal — Static Website

## Project Understanding
You need assistance with: 
**v0.4.0 mini apps: a sealed page, its own data, and an agent that works on the same data**

*Project description:*
A **mini app** is an artifact (an `html`, `widget` or `react` page) plus a declared manifest and its own data, hosted by the gateway. Its page runs sealed, like every untrusted page PersonalClaw serves, and reaches its data through one checked message channel to a trusted host shell, which forwards allowed requests to one gateway service. The agent and automations reach the same service through tools and action providers, so all three read and write the same data under one set of rules and one change log. A mini app is promoted from a draft by an owner act with consent bound to what it may do and to the exact code that was checked; it can be pinned and opened anywhere the dashboard runs, and it graduates into a local app when it outgrows its rung.

**Principles, each held by tests**
1. **The seal holds.** The page never gets the network, the owner's session, `/api`, another window or shared storage; it gets one mediated channel.
2. **Data outlives deployment.** Undeploying, unpinning, a new code version, an artifact version prune or a slug reuse never touch data; only the mini-app delete does, after offering an export.
3. **The agent is a first-class user.** Anything the page can do to its data, the agent and automations can do, through the same service and the same change log.
4. **Every rung is a decision.** Promotion, every capability widening and graduation are owner acts with consent.
5. **Local and backed up.** Everything lives under the home, is declared in the durability inventory, and round-trips every backup path.

**The design in one screen** (the full design, threat model and decision records are posted in this issue's comments; the first task commits them to `docs/architecture/mini-apps/` and `docs/adr/`)
- Identity: a mini app has its own id (`ma_<ulid>`); nothing about it is keyed by the artifact slug, which is reused after delete. Data lives in `<home>/miniapps/<id>/` (`miniapp-data.db`, `miniapp-draft.db`, `consent.json`, `draft/`, `checkpoints/`, `assets/`, `links.json`, the active `manifest.json`, `bundles/v<N>/` and `versions/v<N>/`, `gate/`), never under the artifact's folder; the registry is `<home>/miniapps/miniapps-index.db`.
- Page: served under the v0.2.0 serving seal (an opaque origin however it is opened), its assets sealed too; framed by one sealed-page host that this theme builds and app pages running in their own origin (#3874) adopt, speaking protocol 1 over one `MessagePort` per document (a fresh one for every new document, never bound to the frame); every request checked against the promoted manifest, with each method's own size and time limits and channel-wide rate and in-flight limits.
- Service: one entry point `service.call(id, actor, method, params)` over one SQLite file per mini app, guarded by an authorizer with three policies (caller SQL, migration steps, the platform's own SQL), a statement timeout, limits and one storage budget; every write by any actor lands in `_changes` through generated triggers that read a main-schema `_actor` row, a REPLACE's hidden delete included; live updates through a subject-bearing frame on the existing socket.
- Agent: `miniapp_*` tools as thin shims to the service (both runtimes reach one service); rows reach the model fenced; ordinary writes run unasked under one narrow grant the operator ceiling bounds; a bulk write, measured over the whole request and the actor's window, waits for the owner (the agent's) or for a confirmation the host draws (the page's); schema changes run only on a draft store and reach live data by promoting a new version; a private chat reads mini-app data but never writes it or creates a mini app; automations through `miniapp-import`/`-export`/`-write` providers and schedules frozen by the consent.
- Lifecycle: draft → promoted (a quality gate on sample data only, then consent sealed over the capability projection and bound to the bundle digest, checked on every request) → active, with pause, narrowing, versions, Iterate on a draft copy, checkpoints, rollback, graduation and a trash-backed delete with Restore.

**Decisions with recommended defaults** (each is a value in one place; change it before its task starts)
- Bulk threshold: 25 rows over the whole request and the actor's window (the agent's turn, the page's last minute), kv entries and documents included; or one statement deleting every row of a table that held at least 2 rows, or updating every row of one that held at least 5 (config `miniapps.bulk_rows`, a security control).
- The agent's ordinary writes run without asking (config `miniapps.agent_writes`, on, a security control no app can write), held to the operator ceiling.
- Rollback: offer the rows written after the checkpoint for re-apply, none selected.
- A failing functional verdict may be promoted with a confirmation naming what failed; static failures and a seal check that ran and failed always block; a seal check that could not run is shown and does not block.
- Sidebar: at most 5 pinned mini apps in a collapsible Pinned group below projects (`miniapps.sidebar_pins`).
- Deletion: trash kept 30 days (`miniapps.trash_days`); draft data discarded at promotion unless "Keep the draft data" is ticked.
- Name: "mini app".
- Protocol: the host speaks its own small protocol now, with every method declared as a tool definition, so an adapter for the MCP Apps standard can come later without changing any mini app (decision record 0008); the page reaches its data through the host, never through a looser CSP (decision record 0009).

**Phases** (each phase is a sub-epic with its exit gate)
1. A sealed page with shared, audited data, on one reference mini app with `kv` and `tables`: from its page and from chat, backed up, and kept out of private chats.
2. The full store set, files, migrations, bulk asks, undo, schedules and the rest of the quality gate.
3. Reach: pins, Home, palette, phone, deep links; `ask`, `knowledge`, `notify`; graduation; portable bundles.
4. Writes outside the store: spreadsheet write-back; tools and network through the owner's asks and the egress guard.

**Non-goals**: public hosting or share links; multi-user storage; server-side code inside a mini app (needing it is the signal to graduate); network from the page itself; in-place spreadsheet editing before phase 4; a drag-and-drop builder.
