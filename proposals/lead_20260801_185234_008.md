## The defect

A `dry_run=true` dispatch of **701**, **702** or **720** still parks on a **write-environment approval gate** and still loads a **write-scoped credential** from Key Vault. `dry_run` is enforced at the *step* level in these workflows, never at the *job* level — so the job starts, the gate fires, the write token is minted, and only then do the individual steps decide to do nothing.

Measured from the job graphs on `main` (`7bce4f0`) — six jobs, zero of them gated on `dry_run`:

| Workflow | Job | `environment` | `if:` mentions dry_run | credential it loads |
| --- | --- | --- | --- | --- |
| 701 | `dns` | `cloudflare-prod-write` | **no** | `cloudflare-tokens-from-kv` `scope: write` |
| 701 | `repo` | `github-prod` | **no** | `wr-all-cbm-ffc-copilot-mcp-github-pat` |
| 701 | `content` | `github-prod` | **no** | `wr-all-cbm-ffc-copilot-mcp-github-pat` |
| 702 | `clone-deploy` | `github-prod` | **no** | `wr-all-cbm-ffc-copilot-mcp-github-pat` |
| 720 | `create-repo` | `github-prod` | **no** | `wr-all-cbm-github-pat` |

701's `zone_check` is the counter-example that shows this is not "all gates are like that": it is on `cloudflare-prod-read` with a `scope: read` token, so it runs unattended, dry or not.

**111 already does it correctly.** `.github/workflows/111-dns-create-redirect-rule.yml:80` reads `if: inputs.dry_run == false` on its `apply` job, so a dry dispatch never reaches `cloudflare-prod-write` at all. That is the pattern to copy.

## How it was found, and why it matters more than it looks

The Conductor has owed a post-merge verification since run 64 (#858): dispatch 701/702/720 with `dry_run=true` against a real target. It was deferred for four runs. Run 68 executed it, and the reason it had never been done became self-evident — **the dry run cannot finish without a human approving a write gate**, so it is not a check anybody can run in CI or unattended.

- Run [30708948816](https://github.com/FreeForCharity/FFC-Cloudflare-Automation/actions/runs/30708948816) — 701, `dry_run=true`. `resolve` ✅, `zone_check` ✅, then **`dns` waiting on `cloudflare-prod-write`**. Cancelled rather than approved: HARD RULE, a write gate needs Clarke's explicit yes, and "the steps inside are dry" is not the same claim as "the environment is read-only".
- Run [30708961672](https://github.com/FreeForCharity/FFC-Cloudflare-Automation/actions/runs/30708961672) — 702, `dry_run=true`. Refused correctly at preflight (`FFC-EX-technologymonastery.org already serves a live site`). **The guard works**; this is not a bug in 702. But it means the `clone-deploy` job was never reached, so the `github-prod` gate above is derived from source rather than observed.

Three concrete costs:

1. **The dry path is unverifiable.** The whole point of `dry_run` is a safe rehearsal; a rehearsal that needs the same human approval as the live run is not one. This is why #973's `working-directory: target-repo` defect — which would have crashed *every* 702 dry run — survived review until a Conductor read it by eye.
2. **Dry runs pollute the gate queue.** The Conductor tracks pending deployments as its step-2 workload. Every dry dispatch adds a row indistinguishable at a glance from a real pending write. This run added one and had to cancel it to leave the queue at the standing two.
3. **A write credential is materialised for a run that writes nothing.** Least-privilege says a dry run should never hold `scope: write` or a write PAT.

## Scope — one PR

Add a `dry_run`/`DryRun` term to the `if:` of the five jobs in the table, so a dry dispatch skips the gated job entirely, exactly as 111 does.

Watch the downstream `needs.*.result` conditions — 701 already tolerates a skipped `dns` (`needs.dns.result == 'success' || needs.dns.result == 'skipped'` on `repo`, `verify` and `finalize`), so the shape is already anticipated there. **Check the equivalents on `702`/`720` rather than assuming**, and confirm a skipped job does not turn a dry run red.

Note the input names differ: 701/702 use `dry_run` (boolean, default `true`), **720 uses `DryRun` (boolean, default `false`)**. That casing/default mismatch is its own small trap and is worth normalising in the same PR if it does not widen the diff much.
