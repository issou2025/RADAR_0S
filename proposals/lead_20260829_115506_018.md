# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**RFC: Runtime adapters and bounded iterative review loops**

*Project description:*
## Summary

Explore a protocol-level extension for **bounded iterative review loops** and **optional runtime adapters**, informed by [`promptadvisers/claudex`](https://github.com/promptadvisers/claudex) and the existing [`openai/codex-plugin-cc`](https://github.com/openai/codex-plugin-cc) integration pattern.

The goal is **not** to turn Agent Relay into a Claude↔Codex orchestration runtime. The goal is to identify which useful mechanics from Claudex can be generalized into Agent Relay without compromising its existing design: agent-agnostic, tool-agnostic, durable-state based, evidence-first, role-based, provenance-aware, and human-governed.

The core architectural distinction should remain explicit:

> **Claudex is an execution/orchestration runtime. Agent Relay is a coordination and evidence protocol.**

A runtime such as Claudex should be able to execute one or more Agent Relay passes, while Agent Relay defines the durable contract those passes must satisfy.

## Motivation

Agent Relay v0.3.0 already supports:

- five stable roles: Builder, Reviewer, Executor, Verifier, Integrator;
- explicit Reviewer lenses;
- immutable reviewed snapshots;
- structured findings;
- convergence to `FIXED`, `DISPROVED`, `DEFERRED`, or `BLOCKED`;
- Verifier checkpoints before consequential readiness/sign-off claims;
- durable handoff/pass records;
- provenance that is explicitly not authority.

What it does **not** currently define is a reusable mechanism for repeatedly applying Reviewer passes to the same evolving artifact until a bounded termination condition is reached.

Claudex provides useful prior art here. In plan mode it implements roughly:

```text
Draft PLAN.md
    ↓
Reviewer persona 1
    ↓
Revise
    ↓
Reviewer persona 2
    ↓
Revise
    ↓
Reviewer persona 3+
    ↓
No material findings OR max rounds
    ↓
Terminate
```

It also implements practical runtime controls around that loop: status, diagnostics, cancellation, rollback, stale-loop cleanup, concurrent-loop detection, atomic state updates, and bounded rounds.

Those mechanics are useful. Their current Claude Code / Codex-specific implementation should not be copied into the Agent Relay core.

## Prior art

### Claudex

`promptadvisers/claudex` is a Claude Code plugin that uses a Stop hook to drive an autonomous Claude↔Codex loop.

Relevant characteristics:

- Claude authors/revises the artifact;
- Codex acts as reviewer;
- plan review is first-class;
- reviewer perspectives rotate by round;
- loops are bounded by a maximum round count;
- termination occurs when there are no material findings or the bound is reached;
- runtime state is persisted under a project-local state directory;
- runtime controls include `status`, `doctor`, `cancel`, and `rollback`;
- stale and concurrent loops are explicitly handled;
- state transitions are designed to avoid races;
- the hook fails open so a broken orchestration loop does not trap the user.

### codex-plugin-cc

`openai/codex-plugin-cc` provides provider-specific review capabilities such as standard/adversarial review that can be invoked from Claude Code.

Agent Relay should treat this class of tool as a possible **review execution backend**, not as part of the protocol itself.

## Design principle

**Port semantics; adapt runtime contracts; do not port provider-specific orchestration.**

Anything added to Agent Relay should remain meaningful if the participants are, for example:

```text
ChatGPT -> Claude Code -> Codex CLI -> local GPU Executor -> human Integrator
```

or:

```text
Claude -> Gemini -> CI Executor -> ChatGPT
```

or a completely different set of agents and tools.

## Proposed capability 1: bounded iterative review

Add a protocol-level concept for an **iterative review cycle** over a durable artifact.

Example:

```text
Builder
  ↓
Artifact revision A
  ↓
Reviewer[design]
  ↓ findings
Integrator
  ↓ accepted repairs
Builder
  ↓
Artifact revision B
  ↓
Reviewer[security]
  ↓ findings
...
  ↓
Verifier
  ↓
Integrator
```

The cycle MUST be bounded. It must never imply an unbounded "agents argue until they agree" swarm.

A cycle should define at least:

- cycle ID;
- target artifact/repository;
- initial immutable snapshot;
- current immutable snapshot;
- maximum review rounds/passes;
- selected lens or lens sequence;
- mutation authority/boundaries;
- per-round findings;
- finding disposition;
- executed/inspectable evidence;
- termination reason;
- unresolved concerns;
- next required role/pass if termination is not a clean completion.

Possible termination reasons:

```text
NO_MATERIAL_FINDINGS
MAX_ROUNDS_REACHED
BLOCKED
CANCELLED
SUPERSEDED
AUTHORITY_REQUIRED
ENVIRONMENT_REQUIRED
```

Exact names are open for discussion.

### Important distinction

`NO_MATERIAL_FINDINGS` is **not equivalent to VERIFIED, READY, RELEASED, or APPROVED**.

A Reviewer loop can establish that no further review findings were produced against a given snapshot. Consequential readiness still follows the existing rule:

```text
Reviewer -> Verifier -> Integrator
```

unless adequate current evidence already exists.

## Proposed capability 2: first-class plan/design review workflow

Adapt Claudex's strongest idea: perform adversarial review **before implementation**, while the primary artifact is still a plan/design/specification.

Agent Relay already supports `Reviewer[design]`; this RFC proposes making the workflow explicit.

Example:

```text
Idea / requirement
    ↓
Builder produces PLAN.md / design artifact
    ↓
Reviewer[design]
    ↓
Builder revises
    ↓
Reviewer[security]
    ↓
Builder revises
    ↓
Reviewer[reliability]
    ↓
Integrator reconciles remaining concerns
    ↓
Verifier checks required factual/spec claims where applicable
    ↓
Implementation may begin
```

The plan itself should be treated as durable state with revision identity. Avoid a semantic "plan locked" state that could be confused with approval; prefer an immutable accepted/reviewed snapshot plus explicit unresolved concerns and authority state.

Potential protocol artifact:

- `assets/REVIEW-CYCLE.md`, or
- extend `assets/AGENT-PASS.md` with optional cycle metadata.

Avoid creating parallel evidence schemas if the existing pass/finding contract can be extended cleanly.

## Proposed capability 3: reviewer-lens sequencing

Claudex rotates fixed reviewer personas:

1. senior engineering/design;
2. security/data integrity;
3. operations/SRE.

Agent Relay can generalize this as **lens sequencing** without encoding personas or providers.

Example sequence:

```text
Reviewer[design]
-> Reviewer[security]
-> Reviewer[reliability]
```

Other workflows might use:

```text
Reviewer[spec-conformance]
-> Reviewer[test-gap]
-> Reviewer[readiness]
```

or repeat one lens against a repaired snapshot.

Requirements:

- lens sequence MUST NOT create new roles;
- selecting a lens MUST NOT grant mutation authority;
- each pass records the exact snapshot reviewed;
- repeated passes should distinguish new findings, persistent findings, disproved findings, and already-resolved findings;
- a runtime may choose/adapt the sequence, but the durable record must state what actually occurred.

## Proposed capability 4: runtime adapter contract

Define a **non-normative adapter boundary** that allows external runtimes to execute Agent Relay roles/passes.

Examples of potential adapters/backends:

- Claudex;
- `codex-plugin-cc`;
- Claude Code subagent/plugin workflows;
- Codex CLI;
- ChatGPT/Codex connected GitHub workflows;
- Gemini CLI;
- CI/CD systems;
- local shell/Docker/GPU executors;
- future orchestrators.

The core protocol should not invoke them directly.

A runtime adapter should consume something equivalent to:

```yaml
protocol: agent-relay-v1
cycle_id: plan-review-001
role: reviewer
review_lenses:
  - security
source_snapshot: <immutable-id>
mission: <task>
mutation_boundary: read-only
acceptance_criteria:
  - <criterion>
required_return:
  - findings
  - evidence
  - unverified_surfaces
  - source_snapshot
  - provenance
```

and return an ordinary Agent Relay pass/finding record.

The adapter interface should be conceptual/data-contract level unless and until there is a strong reason for executable adapter code.

## Proposed capability 5: operational loop semantics

Claudex contains several runtime engineering ideas worth adapting as **recommended runtime behavior**, not normative core execution code.

### Status

A runtime executing a review cycle should be able to expose, where applicable:

- cycle ID;
- phase/current role;
- round/pass number;
- current snapshot;
- findings by state/severity;
- blocked/unverified surfaces;
- next transition;
- termination condition/budget.

### Diagnostics / doctor

Before autonomous iteration, a runtime should be encouraged to validate the capabilities actually required for the declared route:

- required CLI/tool available;
- repository/artifact accessible;
- requested mutation authority available;
- required environment available;
- source snapshot resolvable;
- state directory/storage writable if needed;
- provider/tool authentication present when applicable.

This is runtime guidance; Agent Relay itself must not claim capabilities it cannot inspect.

### Cancel

A cycle needs a durable cancelled state rather than silently disappearing.

Cancellation should preserve:

- last completed snapshot;
- completed findings/evidence;
- unresolved findings;
- reason if known;
- whether partial mutations occurred;
- recommended recovery/next role.

### Rollback

Do **not** define rollback as a universal Agent Relay action. Different substrates have very different mutation semantics.

Instead define a runtime/adaptor expectation:

- if the runtime offers rollback, state precisely what state it can revert;
- never imply Git rollback, artifact rollback, production rollback, and orchestration-state cleanup are the same operation;
- destructive rollback remains subject to mutation authority.

### Stale/concurrent cycle handling

Recommended runtime behavior may include:

- explicit active-cycle ownership;
- stale-cycle detection;
- refusal or reconciliation when conflicting active cycles target the same mutation surface;
- atomic/CAS-like state transitions where the substrate supports them.

These should be documented as runtime safety patterns, not imposed on substrates that cannot implement them.

## Proposed capability 6: loop budgets

Iteration has real cost: tokens, API/tool calls, CI minutes, human attention, GPU time, and wall-clock execution.

A review cycle should support a declared budget such as:

- max rounds/passes;
- optional max findings repaired per cycle;
- optional execution/tool budget;
- explicit escalation when the budget is exhausted.

The protocol should not prescribe provider pricing or token accounting.

A bounded loop terminating with unresolved findings is valid and should report them, rather than manufacturing an LGTM state.

## Fail-open vs fail-closed semantics

Claudex's Stop hook intentionally **fails open**: orchestration errors should not trap a Claude Code session.

Agent Relay has a different concern: consequential evidence/readiness decisions should remain conservative.

This RFC should make the distinction explicit:

### Runtime/orchestration liveness

A runtime MAY fail open so the user regains control when automation breaks.

Example:

```text
hook/adapter failure -> stop autonomous loop -> return control to user
```

### Evidence and authority gates

Agent Relay MUST NOT translate runtime failure into successful verification/readiness.

Example:

```text
review runtime failed
!=
NO_MATERIAL_FINDINGS
!=
VERIFIED
!=
READY
```

In other words:

> **Fail open for control flow; fail closed for evidence, authority, and readiness claims.**

## What should be ported/adapted

| Claudex concept | Agent Relay treatment |
| --- | --- |
| Bounded review rounds | **Adapt into protocol-level review-cycle semantics** |
| Different reviewer perspectives per round | **Generalize as Reviewer lens sequencing** |
| Plan review before implementation | **Add first-class plan/design review workflow** |
| Persistent loop state | **Represent through durable cycle/pass state** |
| No-findings / max-round termination | **Generalize into explicit termination reasons** |
| Status | **Recommended runtime capability / portable status fields** |
| Doctor/preflight | **Recommended runtime capability feasibility checks** |
| Cancel | **Define durable cancellation semantics** |
| Rollback | **Adapter-specific; document boundaries, never universalize** |
| Stale-loop cleanup | **Recommended runtime safety pattern** |
| Concurrent-loop rejection | **Recommended runtime safety pattern** |
| Atomic/CAS state transitions | **Recommended when substrate supports it** |
| Fail-open Stop hook | **Generalize only as runtime liveness guidance** |
| `PLAN.md` | **Treat any durable plan/design/spec artifact equivalently** |
| Claude author / Codex reviewer | **Do not port; use roles, not products** |
| Claude Code Stop hook | **Do not port into core** |
| `codex exec` invocation | **Do not port into core** |
| Fixed persona names/order | **Do not make normative** |
| Reviewer-issued `LGTM` as final authority | **Do not port; preserve Verifier/Integrator separation** |

## Example: Claudex as an Agent Relay runtime adapter

A future Claudex adapter could conceptually execute:

```text
Agent Relay cycle request
  role: Reviewer
  lenses: [design, security, reliability]
  source: PLAN.md @ digest/commit
        ↓
Claudex runtime
  Claude revises
  Codex reviews
  bounded rounds
        ↓
Agent Relay records
  reviewed snapshots
  per-round findings
  revisions
  remaining concerns
  termination reason
  provenance
        ↓
Verifier / Integrator as required
```

This lets Claudex remain opinionated and provider-specific while Agent Relay remains portable.

## Non-goals

This RFC should **not**:

- turn Agent Relay into an autonomous swarm framework;
- add a built-in Claude↔Codex execution loop;
- add Claude Code hooks to the core skill;
- require Codex, Claude, ChatGPT, Gemini, or another named provider;
- require GitHub or Git;
- let a runtime adapter grant permissions or mutate outside declared boundaries;
- collapse Reviewer into Verifier;
- let repeated reviewer agreement substitute for executable/inspectable evidence;
- define `LGTM` as release/merge authority;
- require all review cycles to use three passes;
- require a fixed lens sequence;
- make rollback a substrate-independent promise;
- expose or relay private chain-of-thought.

## Design questions

1. Should `review cycle` become a named protocol concept, or can it remain a composition of ordinary Agent Relay passes plus optional cycle metadata?
2. Is a separate `REVIEW-CYCLE.md` useful, or should cycle state live entirely in `AGENT-PASS.md` plus findings?
3. Should lens sequencing be declarative (`[design, security, reliability]`) or simply recorded after each independently routed pass?
4. Which termination reasons need to be normative versus illustrative?
5. Should a cycle distinguish `NO_MATERIAL_FINDINGS` from a weaker state such as `NO_NEW_FINDINGS`?
6. How should repeated findings be correlated across changing snapshots without creating a second finding-lifecycle system?
7. Should runtime adapter guidance remain entirely documentation, or is a small non-normative schema/validator warranted?
8. How much concurrency/staleness guidance belongs in Agent Relay versus the runtime implementing the adapter?
9. Should plan/design review get its own recommended route, for example:

```text
Builder -> Reviewer[design] -> Builder -> Reviewer[security] -> Builder -> Reviewer[reliability] -> Integrator
```

with Verifier added only when the claims/gates require verification?

## Acceptance criteria

- [ ] Agent Relay still has exactly five core roles.
- [ ] The RFC clearly distinguishes protocol semantics from runtime execution.
- [ ] Iterative review is explicitly bounded and cannot imply an infinite autonomous loop.
- [ ] Every review pass remains tied to the immutable snapshot actually reviewed.
- [ ] Reviewer lens sequencing does not create provider/persona-specific roles.
- [ ] No-findings termination is explicitly distinct from verification/readiness/sign-off.
- [ ] Existing finding states (`FIXED`, `DISPROVED`, `DEFERRED`, `BLOCKED`) remain authoritative for finding lifecycle.
- [ ] Cancellation/incomplete termination preserves evidence and unresolved findings.
- [ ] Runtime failures cannot be converted into evidence of success.
- [ ] Mutation boundaries survive every cycle transition and adapter invocation.
- [ ] Runtime adapters cannot grant capabilities or authority.
- [ ] Plan/design/spec artifacts can participate without requiring `PLAN.md` specifically.
- [ ] Claudex and `codex-plugin-cc` can be described as possible execution backends without becoming dependencies.
- [ ] Any new cycle-level schema reuses the existing evidence/provenance model rather than creating a competing one.
- [ ] At least one end-to-end example demonstrates a bounded plan-review cycle followed by Builder/Verifier/Integrator behavior.

## Expected outcome

Agent Relay should remain the coordination layer:

```text
              Agent Relay
     roles / evidence / lifecycle
       handoffs / provenance
              ↑       ↑
              │       │
       runtime adapters/backends
        ↙        ↓         ↘
    Claudex   Codex CLI   local Executor
```

The useful lesson from Claudex is not "Agent Relay should automate Claude and Codex." It is that **iterative review needs explicit convergence, bounded execution, durable state, operational controls, and clear termination semantics**.

Those ideas can be adapted while preserving Agent Relay's stronger separation between review, verification, execution, integration, authority, and provenance.
