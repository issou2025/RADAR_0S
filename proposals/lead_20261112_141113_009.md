# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Investigate standards-compliant OAuth 2.0 / OIDC redirect sign-in across ThunderID SDKs**

*Project description:*
### What problem are we solving?

ThunderID SDKs should work with any standards-compliant OAuth 2.0 / OpenID Connect provider for redirect-based sign-in, not only with a ThunderID server. A test of the quickstart samples against another compliant provider (Asgardeo) shows that today they only work with ThunderID-specific assumptions or workarounds:

| SDK | Result | Cause |
|---|---|---|
| JavaScript / React (`@thunderid/react` 1.4.0) | Sign-in silently fails; app stays signed out after a successful token exchange | Discovery is fetched only from `{baseUrl}/.well-known/openid-configuration`. When that fails, endpoints are derived from `baseUrl` and the expected issuer is set to `baseUrl`, so a provider whose `iss` differs (for example `{baseUrl}/oauth2/token`) fails ID token validation. Works only after setting `endpoints.wellKnown` by hand. |
| Node (`@thunderid/node` 1.3.0, client credentials) | Works, with a discovery warning | Same discovery path assumption. |
| Flutter (`thunderid_flutter` 1.6.0, iOS SDK 1.9.0) | `401 invalid_client` | The released iOS SDK sends the token request as JSON. RFC 6749 requires `application/x-www-form-urlencoded`. Fixed in iOS SDK 1.10.0, but the Flutter plugin pins `1.9.x`. |
| Flutter with iOS SDK 1.10.x | `ID token iss mismatch` | iOS and Android require the ID token `iss` to equal `baseUrl` exactly, with no way to configure the issuer. Works only with `validateIssuer: false`. |
| React account pages, `/flow/meta` | Fail | ThunderID-only APIs (`/users/me`, `/flow/meta`) are called with no fallback to standard ones (`/oauth2/userinfo`). |

The issuer assumption is also fragile on ThunderID itself, since the server's issuer comes from `JWT.Issuer` config and need not equal `baseUrl`.

### Who are we solving this for?

**Primary:** Application developers adopting ThunderID SDKs

* **Goal:** Use one SDK for redirect-based sign-in whether their app talks to ThunderID or to another OIDC provider, and switch providers by configuration.
* **Pain:** Sign-in breaks in ways that are hard to debug (silent sign-out, `iss mismatch`, `invalid_client`), and the only fixes are undocumented overrides or turning off issuer validation.

### Why should we solve this now?

**Why now:**

* **Value to Persona:** Standards-compliant SDKs remove vendor lock-in and let developers trust that the SDK follows OAuth 2.0 and OIDC rather than one server's conventions.
* **Value to Org:** Interoperability is a requirement for adopters that run mixed identity stacks, and a standards-first SDK is a stronger adoption argument than a server-specific one.

### Proposed Solution

Investigate every ThunderID SDK (JavaScript family, Node, Express, Next.js, Nuxt, iOS, Android, Flutter) for standards-compliant redirect-based sign-in, and file fixes per SDK. Without breaking ThunderID, the SDKs should:

1. **Resolve the issuer from discovery**, per OIDC Discovery 1.0 §4.3, instead of assuming `iss == baseUrl`. Allow an explicit `issuer` / `wellKnown` override in config on every platform. Fall back to `baseUrl` only when no discovery document is available, which keeps current ThunderID behavior.
2. **Use standard OAuth wire formats.** Send token, revoke and introspection requests form-encoded (RFC 6749). Release a Flutter SDK that picks up iOS SDK 1.10.x, and check Android.
3. **Keep ThunderID-specific APIs optional.** For `/users/me`, `/flow/meta` and the flow APIs, either fall back to standard endpoints (`/oauth2/userinfo`) or degrade without failing the sign-in.
4. **Document** how to point each SDK at a non-ThunderID provider.
5. **Add a compatibility check in CI** that runs the redirect quickstarts against ThunderID and at least one other compliant provider.

### Alternatives

Developers can set `endpoints.wellKnown` (JavaScript) or turn off issuer validation (mobile). This is undocumented, differs per SDK, and turning off issuer validation weakens security.
