# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Canvas widgets: user-installed tools, sandboxed and shareable**

*Project description:*
## Why
People's experience differs, so adding more built-in tools to the canvas doesn't help everyone (we removed the axes, guides and tape for that reason: #145, #146). Instead, the canvas itself is the "artifact": it starts minimal, and each user customises it with **widgets** (coordinate systems, structural grids, guides, tapes, sun studies, area tables…) and their own **items** (looks, which already exist). The agent installs widgets on request ("add a 3.6 m grid on the south wall, with snapping"), tunes them, or writes new ones. Widgets, items and whole canvases can be shared.

## Phases
Each phase is a sub-issue with its own PR, tested and merged on its own.
- #159 Phase 1: `@plinth/sandbox` package (infrastructure).
- #160 Phase 2: core format, script runner, widget libraries, capabilities.
- #161 Phase 3: canvas, panel, and the first two widgets (grid, coordinate system). This is the first user-visible step.

Later phases, opened when needed:

- `propose`;
- moving looks into the sandbox (decide then whether look scripts stay JSONata, run inside the sandbox, or become JS).

## Decisions
- Package: `packages/sandbox` (`@plinth/sandbox`).
- Widgets live in **their own library files**, separate from look libraries: `libraries/*.widgetlib.json`, format in `libraries/widgetlib.schema.json`.
- Entry point: "小组件" in the ⋯ menu (can move to the toolbar later).

## What a widget is
A description that the canvas interprets, plus a script run in a sandbox. It never runs in the page.

- **Parameters**: different for every widget, declared with the same JSON Schema keywords as looks (`type`, `default`, `title`, `minimum`/`maximum`, `enum`/`enumTitles`, `description`). The canvas generates the widget's panel from them (shadcn controls); a widget cannot draw its own UI.
- **Script**: plain JavaScript, `widget(project, params)`, a pure function of the project (read-only) and the params. It returns a fixed set of primitives the canvas knows how to draw in plan and 3D:
  - `lines` (from, to, dash);
  - `labels` (at, text; always drawn as text);
  - `points` and `areas`;
  - `handles` (at, param): the canvas does the dragging, writes the param and runs the script again; the script holds no state;
  - `snaps`: points that placing and dragging snap to.
- **Agent part**: `description` plus the params' descriptions, so the agent can tune an installed widget by voice ("move the origin to the south-east corner"). It is read as untrusted reference data, never as instructions.
- **Permissions**: declared and shown on install. Start with `draw` only. Later `propose`: the script returns capability calls, previewed, confirmed by the user, run in one transaction through the capability registry (undoable; integrity rules roll back), never beyond the user's own rights.

Draft format (structural grid):
```jsonc
{
  "id": "grid", "name": "轴网", "version": 1,
  "description": "A structural grid with numbered axes; lines snap furniture and walls.",
  "permissions": ["draw"],
  "params": {
    "spacing": { "type": "number", "default": 3600, "minimum": 300, "title": "间距" },
    "origin":  { "type": "array", "default": null, "title": "原点" },
    "snap":    { "type": "boolean", "default": true, "title": "吸附" }
  },
  "script": "function widget(project, params) { … return { lines, labels, handles, snaps } }"
}
```
Coordinates are plan millimetres to start with (drawn in plan and on the 3D ground); heights come later.

## Sandbox
The engine lives in its own package, `packages/sandbox` (`@plinth/sandbox`). It only runs JavaScript safely and knows nothing of widgets, looks or libraries, so looks and anything else that runs user code can use it later. Engine version, upgrades and the wasm build scripts are kept there alone.

The package provides the mechanism: **realms** (one wasm instance each, with its own memory) and **scripts** (one context each inside a realm, with their own globals and built-ins). The caller chooses the keys; see "Isolation" for who decides them.
```ts
const sandbox = await createSandbox({ memoryMB: 32, deadlineMs: 200 });
const realm = sandbox.realm(realmKey);                  // a wasm instance, created on first use
const script = await realm.script(scriptKey, source);   // a context in it, created on first use
await script.setData('project', json);                  // kept inside, reloaded only when it changes
const out = await script.call('widget', [params]);      // JSON in, JSON out
realm.dispose();                                        // drops the instance and all its scripts
```
In the browser it runs in the isolated worker below; in Cloudflare Workers, in place.

Layers:
1. **QuickJS compiled to WebAssembly** (`quickjs-emscripten`; see "Engine and upkeep" for the version). The script runs in a separate engine with its own memory and no host functions: only standard built-ins, no DOM, network, storage or timers. Data goes in and comes out as JSON text. Memory limit, stack limit, and an interrupt deadline.
2. **A dedicated Web Worker started from an opaque-origin sandbox with CSP `connect-src 'none'`**: a slow script can't block the UI and is terminated on timeout. Even if a script escaped QuickJS, it would land in a thread with no session, no page and no network.
3. **Output validation** before drawing: only the known primitives, finite numbers, capped counts. Anything else drops the whole output.

### QuickJS experiment
The grid widget above runs against the wushi-10 sample: 60 walls, 10 axes, snaps where axes cross walls, origin dragged. Run with `quickjs-emscripten` 0.31.0 (QuickJS 2024-02-14); see "Engine and upkeep" for why that version is not the one to ship.

**Size and start-up**

| | Result |
|---|---|
| wasm | 519 KB (236 KB gzipped) |
| JS glue | 94 KB |
| Load and compile in Chromium | ~74 ms |
| Runtime and project load | ~79 ms, once per open |

**Cost per run**, with the project kept in the VM and only params passed (the drag case):

| | Per run |
|---|---|
| Native JS, no sandbox | 0.03–0.07 ms |
| QuickJS | 0.8–0.9 ms (Node and Chromium) |
| QuickJS, passing the whole project each time | 5.8 ms (so the project must stay in the VM) |
| The same widget in JSONata | 21.5 ms (more than a frame) |

**Limits and isolation**
- An infinite loop was interrupted at the 200 ms deadline.
- A memory bomb hit the 32 MB limit and failed with "out of memory".
- `fetch`, `XMLHttpRequest`, `window`, `process`, `require`, `setTimeout`, `WebAssembly` and `importScripts` are all undefined in the guest.
- Polluting `Object.prototype` in the guest doesn't touch the host.

**Cloudflare Workers** (local workerd): the host's `new Function` is blocked ("Code generation from strings disallowed"), yet QuickJS runs the widget correctly. Widgets and looks can therefore also run server-side.

**JSONata pitfalls met while writing the same widget**
- A nested-array shape error on `$min`.
- `[0, 0]` is falsy, so an origin at (0, 0) silently fell back to the default.

Phones will be a few times slower. That still leaves a simple widget well inside a frame; for heavy ones, throttle re-runs while dragging.

## Engine and upkeep
QuickJS is widely used:
- `quickjs-emscripten`: about 2M weekly npm downloads.
- Shopify Functions, through Javy (now a Bytecode Alliance project).
- NGINX njs offers QuickJS as an engine, linking an external Bellard or QuickJS-NG build and following upstream closely.

It also has a real CVE record: 29 NVD entries for "quickjs".
- Early ones are mostly crashes.
- A batch of seven in October 2025 (CVE-2025-62490…62496, up to 8.8) includes use-after-free, type confusion and overflows.
- QuickJS-NG entries in 2026 include CVE-2026-37630, described as code execution.
- CVE-2026-88378 (9.8) is a heap out-of-bounds write in bytecode reading.

`quickjs-emscripten` releases slowly (0.31.0 in September 2024, 0.32.0 in February 2026), and its README says it has not been audited. Hence:

1. **Ship `quickjs-emscripten` 0.32.0**, not the 0.31.0 used in the experiment. 0.31.0 vendors QuickJS 2024-02-14, from before the October 2025 CVEs. 0.32.0 vendors QuickJS 2025-09-13 plus later commits (2026-02-15); a QuickJS-NG 0.12.1 variant is also available. Check which published CVEs it fixes before shipping.
2. **Build it ourselves when the package lags**: if a CVE affecting the engine core is published and the package isn't updated within a few weeks, build the wasm from QuickJS upstream with the package's build scripts at the fixed commit. This is how NGINX does it: follow upstream rather than wait for a packager.
3. **Two rules, enforced in code and tests**:
   - Only ever evaluate source. Never load bytecode (`JS_ReadObject`/`JS_ReadFunctionTag` and friends), which keeps the bytecode-reader CVEs (CVE-2025-46687, CVE-2025-46688, CVE-2026-88378) out of reach.
   - Give the engine no host functions and no standard library: data in, JSON out. njs's changelog is a long list of use-after-free, leaks and out-of-bounds reads in the host features it adds on top of QuickJS (fetch, XML, zlib, Buffer); the less the host exposes, the less there is to break.
4. **All three sandbox layers are required.** An engine bug in wasm corrupts only the engine's own memory: the worst outcome is a wrong or forged drawing, or a crash. The worker sandbox is the backstop if wasm itself is ever escaped.
5. **Watch advisories** for QuickJS and QuickJS-NG; assess each new one and upgrade.

## Isolation
Scripts sharing an engine can spy on and tamper with each other. Experiment: a malicious script ran first and replaced `Array.prototype.map` and `JSON.stringify`; then a normal widget computed `[1,2,3].map(x => x * 2)`.

| Isolation | Normal widget's output | What the malicious script got |
|---|---|---|
| Same context | `[999,999,999] <tampered>` | the widget's function source |
| Separate contexts in one runtime | `[2,4,6]` | nothing (it can't even see the other's function) |
| Separate wasm instances | `[2,4,6]` | nothing |

Separate contexts isolate globals and built-ins, but share one wasm linear memory. An engine memory-corruption exploit could reach another script's data there. Separate wasm instances each have their own memory.

### The rule: isolate by source, not by count
One instance per widget or per item would not scale: a project has hundreds of items (200 instances would be over 3 GB of initial wasm memory). The boundary that matters is who wrote the script.

- **One realm (wasm instance) per library.** A library is one author and one source: the default library, another built-in one, my personal library, a team library, a library shared with me. A bad script can then only reach scripts by the same author, which its author could edit anyway. Scripts from different libraries never share memory, globals or built-ins, so someone else's library can't touch the default library or mine.
- **One script (context) per look or widget definition, keyed by id, version and source hash.** Scripts in the same library have their own globals and built-ins. A context costs ~3 ms and is created when first needed.
- **One context serves every use of the same definition.** Thirty identical chairs share one context and differ only in params. Results are cached by script and params, as looks already are (`looks/cache.ts`). State a script keeps between its own runs affects only its own output.
- **Data is per context, deep-frozen.** The project copy given to a script is its own and read-only.
- **Outputs are validated, stored and drawn per widget or item.** Snaps carry their widget, so a misleading one can be hidden.

Example: 200 items using 40 looks from 3 libraries, plus 5 widgets, gives 3–4 wasm instances and about 45 contexts, each built once, with runs deduplicated by script and params.

What it gives up: scripts from the same library share one wasm memory, so an engine exploit could affect the author's own other scripts, which is no new power. Cross-library isolation and the outer two layers stay.

### Where the rule lives
- **`@plinth/sandbox`** is mechanism only: realms and scripts with caller-chosen keys, limits, crash handling (a trapped instance is discarded and its scripts rebuilt on next use). It knows nothing of libraries.
- **`@plinth/core`** holds the policy, in one place: a small script runner used by both looks and widgets. It turns a definition into keys:
  - realm key: the library's identity, e.g. `builtin:default`, `user:<user id>:<library id>`, `team:<team id>:<library id>`;
  - script key: `<kind>:<id>@<version>#<source hash>`.

  Neither looks nor widgets pick keys themselves, so the rule can't drift between them.
- **The app injects the sandbox into core**: the web app supplies the worker-backed one, the server the in-place one. Core stays free of browser and worker code.

### No instance reuse
An instance is never handed from one library to another. Memory can't be reliably wiped, and reuse would reopen the leak above. What is shared is the **compiled** WebAssembly module (compile once per page). A realm lives while its library is in use and is discarded after.

Measured in Node: compiling once took ~7 ms; a fresh instance from the compiled module, through runtime, context, script, project load and first result, took ~7–19 ms (the very first ~49 ms). That happens only when a library is first used, never while dragging. So no warm pool is needed. Add one spare pre-instantiated instance only if phones measure slow first use.

### The five extensions
All keep the safety model: a widget only computes. The canvas hands events in and takes results out; a widget never touches the page or the model directly.

1. **Tool events** (SketchUp's `Tool`):
   ```js
   function onEvent(project, params, state, event) {
     // event: { type: 'move' | 'click' | 'text' | 'cancel', point, pick, text }
     // point is already inferred by the canvas (midpoint, axis lock…)
     return { state, params, preview: { lines: [...] }, done: false };
   }
   ```
   The canvas keeps a multi-step tool's `state` and passes it back each event, so the script holds none. A run is ~1 ms, fine for mouse moves.
2. **Picking and selection**: events carry the picked element id; `ctx.selection` lists the current selection.
3. **Inference**: snap targets grow from points to lines and directions. Inference itself (axis lock, colour cues) stays in the canvas, so every tool feels the same and none can subvert it.
4. **More outputs**:
   - 3D primitives: lines with height, planes, boxes;
   - `overrides`: highlight, dim or hide elements, in a few theme-defined styles;
   - `table` for the panel.
5. **`propose`**: capability calls, previewed, confirmed, run in one undoable transaction.

The first step reserves room for all of these: outputs are a typed list, and events go through a single entry point. Adding them later then extends the format without replacing it.

## Sharing
- Widgets live in widget libraries (`*.widgetlib.json`): built-in, personal, team, and later public.
- A project records which widget, which version, and which params it uses.
- Installing copies a pinned version. Updates need the user's confirmation and show what changed and whether permissions grew.
- Sharing a project shows the same widgets. A widget library or an item can be shared on its own.
- Scope: personal and team first. Public sharing only for `draw`-only or reviewed widgets, with report and takedown.
- Where a widget is installed: both levels. A user's own set follows the user across projects; a project can carry widgets of its own.

## Later, not in the first step
- The five extensions above: tool events, picking and selection, inference, more outputs (3D, overrides, tables, camera), `propose`.
- Moving look scripts from JSONata on the main thread into the same sandbox (they are shared executable code today), under the same rule: realm per library, context per look.
- Widgets reading external data: only through our server proxy, with an allowlist and an explicit permission.
- Free-form widget UI in an isolated iframe, like Claude artifacts.
