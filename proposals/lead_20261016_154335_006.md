# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[iOS] Data race in FlutterPlatformViewsController: computeViewsToDispose mutates raster-thread-only state on the platform thread (SIGSEGV in submitFrame)**

*Project description:*
### Steps to reproduce

Preconditions: any iOS app that embeds `UiKitView` platform views and pops a route containing them while frames keep rendering (a normal `MaterialPageRoute` transition is enough). The field crash below came from an app whose nav bar on most pages holds `UiKitView`-backed `UIVisualEffectView(effect: UIGlassEffect())` buttons, so every back navigation disposes one to three platform views mid-animation.

1. Push a route that contains one or more `UiKitView`s. Let the transition finish.
2. Pop the route. When the route is removed, Dart sends `dispose` for each platform view → `onDispose:` adds the id to `viewsToDispose` (platform thread).
3. The next `submitFrame:` on the raster thread posts `performSubmit:` to the platform thread. `performSubmit:` calls `computeViewsToDispose`, which erases the id from `currentCompositionParams` and `viewsToRecomposite` **on the platform thread**.
4. Meanwhile the raster thread is already in `submitFrame:` for the following frame and copies those same two containers by value into the task lambda. Two threads, one `std::unordered_set` / `std::unordered_map`, no lock.

The window is a few microseconds per dispose, so the field rate is low: 1 crash on 1 device over 14 days of daily TestFlight use. Stress harness and the result of running it are in **Code sample** below.

### Expected results

Disposing a platform view must not mutate raster-thread-only state from the platform thread. No crash.

### Actual results

`EXC_BAD_ACCESS (SIGSEGV)`, `KERN_INVALID_ADDRESS`, on the raster thread inside `-[FlutterPlatformViewsController submitFrame:withIosContext:]`, while the platform thread is simultaneously inside `-[FlutterPlatformViewsController performSubmit:...]` removing the disposed view from the hierarchy.

Register state is consistent with the copy constructor walking into a freed hash node: the fault address `0xdc086af624ccab00` is `x19 + 0x10`, which in libc++'s `unordered_set<int64_t>` node layout (`__next_`, `__hash_`, value) is the value slot; `x19 = 0xdc086af624ccaaf0` is not a valid pointer (the log flags "possible pointer authentication failure", the kernel's heuristic for high-bit garbage). The copy followed a `__next_` pointer of a node that the platform thread had just erased and freed.

### Analysis

The engine's own header documents the invariant that is violated. In `FlutterPlatformViewsController.mm` (tag 3.47.4, the version that built the crashing binary; the file is byte-identical in 3.47.7):

- [`currentCompositionParams`: "This state is only modified on the raster thread."](https://github.com/flutter/flutter/blob/9584c6713b324636289d067944a46fd6b49df14b/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L193-L197)
- [`viewsToRecomposite`: "This state is only modified on the raster thread."](https://github.com/flutter/flutter/blob/9584c6713b324636289d067944a46fd6b49df14b/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L215-L218)

Raster-thread accesses (all unlocked):

- [`prerollCompositeEmbeddedView:` inserts into both (L527-L543)](https://github.com/flutter/flutter/blob/9584c6713b324636289d067944a46fd6b49df14b/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L527-L543)
- [`submitFrame:` reads `currentCompositionParams` (L849, L895) and copies both into the task (L929-L947)](https://github.com/flutter/flutter/blob/9584c6713b324636289d067944a46fd6b49df14b/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L929-L947)
- [`reset` clears both (L794-L812)](https://github.com/flutter/flutter/blob/9584c6713b324636289d067944a46fd6b49df14b/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L794-L812)

Platform-thread mutation:

- [`performSubmit:` (`FML_DCHECK` main thread, L996) → `computeViewsToDispose` (L1010)](https://github.com/flutter/flutter/blob/9584c6713b324636289d067944a46fd6b49df14b/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L986-L1011)
- [`computeViewsToDispose` erases from `currentCompositionParams` and `viewsToRecomposite` (L1104-L1126, erases at L1120-L1121)](https://github.com/flutter/flutter/blob/9584c6713b324636289d067944a46fd6b49df14b/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L1104-L1126)

Sequence: `submitFrame(N)` on the raster thread posts `performSubmit(N)` to the platform thread via `runNowOrPostTask`. Nothing stops the raster thread from starting frame N+1 (`beginFrameWithSize:` → preroll → `submitFrame(N+1)`) while `performSubmit(N)` is still running. If `performSubmit(N)` is disposing a view, its `erase` on the two containers races with the raster thread's inserts, reads, and the by-value copies at L932-L933. This is undefined behaviour; the crash above is one way it manifests. The raster thread was unmerged from the platform thread for platform views in flutter/engine#53826 (Aug 2024), so every stable release since then carries this; the same erase exists in [3.41.8 (L999)](https://github.com/flutter/flutter/blob/3.41.8/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L999) and on [current master (L1043-L1044)](https://github.com/flutter/flutter/blob/2e53c3af41adee44d27fabf67178209c80ee73c0/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L1027-L1049), with the matching copies at [master L853-L854](https://github.com/flutter/flutter/blob/2e53c3af41adee44d27fabf67178209c80ee73c0/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterPlatformViewsController.mm#L853-L854).

Side note: the `viewsToDispose` comment says it "is modified on both the platform and raster thread", but today it is only touched by `onDispose:` and `computeViewsToDispose`, both on the platform thread. The comment looks stale; the real cross-thread mutation is the one above.

### Proposed fix

Either keeps the documented invariant:

1. **Move the erase to the raster thread.** Let `computeViewsToDispose` mutate only `platformViews` (platform-thread state) and push the disposed ids into a mutex-guarded `_disposedViewIds`. In `submitFrame:` (raster thread), drain that set under the mutex before the captures at L932-L933 and erase from `currentCompositionParams` / `viewsToRecomposite` there. A disposed view is never in the next frame's layer tree, so preroll cannot re-insert it.
2. **Guard the two containers with a `std::mutex`** taken in `prerollCompositeEmbeddedView:`, the read/copy section of `submitFrame:`, `reset`, and `computeViewsToDispose`.

Option 1 avoids taking a lock on the raster hot path for every frame.

### Code sample

A stress harness (36 `UiKitView`s pushed and popped every 0.9 s for 10 minutes on an iOS 27 Simulator, Flutter 3.47.7 debug) did **not** reproduce the crash. The race is established by the source and the field crash log above; a deterministic confirmation needs a local engine build (ThreadSanitizer, or a `usleep` between the captures at L932-L933 of `submitFrame:`). The harness is kept below for anyone who wants to try it on a device.

That is not surprising for a window a few microseconds wide on a fast host, and the field crash above came from an AOT release build on a device. The race itself is established by the source (documented raster-thread-only state, unlocked erase from the platform thread) and by the two simultaneous stacks in the crash log. To confirm it deterministically with a local engine build, either run the harness under ThreadSanitizer, or insert a short `usleep` between the two captures at L932-L933 of `submitFrame:` and pop a page containing platform views: `performSubmit:` on the platform thread then erases from the containers while the raster thread is still copying them.

```dart
// Stress harness: repeatedly push a page full of UiKitViews and pop it while
// frames keep flowing, so platform views are disposed while the raster thread
// is already preparing the next frame.
import 'dart:async';

import 'package:flutter/material.dart';
import 'package:flutter/services.dart';

void main() => runApp(const App());

class App extends StatelessWidget {
  const App({super.key});

  @override
  Widget build(BuildContext context) => const MaterialApp(home: Home());
}

class Home extends StatefulWidget {
  const Home({super.key});

  @override
  State<Home> createState() => _HomeState();
}

class _HomeState extends State<Home> {
  Timer? _timer;
  int _cycles = 0;
  bool _pushed = false;

  @override
  void initState() {
    super.initState();
    // 450 ms > the 300 ms route transition, so each pop starts after the push
    // transition has settled and the platform views are fully composited.
    _timer = Timer.periodic(const Duration(milliseconds: 450), (_) {
      if (!mounted) return;
      if (_pushed) {
        Navigator.of(context).pop();
        _pushed = false;
        setState(() => _cycles++);
      } else {
        _pushed = true;
        Navigator.of(context).push(
          MaterialPageRoute<void>(builder: (_) => const PlatformViewsPage()),
        );
      }
    });
  }

  @override
  void dispose() {
    _timer?.cancel();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Center(
        child: Column(
          mainAxisSize: MainAxisSize.min,
          children: [
            // Keeps the raster thread busy between navigations.
            const CircularProgressIndicator(),
            const SizedBox(height: 16),
            Text('push/pop cycles: $_cycles'),
          ],
        ),
      ),
    );
  }
}

class PlatformViewsPage extends StatelessWidget {
  const PlatformViewsPage({super.key});

  static const int viewCount = 36;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('36 UiKitViews')),
      body: Column(
        children: [
          const LinearProgressIndicator(),
          Expanded(
            child: GridView.count(
              crossAxisCount: 6,
              padding: const EdgeInsets.all(8),
              children: List.generate(
                viewCount,
                (i) => Padding(
                  padding: const EdgeInsets.all(4),
                  child: ClipRRect(
                    borderRadius: BorderRadius.circular(8),
                    child: UiKitView(
                      viewType: 'plain-view',
                      creationParams: i,
                      creationParamsCodec: const StandardMessageCodec(),
                    ),
                  ),
                ),
              ),
            ),
          ),
        ],
      ),
    );
  }
}
```
