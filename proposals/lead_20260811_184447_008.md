# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[EPIC] Android v0.1 — native Kotlin WebView port with user-owned assets**

*Project description:*
## Objective

Deliver a reproducible Android v0.1 port of Red Alert 2 / Yuri's Revenge by preserving the existing deterministic TypeScript/Three.js game engine and adding a native Kotlin Android shell.

Baseline:

- Fork: `ImL1s/RedAlert2-Mac-iOS-iPad`
- Upstream: `ammaarreshi/RedAlert2-Mac-iOS-iPad`
- Initial fork pin: `991945d60a7139d3c4c438326abb6d3c093b2497`

This is **not** an engine rewrite, Wine port, x86 emulation project, or Flutter wrapper. The architecture is a secure full-screen Android WebView hosting the existing web engine, with native Android code owning lifecycle, storage authorization, local asset serving, renderer recovery, thermal/power state, audio focus, diagnostics, and packaging.

## Android v0.1 product contract

- Android 10 / API 29 or newer.
- Kotlin + AndroidX WebKit native shell; Compose is optional for setup/diagnostics only.
- Landscape-first phone, tablet, and foldable support.
- Offline RA2 and Yuri's Revenge skirmish using assets derived from a copy owned by the user.
- No EA retail assets committed to Git, uploaded by public CI, or distributed in public APK/AAB artifacts.
- Desktop-generated resource pack selected through Android Storage Access Framework.
- Verified and resumable seed into the existing origin-private filesystem for MVP.
- Existing TypeScript simulation, determinism, renderer, touch semantics, save/load, and AI remain authoritative.
- Production flavor has no arbitrary remote-content path, unsafe file access, or debug REPL.
- Public distribution stays blocked until the dedicated licensing/provenance gate is explicitly resolved.

## Architecture constraints

1. Preserve the shared TypeScript simulation and Three.js/WebGL renderer.
2. Do not add Flutter or another rendering engine around the WebView.
3. Do not use `file://`, `MANAGE_EXTERNAL_STORAGE`, broad filesystem permissions, or universal file URL access.
4. Serve local content from a strict HTTPS-style same-origin route, with path allowlisting and streaming for large files.
5. Avoid unrestricted `addJavascriptInterface`; keep the native shell contract typed, minimal, and origin-bound.
6. OPFS duplication is acceptable for v0.1 if verified and resumable. Native VFS is post-MVP research.
7. Any build embedding user-owned retail assets is `PRIVATE_TECHNICAL_PROBE` only and must be structurally excluded from CI uploads/releases.

## Release truth vocabulary

- `PRIVATE_TECHNICAL_PROBE`: local-only build that may contain the developer's own assets; never uploaded.
- `SIDELOAD_NO_RETAIL`: redistributable shell/source only; user supplies a verified pack.
- `PUBLIC_RELEASE_BLOCKED`: default until licensing/provenance is resolved.
- `PUBLIC_RELEASE_ELIGIBLE`: cannot be inferred from green tests.

## Epic acceptance criteria

- [ ] Clean clone builds a no-retail Android debug APK with documented commands.
- [ ] APK shows an honest setup screen when no pack is authorized.
- [ ] Valid RA2/YR pack can be selected through SAF without broad storage permission.
- [ ] Every consumed resource is bound to a versioned manifest and verified.
- [ ] Interrupted verification/seed resumes without trusting stale flags.
- [ ] Representative devices can start, play, save, load, background, resume, and exit a skirmish.
- [ ] RTS touch controls and cancelled gesture handling remain correct.
- [ ] Renderer death has bounded recovery and an honest terminal failure state.
- [ ] Thermal/power pressure may reduce rendering only, never simulation semantics.
- [ ] Production APK contains no retail MIX/CSF/media/map content and no hidden debug/network channel.
- [ ] CI fails closed on forbidden assets and release-flavor violations.
- [ ] A 60-minute representative-device soak passes crash, memory, AI-liveness, and structure-spam gates.
- [ ] Documentation clearly distinguishes private development, no-retail side-loading, and public-release eligibility.

## Non-goals for v0.1

- Native engine rewrite.
- Shipping retail game data.
- Google Play publication before legal/provenance approval.
- Full campaign parity.
- Production matchmaking.
- Native VFS, raw on-device retail conversion, controller parity, or LAN unless separately promoted.
