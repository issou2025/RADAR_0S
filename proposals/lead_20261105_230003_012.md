## Summary

- Editors and the owner of a shared Markdown note can draw together in each inline sketch. A sketch remains a fixed-size box in the note; it is not promoted to an infinite canvas.
- The shared note keeps its text CRDT. Each sketch ID gets a separate item-based sketch document alongside that text, reusing the stroke maps, chunks, tombstones, projection, presence and compaction used by `CanvasDoc`.
- The Y.Text body carries only a small sketch reference (stable ID and box size), never stroke JSON. The library body is a validated projection for the preview, search, API, export and offline reading.
- Drawing, erasing and lasso edits stream live. Offline edits stay in the local encrypted collab outbox and merge when the member reconnects.
- View and comment members see the latest drawing but cannot change it. Comment members retain the existing note-comment permission. Only edit and owner members may draw.
- Existing shared notes with sketch fences need a one-time, idempotent migration from fence JSON to per-sketch CRDT entries. Compatibility with older clients must be decided and gated before those notes can be edited with the new format.
- “Copy as canvas” remains available. Promotion that rewrites a shared note is still not offered.

## How it works for the user

### Desktop

A member with **Edit** or **Owner** opens a shared note in Split or Preview. Existing sketch blocks render as they do today. The user can draw with the same pen, pencil, marker, highlighter, eraser, partial eraser and lasso tools as a private sketch. A stroke appears locally as it is made; connected collaborators see its points arrive in chunks and see the contributor’s pointer, tool and assigned colour. A short delay batches the saved Markdown projection; it does not delay the live drawing.

**Insert sketch** in a shared note creates the fence and its empty sketch document as one shared edit. The box stays fixed at the selected size. There is no pan, zoom, text card, image card, arrow or canvas surface inside the sketch. “Copy as canvas” remains available from the sketch toolbar and leaves the shared note unchanged.

A member with **View** or **Comment** sees the current strokes and other members’ pointers, but has no drawing toolbar. A view member cannot comment. A comment member can use the shared note’s existing comment controls on note text; sketch-specific comments and per-stroke comments are not part of the proposed scope. The Share sheet and footer continue to identify their role.

### Phone

In the Flutter note preview, a member with Edit or Owner taps the sketch and draws with the stylus, mouse or the existing “Draw with a finger” setting. The note still scrolls when a finger is used for scrolling. Other members see the in-progress strokes and pointers. The same view-only state and “Copy as canvas” action appear to View and Comment members.

The phone opens the sketch through `kanso-mobile` and the Rust bridge, but now attaches that session to the shared note’s sketch document. It must not use the current private-note path that saves a replaced JSON fence after the idle timer.

### Offline and reconnection

When the member is offline but still signed in with the share keys available, drawing and text edits are kept in the local collab state and outbox. Show the connection state and this proposed message: “Offline. Your changes will sync when you’re back online.” When the member reconnects, Yrs merges queued operations with updates received from other members. Independent strokes survive; deleting one stroke uses a tombstone so an old offline copy cannot resurrect it. The offline queue and replay path for the new sketch maps is *(unverified)* until it is exercised through the mixed-document engine.

A collaborator’s changes that have not reached this device cannot appear in its offline preview or export. Reconnection merges them before the next projection. Signing out is not offline editing: a member without the engine and its keys is read-only, as today.

### Concurrent edits and removal

Two members drawing on one sketch create separate stroke IDs; they do not replace one JSON block. Erasing is an item operation. Partial erase tombstones the old stroke and adds the remaining pieces together, as on a shared canvas. Text edits continue through the note’s text CRDT.

Removing a sketch fence while someone is drawing is a cross-structure conflict. The proposed rule is that a removed fence tombstones its sketch document in the same Yrs transaction. The visible sketch disappears; later chunks for a sketch already known to be deleted are refused. If a draw and delete arrive concurrently while members are offline, the proposed behavior keeps the document tombstoned and retains concurrent ink with it for undo/recovery instead of silently discarding it. This mixed-document recovery behavior is *(unverified)*. The exact recovery and undo rule is an owner question below.

### Size and error wording

Use the shared-canvas thresholds for each SketchDoc: warn at 700,000 bytes and refuse new points at 1,000,000 bytes. In a shared note, the recovery action is **Copy as canvas**, which leaves the note unchanged. Proposed messages are: **“This sketch is nearly full. Copy it as a canvas to keep drawing without a limit.”** and **“This sketch is full. Copy it as a canvas to keep drawing.”** If the whole-note body cap is reached first, show: **“This note's sketches are full. Copy one as a canvas.”** A cap hit never writes truncated or invalid JSON. How to finish an in-flight stroke and resolve concurrent edits that jointly exceed a cap need the owner's decision below.

A malformed, duplicate-ID, deleted or unavailable sketch cannot be guessed from its block position. The app leaves surrounding text alone, marks the sketch unavailable, and offers the recovery action approved by the owner. It does not replace the first `sketch` fence it finds.

### Export, publishing, local API and MCP

The sketch’s stored Markdown projection remains the familiar `sketch` fence containing its current Canvas JSON, so HTML, PDF, published pages and Markdown exports use the existing renderer. A shared note is not locked and follows the normal shared-note export and publish rules. Export and publish should flush the local projection first; when offline they include only the latest state on this device. Flush behavior with a live shared sketch is *(unverified)* until the new session path is implemented and exercised.

`GET /note:<id>` and MCP `read-note` return the normal Markdown projection, not the internal Yrs state. List and search results should not return large stroke arrays as prose: keep the note’s text summary and replace each Kanso sketch fence with a short “Inline sketch” marker. Writes to a shared note that add, replace or remove a sketch must go through the sketch-aware shared engine path. A raw store write or MCP/API body replacement must not bypass the CRDT. No new raw Yrs endpoint is exposed.

### The pieces to add

#### Mixed text-and-sketch shared document

A shared Markdown note needs one Yrs document containing the note text and the sketch maps. The proposed root is:

```text
root
├─ title:    Y.Text
├─ body:     Y.Text             Markdown; a sketch reference holds ID and box size only
└─ sketches: Y.Map<sketch_id, SketchDoc>
     ├─ meta:    Y.Map           schema, width, height, deleted/tombstone, version
     ├─ nodes:   Y.Map<node_id, Y.Map>
     └─ strokes: Y.Map<stroke_id, Y.Map>
          └─ points: Y.Array    append-only point chunks
```

`SketchDoc` uses the same IDs, node/stroke maps, appended point chunks, `done` marker, tombstones and sanitized projection as `CanvasDoc`, but permits only the fixed sketch box and ink nodes. It has no canvas title, cards, edges, groups, pan or zoom. Refactor the item-map implementation so a `CanvasDoc` can own a root document and a sketch can live under its parent shared note’s Y.Map. Do not store a JSON string in a Y.Map and call it a CRDT.

All fence and sketch-document changes use one Yrs document and one transaction. That allows inserting a reference plus an empty SketchDoc, or deleting a fence plus tombstoning its SketchDoc, atomically. A sketch’s `kansoSketchId` is the map key. A sketch ID is unique within its shared note for its entire tombstone lifetime; it is never re-used after deletion.

The CRDT’s fence reference contains only the sketch ID and size. The library note’s `body` is a checked materialized projection: Kanso expands each reference from its SketchDoc into the existing full JSON fence before writing the note. The renderer, API `GET`, Markdown export, HTML/PDF export and publish continue to consume that projection. This keeps stroke JSON out of character-level merges while retaining the current local note format.

#### Sync, projection and presence

Add a mixed text/sketch shared document variant or a versioned extension to `CollabDoc`; do not represent a Markdown note as `SharedDoc::Canvas`. The engine merges ordinary prose through `CollabDoc` text operations and merges each SketchDoc with CanvasDoc item operations. Both use the existing sealed `Kind::Update` envelopes and local collab outbox. A document’s kind/schema is recorded and validated when a share is opened; malformed or unsupported state never silently loads as a plain text doc.

Add engine operations to open/sync a sketch, apply a local edit, stream a stroke, cancel or finish a stroke, set/clear a pointer and read remote pointers. Every operation takes the note’s share ID and sketch ID; there is no “first sketch” routing. Pointer presence adds `sketchId` to the current canvas pointer payload. It reuses the existing encrypted presence envelope, rate limit, sequence check and expiry. Role checks happen in the engine as well as in the UI: only Edit and Owner may mutate a sketch; viewers and commenters may receive pointers and drawing updates.

The engine projects the latest merged sketches into the note body no more often than the existing two-second canvas projection interval, and on detach/flush. A body write validates every fence and the full note length. It never uses `clamp_text` on JSON. If the projected body does not fit, it keeps the last good stored body, reports that the sketch is full, and refuses additional local edits. The state still has to remain readable from the collab snapshot; do not silently drop remote strokes to make the projection fit.

The target in #312 is the same 1 MB (1,000,000-byte) budget as a canvas for each per-sketch `CanvasDoc`, with “Move to a new canvas” when full. Today inline sketches are capped at 256 KiB each and 512 KiB together per note, so those shipped limits must be reconciled. The projected Markdown note also has a 1,048,576-character body cap, which can fill before an individual sketch reaches its canvas-sized ceiling. `MAX_FIELDS_JSON` is a 1.4 MB sync fields cap; shared note title and body are excluded from private sync, so that cap is not the shared sketch-state limit. The shared collab envelope separately caps each update at 256 KiB and each snapshot at 4 MiB. The engine’s 1 MiB compaction trigger is a snapshot cadence, not a size cap. The owner must decide what to do when the whole-note body cap is reached before a sketch reaches its own limit and how to handle points in a stroke that is already in flight. Test concurrent merges across each approved cap and keep the last good projection rather than truncating JSON.

#### Insert, delete, duplicate and undo

The shared editor’s insertion path writes a reference and creates a SketchDoc in the same transaction. Paste of a Kanso sketch fence is handled as an explicit sketch insertion: generate a fresh ID for the destination note, seed its sketch map from the copied Canvas JSON, and assign fresh IDs to any items that must not be shared with the source. A duplicated ID in the same note is rejected or repaired before the edit reaches Yrs; it never points two fences at one sketch.

A fence deletion tombstones the corresponding SketchDoc in the same transaction. Undo of the local deletion restores the fence and document together. Sketch drawing undo stays local to the member’s own operation stack and writes compensating item operations; it never undoes another member’s work. Remote edits are not included in local undo. How long a removed SketchDoc remains recoverable and how a draw racing a remote deletion is surfaced are owner decisions below.

The 2-second idle projection is not the durability boundary. Every live stroke update is persisted to the local collab state/outbox before the projection debounce. On close or note change, flush pending sketch and text operations before leaving. When a sketch doc is full, stop accepting points before an update that would violate the approved limit; finalize or cancel the accepted prefix using the owner-approved rule and show the existing full message. Never save a partial JSON fence.

#### Migration and older clients

When a new shared note is created, seed one SketchDoc per valid sketch fence before writing the first shared snapshot. For a pre-existing shared text note, parse each valid `sketch` fence from the current shared body, preserve its ID, box, node IDs, stroke IDs, points and tombstones, seed a SketchDoc, and replace the Y.Text JSON with the ID-and-size reference. Write a schema marker and migration update atomically; the operation is idempotent and does not rewrite an already-migrated sketch. Unknown or malformed `sketch` code fences remain ordinary text and are not consumed.

Migration must not lose note prose, comment anchors or a sketch’s existing strokes. Existing comments are anchored to sticky text positions, not sketch IDs; the placement of a comment anchored inside a legacy sketch fence after JSON replacement is *(unverified)* and needs a tested result. Concurrent migration by two members must not append the same legacy points twice; that race is *(unverified)*.

The current `SharedKind::parse` maps every unknown kind to Text. Add an explicit schema/capability rule before introducing mixed state. Older clients know the existing full-JSON fence but not the sketch map. They must never be allowed to write a migrated reference-only body as if it were ordinary Markdown. The safe proposal is to keep a full materialized body for reading, mark a migrated share’s schema, allow older clients to view the last projection where possible, and reject their writes until a compatible client opens it. Whether the collab service can enforce that writer gate, and what a downgraded client can render, must be verified before migration ships.

#### Local API, MCP, export and comments

`GET /note:<id>` and `read-note` return the full projected Markdown body. List/search return prose plus a short sketch marker, not stroke JSON. Search continues to use `sketch::index_text` so JSON numbers do not pollute the index. Writes that alter a sketch fence go through the mixed shared engine, which validates and translates the edit into text and SketchDoc operations atomically. API/MCP code may not write CRDT state or mutate the store body directly. If an API write cannot be expressed safely (for example a duplicate sketch ID or stale fence), it returns a conflict with no partial write.

Existing note comments remain in the comments log and retain their text anchors. Comment-role members may add, edit and resolve them under current rules but cannot draw. There are no per-stroke comments in this feature. A comment anchored inside a migrated sketch fence must remain visibly anchored or become a clear orphan; it must not disappear silently.

The existing sketch SVG renderer consumes the materialized fence, so HTML/PDF/publish and phone preview need no new drawing format. Export flushes the local projection first, excludes presence and Yrs metadata, and includes only content this device has merged. Shared notes remain un-lockable under the existing store guard.

## Security and privacy

| Threat | What stops it |
|---|---|
| Collab relay reads sketch contents | Text updates, SketchDoc updates and presence use the existing note-key sealed and signed envelopes. The relay receives opaque updates and presence. It can still observe envelope sizes and timing, as it can for text and canvases. |
| View or Comment member forges a drawing update | The engine checks `Role::may_edit` before enqueueing or applying local sketch operations. UI disabling is supplementary; the store still protects role-limited note text. |
| Stale offline stroke resurrects a deleted sketch or stroke | Sketch and stroke deletions are tombstones. Tombstones are retained through compaction under the same rules as CanvasDoc. Sketch IDs are not reused. |
| Bad or hostile CRDT data breaks the renderer | Sketch projection validates the fixed box, finite points, IDs, point counts and byte limits; `Canvas::sanitized`-style projection yields valid ink-only sketches. Invalid projection does not replace the last good body. |
| One member writes arbitrary note text or another sketch’s data through API/MCP | API/MCP writes route through the shared engine and enforce role, share ID, sketch ID, validation and size checks. Internal Yrs state is never an API field. |
| Shared content is exposed through a lock | A shared note cannot be locked or moved into a locked notebook (`guard_shared`). The member list grants access to the whole note and all of its sketches; there is no per-sketch permission boundary. |
| Export or publish exposes hidden collaboration state | Exports contain the normal visible drawing projection only. They do not contain member keys, Yrs updates, tombstones, cursors or presence. Publishing a shared note remains a deliberate normal publish action. |
| Comments disappear during migration | Migration maps or preserves sticky text anchors and tests comments in prose and in sketch fences before deleting legacy JSON from the text CRDT. |

## What this costs

The original #45 open-question estimate was about 1.5 weeks. This complete scope also includes safe migration, a mixed text/sketch projection, desktop and phone sessions, downgrade handling, shared-note API writes, and concurrency tests. The build-order rows total **19–27 developer days (about 4–6 weeks for one developer)**, including review and tests. A server-side legacy-client gate that requires additional service changes beyond step 4 adds about 3–5 days and must be estimated with the cloud work.

There is no new ink format or rendering dependency. The costs are the additional Yrs map state and updates, the local Markdown projection, a schema/migration path, one new pointer shape, regenerated mobile bridge code, and tests for two independent editors plus offline replay. The shared document must remain under the existing envelope limits, and the projected note body must remain under `MAX_BODY_LEN`.

## Open questions for the owner

Each recommendation is a proposal, not an answer. Costs are stated and are not used to choose.

1. **Mixed-document format and older clients.** Options: add a versioned text-with-sketches schema and gate legacy writes; keep the old full-JSON text CRDT with a translating adapter; or require the note to be stopped and re-shared before co-drawing. **Recommendation:** version the mixed document and refuse legacy writes after migration; keep an old-format projection for reading if it is safe. If the service cannot reject old writes, do not migrate an active share until the owner has confirmed the supported-client policy. **Cost:** 3–5 days if a server-side capability or update gate is needed. The behavior of a downgraded client and service enforcement are *(unverified)*.
2. **Who migrates existing shared notes, and when?** Options: first capable client to open; owner-only one-time migration; or stop/re-share after upgrading members. **Recommendation:** owner-authorized, idempotent migration, with other clients remaining read-only until the schema marker is committed. This avoids competing JSON-to-map seeds. **Cost:** 2–3 days plus compatibility tests.
3. **A fence is deleted while a member is drawing.** Options: deletion removes the sketch and concurrent ink; deletion hides a tombstoned sketch kept for undo/recovery; or pause deletion and ask the member. **Recommendation:** deletion wins the visible note, while the tombstone retains concurrent ink until the approved recovery window; known-late chunks are refused. **Cost:** 2–3 days. Decide whether an editor can restore a remote deletion or only recover a private copy.
4. **Copy/paste and duplicate sketch IDs.** Options: refuse a duplicate fence; let two fences point at the same document; or assign a new ID and clone the copied strokes. **Recommendation:** assign fresh IDs on every paste into a note and reject any duplicate that remains after normalization. **Cost:** about 1 day.
5. **Undo across text and sketch state.** Options: separate text and sketch undo; one combined note undo for everything; or combine only fence lifecycle operations while keeping stroke undo local. **Recommendation:** fence insertion/deletion and its map change are one undo step; a member’s stroke/erase undo is local and never undoes another member’s operations. **Cost:** 2–3 days.
6. **Size cap hit mid-stroke.** #312 sets the 1,000,000-byte canvas budget for each sketch; today inline sketches are capped at 256 KiB each and 512 KiB per note, and the projected note has its own 1,048,576-character cap. If the whole-note cap hits first, options are to refuse the next chunk and keep the accepted prefix, cancel the entire in-flight stroke, or keep its unsent tail for recovery. At the per-sketch cap, the same choices apply. **Recommendation:** stop before an update would make the projection invalid, keep the last good body, and use the proposed “Copy as canvas” wording above. **Owner decision needed:** choose whether to finalize accepted points or cancel the in-flight stroke, and what should happen to any unsent tail. **Cost:** 1–2 days for cap reconciliation and concurrent-crossing tests.
7. **Comments and API/MCP editing.** Options: preserve existing note-text comments and expose only projected Markdown; add stable comments on sketch IDs; or add full stroke/sketch comment tools and API operations. **Recommendation:** preserve note comments, make list/search summaries omit JSON, return the full projected fence from read-note, and route body writes through the shared engine. Do not add per-stroke comments in this issue. **Cost:** 2–3 days for the API/MCP routing and summaries; 3–4 additional days for sketch-targeted comments.
