# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: Formidable 0.1.0**

*Project description:*
## Problem Statement

Building forms in Flutter takes too much code, and that code is easy to get wrong. Developers who want reactive forms have to put up with the following:

- They build the form structure imperatively, and look up controls by string name or dotted path. Typos and type mismatches only show up at runtime, as casts that fail.
- Validation rules are attached by hand to every control. Rules that span several fields need string keys, and they work through side effects that overwrite errors set by other rules.
- Common validators keep being rewritten from scratch in every project: IBAN, password strength, date ranges, "required if another field is set" and many more.
- Converting a field's value to what a widget shows, such as an `int` shown as text or a `DateTime` shown as a formatted string, needs verbose, stateful adapter classes. When parsing fails, the value silently becomes null.
- "Required" and "nullable" get mixed up. A null value cannot be a legitimate choice, as in a three-option radio group where one option means "no preference".
- UI updates are coarse. A widget that only cares whether the form is valid rebuilds on every status change anywhere in the form, and reactive builders often have no synchronous initial value.
- Getting a typed domain object out of a valid form needs boilerplate, and that boilerplate can crash when the form is not actually valid.
- Translating error messages is clumsy. Error keys are strings, and global message configuration does not react to changes in locale.
- Recent Flutter releases move Material and Cupertino into separate `material_ui` and `cupertino_ui` packages. A form library should depend only on what it needs, and should work with those packages.

## Solution

Formidable is a reactive form library for Flutter that is built for developer experience. Its main mechanisms are:

- **A Schema declares the form.** The developer writes a plain Dart class, the Schema, and marks it with the `@Formidable()` annotation. Each final field becomes a Field. Validators, Normalizers and cross-field rules are declared as annotations on those fields.
- **The generator produces a typed Form.** For each Schema it generates a Form class, so `SignUp` becomes `SignUpForm`. Every Field is reached through a typed handle. There are no string paths and no casts.
- **Required-ness comes from the Schema type.** Non-nullable Fields without a default are required, and nullable Fields are optional. Unset is a state separate from null, so null can be a legitimate choice.
- **Typed output.** When the Form is valid, it produces an instance of the Schema through a sealed submit result or a nullable synchronous value.
- **Bloc-style reactivity, without bloc.** Builder, Listener and Selector widgets work at Field level and at Form level. They get a synchronous initial value and rebuild selectively.
- **Two layers of UI binding.** A headless Binding works with any widget, and thin convenience widgets for Material and Cupertino are built on top of it.
- **Pure Codecs replace stateful adapters.** A Codec converts between a Field's value and a widget's value. A parse failure becomes a typed Validation Error.
- **A large validator catalog ships with the library.** It covers strings, formats, numbers, dates, collections, files, choices, network, finance, locale codes and cross-field rules. Every message is localized in English, Italian, Spanish, French and German.

The first release is 0.1.0. Signatures and behavior are expected to change across 0.x releases.

## User Stories

### Declaring a form

1. As a developer, I want to declare a form by annotating a plain Dart class with `@Formidable()`, so that the form's structure lives in one readable place.
2. As a developer, I want each final field of my Schema to become a Field automatically, so that I don't have to register controls by hand.
3. As a developer, I want the generator to produce a `SignUpForm` class from my `SignUp` Schema, so that the naming is predictable.
4. As a developer, I want my Schema to stay a plain class with no dependency on other code generators, so that I'm not tied to extra packages.
5. As a developer, I want the generator to match constructor parameters to fields by name, whether they are positional or named, so that I can write my constructor the way I prefer.
6. As a developer, I want a build error when a final field is missing from the constructor, or when a constructor parameter has no matching field, so that mismatches never reach runtime.
7. As a developer, I want getters on my Schema to be ignored, so that I can keep computed properties on the Schema.
8. As a developer, I want fields inherited from a superclass to be included when they appear in the constructor, so that I can share common fields between Schemas.
9. As a developer, I want a build error when I annotate a generic Schema, so that I know right away it's not supported.
10. As a developer, I want the generated code to stay small, so that my builds are fast and the output is easy to read.

### Required and optional Fields

11. As a developer, I want a non-nullable Field without a default to be required automatically, so that I don't have to repeat what the type already says.
12. As a developer, I want a nullable Field to be optional automatically, so that leaving it blank gives null in the output.
13. As a developer, I want a Field with a constructor default to use that default when it is left Unset, so that "intentionally empty" values such as an empty notes string work naturally.
14. As a developer, I want to put `@Required()` on a nullable Field, so that the user has to make a choice even when null is one of the choices.
15. As a developer, I want a warning when `@Required()` sits on a non-nullable Field, so that I notice annotations that do nothing.
16. As a user filling in a form, I want a three-option radio group where one option means "no preference" to accept that option as an answer, so that I'm not forced into yes or no.
17. As a developer, I want a completely empty text input to count as Unset, so that blank text never ends up in my output as an empty string.
18. As a developer, I want trimming to be opt-in through `@Trim()`, so that whitespace the user typed on purpose is kept unless I decide otherwise.
19. As a developer, I want an empty multi-select to count as Unset, so that a required multi-select reports a missing value.
20. As a developer, I want to check whether a Field is set separately from reading its value, so that I can tell "nothing chosen" from "null chosen".

### Validators

## Implementation Decisions

### Architecture and packages

- **Five packages, all at the same version, starting at 0.1.0.**
  - The core: runtime, annotations, Validators, Normalizers, Codec contracts and validation errors. Pure Dart, no Flutter dependency.
  - The generator: build_runner and source_gen.
  - The Flutter bindings: Form Scope, Binding, builders, listeners, selectors, configuration, localizations and pop scope. Depends only on the Flutter widgets library.
  - Material convenience widgets, built on `material_ui`.
  - Cupertino convenience widgets, built on `cupertino_ui`.
- **Minimum versions:** Dart 3.8 for the core, Dart 3.11 for the generator (ADR-0004), Flutter 3.50 for the Flutter packages.
- **Repository layout:** a melos monorepo with a single example app, docs on docs.page, and GitHub Actions workflows for analyze, test and publish. Publishing uses pub.dev automated publishing through OIDC, triggered by tags, and waits for pub.dev to index each package before publishing the next. The Flutter packages need a publish job that can run Flutter.
- **Generator output:** a part file next to the Schema, declared in the Schema's library.
- **The runtime is written from scratch** and accesses Fields through typed handles (ADR-0001).
- **Reactivity is our own.** State snapshots are immutable and notification is synchronous and compatible with `ValueListenable`. Bloc is not a dependency (ADR-0002).
- **Unset and null are separate states.** "Required" means "not Unset" (ADR-0003).

### Generator contract

- **Constructor and fields.** The generator reads the Schema's unnamed generative constructor and matches its parameters to final fields by name. It ignores getters. Inherited fields are included when they appear in the constructor.
- **Build errors.** The generator fails the build for:
  - a final field missing from the constructor;
  - a constructor parameter with no matching field;
  - a generic Schema;
  - a set of Schemas;
  - a Validator whose type doesn't fit the Field;
  - a cross-field reference to a Field that doesn't exist or has an incompatible type.
- **Warning.** `@Required()` on a non-nullable Field produces a warning.
- **Rebuilding annotations.** Annotations are const instances. The generator rebuilds Validator and Normalizer expressions in the generated code using only the public analyzer API.
- **What gets generated, and nothing else:**
  - the Form class with one typed getter per Field (Nested Form, Field Array and Dynamic Form getters included);
  - a constructor from an existing Schema instance;
  - a partial constructor, in which an omitted or null argument leaves the Field Unset and Passthrough Fields are required when non-nullable without a default;
  - typed named parameters for every injected Async Validator and async Form Validator;
  - a typed patch method;
  - construction of the output;
  - the Form Scope with its `.value` variant;
  - a context extension for lookup.

  All behavior lives in the generic runtime.

### Presence rules

- **Default required-ness from the type.** Non-nullable without a default means required. Nullable means optional. A Field with a default starts with a value.
- **`@Required()`** applies only to nullable Fields. It makes Unset block submit, and a chosen null still counts as a value.
- **Output of an Unset Field at submit,** checked in order:
  1. the default, if the Field has one;
  2. null, if the Field is nullable;
  3. otherwise a required Validation Error.

  For Fields marked `@Required()`, Unset always produces the error.
- **What counts as Unset** is decided by the Codec or widget. Empty text is Unset. An empty multi-selection is Unset. A radio option that represents null sets the value to null. Whitespace-only text is a value unless `@Trim()` is declared.
- **Passthrough Fields** can never be Unset, and their handle type has no clear operation.

### Validation pipeline

- **Order on every change, whether from the user or from code:** Normalizers, then Form Effects, then synchronous Field Validators, then Form Validators, then Async Validators.
- **When Validators run.** Validators run only when the Field has a value. A Validator typed for a non-nullable value is skipped when the chosen value is null.
- **Built-in cross-field rules.**
  - They are annotations on the Field that receives the error. They reference other Fields by Dart symbol, which the generator resolves to typed code.
  - Custom cross-field rules are Form Validator classes typed on the Form.
  - Errors from Form Validators are added to Field errors, never written over them.
- **Async Validators.**
  - They run only when the Field has a value and its synchronous Validators pass.
  - Debounce is per Field. Only the most recent result counts. The Field is pending while they run.
  - Going back to Unset cancels the check.
  - `submit()` waits for pending checks.
- **Async Form Validators** follow the same lifecycle. They declare the Fields they depend on, and run only when those Fields have values and pass synchronous validation.
- **Form Effects.**
  - They run synchronously after a change and before validation, and also once when the Form is created.
  - Debug builds detect re-entrant loops.
  - Changes they make don't mark Fields as touched.
- **Disabled Fields** skip Validators but still contribute to the output and still follow the presence rules.
- **Combinators.** The only built-in combinator is `AnyOf`.

### Built-in catalog for 0.1.0

- **Scope.** Every entry marked v1 or v1-cross in the validator catalog research document.
  - Field Validators: strings, formats, numbers, dates, collections, files, choices, network, finance, locale codes.
  - Cross-field rules: must match, different, compare, date range order, the required-if/with/without family, the prohibited family, conditional acceptance, at least/exactly/at most one of, contained in list, unique by key.
- **Excluded from the catalog:**
  - Checks that need large datasets or a server: full phone metadata, postal codes and tax IDs by country, uniqueness checks.
  - Parsing concerns, which belong to Codecs.
- **Messages.** Every built-in Validation Error has a message in English, Italian, Spanish, French and German.

### Form API

- **Writing Fields.**
  - Field handles have a setter typed exactly as the Field type, a clear operation (except on Passthrough Fields), focus and unfocus, and their state snapshot.
  - Writes to the Form are patch (typed, atomic, one notification; an omitted argument leaves the Field unchanged), replace and reset. Commit makes the current state the initial state.
  - There is no silent-update flag.
- **Dirty** compares value and presence with the initial state. The history-based "pristine" concept is not exposed.
- **Submit.**
  - `submit()` is asynchronous and returns a sealed result: valid with the Schema instance, or invalid with the errors.
  - It marks every Field as touched and focuses the first invalid Field in Schema declaration order.
  - It does not track the state of the caller's own side effects, so there is no "submitting" state.
- **Synchronous value.** `value` returns the Schema instance only when the Form is valid and not pending, and null otherwise.
- **Applying errors** adds Field-level and Form-level errors. Field-level ones clear on the next change to that Field.
- **Field Arrays** have add, insert, remove at index, move, clear, a stable identifier for each item, and their own Validators.
- **Dynamic Forms** register Fields with an explicit type and runtime Validator instances, do a type-checked lookup by key, remove Fields, and register Nested Forms. Their output is a map.

### Flutter layer

- **Form Scope.**
  - The default constructor creates the Form and disposes it.
  - The `.value` constructor only exposes the Form.
  - Lookup works through a context extension and a static accessor.
- **Form-level widgets.**
  - Form Builder, Form Listener and Form Selector take an optional Form. Without one, they look it up in the tree and throw an error that names the missing scope if it isn't there.
  - When they look it up, they need the Form type and the Schema type as type parameters.
  - There is no dedicated value-builder widget: the "enable button when valid" pattern uses the Form Selector over the Form's value.
- **Field-level widgets.** Field Builder, Field Listener, Field Selector and Field Array Builder always take an explicit handle.
- **Initial value.** Every builder has a synchronous initial value.
- **Headless Binding.** It exposes value, whether it is set, error text, change and touch callbacks, focus node, text controller and enabled state. It owns the focus node and text controller unless they are supplied, in which case it uses them without disposing them.
- **Focus and touched.**
  - A Field becomes touched on blur for focusable widgets and on first interaction for the others.
  - When several widgets bind to the same Field, focus goes to the last one registered.
  - Schema declaration order sets keyboard "next" navigation and submit focus. Fields with no binding are skipped. Each widget can override this.
- **Codecs.**
  - A Codec is pure: format to the view type, and parse to a result that is either a value, Unset, or a typed parse error.
  - The raw view input is kept when parsing fails.
  - Default Codecs come from a registry chosen by the pair of types. The registry can be extended in the configuration widget.
- **Error display.** The policy is when touched, when dirty, or on submit. It can be set globally and per Form, and defaults to when touched.
- **Messages,** looked up in order:
  1. the widget override;
  2. the typed registry in the configuration widget;
  3. the localizations delegate;
  4. the error's string form.

  The configuration is an inherited dependency, so changes cause a rebuild.
- **Pop scope.** It is driven by dirty and has a callback for showing a confirmation.

### Naming

- **Library types.** Every public library type starts with `Formidable`: Field, Field Array, Field and Form state, submit result, Validator, Async Validator, Form Validator, Async Form Validator, Effect, Normalizer, Codec, Validation Error, Binding, builders, listeners, selectors, configuration, localizations, pop scope and the convenience widgets.
- **Annotations.** The class annotation is `@Formidable()`. Validator, Normalizer and other Field annotations have no prefix.
- **Generated types** use the Schema name with the `Form` and `FormScope` suffixes.

## Testing Decisions

- **What makes a good test.** It exercises public behavior through one of the agreed seams and makes assertions on observable results: state snapshots, submit results, notifications, rendered text, focus and build diagnostics. It never asserts on private members, on how the runtime is structured internally, or on the exact text of generated code.
- **Seam 1: the generated Form, in pure Dart.** This is the main seam.
  - A test-only package declares real Schemas. The real generator processes them, and the tests drive the generated Forms only through their public API.
  - It covers the runtime, the generated code, presence rules, Validators, cross-field rules, Form Validators, Async Validators with a fake clock, Normalizers, Form Effects, patch, replace, reset and commit, dirty, submit, applied errors, Field Arrays and Dynamic Forms.
  - Built-in Codecs are pure functions, so this seam also covers them directly.
  - Tests run with `dart test`.
- **Seam 2: widgets.** Widget tests mount a generated Form Scope with Material and Cupertino convenience widgets and real generated Forms. They simulate typing, tapping and focus changes, then make assertions on displayed text, error messages, focus movement, keyboard actions, pop scope behavior and localized messages. The headless Binding is tested through this seam, not on its own.
- **Seam 3: generator diagnostics.** Builder tests feed invalid Schemas to the generator and assert that the expected build error or warning is reported, covering every diagnostic in the generator contract above.
- **No golden tests** of generated output.
- **Prior art.** The repository has no tests yet. These three seams set the patterns that all later tests follow.

## Out of Scope

- Form Map Fields, meaning a map from keys to Schemas as keyed Nested Forms. Planned for a later release.
- Locale-specific Validators that need large datasets: phone numbers checked against numbering plans, postal codes, VAT numbers and tax IDs by country, passports. Planned as a separate package later.
- Convenience widgets that wrap third-party input packages. Planned later as satellite packages built on the headless Binding.
- An adapter for bloc.
- Forms with no Schema at all. Dynamic behavior is only available inside a Schema, through Dynamic Forms.
- Generic Schemas.
- Integration with other code generators for the Schema class.
- Exposing a history-based "edited at least once" flag, separate from touched and dirty.
- Tracking the state of the caller's own submit side effects.
