## Agent Brief

**Category:** enhancement

**Summary:** Give every build a log trail, an in-app way to upload the database and logs to S3, and the owner's phone a debuggable build that installs over the release app without losing data.

**Current behavior:**
- **The Flutter app logs nothing.** It has no logging calls and no global error handler, so an API decode failure leaves no trace anywhere.
- **The database can't be pulled off the phone.** Release builds aren't debuggable, so adb can't copy the app's database.
- **Export DB was dropped in the port.** The previous app had a developer-only "Export SQLite DB" action. It uploaded the database to an authenticated backend endpoint, which wrote it to S3. Three problems:
  - **The endpoint is orphaned.** It's still live in prod, but nothing in the Flutter app calls it.
  - **Every export overwrote one shared S3 key.**
  - **The bucket deletes everything after one day.**
- **The API gateway keeps no access logs.**

**Desired behavior:**
1. **Logging in every build.**
   - These go to the platform log under a stable `glean` tag, and to a small rotating log file in the app's support storage:
     - API errors and response-decode errors, naming the endpoint and the missing or invalid field;
     - uncaught Flutter framework errors;
     - uncaught async errors.
   - Never log auth tokens or full request or response bodies.
2. **Export diagnostics, restored and fixed.**
   - **Where it lives.** A Settings action, hidden behind a developer mode that can be unlocked on release builds. The recommended unlock is tapping the version label 7 times; see the triage notes.
   - **What it uploads.** A *consistent snapshot* of the database (not the live file) plus the rotating log file, through the existing authenticated export endpoint.
   - **Endpoint changes.** The endpoint accepts both files, writes them under a per-user, timestamped prefix (`db-exports/<user id>/<UTC timestamp>/`), and returns the location. That prefix keeps objects for about 30 days, not the bucket's 1-day expiry.
   - **No allowlist.** It only ever uploads the signed-in user's own data.
3. **The owner build.**
   - **What it is.** A release-speed build with Android's debuggable flag on, the **same application id and the same release signing key** as tester builds. It installs over the existing app and keeps all data, so adb can copy the database and log file off the phone and stream the log live.
   - **Where it's built.** On gordon, and installed directly over adb. The toolchain and an adb connection over Tailscale already exist.
   - **Signing key handling.** The key is read from the password manager at build time into a temporary file only the owner can read, and deleted afterwards. It's never written into the repo or left on disk.
   - **Version codes are build timestamps (maintainer's decision, 2026-10-15).** Every build, Codemagic tester or gordon owner, sets its versionCode to the **minutes since 2024-01-01 00:00 UTC** at build time.
     - That always increases, whichever pipeline built last, so Android never refuses an install as a downgrade. Neither pipeline needs to know about the other: no reading the phone, no shared counter.
     - The first timestamped build (around 1.47 million) installs over today's versionCode 4.
     - versionName ("1.0.0") is unchanged and independent. Android never compares it.
     - Codemagic's own build number stays in the release notes for people.
   - **Tester builds stay non-debuggable.**
4. **Separately:** turn on access logging for the API gateway.

**Key interfaces:**
- **The app's API client error types.** The API exception and the response-decode exception are the main things logged.
- **The app's global error hooks:** the framework error handler and the platform dispatcher's error handler.
- **The export endpoint's contract.** Today it takes one database file and writes one fixed key. It changes to take a database snapshot plus a log file, write per-user and timestamped, and return the stored key.
- **The receipts bucket's lifecycle configuration.** It gets a longer-retention rule for the export prefix only.
- **The Android release build configuration.** It needs a debuggable owner variant with the same id and key, plus a version-code scheme shared with the tester build pipeline.
- **The build-number argument in both pipelines.** Codemagic's tester workflow and the gordon owner-build command both pass the timestamp versionCode instead of Codemagic's counter.

**Acceptance criteria:**
- [ ] A forced response-decode error on a release build appears in the exported log file, and on an owner build it also appears in the platform log under the `glean` tag.
- [ ] Export diagnostics on a release build stores a database file that opens with `sqlite3`, plus the log file, under a per-user, timestamped prefix that still exists 7 days later.
- [ ] Two exports in a row produce two separate prefixes; nothing is overwritten.
- [ ] Exported logs contain no auth tokens.
- [ ] Installing the owner build over a tester build keeps the pantry, plan and shopping list, and adb can then copy the app's database. This is proven first on an emulator with a tester build and data installed, and only then on the owner's phone, after a verified export.
- [ ] A tester build made after an owner build still installs over it, and the other way round. Both pipelines set versionCode to minutes since 2024-01-01 UTC.
- [ ] Two owner builds in a row both install with `adb install -r` with no manual numbering. The release notes still show Codemagic's build number.
- [ ] Tester builds are verified non-debuggable by an automated check.
- [ ] API gateway access logs are being written.
- [ ] Before the first owner-build install, a verified Export diagnostics of the phone exists: it downloads, opens with `sqlite3`, and its row counts match.
- [ ] The owner build never installs with a lower version code than the installed app, and never by uninstalling first. Only `adb install -r` with the release key is used.
- [ ] The project's agent guidance for the Flutter app is amended in the same PR. Its "User data safety" section currently says phone updates go through Codemagic. It should also allow the release-key owner build installed with `adb install -r`, under the conditions above.

**Out of scope:**
- Crash-reporting services (Crashlytics, Sentry); possibly later.
- Restoring a backup onto a phone (#121).
- Recovering logs from before this ships.
