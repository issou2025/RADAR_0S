## Summary

**Reviewed by three adversarial reviews on 2026-09-03. The original framing was wrong and its
central safety claim was false. This issue is now the tracking issue for a five-way split; see
"Split" at the end. Nothing here should be implemented before the blocker in §1 is closed.**

The toolkit analyzes Screaming Frog exports. Mode B requires a human to run a crawl and click
through export dialogs, so the toolkit's own thesis — a local CLI and stdio MCP an agent can
drive — stops at the one step that needs hands.

That, not the licence, is the reason to build a collector. Anyone doing paid audits already owns
Screaming Frog; it is the cheapest line item in the business, and "so buy one" is a fair answer
to a licence argument. The honest argument is different: **an agent cannot click thirty export
buttons.** A native collector is what makes `seohead audit <url>` possible unattended, in Docker,
in CI, on a VPS.

Everything below is scoped by that. It is not Screaming Frog parity and must never be sold as
such.

## Blocker: the invariant this whole design rested on does not exist

The previous revision of this issue promised: "missing sources stay in `exports_missing`, so
dependent checks are skipped rather than reported clean." **That is not what the code does.**

- `LoadedExports.missing` is populated in `sf/core/loader.py:137-140` and then written straight
  into the report at `sf/core/audit.py:148`. **No code reads it to skip anything.** It is
  cosmetic metadata.
- Skipping is per-check and hand-written (`ctx.skip()` in `rules.py`, `inlinks.py`,
  `heuristics.py`, `sitemap.py`). Only **19 of the 96 checks** carry an explicit skip path.
- So a check whose evidence a native crawl cannot produce does not report "skipped". It reports
  **nothing**, which the report renders as clean.
- And it gets worse arithmetically. `aggregate.py` computes `100 - (penalty / n_pages) * 10`.
  Fewer checks firing means less penalty means a **higher** score. A native crawl would score
  the same site *better* than a Screaming Frog crawl, purely because it measured less.

That is the same false-green defect fixed in #7, reappearing structurally rather than in one
function.

**Consequence, and it contradicts a rule this issue previously stated.** The earlier revision
said "no SF code path may be refactored on the way to mode C". That rule cannot survive this
finding. A check-precondition layer — each check declares the fields and frames it requires, and
the engine skips it when they are absent — is prerequisite work **inside `seohead/sf`**, and the
health score must be normalized by the checks that actually ran, or suppressed entirely for a
partial evidence source.

This is split out as its own issue and **blocks everything else here**. Building the collector
first would ship a tool that flatters broken sites.

## The first slice is list mode, not breadth-first crawling

`seohead crawl --urls <file>` → bounded fetch → projection → the existing checks.

It is a strict subset of the crawler: no frontier, no scope model, no politeness ceiling, no
traps, deterministic by construction. And it does three real jobs immediately — verify a redirect
map after a migration, re-check the forty URLs a developer says are fixed, audit a Search Console
URL export.

Breadth-first discovery lands second, on the same projection. Shipping BFS first would ship a
worse Screaming Frog, and nobody switches to that.

## Two modes, both first-class

| Mode | Input | Status after this work |
|---|---|---|
| A — Screaming Frog | licensed SF CLI crawl | unchanged, still the reference |
| B — SF exports | ready CSV/XLSX exports | unchanged, still the default in CI |
| **C — native crawl** | start URL, no SF licence | **new** |

Mode C is an additional evidence source, not a replacement. Every mode feeds the *same*
96-check pipeline and produces the same `audit.json` contract. Screaming Frog remains the
reference implementation the native crawler is measured against: where they disagree, SF is
assumed right until proven otherwise.

Concretely: the existing SF regression tests must stay green and unmodified. Note that the
earlier blanket rule "no SF code path may be refactored on the way to mode C" is **withdrawn** —
see §Blocker: the precondition layer is unavoidable SF work, and pretending otherwise is what
produced the false invariant in the first place. The narrower rule stands: SF behaviour does not
change, only its ability to declare what it could not measure.

## Module boundary — the crawler must not blur into the analyzer

The crawler collects evidence. It never decides what is wrong. Ownership of checks,
severities, fingerprints, health score, `audit.json`, tasks and reports stays entirely with
`seohead/sf`.

```text
start URL
  -> seohead/crawl          bounded collector, HTTP + parsing only
  -> crawl.v1               collector output (pages + link edges)
  -> seohead/crawl/evidence projection onto the existing LoadedExports contract
  -> seohead/sf             unchanged 96-check pipeline
  -> audit.json / audit.md / tasks
```

Rules that keep the boundary real, and that should be enforced by the existing CI contracts
job rather than by review discipline:

1. `seohead/crawl/**` must not import `seohead.sf`, `seohead.servers` or `seohead.cli`.
   It already holds for `sf`, `tools` and `recon`; extend the same grep to `crawl`.
2. `seohead/sf/**` must not import `seohead.crawl`. The analyzer stays unaware of where its
   evidence came from. The only meeting point is the `LoadedExports` contract.
3. Nothing in `seohead/crawl` writes an issue, a severity or a score. If a reviewer finds the
   word "severity" in that package, the boundary has been crossed.
4. The crawler is optional at import time: the package must remain importable and the CLI must
   remain usable with the crawl extra uninstalled.

## The point is site-wide reach, not new extractors

Most of what a crawl should report already exists here as **single-page** tools. The value is
applying them to a corpus, because the interesting questions are set questions:

| Already implemented | Where | What site-wide reach unlocks |
|---|---|---|
| JSON-LD / Microdata / RDFa | `tools/parser._extract_jsonld`, `tools/schema.py` | schema coverage and per-type validity across the site |
| title / description / canonical / robots / OG | `tools/parser.py`, `tools/social_meta.py` | duplicate and missing meta — unanswerable on one page |
| analytics fingerprints (GTM, GA4, Metrika, Matomo) | `recon/tech.py` | **"is the counter on every page?"** |
| raw vs rendered DOM comparison | `tools/render.py` | which templates actually need JavaScript |
| citability scoring | `tools/citability.py` | which sections answer engines can quote |

Design rule: the collector **calls** these, and a second copy of JSON-LD parsing inside
`seohead/crawl` is a defect.

**But the rule has a hole that has to be fixed first.** `recon/tech.py` exposes only
`detect_tech(url, timeout)`, which fetches its own page; there is no `detect_from_html(html,
headers, cookies)`. Used per page in a crawl it would double every request — the exact
duplication this rule forbids. The same applies to any tool whose entry point takes a URL. So a
prerequisite task is to split fetch from analysis in those tools, which contradicts the earlier
"nothing below should be rewritten" and is acknowledged as such.

### Tag coverage, with the subtleties the first draft missed

`recon/tech.py` signatures are **name-only substring markers with no capture groups**, so
"two conflicting GA4 ids" is currently unanswerable. It needs id capture (`GTM-[A-Z0-9]+`,
`G-[A-Z0-9]+`, `ym\(\d+`, `UA-`).

And the naive report would be wrong in ways that cost credibility:

- GTM commonly injects GA4, so a page with GTM and no gtag is **correct**, not broken.
- Consent mode gates tags; a pre-consent static fetch sees less than a real visit.
- Tags that only fire after JavaScript are invisible to a static crawl.
- `dataLayer` presence is not container presence.
- Server-side tagging on a first-party subdomain is invisible to substring fingerprints entirely.

Therefore: report per **template**, not per path prefix (one prefix holds several templates),
include captured container ids, and stamp every row with how it was measured — "static HTML,
pre-consent, no JavaScript". Without that stamp we hand a client "Metrika missing on 12% of
pages", they discover it is GTM-injected, and the audit loses its authority.

### Content as Markdown — two renderings, and the second one is the interesting one

Demoting this in the previous revision was wrong. Every crawled page produces **two** Markdown
renderings, and they answer different questions:

**1. `content.md` — main content only.** Header, footer, navigation and asides stripped.
Resolution order for the main region: `<main>`, then `[role="main"]`, then `<article>`, then the
largest contiguous text block; the chosen strategy is recorded per page so a wrong pick is
visible rather than silent. This is the representation that is worth diffing between crawls,
worth feeding to `citability.py`, and worth handing to a model — a flat text blob is not.

**2. `full.md` — everything, header and footer included.** Not a debug artifact. It exists so
the crawl can answer a question that is unanswerable on a single page:

> **Is the boilerplate actually the same everywhere?**

Hash the header, navigation and footer regions per page, group pages by hash, and report every
group that is not the dominant one. That single derivation catches a family of real defects that
no per-page tool can see:

- a navigation block that lost links on one template, quietly cutting internal linking to a
  whole section;
- a footer that differs on old pages because they were never migrated to the current template;
- a menu that renders differently under one language or one URL branch;
- header markup that changes only where a legacy template survives — usually the same pages that
  are also missing the analytics tag, which is why this pairs naturally with tag coverage.

Reported the same way as tag coverage: as a fraction, grouped by template, with the minority
groups listed and a sample URL each. "The footer on 340 pages is missing the contacts block" is a
finding a client can act on; "some pages differ" is not.

**Determinism.** Boilerplate hashes are computed from our own DOM regions and are deterministic,
so they stay inside the determinism gate. The Markdown text itself, if boilerplate removal ever
uses trafilatura, is version-dependent output and therefore lives outside the byte-comparison
gate with its version pinned and recorded in the bundle.

### Custom extraction — missing entirely from the first draft, and worth more

`--extract name=<css-or-xpath>` answers the questions that arrive every week: which pages still
carry the old phone number, a staging canonical, the previous GTM id; which product pages have no
price. A Python plugin means a code change per client; Screaming Frog needs a text box. This
should outrank Markdown extraction.

## JavaScript rendering is in scope, and needs a gate before it exists

Required, not optional: sites whose raw HTML is an empty shell are common, and a static-only
crawler reports them as broken. The capability already exists — `tools/render.py` drives
Playwright, builds comparable raw and rendered snapshots, extracts JSON-LD types from both, and
detects an empty shell.

Sequencing: the static contract ships first because rendering multiplies per-URL cost by roughly
an order of magnitude, and a rendered crawl whose static projection is already wrong is
untestable. Rendering then arrives **selectively** — detect JS-dependent templates on a sample
per URL pattern, re-fetch only those within a separate budget, and record per page which
representation its evidence came from so no check mixes the two.

**Gate that must exist before then, because the current one does not cover it:** an invalid crawl
is currently only one that fetched nothing. A Next.js shell fetches fine, yields one URL and a
clean-looking audit. So: shell detected, or a start URL yielding zero internal links, must set
`render_required` and refuse a health score.

Two security preconditions inherited from `render.py` and not yet met: the browser route guard
uses `page.route("**/*")`, which does not cover WebSocket connections and is bypassed by service
workers under the default `service_workers="allow"`; and Chromium re-resolves DNS itself after
`route.continue_()`. Selective rendering must not ship before those are closed.

## Prior art: what the open-source field already solved

Licences verified against the GitHub API on 2026-09-03. This table is the reason the
implementation should be short: almost every hard part has a known good answer.

| Project | Licence | Lang | Worth taking |
|---|---|---|---|
| [Scrapy](https://github.com/scrapy/scrapy) | BSD-3-Clause | Python | AutoThrottle; request fingerprinting for dedup; depth and offsite middleware; retry with backoff; `JOBDIR` resumability |
| [Katana](https://github.com/projectdiscovery/katana) | MIT | Go | Scope model (`dn` / `rdn` / `fqdn` + in/out-of-scope regex); "known files" (robots.txt, sitemap.xml) as an explicit opt-in; crawl-duration budget as a first-class limit |
| [Colly](https://github.com/gocolly/colly) | Apache-2.0 | Go | `LimitRule` per host-glob (parallelism + delay + randomness in one object); pluggable storage behind a tiny interface |
| [Crawlee](https://github.com/apify/crawlee-python) | Apache-2.0 | Python | `RequestQueue` with built-in dedup; adaptive HTTP↔browser decision that *learns* per site instead of a global flag |
| [advertools](https://github.com/eliasdabbas/advertools) | MIT | Python | The SEO column set itself — the closest existing analogue to what this toolkit needs; discover-vs-list mode split |
| [unlighthouse](https://github.com/harlan-zw/unlighthouse) | MIT | JS | URL-discovery priority chain (explicit URLs > sitemap > crawl); disabling the crawler when a sitemap is large enough; self-heal to JS execution when a page yields zero internal links |
| [supercrawler](https://github.com/brendonboshell/supercrawler) | Apache-2.0 | JS | Small, readable URL-list abstraction with three interchangeable backends |
| [trafilatura](https://github.com/adbar/trafilatura) | Apache-2.0 | Python | Main-content extraction and boilerplate removal, if a text-quality signal is ever wanted |
| [courlan](https://github.com/adbar/courlan) | Apache-2.0 | Python | URL cleaning and normalisation rules, including tracking-parameter stripping |
| [Protego](https://github.com/scrapy/protego) | BSD-3-Clause | Python | Reference robots.txt semantics — already in the lockfile via Scrapy |
| [Nutch](https://github.com/apache/nutch) / [StormCrawler](https://github.com/apache/stormcrawler) | Apache-2.0 | Java | Frontier and politeness-at-scale designs — instructive, far beyond this scope |

Three specific designs are worth lifting rather than reinventing:

**1. AutoThrottle instead of a fixed delay.** Scrapy sets the next delay from the observed
latency: `target_delay = latency / target_concurrency`, then averages it with the current
delay, and never lets a non-200 response *reduce* the delay. That last rule is the important
one — it means a site that starts erroring is automatically given more room rather than being
hammered harder. A fixed `--max-urls-per-second` stays as the hard ceiling; AutoThrottle only
moves *below* it.

**2. Scope as a named model, not a boolean.** Katana's `dn` / `rdn` / `fqdn` distinction is
exactly the vocabulary an SEO audit needs: "same registrable domain" is a different question
from "same host", and subdomain handling is a decision the operator should make explicitly.
`tldextract` is already in the lockfile, so this is cheap.

**3. Discovery priority chain.** unlighthouse resolves URLs in a strict order and lets an
earlier source switch off the later ones. Worth adopting, with one deliberate difference:
explicit URLs should *not* silently disable sitemap and crawl discovery, because in an audit
"also check these" is a more common intent than "only these". Make it an explicit flag.

## Build vs reuse: the advertools question, answered honestly

**Scrapy 2.17 and advertools 0.18 are already resolved in `uv.lock`** through the `sitemap`
extra. advertools is an MIT, Scrapy-based SEO crawler that already emits title, headings,
status, response and request headers — much of the first-slice column set. Not evaluating it
before writing a new crawler would be wasteful.

Arguments for reusing `advertools.crawl()`:

- Scrapy's scheduler, dedup, retry, robots handling and AutoThrottle are battle-tested.
- Resumability (`JOBDIR`) comes free, and it is the thing hand-rolled crawlers get wrong.
- No new transport code means no new SSRF surface of our own.

Arguments against:

- It inverts control: Scrapy owns the process, settings and reactor. This package is a
  library with a thread-pool house style and an explicit no-async, no-framework stance.
- It brings a heavy transitive tree for a narrow need. That tree currently includes
  **twython 3.9.1, published July 2021 and unmaintained** — pulled in only for a Twitter
  client nothing here calls. Making the crawler depend on it promotes that from an optional
  extra to a core path.
- Output shaping would still be needed: the projection onto `LoadedExports` is most of the
  work either way.
- Politeness limits, private-network guards and determinism would have to be re-expressed as
  Scrapy settings and re-verified, rather than reusing `seohead/recon/net.py` directly.

**Requested resolution:** treat this as an explicit, documented decision rather than an
assumption. Prototype the first slice both ways against the same fixture site and record the
outcome in `docs/DECISIONS.md`, measuring: wall-clock on ~500 URLs, resident memory, added
transitive dependencies, and lines of our own code. The default hypothesis is native
(control, dependency weight, house style), but it should be a measured default, not a
reflex. If native wins, consider dropping `advertools` from the `sitemap` extra entirely —
`seohead/tools/sitemap.py` already parses sitemaps independently, and that would remove the
twython path from the tree as a side effect.

## What the module reuses from inside the toolkit

Nothing below should be rewritten:

- `seohead/recon/net.py` — `http_client` (pooled, HTTP/2), `validate_url`,
  `resolve_socket_addresses`, `normalize_url`, the shared user agent.
- `seohead/tools/robots.py` — `parse_robots` / `is_allowed`, already implementing
  longest-match with `Allow` winning ties, `*` and `$`.
- `seohead/tools/parser.py` — `parse_html`, `document_base_url`, `is_external`. Link
  extraction is solved; the crawler must not grow a second copy.
- `seohead/tools/sitemap.py` — sitemap-tree expansion, and the existing level-batched
  `ThreadPoolExecutor` frontier pattern in `crawl()`.
- `seohead/data_sources/arsenkin.py` — `RateLimiter`, written for exactly this problem.

## Speed: the honest arithmetic

The previous claim of "5-10x lower wall-clock" was marketing. The real ceiling is
`min(workers / RTT, rate_limit)`, and because scope is same-host, **per-host politeness is the
global rate** — workers stop mattering once the rate limit binds.

A sequential baseline at 300 ms RTT plus a 100 ms sleep is 2.5 URL/s. At a polite 5 req/s the
gain is about **2x**, not 5-10x. Reaching 10x would need roughly 25 req/s against a single host,
which is not a concurrency win but a politeness relaxation wearing a concurrency costume.

There is a second ceiling nobody costed: parsing. `parse_html` measures at roughly **48 ms per
172 KB page, about 21 pages/s on one core**, and it is Python-level tree walking under the GIL.
Add the per-page extractor stage and the pool never reaches its network ceiling anyway.

Note also that Scrapy's `AUTOTHROTTLE_TARGET_CONCURRENCY` defaults to 1.0; ported faithfully,
AutoThrottle *cancels* the thread pool. It is still the right mechanism for backing off, but it
is not a speed feature.

**Revised claim:** roughly 2x over a naive sequential loop at equal politeness, with the real win
being that no human has to click export buttons. Any benchmark row that beats Screaming Frog by
crawling harder is disqualified, not celebrated.

### Back-off and persistence, corrected by field data

Measured on a real MODX catalogue (862 sitemap URLs, shared hosting, idle TTFB 1 196 ms) during
three failed mode-A attempts on 2026-09-03. Under a polite 1.5 URL/s the origin degraded from
**1 196 ms to 16 455 ms TTFB** and then began refusing TLS handshakes, and a 75-minute crawl
produced no output at all.

Three requirements follow, and they are not optional refinements:

1. **The back-off trigger is wider than non-200.** That host never returned an error status
   worth slowing for — it simply got slower, then stopped completing TLS. Connection, TLS and
   read timeouts are therefore the **strongest** back-off signal, and must never be treated as
   "retry immediately". Rising latency alone must widen the delay, which the Scrapy formula
   already does; timeouts must widen it hard.
2. **Concurrency adapts per origin, not just the rate.** In the same session, at concurrency 4,
   site-level requests failed on TLS timeouts while page-level fetches kept succeeding. A fixed
   URL/s ceiling with unbounded concurrency reproduces exactly this failure.
3. **Incremental persistence belongs in phase 1.** Screaming Frog writes its exports at the end,
   which is why 75 polite minutes yielded literally nothing. A collector that batches output to
   the end inherits that failure on precisely the sites where crawling is hardest. `crawl.v1`
   rows are written as they are collected, so an interrupted run is still evidence, flagged
   `crawl_partial`.

The same session also settles the throughput question from the other direction: `site-audit`
completed **150 pages across three tools, about 450 requests, in 122 seconds** against that host.
Python is not the constraint. Politeness and origin capacity are.

### Acceptance corpus

A real site with hand-established ground truth is available as a regression target, and several
of its facts are exactly what a naive collector gets wrong: a `<base href>` with relative links
throughout (the bug fixed in #4, which without the fix invents thousands of 404s here); an
invalid JSON-LD block on every page, where the correct projection is "blocks found 1, parsed 0"
rather than "no structured data"; `Product`/`Offer` microdata on `http://schema.org` as the only
valid markup, easy to miss when only JSON-LD is projected; a 31-URL numeric near-duplicate
cluster; and a meta baseline of 12 pages with no H1, 120 of 150 with a short description, and no
Open Graph at all.

The domain stays out of this issue; the recorded baseline is handed over separately.

### Determinism, restated so it is achievable

"Byte-identical output across runs" is unachievable and was wrong to promise: response times and
timestamps are in the output, AutoThrottle changes which URLs are reached before a budget binds,
error strings carry resolved addresses, and exclusion order is arrival order.

The gate becomes: **given identical responses, queue order and output order are identical**, with
a declared allowlist of volatile fields (timings, generated_at, error text) zeroed before
comparison. Note the draft sorts children alphabetically, which is not document order and biases
a truncated crawl toward `/about` over `/catalog` — the sample must follow document order.

## Compatibility: a projection onto Screaming Frog's schema, not a neutral contract

Calling `crawl.v1` a "neutral evidence contract" was wishful. `normalize.py` resolves records by
**literal Screaming Frog column headers**, and some checks match on SF's English UI strings
(`rules.py:92` tests `"blocked by robots" in status`; `rules.py:466` tests `"difficult" in
readability`). There is exactly one consumer and it has SF's schema. Name it a projection.

Corrections to the previous matrix, all verified against the code:

**Genuinely unavailable natively, and previously omitted:** redirect chains and loops (no chain
detection natively); near-duplicates and closest-similarity (SF uses minhash); readability,
Flesch, spelling, grammar; link score; title and meta-description **pixel** widths, which is what
four length checks actually test.

**Listed as supported but worthless as drafted:** the page "hash". The draft computes sha256 over
raw bytes, so one CSRF token or timestamp defeats it and `DUPLICATE_BY_HASH` finds nothing. It
needs a normalized-content hash or it should be dropped.

**Listed as work but dead:** the 3xx/4xx/5xx "logical frames", plus `titles_duplicate`,
`desc_duplicate`, `crawl_overview` — eight of the 29 loader keys are referenced by no check at
all. Synthesizing them buys nothing.

**Wrongly deferred — we already hold the evidence.** Link position and Link Path/XPath were
marked "unavailable, emitted blank". The collector has the parsed DOM; landmark and ancestor
classification plus a CSS path is cheap. `sf/core/inlinks.py` states this is the module's core
purpose — knowing whether a broken link sits in the nav or in body copy is what turns 400 broken
links into one template ticket. Blanking it would gut the toolkit's best output. It belongs in
the first slice.

Also derivable today from `parse_html` and wrongly deferred: image alt and size, mixed content,
OG tags, multiple or relative canonicals, meta refresh, noarchive/nosnippet, URL hygiene. Roughly
10-15 checks move from skipped to served for near-zero work.

**`ORPHAN_PAGE` deserves its own line.** A native crawl reaches every page by following a link,
so every discovered page has at least one inlink by construction and the check can never fire. It
must be declared unavailable for mode C, not left to report clean.

## Benchmark: measure agreement on the audit, not the URL count

Finding *more* URLs than Screaming Frog is usually a **defect** — facets, session ids, calendar
traps, mishandled canonicals. The previous framing rewarded the wrong behaviour.

Measure instead: run both collectors, project both through the *same* analyzer, and diff
`audit.json` per check per URL. Acceptance is a stated URL-level verdict-agreement threshold on
supported checks, with every disagreement class named and explained.

Metrics that were missing and matter more than speed:

- **False positives** — invented URLs, misclassified statuses. Reporting links as broken when
  they are not destroys client trust faster than being slow.
- **Run-to-run stability against a live site.** If the 4xx set moves between two runs an hour
  apart, the tool is unusable for client work at any speed.
- **Time to first usable audit including the human steps.** This is the comparison mode C
  actually wins, and the first draft never thought to measure it.
- Politeness actually used, so a speed row cannot be won by crawling harder.

### Benchmark ethics — the first draft was indefensible

"A fixed set of public sites… one deliberately slow host", with results published under their
names, meant deliberately loading servers we do not own. Replaced by:

- The published table uses a **local fixture site with a known URL count** and **properties we
  own**. Ground truth beats consensus anyway.
- Third-party runs, if any: robots-respecting, rate-capped, reported **anonymised by shape**
  ("large catalogue, roughly 40k URLs"). No site names, and no crawled content in the repository
  — third-party page text in a public repo is also a personal-data exposure.
- Slow-host behaviour is tested against our own throttled fixture, never someone else's server.
- **Blocking before any Screaming Frog row is published:** obtain and cite the current SF EULA
  clauses on benchmarking, automation and comparative claims. `docs/COMPARISON.md` currently
  states EULA-shaped conclusions without a citation and nobody has read the document.

## Safety and correctness gates

1. No request to another host, an unsupported scheme, or a URL with embedded credentials.
2. Robots-disallowed URLs are recorded as data but never fetched — **and robots must actually be
   enforced**, which it currently is not: `is_allowed` has one non-test caller, and that one is a
   reporting path.
3. `Crawl-delay` is honoured as a floor beneath AutoThrottle. It is not parsed at all today.
4. A robots.txt that answers 5xx means **crawl nothing** (RFC 9309 §2.3.1.4). Today
   `robots.py:100` treats any status ≥400 as "no robots.txt (crawl allowed)", so a site failing
   under load gets crawled harder. An explicit operator override may exist, but the default must
   be to stop.
5. User-agent group selection follows longest-token match per RFC 9309. Today `_rules_for` keeps
   the **last** matching group and matches by substring, so `User-agent: Mozilla` captures our UA.
6. `Retry-After` is honoured, and repeated 429/5xx **stops** the crawl rather than merely being
   measured.
7. Redirects are followed one hop at a time, stay in scope, and consume the global URL budget.
8. Given identical responses, queue and output order are identical; volatile fields are declared
   and zeroed before comparison. Children are enqueued in **document order**, not sorted.
9. Query variants per path are capped, and the counter must be charged only for URLs actually
   accepted.
10. Oversized responses are marked unavailable **without** being reported as non-indexable.
11. Output is written atomically, streamed to disk rather than accumulated in memory, and contains
    no raw HTML and no credentials.
12. Projected evidence produces a schema-valid audit through the analyzer, and every check whose
    evidence is unavailable is **skipped**, not silently clean — which requires the §Blocker work.
13. Screaming Frog modes stay byte- and behaviour-compatible under their current tests.
14. Scheduling state is mutated on one thread only; the draft mutates shared dicts from workers.

## Borrowing boundary — not a clean room

The previous revision called this a "clean-room boundary". Wrong label, worth correcting
precisely: a clean room means an implementer who has never seen the source. This issue's own
prior-art table is a written, dated record of having read ten codebases. Claiming a process we
are not running is worse than claiming nothing.

What we actually do, and what it permits:

- **Independent implementation from public specifications and documented behaviour.** Algorithms
  are not protectable, so describing AutoThrottle as `target_delay = latency / target_concurrency`
  with "a non-200 response may never reduce the delay" is fine. Short names such as `dn` / `rdn` /
  `fqdn` are not protectable either; the scope *model* is an idea and may be adopted.
- **Not permitted:** transcribing a function body or a settings vocabulary, or a line-by-line
  Go-to-Python rendering of someone's scope module. Translation is expressly a derivative work.
- **Photon (GPL-3.0) has been removed from the prior-art table.** No specific idea from it was
  ever named, so listing it bought nothing and only documented access to GPL code.

`THIRD_PARTY_NOTICES.md` currently cannot receive an attribution: prose bullets, no copyright
lines, no licence texts, and an assertion that only independently implemented ideas are used —
a sentence that becomes false the day one line is ported. Before any port merges it needs a
`## Ported code` section carrying, per port: source repository and commit, copyright holder,
verbatim licence text, destination file, and a statement of changes, plus SPDX headers in the
ported files.

`TRADEMARKS.md` covers only SEOHEAD's own marks and carries no third-party line, although
Screaming Frog appears in the README headline. It needs the standard non-affiliation notice.

## Current state of the draft

`feature/self-hosted-crawler` holds an **uncommitted** `seohead/crawl/collector.py`. It does not
import (`__init__.py` pulls `build_loaded_exports` / `write_evidence` from an `evidence.py` that
was never written), has no tests and no registration. Defects found in review, to fix rather than
inherit:

- children sorted alphabetically, biasing a truncated crawl toward `/about` over `/catalog`;
- decoding uses only the header charset, so `<meta charset=windows-1251>` yields mojibake titles
  on exactly the RU sites this toolkit serves;
- the query-variant counter increments before the URL-budget check, so rejected URLs consume
  variant slots; one depth check is unreachable;
- `links` and `pages` accumulate unbounded in memory — at the 10 000-URL ceiling that is over a
  million dicts before the inlink index doubles it;
- an oversized response marks a 200 HTML page Non-Indexable, producing a false
  `NON_INDEXABLE_LINKED`;
- robots is evaluated as `SEOHEAD-Tools` while the header sends the full UA string;
- `text_ratio` divides characters by bytes, wrong for UTF-8;
- scheduling mutates shared state from worker threads.

## Execution order

Kept as one issue by decision, with a hard ordering. Each phase is shippable and each one is
useless before the previous.

**Phase 0 — honest scoring (blocks everything).** Check preconditions in `seohead/sf`: every
check declares the fields and frames it needs, the engine skips it when they are absent, and the
health score is normalized by the checks that actually ran or suppressed for a partial source.
Until this lands, any new evidence source silently flatters broken sites.

**Phase 1 — list mode.** `seohead crawl --urls <file>` → bounded fetch → projection → existing
checks. No frontier, no scope model, no traps. Deterministic by construction.

**Phase 2 — breadth-first discovery** on the same projection: frontier, scope model, politeness,
budgets, link position and CSS path from the DOM.

**Phase 3 — site-wide derivations.** Pure seams in `recon/tech.py` and friends, the extractor
stage, tag coverage with id capture, both Markdown renderings and the boilerplate-consistency
report, custom `--extract`.

**Phase 4 — selective JavaScript rendering,** after the render-guard security preconditions are
met.

**Phase 5 — benchmark harness and report.**

Not part of this issue: the HTTP time-of-check-to-time-of-use gap affects every shipped live tool
today, not a future one, and is handled through private security reporting per `SECURITY.md`.

## Adjacent gaps the reviews surfaced

Recorded because they were raised and are real, not because they belong to this work. Two of them
were judged more valuable to an auditor than the crawler itself:

- **No crawl-to-crawl diff anywhere in the repo.** "What changed, did the developer ship the fix,
  did the migration break anything" is the most repeated billable deliverable. `audit.json` is
  already a stable contract, so diffing issues per check per URL is small and immediately
  sellable. Screaming Frog has crawl comparison; this toolkit has none.
- **Nothing joins Search Console or traffic.** Every check is traffic-blind: `THIN_CONTENT` on a
  page with no impressions and on one with twelve thousand carry identical severity, so the
  backlog is not actually prioritized.
- No check output is segmented by template, although page-type classification exists. Ninety-six
  checks over forty thousand URLs is a list nobody reads.
- `logs.py` exists but is never joined to a crawl, so orphan detection and crawl-waste analysis
  stay unavailable.
- Near-duplicates and spelling are deferred to Screaming Frog exports although the crawl holds
  the text and `duplicate.py` exists.
- `sf/core/runner.py` lets a config-supplied `_trusted_loopback_proxy` bypass `validate_url`.
  That path must be audited before mode C reuses it.

## Acceptance criteria — phases 0 to 2

- **Phase 0:** a test asserts that removing an export frame moves its dependent checks into
  `checks_skipped` rather than leaving them silently clean, and that the health score does not
  rise when fewer checks run.
- `seohead crawl --urls <file>` (list mode) produces a bundle the analyzer consumes into a
  schema-valid `audit.json`.
- Two runs on the same fixture produce identical output once volatile fields are zeroed.
- Modes A and B are unchanged: their existing tests pass without modification.
- Every check whose evidence the collector cannot produce appears in `checks_skipped`. Verified by
  a test that asserts the count, so the list cannot silently shrink.
- The health score for a native crawl is never higher than for a Screaming Frog crawl of the same
  fixture.
- Robots enforcement, `Crawl-delay`, and the 5xx-means-stop rule each have a test.
- Boilerplate-consistency grouping is deterministic and reports minority groups with a sample
  URL each.
- An interrupted run leaves behind what it had already collected, marked `crawl_partial`.
- A simulated origin that degrades and then refuses TLS causes the collector to widen its delay
  and reduce concurrency, not to retry immediately.
- `pytest -q` green and network-independent.

## Honest positioning once slice 2 ships

> SEOHEAD includes a bounded native collector that discovers and fetches URLs without a Screaming
> Frog licence, so an agent can run an audit unattended. It is not Screaming Frog parity: no
> JavaScript rendering by default, and any check whose evidence the collector cannot gather is
> reported as skipped, never as clean. Screaming Frog exports remain the reference input; where
> the two disagree, Screaming Frog is assumed right.

Overclaims to avoid: "site crawler", "Screaming Frog alternative", any URL-count win, and any
tag-coverage claim that omits "static, pre-consent, no JavaScript".

## Non-goals

Out of the first slices but planned: JavaScript rendering, Markdown extraction, tag coverage.

Out of scope entirely: cookies, fetching external hosts, distributed queues, a GUI, a hosted
service, telemetry, and any claim of Screaming Frog parity. Authentication is **narrowed rather
than excluded**: HTTP basic auth for staging is an environment variable and a weekly need.
