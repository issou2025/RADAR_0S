# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Receipt QR code on the existing confirmation screen**

*Project description:*
## Problem Statement

`ConfirmationScreen` (`flutter/lib/features/queue/confirmation_screen.dart`) already shows queue position, batch, and pickup status after a reservation — but there's nothing a store owner could scan at pickup time, and nothing the user can save/show if their phone is offline at the store.

## Solution

Add a QR code to the existing `ConfirmationScreen` (no new screen — this is an addition to what's already there) encoding enough of the purchase to be self-explanatory without a live lookup: purchase ID, buyer name, store name, purchase date. Add a "save/share" action so the user can keep the QR outside the app.

## User Stories

1. As a user who just reserved a bag, I want to see a QR code on the same confirmation screen I already land on, so there's one place for "my proof of reservation," not a separate detour.
2. As a user, I want to save or share the QR image, so I can show it at the store even without the app open.
3. As a store owner scanning (or just eyeballing) a customer's QR, I want the encoded info to include the buyer's name, store, and date, so it's self-explanatory without a database round-trip.
4. As a developer, I want the QR payload to be a small, testable pure function, so the encoding logic doesn't get tangled with the widget that renders it.

## Implementation Decisions

- `ConfirmationScreen` currently takes `controller` + `purchaseId` only. It needs the buyer's name to encode in the QR — thread `currentUser` (the same `DemoUser` already available in `PurchaseScreen`, which pushes `ConfirmationScreen`) through as a new required param, matching how `PurchaseScreen` already receives it.
- QR payload: plain JSON — `purchase_id`, `user_name`, `store_name`, `purchase_date`. No signing/crypto — there's no backend to validate a signature against (explicitly deferred to production infra, not this prototype). Put the encode/decode logic in one small, framework-free class (e.g. `lib/features/queue/qr_payload.dart`) so it's trivially unit-testable and reusable by the redemption-scanning work that follows this issue.
- Render the QR with `qr_flutter` (already a pubspec dependency, unused so far — first real usage). Add it below the existing status card, inside the same `ConfirmationScreen` layout (`ConstrainedBox(maxWidth: 480)` etc. — match the existing structure, don't restructure the screen).
- "Save/share": use `share_plus` (already a dependency, unused so far) to share the QR as an image — simplest path, no platform-specific save-to-gallery code needed.
- Only render the QR once `purchase` is non-null (mirrors the existing `if (purchase == null) return const SizedBox.shrink();` guard already in the screen).

## Testing Decisions

- Unit test the QR payload encode/decode: given a purchase/user/store, the encoded JSON round-trips through decode back to the same fields.
- Widget test: given a completed purchase, `ConfirmationScreen` renders a QR widget once `purchase` resolves.
- CI-only verification for this task (`flutter analyze` / `flutter test` / `flutter build apk --debug`) — no browser. Visually confirming the QR renders correctly, is scannable-looking, and the share action feels right happens in a live session afterward, not required for this PR to merge.

## Out of Scope

- QR signing/cryptographic validation.
- The store-owner scanning side (reading this QR back) — that's the next issue in this sequence; this one only produces the QR.
- A "my receipts" history screen — only the just-completed purchase's QR, on the screen that already exists for it.
- Live UI/browser verification as part of this task's Done criteria.
