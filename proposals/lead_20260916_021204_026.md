## Project Understanding
You need assistance with: 
**The unit suite does not pass on Windows (27 failures, 5 root causes) — and CI is ubuntu-only, so nothing says so**

*Project description:*
`pytest -q` on Windows 11 / CPython 3.14, clean checkout of `main`: **33 failed, 2053 passed**. After #451 (the token-hardening fix) it is **27**. CI is `ubuntu-latest` only, so the suite has never been run on Windows by anything automatic.

`CLAUDE.md` says a low skip count means a gate leaked. It does not currently say anything about a *high failure count on the developer's own platform*, because until now nobody had measured one.

## Why this is worth fixing rather than documenting

Two separate reasons, and the second is the stronger one:

1. **A Windows contributor cannot verify their own work.** 27 red tests is indistinguishable from "I broke something", so the suite stops functioning as a signal. The practical workaround is to stop running it locally, which is worse than the failures.
2. **#451 found a real security defect in this class.** The token file's `0o600`/`O_NOFOLLOW` hardening was a silent no-op on Windows, and `THREAT_MODEL.md` T5 cited it as its mitigation (#452). That was not found by reading; it was found because the assertions failed on Windows and somebody looked. The other 27 have not been looked at.

## Root causes

### 1 — `subprocess(env=…)` without `SystemRoot` (13 failures, `test_mcp_wire_protocol.py`)

The harness builds a deliberately minimal environment:

```python
env = {"PATH": ..., "PYTHONPATH": ..., "CSA_GW_ALLOWLIST_READ": "*", "CSA_GW_TOKEN": ...}
```

On Windows, Winsock cannot initialise without `SystemRoot`, so `asyncio` fails to import and the server dies **before reading stdin**:

```
File "...\asyncio\windows_events.py", line 8, in <module>
    import _overlapped
OSError: [WinError 10106] The requested service provider could not be loaded or initialized
```

The test then reports `no answer ... within 60s` — but fails in 0.48s, because the process is already gone. **The MCP server itself is fine on Windows**; it starts and answers `initialize` correctly once `SystemRoot` is in the env. Verified both ways.

Fix: add `SystemRoot` (and probably `SYSTEMDRIVE`) on `os.name == "nt"`. The minimal env is deliberate and worth keeping — it should just be minimal *and viable*.

### 2 — `read_text()` / `open()` with no `encoding=` (6 failures, `test_readme_tools.py`)

```
README.read_text()
UnicodeDecodeError: 'charmap' codec can't decode byte 0x90 in position 28226
```

Python uses the locale encoding when none is given; on Windows that is cp1252, and `README.md` is UTF-8. Every `read_text()`/`open()` on a repo file needs `encoding="utf-8"`.

Worth a lint rule rather than a sweep — this is the same defect family as #449 (a BOM breaking `json.load`), and it will come back. `ruff` has `PLW1514`/`W1514` (`unspecified-encoding`) for exactly this.

### 3 — `/` vs `\` in the repr-redaction guard (2 failures, `test_repr_redaction.py`)

The guard builds class ids from paths and compares them to a hard-coded safe-list:

```
computed : demo\_plan.py::Outcome
declared : demo/_plan.py::Outcome
```

So on Windows it reports **every** class as undeclared *and* the entire safe-list as naming classes that no longer exist — simultaneously, which is the tell. Not silent, but the guard certifies nothing there. Fix: normalise to `/` when building the id.

### 4 — `expanduser("~")` ignores a monkeypatched `HOME` (2 failures)

`test_export_paths_and_injection.py` and `test_scope_short_token_message.py` redirect `~` by setting `HOME`. On Windows `os.path.expanduser` prefers `USERPROFILE`, so `~` resolves to the real profile and the assertion compares a real path against `tmp_path`. Fix: set `USERPROFILE` too, or patch `expanduser` directly.

### 5 — `0o600` asserted against Windows (4 failures, `test_desktop_config*.py`)

`assert 438 == 384` is `0o666 == 0o600`. Same family as the token-file defect #451 just fixed, and **one of them is a real finding, not just a test problem**:

```
AssertionError: config written 0o666; it names the token path and the allowlist
```

`claude_desktop_config.json` is written `0o600` on POSIX (audit finding T26). On Windows that is a no-op, so the file naming the token path and the allowlist is at whatever the directory grants. #451 added `auth.file_is_owner_only()` and `auth._harden()`; `_desktop.py` should use them.

**This one should probably be split out and treated as security**, like #452 — I have left it here rather than pre-judging it.

## The part that is above this repo

None of the above is visible to CI. Options, in increasing order of cost:

- **(a)** Add `windows-latest` to the `test` matrix. Honest, and stops the gap widening. Costs minutes per PR and would be red until the above are fixed, so it lands *after* them or as `continue-on-error` first.
- **(b)** Add `windows-latest` for one Python version only.
- **(c)** Leave CI alone and fix the failures, accepting that they will drift back.

I would do the fixes, then **(b)**, then widen — but whether CSA repos should carry a Windows CI leg by default is a policy question, not this repo's to settle. It is going to CINO-Platform-Engineering along with the reusable gotchas, since none of the five root causes is specific to this project.
