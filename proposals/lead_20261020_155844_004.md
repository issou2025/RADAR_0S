*Project description:*
## Problem Statement

KamiKon is meant to be an inter-university academic event platform for Rwanda, but today the codebase is an empty Django scaffold: six app shells with no models, one empty `User`, no URLs beyond the admin, no templates, no service-layer convention and no domain glossary. Developers cannot start building the MVP flow (an Organizer publishes an Event, a verified student discovers it and RSVPs) because the structure, vocabulary and testing approach it should stand on do not exist. The design docs also contradict the repo (they describe an `institutions` app that does not exist, and call the access model both "Access Scope" and "Access Policy", "4-Tier" while listing five values).

## Solution

Lay the foundation the MVP will be built on, with the smallest working vertical slice proving it: a page-rendering skeleton where a student can sign up, be verified by email domain, see a list of approved Events, and an Organizer can submit an Event that is only visible once an Approver has approved it (unless the Organizer is themself an Approver). The spec fixes the app boundaries, domain vocabulary, model shapes, service-layer convention, base UI shell and test seam so that later specs (RSVP, notifications, tickets, discovery) add behaviour without reworking structure.

## User Stories

1. As a developer, I want a documented domain glossary (University, Campus, Hub, Host, Event, Access Policy, Delivery Mode, Organizer, Approver, Verified Member, Community Guest), so that code, issues and design docs use one consistent vocabulary.

4. As a developer, I want a single test seam (the Django test client over HTTP against a test database), so that tests assert external behaviour and survive refactors.
5. As a developer, I want the existing settings tests kept passing, so that environment and security configuration stays protected.
6. As a developer, I want CI to run lint and the full test suite on every push, so that regressions are caught early.
7. As a developer, I want all UI strings wrapped for translation from the start, so that Kinyarwanda and French can be added later without a rewrite.
8. As a platform superadmin, I want to create Universities, Campuses (with a parent University) and Hubs in the admin, so that institutions are onboarded without code changes.
9. As a platform superadmin, I want to register the email domains that belong to a University, so that members are verified automatically.
10. As a visitor, I want to register with an email and password, so that I can use the platform.
11. As a visitor with an email on a registered University domain, I want to be recognised as a Verified Member of that University, so that I can access academic-only Events.
12. As a visitor with any other email, I want to be registered as a Community Guest, so that I can still use public parts of the platform.
13. As a user, I want to log in and out, so that my session is secure.
14. As a Verified Member, I want my University shown on my profile, so that others see my affiliation.
15. As an Organizer, I want to create an Event with title, abstract, category, start and end time, Host (Campus or Hub), Access Policy and Delivery Mode, so that attendees know what it is and who can come.
16. As an Organizer, I want to choose an Access Policy from public community, open to all universities, institution only, or campus only, so that eligibility is explicit.
17. As an Organizer, I want to choose a Delivery Mode of in-person, online or hybrid separately from Access Policy, so that how people attend is independent of who may attend.
18. As an Organizer, I want to enter a venue for in-person and hybrid Events and a meeting link for online and hybrid Events, so that attendees can find or join it.
19. As an Organizer, I want my new Event to start in a pending state, so that it is reviewed before anyone sees it.
20. As an Organizer, I want to see the status of my Events (pending, approved, rejected), so that I know where they stand.
21. As an Organizer, I want to edit my pending or rejected Event and resubmit, so that I can address reviewer feedback.
22. As an Approver (moderator), I want a queue of pending Events, so that I can review them in one place.
23. As an Approver, I want to approve an Event, so that it becomes publicly visible.
24. As an Approver, I want to reject an Event with a reason, so that the Organizer knows what to fix.
25. As an Approver, I want Events I create to be approved immediately, so that trusted staff are not blocked by their own queue.
26. As a Verified Member, I want to see a list of approved upcoming Events, so that I can find things to attend.
27. As a Community Guest, I want to see approved upcoming Events open to the public, so that I can participate without a university email.
28. As a visitor, I want to see an Event detail page, so that I can read the abstract, time, Host, Access Policy and Delivery Mode.
29. As a user, I should not see pending or rejected Events from other Organizers, so that unreviewed content is never exposed.
30. As a user, I should not see Events my Access Policy excludes from the list, so that I only see Events I can attend.
31. As a user on a slow mobile connection, I want light server-rendered pages with minimal JavaScript, so that the site is usable on limited data.
32. As a user, I want the layout to work on a phone-sized screen first, so that I can browse on my phone.
33. As a user, I want the site in English now, with a structure ready for Kinyarwanda and French, so that I can be served in my language later.
34. As a developer, I want a base template with navigation, messages and a content area using Tailwind and HTMX, so that every page shares one shell.
35. As a developer, I want seed data (one University with domain, one Campus, one Hub, sample Events), so that I can run the app and see the slice working.

## Implementation Decisions

- **Apps and ownership.** Add an `institutions` app (University, Campus, Hub, University email domains). `accounts` owns the User and verification tier. `events` owns Event and its approval state. `discovery`, `tickets`, `notifications` and `community` remain empty shells for later specs but stay registered.
- **Host.** An Event's Host is always a Campus or a Hub, never a free-text club. A club or department name is just an optional label on the Event.
- **Access Policy vs Delivery Mode.** Two separate fields on Event. Access Policy has exactly four values: public community, open to all universities, institution only, campus only. Delivery Mode has three: in-person, online, hybrid. "Access Policy" is the one canonical term; "Access Scope" is retired.
- **Roles.** Organizer and Approver are permissions on a User, not separate user types. An Approver may also be an Organizer.
- **Verification.** At registration, the email domain is matched against registered University domains. A match makes the user a Verified Member of that University; otherwise a Community Guest. No ID-photo or OTP flow in this spec.
- **Event approval.** Event status is pending, approved or rejected. New Events are pending, except when created by an Approver, which are approved immediately. Rejection stores a reason. Only approved Events appear in public lists and detail pages; Organizers also see their own Events in any state.
- **Eligibility in the list.** The list is filtered by a single eligibility decision of the form (user, event) → eligible or not, based on Access Policy and the user's University and Campus. It is built as one module even though only the list uses it now, so RSVP and discovery reuse it later.
- **Service layer.** Each use case (register user, create event, approve event, reject event, list visible events) is a function in its app's service module with plain-data inputs. Views call these functions and contain no business rules.
- **User model.** Extend the existing custom User with the minimum fields needed: verification tier and an optional University and Campus link.
- **UI.** Server-rendered Django templates with Tailwind and HTMX, mobile-first, no map, no full-text search, no heavy JavaScript. Strings wrapped with `gettext`; English only now.
- **Seed data.** A management command creates a University with a domain, a Campus, a Hub, an Approver and sample approved Events.
- **Documentation.** Create the root glossary file with the terms above and an ADR recording the Host and Access Policy / Delivery Mode split, since both are hard to reverse and surprising without context.

## Testing Decisions

- **Good tests** drive real URLs with the Django test client against a test database and assert on status codes, redirects and rendered content. They do not call model internals or assert on private functions.
- **One seam:** the HTTP test client. Service-layer use cases are exercised through the views that call them.
- **Behaviours to cover:** registration verifies by domain and falls back to Community Guest; Organizer-created Events are hidden until approved; Approver-created Events are visible immediately; rejection records a reason and hides the Event; users do not see Events their Access Policy excludes; pending Events are visible to their Organizer but not to others.
- **Prior art:** the existing settings tests (pytest with pytest-django). New tests follow the same runner and conventions.
