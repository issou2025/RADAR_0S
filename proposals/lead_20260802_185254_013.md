# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Design and implement model-perf for single- and multi-ELF model benchmarking**

*Project description:*
## Summary

Add an installed C++ command-line tool named `model-perf` to Core for repeatable performance benchmarking of a logical model containing either one ELF or multiple ELF stages.

The tool should benchmark the model described by its MPK manifest rather than treating ELF files as an untyped list. Single-ELF and multi-ELF models should use the same CLI, execution path, measurement semantics, and result schema.

The proposed first release supports deterministic synthetic inputs and validated linear model routes. Its primary outputs are end-to-end latency, asynchronous throughput, power/energy when available, measurement-quality checks, and optional per-stage diagnostics.

## Motivation

Core currently exposes `Model::benchmark()`, which is useful for a model pack containing the currently supported single MLA/ELF inference stage. It already:

- generates deterministic synthetic tensors from `Model::input_specs()`;
- uses separate warmed-up single-flight latency and asynchronous throughput windows;
- reports logical inferences per second using compiled batch size;
- optionally collects plugin latency;
- samples board power during the throughput window.

However, the public `BenchmarkReport` contains only average latency, FPS, average power, and energy, and `Model::benchmark()` prints directly to stdout.

More importantly, Core's model planning and materialization currently assume a singular MLA stage in several places. A CLI alone cannot provide correct multi-ELF benchmarking until Core preserves and materializes every MLA stage and its intermediate transforms.

## Design principles

1. **Benchmark a logical model, not a list of binaries.**
   The MPK manifest is the source of truth for stage ordering, ingress/egress tensor contracts, dtype, shape, batch size, routing, and required transforms.

2. **Do not infer a model contract from naked ELF files.**
   ELF section inspection may supplement topology validation, but it is not sufficient to infer the model route. A bare-ELF compatibility path, if provided, must require an explicit MPK manifest/contract sidecar.

3. **Make stage count transparent to the benchmark engine.**
   Once `Model::build()` can materialize the resolved model route, benchmarking should operate on the resulting runner without special one-ELF versus multi-ELF branches.

4. **Keep measurement semantics explicit.**
   Single-flight timing is latency. Timing from an asynchronous queued throughput window is queue-inclusive residency and must not be presented as standalone model latency.

5. **Fail rather than publish misleading results.**
   Do not publish a valid benchmark when outputs are missing, samples cannot be correlated, drops occur, contracts are incomplete, or the requested route is unsupported.

6. **Use C++ for the installed implementation.**
   `model-perf` should call Core's C++ model/runtime/measurement path directly and install into `${CMAKE_INSTALL_BINDIR}`. Python may invoke the executable later but should not be the primary implementation.

## Proposed CLI

```console
# Same command for a one-ELF or multi-ELF model pack
model-perf run model.tar.gz

model-perf run model.tar.gz \
  --warmup 50 \
  --samples 1000 \
  --inflight 4 \
  --plugin-latency \
  --output result.json

# Validate the package and show its resolved stages/contracts without running it
model-perf inspect model.tar.gz

# Contract/runtime preflight without a measurement window
model-perf validate model.tar.gz

# Compare independent model variants under identical settings
model-perf compare model-a.tar.gz model-b.tar.gz \
  --samples 1000 \
  --trials 5 \
  --output comparison.json
```

Proposed subcommands:

- `inspect`: show MPK identity, ordered stages, ELF artifact associated with each MLA stage, tensor contracts, intermediate transforms, batch size, and graph edges;
- `validate`: perform MPK contract validation and runtime preflight;
- `run`: execute one logical model benchmark;
- `compare`: execute multiple independent model packages with identical options and summarize differences.

Do not define repeated `--elf` arguments as model composition. If direct artifacts are supported, require an explicit contract:

```console
model-perf run --manifest model_mpk.json --artifact-dir ./model-files
```

## Current Core gaps

The implementation should begin by recording the existing limitation with tests.

Current singular assumptions include:

- `get_mla_stage_io_contract()` returns null when more than one MLA plugin is present;
- `make_mla_stage_from_contract()` creates at most one MLA execution stage;
- `build_execution_plan_from_mpk_contract()` inserts at most one stage into `plan.infer`;
- MLA runtime properties such as model path and batch size are resolved globally rather than for the current execution stage;
- fragment materialization is linear and currently receives a singular MLA-oriented set of contract helpers;
- pre/infer/post partitioning is based around one MLA boundary.

## Core architecture changes

### 1. Add plural, stage-specific MLA contract access

Introduce internal APIs along these lines:

```cpp
std::vector<std::size_t> get_mla_stage_indices(const MpkContract&);

const MpkPluginIoContract&
require_mla_stage(const MpkContract&, std::size_t plugin_index);
```

Contract extraction, ELF topology lookup, batch metadata, and runtime-property rendering must take a stable stage ID or MPK plugin index.

Keep existing single-stage helpers for compatibility where needed, but do not silently select the first stage when multiple MLA stages exist.

### 2. Preserve the complete execution route

For a multi-ELF route, partition the resolved route as:

- **preprocess**: stages before the first MLA stage;
- **inference**: the first MLA through the last MLA, including intermediate CVU transforms, transport, packing/unpacking, quantization, tessellation, and detess/dequant stages;
- **postprocess**: stages after the last MLA stage.

Conceptually:

```text
input -> preproc -> quant/tess -> mla_0
      -> detess/dequant -> quant/tess -> mla_1
      -> postprocess -> output
```

Each resolved execution stage should retain at least:

```cpp
struct ExecutionStage {
  StageId id;
  std::size_t mpk_plugin_index;
  ExecutionStageKind kind;
  std::string executable;
  TensorContracts inputs;
  TensorContracts outputs;
};
```

The executable, batch properties, and compiled contract must come from that stage's MPK entry.

The internal representation should preserve graph edges even if v1 materialization accepts only a linear chain. Unsupported fan-out/fan-in should fail during validation with an actionable structured error rather than being flattened incorrectly.

### 3. Materialize every stage deterministically

Update model route materialization so:

- every MLA stage receives a distinct stable element/stage name;
- each `neatprocessmla` instance receives the correct stage-specific ELF and batch properties;
- intermediate tensor contracts are validated before runtime;
- model lineage and node attribution distinguish the stages;
- terminal policy can resolve and truncate a multi-stage inference route deterministically;
- pipeline descriptions and exported run JSON show the complete route.

### 4. Extract a reusable benchmark engine

Refactor the loops currently implemented in `Model::benchmark()` into a shared internal C++ engine, for example:

```cpp
namespace simaai::neat::internal {

struct BenchmarkExecution {
  MeasureReport latency;
  MeasureReport throughput;
};

BenchmarkExecution run_model_benchmark(
    Model& model,
    const BenchmarkOptions& options,
    const BenchmarkExecutionOptions& execution_options);
}
```

Responsibilities:

- validate options and concrete input contracts;
- generate deterministic synthetic inputs;
- perform warmup outside measured windows;
- perform a single-flight latency measurement;
- perform a separate asynchronous throughput measurement;
- close input and drain outputs with bounded teardown;
- require the expected number of outputs;
- reject drops and unreliable sample correlation;
- return full `MeasureReport` objects without printing.

The existing public `Model::benchmark()` should remain source-compatible. It should call the shared engine, retain its existing compact stdout behavior, and project the detailed measurements into the existing four-field `BenchmarkReport`.

The CLI should call the same engine and own text/JSON rendering. This avoids immediately stabilizing a large new public C++ API.

## Measurement protocol

### Latency window

- Default warmup: 50 completed inputs, configurable.
- One input in flight: push one, pull one.
- Fixed sample count.
- Report count, average, min, p50, p90, p95, p99, and max.
- Define semantics as graph entry to public pull for the complete logical model.
- Exclude package loading, pipeline construction, and warmup by default.

### Throughput window

- Independent runner/window from latency measurement.
- Configurable in-flight depth.
- Push and pull asynchronously.
- Report batches/s and logical inferences/s.
- Multiply batch throughput by the compiled logical batch size exactly once.
- Sample board power over this window when supported.
- Require pushed/pulled/output counts to agree.
- Require zero input/output drops.
- Drain all in-flight work with bounded teardown.

### Optional cold-start mode

A later or optional `--cold-start` measurement may report package load, graph build, runtime startup, and first-result timing. These values must remain separate from warmed inference latency.

### Stage diagnostics

When `--plugin-latency` is enabled, report per-node/plugin rows with stable stage attribution and explicit collection status.

These metrics are diagnostic and may be nested or overlapping. The CLI and JSON schema must state that plugin durations must not be summed to derive end-to-end latency.

Board power is reported for the whole measurement window. Do not claim per-ELF power attribution.

## Error handling

Failures should include structured, actionable context, including the model path, MPK stage name/plugin index, ELF path, tensor/edge identity, and next corrective action where possible.

Examples that must fail clearly:

- MPK manifest missing;
- more than one MLA stage encountered on an unsupported build;
- missing ELF for a declared stage;
- duplicate or unresolved stage identity;
- incompatible producer/consumer tensor contracts between ELF stages;
- dynamic or otherwise non-concrete synthetic input contract;
- unsupported branched multi-ELF route in v1;
- unavailable required runtime/plugin/device;
- timeout, failed push/pull, missing output, output-count mismatch;
- measurement drops or unreliable sample correlation.

Do not inspect other JSON files in the model archive as a fallback.

## Testing plan

### Contract and planning unit tests

- one MLA stage remains unchanged;
- two MLA stages are returned in deterministic MPK execution order;
- each stage resolves its own ELF and batch metadata;
- inter-MLA transforms remain inside the inference region;
- missing or incompatible inter-stage contracts fail;
- duplicate names are resolved or rejected deterministically;
- fan-out/fan-in is rejected clearly in the linear-v1 implementation;
- terminal policy resolves the intended stage;
- old single-stage helpers and public model usage retain compile coverage.

### Fragment/materialization tests

- stable element names for each MLA stage;
- correct stage-specific `model-path`;
- expected complete backend fragment;
- per-stage contract facts and lineage;
- validation success and parse failure paths.

### Benchmark engine tests

- deterministic synthetic inputs;
- warmup excluded from measured counts;
- latency window is single-flight;
- throughput window uses the configured in-flight depth;
- logical batch arithmetic is correct;
- expected input/output counts are enforced;
- drops and correlation misses invalidate the report;
- teardown remains bounded after push, pull, or measurement failure;
- plugin-latency unavailable/failed states are preserved;
- power unavailable is represented as status, not a misleading zero measurement.

### CLI tests

- argument validation and exit codes;
- `inspect`, `validate`, `run`, and `compare` happy paths;
- deterministic text and JSON rendering;
- JSON schema-version coverage;
- atomic output writes;
- no partial result on failure;
- no Python runtime dependency.

### Hardware/integration tests

- existing single-ELF model benchmark regression;
- representative two-ELF linear MPK benchmark;
- output-count and lifecycle validation;
- latency/throughput measurements are finite and positive;
- plugin attribution distinguishes both MLA stages;
- power fields are valid when telemetry is available.

Use DevKit wrappers for aarch64 binaries and mark hardware-resource tests with the existing performance-device resource lock.
