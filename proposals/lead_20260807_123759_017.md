# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**PermissionError escapes both no-FDA fallbacks: get_emails() fails outright, and attachment reads report "not found"**

*Project description:*

Running without Full Disk Access — which the docs describe as supported ("The MCP server itself does **not** need Full Disk Access — only the `index` and `rebuild` commands do", `docs/troubleshooting.md`) — two code paths fail in ways that look like different bugs but share one root cause.

`PermissionError` subclasses `OSError`, not `FileNotFoundError`. Both sites below have a handler that clearly intends to cover an unreadable Mail store, and `PermissionError` walks straight past it.

Happy to be told I've misread either of these.

## 1. `get_emails()` fails instead of falling back to JXA

`server.get_emails()` Strategy 0 catches:

```python
except (FileNotFoundError, sqlite3.OperationalError, MailboxNotFoundError) as exc:
```

Without FDA, `find_mail_directory()` raises `PermissionError`, so the call fails outright and never reaches the Strategy 1 JXA fallback — which needs no FDA and works fine, since Mail.app automation is a separate permission.

```
$ apple-mail-mcp emails --account Google --limit 2
Error: Cannot access /Users/<me>/Library/Mail/V10
```

This also takes out the `emails` CLI command, which calls straight into `get_emails()`.

Adding `PermissionError` to that tuple restores the fallback, and the command works:

```
$ apple-mail-mcp emails --account Google --limit 2
[ ... 2 messages, via JXA ... ]
```

## 2. Attachment reads report "not found" for a permission problem

`disk.get_attachment_content()` ends with:

```python
except (OSError, ValueError, UnicodeDecodeError):
    return None
```

The `PermissionError` from `read_bytes()` is swallowed into `None`, and `server.get_email_attachment()` turns that into:

```
$ apple-mail-mcp extract 78595 --filename "Invoice-XXXX.pdf"
Error: Attachment 'Invoice-XXXX.pdf' not found in email 78595.
```

The attachment is present — `read`/`get_email` lists it with the right filename, mime type and size. Only the `.emlx` read is denied. As a user this sends you looking for a data or MIME-parsing bug that isn't there.

One detail that made this confusing to track down: on macOS, `stat()` on a TCC-protected `.emlx` **succeeds**, and only the read is refused. So the denial surfaces at `read_bytes()`, not at the `exists()` check above it:

```python
>>> os.stat(p).st_size
55963
>>> open(p, 'rb').read()
PermissionError: [Errno 1] Operation not permitted: '.../78595.partial.emlx'
```

I don't think attachment *content* can work without FDA — that seems inherent. The ask is just that the error names the real cause, since the metadata path works fine and users can act on a permission problem.
