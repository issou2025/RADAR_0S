## Destination

A v1 spec for Project Cherry: a Flutter phone app (iOS first, Android too) that helps an ADHD brain manage tasks and see how long things really take. The spec covers the core loop, domain model, screens, logic rules, and tech stack, ready to hand to build sessions. Full depth: todos, breakdown, retrospective. Core: similar-task hint shown at estimate time. Basic: weighted-random suggestion by time bucket.

## Notes

- **Domain**: mobile app product design + Flutter engineering. Developer is a Flutter beginner (one prior app) — weigh simplicity and documentation quality.
- **Planning only**: tickets resolve decisions; no app code in this map (prototypes are throwaway).
- **Tracker**: GitHub issues on `Jakeplusplus/project-cherry`. This issue is the map; tickets are its sub-issues labelled `wayfinder:<type>`; blocking uses native issue dependencies. Build stories/tasks after the spec also go to GitHub issues.
- **Skills**: `/grilling` + `/domain-modeling` for grilling tickets; `/prototype` for prototype tickets; `/research` for research tickets (findings in `research/<slug>.md` on a `research/<slug>` branch).
- **Standing constraints** (settled while charting — do not reopen without the user):
  - On-device only. No accounts, ever, unless a real reason to leave the device appears.
  - Built for the author first; avoid choices that block a public release later.
  - Phone only: iOS + Android. Author carries iOS — first test target.
  - Assistive tool, not a planner replacement.
  - Estimate is a **bucket** (short / medium / long / whole day); actual is **precise minutes**.
  - Three numbers per timed thing: estimate (before), felt guess (after, before reveal), actual (clock).
  - Timer is primary, with a forgiving repair path and a lower-confidence self-report fallback.
  - Micro-retro at every completion (light, skippable) + a pull-only insights screen. No rituals, no streaks.
  - Two levels only: task → steps. Steps are estimated and timed. A too-big step is promoted to its own task.
  - Capture requires title + bucket only. Optional: category, due date, important flag.
  - Positioning: "see your real numbers" — an external record, not a promise to train time sense. The app says "here's what happened", never "you're improving" or "you're slipping".
  - Similar-task hint is core: a passive line at estimate time whenever history exists. Similarity precedence: exact title (case-insensitive, trimmed) → category + bucket → bucket alone.
  - Felt guess: one tap, always skippable, never scored; timed sessions only.
  - Suggestion = weighted random among tasks fitting the stated time bucket.
  - Breakdown = guided manual workflow at full depth; AI assistance only if on-device.
  - Notifications are timer-tied only: lock-screen presence + overrun check-in.
  - Stack chosen from research, not taste.

## Decisions so far

<!-- one line per closed ticket -->

- [State management and app architecture for a Flutter beginner](https://github.com/Jakeplusplus/project-cherry/issues/5) — official Flutter MVVM (ChangeNotifier + provider + go_router) ranked first, Riverpod second; flips if a reactive-stream database is chosen. Input to the stack decision, not the decision itself.
- [Local persistence options](https://github.com/Jakeplusplus/project-cherry/issues/4) — Drift (SQLite) recommended, sqflite fallback; Isar/Hive/Realm/Floor ruled out. Caveat: Drift 3 in alpha. Reactive query streams available, which favours Riverpod in the state-management ranking. Input to the stack decision.
- [On-device LLM feasibility for task breakdown](https://github.com/Jakeplusplus/project-cherry/issues/2) — feasible only as an optional "suggest steps" button using OS-provided models (strong on iPhone 15 Pro+, weak on Android); no bundled model. Output quality unverified — spawned a prototype ticket.
- [Background timer and lock-screen presence from Flutter](https://github.com/Jakeplusplus/project-cherry/issues/3) — no background timer: store start timestamp, compute elapsed. Overrun check-in = scheduled local notification. iOS Live Activity needs no push server but needs a native SwiftUI widget extension and caps at 8 h; Android needs no native code. Device behaviour unverified — spawned a prototype ticket.
- [Task breakdown techniques that lower the barrier to starting](https://github.com/Jakeplusplus/project-cherry/issues/7) — find one startable first step rather than a full plan ("can't start = step too big"); plan less than feels natural; bucket steps after listing; long/whole-day step triggers promotion. Three candidate guided sequences. Evidence is weak and none is app-delivered — treat as prototype input.
- [Evidence on training time estimation in ADHD](https://github.com/Jakeplusplus/project-cherry/issues/6) — no direct evidence the loop trains time sense in ADHD; best-supported mechanism is showing the real past number at the next estimate for a similar task; reason attribution looks unhelpful; framing must avoid self-directed criticism. Mostly extrapolated. Challenges two standing constraints — spawned a decision ticket.
- [Does the evidence change the v1 shape?](https://github.com/Jakeplusplus/project-cherry/issues/20) — positioning becomes "see your real numbers" with improvement tracked but never promised; similar-task hint promoted to core, passive at estimate time, keyed title → category + bucket → bucket; felt guess kept as a skippable one-tap. Edited the standing constraints.

## Not yet specified

- **Insights screen content** — which patterns are shown and how; leads with real numbers, estimate-accuracy trend secondary; depends on what the micro-retro stores.
- **Similar-task hint statistic and placement** — mean vs median vs range, minimum sample count before a hint shows, and exactly where the line sits on the estimate UI; depends on domain model, bucket decisions and the screens prototype.
- **Backup / export** — on-device only means a lost phone is lost data. Some escape hatch (file export, OS backup behaviour) probably needed; shape unclear until persistence is chosen.
- **ADHD UX principles and accessibility** — friction budget, tone, visual load; likely falls out of the prototypes.
- **First-run experience** — what an empty app shows; matters more for the public door than for the author.
- **Final spec assembly** — format and location of the spec document once decisions are in.

## Out of scope

- Accounts, sync, cloud storage — violates the on-device constraint.
- Desktop and web targets — no sync means stranded data per device.
- Reminders, due-date alerts, calendar, scheduling, daily planning — planners already do this; the app assists, not replaces.
- Recurring tasks — strong similarity signal but large complexity; later effort.
- Energy level and context/location fields — capture friction; later effort.
- Smart similarity matching (fuzzy text, embeddings) — v1 uses exact title, category and bucket only.
- Hint disagreement nudge ("you picked short; these usually run 50m") — tone risk; later effort.
- Monetization, store listing, marketing.
