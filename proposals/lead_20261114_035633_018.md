## Design plan

### Goal
A switch on the Agents tab: "Let agents read verification codes and verify for you". Off by default, set per device. When on, an agent signing in on a Mac can ask PassBridge to finish Apple's verification step. A small macOS reader waits for Apple's "sign in requested" prompt, presses Allow and reads the 6-digit code. PassBridge fills the code into the agent's own tab. The code never reaches the agent, a log or storage.

### How it works today
- Agents tab: `src/ui/options-screen.jsx:485-521` (`AgentsTab`); extra switches are locked unless `agentSignIn` is on (`:495`, `:501`).
- Settings defaults `src/settings.js:24-31` live in `chrome.storage.sync` (`:46-47`), so they follow the profile to every machine. Per-device state uses `chrome.storage.local` (precedent: passkey setting, `src/ui/options.jsx:130-150`).
- Agent ops: `handleAgentRequest` `src/agent.js:216-321` accepts only `status`, `pair_*`, `logins`, `sign_in`, `save` (`:249`). `fill_code` was removed (`docs/agent-protocol.md:131`).
- `sanitizeReply` (`src/agent.js:127-142`) drops code/otp/password keys; the protocol promises no reply holds a code (`docs/agent-protocol.md:5`).
- No per-client auth: socket mode 0600 only (`native/passbridge-agent.py:173-175`, `docs/agent-protocol.md:44-55`).
- Activity log: 200-entry ring in `chrome.storage.session` (`src/agent.js:25-26`, `logEntry` `:102-120`, never stores a password).
- Code fill already exists: `fillOneTimeCode` `src/background.js:1699-1722` sends `fillOtp` with `expectedHost`; `src/content.js:447-454` fills only on that host.
- The Mac relay (`native/passbridge-agent.py`) calls no permission-gated macOS API. A pairing-code reader was removed in `4212455` because auto-reading also removes Apple's check that a person approved the browser. No reader exists in any sibling project to reuse.

### Plan
1. **Switch**: `agentCodeReader` in `chrome.storage.local` only (never in `SETTINGS_DEFAULTS`, never syncs). Locked unless Allow agent sign-in is on; locked with "macOS only for now" elsewhere. Turning it off cancels a read in progress within one second.
2. **Request `verify_code`** `{tabId, site}` (CLI: `verify-code <tabId> [site]`). Checks in order: sign-in on, reader on for this device, macOS, same tab/site/allowlist checks as `sign_in`, shared limit plus 3 `verify_code` per 10 min, paired, tab has a code field. Then the relay asks the reader; the code is filled with the existing `fillOtp` into frames on the tab's host. Reply is `{ok, domain, filled:true}`, never the code. It does not submit. Each read shows a notification naming the host.
3. **Reader (macOS)**: the relay starts a small Swift app (`com.passbridge.codereader`, no Dock icon) through `open -g -j -n` so the Accessibility grant belongs to the reader, not Chrome or python. One-shot 0600 socket plus random nonce. The reader watches only Apple's prompt process by bundle id, ignores prompts open before the request, refuses two at once, presses Allow, reads exactly one `^\d{3}\s?\d{3}$` text, sends it and exits. It writes nothing to disk, stdout or stderr. A `--describe` mode (digits masked) fixes the real bundle id and button ids once.
4. **Audit**: Activity rows `{t, op:"verify_code", host, result}` with reasons (`code_reader_off`, `mac_only`, `no_field`, `reader_permission`, `no_prompt`, `several_prompts`). No value anywhere.
5. **Docs**: `docs/agent-protocol.md`, `SETUP.md` (permission step, how to turn off).

### Security / risks
- Removes Apple's human-presence check (why the old reader was removed). Limits: opt-in per device, only a prompt that appears after the request, one prompt at a time, allowlisted tab only, 3 per 10 min, notification per read.
- Any same-user process can send `verify_code` (no per-client auth); it only gets a filled field on an allowlisted host, never the digits.
- Accessibility is granted to the reader app alone, not Chrome (otherwise every native host would inherit it). Firefox hit the same attribution problem (https://bugzilla.mozilla.org/show_bug.cgi?id=1576733); permissions follow the responsible process (https://developer.apple.com/forums/thread/805245).
- Window matching by bundle id plus fresh window plus exactly one 6-digit text, not by title.
- Ad-hoc signing changes on rebuild and voids the grant: `install.sh` rebuilds only when the source hash changes.

### Decisions
- D1 scope: A) Apple's prompt on the Mac only (recommended) B) A plus SMS from Messages (needs Full Disk Access) C) A plus B plus email D) do not build, rely on Apple's AutoFill
- D2: A) reader presses Allow itself (recommended) B) the person presses Allow, reader only reads the code
- D3 code destination: A) filled into the agent's allowlisted tab, never returned (recommended) B) also returned over the socket behind a second switch (needed to sign in on another machine with this Mac as trusted device; breaks the "no reply holds a code" rule)
- D4 build: A) `install.sh` builds with `swiftc`, ad-hoc signed (recommended) B) signed with a Developer ID in `release.yml`
- D5: A) one Apple sign-in is started once so `--describe` records the real prompt structure (recommended) B) build from guesses

### Alternatives (fetched this session)
- Apple's Security Code AutoFill needs a person to click the suggestion and does not cover the trusted-device prompt (https://www.macrumors.com/2025/06/12/ios-26-macos-tahoe-expand-one-time-code-autofill/).
- Reading the Messages database: SMS only, needs Full Disk Access (https://dev.to/mparker25/bypassing-2fa-in-web-scraping-why-imessage-is-a-local-sql-database-and-how-that-changes-everything-2olg); Apple sends codes to trusted devices first (https://support.apple.com/en-us/102606).
- Reading from the Python relay or osascript: the permission would land on python3/osascript/Chrome. Rejected.
- System Settings "Get Verification Code" (https://support.apple.com/en-us/102660): fragile across macOS versions; kept as fallback.
- Chrome native hosts are child processes (https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), hence the reader is launched through `open`.
- Not building it: status quo since `4212455`.
