# Project Proposal — Quantity Takeoff

## Project Understanding
You need assistance with: 
**Stop the schedule-boundary and entity-inspection pollers while the tab is hidden**

*Project description:*
Two frontend pollers keep issuing websocket requests while the tab is hidden. `cards/helman/data-changed.ts` already establishes the pattern this repo wants — it checks `document.hidden`, parks the pending kinds, and flushes them on `visibilitychange` — but two timers were written independently of it and never picked it up.

The numbers below are measured, not estimated: response sizes were read off a live websocket against a real instance, and **wire bytes are after `permessage-deflate`, which Home Assistant negotiates** (raw JSON size overstates the cost by 15-25x on these payloads, so it is the wrong number to plan against).

A dashboard with the inspector and schedule cards open costs **~85 KB/hour** in total — negligible, and correctly suppressed when hidden. The config panel left open costs **~5.1 MB/hour, around 123 MB/day**, and none of it stops when the tab goes to the background. Row 7 is, by two orders of magnitude, the only frontend-initiated traffic worth acting on; row 6 is included because it is the same three-line fix and it is the only other path that fetches with nobody watching.

**Not the state stream.** Separately measured, helman's derived sensors push ~300k state changes/day, costing ~15 MB/day per connected client on the wire (~4% of everything the instance pushes). That is a backend concern — unthrottled `update_value` in `HelmanBatteryTimeSensor` and `HelmanSourceRatioSensor`, plus `history_bucket_duration: 1` — and is deliberately **not** part of this issue.

**Event frequency caveat.** Rows 2-5 fire at most 4/h, driven by `_async_refresh_forecast` on `async_track_time_change(minute=[0,15,30,45])` (`coordinator.py:4284`) whose re-plan fires `_fire_data_changed(PLAN)` unconditionally (`coordinator.py:654`). On an instance without `automation.execution_optimizers` that path short-circuits at `coordinator.py:2675`: a 10-minute subscription measured **0 events**. So rows 2-5 are a ceiling, not a steady cost. Rows 6 and 7 are unconditional.

## Goals

**G1 — No helman websocket request originates from a hidden tab.** The two guarded timers join the three paths that already behave, so "the app is in the background" means "helman is quiet" without exception.

**G2 — Coming back to the tab shows current data immediately.** Suppression must not turn into staleness: returning to a hidden tab refetches at once rather than waiting for the next natural tick, which for row 6 could be a full slot boundary away.

## Plan

- **Add `frontend/cards/shared/document-visibility.ts`.** Two exports and nothing more: `isDocumentHidden(): boolean` (the `typeof document !== "undefined" && document.hidden === true` check, so the bundles still load under SSR/test contexts without a `document`), and `whenVisible(callback: () => void): () => void`, which registers a `visibilitychange` listener firing `callback` only on the hidden→visible edge and returns its unsubscribe. `cards/shared/` is the right home: the config-editor bundle already imports from it (`config-editor/helman-config-editor.ts:70`, `:90`, `:97`) and so does every card.

- **Guard the entity-inspection poll (row 7)** in `config-editor/helman-config-editor.ts`. `_pollEntityInspections` already discriminates its caller via `trigger: "idle" | "change"` (`:4063`), so the guard is one line beside the existing in-flight check at `:4065` — `if (trigger === "idle" && isDocumentHidden()) return;`. Only the idle tick is suppressed; a `"change"` trigger comes from a user edit and cannot occur in a hidden tab. Leave the `setInterval` itself running — it costs nothing once its callback returns early, and letting it run keeps `_restartEntityInspectionTimer`'s rhythm intact.

- **Guard the schedule boundary refresh (row 6)** in `cards/shared/schedule/schedule-owner.ts`. **The trap here is that the timer is self-perpetuating** — `_refreshSchedule`'s `finally` block calls `_scheduleNextBoundaryRefresh()` (`:343`), so a guard that simply skips the fetch also kills the chain and the timer never returns. Instead, in the `setTimeout` callback at `:375`: when `isDocumentHidden()`, skip `refresh()` and call `_scheduleNextBoundaryRefresh()` directly to re-arm for the following boundary, and set a `_boundaryMissedWhileHidden` flag. No network, chain alive.

- **Wire both to `whenVisible`.** The config editor registers in `connectedCallback` and disposes alongside the existing timer teardown in `disconnectedCallback` (`:1035-1050`); on the visible edge it calls `void this._pollEntityInspections("idle")` once. `ScheduleOwnerImpl` registers when its first listener arrives (beside `_ensureDataChangedSubscription`, `:269`) and unregisters in `_dispose` (`:405`); on the visible edge it calls `void this.refresh()` if `_boundaryMissedWhileHidden` is set, then clears the flag. Both unsubscribes must be idempotent and must run on teardown — a leaked `visibilitychange` listener holding a card instance is the failure mode this shape can introduce.

- **Cover both in Playwright.** New specs alongside the existing `tests/auto-refresh-config-editor.spec.ts` and `tests/auto-refresh-inspector.spec.ts`, following their shape: mount the compiled bundle with `page.addScriptTag`, stub `hass.callWS` with a call counter. Drive visibility with `Object.defineProperty(document, "hidden", { value: true, configurable: true })` followed by `document.dispatchEvent(new Event("visibilitychange"))`, since `document.hidden` is read-only. Assert, for each of the two pollers: the call count does not advance across a tick while hidden, it advances exactly once on the visible edge, and it resumes its normal rhythm afterwards.

## Acceptance

- With the config panel mounted and the document hidden, no `helman/inspect_entities` request is issued; the count advances by exactly one when the tab becomes visible again. Asserted by a new spec.
- With a schedule loaded and the document hidden, a crossed slot boundary issues no `helman/get_schedule`; one is issued on the visible edge, and the boundary timer is still armed for the next boundary afterwards — the self-perpetuation must survive. Asserted by a new spec.
- The three already-guarded paths (rows 2-5) are unchanged: `tests/auto-refresh-config-editor.spec.ts` and `tests/auto-refresh-inspector.spec.ts` still pass untouched.
- `cd frontend && npm run build` clean, then `npx playwright test` green — the specs mount the compiled bundles, so the build must run first.
- `/code-review` run on the change and its findings resolved before the PR.

## Deliberately not doing

**Shrinking the `inspect_entities` request.** Each idle tick ships the whole config plus `saved_config` — 19.3 KB raw, 2.7 KB on the wire. Sending a hash and the full document only on a mismatch would cut the foreground cost too, but it changes the `helman/inspect_entities` backend handler as well as the client, and the visibility guard already removes the entire background cost. The foreground cost is only paid while someone is actively looking at the panel, which is the one time it is justified. Worth revisiting only if the panel's foreground traffic is ever measured as a problem in its own right.

**Migrating `data-changed.ts` onto the new helper.** It has its own `_ensureVisibilityListener` / `_isHidden` pair (`:180-195`), which is the third copy of this pattern and an obvious DRY target. Left alone on purpose: it guards *events*, not a timer, and its listener is entangled with `_clearFlushTimer` and the parked `_pendingKinds` set, so the helper would replace about three lines of well-tested working code while putting the one path that currently behaves correctly at risk. It can adopt the helper later, separately.

**The backend state-stream churn.** The unthrottled `update_value` in `HelmanBatteryTimeSensor` (`sensor.py:167`) and `HelmanSourceRatioSensor` (`sensor.py:342`) — which the May 2026 hysteresis pass `b5304f2` skipped — plus `history_bucket_duration: 1`, together account for ~15 MB/day per client. Real, and larger than rows 6 and 7 combined in absolute terms, but it is backend work with a different risk profile and belongs in its own issue.

**Compensating for browser timer throttling.** Hidden tabs already clamp `setTimeout`/`setInterval` to roughly one minute, so row 6 fires late in the background today and row 7 is already slowed. That throttling is a happy accident, not a guarantee, and it varies by browser and by the companion app's webview; the guards make the behaviour explicit rather than depending on it. No attempt is made to detect or tune around the throttle.
