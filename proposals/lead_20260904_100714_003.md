# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**RFC: versioned add-in folders behind a stable shim, so updates never need Revit to close**

*Project description:*
## Problem

Every add-in update today has to close Revit, per installed version, because Revit holds the loaded `MCPBridge.AddIn.dll` and its dependencies open and Windows will not let the installer replace them. Everything temperamental about self-update follows from that one constraint: the 30 s close wait, the deferred path with its process watcher, logon task and re-run rules (#210), the "did it close, will it close" uncertainty for the user, the per-version bookkeeping (`deployed` / `deferred` / `skipped`), and a Status window that has to explain which of several states each Revit is in (#209). The server half already avoids the problem with a staged swap plus self-eviction (#205); this RFC does the equivalent for the add-in.

## Proposal

Install a small, stable **shim** as the Revit add-in, and have it load the real add-in from a **versioned folder** at Revit startup.

```
%APPDATA%\Autodesk\Revit\Addins\2027\MCPBridge.addin      -> points at the shim (unchanged across releases)
%APPDATA%\Autodesk\Revit\Addins\2027\MCPBridge.Shim.dll    (tiny, rarely changes)
%LOCALAPPDATA%\Programs\MCPBridge\addin\
    current.json                          {"version":"v0.1.5"}          (atomic pointer, written last)
    v0.1.4\2025\...  v0.1.4\2027\...      (full add-in payload per Revit version, as today's addin-<year>/)
    v0.1.5\2025\...  v0.1.5\2027\...
```

- **Shim** (`IExternalApplication`): reads `current.json`, `Assembly.LoadFrom`s `addin\<version>\<revit-year>\MCPBridge.AddIn.dll`, registers an `AssemblyResolve` handler for that folder (the real add-in already does this for Roslyn/SQLite via `AssemblyResolution`/`RoslynAssemblyIsolation`; the shim's handler just adds the folder to the probing list), instantiates the real `MCPBridgeApplication` and forwards `OnStartup`/`OnShutdown`. On any failure it logs to `startup-errors.log` and returns `Result.Failed` — never takes Revit down. If `current.json` names a folder that lacks this Revit year's payload, it falls back to the newest folder that has one (a release may ship for one version only).
- **Installer**: an update becomes *download → verify → write `addin\<new>\...` → atomically replace `current.json`*. No process is asked to close. Revit instances already running keep the version they loaded (its files stay untouched); the new version loads on their next start. Old version folders are deleted on a later run once no Revit process has them mapped (same shape as `Remove-StaleBrokerImages`). The server keeps its staged swap + self-eviction.
- **Ribbon**: Update Now becomes "download and install now; the new add-in loads when you next start Revit" with an optional "Restart Revit now?" that asks to close (Revit's own save prompt) — a convenience, never a requirement. Status shows `MCP Bridge (add-in): v0.1.4 running, v0.1.5 installed — restart Revit to load it`, the same shape the server line already has.
- **`update_connector`**: `apply` no longer closes anything; the result says which Revit versions are running an older add-in than installed.

## What this removes
The close wait, `Stop-RevitProcessGracefully`, the deferred-update watcher and its logon task, the pending-update manifest and `-ApplyPendingUpdate`, the `deferred` marker state, and most of #209/#210. Multiple Revit versions stop being a special case: each is just a folder under the version.

## What it costs / risks
- **Migration**: the first install of the shim replaces today's flat Addins layout, which needs Revit closed one last time (the existing close/defer machinery does that job once, then retires).
- **Trust prompt**: Revit's "unsigned add-in" prompt is keyed by the loaded assembly's content. The shim rarely changes (prompt once); whether Revit also prompts for assemblies the shim `LoadFrom`s must be verified live on 2025 and 2027 — if it does, the real add-in must be signed with the same certificate and the prompt is still once per release, no worse than today.
- **Load context**: `LoadFrom` into the default context is what Revit does today for the add-in itself; Roslyn script references (`LoadableReferences()` enumerates the AppDomain) and `Eichler.Connectors.Revit` discovery are unaffected as long as the same assemblies load once. Two different versions must never load in one process — the shim loads exactly one and the pointer is read once at startup.
- **Ribbon `PushButtonData`** takes an assembly path for the command classes — it must be the versioned real assembly's path, which the shim knows at load time (today it is `typeof(MCPBridgeApplication).Assembly.Location`, so this is already the case).
- **Uninstall**: remove shim + manifest + the whole `addin\` tree; nothing else changes.
- **Disk**: one payload per installed release until cleanup; ~a few MB per version-year, acceptable.

## Verification plan
1. Shim + one versioned folder on both Revit years: add-in loads, ribbon works, discovery and scripts unaffected (tier 2 sweep).
2. Drop a second version folder + pointer while Revit runs: nothing happens; restart Revit: new version loads; old folder is cleaned on a later installer run once unmapped.
3. Trust-prompt behaviour on first load of a new version folder, per Revit year.
4. Installer: fresh install, update, update with a running Revit (no close, no defer), uninstall.

## Relationship to other items
- #202 (service-hosted primary) is the server-side counterpart: both remove "a process must exit for the update to take effect". Either can go first; together they make an update "download now, take effect at next start" for every component.
- #209 and #210 become mostly moot; worth doing only the parts that still apply while this RFC is pending.
