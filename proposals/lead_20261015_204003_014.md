## Destination

A spec, with its build tickets, for each of these 11 items, so the kit is something a non-builder can start in minutes and a developer can trust:

1. **Solo mode:** start attended work in minutes with no ruleset or cloud environments, refuse the dangerous pushes outright while there's no ruleset, and offer the full set-up later. **Spec:** [#32](https://github.com/medTech-group/pairnexus-workflow/issues/32) (tickets: #43, #44, #45, #46, #47, #48, #49, #50; owner task #51).
2. **Guard robustness:** the hooks fail closed when they can't run (old Python, a missing copy), and the permission modes behave as the docs say. **Spec:** [#33](https://github.com/medTech-group/pairnexus-workflow/issues/33) (tickets: #52, #53, #55, #56, #57; owner task #54).
3. **`workflow doctor`:** one report of what's set up and what isn't, with plain fixes; it never changes anything. **Spec:** [#34](https://github.com/medTech-group/pairnexus-workflow/issues/34) (tickets: #58, #59, #60, #61, #62, #63, #64; owner task #65).
4. **Automated GitHub set-up:** the ruleset and merge settings created through the API after one confirmation, once CI has produced its check names; the click-by-click steps as a fallback. **Spec:** [#38](https://github.com/medTech-group/pairnexus-workflow/issues/38) (tickets: #66, #67, #68, #69, #70, #71; owner task #72).
5. **A quickstart and a glossary for non-builders:** what you need (Claude plan, GitHub, local or cloud), the first ten minutes, and plain words for PR, CI, merge and revert. **Spec:** [#35](https://github.com/medTech-group/pairnexus-workflow/issues/35) (tickets: #73, #74, #75, #77; owner task #78).
6. **Judging a PR without reading code:** a plain-language summary, a merge helper that never says "ready" while CI is red, and a link to try it. **Spec:** [#39](https://github.com/medTech-group/pairnexus-workflow/issues/39) (tickets not yet written).
7. **One starter template:** a web app with tests, CI, a filled profile and the kit installed, created from the guided start. **Spec:** [#40](https://github.com/medTech-group/pairnexus-workflow/issues/40) (tickets not yet written).
8. **A preview deploy per PR**, so a person can try a change. **Spec:** [#41](https://github.com/medTech-group/pairnexus-workflow/issues/41) (tickets not yet written).
9. **A session budget and a light review preset:** usage shown and capped through the levers the kit has (sessions, parallelism, review rounds, end time). **Spec:** [#42](https://github.com/medTech-group/pairnexus-workflow/issues/42) (tickets not yet written).
10. **A release trust gate:** the unproven rows of `docs/spike.md` closed on a demo repo, then re-run before each release. **Spec:** [#36](https://github.com/medTech-group/pairnexus-workflow/issues/36) (tickets not yet written).
11. **Open-source readiness:** the name, PAIR-specific text, and the support promise. **Spec:** [#37](https://github.com/medTech-group/pairnexus-workflow/issues/37) (tickets not yet written).

## Notes

- **Every Destination item has its spec.** Next: build tickets for each spec with `to-tickets`, one spec per session. Build tickets wait until every item has its spec and tickets (the flow's gate).
- **Who it's for:** people who don't know how to build software and need a way to, and developers who want extra help (the owner's vision). The kit asks each person which they are and adapts (see Decisions so far).
- **Where the reasoning comes from:** the recommendations and their second look (an independent review) are in the session that charted this map. The review's main corrections:
  - trust comes before features;
  - the guard fails open on old Python;
  - solo mode is mostly a set-up path, plus denying risky pushes when there's no ruleset;
  - one starter, not four;
  - preview deploys rather than screenshots;
  - a budget the kit can enforce, not a usage cap it can't measure;
  - local unattended runs would remove the credential-free boundary.
- **Skills each session consults:** `grilling` and `domain-modeling` for every grilling ticket, `research` for research, `prototype` for prototypes. Specs come from `to-spec`, tickets from `to-tickets`.
- **This repository isn't set up with the kit itself** (no profile), so work this map with `/wayfinder <this map>` rather than `/next`.
- **The demo repository** is the existing `medTech-group/pairnexus-workflow-sandbox` (private, kit vendored, ruleset active, environments `workflow-ticket` and `workflow-conductor`, Cloudflare Workers Builds connected with previews on).
- **Fixed, apart from the map:** [The hooks fail open when python3 is older than 3.11](https://github.com/medTech-group/pairnexus-workflow/issues/22), in 0.1.8 ([#24](https://github.com/medTech-group/pairnexus-workflow/pull/24)). That covers Destination item 2's "old Python, a missing copy" half for ticket and conductor sessions; its spec ([#33](https://github.com/medTech-group/pairnexus-workflow/issues/33)) owns the permission-mode half and the remaining ways the guard fails open (attended failures, timeouts, the plugin, `Monitor` and `PowerShell`).
- **Found apart from the map, while writing #35's tickets:** [The flow the context hook adds is longer than Claude Code's 10,000-character limit](https://github.com/medTech-group/pairnexus-workflow/issues/76), to confirm live first.
- **The order:** launch-critical first (items 1, 2, 3, 5, 10, 11), then 4, 6, 7, 8, 9.

- [Can a cloud session create a ruleset and change merge settings?](https://github.com/medTech-group/pairnexus-workflow/issues/14): no through the MCP tools, unknown through the proxy; yes from a local session with the owner's own `gh`. So automated set-up runs locally, with the click-by-click fallback; a cloud session can still read rulesets and merge settings, which is enough for `workflow doctor`.
- [Which host gives a free preview deploy per PR, and how does it fit?](https://github.com/medTech-group/pairnexus-workflow/issues/18): Cloudflare, connected through its own GitHub App (Workers Builds previews; Pages for static sites). It is the only free tier that allows commercial use and builds commits Claude authored on a private org repository; the link arrives as a PR comment and check, with no secret in GitHub. Previews are public by default, so synthetic data only, and Cloudflare Access where the profile has `[sensitive]` rules. Not a required check at first. Unverified points go to [Try a Cloudflare preview with Claude-authored commits on the demo repository](https://github.com/medTech-group/pairnexus-workflow/issues/23).
- [Does the guard's ask reach the person in every permission mode?](https://github.com/medTech-group/pairnexus-workflow/issues/15): yes in `default`, `acceptEdits` and `auto` (documented). Unconfirmed in `bypassPermissions`, so the kit never relies on it there. A headless session refuses an `ask`. Exit 1 fails open (fixed in 0.1.8). The owner chose not to run a live interactive check.
- [Who is the first user we design for?](https://github.com/medTech-group/pairnexus-workflow/issues/16): nobody in particular; the kit asks each person.
  - Two levels, *new to building* or *developer*, asked once as the guided start's first one-tap question (skipping means new).
  - Kept as a per-person override (a cloud environment's `WORKFLOW_EXPERIENCE`, or a local uncommitted file), else the project's default `experience` in the profile, set at set-up.
  - It changes only wording and pacing, never safety. GitHub writing is the same for all, plain summary first.
  - The quickstart and starter are written for someone new to building. It lands in items 1, 5 and 7.
- [Without a ruleset, should a push to the base branch be denied or asked?](https://github.com/medTech-group/pairnexus-workflow/issues/17): denied.
  - In solo mode, attended sessions are refused what touches the base branch (push, force-push, delete, `--admin` merge, changing it or its protection). Feature branches stay "ask".
  - Creating a ruleset is asked; editing or deleting one is refused.
  - A profile setting (`ruleset = false`) marks solo mode: set-up writes it, moving to the full set-up flips it, `workflow doctor` checks it, and projects without it behave as today.
  - The refusal explains, gives the command to run by hand and offers the set-up.
  - Unattended runs in solo mode are allowed after a plain warning the owner confirms (the owner's choice).
- [What stack is the first starter, and where does it live?](https://github.com/medTech-group/pairnexus-workflow/issues/20): TypeScript on Cloudflare (React + Vite, Hono on Workers, D1).

  - Its own template repository under medTech-group; the guided start creates a project from it locally with `gh`, else gives GitHub's "Use this template" link.
  - Projects made from it start in solo mode with `experience = "new"`, and get the weekly update check.
  - It tests itself (Vitest, Playwright); the release gate checks a fresh copy.
  - D1 on previews is still untried (the trial's Worker had no database): the starter's own trial checks it.
- [Keep the name pairnexus, and how much support do we promise?](https://github.com/medTech-group/pairnexus-workflow/issues/21): keep `pairnexus-workflow` (PAIRnexus as the umbrella brand), and stay at medTech-group for launch.
  - Support is best-effort, plus security reports acknowledged within 5 working days and a fix release when a Claude Code change breaks the guard or hooks.
  - The README's opening speaks to the reader; PAIR's story moves to a short "Where it came from".
  - Past commit history stays; new commits use the owner's noreply address.

- [Try a Cloudflare preview with Claude-authored commits on the demo repository](https://github.com/medTech-group/pairnexus-workflow/issues/23): previews work for Claude's commits, with no approval hold.

- [How does a project move from solo mode to the full set-up?](https://github.com/medTech-group/pairnexus-workflow/issues/26): two separate upgrades, "Protect `main`" (ruleset + merge settings) and "Set up unattended runs" (the two cloud environments).
  - Offered only when asked, in the guard's refusal, before an unattended run in solo mode, and in `workflow doctor`.
  - The ruleset is made at once (pull requests only, no force-push, no deletion); required checks are added once CI has run.
  - A small PR flips `ruleset = true`; partial progress is only ever stricter.
  - Automatic locally with `gh`; guided clicks with a read-back in the cloud; a ready message for the owner when the person isn't an admin.
  - Removed protection is flagged by `doctor` and treated as solo mode by the conductor.
- [What does `workflow doctor` check, and how does it report it?](https://github.com/medTech-group/pairnexus-workflow/issues/27): one CLI command, plus a session skill `check-setup` (not `doctor`, which Claude Code already has) handing it what only a session sees.
  - Checks the computer, the kit, the settings, GitHub's ruleset and merge settings, CODEOWNERS, the environments and Cloudflare's `[previews]`; not what's inside an environment, nor usage.
  - Grouped lines with a one-sentence fix each, worded by experience; `--json`; `--strict` for CI and the release gate.
  - Offered by the guided start, run by the conductor's pre-flight, never at every session start; same in plugin mode.
- [Where does the quickstart live, how long is it, and which words does the glossary define?](https://github.com/medTech-group/pairnexus-workflow/issues/28): `docs/quickstart.md`, linked from the README's top and the starter.
  - One page, at most 10 steps, cloud sessions only: from nothing to a first merged change; protecting `main`, previews and unattended runs as next steps.
  - Previews get their own step-by-step page, `docs/previews.md`, avoiding the trial's three traps.
  - One `docs/glossary.md` ("Building words", "The kit's words"), about 20 words; Claude explains each once at first mention to someone new to building.
- [How does the release trust gate run, and what must pass?](https://github.com/medTech-group/pairnexus-workflow/issues/29): on the release PR, before it merges (merging publishes).
  - Must pass on the sandbox: the update with CI green, `doctor --strict`, the guard's refusal in a cloud ticket session, the ruleset's refusal, and (once it exists) a fresh starter project with CI green and a working preview. Rows 13, 17 and MCP-merge misuse are proven once, in the next real run.
  - Run by a kit-only `release-gate` skill in a cloud session; a required "release gate" check reads its pass line for the PR's exact commit.
  - Every release; an urgent fix may skip with a label and a written reason, shown in the release notes, never twice in a row.
  - The candidate goes onto a sandbox branch, merged only after the release is published.
- [What does a plain-language PR summary say, and when may the merge helper say "ready"?](https://github.com/medTech-group/pairnexus-workflow/issues/30): every PR opens with "In plain words" (what changes for you, how to try it, what could go wrong), written by `build-ticket` and a PR template set-up installs.
  - A `merge-check` skill answers in the chat: "ready" only with every required check green on the latest commit, no conflict, no unanswered comment and a clean last review round; "Not yet" with the reason otherwise; kit and CI files always need the owner.
  - "Ready" means try the preview first; a failed preview blocks, no previews doesn't.
  - A one-tap "Merge it now"; the conductor uses the same rules.
- [Which levers does the session budget use, and what are its presets?](https://github.com/medTech-group/pairnexus-workflow/issues/31): three presets (Light, Normal, Thorough) bundling the charter's limits, review rounds and the UI explorer.
  - "Quick build #12" uses the light review in attended sessions, still never merging while CI is red.
  - The estimate before a run is in sessions and hours, refined by past run reports.
  - The charter offers the presets first; the default is `run.preset` in the profile.

## Out of scope

- **Local unattended runs** (headless `claude -p` on the owner's machine): later, and only inside a container with no credentials, since ticket sessions would otherwise run beside the owner's `gh` token and keys.
- **More than one starter** (Flutter, API-only and others): after the first proves itself.
- **Production deploy recipes for hosting providers:** preview deploys per PR are in (item 8); deploying to production is a later map.
- **A docs site:** the quickstart and glossary cover launch.
- **A cheaper model for ticket sessions:** later, once the release gate can measure quality ([Which levers does the session budget use, and what are its presets?](https://github.com/medTech-group/pairnexus-workflow/issues/31)).
