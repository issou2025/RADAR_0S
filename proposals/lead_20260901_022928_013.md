## Project Understanding
You need assistance with: 
**[Bug]: Installer prints an `Installer log:` path that is normally deleted before the user can read it**

*Project description:*
## Summary

When an npm install fails, `print_npm_failure_diagnostics` offers the user a path to the captured log:

```bash
echo "  Installer log: ${log}"   # L1191
```

That log is allocated through `mktempfile` (L1222), which registers it for deletion:

```bash
mktempfile() {
    local output_var="${1:?output variable required}" f
    f="$(mktemp)"
    TMPFILES+=("$f")            # L73
    printf -v "$output_var" '%s' "$f"
}
```

and `cleanup_tmpfiles` removes every registered path on exit:

```bash
for f in "${TMPFILES[@]:-}"; do rm -rf "$f" 2>/dev/null || true; done   # L47-48
trap cleanup_tmpfiles EXIT                                              # L51
```

The file still exists at the moment L1191 prints. But on an unrecovered failure the script then exits, the trap runs, and the path is gone before the invoking shell returns control — which is when a user actually reads the message and tries to open it.

I hit this while investigating #134201: both `Installer log:` paths the installer offered were already gone by the time I looked, which is part of why that bug took as long as it did to characterize.

## Scope — where this does and does not apply

Being precise about this, since the failure modes differ:

- **Applies:** an npm failure that reaches L1234 and is not subsequently recovered — the script exits, the trap fires, the advertised path is gone.
- **Does not apply:** build-tool remediation succeeding at L1228-1230 returns before diagnostics are printed at all.
- **Diagnostics printed ≠ terminal failure:** L1234 runs *before* the ENOTEMPTY (L1248-1250) and EEXIST (L1258-1260) recovery branches, so the installer can print a log path and then recover and succeed. The path is still deleted at exit, but no one is looking for it.
- **Trap does not always run:** a successful `exec "$claw" onboard` at L4051 replaces the shell, so the EXIT trap never fires and the registered temp files survive.
- The deletion is `rm -rf ... || true` — an attempted deletion, not a guaranteed one.

So this is not "always"; it is "on the path where the message matters most."

## Why the surrounding output does not compensate

- **`tail -n 80 "$log"` (L1242)** runs only when `VERBOSE != 1`, and 80 lines routinely truncates node-gyp/cmake failures — the installer's own build-tools detector at L823 matches strings (`gyp ERR! find Python`, `CMAKE_MAKE_PROGRAM is not set`, `Failed to build llama.cpp`) that appear deep inside multi-hundred-line build output.
- **The log is overwritten per attempt** — `>"$log"` in the plain branch (L1129), the gum branch (L1126), and `tee "$log"` in verbose (L1120) all truncate rather than append. After a retry, the earlier attempt's full content is gone; at best its last 80 lines were printed before the retry.
- **The npm debug-log breadcrumb is conditional** — L1208-1211 prints `npm debug log:` only when `extract_npm_debug_log_path` succeeds. The line that always prints on failure is the one that stops resolving.

## Suggested fix

Either resolution is fine:

1. **Preserve on failure** — unregister the log from `TMPFILES`, or copy it to a stable location, before returning from the unrecovered-failure path, so the advertised path resolves.
2. **Stop advertising it** — drop L1191 and rely on the conditional `npm debug log:` line plus the tail.

The state worth removing is the one where the installer names a path the user cannot open.

If preservation is chosen, note that the captured content is not guaranteed to be low-sensitivity: `NPM_LOGLEVEL` is `${OPENCLAW_NPM_LOGLEVEL:-error}` (applied at L1110), so `error` is only the default and can be raised, and npm lifecycle scripts can emit arbitrary output including paths or secrets. Retaining a file on disk has a different exposure model than printing to a terminal, so a preserved log may deserve a predictable location the user can find and delete rather than a random temp name.
