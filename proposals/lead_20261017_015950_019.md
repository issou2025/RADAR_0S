# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**feat(gate): hold every push to zero leftovers, zero leaked processes and a peak temporary-disk budget**

*Project description:*
## What

Make every publishing push of this repository record three facts about its complete gate's effect on the host, hold the push to three new strict root budgets over them, and fix every leak `spike-gate-host-impact-report` found, so those budgets land green.

### 1. The recorder, `orchestrator/gate_impact.py`

A module of the `orchestrator` package. It is the one source of the record's shape, the CLI and the scratch registry below. Its writer and its reader are both in it, so the shapes cannot drift between them. The spike's `spikes/gate-host-impact/record.py` is a working prototype of most of it.

**`python -m orchestrator.gate_impact run [--push ID] [--summary FILE] -- COMMAND [ARG...]`** runs COMMAND and exits with its status (128 + the signal number when a signal ended it):
- It makes a fresh root with `mkdtemp(prefix="g-")` under `${XDG_CACHE_HOME:-$HOME/.cache}/ai-orchestrator/gate-tmp/`. On this host that puts `<root>/tmp` at 57 bytes on `/home`. The root must sit outside every checkout `config/onevcs.checkouts` registers, because under one the suite's checkout-read guard (`tests/conftest.py` `_checkout_reads_are_declared`) refused ~3,400 tests in the spike's attempt 4. It must also stay about this short, because Chromium's `SingletonSocket` under a deeper root broke the `render-diagram` journeys in the same attempt. The exception is a recorder started inside another recorder's command, which `ORCHESTRATOR_GATE_SCRATCH` being set reveals: its root goes inside the outer one's `TMPDIR`, so the outer recorder counts it. The root holds `tmp/` and `scratch/`.
- It exports `TMPDIR`, `TMP` and `TEMP` as `<root>/tmp`, and `ORCHESTRATOR_GATE_SCRATCH` as `<root>/scratch`, to COMMAND. It unsets `ONEPIPELINE_NODE_SCRATCH_DIR` and `PYTEST_DEBUG_TEMPROOT` for COMMAND. A push from a dispatch inherits both, and writers that prefer them over `TMPDIR` (`orchestrator/follow_up_drafts.py`, `scripts/allowlist-probe.py`, `scripts/node-scratch-dir.sh`, `tests/pytest_temp_root.py`) would otherwise write outside the root.
- It calls `prctl(PR_SET_CHILD_SUBREAPER, 1)` before starting COMMAND, so every descendant orphaned while COMMAND runs is re-parented to the recorder, and it reaps adopted zombies while COMMAND runs. Adoption only re-parents orphans, and an adopted process can still have live children of its own, so every snapshot and every signal below covers the recorder's whole descendant tree, never only the processes re-parented to it.
- Every 5 s while COMMAND runs, and once the moment it exits, it samples the allocated size (`du -s --block-size=1`'s figure) of `<root>/tmp` plus every registered path that exists, and times the walk. Samples never overlap: a walk longer than the interval delays the next sample. In the spike a walk took 0.33 s on average and 1.59 s at most, but 7.3 s once under load1 41. The largest sample is the peak. An allocation created and removed between two samples is not seen; that limit is an escalated exception, stated once in the module's docstring.
- The moment COMMAND's own process exits, it snapshots every process in the recorder's own descendant tree, found recursively (each adopted process, its children, their children, and so on, by walking parent links in `/proc` down from the recorder's pid, excluding the recorder and its own sampler) alive then, zombies excluded. Each is leaked, and is counted even if it exits a moment later.
- Before it signals anything, it counts the entries and bytes in `<root>/tmp` and in each registered path that still exists. So a leaked process that removes its files when stopped cannot erase them from the record. Zero-byte top-level files matching `uv-[0-9a-f]{16}.lock` are counted separately and left out of the leftover figure.
- It then waits up to 10 s for the leaked processes to exit on their own, reaping each that does, sends TERM to every member of the tree still alive, then re-walks the tree and sends KILL to every member still alive 5 s later, children started meanwhile included. The wait only bounds how long it lets them stop; it changes nothing about what was counted. `stopped_by` records `"exited"`, `"TERM"` or `"KILL"`.
- It writes the record, then removes its root and every registered path outside it, first restoring owner permissions on any directory a test left unreadable (the spike met a mode-000 `runs` directory that defeated `shutil.rmtree`). So the host is left clean whatever the verdict. It removes only paths registered in its own `scratch/` directory, and signals only processes in its own descendant tree, so concurrent recorders never touch each other's files or processes.
- With `--push`, it writes the record to the push file; with `--summary`, to FILE. Either way it prints a one-line summary on stderr. It never holds the caller's stdout or stderr open past its own exit.

**The record**, one JSON object written whole and renamed into place, at `${XDG_STATE_HOME}/ai-orchestrator/gate-host-impact-push.json` (an absolute `XDG_STATE_HOME`, else `$HOME/.local/state`, by `scripts/lock-timeout.sh`'s `local_direct_gate_state_file` rule):
- `schema_version`: `1`.
- `push`: string, the `ORCHESTRATOR_GATE_PUSH` the hook named.
- `exit_status`: integer, COMMAND's status.
- `sample_seconds`: number, `5`; `samples`: integer, how many samples were taken; and `longest_walk_seconds`: number, the longest sample's walk.
- `peak_bytes`: integer, and `peak_top`: up to 10 `{path, bytes}` objects, the largest top-level entries at the peak sample, each `path` relative to `<root>/tmp` or absolute for registered scratch.
- `leftover_entries`: integer, excluding the uv locks; `leftover_bytes`: integer; `excluded_uv_locks`: integer; and `leftover_top`: up to 20 `{path, entries, bytes}` objects, largest first.
- `settle_seconds`: number, `10`, the longest the recorder waits before TERM.
- `leaked`: a list of `{pid, ppid, command, stopped_by}` objects, where `command` is the command line with credential values redacted by the package's existing redaction rule (`orchestrator/redaction.py`) and `stopped_by` is `"exited"`, `"TERM"` or `"KILL"`.

**`python -m orchestrator.gate_impact report leftovers|peak-temp-disk|leaked-processes`** is the one command all three budgets register. It reads the record for the push `ORCHESTRATOR_GATE_PUSH` names and writes onebudgetspec's result to the file `ONEBUDGETSPEC_RESULT` names. The value is `leftover_entries`, `peak_bytes` in GiB, or `len(leaked)`, and the detail is the breakdown each budget's measure names. It refuses, naming the file and the remedy as `scripts/budget-gate-time.sh` does, a missing record, an unreadable one, or one recorded for another push. It never compares a figure with a threshold.

**The scratch registry.** `register_scratch(path)` in the module, and `python -m orchestrator.gate_impact register PATH` for shell callers, each write one file into the `ORCHESTRATOR_GATE_SCRATCH` directory holding `path`, absolute. Both do nothing when the variable is unset. It is how a helper that must write outside `TMPDIR` has that scratch counted at every sample and as a leftover, and removed by the recorder once counted. No other code writes into that directory.

### 2. The hook runs the gate through it

### 4. Out of scope

Other repositories' suites, the Nx, uv and plan-store caches under `~/.cache`, and the host sweep are untouched. So are memory, CPU, network and quota, and any disk-floor stop of the gate: the spike's floor was its own protection for a throwaway run, not part of the recorder.

## Why

Test runs have repeatedly harmed the host every agent on it shares. One pytest root reached 38 GiB overnight. `/tmp` filled with tens of thousands of directories the suite never removed, until gates, test tiers and builds failed with "No space left on device". In another repository, test processes that outlived their tests held a CI step open until its timeout. Nothing today attributes what a gate leaves behind, so each regression is found only once the disk is nearly full, and every concurrent dispatch fails with it. Holding every push to zero leftovers, zero outlived processes and a bound on temporary disk catches the change that introduces such a harm at the push that introduces it. The push is refused with the leak named, and the host stays clean either way, because the recorder removes what it measured. Because the measurement is the existing gate run's own telemetry, it adds no second gate run and almost no time to a push.

- **Id:** `gate-leftovers`

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or

so it applies to every wait you write.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
