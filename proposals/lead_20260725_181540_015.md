# Project Proposal — Quantity Takeoff

## Project Understanding
You need assistance with: 
**generate_driving_distances_cli: dropped/unrouted origins are silent, undocumented, and validated too late**

*Project description:*
## Summary

`generate_driving_distances_cli.py` and the driving-distance-matrix pipeline it calls into can silently drop origins that ORS cannot route and has no in-range haversine neighbor to snap to (`_snap_unroutable_origins`, `python/utils/driving_distance_matrix.py:271-326`). Neither the diagnostic `--check-bad-locations` mode nor the normal run path treats this as a failure — both exit 0 regardless. The only enforcement point in the whole pipeline is much later, at model-run time (`python/solver/model_data.py:751-775`), decoupled in time, person, and context from wherever the CSV was generated. This ticket tracks making unrouted-origin handling explicit, documented, and validated at generation time, with a human in the loop rather than automated resolution — including removing the automated haversine-neighbor estimation step entirely (see #6).

Furthermore, `resume_from_partial_output` seems to accidentally protect against the case where potential_locations_files are changed. But this is not documented.

Reviewed as part of PR #321.

## Problems

### 1. Dropped origins never block progress anywhere in this script

- `--check-bad-locations` mode (`generate_driving_distances_cli.py:269-280`) computes the set of unroutable origins and prints/logs it, but always `return 0` regardless of whether any were found.
- The normal (write) path (`generate_driving_distances_cli.py:282-317`) is worse: it doesn't even print an aggregate summary. The only trace of a dropped origin is a single inline log line emitted during `build_distance_matrix` (`unroutable origin X: no neighbor within 1km, dropped`) — no end-of-run rollup.
- Every populated block needs a real driving distance for the solver to run at all (enforced later at `model_data.py:751-775`). Silently proceeding here just relocates the failure to a confusing, disconnected point later in the pipeline, potentially hit by a different person than whoever generated the file.
- **Needed:** when any origin is dropped, still write the CSV with whatever was successfully computed (don't lose completed work — this also composes correctly with `resume_from_partial_output`, see #3), but exit non-zero and print a clear, actionable message enumerating exactly which origins are missing. This is expected to require human intervention (e.g. manually researching/entering a distance, correcting a bad centroid) rather than automated resolution.
   - **Needed:** Clear instructions of how a human should handle the data fixes. Changes to census data? changes to a temp file? Does this need a helper script? What is the process?

### 2. `--check-bad-locations` has zero documentation. Why is it needed?

- Not mentioned anywhere in `docs/*.md` or `README.md` — the only description is its own one-line `--help` string (`generate_driving_distances_cli.py:65-67`).
- `docs/to_run.md`'s "Generating driving distances" section (lines 114-183) documents the rest of this CLI's usage in detail and never mentions this flag or when to use it.
- Given point 1 above, a system that just logs missing origins, or worse, allows for them not be logged at all, is problematic.

### 3. `resume_from_partial_output`'s purpose is undocumented, and its stated justification doesn't check out

- Its docstring (`driving_distance_matrix.py:396-413`) and the commit that introduced it (`cbe440dd`) claim it "fixes the upstream geolib bug where an existing partial output caused [...] to return without writing anything." `geolib` is not a dependency anywhere in this repo (checked `environment.yml`; no requirements file exists; no import anywhere). The function name cited in the test docstring, `get_all_distances` (`driving_distance_matrix_test.py:179-184`), does not exist anywhere in this codebase or its git history. This claim cannot be verified from anything in this repository — substantiate it (find/link the actual prior bug) or remove it.
- Verified fact, independent of the above: nothing is persisted incrementally during a run. `write_output_csv` is called exactly twice in `main()` — once in the no-op short-circuit, once after `build_distance_matrix` fully completes in memory. So this mechanism does not protect against losing progress from an interrupted ORS batch; that scenario loses everything from that attempt regardless of this function's existence.
- What it actually protects against, and should be documented as such: (a) the origin/destination set growing between runs (e.g. a new potential polling location added to `<County>_<ST>_potential_locations.csv`) — without this, regenerating would re-query ORS for the entire county instead of just the delta; (b) a human manually patching previously-dropped rows into the output CSV per #1 — resume correctly recognizes those pairs as satisfied on the next run instead of re-querying or clobbering them. This second case becomes the *only* recovery path once #6 lands.
- The fix to this is not just "document this case". It is to consider how best to address the situation where a user changes the potential locations file (adds locations) and implement that solution, denovo.

### 4. `insert_driving_distances`'s docstring overstates its own contract

- `model_data.py:471-472` docstring claims `Raises: ValueError - if anything goes wrong (missing file, bad format, missing data)`. The function itself (`model_data.py:458-484`) only raises on missing *columns* (lines 478-479). The actual missing-*data* validation lives in the caller, further down at `model_data.py:751-775`. Fix the docstring to accurately describe where completeness is actually enforced.

### 5. Open question: does a shrinking potential-locations file need to be caught at generation time?

- Team convention is that a discontinued polling location should be relabeled and added to the `bad_types` config field, not deleted from the CSV — so this should be rare in practice — but nothing in the code enforces that convention; a human could still delete a row outright.
- If a destination is removed, should `generate_driving_distances_cli.py` detect and react to that, or is it acceptable to rely entirely on the downstream "all expected locations present" check that already exists at model-run time (`model_data.py:751-775`)? Needs a decision, not just a fix. Leaning toward relying on the downstream check given the convention above, but confirm before closing this out.

### 6. `_snap_unroutable_origins`/`estimate_origin` let automation make a judgment call that should require a human — remove them

- When ORS can't route an origin at all, `_snap_unroutable_origins` (`driving_distance_matrix.py:271-326`) tries `estimate_origin` (`driving_distance_matrix.py:112-150`): for each destination independently, it finds the nearest already-routed origin within `HAVERSINE_SNAP_RADIUS_METERS` (hardcoded to 1000m, `driving_distance_matrix.py:25`, with no stated justification for that specific value) and substitutes that neighbor's real distance plus the haversine gap between the two origins. This silently fabricates a plausible-looking distance for a block that was never actually routed, indistinguishable in the output from a real ORS route.
- This is *not* the same thing as ORS's own internal point-to-road snapping (a separate, necessary approximation for any geometric centroid, which this codebase doesn't implement or control) — it's a much coarser substitution, borrowing a different block's real route entirely, over a radius an order of magnitude larger than ORS's own snap tolerance.
- **Prescribed fix: remove `_snap_unroutable_origins` and `estimate_origin` entirely.** Every origin ORS can't route directly should simply drop and surface through the fail-loud mechanism in #1 (write partial output, exit non-zero, list exactly what's missing). A human then corrects the underlying problem (e.g. fixes a bad centroid, or otherwise makes the origin routable) and reruns; `resume_from_partial_output` (#3) picks up the correction automatically on the next run. This collapses two separate silent-recovery paths (snap and drop) into the single explicit, human-gated path #1 already describes, instead of leaving a second, quieter path where an origin looks handled but was never actually routed.
- **Scope: this removal is narrow.** It does *not* include ORS's own internal road-snapping, `_retry_sources_individually` (legitimate retry of a failed batch API call, not a data-fabrication step), or `_reject_negative_metric_values`/the negative-distance handling (already correctly fail-loud, per the #294 decision). Only the neighbor-substitution fallback is in scope for removal.
  - As of this writing, the only real (non-testing) county with a committed driving-distances file is `Monongalia_County_WV`. Local generation logs (gitignored, not part of the durable record, so this check is not repeatable once they're cleaned up) show a clean run: 66,528 rows written, exactly matching the full `2772 origins × 24 destinations` product, with zero "unroutable"/"snapped"/"dropped" mentions across all available runs. No known instance of this risk is currently baked into published data.
- **Depends on / blocks `feature/driving-time-metric` (#227) — needs a follow-on ticket, not resolved here.** That branch's `estimate_origin` carries a snapped row's `duration_s` unchanged while correcting `distance_m` by the haversine offset (explicitly, because "converting that offset to a travel time would require an invented speed constant") — creating a real inconsistency between the two metrics on the same row. Removing `estimate_origin` here makes that duration-handling code moot; that branch will need to be reconciled against this change separately, once this lands.

### 7. Documentation gaps are systemic in this file and its dependencies, not isolated to the items above

Several items above (#2, #3, #4, #6) are each specific instances of the same broader pattern: this file and its immediate dependencies document *what* the code does, rarely *why* a design choice was made — leaving reviewers and future maintainers to reconstruct author intent from evidence rather than read it. Further instances found during this review, not otherwise covered above:

- Why `build_arg_parser` (`generate_driving_distances_cli.py:38`) is a separate function rather than inline like this CLI's older siblings (`model_run_cli.py`, `db_import_cli.py`) — reasonable in retrospect (testability under this repo's TDD mandate), but not stated anywhere.
- Why `_pick_coord_extractor` (`generate_driving_distances_cli.py:117`) has a branch for separate `Latitude`/`Longitude` columns alongside the documented `Lat, Lon` schema — turned out to be driven by redundant columns in the `testing` fixture rather than a second real-world schema (see #324), but nothing at the code site said so.
- Why `derive_origins_and_destinations` (`generate_driving_distances_cli.py:82-114`) ignores `config.data_source` and always reads from CSV, never the database — no comment says whether this is deliberate or an oversight.
- Why `--state` needs an override at all — the mechanism is documented, but the motivating case (the `testing` fixture's non-conforming `location` field) is only discoverable by cross-referencing `docs/to_run.md`'s example command, not from anything at the error site itself.

**Recommend:** as part of whatever redesign comes out of this ticket, adopt a standing practice of documenting *why*, not just *what*, for any non-obvious design choice — particularly anywhere that trades robustness or completeness for convenience, as several items in this ticket do. It is quite possible that a human will have to add the why, as an agent is unlikely to have enough context to understand which "why"s are relevan.

## Explicitly deferred — not in scope for this ticket

- **`check-bad-locations` checks origin-level presence/nulls, not `(origin, destination)`-pair-level completeness**, so it could report "no bad locations" while specific pairs are still silently missing (see `_snap_unroutable_origins`'s per-cell drop behavior inside `estimate_origin`, `driving_distance_matrix.py:112-150` — moot once #6 lands and removes this function, but noted here in case removal is delayed). This is real but expected to be rare, and may be made irrelevant by nuances of the optimization engine that haven't been evaluated yet. Leave a `# TODO` code comment at the check-bad-locations logic (`generate_driving_distances_cli.py:269-280`) flagging this as a known potential gap. Do not fix it as part of this ticket.
