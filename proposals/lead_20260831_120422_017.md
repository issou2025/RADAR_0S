# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Implementer delegates to a background sub-agent and ends its turn — run dies with no commits, and the fallback retry cannot recover it**

*Project description:*
Two defects, observed together on one run. The first is a recurrence; the second is new and makes the first unrecoverable inside the workflow.

## 1. Background-promise: implementer delegates, then ends its turn

`mctl-agents-implement-9e630443` (mctl-api, `issue-198-pin-github-ssh-host-keys-in-gitops-reade`, 2026-08-30 23:41:48–23:43:00Z) finished with `no-commits`.

From the `run-implementer` log, the top-level agent spawned a sub-agent as a **background task** and then ended its own turn:

```
SystemMessage(subtype='background_tasks_changed', data={... 'tasks': [
  {'task_id': 'aa579b8a3b3da7a8e', 'task_type': 'local_agent',
   'description': 'Implement pinned GitHub SSH host keys'}]})
...
stop_reason='end_turn'
result="The implementer sub-agent is now running in the background on this task.
        I'll wait for it to complete before reporting results."
```

It did not wait — `end_turn` terminates the run, the pod goes away, and whatever the sub-agent was doing is discarded. `git log --oneline origin/HEAD..HEAD` then returns empty and the run is classified `implementer produced no commits`.

Note the run was not cheap: ~$0.35, 343k cache-read tokens, 5.5k output tokens. It did the reading and planning, then threw it away at the last step.

This is the same failure class seen before on portal#80 and on shepherd's `EXIT_NO_FOLLOWUP_COMMITS` path. The pattern is stable enough to guard against directly:

- The implementer prompt should forbid delegating to a background task — do the edits in-turn.
- If a background task is spawned anyway, the harness should either block `end_turn` while a `local_agent` task is live, or await outstanding tasks before evaluating commits. Ending the turn with live background tasks is never a correct outcome here.
- A cheap detector: if the run ends with zero commits **and** `background_tasks_changed` appeared in the transcript, classify it as this specific failure rather than the generic `no-commits`, so it stops looking like "the model found nothing to do".

## 2. The in-workflow fallback-token retry is dead for any failure that changes status

Same workflow, second step:

```
↻ Primary implement did not succeed — retrying on fallback OAuth token (account 2).
→ python -m orchestrator.run_implementer --service mctl-api --slug issue-198-... --max-proposals 1
info: no accepted proposals found.
```

The retry re-queries for `accepted` proposals — but the primary failure has already moved this one to `needs-triage`. So the fallback exits immediately having done nothing, and reports success at the Argo level while the proposal sits in `needs-triage`.

That makes the fallback useful only for failures that leave status untouched (quota exhaustion at the very start). For every failure that transitions status — which includes this one, and every `no-commits` — the retry is structurally incapable of running. It is also misleading: the workflow shows `succeeded`.

Fix options, roughly in order of preference:
- Have the retry target the slug it was invoked with, regardless of current status, rather than re-running the "find accepted proposals" query.
- Or defer the status transition until after the fallback has had its turn.
- Either way, the retry should fail loudly when it finds nothing to do, instead of exiting 0 and letting the workflow report success.

## Impact

The proposal has been re-armed manually (`accepted`, retry attempt 2) with the root cause recorded in `.status.yaml`. Without that manual step it would have sat in `needs-triage` indefinitely, since automation does not retry that state.
