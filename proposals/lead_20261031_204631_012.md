# UI-01 — Flutter Capture workspace presentation

Suggested labels: `type:task`, `area:quotes`, `area:frontend`.

## Outcome and boundary

A developer can open a clearly labeled synthetic Flutter Capture preview and exercise typed notes, record/stop requests, clip deletion and supplied save/busy/error states using the same presentation widgets intended for later real capture. The preview establishes the visual and callback boundary while actual recording, save/reload and Extraction remain unimplemented.

Build for Android and iPhone while retaining Stima's existing identity and domain behavior. The design oracle is `frontend/UI_SYSTEM.md` plus executable tokens in `frontend/src/index.css`.

Non-goals: backend calls, accounts/auth, real microphone/permissions/settings deep links, local storage, outbox, uploads, jobs, working audio playback, full Home/Review/Share screens, persisted theme preferences, additional packages, font acquisition, publication or store submission. Do not change the web app.

## Basis and settled behavior

- Current Capture header is **Capture Job Notes**, clips followed by **Written Description**, record/stop, local status and **Extract Line Items** (`frontend/src/features/quotes/components/CaptureScreen.tsx:386–428`; `CaptureInputPanel.tsx:41–155`; `CaptureScreenFooter.tsx:14–34`). Preserve order and labels; reduce the empty clip region rather than adding an unrelated dashboard.
- Notes-only and clips-only are valid capture inputs; blank document is a secondary path (`CaptureScreen.tsx:83–84,341–369`). UI-01 exposes the secondary blank request without creating a Quote Draft.
- UI recording cap is five clips; the notes field's existing 50,000 limit is measured in UTF-16 code units (`frontend/src/features/quotes/hooks/useVoiceCapture.helpers.ts:20–21`; `frontend/src/shared/lib/inputLimits.ts:4`; `CaptureInputPanel.tsx:97–105`). HTML `maxlength` counts code units, whereas Flutter `TextField.maxLength` counts grapheme clusters; copying the integer into that property alone is insufficient. Preserve the current UI ceiling without splitting a Unicode character or discarding the previously accepted value. [HTML maxlength](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#attr-fe-maxlength), [Flutter maxLength](https://api.flutter.dev/flutter/material/TextField/maxLength.html). Clip metadata has number/duration; existing playback icon is decorative, so do not invent working playback (`CaptureInputPanel.tsx:59–82`).
- Local save and Extraction are distinct (`CaptureScreen.tsx:369–374`; `frontend/src/features/quotes/offline/localCaptureStatusCopy.ts:3–9`). Show supplied state rather than infer success from elapsed time or a callback request.
- Current default theme is dark with light/system choices (`frontend/src/shared/lib/theme.ts:22–60,89–111`). UI_SYSTEM/executable tokens are the visual authority; do not copy superseded radius/button directions from `docs/DESIGN.md`.
- Core terms remain Capture, Extraction, Quote Draft and Local Review Draft (`CONTEXT.md:10–17`). No glossary or API changes are needed for a presentation-only Task.

The layout retains existing Stima hierarchy rather than adding a new design kit. Use SDK controls and one small central theme. A full Cupertino/Material screen split has no established consumer need yet. The first version uses two settled behaviors: stop safely and preserve audio on lock/background, and lock submitted capture editing until Extraction completes or fails, retaining input and unlocking after failure. UI-01 renders these supplied states without implementing their operational lifecycle or a new unsent-revision subsystem.

## Presentation boundary and sequence

1. Map the existing dark/light surface, text, warning/error and action roles into the theme; use existing primary-container for the dark filled CTA when needed for 4.5:1 normal-label contrast. Keep 12 logical-pixel document radii and at least 48×48 interaction regions. Use SDK typography initially.
2. Build one Capture screen with a thin header, compact clips panel, labeled multiline notes, record/stop input control, persistent feedback region and Extract footer. Use scrollable content and keyboard insets; keep the footer outside OS gesture regions. No bottom navigation on this workflow screen.
3. Accept immutable presentation data and callbacks. A caller supplies notes, clip identity/sequence/duration, recording phase (`idle`, `starting`, `recording`), elapsed display, feedback/loading/error text, a submitted-input lock and which actions are enabled. Typed edits request a new notes value; Delete requests the stable clip id; other actions request Start, Stop, Extract, Start blank and Back. The supplied Extraction-busy fixture locks editing/clip mutations/new recording/blank/Extract requests. A failure fixture clears that lock and preserves notes/clips. Back remains a caller request, not a discard decision. Do not design a persisted lifecycle or add a DTO/codegen framework. Equivalent simple constructor/value shapes are allowed.
4. Add one synthetic preview entry using those actual widgets. A persistent **“UI preview · synthetic data. Recording, saving and extraction are simulated.”** notice stays visible. The local fixture can change notes/clips/state in memory; it never claims that input survived restart. A callback request must produce visible preview feedback or a deliberate fixture transition, never an enabled no-op. Supplied states may be selected by developer controls outside the product screen area.
5. Verify interactions and render the selected states; retain a short set of inspected captures and update the mobile README's preview entry and limits. Do not create a component catalog app or general fixture framework.

The valid intermediate result is an explicitly synthetic Capture showcase. It remains useful for learning/widget work even if real capture never lands; it is not a user-ready capture feature.

## Acceptance

1. Idle/empty, notes-only and clips-with-notes use the real presentation widgets. Notes changes appear through the preview caller, whitespace-only notes do not enable the ready fixture's Extract action, and the field enforces the existing 50,000 UTF-16-code-unit ceiling. A real widget-input case containing a multi-unit character must distinguish this from a grapheme limit: for example, 49,999 ASCII characters followed by decomposed `e\u0301` cannot leave a 50,001-code-unit accepted value. Keep accepted text valid, and preserve the prior accepted value if an over-limit edit is rejected. Content survives ordinary widget rebuilds; no restart durability is claimed.
2. Record and Stop have visible and programmatic names. `starting` prevents repeated Start; `recording` shows supplied elapsed time and Stop. Five supplied clips disable Start with a clear limit message. The preview visibly acknowledges the emitted action; it does not fabricate microphone success. Extract/blank/Delete enabled states come from the caller; disabled controls emit no action.
3. Delete targets the correct clip id and removes that fixture row after the caller updates data. Clip number and duration remain legible. No play control is shown because playback is outside this Task.
4. Supplied saving, saved-locally, local-save error, microphone-denied/unavailable, recording-interrupted, generic Extraction busy, and generic Extraction error states show persistent explanatory text near the affected section. A save error cannot simultaneously say “Saved on this device.” An interruption notice does not claim a clip is saved unless its supplied state confirms that. In the Extraction-busy fixture notes and clip mutations are locked; after supplied failure, the same notes/clips remain and editing is available again. Busy state does not fabricate percent/progress stages or navigate to a Quote Draft. Do not assume every combination is valid: fixture variants are representative supplied states, not a new production transition model.
5. Back/Start blank/Extract are visible requests in this preview; none performs navigation to unbuilt product screens, creates documents or sends data. An enabled request yields visible preview feedback. Back does not imply a discard/retention decision; real unsaved-exit and OS-back policy belongs to functional capture.
6. Content and essential controls fit without overflow or inaccessible clipping at 360×800 and 390×844 logical-pixel portrait constraints, and remain reachable by scrolling in 800×360 landscape and a 300-pixel bottom-keyboard-inset case. Test long notes, five clip rows, long feedback, and both themes. Avoid fixed panel heights that conceal the notes/call-to-action when the keyboard appears.
7. New controls retain native input/focus behavior, named semantics, disabled state and keyboard activation where applicable; at least 48×48 logical-pixel targets and 4.5:1 normal-text / 3:1 large-text and non-text contrast. No broad maximum-text or screen-reader certification is required for this prototype. No real recording, persistence, offline sync or iPhone device success is claimed by widget/platform-override tests.

## Verification plan

First falsifier: through the actual `CaptureScreen` widget inside the synthetic caller, enter notes at a narrow viewport with keyboard inset, request Start once, set the caller to `starting`, and attempt Start again. Assert visible notes and starting feedback, reachable essential controls and no second accepted request. This exercises the presentation boundary without reimplementing any recording owner.

Focused widget test families (`ship`): notes and UTF-16 limit behavior including the multi-unit boundary; stable-id Delete; enabled/disabled action requests and idle/starting/recording; mutually truthful save/error/busy feedback, including busy→failure preserving input and restoring editing; constrained layout with keyboard inset. Use a small test caller only to update supplied data and show request outcomes. Callback counts alone are supplemental; assert the resulting visible behavior. No source-text, constant-self-equality, class-existence or golden-equality test is required.

From `mobile/`, using the foundation's pinned SDK, run:

```text
dart format --output=none --set-exit-if-changed lib test

```

Before checks that could write, capture git status; inspect it and the diff afterward. Foundation's independent green platform build is reused unless UI changes invalidate it. The web/backend remain untouched, so their broad gates do not prove this Dart UI.

Rendered inspection: use the real Flutter widget test/render environment with Android and iOS target-platform overrides at the portrait sizes above and the constrained cases; inspect both palettes. Capture default populated, recording, local-save-error and keyboard layouts, labeling revision, environment, platform override and synthetic fixture. These are renders of the implementation, not physical-device proof. A single comparison sheet may hold several inspected states.

Remaining platform proof, owned by platform/capture implementers before functional delivery: actual Android and iPhone keyboard/selection behavior, OS back/edge swipe, permission dialogs, interruption/background recording, and local save/restart.
