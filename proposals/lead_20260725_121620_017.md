## The problem, in one line

**34 of the 44 Node apps in the FFC-EX fleet have no dependency-vulnerability detection of any kind** — no `security-audit.yml`, no `audit:high` script — so a published advisory against a charity site is invisible until somebody sweeps by hand.

This is the layer **underneath #822**. #822 says "sweep + fix any FFC-EX repo on `<16.2.11`" and estimated **13 repos**. The real number is **38**. The estimate was not careless — it was the honest count of what anything could *see*. You cannot triage a fleet you are not measuring.

## The evidence

Swept every non-archived repo in the org this run (`.github/workflows` listing + `package.json` `scripts`):

| | count |
| --- | --- |
| FFC-EX repos, non-archived | 62 |
| …with a `package.json` (a Node app — the ones that can have vulnerable deps) | **44** |
| …of those, with `security-audit.yml` **and** `audit:high` | **10** |
| …of those, with **neither** | **34** |
| FFC-EX repos with no `package.json` (static/placeholder — correctly out of scope) | 18 |

The two markers are perfectly correlated — the same 10 repos have both — which says they were provisioned together and the fleet simply was never backfilled when the template gained the workflow. Nothing regressed; the backfill just never happened.

**And the 10 that do have detection prove it works.** 8 of them install a vulnerable `next` and **all 8 have failed their scheduled Security Audit on 07-22, 07-23 and 07-24** — three consecutive days red, unremarked:

`bearupinternationalministries.org` · `cactuswrenpreschool.com` · `catnipandcattitude.org` · `compassionstl.org` · `garrisonareacaregivers.org` · `hclwellness.org` · `restoredradiancefoundation.org` · `theafghanistanaffairs.org`

So the fleet's security posture has two independent holes, and this issue is only the first:
1. **34 repos: no signal generated.** ← this issue
2. **8 repos: signal generated, nobody listening.** ← noted on #832; its alerter is hub-scoped and does not watch fleet repos.

This is the exact shape of #830 one level out. There, one repo with no Security Audit was silent and silence read as green. Here it is 34 repos.

## Scope — one PR to the hub, then a fleet rollout

Per the AGENTS.md fleet-file rule this is the hub tracking issue. The file being synced across the fleet is `.github/workflows/security-audit.yml`.

**Source of truth to copy — do not write a new one:** `FFC-IN-FFC_Single_Page_Template/.github/workflows/security-audit.yml` (daily `cron: '17 6 * * *'`, plus `pull_request` on `package.json`/`package-lock.json`, `permissions: contents: read`, `npm ci --ignore-scripts` then `npm run audit:high`). It is already proven on SPT, FOT and the 10 wired FFC-EX repos.

Each target repo needs **both** halves — the workflow alone fails immediately without the script:
1. `.github/workflows/security-audit.yml` — copied verbatim from SPT
2. `package.json` — add `"audit:high": "npm audit --omit=dev --audit-level=high"` to `scripts`

**Stagger the cron.** 34 more repos all firing at `06:17` will collide with the existing 10 and with the `07:0x` band already in use. Offset by repo (e.g. derive minutes from the repo name hash, or hand-assign across `06:00–06:59`) — #830's rollout already established staggering as the convention, and the hub's own daily workflows follow it.

**Prefer a hub workflow that does the rollout over 34 hand-made PRs.** `738-fleet-smoke-engine-drift-audit.yml` is the pattern to copy: it audits one fleet-synced file across the fleet and reports drift. The durable version of this issue is the same thing for `security-audit.yml` — detect *and* backfill — so the 35th repo provisioned next month is covered without anyone remembering. If that is too much for one PR, split: (a) the drift audit that reports which repos lack it, (b) the backfill.

**Out of scope:** the 18 FFC-EX repos with no `package.json`. They have no dependency tree; adding an audit there would only manufacture red. Also out of scope: bumping any version — that is #822's job. This issue only makes the vulnerabilities *visible*.

**Note on `FFC-IN-ffcadmin.org`:** it is on pnpm (`pnpm-lock.yaml`, no `package-lock.json`), so if the rollout is ever extended to the `FFC-IN-*` repos the npm-specific steps do not transfer. Not needed for this issue — ffcadmin is already audited — but do not blind-copy. See #771.

## Verification

```bash
# every non-archived FFC-EX repo: does it have a package.json, the workflow, and the script?
for r in $(gh api "orgs/FreeForCharity/repos?per_page=100" --jq '.[]|select(.archived==false)|.name' | grep '^FFC-EX-'); do
  pkg=$(gh api "repos/FreeForCharity/$r/contents/package.json" --jq '.content' 2>/dev/null)
  [ -z "$pkg" ] && continue
  wf=$(gh api "repos/FreeForCharity/$r/contents/.github/workflows" --jq '[.[].name]|join(",")' 2>/dev/null | grep -c security-audit.yml)
  ah=$(echo "$pkg" | base64 -d | grep -c '"audit:high"')
  echo "$r wf=$wf audit_high=$ah"
done
```
Expect `wf=1 audit_high=1` on all 44. Then dispatch Security Audit on three of the newly-wired repos and confirm each produces a real conclusion (green on a clean tree, red on a vulnerable one) rather than skipping.
