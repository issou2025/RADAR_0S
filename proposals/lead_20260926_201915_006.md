# Project Proposal — Flutter App

**[CHORE] CI workflow — build from any branch and upload to Firebase App Distribution**

*Project description:*
## Purpose
Add a GitHub Actions workflow that builds the app from a branch of your
choosing and uploads it to Firebase App Distribution, so a build can be put on
a real phone without anyone needing Flutter, Xcode or Android Studio installed.

The repo has no `.github/` directory at all today — this starts from scratch.

## Scope
- **Android (APK) first.** iOS is deliberately split out — see "Why iOS is a
  separate job" below.
- Triggered manually (`workflow_dispatch`) with the branch picked at run time,
  so any branch or a PR head can be built, not just `main`.
- Runs `flutter analyze` and the full test suite before building. A branch that
  fails either should never reach a tester's phone.

## ⚠️ The one thing that will silently break this
`android/app/build.gradle.kts:38` signs **release** builds with the **debug**
keystore:

```kotlin
release {
    // TODO: Add your own signing config for the release build.
    signingConfig = signingConfigs.getByName("debug")
}
```

Locally that's harmless — your machine reuses the same `~/.android/debug.keystore`
every time, and its SHA-1 is registered in the Firebase console, so Google
Sign-In works.

**A CI runner generates a brand-new debug keystore on every run.** Its SHA-1
won't match anything registered in Firebase, so the uploaded build will install
fine, open fine, and then **fail at Google Sign-In** — most likely with
`ApiException: 10 (DEVELOPER_ERROR)` and no useful on-screen message. The app
will look broken to whoever you sent it to.

So this issue has to solve signing, not just uploading. Two options:

- **A. Commit to a real upload keystore.** Generate one, store it as a secret,
  register its SHA-1 *and* SHA-256 in Firebase, and wire a proper
  `signingConfig`. More setup now, but it's needed for Play Store later anyway,
  and every build from then on is identical.
- **B. Pin the debug keystore.** Store your existing `~/.android/debug.keystore`
  as a secret and have CI use that exact file. Less work, keeps the existing
  SHA-1 registration valid, but it's still a debug-signed build and can't go to
  the Play Store.

Recommendation: **A**, because the Play Store path needs it regardless and B
just defers the same work. Either way the SHA registration step below applies.

## What you need to do (manual — can't be automated)

These all have to exist before the workflow can run green.

1. **Create a signing keystore** (option A above)
   ```bash
   keytool -genkey -v -keystore upload-keystore.jks \
     -keyalg RSA -keysize 2048 -validity 10000 -alias upload
   ```
   Keep this file and its passwords safe — losing it means you can never update
   the app under the same identity on the Play Store.

2. **Get its SHA-1 and SHA-256**
   ```bash
   keytool -list -v -keystore upload-keystore.jks -alias upload
   ```

3. **Register both fingerprints in Firebase** → Project settings → Your Android
   app (`com.madhusangita.shared_tasks`) → "Add fingerprint". Do this for
   **`shared-tasks-dev`**. Google Sign-In will not work without it.

4. **Re-download `google-services.json`** after adding the fingerprints, since
   its contents change.

5. **Create a service account for App Distribution** → Firebase console → Project
   settings → Service accounts → Generate new private key. Grant it the
   **Firebase App Distribution Admin** role in Google Cloud IAM.

6. **Find your Firebase Android App ID** — Project settings → Your apps. Looks
   like `1:123456789012:android:abc123def456`.

7. **Decide how testers get in** (see "Getting it onto a stranger's phone")
   and create a tester group in App Distribution if you go that route.

8. **Add these GitHub secrets** (Settings → Secrets and variables → Actions):

   | Secret | What it holds |
   |---|---|
   | `GOOGLE_SERVICES_JSON` | Full contents of `android/app/google-services.json` — it's gitignored and untracked, so CI has no Firebase config without it |
   | `ANDROID_KEYSTORE_BASE64` | `base64 -i upload-keystore.jks` output |
   | `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
   | `ANDROID_KEY_ALIAS` | `upload` |
   | `ANDROID_KEY_PASSWORD` | Key password |
   | `FIREBASE_SERVICE_ACCOUNT` | Full JSON from step 5 |
   | `FIREBASE_ANDROID_APP_ID` | From step 6 |

## Getting it onto a stranger's phone
Worth deciding up front, because plain App Distribution is a poor fit for
"anyone can try it": by default you add each tester's email by hand, and they
must install the **Firebase App Tester** app and sign in with that Google
account. That's a lot of friction for someone arriving from a LinkedIn post.

Options:

- **App Distribution invite links** — App Distribution can generate a public
  link that lets anyone who opens it add themselves as a tester, with no manual
  email entry. Still requires the App Tester app, but it's self-service. Gives
  you install counts and tester feedback.
- **Attach the APK to a GitHub Release** — zero friction, no account, no extra
  app. They download and sideload, accepting Android's "install unknown apps"
  prompt. No analytics, and the APK is public.
- **Google Play internal/open testing** — the most trustworthy install
  experience, but needs a Play Console account (one-off $25), a properly signed
  release, a privacy policy and review time.

These aren't exclusive. A sensible combination is App Distribution for people
you actually want feedback from, plus a GitHub Release for drive-by curiosity.
Pick before implementation, since it changes what the upload step does.

## Why iOS is a separate job
Not in scope here, and worth its own issue:
- Requires an Apple Developer Program membership ($99/year)
- Needs a distribution certificate and a provisioning profile, both stored as
  secrets and rotated when they expire
- Must build on a **macOS** runner, which bills at 10× the Linux rate on
  GitHub-hosted runners
- Ad-hoc distribution requires every tester device's UDID registered in advance
  — genuinely incompatible with "anyone can try it"; that path is TestFlight

## Technical Notes
- Files to create: `.github/workflows/` (name TBD, e.g. `distribute-android.yml`)
- Files to update: `android/app/build.gradle.kts` (real `signingConfig` reading
  from `key.properties`/env), `.gitignore` if a new key file path is introduced,
  `README.md`
- `**/android/key.properties` is already gitignored (line 59), so the standard
  Flutter signing pattern fits without gitignore changes
- Pin the Flutter version in the workflow rather than using `stable`, so a
  Flutter release can't break distribution without a deliberate bump
- Cache pub and Gradle to keep runs reasonable
- Depends on: nothing
