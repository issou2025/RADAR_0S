# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**管理页：Parody/Character 字典管理 + chip 流式列表与自适应详情**

*Project description:*
## Problem Statement

管理页（「管理」/ `/metadata`）目前只支持 Author 与 Tag 的字典管理，且以「一行一个实体」的列表渲染，信息密度低、操作也挤在行内。Parody 与 Character 已作为 Named metadata facet 存在于库与 Comic 元数据表单中，但用户无法在管理页浏览、新建、重命名或删除它们。同时，用户希望用更紧凑的 chip 流式浏览，点开后再看 Named facet attachment count 并执行改删；列表底部需要触底加载；顶部关键词实时过滤（含拼音辅助）行为保持不变。

## Solution

将 Author、Tag、Parody、Character 四个 Named metadata facet 统一到同一套管理面：等高校 chip 流式换行列表、顶栏搜索不变、空关键词服务端分页触底加载、有关键词时全量 + 客户端 Pinyin-assisted name match。点击 chip 打开 AdaptiveFormSurface 详情（随视口在 dialog 与 compact 全页间 morph），展示显示名与 Named facet attachment count，并提供重命名与删除。为 Parody/Character 补齐与 Tag/Author 对齐的字典 CRUD（经 JunctionNamedFacet 泛化），并增加对应管理 Tab 与 `?tab=` 路由。

## Implementation Decisions

- **Unified management surface**: Refit the metadata management page so Author, Tag, Parody, and Character all use chip wrap list + detail surface; do not leave Author/Tag on the old one-row-per-entity list.
- **Tabs & routing**: Tab order Authors → Tags → Parodies → Characters. Extend `?tab=` with `parodies` and `characters`; keep existing `authors` / `tags` and legacy `/tags` → tags, `/authors` → authors redirects.
- **List presentation**: Equal-height flowing wrap of chips (not true masonry). Reuse interactive `OutlinedMetaChip` (idle/hover/press). Chip label is display name only—no attachment count badge, no inline rename/delete.
- **Chip action**: Primary activation opens detail only.
- **Detail chrome**: Open via existing `showAdaptiveFormSurface` / `AdaptiveFormSurface` so medium/expanded is dialog and compact is full page, including live morph when breakpoint changes while open.
- **Detail content (this slice)**: Display name, Named facet attachment count, Rename action, Delete action. No avatar, external link, description, or “attached Comics” browser.
- **Rename UX**: From detail, open the existing name editor dialog pattern; on success, refresh detail title and list data.
- **Delete UX**: Confirm dialog includes Named facet attachment count; on success, dismiss detail surface and refresh list.
- **Create UX**: Header “+” / existing shortcut only → name editor dialog; not from detail. Empty-state CTA may point at the same create path.
- **Search**: Keep top search box. Empty keyword → server page fetch (limit/offset) + infinite scroll load-more. Non-empty keyword → full dictionary list + client Pinyin-assisted name match (do not page-filter in a way that misses unloaded pinyin hits). Do not move pinyin matching into core in this slice.
- **Sort**: Management browse/pagination remains name ascending, matching current Tag/Author management list behavior (distinct from form-picker ordering by attachment count).
- **Zero-attachment rows**: Dictionary names with attachment count 0 remain visible and searchable.
- **Parody/Character CRUD**: Add dictionary add / rename / delete / page (and any watch needed for parity) aligned with Tag/Author; implement by extending `JunctionNamedFacet` / named-facet dictionary management rather than copying Tag/Author modules four ways.
- **Delete/rename semantics**: Mirror Tag/Author—rename updates dictionary identity and rewrites Comic junction attachments; delete removes the dictionary name per existing facet deletion behavior.
- **Tag delete-all**: Keep Tag-only overflow “delete all”; do not add equivalent for Author/Parody/Character.
- **Attachment count source**: Use Named facet attachment count (global junction rows across Libraries), consistent with form-candidate counting—not a current-library-only count.
- **Future extension**: Detail shell may later host Author avatar/link or Tag description; those fields are not domain or schema work in this issue.
- **Layers**: Business rules and SQL stay in Rust core; Flutter metadata feature wires repositories/FRB and UI. Prefer one facet-parameterized management notifier/panel over four divergent copies where practical.

## Testing Decisions

- **Good tests** assert external behavior only: given dictionary state and user-visible actions, names appear/disappear, pagination advances, search hits (including pinyin-assisted cases already covered elsewhere), detail shows count, rename/delete change dictionary and attachments as specified. Do not assert private widget tree structure or incidental layout pixels.
- **Primary seam**: One **Named metadata facet dictionary management** port (list/page/add/rename/delete + attachment count). Prefer core tests parameterized by facet kind (Tag/Author/Parody/Character) over four isolated suites. Ideal number of new conceptual seams: one.
- **UI tests**: Metadata management page behaviors—chip list rendering, scroll load-more when keyword empty, filter when keyword non-empty, opening AdaptiveFormSurface, rename via name editor, delete confirm showing count then dismiss. Prefer highest existing widget/integration harness patterns in `app/test`.
- **Prior art**:
  - Core: `named_facet` tests; Tag dictionary import tests; Tag/Author rename/delete/page APIs.
  - Flutter: `tag_name_editor_dialog_test`, `tag_confirm_delete_dialog_test`; library search/catalog load-more patterns for infinite scroll behavior.
- **Coverage focus for new work**: Parody/Character CRUD parity; management pagination vs search hybrid; detail count accuracy; rename junction rewrite; delete confirm + list refresh.

## Out of Scope

- Author avatar, profile link, Tag description, or other new Named metadata facet attributes.
- True masonry / staggered unequal-height waterfall.
- Attachment count (or rename/delete controls) on the chip itself.
- Moving Pinyin-assisted name match into core / server-side filtered paging.
- Navigating from detail to a filtered Comic list of attachments.
- Managing Language, Format group, Series, or Library entities on this page.
- Re-enabling or redesigning Tag dictionary import UI entry (remains deferred until self-hosted dictionary work).
- Changing Comic metadata form MultiSelect / Smart facet match behavior beyond what dictionary CRUD naturally implies.
- New ADR solely for this UI refresh (reuse AdaptiveFormSurface + JunctionNamedFacet; no hard-to-reverse surprising trade-off beyond the documented hybrid search/paging choice in Implementation Decisions).
