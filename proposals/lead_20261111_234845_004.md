Run `plan-review/runs/2026-11-11T18-11-53-403Z-implementation-139` (iou-notes item #139). Execution committed the work (82726a4).

- **The issue.** Code review 1, cycle 1: Codex raised one minor issue, W1-R1-S1-1. The report of step S1 omitted whether a navigation-rail destination's accessible name changes after selection, which S1's text said to report. Codex stated: "nothing in the work would differ".
- **The answer.** Claude Code accepted it in part. Its resolution was to amend S1's report: the name after selection was not recorded (the one-time probe and its output were deleted in S3), what was observed, and why it does not bear on the journey. It stated "Nothing in code, tests or the commit changes" and "nothing in the work would differ".
- **What Interloq did.** Cycle 2 raised nothing new. Interloq said "Work review 1 raised no new issue in cycle 2; Interloq leaves for planning with the issues accepted in every cycle of this review" (`collectedLeaveLine`, issue #252) and went on to planning phase 2, then execution phase 2 and code review 2, all to add a few sentences to a report.
- **The line misled.** The developer asked why there was a planning phase after a review that "ended with no issues". The line says the last cycle raised nothing and does not say what was accepted, or when.

The cost: model time, wall-clock time before the developer can push, and tracker requests. Nothing in the commit can change. This is an unnecessary wait in an unattended run, which the developer's instruction of 19 Oct 2026 asks to eliminate.

## What the change must achieve

- **A correction of the records alone does not re-plan.** Where every issue a code review accepted has an agreed correction limited to the run's records (an execution's report, its checks or test-first record), and nothing in the work, Interloq applies it without a planning phase, an execution phase or another code review. It then goes on as after a review with no counted issue: the final commands where the project names them (behavior 12), the commit check, the run's end.
- **How it is applied.** One call writes the amendment, in the code review's own session, read-only toward the project, and it is recorded beside the report it amends. The refinement settles whether Interloq or Claude Code writes it.
- **Which issues qualify is data, not prose.** An accepted issue states, in a field both agents fill and the program validates, whether its correction changes the work or only the run's records. Today's `work_effect` (issue #183) is null on an accepted issue (`ValidatedDisposition.workEffect`, `src/round.ts`), and its `none` was never meant to cover a correction someone accepted, so the refinement settles whether `work_effect` is extended or a new field is added. A mixed review, with any accepted issue that changes the work, re-plans as now with every issue.
- **The leave line says what was accepted.** It names the issues accepted and in which cycles, and that Interloq returns to planning to carry them out, for example: "Code review 1 accepted 1 issue (cycle 1) and raised none in cycle 2; Interloq returns to planning to carry it out." It never reads as a review that found nothing.

## What the refinement must settle

- **Where the amendment is written.** In the execution's `result.json`, in a record of its own beside it, or both, and whether a later code review reads it.
- **Whether Codex checks it.** One more Codex turn over the amendment, or none since both agents agreed on its text.
- **The plan review.** Whether an accepted plan-review issue limited to the records exists at all, or this applies to the code review alone.

## A second case, 11 Nov 2026 (iou-notes item #140)

Run `plan-review/runs/2026-11-11T19-36-33-981Z-implementation-140`. Execution phase 1 committed the work (49d8f6e).

- **The issues.** Code review 1 raised four minor issues (W1-R1-S1-1, W1-R1-S1-2, W1-R1-S2-1, W1-R1-S3-1). Each said only that a check a step named was missing from the phase's report: `git status --short flutter/`, `test -s …/probe-findings.md`, `grep -n 'Active Cases' acceptance/browser/README.md`, and `git status --short` before staging and after committing. These are raised under `WORK_CHECK_CRITERION` (issue #245).
- **What followed.** All four were accepted, each with "No repository file changes", and the run went through planning phase 2, execution phase 2 and code review 2 to record them.
- **What they cost to settle.** The developer's own session checked all four facts in one command of a few seconds. One of them, the status before staging, cannot be observed after the commit at all, so the extra phases could only record that it had not been recorded.

**The developer's further request.** A missing check matters where it may mean the check was never run. The least costly remedy is for the reviewer to run a check that takes seconds and has no side effects, and record its result in the review log, as Codex did in #138's code review: it ran the step's `node --test` command and recorded that it passed. Only a check whose result shows a defect sends the run back to planning; a check that can no longer be observed is recorded as not recorded, with no re-plan.

## What the refinement must also settle

- **Which checks the reviewer runs.** How a check is known to be without side effects and short: the step's named check commands only, a read-only command (`git status`, `test`, `grep`, a test runner) or any, and a bound on its time. The project snapshot guard of behavior 5 already halts a Codex turn that changes the project.
- **How `WORK_CHECK_CRITERION` changes.** Whether a named check missing from the report is raised at all where the reviewer ran it and it passed, or recorded in the log as checked by the reviewer.

## Tests

- **The state machine:** a collecting review whose every accepted issue is limited to the records ends without `revise`; a review with one issue that changes the work still leaves with `revise`; with a property over mixes.
- **A scenario over `testWiring`:** this run's case, a code review accepting a report-only issue in cycle 1 and raising nothing in cycle 2, the amendment recorded, the final commands run, and the run ending 0 with one planning phase and one execution phase.
- **The leave line's text,** with a property: it names every accepted issue's cycle.
