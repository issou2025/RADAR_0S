# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Naming-standards workflow across categories: settle global rules first, then rename**

*Project description:*
## Context

A user cleaned up naming standards in a workshared project model, across many categories: view templates, text and dimension types, line styles, loadable families and family types, filled region types and fill patterns. No `am-*` skill covers this, so the agents wrote every inventory, rule and rename by hand. #77 covers one part (filled regions and fill patterns). This issue covers the workflow across categories and the rename steps that every category needs.

## What happened

1. **The rules grew one category at a time, so renames were done again.** The view templates were renamed three times in one day: first an all-caps `(PURPOSE)_` prefix, then PascalCase `(Purpose)_` with a new scale format, then no brackets (`Purpose_`). Text and dimension types were renamed, and then the user asked for `_` between every part. Global rules came late and in pieces: PascalCase everywhere, acronyms in capitals, `TRN`/`OPQ` in capitals, no `( )` or `[ ]`, the option separator. Each new global rule made earlier renames in other categories out of date.
2. **Scale tokens.** The first proposal used `1in=30ft`. The user said that architects read `1-30` (engineering) and `1-32in` (architectural).
3. **Name parts that come from data.** Filled region type names contain an area-scheme value (the department name). A PascalCase transform cannot keep them equal to the scheme value: `&` and `+` have no rule, a script cannot tell an acronym from a word in all-caps text, and dropping `/`, `-` and `( )` cannot be reversed. The user kept the scheme value exactly, as an exception. Later the "no ( )" rule was reported as done, but a final check found three names that still had `( )`, because their scheme values have `( )`.
4. **Line style rename.** Setting the name on the line style object failed with "This element does not support assignment of a user-specified name". The agent said the API cannot do it and proposed a manual rename. The user corrected it: `doc.GetElement(subcategory.Id).Name = new_name` works. `Category.Name` and the `GraphicsStyle` name are read-only. Ids and line assignments stay the same.
5. **Usage counts mislead.** Default linear dimension styles showed about 229,000 uses. These are Revit's internal sketch dimensions. Heads, marks and view titles showed 0 instances, but level, grid and viewport types use them. One type name stated a size that its real text size did not match.
6. **Delete or merge a type.** "Is this type still used" by `FilteredElementCollector` missed a hidden member of a detail group type with no placed instance. The dry run of the type delete then deleted that filled region. The member type cannot be changed either, so the old type had to stay.
7. **Name-based references are not checked.** One view filter still matched a filled region type name that no longer exists. The brief asked the agent to skip names that view filters, schedule filters or scripts use, but no tool checks this.
8. **Reference views for other categories.** After each rename, the labels in the line style, text style and dimension style reference views had to change. Pairing is different per view: some labels have a sample line whose style does not exist, sample text notes start with their own type name, a dimension example group has no labels. #77 covers the filled region swatch view only.

## Proposed change

A naming-standards skill (for example `am-naming-standards`), or a section in `am-safe-change`:

1. **Inventory** per category: names, usage counted through referencing types (heads, tags, view titles), internal sketch dimensions left out, and a check of the size in the name against the real property.
2. **Global rules first.** Before any rename, settle the rules for all categories: case, separators, allowed characters (Revit rejects `[ ]`; decide about `( )`), prefix list, scale and size tokens, acronyms. Find name parts that are keys to other data (scheme values, department or room names) and decide how they are treated. Get the user's sign-off on the full rule set.
3. **Rename per category**, with a rename table that the user approves. Before and after: scan view filter rules and schedule filters for the old names. Use the right name path per category (line styles through the subcategory element).
4. **Merge or delete types**: count use including members of unplaced group types; swap instances to the target type first; compare the dry-run deleted list with the expected list.
5. **End step**: update the labels in every reference or legend view that shows renamed type names (extends #77 to all categories).

## Acceptance ideas

- On a model where a view filter uses a type name, the rename preview lists that filter.
- A line style rename works on the first try.
- A type delete whose type is used by a hidden member of an unplaced group type is flagged before the dry run.
- A rule set with "no ( )" reports names whose data-derived part has `( )` before the rename is called done.

## Not verified

- Whether the skill should also cover view names and system family types (walls, floors) whose names need sizes.
