# Project Proposal — Scan To Bim

## Project Understanding
You need assistance with: 
**Spike: capability inventories for the rest of the suite**

*Project description:*
As a core architect, I want the capability inventories of the other programs in the suite, so that the foundations and the structural BIM MVP don't need redesigning when those disciplines arrive.

Only Revit has a capability inventory so far. This spike defines what "complete" means for the rest of the suite (see Discussion #80, suite definition). It belongs in M0 because its findings can change the core's foundations: element model, geometry kernel, coordinates, file format and ports.

### Acceptance criteria
- [ ] Capability inventory for each candidate area:
  - 2D drafting (AutoCAD)
  - civil and infrastructure (Civil 3D, InfraWorks, OpenRoads)
  - structural analysis and design (CYPECAD, ETABS, SAP2000, SAFE, STAAD.Pro, Robot)
  - detailing (Tekla, Advance Steel)
  - geotechnical and water (PLAXIS, HEC-RAS/HMS, EPANET, SWMM, WaterGEMS)
  - coordination and reality capture (Navisworks, ReCap)
  - visualization (3ds Max)
  - project management (4D/5D)
- [ ] For each area, the **core requirements** it implies, such as:
  - element and relationship types
  - geometry representations (TIN, alignments, point clouds, FE meshes)
  - coordinate scale and georeferencing
  - solver and adapter ports
  - 2D primitives
  - performance at fabrication scale
- [ ] Those requirements are checked against the M0 spikes (geometry kernel #2, storage and file format #5, BIS/IFC study #6) and the M1 epics
- [ ] Recommendations on which programs are in scope, and which solvers to wrap rather than replace
- [ ] An ADR in `docs/decisions` records the suite definition. Discussion #80 is marked answered with a link to it.

### Where results go: GitHub-native tools, not plain text on this issue
Store each result in the GitHub tool built for it. Don't post long findings as comments on this issue. Comments here should only be short progress notes and links.

| Result | Where it goes |
|---|---|
| One capability inventory per area | A **Discussion** in the Research category, so it can be commented on and extended |
| A requirement that changes a foundation decision | Linked as a **sub-issue or comment link** on the affected spike or epic (#2, #5, #6, E03–E12), never only described here |
| New work the inventory reveals | New **stories or spikes**, created as sub-issues of the relevant epic, with labels and milestone |
| Updates to future epics (E14, E15, E21, E24–E27, E29) | Edits to those **epic issues** themselves, plus new stories where they're now clear |
| Program scope and priority | **Labels** and fields on the project board, where they fit |
| The suite decision | An **ADR** in the repo (decisions stay versioned with the code) |

This issue is done when every result lives in one of those places and is linked from the checklist above.
