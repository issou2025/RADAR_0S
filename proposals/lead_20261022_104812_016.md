### F-1 · Medium · Release bytecode is not independently verifiable by users; no signed provenance

What users install is **compiled LuaJIT bytecode** inside game `.patch_0` bundles, not the Lua source. The build is *designed* to be reproducible and verifies itself:


**[`CONTRIBUTING.md` L16](https://github.com/CowboyBingus/VanillaPlusMegapack/blob/526750bb7e99dea6a707e5649fda488d91f3be86/CONTRIBUTING.md#L16)**
```text
`components/` contains the reviewed Lua source and test snapshots. `components.lock.json` pins their revisions, source hashes and original standalone resource hashes. The builder recreates the original wrappers (with each component's own `scripts/entry.py` or `scripts/module.py` where it has one) and requires every compiled gameplay resource to match its original release byte for byte; a component that ships more than one resource (Hellpod Drop Hold) pins the others in `extra_resources`. A changed source or mismatched compiler fails the build. The pack adds its identity and wraps each public resource in a plaintext discovery entry. Final ZIP checks reconstruct and compare the embedded bytecode. See [migration details](docs/DISCOVERY_MIGRATION.md).
```

That is a strong control **for the author**. For a user or third-party auditor it is hard to exercise: rebuilding needs Windows x64 + MSVC + the pinned LuaJIT, a build of Bingus Shared Loader, and (for the Sound Systems Rebalanced option) the game's own music banks extracted from a Steam install (`CONTRIBUTING.md` L14). The release publishes `SHA256SUMS.txt` **in the same release as the files**, which detects corruption but not tampering, and there is no signature, signed tag or build-provenance attestation linking the zip to a commit.

**What I verified instead (partial, not equivalent to a rebuild):**
- `SHA256SUMS.txt` matches both zips. ✔
- The source zip is **byte-identical** to the `v42` git tree (720 files, 0 differences). ✔
- The install package contains no PE/ELF/script files (`.exe/.dll/.bat/.ps1/.vbs/.cmd`: none). ✔
- The 25 bundles are uncompressed (entropy 2.65–5.79 bits/byte; compressed data is ≈7.9), so string extraction is meaningful. ✔
- The 40 Windows/CRT symbols visible in the shipped bytecode are **all** present in the source; **none** are extra. ✔
- No IPs, no process/network API names, no shell strings in any bundle; the only URL anywhere in the package is the README's link to the loader's releases page. ✔
- The release's own manifest lists the hash of 53 of 55 non-empty files, including all 25 bundles (self-consistency only; same author).

**Residual risk:** a tampered release built from clean source would not be caught by any of the above except by a full rebuild. **Suggested:** publish a build-provenance attestation (e.g. `actions/attest-build-provenance`) or sign `SHA256SUMS.txt`, and add a Windows CI job that rebuilds the components that need no game files and compares hashes (this fork already has a Windows LuaJIT job that builds the pinned commit).

### F-2 · Medium · *(this fork's pipeline)* Automatic upstream merge + advisory AI audit is not a gate

This fork's `upstream-sync.yml` merges upstream `main` into the fork's `main` daily and pushes it if the merge is clean; `release-please` then proposes a release containing it:

**[`.github/workflows/upstream-sync.yml` L45–L47](https://github.com/grenudi/VanillaPlusMegapack/blob/main/.github/workflows/upstream-sync.yml#L45-L47)**
```yaml
          if git merge --no-ff upstream/main -m "merge: sync with upstream ${UPSTREAM} main"; then
            echo "result=clean" >> "$GITHUB_OUTPUT"
          else
```

**[`.github/workflows/upstream-sync.yml` L55–L56](https://github.com/grenudi/VanillaPlusMegapack/blob/main/.github/workflows/upstream-sync.yml#L55-L56)**
```yaml
          git push origin HEAD:main
          git push origin --tags
```

So a malicious or compromised upstream commit would reach this fork's `main` without review. The `ai-audit` step does not stop that: it runs only on the *release PR*, is advisory, and sends the raw diff to the model inside the prompt:

**[`.github/scripts/ai_audit.py` L71–L73](https://github.com/grenudi/VanillaPlusMegapack/blob/main/.github/scripts/ai_audit.py#L71-L73)**
````text
Diff to review:
```diff
{diff}
````

Text inside a diff (comments, strings) can try to steer the model (prompt injection), so an AI "nothing suspicious" must never be the only control. (Mitigating fact: the default token cannot push changes to `.github/workflows`, so upstream cannot silently add workflows to this fork.)

**Suggested (not done here):** make the sync open a PR instead of pushing; require checks on it (privacy audit, lint, tests); add a deterministic **capability-diff gate** that fails when an incoming change adds a new imported Windows API (`__asm__("…")`), a new `ffi.load` target, any network/`os.execute`/`loadstring` use, or a new writer — and keep the LLM report as an advisory second opinion.

### F-4 · Low · Two mods temporarily change page protection; the failure path leaves a page writable

`ArcThrowerRevamped` and `LaserSentryCooldown` edit the game's *weapon data library*, which lives in committed **private, read-only** memory. Each checks the page type right before writing, flips it to read-write for the write, and restores it. This is bounded and well-checked — the only residual concern is the path where restoring fails:

**[`components/ArcThrowerRevamped/src/arc_thrower_auto.lua` L241–L266](https://github.com/CowboyBingus/VanillaPlusMegapack/blob/526750bb7e99dea6a707e5649fda488d91f3be86/components/ArcThrowerRevamped/src/arc_thrower_auto.lua#L241-L266)**
```lua
local function write_data(address, data)
    if not state.bound then return false, 'bindings unavailable' end
    local protection = private_protection(address)
    if protection == PAGE_READWRITE then
        if write(address, data) then return true end
        return false, 'record write failed'
    end
    if protection ~= PAGE_READONLY then
        return false, 'record page is not private read-only memory (' .. page_text() .. ')'
    end
    if kernel.atr1_VirtualProtectEx(state.process, address, #data, PAGE_READWRITE,
                                    previous_protection) == 0 then
        return false, 'record page protection could not be changed'
    end
    local ok = write(address, data)
    if kernel.atr1_VirtualProtectEx(state.process, address, #data, previous_protection[0],
                                    restored_protection) == 0 then
        if not state.protection_lost then
            note(string.format('Weapon data page at %#x could not be made read-only again.', address))
        end
        state.protection_lost = address
        return false, 'record page protection could not be restored'
    end
    if ok then return true end
    return false, 'record write failed'
end
```

**[`components/LaserSentryCooldown/src/laser_sentry_cooldown.lua` L247–L256](https://github.com/CowboyBingus/VanillaPlusMegapack/blob/526750bb7e99dea6a707e5649fda488d91f3be86/components/LaserSentryCooldown/src/laser_sentry_cooldown.lua#L247-L256)**
```lua
-- Writes edits ({offset, bytes} from base, in address order) into the weapon data library: committed private
-- memory that the game keeps read-only. The span they cover is checked right before the writes (one
-- VirtualQuery), made writable for the writes only and given its protection back at once (one VirtualProtectEx
-- each way, whatever the number of edits); a span that is already private read-write is written directly. The
-- edits are read back in one read. Returns true, or false, why, whether the original protection could not be
-- restored and whether any write landed (then the caller must put the old bytes back).
function Cooldown.protected_write(api, base, edits)
    local address, length = span(base, edits)
    local protection, why = private_protection(api, address, length)
    if not protection then return false, why end
```

If `VirtualProtectEx` fails to restore protection, the page stays read-write (Arc Thrower records `state.protection_lost` and logs it; LaserSentryCooldown returns `lost`). It is a *data* page in the game's own process, never code, and the exposure is limited to this process. **Suggested:** on a failed restore, disable the mod for the session rather than continue.

### F-5 · Info · 14 of 25 components write game memory (all bounded)

Components with `WriteProcessMemory` (see the full matrix in the first comment): ArcThrowerRevamped, BetterStratagemBounce, ConsistentVaulting, ControllableHoverPack, FlameDamageFixed, FoliagePassThrough, HellpodDropHold, HellpodSteeringUnlocked, LaserSentryCooldown, ReinforcementBeaconsFixed, SentryAimRetention, ShallowWaterDiving, StickyGrenadeHandles, StratagemHeroExpanded.

**One guard, not eleven.** Eleven of them vendor `bingus_write.lua`; all 11 copies have the **same SHA-256** (`9a0a2178…d596160`) and all 25 copies of `bingus_memory.lua` are also identical (`3973924b…65172b416`), so the guard needs reviewing once. It permits writes only into committed, private, read-write memory — never code, read-only, guard or image pages:

**[`components/BetterStratagemBounce/src/bingus_write.lua` L21–L29](https://github.com/CowboyBingus/VanillaPlusMegapack/blob/526750bb7e99dea6a707e5649fda488d91f3be86/components/BetterStratagemBounce/src/bingus_write.lua#L21-L29)**
```lua
-- Writes go only into memory that is already committed, private and read-write:
-- never code, read-only, guard or module image pages. Each write checks its whole
-- range with api.writable_data right before writing (one VirtualQuery per memory
-- region, about 0.29 ms each in game; api.queries counts them), so write only on
-- frames that act. Nothing here changes page protection or allocates memory
-- pages. WriteProcessMemory is declared under a private, versioned name
-- (bingus_write1_*, an __asm__ label naming the real export), at most once per
-- version in the whole game; the marker type bingus_write1_declared is this
-- file's sentinel.
```

**[`components/BetterStratagemBounce/src/bingus_memory.lua` L257–L268](https://github.com/CowboyBingus/VanillaPlusMegapack/blob/526750bb7e99dea6a707e5649fda488d91f3be86/components/BetterStratagemBounce/src/bingus_memory.lua#L257-L268)**
```lua
    function api.writable_data(address, size)
        if type(size) ~= 'number' or size <= 0 then return false end
        local cursor = address_of(address)
        local finish = cursor + size
        while cursor < finish do
            api.queries = api.queries + 1
            if query(cursor, region, region_size) ~= region_size then return false end
            if region.state ~= MEM_COMMIT or region.type ~= MEM_PRIVATE or region.protection ~= PAGE_READWRITE then
                return false
            end
            local region_end = region.base_low + region.base_high * HIGH + region.size_low + region.size_high * HIGH
            if region_end <= cursor then return false end
```

Three components have their own write path with an equivalent check: Arc Thrower and LaserSentryCooldown (§F-4) and FlameDamageFixed:

**[`components/FlameDamageFixed/src/flame_damage_fixed.lua` L1075–L1080](https://github.com/CowboyBingus/VanillaPlusMegapack/blob/526750bb7e99dea6a707e5649fda488d91f3be86/components/FlameDamageFixed/src/flame_damage_fixed.lua#L1075-L1080)**

    local function private_rw(address)
        if query_memory(address, region, REGION_SIZE) == 0 then return nil end
        local w = region_words
        if w[8] ~= 0x1000 or w[10] ~= 0x20000 or w[9] ~= 4 then return nil end

*Depth caveat:* the shared guard and the Arc Thrower / FlameDamageFixed / LaserSentryCooldown paths were read in full. Four more components (StratagemHeroExpanded, ControllableHoverPack, SentryAimRetention, ShallowWaterDiving) also declare `WriteProcessMemory` in a file of their own (e.g. a `native.write` wrapper in `stratagem_hero_expanded.lua` L269); their comments say they are layered on the shared guard, but I did not independently trace each wrapper's bounds check to the same depth.

Every process handle in the codebase is `GetCurrentProcess()`; there is **no** `OpenProcess`, so nothing can reach another process. What is written is small and specific — e.g. Arc Thrower sets a single byte (`0x01`) at record offset 184 and remembers the original to put back.

`BetterLobbyManagement` goes further: it **calls game functions by address** and sends in-game chat / RPCs (new-host notice, kick). It first verifies the bytes at each address and refuses to run on a mismatch, which is good integrity design:

**[`components/BetterLobbyManagement/src/chat.lua` L67](https://github.com/CowboyBingus/VanillaPlusMegapack/blob/526750bb7e99dea6a707e5649fda488d91f3be86/components/BetterLobbyManagement/src/chat.lua#L67)**

That is the declared feature, but it is worth stating that this mod acts *on other users*, not just on the local game. Memory writes and function calls into a live game can also conflict with the game's anti-cheat/terms; that risk is to the *player's account*, not to their machine, and I did not assess it.

### F-6 · Info · The loader is the trust root; installed Lua mods are unsandboxed

The pack states it "contains no shared startup loader, `boot` replacement or Wwise call" (`README.md` L68) — that role belongs to the separate **Bingus Shared Loader**, which every option requires (`README.md` L7). I scanned it with the same sweeps (10 non-test Lua files, ≈2.9k lines): **0** memory-write/protect/alloc, **0** network, **0** shell/process, **0** input/clipboard/registry, only system-library `ffi.load('kernel32')`, and its `require()` sites are for builtins such as `ffi`:

**[`src/discover.lua` L22–L27](https://github.com/CowboyBingus/BingusSharedLoader/blob/9471bcb16f3a479efdff3e0520def4573ae0a028/src/discover.lua#L22-L27)**
```lua
local function builtin(name)
    local loaded = package and package.loaded and package.loaded[name]
    if loaded then return loaded end
    assert(package and package.preload and package.preload[name], name .. ' builtin unavailable')
    return require(name)
end
```

Design consequence: any Lua mod installed under this loader runs **in-process with full FFI access to the Windows API** — there is no sandbox. The audit above therefore establishes what *this pack's* code does, not what a different mod installed alongside it could do. The loader repository's GitHub license metadata reads `NOASSERTION`.

## 5. Not verified / limits

- **No dynamic analysis.** I did not run the game, the mods, or the loader, and did not observe runtime behaviour or traffic.
- **No rebuild.** The shipped bytecode was inspected (imports, strings, entropy, checksums) but **not** reproduced from source (§F-1).
- **The game, its anti-cheat, Arsenal / HD2MM and the standalone component repositories** were out of scope (the standalone repos were not compared with the vendored copies here).
- **Write-path depth.** See the caveat in §F-5: four of the 14 writers have their own wrapper that, per its comments, is layered on the shared guard, but I did not trace it line by line.
- **Third-party Lua mods** a user installs alongside this pack are, by design, unsandboxed (§F-6) and were not assessed.
- **Static review limits.** A determined author could hide behaviour in game-resource data (e.g. offsets/IDs that mean something to the engine). I checked that written values are small and specific where I read them, but did not semantically verify every one of the ≈25 components' game-data tables.
- **AI-assisted.** This report was produced by an AI model reading the code. Treat it as a structured second opinion that is cheap to re-run, not as a certification.
