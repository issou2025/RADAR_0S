### Fault 1 — `phoenix_trace_url` emitted when the test expects `None`

`tests/api/test_lsat.py:1807` :: `test_tutor_reports_no_trace_when_telemetry_is_disabled`

```text
        assert "trace_id" in body
>       assert body["phoenix_trace_url"] is None
E       AssertionError: assert 'http://localhost:6006/projects/law_ai/traces/7b66a75d7fb0b561c02c7cc6c2693ff1' is None
tests/api/test_lsat.py:1807: AssertionError
```

**Resolved during intake: this is a test-environment fault, not a telemetry leak.** The original report flagged this as a judgement call worth deciding before touching the assertion; the configuration answers it. Three facts, each observable:

1. The test body (printed by pytest in the log) takes **only** the `client` fixture and **never disables telemetry**. Its docstring — *"Local-first default: no collector, no trace, and no broken link"* — shows it was written to assert an *ambient default*, not a switch.
2. `docker-compose.yml` sets telemetry ON for the `backend` service the tests run in: `PHOENIX_COLLECTOR_ENDPOINT=http://phoenix:6006/v1/traces`, `PHOENIX_UI_URL=http://localhost:6006`, `PHOENIX_PROJECT_NAME=law_ai`, `OBSERVABILITY_BACKEND=${OBSERVABILITY_BACKEND:-phoenix}` (lines 27–32). The `PHOENIX_COLLECTOR_ENDPOINT=` empty override exists only on `backend-e2e` (line 321, profile `e2e`) — a different service, not used by `test-coverage`.
3. `nightly-tests.yml:84` starts **`phoenix`** as part of `Start infrastructure services`.

The failing value is exactly `PHOENIX_UI_URL` + `/projects/` + `PHOENIX_PROJECT_NAME` + `/traces/` + trace id. The application emitted a trace URL because it was configured with a collector and told where the UI lives. It behaved correctly. The test asserts a condition its own name claims but never establishes, and the compose default contradicts.

The privacy gate the test is *named* after — "no trace URL when telemetry is disabled" — is therefore currently **unverified**, in either direction. The fix must make the test set the disable state explicitly, which both fixes the failure and gives the gate its first real coverage.

### Faults 2 & 3 — the local model does not serve the autonomy cycle

`tests/core/test_run_autonomy_integration.py:192`, from the shared helper `_assert_the_local_model_answered`, in both `test_lsat_content_cycle_lands_pending_drafts_and_one_is_approvable` and `test_the_cycle_is_audited_and_never_touched_a_hosted_tier`:

```text
>       assert ends[-1].get("degraded") is False, (
E       AssertionError: the cycle degraded to the offline fallback — the local model did not serve it:
E       {'type': 'autonomy_cycle.end', 'cycle_type': 'lsat_content',
E        'duration_ms': 723656.01, 'status': 'ok', 'drafts_persisted': 2,
E        'model': 'fallback/offline', 'degraded': True, ...}
E       assert True is False
```

The second cycle is the same shape at `duration_ms: 722779.28`. Both reached `status: ok` on `model: fallback/offline` with `degraded: True`.

The model is **present but not serving**: `Pull the LegalBench gate model` (`nightly-tests.yml:99-105`) runs `docker compose exec -T ollama ollama pull "$GATE_MODEL"` followed by `ollama list`, and the step reports `success`. `ollama` is started at line 84 and the backend is pointed at it (`OLLAMA_BASE_URL=http://ollama:11434`, `docker-compose.yml:25`).

Two observations intake can add, both short of a diagnosis:

- **~24 of the job's 54 minutes go into these two fallbacks** — 723,656 ms + 722,779 ms. That is the cost story as well as the correctness one, and it is why a readiness/timing probe pays for itself immediately.
- The runner is **CPU-only** — this repo carries a `docker-compose.gpu.yml` overlay (`Makefile:524`, `DC_GPU`) that the nightly does not use. A 12-minute wall clock ending in a graceful fallback is at least as consistent with *"CPU inference exceeded the client's deadline"* as with *"endpoint unreachable"*. Note also that `OLLAMA_REQUEST_TIMEOUT_S` is set only on `backend-e2e` (`=5`); the `backend` service leaves it to the application default, so whatever deadline triggers the fallback is currently implicit and unlogged.

Distinguishing "unreachable" from "too slow" needs the compose runtime and cannot be settled from the log. That is what the probe in step 1 of the work plan is for.

### Fault 4 — async fixture / event-loop scope mismatch

`tests/db/test_backfill_commands_integration.py:102` :: `test_densify_backfill_commit_writes_the_missing_cites_edge`

```text
E   RuntimeError: Task <Task pending name='Task-5326'
    coro=<test_densify_backfill_commit_writes_the_missing_cites_edge()
    running at /app/tests/db/test_backfill_commands_integration.py:102>
    cb=[_run_until_complete_cb() at /usr/local/lib/python3.12/asyncio/base_events.py:181]>
    got Future <Future pending> attached to a different loop
/usr/local/lib/python3.12/asyncio/streams.py:545: RuntimeError
```

A connection/session created on one event loop is awaited on another — the classic asyncio-fixture scope mismatch. The same run carries the matching symptom from the other end:

```text
/app:0: PytestWarning: Error when trying to teardown test databases:
OperationalError('database "test_law_ai" is being accessed by other users
DETAIL:  There is 1 other session using the database.')
```

a leaked session outliving its test. Both should disappear together.

### Also observed — a silently skipped local-AI health check

Not one of the four failures, but directly relevant to faults 2/3, from the same log's skip list:

```text
SKIPPED [1] tests/api/test_local_ai_health.py:10: could not import 'fastapi': No module named 'fastapi'
```

The one test named for local-AI health does not run at all in this image, because `fastapi` is not installed in it. Whatever it checks has been silently absent for the whole 38-run history — a `skip` on a missing import is indistinguishable from an intentional opt-out in the summary line. Worth deciding whether that test still belongs (does this backend still use FastAPI?) or whether the image is missing a dependency.

## Acceptance criteria

Scoped per fault, so progress is checkable even if the work lands in more than one change.

**Fault 1 — telemetry gate**

- [ ] `test_tutor_reports_no_trace_when_telemetry_is_disabled` explicitly establishes the disabled state (monkeypatched setting or an empty `PHOENIX_COLLECTOR_ENDPOINT` for the test) rather than relying on ambient configuration. Verifiable by reading the test.
- [ ] The test passes in the `backend` service **with** compose's telemetry variables set — i.e. `docker compose run --rm --no-deps backend pytest tests/api/test_lsat.py::test_tutor_reports_no_trace_when_telemetry_is_disabled` is green without editing `docker-compose.yml`.
- [ ] A companion assertion covers the enabled case (telemetry configured → `phoenix_trace_url` is a well-formed URL), so the pair actually gates the behaviour in both directions.
- [ ] The assertion is not deleted, skipped, or `xfail`ed.

**Faults 2 & 3 — local model serving**

- [ ] `nightly-tests.yml` gains an Ollama **readiness/serving** probe after `Pull the LegalBench gate model` that issues a real generation against `$GATE_MODEL` and fails the step if it does not answer within a stated deadline. Verifiable by reading the workflow and by the step appearing in a run.
- [ ] `OLLAMA_REQUEST_TIMEOUT_S` (or the equivalent deadline) is set explicitly for the `backend` service so the fallback threshold is configuration, not an implicit default.
- [ ] `autonomy_cycle.end` records `degraded: False` and a real `model` value (not `fallback/offline`) in a nightly run — or, if the model genuinely cannot serve on a CPU runner, the job fails at the probe in seconds instead of after two 12-minute cycles.
- [ ] Total wall clock for `Run test coverage` drops by roughly the 24 minutes currently spent in the two fallback cycles (compare against this run's `2831.39s`).
- [ ] `_assert_the_local_model_answered` is unchanged in strictness.

**Fault 4 — async fixture scope**

- [ ] `test_densify_backfill_commit_writes_the_missing_cites_edge` passes; no `got Future <Future pending> attached to a different loop`.
- [ ] The `PytestWarning: Error when trying to teardown test databases: … "test_law_ai" is being accessed by other users` warning no longer appears in the run.

**Whole gate**

- [ ] A scheduled or `workflow_dispatch` run of *Nightly Tests & Autonomy* reaches `conclusion: success` — the first in 39 runs.
- [ ] The ~15 previously-skipped steps report a real conclusion (`success`/`failure`), not `skipped`. Verifiable with `gh run view <id> -R bamr87/law-ai --json jobs`.
- [ ] No `continue-on-error:`, `|| true`, `@pytest.mark.skip`, or `xfail` is added to any of the four failing tests or to `Run test coverage` to achieve the above.
- [ ] `tests/api/test_local_ai_health.py` either runs (its import resolves) or carries an explicit, intentional skip reason — not `could not import 'fastapi'`.

## Why an issue and not a PR

Per the loop's own rule that a wrong fix costs more than a good description:

- These are **four unrelated application-level defects** — telemetry gating, local-model serving, and async DB fixture scope — not a CI-configuration fault the doctor can fix in a workflow file.
- `law-ai` is **private** and a legal-AI domain codebase. Fault 1 in particular is a judgement call between "the product leaks telemetry when disabled" and "the test's fixture drifted", and getting that backwards would suppress a real privacy gate.
- Fault 4 needs the async fixture topology, and faults 2–3 need the compose/Ollama runtime — neither is safely inferable from a log.
- The right sequencing is also non-obvious: a workflow red for 38 consecutive runs is a repo-health project, not a one-line patch.

I did **not** apply any `continue-on-error` or test-skip to make it green.

## Proposed work, in order

1. **Fault 2/3 first** — biggest win. Add an explicit Ollama readiness probe after `Pull the LegalBench gate model` and fail the step if the model will not serve. Recovers ~24 min/run and converts a 12-minute silent fallback into an immediate, legible failure.
2. **Fault 1** — determine whether `phoenix_trace_url` is emitted because telemetry genuinely is not disabled (fix the product) or the fixture stopped disabling it (fix the test). Treat as a privacy gate until shown otherwise.
3. **Fault 4** — align the async fixture's event-loop scope with the test's; the "being accessed by other users" teardown warning should disappear with it.
4. Once green, consider whether `Run test coverage` should be non-blocking for the *later* gates, so a unit-test failure stops masking the LegalBench, Playwright, and validator signals entirely.
