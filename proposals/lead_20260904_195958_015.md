# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Audit repository engineering and portfolio quality**

*Project description:*
## Purpose

Perform a read-only audit of this public repository as both an engineering artifact and a portfolio artifact for prospective employers.

The audit should answer two questions at once:

1. Is the repository correctly structured, coded, tested, secured, documented, and maintained?
2. What would a strong engineering reviewer infer about the maintainer's abilities from a cold review of the repository?

## Frozen audit target

Audit the published repository at exact revision:

`0e3fc54773dd0177ecd7b0b8a9e75ea0d76db41d`

Do not evaluate a moving `main` implicitly. Findings should be tied to this revision unless a later audit step explicitly records a newer target.

## Stage 1 boundary

Stage 1 is read-only investigation.

Do not during the audit:

- modify repository files;
- create implementation branches or pull requests;
- rewrite documentation;
- refactor code;
- change dependencies or CI;
- change validator behavior;
- add portfolio decoration or badges;
- create remediation issues before findings are consolidated and reviewed;
- create work-log entries.

The audit should identify strengths, weaknesses, and candidate improvements before any remediation is authorized.

## Review passes

### 1. Cold-reader / first-impression review

Review the repository as a prospective employer arriving without project history.

Assess:

- whether purpose is understandable within roughly 30 seconds;
- whether repository responsibility and boundaries are clear;
- whether the work appears deliberate, finished, and maintained;
- whether strong engineering signals are visible without reconstructing issue history;
- confusing, excessive, unfinished, or awkward public-facing elements;
- likely impressions for an engineering manager, senior/staff engineer, and platform/security-minded reviewer.

### 2. Repository architecture review

Assess:

- whether each root file and directory has a clear responsibility;
- separation of templates, guidance, tooling, tests, automation, and generated state;
- unnecessary overlap or duplication;
- missing structure justified by a real responsibility;
- unnecessary machinery or conventional files added without a forcing need.

### 3. Code-quality review

Review executable repository tooling, especially:

- `scripts/validate.py`;
- `scripts/update_repository_structure.py`;
- `scripts/setup_git_hooks.py`;
- `.githooks/`;
- related Python modules if any.

Assess responsibility boundaries, cohesion, naming, duplication, error handling, filesystem safety, symlink handling, subprocess behavior, encoding assumptions, deterministic behavior, regex maintainability, hidden platform assumptions, complexity, and testability.

### 4. Test-quality review

Assess:

- meaningful behavioral coverage;
- negative and boundary cases;
- filesystem and symlink edge cases;
- malformed-input behavior;
- error-path testing;
- isolation and fixture clarity;
- brittleness;
- tests that merely freeze incidental implementation details;
- important behavior lacking regression coverage.

### 5. CI, dependency, and security review

Assess:

- workflow permissions and token scope;
- third-party Action provenance and pinning;
- dependency/update automation;
- timeout and concurrency behavior;
- local/CI parity;
- private vulnerability reporting;
- branch/ruleset posture where visible;
- secret scanning, push protection, code scanning, and other applicable GitHub security capabilities;
- deterministic/reproducible validation;
- unnecessary security theater or machinery.

### 6. Documentation and contributor-experience review

Assess:

- README effectiveness;
- catalog/navigation clarity;
- contributor onboarding;
- local validation instructions;
- terminology consistency;
- security-reporting usability;
- duplicated or contradictory guidance;
- dead-end navigation;
- verbosity and unnecessary bureaucracy.

### 7. Standards/content architecture review

Assess reusable templates for:

- scope clarity;
- normative calibration;
- requirement identity and reference integrity;
- dependency declarations;
- cross-template boundary integrity;
- organization neutrality;
- accidental implementation prescription;
- overbroad legal/security claims;
- stale external assumptions;
- Web Standards Suite Baseline/core/optional architecture and ownership boundaries.

### 8. Human-authorship / AI-footprint review

Evaluate whether the public repository reads like deliberately authored and edited engineering work rather than unedited model output.

Look for:

- repetitive sentence structures or stock phrasing;
- excessive boundary/disclaimer repetition;
- suspiciously uniform document structures;
- abstract governance language where simpler engineering language would be stronger;
- unnecessary symmetry or exhaustive enumeration;
- comments/docstrings that explain the obvious;
- issue/document tone more formal than the underlying problem warrants;
- overengineering that could itself create an AI-generated impression.

Do not recommend fake informality, intentional errors, artificial inconsistency, or concealment tactics. Prefer earned structure, specific language, editorial compression, and proportionate detail.

### 9. Portfolio-signal review

Assess whether a cold reviewer can discover evidence of:

- architectural judgment;
- restraint and proportionality;
- testing discipline;
- validation design;
- deterministic tooling;
- security awareness;
- compatibility/migration thinking;
- standards and dependency design;
- end-to-end ownership;
- knowing what not to generalize or automate.

Identify strong work that is unnecessarily hidden as well as anything that could create the wrong impression.

## Finding classification

Classify each consolidated observation as one of:

- **A — Correctness / security:** actual defect, unsafe behavior, false claim, or broken invariant.
- **B — Engineering quality:** maintainability, reliability, design, test, or implementation improvement.
- **C — Reviewer clarity:** good engineering exists but is difficult for a cold reviewer to understand or discover.
- **D — Useful polish:** small presentation improvement with genuine value.
- **Reject:** cosmetic churn, resume theater, unearned complexity, or a suggestion whose cost exceeds its value.

Do not turn every observation into a remediation candidate.

## Reviewer model

Use multiple independent perspectives before remediation:

1. ChatGPT: cold-reader, architecture, documentation, standards boundaries, portfolio signal, and consolidated planning review.
2. Codex: code, tests, tooling, CI, filesystem, and implementation-detail audit.
3. Claude: adversarial review of the repository and prior findings, including overengineering and AI-footprint concerns.

Disagreements should be surfaced rather than silently averaged away.

## Stage 1 deliverable

Produce a consolidated findings report containing:

- executive assessment;
- strongest engineering signals worth preserving;
- A findings;
- B findings;
- C findings;
- D findings;
- rejected/non-actionable observations;
- reviewer disagreements;
- prioritized remediation candidates;
- explicit areas where no change is justified.

No remediation begins until the findings report is reviewed and explicitly dispositioned.
