# Project Proposal — Flutter App

## Project Understanding

## Problem

The app has no test that talks to a real API. `test/integration/` uses mockito, and `pubspec.yaml` has no `integration_test` dependency. A UI-level e2e check of a backend change is therefore impossible.

## Approach

Add a Flutter `integration_test` suite that runs on the **Linux desktop** target under Xvfb against a local API started by the API repo's `e2e/up.sh` (SHUKE-LABS/HappyNotes.Api#79).

Feasibility was verified on 2026-11-06 on the local host (Flutter 3.38.6) at master `71140c5`:

- `flutter build linux --debug` succeeds once a `.env` file exists.
- An `integration_test` that calls `app.main()` and finds the login `TextField`s passes under `xvfb-run -a flutter test integration_test/<file>.dart -d linux`.

Implementation:

- **Dependency**: add `integration_test: sdk: flutter` to `dev_dependencies`.
- **API URL via `.env`**: `.env` is a gitignored asset that the build requires (`pubspec.yaml` asset `.env`). `main.dart` loads it with `mergeWith: Platform.environment`, but file entries win over environment variables, so the API URL cannot be injected through the environment. The runner script therefore generates `.env` with `API_BASE_URL` pointing at the e2e API.
  - Because generating `.env` overwrites the file, the runner must work in a dedicated clone or worktree, never in a developer checkout.
- **Per-run state isolation**: point `XDG_DATA_HOME` (and `HOME` if needed) at a per-run temp directory, so `SharedPreferences` tokens from a previous run or from the developer's own app never leak in.
- **Stable keys**: add `Key`s to the widgets the scenarios drive:
  - login username, password, and submit;
  - the new-note entry point, editor, and save;
  - the note list item;
  - the search entry and its results.
- **Runner**: `tool/e2e/run.sh <run-state-file> <evidence-dir>`. It reads the API base URL and seed credentials, generates `.env`, and runs the suite under `xvfb-run -a ... -d linux`. Screenshots go to `<evidence-dir>/app/`; with the Linux desktop target, use `RenderRepaintBoundary` / `toImage` captures rather than `binding.takeScreenshot`.
- **Initial scenario (core smoke)**: password login (Google Sign-In is out of scope) → create a note through the UI → it appears in the list → search finds it → delete it through the UI → it disappears.

## Acceptance criteria
