## Context

[workmux](https://workmux.raine.dev/) is a tmux (also Kitty/WezTerm/Zellij) workflow tool built exactly around the two things being asked for here:

* **A single view of worktrees and agents.** `workmux add <task>` creates a git worktree plus a matching tmux window (or session, see Open questions) in one command, runs `post_create` hooks, sets up a configured pane layout, and can show live agent status (working, waiting, done) directly in the tmux window name. A `workmux dashboard` TUI gives a centralized view across all worktrees/agents for monitoring, reviewing diffs, and sending commands.
* **A client/server architecture with independent views.** This is exactly what tmux already provides and what #13 already scoped out: the tmux server holds the live state, and any client (a real terminal or a VS Code integrated terminal) is just a view into it. #13's session group trick (`tmux new-session -t main -s main-vscode`) gives a VS Code terminal its own current-window pointer without disturbing the master terminal's view. workmux does not replace this, it sits on top of the same tmux server, so the trick still applies to whatever window/session workmux creates.

This repo has no tmux config tracked yet (`tmux` is only in `brew/Brewfile`, line 78; see #13). It also already has a mature worktree tool in place: `worktrunk` (`wt`/`cop`, stowed at `worktrunk/.config/worktrunk/config.toml`), whose `post-start` hooks symlink `.venv`, open the worktree in VS Code (`code -n`), register the repo for `coppice list`, and walk up to sync `AGENTS.md`/`CLAUDE.md` into the worktree. Any workmux adoption needs to say explicitly how it coexists with that, not quietly duplicate or fight it (see Open questions).

Related: this supersedes #13 in scope. The tmux base config and session group technique from #13 are folded in below as steps 2 and 6, generalized to work against whichever session workmux is actually using (window mode vs session mode) instead of a single hardcoded `main` session.

## Goal

End state: one tmux master session per project shows every active worktree as a window (or session) with live agent status visible at a glance, a `workmux dashboard` window gives a centralized overview of all of them, and any of those windows/sessions can be opened as an independent view from a VS Code integrated terminal (its own current-window pointer, detaching or navigating it never touches the master), the same guarantee #13 already established, now generalized to workmux managed windows/sessions instead of a single fixed session name.

## Features checklist

Mapping the ask to the plan below, so nothing gets dropped along the way:

- [ ] Single window/dashboard showing all worktrees and their agents, live (steps 4, 8, 9)

## Implementation plan

1. **Reconcile scope with worktrunk first.** Before installing anything, write down (as a comment on this issue) which tool owns worktree creation for which case. Starting position to validate: worktrunk keeps owning deliberate, longer-lived feature branches (it already handles VS Code opening, `AGENTS.md`/`CLAUDE.md` sync, `.venv` symlink, `code-review-graph` registration, cross-repo registry); workmux owns short-lived, agent-driven task worktrees where its dashboard and one-command `merge` cleanup add value that worktrunk doesn't have. The two should not both try to create a worktree for the same task.

2. **New `tmux` stow package.** Same as #13 step 1: minimal `tmux/.tmux.conf` (or `tmux/.config/tmux/tmux.conf`, check which path this machine's `brew install tmux` actually reads) with sane prefix, mouse mode, and a status line that shows session name and window name prominently (workmux writes agent status icons into window names, so the status line needs room to show them). No plugin manager, no theme overhaul, see Non-goals.

3. **Install workmux and set global config.** `brew install raine/workmux/workmux`, add the line to `brew/Brewfile` next to the existing `tmux` line. Run `workmux config edit` and set, in `~/.config/workmux/config.yaml`: `agent: pi` (this machine's actual CLI agent, confirmed supported, see Open questions on the missing waiting-state indicator), `base_branch: auto`, `merge_strategy` and `merge_keep` to match how cleanup should behave by default, `mode: window` to start (see Open questions), and a `window_prefix` if the default icon/`wm-` prefix should be overridden.

4. **Pilot `.workmux.yaml` in one repo.** Pick one low-risk repo first, not a blanket rollout. Configure `panes` (an agent pane running `pi` with `focus: true`, plus a shell/dev pane), `files.symlink`/`files.copy` for whatever worktrunk currently handles manually for that repo (`.env`, `node_modules`, or similar), and a `post_create` hook only for what worktrunk's `post-start` hooks don't already cover, to avoid duplicating the venv symlink and VS Code launch logic.

5. **Status tracking.** Confirm the `pi` agent's status shows up in tmux window names (workmux docs list Pi as supported, without a waiting-state icon). If it doesn't render out of the box, check `workmux setup` for whatever lifecycle hooks it installs for status tracking.

6. **Generalize the #13 linked-view technique.** Replace the old `tmv` design's hardcoded `main`/`main-vscode` names with a target session argument, e.g. `tmux new-session -A -t "$1" -s "$1-vscode"`. In window mode there's one session per project (whatever the master attached with), so the target is just that session name. In session mode workmux creates one session per worktree; confirm its actual naming scheme via `tmux ls` once step 4 is running, and use that as the target instead. Either way, the client/server guarantee from #13 (independent current-window pointer, detach never touches the master) is unchanged, only the session name being linked to changes.

7. **Shell helper + VS Code terminal profile.** Port `tm`/`tmv` from #13's plan into the `zsh` package (funcs file) with the session-name parameter from step 6, and add the corresponding opt-in `terminal.integrated.profiles.osx` entry in `vscode/Library/Application Support/Code/User/settings.json` that runs the generalized `tmv <session>` for the worktree it's opened in (worktrunk already runs `code -n {{ worktree_path }}` on creation, so the profile should resolve the session name from the worktree path/branch rather than requiring manual input).

8. **Dashboard window.** Add a way to open `workmux dashboard` (or the lighter-weight sidebar variant) in a dedicated window of the master tmux session, so "see all worktrees and agents at a glance" is a window switch away, not a separate command to remember.

9. **Docs.** Update this repo's `README.md` (or a `tmux/README.md`) covering: starting the master session, `workmux add`/`merge`, opening the dashboard window, opening an independent VS Code view for any window/session, and how the worktrunk/workmux split from step 1 actually works in practice.

## Verification

- `brew install raine/workmux/workmux` succeeds, `workmux --version` runs.
- New terminal loads the `tmux` base config; status line shows session and window names.
- `workmux add test-feature` in the pilot repo creates a worktree, a tmux window/session with the configured pane layout, and switches the tmux client to it.
- The `pi` agent pane shows a status change in the window name/dashboard while working.
- `workmux dashboard` (in its own window) lists the new worktree and its agent status.
- From a VS Code integrated terminal in the pilot repo's worktree, the new VS Code profile opens an independent view (confirm via `tmux ls`/`#{session_group}` per #13's verification steps); navigating windows in that view does not change the master terminal's current window, and vice versa.
- Detaching the VS Code view leaves the master session and all workmux managed windows untouched and running.
- Re-running the VS Code profile/command from a second tab attaches to the existing linked view instead of creating a duplicate.
- `workmux merge` on the pilot worktree cleans up the worktree, branch, and tmux window/session, and the dashboard reflects the removal.

## Open questions

1. Worktrunk vs workmux scope split (step 1): confirm the starting position above, or decide to fully migrate one workflow to the other. This blocks step 4 and should be answered first.
2. Window mode vs session mode (`mode` config): leaning window mode to start, closer to #13's original single-session assumption and simpler to link a VS Code view against. Revisit session mode only if a worktree needs multiple independent windows (editor + tests + logs) at once.
3. `agent: pi` has no waiting-state indicator in the dashboard/window name (per workmux's agent support table). Acceptable for v1, or worth checking `workmux setup`/named agent profiles for a workaround?
4. Should the dashboard window (step 8) be always open in the master session, or launched on demand? Leaning on demand at first, same reasoning as #13's "manual, not auto-start" call on `tm`.
5. Sandbox mode (containers/Lima VMs for agent isolation) is a workmux feature but wasn't part of the original ask. Defer to a follow-up issue unless there's a concrete need now.
6. If session mode is chosen (question 2), should workmux's per-worktree session name match worktrunk's existing `{{ repo }}-{{ branch | sanitize }}` label scheme, for consistency with how herdr worktree labels already work?

## Non-goals

- A full tmux theme/plugin overhaul (`tpm`, statusbar plugins, custom keytables). Base config only (carried over from #13).
- Migrating every existing repo/worktree to workmux on day one. Pilot one repo first (step 4).
- Sandbox/container isolation for agents (Open question 5).
- Cross-machine socket forwarding; master and VS Code view are assumed to be on the same host, or both connected to the same remote host via VS Code Remote-SSH (carried over from #13).
- Any change to herdr's own session/workspace model, a separate multiplexing layer living entirely inside a single shell (carried over from #13).
