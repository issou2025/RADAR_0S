## Problem and intended outcome

Flutter applications will use app-owned `google_sign_in` and `sign_in_with_apple` to authenticate with Google and Apple. They need a supported way to exchange that authentication for a Lantern-owned native end-user session and use it through the Dart SDK.

The current Server has browser-cookie sessions and an RFC 9068 API Bearer verifier, but no native provider-login/session contract. A Google/Apple ID token is not accepted by that existing API Bearer profile. Dart already has per-attempt `TokenProvider` injection; its missing piece is a typed client for the new Server contract, not a Flutter authentication implementation.

Deliver one bounded Server-first implementation with a matching pure-Dart facade, Flutter example, documentation and relevant tests:

```text
app-owned provider plugin
  -> provider credential over HTTPS
  -> dedicated Lantern native login
  -> verified (issuer, subject) + current Principal/Role policy
  -> opaque native end-user session
  -> Dart TokenProvider -> Lantern RPC
```

Google and Apple remain the IdPs. Lantern manages only its own application sessions.

## Scope and ownership

### 1. Server native login contract

- Define bounded typed native login requests/responses, errors and any required provider-specific challenge/completion transaction. Choose the HTTP/Connect shape before implementing consumers; endpoint names are not prescribed here.
- Keep provider/client profiles in trusted operator/security configuration. Pin allowed Issuers, Google backend audiences/client policy, and Apple native Bundle/App IDs versus web Services IDs. Never accept caller-selected Discovery/JWKS/token URLs or arbitrary client/redirect combinations.
- Identify users by exact verified `(iss, sub)`. Reuse explicit Principal registration and Role assignments; unknown/suspended users are refused. Login does not grant data access, enroll arbitrary subjects, or link accounts by email.
- Document provider-specific login CSRF, nonce and replay semantics against the actual plugin/platform APIs. Bound requests, transactions, network work and errors; redact credentials and use the existing safe-fetch/secret-destination boundaries.
- Preserve original signed authentication evidence. Missing/older `auth_time` remains valid for ordinary login/authorized ordinary work; token issuance, plugin success, session renewal or callback time does not create recent-auth evidence. Preserve separate high-impact approval and human/machine policy.

### 2. Google plugin credential verification

- Accept the Google signed ID token at the dedicated login boundary and validate signature, exact accepted Issuer, configured backend audience/client policy and required time claims. Derive identity from verified `sub`, not app-supplied user ID/email.
- Configure the example's `serverClientId` and platform registrations consistently with the Server's expected audience. Do not require Google API scopes or `serverAuthCode` merely to sign in to Lantern.
- Account for the inspected `google_sign_in` API: nonce is supplied to exactly-once `initialize()`; `authenticate()` has no per-call nonce. Do not implement repeated initialization or assume a fresh Server nonce can be supplied on every login. Record and test the supported nonce/replay policy, including repeated sign-in and restored/lightweight authentication; do not describe an unproven event as fresh.
- Keep Google API access/offline authorization outside this feature.

### 3. Apple plugin credential verification

- Accept the identity token and authorization code with the appropriate login context. Verify signature, exact Issuer, matching registered native/web audience, expiry and the expected nonce, then perform the required Server-owned code exchange once.
- Explicitly define the nonce representation and comparison. The plugin forwards its supplied nonce; a blanket raw-versus-SHA-256 convention must not be inferred from another backend's integration.
- Supply/update the signed Apple `client_secret` securely and support `client_secret_post`. Keep private keys, client secrets and any retained provider refresh tokens Server-private; do not expose them through session responses, shared public graph data, logs or example build defines.
- Use the correct Bundle/App ID for native Apple-platform credentials and Services ID for the Android web-backed flow. Send a registered `redirect_uri` only when the original authorization request supplied one.
- Include the Android Apple plugin flow: configured HTTPS callback and safe return to the registered application, with state/transaction validation and bounded POST parsing where `form_post` is used. iOS native sign-in does not require this web bridge. Do not return a long-lived Lantern credential in a redirect URL or let unverified callback data replace the current app session.
- Implement an explicit supported Apple profile; do not silently weaken Google/browser PKCE contracts or claim that Apple PKCE was verified.

### 4. Native end-user session

- Issue an unguessable opaque session credential only after successful authentication and current authorization checks. Define fixed/absolute expiry, client/endpoint binding where appropriate, session metadata, logout and revocation semantics.
- Treat it as a distinct end-user credential profile from browser cookies, RFC 9068 external API access tokens and native machine tokens. Provider ID/access tokens remain login inputs, not a new permissive fallback in the ordinary RPC verifier.
- Integrate issuance, authentication and revocation with existing current-v2 trusted credential evidence, durable security state, admission, policy freshness and output fencing. No side authorization cache, per-data-RPC persistence or anonymous fallback. Suspension, Issuer disable, Role withdrawal and session revocation must affect RPC/stream serving under the existing guarantees.
- Keep issuance/revocation failure and response-loss behavior explicit and fail closed; a timeout is not proof of rollback.
- Initial delivery may use fixed expiry followed by re-login. Record the selected lifetime and provider-disconnect policy before implementation. Refresh is not required for initial completion; if selected, specify atomic rotation/reuse detection or sender binding, absolute lifetime and logout/revocation before implementing it.
- Distinguish Lantern logout from provider sign-out, consent revocation and account deletion. If provider-revocation convergence is promised, define its bounded policy and implement the needed Apple status/notification or other provider integration; do not invent immediate revocation from local plugin sign-out.

### 5. Pure-Dart SDK and app-owned Flutter integration

- Add typed native login/session/logout requests, results and errors to `lantern_client`, exposing only the selected Server contract. Reuse HTTPS/deadline/cancellation/redaction and existing `TokenProvider` for RPC authentication.
- Keep `lantern_client` pure Dart: no Flutter dependency, provider plugin, platform channel, native implementation or secure-storage dependency in the SDK runtime. Keep generated RPC types private and regenerate affected outputs normally.
- The maintained Flutter example owns both plugins, platform/client setup, sign-in cancellation/UI, secure credential storage, session lifecycle and any refresh single-flight coordination. Resolve plugin versions against repository Dart/Flutter pins; do not assume the newest plugin is compatible.
- On logout/account change, cancel old foreground work and isolate cache/offline partitions. Preserve possibly dispatched mutation identities and status-first recovery; do not silently replay another account's outbox.
- Do not create `lantern_auth` as part of this feature. Revisit package extraction only after actual shared integration code justifies it.

## Non-goals

- Lantern as a general IdP/OIDC Provider or an external authentication broker.
- AppAuth integration or app-facing custom OAuth `authorize`/`token` endpoints.
- Google API authorization, automatic public signup, email-based account linking, implicit Role grants, or machine-token reuse for human sessions.
- A blanket PKCE or fresh-per-login Google nonce requirement that the chosen provider/plugin API cannot satisfy.
- Mandatory refresh, background authentication, new SQL/runtime services, provider client creation, deployment, tags or package publication as part of Issue creation.
