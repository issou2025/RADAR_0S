# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**The whole WebView UI freezes during a long Revit operation — including the indicator that exists to report it**

*Project description:*
Found in the plugin log of a 1.5.0 session, not reported by hand — nobody was watching the window at the time.

## Evidence

A long `ExecuteRevitCode` starts, and the WebView's status poll stops dead for **six and a half minutes**:

```
22:58:43.185  Command ExecuteRevitCode invoked via mcp
22:58:43.186  ExecuteRevitCode: compiling ad-hoc snippet (6827 chars)
              ← no webview2 poll at all for 6m22s
23:02:47.297  Command GetQueueStatus invoked via mcp      ← MCP still answering
23:02:51.118  Command GetQueueStatus invoked via mcp
23:04:30.105  Command GetQueueStatus invoked via mcp
23:05:05.344  Command GetQueueStatus invoked via webview2 ← UI comes back
```

Before and after that window the WebView polls every two seconds without a gap, so this is not the poller stopping itself.

## Why it matters more than a frozen window usually does

`GetQueueStatus` is designed never to touch the Revit thread precisely so it can answer while Revit is blocked, and over MCP it did — three times, during the freeze. The WebView could not ask. So the component whose entire job is to say **"Revit is busy, that is why nothing is responding"** is the one that goes silent exactly when it is needed, and the user sees a dead window with no explanation.

## Where to look

The command itself is correctly off the Revit thread, so the block is on the way in or out: the WebView2 message pump, or `WebView2Transport`'s dispatch, sharing a thread with the blocked Revit work. Worth establishing first whether the poll request never leaves the page or never gets answered — the log only shows that it never reached `CommandQueue`.
