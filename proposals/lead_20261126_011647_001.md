## Goal

The pyRevit agent skills (`pyrevitlib/pyrevit/agent/skills`: `revit-scripting`, `pyrevit-library`,
`modeling`, `drawings`, `views`, `scheduling`, `family-editing`, `family-geometry`, `revit-files`,
`extension-authoring`) reach every MCP-capable coding agent, loaded on demand, with no manual copying and
no loss of the current safety properties (shipped skills win over user skills, bounded files, digests,
reparse-point checks).

## What exists today

- `PyRevitAgentSkills` loads skill folders (shipped, plus `%APPDATA%\pyRevit\agent\skills` when enabled).
- `PyRevitMcpServer` serves them through the tools `list_skills` and `get_skill(name, file)` and puts the
  skill list in the `instructions` of the `initialize` result (`INSTRUCTIONS.md` with `{skills}`).
- The server declares only `tools`, protocol 2025-06-18 (older: 2025-03-26, 2024-11-05).
- Every client therefore gets skills through two channels that work everywhere: `instructions` and tools.
  The cost is that the model must call a tool to read a skill, and the skill is not a first-class citizen of
  the client (no slash command, no per-skill permission, no progressive disclosure by the client).

Skills over MCP (`io.modelcontextprotocol/skills`, SEP-2640):

- Settings `{"directoryRead": bool}`. Server declares `resources` plus the extension in `server/discover`;
  client advertises it in request `_meta["io.modelcontextprotocol/clientCapabilities"]`.
- Methods: `skills/list` (paginated, entries with `uri`, `frontmatter`, `resources` manifest of
  `{uri, digest: "sha256:...", size}` or `"dynamic"`, plus `ttlMs` and `cacheScope`), `skills/get {uri}`,
  `resources/read` on `skill://<name>/SKILL.md`, optional `resources/directory/read`.
- Requires the 2026-07-28 revision (stateless, `server/discover`). Older revisions only work where both
  sides carry `capabilities.extensions` in `initialize`, which the schemas do not define.
- Hosts must verify size and digest, bind approval to the digests, treat content as untrusted, and not
  fetch files ahead of need. Limits: 512 files, 16 MiB per skill. No `list_changed` for skills; freshness is
  `ttlMs`.
- Client support: Claude Code (beta). opencode and Codex CLI: no evidence. SDKs: C# 2.4.0 (experimental),
  TypeScript 2.4.0, Rust rmcp 3.9.0, FastMCP 4.2.0, Python merged, Go/Java/Kotlin/PHP in progress.

## Decisions

1. **Phase 1 is files, not protocol.** A CLI command installs the shipped skills into `.agents/skills`
   (read by opencode and Codex, and by Claude Code through `.claude/skills` if asked). This is the only route
   that reaches opencode and Codex today.
2. **Keep `get_skill` / `list_skills` and `instructions` unchanged.** They are the fallback for every client
   and for sessions where installed skills are disabled or missing.
3. **Phase 2 adds the extension behind negotiation, never instead of the tools.** Declared only when the
   client declares it, so older clients see no change.
4. **One source of truth.** Installed copies and the MCP-served copies are generated from the same folders;
   the SHA-256 the server already computes is the identity of a skill version.
5. **No behavior depends on a client feature.** Run approvals stay in Revit; elicitation and tasks are out of
   scope here.

## Phase 1: install into agent skill folders

### Command

```
pyrevit agent skills install [--scope=<project|user>] [--target=<agents|claude|opencode>] [--path=<folder>] [--force]
pyrevit agent skills status [--json]
pyrevit agent skills uninstall [--scope=<project|user>] [--target=...]
```

(`pyrevit configs agent skills enable|disable` keeps its meaning: whether user skills from
`%APPDATA%\pyRevit\agent\skills` are loaded by the server.)

- `--scope=project` (default): `<--path or cwd>/.agents/skills/`, read by opencode, Codex and Antigravity
  with no extra step. `--scope=user`: the user-level folder of each chosen target.
- `--target=agents` (default) writes `.agents/skills` (user scope `~/.agents/skills`: opencode, Codex, Cursor,
  VS Code);
  `copilot` writes `.github/skills` (project) or `~/.copilot/skills` (user) for VS Code sessions that do not
  read `.agents/skills`;
  `antigravity` writes the user scope to `~/.gemini/config/skills` (the project scope is the same
  `.agents/skills`); `claude` writes `.claude/skills` or `~/.claude/skills`; `opencode` writes
  `.opencode/skills`. Several targets may be given.
- Each skill folder is copied whole (SKILL.md and its markdown files) under the skill's own name.

### Naming and front matter

- Folder name equals the `name` front matter, lowercase kebab-case, 1-64 characters (already the rule in
  `SkillName`). opencode derives the ID from the path, so this must hold.
- Prefix to avoid collisions with the user's own skills: install as `pyrevit-<name>` only if the plain name is
  taken by a folder pyRevit did not write; otherwise keep the shipped name. A marker file
  `.pyrevit-skill.json` (`{source, version, sha256}`) in each folder identifies pyRevit-owned copies.
- `description` must stay informative on its own: Codex budgets 2% of context (about 8,000 characters) for all
  skill metadata and may shorten or drop descriptions, so each shipped description is at most 240
  characters and front-loads the trigger ("Use when ...").

### Safety rules

- Never overwrite or delete a folder without `.pyrevit-skill.json`; `--force` only replaces pyRevit-owned
  folders whose hash differs.
- Refuse reparse points and paths outside the target; write to a temp folder and rename.
- Installed copies are guidance, not policy: they cannot carry or change approvals (same statement as
  `docs/agent-runtime.md` Skills).
- `status` compares the marker hash with the shipped hash and reports `current`, `stale` or `missing` per
  skill and target. A stale install is a warning, never a block.

### Updates

- `pyrevit agent skills install` is idempotent; the installer and `pyrevit` upgrades print a one-line hint
  when `status` finds stale copies. No background updater.
- The command prints the per-client follow-up: Antigravity CLI needs `/skills reload`; Antigravity and
  opencode list the skills by folder name, so the folder name stays the contract.
- The MCP `instructions` text gains one line when the server sees that the project has no installed copy:
  "Skills are also available as files: run `pyrevit agent skills install`." (Text only; the server never
  writes outside `%APPDATA%\pyRevit`.)

### opencode catalog option

opencode accepts http(s) catalog entries and local paths in the `skills` array of `opencode.json`. A later
option is `install --target=opencode-config`, which adds the shipped skills folder
(`pyrevitlib/pyrevit/agent/skills` of the active clone) to that array instead of copying. Out of scope for
the first cut: it edits a user config file and needs its own consent step.

## Phase 2: skills over MCP (extension `io.modelcontextprotocol/skills`)

Gate: start only when `PyRevitMcpServer` supports protocol 2026-07-28 and at least one of opencode, Codex
or Claude Code is verified to use the extension against a test server.

### Protocol work (prerequisite, own issue)

- Add 2026-07-28 to `SupportedProtocolVersions`: `server/discover`, request `_meta` handling, stateless
  semantics, stdio kept.
- Keep 2025-06-18 and older as they are.

### Server surface

- Capabilities: `resources` plus `extensions["io.modelcontextprotocol/skills"] = {directoryRead: false}`.
- `skills/list`: from `PyRevitAgentSkills.Load()`. Entry: `uri` `skill://<name>/SKILL.md`, `frontmatter`
  (unchanged fields), `resources` manifest with `sha256:` digests and sizes of every served file (markdown
  only, as in `Read`); `ttlMs` 300000, `cacheScope` `public` for shipped skills and `private` for user skills.
- `skills/get {uri}`: same entry; -32602 for unknown URIs.
- `resources/read` for each manifest URI, `text/markdown`, same bounds as `Read` (128 KiB per file, inside
  the skill folder, reparse points refused).
- User skills (when enabled) are listed with their source in the frontmatter-adjacent metadata only through
  the URI authority rules the extension allows; shipped skills win on name collisions, exactly as today.
  A user skill never appears in `instructions` or tool descriptions (existing invariant).
- Not implemented: `resources/directory/read` (`directoryRead: false`), `dynamic` manifests.

### Client behavior to verify, per client

| Check | Pass condition |
|---|---|
| Negotiation | Client lists `skills/list` only after the server declares the extension |
| On-demand | No file read on connect; only the chosen skill's files are read |
| Integrity | Client rejects a skill whose digest was tampered with in a test build |
| Duplicates | A skill that is also installed from Phase 1 is not shown twice, or the duplicate is harmless |
| Fallback | With the extension undeclared, `get_skill` and `instructions` still work |

## Risks and open questions

- Installing both `.agents/skills` and `.claude/skills` or `.github/skills` can list a skill twice in
  Cursor, VS Code and opencode, which read several folders. The installer defaults to `.agents/skills` only
  and `status` warns when a pyRevit-owned copy exists in more than one folder a client reads.
- VS Code and Cursor reject or silently drop a skill whose `name` differs from its folder name; the
  `pyrevit-` prefix rule must rename the front matter and the folder together.
- VS Code skills over MCP is experimental and off by default; Phase 2 must not assume it.
- Client-matrix cells for Cursor and VS Code could not be read; recheck them before Phase 2.
- Antigravity's global skill folder moved between versions (`~/.gemini/antigravity/skills` legacy,
  `~/.gemini/config/skills` current); detect the existing folder before writing and prefer the current one.
- Antigravity may not inject MCP `instructions`; without an installed copy it only has tool descriptions.
  Verify with a real run, and if confirmed keep the key routing hints in the tool descriptions.
- Antigravity workflows are being folded into skills (a migration guide exists); not read, so nothing here
  depends on workflows.
- Codex may also read `~/.codex/skills`; the docs found do not say. Verify before choosing the user folder
  for Codex.
- Codex's metadata budget can drop skills when many are installed; ten skills with short descriptions should
  fit, but check with the real client.
- opencode's skill ID comes from the path, so the folder name is the contract; a rename breaks permission
  rules users wrote for it.
- Skills installed to `.claude/skills` are also read by opencode, so installing both `agents` and `claude`
  targets can list a skill twice in opencode. Default stays `agents` only.
- Claude Code docs say skills over MCP are not scanned for `claude mcp add` servers and are limited
  (100 skills, 100 KB per file for scanned ones); our skills are well under these.
- Findings come from summarized docs and no client source was read; confirm the table with a real run before
  Phase 1 ships.
