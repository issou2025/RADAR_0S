# Project Proposal — Dwg To Revit

## Project Understanding
You need assistance with: 
**Smoke tests for tool usage on RVT, NWD and IFC files**

*Project description:*
## Summary

Add smoke tests that exercise the viewer tools on RVT, NWD and IFC files, without a manual sign-in where possible. This is a big one: split it into the phases below.

## Current coverage

Read from the scripts, nothing was run for this issue; none of the timings are measured.

- `e2e/mock_smoke.py` covers the whole app, but only on the SVG mock viewer (no real geometry).
- `e2e/smoke.py` needs a signed-in profile and opens the first model it finds in the hub (`.rvt .nwd .nwc .ifc .dwg`); a single-model run checks xlsx export only. `--multi` and `--combined` use RVTs plus NWDs.
- `e2e:glb`, `e2e:ifc` and `e2e:state` use a two-legged token but only one RVT, hard-coded in `e2e/harness/export_harness.ts:18`.
- Never exercised on a real model: explode, measure, section buttons, CSV and JSON export, selection sets, dashboard and colors; paint only in the combined checks. `.dwf` is in no script.
- No e2e script runs in CI (Biome, typecheck and vitest only).

## IFC

- The app exports IFC (`src/web/ifc/*`) but has no IFC import, and no test has opened a real IFC in the viewer.
- APS lists IFC and NWD as inputs that produce SVF and SVF2 ([supported translations](https://aps.autodesk.com/en/docs/model-derivative/v2/developers_guide/supported-translations)); IFC loader versions differ ([FAQ](https://aps.autodesk.com/blog/faq-and-tips-ifc-translation-model-derivative-api)).
- Not confirmed: whether this account gets SVF2 for IFC, and whether IFC properties look the way `readScopedRows` and the IFC export expect.

## Proposal

- [ ] **P0** Let the harness take the model name from the URL or env. Add `e2e/fixtures.py`: an env-driven URN table (`E2E_REVIT_URN`, `E2E_NWD_URN`, `E2E_IFC_URN`) with a manifest gate that skips untranslated files with a warning.
- [ ] **P1** `e2e:formats` opens each fixture through the harness: viewer opens, tree has leaves, properties read, no console errors. This answers the IFC-in-viewer question.
- [ ] **P2** Per type, run the tool matrix: exports (xlsx, csv, json, GLB, IFC checked with IfcOpenShell), state round trip, section, explode, measure, paint and undo.
- [ ] **P3** `smoke.py --multi` and `--combined` stay local (they need the owner's profile).
- [ ] **P4** Opt-in `workflow_dispatch` and nightly workflow with APS secrets; PR CI unchanged.
- Fixtures live in the app's APS bucket, uploaded and translated once (the two-legged token cannot reach hub files). Public IFCs (for example buildingSMART Sample-Test-Files) are fetched by URL and hash after the licence is checked. No public NWD sample was found.
- Budget 10 minutes or less in total, 300s per file, one retry on viewer load.

## Questions

1. Is the goal "the viewer opens IFC" or "the app's tools work on IFC properties"? The effort differs a lot.
2. Can the APS client get `bucket:create` and `data:write`, and is a repo secret acceptable for a nightly job?
3. Which small IFC may be used, and are binaries committed or only referenced?
4. Should smoke cover `.nwc` and `.dwf`, which only the owner's hub has?

## Acceptance criteria

- One command runs RVT, NWD and IFC and prints a per-type, per-tool pass, fail or skip table.
- A missing or untranslated fixture skips with a warning, not a failure.
- Every tool in the matrix runs on at least one real file type; remaining gaps are listed in `docs/development.md`.
- Only Camoufox is used, and no signed-in profile is read in the CI path.
- A nightly run is green twice in a row before it is made required.
