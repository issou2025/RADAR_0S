# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**kanban: connect(board=slug) silently re-creates an archived board -- archive is not durable**

*Project description:*
## Behavior

Archiving a board is not durable: if any process references the archived slug again, `boards/<slug>/` is silently re-created as a fresh, empty, schema-only board — no `board.json`, zero tasks — and `hermes kanban boards list` then shows it as an active board again (archived=false). The real data stays under `boards/_archived/`, but the registry now holds a live-looking zombie with the same slug.

## Root cause

`connect(board=slug)` unconditionally materializes the board directory and schema-inits it:

- `hermes_cli/kanban_db.py:2338` — `def connect(...)`
- `hermes_cli/kanban_db.py:2365` — `path.parent.mkdir(parents=True, exist_ok=True)` followed by schema init, with no check that this slug was ever an intentionally created board

Meanwhile `remove_board` (`hermes_cli/kanban_db.py:1000-1041`) only renames `boards/<slug>` to `boards/_archived/<slug>-<ts>/` and drops the init-cache entry. Its own inline comment (`:1026-1029`) names the exact hazard:

> A concurrent connect(board=normed) after the rename/delete recreates an empty sqlite file via mkdir(exist_ok=True); the cache entry must be dropped first so the schema init pass re-runs on that fresh file.

…i.e. the code anticipates the re-creation and accommodates it, instead of refusing it. The window is not just "concurrent": any later reference — a gateway board watcher or dispatcher still holding the slug, a dashboard poll, a script that connects by slug — re-creates the board any time after the archive.

## Reproduction

1. Create a board and put at least one card on it:
   `hermes kanban boards init demo && hermes kanban --board demo create "x"`
2. Archive it:
   `hermes kanban boards rm demo` → data moves to `boards/_archived/demo-<ts>/`
3. Reference the slug again from any process that connects by slug, e.g. Python:
   `python -c "from hermes_cli.kanban_db import connect; connect(board='demo')"`
4. `ls ~/.hermes/kanban/boards/` → `demo/` exists again: a `kanban.db` with fresh schema, no `board.json`, no tasks.
5. `hermes kanban boards list --json` → `demo` listed as active (archived=false), counts all zero.

(Note: the per-board CLI `hermes kanban --board demo list` does NOT trigger this — it errors with "board does not exist"; the guard is only on that path. The re-creation comes via `connect()` used as get-or-create by long-lived processes.)

## Observed evidence

Seen in production use: a board archived with 9 real cards re-appeared minutes later as an empty active board with the same slug (fresh 118 KB schema-only `kanban.db`, no `board.json`, zero tasks/events), while a background watcher kept connecting to the slug. The board ended up archived twice under `_archived/` — once with the real data, once with the empty re-creation — which is itself a monotonicity violation for anything that assumes one archive per slug.

## Impact

- "Archived" does not mean archived: the slug namespace stays hot and the active-registry view lies.
- Automation that enumerates active boards (dispatchers, dashboards, cleanup scripts) picks up zombie boards.
- Double-archive under `_archived/` breaks any assumption of slug monotonicity in backup/restore tooling.
- Data is not lost (the real archive survives), but the failure is silent — nothing errors, the board just quietly resurrects.

## Suggested direction

`connect()` should not mkdir+schema-init a slug that has no `board.json` — i.e. treat "no board.json" as "this board does not exist" and raise (or return a miss) instead of creating, leaving explicit board creation to the create/init path. Alternatively, refuse re-creation for slugs known to be archived. The `remove_board` comment shows the re-creation scenario is already understood at that call site; the fix belongs in `connect()` so the invariant "archived boards never re-enter the active registry" holds for every caller.

Happy to turn this into a PR if the maintainers agree with the direction — the no-board.json guard looks small, but I suspect some get-or-create call sites rely on the current semantics, so that audit is where the real work is.
