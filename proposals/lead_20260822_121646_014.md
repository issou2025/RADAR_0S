## Summary

The canonical dashboard process (the one long-running server operators actually use, as opposed to the many short-lived debug servers in #154) does not pick up code changes when `main` is merged. It must be manually restarted after every merge that touches `mctl_dashboard/` for the fix to actually reach anyone looking at that server, and nothing in tonight's workflow does this automatically or reminds anyone to.

## Symptom

```
$ curl http://127.0.0.1:<port>/junk
404

$ curl http://127.0.0.1:<port>/queue | grep -c junk
0
```

The junk lane (#141, merged as `9557ac9`, part of current `main` at `185625a`) does not exist on the running server, despite the checkout it serves from being fully up to date.

## Minimal reproducible example

1. Start a dashboard server: `python3 assets/scripts/mctl.py dashboard serve --city <city-root> --port <port> &`, note the PID.
2. Merge any change touching `assets/scripts/mctl_dashboard/` into `main` (or `git pull` the checkout the server's cwd points at).
3. `curl http://127.0.0.1:<port>/<a route the merge added or changed>` — the old behavior is still served.
4. `lsof -p <PID> | grep cwd` confirms the process's checkout has the new commit on disk; the running behavior does not reflect it.

expected: a route the merge changed reflects the merge → got: the pre-merge behavior, indefinitely, until the process is manually killed and restarted.

## Root cause

`assets/scripts/mctl_dashboard/server.py` and `mctl.py dashboard serve` import their handler modules once at process start; there is no code path that re-imports or reloads on file change (no debug/reloader mode, no file-watcher). This is standard behavior for a plain script-started long-running Python process and is not itself a bug in isolation — the defect is that the *workflow* around it has no step that restarts the canonical server after a merge, so a merge and its actual effect on what an operator sees can silently diverge for an unbounded amount of time. Confirmed live: a process running continuously since ~19:00 was still serving pre-19:00 behavior after several merges landed, including the one this issue's own symptom is about.

## Fix candidates

**A. Document and rely on a manual restart step.** Whoever merges a `mctl_dashboard`-touching change also restarts the canonical server (or asks the operator to).
- Scope: process/documentation only, no code.
- Trade-off: cheap, but relies on someone remembering every time — the exact discipline gap this tracker has repeatedly found this week in other contexts (#154, the create-issue skill not being named).

**B. A restart-on-merge hook or a lightweight file-watcher/reloader for the dashboard process.** Either the merge step itself restarts the canonical server automatically, or the server watches its own source tree and reloads.
- Scope: a small script/hook for A's automation half, or a reloader wrapper (e.g. a watcher process that kills and respawns `dashboard serve` on file change) for the reload half.
- Trade-off: more to build, but removes the "someone forgot" failure mode entirely rather than relying on discipline.

**Recommendation:** A immediately (say, as part of whatever routes/executes a merge tonight — the coordinator role already restarts nothing but could add "and restart the dashboard if this touched mctl_dashboard/" as one line), B as a real fix once the immediate gap is closed. This is time-sensitive precisely because Taylor is expected to look at this dashboard directly.

## Blast radius

Every dashboard-touching fix merged since the canonical server's last restart is invisible to whoever is actually looking at it, with no error or indication that anything is stale — the page renders normally, just with old behavior. This is the same failure family as #153 (backend exists, nothing renders) one layer further out: here, the *frontend* exists and *did* render, at some point in the past, and the operator has no way to tell it stopped reflecting reality.
