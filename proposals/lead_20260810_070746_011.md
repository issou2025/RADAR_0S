# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Create a Fieldwork-to-Scrapbook harvest lane for useful finished work**

*Project description:*
## Context

Issue #557 correctly calls for a practical corpus derived from Stensibly, Fieldwork/Linux Fieldwork, current interview work, and original analysis. The new Scrapbook contribution contracts also give agents clear Guest Check-in and Bot Desk paths once they are already looking at Scrapbook.

The remaining gap is upstream discovery: many of the strongest future Space records and Desk essays are born in other owned repositories. A completed investigation may contain a reusable lesson, but nothing currently carries that candidate toward Scrapbook unless someone remembers to do it manually.

## Goal

Create a lightweight harvest path from completed owned-repository work into Scrapbook **candidate material**, without creating an automatic publishing pipeline.

The harvest step should answer only:

> Did this finished work produce something Scrapbook may want to keep, study, or publish?

Publication remains a separate Scrapbook decision.

## First slice

Dogfood the convention with Fieldwork/Linux Fieldwork before spreading it to every repository.

At closeout, allow one bounded optional disposition:

```text
Scrapbook: none | space-candidate | desk-candidate | both
Candidate: one sentence naming the durable lesson/question
Evidence: canonical completed work URL
```

Then provide a Scrapbook-side intake view or repository-backed candidate list that can:

- show unresolved candidates newest-first;
- point directly to originating evidence;
- classify the candidate as Space, Desk, both, duplicate, or skip;
- record a durable destination when material is published;
- close a candidate without publishing when the lesson is too narrow, stale, duplicated, private, or already captured elsewhere.

The first implementation may be a small repository-backed file or GitHub issue convention. Avoid a new database and avoid cross-repository write automation until real use clarifies the model.

## Strong initial dogfood candidates

Recent work already supplies examples worth evaluating:

- invalid `.venv` behavior across read-only and mutating uv commands;
- Python registry 404/cache semantics;
- installed-tool environment identity and option compatibility;
- compound stub-package name normalization across build backends;
- hostile/foreign error metadata as an input boundary in Stensibly;
- observed repository default branch versus guessed branch;
- observation versus authorization during repository onboarding;
- disposable one-job worker reconciliation in SmolRunner.

These examples are candidate inputs, not pre-approved publications.

## Guardrails

- no automatic creation of a Desk piece or Space record;
- no raw transcript ingestion;
- no private repository material becomes public through the harvest path;
- one completed work item can yield zero, one, or both candidate kinds;
- duplicate/superseded candidates should disappear cleanly rather than accumulating forever;
- originating repository instructions remain authoritative for that repository's own evidence and interaction policy;
- use the current Scrapbook contribution contracts when a candidate advances to publication.

## Acceptance

- [ ] at least ten completed Fieldwork/Linux Fieldwork results can be triaged without manually reconstructing their evidence;
- [ ] each retained candidate has one clear question/lesson and one canonical evidence source;
- [ ] candidate state distinguishes waiting, accepted for Space, accepted for Desk, published, skipped, and duplicate/superseded;
- [ ] no candidate grants publication authority;
- [ ] the process creates less overhead than manually browsing closed work;
- [ ] after dogfood, either retain the convention, simplify it, or remove it with a written reason.
