## Challenge hypotheses
Attempt to demonstrate one or more of the following:

1. **False completeness:** A source can exist in current canonical repository state yet escape inventory coverage, or duplicate/alias entries make the claimed coverage misleading.
2. **False API inference:** Text-pattern classification can incorrectly label a portal/download as an API, or miss a real machine interface in a way that would materially mislead agents.
3. **False licence safety:** Existing wording can evade restriction flags (e.g. research-only, no resale, attribution/share-alike, originator-specific rights, database rights, click-through/API terms) and still lead to an unsafe automation decision.
4. **Verified-source overreach:** A verified manifest licence can be mistaken for permission to use a separate provider API/service or for permission to publish acquired raw bytes.
5. **Credential/network escape:** A crafted contract can introduce arbitrary remote hosts, query URLs, headers, credentials, signed URLs, traversal or unsafe execution despite the validator/schema.
6. **Schema drift:** Portable JSON Schema and executable validator can disagree in a security- or governance-relevant way.
7. **Maintenance drift:** A new source, manifest or contract can be added without forcing the necessary access/licensing review, despite the intended automatic coverage.
8. **Wrong abstraction:** The common contract cannot accurately represent REST/FDSN/STAC/OGC/file/object-store/federated/provider-account cases without becoming either too permissive or misleading.
9. **Restricted examples:** ESWD and IOC/VLIZ SLSMF contracts accidentally imply more access or rights than the existing source evidence supports.
10. **Collision/integration risk:** This PR conflicts semantically with #165/#166 or weakens existing provenance/sample-admission boundaries.
