*Project description:*
## What

Give `onevcs pool maintain` the capability to prune superseded cargo build output in idle pool slots, judged by modification time (mtime) and never by access time (atime), and apply it **only where a policy is declared for the repository**. onevcs derives no default from a checkout's files: a repository that declares nothing, and that no host rule names, is never pruned. A repository declares its own policy in a file it tracks, `build-output.toml` at its root, read the way onevcs already reads a repository's own `release-targets.toml`. A host's workspaces file may declare a policy on a `rules:` entry for a repository that declares none.

**The contract (this node is its one statement; later nodes restate it from here).**

*The repository's declaration*, `build-output.toml` at the repository root, TOML:
```toml
# Why this repository prunes its build output, and what — prose is the file's own.
schema_version = 1

[cargo]
keep_within = "2d"          # required in [cargo]; the workspaces file's existing `Span` grammar
target_dirs = ["target"]    # optional; default ["target"]
```
- `target_dirs` entries are repository-relative directories. An absolute path, a `..` component or an empty list is refused.
- A file with no `[cargo]` table declares that nothing is pruned. That is the repository's own answer, so no host rule applies to it.
- An unknown key at `schema_version = 1` is refused, naming the key and its line. A `schema_version` above the one this build writes is read as version 1, with the keys it does not know ignored, as `release-targets.toml` is read. A missing or non-integer `schema_version` is refused.
- The file is fixed by name, `build-output.toml`, as `pub const FILE` in a new `onevcs::build_output` module, the way `declaration::FILE` names `release-targets.toml`.
- **Where it is read.** It is read from the identity's publication checkout on its base branch, through the same checkout resolution `release.rs`'s `declared_in` uses, and never from a slot's own worktree or a session's branch. A change under review cannot then rewrite the policy that prunes its own pool. Every reason that checkout cannot be read makes the policy **unreadable**, never undeclared.

*The host's rule.* A `rules:` entry of the workspaces file may carry a new optional key, `build_output`:
```yaml
rules:
  - match: {host: github.com, owner: o, name: n}
    build_output: {cargo: {keep_within: 2d, target_dirs: [target]}}   # or {cargo: off}
```
`default:` carrying `build_output` is refused when the file loads, with a message saying a host declares build-output policy per repository and never as a default.

*Resolution*, one function, applied per identity at every `pool maintain` pass and by `pool status`:
1. The repository's declaration, when its publication checkout holds a readable `build-output.toml`.
2. Otherwise, when the checkout holds no such file, the `build_output` of the host rule matching the identity, if any.
3. Otherwise nothing is pruned.

An unreadable declaration (a malformed file, or no readable publication checkout) prunes nothing and never falls through to the host rule.

Rust, beside the existing types (`onevcs::workspaces` and the new `onevcs::build_output`):
```rust
pub struct BuildOutputPolicy { pub cargo: CargoBuildOutput }
pub enum CargoBuildOutput { Off, Prune { keep_within: Span, target_dirs: Vec<PathBuf> } }
// WorkspaceRule gains (WorkspaceDefault does not):
pub build_output: Option<BuildOutputPolicy>
pub enum BuildOutputSource {
    Declared { document: PathBuf, policy: BuildOutputPolicy },
    HostRule { policy: BuildOutputPolicy },
    Undeclared { looked_in: PathBuf },
    Unreadable { reason: String },
}
pub fn read_build_output_declaration(path: &Path) -> Result<BuildOutputPolicy>   // path: a repository root or the file itself
pub fn validate_build_output_declaration(document: &str, origin: &str) -> Result<BuildOutputPolicy>
```
A missing file is refused by `read_build_output_declaration` rather than read as an empty policy. Its refusals name the document and the line.

The report from `pool_maintain(scope, older_than)` (signature unchanged):
```rust
pub enum SlotOutcome { /* NotDue, InUse, Unavailable, Broken unchanged */
    Ran { outcome: Option<MaintenanceOutcome>,  // None when no `maintain` command ran
          duration_ms: u64, log: Option<ArtifactId>,
          build_output: Option<BuildOutputPruned> } } // None when the resolved policy prunes nothing, or no declared target dir exists in the slot
pub struct BuildOutputPruned { pub profiles: u32, pub builds_removed: u64,
    pub bytes_freed: u64, pub bytes_retained: u64, pub skipped: Vec<String> }
```
- In JSON: `{"ran": {"outcome": "succeeded"|{"failed":…}|"timed-out"|null, "duration_ms": N, "log": "<id>"|null, "build_output": {"profiles": N, "builds_removed": N, "bytes_freed": N, "bytes_retained": N, "skipped": ["<path>: <why>"]}|null}}`.
- `bytes_freed` and `bytes_retained` are disk usage (allocated blocks, as `du` counts it). A removed file still hard-linked elsewhere frees nothing and is not counted as freed.
- `IdentityOutcome::NoMaintainCommand` keeps its name. It now means the resolved policy names no `maintain` command *and* prunes nothing.

*Reading verbs.*
- `onevcs pool status <repo>`, human and `--json`, shows the resolved policy and where it came from. The human lines are `build output: cargo, keep within 2d, target dirs: target (declared in <path>)`, `… (host rule)`, `build output: none declared` and `build output: unreadable — <reason>`. The JSON is a new `build_output` field: `{"source": "declared"|"host-rule"|"undeclared"|"unreadable", "document": "<path>"|null, "policy": {...}|null, "reason": "<text>"|null}`.
- **New read verb** `onevcs pool declaration <path>`, where `<path>` is a repository root or the file. It reports what a checkout's own `build-output.toml` declares, the way `onevcs release declaration` does, and needs no registration. Exit 0 prints `build output: cargo, keep within <span>, target dirs: <dir>, <dir>`, or `build output: none declared (no [cargo] table)`. `--json` prints the policy. A malformed file exits non-zero naming the document and line, and a missing file exits non-zero naming the directory looked in. Each repository's declaration is validated with this verb.

**The pruning rule** (unchanged from the earlier design; it applies to each slot whose resolved policy is `Prune`).
- **Order and limits.** It runs in a claimed idle slot, under the existing claim, the at-most-one-slot rule and the identity lock. It runs before the `maintain` command (when there is one), and both are inside the slot's `timeout`.
- **What a profile directory is.** Any directory under one of the policy's `target_dirs` in the slot worktree that holds a `.fingerprint/`. That covers `<dir>/debug`, `<dir>/release`, `<dir>/<triple>/<profile>` and `<dir>/llvm-cov-target/<profile>`.
- **Builds in `deps/`, `.fingerprint/` and `build/`.** Within each profile directory, entries there are grouped into builds by unit name plus metadata hash, parsed from names of the form `[lib]<name>-<16 hex>[.<ext>]`. A build's time is the newest mtime among its entries, recursing into directories. For each unit it keeps the newest build plus every build whose time is within `keep_within` of now, and removes every other build's entries from all three directories.
- **Incremental output.** `incremental/<name>-<id>` directories are grouped by name and kept or removed by the same rule.
- **What it never touches.** Nothing else is removed: profile-root files, `doc/`, `tmp/`, any directory the policy does not name, anything outside them.
- **Failures.** An entry that cannot be removed is listed in `skipped` and never fails the slot. Pruning never reads or depends on atime.

**This repository's own declaration.** onevcs's slots on a host hold its cargo build output too, so this node adds onevcs's own `build-output.toml` at the repository root: `keep_within = "2d"`, `target_dirs` naming the directory its `.cargo/config.toml` sets (`target`). A comment says what the file is for and that onevcs reads it from the publication checkout's base.

**Evidence for the policy.** Read `/home/whoop/ai-orchestrator/scratch/prune-superseded-builds.py` (an untracked file on this host) as evidence of a policy that freed 605 GiB here. It is not code to port.

**Documentation and contract.** Amend `docs/contract.md`'s pool and "Maintaining the pool" amendments, `docs/inferred-surface.md`, `DESIGN.md`, `README.md` and `crates/onevcs/AGENTS.md` wherever they state the workspaces schema, the maintain report or `cargo sweep --time 7` as the example. `docs/contract.md` states the declaration's schema, where it is read from, the resolution order, and that nothing is pruned without a policy. **Out of scope.** No size cap of any kind. No default policy, and no detection of a repository's language or files. No change to placement, return, `delete`, shedding or `pool prune`. No public item beyond those named above.

## Why

On this host about 926 GB of a 1.8 TB disk was superseded Rust build output in warm-pool slots, and the disk has nearly filled twice in four days, needing a manual cleanup each time. Pool maintenance today runs whatever command a host names, and the usual `cargo sweep --time 7` frees almost nothing: it judges age by access time, which its own fingerprint reads keep fresh. Pruning by modification time inside onevcs keeps each unit's newest build warm, so rebuild speed is not lost, and never touches a slot a session holds. Applying it only where a repository declares its own rule, in a file reviewed with that repository's code, means no library or host deletes a repository's output under a rule nobody declared for it. Each repository then owns how its own build output is cleaned up.

## Budgets

### Time one warm slot is out of service while pruned

- **Id:** `pool-build-output-prune-seconds`
- **Measure:** Wall-clock seconds one `onevcs pool maintain` pass holds one idle slot claimed while it prunes that slot's superseded cargo build output, which is how long the slot is out of service for new sessions. The detail reports entries walked, profile directories, builds removed, bytes freed, and seconds walking versus removing.
- **Inner measure, because:** The slot's claim also runs the `maintain` command a host rule names, when one does: that command is whatever a host writes, this change neither adds nor alters it, this host names none once cargo-sweep is retired, and it is already bounded by the slot's `timeout` and reported as `duration_ms`. Pruning is the part this change adds to the claim of every slot whose repository declares a policy, so it is the only part this budget can move.
- **Target:** at most 60 seconds
- **Basis:** estimate
- **Measurement source:** telemetry
- **Check runtime:** approximately 2 seconds
- **Workload:** One idle slot of a repository whose `build-output.toml` declares `keep_within = "2d"`, its `target/` holding about 160,000 entries over 4 profile directories (debug, release, a cross-target debug, llvm-cov-target), about 1,400 units with 2–8 builds each and half of them superseded beyond the 2-day window. It is generated as sparse files. The largest real slot on this host held 156,788 entries and 77.7 GiB on 2026-10-11.
- **Evidence:** A stat walk of that real slot (onetaskgraph slot 2) took 3.64 s warm on this host on 2026-10-11. Removing the superseded half is estimated at under ten times the walk. 60 s keeps a slot out of service for under a minute, against the 30-minute maintain timeout. The check reads one recorded JSON file, about 2 s with node start-up, estimated from the repository's existing budget scripts.
- **Command:** `node pool-prune-budget.mjs`
- **Registered in:** `crates/onevcs/tests/pool-workload/budgets.yaml` of `github.com/nickderobertis/onevcs`, an entry this task adds

**A publication check runs downstream, so no worker can run it and none is judged on it.**

**Never signal a process you did not identify by PID, and a PID you got from a pattern is
still a pattern kill.** Several managers share this host, and their dispatches, drivers,
publications and test servers run under the same few binary names — `just`, `node`,
`python`, `onepipeline-api` — so a kill by name knows nothing about *whose* work it
matched. The distinction is the tool rather than the pattern: `pgrep` and `ps` **read**,
and either spelling of them is fine, `pgrep -x` included; `pkill` **signals**, and it is
never the answer here, in any spelling. `-x` is the trap, because it reads as the careful
one — `pkill -f 'just gate'` at least needs a narrowing pattern, while `pkill -x just`
takes every `just` on the machine. Reading the table first and piping the pids into `kill`
is no way around it: that is the same pattern kill with more steps.

manager's dispatch had been live over an hour. One ran `pkill -TERM -x just`. The other
ran `ps -eo pid,args | grep 'onepipeline-api serve' | awk '{print $1}' | while read pid;
do kill "$pid"; done` — which obeys the letter of every paragraph below and does the same
damage, because `just dag-ui` and the e2e suites both spawn that server and a pytest run's

**The one process you may signal is one you started yourself, so capture its PID as you

    cmd & MYPID=$!
    kill "$MYPID"

Anything you did not start belongs to somebody. Read what it is, report what you found,
and leave it running.

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or
`publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

That has wedged four workers here, and then two more workers and the manager itself in one
night: seven instances of one defect. A crozier corpus audit waited in `until ! pgrep -f
'scripts/fetch-corpus.sh'` with no fetch running at all — the only two matches were its own
polling shell and the manager's diagnostic shell — and waited until it was interrupted. A
`check-plan-bar-conflict` dispatch waited on `! pgrep -f "llmlint-judge.sh"`, whose negation
could never become true, and was cancelled and killed; its replacement then reached for

signal attached, and is refused above. And the manager, an hour after instructing a worker

the evidence that matters most — a rule its own author reproduces an hour after issuing it
is a rule whose wording is the problem rather than its reader.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.

**To ask whether a process is running at all, match the executable, not the command line.**
`pgrep -x onepipeline` matches process *names* exactly — the binary, not its arguments — so
the shell doing the asking, whose own name is `bash`, cannot match it however the pattern
is spelled. Where the binary name is not distinctive enough to identify what you mean
(`just`, `node` and `python` run everything), read the process table instead and drop the
one self-match that form has:

    ps -eo pid,args | grep -v grep | grep 'lint-llm-diff'

Both of those are **reads**, which is what makes `-x` safe here and forbidden the moment
the tool signals. The replacement for the worker wedged above reached for `pkill -f "just
gate"`, `pkill -f "just check"` and `pkill -f "nx run"` while another manager's run was
live. Read to learn what is running, report what you found, and signal nothing you did not
start.

**One sentinel and one log per invocation, and look before you launch one.** That pair is a
shape rather than two literal paths. Several dispatches run on this host at once and they
share `/tmp`, so a second worker writing `/tmp/check.log` writes into the first one's — and
`until [ -f /tmp/check.exit ]` returns immediately on somebody else's exit file, reporting
their result as yours. Name both after the invocation (`/tmp/check.$$.log`, or the node
id), and, before starting it, check whether its sentinel path is already in use by another
invocation; if so, choose a different invocation-specific pair. This path-ownership check
does not prohibit concurrent checks or judged tiers. Three workers collided on shared names
today and not one of the three failures read as what it was: two

**One suppression policy, and this is the whole of it.** A site-scoped `ignore` directive
is permitted where the rule is genuinely misapplied at that site **and** the directive

Suppressions elsewhere in the tree are not yours to inventory: this repository carries several hundred standing directives, and

the change under review.

**`--no-verify` is not an acceptable response to a slow or inconvenient hook.** The hooks

**Commit a coherent working piece the moment it works.** A dirty worktree does not

**Draft a follow-up that can wait; never draft one that cannot.** Work you notice that
