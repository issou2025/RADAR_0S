--------------------------------------------------------------------------------
1. HEADLINE
--------------------------------------------------------------------------------
  a) The documented WiFi sequence does not work on fw 1.8, but a REORDERED one
     does: stage the file BEFORE APP&WIFIO. Then the AP really broadcasts, BLE
     survives, and WIFIS reaches 1 (READY). Full sequence in section 3.
  b) `wifi-discover` cannot succeed as written. While genuinely joined to the
     device AP, it finds nothing (section 4) — because the device serves files
     over a raw socket with a framed RANGE protocol, not HTTP (section 7).
  c) The Pocket AP gateway is 192.168.200.1, not 192.168.4.1.
  d) Two of the three CANDIDATE_HOSTS collide with a typical home LAN and
     produce confident false positives (section 8).

--------------------------------------------------------------------------------
2. WHAT THE DOCUMENTED SEQUENCE DOES (PROTOCOL.md order) — FAILS
--------------------------------------------------------------------------------
  >> APP&U&WIFI     -> (no response)
  >> APP&WIFI       -> MCU&WIFI&PKT01_<COLOR>_<mac-suffix>&<8 chars>
  >> APP&WIFIO      -> MCU&WIFIO
  >> APP&WIFIS      -> MCU&WIFIS&3        ("AP created, waiting for a client")
     ... device tears down the BLE link ~4s later ...

  * No SSID is ever broadcast. Verified from macOS AND from an Android phone
    (Android does not redact SSIDs; macOS 15 does, so the phone is the reliable
    witness). Reproduced 3/3.
  * wifi_wait_ready() therefore never observes status 1; it raises
    BleakError("Service Discovery has not been performed yet") mid-poll, and
    wifi_select_file()/wifi_begin_transfer() after it are unreachable.
  * `pocket-libre wifi-transfer` crashes in _stage() before printing its
    "Join this WiFi network now" panel.
  * WORSE: afterwards the device stops advertising on BLE entirely and only
    returns after a PHYSICAL POWER-CYCLE. APP&WIFIC cannot recover it because
    BLE is already gone. This deserves a README warning.

--------------------------------------------------------------------------------
3. THE SEQUENCE THAT WORKS ON FW 1.8  <<< KEY FINDING
--------------------------------------------------------------------------------
  Stage the file BEFORE raising the AP — the reverse of PROTOCOL.md, which
  stages at step 5 after the AP is up.

  >> APP&U&WIFI                        -> (no response)
  >> APP&WIFI                          -> MCU&WIFI&<ssid>&<8 chars>
  >> APP&U&2026-09-03&20260903145856   -> MCU&U&6653128        <-- STAGE FIRST
  >> APP&WIFIO                         -> MCU&WIFIO
                                          MCU&OFF   (see section 6)
     t+ 0.8s   MCU&WIFIS&3     AP created, waiting for a client
     t+ 8.0s   MCU&WIFIS&2     client connecting
     t+ 9.8s   MCU&WIFIS&1     READY FOR TRANSFER

  Results, reproduced 4/4:
    * The AP genuinely broadcasts and is joinable.
    * BLE SURVIVES — no disconnect, no power-cycle needed afterwards.
    * WIFIS reaches 1, the state upstream's code waits for and never sees.

  Timing note: the AP window is only seconds wide. The join must run
  CONCURRENTLY with the status polling. Raising the AP, polling for 30s, and
  only then joining always misses it.

  Joined-state details:
    client IP     192.168.200.2/24  (DHCP from the Pocket device)
    gateway       192.168.200.1     (= the Pocket; BSSID matches the device)
    security      WPA2-PSK, 2.4 GHz
    AP password   first 8 characters of the session key (confirmed)

5. EXHAUSTIVE NETWORK PROBE OF THE DEVICE, WHILE JOINED AND READY
--------------------------------------------------------------------------------
  TCP scan, ALL 65535 ports on 192.168.200.1
      open: [53]        <- ESP32 captive-portal DNS only
      Identical before and after APP&U&WIFI ("begin transfer").

  UDP probes (37 likely ports, unicast + broadcast, several payloads incl.
  "RANGE 0 4096", "RANGE\n", "APP&WIFI")
      no replies from 192.168.200.1.
      (Broadcast produced TFTP errors from 192.168.200.2 — that is this Mac's
      own tftpd answering its own broadcast, not the device.)

  mDNS / Bonjour browse (_services._dns-sd._udp, _http._tcp, _pocket._tcp)
      nothing advertised.

  ARP sweep of 192.168.200.0/24
      only .1 (the device) and .2 (this Mac). No third host.

  REVERSE DIRECTION TEST — does the device connect out to the client?
      Bound 19,996 TCP listeners + 3,999 UDP receivers on ports 1024-21024,
      then sent APP&U&WIFI (begin transfer) over BLE while joined.
      Nothing connected. Nothing arrived. (Ports <1024 need root and were
      not covered.)

  So: with the device in WIFIS=1 READY, nothing is listening for a file
  transfer, and the device initiates nothing.

--------------------------------------------------------------------------------
6. ANOMALIES WORTH A DEVELOPER'S EYE
--------------------------------------------------------------------------------
  * APP&U&WIFI returns NO response, ever — at the start of the sequence and
    again as PROTOCOL.md's step 6 "begin transfer". PROTOCOL.md documents
    MCU&U&WIFI followed by MCU&U&<size>. Neither arrives on fw 1.8.
  * MCU&OFF arrives spontaneously right after APP&WIFIO, and again after other
    commands. PROTOCOL.md defines MCU&OFF as the device signalling transfer
    completion. If it means the staged transfer is being torn down, that would
    explain why nothing ever listens. Re-staging after joining (APP&U&<date>&
    <ts> -> MCU&U&6653128 again, WIFIS still 1) did not change anything.
  * MCU&F size field is DURATION IN SECONDS, not kilobytes. The device reported
    25 for a file whose download is 101,996 bytes and whose ffprobe duration is
    25.499 s. `list` labels this column "Size (KB)" and derives "~Duration"
    from it as kilobytes, so both columns read ~4x low. Cross-check: staging
    the 1663-second recording returns MCU&U&6653128 bytes = 1663 s x 4000 B/s
    at 32 kbps.

--------------------------------------------------------------------------------
7. WHY HTTP PROBING CANNOT WORK — FROM THE VENDOR APP BINARY
--------------------------------------------------------------------------------
  Strings in libapp.so (Flutter/Dart) describe a socket transfer stack:

      PocketWifiFileTransferClient        PocketWifiFileTransferConnection
      PocketWifiFilePacketParser          PocketWifiTransferSession
      PocketWifiStreamMode                PocketWifiPrewarmOperation
      openingWifiSocket                   wifiSocketConnected
      PocketWifiSocketClosedException     PocketWifiInvalidFrameException
      PocketWifiTruncatedFrameException   PocketWifiChecksumException
      PocketWifiBufferOverflowException   PocketWifiReadinessTimeoutException

  The transfer verb is RANGE, not GET:

      "RANGE request bytes="
      "RANGE complete received="
      "RANGE cancel generation="

  Also: checklist_wifi_multiple_file_download_same_socket_title
        keepWifiSessionOpen, normalizePocketWifiSsid, PluginPocketWifiConnector

  The only device-local IP anywhere in the binary is 192.168.200.1. (Caveat: it
  sits near WiFi-firmware-update strings — WifiFirmwareUpdateService,
  pocket_wifi_1.4.2.bin — so it may be the OTA address; it is nonetheless the
  address the device hands out as gateway, confirmed by DHCP.)

  The socket PORT is a Dart integer constant and is not extractable from
  strings. It was not found by scanning either (section 5).

  Implication: discover_endpoint() probes HTTP path templates with urllib and
  tests for an MP3 magic number. Against a framed socket protocol that is not
  a near-miss — it is the wrong protocol, and no host/port/path list will fix it.

--------------------------------------------------------------------------------
8. BUG: CANDIDATE_HOSTS COLLIDE WITH A NORMAL HOME LAN
--------------------------------------------------------------------------------
  CANDIDATE_HOSTS = ["192.168.4.1", "192.168.1.1", "10.0.0.1"]

  192.168.1.1 and 10.0.0.1 are the default gateway on a large share of home
  networks. Running wifi-discover while NOT on the device AP probed my own
  router and reported:

      open 192.168.1.1:80
      200 http://192.168.1.1/ (664B)

  — the router's login page, nothing to do with the Pocket. A second run hit
  192.168.200.1 through the gateway in a double-NAT setup and got a 301.

  Suggested fix: require the local interface address to be inside the AP subnet
  before probing at all, and drop the colliding hosts from the default list.

9. UNDOCUMENTED BLE COMMANDS PRESENT IN THE APP
--------------------------------------------------------------------------------
  APP&WIFI&SWITCH   APP&WIFID     APP&WPING     APP&WOTA
  APP&OTA&WIFI&     APP&OTA&      APP&OT&OVER
  APP&BLE&OFF       APP&BLE&RESET APP&SHUT
  APP&D&            APP&LNP&      APP&LNS&      APP&USB&
  APP&PAU           APP&RESU      APP&STA       APP&STO

  Undocumented responses:
  MCU&DISK&ERR  MCU&FILE&NULL  MCU&D&ERR  MCU&DIRS_SUM&
  MCU&LOG&  MCU&LOG&ACK&  MCU&LOG&BATCH&  MCU&LOG&EMPTY  MCU&LOG&END&

  Tested on hardware (fw 1.8):
      >> APP&WPING        << MCU&WPING                  (real, distinct)
      >> APP&WIFI&SWITCH  << MCU&WIFI&<ssid>&<8 chars>  (same as APP&WIFI)
      >> APP&WIFID        << MCU&WIFI&<ssid>&<8 chars>  (same as APP&WIFI)

  So the fw 1.8 parser appears to PREFIX-MATCH on "WIFI": WIFI&SWITCH and
  WIFID are swallowed and answered as plain APP&WIFI. They may be meaningful on
  other firmware. None of these probes disturbed the device — APP&WIFIO is
  specifically what leaves it needing a power-cycle.

  Untested and potentially destructive: APP&BLE&OFF, APP&BLE&RESET, APP&SHUT.

--------------------------------------------------------------------------------
10. THE SESSION KEY IS THE ACCOUNT USER ID (AND IT IS LOGGED)
--------------------------------------------------------------------------------
  The app writes analytics to logcat containing distinct_id, a 28-character
  account/user ID. Verified against a key captured from an HCI trace:

      session key length      : 16
      distinct_id length      : 28
      distinct_id[:16] == key : True

  So the key is PER-ACCOUNT, not per-device as PROTOCOL.md describes, and it
  can be read from `adb logcat` with no HCI snoop log, no Full mode and no bug
  report — a far simpler recipe than the one in the README.

  Also a privacy note for users: that value, whose first 8 characters are the
  device's WiFi AP password, is written to the system log and transmitted to a
  third-party analytics endpoint on every event.

  (For anyone still capturing via HCI: a normal Android bug report is NOT
  sufficient. Its btsnooz_hci.log truncates every ACL packet to 15 bytes — 3
  bytes of ATT payload — so APP&/MCU& frames are unreadable. You need
  Developer options > "Bluetooth HCI snoop log" = Full, then a Bluetooth stack
  restart, which makes dumpstate include the untruncated btsnoop_hci.log.)

--------------------------------------------------------------------------------
11. SUGGESTED CHANGES
--------------------------------------------------------------------------------
  1. Reorder the WiFi sequence: stage the file BEFORE APP&WIFIO, and join
     concurrently with the status poll. This is what makes the AP appear and
     keeps BLE alive.
  2. Replace the HTTP client in wifi.py with a socket client speaking the
     framed RANGE protocol. download_file()/discover_endpoint() as written
     cannot work.
  3. Default host 192.168.200.1; drop 192.168.1.1 and 10.0.0.1, or gate
     probing on being on the AP subnet.
  4. Warn in the README that APP&WIFIO on fw 1.8 (documented order) can leave
     the device needing a physical power-cycle.
  5. Fix the `list` size/duration columns — the field is seconds, not KB.
  6. Replace the session-key capture instructions with the adb logcat method.

  Still unknown, and where the maintainer's knowledge would help most:
    * the socket port, and whether it ever opens on fw 1.8
    * the frame format (header, length, checksum) for RANGE
    * whether MCU&OFF after WIFIO means the staged transfer is being cancelled
    * what actually triggers the listener — nothing we sent did

  Happy to run further command sequences on fw 1.8 hardware on request.
