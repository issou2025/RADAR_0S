*Project description:*
# Rating v3 (Feedback) — implementation plan

**Status:** Approved concept → phased implementation plan

Concept and trade-offs: see the brainstorming comment and the two decisions comments below it.

Goal: replace the unused Rating v2 (templates, signed weights, 0–10 scores) with **Feedback**. It is a fixed, roughly 10-second debrief after a ride: one comparison against a previous setup, a few 5-step "just right" scales per component type with concrete symptoms, optional custom measurements, and notes. Setups are **ranked** from the comparisons. The scales show what is **still off**. On top of that come **test sessions** that guide back-to-back runs (bracketing), **rule-based suggestions**, and, in the last phases, **Strava starred-segment times** as objective data.

## Resolved open questions

- **A. Capture: a fixed debrief.** No user-built templates. Scales are 5 steps (−2 … +2, centred on "just right"). Each pole has **symptom chips**, stored as their own observations. **Notes** stay free text, with a helper text: not used for ranking or suggestions.
- **Scales are per component type** (`fork`, `shock`, `tire`), plus bike-level scales (`bike`). A component type gets scales only when it is installed on the bike at the feedback time. Multiple forks/shocks on one bike are not handled.
- **Tyre position from the installation tree:** a tyre on a `wheelFront` component → `tire.front`; on a `wheelRear` component → `tire.rear`; directly on the bike → shared `tire`. Position is the last key segment, so analysis can merge by prefix.
- **B. Ranking = Bradley-Terry over pairwise comparisons**, per bike. Shown as **"#2 of 7"** once enough comparisons exist, otherwise nothing.
- **B3 (internal only):** a "dialled-in" value computed from the scales, used by suggestions and analysis. The UI shows **"open issues" chips** (*"Shock: too soft"*) or a plain **"Dialled in"**. Never a number.
- **Comparisons:** the default reference is the **previous setup**. Any earlier setup can be chosen (in a session: any earlier run). A full comparison matrix is never required. A comparison stores only the **reference** setup + outcome (−2 … +2). The rated side is **the feedback's resolved setup**. Self-comparisons are ignored.
- **Setup linkage (unchanged from v2):** the stored `setupId` is write-once provenance. Display and ranking use the setup resolved from the timeline. A mismatch shows the drift warning with **Relink**.
- **C. Measurements:** a single custom field (an `Adjustment` definition + direction +1 / −1 / 0) **per bike**, with `archivedAt`. When created inside a test session: a switch **"Archive after session"** (default on) → nullable `Measurements.testSessionId`. Otherwise archived by hand.
- **D. Storage:** `Feedbacks`, `FeedbackObservations` (long table, semantic `key`, raw `value` / `textValue`), `FeedbackComparisons`, `Measurements`, `TestSessions` (with `proposals` JSON), nullable **`Setups.testSessionId`**, and in the last phases `StravaSegmentEfforts`. Keys: `scale.<type>[.<position>].<axis>`, `symptom.<type>[.<position>].<symptom>`, `custom:<measurementId>`.
- **No migration of v2 data.** `Ratings`, `RatingMetrics`, `RatingEntries` and `RatingEntryValues` are dropped with their data. Old backups that contain `ratings` / `ratingEntries` keys import without error (keys ignored).
- **E. UI name: "Feedback".**
- **F. Capture moments:** manual from a setup, and **every ride since the current setup** through a button on the existing Strava **import notification**. In-app CTA spots (activity tile, activity sheet card, SetupList header when no AppHint shows) are decided in Phase 9. Never a blocking dialog, and fast setup recording stays untouched.
- **Strava segments: starred only, last phases.** Efforts are **Strava-synced data**, deleted together with their activity and cleared on disconnect, like activities today. Per-setup times are derived at read time by resolving each effort's start time to the active setup, so added or removed activities recompute automatically. A feedback keeps a **soft** `stravaActivityId` that may dangle.
- **G. Test sessions:** a session groups runs (setups with `testSessionId`). Starting one creates run 1 as a copy of the current setup, stamped at start. **1 adjuster → bracketing; several → one change at a time.** Proposals are stored in `TestSessions.proposals`.
- **Manual lap times:** a session switch "Track lap times" creates a Duration measurement entered after each run. **Feel decides; lap time breaks ties** above a noise threshold. Strava efforts later appear **next to** the manual times, never merged.
- **H. Suggestions:** first a symptom/scale → adjuster + direction rule table, confirm-only and never applied automatically. Then a "Copy context for AI" export of setups + deltas + feedback + notes + weather.
- **Navigation:** the v2 "Ratings" tab and FAB are removed. Feedback lives in the setup timeline. "Start test session" goes in the SetupList menu and on bike details. A running session shows a banner.
- **Follow-ups (not in this plan):** method picker (bracketing / one at a time / Bayesian G4), "decide by lap time", blind mode, engine-suggested extra comparisons, cross-user pooling.

## Feature flag

Reuse **`AppSettings.enableRating`** (label "Feedback" on the FeaturesPage, wrapped in `kDebugMode` until release). It gates all Feedback, Measurement, Test session and Suggestion UI, the timeline layer, map/calendar items and the setup rank/open-issues display. Strava parts additionally require an active Strava connection. **Backend segment storage (Phase 14)** runs only for athletes whose app turned it on, via a flag on the Firestore user document written while `enableRating` is on.
