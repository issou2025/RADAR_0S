## Goal and boundary
Install Kinaiya as a normal signed Android app that connects to a configured Linux host. Installation/update/onboarding is the scope; working system-call integration, push, background audio and locked-screen calls require their own #11 acceptance evidence.

## Implementation plan
1. Inventory owner and companion Flutter entry points, native plugins and Android requirements. Decide package/flavor exposure, minimum OS, device ABI matrix and supported feature subset. Do not put owner/service credentials into the scoped companion app.
2. Set production signing identity, application IDs, versionCode/name and stable/nightly flavors. Recommend separate stable/nightly IDs and isolated local settings; test coexistence. Keep signing secrets out of the repo and ordinary CI logs.
3. Provide signed test APK installation for bounded demos if needed, clearly labelled as test distribution with source and digest verification; do not make manual APK replacement the unqualified public-store experience. For standard distribution prepare Play App Signing/AAB delivery, internal/closed testing for nightly and approved production for stable, subject to account/access/review prerequisites.
4. Add first-run host configuration and scoped secure pairing: authenticated HTTPS off-loopback, explicit host identity, expiring one-time grant, cancellation, wrong-host/error handling, revocation and re-pairing. Use platform-backed secure credential storage only after its threat model and explicit implementation are tested; current appearance persistence is not credential persistence.
5. Add connection diagnostics distinguishing offline, invalid certificate, auth/revocation and unsupported host protocol. No silent insecure HTTP fallback; any emulator/loopback exception stays explicitly developer-only. Never embed tokens in deep links/logs/analytics or share owner credentials as a shortcut.
6. Show version/channel/build and host compatibility. Delegate native app installation/update to Android's distribution mechanism. An in-app update notice may open the correct supported store/testing route; app code must not fetch Git and overwrite itself. Host release checks are separate and do not execute privileged host updates without owner authority.
7. Preserve appearance and supported user data across updates; define secure sign-out/unpair, device credential invalidation, supported migration/downgrade behavior and nightly-to-stable install path. Coexisting flavors must not silently share pairing grants.
8. Complete permission UX only for implemented features: request microphone/notifications at the point of use, explain denial/revocation and retain non-audio fallback where supported. Publish privacy/data safety, asset licenses, tester install/update/uninstall and host reachability guidance. Packaging must not claim native speech works when the current adapter is a stub.

## Acceptance / device evidence
- [ ] Signed artifact installs and upgrades with the intended signing identity through the documented route on actual claimed Android devices.
- [ ] Stable/nightly coexist or their switching limits are documented; increasing build versions and preserved local data are verified.
- [ ] First-run host setup/pairing, permission denial, TLS failure, offline/reconnect, expired/revoked grant, logout/unpair and incompatible host are tested against real host routes without granting companion owner privileges.
- [ ] Update notification opens the correct distribution route; failed/unavailable check is not 'up to date'; unsigned CI APK compilation alone is insufficient.
- [ ] Device/OS/build/host revision, exact exercised capabilities and unimplemented mobile media/background limits are included in evidence and release notes.


## Owner clarification: prioritize GitHub Releases APKs
Immediate delivery is signed APK files hosted on GitHub Releases for stable/nightly. Google Play Console app/identity exists, but Play publishing is not the focus now. Build distinct channel identities, show provenance and update availability, and hand installation/update to Android's user-confirmed package installer or verified download route. No silent self-replacement, no debug-signed APK described as a production-signed release, and no new signing identity silently substituted for an existing maintained identity. Signing configuration and physical-device qualification remain evidence requirements; the optional Play route must not block the GitHub APK code path.
