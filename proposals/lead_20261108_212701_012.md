# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**New installer: rm -rf of existing install dir without ownership check (data loss), dropped legacy guarantees**

*Project description:*
`install.sh` and `install.ps1` recursively delete whatever directory `--install-dir`, `ACQ_INSTALL_DIR` or `XDG_DATA_HOME/acq` resolves to, with no check that it is an acq install. This happened for real during this review: a test run that inherited `XDG_DATA_HOME` and omitted `--install-dir` wiped the reviewer's real `~/.local/share/acq`. That directory holds the Bash file-fallback secret store and the provider-input-validator runtime, so an upgrade from Bash deletes them. The rewrite also silently drops the legacy installer's guarantees (msb install and version policy, WHP check, Git Bash, `--method`/`--sha`) while the docs still describe them. The curl-pipe-sh path never asks for PATH consent, and the 'Python v1' installer leaves `acq` running Bash by default.

Reviewed at `11a94febca22` (fork `main` before mogul/agentic-coding-quickstart#105 merged). Severities are after adversarial verification; each item was attacked by a skeptic agent that tried to refute it with its own reproduction.

## Findings

### MEDIUM: install.sh runs rm -rf on any existing --install-dir/ACQ_INSTALL_DIR/XDG_DATA_HOME/acq with no ownership check, and the replace step is not atomic
`install.sh:391` · confirmed by skeptic

The publish step deletes whatever exists at INSTALL_DIR unconditionally, then mv's the staging tree into place. Nothing checks that the directory is a previous acq install: there is no marker file and no 'not an acq install, move it aside' refusal. `--install-dir ~` or a mistyped ACQ_INSTALL_DIR/XDG_DATA_HOME wipes user data. The default path ($XDG_DATA_HOME/acq) is also exactly the legacy installer's managed git CLONE_DIR, so upgrading silently destroys that clone and any local changes in it. The comment at :353 says 'publish atomically', but rm-then-mv is not atomic. staging lives under ${TMPDIR:-/tmp}, and when that is a different filesystem mv becomes copy+delete. A failure there (ENOSPC, unreadable file) leaves no install at all, and ~/.local/bin/acq is left dangling.

**Bash behaviour:** The legacy installer refused to touch an existing non-clone CLONE_DIR and updated an existing clone in place (fetch/checkout). It never ran rm -rf on it.

<details><summary>Reproduction</summary>

```text
Build any archive that passes the gates (acq, acq-python, py-acq/runtime/bin/python3, py-acq/src/acq_py/__init__.py, wheelhouse/), put SHA256SUMS and provenance.json beside it, then run install.sh --source DIR --install-dir <dir with user files>. Fix: refuse when the dir exists without an acq install marker, and stage next to the target (same filesystem) followed by rename-swap, removing the old tree only after the swap succeeds.
```

</details>

### MEDIUM: Installers recursively delete whatever directory --install-dir / -InstallDir names, with no check that it is an acq install
`install.sh:392` · confirmed by skeptic

install.sh runs `if [ -e "$INSTALL_DIR" ]; then rm -rf "$INSTALL_DIR"; fi` before `mv`, and install.ps1:195-197 does `Remove-Item -LiteralPath $InstallDir -Recurse -Force`. There is no marker or ownership check. `--install-dir ~`, `--install-dir .` from a project directory, `ACQ_INSTALL_DIR=$HOME/code`, or an XDG_DATA_HOME that resolves somewhere unexpected wipes that tree silently. The legacy installer refused a non-acq directory.

**Bash behaviour:** Legacy install.sh refused an existing non-acq directory.

### LOW: The documented 'curl | sh' interactive install never asks for PATH consent, because the /dev/tty fallback was dropped
`install.sh:219` · confirmed by skeptic

The header advertises `curl -fsSL <release>/install.sh | sh   # interactive (prompts for PATH)`. confirm() returns 'no' whenever stdin is not a TTY, and under curl|sh stdin is always the script pipe. So the main documented path never prompts: it always declines and prints manual instructions, even with a real terminal attached. The legacy installer read the answer from /dev/tty in exactly this case. This is safe as fail-closed behaviour, but the documented UX claim is false, and it is a regression from the legacy guarantee.

**Bash behaviour:** The legacy confirm() prompted on /dev/tty when stdin was a pipe, and declined only when /dev/tty was unusable.

<details><summary>Reproduction</summary>

```text
script -qec 'cat install.sh | sh -s -- --source <offline set> --install-dir /tmp/i --bin-dir /tmp/b' /dev/null and observe that no prompt appears.
```

</details>

### LOW: The 'Python v1' installer leaves acq running Bash by default, and its gates accept an archive without acq.backends, which breaks even ACQ_IMPL=python
`install.sh:383` · confirmed by skeptic

The installer describes itself as installing 'the acq v1 Python replacement' and links ~/.local/bin/acq to $INSTALL_DIR/acq. That file is the Bash dispatcher, and ACQ_IMPL defaults to bash (acq:757), so `acq` runs the Bash implementation. Bash `acq` sources acq.backends/common.sh at line 32, before the ACQ_IMPL switch at line 757. Yet neither the completeness gates (install.sh:383-387) nor installer/assets.json list acq.backends/. An archive built to the enumerated set therefore installs with rc=0, and then both `acq` and `ACQ_IMPL=python acq` fail; only `acq-python` works. Windows has the same problem: acq.cmd -> acq.ps1 defaults to Git Bash, but the new install.ps1 no longer installs or checks Git Bash, so a fresh host gets 'Git Bash was not found' from `acq version`. The unit test test_offline_install_succeeds never runs the installed launcher, so it cannot catch this.

**Bash behaviour:** The legacy installer installed the full repo tree (clone/npm/brew), so acq.backends was always present, and on Windows it installed Git Bash.

### LOW: The installer checks integrity only: SHA256SUMS comes from the same origin as the archive and nothing verifies authenticity
`install.sh:314` · confirmed by skeptic

SHA256SUMS, provenance.json and the archive are all fetched from the same $SOURCE. The archive is compared only against that co-located SHA256SUMS, so anyone who can serve or replace release assets (a compromised release token, an ACQ_INSTALL_SOURCE override, a mirror) can supply a matching pair. No hash is baked into the installer, no GitHub attestation is checked, no signature exists, and provenance.json is only tested for existence: it is not in the archive hash check, and its content is never parsed. --source accepts http:// and file://, and curl -fsSL follows redirects with no --proto =https / --tlsv1.2, so an https->http downgrade or a plaintext source goes through. The legacy installer had an independent anchor: release automation baked the release commit SHA (DEFAULT_RELEASE_SHA) into the attested install.sh, and it verified the clone HEAD against it. ADR-0042m says provenance …

**Bash behaviour:** The legacy clone path verified HEAD against a commit SHA baked into the attested installer asset, which is an anchor independent of the download origin.

### LOW: Installer 'never elevates' bats guard misses elevation wrapped in run() or done via doas
`test/bats/05-install.bats:96` · low, not skeptic-verified

The guard regex `^[[:space:]]*(sudo|pkexec|runas)[[:space:]]` only matches lines that start with sudo. install.sh runs privileged-looking work through `run CMD...` (lines 402-404), so `run sudo mkdir -p "$BIN_DIR"` or `run doas ln ...` would not be caught. The inventory names this guard (G19) as the evidence for ADR-0042m's no-elevation rule.

<details><summary>Reproduction</summary>

```text
sed 's|^run mkdir|run sudo mkdir|' install.sh > x.sh; grep -nE '^[[:space:]]*(sudo|pkexec|runas)[[:space:]]' x.sh; echo $?  # 1
```

</details>

### LOW: install.ps1 has weaker completeness gates than install.sh, and the embedded runtime's ._pth probably ignores the PYTHONPATH acq.ps1 relies on
`install.ps1:185` · low, not skeptic-verified

install.ps1 checks only acq.cmd and py-acq\runtime\python.exe. It does not fetch or check provenance.json and does not check py-acq\src\acq_py or the wheelhouse, which install.sh treats as fail-closed gates. That breaks ADR-0042m's per-platform enumerated set and the parity the comments claim. Separately, acq.ps1:37 imports acq_py by setting $env:PYTHONPATH. A python.org embeddable runtime ships a pythonXY._pth file, and when that file is present CPython ignores PYTHONPATH. release.yml:185 writes exactly such a ._pth for the validator runtime. A runtime packaged the same way would fail to import acq_py unless the ._pth lists ..\src.

<details><summary>Reproduction</summary>

```text
Live check on windows-x64: unpack the python.org embed zip as py-acq\runtime, then run `$env:ACQ_IMPL='python'; .\acq.cmd version`. Expect ModuleNotFoundError: acq_py unless the ._pth includes the src path.
```

</details>

### INFO: requires-python >=3.12 is not enforced by any launcher; the PATH fallback picks macOS's Xcode python3 (3.9) silently (works today, but nothing tests it)

pyproject declares requires-python >=3.12. acq-python, the acq ACQ_IMPL=python fallback and runtime.py fall back to the first python3 on PATH with no version check, and doctor reports that interpreter as 'pass'. On macOS without the bundled runtime (any git-clone user, and currently every user, since releases ship no runtime), that is /usr/bin/python3 3.9.x. I ran the full corpus on CPython 3.9.23 and all 159 vectors pass, and the bash 3.2 launcher path works, so this is not a live break for the user's macOS/bash-3.2 concern. The risk is drift: nothing in CI runs below 3.12, and msb._guest_path already uses ntpath.splitroot (3.12+) on the Windows path, so an older Windows interpreter would crash there.
