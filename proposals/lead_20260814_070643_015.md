## 4. The one real defect: `src/` is excluded from ruff

`aislop` reports `src/dependamerge/cli.py` as incorrectly formatted, while
`prek run` passes. Both are right — the pre-commit hooks never look at `src/`.

`.pre-commit-config.yaml` lines 55-62:

```yaml
- repo: https://github.com/astral-sh/ruff-pre-commit
  rev: 7c55798a78262d14b2074abf623d8a992ebb70d4  # frozen: v0.16.2
  hooks:
    - id: ruff
      files: ^(scripts|tests|custom_components)/.+\.py$
      args: [--fix, --exit-non-zero-on-fix]
    - id: ruff-format
      files: ^(scripts|tests|custom_components)/.+\.py$
```

Two problems:

1. **`src/` is not in the pattern.** All **37** Python files under `src/` —
   the entire shipped library — are excluded from both `ruff` linting and
   `ruff-format`. Only the 65 files under `scripts/` and `tests/` are checked.
2. **`custom_components/` does not exist** in this repository. It is a
   Home Assistant convention and appears to be a leftover from whatever
   template the config was seeded from.

Confirmed:

```console
$ ls -d scripts tests custom_components src
ls: cannot access 'custom_components': No such file or directory
scripts  src  tests

$ uv run ruff format --check src/
Would reformat: src/dependamerge/cli.py
1 file would be reformatted, 36 files already formatted
```

Only one file has actually drifted, so the blast radius today is small — but
the gap is systemic and silent, and it is why this reached `main`. The drift
itself is trivial:

```diff
-        console.print("Override SHA validated. Proceeding with non-automation PR merge.")
         console.print(
+            "Override SHA validated. Proceeding with non-automation PR merge."
+        )
```

**Suggested fix:** widen the pattern to include `src` and drop the
non-existent directory:

```yaml
files: ^(src|scripts|tests)/.+\.py$
```

Then run `uv run ruff format src/` once to clear the backlog. Worth doing as a
standalone PR, since it is small, mechanical, and independent of the
refactoring below.

## 6. Suggested approach

The formatting fix (§4) is small and should go first and separately.

The 51 complexity findings are real technical debt but are **not** a
mechanical fix, and attempting them in bulk would be high-risk against a merge
engine with 1,600 tests and considerable production subtlety. Suggested
sequencing:

1. **Fix the ruff scope** (§4). Independent, mechanical, unblocks consistent
   formatting going forward.
2. **Agree a policy for new code**, so the number stops growing: no new
   function over 80 lines, no new module over 400. Cheap to hold, and the
   scan already enforces it per-PR.
3. **Decompose opportunistically, along seams the work already suggests.**
   `merge_manager.py` at 6,769 lines is the dominant contributor and has
   natural fault lines that the performance work has been circling anyway:
   - the waiting/polling loops (`_wait_for_auto_merge`,
     `_trigger_stale_precommit_ci`, `_trigger_dependabot_recreate`,
     `_wait_for_recreated_pr_checks`) — these are precisely what the P1
     GraphQL batching work in `docs/BULK_RUN_PERFORMANCE_AUDIT.md` will
     rewrite, so extracting a polling module is close to free at that point;
   - failure classification and reporting (`_get_failure_summary`,
     `_predict_merge_outcome`, `_check_merge_requirements`);
   - conflict/rebase recovery (`_handle_merge_conflict` and the recreate path).
4. **Consider whether `src/dependamerge/engine/` should absorb some of this.**
   That package is currently unimported by `src/` (noted in
   `docs/BULK_RUN_PERFORMANCE_AUDIT.md` §2.8) and was designed as the
   decomposition target for exactly this orchestration code. Either wire it in
   or delete it, but leaving it as a phantom third option makes the
   refactoring conversation harder.
5. **Set a `.aislop/config.yml` gate** once the trend is downward, e.g.
   `ci.failBelow` at the then-current score, so the number ratchets in the
   right direction. `lfreleng-actions/aislop-scan-action` does this for itself
   at `failBelow: 100`.

Deliberately **not** suggesting a big-bang refactor: `merge_manager.py`
encodes a lot of hard-won GitHub API behaviour, and the audit already shows
how easily a plausible-looking change to that file goes wrong.
