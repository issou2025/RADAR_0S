# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**The shared CI meets its goal and principles**

*Project description:*
## Problem Statement

A maintainer of a repository that calls the shared CI expects a verdict that can be trusted and that arrives fast: 99% of runs within 3 minutes and half of the runs that select no tests within 1 minute, without work repeated for inputs that did not change. The shared CI misses that goal. A review of the shared CI against its goal and principles (#157, research record on the branch `research/157-ci-principles`) found, among others:

- The verdict can be green while a planned check was skipped, never started, or the plan output was missing.
- A merge onto a moved base narrows its selection without checking that the newer base passed.
- One shared digest covers every platform and the selection code, so a change to a Windows-only tool reruns every Linux suite, and every move of `v1` that changes a shared file reruns every suite in every consumer.
- Three jobs each decide part of the plan, each with a full clone; the merge of a tree that passed reruns every part outside the suite selection.
- Gitleaks scans the full history of every ref on every run, and the commit check starts processes for every commit, so hygiene grows with the repository.
- A title edit reruns code checks and can clear a failure.
- The push lookup and the shared lookup read their state from log lines; the shared lookup stops after 20 commits; neither counts a fallback.
- Only the full recording removes a stored read, and it never does so for an entry file run with pytest's quiet summary (#165); a Git revision argument is stored as an existence read.
- A merge followed by a failed dispatch leaves the default branch without a run.
- Nothing measures the goal.

## Solution

The existing shared CI is repaired so that it follows the goal and the principles in `docs/agents/ci.md` and ADR 0006 by its own design. The plan decides every check of a run before any check starts; the verdict stands for every gating check; selection sees every input, including tooling per platform and per tool; passed results are taken over from the same change or from the protected default branch through a structured record; stored lists are replaced by complete runs; hygiene works on what a run adds; superfluous jobs, routes and listeners go; and one scheduled measurement reports both targets for every repository. Consumers receive the repair with one `v1` promotion.

## Implementation Decisions

**Plan and verdict.** The plan holds the push lookup, the shared lookup, suite selection and the hygiene change detection, with one checkout; the light hygiene checks run inside it, and a check moves to its own job only where a measured duration would hold back the goal. The plan reads the lookup and turns off every part whose inputs the change cannot affect, including on a merge whose tree passed. The verdict compares each job's result with the plan and the selected unit count: a planned check that ends skipped, timed out or not started, or a missing plan, makes it red, and a check the plan did not select counts as not run. The verdict runs unless the run was cancelled, so a superseded run gives no verdict. Both fixed pipeline callers get a workflow-level concurrency group: one group per pull request for pull-request events, in which a newer push cancels the older run; a unique group for every push and dispatch run, which is never cancelled; and a run for an edited title or description that cancels no code run. A cancelled run's results are never stored or reused; a manual re-run reuses nothing and carries its attempt identity. Every job and every entry file gets a time limit from the plan. A dispatch run always passes its dispatch check, and hygiene runs only when the plan succeeded. The consumer checks of the fixed callers run as one check, with retries, only on events where they can change the verdict. The verdict lists per check what ran, was skipped or was taken over, and why.

**Inputs and digests.** The single shared digest is replaced by one digest per platform and one per tool or language step, without the selection code; a part's own shared code, its pins, its declared project, working directory and install files are inputs. A part without declared inputs runs on every change and the plan reports it as a departure with the reason "inputs unknown"; a `paths` pattern that matches no tracked file is reported. An unreadable digest or record counts as changed. Expressions selection cannot evaluate, Markdown-only changes in the Python tests route, `always` removal, ungated step files, estimate-only changes, `.pinned` files, top-level `env` and the language step on a moved digest are made inputs or select more.

**Reuse and records.** Passed default-branch runs store a structured record (passed unit keys, the tested tree and the digests) in a cache entry in the default branch's scope; pull requests restore it and never write it (ADR 0006). A record that is missing, evicted or unreadable counts as changed. The push lookup reads this record with no fixed walk limit, uses the digest the pull request was tested under on a merge onto a newer base, and takes over nothing the newer base can affect until a passed run on that base exists. Every fallback to running more emits a counted notice by reason. New suites and entry files are keyed under a key that is never looked up until they pass, units reused in an additions run are keyed again, and a unit's key covers only the module-lookup names it used, so a new name in a directory does not change the keys of other units.

**Recording and stored lists.** The stored lists stay in the tracked suite list. A run that recorded all reads of an entry on a platform replaces that entry's lists; any other run only adds. A pytest run proves completeness from its quiet and framed summaries; a skipped or deselected test makes the run incomplete. A revision-and-path argument of a Git process is never stored as an existence read; the Git process stays recorded as reading every tracked path. Pull-request runs trace link targets. Which `stat` variants pull-request runs trace is settled by one trace of a representative test on the pinned runner image, recorded with its question, method and result; the strace and ETW fixtures are recorded again on the pinned runner images with the repository's fixture recorders, so the recording tests rest on what the tracers emit there. Write opens are recorded and judged against the setup's grants; a write outside them is reported as a departure. The full-recording close fails visibly on a missing shard and opens no pull request; a partly recorded suite keeps its lists and is reported while complete suites are applied; an empty glob does not crash the close. The recorder's remaining defects are fixed: lookup reports that drop lines under thread contention, listings credited to the wrong thread, classification gaps and quadratic list operations in applying lists, and unchecked event data, missing status codes, process-id reuse and share-mode classification in the ETW consumer.

**Hygiene and publication checks.** Gitleaks scans the commits a run adds to a ref; a full scan runs when the Gitleaks configuration, the baseline or the pinned version changes; an identical tree does not skip the scan. The publication checks' commit check lints every message of the pull request in one process from one read of the history and fails when it cannot start. One failing install or step does not skip the other hygiene steps, and a failed lookup selects more, not nothing. The defects in the link check, the Dependabot coverage check, hygiene and the pin and specification updaters are fixed, and the updaters no longer repeat their queries in the write job.

**Jobs and time.** Shards are sized from durations measured and recorded in every run, longest first, with a bound that leaves room for the run's measured fixed cost within the goal; an entry without a measured duration gets its own shard until it has one. Windows is not sharded. A Python project installs once per run; tool and dependency installs use caches keyed by pin and lock hash. Automation jobs start only on runs they act on (conclusion and parity checks in job conditions, listeners only for relevant workflows). The test runner parts no longer hide a corrupt report behind another, accept an empty test script, reinstall a package manager unconditionally or allow unbounded setups; the suite jobs record nothing for an empty shard, upload Windows results after a setup failure and use the cache prefix; the language step does not crash on a malformed type-checker configuration.

**Default branch, promotion, release, sync.** Auto-merge requires `ci / verdict` by name; a merge whose default-branch run did not start is detected and its run dispatched again. The promotion consumes the completed verdict, fails visibly when it cannot get one, rechecks at the tag write, and states the digests a promotion moves. The release caller decides before cloning, binds the tag object and its name, and requires the passed verdict of the tagged commit. The sync works from one snapshot with fewer calls. The issue-title part reads only the file it needs, never overwrites a newer title and retries; the additions part reports a failed apply and checks the head on every route; the auto-merge part carries no paths of this repository and handles its disable and version-prefix cases.

**Shared Workflows' own CI.** This repository requires only `ci / verdict`; its standalone hygiene, Python tests and auto-merge callers are removed, with the title and description checks running on `edited` in the pipeline; fixture `paths` are narrowed. The legacy suite workflows are retired; a consumer that still calls one gets a dated transition with a named person responsible and a removal condition. The rebuild workflow leaves the shared automation workflow and runs from one route in this repository. The suite list no longer names a deleted workflow.

**Measurement.** One scheduled workflow in the management repository reads every consumer's runs and reports per repository, over a rolling four weeks of runs that reach a verdict with manual re-runs excluded: the share within 3 minutes from trigger to verdict, the median of runs whose plan selects no tests, fallbacks by reason, and the parts that run with unknown inputs; it opens an issue on a miss.

**Principle text and glossary.** The Reuse principle in the CI guide template and in this repository's guide reads: "one tested on an older base runs what the change and the newer base can each affect, and takes over nothing the newer base can affect until that base has passed." The glossary entries for Verdict, Full recording, Clean entry file, Stored lists, Shared digest, Push lookup and Plan change to the repaired behaviour, with any term the repair introduces.

## Testing Decisions

A good test exercises a shared part through the public command its workflow calls, with recorded fixtures for inputs that come from Git, GitHub or a tracer, and asserts the outcome (the plan, the verdict, the selected units, the stored lists, the scanned range, the report), never the wording of a file. The seams, each with what it catches and what it misses:

1. The plan command (configuration, change, lookup record, digests -> plan with reasons, fallbacks, departures, time limits). Catches Selection and Reuse for every part, unknown inputs and departures, title edits, identical and newer-base merges, per-check time limits. Misses whether GitHub runs the job conditions; seam 8 and the integration branch's own runs cover that.
2. The plan command's verdict (needs context and plan -> verdict), the single verdict once the suite selection's own verdict retires. Catches skipped, never-started and timed-out planned checks and a missing plan. Misses how GitHub fills the needs context, whose result values are documented.
3. The suite selection commands (lookup, select with sharding, store) with fixture repositories and a default-branch record, plus the recording digest command and the language step for per-tool and per-language-step digests. Catches ADR 0006, the newer-base rule, digests per platform, tool and language step, counted fallbacks, shards sized from measured durations with unmeasured entries alone, re-run attempt identity and no stored cancelled results. Misses GitHub's cache scoping, which GitHub documents (pull requests restore base-branch caches; their own caches are scoped to their merge ref).
4. The recording commands (exec, check, apply, full) with trace fixtures recorded on the pinned runner images. Catches list replacement after a complete run, pytest completeness, Git revision arguments, recorded writes outside the setup, per-entry time limits, durations recorded every run, keys for new units, the full-recording close.
5. The hygiene commands and the publication checks' commit check against fixture Git repositories. Catches the Gitleaks range and full-scan triggers, the one-process commit lint, decoupled steps.
6. The measurement command with recorded API responses. Catches both targets, fallbacks, parts with unknown inputs, an issue on a miss. Misses live API behaviour; the fields it reads are documented.
7. `promote_v1`, release, sync and automation through their existing commands and fixtures. Catches the completed verdict as precondition, visible failure, the digests a promotion moves, detection and re-dispatch of a missing default-branch run, automation jobs that start only with work. Misses a real tag move.
8. A workflow contract per fixed caller and shared workflow: structural assertions on the parsed workflow files, replacing text assertions. Catches the concurrency groups and their cancellation per event, `edited` in the pull-request triggers, the verdict's `needs` covering every job and its `!cancelled()` condition (so a superseded run gives no verdict), and the retired callers, routes and catalogue entries. Decisions live in the plan and automation command output, which conditions only compare; seams 1 and 7 test them.

Durations, cache gains and shard bounds are judged from the runs' own durations and the measurement; the `stat` question is settled by its trace.

Prior art: the suite-selection reuse tests and fixtures, the recording tests with the strace stand-in and recorded fixtures, the hygiene Gitleaks, changes and v1-promotion tests, the pipeline and consumer-kit fixtures, the sync fixtures, and the catalogue, shared-surface, ETW consumer, automation, publication commit and consumer-kit template tests.

At the pre-merge gate, the integration branch's normal pull-request runs on this repository, which calls its own parts by local path, and plan-only output for representative changes are the evidence; no runs are added only to prove the change.

## Delivery Strategy

**Delivery path:** dedicated-branch
**Publish boundary:** merge
**Required validation:** the commands and workflows under `## Testing instructions` in `AGENTS.md`, the entry files of the changed behaviour while building, Gitleaks before every push, a green CI run on every pull request, the plan-only evidence above, and after the merge to `main` the promotion preparation and the one-way-action question that `docs/agents/publication.md` requires.
**Reason:** every change touches the shared surface or this repository's own CI and reaches every consumer only when `v1` moves; CI on the pull request is the only gate, and the template and write classes change, so the promotion is a one-way action under `docs/agents/publication.md`.

## Out of Scope

- Test code in consumer repositories, such as slow entry files that repeat work; each consumer fixes its own tests.
- A consumer's own configuration, such as declaring the inputs of its parts; the repair reports parts with unknown inputs.
- Moving the stored lists out of the tracked suite list; the measurement shows whether runs still fail on additions alone.
- Pinning a commit in the fixed callers; tooling inputs are made visible through digests.
- Sharding the Windows job; it is split only when a measured duration holds back the goal.
- A merge queue; it is not available for repositories owned by a personal account.
- A merge route through the App for recovering a default-branch run.
- The agent tooling that assesses and sets up a repository's CI; it follows the repaired CI separately.
