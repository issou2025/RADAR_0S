# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Input validation and workout logging rules across every page**

*Project description:*
## Problem Statement

A user can enter almost anything almost anywhere in the app, and the app reacts differently each time.

Many fields have no upper limit on the server, and every text column in the database is unbounded. In the exercise card there is no client-side limit on Gewicht, Wiederholungen or RIR at all, so a negative weight only fails when the server rejects it. Several names (Zyklus, Trainingstag, the "save as Vorlage" name) can be any length. Some query parameters have no validation, and no path parameter is validated.

Feedback looks different on every screen. The registration page shows the browser's own validation popup, other screens use `Alert` boxes, inline text, toasts or native `alert()` and `confirm()` dialogs. The user can't predict what an error looks like, or sometimes why they are blocked at all.

The workout logging rules are also too loose. A set can be logged with fields missing. Sets can be logged out of order. RIR is shown on warm-up sets, where it means nothing. "Beenden" is enabled as soon as every Übung has one logged set, so a workout with unlogged sets can be saved. A forgotten workout keeps running indefinitely and distorts its own duration.

A second active Zyklus can't be saved, but a user can open the wizard from a past Zyklus and fill in every step before finding that out. The check also reads before it writes, so two simultaneous requests could both succeed.

Finally, there are gaps around sign-in: e-mail addresses are case-sensitive, so `Niko@x.com` and `niko@x.com` are different accounts, and login answers faster for an unknown address.

## Solution

Every input in the app follows one set of named rules, checked on the server and mirrored on the client, and the user gets feedback in exactly three consistent forms: a field error, a field warning, or a toast.

Text is stored as typed, apart from trimming. Values that break a rule are rejected, not silently altered. React and Prisma keep handling escaping on output, so no text is rewritten on the way in.

The active workout gets strict, explainable logging rules. A set needs all its fields, sets and Übungen are logged in order, warm-ups have no RIR, and a workout can only be finished once everything is logged or swiped away. If something blocks the user, a toast says exactly what.

A workout left running for 5 hours asks whether the user is still training. If nobody answers, a complete workout is saved and an incomplete one is discarded.

Only one active Zyklus can exist per user, enforced by the database, and the wizard won't open if one already exists.

## Implementation Decisions

### Principles

- **Sanitizing means validating on the way in and escaping on the way out.** Input isn't rewritten beyond trimming (and lowercasing e-mail). No HTML sink exists in the app, so DOMPurify isn't added. There are no file uploads, so no file validation is needed. All database access is parameterized through Prisma, and no user input reaches raw SQL.
- **The password stays in the login request body.** TLS protects it in transit, and hashing in the browser would make the hash the password. HSTS and forced HTTPS stay with Cloudflare, confirmed by the owner.
- **The server is the authority** and the client gives early feedback with the same limits. The one exception is the typed duration below.
- **Search terms are never restricted by character.** They are trimmed and capped at 100 characters.

### Field rules

- One rule module per side: backend DTOs use it through a small set of custom validators, and the frontend has a mirror. There is no shared package, because the frontend image contains only `apps/frontend`.
- Rules use stable constraint names, each with `de` and `en` entries under `ApiErrors.validation`, following ADR-0009. Client checks use the same keys, so the user sees the same text whichever side catches the error.
- Limit messages use the user's unit.
- Every text field shares one base rule: trimmed, control and zero-width characters rejected, length capped, non-empty where required.
- **Personenname rule:** starts with a Unicode letter, then letters, combining marks, spaces, apostrophes, periods and hyphens. Length 1-50.
- Number fields stay `type="number"` per ADR-0005, hardened by blocking `e`, `E`, `+` and `-`, ignoring wheel changes, and enforcing `min`, `max` and `step` from the rules. Nutrition keeps its text inputs and comma-tolerant parsing.

### Limits

| Field | Rule |
|---|---|
| E-Mail | Lowercased, max 254 |
| Passwort (register, change, login, current password) | 8-100 |
| Vorname, Nachname | Personenname rule, 1-50 |
| Geburtsdatum | Age 13-120, not in the future |
| Größe | 100-250 cm (whole inches for imperial users) |
| Körpergewicht | 30-400 kg, at most 1 decimal as typed |
| Gym, Übung, Vorlage, Zyklus and "save as Vorlage" names | 1-100 |
| Trainingstag name | 1-50 |
| Lebensmittel name and brand, Mahlzeit name | Up to 120 |
| Schnelleintrag name | Up to 120, so "save as Lebensmittel" can't fail |
| Abschnitt name, Portionsgröße label | Up to 60 |
| Search terms, everywhere | Up to 100, any characters |
| Satz weight | 0-1000 kg; 0 only for Bodyweight when logging |
| Wiederholungen | Whole number, 1-100 |
| RIR | Whole number, 0-10 |
| Rest | Non-negative whole number up to the column maximum; never a user-facing error |
| Tracked `totalDuration` | Non-negative whole number up to the column maximum; never a user-facing error |
| Typed workout duration | 1-480 minutes, client only |
| Date of a past workout | Not in the future, not before 2000-01-01 |
| Zyklus duration | 1-52, also enforced on Enter |
| Zyklus start date | Today (in the user's time zone) to 1 year ahead; on update, checked only if it changed |
| Verlauf custom range | Start on or before end |
| Lebensmittel kcal per 100 g/ml | 0-900, at most 1 decimal |
| Carbs, protein, fat per 100 g/ml | 0-100 each, sum at most 100 |
| Schnelleintrag | kcal 0-10000, macros 0-1000 g |
| EAN | 8, 12 or 13 digits with a valid check digit, same rule on both sides |
| Portionsgröße grams, diary grams and quantity | 0.1-5000 |
| Meal factor, portion multiplier | 0.5-20 |
| Tagesziele | kcal 500-10000, macros 1-1000 |
| Array sizes | Sets per Übung 20, Übungen per workout 30, Trainingstage per Zyklus 7, Portionsgrößen 10, gyms 10, Abschnitte 10 |

The 3-decimal limit on weight applies to the value as typed in the user's unit. It is client only. Storing a cap on kilograms would break the exact conversion ADR-0005 relies on (225 lb is 102.05828325 kg).

900 kcal is the physical ceiling: fat has 9 kcal per gram.

`OPEN_FOOD_FACTS` foods aren't affected, because only `USER` foods go through these rules.

### API surface

- One shared ID pipe validates every path parameter. It can't require a UUID, because seeded Übungen use `seed-…` IDs.
- Every query parameter gets a DTO. This covers the workouts date range and filters, the analytics PR endpoint, and the `mine` and `includeCustom` flags. Analytics `muscleGroup` and `equipment` are checked against their enums.
- The `description` field on the create-Übung DTO has no column behind it and is removed.
- Path parameters on the client are encoded consistently.
- `/auth/change-password` gets the same 5-per-minute limit as login. `/auth/refresh` gets 30 per minute.
- Login verifies against a dummy hash when the address is unknown. Registration may still reveal that an address is taken.

### Feedback

- Three kinds of feedback, each always shown the same way:
  - **Field error:** red border, red text under the field, `aria-invalid`, blocks saving, focus moves to the first invalid field on submit.
  - **Field warning:** amber border and hint under the field, doesn't block.
  - **Toast:** flow rules and server or network failures, through one wrapper with fixed durations per kind.
- `FieldError` and `FieldWarning` are added to the existing field primitives.
- Every `<form>` gets `noValidate`.
- All `alert()` and `confirm()` calls become `AlertDialog`.
- Server validation failures reach the form per field through `ApiError.fieldErrors`. If no field matches, including nested workout payloads, they fall back to a toast. The message hook must stop being the only path, because it joins all failures into one string.
- The default placeholder in the shared date picker moves into the message catalogue.
- Remaining native UI is accepted: the camera permission prompt, the "Leave site?" dialog in the meal editor, password-manager prompts, native date pickers and native selects.

### Logging rules

- To log a working set: Gewicht, Wiederholungen and RIR are all required. Unilateral Übungen need every per-side field. Wiederholungen are at least 1. Weight above 0 is required, except 0 is valid on Bodyweight Übungen.
- A warm-up set needs Gewicht and Wiederholungen, and RIR is hidden. The server rejects a non-null RIR (including per-side RIR) on a warm-up set.
- The server does not require RIR on a working set, because existing history contains working sets without one and editing resends the whole tree through `replaceTree`.
- Switching to warm-up clears RIR. Switching to working shows RIR empty as a field error, and on a logged set blocks finishing.
- RIR 3-10 on a working set shows the amber warning in every flow where sets are entered, including Vorlagen and Blueprints.
- Planned working sets in the plan editors require RIR. The behaviour that writes 0 when the field is cleared is removed.
- Set order (within an Übung) and Übung order (the card directly above, in current order) are enforced in the active workout only, in the UI, with toasts. There is no un-log action, so "logged sets form a block" holds without further rules. The Übung-order toast suggests dragging the Übung up.
- All log paths (tick, swipe, and auto-commit when tracking a past workout) share one guard. Auto-commit stops requiring a weight above 0, so 0 kg Bodyweight sets save.

### Workout completeness

- One pure completeness function takes the workout and its skip state, and returns either complete or the first problem. The "Beenden" action, the Übung-order lock, the finish toast, past-workout tracking and the 5-hour outcome all use it.
- A workout is complete when every planned set and every added set row is logged or swiped away, every logged working set has RIR, and at least one set is logged overall.
- An Übung with all sets swiped away counts as complete and is left out of the payload. An Übung with no planned sets and nothing logged is not complete.
- Skip state and added-set rows move out of the exercise card into `workout-context`, and skip state is persisted with the draft.
- "Beenden" looks enabled and, when incomplete, shows a toast naming the first problem and scrolls to it. The confirm dialog opens only for a complete workout.
- Tracking a past workout uses the same rule: empty rows show field errors and block saving until filled in or swiped away.

### 5-hour prompt

- Live workouts only. Timestamps decide, because the active workout exists only in localStorage until finished, and there is no service worker or push.
- The trigger is 5 hours since the workout started, including paused time. Pausing shifts the existing timer start, so this needs its own timestamp that pausing never touches.
- Checked on a timer while the app is open, and whenever it opens or returns to the foreground.
- Actions: "Weiter trainieren" (ask again after 1 hour), "Workout beenden" and "Verwerfen". The re-ask time is stored with the draft.
- The 5-minute countdown runs only while the app is on screen, and restarts at a full 5 minutes each time it returns. If the app stays closed, the draft waits.
- Outcome with no answer: if the completeness check passes, the workout is saved; otherwise it is discarded. A toast reports which, the next time the user sees the app. A discard can't be undone, which is accepted.
- An automatic save ends at the last logged set: `totalDuration` is measured to that moment and `localDate` is that set's date, so an old workout doesn't mark today as done (the rule in "Today's workout is the one whose weekday is today").
- An automatic save doesn't touch Blueprints or Vorlagen.
- If an automatic save fails, the draft stays.

### One active Zyklus

- The database gets a partial unique index on `WorkoutCycle(userId) WHERE status = 'ACTIVE'`, written as raw SQL in a migration. The service keeps its check, and a lost race maps `P2002` back to `ACTIVE_CYCLE_ALREADY_EXISTS`, the same pattern as the weekday index.
- The guard moves into the wizard route, covering every entry point. An existing active Zyklus redirects to the Zyklen page with a toast, and the client-side check on that page goes away.
- The "new Zyklus" button on a past Zyklus stays visible and relies on that guard.
- A Zyklus scheduled for the future has status `ACTIVE` and counts as active. This is unchanged behaviour.

### E-mail

- E-mail is trimmed and lowercased on register, login and profile update.
- A migration lowercases existing addresses. The read-only check reports case-insensitive duplicates first, and those need a manual decision.

### Data safety

- A read-only `check:input-rules` script, following `check:duplicate-weekdays`, reports every row that breaks a new server rule, including users with more than one active Zyklus and case-insensitive e-mail duplicates.
- A data migration corrects what is safe: RIR on warm-ups becomes null, e-mails are lowercased, names are trimmed.
- Anything else the script reports is fixed by hand before deploying. It must be run against the Raspberry Pi database before the migration.

### Bugs included

- The date shift when editing a past workout in UTC-negative time zones.
- The wizard's UTC default start date.
- Zyklus duration clamped only on blur.
- Weak EAN check in the Lebensmittel editor and on the server.

### Documentation

- `AGENTS.md` gets domain invariants for workout completeness, one active Zyklus, and tracked values having no user-facing limit.
- A new ADR records "only complete workouts are saved", including the accepted cost that an unanswered, incomplete workout is discarded.
- `CONTEXT.md` gets the new terms where needed.

## Testing Decisions

A good test checks behaviour through the highest available seam, not how the code is arranged. It sends a payload and checks the result, or renders a screen and checks what the user sees. It doesn't assert on internal state or which helper was called. Tests must survive a refactor that keeps behaviour the same.

| Seam | Covers | Prior art |
|---|---|---|
| The global `ValidationPipe` on real DTOs: send a payload, assert `{property, constraints}` | Limits, text rules, Personenname, IDs, query DTOs | `create-workout.dto.spec.ts`, `validation-pipe.spec.ts`, `analytics-filter.dto.spec.ts` |
| Service methods with Prisma mocked | Warm-up RIR, Zyklus start date, one active Zyklus including the lost race, e-mail lowercasing, login timing | `workout-cycles.service.spec.ts`, `auth.service.spec.ts` |
| Client field rules as pure functions, plus a test that reads the backend rules file as text and fails on a differing limit | Client checks and drift | `log-set-guards.test.ts`, the backend error-code test added in `7feb8de` |
| The workout completeness function (new) | "Beenden", the Übung-order lock, past-workout tracking, the 5-hour outcome | `workout-order.test.ts` |
| Exercise card and active workout screen rendered with Testing Library | Toasts, hidden RIR, red and amber states, swipe and tick sharing one guard | `exercise-card-unilateral-edit.test.tsx`, `weight-input.test.tsx` |
| `workout-context` with fake timers | 5-hour prompt, countdown restart, re-ask after 1 hour, skip state surviving a reload, auto-save date and duration | `workout-timer-flutter.test.tsx`, `workout-draft-storage.test.ts` |

Not covered automatically:

- **The partial unique index and the data migration** are verified by hand on a real database. Mocks only prove the `P2002` mapping. During that check, confirm Prisma 7's `migrate dev` leaves the partial index alone (see the known `Workout.updatedAt` drift).
- **`AlertDialog` replacements** have no new seam and are tested only where an existing test touches the flow.
- **Visual consistency** needs a manual pass across screens. The repo has no browser or end-to-end tests.

Every rule on both sides is tested at the boundary: the last valid value and the first invalid one.

## Out of Scope

- Supersets and circuit training.
- Assisted Übungen and negative weights.
- A planned state for Zyklen, so a follow-up can be prepared while one is running. This belongs in its own issue.
- Push notifications or a service worker for the 5-hour prompt.
- Keeping logged sets as a recoverable draft when a forgotten workout is discarded.
- An analytics filter for rest or duration outliers.
- Server enforcement of set order, Übung order or required RIR.
- A shared validation package.
- A shared calendar replacing native date pickers.
- Password complexity rules beyond the 8-100 length and the existing breach check.
- Changing the mechanism of localization (#176, closed). This spec only adds catalogue entries.

## Further Notes

- **Older workouts in Verlauf:** unchanged working sets with no RIR don't block saving. The required-field rules apply to sets the user changes. This keeps the promise that old workouts stay editable, and goes slightly beyond "same rules as the active workout". Confirm or adjust when implementing.
- **Skip state after reload:** by reading the code, swiped-away sets appear to come back after a page reload today. This wasn't tested.
- **Open browser tabs:** the draft is shared by tabs in one browser, so two tabs could both reach the 5-hour outcome. The implementation must make it run once.
- **Dependencies:** field rules and the feedback primitives come first. `check:input-rules` and the migration must land before the server rules and the partial index go live. The 5-hour prompt depends on workout completeness.

1. Field rules, drift test, `FieldError`/`FieldWarning`, toast wrapper, `noValidate`, stricter number inputs, per-field server errors.
2. Server rules: DTO limits, ID pipe, query DTOs, removal of `description`.
3. `check:input-rules` and the data migration.
4. Auth: e-mail lowercasing, password limits, rate limits, login timing.
