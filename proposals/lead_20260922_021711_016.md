## Problem

The GitHub PR reviewer begins a full technical review before deciding whether a change belongs in the repository or has the required product/architecture direction. Broad PRs can consume a long agent trajectory even when the correct first outcome is a maintainer scope decision.

OpenHands/OpenHands #16632 is a concrete example: it changes 240 files to add two built-in light themes, but its linked issue has no maintainer product decision. The reviewer spent more than 10 million accumulated prompt tokens auditing implementation details before surfacing the missing scope decision.

The existing maintainer handoff runs only after a positive technical verdict. Scope outcomes also need a deterministic human handoff without being treated as approval.

## Acceptance criteria

- The reviewer evaluates repository ownership and product/architecture scope before detailed code inspection or test execution.
- Repo-specific guidance can define out-of-scope **categories** and ownership boundaries; it does not maintain lists of individual PR numbers.
- The reviewer supports a concise, machine-recognizable “maintainer decision required” outcome distinct from approval and changes requested.
- That outcome does not approve the PR and does not auto-merge it.
- The completion handler deterministically selects and requests a configured maintainer using the existing code-aware/load-balanced handoff mechanism.
- The review explains one of: wrong repository, unresolved product/architecture decision, obsolete/duplicate/current-direction conflict, or another repo-defined scope reason.
- Wrong-repository results identify the likely owning repository when evidence is sufficient.
- Tests cover early termination and maintainer handoff without launching a second agent.
- Existing approval and changes-requested behavior remains unchanged.

## Validation

Demonstrate the behavior on a live Agent Canvas review where the PR is intentionally outside the configured repository scope or lacks a required product decision. The agent should stop before a full technical audit and the automation should request a maintainer.

## OpenHands AI triage
**The following comments and acceptance criteria were added by the OpenHands AI agent.**

### Triage
Bounded scope: extend the existing `skills/github-pr-reviewer` automation - the review prompt builder in `scripts/main.py`, the exact-head completion handler in `scripts/worker.py`, and the existing deterministic handoff in `scripts/maintainer_handoff.py` (`request_maintainer_review`). The third outcome reuses the established body-verdict convention (today `✅ APPROVED` / `🔄 CHANGES REQUESTED`, published as a native `event: COMMENT` review) rather than adding a new channel. The scope categories and ownership boundaries themselves are out of scope here; they belong to the repository review guide tracked in #641.

Non-goals: no lists of individual PR numbers, no change to the `APPROVED` / `CHANGES REQUESTED` paths, no auto-merge, no separate pre-review conversation, and no edits to the repository review guide (#641).

### Desired Behavior
A review of a PR that is owned by another repository, or whose product/architecture direction is unresolved, obsolete/duplicated, or contrary to the current direction, ends with a maintainer-decision outcome before detailed code inspection or test execution. The automation then requests one configured maintainer through the existing code-aware/load-balanced handoff, without approving or merging the PR.

### Acceptance Criteria
- [ ] Before inspecting changed files, diffs, or running tests, the review prompt places a repository-ownership and product/architecture scope gate ahead of the existing inspection and test steps; the gate consumes repo-defined scope categories and ownership boundaries, not lists of individual PR numbers.
- [ ] A scope-stopped review publishes exactly one native review with `event: COMMENT` whose body ends with a distinct, machine-recognizable maintainer-decision verdict that is not `✅ APPROVED` and not `🔄 CHANGES REQUESTED`.
- [ ] The completion handler in `scripts/worker.py` treats that verdict as neither approval nor changes-requested: it does not record the PR as approved, does not post an approval, and does not merge or enable auto-merge.
- [ ] On that outcome the handler deterministically selects one configured maintainer through the existing code-aware/load-balanced mechanism in `scripts/maintainer_handoff.py` and requests their review on the PR.
- [ ] The review body states which scope reason applies: wrong repository, unresolved product/architecture decision, obsolete/duplicate or current-direction conflict, or another repo-defined scope reason.
- [ ] A wrong-repository outcome names the likely owning repository when evidence is sufficient, and omits it when it is not.
- [ ] A scope-stopped review is recorded as handled so the same trigger is not reprocessed on the next poll, and its checkout/trigger label reaches the same terminal handling as an existing completed review.
- [ ] The maintainer-decision path introduces no new secret or permission: it reuses the existing token, and an unusable roster still produces the existing configuration-failure comment instead of silently proceeding.
- [ ] Automated tests cover early termination at the scope gate and the maintainer handoff, and assert that no second agent conversation is launched.
- [ ] Existing `✅ APPROVED` and `🔄 CHANGES REQUESTED` behavior is unchanged: approval still triggers the post-approval handoff and changes-requested still triggers no handoff.
- [ ] `skills/github-pr-reviewer/SKILL.md` and `README.md` document the scope gate and the maintainer-decision outcome (including that it neither approves nor merges), and the `automations/catalog/github-pr-reviewer/manifest.json` bundle version is bumped because the shipped files changed.
