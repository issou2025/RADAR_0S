## Objective

Qualify the same Project Anatomy stable identities and source-scoped claims across the first-wave professional purposes — architecture, economy/quantities, construction/DET, thermal/RE2020 preparation and ACV/carbon — without introducing métier-specific object identities, a universal current-value owner, a generic sufficiency engine or automatic professional conclusions.

H5.7 is primarily a read-projection/qualification slice. New persistent state is out of scope unless a concrete scenario proves that an existing owner cannot truthfully carry the required information.

## Repository truth verified before change

H5.1–H5.4 and H5.6 are merged. H5.6 now provides one multi-source reviewed identity path across document/PDF, IFC and Revit-shaped Observation Bundles.

The existing Project Anatomy knowledge structure already defines the first professional wave over the same APU identities:

```text
architecture and spatial design
project economy and quantities
construction-site review and DET support
thermal-data preparation and RE2020 consistency
life-cycle assessment and carbon analysis
```

It explicitly states:

```text
APU quantity != accepted DPGF quantity
quantity x unit price != approved budget
photo timestamp != work acceptance
site observation != as-built canonization
calculation input candidate != validated input
calculation success != compliance decision
product candidate matched != product specified
FDES referenced != FDES applicable
carbon result computed != ACV approved
```

The V0.2 model also freezes the rule that there is no universal stored `current_value`; purpose-specific lenses calculate projections. Future Proof qualifies sufficiency for a declared purpose rather than universal truth.

Separately, the existing professional-document lifecycle already owns purpose-specific *document currentness*. Its canonical projection uses purpose-specific resolution and refuses newest-wins. The executable MVP currently resolves only the purposes it can justify (`latest_received`, `current_working`, `current_for_coordination`) and returns consequential purposes such as contractual/execution/site currentness unresolved when no sufficient authority owner exists.

Therefore H5.7 must **reuse document currentness where document currentness is the question**, while keeping Project Anatomy purpose projection distinct from document revision authority. It must not invent a second generic currentness vocabulary.

## Required cross-purpose scenarios

Use a bounded shared project world rather than five independent fixtures.

1. **One opening, several purposes**
   - same stable object is used by architecture, economy, RE2020 and ACV;
   - PDF, IFC and Revit width claims conflict;
   - no global winner is stored;
   - each purpose exposes its exact basis/conflict without cloning identity.

2. **Quantity vs contractual quantity**
   - PDF/IFC observed count differs from DPGF value;
   - economy projection may expose both;
   - no payable/adopted quantity is inferred.

3. **Current document differs by purpose**
   - latest received revision C coexists with coordination-current B;
   - Project Anatomy claims from both remain provenance-preserving;
   - H5.7 reuses existing document-currentness output and does not make C universally current.

4. **DET installation posture**
   - equipment is observed installed;
   - attestation/test is missing;
   - projection must not collapse this into compliant/received.

5. **Thermal input incomplete**
   - geometry exists but one required thermal property is absent or conflicting;
   - no default is invented;
   - external calculation is not authorized or treated as compliant by the projection.

6. **ACV product ambiguity**
   - two possible product/FDES candidates exist with different applicability assumptions;
   - no automatic product adoption or FDES applicability conclusion.

7. **Purpose disagreement without truth conflict**
   - a source can be useful/current enough for coordination but not for contractual or thermal use;
   - purpose-specific posture must coexist without rewriting source history.

8. **Human correction**
   - a human-reviewed source-backed claim supersedes a machine candidate for one purpose;
   - previous claim remains historical; other purposes are not silently updated unless their basis actually changes.

9. **Group granularity**
   - a CCTP/DPGF statement applies to a group/class while Revit/IFC observations are item-level;
   - projection must not silently duplicate group assertions onto each stable object.

10. **Landscape/non-BIM identity**
    - one site object (e.g. drainage swale/retention/hedge) participates in design, quantity and carbon-related preparation without requiring BIM-only identity semantics.

## Projection semantics

Before adding a generic status vocabulary, H5.7 must try to express each purpose result through existing material:

- exact stable object refs;
- exact source representation / claim refs;
- requirements and governed cross-family refs;
- document currentness projection where relevant;
- conflicts / missing requirements disclosed as lists;
- limitations and provenance;
- explicit false authority.

Do **not** generalize the document-currentness `resolved | unresolved | conflicting` vocabulary into a universal Project Anatomy status merely for symmetry. If a common posture becomes demonstrably necessary, add a failing scenario first and justify the smallest responsibility-named contract.

H5.7 is complete when one shared Project Anatomy world can be projected for architecture, economy, DET, thermal/RE2020 preparation and ACV/carbon preparation while:

1. stable identities remain shared;
2. source and claim provenance remain exact;
3. contradictory values remain explicit rather than globally resolved;
4. purpose-specific document currentness is reused where applicable;
5. accepted/payable/contractual/compliant/received/approved semantics are not inferred;
6. missing purpose inputs remain explicit and are not synthesized;
7. group-vs-item granularity remains truthful;
8. external runtime/calculation success remains non-authoritative;
9. no persistent purpose owner or métier-specific object model is introduced without demonstrated need;
10. Next doctrine/contracts, MVP projection/tests and Cockpit semantics remain consistent.
