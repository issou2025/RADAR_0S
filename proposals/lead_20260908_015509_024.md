# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Apply bounded SnapOtter-inspired reliability improvements and evaluate OCR selection**

*Project description:*
## Problem and intended outcome

A source comparison with SnapOtter identified a small set of improvements to EVB Viewer's existing behavior. The clearest are accurate stress-test completion reporting and ownership of temporary files created by native PDF work. One existing zoom test can assert a stronger observable invariant. A further source trace found that oversized encrypted documents lose their specific native failure classification before the UI presents the error. OCR candidate selection merits a bounded experiment, with production adoption conditional on measured accuracy and resource results.

Keep the present product scope. This issue does not propose a file-processing suite, new editor architecture, new PDF engine, additional OCR engines or a general workflow system.

| Work item | Evidence today | Intended outcome | Estimated scope |
| --- | --- | --- | --- |
| A. Reject an all-skipped stress pass | Directly reproduced with the existing verdict function | A completed run with no executed scenarios is `incomplete`, exits unsuccessfully and cannot update a baseline | Small |
| B. Own native PDF temporary files at the operation level | Current creation, invocation and cleanup paths traced; hard-kill orphan not reproduced in this research | Confirmed dead operations leave no owned scratch; live operations and recoverable documents remain intact | Hard, Rust/Electron process lifetime and cross-platform verification |
| C. Assert cursor-point preservation in the preview zoom test | Existing test checks movement direction rather than exact anchoring | An incorrect translation magnitude fails the existing interaction scenario | Small, test only |
| D. Evaluate quality-selected OCR candidates | Source-backed opportunity; no EVB accuracy or performance gain measured | Adopt only if an independent corpus comparison shows a worthwhile gain within current resource limits, otherwise record rejection | Medium experiment, conditional production work |
| E. Explain encrypted-document admission failures | Native limit and error propagation traced; no new GUI reproduction claimed | A document above the encrypted-input limit receives a specific localized explanation without changing the safety limit | Medium, native-to-UI error contract |

The complete issue is labelled `hard` because native process ownership crosses Rust, Electron, recovery and operating-system behavior. That estimate includes implementation and verification of the full scope, not just the small reporting change.

## A. Require executed work for a successful stress verdict

### Existing behavior and reproduction

[resolveStressRunVerdict](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/stressReport.ts#L35-L51) counts scenario statuses, returns `incomplete` when the run is unfinished, and otherwise returns `passed` if no scenario failed or infrastructure-failed. It does not require any scenario to have executed successfully.

A nonempty selected workload can become all-skipped through [missing fixtures](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/runStress.ts#L247-L252) or [run deadline/cost-cap exhaustion](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/runStress.ts#L585-L602). The [final verdict, baseline gate and CLI return](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/runStress.ts#L613-L632) then treat the resulting `passed` value as successful evidence.

The following diagnostic invokes the actual exported function from a checkout with dependencies installed. It does not launch Electron or write a baseline:

```sh
pnpm exec tsx -e '
import { resolveStressRunVerdict } from "./scripts/stress/stressReport.ts";
const finishedAt = "2026-09-08T00:00:00.000Z";
for (const [name, scenarios] of [
  ["empty", []],
  ["all-skipped", [{status: "skipped"}]],
  ["passed-plus-skipped", [{status: "passed"}, {status: "skipped"}]],
  ["failed", [{status: "failed"}]],
]) {
  console.log(JSON.stringify({case: name, verdict: resolveStressRunVerdict({finishedAt, scenarios} as any)}));
}'
```

Observed output:

```json
{"case":"empty","verdict":"passed"}
{"case":"all-skipped","verdict":"passed"}
{"case":"passed-plus-skipped","verdict":"passed"}
{"case":"failed","verdict":"failed"}
```

The minimal diagnostic objects contain the fields this function reads. The empty-list result is only a function-level observation: [production selection rejects an empty scenario list](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/runStress.ts#L464-L465). The actionable case is a valid nonempty selection whose scenarios are all skipped. The CLI consequences above follow from its source; the complete CLI flow was not executed during the research.

### SnapOtter precedent

[GeneratedCaseAccounting](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/tests/helpers/generated-case-accounting.ts#L121-L164) verifies requested attempts and conservation across accepted, rejected and skipped cases. It requires meaningful coverage, with an explicit missing-host-binary exception. The [pairwise caller also requires an accepted result](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/tests/integration/generated/settings-pairwise.test.ts#L104-L126).

Borrow the accounting principle. Do not claim SnapOtter universally rejects all-skipped work, and do not import its full generated-test framework.

### Intended change

Extend the existing verdict function and report/CLI tests. A normal finished workload with no failures and no passed scenario must be `incomplete`. Failed and infrastructure-failed work must remain `failed`. A finished workload with passed scenarios and optional skips may remain `passed`.

Preserve [the documented optional-fixture policy](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/README.md#L102-L109), [the existing passed-plus-skipped test](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/tests/unit/scripts/stress/stressReport.test.ts#L134-L141), [calibration-only success](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/runStress.ts#L567-L576) and [dry-run behavior](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/stress/runStress.ts#L491-L505). Calibration-only and dry-run paths have different success criteria and bypass ordinary workload completion.

Keep each skip reason visible. A separate policy requiring every explicitly selected scenario to execute is outside this first fix.

### Acceptance

- [ ] A nonempty workload entirely skipped because fixtures are unavailable reports `incomplete`.
- [ ] A nonempty workload entirely skipped because the run budget is exhausted reports `incomplete`.
- [ ] Both cases produce a nonzero CLI exit and cannot update a baseline.
- [ ] Successful executed work plus an optional fixture skip remains `passed`.
- [ ] Actual failures plus skips remain `failed`; unfinished runs remain `incomplete`.
- [ ] Calibration-only success and dry-run success remain unchanged.
- [ ] Existing summary counts and skip explanations remain accurate.
- [ ] Regression coverage extends [stressReport.test.ts](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/tests/unit/scripts/stress/stressReport.test.ts) and [runStress.test.ts](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/tests/unit/scripts/stress/runStress.test.ts), with no real-app launch needed for the verdict logic.

## B. Bring native PDF scratch under operation ownership

### Existing behavior

EVB already has managed scratch scopes, ownership markers and stale cleanup in [managedScratchTemp.ts](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/utils/managedScratchTemp.ts#L106-L183). The gap is applying that mechanism to native-created artifacts:

| Current creator | Location and normal cleanup | Interruption gap |
| --- | --- | --- |
| [OverlaySourceTempDir](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/native/pdf-page-ops/src/text_layer.rs#L1248-L1277) | Creates `evb-overlay-text-*` under `std::env::temp_dir()` and removes its batch PDFs through Rust `Drop` | Forced termination cannot execute `Drop`; no matching overlay stale sweep was found |
| [TempQpdfFiles](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/native/pdf-page-ops/src/incremental_document.rs#L94-L147) | Places structural JSON and diagnostics under OS temp; removes them through `Drop` and a subsequent age-based sweep | The recovery sweep runs only on a later structural parse, rather than through the operation owner's lifecycle |

The structural parser has a [512 MiB JSON budget and ten-minute stale age](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/native/pdf-page-ops/src/incremental_document.rs#L11-L19). These are code limits, not measurements of abandoned disk consumption.

The [native mutation call](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/features/documents/main/nativePdfMutationSaveHandlers.ts#L326-L351) does not pass an operation-specific temp environment. [runNativeToolCommand](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/native-tools/runNativeToolCommand.ts#L185-L191) selects the binary directory as the default working directory and adjusts PATH. [runNativeCommand](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/native-tools/runNativeCommand.ts#L191-L211) merges caller environment and [passes it to spawn](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/native-tools/runNativeCommand.ts#L248-L269). Changing the working directory does not redirect Rust's explicit OS-temp allocation.

No application TMPDIR, TEMP or TMP override was found in the inspected Electron source. External launch environment could relocate OS temp, but it would not itself establish operation ownership. The [managed scratch sweep](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/utils/managedScratchTemp.ts#L143-L163) and [application namespace sweep](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/utils/appTempDir.ts#L267-L288) use recognized prefixes and ownership markers; neither currently owns these two native allocation paths.

### SnapOtter precedent and adaptation

SnapOtter's [route-scratch.ts](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/apps/api/src/lib/route-scratch.ts#L18-L41) assigns each operation one root with scoped cleanup. EVB already implements that abstraction, so extend it instead of importing a new helper.

Pass a parent-owned scratch root into relevant native PDF invocations and use it for structural qpdf files and overlay batches. Prefer an explicit scoped parameter or per-child environment over changing global process environment. Trace all production callsites that reach these creators, including scan-cleanup overlay work, before declaring coverage complete. Keep user-selected outputs and recoverable working copies outside ephemeral scratch.

Cleanup must wait for proven termination of the owned process tree. [The native runner distinguishes confirmed termination from an exhausted termination wait](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/native-tools/runNativeCommand.ts#L392-L435). If termination is uncertain, retain both the directory and sufficient process identity for later safe recovery. An unconditional `finally` deletion can race a live descendant and is not an acceptable implementation.

Preserve standalone CLI and browser/Wasm behavior. Do not make a desktop scratch-path convention a mandatory browser request field. If a native protocol change is necessary, define compatibility and validate it at the existing boundary. Retire superseded cleanup only when its callers have moved and its standalone behavior is covered.

### Acceptance

- [ ] Before changing behavior, reproduce baseline scratch lifetime using real structural-parse and overlay-text fixtures. Record the exact fixture identity, scratch locations, process identities and bytes.
- [ ] Normal completion and native error reclaim operation scratch after confirmed termination.
- [ ] Cancellation after scratch creation and forced native termination reclaim owned artifacts while preserving the source and working copy.
- [ ] An application crash followed by restart reclaims abandoned operation scratch through safe recovery.
- [ ] A still-running descendant prevents deletion; cleanup becomes eligible after its death is established.
- [ ] Concurrent operations and different application profiles cannot delete one another's files.
- [ ] Identity mismatch, ambiguous ownership and incomplete termination information retain files rather than risk live work.
- [ ] Original PDF hashes and intentional recoverable working copies remain unchanged by cleanup.
- [ ] Windows path, environment and process-tree behavior are verified, alongside the affected POSIX path.
- [ ] Existing native output validation, publication and save guarantees continue to pass.
- [ ] Extend the existing [managed scratch tests](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/tests/unit/electron/managedScratchTemp.test.ts), [process-tree tests](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/tests/unit/electron/utils/processTree.test.ts), relevant native tests and shared automation. Do not add a second cleanup framework.

The expected benefit is less abandoned disk use after interruption. Normal successful operations already remove their temporary files, so throughput or routine memory improvement is not an acceptance claim.

## C. Assert exact cursor-point preservation in the existing zoom test

### Evidence

SnapOtter's [pure preview zoom calculation](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/apps/web/src/hooks/zoom-pan-math.ts#L64-L81) has a [numerical test](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/tests/unit/web/zoom-pan-math.test.ts#L67-L89) that reconstructs the original content point and projects it through the new zoom and pan. Both resulting screen coordinates must equal the original cursor coordinates.

EVB already implements this behavior in [useScanCleanupPreviewZoom.ts](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/app/modules/scan-cleanup/composables/useScanCleanupPreviewZoom.ts#L103-L129), including surface offsets, overlay bounds, fitted-stage center and pan clamping. Its [current 150-DPI cursor zoom scenario](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/tests/unit/app/modules/scan-cleanup/scanCleanupComponents.test.ts#L3311-L3350) checks that scale increases and translation is negative. An incorrect correction magnitude could satisfy those assertions while moving the point under the cursor.

The [existing mounting helper](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/tests/unit/app/modules/scan-cleanup/scanCleanupComponents.test.ts#L891-L989) already supplies transform-aware rectangles. Reuse it. No current runtime cursor drift was established.

### Scope and acceptance

- [ ] Strengthen the existing component scenario to capture a content point before the wheel event and compare its projected screen position afterward.
- [ ] Test unclamped zoom in and zoom out with nonzero initial pan and an off-center cursor on both axes.
- [ ] Assert both coordinates with an explicitly justified small numerical tolerance.
- [ ] Keep the oracle independent of the production correction equation; duplicating the equation would risk duplicating the same defect.
- [ ] Treat clamp-bound cases separately. If bounds make exact anchoring impossible, assert the intended clamped result.
- [ ] Demonstrate a negative control: halving or otherwise corrupting the correction must fail even though its sign remains correct. Remove the injected fault afterward.
- [ ] Preserve existing actual-size, below-fit zoom, view-switch, pan-bound and overlay-coordinate scenarios.
- [ ] Add no production zoom module, gesture library, animation policy or new fixture framework.

If this exposes a production geometry defect, separately record its reproduction and verify any fix with a real pointer interaction. The present work item is a test-strengthening task.

## D. Run a bounded OCR candidate-selection experiment

### Existing EVB behavior and available machinery

When cleanup is requested, [the worker](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/ocr/worker/main.ts#L405-L457) accepts a successfully preprocessed image if its dimensions match, then runs one Tesseract pass. [Preprocessing failure](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/ocr/worker/tryPreprocessOcrImage.ts#L136-L168) or a geometry-size change falls back to the original. Recognition quality does not decide between raw and cleaned images.

[TSV parsing](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/ocr/worker/tesseractRunner.ts#L455-L490) reads confidence and filters low-confidence word geometry, then returns text and boxes without a candidate score. The runner already accepts [segmentation settings](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/ocr/worker/tesseractRunner.ts#L76-L89) and generates [TSV and a text-only PDF in one pass](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/ocr/worker/tesseractRunner.ts#L152-L169). [Page resource admission](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/ocr/ocrResourceGovernor.ts#L94-L124) already accounts for CPU, estimated resident bytes and a native process token.

### What SnapOtter actually demonstrates

- Its accurate Python runtime [recognizes the original and a separate contrast-adjusted candidate](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/ai/python/ocr_runtime.py#L1443-L1510), accepting the adjusted candidate only after a sufficient score gain. Failure retains the original. [Mock-based tests](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/ai/python/tests/test_ocr_runtime.py#L1101-L1148) cover acceptance, marginal-gain rejection and source preservation, not real-world superiority.
- Its Tesseract path uses [character-weighted confidence and high-confidence coverage](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/ai/src/tesseract.ts#L194-L252), [a minimum selection margin](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/ai/src/tesseract.ts#L282-L290), and [one monotonic deadline across candidate passes](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/ai/src/tesseract.ts#L317-L379).
- The fast PDF path is different: it [replaces the raster with enhanced pixels and deletes the original before recognition](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/ai/src/tesseract-pdf.ts#L589-L611). Do not attribute raw-versus-clean selection to every SnapOtter OCR route.

Confidence is not correctness. SnapOtter's [heuristics reflect Latin receipts and CJK material](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/ai/src/tesseract.ts#L77-L105). Those thresholds do not establish quality for EVB's Cyrillic, Greek or RTL documents. EVB's [language contract](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/packages/contracts/ocrLanguages.ts#L6-L19) and [OCR guidance](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/docs/ocr.md#L3-L10) remain authoritative.

### Experiment boundaries

Start offline through EVB's production OCR runner, using the current Tesseract engine and model policy. First compare raw versus current cleanup. Assess at most one alternate segmentation on weak pages as a separate experiment. Do not run a combinatorial candidate search or add recognition passes to every page by default.

Keep explicit user segmentation and language choices. Any candidate retry shares the existing page budget, cancellation signal and resource ownership. Keep selected transcript, word boxes and searchable PDF as one result; changing only UI text would make the saved artifact disagree with the chosen recognition.

A conditional implementation would need an internal score, unique candidate artifact names, losing-candidate cleanup and bounded selection under one deadline. Extend the worker, checkpoints and current quality runner. No new OCR package, engine, model family, public result schema or UI control is justified by this experiment.

### Corpus and measurement

EVB already computes character error rate, word error rate and critical-token checks for both [runner text and extracted PDF text](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/test-ocr-quality-corpus.mjs#L175-L207). Its focused [quality corpus](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/fixtures/ocr-quality-corpus.json#L1-L62) contains three synthetic English, Russian and mixed cases, with [deterministic one-font generation and degradation](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/test-ocr-quality-corpus.mjs#L51-L87). There is also an existing [OCR profile benchmark](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/scripts/devkit/ocr-profile-benchmark.py#L3-L7).

Extend those mechanisms with legally usable real scans. Freeze development and untouched holdout cohorts before tuning, including degraded and clear controls, mixed language, diacritics, numbers and geometry. Cover each affected script group. Pin input hashes, reference transcripts, critical tokens and provenance. SnapOtter's [frozen real-image manifest](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/tests/fixtures/ocr-real/manifest.json#L2-L13) and [provenance notice](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/tests/fixtures/ocr-real/NOTICE.md#L3-L27) are useful examples, but the inspected material does not establish an independently validated development/holdout benchmark there.

Proposed decision thresholds for this experiment, not existing product policy or measured gains:

- At least 10% lower aggregate character error rate on the degraded holdout cohort, with the aggregation method fixed before evaluation.
- No worse character or word error rate for any affected script cohort and no lost predefined critical token.
- Ordinary-page p95 latency within 5% of baseline, at most one additional recognition pass on selected pages, and unchanged resource ceilings.
- Clear-page output unchanged when no retry is warranted.

If baseline errors are near zero or the cohort is too small for a credible conclusion, report insufficient evidence instead of claiming a confidence-score win. Record exact tool/model versions, input hashes, sample counts, per-page results, page latency, peak RSS, scratch bytes and rejection cases. Changes to the proposed thresholds must be justified before looking at holdout results, not selected afterward to make the result pass.

### Acceptance and stop conditions

- [ ] Publish the experiment method, corpus provenance and frozen input identities.
- [ ] Compare the current baseline with raw/clean selection and separately with the bounded segmentation alternative.
- [ ] Evaluate actual transcript/PDF accuracy, not only confidence.
- [ ] Ensure selected text, copy/search results, boxes and independent PDF extraction agree.
- [ ] Preserve page pixels, annotation content and text-layer alignment. Equal image dimensions alone do not prove identical coordinates.
- [ ] Verify cancellation, deadline expiry, losing-artifact cleanup, resume and existing resource limits if a production candidate is implemented.
- [ ] Produce a written adopt/reject/insufficient-evidence decision with all limits disclosed.
- [ ] Adopt production behavior only if the declared criteria pass. Otherwise keep the current production pipeline and record the negative result.

A documented negative experiment is a valid disposition. This issue does not require shipping OCR behavior that fails to earn its added cost.

## E. Preserve the encrypted-document resource-limit outcome

### Existing behavior and user impact

The native reader sets a [512 MiB encoded-input ceiling](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/native/pdf-page-ops/src/load_policy.rs#L8-L15). When a larger input has an encryption entry, [decryption returns `too-large`](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/native/pdf-page-ops/src/decrypt.rs#L123-L140), before attempting the bounded whole-file load. This is a deliberate resource policy, not evidence that the limit itself is wrong.

The Electron caller [maps only password and unsupported-encryption failures](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/file-access/workingCopyDecryption.ts#L96-L106), invokes [the native decrypt command without a fallback](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/file-access/workingCopyDecryption.ts#L148-L175), and rethrows the resource-limit error. The [document-open handler](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/electron/features/documents/main/documentOpenHandlers.ts#L231-L238) wraps that error as an open failure. The [UI classifier](https://github.com/evb0110/evb-viewer/blob/efea01b3bd9b3399e8e8467c28f1dcfd4430b288/app/modules/workspace-shell/composables/document-session/classifyDocumentOpenError.ts#L6-L20) returns its message rather than a dedicated size-limit explanation.

The source-backed weakness is loss of actionable error classification. The expected user-facing outcome is a localized explanation such as "This encrypted PDF exceeds the current 512 MiB opening limit." It must not imply that the password is wrong or invite repeated password retries. This trace does not claim a fresh running-app reproduction.

### Intended change and boundaries

Carry this specific resource-limit outcome through the existing native, Electron and UI error contracts. Reuse the error boundary already responsible for password/encryption failures, and preserve the native error code for diagnostics. Cover ordinary file opening, password retry and batch-open result handling as applicable to the current call graph. Use the existing localization contract, including English and Russian.

Keep the 512 MiB ceiling, resource admission, source-file preservation and confidential password transport unchanged. Do not add qpdf fallback, another reader, a new dependency, automatic decryption retries or a higher byte limit as part of this item. Unencrypted path-backed documents above the ceiling are a distinct case and must not acquire an encrypted-file rejection.

SnapOtter's [qpdf decrypt wrapper](https://github.com/snapotter-hq/SnapOtter/blob/983a94ac1f8efc9c0a8f29f7f49f2236f1a41961/packages/doc-engine/src/pdf-ops.ts#L100-L108) accepts paths without this application-level input ceiling. That suggests a later experiment for very large encrypted books, not proof of bounded memory use or grounds to remove EVB's guard. Its argv password transport is also a reason to preserve EVB's current password-file design.

### Acceptance

- [ ] The encrypted-input `too-large` outcome retains its identity across the native-to-renderer boundary.
- [ ] A valid encrypted input above the admission limit produces a specific localized explanation, not generic open/password guidance.
- [ ] Regression coverage proves the native admission decision and the displayed outcome through existing integration mechanisms. Use a valid fixture with known size and provenance; a fabricated error alone does not prove the native path.
- [ ] Wrong-password and unsupported-encryption handling remain distinct and retain their current retry behavior.
- [ ] Unencrypted path-backed inputs above the ceiling retain their existing admission behavior.
- [ ] The failed operation preserves the source, cleans only owned scratch and produces no partial decrypted document.
- [ ] The byte ceiling and password-file transport remain unchanged, and no password reaches argv, logs or the displayed error.
