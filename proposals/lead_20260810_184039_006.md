# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Move the env file under an asset directory so .env can be gitignored again**

*Project description:*
## Context

#5 fixed the fresh-clone build by committing `.env` as an empty placeholder, because a declared-but-missing Flutter asset fails bundling before Dart runs. That works, but it leaves a residual risk which was called out in that PR rather than hidden:

**`.env` is now a tracked file.** A developer who fills in real Supabase keys is holding them in a tracked file in a public repository, one `git add -A` away from publishing them. `SETUP.md` requires `git update-index --skip-worktree .env` right after filling values, which defuses it — but nothing enforces that step, and a contributor who skips it gets no warning.

It also adds day-to-day friction: with `skip-worktree` set, `git checkout` across branches that touch `.env` aborts with "Your local changes would be overwritten", which is confusing for anyone who did not set the bit themselves.

## The durable fix

Flutter treats a declared asset **directory** differently from a declared file: the directory must exist, but individual files inside it are enumerated, so a missing one is not a build error. Moving the env file under such a directory lets the real file go back to being gitignored:

- `pubspec.yaml` declares `- assets/env/` instead of `- .env`
- `assets/env/env.example` is committed (so the directory always exists)
- developers create `assets/env/env`, which is gitignored
- `EnvConfig.load()` defaults to that path

Fresh clone: directory exists, no `env` file, `dotenv.load` throws, `EnvConfig` catches it and falls back to defaults — which is already its behaviour. Build succeeds. No tracked secret-bearing file anywhere.

## Acceptance criteria

1. `.env` is removed from `pubspec.yaml` assets and from the repository, and `.gitignore` ignores the developer's real env file again.
2. From a clean worktree with no developer env file present, `flutter pub get && flutter build web --debug` succeeds:
   ```bash
   git worktree add /tmp/grex-env-check HEAD
   cd /tmp/grex-env-check && flutter pub get && flutter build web --debug
   ```
3. In that same worktree, `flutter test test/core/config` passes.
4. With a populated env file at the new path, `flutter test test/core/config` **also** passes — no test may assert the contents of the developer-editable file. (This is the exact defect #5 hit; see `docs/verification/issue-5/README.md`.)
5. With a populated env file, `flutter build web --debug` succeeds and its values take effect, asserted by a precedence test.
6. All three deploy workflows (`deploy-web.yml`, `deploy-android.yml`, `deploy-ios.yml`) write their env file from GitHub Secrets to the **new** path. Each has a "Write .env from secrets" step that hardcodes `.env` today. `(human)` — these cannot be run from an agent session and need a maintainer to confirm a real deploy still picks up its secrets.
7. `scripts/windows/database/utils/rotate-api-keys.ps1` writes to the new path, or is updated to say where it writes.
8. `SETUP.md`, `.env.example` and the `pubspec.yaml` comment describe the new layout, and the `git update-index --skip-worktree` instruction is removed since it is no longer needed.
9. `flutter analyze` 0 issues; `dart format --set-exit-if-changed .` passes; `flutter test` green with no new `skip:`.

## Notes

Verify criterion 2 before writing any code — the whole approach rests on Flutter tolerating a missing file inside a declared asset directory. If that turns out to be false, close this issue and say so rather than working around it.

The deploy workflows are the risky part and are untestable from an agent session, which is why criterion 6 is marked `(human)`. Do not close this without that confirmation.

Does not change the F4 service-role-key exposure: anything in the env file is still bundled and served publicly on web.
