## Purpose

Shape a repository-governed operator toolkit that can run on the owner’s macOS environment when ChatGPT reaches a legitimate local-capability or owner-local evidence boundary.

The toolkit should reduce bespoke shell handoffs, improve evidence completeness and sanitisation, and let governed workflows resume from one stable, fail-closed command output without weakening repository authority or turning local utilities into an uncontrolled automation plane.

## Problem evidence

Recent governed work repeatedly required owner-local assistance for cases including:

- diagnosing `gh` authentication/capability before a guarded operation;
- reconstructing exact PR candidate identity, complete changed-file/review/check state and pagination-sensitive evidence;
- reading branch protection, required-check/App binding, rulesets and bypass actors completely;
- reading protected-environment variables, branch policy and secret-name presence without exposing secret values;
- running exact-head local validation/build/proof in a temporary checkout or worktree;
- reducing GitHub Actions failures to bounded, sanitised evidence rather than pasting full logs;
- producing complete external evidence that ChatGPT can consume directly and safely.

Ad hoc scripts have worked, but they repeatedly rediscover authentication, API representation, sanitisation, pagination, expected-state guards and evidence-format concerns.

## Shaping objective

Record one exact design contract for a small project-aware operator interface, then conduct a genuinely fresh substantive review before implementation.

The design must resolve at minimum:

- CLI and implementation shape;
- supported local platform and prerequisites;
- read-only versus mutating authority boundaries;
- GitHub REST/GraphQL/`gh`/local Git responsibilities;
- complete pagination and fail-closed evidence semantics;
- human-readable and machine-readable output contracts;
- secret/token/private-key redaction and allowlisting rules;
- temporary worktree lifecycle and cleanup;
- deterministic exit/status semantics;
- evidence versioning and safe paste-back to ChatGPT;
- initial command tranche and staged delivery order;
- validation, fixtures and negative-path testing;
- when, if ever, a later separately governed mutation surface may be introduced.

## Minimum-change preference

Prefer one repository-local command surface under `tools/operator/`, backed by Python with a minimal launcher and minimal dependencies. Reuse existing `git`, `gh`, repository validation and GitHub APIs rather than introducing a service, daemon, hosted control plane or new credential store.

The first implementation should be read-only and should prove the common evidence/redaction substrate before adding privileged repository-state inspection. Mutation must remain a later, separately designed and authorised capability.

## Explicit exclusions from shaping authority

This issue does **not** itself authorise:

- implementation or repository file changes;
- GitHub settings mutation;
- branch protection/ruleset/environment/App mutation;
- workflow dispatch, PR merge, deployment or publication;
- new long-lived credentials, token storage or secret material in Git;
- a generic cross-repository admin framework;
- weakening existing Promptbook, `AGENTS.md`, branch-protection, review or fresh-context boundaries;
- using local evidence as a substitute for authoritative GitHub state where authoritative state is available.
