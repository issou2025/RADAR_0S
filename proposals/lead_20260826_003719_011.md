# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Image.asset with a hand-written path breaks in release builds only**

*Project description:*
`Image.asset('assets/ui_panel.png')` — the obvious way to put game art in a
Flutter menu — works in development and throws at run time in release. Nothing
catches it.

## The chain, verified

1. `good build` in release packs every declared asset into chunks.
2. It then calls `_stripLoose` **unconditionally**
   (`commands/build/build_sub_command.dart:320`).
3. `stripLoose` deletes `File('${assetDir.path}/$relative')` —
   `assets/strip.dart:52`, `file.deleteSync()`. That is the **project's own
   asset directory**, not a staging copy.
4. Flutter then bundles nothing at that path, so `Image.asset` throws.

In development it works: `packAssets` returns an empty mapping and nothing is
stripped (`pack.dart:327-332`). So this is a clean *works on my machine, fails
in release*.

**Sharper still:** because the strip is against the source tree, a subsequent
**debug** run is also broken until `good assets compact` re-runs. #112 already
records the symptom from the developer's side — *"assets vanished from
assets/"* needed a troubleshooting entry — but not this consequence.

## Nothing detects it

`findMissingAssets()` walks `Textures.values`. An `Image.asset` path is a string
in widget code and appears in no generated enum, so the one check that could
notice never sees it.

## Why it matters more than it looks

There is no other way to draw game art in a Flutter widget today. #120 proposes
`SpriteWidget` and frames `Image.asset` as the *inconvenient* alternative that
"bypasses the asset pipeline". It is worse than inconvenient — it is
release-only-broken, silently.

So a developer building a menu does the obvious thing, sees it work all through
development, and finds out at release. That is the most expensive time to find
out.

## What to settle

- **Should the strip be against a staging copy rather than the source tree?**
  That would fix the debug-after-release half outright and is orthogonal to
  everything else here. #112 argues the whole class dissolves under #108's
  layout, where `assets/` is never declared — worth checking whether this
  dissolves with it.
- **Should anything detect a bundled-asset path that no longer resolves?** A
  build-time scan for `Image.asset(` / `AssetImage(` string literals is crude
  but would catch exactly this, and the CLI already parses project sources.
- **Or is the answer simply that `SpriteWidget` (#120) exists and the guide says
  to use it?** That is defensible, but it needs the guide to say so, and #120's
  own first slice does not cover a pre-`Game.start()` menu.

## Done when

Either a hand-written asset path keeps working in release, or something tells
the developer at build time that it will not.

The test has to be able to fail in the direction that matters: assert the file
is **absent from the release bundle** after `good build`, not merely that
packing produced chunks. A test that only checks the chunks exist passes today.
