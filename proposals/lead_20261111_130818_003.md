# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: LIBRAS Tier 1 - mobile app for Members and the Librarian desk**

*Project description:*
## Problem Statement

Members of the University of Makati library have no way to find a Book, see whether a Copy is available, or keep track of what they have borrowed without going to the desk. Librarians record Loans by hand. The LIBRAS project has requirements, designs, two benchmarked algorithms and a set of required security controls, but no working system: only the algorithm benchmark prototypes exist. The final demo and defense is on 2026-11-24, with a freeze on 2026-11-22.

## Solution

Tier 1 of LIBRAS: an Android mobile app for Members, plus the smallest Librarian-side capability needed to complete a Loan.

A Member signs up under one of five Account Types, verifies their email, and signs in. They search the catalog with typo tolerance, open a Book, and see how many Copies are available. To borrow, they tap Borrow, which shows their Digital ID; the Librarian scans the Digital ID and then the Copy at the desk, and the Loan appears in the Member's app. If no Copy is available, the Member places a Hold; when a Copy comes back, the next Hold is chosen by role-weighted priority, the Copy is set aside for a Pickup Window, and the Member is told by email and in the app.

The Librarian works on a desktop desk page. For the demo, the Librarian's phone pairs with the desk page and acts as the barcode scanner. A USB barcode scanner can replace the phone later without code changes.

## User Stories

### Sign-up and sign-in

1. As a prospective Member, I want to choose my Account Type (UMAK Student, Faculty, NTP / Employee, Visitor, Alumni) when I sign up, so that I get the sign-up form and privileges that fit me.
2. As a UMAK Student, I want to sign up with my `@umak.edu.ph` email and my student details, so that the library knows I am a current student.
3. As a Faculty member, I want to sign up with my `@umak.edu.ph` email and my faculty details, so that I get Faculty privileges.
4. As an NTP / Employee, I want to sign up with my `@umak.edu.ph` email and my employee details, so that I get NTP / Employee privileges.
5. As a Visitor, I want to sign up with any email address, so that I can use the catalog before visiting the library.
6. As an Alumni, I want to sign up with any email address, so that I can use the catalog as a graduate.
7. As a prospective Member choosing a UMAK Account Type, I want a clear error when my email is not an `@umak.edu.ph` address, so that I know why I cannot continue and how to fix it.
8. As a prospective Member, I want to see and accept the terms before my account is created, so that I know what I am agreeing to.
9. As a prospective Member, I want to receive a verification code by email and enter it in the app, so that my email is confirmed.
10. As a prospective Member, I want a clear error when I enter a wrong or expired verification code, so that I can try again.
11. As a prospective Member, I want to request a new verification code, so that I am not stuck if the first email never arrives.
12. As a new Member, I want my account to be active as soon as my email is verified, so that I can use the app without waiting for approval.
13. As a Member, I want to sign in with my email and password, so that I can reach my account.
14. As a Member, I want a clear error when my email or password is wrong, so that I can correct it, without the app revealing which of the two was wrong.
15. As a Member, I want sign-in to be temporarily blocked after repeated failures, so that nobody can guess my password.
16. As a Member, I want to stay signed in between app launches, so that I do not sign in every time.
17. As a Member, I want to sign out, so that nobody else can use my account on my phone.

### Home

18. As a Member, I want a home screen with a search bar, so that I can start looking for a Book immediately.
19. As a Member, I want the home screen to summarise my current Loans and Holds, so that I see what needs my attention.
20. As a Member, I want to reach my Digital ID from the home screen, so that I can show it at the desk quickly.

### Search and Books

21. As a Member, I want to search the catalog by title or author, so that I can find a Book.
22. As a Member, I want search to tolerate typos in title and author words, so that a misspelling still finds the Book.
23. As a Member, I want to search by ISBN, accession number or LC call number, so that I can find an exact Book or Copy.
24. As a Member, I want each search result to show how many Copies are available, so that I know whether I can borrow it now.
25. As a Member, I want a clear "no results" state, so that I can tell an empty result from a failure.
26. As a Member, I want search results within one second, so that searching feels immediate.
27. As a Member, I want to open a Book and see its details, so that I can confirm it is the one I want.
28. As a Member, I want the Book page to show the availability of its Copies, so that I know whether to go to the desk or place a Hold.
29. As a Visitor or Alumni, I want to search and view Books and availability, so that I can plan an on-site visit, even though I cannot borrow.

### Digital ID and Loans

30. As a Member who can borrow, I want a Borrow action on a Book with an available Copy, so that I know what to do next.
31. As a Member, I want the Borrow action to show my Digital ID with the instruction to show it to the Librarian, so that the Librarian can identify me.
32. As a Member, I want my Digital ID to be a 1D barcode with a short typed code beneath it, so that it can be scanned or typed in if scanning fails.
33. As a Member, I want my Digital ID to change every 60 seconds, so that a screenshot of it cannot be reused by someone else.
34. As a Member, I want the Digital ID to refresh by itself while I have it open, so that it is always valid when the Librarian scans it.
35. As a Member, I want to see a "Successfully Borrowed" confirmation once the Librarian confirms the Loan, so that I know the Book is on my account.
36. As a Member, I want a list of my current Loans with checkout dates and due dates, so that I know what to return and when.
37. As a Member, I want an overdue Loan to be clearly marked, so that I notice it.
38. As a Member, I want to see my past Loans, so that I have a history of what I borrowed.
39. As a Member, I want to see only my own Loans and Holds, so that my borrowing is private.
40. As a Visitor or Alumni, I want the app to tell me that my Account Type cannot borrow, so that I am not sent to the desk for nothing.

### Holds

41. As a Member who can borrow, I want to place a Hold on a Book that has no available Copy, so that I get a Copy when one is returned.
42. As a Member, I want to be prevented from placing a second Hold on the same Book, so that I do not hold two places in one queue.
43. As a Member, I want to see my Holds and their status (waiting, ready for pickup, expired), so that I know where I stand.
44. As a Member, I want to cancel a Hold, so that I leave the queue when I no longer need the Book.
45. As a Member, I want an email when my Hold is ready, so that I know to come to the library.
46. As a Member, I want to see when my Pickup Window ends, so that I collect the Copy in time.
47. As a Faculty member, I want my Hold to be weighted ahead of Holds placed up to 24 hours earlier by UMAK Students, so that teaching needs are served first.
48. As an NTP / Employee, I want my Hold to be weighted 12 hours ahead, so that staff needs rank between Faculty and UMAK Students.
49. As a Member with a waiting Hold, I want the next Hold to be chosen automatically when a Pickup Window passes unused, so that the Copy does not sit idle.
50. As a Member whose Hold is ready, I want the set-aside Copy to be loanable only to me during my Pickup Window, so that nobody else takes it.

### Librarian desk

51. As a Librarian, I want to sign in to a desk page on the desktop, so that only library staff can confirm Loans.
52. As a Librarian, I want to pair my phone with the desk page using a code, so that my phone works as the barcode scanner.
53. As a Librarian, I want every barcode my phone reads to appear on the desk page immediately, so that scanning feels like using a real scanner.
54. As a Librarian, I want the desk page to accept typed input ending in Enter, so that a USB barcode scanner or manual typing works too.
55. As a Librarian, I want to scan a Member's Digital ID and see who they are, their Account Type, and their current Loans against their limit, so that I know whether they may borrow.
56. As a Librarian, I want an expired or already-used Digital ID to be rejected with a clear message, so that I ask the Member to show a fresh one.
57. As a Librarian, I want to scan a Copy's barcode after the Digital ID and confirm the Loan, so that the Loan is recorded with its due date.
58. As a Librarian, I want the desk page to refuse a Loan that breaks the Loan Policy (limit reached, Account Type cannot borrow), with the reason shown, so that I can explain it to the Member.
59. As a Librarian, I want the desk page to refuse a Loan of a Copy that is already on Loan or set aside for another Member's Hold, so that records stay correct.
60. As a Librarian, I want to scan a Copy's barcode to record its return, so that the Copy becomes available again.
61. As a Librarian, I want to be told when a returned Copy is now set aside for a Hold, and for which Member, so that I put it on the hold shelf and not back on the stacks.
62. As a Librarian, I want to type an accession number when a barcode cannot be read, so that I am never blocked by a damaged label.
63. As a Librarian, I want clear feedback for an unreadable or unknown barcode, so that I know to rescan or type it.

### Security and operations

64. As a Member, I want my account data and borrowing records to be visible only to me and to library staff on duty, so that my privacy is protected.
65. As the library, I want every Loan, return, Hold dispatch and failed sign-in recorded in an audit log that cannot be edited or deleted, so that circulation can be reviewed and tampering is detectable.
66. As a Member or Librarian, I want error messages that explain what I can do next and never show internal details, so that failures are understandable and safe.
67. As the developer, I want one guided setup script for the Supabase project, the Render service and the email service, so that keys are created once and stored correctly.
68. As the developer, I want a seed script that creates a realistic catalog of Books and Copies, the Loan Policy for each Account Type, and Librarian accounts, so that the system is demo-ready without an admin module.
69. As the developer, I want secret scanning and static code scanning to run in CI, so that leaked keys and common vulnerabilities are caught before merge.

## Implementation Decisions

### Shape

- One repository with separate packages: the mobile app, the API, the Librarian web pages (desk page and phone scanner page), and a shared TypeScript package for types, validation schemas and the search module.
- Mobile app: React Native with TypeScript, built with Expo, targeting an Android APK (ADR 0002). The first ticket that touches the app must prove a real APK build.
- Backend: Supabase (PostgreSQL and Supabase Auth) and a Node.js, Express and TypeScript API hosted on Render (ADR 0003).
- The mobile app and the Librarian pages talk only to the API, never directly to the database. The API passes the signed-in person's identity through to PostgreSQL so that row-level security applies as a second layer behind the API's own checks.
- Vocabulary follows the glossary: Member, Account Type, Librarian, Book, Copy, Loan, Hold, Pickup Window, Digital ID, Loan Policy. Reservation is not a concept in LIBRAS.

### Accounts

- A Member has exactly one Account Type, fixed at sign-up: UMAK Student, Faculty, NTP / Employee, Visitor, Alumni.
- UMAK Student, Faculty and NTP / Employee require an `@umak.edu.ph` email. Visitor and Alumni accept any email.
- Sign-up collects the profile fields shown in the Figma onboarding flow for that Account Type, and requires accepting the terms.
- Email is verified by an emailed code. The account is active as soon as the code is accepted; there is no manual approval.
- Sign-in is email and password only. Sign-in failures are rate limited per client address.
- Staff (Librarian) are not Members. Librarian accounts are created by the seed script.

### Catalog and search

- A Book is a title and edition; a Copy is one physical item with an accession number and a 1D barcode. Availability is derived from Copies.
- Search runs in the API. Title and author words use the Bounded Levenshtein Trie Search in its flat typed-array form (ADR 0001), promoted from the benchmark prototype into the shared package. ISBN, accession number and LC call number match exactly.
- The trie is immutable: it is rebuilt and swapped atomically when the catalog changes. `pg_trgm` is not used for typo tolerance.
- Each result carries the count of available Copies.

### Digital ID

- The Digital ID is a short code, rendered as a 1D barcode with the same code printed beneath it for manual entry.
- It rotates every 60 seconds and is derived from a per-Member secret and the current time window, so the API can verify it without the phone sending anything. The API accepts the current window and the one before it, to tolerate the time it takes to scan.
- A Digital ID identifies a Member only. It does not carry a Book or Copy.
- The exact 1D symbology and code length are chosen so the code is readable from a phone screen by a phone camera and by common USB scanners; this is settled in the ticket that builds the Digital ID.

### Loans

- A Loan links one Member to one Copy, with a checkout time, a due date and a return time. A Loan is created only by a Librarian confirming it at the desk.
- The Borrow action in the app records nothing; it opens the Digital ID. The app learns that the Loan exists from the API and then shows the confirmation.
- Loan Policy is stored per Account Type: loan limit and loan period. Seeded placeholder: 3 Copies and 7 days for UMAK Student, Faculty and NTP / Employee; a limit of zero for Visitor and Alumni. The real UMAK policy replaces these as a data change.
- Confirming a Loan is refused when the Member is at their limit, the Account Type cannot borrow, the Copy is already on Loan, or the Copy is set aside for another Member's Hold. Each refusal returns a reason the desk page can show.
- A return closes the Loan, then triggers Hold dispatch for that Book.
- Overdue is derived from the due date; Tier 1 shows it but charges nothing.

### Holds

- A Member who can borrow may place a Hold on a Book only when it has no available Copy, and may have at most one active Hold per Book.
- Dispatch is the Role-Weighted Priority Queue Dispatcher from ADR 0001: one PostgreSQL query over an index on Book, score and sequence, where score is the arrival time minus the role weight (Faculty 24 hours, NTP / Employee 12 hours, UMAK Student 0). There is no in-memory copy of the queue.
- Hold states: waiting, ready (a Copy is set aside and the Pickup Window is running), fulfilled (the Member borrowed the Copy), expired (the Pickup Window passed), cancelled.
- When a Copy is returned and the Book has waiting Holds, the chosen Hold becomes ready and that Copy is set aside for its Member for the Pickup Window. The Pickup Window length is a stored setting, seeded as 24 hours.
- When a Pickup Window passes, the Hold expires and the next waiting Hold is dispatched for the same Copy; with none waiting, the Copy becomes available.
- A ready Hold triggers an email to the Member. The app shows Hold status and the end of the Pickup Window.

### Librarian pages and scanning

- The desk page is a desktop web page with three jobs: sign in, confirm a Loan (Digital ID, then Copy), and record a return (Copy).
- The desk page has one scan input point. Everything that produces a scan feeds it the same way:
  - keyboard input ending in Enter, which is how USB barcode scanners behave and also covers manual typing;
  - the paired phone scanner page.
- The phone scanner page is a web page opened in the phone's browser. The desk page shows a short pairing code; entering it on the phone links the two for that Librarian session. Each barcode the phone camera reads is delivered to the desk page in real time.
- Adding a physical scanner later needs no change to the desk page.

### Security controls in Tier 1

- Row-level security on Member-owned records: a Member reads only their own profile, Loans and Holds.
- Input validation with shared schemas on every endpoint, parameterized queries only, and a whitelist pattern on anything that arrives as a scan.
- Rate limiting on sign-in.
- An append-only audit log covering Loans, returns, Hold dispatches and failed sign-ins. Each entry stores a SHA-256 hash that chains to the previous entry, and the database refuses updates and deletes on it.
- Errors returned to clients carry a safe message and a code, never a stack trace.
- Secret scanning and static code scanning in CI.
- Transport security is provided by the hosting platforms.

### Setup and seed

- A guided setup script, written with the `/wizard` skill, walks the developer through creating the Supabase project, the Render service and the email-sending service, and stores the keys in the local environment file and GitHub secrets. This is the first task.
- A seed script creates a realistic sample catalog sized to the benchmark scale (about 50,000 search tokens), the Loan Policy rows, the Pickup Window setting and Librarian accounts.

### Screens

- Screens that exist in Figma are built from the mobile page of the design file, using the Figma screen inventory in the repo to find node IDs. Frames `iPhone 17 - 392` to `396` are never used.
- The Figma file defines almost no variables, so the app defines its own color, type and spacing tokens once, taken from the designs, and every screen uses them.
- Screens with no design (My Loans, Holds, the 1D Digital ID, the desk page and the scanner page) are built directly in code in the same visual style. The Figma "Show this to the librarian" screen shows a QR code; the built screen shows a 1D barcode instead.
- The Tier 1 home screen keeps the Figma home layout but shows only the search bar, the Loans and Holds summary and the Digital ID entry. The recommendation sections are left out.

## Testing Decisions

A good test checks behaviour that a Member, a Librarian or another system can observe, through the same interface they use. It does not check internal structure, so it survives refactoring.

- **The API over HTTP is the main seam.** Tests send real HTTP requests to the API running against a real local Supabase PostgreSQL. This covers sign-up rules per Account Type, sign-in rate limiting, search results, Loan confirmation and refusals, returns, Hold dispatch order, Pickup Window expiry, the audit log chain, and row-level security (one Member cannot read another's records).
- **Two things are swappable for determinism:** the clock (Digital ID rotation, due dates, Pickup Window) and the email sender (tests capture messages instead of sending them).
- **The search module keeps pure-function tests**, following the existing benchmark tests, which use Node's built-in test runner. Hold dispatch is tested through the API seam because it is a PostgreSQL query.
- **One end-to-end path per client:**
  - the mobile app on an Android emulator: sign up, search, open the Digital ID, and see a Loan appear after it is confirmed;
  - the Librarian pages in a browser: scans arrive as typed input ending in Enter, the same path a USB scanner uses, and through an injected scan standing in for the paired phone.
- **The phone camera is not automated.** Scans are injected at the scan input point in tests, and camera scanning gets a manual check on real devices.
- **Screens and components get no separate unit tests.** The end-to-end paths cover them, and each ticket checks its screens against the Figma designs.
- Each bug fix starts from a failing end-to-end or API test that reproduces it.

## Out of Scope

- The admin and Super Admin module, beyond the Librarian desk and scanner pages: dashboard, member management, reports, loan settings screens, clearance, inventory and accession.
- Reservations.
- The passwordless "Continue with UMAK email" sign-in.
- Tier 2, to be specified separately if time allows: renewals, fines and clearance status, forgot password, change password, overdue emails.
- Tier 3, to be specified separately after that: saved books, the in-app notification inbox, home recommendations, search history, settings, and the Visitor reading pass and session.
- Push notifications, iOS, and offline use.
- Encrypted backups with point-in-time recovery, MFA for Librarians, mTLS, the consent endpoint and crypto-shredding.
- Frames `iPhone 17 - 392` to `396` in the Figma file.
- Updating the IAS security spec and the milestone documents to match these decisions.
