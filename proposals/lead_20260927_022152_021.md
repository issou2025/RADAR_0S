*Project description:*
## What

Unblock printobserver's automatic release of the Windows and macOS work. Make generated clients survive a release version bump without manual edits, and have release automation enable automatic merging of its own release proposal after required checks pass.

## Why

“wait printobserver never got released your main work is not done.” The user wants Windows and macOS support for people who install printobserver. Work in the source tree has not reached them: the release proposal changes the version and fails the check that generated clients match their generator. Tests against registry packages deliberately run after release, so the blocked release also blocks that evidence.

## Architecture

The generator writes client source that stays identical across version bumps. Each client still reports the contract version—the version of the interface it describes. Rust takes that value when compiled. Python and Node read the checkout's version when used from source; package building writes the release version into their published copies. This commits packaging to preserving the version agreement while keeping installed clients independent of a checkout. Moving that boundary again would require coordinated changes to packaging and its tests.

The existing release automation, release-plz, drafts or refreshes a release pull request. It will also enable automatic merging for that specific proposal. GitHub merges it once required checks pass, and the resulting push to main publishes what is due. The existing rule that a release commit cannot itself propose another release prevents a loop.

There is no human release task: the repository's publication policy already automatically merges the implementation change, and the repaired release workflow completes the next handoff. Existing post-release jobs test registry packages, installation routes and clients. There is no post-release task in this plan: the manager reads those results and dispatches repairs if needed. This plan enables that evidence; it does not promise that unseen platform failures have already been repaired.

## Contracts

- The generator must reproduce every committed client exactly, including after a version bump. Clients retain their public version constant and report the version of the checkout or release they came from.
- Python and Node clients used from source refuse to load if the checkout's version cannot be read. Published packages carry the release version without looking for a checkout; packaging fails visibly if it cannot write that value.
- Release automation enables automatic merging only for its own release proposal and reports failure if it cannot. Required checks still decide whether it can merge. The worker changes the automation, without manually editing or merging the release proposal.
- Publication starts the existing registry proofs. Their results remain the manager's responsibility; post-release repairs, unrelated tickets and draft pull request #101 are outside this plan.

## Acceptance criteria

- A release version bump leaves generated source unchanged while source clients and built packages report the correct version. Regression evidence exposes the original failure, and existing protections against edited generated clients remain intact.
- The release proposal needs no manual client edits or human merge step. Tests demonstrate that automation enables merging only for that proposal, reports refusal, and cannot start a release loop.
- The affected client, packaging and workflow checks pass locally. Hosted release and platform results remain downstream evidence, not a claim implied by completing this change.
