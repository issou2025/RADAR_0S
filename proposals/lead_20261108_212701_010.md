# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Generator bumps stall until someone regenerates by hand**

*Project description:*
Dependabot can't run a code generator, so a generator bump that changes the output leaves the codegen freshness check red until someone commits the regenerated files by hand. `LahaLuhem/text_sight#115` (pigeon 29.0.8 to 29.1.0) sat open from 2026-10-28 to 2026-11-08 for exactly that. `LahaLuhem/text_sight#95` (copy_with_extension_gen) was the same shape.

The fix: CI owns the generated output. Generators stop being Dependabot's, and when the freshness check fails a dartender workflow regenerates and puts the diff where it was caused.

## The wider picture

The brief named pigeon and build_runner. The actual spread is four generators across two repos, and two of them have no freshness check at all:

| Repo | Folder | Generator | Constraint | Output tracked | Checked today |
|---|---|---|---|---|---|
| text_sight | `.` | pigeon | `29.1.0` exact | `lib/src/platform/messages.g.dart`, `lib/src/recognition/darwin_options.g.dart` | yes |
| text_sight | `.` | copy_with_extension_gen | `>=17.1.0 <19.0.0` | via build_runner | yes |
| text_sight | `example` | flutter_gen_runner | `5.15.0` exact | `example/lib/features/core/data/constants/assets/assets.gen.dart` | **no** |
| hive_box_manager | `.` | mockito | `^5.8.1` via build_runner | `test/support/mocks.mocks.dart` | **no** |

> [!IMPORTANT]
> **Neither repo commits a root `pubspec.lock`**, which is correct for a library. So a range or a caret resolves fresh on every run, and an unpinned generator can change its output with nothing in the repo having changed. The check then goes red on a PR about something else, and `git log` has no explanation.

None of the four generated files stamps a generator version (`// Autogenerated from Pigeon`, `// GENERATED CODE - DO NOT MODIFY BY HAND`, `///  FlutterGen`, `// Mocks generated by Mockito from annotations`), so a bump is usually a no-op. That is exactly why the rare one that isn't arrives as a surprise.

### Half the cause is already fixed, and that fix is load-bearing

text_sight's `9e72b7e` (2026-09-30) added `tool/pigeon.dart`, which sets `includeVersionInGeneratedWarning = false`: *"Without the version in the headers, a Pigeon bump that changes no code leaves no diff."* Before it, every pigeon bump dirtied the output.

It reaches that flag through `package:pigeon/src/generator_tools.dart`, a private path, which is the reason that pubspec already gives for the exact pin: *"no root lockfile, and tool/pigeon.dart uses Pigeon internals, so bumps get their own PR."* The symbol is still there in pigeon's current source, so the workaround holds for now.

Extracted hive_box_manager at `origin/master`, resolved, ran `build_runner build`, formatted at the project's width. > [!IMPORTANT]
> **No environment reproduces the committed file.** macOS with Flutter's bundled Dart, Docker with Dart 3.13.7 and Docker with 3.13.5 all produce the same output, one line off what is committed. That is the defect under the one in the title: a human is the regenerator, and a human's machine resolves differently from a fresh checkout. Local `dart pub get` reuses a gitignored lockfile indefinitely while CI resolves fresh every run, so the committed output records whichever the human happened to have.

## The design

**CI owns the generated output, and humans never commit it.** A developer's resolution provably differs from a fresh checkout's, so a hand regen keeps producing files CI disagrees with. Only the environment that is reproducible from a clean checkout writes these.

An **exact-pinned dev dependency is a generator, and the job owns it.** Dependabot gets an `ignore` entry for each, and the repair workflow bumps the same set with `flutter pub add dev:<pkg>:<latest>`, since `pub upgrade --tighten` leaves exact pins alone.

Source of truth splits in two:

| What | Where | Why |
|---|---|---|
| Which packages the job owns | **derived** from the pubspecs: any exact-pinned dev dependency | no list to drift. The same rule feeds Dependabot's `ignore` and the bump job |
| How to regenerate | **declared** in `.github/codegen.json`, per folder | can't be derived. Shaped like `lint-checks.json`, but with a folder per step, since text_sight regenerates root and example |

A separate file rather than another key in `lint-checks.json`, because those commands run inside the `linterpol` image while codegen needs Flutter and the repo's own pub dependencies on the runner.

## Pieces, in dartender

1. **`actions/codegen`** runs the steps from `.github/codegen.json` in each step's folder. One place that both the check and the bump job call.
2. **`ci.yml` gains a `codegen` job**, gated on `detect.sh` emitting `codegen=true`, running the action then `git add --intent-to-add .` and `git diff --exit-code`. text_sight's `plugin.yml` loses its copy and hive_box_manager gains the check for nothing.
3. **`.github/workflows/codegen.yml`**, a reusable workflow the failing check triggers, not a clock:
   - Failing on a PR: push the regen onto that PR's branch, so the diff is reviewed where it was caused.
   - Failing on the default branch: open a regen PR against it.
   - It bumps the exact-pinned generators first, so a bump and its output land in one commit.
   - The changelog App's token throughout. A `GITHUB_TOKEN` push starts no checks, so the PR would sit red forever.
4. **`scripts/setup/dependabot.sh`** writes an `ignore` entry for every exact-pinned dev dependency it finds.
5. **`scripts/detect.sh`** emits `codegen` next to `lint-checks`.
6. **The brick** gains a `codegen` caller.

Never push to the default branch directly, because the App bypasses the rulesets.

## Decisions

| | Decision | Why, and what it costs |
|---|---|---|
| **C1** | Pin `copy_with_extension_gen` and `mockito` exactly, in this change | They're the two generators Dependabot can still move on its own, so a bump arrives buried in a group PR about five other packages. The pin gives it its own PR. It does **not** make generation reproducible, see the callout above. `build_runner` stays on a caret, and a bump of it that changes output is drift like any other |
| **C2** | The `example` folder gets codegen steps too | flutter_gen_runner is already exact-pinned, so the job will bump it. Without a check there, the job bumps a generator whose output nothing verifies, which is worse than today. There's no `build.yaml`, so the step is `dart run build_runner build` in `example` |
| **C3** | The codegen check lives in dartender's `ci.yml`, not per repo | hive_box_manager gains a check it doesn't have, `detect.sh` gating is the existing pattern, and the check and the bump job then call the same action. Costs text_sight's `plugin-ok` dropping `codegen` from its `needs`, with `ci / ok` covering it instead. Both are required, so no gap |
| **C4** | The repair PR merges with the App token, not `github.token` | see below |
| **C5** | The repair is triggered by the check failing, not by a schedule | Drift is not time-based in any predictable way, and a weekly window means days of red for something a machine fixes in a minute. The check already runs on every default-branch push, so drift there is caught at the next one. Costs a `workflow_run` workflow, which can only be exercised from the default branch |
| **C6** | The check runs wherever output is committed, so all four generators | With C5 in place a red check means *this* PR changed the output, which is the signal worth having. Without one it would mean someone else's staleness, landing on whoever pushed next. Costs firing on cosmetic drift too, which is the price of not judging it per generator |

## Where this meets the cache work

**The bump PR must merge with the App token.** `ci.yml`'s auto-merge job runs `gh pr merge --auto` with `github.token`, and a `GITHUB_TOKEN` merge starts no workflow run. Leaning on it would land regenerated output on the default branch with no run behind it, and skip the cache re-save. Unlike a Dependabot run, a `schedule` or `workflow_dispatch` run can read repo secrets, so this workflow already holds the App token it needs. It is the one auto-merge path that can be fixed without the Dependabot-secrets plumbing.

**One `*[bot]` exemption covers both bots.** The cache work exempts any `*[bot]` author in the conventions gates, so this needs no edit of its own.

**Renovate can't do this instead.** `postUpgradeTasks` is gated by `allowedCommands`, which is `globalOnly: true` with `default: []`, so the hosted Mend app can't run post-upgrade commands. Folding codegen into Renovate means self-hosting it as a GitHub Action, which costs a workflow and a PAT or App token in every repo, puts Renovate on our Actions minutes, and couples two jobs with different cadences. Keeping them apart leaves the hosted app doing one line of `.fvmrc` config and dartender's own workflow doing codegen, which is how this repo already works.

## Suggested approach

Dartender first. Everything that touches a caller repo waits for one pass at the end, shared with #21's caller work, so each repo is opened once.

1. **`actions/codegen`** plus the `.github/codegen.json` shape, and `detect.sh` emitting `codegen`. No behaviour change yet.
2. **Move the check into `ci.yml`**, with `codegen` in `ok`'s `needs`.
3. **`dependabot.sh` writes the `ignore` entries**, with specs.
4. **`codegen.yml`** and its caller in the brick.
5. **Regenerate from CI**, not locally, in both repos, so the check has a baseline it can reproduce. Until that lands the check goes red on its first run for a reason nobody caused.
6. **The caller pass**, together with #21's: pin `copy_with_extension_gen` and `mockito`, write each repo's `.github/codegen.json`, drop text_sight's own `codegen` job so it never runs twice or not at all, and run `setup.sh`.

### How we'll know it worked

- [ ] A CI regen of hive_box_manager's mocks reproduces byte for byte on a second run, so the baseline is stable before the check is switched on.
- [ ] The check goes red on a deliberately stale generated file, in both repos, and green after the repair runs.
- [ ] A red check on a PR gets the regen pushed onto that PR's branch, and the push starts checks, so the App token is doing it.
- [ ] A red check on the default branch opens a regen PR against it.
- [ ] Dependabot stops opening PRs for the four generators.
- [ ] text_sight's example assets are covered, which they aren't today.

**Open before building:** whether pushing to a Dependabot branch stops Dependabot managing that PR. Generators leave Dependabot here, but `build_runner` and the transitives do not, so a Dependabot PR can still trip the check.
