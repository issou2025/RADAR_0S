- Type (maps to Conventional Commits): `type: bug`, `type: feature`, `type: docs`, `type: chore`, `type: refactor`, `type: test`, `type: ci`, `type: perf`

- Upstream: `upstream: pr-open`, `upstream: candidate`, `upstream: sync`, `fork-only`
- Agent: `agent: ok` (an agent may implement without asking), `agent: plan-only`
- Keep defaults: `duplicate`, `wontfix`, `invalid`, `question`, `good first issue`, `help wanted`. Retire `bug`, `enhancement`, `documentation` in favor of `type:` labels.

**Issue templates** (issue forms, YAML): `bug.yml`, `feature.yml`, `docs.yml`, `upstream-sync.yml`, `demo.yml`, `release.yml`, `config.yml` (keep the security contact link). Each form asks for: target branch, area, affected role, repro or scenario link, and whether it is upstream-bound.

**GitHub Project (v2)**: "MediaCMS fork roadmap", user-level, linked to the fork.

- Fields: Status (Inbox, Triage, Ready, In progress, In review, Upstream review, Blocked, Done), Workstream (WS0-WS6), Priority (P0-P3), Size (XS, S, M, L, XL), Target (beta, stable, upstream), Upstream PR (text), Start and Target dates.
- Views: Board by Status, Table by Workstream, Roadmap by Target date grouped by milestone, "Blocked" filter, "Needs Joshua" filter.
- Dependencies: parent/child with **sub-issues** (this issue -> WS epics -> tasks). Cross-stream order with native **Blocked by / Blocking** relationships. Only `blocked` label when the blocker is outside GitHub.
- Built-in workflows: auto-add fork issues and PRs, set Status=Done on close, set In review when a PR links.

**Triage flow**

1. New issue gets `triage: needs-triage` and Status=Inbox (template default).
2. Agent applies skill `issue-triage`: confirm it still applies on the target branch, add `type:` + `area:`, Priority, Size, Workstream, and a short plan (root cause, files, test plan).
3. Needs a decision -> `triage: needs-joshua`. Otherwise `triage: ready` (+ `agent: ok` if Joshua allows unattended work in that area).
4. Weekly: agent posts a digest of Inbox, Blocked, and Needs Joshua items.

**Branch and PR flow**

- Fork flow (D1): topic branch -> PR into `mediacms-next` -> PR `mediacms-next` into `main`. Title in Conventional Commits (checked by `semantic-pull-request`), `Closes #N`, pre-commit + `TESTING=True` pytest green.
- Upstream work: branch from **upstream** `mediacms-io/mediacms` `main` (not fork `main`, which no longer mirrors it), smallest possible change set, PR to `mediacms-io/mediacms`, track with an `upstream: pr-open` issue on the fork.
- Sync: when upstream `main` moves, one `upstream: sync` issue per event: merge upstream `main` into `mediacms-next` through a PR, then rebase or merge open upstream PR branches. Fork `main` picks it up on the next promotion.
- Never commit `deploy/docker/local_settings.py`. No force-push to shared branches without Joshua.

**Release process** (from skill `fork-docs-release`, no semantic-release)

- Beta: automatic on every push to `mediacms-next` (pre-release + `:beta`).
- Stable (D2): date-stamped tag `v10.0.0.YYYYMMDD[.N]` on `main`, no separate stable branch -> Release + `:stable`. One `release` issue per stable cut with a checklist: fork-whats-new Upgrade impact table, permissions-changes page, migrations note, docs channel, smoke on `:beta` first.
