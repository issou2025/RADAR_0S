# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Verify a gate sign-off landed, and decide whether GitHub labels or workflow_type is authoritative**

*Project description:*
Split out of #441, which is now scoped to the owner-name drift that #442 fixes. These two items are real but distinct, and each needs a decision rather than a mechanical correction.

## 1. Verify the sign-off landed

After a gate agent runs, nothing re-reads the entity to confirm `gate_status.<gate>` actually changed. A dispatch returning exit 0 is treated as evidence the gate signed.

`swarm_dispatch.py` already sets the precedent for exactly this, for a different mutation:

> A deterministic mutation with no judgement in it … is performed directly by the dispatcher and then VERIFIED by re-reading the entity, because an LLM turn asked to persist a mechanical mutation can silently no-op or partially apply (and did, three times, on ateles#241).

The owner-drift bug (#441) hid behind this gap: Waxwing ran, returned ok, wrote a real Security/Arch section, and the gate stayed `pending` for four days on #416 with nothing reporting a problem. #442 catches the *cause* of that particular instance; this catches the *symptom* regardless of cause — a gate that was supposed to sign and didn't.

**Proposed:** after any gate-owning agent run, re-read the issue entity and compare `gate_status.<gate>` against its pre-run value. If unchanged and the agent reported success, log a warning naming the issue, gate, and agent. Do not infer sign-off from an exit code.

**Acceptance:** a gate agent that returns ok without mutating `gate_status` produces a warning naming issue + gate + agent. Regression test asserting the mismatch is detected, not that the agent was called.

## 2. Decide label authority

`gate_status` initialization depends on which workflow applies, and two sources currently disagree.

On #430: the Neotoma entity recorded `workflow_type: "bug"` and `labels: ["bug"]`, while GitHub showed only `lanius-triage` — no `bug` label. Lanius correctly read GitHub at triage time and applied `ateles|feature`, so the entity's own `workflow_type` contradicted the gate set it carried.

This matters because the two workflows differ materially: `ateles|bug` declares **no arch gate at all** (pm → impl → pr_review → qa → release), while `ateles|feature` requires arch. So the same issue gets a different gate set depending on which source is believed.

Related: #416, #431, #414 were all bug reports carrying no `bug` label on GitHub, so all inherited an arch gate their nature did not call for. (Labels have since been applied by hand; that is a one-time correction, not a rule.)

**The decision:** is GitHub the source of truth for workflow selection, with the entity mirroring it — or is the entity authoritative once triaged, with labels advisory? Either is defensible; what is not defensible is the current state where they can disagree and nothing notices.

**Acceptance:** one source is documented as authoritative; a disagreement between them surfaces as a warning rather than silently selecting a gate set.

Related: #241 (mechanical mutations silently no-op), #442 (owner-name drift guard), #416, #430.
