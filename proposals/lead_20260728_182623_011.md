*Project description:*
## In plain terms

`polygres-wizard` already automates one part of setting up Polygres: installing the CLI/SDK and logging you in, so you don't do that by hand. `analyze` is the next automation layer this roadmap builds — it's meant to do the *database and retrieval-config* work a developer would otherwise do manually through the Polygres CLI and docs: looking at your schema, figuring out which tables need graph search (relationships), semantic/vector search, or keyword search, and turning that into real Polygres configuration — plus, eventually, the application code that uses it.

We haven't yet decided *how* the wizard should register "this project now depends on the Polygres SDK" in your project files — which manifest format, what version to pin, whether it needs its own confirmation screen. Nothing in the "write code" stage (I17/I18 above) can ship until this is actually decided.

---

## This is a design decision, not a build task

`docs/design/sdk-manifest-dependency.md` documents that `bin/wizard.cjs` installs `polygres-sdk` into whatever Python environment is active, but never records it as a dependency of the *target repo*. This is harmless today (nothing generates code that imports it), but becomes load-bearing the moment any Stage 8 variant ships — generated code that imports an untracked dependency works on the machine that ran the wizard and silently breaks for a teammate, a CI build, or a fresh clone.

**The design doc explicitly states this must close before any Stage 8 variant ships — not "nice to resolve eventually."**

## Open questions (5, none answered yet)

1. **Hook point** — extend Stage 0's `installSdk` to also write the manifest entry (if a target repo happens to already be known), or add it as a Stage 8 pre-check right before any variant generates SDK-importing code? The doc leans toward the latter as more correct (first point where "target repo" is unambiguous) but this isn't decided.
2. **Version pinning** — pin to the currently-installed `polygres-sdk` version, unpinned latest, or a range? Should probably match whatever convention the target repo's manifest already uses rather than imposing one.
3. **Poetry/lockfile consistency** — hand-editing `pyproject.toml` under `[tool.poetry.dependencies]` without running `poetry lock` leaves `poetry.lock` stale. Likely needs to shell out to `poetry add polygres-sdk` rather than editing TOML directly.
4. **Approval shape** — does a manifest edit need its own confirm step (consistent with "show target + reversibility before mutating," used everywhere else in this design), or is it low-stakes enough to bundle into Stage 6/8's general approval?
5. **Multi-manifest disambiguation** — a monorepo with multiple Python subprojects may have more than one manifest; which one is "the" target for code Stage 8 is about to generate? (Note: #27/I16 already handles *repo-root* disambiguation — this question is specifically about manifest-file disambiguation within a resolved root, which may or may not be the same problem.)

## What resolving this looks like

A decision recorded in `docs/design/sdk-manifest-dependency.md` for each of the 5 questions above (even "defer to a follow-up" is a valid recorded answer for a lower-priority one). Once recorded, this issue can be closed and #28 (I17) and #29 (I18) — currently blocked — can be scoped and started.
