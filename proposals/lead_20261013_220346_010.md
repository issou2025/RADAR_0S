*Project description:*
## Problem Statement

Kalé promises that people can record their finances on their phone, with or without a connection, and never lose them. Today that promise is broken in ways the user cannot see:

- Money entered while signed in can disappear from the phone: a routine background refresh replaces local data with the server copy, wiping entries that have not been backed up yet.
- Savings goals and contributions are never backed up at all. Their queued changes are silently skipped.
- Changes made while already online are not sent until the connection drops and comes back.
- After five failed attempts, a change is abandoned silently, and the user still believes it is backed up.
- Someone trying the app as a guest loses everything when they create an account, and their guest changes can never be backed up.
- Logging out erases changes that were not yet backed up, without warning.
- Amounts in different currencies are added together as if they were the same money, and amounts are stored as floating-point numbers.
- Deleted entries can come back after a restore.
- The backend schema and its access rules are not in the repository, so environments cannot be recreated or reviewed, and one server trigger would double-count savings once savings sync works.

## Solution

The phone becomes the trustworthy source of truth for a user's money, and the server becomes a reliable, invisible backup:

- Every change is saved on the phone immediately and backed up automatically: right after the change, when the app comes back to the foreground, when connectivity returns, or when the user taps retry.
- The user can always see whether their data is backed up. Changes that cannot be backed up are shown persistently with a retry action, never dropped.
- Restoring on a new or reinstalled phone, or pulling to refresh, merges server data without ever overwriting local changes that are not backed up yet, and deletions travel correctly in both directions.
- Everyone, including people trying the app without an account, has a real (anonymous) account from the first launch, so their data is backed up like everyone else's. Creating an account keeps everything they entered. If the sign-in they choose already belongs to an existing account, they are asked whether to add their guest data to it.
- Logging out never silently loses data.
- Each account has one base currency, chosen at onboarding, and amounts are stored exactly as whole minor units.
- The backend (schema, access rules, maintenance jobs) is defined in the repository and deployed identically to separate staging and production environments.

This spec covers Phase 0 (foundations) and Phase 1 (sync correctness) of the agreed decision record. The schema is reset rather than migrated, on the assumption that no external users have data today.

## User Stories

### Recording and backing up

1. As a user, I want every transaction I enter to be saved instantly, even offline, so that I never wait on the network to record my spending.
2. As a user, I want a change I make while online to be backed up within a few seconds, so that my backup is never stale while I'm connected.
3. As a user, I want my pending changes to be backed up automatically when my connection returns, so that I don't have to remember to do anything.
4. As a user, I want my pending changes to be backed up when I reopen the app, so that changes from an earlier session aren't left behind.
5. As a user making several quick edits, I want them backed up together after a short pause, so that the app doesn't waste my mobile data on every keystroke.
6. As a user, I want to see at a glance whether all my data is backed up, so that I can trust the app with my money.
7. As a user, I want to see how many changes are not yet backed up, so that I know how much is at risk.
8. As a user whose change repeatedly fails to back up, I want it shown as "not backed up" with a retry button, so that it's never silently abandoned.
9. As a user, I want a temporary outage not to permanently strand my changes, so that a bad network day doesn't cost me data.
10. As a user, I want to manually retry backing up stuck changes, so that I'm in control when something goes wrong.
11. As a user, I want my savings goals backed up, so that I don't lose them when I change phones.
12. As a user, I want each contribution I add to a savings goal backed up, so that my savings history survives a reinstall.
13. As a user, I want a goal's saved amount to stay correct after backup and restore, so that my progress is never doubled or lost.
14. As a user, I want my budgets backed up, so that my plans survive a reinstall.

### Restore and refresh

15. As a user installing Kalé on a new phone, I want to sign in and get all my data back, so that changing phones is painless.
16. As a user with a long history, I want restore to show progress and load my data in pages, so that it works on a slow connection and a low-end phone.
17. As a user, I want pull-to-refresh to bring in changes from my backup without touching my unsaved changes, so that refreshing is always safe.
18. As a user, I want a newer version of an entry to win over an older one when merging, so that I always see my latest edit.
19. As a user, I want reading my data never to trigger an overwrite from the server, so that simply opening a screen can't lose my changes.

### Deleting

20. As a user, I want an entry I deleted offline to stay deleted after I refresh, so that deleted spending doesn't reappear.
21. As a user restoring on a new phone, I want entries I deleted before to stay deleted, so that my restored history matches what I left.
22. As a user signed in on two phones, I want a deletion on one to reach the other on refresh, so that both show the same data.
23. As a user, I want deleted entries to disappear from every list, total, and chart immediately, so that my numbers are right.

### Guest (anonymous) use

24. As a new user, I want to start using Kalé without creating an account, so that I can try it before committing.
25. As a guest, I want my entries backed up just like a signed-up user's, so that trying the app isn't risky.
26. As a guest, I want to create an account by email (with OTP), Google, or Apple and keep everything I entered, so that signing up never costs me data.
27. As a guest whose chosen sign-in already belongs to an existing Kalé account, I want to be asked whether to add my guest entries to that account, so that I decide what happens to my data.
28. As that guest, I want "add my entries" to be the default choice, so that the safe option is the easy one.
29. As that guest, I want to be told how many entries are involved before choosing, so that I understand the consequence.
30. As a guest, I want to be offered "Create an account to save your data" instead of "Log out", so that I can't accidentally throw away an account I can never sign back into.

### Logging out

31. As a signed-in user, I want logout to back up my pending changes first, so that logging out is safe when I'm online.
32. As a signed-in user with changes that cannot be backed up, I want logout to warn me how many changes will be lost and require explicit confirmation, so that I never lose data by accident.
33. As a user, I want logout to remove all my data from the phone once it's safe, so that the next person using the phone can't see my finances.

### Money and currency

34. As a new user, I want to choose my base currency during onboarding, so that all my amounts are shown in the money I actually use.
35. As a user, I want amounts recorded exactly, without rounding drift, so that my totals are always correct to the unit.
36. As a user, I want amount entry and display to follow my currency's decimal places (none for XOF, two for EUR, GHS, NGN), so that inputs and totals look right.
37. As a user, I want totals, budgets, and savings to be in one currency, so that the app never adds different currencies together.
38. As a user with no transactions yet, I want to change my base currency freely, so that I can fix a wrong choice.
39. As a user with existing transactions, I want to be warned that changing my base currency only relabels my amounts, so that I don't expect a conversion.

### Budgets (schema groundwork only)

40. As a user, I want a budget's period stored as calendar dates, so that time zones or clock changes never shift which day my budget covers.
41. As a user paid on a fixed day, I want my budget periods to be able to start on that day, so that budgets follow my pay cycle. (The UI for this is a later phase; this phase stores it.)

### Performance

42. As a user with thousands of transactions on a low-end phone, I want lists, totals, and charts to stay fast, so that the app stays usable as my history grows.

### Security and privacy

43. As a user, I want only me to be able to read or change my data on the server, so that my finances stay private.
44. As a guest, I want my data protected by the same server rules as a signed-up user's, so that anonymity doesn't weaken my privacy.
45. As a user, I want server secrets never to ship inside the app, so that nobody can extract them from the installed app.
46. As the operator, I want anonymous accounts inactive for 90 days deleted with their data, so that abandoned data isn't kept indefinitely.
47. As the operator, I want anonymous sign-ups rate-limited, so that the open sign-up door can't be abused to flood the backend.
48. As the operator, I want deleted-entry markers purged from the server after 30 days, so that tombstones don't accumulate forever.

### Developer and operator

49. As a developer, I want the full backend schema, access rules, and jobs in the repository, so that any environment can be recreated and every change reviewed.
50. As a developer, I want separate staging and production backends chosen by build flavor, so that testing never touches real users' data.
51. As a developer, I want the server never to compute a value that the client also writes, so that sync can't double-count anything.
52. As a developer, I want each syncable entity type to have exactly one registered sync handler, enforced by an automated check, so that a missing handler can never silently drop data again.
53. As a developer, I want the sync behavior covered by tests at the repository level, so that I can change the engine without fear.

## Implementation Decisions

### Backend (server)

- Restore the backend definition (schema, row-level-security policies, functions, triggers, seed data) from git history into the repository as Supabase CLI migrations. It becomes the single source of truth. Diff it against the live project before the reset to catch dashboard-only drift.
- Two Supabase projects: staging and production. Builds select one through Flutter build flavors with per-flavor define files. The bundled `.env` asset is removed. Only client-safe values (project URL, anon key, OAuth client IDs, Sentry DSN) are compiled in. The FCM server key is removed from the app entirely; there is no server push in v1.
- **Schema reset** (no data migration; no external users assumed):
  - Every user-owned table has `user_id`, a client-generated UUID primary key, `created_at`, `updated_at`, and `deleted_at` (nullable soft-delete marker).
  - Money columns are integers holding **minor units**. Per-entry currency columns are removed. The account's **base currency** lives on the user profile.
  - A currencies reference table holds the code, symbol, and number of decimal places (XOF 0, EUR/GHS/NGN 2, and so on).
  - Budget periods are stored as **dates** (no time component), plus a period start day.
  - Savings contributions are their own table, owned through their goal.
  - The trigger that updated a savings goal's amount from contributions is **dropped**. The client owns derived values.
  - Index on `(user_id, updated_at)` for every synced table to support paged restore and refresh.
- RLS: a user can read and write only rows they own, directly or through a parent they own. Policies treat anonymous users exactly like permanent users. Ownership is modeled so that group-membership-based sharing can be added later without rewriting policies.
- Scheduled jobs: purge rows with `deleted_at` older than 30 days; delete anonymous users (and their data) inactive for 90 days.
- Anonymous sign-ups are enabled with rate limiting or CAPTCHA.

### Device database

- The Drift database restarts at schema version 1, mirroring the server columns: minor-unit integers, `deleted_at`, date-only budget periods, period start day, base currency, a currencies table, and separate goal and contribution tables.
- Indexes: transactions on date, and on category plus date.
- Every DAO read excludes soft-deleted rows. Deleting a row sets `deleted_at` and `updated_at` and marks it unsynced.

### Sync engine

- **Push triggers**: (1) after any local write, debounced about 2 seconds; (2) app resume; (3) connectivity regained; (4) manual retry. Overlapping triggers coalesce into one run.
- **Operations**: a delete is pushed as an update carrying `deleted_at`. Create and update are upserts keyed by the client UUID, so pushes are idempotent and safe to retry.
- **Failure handling**: a network error leaves the entry pending without consuming a retry; other errors consume a retry with exponential backoff. An entry that reaches the retry limit is marked **stuck**, never skipped or dropped. Stuck entries are still retried by a manual retry. All retry counts reset at app start.
- **Status**: the engine exposes an observable summary of pending count, stuck count, syncing state, and last successful backup. UI surfaces read it: the existing sync banner shows stuck changes with a retry action, and settings shows backup status.
- The dead HTTP-409 conflict path is removed. Conflicts are resolved by the pull merge rule below.
- **Handler registration** happens eagerly when the engine is created, for every syncable entity type, not lazily when a feature's repository is first read. Entity types: transaction, category (user-created only), budget, budget category, savings goal, savings contribution.

### Pull (restore and refresh)

- Pull runs only (a) after sign-in on a device whose local database is empty (restore), and (b) on explicit pull-to-refresh. The background refresh on reads is removed, and so is the whole-table replace.
- Pull is paged by `(updated_at, id)` keyset per table, from a stored per-table watermark, with progress reported for restore.
- **Merge rule per row**: if the local row is unsynced, keep local. Otherwise, if the server row is newer by `updated_at`, apply it (including `deleted_at`). Otherwise keep local.
- The post-login data refresh in the auth flow becomes "restore if the local database is empty".

### Auth

- On first launch with no session, the app signs in anonymously. "Guest mode" as a separate auth state goes away. Anonymous users are authenticated users with an `isAnonymous` flag.
- **Upgrading**: email plus OTP links an email to the current user; Google and Apple link an identity through ID-token linking. All local data stays, because the `user_id` does not change.
- **Identity already in use**: if linking fails because the identity belongs to another account, show a choice dialog with the count of local entries: "Add my N entries to that account" (default) or "Discard them". On "add": sign in to the existing account, then re-stamp and re-queue all local rows as creates, which append safely because the UUIDs don't collide. On "discard": sign in, wipe local data, then restore.
- **Logout guard**: first attempt a push. If changes remain pending or stuck, block with an explicit destructive confirmation stating how many changes will be lost. After logout, wipe the local database and queue. Anonymous users are shown "Create an account to save your data" instead of "Log out".

### Money

- Money is a domain value type: integer minor units plus the currency's decimal places. Arithmetic stays in minor units. Formatting and parsing follow the currency's decimals and the device locale with `fr` as fallback.
- Domain entities, models, use cases, and repositories take and return the money type or minor-unit integers. Floating point is never used for stored or summed money.
- Base-currency rules: changeable freely while the account has no transactions; afterwards a relabel only, after an explicit warning. No conversion exists.

### Modules touched

The core database, the sync engine and its providers, the network/session layer, the auth feature (all layers), the transactions, budget, and savings features (data and domain layers, plus the minimal presentation changes needed for currency, logout, and the sync status), the shared money-formatting utilities, onboarding (base-currency step), and the backend migrations. Feature UI beyond those minimal changes is out of scope.

### Documentation and skills

In the same change, update the architecture doc, the offline-sync doc, the development doc (flavors, define files), and the agent skills that encode the old patterns (the syncable-entity and feature-operation skills, and the sync wiring check script) to describe soft deletes, minor units, merge-on-pull, and eager handler registration.

## Testing Decisions

- **What makes a good test**: it drives the system through its public interface and asserts outcomes the user or the server would observe (what a list shows, what a total equals, what reached the backend, what the status says). It never asserts which DAO method was called or the internal order of operations. A refactor that keeps behavior must not break tests.
- **Seam 1, the primary seam (data layer).** Tests drive a feature repository together with the sync engine against a real in-memory Drift database, with the existing mock remote datasources acting as the server (extended where needed to record calls and to fail on demand). Only public operations are used: create, update, delete, the watch streams, pull and restore, and triggering a sync. This one seam covers push triggers and debouncing, network-versus-server failure handling, stuck entries and retry reset, idempotent upserts, the merge rule (unsynced local wins, newer `updated_at` wins), tombstones in both directions, paged restore, minor-unit totals, savings goal and contribution sync without double-counting, and that every enqueued entity type has a registered handler.
- **Seam 2 (auth flows).** Tests drive the auth notifier with use-case providers overridden: anonymous first launch, linking by email, Google, and Apple, the identity-in-use choice (add versus discard), the logout guard (clean push, blocked with pending changes, explicit destructive logout), and anonymous users never being offered logout.
- **Seam 3 (server).** SQL tests run by the Supabase CLI against a local stack: RLS isolation between two users (including anonymous), ownership through parent rows, the tombstone purge job, the anonymous-account cleanup job, and the absence of any trigger writing client-owned values.
- **Prior art**: the auth repository and notifier tests (mocktail, provider overrides, `registerFallbackValue`) and the shared mocks and test-app helpers. Seam 1 deliberately departs from the auth repository tests' style of mocking every collaborator: sync behavior lives in the interplay of DAOs, queue, and engine, so the database is real and only the remote is faked.
- The sync wiring check script stays as a fast static guard in CI, alongside these behavioral tests.
