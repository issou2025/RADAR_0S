## Proposal for maintainer feedback

Could you try requesting a test bundle from your own laptop and tell us whether this would make testing easier? The experiment is on `experiment/github-actions-builds`; nothing is merged into `main`.

The flow is: choose a target platform → GitHub-hosted runner analyses, tests and builds → the requesting laptop downloads the matching archive. Flutter and the target platform's build toolchain are not needed on the laptop. Both maintainers can request Windows and Linux bundles independently of whose computer is available.

## Try it

Follow the [handover instructions in the experiment README](https://github.com/topse/moocp/blob/experiment/github-actions-builds/README.md#übergabe-vom-eigenen-laptop-bauen-lassen). They cover a separate checkout, Git identity, Python, GitHub CLI login and HTTPS Git credentials.

From that clean checkout:

- Windows PowerShell: `py -3 tool/ci_bau.py windows`
- macOS Terminal: `python3 tool/ci_bau.py windows`
- Replace `windows` with `linux` or `both` to select the target platforms.

The client creates an empty trigger commit on the experiment branch, pushes it, waits for that exact commit's CI run and downloads to `build/ci-downloads/<commit>/<platform>/`. A Mac can request a Windows bundle, but running it requires Windows. There is no `macos` build target yet.

Failed or cancelled runs stop the client without downloading a substitute bundle. Concurrent requests on this shared branch can cancel each other. Archives expire after three days. The README covers download-only use, extracting and starting bundles, and recovering from an outdated checkout.

## Test bundles and release publication are separate

Bundles are inputs to manual testing and integration testing before publication. A green build does not approve a release. The experiment creates no tags, publishes no releases, and neither installs nor starts the downloaded app. Publication must remain a separate, explicit action after the required testing and review.

## Future macOS builds

Extend the workflow with a GitHub-hosted Mac runner, agree on Apple Silicon and/or Intel targets, package the complete `.app` preserving permissions, and add a Mac download target to the client. Agree on the required Mac testing before enabling publication.

For distribution outside the App Store, provision the appropriate Apple Developer ID identity and notarization access through protected CI secrets/environments. Signing and notarization can run in GitHub Actions; neither maintainer needs the other's physical Mac. See [Flutter macOS deployment](https://docs.flutter.dev/deployment/macos) and [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

This issue requests feedback on the experiment and the future Mac path. It does not authorize merging, signing setup or release publication.
