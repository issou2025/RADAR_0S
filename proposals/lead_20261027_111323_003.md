*Project description:*
## Vision

A Signlytic AI app for Android and iOS that works like a familiar phone translator, two panes with a direction switch, but for **British Sign Language (BSL) and English**. A hearing person types or speaks English and a signing avatar shows it in BSL. A Deaf person signs to the camera and the app shows, or speaks, the English.

This issue is the roadmap and the place to discuss it. **It is a plan, not a commitment to dates**, and no implementation has started. Each task below will become its own issue once the approach is agreed.

## Be honest about what is ready

Half of this can be built today from parts that already work. The other half depends on research that is not finished, and the app must not promise more than the models can do.

| Direction | Status today | What that means for mobile |
|-----------|--------------|----------------------------|
| English text to BSL signing | **Works** on the website, Chrome extension and desktop app | Ready to build on |
| English speech to BSL signing | **Works** in the apps | Ready to build on, using the phone's own speech recognition |
| BSL glosses to English text | **Works** (rule-based, or a hosted language model) | Ready to build on |
| English to speech | **Works** with the phone's built-in text to speech | Ready to build on |
| BSL signed to the camera, to English | **Research prototype.** It recognises isolated signs, not continuous signing, and has no held-out accuracy figure yet (#7) | Not ready. Gated on research, see Milestone 4 |
| Offline signing | **Blocked on licensing.** Sign motion data and avatar models are licensed for research and served at runtime, not bundled | Only the parts the licences allow, see Milestone 5 |

Camera recognition today is a stock Video Swin Transformer (Swin3D-T) that matches a clip against a dictionary of 5,203 sign videos. The published "100% Top-1" is that dictionary finding its own videos, not a measure of how well it reads a new signer. Getting from there to a real-time phone feature is a research problem first and an app problem second.

## What can be reused

All of this already exists in this repository:

- **English to gloss converter:** `signlytic-extension/gloss/converter.js`. Pure JavaScript, no dependencies, runs offline.
- **Signing renderers:** `signlytic-extension/overlay/avatar3d.js` (3D avatar, Three.js) and `skeleton2d.js` (2D skeleton). The website and the desktop app already embed these same files. Edit them only in the extension; the other copies are generated.
- **Sign data API:** `GET /api/signs/{gloss}` on the website returns the motion frames for one sign, and is already cached and served with CORS.
- **Avatar API:** `GET /api/avatar/{male,female}` serves the 3D models at runtime.
- **Language model translation:** `/api/english-to-glosses` and `/api/glosses-to-english` on the website, and the gloss to English path in `src/inference/gloss_to_text.py`.
- **Recognition and assembly server:** `app_server.py` (FastAPI) exposes `/api/live/frame` and `/api/live/assemble`, which the desktop dashboard uses for webcam recognition. It needs a GPU.
- **Caption sentence assembly:** `signlytic-desktop/main/captions/caption-assembler.js`, which turns a stream of partial captions into whole sentences. The same problem arises with live speech.

## Proposed technology stack (for discussion)

**Recommendation: React Native (with Expo), embedding the existing renderers in a WebView.**

- The renderers and the converter are JavaScript. A WebView runs `avatar3d.js` and `skeleton2d.js` unchanged, so the phone signs exactly like the website, with one source of truth, instead of a second avatar engine to keep in step.
- `converter.js` runs directly in React Native, with no port.
- One codebase for both platforms suits a small volunteer team.
- Camera: `react-native-vision-camera`. Speech: the platform recognisers (`SFSpeechRecognizer` on iOS, which can run on-device, and `SpeechRecognizer` on Android). Text to speech: `AVSpeechSynthesizer` and Android `TextToSpeech`.
- No API keys in the app. Calls that need a language model go through a server endpoint with rate limiting, never straight to a provider.

Flutter and fully native apps are reasonable alternatives. The deciding question is the avatar: either keep the shared Three.js renderer in a WebView, or rebuild it in a native 3D engine. The first task below is to settle this in a short written decision before any app code.

## Milestones

### Milestone 0: Decisions and design
- [ ] Architecture decision record: React Native and WebView, Flutter, or native, judged on renderer reuse, performance on mid-range phones, accessibility and how many maintainers it needs.
- [ ] Measure the shared renderer in a WebView on a mid-range Android phone and an iPhone: frame rate, memory, and time to first sign.
- [ ] Interface design (Figma or similar) for the two-pane translator, reviewed by Deaf BSL users before it is built.
- [ ] Confirm with the data and model licence holders what a phone app may store on the device (signs, avatar models, recognition features). This decides Milestone 5.

### Milestone 1: English to BSL (text)
- [ ] App shell with the two-pane layout, a direction switch, and the 2D and 3D renderers.
- [ ] A packaged renderer page for the WebView, with a small message API: `play(glosses)`, `pause`, `stop`, `speed`, and an event for each sign as it plays.
- [ ] English to glosses: the rule-based converter on the device, with an optional language model through the server for better word order.
- [ ] Each sign named under the avatar as it plays, so nobody depends on the animation alone.
- [ ] Unknown words fingerspelled (depends on #2).
- [ ] History and favourites, stored only on the device, with a clear delete.

### Milestone 2: English speech to BSL
- [ ] Speech input with the platform recognisers, on-device where the phone supports it.
- [ ] Split live speech into sentences, reusing the caption assembler's approach.
- [ ] A clear indicator when the microphone is on, and nothing recorded or uploaded without saying so.

### Milestone 3: Beta release
- [ ] Accessibility audit with TalkBack and VoiceOver, large text sizes, and reduced motion.
- [ ] Privacy policy and store data-safety answers that match what the app really does.
- [ ] TestFlight and Google Play internal testing builds, with continuous integration for both.
- [ ] Feedback from Deaf BSL users on the beta before any public release.

### Milestone 4: BSL to English with the camera (research-gated)
Starts only when the held-out signer evaluation (#7) shows recognition is good enough to put in front of people.
- [ ] A hosted recognition endpoint with a GPU, rate limiting, and no storage of frames.
- [ ] Camera capture that sends clips only after explicit consent, with an on-screen indicator.
- [ ] Results shown with their uncertainty, and the top alternatives, never as a confident translation.
- [ ] English output as text and through the phone's text to speech.
- [ ] Longer term: continuous signing recognition, and on-device inference if a model small enough and licensed for redistribution exists.

### Milestone 5: Offline, where possible
- [ ] Offline now: the rule-based converter, on-device speech recognition, history and favourites.
- [ ] Offline signing only if the licence check in Milestone 0 allows sign data and avatar models to be stored on the device. Until then, signing needs a connection.

## Technical challenges

- **Recognition accuracy.** The hardest problem, and a research one. See #7 and #12.
- **Licences.** The sign motion data comes from research datasets and the avatar models are not redistributable. Both are served at runtime and must not be bundled into the app, committed, or published.
- **Rendering on phones.** Three.js in a WebView has to hold a smooth frame rate on mid-range Android phones, not just new iPhones. Related: #11 (the website panel on phones).
- **BSL is not English word by word.** Gloss order, fingerspelling, and facial expression all carry meaning. The avatar has no facial expression yet (#3).
- **Privacy.** Camera and microphone input from Deaf users is sensitive. Default to processing on the device, never keep media on a server, and say plainly what leaves the phone.
- **Cost.** Hosted language model calls and GPU recognition cost money per use, so rate limits and caching are needed from the first public build. App store accounts also carry fees, which the maintainer would need to decide on.

- **Mobile developers:** the Milestone 0 measurements and the decision record are the best starting points, followed by the renderer WebView package.
- **Designers and accessibility specialists:** the interface design, and the accessibility audit criteria for Milestone 3.
- **BSL users, especially Deaf BSL users:** reviewing the design and, later, the beta. This is the most valuable help of all.
- **AI researchers:** #7 (held-out signer evaluation) and #12 (an English to gloss evaluation set) decide when Milestone 4 can start.
