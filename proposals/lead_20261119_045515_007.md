**With `xsVerbose` on, `_xsLogs` has no upper bound in a long-lived app, and once it's over `xsVerboseLogMax` every new entry re-partitions and re-sorts the whole buffer.** Bram's agent pane, open about 40 minutes with `xsVerboseLogMax: 200`, held 7,516 entries. Three findings:

- **The cap doesn't apply to the "preserved" kinds.** `splicePreservingInteractions` never evicts 16 kinds (`interaction`, `api:start`/`complete`/`error`, `handler:start`/`complete`, `value:change`, `method:call`, `navigate`, `modal:*`, `toast`, `submenu:open`, `selection:change`, `focus:change`) or any `native:*` entry. In an app whose DataSources refetch and whose handlers fire all day, those are most of the entries, so the buffer grows for the app's whole life.
- **Each push past the cap costs O(n log n) in the buffer size.** `pushXsLog` calls `splicePreservingInteractions(w._xsLogs, xsLogMax - 1)` on every push once at capacity. That partitions the whole array, builds a merged copy, sorts it by timestamp and rewrites it in place. At 7,500 entries that's a full sort plus several throwaway arrays per traced event, and the cost keeps growing.
- **The design fits a test capture, not a long session.** The function's comment says the preserved kinds exist for Playwright test generation and trace comparison. That's reasonable for a short capture. For an app left open with tracing on, it's an unbounded buffer and a per-event cost that rises with uptime.

Data: `window._xsLogs.length` and `window.__xsVerbose` read in Web Inspector's console in Bram's pane (XMLUI standalone build vendored in Bram 0.8.10). Source references are to `main` at `600677866`.

<details>
<summary><b>1. Where the cap is skipped</b></summary>

`xmlui/src/components-core/inspector/inspectorUtils.ts`:

- `pushXsLog` (around line 395): at capacity with the default `drop-oldest`, it calls `splicePreservingInteractions(w._xsLogs, xsLogMax - 1)` and then pushes.
- `splicePreservingInteractions` (line 446): the entries are split into `keep` (preserved kinds and `native:*`) and `evictable`. `evictableSlot = maxSize - keep.length`. When `keep.length >= maxSize` it keeps **all** of `keep` and none of `evictable`, so the result is still over `maxSize`, and the next push runs the whole trim again.

The direct pushes at `inspectorUtils.ts:519` and `audit/pipeline.ts:342` also bypass the cap, but those look bounded (once per kind) or rare.

**Suggestion:** give the preserved kinds a bound of their own: a separate, larger cap (say 10× `xsVerboseLogMax`), dropping their oldest once it's reached. Trim in batches, for example back down to 90% of capacity, so the partition and sort run once per batch rather than once per push. A ring buffer per class would avoid the sort entirely.
</details>

<details>
<summary><b>2. What it cost in Bram</b></summary>

Bram had `appGlobals.xsVerbose: true` in its pane's config since May, so every Bram user ran with tracing on all day. That was Bram's choice, and it's being turned off by default on Bram's side (Worklist item `xs-verbose-off-by-default`), with `localStorage["xmlui:xsVerbose"] = "true"` for debugging sessions.

- The pane already had an open report that it "slows with use until a reload" ([judell/bram#482](https://github.com/judell/bram/issues/482)). Its focused stall rate climbed from 19 to 127 an hour over the first two hours of use. A per-event cost that rises with buffer size has that shape. We haven't yet measured whether this is the cause.
- Memory: the buffer itself is modest (7,516 entries, inside about 60 MB of live JS objects in a heap snapshot). The renderer's total is much larger (500–800 MB of dirty heap), and we're measuring how much of that verbose mode accounts for. We'll add the result here.

One note for anyone embedding XMLUI: `pushXsLog` treats "an `_xsLogs` array exists" as "tracing is on". Bram's shell created that array unconditionally before XMLUI loaded, so any push that gates only on the array (`pushXsLog`, the audit pipeline's push at `audit/pipeline.ts:342`) could write with verbose off. We haven't confirmed that it did. Bram is removing that. Gating on `window.__xsVerbose` as well would make it robust to hosts that do this.
</details>
