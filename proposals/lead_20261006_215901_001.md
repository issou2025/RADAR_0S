# RVT Viewer v1 — Interactive BIM Model Viewer

## Problem Statement

Architects, engineers, and stakeholders need to view and interact with BIM models in a web browser without requiring Autodesk Revit or any proprietary desktop software. Sharing and inspecting building models currently creates friction in collaboration and review workflows — every participant needs expensive, platform-locked software installed.

## Solution

A web application where users upload IFC files, view them as interactive 3D models in the browser, select BIM Elements to inspect their BIM Properties, and navigate the model using orbit and walkthrough camera modes. All heavy lifting (IFC parsing, geometry extraction, property reading) happens client-side via WebAssembly — no server-side rendering or proprietary dependencies needed.

## User Stories

1. As an architect, I want to upload an IFC file through a drag-and-drop interface, so that I can make my building model available for viewing without converting it to another format.
2. As an architect, I want to see a list of all uploaded Models with their filename, size, and upload date, so that I can manage and find previously uploaded files.
3. As an architect, I want to open a Model from the list and see its 3D geometry rendered in the browser, so that I can visually inspect the building design.
4. As an architect, I want to orbit the camera around the model by dragging with my mouse, so that I can view the model from any angle.
5. As an architect, I want to zoom in and out using the scroll wheel, so that I can inspect details at different scales.
6. As an architect, I want to pan the camera by holding the middle mouse button, so that I can shift my view laterally.
7. As an architect, I want to click on a BIM Element (wall, door, beam, etc.) in the 3D Viewer to select it, so that I can inspect that specific component.
8. As an architect, I want selected BIM Elements to be visually highlighted, so that I can clearly see which component I'm inspecting.
9. As an architect, I want to see the BIM Properties of a selected element (name, material, dimensions, classification) in a side panel, so that I can understand the component's specifications.
10. As an engineer, I want to switch to a first-person Walkthrough camera mode, so that I can move through the building interior as if I were walking inside it.
11. As an engineer, I want to move forward, backward, left, and right using WASD keys in Walkthrough mode, so that I can navigate fluidly through the space.
12. As an engineer, I want to look around using mouse movement in Walkthrough mode, so that I can survey the environment from a human perspective.
13. As an engineer, I want to switch between orbit and walkthrough camera modes easily, so that I can choose the right navigation style for my current task.
14. As a stakeholder, I want to see the Spatial Structure (Project → Site → Building → Storey) of the model, so that I can understand the organizational hierarchy.
15. As a stakeholder, I want to deselect a BIM Element by clicking on empty space, so that I can clear the properties panel.
16. As an architect, I want to delete a Model I no longer need, so that I can keep my workspace clean.
17. As an architect, I want to see a loading indicator while the IFC file is being parsed, so that I know the Viewer is working and not frozen.
18. As an architect, I want to receive a clear error message if I try to upload a non-IFC file, so that I understand why the upload was rejected.
19. As an architect, I want to receive a clear error message if the IFC file cannot be parsed, so that I understand what went wrong.
20. As an architect, I want the application to work on Chrome, Firefox, and Edge, so that I'm not locked to a specific browser.
21. As an architect, I want a responsive layout that works on different screen sizes, so that I can use the app on a laptop or desktop monitor.
22. As an architect, I want to see the filename and model metadata in the Viewer header, so that I always know which model I'm looking at.
23. As an engineer, I want to reset the camera to the default view, so that I can quickly return to a known perspective after navigating.
24. As an architect, I want the IFC file to be parsed in the browser (not on the server), so that model data stays on my machine and uploads are fast.
25. As a stakeholder, I want the UI to be clean and minimal, so that the 3D model is the primary focus and the interface doesn't distract from it.

## Implementation Decisions

### Architecture

- **Monorepo** with `frontend/` (React + TypeScript + Vite) and `backend/` (ASP.NET Core 8 Web API). One clone, one pipeline.
- **IFC.js (web-ifc-viewer)** as the 3D viewer library. Parses IFC files client-side via WebAssembly. Built on Three.js.
- **REST API** as the single communication boundary between frontend and backend.
- **SQLite + Entity Framework Core** for Model metadata persistence. Zero-setup, file-based, easy migration path to PostgreSQL.
- **File Store abstraction** (`IFileStore` interface) for file persistence. `LocalFileStore` for v1; swappable to blob storage later.
- **No authentication for v1**. Focus on core viewer functionality; add auth when access control is needed.
- **Tailwind CSS + shadcn/ui** for styling and UI components.

### API Contract

REST endpoints for Model management:

- `POST /api/files` — Upload an IFC file (multipart/form-data). Returns Model metadata (id, filename, size, uploadDate).
- `GET /api/files` — List all uploaded Models with metadata.
- `GET /api/files/{id}` — Download/stream the IFC file binary.
- `GET /api/files/{id}/metadata` — Get Model metadata only.
- `DELETE /api/files/{id}` — Delete a Model and its stored file.

Error responses use standard HTTP status codes with a JSON error body containing a message field.

### File Storage

- Uploaded IFC files stored on local filesystem at `uploads/{fileId}.ifc`.
- File Store interface abstracts storage: `Save(fileId, stream)`, `Get(fileId)`, `Delete(fileId)`, `Exists(fileId)`.
- Filesystem-backed implementation for v1; interface designed for future swap to blob storage.

### Database Schema

Single `Models` table:
- `Id` (GUID, primary key)
- `Filename` (original upload filename)
- `FileSize` (bytes)
- `ContentType` (always "application/x-step" for IFC)
- `UploadedAt` (UTC timestamp)
- `StoragePath` (relative path in File Store)

### Frontend Components

- **FileUpload** — drag-and-drop + click-to-browse upload area. Validates file extension (.ifc). Calls `POST /api/files`.
- **ModelList** — displays uploaded Models in a list/card view. Shows filename, size, date. Click to open in Viewer. Delete button.
- **Viewer** — wraps IFC.js. Loads IFC file from `GET /api/files/{id}`. Renders 3D geometry. Handles orbit and walkthrough camera modes. Emits Selection events.
- **PropertiesPanel** — side panel displaying BIM Properties of the currently selected BIM Element. Shows name, material, dimensions, classification.
- **Layout** — application shell with header, sidebar (ModelList), main content (Viewer + PropertiesPanel).

### Frontend-Backend Data Flow

1. User uploads IFC file → frontend POSTs to backend → backend saves file via File Store, records metadata in SQLite → returns Model.
2. User opens a Model → frontend requests `GET /api/files/{id}` → backend streams IFC file → frontend loads into IFC.js via WASM.
3. User clicks a BIM Element → IFC.js fires Selection event with element ID + BIM Properties → PropertiesPanel displays the data.
4. User navigates → orbit or walkthrough camera mode handled entirely in the browser by IFC.js.

### Testing Decisions

**What makes a good test:** Tests verify external observable behavior at seam boundaries. No testing of implementation details, internal state, or rendering output.

**Seams to test:**

1. **REST API boundary** (primary, integration tests) — send HTTP requests to the API, verify responses and side effects. Tests cover: successful upload, upload with invalid file type, list all models, get model by id, get file stream, delete model, error cases (not found, bad request).

2. **IFileStore interface** (unit tests) — test the contract: save a stream, retrieve it, check existence, delete. Verify that LocalFileStore correctly reads/writes to filesystem. Swap to InMemoryFileStore for controller tests.

3. **Viewer component boundary** (component tests) — verify that the Viewer component accepts an IFC URL prop and emits `onSelectionChanged` events. Do not test 3D rendering output — that's IFC.js's responsibility.

**Testing stack:**
- Backend: xUnit + ASP.NET Core integration test host (`WebApplicationFactory`). SQLite in-memory for test database.
- Frontend: Vitest + React Testing Library for component tests. Mock Service Worker (MSW) for API mocking.

## Out of Scope

- **RVT file support** — no open-source cross-platform parser exists. IFC only.
- **Authentication and user accounts** — added in a later phase when access control is needed.
- **Section cuts** — interactive plane-based cross-section views. Fast-follow after v1.
- **Measurements** — distance measurement between points. Fast-follow after v1.
- **Annotations** — pinning notes on BIM Elements. Fast-follow after v1.
- **Explode view** — separating floors/layers. Fast-follow after v1.
- **Server-side rendering or conversion** — all rendering is client-side via WASM.
- **Multi-file upload** — one file at a time for v1.
- **Real-time collaboration** — single-user experience for v1.
- **Cloud storage (Azure Blob, S3)** — local filesystem for v1; abstraction layer in place for future swap.

## Further Notes

- The sample file `dach-sample-project.rvt` is a Revit file and cannot be used directly. It must be exported to IFC from Revit first. For testing, an IFC file exported from this RVT should be used.
- IFC.js uses WebAssembly, which requires modern browsers with WASM support. Chrome 57+, Firefox 52+, Edge 16+.
- The application should gracefully handle large IFC files (100MB+). Show progress indicators during upload and parsing.
- All open-source dependencies: IFC.js (MIT), Three.js (MIT), React (MIT), ASP.NET Core (MIT), EF Core (MIT), SQLite (public domain), Tailwind CSS (MIT), shadcn/ui (MIT).
