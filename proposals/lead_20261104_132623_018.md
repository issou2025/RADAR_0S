*Project description:*
## Summary

Running `setup.py --backend sycl --family unsloth --model UD-IQ4_XS` a second time (to resume an interrupted download) finishes all the real work — model shards, pack, vision encoder, MTP draft layer all print `[ok]` — and then aborts in Step 7 with:

```
[X]  /work/Strata-data/packs/unsloth-ud-iq4_xs is outside /home/maddy/sandbox, which the SYCL engine's container mounts
Setup stopped. Fix the item above and run it again - everything already done is kept and skipped.
```

Exit code 1. Nothing is actually wrong: the server starts fine against the produced files and serves correct output. The failure is a **double translation**: `sycl_path()` is applied to arguments that are already container paths, because the setup carries `args` over from the previous run's config.

Note the irony: the run **explicitly keeps** `args --pack …` from the earlier config, and then rejects those very arguments one step later.

## Root cause

`sycl/setup_intel.py:312-316` translates every path-valued argument through `sycl_path()`:

```python
for f in ("--pack", "--native", "--ple-gguf", "--expert-profile", "--mtp", "--control-vector-scaled"):
    if f in args:
        v = args[args.index(f) + 1]
        path, _, scale = v.rpartition(":") if f == "--control-vector-scaled" else (v, "", "")
        args[args.index(f) + 1] = sycl_path(path) + (f":{scale}" if scale else "")
```

and `sycl_path()` (line 108) is not idempotent — it requires the path to be **under** `MOUNT` (the host-side Strata root) and fails otherwise:

```python
def sycl_path(path) -> str:
    p, root = Path(path).resolve(), MOUNT.resolve()
    try:
        return "/work/" + p.relative_to(root).as_posix()
    except ValueError:
        S.fail(f"{p} is outside {root}, which the SYCL engine's container mounts", ...)
```

When `args` comes from an existing config, its values are already `/work/Strata-data/packs/…`. Resolving that against the host root raises `ValueError` → `S.fail()`. A container path is being checked against the host filesystem.

This is the same class of bug as the drafting check in #5138 ("`/work` paths are checked outside the engine container"), but in the **setup** path rather than the launch path — so a fresh install never hits it and every re-run with an existing config does.

## Impact

- Setup reports failure although the model, pack, vision encoder and MTP layer are complete and usable. Automation that checks the exit code treats a successful setup as broken.
- The message sends the user looking for a directory problem (`--models-dir`/`--data-dir`) that does not exist. Here the hint is actively misleading: the files are exactly where they belong, under the mount root.
- Re-runs are common after an interrupted download — exactly the case where the user is already under time pressure.

## Suggested fix

Make `sycl_path()` idempotent — pass container paths through unchanged:

```python
def sycl_path(path) -> str:
    p = Path(path)
    container = Path("/work")
    if p.is_absolute() and (p == container or container in p.parents):
        return p.as_posix()          # already a container path, nothing to translate
    p, root = p.resolve(), MOUNT.resolve()
    try:
        return "/work/" + p.relative_to(root).as_posix()
    except ValueError:
        S.fail(...)
```

Two independent improvements on top of that:

1. **Validate before building, or at least report the state.** The check sits in Step 7, after the ~94 GB download and the pack build. A failure there costs the user a full re-run even though everything is on disk. Validating the paths first, or wording the message as "the model is ready; only the start script could not be written", removes the false failure.
2. The `.bak` handling is fine — the config was byte-identical to its backup after this run, so nothing was lost.
