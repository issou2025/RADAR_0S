# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: v0.3 desktop app (tray + local web UI) for non-technical users**

*Project description:*
## Problem Statement

Apartment Hunter is useful only to people who are comfortable with a terminal. To use it today, someone has to install Python and uv, clone a repo, edit a TOML config file and an `.env`, find a Discord webhook URL, and keep a terminal window open. If it stops working (apartments.com blocks it, the webhook is wrong, the machine reboots), the only evidence is in a log they'll never read.

Friends and family looking for an apartment can't use it. Even technical users would like to add a search or check whether it's healthy without opening a config file.

## Solution

A desktop app for Windows, macOS and Linux that a non-technical person can download, double-click and set up in a couple of minutes, without touching a terminal.

The app lives in the system tray, or runs as a background app on desktops with no tray. It opens a simple local web page in the user's browser where they:

- paste an apartments.com search URL and give it a name,
- paste a Discord webhook (with a walkthrough and a "Send test message" button),
- see at a glance whether each search is working, what it last found, and what to do if something is wrong.

It starts when they log in, runs quietly in the background, and tells them when a new version is out.

The existing CLI, `config.toml` and Docker paths keep working unchanged. The app is a second front end over the same core (Search, Listing, Scraper, Notifier, Store, SearchRunner), not a separate product.

## User Stories

### Installing and launching

1. As a non-technical user, I want to download one file from the GitHub Releases page for my OS, so that I don't have to install Python, uv or anything else first.
2. As a Windows user, I want a normal `.exe` installer, so that the app installs like any other program.
3. As a macOS user, I want a `.dmg` containing an `.app` I can drag to Applications, so that installing feels familiar.
4. As a Linux user, I want a single AppImage file, so that it runs on my distro without a distro-specific package.
5. As a user of the unsigned app, I want the README to show, with screenshots, how to get past the Windows SmartScreen and macOS Gatekeeper warnings, so that I'm not scared off or stuck.
6. As a user, I want the app to open its web page in my browser automatically on first launch, so that I know where to go next.
7. As a user, I want to see a tray icon while the app is running, so that I know it's working in the background.
8. As a user, I want the tray menu to offer Open, Start/Stop and Quit, so that I can control the app without hunting for a window.
9. As a GNOME user (or anyone whose desktop has no tray), I want the app to open its web page on launch and keep running in the background, so that it still works without a tray.
10. As a user with no tray, I want a desktop/menu shortcut that reopens the web page while the app is running, so that I can always get back to it.
11. As a user who launches the app a second time by accident, I want it to open the existing app's page instead of starting a second copy, so that I don't get duplicate alerts.
12. As a CLI user, I want the CLI and the desktop app to refuse to run at the same time against the same data, so that two scrapers never run at once.

### First-time setup

13. As a first-time user, I want a short guided setup (webhook → first search), so that I know exactly what to do in order.
14. As a user who has never used webhooks, I want step-by-step instructions (with pictures) for creating a Discord webhook, so that I can get one without searching online.
15. As a user, I want to paste my webhook and click "Send test message", so that I see a message arrive in Discord and know it works before going further.
16. As a user who pasted a wrong webhook, I want a plain-language error ("Discord says this webhook doesn't exist; copy it again from Channel settings → Integrations → Webhooks"), so that I can fix it myself.
17. As a user, I want the app to explain how to build a search on apartments.com (apply filters, then copy the address bar), so that my search URL has the filters I care about.

### Managing searches

18. As a user, I want to add a search by pasting an apartments.com URL and giving it a name, so that I can watch a new area or filter set.
19. As a user, I want the first run of a new search to happen immediately when I add it, so that I find out straight away whether the URL works.
20. As a user, I want to see "✅ Found 37 listings. You'll be alerted about new ones" after adding a search, so that I know it's set up and won't flood me with current listings.
21. As a user who pasted something that isn't an apartments.com search results page, I want to be told that clearly, so that I can paste the right link.
22. As a user, I want to choose how often each search runs (with a sensible default and a minimum), so that I can balance speed against being polite to the site.
23. As a user, I want to send a search's alerts to a different Discord webhook than the default, so that different searches can go to different channels or people.
24. As a user, I want to edit a search's name, URL, interval or webhook, so that I can adjust it without deleting it.
25. As a user, I want to be warned that changing a search's URL or name starts it fresh (its next run counts as a first run), so that I'm not surprised.
26. As a user, I want to delete a search with a confirmation, so that I don't remove one by accident.
27. As a user, I want to pause and resume an individual search, so that I can stop alerts for an area without losing its settings.

### Seeing what's happening

28. As a user, I want a status table showing each search's state (Healthy / Running / Paused / Needs attention), last run time, next run time and listing count, so that I can see at a glance that everything works.
29. As a user, I want a list of recent alerts (new listings and price drops) with links, so that I can catch up on what was sent even if I missed the Discord message.
30. As a user, I want "Run now" for each search, so that I can check immediately instead of waiting for the interval.
31. As a user, I want a global Start/Stop, so that I can pause everything (for example after I've signed a lease).
32. As a user, I want the status page to update on its own while it's open, so that I don't have to keep refreshing.
33. As a user whose search is blocked by apartments.com, I want a plain-language explanation and next step ("This usually clears up on its own. If it keeps happening, turn on *Show browser while scraping*"), so that I know whether to act.
34. As a user whose scraper has broken (several failed runs in a row), I want the status page to say so prominently, in addition to the Discord health alert, so that I notice even if I've muted Discord.
35. As a user with no supported browser installed, I want a clear message telling me to install Google Chrome, with a link, so that I can fix it in one step.
36. As a user reporting a bug, I want "Show details" and "Copy log" buttons, so that I can paste the technical details into a GitHub issue.
37. As a user, I want an "Open data folder" button, so that I can find my config, database and logs if someone asks for them.

### Settings and background behaviour

38. As a user, I want "Start when I log in" on by default once I've added my first search, so that it keeps watching after a reboot without me remembering.
39. As a user, I want to turn "Start when I log in" off, so that I'm in control of what runs on my machine.
40. As a user, I want scraping to happen without browser windows popping up in my way, so that the app doesn't interrupt my work.
41. As a user troubleshooting blocks, I want a "Show browser while scraping" setting, so that I can see what the site is showing.
42. As a user, I want the app to tell me when a new version is available, with a download link, so that I don't keep running a scraper that broke when the site changed.
43. As a user who doesn't want the app contacting GitHub, I want to turn off the update check, so that it makes no network calls beyond scraping and Discord.

### Safety and privacy

44. As a user, I want the web page to be reachable only from my own computer, so that nobody else on my Wi-Fi can see or change my searches.
45. As a user, I want my webhook URLs, searches and history stored only on my own machine, in the standard app-data folder for my OS, so that my data stays private and in a predictable place.
46. As a user, I want the app to keep the same polite defaults as the CLI (minimum interval, one search at a time, random pauses between pages, page cap), so that I'm not hammering the site.

### Technical users and maintainers

47. As a technical user, I want the desktop app to read and write the same config format the CLI uses, so that I can switch between them or edit the file by hand.
48. As a technical user, I want the CLI and Docker image to keep working exactly as before, so that the app adds an option without forcing a change.
49. As a maintainer, I want every GitHub Release to build all three app formats automatically in CI, so that releasing doesn't involve manual packaging on three OSes.
50. As a maintainer, I want CI to launch each built app in a self-test mode that starts and exits cleanly, so that a broken package is caught before release.
51. As a maintainer, I want the GUI's behaviour tested through its HTTP interface with fake Scraper and Notifier implementations, so that tests are fast, deterministic and never touch apartments.com or Discord.

## Implementation Decisions

### Architecture

- **One core, two front ends.** The app reuses the v0.2 core unchanged where possible: Search and Settings (config), Listing, the Scraper interface and the apartments.com Scraper, the Fetcher implementations, the Notifier interface and Discord Notifier, Store (SQLite) and SearchRunner. The CLI and the app are both thin shells over it.
- **A background scheduler service** replaces the blocking scheduling loop for the app. It runs searches one at a time (never in parallel) on a background thread with the same ±20% jitter, and supports start/stop overall, pause/resume per search, and "run now" (queued, still sequential). The CLI's loop is reimplemented on top of this service so there is one scheduler.
- **Application factory.** The web app is built by a factory that takes its dependencies (a Scraper, a notifier factory keyed by webhook URL, a Store, the data directory, a clock) and returns the FastAPI app. Production wires the real implementations; tests wire fakes. This is the main test seam.
- **Tray as a thin shell.** The tray (pystray) only calls the same actions the web UI exposes (open, start/stop, quit). It holds no logic of its own.
- **No-tray fallback.** On startup the app checks whether a system tray is available. If not (stock GNOME, some Wayland setups, any failure to create the icon), it opens the web UI and runs as a background process. Quit is offered in the web UI in every mode.

### Web UI

- FastAPI with Jinja templates and htmx. No JavaScript framework, no Node or npm build step; static assets ship inside the Python package.
- Listens on 127.0.0.1 only. No authentication. A fixed default port, falling back to a free port if it's taken; the chosen port is recorded in the data directory so a second launch can find it.
- Pages: setup wizard (webhook → first search), dashboard (status table, recent alerts, global Start/Stop), search add/edit, settings (start at login, show browser while scraping, update check, open data folder, copy log).
- The status table refreshes itself with htmx polling while the page is open.
- Every user-facing status and error is a plain-language message with a suggested fix. Raw exception text appears only under "Show details". The core error types map to messages: blocked by bot protection, zero listings on page 1 / not a results page, browser not found, browser failed to start, webhook invalid, Discord unreachable, page cap hit.

### Search lifecycle

- Adding a search saves it, then immediately queues its first (seeding) run and reports the outcome on the page: listing count on success, plain-language reason on failure. A search whose first run failed is kept but marked "Needs attention".
- Search name remains the Store key, as in v0.2. Renaming or changing a search's URL resets its state (it is seeded again on its next run), and the UI warns about this before saving.
- New per-search state: **paused**. Store gains a way to record and read paused status. Paused searches are skipped by the scheduler.
- Store gains a **recent alerts** record (search, listing id, kind: new or price drop, price, URL, time), written when an alert is delivered, read by the dashboard. Retain a bounded number (for example the last 200).

### Config and data location

- The app reads and writes the same TOML config format as the CLI. Writes are atomic (write to a temp file, then rename). Comments in a hand-edited file are not preserved when the app saves; the app's settings page says so.
- New config keys: start at login, update check enabled, per-search paused (or kept in Store; whichever, it must survive restarts).
- The desktop app keeps config, database, browser profile, logs, lock file and port file in the per-user app-data directory (via platformdirs). The CLI keeps its current defaults (current directory / `--config`) and gains a flag to use the app-data directory, so a technical user can point the CLI at the app's data.
- Logs go to a rotating file in the data directory in addition to stdout; "Copy log" reads from it.

### Single instance

- A lock file in the data directory, acquired by both the CLI and the app, held for the life of the process and released on exit (stale locks from crashed processes are detected and taken over).
- A second app launch that finds a live lock reads the port file and opens the browser to the running instance, then exits. A second CLI launch exits with a clear message.

### Browser

- Browser detection extends the v0.2 lookup to standard install locations, not just PATH: Chrome, Edge and Brave on Windows (Program Files and per-user locations); Chrome, Edge and Brave in `/Applications` on macOS; existing PATH lookup plus Chrome/Chromium/Brave/Edge on Linux. Detection is a pure function of (OS, path-exists check, env) for testing.
- No browser is bundled.
- Fetching uses the v0.2 `chromium` mode only: launch the detected browser with the search URL as a launch argument and a dedicated, persistent profile in the app-data directory, then attach over CDP only to read the page. This is the only method confirmed to get past apartments.com (see Further Notes). The experimental Scrapling `stealth` mode is not exposed in the GUI.
- Window behaviour: **headless is confirmed blocked**, so the browser always runs as a real window. By default it is placed off-screen and minimised, so it stays out of the user's way. "Show browser while scraping" puts it in a normal visible position. Off-screen placement must be verified on each OS: Wayland compositors may ignore window-position flags. Where off-screen placement doesn't work, fall back to starting minimised, and if that doesn't work either, accept a briefly visible window and document it.

### Start at login

- Per-OS implementation: a Startup-folder shortcut or HKCU Run registry entry on Windows, a LaunchAgent plist on macOS, an XDG autostart `.desktop` entry on Linux. Turned on automatically after the first search is added; toggled in settings.

### Update check

- On startup (and daily while running), when enabled, the app queries the GitHub Releases API for the latest release, compares versions, and shows a dismissible "New version available → Download" banner linking to the release page. No auto-update. Network failure is silent.

### Packaging and release

- PyInstaller builds per OS in a GitHub Actions matrix triggered by version tags: a Windows installer `.exe`, a macOS `.app` in a `.dmg`, and a Linux AppImage. Artifacts are attached to the GitHub Release.
- All builds are unsigned for now. The README documents the SmartScreen and Gatekeeper "open anyway" steps with screenshots.
- Each build supports a `--self-test` flag: start the core and web server on a free port, hit its health endpoint, shut down, exit 0. CI runs it on every built artifact.

### Notifications

- Discord only. The existing Notifier interface and its webhook check are reused for "Send test message" and webhook validation.

## Testing Decisions

- **What a good test is here:** it drives the system the way a user or OS would and asserts on externally visible results: HTTP responses and rendered page content, messages sent to the fake Notifier, state reported back through the UI. It does not assert on internal calls, private functions or template structure beyond the user-visible text and controls.
- **Main seam: the web app's HTTP interface.** Tests build the app with the application factory, wiring a fake Scraper (scripted results and errors), a fake Notifier (records messages, can be made to fail), an in-memory or temp-directory Store and a temp data directory, and drive it with FastAPI's TestClient. This covers the setup wizard, add/edit/delete/pause search, seeding on add, plain-language error mapping, Run now, Start/Stop, the status table, recent alerts and settings persistence (config written and re-read).
- **Scheduler:** tested through the web seam where possible ("Run now" runs once, paused searches are skipped, Stop halts runs). An injected clock and a synchronous "run pending work" hook keep these tests deterministic without real threads or sleeps.
- **Small pure-function tests** for logic outside the web app:
  - browser detection: given OS, a path-exists function and env, returns the expected browser or none;
  - update check: given current version and a fake releases response, decides whether to show the banner;
  - single-instance lock: a second acquire in the same data directory fails; a stale lock is taken over;
  - start-at-login: given OS and data, produces the expected autostart entry content and location (writing is a thin wrapper).
- **Existing tests stay and keep passing unchanged:** SearchRunner behaviour with fake Scraper/Notifier/Store, the apartments.com parser against saved HTML, the Discord HTTP layer with patched requests, config loading. These are the prior art for the new tests' style (plain pytest, hand-written fakes, no mocking library, no network).
- **Not automated:** the tray icon (kept logic-free) and real-desktop behaviour (tray availability, autostart actually firing, OS security prompts). Each release gets a short manual check on each OS. Packaging is covered by the CI `--self-test` smoke run on every built artifact.
- No test ever contacts apartments.com, Discord or GitHub.

## Out of Scope

- Browsing, filtering or favouriting listings inside the app (apartments.com already does this).
- User accounts, login, multi-user support, or a hosted/cloud version.
- Remote access to the web UI from phones or other devices.
- Notification channels other than Discord (ntfy, email, Telegram and so on), though the Notifier interface keeps the door open.
- Sites other than apartments.com.
- Code signing and notarisation for Windows and macOS.
- Auto-update (download and install); only an "update available" banner.
- Bundling a browser with the app.
- Commute-distance calculation.

## Further Notes

- **Prerequisite:** the v0.2 core is complete and committed on branch `v0.2-rewrite` (Docker image, README, CI and MIT license included). It has been validated end to end with a real search and a real Discord webhook, both locally and inside the container (built and run with Podman). It must be merged to `main` before v0.3 work starts.
- **What gets past apartments.com's Akamai bot protection** (tested from the developer's network, Linux, Scrapling 0.5.1):

  | Method | Result |
  |---|---|
  | Installed Chromium launched with the URL as an argument, page read over CDP, visible window | ✅ works (desktop and Xvfb in Docker) |
  | Same, but headless (`--headless=new`) | ❌ Access Denied |
  | Playwright / Scrapling `DynamicFetcher` | ❌ Access Denied |
  | Scrapling `StealthyFetcher` / `StealthySession` (all stealth options, system Chromium via `executable_path`) | ❌ Access Denied |
  | Navigation driven over CDP into an already-running browser | ❌ Access Denied |
  | Plain HTTP request impersonating Chrome | ❌ Access Denied |

  The common factor is that automation-driven navigation and headless are rejected, while a browser that opens the URL itself is accepted. This can change at any time, which is why health alerts, plain-language blocked messages and the update banner matter for non-technical users.
- **Unverified:** Google Chrome, Edge and Brave on Windows and macOS have not been tested against the block. Testing them is an early task. If one of them is rejected, browser detection should prefer the ones that pass.
- Pages are fetched one browser launch per results page, sequentially. A 2-page search takes about 15–20 seconds; a search at the 10-page cap takes about 2 minutes. The "first run on add" UI needs a progress state for this.
- The persistent browser profile holds the bot-protection cookies. It must live in the app-data directory, be separate from the user's personal browser profile, and survive app updates.
- The README should keep the personal-use disclaimer from v0.2 (respect the site's terms; the user is responsible for how they use it).
