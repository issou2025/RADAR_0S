## Project Understanding
You need assistance with: 
**[Bug]: Desktop appears finished while async delegation is still pending, then silently returns to Running**

*Project description:*
### Bug Description

Hermes Desktop can show a definitive assistant response and appear finished while a top-level `delegate_task(background=true)` batch is still active. When the full batch later completes, the gateway injects its result as a synthetic message and automatically starts another agent turn. Desktop then switches back to the generic `Running` state even though the user did not send another prompt.

This makes the task look stuck or as if it is responding to itself, and makes it unclear whether the earlier answer was actually final.

Important correction from the original observation: this is **not** a case where Hermes resumed after only one child. The sanitized trace confirms that both subagents completed, waited for each other, and produced one consolidated batch-completion event. The bug is the visible completion/auto-resume lifecycle.

### Steps to Reproduce

Code-level deterministic path (no GUI automation required):

1. Start a session routed through the Desktop/TUI gateway.
2. Dispatch a top-level `delegate_task` batch with `background=true` and at least two tasks.
3. Let the parent agent continue and return a normal `finish_reason=stop` response before the batch completes.
4. The parent turn ends and the visible assistant response appears final, while the delegation remains active in the background.
5. Complete all children so the batch pushes one completion event into the async notification queue.
6. Run `TuiGatewayServer._notification_poller_loop` while the session is idle.
7. Observe that the poller sets `session["running"] = True`, emits `message.start`, and calls `_run_prompt_submit(...)` with the synthetic `[ASYNC DELEGATION BATCH COMPLETE ...]` message.
8. Desktop returns to a generic `Running` state without a new user prompt.

### Expected Behavior

When a visible response is produced while background delegation is still material to the task, the lifecycle should be unambiguous:

- The response/task should remain visibly marked as provisional or pending background work, with a clear indication that Hermes will resume.
- When the batch completes, Desktop should show a distinct status such as “Resuming from completed background delegation,” rather than an unexplained generic `Running` state.
- The consolidated result should still re-enter exactly once and only after all children finish.

Alternatively, Hermes should prevent a conclusive-looking final response when the answer still depends on a pending delegation batch.

### Actual Behavior

- The parent emits a normal, definitive-looking response with `finish_reason=stop`.
- The task appears finished/idle even though background delegation is still active.
- After all subagents finish, Hermes silently starts a fresh full agent turn.
- Desktop changes to generic `Running`, with no new user prompt and no prominent explanation of why the completed-looking task resumed.
- The agent may then perform more tool calls and revise or extend the answer that already looked final.

The behavior follows the current implementation:

- `tools/delegate_tool.py` joins every child in a background fan-out and enqueues one consolidated completion after all finish.
- `tools/process_registry.py` formats the `[ASYNC DELEGATION BATCH COMPLETE ...]` synthetic message.

### Root Cause Analysis (optional)

The automatic fresh turn is intentional and already covered by gateway tests. The user-facing contract around it is incomplete:

1. `delegate_task` tells the parent not to wait, so the parent can emit a conclusive-looking answer while required background work is unresolved.
2. Desktop treats the parent turn as finished once its busy state ends; the pending background state is not durably attached to the apparent final answer.
3. The poller later emits an ordinary `message.start`, without continuation metadata that distinguishes an internal async-delegation resume from a user-initiated turn.
4. Desktop therefore renders the resumed work as generic `Running`, which looks like a stale state or self-triggered response.

Related but non-duplicate issues:

- #70785 tracks a separate Desktop activation race where a submitted prompt disappears from the transcript although the backend executes it. The symptoms are related at the transcript/lifecycle level, but the causes and reproduction paths are distinct.
- #69637 involves the same async-completion-starts-a-new-turn mechanism causing repeated compression timeouts; it is a different symptom.
- #55578 and #53095 cover older wrong-session/rendering failures and are not exact duplicates of this lifecycle issue.

### Proposed Fix (optional)

Minimal compatible fix that preserves asynchronous delegation:

1. Carry an explicit continuation cause and batch metadata (for example, `continuation_reason: "async_delegation"`, batch ID, completed/total counts) from the notification poller into gateway events.
2. Render a persistent pending-background indicator after the parent turn and a distinct “resuming from completed delegation” state when the internal turn begins.
3. Strengthen agent guidance: if the user-facing result materially depends on a pending batch, do not present the current response as final; explicitly call it provisional and state that the task will resume automatically.
4. Add an integration regression covering: visible parent response + active batch → explicit pending state; all children complete → exactly one internal continuation with an explicit reason, not an unexplained generic `Running` transition.
