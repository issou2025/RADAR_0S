# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[Ticket]: just all-checks runs clippy with --fix, so it cannot reproduce CI's just lint verdict**

*Project description:*
### Type

Bug

### Summary

We need `just all-checks` (the documented pre-PR gate) to end on the same verdict as CI's `clippy` job, because today it structurally cannot. `all-checks` runs clippy with `--fix --allow-dirty` (`justfile:68`); CI runs `just lint`, the same command **without** those flags (`justfile:157-158`, `.github/workflows/ci.yml:514-529`). Under `--fix`, clippy exits 0 on code that plain clippy fails with `-D warnings`.

Expected result:

> `just all-checks` exits non-zero whenever `just lint` — the exact command CI runs — would exit non-zero, for every lint in the `-D warnings` set.

### Intent

`CLAUDE.md:21-24` documents `just all-checks` as "the canonical formatting + lint pass; run it before opening a PR." A developer who runs it and sees exit 0 reasonably concludes CI's clippy job will pass. That inference is false today, and it has already cost a red `main`. The intent is to make a green `all-checks` actually predictive — not to relitigate whether `--fix` belongs locally.

### Source of truth (links)

- #772 (merged 2026-08-27) — introduced 3 `clippy::empty_line_after_doc_comments` violations that turned CI's clippy job red on `main`, and therefore on every branch cut from it.
- #773 — the minimal fix, whose own body names this gap and explicitly declines to fix it inline ("Flagging rather than fixing here; happy to open a ticket"). **Open, not merged, as of writing.**
- Prior art, both closed and both about a *different* `all-checks` problem (pre-existing failures rather than flag divergence): #468, #423.
- `justfile:64-70` (`all-checks`), `justfile:157-158` (`lint`), `justfile:25` (`clippy_allow`), `.github/workflows/ci.yml:514-529`, `CLAUDE.md:21-24`.

### Current Behavior

`justfile:64-70`:

```
all-checks:
	just _fmt
	cargo fix --workspace --exclude embedded_flutter_native --allow-dirty
	cargo clippy --workspace --exclude embedded_flutter_native --all-targets --fix --allow-dirty -- -D warnings {{clippy_allow}}
	cargo check --workspace --exclude embedded_flutter_native --all-targets
	cargo deny check
```

`justfile:157-158`:

```
lint:
	cargo clippy --workspace --exclude embedded_flutter_native --all-targets -- -D warnings {{clippy_allow}}
```

`.github/workflows/ci.yml:528-529` confirms the clippy job runs `just lint`, not `all-checks`.

**The only divergence is `--fix --allow-dirty`.** Workspace scope, `--exclude`, `--all-targets`, `-D warnings` and the `clippy_allow` list are byte-identical between the two recipes. There is no other flag drift.

**The masking mechanism is not what it looks like, and it is worse.** The obvious theory — "`--fix` silently repairs the violation, so the check passes" — is wrong for this lint. `clippy::empty_line_after_doc_comments` has **no machine-applicable rewrite**: under `--message-format=json` both violation spans report `"suggested_replacement": null, "suggestion_applicability": null`. Running `--fix` left the file byte-for-byte unchanged (`git diff` empty) and **still exited 0**, because `--fix` mode demotes what would be a `-D warnings` *error* to a non-blocking *warning* whenever the crate still compiles, independent of whether it could rewrite anything.

That is worse than silent auto-repair: there is not even a working-tree diff for a developer to notice. `all-checks` simply reports success on code that will fail CI.

### Expected Behavior

`just all-checks` exits non-zero on any code where `just lint` would, across the full `-D warnings` + `clippy_allow` set — including lints clippy cannot auto-rewrite. Autofix convenience may remain per the options below, but the recipe's final exit code must track `just lint`'s verdict.

### Acceptance Criteria

- [ ] Given a violation clippy cannot auto-rewrite (e.g. `empty_line_after_doc_comments`), when a developer runs `just all-checks`, then it exits non-zero.
- [ ] Given a violation clippy *can* auto-rewrite, `all-checks` never exits 0 while `just lint` on the resulting tree would exit non-zero.
- [ ] `just lint` and the CI clippy job are unchanged — this ticket does not touch the CI-facing recipe.
- [ ] The chosen fix is documented in the justfile comment above `all-checks`, and in `CLAUDE.md:21-24` if user-facing behaviour changes.
- [ ] `all-checks` still runs `_fmt`, `cargo fix`, `cargo check`, and `cargo deny check` as today.
- [ ] Verification evidence provided: repro commands and output, before and after.

### Technical Context

- `justfile:9-25` — `clippy_allow`, shared by both recipes; no change needed.
- `justfile:31-70` — `all-checks`, including its existing block comment about `--exclude embedded_flutter_native` and the no-`--all-features` decision. A verification step should sit after the clippy `--fix` line and ideally after `cargo check` (so a fix that broke compilation is caught first), before `cargo deny check`.
- `justfile:155-158` — `lint`. **Reuse it verbatim (`just lint`) rather than re-deriving the clippy invocation**, so the two cannot drift again.
- `just` recipes fail fast — each line is its own `sh -c` and `just` aborts on first non-zero — so appending `just lint` needs no extra error handling.

**Options** (maintainer decision; recommendation given, not settled):

1. Append a no-`--fix` `just lint` pass at the end of `all-checks`, so the recipe ends on CI's verdict. Simplest, reuses the CI recipe verbatim, keeps autofix convenience. Cost: a second clippy pass (cheap on a warm incremental cache).
2. Make CI and local share one recipe with `--fix` opt-in via a variable. Most principled, guarantees no drift by construction. Cost: more justfile surgery.
3. Drop `--fix` from `all-checks` entirely; add a separate `just lint-fix`. Cleanest semantics, removes the working-tree-mutation surprise. Cost: a workflow change for anyone relying on autofix.

I lean toward option 1 — smallest change that makes the documented gate honest, and it reuses `just lint` so the drift cannot recur.

### Risks

- **Working-tree mutation (flagged, not reproduced for this incident).** `cargo fix`/`clippy --fix` mutate in place, so a developer could end up with unexplained modifications they commit or discard without noticing. Not reproducible for *this* lint — it has no rewrite, so no diff appeared. A plausible general risk of `--fix`-based gates; option 3 removes it, option 1 does not.
- Running clippy twice adds wall-clock time. Should be cheap on a warm incremental cache, but worth a gut-check against how often `all-checks` runs in a tight loop.
- `all-checks` will start failing more often — by design. Developers who relied on `--fix` quietly absorbing lint drift will need to fix by hand or run autofix separately. That is a workflow change, not just a bugfix, and warrants the CLAUDE.md update above.

### Test Plan

- Reproduce the gap: on a tree with an `empty_line_after_doc_comments`-style violation, run `just lint` (expect non-zero) then `just all-checks` (expect 0 today) plus `git status`/`git diff` (expect no changes, confirming exit-code-only masking).
- After the fix: reintroduce the violation, confirm `just all-checks` exits non-zero.
- Confirm a clean tree still passes `all-checks` exit 0, unchanged.
- Confirm `just lint` and CI's clippy job behave identically to before.
- Run `all-checks` end-to-end once on the real workspace; report before/after duration in the PR.
- If option 1 or 2: verify the final pass re-checks the post-`--fix` tree, not a stale incremental result.
