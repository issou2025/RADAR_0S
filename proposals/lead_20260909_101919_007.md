# Project Proposal — Quantity Takeoff

## Project Understanding
You need assistance with: 
**One warm AVAudioEngine per process with tap fan-out; transcribers subscribe instead of owning engines**

*Project description:*
## What and why

Every transcriber allocates its own AVAudioEngine, readiness runs another, hands-free runs a detector engine alongside capture. Each start pays allocation + prepare + start (3 s cold / ~0.7 s warm reported). Own one engine per process, prepared at launch, with a fan-out tap; a recording start becomes 'subscribe' when it is already running.

## Proposed change

New CaptureEngine (SpeakiOS) wrapping one AVAudioEngine and one tap copying into PCMBufferPool and dispatching to registered sinks (ring, converter, recorder, VAD); iOSLiveTranscriber, SharedClientLiveTranscriber, OpenAIRealtimeLiveTranscriber, KeyboardReadinessAudioSession and the hands-free detector register sinks; rebuild lazily on AVAudioEngineConfigurationChange; reference-counted start/stop; engine stops when nothing subscribes.

## Impact

| | Before | After |
| --- | --- | --- |
| Latency | — | Est. 50-250 ms per start in-app; 0 ms engine cost when readiness/hands-free already runs it |
| Reliability | — | Ends the two-engines-at-once hands-free state and centralises configuration-change handling (defect 8) |

## Effort

L: touches five capture owners; do after I32/I30

## Risk

Shared-engine bugs (format changes, sink leaks); keep the mic indicator honest

### Verification

Checked by three adversarial reviewers (each trying to refute it):

| Lens | Verdict | Score |
| --- | --- | --- |
| Platform feasibility | feasible-with-caveats | 6.5/10 |
| Codebase fit | feasible-with-caveats | 4/10 |
| User value / honesty | feasible-with-caveats | 3/10 |

**Platform feasibility** — Legal and consistent with Apple's model. The one hard constraint is documented: 'You can install only one tap on any bus' (AVAudioNode.installTap), which is why the fan-out must be app-side (one tap → `PCMBufferPool` → N sinks) — exactly what the mechanism proposes; taps can be installed/removed while running ('You can install and remove taps while the engine is in a running state'), and the tap block runs off-main. Multiple engines per process are not forbidden (hands-free already runs a detector engine alongside the capture engine; the readiness engine runs alongside the transcriber engine during the swap), so this is an architectural choice, not a policy requirement. Where it earns its keep on Apple's terms: `AVAudioEngineConfigurationChange` ('When the audio engine's I/O unit observes a change to the audio input or output hardware's channel count or sample rate, the audio engine stops, uninitializes itself… The app must reestablish connections') is handled by nobody today (grep: no observer; taps bound to the start-time format at SharedClientLiveTranscriber:305-314, OpenAI:361-365, iOSLiveTranscriber:185-192) — one owner can handle it once, and it eliminates the readiness→capture engine swap that creates the I32 gap. Caveats that cap the score: (1) the headline 3 s cold / 0.7 s warm figures are from one Flutter plugin on iOS 26.5 and Apple DTS's ~200 ms `AudioOutputUnitStart` floor applies per activation regardless of engine reuse, so the saving is engine allocation (tens to low hundreds of ms), not the session-activation cost; (2) a warm engine is dead weight on the cold headless launch that dominates Action Button use; (3) the engine's input format is fixed at `prepare()`; a route flip between readiness options (`.allowBluetoothHFP`) and recording options (`[.allowBluetooth,.defaultToSpeaker,.allowBluetoothA2DP]`) will stop the shared engine mid-swap unless the option sets are unified (same finding as the dossier's quick win); (4) a single tap feeding several sinks must add/remove sinks without locking on the real-time thread and the 4-deep pool must be resized for fan-out; (5) `SonioxRealtimeTTSClient` owns a playback engine and should stay separate; (6) media-services-reset must re-create the engine. Battery/thermal: a prepared-but-stopped engine costs nothing; a running one is already the accepted readiness posture. No App Review angle.

_Caveats:_ Effort L for a gain that is unmeasured and absent on cold launches; sequence it after telemetry (dossier quick win 3) and after I32/I34 option unification. Keep the TTS playback engine out of it.

**Codebase fit** — Not implemented; the opposite is true. Six AVAudioEngine owners exist in SpeakiOS: iOSLiveTranscriber:39, SharedClientLiveTranscriber:35, OpenAIRealtimeLiveTranscriber:85, iOSBatchTranscriber:12, IOSHandsFreeDictationCoordinator:205 (a second engine running alongside the transcriber's), KeyboardReadinessAudioSession:395, plus a playback engine in SonioxRealtimeTTSClient:123. Each transcriber is a fresh object per recording (IOSTranscriptionSession.makeBackend :116-166), so the engine is re-created every session. There is also no AVAudioEngineConfigurationChange handling anywhere on iOS (grep: only SpeakApp/HandsFreeDictationCoordinator.swift:360 on Mac), and three independent AudioSessionManager instances wrap the single AVAudioSession (TranscriptionRecordingService:34, ContentView:41, KeyboardInstantDictationCoordinator:104), each transcriber calling deactivate() on stop/cancel/interruption (iOSLiveTranscriber:347,396,441; SharedClient:147,173). A shared engine would immediately collide with that: one backend's deactivate() tears down the session under the shared engine, and every backend assumes it owns inputNode tap 0. Why the payoff is smaller than claimed: the expensive parts on iOS are session activation and engine.start against the HAL, not AVAudioEngine allocation; a 'warm' (prepared, not started) engine reads inputNode format at prepare time and gets a configuration change when the category is later set, forcing re-prepare; and on the dominant headless journey the process is cold, so nothing can be warm. The Mac precedent (SpeakApp/CaptureWarmCoordinator + SpeakCore/CaptureWarmUp state machine) is platform-neutral in SpeakCore and reusable, but the Mac stages a recorder file, not an engine shared by transcribers. Where the idea is genuinely right: the keyboard handoff. Docs/ios-keyboard-instant-dictation.md:61-62 says the app 'swaps the idle audio tap for the selected transcriber', but the code stops the readiness engine and starts a different one (:223 then startRecording); a narrow CaptureEngine used by the readiness session and the transcriber on that path would make the code match the recorded design, remove the engine swap and the category re-set, and make I32 cover the whole gap. Same for hands-free, which would stop running two engines. As written (one engine for all backends, tap fan-out, PCMBufferPool sinks) the effort is L and touches every capture file; a keyboard+hands-free-only sink abstraction is M. Regression risks: sink leaks keeping the mic hot (orange dot, App Review 2.5.4); a backend stopping the engine while another sink is live; format changes mid-session unhandled (already unhandled today, brief item 8); interruption/deactivate ownership. Tests needed: protocol-abstracted engine so unit tests can assert sink add/remove/fan-out and that stop of one sink never stops another; LivePCMBufferPoolTests (SpeakAppTests) shows the pool is testable; device matrix for AirPods connect/disconnect mid-session.

_Caveats:_ Effort L as written and it must first settle AVAudioSession ownership across three AudioSessionManager instances. Recommend the narrow version (keyboard readiness + hands-free share one engine with sink swap) as the shippable PR; the full fan-out engine is a refactor, not a latency fix, for the Action Button path.

**User value / honesty** — This is an enabling/architectural change dressed as a speed win. Direct user-feelable gain is limited: the dossier's own estimate for AVAudioEngine allocation+start is 30-250 ms, and the research figure cited for 'warm engine' (3 s cold vs 0.7 s warm) comes from a Flutter `record` plugin issue on a different stack, not from AVAudioEngine on iOS; quoting it here exaggerates the benefit. On the headline Action Button cold-launch journey there is nothing to keep warm — the engine must be created after launch regardless. The real value is confined to (a) the keyboard handoff, where a shared engine removes the readiness-to-transcriber swap gap that I32 alone cannot close, and (b) hands-free, where two engines currently run concurrently and the dossier calls that fragile. Against that, the effort is L across five engine owners (iOSLiveTranscriber, SharedClientLiveTranscriber, OpenAIRealtimeLiveTranscriber, iOSBatchTranscriber, readiness, hands-free detector) and the risk is a reliability regression on capture that works today: format/route changes, sink leaks, and tap fan-out semantics under AVAudioEngineConfigurationChange, which no iOS transcriber handles now. The user would not notice a shared engine per se; they would notice the keyboard swap gap disappearing (I32-adjacent) and any new bug. A narrower change — make the readiness engine the capture engine for the keyboard path only (one CaptureEngine used by KeyboardReadinessAudioSession and the transcriber it hands to) — delivers nearly all the felt value at a fraction of the blast radius. Rate as 'enabling', not direct.

_Caveats:_ Treat as an enabler for I32/I34 on the keyboard path; do not sell it as a latency win for Action Button. If pursued, scope to keyboard readiness + transcriber first, add configuration-change handling, and measure engine.start cost on device before and after.

**Must be true before this can be called done:**

- Device timing shows engine allocation/prepare is a material share of trigger→first buffer when the process is resident (instrument before building; RecordingStartTimeline exists in SpeakCore); the option sets for readiness and recording are unified first so the shared engine survives the handoff; the fan-out sink list can be mutated without RT-thread locks.
- AVAudioSession ownership is centralised first, every backend gives up direct AVAudioEngine access in favour of a sink API, and configuration-change handling is added, none of which exists today.
- Per-recording engine creation would have to cost hundreds of milliseconds on real devices (the dossier says 30-250 ms), and the shared engine would need to survive route/format changes at least as reliably as today's per-transcriber engines.
