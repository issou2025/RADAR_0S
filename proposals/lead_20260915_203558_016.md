<p><strong>Filed against:</strong> MTPLX App 2.11.2 (build 2011020), CLI 2.11.2, runtime-venv app-managed (all "latest" per About panel) — M5 Max, 128 GB, macOS 26.6.2.<br>

<h2 data-heading="Title">Title</h2>
<p><strong>A crash-wedged MTPLX daemon (socket alive, <code>/health</code> dead) is classified as "another app" → app moves off the configured port, PERSISTS the fallback, and every client pinned to the configured port is silently stranded</strong></p>
<h2 data-heading="Summary">Summary</h2>
<p>When MTPLX hard-freezes mid-inference, the daemon process can leave its listener on the configured port while <code>/health</code> no longer answers. On next launch, <code>PortPreflight.classify</code> maps "probe timeout" to <code>.foreign</code> ("another app") — <code>PortPreflight.swift</code> L53-56: <em>"Timeouts and protocol garbage both mean 'occupied by something we cannot use'"</em> — and <code>classifySettled</code>'s 5-second re-probe window (L79-96, added for #409) is designed for a <em>draining</em> daemon that recovers; a <em>wedged</em> one never clears the window and never stops being <code>.foreign</code>. <code>MTPLXBackendStore.preflightConfiguredPort</code> then falls into the branch whose own doc comment (L995-1004) says: <em>"CLI-started MTPLX server or a foreign app: never touch someone else's process; move to the next free port, persist it, and surface a one-line banner."</em></p>
<p>Three facts make this a defect rather than a feature:</p>
<ol>
<li><strong>The occupant is probably our own wedged daemon, not a foreign app.</strong> The responsive-<code>.mtplxServer</code> path reads process identity (startup PID, L1035-1043) and replaces a stale app-owned daemon <em>in place</em>. The unresponsive path never checks identity — a timeout is adjudicated as foreignness. So the more severely MTPLX has crashed, the more certainly the escape hatch fires.</li>
<li><strong>The relocation is persisted</strong> (<code>settingsStore.save</code>, L1064; same in <code>remediatePortConflict</code> L1120). A one-restart accident becomes permanent: after the zombie is gone, MTPLX still serves on the fallback port and is "Running" in the dashboard while deaf to every pinned client.</li>
<li><strong>The project's own CLI already declares the opposite policy.</strong> <code>mtplx/commands/public.py</code> (~L13470): <em>"A port the user CONFIGURED must never be silently relocated… the app's persisted port now counts as configured too"</em> — implemented via <code>app_configured_port()</code> + "Keeping the configured port … (never moved silently)". The Swift app path above has no equivalent guard (no configured-port check exists anywhere in <code>MTPLXBackendStore.preflightConfiguredPort</code>). The report's core ask: <strong>make the app enforce the policy its own CLI already ships.</strong></li>
</ol>

<h2 data-heading="Live incident (2026-09-15, M5 Max / 128 GB / macOS 26.6.2, app 2.11.2)">Live incident (2026-09-15, M5 Max / 128 GB / macOS 26.6.2, app 2.11.2)</h2>
<ol>
<li>Chat lane on <code>:8001</code>, model <code>mtplx-flash-next-optimized-speed</code>, 262K context, during a 13-subagent batch classification job. Logs show "no stream output for 149s" (wedge), then hard OS freeze + reboot. Post-reboot, a stale listener still held :8001 — the <em>only</em> diagnostic clue was a one-line "port 8001 in use" flash during the chaos; without watching the screen at that second, undetectable.</li>
<li>On restart MTPLX rebound on <strong>:8003</strong> (fallback after 8001/8002), dashboard showing green "Running".</li>
<li>The downstream consumer — an agent connector configured for <code>:8001</code> (Hermes, via <code>http://host.docker.internal:8001/...</code>) — got connection-refused on 8001 and silence on 8002/8003. From the outside, indistinguishable from "the agent broke": engine Up in its own UI, unreachable on its configured address. Total, silent, <strong>persistent</strong> contact loss (persisted setting).</li>
<li>Recovery required user intervention exactly as designed-to-fail: full app Stop (to release the zombie listener) + manual port reset to 8001. Nothing self-heals.</li>
</ol>
<h2 data-heading="Reproduction (clean state; offer to run with traces)">Reproduction (clean state; offer to run with traces)</h2>
<ul>
<li><strong>A (minimal):</strong> bind any dummy TCP listener on the configured port (e.g. <code>nc -l 8001</code>), launch the app → expect: engine on 8002, settings persisted, one-line notice only.</li>
<li><strong>B (wedge-true):</strong> start normally; mid-inference <code>kill -STOP &#x3C;daemon pid></code> so the socket accepts but <code>/health</code> times out; restart the app → expect same fallback+persist, and the log will call MTPLX's own frozen process "another app". This is the shape of the 09-15 incident. <em>(Reporter's live experience is B; neither A nor B has been executed as an isolated repro yet — offered below, stated here as design-inferred, not verified.)</em></li>

<h2 data-heading="Why it matters">Why it matters</h2>
<ul>
<li><strong>The consumer class is MTPLX's advertised audience.</strong> Agent/automation users pin <code>:8001</code> in connector config; a pinned client cannot discover a relocated port. For them "helpful" relocation is 100% failure, not degraded service. The project tags its own releases "the agent-reliability release" — this is the anti-pattern.</li>
<li><strong>Misdiagnosis is the product cost.</strong> Both reporters (this incident and #409) first suspected their <em>client</em>. Time spent debugging a phantom beats the cost of a loud failure would have been many times over.</li>
<li><strong>The settle window cannot do the job it's given.</strong> Timeout-vs-drain is not resolvable by more probing of the same channel; it's resolvable by process identity — which the codebase already knows how to get, on the other branch.</li>
</ul>
<h2 data-heading="Suggested fix (cheapest first)">Suggested fix (cheapest first)</h2>
<ol>
<li><strong>Mirror the CLI guard in the Swift path:</strong> if the port is user-configured/persisted, a non-adoptable occupant → keep the port, fail the launch with actionable copy ("stop the stale listener on 8001 and retry"), never relocate silently. One function, policy already written.</li>
<li><strong>Identify own-wedged-daemon on the timeout path:</strong> socket accepts + <code>/health</code> timeout + last-app-launch PID/marker matches → route into the existing <code>terminateExternalDaemon</code> replace-in-place path (it already handles the responsive case) instead of the foreign-app flight.</li>
<li>If any fallback mode survives, make it opt-in, <strong>non-persisted</strong>, and a persistent banner until acknowledged — not a sub-second flash.</li>
<li>Update the SYNC PAIR comment to bind both sides to one test (a configured-port test exists in <code>ServerURLsTests.swift</code>; nothing equivalent guards the app path).</li>
</ol>
<p><strong>Offered:</strong> reporter can run repros A and B against 2.11.2 with pre/post logs and settings-diff, and post traces in-thread — say the word in the issue.</p>
<h2 data-heading="Workaround in use (this machine, since 09-15)">Workaround in use (this machine, since 09-15)</h2>

Recorded in reporter runbook (<code>apple-silicon-llm-stack</code> skill, <code>Stack-Snapshot.md</code> §2026-09-15).</p>
