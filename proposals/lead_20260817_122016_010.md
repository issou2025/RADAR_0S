# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat: step-level file dependencies that Dagu transfers to the worker**

*Project description:*
## Is your feature request related to a problem?

When using Dagu with distributed workers, DAG definitions can be executed remotely, but files referenced by a step are not transferred to the worker.

For example, a DAG may contain:

```yaml
steps:
  - name: Backup
    run: |
      & ./scripts/install.ps1
      node ./scripts/backup.mjs
    shell: powershell
```

If the selected worker does not already have those files in its local filesystem, the step fails.

This becomes especially problematic when the scripts are implementation details of a specific DAG. They logically belong next to the DAG, but currently there is no simple way to declare that the step depends on those files and have Dagu send them to the worker.

## Describe the solution you'd like

I would like steps to support declaring file dependencies that are automatically transferred to the worker together with the step/DAG execution.

For example:

```yaml
steps:
  - name: Backup
    run: |
      & ./scripts/install.ps1
      node ./scripts/backup.mjs
    shell: powershell

    dependencies:
      - ./scripts/install.ps1
      - ./scripts/backup.mjs
```

When the step is dispatched to a worker, Dagu would:

1. Resolve the dependencies relative to the DAG file.
2. Transfer those files to the worker.
3. Preserve their relative directory structure.
4. Make them available from the step's working directory.

Conceptually:

```text
Coordinator:

dags/backup/
├── dag.yaml
└── scripts/
    ├── install.ps1
    └── backup.mjs

        ↓ dispatch

Worker temporary directory:

├── scripts/
│   ├── install.ps1
│   └── backup.mjs
└── ...
```

It would also be useful if directories or glob patterns could eventually be supported:

```yaml
dependencies:
  - ./scripts/**
  - ./config/**
```

But support for individual files alone would already solve the main problem.

## Describe alternatives you've considered

### Git checkout inside the DAG

The DAG can clone or pull a repository before executing the actual step.

This works, but adds infrastructure/bootstrap logic to every DAG and requires Git credentials and repository access on workers.

The files may also be very specific to a single DAG, so having the DAG restore its own implementation before every execution feels unnecessary.

### Dagu Actions

Packaged Actions can contain additional files, but they are better suited for reusable functionality.

In this case the scripts are implementation details of a particular DAG, so converting the DAG-specific scripts into reusable Actions introduces another abstraction only to make the files transferable.

### Inline scripts

Scripts can be embedded directly inside the DAG.

This is practical for small shell scripts, but not for complex scripts or programs implemented in PowerShell, Node.js, Python, compiled applications, or projects containing multiple files.

### Shared filesystem

All workers could access the same shared filesystem.

This creates an additional infrastructure dependency and is not ideal for distributed workers running on different machines or operating systems.

### Pre-synchronizing files to every worker

The files could be synchronized independently before Dagu starts.

This works, but requires maintaining a separate file distribution system outside Dagu and ensuring that every worker has the correct version before execution.

## Use case

I use Dagu as a distributed automation system with multiple workers on different machines.

Some DAGs depend on scripts or programs that are specific to that DAG, for example:

```text
backup/
├── dag.yaml
└── scripts/
    ├── prepare.ps1
    ├── backup.mjs
    └── cleanup.ps1
```

These files are part of the DAG implementation and should ideally live together with the DAG.

The coordinator can choose any compatible worker to execute the DAG, so I cannot rely on a particular absolute path or assume that every worker already contains those files.

Being able to declare:

```yaml
dependencies:
  - ./scripts/**
```

would make a DAG self-contained from an execution perspective while still allowing the implementation to remain in normal source files.

This would also make distributed execution behave more naturally: the DAG describes both **what needs to run** and **which local resources are required to run it**.

## Additional context

I am not specifically looking for Git integration here.

The important capability is transferring DAG-local files to the worker selected for execution.

For example, something like:

```yaml
steps:
  - name: Backup
    shell: powershell

    run: |
      & ./scripts/install.ps1
      node ./scripts/backup.mjs

    dependencies:
      - ./scripts/install.ps1
      - ./scripts/backup.mjs
```

could internally result in Dagu packaging those dependencies, sending them along with the execution request, extracting them into the worker's temporary working directory, and then executing the step normally.

This would be especially useful for distributed/shared-nothing worker setups where workers intentionally do not share a filesystem with the coordinator.
