# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**pyrevitlib: sessionmgr.find_all_commands() control_id is not Revit's ribbon command id, so LookupCommandId and PostCommand fail**

*Project description:*
## Summary

`sessionmgr.find_all_commands()` returns command objects whose `control_id` is meant to identify the ribbon button. Passing that value to `UI.RevitCommandId.LookupCommandId` returns `None`, so `PostCommand` cannot run the button. The ids Revit actually registers differ in two ways:

- They leave out the stack name.
- The number of `CustomCtrl_` prefixes depends on the parent type.

This blocks tests and agent sessions that need to click a real pyRevit button through `PostCommand`.

## Steps to reproduce

Revit 2026.1, IronPython 2.7.12, develop at 39774b734. Run this in a Revit session:

```python
from pyrevit.loader import sessionmgr
from pyrevit import UI
c = [c for c in sessionmgr.find_all_commands(cache=False) if c.name == "Sync Views"][0]
result = (c.control_id, UI.RevitCommandId.LookupCommandId(c.control_id) is None)
```

## Expected

`LookupCommandId(c.control_id)` returns the button's `RevitCommandId`, so `uiapp.PostCommand(...)` runs it.

## Actual

`LookupCommandId` returns `None` for every command tried:

| Command | `control_id` reported | Id that works (UI Automation `AutomationId` on the ribbon button) |
|---|---|---|
| Sync Views | `CustomCtrl_%CustomCtrl_%CustomCtrl_%pyRevit%Toggles%toggles2%Sync Views` | `CustomCtrl_%CustomCtrl_%pyRevit%Toggles%Sync Views` |
| Reload | `...%pyRevit%pyRevit%tools%Reload` | `CustomCtrl_%CustomCtrl_%pyRevit%pyRevit%Reload` |

Two more working ids for comparison:

- `CustomCtrl_%CustomCtrl_%CustomCtrl_%pyRevit%Analysis%Inspect%Custom Properties`
- `CustomCtrl_%CustomCtrl_%CustomCtrl_%pyRevit%Modify%Match%Match History Clipboard`

## Suggested change

Build `CommandControlId` the way Revit builds the `AutomationId` of the ribbon item: leave stack names out of the path and take the `CustomCtrl_` prefix count from the parent chain, not a fixed count. If matching Revit's id is not wanted, document the rule instead.

The same id is also used for `findRibbonItem` in `scriptruntime.cs` and shown as the "copy control id" tooltip, so those two uses need a check when it changes. How they behave with the current format has not been verified.

Thoroughly investigate impact. Why was a different way to build the id chosen in the first place?

## Investigation findings (update)

Checked on Revit 2026.1, IronPython 2.7.12, develop at 3e1c77de3, by comparing every `find_all_commands()` control id with the `Id` of each `Autodesk.Windows` ribbon item (461 commands).

**Why the id is built this way.** The id is meant to equal the ribbon item id Revit registers (introduced in d71fd68e8, 2019). It feeds `findRibbonItem` (the `__uibutton__` builtin), the "Copy Control Id" menu item and `CommandTypeGenerator`. `LookupCommandId` is not involved in the id's design; it simply returns `None` when the id is wrong. Two separate causes make the id wrong:

1. **Stack names (oversight in the C# loader, fixed in #4038).** The Python loader passes the parent id through for a stack (`GenericStack.control_id`). The C# port (2bc67c86a, January 2026) added `Stack` to the pulldown branch of `ParsedExtension.CollectInto`, so it added the stack name and an extra `CustomCtrl_`. The test asserted the wrong id and carried a comment saying it "may need adjustment". Result before the fix: 208 of 461 control ids matched a ribbon id. With #4038: 382 of 461. Sync Views and Reload resolve through `LookupCommandId` and `findRibbonItem`.
2. **Panel title versus folder name (still open).** `PanelBuilder.CreatePanel` creates the ribbon panel with the localized `bundle.yaml` title, so Revit's ids contain the title; the control id uses the folder name. In English only `Drawing Set.panel` differs (title `Drawing set`), about 67 commands. 14 of 19 bundle files with a title use localized titles, so other UI languages are likely affected in many more panels (not verified, only the English UI was run). User extensions with a differing title are affected too. Tabs were not checked.

Smaller remaining case: 7 `createsection%Section_Tools` commands are a pulldown nested in a split button and have no ribbon item at all, most likely a Revit limitation.

**Prefix count.** The suggestion to derive the `CustomCtrl_` count from the parent chain matches what the code already does for pulldowns and split buttons (children get one extra `CustomCtrl_`); only stacks were wrong. Every pulldown and split-button child in the pyRevit extensions matched Revit's id.

**Duplicates.** Revit rejects a second item with the same name within one panel (stacks included) and within one pulldown (`The name already exists`). The same name in different panels or pulldowns stays distinct because the id carries tab, panel and pulldown. There are no duplicate control ids among the 461 commands.

**Cache.** The id is embedded in the cached extension assemblies and the cache key did not cover the id logic, so #4038 also bumps `CommandTypeGeneratorSchema`.

**Not verified:** running a button through `PostCommand`, other UI languages, tabs.

Status: the stack cause is fixed in #4038 (referenced as "Part of" this issue). The panel-title cause is still open.
