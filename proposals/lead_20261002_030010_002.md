# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Fidelity levels: let a bundle publish MAX, MED and MIN versions of a deliverable, chosen at import (consumer side)**

*Project description:*
> **Status, 2026-10-01.** This is now the map (`wayfinder:map`) of the **consumer side** of the effort: what the host plugins do with published **fidelity levels** (MAX, MED, MIN). That term replaces "scale" and "tier" below. Deriving the levels, the manifest fields that publish them, and whether the platform builds every host's files and every level at procurement are the platform's pipeline work, tracked on the platform's side. The decisions so far are in the design-note comment. Children: #284 (the inventory) and PR #289 (the glossary entry).

**Hosts:** Revit and Unreal, and any later host. **Found in:** #258. **Nothing is implemented here.** This issue describes an effort a later session takes on as its own piece of work.

**What this asks for.** A general way for a bundle to offer **several scales** of what it delivers, so the user chooses one at import:

- tree density;
- imagery and texture resolution;
- how many subdivisions are cut;
- anything else whose cost grows with its size.

This should not be a Revit-only or a tree-only fix. The work **starts with an inventory** of what each plugin imports, and when, so that we can decide where several scales make sense.

## 1. What we ran into

All figures below are from order `4276ef78` on one machine, measured for #258. Its comment "What each box in the Revit import costs, per version" holds the full on/off matrix.

**Revit, every checklist box ticked**

- About **37 to 42 minutes** in the layers phase (the importer with no window), as the mean per version across 2025, 2026 and 2027.
- **44 to 51 minutes** through the real import window.
- The target in #258 is under 5 minutes.

**With the subdivision layers starting unticked** (PR #282, merged)

- Land use, land cover and road subdivisions start unticked.
- The 2025 default import measured **301 s**.
- **Planting took 220 s of that, for 19,755 trees.** Trees are now most of what is left.

### Why the plugin cannot make the trees cheaper

- Revit charges about **8 to 11 ms per tree** at the commit, in 2025 and 2027.
- **The cost is per tree, not per commit.** In Revit 2027, 1,000 trees per commit cost the same per tree as 200 (7.9 against 7.7 ms).
- **Batch creation did not lower it.** `NewFamilyInstances2`, timed against one call per tree, was 7% cheaper on average in 2027 and no cheaper in 2025, both inside the spread between repeat runs. The note on the chunk size in `revit/src/MantlePlace.Revit.Core/ImportChunking.cs` records both results.
- So **fewer trees is the only lever proven so far.** Planting time follows the tree count. The table below is an estimate, not a measurement. It scales the planting step measured in full imports (3:46 to 4:23 for 19,755 trees, so about 11 to 13 ms per tree all in) by the tree count. The commit alone, at 8 to 11 ms per tree, would give 2:38 to 3:37 at full scale.

| Trees kept | Count | Planting, about |
|---|---:|---|
| 100% | 19,755 | 3:40 to 4:20 |
| 50% | 9,900 | 1:50 to 2:10 |
| 25% | 4,900 | 55 s to 1:05 |

- **Import time is not the only cost.** Every tree is an element in the user's model, and it weighs on view regeneration, file size and every later save, long after the import.

### The subdivisions

- Each land use, land cover, water and road polygon becomes one toposolid subdivision. On this order that is 405 subdivisions, 344 of them roads.
- **Revit rebuilds the terrain's relations at each subdivision commit, so each cut costs more as more exist.**
- Unticking **road subdivisions** alone saves **19 to 32 minutes**.
- Unticking **land cover** saves **19 to 25 minutes**: 4 to 10 times its own step, because roads and land use become much cheaper without it.

### Other costs

| Step | Cost |
|---|---|
| Imagery drape | About **15 minutes** in 2026 and 2027 while any subdivisions exist; about 2 s with none |
| Planting | About **4 minutes** with every box ticked (3:46 to 4:23) |
| Context buildings | About 35 to 45 s |
| Site model | About 35 to 45 s on a cold conversion; about 4 s on a repeat import |
| Terrain, contours, centrelines, water | Seconds each |

**Unexplained so far.** In 2026 and 2027, the site context view step takes about **3 to 4 minutes** in every run where the drape and the road subdivisions are both ticked, and under a minute when either is unticked. That belongs to #258, not here. It is listed so the inventory does not count it as a cost of either layer.

## 2. Why the plugin may not thin the data itself

The repository's boundary is that **the plugins apply pre-derived values and never derive them** (root `CLAUDE.md`, "The boundary that keeps this client thin"; `HPS-33`).

- Choosing which trees, polygons or pixels survive by clustering, density maths, area thresholds or simplification is **derivation**. #147 already names "thinning a set" as refused at review.
- A naive "keep every Nth row" in the plugin is borderline at best. It is also uneven: the outcome depends on the order the platform happened to write the rows in, which no contract states. The result would be dense patches and bald patches.

**The principle:**

- **The platform derives scale-ordered content.**
- **The bundle publishes it.**
- **The plugins only choose a published scale and apply it verbatim.**

## 3. A possible solution, to sketch rather than finalise

### What the manifest already publishes (MPB 1.8.0)

No published field offers a choice of scale yet, but several are precedents for one:

- `landcover.tree_points.point_count`, and `hosts.unreal.foliage_points.point_count` for the same trees: **the tree cost driver is already published.**
- `landcover.tree_points.truncated_to_tallest`: present only when the platform capped the layer, keeping the tallest. That is **one published scale today**, chosen by the platform, by a ranking it already computes.
- `buildings.decimated` and `hosts.revit.surface_dxf.decimated_from_triangle_count`: single-scale decimation, disclosed.

The inventory starts from these.

### A generic "scales" concept in the bundle manifest (MPB)

A deliverable may carry its scales in one of two shapes. The platform picks the shape that suits the deliverable.

1. **Ordered tiers.** One file or pointer per scale, ordered from fullest to lightest.
   - Each tier publishes its own **cost driver**: element count, pixel count, polygon count or vertex count. That lets a host predict cost from the manifest before it opens the file.
   - Each tier states its own frame and datum, like any other file. #280 shows a host refusing a layer it cannot prove is in its frame, and a tier gets no exemption from that.
2. **A progressive order.** One file, with a per-row rank chosen by the platform, so that **any prefix of the list is an even subset**.
   - A host that wants a quarter of the trees takes the rows whose rank is below a quarter of the count.
   - The platform owns evenness. It might use a spatially even ordering for forest, and rank specimen or street trees first so they survive every cut.
   - This costs one column, not one copy per scale. `spec/format.md` §4.4 already says a minor release may append a column and a reader must ignore one it does not know.

**Host behaviour**

- A host shows the published scales in its import UI, next to the time cost **it has measured itself** in that host and version. The platform cannot know what a Revit commit costs.
- It picks a tier, or takes the first N rows by the published rank.
- **It never computes the subset.** No re-ranking, no spatial filter, no simplification.

**Format compatibility** (`spec/compatibility.md`)

- Every new field is **additive**, so it ships as an MPB minor.
- A host that does not know the fields reads the deliverable it reads today, in full. A manifest without them means "one scale: all of it".
- The full-scale pointer keeps its current key and meaning. A field is never reused with a changed meaning, so the lighter tiers sit beside it and never replace it.
- Pointers stay pointers (`HPS-32`). A host finds a tier by its published value, never by a filename pattern such as `_25pct`.

### Tailored per category

For each category: its cost driver, a candidate scale axis, what the user loses at lower scales, and which host gains. **Every row is a hypothesis until the inventory measures it.**

| Category | Cost driver | Candidate scale axis | Lost at lower scales | Who gains |
|---|---|---|---|---|
| **Trees** (`landcover.tree_points`, `hosts.unreal.foliage_points`) | Element count. Revit: about 8 to 11 ms per tree, plus model weight afterwards | A progressive rank, or density tiers that keep spatial evenness. ## 5. Open questions

1. **UI shape.** One global "detail" choice, one per category, or both, with the global choice setting the defaults per category. Revit's checklist (`HPS-51`) and Unreal's planned picker (#93) are the natural places.
2. **Defaults per host.** Full scale with a warning, or a lighter scale by default? PR #282 picked "unticked, with a measured warning" for whole layers; a scale is a finer version of the same choice.
3. **When the user chooses.** At ordering time on the platform, so only one scale is built and downloaded? Or at import, so every scale ships in the bundle? A rank costs no extra bytes; tiers cost the download size of each one.
4. **Re-import identity.**
   - ADRs 0004, 0011 and 0013 make a re-import **reuse** what the same build made and **refuse** what an earlier build made. #281 adds the datum to that question.
   - A **different scale of the same build** fits neither arm. Today a re-import at a larger scale would either "reuse" and add nothing, or place a second set over the first.
   - **A scale change must never double-place trees or polygons.** With a rank, a scale-up might place only the missing ranks and a scale-down remove only the ones above the cut. Whether a host may remove what it placed is a decision of its own. The scale probably needs to be part of each element's stamp.
5. **Stating the cost per scale once.** How does a host show the measured cost of each scale without restating figures in its code, its README, the inventory and the warning text? The cost driver in the manifest and the per-unit cost in the host probably give `cost ≈ driver × unit cost`. That is arithmetic on a published count, not derivation of a placement value, but the effort should say so out loud.
6. **Evenness as a contract.** If a progressive rank is published, what does "any prefix is even" promise, and can the conformance corpus check it, or only the platform?
7. **Built at procurement, or on Prepare.** Today the platform builds a host's files when that host asks for them, a Prepare (the platform's API calls it a materialize). The maintainer is considering building everything, every host's files and every scale, when the order is first procured, on the grounds that the build and Prepare paths have become much faster. That decision is the platform's, for its pipeline and storage cost, and is not tracked here. This effort depends on it:
   - It answers question 3: every scale is built up front, and the choice moves to import.
   - **A rank costs no extra bytes**, so building it up front is free. **Tiers cost every user every tier's download** for as long as a bundle is one zip, unless a tier can be fetched on its own, which would change the zip layout in `spec/format.md`.
   - The hosts should not block the switch. `HPS-47` decides whether a bundle is materialized from the manifest's neutral signals, and `HPS-24` has a no-op outcome for a Prepare of a bundle that is already built. That is read from the contract, not yet run end to end.
   - A host could drop its Prepare step, and the machinery that exists because a Prepare is slow and can outlive its window, only once no unbuilt bundle is left in anyone's vault. That would be its own issue here.
