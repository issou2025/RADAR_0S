# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Geometry Import & Repair UX: productize #167 into guided mesh QA, repair preview and solver-readiness workflow**

*Project description:*
## Summary

#167 completed the important backend/authority foundation for imported geometry:

- exact OBJ/GLB `RawVisualMesh` ingestion;
- immutable source bytes / SHA-256 provenance;
- deterministic defect diagnostics;
- explicit bounded `RawMeshRepairPlan` / repaired-mesh lineage;
- RawVisualMesh → SemanticAcousticGeometry conversion;
- SceneRevision binding;
- R120 compiled geometry / region / portal / boundary readiness.

That work is intentionally fail-closed and correct.

However, the remaining product gap is now clear: **a normal user still needs a guided native workflow that turns a real imperfect scan/CAD mesh into a solver-usable acoustic model without understanding internal mesh/authority concepts.**

#167 completion explicitly leaves arbitrary hole filling, non-manifold surgery, remeshing/reconstruction and acoustic-room inference unsupported. Mature acoustics tools distinguish themselves not only by import format support but by geometry QA, leak diagnostics, repair assistance and clear model-readiness feedback.

This Issue productizes the existing #167 foundation. It must not introduce a second geometry truth.

Related: #167 #101 #456 #589 #359 #653 #656 #727 #761

---

## Product goal

After importing a real-world OBJ/GLB or Capture-derived mesh, the user should be able to answer:

1. **What is wrong with this geometry?**
2. **Where is the problem in 3D?**
3. **Is it safe to repair automatically?**
4. **What semantic decision do I need to make manually?**
5. **What changed after the repair?**
6. **Is the result usable for visualization only, semantic room geometry, GA, wave solver, or none of those yet?**

The normal workflow should be:

```
Import
→ Geometry health scan
→ inspect defects in 3D
→ preview safe repair(s)
→ apply explicit repair plan
→ resolve semantic openings/regions/surfaces
→ re-run diagnostics
→ review approximation / unresolved items
→ compile/check solver readiness
```

The raw imported asset always remains immutable and inspectable.

# 1. Geometry Health Summary

Immediately after import, derive a user-facing summary from canonical diagnostics.

Suggested categories:

### Topology
- open boundary edges;
- disconnected components;
- non-manifold edges/vertices;
- duplicate vertices/faces;
- unreferenced vertices;
- inconsistent winding;
- self-intersection where detection is reliable.

### Surface quality
- zero-area / near-zero-area triangles;
- extreme slivers;
- duplicate/overlapping coplanar faces where bounded detection is reliable;
- degenerate normals.

### Acoustic-model concerns
- holes that may leak a room volume;
- multiple disconnected candidate air volumes;
- surfaces below selected/estimated acoustic spatial resolution;
- very thin structures whose representation needs an explicit boundary model;
- ambiguous openings;
- geometry that cannot yet define explicit region/portal semantics.

Do not show a single opaque `health score`.

Show counts + severity + exact impact:

```
12 open boundary edges
Impact: closed-room wave model unavailable
Action: inspect boundaries
```

---

# 2. Defect localization in the viewport

Every diagnosable defect should be inspectable spatially.

Requirements:

- click issue row -> focus/highlight exact affected vertices/edges/faces;
- next/previous defect navigation;
- isolate selected connected component;
- transparent/X-ray option when the defect is hidden inside geometry;
- camera fit to affected region;
- retain stable defect references for the current raw/repaired artifact.

Do not require users to infer geometry errors from triangle/vertex IDs.

Advanced details may show IDs.

---

# 3. Classify repair actions by risk

Do not create a generic “Fix all” button.

Repairs should be classified.

## A. Safe / deterministic structural cleanup

Examples where exact bounded semantics exist:

- merge exact/within-explicit-tolerance duplicate vertices;
- remove unreferenced vertices;
- remove exact duplicate faces;
- normalize winding only when orientation can be resolved deterministically;
- remove zero-area primitives where source topology semantics are unchanged.

These may be batchable, but still produce an explicit previewable RepairPlan.

## B. Bounded geometry-changing repair

Examples:

- close a small planar hole;
- collapse a tiny isolated artifact;
- simplify features below an explicitly selected threshold;
- resolve a narrowly defined sliver.

These require:
- explicit tolerance;
- before/after geometric delta;
- affected area/volume;
- warning that acoustic geometry changes;
- user confirmation.

Do not silently choose the threshold from solver grid size and mutate source geometry.

## C. Semantic/manual resolution

Examples:

- door/opening vs accidental hole;
- adjacent room vs outside termination;
- wall thickness / two-sided sheet meaning;
- portal placement;
- furniture vs room-boundary component;
- open stairwell / corridor;
- intentionally disconnected geometry.

These are not “mesh repairs”.

They require explicit semantic authoring using existing R110/R120 authority.

---

# 4. Small-hole closure contract

Small-hole repair is useful but high-risk.

If implemented, require a narrow first version:

- one simple boundary loop;
- approximately planar loop under explicit tolerance;
- no non-manifold adjacency;
- bounded maximum diameter/area;
- deterministic triangulation;
- before/after preview;
- exact patch provenance.

The UI must ask what the patch represents.

Example:

```
Patch this boundary as a physical wall surface?
[Yes, create surface]
[No, this is an intentional opening]
[Keep unresolved]
```

Do not infer “wall” from a hole.

---

# 5. Non-manifold handling

Non-manifold geometry often requires reconstruction, not cleanup.

First product slice should:

- detect;
- localize;
- explain why solver compilation is blocked or limited;
- allow only narrowly validated operations.

Potential later operations:

- split duplicated shells;
- duplicate/split vertices to restore manifold surfaces where topology intent is unambiguous;
- delete clearly isolated artifact geometry.

Do not implement a broad automatic surgery engine without fixtures demonstrating topology preservation.

---

# 6. Connected components / noise cleanup

Scans may contain floating fragments.

Provide component inventory:

```
Component 1  42.8 m² surface  likely main room shell
Component 2  0.001 m²         small isolated fragment
Component 3  ...
```

The user may explicitly:
- keep;
- hide as visual-only;
- exclude from semantic conversion;
- delete in a derived repaired mesh.

Do not automatically discard a component solely because it is small; it may be a speaker, treatment, fixture or intentional obstacle.

---

# 7. Resolution/readiness diagnostics

Make “too detailed for current acoustic representation” understandable.

For a selected solver/backend/resolution context, visualize:

- features thinner than reliable representation;
- small gaps that may disappear;
- narrow passages;
- stair-step approximation risk for wave grids;
- faceting error for curved surfaces;
- unsupported thin-sheet semantics.

Important:

This is a **diagnostic**, not permission to automatically simplify geometry.

Any derived simplification must have its own exact spec/provenance.

---

# 8. Solver-specific readiness without coupling truths

Present separate readiness states.

Example:

```
Visual mesh                READY
Semantic room surfaces     2 unresolved openings
GA direct/early subset     READY with limitations
Wave closed-volume model   BLOCKED
General-3D production      NOT_VALIDATED
```

Use #727 validation semantics.

Do not reduce this to `solver_ready=true/false`.

Do not let a geometrically valid mesh override a provider-level NO_GO/NOT_VALIDATED state.

---

# 9. Before/after repair comparison

Every geometry-changing repair must support a review surface.

Show:

- changed vertices/faces;
- added/removed surface area;
- bounds delta;
- volume delta if meaningful;
- newly closed/open boundaries;
- defect count before/after;
- semantic refs affected;
- exact RepairPlan identity.

For small modifications, a 3D ghost/diff overlay is preferred.

The original imported mesh is never overwritten.

---

# 10. Undo / history / Scene integration

Distinguish:

- UI preview: no persistent mutation;
- accepted `RawMeshRepairPlan`: immutable derived artifact;
- semantic promotion: explicit authority transition;
- resulting SceneRevision: normal revision lineage.

Undoing a Scene action must not delete raw imported evidence.

Reopening a project must reproduce the same repair and diagnostics from exact stored authority.

---

# 11. Capture integration

For Capture-origin geometry:

- preserve Capture delivery/source hash;
- never rewrite Capture evidence;
- repairs create HTDT-derived geometry authority;
- conflict/promotion semantics remain #589/#359;
- show whether a defect originates in raw Capture geometry or later HTDT repair.

Future Capture improvements may produce cleaner meshes, but HTDT still needs a robust ingestion/repair review path.

---

# 12. UX: normal vs advanced

## Normal

Use user language:

- “Room shell has 2 open gaps”
- “This opening prevents closed-room wave prediction”
- “Select the gap to inspect”
- “Mark as doorway / close as wall / leave unresolved”

## Advanced

Expose:

- edge/face IDs;
- thresholds;
- exact RepairPlan;
- semantic hashes;
- compiler diagnostics;
- approximation metadata.

Do not expose raw mesh terminology as the only workflow.

---

# 13. Performance

Large imported meshes must remain interactive.

Requirements:

- diagnostic work may run as a cancellable job where needed;
- progressive UI feedback;
- no full immutable Scene duplication of triangle payloads (compose with #653);
- highlight data should avoid rebuilding the entire render pipeline for every defect;
- repeated diagnostics on identical exact input/spec may reuse cache.

No dedicated performance test is needed unless implementation introduces a meaningful new algorithmic risk; validate against representative project/mesh budgets under #663.

# Acceptance criteria

- [ ] importing a representative imperfect OBJ/GLB automatically surfaces a geometry-health summary in native UI.
- [ ] every supported defect type can be localized/focused in the 3D viewport.
- [ ] existing safe #167 repair operations can be previewed before persistence.
- [ ] repair never overwrites the original raw asset.
- [ ] same raw asset + same RepairPlan reproduces the same derived repair identity.
- [ ] geometry-changing repair shows an explicit before/after diff and quantitative delta.
- [ ] intentional opening and accidental hole are never silently conflated.
- [ ] non-manifold geometry that cannot be safely repaired remains blocked with a concrete explanation.
- [ ] after repair, diagnostics are re-evaluated and remaining blockers are shown.
- [ ] readiness is shown separately for visual / semantic / GA / wave / provider-validation scope.
- [ ] user can complete the common repair workflow without triangle IDs, UUIDs, CLI or editing JSON.
- [ ] save/reopen retains raw asset, repair lineage, semantic promotion and diagnostics.
- [ ] Capture-origin evidence remains immutable and distinguishable from HTDT-derived repair.
- [ ] no repair operation implicitly invents material, boundary physics, portal or adjacent-region authority.
- [ ] production solver availability still follows #101/#727 validation gates.

## Non-goals

- full Blender/MeshLab replacement;
- general-purpose CAD healing;
- arbitrary self-intersection reconstruction;
- unrestricted automatic hole filling;
- BIM topology inference;
- silent remeshing;
- “AI guessed room” authority promotion;
- making an unvalidated acoustic solver production-ready merely because geometry compiles.
