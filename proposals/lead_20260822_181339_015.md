## The gap has a tripwire already in the tree

`config.PROVIDER_RUN_DTYPES["kartaview"]` exists (`config.py:110`) but is **unreachable**, because both filename regexes gate on `naming.KNOWN_PROVIDERS`, which is still `("gsv", "mapillary")` (`naming.py:27`). `tests/test_census.py` pins exactly this with a strict xfail:

```python
@pytest.mark.xfail(
    strict=True,
    reason=(
        "#225 phase 3b: kartaview has a run schema but no naming.KNOWN_PROVIDERS "
        "token yet, so its runs would read with the Mapillary schema. When 3b "
        "lands this XPASSes and fails -- delete the marker then."
    ),
)
def test_a_run_schema_is_reachable_from_a_filename():
```

It is a strict xfail rather than a plain assertion because `test_every_known_provider_has_a_run_schema` checks the containment in the direction this state satisfies *vacuously* — a provider with a schema and no token passes it.

**What the unreachable schema costs, concretely:** a KartaView run read under the Mapillary fallback infers its nullable-`Int64` `sequence_index` to `float64` and its numeric-looking string `way_id` to a float that eats leading zeros — differently depending on which module opened the file. Harmless only because nothing writes a KartaView run yet.

## What is missing

1. **The grid-run wrapper.** There is no `download_kartaview_metadata_async`. The census seam extracted in #237 means this is a ~60-line wrapper — preamble → `census.build_grid` → `fetch_city_images_async` → `census.write_census_grid_run` — but only two of the three provider bindings the tail needs exist (`_kartaview_image_columns`, and `build_image_rows`/`build_empty_rows`). The third, `capture_dates_for(census, positions)`, does not.

2. **The `naming.KNOWN_PROVIDERS` token.** One line, and it is the master gate: both filename regexes derive from it, `PROVIDER_RUN_DTYPES["kartaview"]` becomes reachable, and `_STREETWALK_PROVIDER_ALT` updates for free.

3. **CLI dispatch.** `cli.py:103`'s `choices`, the dispatch branch at `cli.py:512` (currently `if mapillary / else gsv`), and a `--kartaview-max-requests-per-minute` flag — a separate one from both the GSV project-quota figure and the Mapillary tile cap, following the existing precedent. `load_config("kartaview")` already exists. `streetscape_street_analyzer/analyze.py:166` and `scripts/recompute_run_stats.py:154` hardcode the same two-provider `choices`.

4. **The frontend registry entry.** After #233 the frontend asks capability questions rather than identity questions, so this is one `PROVIDERS` entry in `streetscape-utils.js` — the radio group, `?provider=` validation, the colour ramp and the grid/streets filter options all derive from it.

## One hazard the token flip creates, which this issue should close in the same change

Adding the token makes `[providers.kartaview]` **parse** — `load_scheduler_config` gates on `KNOWN_PROVIDERS` — while three scheduler arms stay fail-open:

- `city_timeout_seconds` (`scheduler.py:750`) returns the flat `city_timeout_minutes` floor for any channel not in its allow-list. At the sweep's 16 req/min that SIGKILLs Singapore (~9,974 requests ≈ 10.4 h) at 180 minutes, and a killed child records **no** `api_usage`, so its spend vanishes from the ledger. That is #238.
- `estimate_requests` (`scheduler.py:567`) falls through to the **GSV grid formula** — 2,601 "requests" for a 1,000 m grid at 20 m step, where the real sweep is a handful of circles. That mis-prices the budget guard in both directions.
- `enabled_providers`'s `rank.get(p, 99)` sorts an unranked channel last by accident rather than by decision.

So the token flip should land together with an explicit refusal of `[providers.kartaview]` in `load_scheduler_config` until the scheduler arms exist. `CHANNEL_HOSTS["kartaview"] = (HOST_KARTAVIEW,)` is required regardless — `test_every_scheduled_channel_declares_its_per_ip_hosts` asserts set **equality** against `KNOWN_PROVIDERS`, so it goes red the moment the token lands. That equality is the tripwire working as designed.
