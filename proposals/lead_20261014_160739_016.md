## What happens

Decompiling a `.pyc` whose module-level code combines `try/except` with nested dict/generator comprehensions crashes inside source reconstruction:

```
IndexError: list index out of range
...
pylingual/control_flow_reconstruction/source.py:94 in __getitem__
pylingual/control_flow_reconstruction/cft.py:394 in to_indented_source
    lines = [] if self.inst.starts_line ... source.lines[self.inst.starts_line - ...]
```

The traceback is rendered into the `[NOTE] From source reconstruction` / `From error correction` annotations by rich, and then — this is the dangerous part — **the process exits with code 0 while writing no result file to the output directory**. From a scripting/automation perspective the run looks completely successful; you only notice when you go looking for the output and find the directory empty.

Minimal reproducible sample (compile with 3.10, then `pylingual sample.pyc -o out`):

```python
import os, json

def triage(paths, threshold=32):
    results = []
    for p in paths:
        try:
            size = os.path.getsize(p)
        except OSError as e:
            print("skip %s: %s" % (p, e))
            continue
        if size > threshold:
            results.append({"path": p, "size": size, "tag": "BIG" if size > 1024 else "small"})
    summary = {t: sum(1 for r in results if r["tag"] == t) for t in {"BIG", "small"}}
    return json.dumps(summary, indent=2)
```

Result: `out/` stays empty, exit code 0.

## Workaround

`--trust-lnotab` (bypassing the segmentation model) decompiles the same file without issue and produces verified-correct output, so the bug is specific to the ML-segmentation reconstruction path.

## Suggestion

Even when reconstruction of a code object fails, it would help automation a lot if the CLI either wrote a best-effort output (like it does for per-function `Failure` annotations) or at least exited non-zero when it produced no output file at all — right now the silent-0 exit makes it indistinguishable from success in pipelines.
