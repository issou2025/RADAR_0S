## What

`SNAP_GRID` in `rust/geometry/src/kernel/mesh_bridge.rs` is documented in METRES:

```rust
/// f32-near-coplanar reconciliation snap grid (metres). [...] Resolution is
/// tunable against the test corpus; 2^-16 m ~= 15 um.
pub(crate) const SNAP_GRID: f64 = 1.0 / 65536.0;
```

It is applied by `mesh_to_tris` to whatever coordinates the caller hands the kernel, and those are not consistently metres.

MEASURED, on the void path: for `ara3d/S_Office_Integrated Design Archi.ifc` (`.MILLI.` `.METRE.`), the operands reach the kernel with per-axis extents `[3750, 20, 3250]` for a panel whose world bounding box is 3.75 x 0.09 x 3.25 m sitting 66 m from the origin. Neither the world position (66/41/16) nor metres (3.75/0.09/3.25) match; `3750` is the panel's own size in MILLIMETRES. The operands are local-frame and file-unit.

`csg/plane_eps.rs` documents the same split for the half-space boolean path, where `BooleanProcessor::process` clips at `router/processing.rs:818` and the result is unit-scaled only afterwards at `:846`, while the layered-material caller in `router/layers.rs` is already in metres. One kernel constant, two denominations decided by the caller.

So `SNAP_GRID`'s physical size is whatever the file's length unit is:

| file authoring | SNAP_GRID physically | near-band floor (`8*SNAP_GRID`) physically |
| --- | --- | --- |
| `.METRE.` | 15.3 um | 122 um |
| `.MILLI.` `.METRE.` | 15.3 nm | 122 nm |

A 1000x difference in physical resolution for identical geometry, decided entirely by how the file happens to be authored.

## Why it matters, with a measurement

This is not theoretical. It is the reason the watertightness census corpus split the way it did in #2681.

The near-coplanar band is `max(8*SNAP_GRID, extent * 2^-22)`, so the magnitude term only overtakes the floor above **512 kernel units**. Which side of that crossover a model lands on is a units question, not a geometry question:

- A 3.75 m panel in a **metre**-authored file enters the kernel with extent `3.75`. The term is `8.9e-7`, 137x below the floor. The floor decides everything.
- The same 3.75 m panel in a **millimetre**-authored file enters with extent `3750`. The term is `8.9e-4`, 7.3x ABOVE the floor. The magnitude term decides everything.

Measured on `ara3d/S_Office_Integrated Design Archi.ifc` (`.MILLI.` `.METRE.`, 66 m from the origin, panels of 3750 x 20 x 3250 kernel units): 205 near-coplanar comparisons on a single host sat in the window between the two regimes. In a metre-authored file the identical geometry would not have reached that window at all.

The practical consequences:

1. Two files describing the same building classify coplanarity differently.
2. The snap grid's own purpose (make an intended-flush face EXACTLY coplanar after f32 import) is served at 15 um in one file and 15 nm in the other. At 15 nm it is far finer than the f32 import noise it exists to absorb, so intended-flush faces in millimetre files rely on the band rather than the snap.
3. The `8*SNAP_GRID` floor inherits the same divergence, since it is defined as a multiple of the grid.

## Prior art in this repo

`rust/geometry/src/csg/plane_eps.rs` already documents the identical divergence for the clipper's epsilon floor, under a heading of its own:

> KNOWN LIMITATION (pre-existing, not introduced by the magnitude-scaling fix; applies to the FILE-UNIT boolean path [...]): because the floor is a fixed constant with no unit attached, identical physical geometry can classify differently depending on whether the file is authored in metres or millimetres.

That module deliberately left it undone, with the reasoning worth repeating here:

> Left undone deliberately: rescaling this floor by `unit_scale` is exactly the kind of tolerance change that needs its own PR with its own corpus evidence, not a fold-in-on-review-comment fix.

The same applies to `SNAP_GRID`, and more strongly: the grid is not only a tolerance, it MOVES coordinates. Rescaling it changes which faces become exactly coplanar, which changes every determinism manifest.

## Not fixed in #2681

#2681 projects the near band onto the plane normal and deliberately leaves the floor and the grid alone. The projection is orthogonal to this: it fixes which AXES may widen the band, not what unit the band is denominated in.

## What a fix would need

- A decision on whether the grid should be `unit_scale`-relative (a fixed physical size) or stay file-unit-relative (a fixed relative precision), with the argument written down. The current state is neither on purpose.
- Corpus evidence, since changing the grid perturbs the pinned mesh-determinism manifests (`rust/processing/tests/manifests/mesh_determinism.json`) and the watertightness census by construction.
- A joint decision with `plane_eps.rs`'s floor and `clash_solid.rs`'s trust band, which carry the same unit question.
