**Is your feature request related to a problem? Please describe.**

For the purpose of running an IPsec gateway whose IKE authentication key can never leave the device, I am missing a way to use a private key stored in a TPM 2.0 with OPNsense's strongSwan. Many appliances and VMs (vTPM on KVM/Proxmox/VMware/Hyper-V) provide a TPM 2.0, FreeBSD supports it (`tpm(4)`, `/dev/tpm0`), and strongSwan has a `tpm` plugin for exactly this, but the OPNsense `strongswan` package is built without the `TPM`/`TSS2` port options. Currently one has to rebuild `security/strongswan` and `security/tpm2-tss` from ports and lock the packages, which has to be repeated after every OPNsense update (see #10884 and opnsense/tools#519 for the build side).

**Describe the solution you like**

Three steps, of which the first two are already proposed as pull requests:

1. Build `security/strongswan` with `TPM TSS2` (opnsense/tools#519). Adds `security/tpm2-tss` as runtime dependency; plist is fully `%%TPM%%` guarded, `check-plist` is clean.
2. Point the plugin at the FreeBSD device by default (#10884): strongSwan selects the TCTI by looking for `/dev/tpmrm0` (Linux in-kernel resource manager). FreeBSD only has `/dev/tpm0`, so without configuration charon falls back to the D-Bus `tabrmd` TCTI, which does not exist, and the plugin does not load. Setting `charon.plugins.tpm.tcti { name = device, opts = /dev/tpm0 }` in the generated `strongswan.conf` fixes this. On systems without a TPM the plugin loads but never opens the device unless a TPM key is referenced.
3. UI: a new key type in *VPN: IPsec: Key pairs*. Proposal: extend `keyType` with `tpm` ("TPM 2.0 persistent handle") plus a `tpmHandle` field (hex, e.g. `0x81010002`); the public key can be fetched from the TPM via `pki --pub --keyid <handle> --outform pem` when saving, so the existing `publicKey` field and the public-key based selection in *Connections: Local* keep working unchanged. `ipsec_write_keypairs()` would then emit, instead of a private key file,

   ```
   secrets {
       token-<uuid> {
           handle = 0x81010002
       }
   }
   ```

   into `swanctl.conf`, which is how `swanctl --load-creds` hands a TPM key to charon. No PIN/module fields are needed for the tpm plugin.

**How TPM 2.0 is used on FreeBSD in this case (documentation)**

- Kernel: `kldload tpm` (`tpm_load="YES"` in `loader.conf`) attaches `tpmcrb0`/`tpmtis0` and creates `/dev/tpm0`. The module is already part of the OPNsense kernel set. There is no in-kernel resource manager on FreeBSD, so only one process should hold the device at a time; charon opens it per operation and closes it again (verified: tpm2-tools work while charon runs, and no transient objects are left behind after IKE signatures).
- Software stack: `security/tpm2-tss` provides `libtss2-sys`/`libtss2-esys` and the `device` TCTI (with FreeBSD patches that drop `/dev/tpmrm0` from the search list). `security/tpm2-tools` (not in the OPNsense repo, could become an `os-` plugin dependency) is used to create keys.
- Key creation (persistent, signing-only, fixed scheme; the fixed scheme is required, otherwise strongSwan reports `no signature scheme found`):

  ```
  export TPM2TOOLS_TCTI=device:/dev/tpm0
  tpm2_createprimary -C o -G ecc256 -c primary.ctx; tpm2_flushcontext -t
  tpm2_create -C primary.ctx -G ecc256:ecdsa-sha256 -u key.pub -r key.priv \
      -a "fixedtpm|fixedparent|sensitivedataorigin|userwithauth|sign"; tpm2_flushcontext -t
  tpm2_load -C primary.ctx -u key.pub -r key.priv -c key.ctx
  tpm2_evictcontrol -C o -c key.ctx 0x81010002; tpm2_flushcontext -t
  ```

  (`tpm2_flushcontext -t` is needed because there is no resource manager.)
- Certificate: `pki --req --keyid 0x81010002 --dn "CN=gateway" --outform pem` creates a CSR signed inside the TPM (or `pki --self` for a self-signed test certificate); the signed certificate is imported as usual under *System: Trust: Certificates* (without private key).
- strongSwan: with the TCTI setting from step 2 and the `token-…` secret from step 3, `swanctl --load-creds` logs `loaded ECDSA private key from token` and charon signs IKE_AUTH inside the TPM. Verified end to end on OPNsense 26.7.3 with a vTPM (swtpm) and on a FreeBSD 15.1 VM with the packages built from the current ports tree; on machines without a TPM the plugin loads and stays idle, and referencing a TPM key fails cleanly with `no TPM 2.0 found` while charon keeps running.

**Describe alternatives you considered**

- Rebuilding the packages locally and locking them (current workaround, breaks the update path).
- `PKCS11` option with `tpm2-pkcs11`: heavier stack (Python, a key store database) and still needs the same build change; the native `tpm` plugin is simpler and what upstream strongSwan recommends for TPM 2.0.
- Steps 1 and 2 only, with the key configured manually through `swanctl/conf.d/*.conf` (what works today after the rebuild). This already gives a usable feature for advanced users; the UI part in step 3 could follow separately.
