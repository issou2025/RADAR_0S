# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Agent runtime: record/stop session recorder so an agent can see how a bug was reproduced**

*Project description:*
## Is your feature request related to a problem? Please describe

When an extension misbehaves, an agent working through the MCP server only sees what the user describes afterwards. The MCP tools are pull-only: `get_context` is a snapshot of the document, view and selection, and `capture_view` is a single image. Nothing records the sequence of actions, model changes and errors that led to the bug between two calls.

That sequence is what is needed for bugs that depend on order or state, for example geometry created by one command and broken by the next. The user's memory of "I did X, then Y happened" is the weakest input to a diagnosis.

## Describe the solution you'd like

An explicit **record / stop** mode in pyRevit, with a matching MCP tool.

1. **Start/Stop.** The user presses Record, reproduces the problem and presses Stop. The recorder only runs between those two actions and is off otherwise.
2. **Captured, purely mechanical (no user narration):**
   - **Element changes** per transaction, from `DocumentChanged`: added, modified and deleted elements with transaction name, category, family/type name and location (point, curve endpoints or bounding box). No full parameter diffs.
   - **Screenshots**, configurable: a default trigger such as after each commit and on error dialogs, plus a throttle and a maximum count.
   - **pyRevit command and script output**: which button ran, console output, logger messages and tracebacks.
   - **Native Revit activity** (best effort): command names, warnings and error dialogs, view and selection changes.
3. **Extension trace API.** A small call such as `recorder.mark(source, data)` that extensions can use to emit structured breadcrumbs. It is a no-op when not recording. Without it, the recorder still captures the existing logger and console output.
4. **Agent access.** A new MCP tool, `get_recording`, returns a structured timeline (JSON) with screenshot references, addressed by recording ID.

This builds on what pyRevit already has: the event hooks (`doc-changed`, `command-before-exec`, `view-activated` and others) and the MCP server.

## Describe alternatives you've considered

- Describing the steps in chat and using `capture_view` for the end state. This loses the order of events and any intermediate state.
- Reading Revit journal files after the fact. They are large, hard to parse and do not tie changes to pyRevit commands or screenshots.
- Each extension writing its own logging. This works for one extension but gives the agent no common format and no view of native Revit activity or model changes.
- A rolling always-on buffer or a live watch mode. I prefer explicit record/stop because it limits the performance cost, the privacy exposure and the amount of data the agent has to read.

## Additional context

Open questions:

- Can native command names and dialogs be captured reliably, or only partly (journal parsing, `Idling`, a dialog-box-showing event)?
- Where do recordings live, how long are they kept, and how are they cleaned up?
- Privacy: element names, parameters and screenshots can contain client data, so recordings should stay local unless the user explicitly shares them.
- Performance cost of screenshots and location lookups on large models, and whether a category filter is needed.

My use case is debugging my own pyRevit extension with an agent, where failures depend on the order of operations and on geometry state.
