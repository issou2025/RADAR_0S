## Problem

`hdrshot/__main__.py::cmd_full` resolves a requested display with:

```python
targets = disps if args.all else [d for d in disps if d.index == args.display] or disps[:1]
```

If the caller supplies a nonexistent index, the empty match silently falls through to `disps[:1]`. The command then captures and saves a different monitor while reporting success.

This contradicts both:

- the agent CLI path, which rejects out-of-range display indexes; and
- the repository's stated principle in `CONTRIBUTING.md`: **loud failures over silent fallbacks**.

It also makes the changelog claim that invalid display indexes were fixed inaccurate for the legacy `full` command.

## Impact

A typo or stale monitor index can capture the wrong screen, potentially saving unrelated or sensitive content. Automation cannot detect the mistake from the exit code or JSON because the operation appears successful.

## Recommended fix

- Resolve an explicitly requested display index exactly once through a shared helper used by both `full` and `capture`.
- If no display matches, raise/report a structured capture error before calling `capture_all()` or any encoder.
- Keep the current default-primary behavior only when the user did not explicitly request an index; do not implement it through an `or disps[:1]` fallback after lookup.
- Keep `--all` behavior unchanged.

## Acceptance criteria

- [ ] `hdrshot full --display 999` exits nonzero and does not capture or write a file.
- [ ] `hdrshot full --display 999 --json` emits the documented structured error payload and capture-error exit code.
- [ ] A valid explicit index still captures that exact display.
- [ ] The default invocation still captures the intended default display.
- [ ] Unit tests mock display enumeration/capture and prove that the backend capture method is never invoked for an invalid index.
- [ ] Changelog/docs no longer imply all display-index paths are strict unless they are.
