Title: kmx cannot express Tool/coordination/scheduling, and Task execution is tightly coupled to Agent creation (poor re-run DX)

## Summary

We recreated a real-world Orka workflow twice: once by applying Orka CRDs
directly (`kubectl apply`), and once trying to drive the *exact same*
workflow using only `kmx` (no direct Orka CRD creation), per
`kaimahi-agents/kaimahi` main @ `795b43a`. The second attempt could not
achieve feature parity with the first. This issue documents exactly what
worked directly against Orka, what kmx could and couldn't reproduce, and a
specific DX problem: **kmx has no way to run a Task against an existing Agent
without re-declaring the entire Agent/Provider every time.**

## The workflow we were reproducing

This is based on a published example Orka workflow:
https://gist.github.com/yolossn/28f9c0841da4eaa398c7e1a3d71ce3d9

A "shift active-hours report" Agent:
1. Fetch a CSV shift log from a URL (`Tool: log-fetch`, HTTP GET).
2. Compute `active_hours = logout - login` per row precisely, by spinning up
   a child container Task (`create_container_task`, `python:3.12-slim`) —
   deliberately delegated so the LLM never does date math itself.
3. Flag `OVERTIME` (>10h) / `SHORT` (<6h).
4. Publish a markdown report to a webhook (`Tool: report-publish`, HTTP POST
   with an injected auth Secret never exposed to the LLM).
5. Run on a daily cron schedule (`0 18 * * *`, `Asia/Kolkata`), plus an
   ad-hoc one-off run to trigger it immediately.

## Part 1 — directly on Orka (kubectl apply), fully worked

Applying Orka CRDs directly (`Provider`, `Tool` x2, `Agent` with
`coordination.enabled: true`, `Task` with `schedule`/`timeZone`), we got:

- Both `Tool`s (`log-fetch`, `report-publish`) `Available: true`.
- `Agent` `Ready: true` with `coordination.enabled: true`, giving it access
  to built-in tools (`update_plan`, `create_container_task`,
  `wait_for_tasks`, `remember`).
- A **scheduled** `Task` correctly computed its next cron run
  (`0 18 * * *ASia/Kolkata`).
- A **manual** one-off `Task` executed the full tool-call sequence:
  `update_plan → log-fetch → update_plan → create_container_task →
  wait_for_tasks → update_plan → report-publish → remember → update_plan →
  completed`, with the child container Task correctly computing active
  hours, and the webhook receiving the real published report with the auth
  header redacted from the LLM's view.

Everything the original workflow needed was expressible as plain Orka CRDs.

## Part 2 — attempting the same purely via kmx

We built kmx from `main` (`795b43a`) and tried to reproduce the same
workflow using only documented `kmx` commands (`kmx up`, `kmx orka install`,
`kmx agent create`, `kmx agent lift`, `kmx agent chat`), with the explicit
constraint of never `kubectl apply`-ing an Orka CRD ourselves.

### What kmx *could* do
- Provision a kind cluster (`kmx up --step cluster`) and install Orka
  (`kmx orka install --provider -`) without a raw Helm/kubectl call.
- Create a `Provider` + `Agent`, and run a single-shot `Task`
  (`kmx agent create <name> --provider-type openai --model ... --base-url
  ... --secret ... --instructions ... --task "..." --result-service-account
  ...`), which printed the model's final answer to stdout after the Task
  succeeded.
- Reuse an Azure AI Foundry deployment (an xAI Grok model) as an `openai`
  Provider via Azure's v1 GA OpenAI-compatible endpoint
  (`https://<resource>.cognitiveservices.azure.com/openai/v1`), even though
  kmx's dedicated `--provider-type azure-openai` is explicitly rejected
  (`internal/kmx/scaffold/orka.go: ValidateOrkaProvider`, error:
  *"azure-openai requires separate deployment/version fields that are not
  scaffolded; use openai or anthropic"*).

### What kmx *could not* do
1. **Create custom `Tool` CRs.** `kmx agent create --tools` only accepts
   *names* of Tools that must already exist; `kmx agent lift` explicitly
   refuses too, erroring "Tool/%s is missing in namespace %s; provision the
   Tool before lifting" (`internal/kmx/app/agent_bundle_lift.go`). There is
   no `kmx tool create` or equivalent anywhere in the command tree. The only
   Tool kmx ever creates is one hardcoded read-only Kubernetes inventory tool
   installed by `quickstart-wizard` (`docs/orka-k8s-tool.md`) — not a general
   mechanism. **Impact: our `log-fetch`/`report-publish` Tools could not be
   reproduced at all.**
2. **Enable Agent `coordination`.** The scaffold that generates the Agent
   YAML (`internal/kmx/scaffold/orka.go`) never sets `coordination.enabled`,
   and there is no CLI flag for it. Without it, the Agent has no access to
   `create_container_task`/`wait_for_tasks`/`update_plan`/`remember`.
   **Impact: no way to reproduce the "delegate exact date math to a child
   container" step, or any multi-step tool-using Agent.**
3. **Scheduling.** `grep -rn "schedule|cron"` across the entire non-test
   source returns zero results. No flag, no bundle field, nothing.
   **Impact: the daily 18:00 cron run is entirely inexpressible via kmx.**

We ended up demonstrating only a reduced version of the workflow: the CSV was
pasted inline into the `--task` prompt, and the model was asked to return the
computed report as plain text — no real HTTP fetch, no child container, no
webhook publish, no schedule.

## The specific DX problem: "run a Task" == "create an Agent"

Even for the reduced, single-shot version that *did* work, we hit a real
usability problem:

- The **only** non-interactive way to execute a Task against an Agent is
  `kmx agent create <name> --provider-type ... --model ... --base-url ...
  --secret ... --instructions ... --task "..."` — i.e., you must resupply
  the Agent's **entire definition** (Provider type, model, base URL, secret,
  secret key, full instructions file) on every single invocation, even
  though the Agent and Provider are unchanged and get correctly detected and
  `reused`, not recreated.
- You must also choose a brand-new `--out <path>` file on every run — reusing
  the same path fails with: *"agents/<name>.yaml already exists and cannot
  match this run: --task names a fresh Task every time — refusing to
  overwrite it."*
- The only alternative Task-triggering path, `kmx agent chat <name>
  <message>`, **requires `--interactive`** (a TUI session) — it explicitly
  refuses a plain scripted invocation: *"Orka chat requires --interactive."*
- There is no `kmx task create <agent> --prompt "..."`, no `kmx agent run`,
  no `kmx agent trigger` — nothing that takes just an Agent name and a
  prompt/schedule-tick and creates a Task.

This means:
- Simple automation (e.g., "run this Agent nightly from a script/CI job")
  requires re-embedding the Agent's full Provider/model/secret/instructions
  config in every invoking script, rather than referencing an Agent that
  already exists and is `Ready`.
- It conflates two very different operations — **declaring** an Agent
  (idempotent, rare) and **invoking** it (frequent, cheap) — into one command,
  making the common case (re-run the same Agent) as verbose as the rare case
  (define a new Agent).
- It's inconsistent with how the underlying Orka CRDs actually model this:
  Orka has a distinct `Task` resource, decoupled from `Agent`, exactly so a
  Task can be created against an existing, already-`Ready` Agent with a
  one-line CRD. kmx's CLI doesn't expose that decoupling.

### Bonus: results are effectively single-use via kmx

`kmx agent create --task` prints the Task's answer to stdout exactly once,
the moment it completes, via an internal port-forward + ServiceAccount token
fetch against Orka's `orka-api` `GET /api/v1/tasks/{name}/result` endpoint.
There is no `kmx task result <name>` to repeat that fetch later. (Orka itself
*does* persist the result durably and exposes it via that same REST endpoint
and its own native `orka task result <name>` CLI command — this is purely a
missing kmx convenience wrapper, not a limitation of Orka.)

## Suggested improvements

1. Add `kmx tool create` (or an equivalent bundle field) so HTTP Tools can be
   declared and applied through kmx, mirroring how Providers/Agents are
   scaffolded today.
2. Add a `--coordination` flag (or equivalent) to `kmx agent create` to
   enable Orka's built-in coordination tools.
3. Add `--schedule`/`--timezone` flags (or bundle fields) so recurring Tasks
   can be created via kmx, mirroring Orka's native `Task.spec.schedule`.
4. Decouple Task creation from Agent creation: add something like
   `kmx task create <agent-name> --namespace ... --prompt "..."` (or
   `kmx agent run`) that only needs an Agent name + prompt, doesn't require
   re-declaring Provider/model/secret, and doesn't require picking a new
   output file path per invocation.
5. Add `kmx task result <name>` to re-fetch a previously completed Task's
   answer without re-running the Task or hand-rolling Orka's REST API call.
