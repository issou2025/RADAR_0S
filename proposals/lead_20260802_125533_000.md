## Summary

The parity standard for this workstream requires four states to be visually distinct on every surface — **loading / empty / error / forbidden** — and requires forbidden to **say why**, naming the capability ("Only a project manager can curate albums").

Three of the four are being delivered. **Forbidden is not**, and it is not evenly missing: one surface implements it well, one implements something adjacent, and one has nothing at all. Recording it as an issue because a note in a PR body disappears when that PR merges, and this outlives #550.

**Not fixed here.** #547 is the prerequisite — see the last section.

## Measured state, per surface

### BCC / Revit plugin — nothing

```
$ grep -rc "403\|Forbidden" StingTools/UI/SitePhotos*.cs
0   (across every SitePhotos*.cs)
```

No 403 handling in the site-photo UI, and none in `PlanscapeServerClient.SitePhotos.cs` either. A 403 falls through the generic failure path and renders as the **couldn't-load** treatment — red, with the server's reason.

Worth being precise about what that is and is not. It is **not** a regression, and **not** the empty-list fabrication #550 set out to kill: a refusal shows as a failure, not as "no albums here". But it is indistinguishable from the server being unreachable, so an operator who lacks a capability is told the system is broken rather than told they lack permission. Those warrant different actions — one is "call IT", the other is "ask your PM".

### planscape-web — the standard already exists here, in two places

This is the model implementation, `app/settings/team/page.tsx:260`:

```ts
if (e.status === 403) return 'You need the Owner or Admin role to invite people to the firm.';
```

Distinct, and it says why, naming the role. `ArchiveProjectDialog.tsx:62-64` does the same, with a comment framing a 403 as *"a real, expected answer"* — which is the right mental model.

But it is applied on roughly three surfaces out of the whole app, hand-written each time, with the role names hard-coded at the call site. `lib/data.ts` documents which endpoints 403 in docstrings (`:77`, `:216`, `:475`, `:538`) without a shared way to render it.

### Mobile — present, but mostly a different thing

403 appears in eight-plus files, but in the site-photos area it is `403 nda_required` (`src/components/site-photos/NdaPromptModal.tsx`) — **content gating, not capability gating**. An NDA prompt is a specific, well-handled flow; it is not the general "you lack this capability" state. Whether the other surfaces (`documents`, `issues`, `members`, `project-settings`) render a distinct forbidden message or just swallow the status needs a per-file pass.

## The root cause is derivation, not rendering

The inconsistency is a symptom. Every one of the places above **hard-codes its own knowledge of the role rules** — `'You need the Owner or Admin role…'` is a string literal that encodes an authorization decision made on the server. Three clients each maintain their own copy, and they drift.

That is exactly what **#547** (serve project capabilities) exists to stop, and why it is the prerequisite here rather than a nice-to-have. Building a fourth hand-rolled forbidden state before capabilities land would add a fourth thing to migrate.

Note also that until **#540** merges, the eleven authorization gates it replaces are dead, so some of these 403s are not currently being raised at all — meaning a forbidden state built today could not even be exercised end to end on those paths.

## What "done" looks like

1. **One shared forbidden treatment per client** — not per screen. Visually distinct from the error state, not merely a differently-worded error.
2. **The message names the capability**, not the HTTP status: *"Only a project manager can curate albums."* The web string at `settings/team:260` is the right register; it should come from a shared helper rather than be retyped.
3. **Driven by the capabilities endpoint** (#547) so the client stops deriving role rules. Where a capability is known to be absent, the control should be disabled with the reason attached, rather than inviting a click that 403s.
4. **Attempt-then-report the 403 remains correct in the interim** — it is honest, and it is what the parity bar specifies until #547 lands. This issue is not a request to guess permissions client-side.
5. **Covers BCC, planscape-web and mobile.** Per the workstream rule that a phase is not done until every listed surface is done — no web-only fix.

## Scope note

Deliberately excluded: the NDA flow. `nda_required` is content gating with its own accept-and-retry journey, it already works, and folding it into a generic forbidden state would make it worse.
