# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Question: signed receipts for selected security automation / recon handoffs?**

*Project description:*
Hi — I found ECLYPSA AI while looking at security automation projects where agent task outputs, plugin results, recon artifacts, or exported reports may need evidence that survives outside the original runtime.

I’m building BoundaryAttest, a small open-source project for portable signed receipts around selected claims, actions, artifacts, or handoffs that cross trust boundaries:

https://github.com/cullenmeyers/BoundaryAttest

The idea is not to replace ECLYPSA AI’s ReAct agent loop, plugin bridge, local/cloud LLM provider handling, Go recon engine, REST API, dashboard telemetry, Docker runtime, logs, or normal task history. The receipt only proves a narrow claim:

> a specific signer signed a specific claim, and the signed claim has not been altered.

ECLYPSA AI seemed relevant because it combines a Python ReAct agent loop, dynamic plugin loading, security/recon plugins, a Go-powered network scanner/banner grabber, REST API, dashboard monitoring, and local-first LLM execution for privacy-focused security automation.

A receipt could potentially bind selected authorized security task events like:

* task/session ID;
* agent/provider/model reference;
* plugin/tool name and version;
* target reference or target hash;
* scan/recon result hash;
* banner-grab output hash;
* plugin input/output digest;
* policy/scope/authorization reference, if available;
* dashboard/export artifact hash;
* final task summary/report hash;
* status, such as planned, executed, failed, summarized, exported, or handed off;
* timestamp/event ID;
* signer/public key ID.

The strongest use case would be when an ECLYPSA task result, recon output, plugin-generated artifact, dashboard export, or security automation report is handed to another analyst, reviewer, customer, CI job, incident process, bug bounty record, or downstream workflow, and they should not have to fully trust the original local runtime, dashboard state, or logs.

BoundaryAttest would not prove the scan was authorized, the result is complete, the target was in scope, the finding is correct, the action was safe, or the runtime was uncompromised. It would only prove that a specific claim about a selected ECLYPSA artifact/action/handoff was signed and has not been altered after export.

There are a few small external interop patterns/examples here:

https://github.com/cullenmeyers/BoundaryAttest/blob/main/docs/external-interop-patterns.md

Does this kind of portable signed receipt fit any workflow you imagine for ECLYPSA AI, especially around authorized recon outputs, plugin results, task summaries, dashboard exports, or security automation handoffs? Or are the current logs, dashboard, and task outputs enough for the project’s current scope?

No pressure if it is not relevant — I’m mainly trying to learn where signed receipts are actually useful around security automation agent workflows.
