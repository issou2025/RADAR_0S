## Project Understanding

**Tooling: spec-kitty upgrade fails on _recheck_command_completion, needs three invocations to converge**

*Project description:*
## Summary

`spec-kitty upgrade` cannot complete in a single invocation. The first run aborts with `Completed command output changed: <repo>\.agents\skills` and `Unresolved tool-surface drift in 22 file(s)`; a second run makes partial progress; a third finally reports `Project is already up to date!`. Progress is real but incremental — the projected skills directory went 15 → 70 → 70 entries across the three runs. The failure is in `managed_skills.py:180 _recheck_command_completion`, which is the sibling race upstream **already documents as deliberately out of scope** for the #4703 re-assess-under-lock work. This issue is to track that the deferred follow-up is now biting a real upgrade, not to re-report the mechanism.

## Versions

- **spec-kitty-cli**: 4.0.0rc4, build `619bd1137` (installed from `git+https://github.com/spec-kitty/spec-kitty.git@619bd11376342abaae67e18588ff12c2def336f1`)
- **codex / antigravity / other relevant agent CLI**: Claude Code (Claude Opus 5)
- **OpenClaw** (if relevant): n/a

## Reproduction

### Prerequisites

- A project upgrading from a 3.x-era `.kittify` to the 4.0.0rc4 build
- Multiple agents configured (`copilot`, `claude`, `gemini`, `codex`, `antigravity`) so the doctrine-skill projection is large — the plan carried 529 effects and ~408 missing managed doctrine skills
- `.agents/skills/` gitignored and absent or partially populated

### Steps

```bash
spec-kitty upgrade --yes    # attempt 1
spec-kitty upgrade --yes    # attempt 2
spec-kitty upgrade --yes    # attempt 3
```

### Expected Behavior

One invocation applies the plan and converges.

### Actual Behavior

Attempt 1:

```text
Errors:
  ✗ Completed command output changed:
C:\Users\Kent\Vaults-repos\kg-automation\.agents\skills
  ✗ Completed command output changed:
C:\Users\Kent\Vaults-repos\kg-automation\.agents\skills
  ✗ Unresolved tool-surface drift in 22 file(s); run 'spec-kitty doctor
tool-surfaces' to review.

Upgrade failed.
```

(note the identical error emitted twice)

Attempts 2 and 3 as measured:

```text
=== attempt 2: exit=1 ===
  skills dir now: 70 entries
=== attempt 3: exit=1 ===
  skills dir now: 70 entries
```

Attempt 3's output ends `Project is already up to date!`. Confirmed converged afterwards: `pending_migrations: []`, and `spec-kitty doctor tool-surfaces` exits 0 with zero `is missing` findings — down from 408 before the first attempt.

(The exit=1 on attempt 3 is a separate defect — the `--yes` prompt / false-failure exit code — filed independently.)

## Root Cause

`specify_cli/tool_surface/providers/managed_skills.py:180`:

```python
raise ValueError(f"Completed command output changed: {effect.destination}")
```

raised from `_recheck_command_completion` (defined at line 165, called at line 346).

This is precisely the race the `ensure_runtime` docstring in `specify_cli/runtime/bootstrap.py` names as excluded from the #4703 fix:

> Scope caveat (not a claim of totality): `tool_surface/providers/managed_skills.py`'s paired global+project composition apply (`ManagedSkillsProvider.apply_composition` / `apply_installation` / `GlobalSkillAssetsProvider`) is NOT covered by this seam -- its `_PAIRED_GLOBAL`/`_PROVISIONING_PAIR` cross-owner coordination would need a rebuild callable threaded through `upgrade/assessment.py` as well, and that composition already carries a separate, documented, scoped-out race of its own (`_recheck_command_completion`'s manifest `installed_at` timestamp never converges across two independent assessments -- see `tests/runtime/test_generic_asset_scope.py`'s `TestRecheckCommandCompletionConcurrentPeerVerdict`). Extending the re-assess seam there is tracked as a follow-up, not silently assumed.

So the mechanism is known and the follow-up is already tracked upstream. What is new here is the field consequence: on a large multi-agent projection it is not a rare concurrent-peer race but a **deterministic** single-process failure that costs three invocations to work through.

## Workaround Applied

Re-ran `spec-kitty upgrade --yes` until it converged (three invocations). Verified the end state independently rather than trusting the exit code.

## Suggested Fix

Option A: Land the already-tracked follow-up — thread the rebuild callable through `upgrade/assessment.py` so `managed_skills`' paired composition adopts the same `apply_with_reassess` seam as the other owners.

Option B: Exclude the `installed_at` manifest timestamp from the completion recheck comparison. The docstring identifies it as the field that never converges; if it is bookkeeping rather than content, it should not be able to fail the recheck — this mirrors how `_is_bookkeeping_write` is already treated in `asset_preparation.py`.

Option C: Failing either, make the upgrade self-retry the composition apply to convergence rather than surfacing a hard failure that the operator has to resolve by re-running.

Also: the identical `Completed command output changed` error is printed twice for one destination — worth de-duplicating.

## Impact

- **Who hits this**: any project upgrading into 4.0.0rc4 with a large managed-skills projection; more agents configured means more surface and a bigger window.
- **Frequency**: deterministic on the first run here; three runs to converge.
- **What breaks**: the upgrade reports `Upgrade failed` while having partially applied — on attempt 1 the version stamp had already advanced to 4.0.0rc4 and two `.kittify` manifests were modified, while `skills-manifest.json` was not yet created and 22 files of drift remained. An operator who trusts the failure message is looking at a half-applied project.
- **Severity**: workflow friction, recoverable by re-running — but the partial-apply-then-report-failure shape is the dangerous part, not the retry count.
