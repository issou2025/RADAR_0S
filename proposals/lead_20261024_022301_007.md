# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Autonomy 3/4: job runner with progress, stop conditions, resumable journal and a handoff page**

*Project description:*
## Goal

Let the agent hand the connector a **whole job** — an ordered list of tool calls with simple result binding — that the add-in runs on its own, one step per Revit idle slot, under one approval, with progress the agent can poll cheaply, a persisted journal that survives a Revit restart, stop conditions (failures, new Revit warnings, time), and a **handoff page** at the end that the user reviews without the agent.

| Tool | Permission | Purpose |
|---|---|---|
| `revit_job_submit` | RequiresApproval | Submits steps + plan envelope; the approval activates the plan (#99) and starts the job |
| `revit_job_status` | ReadOnly | Progress, per-step results, counters; `waitSeconds` long-polls until something changes |
| `revit_job_list` | ReadOnly | Jobs of the open documents and persisted ones; `removeJobId` |
| `revit_job_cancel` | ReadOnly (model) | Stops after the running step; nothing is undone |
| `revit_job_resume` | RequiresApproval | Resumes a paused, suspended or failed job from its first unfinished step |
| `revit_job_report` | ReadOnly | Publishes (or re-publishes) the handoff page for a job |

Depends on #98 (checkpoints, warnings) and #99 (plans, `TransactionGroup` authorization). The user's vision — "it works in Revit independently while I focus on something else" — is this issue; #98 and #99 are its safety rails.

## Why

Today each step costs an agent round trip and, in ApprovalRequired mode, a click. The agent has to stay in the loop to sequence calls, and a Revit restart loses everything. With a job the agent spends tokens on *planning* (reading the model through the graph, choosing ids, writing the steps) and the connector spends none on *executing*. The user comes back to a page that says what happened.

## Design

### Job model (Addin, pure)

```csharp
sealed class JobStep
{
    int Index;
    string Tool;                                  // any registered tool name
    Dictionary<string, object?> Arguments;        // may contain "{{var}}" placeholders (string values, or whole array values)
    Dictionary<string, string>? Bind;             // var → JSON path into this step's result, e.g. "ids": "$.data.items[*].id"
    string? Title;                                // shown on the page; default: tool name
    bool ContinueOnError = false;                 // step failure stops the job unless true
    bool Optional = false;                        // a tool refusal (validation_failed) is skipped, not failed
    JobStepState State;                           // Pending | Running | WaitingApproval | Succeeded | Failed | Skipped | Cancelled
    string? Status; string? Message; long DurationMs; int Touched;   // from the McpToolResult / plan counters
    DateTimeOffset? StartedAt, FinishedAt;
}

sealed class JobStopConditions
{
    bool StopOnFailure = true;                    // overridden per step by ContinueOnError
    string StopOnNewWarnings = "error";           // none | error | any  — evaluated after every write step via WarningDiff against the job's checkpoint
    int MaxNewWarnings = 0;                       // with "any": tolerate this many
    int MaxDurationMinutes = 120;
    int MaxConsecutiveBusy = 20;                  // revit_busy retries before suspending
}

sealed class Job
{
    string Id;                                    // "job-" + 6 hex
    string Title; string ClientName;
    string ModelId; string DocumentTitle; object? DocumentToken;
    string PlanId; string CheckpointId;           // from #99 / #98 on activation
    PlanEnvelope Envelope;                        // what was approved, kept for resume
    JobStopConditions Stop;
    List<JobStep> Steps;                          // ≤ 200
    Dictionary<string, JToken> Variables;         // bound results
    JobState State;                               // Proposed | Running | WaitingApproval | Paused | Suspended | Completed | Failed | Cancelled
    string? StopReason;
    DateTimeOffset CreatedAt; DateTimeOffset? StartedAt, FinishedAt;
    string? ReportPageId;
    bool OpenReport = true; string Report = "auto";   // auto | never
}
```

### Flow

1. **Submit.** `revit_job_submit` takes `title`, `steps[]`, `envelope{}` (same shape as #99), `stop{}`, `report`, `openReport`. The tool validates: every `Tool` exists in the registry (the handler exposes `GetRegisteredToolNames()`), destructive tools are refused unless `allowDestructiveSteps=true` **and** then those steps are marked `WaitingApproval` at run time (they always prompt), placeholders reference variables bound by an earlier step, `Bind` paths parse, ≤ 200 steps. The tool is `RequiresApproval`; `ApprovalSummaryBuilder` renders the #99 plan summary plus a step list and the stop conditions ("JOB: … 14 steps, 9 of them write. Stops on the first failure or the first new Revit error.").
2. **Approve.** The approved request executes `JobService.Start(job, uiapp)`: `PlanService.Activate` with the envelope (one approval covers plan and job — no second prompt), checkpoint created with the envelope scope, journal written, state `Running`, first step enqueued. The result returns `jobId`, `planId`, `checkpointId`. In Direct Edit the job starts immediately.
3. **Run loop** (`JobRunner`, one instance, API-thread-agnostic):
   - a step runs as an **internal request** through `ExternalEventService.DispatchAsync` with `ClientName = "Job <id>"` and `planId` set — the same path the model page listener uses (`ModelPageRevitHandler.SetWritePath`) — so every existing rule applies: `TryRunUnderPlan`, approval fallback, activity log, graph freshness, `revit_busy`. The runner never calls a tool directly and never touches the Revit API itself.
   - **one step per dispatch**: when the result arrives, the runner substitutes bindings, journals, evaluates stop conditions, then enqueues the next step. Between steps the queue is empty, so the user's own Revit commands and other MCP clients interleave normally; nothing holds the API thread.
   - `approval_required` result (a step outside the envelope, or a destructive step): the step and the job become `WaitingApproval`; the runner subscribes to `ApprovalService.OutcomeRecorded` for that requestId and continues with the outcome when the user decides. The Pending tab shows the step like any approval, labelled with the job.
   - `revit_busy`: retry with backoff 5 s → 60 s, up to `MaxConsecutiveBusy`, then `Suspended` with the reason.
   - `plan_envelope_violated` or `plan_exhausted`: the step fails (the call was already rolled back by #99); `StopOnFailure` applies.
   - after every step whose tool is not read-only: `WarningDiff` against the job's checkpoint; a new warning at or above `StopOnNewWarnings` (beyond `MaxNewWarnings`) → `Paused` with `StopReason = "new Revit warning: <text>"` and the step kept `Succeeded`.
   - `MaxDurationMinutes` → `Paused`; plan expiry → `Suspended`.
   - last step done → `Completed`; `PlanService.Complete`; report (step 5).
4. **Status.** `revit_job_status jobId waitSeconds=0..25`: with `waitSeconds` the tool (an `IBackgroundMcpTool`, no Revit access) awaits a `JobChanged` signal or the timeout, then returns — so an agent can block for 25 s per call instead of polling every second. Result: state, `stopReason`, `progress {done, total, running step index}`, `steps[]` (compact: index, title, tool, state, status, message first 200 chars, touched, ms), `counters` from the plan (calls, touched, added/modified/deleted), `newWarnings`, `elapsed`, `reportUrl`. `include=results` adds the full `McpToolResult.Data` of the last `n` steps.
5. **Report (handoff page).** `JobReportHtml.Build(job, checkpointDiff, warningDiff, planStatus)` — deterministic, no AI — produces one self-contained HTML document in the model-page conventions (`docs/model-pages.md`: plain semantic HTML, one plain table per element list, `data-revit-id` on rows, `data-revit-param` on value cells, `<html lang="et">` as a constant — the team's pages are Estonian). Sections:
   - header cards: steps ok / failed / skipped, elements added / modified / deleted, new warnings, duration, plan limits used;
   - **Steps** table: #, title, tool, state badge (`ok` / `bad` / `warn`), touched, ms, message;
   - **Changed elements** table (from `revit_checkpoint_diff include=all`): id, category, name, by, what changed; for snapshotted parameters a `data-revit-param` cell per changed parameter showing *before → now* (`data-revit-param` keeps *now* live and highlights drift);
   - **Added**, **Deleted** tables;
   - **New warnings** table with element ids;
   - **Undo**: the Revit transaction names in order, the checkpoint id and how to roll back (`revit_checkpoint_rollback`) — plain text, no button (rollback stays approval-gated through the agent).
   Published through `ModelPageService.Current.Store.Save(...)` + `UrlFor(...)` with `pageId = "job-<id>"` so re-publishing keeps the link; opened in the browser when `OpenReport`. `report=auto` publishes on `Completed`, `Failed`, `Paused`, `Suspended`, `Cancelled`; `revit_job_report` publishes on demand (also for a running job: a live snapshot). Cap the tables at 2 000 rows with a note, keep under `ModelPageStore.MaxHtmlBytes`.
6. **Resume.** `revit_job_resume jobId` is `RequiresApproval`. For a `Paused` job in the same session whose plan is still active, the approval is one click in ApprovalRequired mode and immediate in Direct Edit; it continues at the next step with the same plan and checkpoint. For a `Suspended` or `Failed` job (plan gone, or Revit restarted): re-bind to the document by `ModelId`, activate a **new plan** with the stored envelope (this approval covers it), create a fresh checkpoint, continue from the first step that is not `Succeeded`/`Skipped`; variables bound by finished steps are restored from the journal.
7. **Cancel.** `revit_job_cancel` (and the UI button) sets `Cancelled` after the running step completes; nothing is undone; `PlanService.Revoke`; report published. `PanicStop` cancels all jobs.

### Journal and persistence

`%LOCALAPPDATA%\RevitMCP\Jobs\<modelId>\<jobId>.json`: the whole `Job` incl. per-step results (the `Data` of each result trimmed to 64 KB) and `Variables`. Written after every state change on a background task (never on the API thread). On startup `JobService.LoadSuspended()` marks every job that was `Running`/`WaitingApproval`/`Paused` as `Suspended` with `StopReason = "Revit was restarted"`; `revit_job_list` shows them; nothing resumes without `revit_job_resume`. Keep ≤ 50 journals per model (oldest completed ones evicted).

### Result binding

`$.data.items[*].id`, `$.data.elementIds.moved[:10]`, `$.data.moves[?(@.status=='Moved')].elementId` — implement the subset used by `RevitMCP.Benchmark` scenarios (`[*]`, `[:n]`, `[n]`, dotted keys) in `JobJsonPath.cs`, plus `[?(@.key=='value')]` equality filter. Placeholder substitution: a string value exactly `"{{ids}}"` is replaced by the bound token (array stays an array); inside a longer string it is formatted as text. Unresolved placeholder → the step fails with `validation_failed` before dispatch. Pure, unit tested.

### UI

New **JOBS** tab in `McpWindow.xaml` (after PENDING): list of jobs for this session and suspended ones (title, client, state badge, progress `7 / 14`, elapsed, stop reason), buttons **Pause**, **Resume**, **Cancel**, **Open report**. Pending items that belong to a job show the job title. Tab header `JOBS (1)` while any job runs.

### Status codes

`job_not_found`, `job_not_resumable` (with the state), `job_step_invalid` (with the step index and reason). Document in `McpToolResult.cs`.

### Activity log

Every step runs through the dispatcher, so it is logged as usual with `Client = "Job <id>"` and `PlanId` (#99). The runner adds entries for start, pause, suspend, resume, cancel, complete and report publication under tool `revit_job_*`.

## Acceptance criteria

- One approval starts a job; the connector runs the steps without the agent; the agent can block on `revit_job_status waitSeconds=25` and gets a change-triggered return.
- Steps run one per dispatch; the user can work in Revit between steps and other MCP calls are served.
- Steps outside the envelope or destructive steps wait on the Pending tab and continue after the decision; the job never bypasses #99's rules.
- A new Revit error warning pauses the job and is named as the reason; resume continues.
- A Revit restart leaves the job `Suspended` with its journal; resume needs one approval and finishes from the first unfinished step.
- The report is a model page: self-contained, rows select elements, changed parameters are live cells, under 2 MB, link stable across re-publication.
- PanicStop cancels jobs; Cancel never undoes anything and says so.
- Unit tests green, both targets build, benchmark report committed, no new `RevitMCP.Core` types.

## Out of scope

Branching or loops inside a job (the agent re-plans between jobs instead); scheduling jobs for a future time; running a job on a non-active document (steps act on the active document, as the tools do today; resume checks `ModelId`); a second Revit instance as a worker (separate issue).
