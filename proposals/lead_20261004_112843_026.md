## Project Understanding
You need assistance with: 
**Feature proposal: non-interactive CLI / automation interface**

*Project description:*
hi @drdewes 

Would you be interested in a PR adding a non-interactive command-line interface to `phpbb-tui`?

**No implementation work has been started yet.** I'm asking first to see whether this is something you would be interested in having upstream before beginning development. If it isn't something you want upstream, I would likely implement and maintain it in a fork instead.

The idea would be to expose the functionality already available through the TUI and `Board` implementation in a form that can also be used by shell scripts, cron/systemd jobs, other programs, and AI/tool integrations without requiring curses or interactive prompts.

For example, commands could cover functionality such as:

- listing forums and topics;
- reading topics/posts;
- using the existing search functionality;
- creating topics and replies;
- quoting and editing posts;
- listing, reading, sending, replying to, and deleting PMs;
- listing, downloading, and uploading attachments where already supported.

The CLI could also provide automation-oriented features such as:

- JSON output;
- stable exit codes;
- stdin/file input for message bodies;
- quiet mode;
- dry-run support;
- pagination;
- explicit non-interactive handling of authentication and errors.

The intention would **not** be to replace or redesign the existing TUI. Running `phpbb-tui` or `phpbb-tui <board>` would continue to work as it does now, with the existing key bindings, menus, workflows, editor behavior, and other interactive behavior preserved.

Where possible, the implementation would reuse the existing authentication, sessions, parsing, posting, PM, attachment, Markdown/BBCode, and other phpBB functionality rather than creating a separate client implementation. Some focused refactoring might be necessary to make functionality currently tied to the UI reusable outside curses.

It would also be useful to keep the underlying operations reusable enough that other interfaces could potentially be added later, such as a Python API or MCP integration, without those being part of this proposal.

Again, **this hasn't been implemented or started yet**. Before putting time into it, I wanted to check whether this is a direction you'd be open to accepting upstream.

If so, I can work on a focused PR with tests and documentation while keeping unrelated cleanup and behavioral changes out of it. If not, no problem; I would keep the additional functionality in a fork instead.

Would you be interested in this?
