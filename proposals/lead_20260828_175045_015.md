# Project Proposal — Python Automation

## Project Understanding

*Project description:*
## The idea

User-submitted concept: use Blender (via the BlenderMCP integration already available in this environment) to generate real, photorealistic-looking UI components — 3D-shaded knobs, faders, textured panel surfaces, real lighting/reflections — for the plugin family (MURMUR, Undertow, Fathom, Splay, Quasar, Drum), instead of (or alongside) the current flat/vector UI. Reddit and other plugin-dev communities have real, visible examples of exactly this technique (baking 3D-rendered hardware-style controls into plugin UIs) — this isn't a novel idea, it's an established, real technique in the commercial plugin space (this is roughly how many hardware-emulation-style plugins from Native Instruments, Arturia, u-he, Softube, etc. get their "real metal knob" look).

## Real current state (so this is scoped against reality, not assumption)

Every plugin's UI today is **procedural, vector-drawn JUCE graphics** — confirmed directly:
- A shared base (`plugin/src/ui/theme/ObsidianLookAndFeel.cpp`) implements `drawRotarySlider()` etc. entirely via `juce::Graphics` calls (rectangles, gradients, computed angles) — no raster/baked imagery anywhere in a knob.
- Each plugin subclasses it (`FathomLookAndFeel`, `SplayLookAndFeel`, etc.) for its own knob styles, but the *technique* is the same: everything is drawn live, every frame, from geometry + color.
- Each plugin already has a real, distinct, **Figma-sourced** brand palette (e.g. `FathomPalette.h`: "a weathered olive-steel/brass 'sonar station' instrument panel," sourced from real Figma fill/stroke data, not eyeballed) — real art direction already exists per plugin, this issue is about *rendering technique*, not needing new brand identity work.

This vector-first approach is very likely a deliberate choice, not an oversight — see "real tradeoffs" below for why.

## The real proposed technique

The proven industry pattern for "photoreal 3D knob in a 2D plugin UI" is **not** real-time 3D rendering inside the plugin (JUCE has no game-engine-grade real-time 3D renderer, and shipping one would be a real performance/compatibility risk across every DAW/OS this targets). It's:

1. Model the control once in Blender (parametric — same knob rig, different material/color per plugin brand).
2. Light it with a real, consistent rig (HDRI environment + key/fill, matching each plugin's real palette — e.g. Fathom's brass/olive-steel, per its Figma spec).
3. Render a **sprite filmstrip**: e.g. 128 frames sweeping the knob's full rotation range, each a transparent PNG.
4. On the JUCE side, a filmstrip-aware `LookAndFeel::drawRotarySlider()` picks the correct frame by `sliderPosProportional` instead of drawing procedurally — a real, well-understood JUCE pattern (`juce::Image` + frame indexing), not exotic.

## What's genuinely already available to build this

This environment already has a real Blender MCP integration wired up: `execute_blender_code` (arbitrary Python — real parametric rig-building, material setup, batch rendering), `get_viewport_screenshot`, `download_polyhaven_asset` (real PBR material/HDRI library), `generate_hyper3d_model_via_text/images`. The scripting/automation half of this is not hypothetical — it's callable today. What doesn't exist yet is the actual rig (the knob/fader models), the per-brand material setup, the batch-render-to-filmstrip script, and the JUCE-side filmstrip `LookAndFeel`.

## Real tradeoffs to weigh honestly before committing

- **Resolution independence.** The current vector approach looks crisp at any window size/DPI/host scaling with zero extra work. A raster filmstrip needs either multiple baked resolutions or accepts blur/pixelation when a user resizes the plugin window larger than the baked resolution — this is very likely *why* the current UI is vector-first, and is the single biggest real design tension with this idea.
- **Binary/installer size.** Photoreal sprite strips are not small — 128 frames × several component types × per-plugin brand variants, even PNG-compressed, adds real, possibly-significant megabytes per plugin. Worth a real size budget before committing broadly.
- **Lighting consistency.** Every component in one plugin's UI needs the *same* light rig/angle, or the "photoreal" look reads as fake/inconsistent the moment two components are on screen together — a real production discipline requirement (a shared, reused Blender lighting setup per brand, not ad-hoc per-asset renders).
- **Live theming.** The current system drives knob color live off `juce::Slider::rotarySliderFillColourId` etc. — real, cheap, host-automatable color theming. Baked photoreal renders lose that unless variants are pre-rendered per state (e.g. active/inactive, or per accent color) — likely fine for a single fixed brand look per plugin, worth being explicit that per-parameter dynamic recoloring goes away.

None of these are reasons not to try it — they're the real, concrete design questions worth answering before scaling this "to all VSTs."

## Suggested real next step

A single, small proof-of-concept: pick **one** component (a rotary knob) on **one** plugin (Fathom is the strongest fit — its real "weathered brass sonar console" theme is exactly the kind of tactile, material-rich look this technique sells hardest) and build the real, full pipeline end to end — Blender rig → batch-rendered filmstrip → a working JUCE `LookAndFeel` override loading it — before deciding whether to invest in doing this "for all the VSTs." That answers the resolution/size/lighting questions with a real artifact instead of a guess.
