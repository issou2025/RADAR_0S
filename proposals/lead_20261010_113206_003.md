## Problem Statement

A generated project configures its coding agents for TanStack (Intent) and shadcn (skill), and for nothing else in the stack. Motion, Hugeicons and Turborepo publish official skills, and shadcn, Motion and Hugeicons publish official MCP servers, but a developer has to find each one, run its installer, and write the MCP config for each agent by hand. Motion's installer is interactive only and has no Codex target. The result is that most generated projects run their agents without the guidance and tools the stack's own maintainers publish.

Research record with citations: the inventory in the thread that produced this issue (2026-10-10). Summary:

| Tool | Official skill | Official MCP server |
| --- | --- | --- |
| Motion | `plugins/motion/skills/motion` in `motiondivision/ai-kit` (MIT) | `https://mcp.motion.dev` (no login), `https://mcp.motion.dev/plus` (Motion+ sign-in) |
| shadcn | already shipped | `npx shadcn mcp`, stdio |
| Hugeicons | `skills/hugeicons` in `hugeicons/hugeicons` (MIT) | `@hugeicons/mcp-server`, stdio |
| Turborepo | `skills/turborepo` in `vercel/turborepo` (MIT) | none |
| TanStack | already shipped via Intent | hosted, undocumented, returns 401; out of scope |
| Biome, Tailwind, pnpm, Lefthook, Base UI, Vite, Vitest, React, TypeScript | none | none |

The `skills` CLI pinned in `packages/cli` installs all three skills, including Motion's from its nested path (`skills add motiondivision/ai-kit --skill motion` writes `.agents/skills/motion`, the `.claude/skills/motion` link and a `skills-lock.json` entry with `skillPath: plugins/motion/skills/motion/SKILL.md`).

## Goals / Success Criteria

1. Every generated project contains the Turborepo and Motion skills at the same locations as the shadcn skill, recorded in `skills-lock.json`, produced by the refresh pipeline at pinned versions and never fetched at scaffold time (ADR 0003).
2. The create command asks which agent integrations to configure, as one grouped multi-select prompt with a flag equivalent: MCP servers, and optional agent files (Motion's Cursor rule). Each item is independently selectable.
3. Servers that need no login are selected by default. Servers that need a login or an account (`motion-plus`) and the optional agent files are not selected by default.
4. The selection is written to `.mcp.json` (Claude Code, project scope) and `.cursor/mcp.json` (Cursor), in the format each agent's docs give. Stdio servers run a pinned package version, never `@latest`.
5. `--yes` and non-interactive runs take the default selection. `--integrations none` produces no MCP files and no optional files. A flag naming items produces exactly those.
6. The generated project's `AGENTS.md` or README tells a Codex user how to add the same servers to `~/.codex/config.toml`, because Codex reads MCP config only from the home directory and no scaffold can write it.
7. For every selection, install, build, check, typecheck and test exit 0, and the e2e snapshot records the files.

## User Stories

1. As a developer, I want the skills the stack's maintainers publish to be in my project from the first commit so that my agent follows their guidance without me installing anything.
2. As a developer, I want to choose which MCP servers my agents get so that I do not run servers I do not use.
3. As a developer, I want servers that need an account left off unless I opt in so that a fresh project never prompts me to sign in to something I did not ask for.
4. As a developer using Codex, I want the exact config to paste so that I get the same servers as Claude Code and Cursor users.

## Testing Decisions

**Approach:** the e2e scaffold test runs the default selection, `--mcp none`, and an explicit list, and snapshots the files each produces. A unit test checks the written JSON against the selection. Exploratory testing opens a default scaffold in Claude Code and confirms each configured server reaches the approval prompt and connects.

**Constraints:** exploratory runs use throwaway scaffolds. No test signs in to Motion+.

## Out of Scope

- TanStack's hosted MCP server: no public docs, requires an API key.
- Lefthook `ai:` hooks: overlaps the Intent hooks in `.claude/settings.json` and `.codex/hooks.json`; needs its own investigation.
- pnpm 12.11 dependency-shipped skills (`pnpm approve`): nothing in the pinned stack ships one yet.
- Writing `~/.codex/config.toml`, `~/.claude.json` or any file outside the project.
- Per-agent selection (for example Cursor on, Claude Code off).
- Prompting for the shadcn, Turborepo, Motion and Hugeicons skills themselves: they always ship.

## Additional Notes

- Read `docs/contexts/scaffold-options.md` before adding the prompt: every prompt has a flag; `--yes` takes defaults; prompts use `@clack/prompts` (`multiselect` exists in the pinned 1.8.1).
- Read `docs/contexts/v0.md`: v0 ships the default stack only. This PRD adds a prompt, not a tool alternative. Owner placed it in milestone v0.
- `.mcp.json` supports `${VAR}` expansion (Claude Code docs). Not needed for the four servers here.
- Claude Code prompts the user to approve project-scoped servers on first use; a cloned repo cannot pre-approve its own servers. Expected and acceptable.
- Server catalog with pinned versions lives in the template, not in CLI source, so the refresh pipeline can bump `shadcn` and `@hugeicons/mcp-server` the way it bumps `package.json` pins.
