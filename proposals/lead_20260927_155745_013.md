### automation-22 (major) — `src_C/Vpc/Automation/StatusRoutes.cs:160`
- Problem: After go-live, nothing measures the quality of auto-accepted cards. Human-on-exception means nobody reviews them. The gate admits precision as low as 0.97, with a CI lower bound of 0.93 (EvalGate.cs:42-43), so a few percent of auto-published cards are expected to be wrong. Yet the only quality metric is the dry-run shadow, which counts would_accept only (StatusRoutes.cs:160-172; AutomationTick.cs:746-755). Each decision keeps accepted_content_sha256 (DraftQaResults.cs:233), but nothing compares it with later human edits or deletes, and no status field, digest line or alarm exists. The runbook's own criterion for enabling auto-publish, 'no auto-accepted card rejected or deleted by a person' (automation-operations.md:98-99), and its undo procedure (:202-214) rest on the owner noticing a bad card unaided.
- Suggested fix: Add `live: { autoAccepted30d, deletedByPerson, editedByPerson, overrideRate }` to the status API. Compute it by joining cards with automation_draft_decisions where state='auto_accepted': a card counts when is_deleted=1, or when its current CardContentHash differs from accepted_content_sha256 after a non-automation edit. Show it on the Overview and in the weekly digest. Raise an exception (for example live_quality_drop) when overrideRate over the last 50 auto-accepts exceeds 0.05. Optionally send a fixed sample, such as every 20th live auto-accept, to a post-publish human spot check. Make the runbook's steps 7-8 numeric on this metric. Test: a deleted auto-accepted card is counted, and so is a human edit; an automation re-hash is not.
- Evidence: StatusRoutes.cs:158-185; AutomationTick.cs:746-755; DraftQaResults.cs:230-237; EvalGate.cs:42-43; automation-operations.md:98-99, 202-214; `grep -i 'sample|spot.check|later.*delet'` over src_C/Vpc/Automation and the console automation feature finds nothing.
- Verifier: Verified. The only quality metrics are the dry-run shadow, which counts would_accept only (StatusRoutes.cs:160-185), and the digest (AutomationTick.cs:746-755). accepted_content_sha256 is read only by AutoPublisher's pending-change check (AutoPublisher.cs:321-324). Nothing measures later deletes or edits of auto_accepted cards, and nothing samples them. The gate admits precision down to 0.97, with a CI lower bound of 0.93 (EvalGate.cs:42-43). The runbook's step-8 criterion and its undo procedure (automation-operations.md:98-99, 202-214) depend on the owner noticing unaided. For a human-on-exception auto-publish system, a production feedback loop is a standard expectation. ### automation-26 (minor) — `src_C/Vpc/Automation/EvalGate.cs:134`
- Problem: An older passing report can override a newer failed evaluation. The only reuse check refuses the sha256 of a revoked row (:134-141), and GateReport.Read never reads the report's createdAt (EvalGate.cs:200-310 contains no createdAt check). If a re-run fails and is recorded as the newest row, re-posting the earlier passing report inserts it again as the newest passed row and makes live effective. That earlier row was superseded, not revoked. A mis-pasted file from evals/reports/ is enough to do this.
- Suggested fix: Refuse with 409 EVAL_GATE_SUPERSEDED a report whose sha256 already exists in any row, or whose createdAt is not later than the createdAt of the newest recorded report (read from report jsonb). Test: pass, fail, then re-post the first report: 409, and the effective mode stays dry_run.
- Evidence: EvalGate.cs:134-150; AutomationMode.cs:64-85; 034_automation.sql:170-184 (no uniqueness on report_sha256).
- Verifier: Verified. The only reuse check refuses a sha of a revoked row (EvalGate.cs:134-141). NewestGateSql picks the newest row by id (:51), and grep finds no createdAt or freshness check in GateReport. Re-posting an older passing report after a newer failed one therefore makes live effective again. It needs a super_admin action (a mis-paste), so minor is right.

### automation-27 (minor) — `src_C/Vpc/Automation/RunnerRoutes.cs:329`
- Problem: An agent that reports it could not do the task is retried as if the failure were transient. AGENT_BLOCKED completes as outcome failed, and the item requeues with a 60- then 120-minute backoff while attempts < 3 (:329-337). Every attempt emails. Attempt 1 sends runner_run_failed (actionable prefix, :386-391). Attempt 2 sends it again (repeated failure). Attempt 3 sends queue_item_failed. One unreadable source therefore costs three subscription runs and three 'Action needed' emails, and the first two ask the owner to act while the system is still retrying on its own.
- Suggested fix: For errors starting with AGENT_BLOCKED, fail the item on the first attempt and send one email carrying the reason (queue_item_failed, or runner_run_failed without a requeue). Alternatively, requeue once with a long backoff and email only on the final outcome. Test: a blocked complete leaves the item failed with exactly one exception row.
- Evidence: RunnerRoutes.cs:329-337, 375-391, 416-438; tools/author-runner/prompts/queue-item.md rule 7.
- Verifier: Verified. A failed outcome requeues while attempts < MaxItemAttempts, whatever the error (RunnerRoutes.cs:326-336). RunFailureNeedsHuman treats AGENT_BLOCKED as actionable on every non-final attempt (:375-391), and the final attempt raises queue_item_failed (:423-431). One blocked source can therefore cost three runs and up to three action emails. Some blocks may be transient (prompt rule 7 includes 'source could not be read'), so a retry is defensible; the email duplication is the real issue. Polish, so minor.

- M2 Live quality measurement. GET /api/v1/admin/automation/status gains `live: { "autoAccepted30d": int, "deletedByPerson": int, "editedByPerson": int, "overrideRate": number|null }` (auto_accepted decisions of the last 30 days; a card counts as deleted when is_deleted, as edited when its current content hash differs from accepted_content_sha256 after a non-automation edit; overrideRate = (deleted+edited)/autoAccepted30d, null when 0). The weekly digest shows it; an exception email subkind `live_override_high` fires (deduped per ISO week) when overrideRate > 0.05 with autoAccepted30d >= 20. The console Overview shows the four numbers.
- M3 Shadow agreement definition. The server's shadow.agreementRate = blindAccepted / blindDecided (blind = the person decided without the automation verdict being shown). The console shows 'X of Y would-accept drafts decided blind were accepted unedited (Z%)' from blindAccepted/blindDecided/agreementRate, plus a second line with the totals (humanDecided in all, of which M after seeing the verdict); it never computes its own rate. Every server surface (status, digest, batch summary) and the runbook's go-live criterion use the same blind rate.
- M4 Eval-gate history. The server refuses (409 EVAL_GATE_STALE) a report whose generatedAt is older than the newest recorded gate's report generatedAt; the console records failing reports too (after a confirm that says it will block live), refreshes after 400 EVAL_GATE_FAILED as after a success ('Recorded as gate #N (failed): live mode now runs as a dry run'), and maps EVAL_GATE_REVOKED and EVAL_GATE_STALE to messages.
- M5 Runner-level failures. When a failure affects every item (claude cannot start, not on the subscription, MCP server not starting, usage/rate-limit text in the CLI result or stderr), the runner completes the current run with error prefix `RUNNER_UNAVAILABLE: <one line, capped>`, releases its remaining claims and stops the loop; for per-item failures the error carries the CLI result subtype and the first 300 chars of the result text (one line). src_C: a complete with a `RUNNER_UNAVAILABLE:` error returns the item to 'queued' WITHOUT charging an attempt and raises an exception email subkind `runner_unavailable` deduped per UTC day; an `AGENT_BLOCKED:` error moves the item to a terminal state that a human resolves (no automatic retry).
- M6 Source-watch heartbeat. The watcher emits EMF metric `SourceWatchRuns` (value 1 per invocation, its existing namespace and Service dimension convention) whatever the outcome; infra adds alarm developercards-${env}-source-watch-missing on it (Sum < 1 over 3 hours, treat_missing_data breaching, alerts topic, with the same actions_enabled lifecycle as the tick alarm).
