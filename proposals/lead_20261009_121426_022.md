*Project description:*
## No way to update/refresh a Hotlink Module's cached content from its source file

### Summary

Tapir has `GetHotlinks`, `CreateHotlinkNodes`, `CreateHotlinkInstances` and `ChangeHotlinkInstances` (`Sources/ProjectCommands.cpp`/`.hpp`), but nothing calls the two hotlink-node-level functions that are missing to round this out:

- **`ACAPI_Hotlink_UpdateHotlinkCache`** - the equivalent of the Hotlink Manager's "Update" button: re-reads the linked source file and refreshes the node's cached content in the current project. This is the specific gap a user asked about (automating "update hotlinks").
- **`ACAPI_Hotlink_ModifyHotlinkNode`** - changes a hotlink node's own `sourceLocation` (repoint it at a different file), `ownerId` or `userData`. `ChangeHotlinkInstancesCommand` only changes placed *instances* (position/transform), not the node's source file - there's currently no way to repoint a hotlink at all via Tapir.

### The two functions (AC27 DevKit, `ACAPI_Database.h`)

```cpp
GSErrCode ACAPI_Hotlink_UpdateHotlinkCache (const API_Guid* hotlinkNodeGuid, API_HotlinkCacheGenerator* hotlinkCacheGenerator = nullptr);
// hotlinkCacheGenerator is for add-on-generated content; omit it (nullptr) for the normal
// "re-read from the linked file" behavior this issue is about.
// Errors: APIERR_BADPARS (null guid), APIERR_BADID (invalid guid).

GSErrCode ACAPI_Hotlink_ModifyHotlinkNode (API_HotlinkNode* hotlinkNode);
// Node identified by hotlinkNode.guid. Per the DevKit remark, "Only the sourceLocation,
// ownerId and userData parameters can be modified" - every other field of API_HotlinkNode
// is read-only through this call.
// Errors: APIERR_BADPARS (null), APIERR_BADID (invalid guid).
```

**Both are documented as "non-undoable data structure modifier" functions** - unlike most element Create/Modify commands elsewhere in this codebase, do not wrap these in `ACAPI_CallUndoableCommand`.

### Suggested shape

- `UpdateHotlinks` - `{"hotlinkNodeIds": [{"guid": "..."}]}` (array, so a caller can batch a whole subtree from `GetHotlinks`'s tree), each calling `ACAPI_Hotlink_UpdateHotlinkCache` with no generator. Response: per-item success/error (`*OrErrors` pattern, see `CommonSchemaDefinitions.json`).
- Consider also exposing `sourceLocation` as settable on an existing node - either a new `ModifyHotlinkNodes` command, or folding it into a small schema addition if there's an existing per-node "set" path already planned; whichever fits the existing `ProjectCommands.cpp` command shape for hotlinks better. Not as central as the update/refresh behavior, include only if it's a small addition on top.
- A Python example under `archicad-addon/Examples/`, a Grasshopper component, per `CLAUDE.md`'s consistency convention. Register at the version `main` currently carries (`tools/package_info.json`).

### What a maintainer/implementer should verify live (no DevKit on the CI runner used for review/triage)

- That `ACAPI_Hotlink_UpdateHotlinkCache` with `hotlinkCacheGenerator = nullptr` does in fact re-read the linked file from disk (vs. requiring a generator even for the plain case - the remark implies it's optional but this wasn't tested against a running Archicad).
- Behavior when the node's source file is unreachable (network path down, deleted file) - what error code comes back, and whether it should be surfaced per-item rather than aborting the whole batch.
- Whether this needs a Teamwork-specific caveat (reserving the hotlink cache - see `ACAPI_Teamwork_ReserveHotlinkCacheManagement` in `ACAPinc.h`, already unused in this codebase too) before updating, on a Teamwork project.

### Context

Tapir 1.7.1 (`main`), ArchiCAD 27 (macOS). Found while looking for a way to automate "update hotlinks" for a user; confirmed directly from the AC27 DevKit headers that these two functions exist and are never called anywhere in `Sources/`.
