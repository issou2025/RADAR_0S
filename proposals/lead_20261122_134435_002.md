## Decisions needed

**D1 · Tag naming.** No repository in the organization has any tag today, so whichever option is chosen becomes the convention - the name propagates into release URLs, tarball URLs, the Zenodo record metadata and the `Releases.md` registry; renaming later means deleting and recreating 7 tags + 7 releases.

- `v0.8.8` - the semver convention, unambiguous as a ref, and it avoids a tag and a branch with the same name (`git checkout 0.8.8` stays unambiguous).
- `0.8.8` - exact 1:1 match with the existing branch names.

**D2 · Zenodo access.** A DOI is minted by publishing a record, which requires an authenticated account (the DOI is attributed to its creator; it cannot be created anonymously). No Zenodo token exists in the workspace. Options as recorded in #16:

1. **Production token** (`zenodo.org/settings/tokens`) - 7 records published immediately, DOIs citable in the papers right away (the token can be revoked afterwards).
2. **Sandbox dry-run first** (`sandbox.zenodo.org` token) - the exact same flow, records visible for review before anything public; sandbox DOIs are not citable. Recommended there because the published record is permanent and carries the creator name.
3. **Manual** - the exact metadata + archive URLs are handed over and the records are created in the Zenodo UI.
4. **Zenodo GitHub integration** (added 2026-10-22 as a fourth option, no token to hand over) - the owner signs in to zenodo.org with GitHub, grants the OAuth app access to `DiGi-Organization` and switches on the seven repositories; every GitHub release published after that is archived and gets a DOI automatically. The switches must be on **before** the releases are published, because a release published earlier is not archived.
