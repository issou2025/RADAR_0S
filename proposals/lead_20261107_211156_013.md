# Project Proposal — Unknown

*Project description:*
## What this is

A list of **trusted people**, kept the way settings are. Each one is a single person mapped across every platform they're on (their Discord, X, Slack and Instagram accounts), with a **role** (teammate, caller, client, friend) and what they're trusted to ask for.

When a message comes in, log works out who that person is across every platform, what their role is, and whether what they're asking for is something they're trusted with. If it isn't, it gets **flagged as an issue**. For now it only flags: nothing is blocked yet.

## Why

On 2026-11-08 a teammate asked for a lot in one conversation:
- access to the dialer;
- access to the Telnyx account;
- more phone numbers, one in a city we don't use and one in a country we don't know how numbers work in;
- a password to the owner's own admin account.

The agent acted on most of it. It bought phone numbers because the teammate asked, until the owner stopped it ("DONT BUY MORE NUMBERS").

The owner had let it run on purpose, to see how the teammate actually works when the context is all there. Each of those asks should still have been flagged as it came in, so the owner could see it and decide.

Today the inbox only knows a sender as a handle on one platform (`people` in `log.db`: platform, account, userId, handle, name). It doesn't know that a Discord handle and an X handle are the same person, and it doesn't know what that person is to the owner.

## What it needs

### 1. One person, every platform

A person record with a stable id that every platform identity points at:

| Field | Example |
| --- | --- |
| `personId` | `p_…` (stable, never a platform id) |
| `name` | the name the owner uses for them |
| `identities` | `discord:<userId>`, `twitter:<userId>`, `slack:<userId>`, `instagram:<userId>`, plus their emails on the owner's tools (Twenty) |
| `role` | `owner`, `teammate`, `caller`, `client`, `friend`, `unknown` |
| `trust` | what they may ask for without a flag (see 3) |
| `notes` | what they work on, which groups they're in |

The mapping is semantic, not just ids. A new identity is matched to an existing person from what's already known (the same name, the same email in Twenty, the same group, the way they write), and the owner confirms the match. Until then they're `unknown`.

### 2. Known on every event

Every inbox event (rule 134) is labelled with its person and role before it's stored, beside `named` (rule 154). The hook lines and the agent's context show the person's name and role ("<name>, teammate"), never just a handle. An event from someone `unknown` says so.

### 3. Flag what isn't theirs to ask

Each request is read for what it asks the owner to do, in kinds:

- **spend**: buy numbers, credits, tools, top-ups;
- **access**: invites, logins, dashboards, API keys, the owner's servers;
- **secrets**: passwords, PINs, keys to the owner's own accounts;
- **act as the owner**: send, post or promise something in the owner's name.

When a request falls outside that person's `trust`, it goes in as an issue, an alert in `log.db` (rule 134), and is put loudly in the agent's context (`>>> NOT TRUSTED FOR THIS`). It shows the person, their role, what they asked for and the exact message. The agent tells the owner. For now the agent may still go ahead if the owner already said to. The flag is the record.

### 4. Settings to manage it

`log people` lists everyone with their identities, role and trust. `log people add|link|role|trust` edits it (MCP tools to match). Changes are kept in `log.db`, and the owner is the only one who can raise someone's trust.

## Shape

```
message lands ─▶ which person is this? (identities ─▶ personId)
              ─▶ role + trust
              ─▶ what is it asking for? (spend / access / secret / act as owner)
              ─▶ inside their trust?  yes ─▶ carry on
                                      no  ─▶ flag: alert + >>> NOT TRUSTED FOR THIS ─▶ owner decides
```

## Done when

- Every person the owner talks to is one record across platforms, with a role.
- Every inbox event shows the person and role, not a bare handle.
- A spend, access, secret or act-as-owner request from someone not trusted for it is flagged, recorded and told to the owner. Nothing is blocked yet.
- `log people` and its MCP tools let the owner see and change it.
- Its spec and SubQ questions are in `docs/specs/` (rule 117).
