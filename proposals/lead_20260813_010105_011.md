## Goal

Let a second person install Greenways OS, join a host-created Hestia room, install locally approved applications, and invoke only the exact shared sources and application operations authorised for that member.

**Hestia owns the room feature.** `greenwaysd` imports and enforces Hestia room authority; it must not define a parallel daemon-specific room descriptor, membership, source-mandate, or room-application-grant protocol.

## Ownership boundary

### Imported from Hestia

- canonical HCV1/HCP1 room descriptors and governance heads;
- invitations, admission proofs, memberships, membership epochs, revocations, and key-rotation effects;
- room-facing node bindings;
- source mandates;
- room application grants;
- closed invocation decisions and exact authority roots;
- canonical room activity and receipts.

### Owned by Greenways OS

- installation and local daemon/node lifecycle;
- operating-system key and provider-credential custody;
- exact local application approvals and local capability grants;
- pinned Hestia package/import metadata and conformance fixtures;
- verified record persistence and projections needed for routing;
- direct or relayed node routes, availability, and source selection;
- reviewed browser adapters and Native Messaging;
- provider/browser execution after both local and Hestia room authority allow it.

A local role such as `desktop`, `cli`, `browser-bridge`, or `developer` authenticates one installed process only. It never implies Hestia room membership, source authority, application authority, or provider access.

## Combined authority chain

```text
exact local application approval
  + active local capability grant
  + verified Hestia room descriptor
  + active Hestia membership at the exact epoch
  + active Hestia source mandate
  + active Hestia room application grant
  + exact operation, policy revision, limits, and observation time
  -> only then durable invocation ownership
  -> only then route/source resolution
  -> only then browser or provider execution
```

Every allowed invocation must retain the exact Hestia membership, mandate, and grant roots together with the local application approval and capability-grant roots.

## Initial import seam

3. Add an internal typed adapter that maps verified Hestia decisions into Greenways route and execution requests without copying Hestia policy.

5. Reject unsupported Hestia protocol/package versions before room state becomes active.
6. Keep Hestia room authority independently replaceable from Desktop, Flutter, Chrome, Tahto, and provider adapters.

## ChatGPT web source

Sharing the ChatGPT web application means sharing a semantic, user-mediated Hestia source such as:

```text
room: room/...
member: profile/...
application: greenways.chat + exact approval digest
source: source/host-chatgpt-browser + exact mandate root
operations:
  - conversation.create
  - message.submit
  - response.read
requires-user-interaction: true
```

The host retains the browser session, cookies, credentials, tab authority, and visible Send/return gestures. The guest receives only the bounded result and attributable receipts.

## Execution order

For every new room invocation:

```text
closed request validation
  -> authenticated local actor
  -> exact local application approval
  -> active local capability grant
  -> Hestia package/version verification
  -> Hestia room decision
  -> durable room invocation claim
  -> route availability/source binding
  -> browser/provider execution
  -> Hestia/Greenways receipt binding
```

A denial must occur before provider claim persistence, vault lookup, browser delivery, or network access and must not reveal whether a host credential or browser session exists.

## Acceptance criteria

- Room authority is implemented and versioned in Hestia, not duplicated in this repository.
- Greenways OS imports a pinned Hestia module and runs its conformance fixtures.
- Changed room, member, node, source, app, approval digest, operation, epoch, policy revision, validity, or root fails closed.
- Local process roles and network reachability cannot create room authority.
- Revocation takes effect before new invocation ownership while historical receipts remain attributable.
- Offline, pending-host, source-unavailable, replicated, queued, completed, and denied results remain distinct.
- Credentials, private keys, browser cookies, key-store handles, and arbitrary signing never enter room records, requests, receipts, logs, or sync state.
- A two-installation proof covers invitation, join, local app approval, shared ChatGPT request, explicit host mediation, signed result, revocation, and immediate denial of the next request.
- Existing daemon replay, collision, restart, provider uncertainty, and browser-role restrictions remain intact.
