## Owner's product outcome

Keep the existing IDE architecture and working features. Simplify code and remove unnecessary duplication *without weakening native controls or deleting functionality*. Clear bugs, improve UI navigation, verify real end-to-end integration on installed Windows and Linux applications. Make Lu's already loaded AI model able to discover and operate approved IDE capabilities through one model-neutral AI execution layer and authenticated, versioned local IPC. Production UX must let users quickly **launch/focus/switch between Lu and Lu IDE** while IDE remains useful independently of Lu. No Docker requirement. Windows physical machine / Radeon R9700 is a first-class release target; Linux is an independent acceptance target.

### Working rules and definitions of done

- Use three ordered milestones: **S (stabilize & native-accept)**, **I (Lu integration & coding agent)**, **R (production release)**. Tasks marked `[ ]` start OPEN/PLANNED, not proven missing implementations; qualify existing code before repairing it.
- Start with inspected source, a reproducing bug/acceptance failure, minimum reviewed repair, regression test, independent installed OS confirmation. Prefer simplifying and reusing existing host/registry/Protobuf/worker/SQLite infrastructure. Avoid new parallel frameworks, duplicate tool registries, arbitrary model-controlled shell, overengineering or expanding product scope.
- Actual status must record task ID, source SHA, platform, repro/test, green and red evidence, owner approvals, remaining blocker. A test *queued* or passing on an older SHA is not current-source acceptance.
- Batch independent corrections; no stacked CI, no changing an active source-lock candidate mid-acceptance, don't disable original negative/security tests to achieve green. Continue independent tasks while acceptance runs.
- Model output can request typed actions but cannot authorize filesystem effects, execute workers, accept its own edits, invent successful tests, or inherit a grant from another conversation/project.

## Milestone I — Lu Integration and Model-Independent Coding Agent

**Exit criterion:** At least one *actually loaded local GGUF model* can inspect an explicitly granted IDE project, generate bounded changes, receive independently verified results, iterate on approved build/test operations and recover cleanly on installed Windows and Linux. Smaller or less tool-capable models must fail visibly and safely; no claim that all models reason equally well.

**Owner's AI framework:** `K(α,N,T)` accounts for architecture, scale and task; `C_{H⊕α}(T)` preserves user intent, creativity, review and judgment while AI contributes reasoning/operations. Operational translation uses Lu's established K/I/A/F execution philosophy: model knowledge; actual installed interfaces; user/host authorization; independent feedback/verification. **One execution layer, many models**; no retraining or model-specific IDE plugins.

- [ ] **IDE-I-01 — Lu Core readiness audit.** Inspect *current exact* Lu main/active core branches and source of model runtime, tool registry, schema catalog, authorization, worker manager, IPC, journal, conversation identity and installed Windows evidence. Identify exact reusable APIs and gaps before choosing transport; do not assume historical Phase 1/2 notes prove current merge or release. Deliver a Lu↔IDE responsibility/capability matrix.
- [ ] **IDE-I-02 — Stable IDE typed capability contract.** Reuse IDE's existing host-level operation identities and Protobuf; advertise installed project-aware read, search, diagnostics, source diff, edit proposal, reviewed apply, build/test, optional debugger/Git, result/recovery/cancel capabilities. Version schema, limits, permissions and explicit unavailable states; no separate giant "AI IDE" subsystem.
- [ ] **IDE-I-03 — IPC transport spike & decision.** Evaluate OS-local `AF_UNIX` (including native Win32 behavior and chosen Rust stable toolchain), versus Linux Unix sockets + Windows named pipes behind one transport trait. Test actual installed packaged processes, OS identity checks, socket path/permissions, endpoint cleanup, framing, concurrency, crashes and packaged-app restrictions. Prefer AF_UNIX on both *only if all real targets pass*; otherwise preserve identical Protobuf semantics with two OS transport adapters. No open LAN/localhost service by default.
- [ ] **IDE-I-04 — Authenticated bridge, broker and session protocol.** Peer/app identity, local discovery, version/capability negotiation, message framing, bounded requests/results, per-project + per-turn authorization, revoke/expiry/replay defense, cancellation, reconnect, crash recovery and clear disconnected state. IPC possession is **not** consent or privilege.
- [ ] **IDE-I-05 — Lu-side model-neutral execution adapter.** Register discoverable IDE tools within Lu's *existing* native catalog: model-facing constrained tool schema → validated model JSON → Lu broker authorization → typed Protobuf IPC → IDE host validation → structured results back to model. Reuse loaded model/runtime; no second mandatory model process or MCP dependency. Degrade clearly when a model fails to select/tools or its context is inadequate.
- [ ] **IDE-I-06 — Scoped project context and coding chat.** User selects project and context; Lu can get bounded tree/source/diagnostics/git state using IDE-owned handles. Keep distinct Lu-native versus IDE coding threads/memories/permissions; support explicit handoff/selected context only, not silent transcript imports. Model should see useful task state and reasons when tools are unavailable.
- [ ] **IDE-I-07 — Read/plan/propose/review/apply.** Model can explain source, propose exact revision-bound multi-file edits and show understandable diffs. IDE rejects tampering/stale source/paths, asks user for necessary approval, applies only reviewed edits atomically and returns receipts. Save unmodified buffers and recover on interruption.
- [ ] **IDE-I-08 — Supervised coding iteration.** After separate grants, model can request format/lint/build/test, inspect authentic structured failures, revise proposals, and continue a bounded plan. Use existing protected IDE workers and Lu's scheduler/journal; no arbitrary model command authority, unbounded loops, auto-approval or execution on project open.
- [ ] **IDE-I-09 — Shared model/session lifecycle and UX.** Lu owns residency, model eject/swap and inference queue; IDE displays connected model, busy/cancel/disconnected state. IDE remains useful without Lu, reconnects without duplicating effects, and can launch/focus Lu. Workspace switch must not leak project grants or cancel unrelated tasks.
- [ ] **IDE-I-10 — Cross-model/OS verification and closeout.** Benchmark genuine Qwen/R9700 loaded GGUF plus another available model (and deliberately weak/tool-incompatible example) on read→diagnose→propose→review→test→recover. Linux and Windows IPC, negative peer/spoof/replay/authorization, crash/cancel and observed-model behavior. Record actual successes and limitations, not universal model claims.

## Milestone R — Production Release and Lu ↔ IDE Switching

**Exit criterion:** A non-developer can install and operate each app independently, connect them through a verified local mechanism, switch in either direction, work on a project through Lu-assisted coding, and safely update/uninstall/recover both applications.

- [ ] **IDE-R-01 — Two-application launch/focus/switch UX.** From Lu: "Open Lu IDE / Open project in IDE"; from IDE: "Open Lu / Return to Lu"; focus existing instance instead of spawning duplicates; Windows taskbar and Linux desktop integration, missing-app/degraded-state guidance, preserved open project/chat state. No required shared-window embed.
- [ ] **IDE-R-02 — Guided first-run and connection UX.** New/open/recent project, model/bridge status, authorization prompt, disconnect/reconnect, separate project/coding chat, plain-language error states and optional advanced controls.
- [ ] **IDE-R-03 — Installers, dependencies and upgrade/rollback.** Real Windows NSIS and Linux deb installation, Lu/IDE co-install and either-alone, signed/protected worker packaging where required, provider/notice inventory, protocol version compatibility, upgrade/rollback/reinstall/uninstall and no lost projects/drafts.
- [ ] **IDE-R-04 — Security and supply-chain release gates.** Repeat user-accessible permission review, OS trust boundaries, secure local endpoint install path, signed artifacts where release policy requires, licenses/notices/SBOM/installer digest/origin, default-off debugger and package authority. No release authorization inferred from source CI.
- [ ] **IDE-R-05 — Full physical release-candidate acceptance.** One exact source/build/installer identity on physical Windows (including R9700/Qwen if configured) and independent Linux; from clean install → start Lu → load model → switch IDE → open project → AI inspected/proposed/reviewed edits → protected tests → return to Lu → restart/cancel/recover → upgrade/uninstall. Include keyboard/accessibility and failed/disconnected branches.
- [ ] **IDE-R-06 — Documentation and supportability.** Short user guide, examples, privacy/offline boundaries, model compatibility limits, logs with redaction, diagnostics/export, known limitations and upgrade/recovery directions.
- [ ] **IDE-R-07 — Release decision and staged shipment.** Explicit product owner acceptance; reconcile all nondeferred blocker defects/required receipts, release tag/installer hashes, release notes, rollback plan, feedback loop. Release only after applicable signing/security/platform/user journeys succeed.
