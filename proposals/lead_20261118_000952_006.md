# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Connect to the YI M1 on Linux**

*Project description:*
## Parent

#1 — Open Gallery and list camera photo filenames.

## What to build

As a YI M1 owner on Pop!_OS 22.04, I want to connect to my camera and see a reliable connection status, so that the app is ready to access the camera without manual network setup.

This is the first of two owner-approved increments. Include the Linux Flutter repository scaffold and a complete UI → application → real camera connection path. Launch directly into the agreed Gallery shell; show discovery, explicit camera selection and **Pair**, progress, connected status, and errors with **Retry**. Until the second increment, the connected state must not imply that filenames have been fetched or that the card is empty.

Connect through BLE session setup, fresh Wi-Fi credential retrieval, automatic Wi-Fi association and a successful harmless camera request. Wi-Fi association alone is not enough to report Connected. Select and document the harmless request from protocol evidence and actual-camera validation; do not list media or change camera settings for this check.

Remember authorized pairing in the desktop keyring and reconnect on later launches without new pairing. A connection failure must not silently initiate pairing. New pairing may replace an existing registration and requires explicit user approval plus any camera-screen confirmation. Do not execute pairing merely because this issue exists.

### Technical scope

- Flutter **3.44.4** / bundled Dart **3.12.2**; Linux only. No SDK upgrade, mobile/web targets, CI project or project-license selection.
- Ports and Adapters; keep application/domain independent of Flutter, BLE, HTTP, D-Bus and keyring APIs. Add only capabilities needed by this increment and wire adapters at the composition root.
- Approved libraries: `bluez` **0.9.0**, `flutter_secure_storage` **11.2.0**, and direct `dbus` with a compatible resolved version. No `nm` wrapper or new state-management/BDD dependency.
- Store camera identity and pairing key/token in the keyring, not Wi-Fi credentials. Read fresh Wi-Fi credentials per connection. Stop on keyring read/write errors; no plain-text fallback, no treating errors as missing pairing, no false persistence success.
- Narrow NetworkManager/D-Bus adapter; use `AddAndActivateConnection2` with `persist="volatile"`. Remove the app-created profile when that network connection ends; do not alter existing user profiles. Verify separately that NetworkManager/desktop agents do not persist the supplied password. Secret flags alone are not proof.
- Standard Material 3; Gallery title and text connection status above the shared content area, no sidebar or custom theme. Initial window **1000 × 700 logical pixels**; verify down to **640 × 480**. No enforced minimum size is implied.
- Connection attempts end within **120 seconds** or fail earlier with the failed step and manual Retry. No automatic retry loop.

### Incremental delivery and validation

The owner approved splitting #1 into connection first, filename listing second. Scaffold and develop the connection path incrementally with BDD/TDD; do not wait for photo-list research or the second increment's final specification. Discover and verify connection prerequisites in dependency order: readiness → discovery/GATT → explicitly authorized pairing → remembered reuse/fresh credentials → Wi-Fi/reachability. Record actual findings as development proceeds. Unknown wire behavior is not a proven contract; fakes/research do not establish hardware support. Existing probe, installation and camera-operation safety approvals remain applicable.

Use standard `flutter_test` and SDK `integration_test`, one failing behavior at a time, then minimum code and refactoring. No bulk test-first implementation. One branch and issue-linked PR for this increment. Update maintained docs with implemented behavior, commands actually run and limitations.

## Acceptance criteria

- [ ] **C1 — First connection:** Given no remembered camera and an available M1, when I launch, select a camera and press Pair, then required approvals lead to BLE setup, automatic camera Wi-Fi association and successful harmless camera response before Connected is shown. Selecting a camera alone never pairs; explicit selection is required even for a single result.
- [ ] **C2 — Remembered connection:** Given a valid stored pairing, when I restart the app, then it reconnects using that pairing and fresh camera Wi-Fi credentials without new pairing.
- [ ] **C3 — Failure and Retry:** Given a missing camera, refused pairing or failed connection step, when an attempt runs, then it stops within 120 seconds, names the failed step and offers manual Retry without an automatic loop. Retrying a remembered connection never silently pairs again. Pairing refusal never silently repeats pairing.
- [ ] **C4 — Storage failures:** Given keyring read or write is locked/unavailable/fails, when storage is needed, then connection stops with a clear storage error and manual Retry, without plain-text fallback, new pairing due to a read failure, or claiming an unsuccessful save succeeded.
- [ ] **C5 — Private persistence:** Given successful first pairing and restart, then the keyring retains only required identity/pairing material. Neither the app nor NetworkManager/desktop agents persist the camera Wi-Fi password. The app's network profile is memory-only and removed on connection end; existing user profiles and remembered pairing remain unchanged.
- [ ] **C6 — Actual UI:** Given discovery, progress, connected and error states, when I use the Linux app at both agreed sizes, then controls remain usable, status is readable text, focus is visible and selection/Pair/Retry work by keyboard. Launch, interact, capture app-window-only screenshots using ImageMagick `import`, inspect them, and embed sanitized revision-specific repository images in the PR.
- [ ] **C7 — Real hardware:** Verify first connection, restart/reuse and affected failure/storage/network behavior on the owner's Pop!_OS 22.04 + YI M1 firmware 3.2-int. Record revision, date, preconditions, expected/observed outcomes, prompts actually encountered and sanitized evidence. Fakes do not satisfy this criterion; communication changes cannot merge with required hardware validation pending.
- [ ] Camera files, clock, capture settings and firmware are unchanged. Publish no credentials, device identifiers or personal media.
