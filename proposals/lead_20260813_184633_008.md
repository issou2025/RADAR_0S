# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Package GripTrack as a local Android app (embedded Python server + WebView)**

*Project description:*
## Problem Statement

The owner has soured on web hosting and no longer wants to run or maintain an
online server for GripTrack. They want to run the app entirely on their own
Android phone, with no network dependency at all — data on-device, works in
airplane mode, no host to pay for or babysit. Today GripTrack is a server-
rendered FastAPI app that assumes a hosted environment (TLS-terminating reverse
proxy, Secure cookies, Alembic migrations run by a container entrypoint), so it
can't simply be "installed" on a phone as-is.

## Solution

Ship GripTrack as an Android app that **embeds a full CPython runtime (via
Chaquopy)** running the existing FastAPI backend on `http://127.0.0.1:<port>`,
with a **WebView** pointed at that loopback address. The database is an
app-private on-device SQLite file; schema and seed data are created on first
launch by running the existing Alembic migrations. **The entire Python backend
is reused unchanged** — the Android project is a thin native shell plus a small
launch entry that reproduces, on-device, what `docker-entrypoint.sh` does in the
container. Login stays exactly as it is today (same screens, same code path):
on a fresh install the owner registers once (becoming admin) and the session
cookie persists across restarts. The result is a self-contained personal app
with zero online server, losing none of today's features.

## User Stories

1. As the app owner, I want to run GripTrack as an installed Android app, so that I no longer depend on any web host or online server.
2. As the app owner, I want all my data stored on my phone, so that nothing leaves my device and there is no server to maintain.
3. As the app owner, I want the app to work fully offline / in airplane mode, so that I can log training in a gym with no signal.
4. As the app owner, I want to keep exactly the features I have today (max tests, Focus session logging, climb logging, history, CSV export, analytics dashboard), so that moving to Android loses nothing.
5. As the app owner, I want to log in once and stay logged in across app restarts, so that I'm not re-entering my password every session.
6. As the app owner, I want the same login screen I already have, so that the app behaves like the web version and the codebase doesn't fork.
7. As the app owner, on first launch with an empty database I want to create my account and become admin, so that I can start using the app with no external setup.
8. As the app owner, I want my data to survive killing and reopening the app, so that persistence is reliable.
9. As the app owner, I want the app to open in a reasonable time, so that logging between hangs isn't gated on a long boot.
10. As the app owner, I want to install the APK directly on my own phone, so that I don't need an app store.
11. As the app owner, I want the analytics dashboard chart to render on-device, so that I can see my TrainingVolume trend without a server.
12. As a developer, I want the Android app to reuse the existing FastAPI backend unchanged, so that I maintain one codebase, not two.
13. As a developer, I want the on-device launcher to reproduce the container entrypoint's migration sequence (set the DB path, run migrations to head, then serve), so that schema and seed data are created the same proven way.
14. As a developer, I want the WebView pointed at the same loopback host:port the app posts to, so that the existing same-origin CSRF check keeps passing without weakening it.
15. As a developer, I want the app to run in non-production cookie mode on http loopback, so that the session cookie isn't dropped for lack of HTTPS.
16. As a developer, I want a device-generated session secret persisted per install, so that sessions stay valid across restarts and aren't signed with the shared dev fallback key.
17. As a developer, I want service-worker registration disabled in the WebView build, so that I avoid unreliable WebView SW behavior that's redundant when the server is already local.
18. As a developer, I want the backend Python source, templates, static assets, and migrations packaged into the app so every file-path read resolves, so that the server imports and serves correctly on-device.
19. As a developer, I want to drop the uvicorn native extras (uvloop/httptools) in favor of a plain ASGI runner on Android, so that I minimize the native-wheel surface.
20. As a developer, I want the existing pytest HTTP-seam suite to remain the backend's coverage, so that behavior stays verified without new test infrastructure.
21. As a developer, I want a written manual on-device smoke checklist, so that the native shell is verified consistently on real hardware.
22. As a developer, I want a single embedded server that survives Android backgrounding/resume, so that resuming the app doesn't spawn duplicate servers or fail to reconnect.

## Implementation Decisions

- **New native shell, reused backend.** Create an Android Studio / Gradle project using the **Chaquopy** plugin (embeds CPython, installs pip requirements). The FastAPI backend, Jinja templates, `/static` assets, and the `migrations/` tree are packaged into the app so all disk reads resolve on-device (the app imports fail if templates/static/migration files are missing — e.g. the service-worker cache-version hash reads static files at import time). Target **Python 3.12** (matches the project).

- **On-device launch sequence (reproduces `docker-entrypoint.sh`), run on a background thread at app start:**
  1. Set `GRIPTRACK_DATABASE_URL` to an app-private **absolute** SQLite path (four-slash `sqlite:////…/files/griptrack.db`). The engine already auto-creates the parent directory and applies WAL + `busy_timeout` per connection, so no concurrency work is needed.
  2. Run **Alembic `upgrade head`** (via the Alembic Python API, with the packaged `migrations/` as the script location and CWD/sys.path set so `backend` imports). This creates the schema and seeds `grip_types` + the global default `training_protocol` on a fresh DB.
  3. Import the existing **`create_app()` factory** and serve `backend.main:app` with a plain ASGI server bound to `127.0.0.1:<port>`.
  4. Poll `/health` until it returns 200, then load the WebView. Show a splash/loading state until then.

- **Cookie / CSRF / HTTPS adaptations for http loopback (no backend logic changes, only how it's launched):**
  - Run with `GRIPTRACK_ENV` **unset** (non-production). Setting production mode forces `Secure` cookies, which a plain-http WebView refuses to store — that would silently break login. Non-production mode keeps `SameSite=Lax`, non-Secure cookies that work on loopback.
  - Provide a **device-generated `GRIPTRACK_SESSION_SECRET`**, created once on first launch and persisted in Android app storage, so sessions survive restarts and aren't signed with the hardcoded dev fallback. (A secret that changes each launch would invalidate the cookie and force re-login every time — explicitly avoid that.)
  - Point the WebView at the **exact same `127.0.0.1:<port>`** used for form posts. The existing CSRF middleware compares `Origin` netloc to `Host`; loopback posts match and pass, **but only if host+port match exactly** — do not mix `localhost` and `127.0.0.1`. Use a fixed loopback host string everywhere and, if the port is dynamic, load the WebView at the actually-bound port.

- **Single long-lived server across the Android lifecycle.** Start exactly one embedded server for the process; on background/resume, reconnect the WebView to the existing server rather than rebinding the port or starting a second instance.

- **Disable the service worker for the WebView build.** The offline caching the SW provides is redundant when the server is on-device, and WebView SW support is unreliable. Guard/skip `register-sw.js` registration for this build; the app works fully without it. The PWA manifest is unnecessary here.

- **Native-dependency surface (the top feasibility risk, called out because we chose not to gate on a spike).** The compiled packages needing Android arm64 wheels under Chaquopy are **`bcrypt`** (Rust `_bcrypt`, used for password hashing) and **`pydantic-core`** (Rust). Confirm these build/run under Chaquopy **early in the build**, before investing in shell polish. Use plain `uvicorn` (drop the `[standard]` extra so uvloop/httptools aren't required), or another pure-Python-friendly ASGI runner. **This work must be sequenced after the matplotlib/pandas removal (issue #87)**, which deletes the two heaviest native deps and is a prerequisite for a tractable dependency set.

- **First-run account creation.** On the empty on-device DB (after migrations), the owner navigates to the existing `/register` screen and becomes the admin. Simplest configuration: **do not set `GRIPTRACK_BOOTSTRAP_TOKEN`**, so first registration needs no code — email + password + unit choice, and they're auto-logged-in with seeded default plates. (Setting a bootstrap token would require typing it into the invite field on first registration; unnecessary on a single-owner device.)

## Testing Decisions

- **Backend: no change in seam.** The reused FastAPI backend keeps its existing **HTTP-seam pytest suite** (`TestClient` against an isolated SQLite DB) as its coverage. Good tests here assert external HTTP behavior, not implementation details — unchanged by this work.
- **Any pure-Python launch/bootstrap helper** introduced for the on-device sequence (env setup + programmatic Alembic upgrade + app construction) should be thin and, where it has logic worth pinning, testable as a plain function or at the existing HTTP seam. Prefer adding no new seam.
- **Native shell: manual on-device smoke checklist** (no new automated Android seam — matches the personal-instrument scope). The checklist verifies, on a real phone: install the APK; cold start reaches the login screen; register the first account (becomes admin); log a work set via the Focus screen; view the TrainingVolume chart on the dashboard; export CSV; **kill and reopen the app and confirm data + login persist**; and run the whole flow in **airplane mode** to confirm no network is required.
- **Prior art:** the existing HTTP-seam tests in `tests/` and the `pytest-playwright` e2e harness (used as the model for how client behavior is smoke-tested, though the Chaquopy/WebView shell itself is verified manually, not via Playwright).

## Out of Scope

- A native rewrite (Kotlin/Flutter/React Native) — that is the separate "Option 4" path and is explicitly not chosen here.
- Removing or decommissioning the existing web/Docker/Fly deployment — it stays in the repo and keeps working; retiring it is a later decision once the Android app is proven.
- App-store (Play Store) publishing, store listing, and store-grade signing — personal sideload/APK install is the target; store distribution is out of scope.
- iOS.
- Any change to authentication, accounts, sessions, or invites — login is kept exactly as-is.
- Offline WorkSet sync (#20), push notifications, background/foreground services beyond keeping the single server alive, and wake-lock behavior.
- Automated Android instrumentation tests (Espresso) or a Playwright-against-local-server proxy.
- The matplotlib/pandas removal and the client-side chart migration — covered by issue #87, which is a **prerequisite** for this work, not part of it.

## Further Notes

- **Sequence after #87.** Removing matplotlib and pandas first shrinks the native-wheel surface to `bcrypt` + `pydantic-core` and moves the dashboard chart client-side (into the WebView), which is exactly what an embedded build wants.
- **Cold start is the known soft spot** (CPython init + imports + the Alembic head-check + server bind, all on ARM). Mitigations to keep in mind during the build: lazy imports on hot paths, a splash while `/health` warms, and keeping the process/server resident so warm starts are instant.
- **Feasibility risk acknowledged:** we deliberately did not gate this spec behind a throwaway spike, so the `bcrypt`/`pydantic-core` arm64-under-Chaquopy question should be answered as the *first* build step — if either can't be made to work under Chaquopy, revisit the approach before building the shell.
- The launch entry is the on-device analog of `docker-entrypoint.sh`; treat that script as the reference for the exact migration/serve sequence to reproduce.
