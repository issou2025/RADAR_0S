## Side A

- **Source**: LiteLLM vendor documentation, `https://docs.litellm.ai/docs/completion/anthropic_advisor_tool` (to be mined as `source-notes/docs-litellm-anthropic-advisor-tool.md`)
- **Claim**: Exceeding `max_uses` is an **out-of-band error that the gateway raises** — `AdvisorMaxIterationsError` — i.e. the cap is enforced as a hard failure of the request path, and `max_uses=0` disables the advisor entirely.
- **Evidence**: The "How it works (LiteLLM native orchestration)" bullet list, quoted verbatim from the page:
  > "Enforces `max_uses` as a hard cap; `AdvisorMaxIterationsError` is raised if exceeded, and `max_uses=0` disables the advisor entirely"
- **Confidence**: emerging (documented vendor capability surface; a named Python exception is a concrete, observable contract)

## Side B

- **Source**: Anthropic vendor documentation, `https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool` (linked as "Anthropic Advisor Tool Documentation" from the LiteLLM page's Additional Resources)
- **Claim**: Exceeding `max_uses` is an **in-band, non-fatal error** — further advisor calls return an `advisor_tool_result_error` block with `error_code: "max_uses_exceeded"`, the executor continues without further advice, and the request itself does not fail. The cap is a per-request cap, not a per-conversation cap, and its default is `unlimited`.
- **Evidence**: The `max_uses` row of the "Tool parameters" table:
  > "Maximum number of advisor calls allowed in a single request. Once the executor reaches this cap, further advisor calls return an `advisor_tool_result_error` with `error_code: "max_uses_exceeded"` and the executor continues without further advice. This is a per-request cap, not a per-conversation cap."

  and the "Error results" section:
  > "The executor sees the error and continues without further advice. The request itself does not fail."

- **Confidence**: settled for the documented response contract (explicit error block shape plus an explicit negative statement that the request does not fail)

## Why is this a contradiction (not just a difference)?

The two pages describe **the same `max_uses` field on the same tool type
(`advisor_20260301`) in the same beta program (`advisor-tool-2026-03-01`)**,
and they agree on the *graceful* part — in both, the executor keeps going
without further advice once the cap is reached. They disagree on **where the
signal lands and whether the request survives**, which is the entire operator
surface:

| | LiteLLM page | Anthropic page |
|---|---|---|
| Failure channel | raised exception (`AdvisorMaxIterationsError`) | in-band content block (`advisor_tool_result_error`) |
| Does the request fail? | not stated; an exception implies a failed call | explicitly "The request itself does not fail." |
| Client-visible signal | transport/SDK error path | 200 with an error block inside `content[]` |
| Default | (not stated) | `unlimited` |
| Silent-failure risk | none — loud | high — a 200 whose advisor never ran past the cap looks like success |

An operator cannot write one alerting rule for "advisor cap reached" across
both paths. Retry logic, error-budget accounting, and the "did the advisor
actually advise anything?" question all branch on this. A gateway that
*transparently* forwards Anthropic-native advisor traffic and *also* offers its
own orchestration loop is exactly the deployment where both semantics are live
at once, so the ambiguity is not hypothetical.

There is a plausible reconciliation — LiteLLM runs its *own* orchestration loop
for non-Anthropic executors (so the gateway, not Anthropic, owns enforcement and
may legitimately surface an exception), while on the native Anthropic path the
upstream server-side loop owns it and returns the in-band block. **That
reconciliation is an inference, not something either page states** — the LiteLLM
page does not scope `AdvisorMaxIterationsError` to the orchestration-loop path
only, and the Anthropic page says nothing about LiteLLM. Resolving this decides
whether the guide's rule is "handle the exception" or "inspect the content
blocks" or "handle both."

## Filer's recommended verdict (optional)

`unresolved` — the two statements may both be true on different code paths
