# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**ENH: IfcObjectType parameter is ignored for IfcCivilElement because it has no PredefinedType**

*Project description:*
### Enhancement Description

When exporting Revit elements as `IfcCivilElement` to IFC4, the value assigned to the Revit parameter `IfcObjectType` is not exported to the IFC `ObjectType` attribute.

This appears to be caused by the current logic in `IFCInstanceExporter.SetObject()`.

For IFC4+, `ObjectType` is calculated from the Revit element only when:

- `PredefinedType == USERDEFINED`, or
- the exported entity is a subtype of `IfcContext`.

As a result, `NamingUtil.GetObjectTypeOverride()` is not called for `IfcCivilElement`.

However, `IfcCivilElement` does not have a `PredefinedType` attribute at all. Therefore, it is impossible to set `PredefinedType = USERDEFINED` for this entity and consequently impossible to export a user-defined `ObjectType` using the standard `IfcObjectType` parameter.

According to the IFC4 Add2 TC1 specification, this is a valid and explicitly described use of `IfcObject.ObjectType`.

The semantic definition of `IfcObject` states that the `ObjectType` attribute is used:

> “to provide a type information (could be seen as a very lightweight classifier) of the subtype of IfcObject, if no PredefinedType attribute is given.”

Official buildingSMART reference:

[[IfcObject — IFC4 Add2 TC1 Reference View](https://standards.buildingsmart.org/MVD/RELEASE/IFC4/ADD2_TC1/RV1_2/HTML/schema/ifckernel/lexical/ifcobject.htm?utm_source=chatgpt.com)](https://standards.buildingsmart.org/MVD/RELEASE/IFC4/ADD2_TC1/RV1_2/HTML/schema/ifckernel/lexical/ifcobject.htm?utm_source=chatgpt.com)

`IfcCivilElement` inherits `ObjectType` from `IfcObject`, while `IfcCivilElement` itself has no `PredefinedType` attribute.

Official buildingSMART reference:

[[IfcCivilElement — IFC4 Add2 TC1 Reference View](https://standards.buildingsmart.org/MVD/RELEASE/IFC4/ADD2_TC1/RV1_2/HTML/schema/ifcproductextension/lexical/ifccivilelement.htm?utm_source=chatgpt.com)](https://standards.buildingsmart.org/MVD/RELEASE/IFC4/ADD2_TC1/RV1_2/HTML/schema/ifcproductextension/lexical/ifccivilelement.htm?utm_source=chatgpt.com)

Therefore, according to IFC4, the following use case should be valid:

```text
IfcCivilElement
ObjectType = "Asphalt pavement"
```

or:

```text
IfcCivilElement
ObjectType = "Lawn"
```

without requiring a `PredefinedType` attribute.

The relevant logic appears to be located in `IFCInstanceExporter.SetObject()`:

[[IFCInstanceExporter.cs — Autodesk/revit-ifc](https://github.com/Autodesk/revit-ifc/blob/master/Source/Revit.IFC.Export/Toolkit/IFCInstanceExporter.cs?utm_source=chatgpt.com)](https://github.com/Autodesk/revit-ifc/blob/master/Source/Revit.IFC.Export/Toolkit/IFCInstanceExporter.cs?utm_source=chatgpt.com)

For IFC4+, the current code essentially determines whether to calculate `ObjectType` using:

```csharp
forceObjectType =
    string.Compare(
        exportType?.PredefinedType ?? enumTypeValue,
        "USERDEFINED") == 0;

calcObjectType =
    forceObjectType ||
    IFCAnyHandleUtil.IsSubTypeOf(
        objectHandle,
        IFCEntityType.IfcContext);
```

`NamingUtil.GetObjectTypeOverride()` is then called only if `calcObjectType` is `true`.

For `IfcCivilElement`:

```text
PredefinedType does not exist
        ↓
PredefinedType cannot be USERDEFINED
        ↓
forceObjectType = false
        ↓
calcObjectType = false
        ↓
IfcObjectType parameter is not read
        ↓
IfcCivilElement.ObjectType remains empty
```

For IFC entities that do not define a `PredefinedType` attribute, the exporter should allow the Revit `IfcObjectType` parameter to populate the inherited `IfcObject.ObjectType` attribute.

For example:

**Revit**

```text
IfcExportAs = IfcCivilElement
IfcObjectType = Asphalt pavement
```

**Expected IFC**

```text
IFCCIVILELEMENT(
    ...,
    'Asphalt pavement',
    ...
);
```

The exact implementation may differ, but conceptually `NamingUtil.GetObjectTypeOverride()` should also be evaluated for IFC entities where no `PredefinedType` attribute exists.

## Use case

This is particularly important for civil/site models.

In IFC4, different civil engineering objects may be exported as `IfcCivilElement`. For example, different site surface or pavement types may need to be distinguished as:

```text
IfcCivilElement.ObjectType = Asphalt pavement
IfcCivilElement.ObjectType = Concrete pavement
IfcCivilElement.ObjectType = Paving blocks
IfcCivilElement.ObjectType = Lawn
```

Currently, these distinctions cannot be exported through the standard `IfcObjectType` parameter in Revit because `IfcCivilElement` has no `PredefinedType` and therefore can never use `USERDEFINED`.

This appears to leave a valid IFC4 `ObjectType` use case unsupported by the Revit IFC Exporter.

Please consider allowing `IfcObjectType` to populate `IfcObject.ObjectType` when either:

1. `PredefinedType == USERDEFINED`, as currently implemented; **or**
2. the IFC entity does not define a `PredefinedType` attribute.

This would align the exporter behavior with the semantic definition of `IfcObject.ObjectType` in IFC4.
