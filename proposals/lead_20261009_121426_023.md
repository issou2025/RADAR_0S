# T832-MIN v4 — build ONE useful ZNP firmware, prove basics, decide quickly

**Goal:** reliable Zigbee2MQTT operation for our real MR4U / CC2674P10 network (last restored vendor20240716 baseline: **103 verified security records**, ~60 routers). **Do not build an academic Zigbee test laboratory.**

**Status:** PLAN ONLY; no implementation, firmware upload, HA/Z2M change, coordinator reset, network restore or new Muse session authorized by this issue. **First decision: the existing vendor baseline was last verified working after a genuine MR4U cold boot on 2026-10-08. Do not disturb it merely to try custom firmware.**

**What has changed:** [v4 overengineering audit and cut list](https://github.com/analienx/Zigbee-Coordinator/issues/48#issuecomment-6078452867). V1–v3 specified useful source research but overcommitted to four variants, 58 negative tests, large reviewer panels, factorial board experiments and a broad NV forensic program. **This v4 is the sole implementation authority.** Old appendices A/B/C/D are optional research references, not work to automatically execute.

## 1. Deliverable and choice of approach

Deliver **one usable, minimally modified CC2674P10 ZNP firmware (T832-MIN)** based on pinned TI SDK 8.32.00.07, with proven MR4U hardware settings and the *few* host/stack adaptations Zigbee2MQTT actually requires. **Do NOT rewrite Zigbee stack.**

**Production goal:** useful stable operation, real unicast, groupcast, joining, reporting, restart/rejoin, correct security retention and capacity for current network and growth. A firmware with a pristine code history but nonfunctional groupcast or broken Herdsman startup is NOT success.

**Source purity is a means, not the end:** start from a pristine, pinned TI upstream checkout and use the existing GitHub Actions build/toolchain recipes only as tools. R10's firmware patcher explicitly imports NV recovery changes; do not call `apply_r6.base()` or silently import R10 NV guards/diagnostics. A *documented* minimum functional patch for host version, extended NV/security access, multicast correctness, MR4U RF/UART etc. is acceptable when source and tests show it is required. Do not copy the entire Koenkk patch wholesale. One patch file/catalog tracking changed source files, reasons and upstream SHA is enough—not a framework for perfect classification of every generated byte.

**No automatic extra firmware variants.** A raw-TI **compile baseline/source diff** is useful; it does not need separate release packaging or a physical test. `GEOM15`/vendor NV reverse compatibility, `CAP192` standalone comparator, TI 8.30/8.33 bisect, extra diag, alternative board/stack are **deferred** until a specific reproducible failure warrants them. The eventual production candidate can have the required **192-slot profile** built into the *same* T832-MIN branch after basic functionality is proven; this is a capability step, not a new speculative firmware family.

## 3. Implement ONE candidate with the existing hosted tooling — M1

Use **one new MIN worktree/branch and one draft PR**, normally based on `main`; where PR46 is a toolchain dependency, extract/copy only verifiably non-behavioral build infrastructure or document the stack dependency. No unnecessary new generator frameworks.

Candidate must support:
1. **Correct MR4U CC2674P10 image:** real silicon target/ISA, linked TI libraries, startup vectors, CCFG ROM BSL recovery, UART and bridge configuration, clocks, HF-XOSC settings, DCDC/VDDR, PA/antenna path. Pin and review the settings that matter. Do NOT copy Ebyte 20 dBm or its old XOSC delta. Unknown safety-critical pin/CCFG/RF remains **HARDWARE_BLOCKED**, even if compilation succeeds.
2. **ZNP compatibility:** demonstrate actual Zigbee2MQTT/Herdsman version feature expectations. Upstream TI product `0` vs later ZStack product `1` changes queue/host behavior; use the supported product/revision semantics and only commands genuinely implemented. Enable appropriate security/NV APIs needed for a future restore. Verify `SYS_PING`, `SYS_VERSION`, startup request path, ZDO, AF, extended NV/security management; don't claim fake adapter smoke is physical RF.
3. **Functional Zigbee semantics:** retain group destination address in APS (Koenkk explicitly switches `MULTICAST_ENABLED FALSE`), normal router join/rejoin, incoming ZCL reporting. Apply minimum source-proven behavior if necessary; no generic routing, NV compaction recovery, queue or scheduler “optimization” without a reproducible failing case.
4. **Persistent state:** consistent NVS base/size/page count across compiled macros, generated SysConfig/NVS_config[0], linker/map and actual HEX. Start with a small disposable NVS for simple smoke; production-capable 150+ sizing is a **later acceptance step in the same branch**. No assumption that matching vendor15 physical region equals matching vendor record format.
5. **Safety:** no writes into configured NVS/CCFG by packaged app image, no destructive autoformatter, no bypass of existing firmware recovery entry and never embed real household Zigbee credentials.

**Exit M1:** one real hosted-built T832-MIN OUT/HEX/BIN (where correctly supported), map, manifest with source/SDK/toolchain and image hashes, and an honest list of any unknown board/hardware facts. **BUILD_OK is not a flash permit.**

## 4. Small, valuable CI suite — M2

**Only GitHub-hosted Actions** for all tests, compilation, audit, acceptance and packaging in this public repository, at the exact final commit SHA. Don't use local/WSL/self-hosted builds. Pin TI SDK 8.32.00.07 and the actual P10 example, compare changes against pristine TI so no R10 NV guards are unintentionally inherited.

Mandatory **focused checks**, not a 58-test certification programme:

- [ ] **T1 Real compile/source:** exact pinned TI compiler, SDK libs and example seed; actual CC2674P10 image; no hidden R10/Koenkk recovery changes. Existing P10 projectspec/5-vs-2 page inconsistency is explicitly resolved in effective build, not ignored.
- [ ] **T2 Boot/image:** valid CCFG/vectors/BSL, no app/NVS/CCFG overlap, correct region/ROM recovery metadata, adequate linker/RAM margin. Treat unknown real board pin/RF proof as a hardware block, not a build failure.
- [ ] **T3 Real host API:** pinned Herdsman fake transport correctly handles actual `SYS_PING`/`SYS_VERSION` and ZDO startup *SREQ/SRSP vs later state9 distinction*; required AF/NV/security commands supported or explicitly blocked. Include one wrong product/revision negative.
- [ ] **T4 Persistence/capacity:** run existing real TI NVOCMP host harness against disposable synthetic records for one representative boot/reopen, near-full region, and interrupted write/compaction negative. Preserve known failures—do not “fix” by silently enabling reformat.
- [ ] **T5 Exact artifact:** source/compile/toolchain SHA, actual linker/NVS region, HEX/OUT hashes and version, no secrets; wrong source or wrong image fails seal. Only deliver firmware that is clearly marked `NOT_PRODUCTION_QUALIFIED`.

Do not require full TI stack call graph, 58 adversarial cases, binary-perfect two-run reproducibility, 3 blind reviewers+challenger or a wide SDK matrix before basic ZNP operation. **One independent critical code review** after M2 is sufficient for an offline candidate; second dedicated deployment/recovery safety review before any **hardware** use.

**Exit M2:** a build and host-protocol candidate we can meaningfully smoke-test, with failures and limitations shown plainly. After **two consecutive blocked iterations on the same problem with no new diagnosis**, do a STOP/REDESIGN decision rather than expanding observability.

## 5. Verify it actually operates Zigbee — M3 (SPARE LAB; separate permission)

Only on a **verified sacrificial/spare CC2674P10/MR4U**, with an independent recovery path and disposable network. **No live household P10** and no cloned production identity. If spare hardware is unavailable, stop at `OFFLINE_READY / HARDWARE_PENDING`; never improvise with the recovered network.

**Minimum practical smoke — one network, few devices, no factorial matrix:**

1. Boot and return real UART `SYS_PING/SYS_VERSION`; form a disposable network, reach ZDO state9 and preserve NIB.
2. Join **two mains-powered, group-capable devices** (at least one router) and, **if available**, one sleepy end device; verify interviews and actual inbound reporting. A single sleepy sensor is not a suitable second groupcast receiver.
3. Test one actual unicast and one **groupcast to the two capable receivers** (source-proven routing/APS behavior); confirm physical receiver state, not merely MQTT publication. If two suitable receivers are unavailable, groupcast is UNTESTED and release cannot claim that feature.
4. Warm restart and genuine full-power restart *on spare only*, verify same identity, counters monotonic, devices rejoin and group/bindings still work.
5. Run ordinary bounded mixed traffic and observe basic error rate/AF/ZDO/SYS responsiveness for an initial soak, e.g. **24–48 hours on approved spare**. This checks obvious instability; it **cannot statistically prove** long-term reliability or reproduce 60+ routers using two devices.

**EXIT M3:** `LAB_FUNCTIONAL` with exact image/run receipt, or `FAIL + one suspected cause`. Record only relevant failures, do not start the four-board X-SDK campaign automatically. If a concrete failure is discovered, allow **one narrow patch/comparator** with a targeted rerun; otherwise STOP/PIVOT.

## 6. Make it suitable for *our* network — M4, only if M3 succeeds

A functioning 2-device toy network is not enough for 103 security records/~60 routers. But extensive NV source archaeology is not required if safe **backup → restore → verify** works on sacrificial data.

- [ ] Size for current **103 key records** AND issue #42 growth target **≥150 devices / preferred 192 TC**. Confirm realistic memory/flash budget, 96 provisional NWK device-list and address-manager sizing, occupancy/neighbor/source-route semantics independently; 13 NV pages is **an estimate**, not a magic constant. One production-capable T832-MIN profile, not a separate CAP192 research family.
- [ ] Real TI-driver NVS population, reboot, updates and compaction at **103** and **192** synthetic security records; check effective image values, monotonic counters, no silent allocation failure.
- [ ] On **spare hardware**, prove a **disposable coordinator backup → candidate restore** with unchanged PAN/extPAN/IEEE/network key, Trust Center keys and counters and actual Zigbee device rejoin. The final restore path cannot depend on mere matching vendor NV physical geometry; require deterministic backup format/security semantics. No actual production backup/keys are put in GitHub.
- [ ] Require a plan for flash erase/write ranges and app-held preboot NVS observation **only if that physical attribution matters to the chosen migration mechanism**. For backup-driven restore to an already disposable/blank lab coordinator, do NOT block basic smoke on forensic ability to preserve raw vendor NV.
- [ ] Recover a bad candidate independently (ROM BSL/known verified rollback) and record exact operator-safe rollback steps; prove that a failed flash cannot permanently strand spare board.
- [ ] Judge whether this candidate actually has a plausible advantage over **last-working vendor20240716**. A newly built firmware is not an upgrade merely because we own its source.

**EXIT M4:** `PRODUCTION_CANDIDATE` **for a proposed separately authorized controlled trial** only when full-restore/security correctness and meaningful groupcast/join/route smoke have passed. It is **not** yet a reliability-certified replacement.

## 7. Decision and STOP rules (the most important gate)

**Choose one of three outcomes:**

| Outcome | Action |
|---|---|
| Vendor20240716 continues operating acceptably and MIN cannot demonstrate a concrete advantage | **STOP, retain vendor firmware.** No risky migration to justify sunk cost. |
| MIN passes required network functions, capacity and disposable backup/restore with a justified benefit | Prepare a separate user-approved production trial with fresh coordinator + Z2M backups, explicit failback, counter/security verification and observation. **This issue itself never flashes production.** |
| Clean/minimal MIN shares unrecoverable P10/SDK hangs, restoring safely fails, or effort repeatedly grows without reducing uncertainty | **STOP custom P10 development**; assess a supported alternative coordinator with **verified restore/no-repairing path** rather than starting R12/R13. |

**Stop triggers:** two blocked cycles with unchanged hypothesis; repeated need for broad NV/queue/routing patches; no spare/recovery available; inability to preserve original identity/keys/counters; severe unfixable TI/ROM defect; inability to show meaningful benefit over running vendor image. No mandatory 7-day test, 150 physical devices, TI CC1354 vs CC2674 2×2 test or full external anecdote audit to pass M1/M2/M3. More work requires explicit evidence explaining why it could change a real decision.
