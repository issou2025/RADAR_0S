# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Engine-token liveness monitoring: a 7-day fleet-wide dev-lead outage went unalerted, and pr-review fails open**

*Project description:*
## Problem

`dev-lead` failed **100% of runs across 8 repos for seven days** (last green `2026-08-23T14:20Z`, still failing `2026-08-30T18:19Z`) and no alert reached a human. The fleet only noticed because a person went looking.

Failure signature (identical on every run, ~3–8s, fails at the first real step):

```
Engine token preflight (#1525)
##[error]CLAUDE_CODE_OAUTH_TOKEN is not provided to dev-lead-reusable.
```

Two separate gaps let a total engine outage run silently for a week.

### Gap 1 — nothing alerts on a sustained preflight failure

Fleet Monitor did file `#1577` and `#1586`, but they are periodic health-check reports that accumulate without escalation; both sat open and unactioned. A workflow that is **100% failing across the whole fleet** is categorically different from a flaky check and needs to escalate differently.

### Gap 2 — `pr-review` has no token preflight at all, so it fails *open* and looks healthy

This is the more dangerous half. `pr-review.yml` declares `CLAUDE_CODE_OAUTH_TOKEN` as `required: false` (correct, per #1525) but — unlike `dev-lead-reusable.yml` — has **no preflight step**. During the same outage `pr-review` reported **96/97 runs successful**, and that number was cited as evidence the engine was healthy. Job conclusion is not evidence that work happened. A tokenless `pr-review` run can exit `success` having reviewed nothing.

## Scope

1. **Add an engine-token preflight to `pr-review.yml`**, mirroring `dev-lead-reusable.yml`'s `Engine token preflight (#1525)` step verbatim — same error text, same `AGENTS_PAUSED` guidance, same `exit 1`. A missing token must fail loudly, not silently no-op.

2. **Add a scheduled engine-liveness check** covering every repo that hosts a `dev-lead` or `pr-review` caller stub. For each, assert the most recent run did **not** fail at the preflight step. Alert on breach — do not just append to a periodic report.

3. **Escalation semantics.** Distinguish, and escalate differently:
   - `AGENTS_PAUSED=true` → deliberate, silent, no alert.
   - Preflight failure on **≥2 consecutive runs in ≥2 repos** → fleet-level alert (the outage class this issue exists to catch).
   - Isolated single-repo failure → normal health-check reporting.

4. **Cover credential expiry generally, not just this secret.** `GH_PAT_DON_PETRY` is a classic PAT and a silent single point of failure for the entire apply-repo-settings initiative (`#984`/`#985`/`#1209`): rotation or revocation surfaces only as an opaque 401/403 on the next scheduled run. Include a scope/expiry check for it in the same monitor.

## Acceptance criteria

- [ ] `pr-review.yml` fails fast with the same actionable single-line error when `CLAUDE_CODE_OAUTH_TOKEN` is absent, and this is covered by a test.
- [ ] A scheduled check reports engine-token liveness per repo for both `dev-lead` and `pr-review`.
- [ ] `AGENTS_PAUSED=true` suppresses the alert entirely (no false alarm on a deliberate pause).
- [ ] Two consecutive preflight failures in two or more repos raises a fleet-level alert distinct from routine health-check output.
- [ ] `GH_PAT_DON_PETRY` scope/expiry is checked and reported.
- [ ] **Red-team verification (required, do not skip):** temporarily withhold the token in a scratch repo, confirm the alert fires, then restore. Per the fleet's standing rule, a green check is not evidence — demonstrate the detection actually triggers rather than asserting it does.

## Notes for the implementer

- Do **not** make the secret `required: true` on the reusable — `#1525` deliberately relaxed that, because a hard requirement fails the *caller* at secrets-evaluation before any step runs and presents as an opaque fleet-wide dispatch failure. Presence is enforced by the preflight step instead. Keep that design.
- Unexplained behaviour worth preserving as a test case: during this outage, `pr-review` **received** the token (`CLAUDE_CODE_OAUTH_TOKEN: ***`) while `dev-lead-reusable` received it **empty**, in the same repo, on the same `secrets: inherit`, with no `environment:` on either job, and with the reusable at tag `dev-lead/v1-stable` byte-identical to `main`. No structural difference accounts for it. Since the cause is unknown, the outage can recur without any config change — which is the whole reason this monitor is needed.
