# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Phase 5 — mDNS Auto-Discovery for diqit-log CLI**

*Project description:*
## Problem Statement

The `diqit-log` Rust CLI currently requires the developer to manually type the POS device's IP address (`diqit-log 192.168.1.5`). In a store environment with multiple devices on WiFi, developers must either memorize IPs, read them from the device settings screen, or guess. This friction slows down the debugging loop — especially when devices restart and get new DHCP addresses.

## Solution

Add **mDNS-based auto-discovery**: the POS app registers a Bonjour/mDNS service when NetworkOutput starts, and the Rust CLI browses the local network to find all running devices. The developer runs `diqit-log` with no arguments, sees a numbered list of discovered devices, picks one, and the TUI launches.

```bash
$ diqit-log
Scanning for POS devices...
  1. 192.168.1.5:9229
  2. 192.168.1.6:9229
Choose a device (1-2) or enter IP: █
```

If no devices are found (or mDNS is blocked), the developer falls back to entering an IP manually.

## User Stories

1. As a developer debugging a store with multiple POS devices, I want to run `diqit-log` with no arguments and see a list of all running devices, so that I don't need to memorize or look up IP addresses.
2. As a developer whose device just received a new DHCP lease, I want the CLI to discover it automatically, so that I don't have to walk to the device to check its new IP.
3. As a developer on a network where mDNS is blocked, I want to fall back to manually entering an IP address, so that the tool still works in all environments.
4. As a developer connecting to a device on a non-default port, I want manually entered IPs to allow a custom port specification, so that I can connect to devices on any port.
5. As a developer running the CLI on Linux or Windows, I want discovery to work without installing additional system services, so that the tool is truly zero-setup.
6. As a developer whose POS app starts after the CLI scan, I want to re-scan by pressing `r` at the selection prompt, so that I don't need to restart the CLI.

## Implementation Decisions

### Dart side: mDNS service registration

- Use raw `dart:io` (`RawDatagramSocket`) for mDNS responder — send DNS-SD announcement packets on UDP multicast `224.0.0.251:5353`
- Register service type `_diqit-log._tcp` with the configured port (default 9229)
- Registration happens in `NetworkOutput.start()` — no new public API, no additional dependencies
- On `NetworkOutput.stop()`, send a goodbye packet (TTL=0) to unregister
- The raw implementation avoids adding a `multicast_dns` dependency to the diqit-logging package

### Rust side: mDNS service discovery

- Use the `mdns-sd` crate to browse for `_diqit-log._tcp` services
- Resolve each discovered service to IP:port
- Timeout after 5 seconds of scanning (fast enough for dev experience, long enough for all devices to respond)
- Display results as a numbered list

### CLI flow

```
diqit-log [address]
  ├─ address provided → connect directly (existing behavior)
  └─ no address → scan mode:
       ├─ devices found → numbered list + prompt
       ├─ none found → "No devices found. Enter IP: █"
       └─ press 'r' → re-scan
```

### Key bindings in scan mode
| Key | Action |
|-----|--------|
| `1`-`9` | Select device by number |
| `r` | Re-scan network |
| Enter on empty | Exit CLI |
| Any IP string + Enter | Connect to manual IP |

### mDNS record format
```
Service: <hostname>._diqit-log._tcp.local
Port:   <networkPort>
TXT:    {"app": "<hostname>"}
```

## Testing Decisions

### What makes a good test
- Test mDNS announcement format generation in isolation (unit test on the DNS-SD packet structure)
- Test that `NetworkOutput.start()` binds the mDNS socket when enabled
- Test that `NetworkOutput.stop()` cleans up the mDNS socket
- Test the Rust scanner by parsing mock mDNS responses (unit test, not real network)
- Do NOT test live network discovery (flake-prone, depends on network environment)

### Test modules
- `lib/src/logger/network_output.dart` — updated with mDNS registration/cleanup
- `cli/src/scanner.rs` — new module for mDNS browsing and result display
- `cli/src/main.rs` — updated flow with scan mode

### Prior art
- Dart: existing `NetworkOutput` tests in `test/src/network_output_test.dart`
- Rust: existing `parser.rs` tests in `cli/src/parser.rs`

## Out of Scope

- App name or metadata in the device list (IP:port only — no TXT record parsing in MVP)
- Continuous discovery while TUI is running (scan happens once at startup)
- IPv6 multicast discovery (IPv4 multicast only)
- Cross-network discovery (same subnet only — mDNS multicast doesn't route)
- Password-protected or access-controlled discovery
- Android/iOS mDNS configuration (Flutter-specific setup deferred to app integration step)

## Further Notes

- mDNS uses UDP port 5353 — must be unblocked on the device's firewall. This is typically open on macOS/Linux but may require configuration on locked-down enterprise networks.
- The `mdns-sd` crate on Rust provides a zero-config implementation via its built-in `ServiceDaemon`; no system Avahi/Bonjour services needed.
- The Dart raw `RawDatagramSocket` approach is inspired by the `shelf_mdns` package's implementation — a few dozen lines of DNS packet construction, well-documented in RFC 6762/6763.
