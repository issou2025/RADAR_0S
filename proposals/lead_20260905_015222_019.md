## Problem

`approval/unattended.py` lets the operator opt into deterministic auto-approval of a scoped set of safe actions, so headless runs are not blocked waiting for a human. The scope is entirely software-engineering shaped:

```python
_DEFAULT_ALLOWED_COMMANDS: tuple[str, ...] = (
    "pytest",
    "python -m pytest",
    "python3 -m pytest",
    "go test",
    "npm test",
    "npm run test",
    ...
)
```

plus file edits confined to the task's own workspace.

Nothing in it describes a *life* action. So for non-engineering automation the choice is all-or-nothing: either every action raises an approval card, or the operator runs in `AUTONOMOUS`, which auto-approves everything short of hard-danger.

## Scope: deliberately small

An earlier draft of this proposed a broad safe-list. On review that is mostly unnecessary. Once north can reach the user on their phone (#2), the answer to most approvals is a single tap, and auto-approval stops being the interesting lever.

What remains worth automating is narrow — three categories only:

1. **Reads.** Fetching, querying, looking something up. No state change.
2. **Messages addressed to the operator themselves.** A notification, a digest, a reminder. Never a message to a third party.
3. **Trivially reversible physical actions.** Toggling a smart-home device, where the undo is another toggle.

## The asymmetry that governs the design

The existing list is defensible because software actions are reversible. A bad `pytest` run costs seconds; a bad edit is `git revert`.

Life actions frequently have no undo. A sent email cannot be unsent. A booked ticket, a submitted form, a payment — all one-way. That difference is the whole reason this list must stay much more conservative than the engineering one, rather than simply being extended by analogy.

Two rules that fall out of it:

- **Sending anything to another human is never auto-approvable**, regardless of how routine it looks.
- **Spending money is never auto-approvable.**

## Proposed fix

Introduce a small, explicit category of safe non-engineering actions alongside the existing command allowlist, honouring the three categories above and the two hard rules. Keep it deterministic and LLM-free, matching the existing module's design — `JudgementFilter` is non-deterministic and is already forbidden from auto-approving these paths.

Stays off by default, like the current behaviour.
