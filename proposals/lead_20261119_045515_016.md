### Expected behavior

A command repeated with the same `--command-id` and the same arguments is recognised as a retry of the first one: it returns the result of the first execution and does not apply the change a second time. `idempotency_conflict` is for a command id that comes back with a different request.

The user guide introduces the option for exactly this purpose (section 5.1):

> Automation options (used by ECOS Studio and CI drivers; optional for interactive use): `--expected-revision N` fails with `revision_conflict` (exit 21) when the workspace revision moved, `--command-id TEXT` stamps the mutation for idempotency/audit, `--no-wait` never blocks on a busy workspace … The same revision/wait flags recur on other mutating commands (`param apply`, `macro import`, `workspace …`)

`--command-id` and `--expected-revision` are described as two independent options; nothing says that the idempotency of `--command-id` depends on also passing `--expected-revision`. The error text itself states the condition that is supposed to be detected: "command id reused with different input".

### Actual behavior

The second, identical call is refused:

```text
$ ecc workspace reset-flow w --command-id K1 --project /path/to/project --plain
workspace_id=w status=flow_reset workspace=/path/to/project/w workspace_revision=2      exit 0
$ ecc workspace reset-flow w --command-id K1 --project /path/to/project --plain
kind=error error=idempotency_conflict reason="command id reused with different input: K1"      exit 1

$ ecc workspace refresh w --force --command-id K2 --project /path/to/project --plain
workspace_id=w status=refreshed workspace=/path/to/project/w workspace_revision=3      exit 0
$ ecc workspace refresh w --force --command-id K2 --project /path/to/project --plain
kind=error error=idempotency_conflict reason="command id reused with different input: K2"      exit 1

$ ecc param apply --workspace w --set design.frequency_mhz=120 --command-id P1 --project /path/to/project --plain
status=applied scope=workspace workspace_id=w workspace=/path/to/project/w workspace_revision=4      exit 0
$ ecc param apply --workspace w --set design.frequency_mhz=120 --command-id P1 --project /path/to/project --plain
kind=error error=idempotency_conflict reason="command id reused with different input: P1"      exit 1
```

With the revision pinned, the same retry is replayed, which is the expected behaviour:

```text
$ ecc workspace reset-flow w --command-id R1 --expected-revision 1 --project /path/to/project --plain
workspace_id=w status=flow_reset workspace=/path/to/project/w workspace_revision=2      exit 0
$ ecc workspace reset-flow w --command-id R1 --expected-revision 1 --project /path/to/project --plain
workspace_id=w status=flow_reset workspace=/path/to/project/w workspace_revision=2      exit 0
```

Summary of an identical retry (same command id, same arguments, no `--expected-revision`):

| Command | Identical retry |
| --- | --- |
| `ecc workspace create w2 --command-id ID` | replayed, exit 0 |
| `ecc workspace archive w --command-id ID` | replayed, exit 0 |
| `ecc workspace reset-flow w --command-id ID` | `idempotency_conflict`, exit 1 |
| `ecc workspace refresh w --force --command-id ID` | `idempotency_conflict`, exit 1 |
| `ecc param apply --workspace w --set K=V --command-id ID` | `idempotency_conflict`, exit 1 |

A real conflict is detected correctly: `--command-id R1 --expected-revision 2` after `R1` was used with `--expected-revision 1` answers `idempotency_conflict`, and a stale `--expected-revision` without a command id answers `revision_conflict` (exit 21) with the expected and the actual revision.

### Root cause

The fingerprint that identifies a request includes the expected workspace revision (`chipcompiler/engine/workspace_lifecycle.py`):

```python
def workspace_command_fingerprint(kind, spec, bindings, expected_revision=None) -> str:
    payload = json.dumps({"kind": kind, "spec": spec, "bindings": bindings,
                          "expectedWorkspaceRevision": expected_revision}, ...)
```

When `--expected-revision` is not given, the handlers fill it in with the workspace's current revision before they call the engine, for example in `reset_workspace_flow`:

```python
current = read_engineering_snapshot_from_directory(ctx.run_dir)
expected = command_input.expected_revision or current["workspaceRevision"]
workspace = reset(ctx.run_dir, expected, command_id=command_input.command_id or str(uuid.uuid4()), ...)
```

The first execution raises the revision by one. On the retry, "current revision" is therefore a different number, the fingerprint differs from the stored one, and `command_retry_matches` reports the retry as a different input:

```python
if not isinstance(record, dict) or record.get("fingerprint") != fingerprint:
    raise WorkspaceLifecycleError("idempotency_conflict", f"command id reused with different input: {command_id}")
```

The same `expected = args.expected_revision or current["workspaceRevision"]` default is in the handlers of `workspace refresh` (`project.py`), `param apply` (`param.py`) and `macro import` (`macro.py`; read in the code, not run here).

### Impact

A client repeats a command with the same id when it does not know whether the first attempt arrived: a timeout, a lost reply, a restarted driver. In that situation it usually does not have the resulting revision either, so it resends the request as it was. That is the case the command id exists for, and it is the one that fails. The error says the input is different, which sends the client looking for a difference that does not exist, and it cannot tell from the answer whether the first attempt was applied.

The workaround, passing `--expected-revision` on every call, is not stated in the guide, and it is not available to a client that does not track revisions.

### Suggested fix

Keep the defaulted revision out of the fingerprint: use the value of `--expected-revision` only when the caller passed it (`None` otherwise), and keep using the current revision for the revision check itself. Alternatively, look up the command id first and, when a record exists, compare it against a fingerprint built without the defaulted revision. A retry with the same explicit `--expected-revision` already works and stays as it is.
