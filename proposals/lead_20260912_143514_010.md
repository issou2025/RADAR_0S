# Project Proposal — Unknown

## Project Understanding
You need assistance with: 
**Provisioning service: close the manual gap between a flashed card and a set-up node**

*Project description:*
Child of #223. The first buildable piece of that epic, and the one that removes a manual gap I hit every time.

## What it is

A small TypeScript/npm service running on the cluster. Cluster-hosted specifically so it can use **1Password and the environment control that already exists there** -- which makes it easy to test and predict, rather than each provisioning run depending on what is on my laptop.

## The gap it closes

Bringing up a card today means a Windows PowerShell invocation against a checkout that lives under WSL, which means a UNC path, which means `-ExecutionPolicy Bypass` and being in the right working directory. It works and it is documented (`dotfiles-symm/pi-image/provision/README.md`), but it is picky, and after the flash there is a manual SSH step with no automation at all.

## The flow, end to end

1. **Insert a flashed card** -- customised with the right hostname, and with a cert/key this service is expected to authenticate with.
2. **Power on.** It boots, cycles, and comes up on WiFi.
3. **Trigger this web app**: it finds the machine, SSHes in, sets up the software stack, and shuts down gracefully. *This is the piece that does not exist.*
4. **Connect** gadget network, camera, sensors.
5. **Power on from flat 5 V** -- BEC or wall power.
6. **Everyone connects.** Coordinator is logging; the campods are capturing stills and accel.
7. **Determine system function.** One shape for this: a probe over MAVLink/ELRS injected into the mavproxy, with the coordinator running a script in response and emitting telemetry observable in the tlog or the live mavproxy stream.

Steps 1, 2, 4, 5 and 6 are the existing physical flow and frame the ask. **Step 3 is the first deliverable. Step 7 is the second.**

## First deliverable: step 3

Look for a particular machine, connect, do the initial setup, shut down cleanly -- so there is **no manual gap** between "card is flashed" and "node is set up".

It builds on what already exists rather than replacing it:

- `pi-image/provision/Flash-Card.ps1` + `firstrun.sh` already handle steps 1-2 (hostname, user, SSH public key, WiFi, locale).
- `host/one_time.sh [coordinator|campod]` is the setup payload to run over SSH.
- `docs/campod.md` "Every update" is the same operation in recurring form -- the service should cover both first setup and subsequent updates, since they are the same SSH-and-run.
- The gadget-net configuration from #224 is what step 4 turns on.

`fleet.env` already carries `SSH_PUBKEY`; this service's key is what belongs there, so the image trusts it on first boot with nothing further to arrange.

## Second deliverable: step 7

A functional check that does not require a laptop or a display -- a probe in, a script run on the coordinator, telemetry back out through a path already being recorded.

## Notes

- Applies to **both** device roles. The coordinator and the campods differ only in the `device_role` argument.
- Discovery mechanism (mDNS, a known hostname, a scan) is an implementation choice, not a requirement here.
