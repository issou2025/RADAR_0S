# Project Proposal — Unknown

## Project Understanding
You need assistance with: 
**rebase mode's force-push auto-closes open sync PRs — branch content survives, the PR silently leaves the open set**

*Project description:*
Observed 2026-08-18/19 on lecture-python.zh-cn during a backlog drain of 29 open sync PRs. Two open sync PRs were silently closed by rebase mode's force-push, with their branch content fully intact. The PR left the open set; nothing was delivered; no error was raised anywhere.

## Mechanism

Each merge of a translation PR triggers `rebase-translations.yml`, which runs the Action in `mode: rebase` and force-pushes every other open sync branch. When the force-push lands, GitHub momentarily evaluates the branch as having no commits ahead of the base and auto-closes the PR. The close is permanent — GitHub does not reopen the PR when the branch is repopulated microseconds later.

The event logs put both events in the same second, which is the signature to look for:

| PR | `head_ref_force_pushed` | `closed` | Branch content after close |
|---|---|---|---|
| lecture-python.zh-cn#240 | 2026-08-18T23:22:43Z | 2026-08-18T23:22:43Z | 6 files (three likelihood lectures + state) |
| lecture-python.zh-cn#247 | 2026-08-18T23:27:11Z | 2026-08-18T23:27:11Z | 30 commits ahead of main, 30 files |

## Why this is worse than it first looks

The closed PR reports `changed_files: 0` and an empty `gh pr diff`, because the PR object is frozen against a head that no longer matches the branch ref. Anyone auditing the tracker after a drain reads that as "already merged, subsumed by another PR" — which is exactly what I concluded before checking the event log, and I posted an incorrect closing comment on #240 as a result. The branch ref is the only place the truth survives; `gh api repos/OWNER/REPO/compare/main...BRANCH` reports the real `ahead_by` and file count.

This is a silent-delivery-loss shape in the same family as #90 and the W1 work in #259, but it lives in the rebase workflow rather than the sync run, so a declared-vs-delivered assertion inside sync mode would not see it.

## Recovery is not simply reopen

`gh pr reopen` fails once the branch has been force-pushed again after the close (the recorded head no longer matches the ref), so recovery meant recreating the PRs from the same branches, as lecture-python.zh-cn#255 and lecture-python.zh-cn#256. A recreated PR is not a first-class sync PR until three things are restored, each of which failed loudly enough to find but would be easy to miss:

1. The labels `action-translation` and `automated` — the review workflow's `if` requires the first, so review runs report `skipped` without it.
2. The original generated PR body — review mode aborts with "Could not find source PR reference in translation PR body" unless the `### Source PR` block is present.
3. A review re-fire, by removing and re-adding the `action-translation` label.

## Suggested guard

After each force-push in `rebaseSinglePR`, assert the PR is still open and reopen it if not; failing that, treat a post-push closed state as a run failure so it surfaces rather than passing silently. Given issue 160 made rebase mode capable of failing, this seems like a natural addition to that path. A cheaper mitigation, if the race is hard to close directly, is to push the rebased content as a single non-empty update rather than any sequence that leaves the branch momentarily empty.

Related: #276 covers a second defect in the same regeneration path observed the same night, and #259 tracks the broader silent-partial-delivery work.
