## Proposed rule: human understanding gate

Before an assistant tells a teammate to start a significant Issue, run Codex, approve a product decision, or merge an important PR, the assistant must explain in plain language:

1. **What already exists**
   - the relevant current behavior/design/code;
   - where it lives in the project.

2. **What this task is trying to change**
   - the concrete feature, rule, screen, architecture, or files affected.

3. **Why the change is needed**
   - what problem it solves or what project requirement it satisfies.

4. **What decisions belong to the humans**
   - choices that are not already fixed by an approved source/specification;
   - alternatives and consequences when useful.

5. **What the expected result will be**
   - what the developers should be able to see, test, read, or understand after the task.

The assistant must not hide the task behind raw GitHub terminology.

## Proposed rule: humans make product decisions

AI assistants may:
- research;
- explain;
- identify inconsistencies;
- propose options;
- recommend a solution;
- draft specifications;
- implement approved work through local Codex;
- review changes.

AI assistants must **not silently decide**:
- product behavior;
- permissions/business rules;
- UX flows;
- visual direction;
- architecture;
- technology choices;
- scope changes;
- important trade-offs.

When the accepted sources do not already determine an answer, the assistant must surface it as a human decision instead of quietly turning a recommendation into a project rule.

The three human developers may delegate a specific decision explicitly, but the default is that they retain the final say.


## Proposed rule: individual deliberation before GitHub

Before proposing a significant product, UX, architecture, workflow, or technical decision on GitHub, the responsible teammate and their assistant should first discuss it in plain language.

The assistant should present:
- its recommendation;
- reasonable alternatives;
- trade-offs;
- assumptions;
- risks;
- any proposed new rules or decisions.

The teammate should be able to challenge, reject, or modify the proposal before anything is recorded as a project proposal.

Only once that teammate understands and supports the proposal should it be recorded on GitHub for the rest of the team to review.

This discussion does not make the proposal a team decision. It only means the proposing teammate understands and supports what they are putting forward.

## Proposed rule: independent teammate review

Other teammates should review significant proposals independently with their own assistants before final team approval.

Their assistants should:
- explain the proposal in plain language;
- identify assumptions, risks, and trade-offs;
- challenge the proposal when appropriate;
- help the teammate form their own opinion instead of simply endorsing another assistant's conclusion.

The team should work asynchronously whenever possible. A teammate should not be blocked waiting for everyone else unless the task genuinely depends on a shared decision, another person's work, or explicit consensus.

Meetings should be used mainly to:
- resolve disagreements;
- settle choices that genuinely require team consensus;
- confirm major phase transitions;
- approve decisions that affect the whole project.

## Proposed rule: plain-language completion review

Before an important PR is merged, the author's assistant must give the human developer a plain-language review containing:

- **What changed**
- **What did not change**
- **Important decisions now represented by the PR**
- **Files/areas affected**
- **How it was verified**
- **Anything the developer should inspect or try personally**

The human should not be told only that a PR is "clean" or "approved".

## Proposed rule: developer understanding when coding starts

For implementation work, completion explanations should teach the developer enough to follow their own codebase.

For each meaningful coding task, explain at an appropriate level:
- which files/components were added or changed;
- what each important part does;
- how data/actions move through the feature;
- where the main business logic lives;
- how to run or test the feature;
- any unfamiliar framework/library concept introduced.

This is not a requirement to explain every line. It is a requirement that the human developers can understand and maintain the application they are building.

## Proposed rule: phase transition walkthroughs

Before moving from one major project phase to another, the team should hold a human walkthrough of the completed phase.

For the Phase 1 -> Phase 2 transition, the walkthrough must cover the complete accepted functional specification in simple language, including:
- V1 scope;
- all actors and roles;
- studios;
- reservation lifecycle;
- approvals;
- quotas/conflicts/cancellation/expiry;
- equipment;
- projects/documents;
- maintenance/incidents;
- notifications;
- QR access;
- unresolved, recommended and deferred items.

The team can challenge, change, reject or reopen any rule during the walkthrough. Any resulting change must be recorded on GitHub before downstream UX or implementation treats it as authoritative.

## Yassine's proposed additions

Yassine independently reviewed the proposed workflow and wants the following three rules added for team review:

### Keep important PRs understandable

Important PRs should stay small enough that another developer can genuinely understand and explain them. A large AI-generated PR is not acceptable merely because automated checks pass. Prefer several focused PRs over one very large change when that improves human reviewability.

### Agree on module boundaries before Flutter implementation

Before Flutter implementation starts, the team must agree on the main module boundaries, ownership, and interfaces between them. This includes areas such as reservations, projects, equipment, notifications, QR access, incidents/maintenance, and the shared design system. The purpose is to reduce overlapping edits, merge conflicts, and unclear ownership while keeping cross-module contracts explicit.

### Risk question before approving an important PR

Before approving an important PR, the reviewer should be able to answer:

> **What would break if this PR were wrong?**

The review should identify the affected behavior, users, modules, data, or workflow rather than relying only on tests or AI review output. If the reviewer cannot explain the practical failure impact, the PR is not yet understood well enough for approval.
