# Project Proposal — Structural Drawings

**[Feature] API Versioning, OpenAPI/Swagger Documentation & Flutter SDK Generation**

*Project description:*
## Feature Description

Implement API versioning, auto-generated OpenAPI/Swagger documentation, and a TypeScript/Dart SDK for the Flutter mobile app to consume the h-dashboard API reliably.

## Motivation

- **Flutter app integration**: The Flutter app currently consumes `/api/*` routes via Sanctum tokens but has no contract/spec to validate against
- **Breaking changes risk**: Any API change (field rename, new required field, response structure change) silently breaks the mobile app
- **Developer experience**: No interactive API docs for frontend/mobile developers to explore endpoints
- **Versioning strategy needed**: As the API evolves, we need a clear versioning scheme (URL-based: `/api/v1/`, `/api/v2/`) to support gradual migrations

## Proposed Solution

### 1. API Versioning
- Implement URL-based versioning: `/api/v1/...`, `/api/v2/...`
- Add `Accept: application/vnd.h-dashboard.v1+json` header support as alternative
- Version negotiation middleware
- Deprecation headers for old versions

### 2. OpenAPI/Swagger Generation
- Use `darkaonline/l5-swagger` (Laravel 11/12 compatible) or `dedoc/scramble` for auto-generation from:
  - Route definitions
  - Controller PHPDoc/attributes
  - FormRequest validation rules
  - API Resources
- Serve Swagger UI at `/api/documentation` (protected by `safe_role_or_permission:op-cache` or similar)
- Generate OpenAPI 3.1 spec JSON at `/api/openapi.json`

### 3. Annotations/Attributes for Documentation
Add OpenAPI attributes to controllers:
```php
#[OA\Get(path: '/api/v1/hardware', summary: 'List hardware')]
#[OA\Parameter(name: 'search', in: 'query', description: 'Search term')]
#[OA\Response(response: 200, description: 'Success', content: new OA\JsonContent(ref: '#/components/schemas/HardwareCollection'))]
```

### 4. TypeScript/Dart SDK Generation
- Add CI step to generate SDK from OpenAPI spec:
  - **TypeScript**: `openapi-typescript-codegen` or `orval` for web admin (if needed)
  - **Dart**: `openapi-generator` with `dart-dio` template for Flutter app
- Publish Dart package to internal pub repository or include as git submodule

### 5. API Contract Testing
- Add Pest tests that validate API responses match OpenAPI schemas
- Contract testing in CI to catch breaking changes

## Acceptance Criteria

- [ ] API routes prefixed with `/api/v1/` (current routes work via alias or redirect)
- [ ] Swagger UI accessible at `/api/documentation` showing all v1 endpoints
- [ ] OpenAPI 3.1 spec available at `/api/openapi.json`
- [ ] All existing API endpoints documented with:
  - Request parameters (query, body, path)
  - Response schemas (success + error)
  - Authentication requirements (Sanctum Bearer token)
  - Organizational scope filtering behavior
- [ ] Dart SDK generated and committed to `flutter-app/lib/api/generated/` (or separate repo)
- [ ] CI pipeline runs SDK generation on API spec changes
- [ ] Contract tests pass in CI validating response schemas
- [ ] Version deprecation policy documented (e.g., 6-month notice, sunset headers)

## Alternatives Considered

| Approach | Pros | Cons |
|----------|------|------|
| Manual OpenAPI YAML | Full control | High maintenance, drift from code |
| `dedoc/scramble` | Zero config, reads code | Less customizable, newer |
| `darkaonline/l5-swagger` | Mature, annotation-based | Requires annotations |
| `knuckleswtf/scribe` | Great docs, less OpenAPI-focused | Not pure OpenAPI 3.1 |

**Recommendation**: `dedoc/scramble` for auto-generation (minimal annotations) + manual attrs for complex endpoints.
