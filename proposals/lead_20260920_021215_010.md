## Describe the bug

The app API-key revocation flow drops the backend result and always takes the success UI path.

`deleteApiKeyServer(appId, keyId)` returns `false` when the DELETE request is rejected or unavailable. But `AddAppProvider.deleteApiKey` currently does:

```dart
await deleteApiKeyServer(appId, keyId);
await loadApiKeys(appId);
```

and ignores that boolean. `ApiKeysWidget._deleteApiKey` then shows `apiKeyRevokedSuccessfully` as long as no exception was thrown.

So a non-200 / null-response delete can leave the key valid while the user is explicitly told it was revoked.

## Reproduce

1. Open an app you own and go to its API Keys section.
2. Make the revoke request fail (offline, null response, or a backend non-200 on `DELETE /v1/apps/{app_id}/keys/{key_id}`).
3. Revoke an API key.

### Current behavior

The provider ignores `false`, reloads the list, and the widget displays **“API key revoked successfully.”**

### Expected behavior

A rejected revoke must take the existing error-snackbar path. The UI must not claim a credential was revoked unless the backend accepted the mutation.

## Proposed fix

- make the provider consume the boolean returned by `deleteApiKeyServer`;
- fail the provider operation when the server returns `false`, so the widget's existing catch/error path is used;
- reload API keys only after a confirmed successful revoke;
- add regression coverage for both rejected and successful revocation.

I have a focused patch + provider regression tests prepared locally. `git diff --check` passes. I have **not** claimed Flutter test execution locally because the current environment does not have Flutter/Dart installed; CI should be the Flutter test authority once the PR is pushed.
