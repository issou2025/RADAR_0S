*Project description:*
Feature request: rule-based classification stored in the IFCX project

Summary
Please add a classification engine that assigns every component to a class based on rules, stored at project level in the IFCX file, so it applies to all models in a federation, including models added later.

Why
Main contractors receive IFC models from many parties (architect, structure, MEP), each with its own way of coding elements: NL-SfB in type names, in layer names, in property sets, in IfcClassificationReference, in Revit Assembly Code, or not at all. To coordinate, we need one consistent classification across all models, without asking every party to change their export and without editing their IFC files. Writing classes into each IFC separately breaks as soon as a new revision arrives.

Proposed behaviour
1. Classification definition (project level, stored in IFCX)
   - A named classification (e.g. "NL-SfB 2-digit") with a list of classes: code, name, optional colour.
   - Per class one or more rules. A rule matches on component type (IFC class) and on any number of columns: type name, name, layer, material, owning application, any property set / property, or an existing IfcClassificationReference.
   - Wildcard matching (* and ?), case-insensitive, optionally regular expressions.
   - Rule evaluation "first match wins" (ordered), with an option for "all matches" (multi-class).
   - A "not classified" bucket that stays visible, so gaps are easy to find.

2. Live application
   - Classes are evaluated on load for every model in the federation, also for models added or replaced later. Nothing is written into the source IFC files.
   - The class becomes a virtual property (e.g. "Classification.NL-SfB") usable everywhere a property can be used.

3. Use throughout the suite
   - Colour by classification, with the class colours from the definition.
   - Selection sets, isolate and hide per class or class group (e.g. "2*").
   - Information takeoff grouped by class.
   - Clash matrix based on classes: per pair of classes a tolerance, a severity (critical / moderate / low) and an auto-accept option (e.g. electrical boxes in walls).
   - Model checks and IDS results filterable per class.
   - BCF issues created from clashes carry the classes of both components in the title or labels.

4. Exchange
   - Import / export of a classification definition as a separate file (JSON), so firms can share one standard across projects.
   - A small example set based on NL-SfB (elementenmethode '91, 2-digit, with N/D split for walls, floors and roofs) would make adoption easy for Dutch users.

5. Transparency
   - Per component: show which class was assigned and which rule matched, to debug the rules.
   - Report: count per class per model, and list of unclassified components.

Benefit
One project-level classification turns a set of differently coded models into one consistent dataset, without changing the models, and makes clash matrices, takeoffs and checks reusable from project to project.
