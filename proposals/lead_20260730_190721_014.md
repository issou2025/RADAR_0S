# Project Proposal — Quantity Takeoff

## Project Understanding
You need assistance with: 
**ci(agents): report issues whose blockers have all closed, and status:ready issues with no binding marker**

*Project description:*
### What happened

The swarm can starve while the board looks healthy, and **nothing detects it**. Two
mechanically-detectable states silently make work unclaimable, and today they took the
claimable queue to **zero** while 52 issues were open.

An autonomous session on 2026-07-30 claimed #222, landed it (#318), and then had nothing
left to do. An adversarial audit of *why* — six independent auditors, each trying to refute
"nothing is claimable" — confirmed the queue really was empty and found the cause is not a
shortage of work. It is bookkeeping.

#### Mode A — `status:ready` with no binding approval marker

`claim.py` requires `status:ready` **and** a `tether-agent-ready` comment whose
`criteria_sha256` binds the issue's current title/body. The label alone is not admission.
Five issues carry the label and no marker, so every one of them answers a claim with exit 3:

```
$ claim.py claim --issue 314 --vendor claude
ineligible: #314 has no maintainer approval binding its current title and body;
            it may have been edited after approval
exit=3
```

Verified live for **#314, #311, #308, #300** (and #272, which the maintainer has separately
recorded as needing a re-scope first). The board shows five ready items; the queue has none.

Worse, that one message covers three different situations a worker cannot tell apart:
never approved · approved then edited so the hash no longer binds · approved with a
malformed marker. Only the second is "your fault for editing"; the first is just a missing
label-partner. A worker burns a session discovering which.

#### Mode B — every declared blocker has closed, but the label still says blocked

Seven issues sit at `status:blocked` or `status:backlog` while the dependency each one names
is already closed or merged. All seven verified by reading the issue's own Dependencies

### Why this is worth automating rather than remembering

- The failure is **silent and asymmetric**: an over-blocked issue costs nothing visible, so
  nothing ever prompts a re-check. It only surfaces when a worker goes looking for work and
  finds none — by which point a session has been spent.
- It is **exactly the reasoning #276 accepted for `agent:conflicted`**: *"a marker that is
  never removed is indistinguishable from one that is never checked."* A `status:blocked`
  label that nothing ever re-evaluates is the same defect on the other axis.
- Both modes are **decidable from the API alone**. No judgement is needed to notice that an
  issue's only named blocker is closed, or that a `status:ready` issue has no marker. What
  to *do* about it is a maintainer call; noticing is not.
- It compounds with #308 (a merged claim leaves `status:in-progress` and `agent:needs-amend`
  behind). That leaves *closed* issues looking live; this leaves *live* issues looking
  blocked. Together the board's status labels stop being trustworthy in both directions.

### Steps to reproduce

1. `gh issue list --label status:ready --json number` → 12 issues.
2. For each, count comments containing the literal `<!-- tether-agent-ready`. Five have zero.
3. `claim.py claim --issue 314 --vendor claude` → exit 3. Same for #311, #308, #300.
   *(Use the uv 3.12 interpreter; see #315 — the default python misreports every failure.)*
4. For each `status:blocked` / `status:backlog` issue, read its Dependencies section and
   query the named issues/PRs. Seven have none still open (table above).

### Expected behavior

A scheduled job reports both classes so they are noticed without a human sweeping 52 issues
by hand. Concretely, it should list:

- **Mode A** — issues labelled `status:ready` whose approval marker is absent, or present but
  no longer binding the current title/body. Distinguishing *absent* from *stale* is the
  valuable part, because the remedy differs: post a marker vs. re-approve after an edit.
- **Mode B** — issues labelled `status:blocked` / `status:backlog` for which every
  issue/PR referenced in their Dependencies section is closed or merged.

Deliberately **report, never act**. Promoting an issue to `status:ready` or posting an
approval marker are maintainer authority — `AGENTS.md` is explicit that eligibility is a
precondition of a claim and never a consequence of one, and an automation that granted
admission would defeat that gate exactly as an agent self-approving would. The output is a
worklist for a human, nothing more.

Open questions for whoever picks this up:

- **Where it runs.** `agent-reaper.yml` is already the scheduled job that cleans up after
  claims and already holds the issue-querying code, so it is the obvious host. A separate
  workflow is defensible if mixing "reclaim dead claims" with "report stale labels" muddies
  it.
- **How it reports.** A workflow-summary table is cheapest and has no failure mode. A sticky
  issue comment is more visible but writes to issues on a schedule. Do not make it *fail* —
  a red scheduled check that is usually red stops being read.
- **Parsing Dependencies is heuristic.** The section is prose and its wording varies
  ("Open dependency: #218", "Dependencies: none", "Blocked by the review-gate rewrite" with
  no number at all — #261 names no issue). Scan for `#\d+` references anywhere in the
  Dependencies block and report the ones where all found references are closed; when the
  block names no issue, report it as *unparseable* rather than as unblocked. A false
  "unblocked" here is worse than a miss.
