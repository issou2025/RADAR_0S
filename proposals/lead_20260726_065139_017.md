## Project Understanding
You need assistance with: 
**hd8: Shizuku self-start fails with EOFException on loopback ADB connect, even with wireless ADB manually restored**

*Project description:*
## Summary

After recovering wireless ADB on hd8 post-reboot (`adb tcpip 5555` over USB — the known workaround for `adb_wifi_enabled` non-persistence, see memory/project_fireos8_adb_wireless_debugging.md), Shizuku still cannot self-start. This is a distinct failure mode from the already-documented OS-level wireless-debugging persistence issue.

## Evidence (2026-07-25 session)

`AdbClient.kt`'s `read()` (`manager/src/main/java/moe/shizuku/manager/adb/AdbClient.kt:133`, first `inputStream.readFully()` right after writing `A_CNXN`) throws `java.io.EOFException` on every attempt to connect to its own loopback `127.0.0.1:5555`. Reproduced identically via:
- The `HEADLESS_START` broadcast
- The in-app "Start" button (interactive, user-confirmed)
- After a full `am force-stop` + relaunch (rules out stale app state)

**Key diagnostic:** the Mac's own *external* plain ADB client connects fine to the same `100.124.55.39:5555`, including brand-new connections after a `disconnect`/`connect` cycle — adbd itself is healthy and accepts plain (non-TLS) `A_CNXN` handshakes from outside. The failure is specific to the **loopback** connection attempt from an app process on-device — it gets zero bytes back before EOF. No matching SELinux denial found in logcat for this specific socket (only unrelated pre-existing `com.termux.api` USB-dir denials).

## Root cause — not confirmed, candidates

1. Fire OS may deliberately handle loopback connections to the ADB port differently than external ones (anti-privesc hardening — this loopback self-auth is exactly the trick Shizuku uses to avoid needing root).
2. A modern-wireless-debugging-vs-legacy-tcpip mode conflict: Shizuku's own `tryEnsureWirelessAdb()` sets `adb_wifi_enabled=1` (the Android 11+ TLS/mDNS system) on top of the manually-forced legacy `adb tcpip 5555` mode — these may not coexist cleanly on this adbd build.

Neither is confirmed. Would need on-device packet capture (no root available) or Shizuku-side protocol tracing to pin down.

## Also found in the same session, separate/minor

`ShizukuStateMachine` never resets from `STARTING` back to `STOPPED` after `AdbStarter.startDirect()`'s 3 retries all fail (`manager/src/main/java/moe/shizuku/manager/adb/AdbStarter.kt` — the failure path only logs a warning, never transitions state). This wedges all future start attempts with "Shizuku is already starting in the background" until an `am force-stop`. Worth a real fix but orthogonal to the EOFException above.
