*Project description:*
Bring Tournament Genie's architecture docs (`docs/architecture/README.md` and its ADRs) in line with
using [`@towerism/selfhost-kit`](https://github.com/Towerism/selfhost-kit), whose architecture and

(the launcher, secret bootstrap, entrypoint, Litestream, image and release CI, the token-vault pattern,

instead, so that a security fix reaches both apps (the adversarial review's Warning #5). Genie's docs
should say so.

From the kit's follow-up draft ([`follow-up-issues.md` #4](https://github.com/Towerism/selfhost-kit/blob/main/docs/architecture/follow-up-issues.md)
and kit ADR-0007 "Genie"), amend:

  `stringVault`), not "the same pattern as attendance's".
- §3 opening paragraph ("reuse what attendance proved") and §10: these pieces are shared through the kit,
  not carried over: the launcher, secret bootstrap, entrypoint, Litestream, image and release
  workflows, security middleware and redaction.
- ADR-0001 consequence "carry over almost as-is" → "shared through `@towerism/selfhost-kit`
  (selfhost-kit ADR-0001)".
- ADR-0009 decision list → the kit's Docker assets and reusable workflows.
- §9 vault row and §10 logs: the key is `NUXT_VAULT_KEY` / `secrets/vault.key` through the kit's
  `aes256Key`; redaction is the kit's base list plus `content`, `notes`, `botToken` and the secret env
  names.
- The `jobs` module stays in Genie (selfhost-kit ADR-0002), but is written so it can be extracted: plain
  TS, storage behind a port, an injected `Clock`. It moves into the kit when a second app needs it.

These are ADR amendments, so they need the owner's approval like any architecture change.

## Context

Genie's accepted architecture (`dbe1ba1`) plans to **copy** attendance's infrastructure:
- §3 says Genie will "reuse what attendance proved (secret bootstrap, launcher, Unraid template, CI, release flow)".
- The Crypto row says the vault is the "Same pattern as attendance's token vault".
- ADR-0001 says these pieces "carry over almost as-is".
- ADR-0009 decides on "reusing attendance's pieces".
- §10 says "Same launcher, secret bootstrap, entrypoint and CI/release flow as attendance".

An adversarial review of Genie's architecture found that copying would leave two versions of
security-sensitive code (the vault, the secret bootstrap, log redaction), so a fix in one would never
reach the other. The kit's ADR-0001 and architecture §1 record this as Warning #5. It is not the W5 in
Genie #1, which is about thread export.

`@towerism/selfhost-kit` was designed to fix that, and its decisions apply to Genie:

| Kit ADR | What it decides |
| ------- | --------------- |
| ADR-0001 | Share these pieces as one npm package |
| ADR-0002 | What is in the kit and what stays in each app. Genie's `jobs` module stays out, under an "extractable" rule |
| ADR-0004 | Share the Docker assets and the reusable image and release workflows |
| ADR-0005 | Semver and the Renovate security-fix path |
| ADR-0006 | The framework-free core, the `/nitro` adapters, module import rules and the `/data/secrets` contract |
| ADR-0007 | Genie starts on the kit from its first commit, pins an exact 0.x version and "never copies 'for now'". It also lists Genie's doc amendments as a follow-up. This spec is that follow-up |

The kit's study also showed that some of Genie's statements about attendance are wrong:
- §5.2 and ADR-0005 say Genie's jobs run on "rails" like attendance's submission jobs. Kit ADR-0002 found attendance has no general runner: its lease is about 40 lines inside its submission service, it marks interrupted work instead of retrying it, and it has no persisted timer.
- §9 says "Renovate … (as attendance)", but attendance has no Renovate config (kit architecture §1.1, finding 5).

**This is a documentation-only change.** Genie has no code yet. The docs are the source of truth for M1,
so they must say "import the kit" before M1 is specced, or M1 will be specced as a copy.

**Scope beyond the issue's list.** The issue names §3, §9, §10, ADR-0001 and ADR-0009, the vault and
redaction, and the jobs rule. This spec also covers:
- the other passages that say the same thing (§6.1, ADR-0002, ADR-0004, ADR-0005, the §3 diagram and layout);
- the places a reader would otherwise get wrong: §11 test rows, §12 risks and §14 M1.

Each is listed so the owner can strike any of them.

**Process.**
1. Nothing is implemented, and no branch is opened, until the owner explicitly approves this spec. The `approved` label on #3 records that approval.
2. The PR then adds ADR-0011 as **Proposed**. Approving this spec is **not** accepting ADR-0011.
3. A separate commit flips ADR-0011 to Accepted only after the owner explicitly approves the PR's content.

## Edge Cases

- EC-1: The kit's exact API changes in its K1 or K2 specs after these docs merge. Genie's docs name functions only and point to kit §5 for signatures. Only a rename or removal makes them stale. M1's spec re-runs check 3 against the kit's then-current docs.
- EC-2: M1 is ready before the kit publishes. The docs say M1's skeleton waits, or Genie contributes the piece to the kit. The work that doesn't wait for the kit (FR-20) goes first.
- EC-3: Genie needs something the kit leaves to apps, such as `/healthz`, the Dockerfile, per-route CSP or the Unraid template. ADR-0011's "stays in Genie" list names it (FR-1). The transcript CSP is applied on top of the kit's global headers, and the global headers survive on that route (FR-19).
- EC-4: A kit link breaks (a moved file or a renamed anchor). Check 5 resolves each link at both refs and fails before merge.
- EC-5: The kit's docs change before this PR merges. The checks read a pinned `1f3c4fa` snapshot. If the kit's `main` moved, checks 2, 3 and 5 are re-run against it, and any difference is noted in the PR.
- EC-6: Drifting to attendance's file names (`token-vault.key`, `NUXT_TOKEN_VAULT_KEY`). Check 2 rejects any vault key other than Genie's.
- EC-7: A reader opens an amended ADR without reading ADR-0011. The amendment line links ADR-0011, and each changed sentence stands on its own.
- EC-8: Wording wrapped across lines ("carried" at a line's end, "over" on the next) would slip past a line-based grep. Check 1 joins each paragraph onto one line before matching.

## Data Models

No database tables change in this spec. M1 defines the table holding sealed values. The data at rest the
docs commit to is the kit's `/data` contract, which is also check 2's fixture:

| Path / variable | Type | Constraints | Owner |
| --------------- | ---- | ----------- | ----- |
| `secrets/` | directory | `dirname(NUXT_DATABASE_PATH)/secrets`, i.e. `/data/secrets/`; mode 0700; never replicated by Litestream | kit |
| `session-password` | file in `secrets/` | generated once (`O_EXCL`), 0600; `NUXT_SESSION_PASSWORD` wins | kit (`sessionPassword()`) |
| `vault.key` | file in `secrets/` | 32 bytes, base64; generated once, 0600; `NUXT_VAULT_KEY` wins; malformed → startup fails, never regenerated | declared by Genie, handled by the kit (`aes256Key`) |

## Test Plan

Planned with `senior-qa`'s references (`testing_strategies.md`, `qa_best_practices.md`,
`test_automation_patterns.md`), applied to a docs-only change.

**Pyramid placement.** There is no executable code, so there are no unit, integration or E2E tests. The
lowest, cheapest layer is a **static check**: a deterministic script over the Markdown. Each AC sits at
the lowest layer that can prove it:
- scripted checks only: AC-2, AC-4, AC-9 and AC-10;
- scripted checks plus a review: AC-1, AC-3, AC-5, AC-6 and AC-7;
- review only: AC-8.

No E2E applies, because there are no code paths ("when NOT to test").

**Coverage set by risk** (instead of line coverage):
- **Highest:** the install-contract values (NFR-2). They ship in M1's first image and can never change, so check 2 asserts pairings against a structured fixture, for 100% of the mentions in the changed files.
- **Medium:** leftover copy language (check 1) and non-existent or missing kit names (check 3). Either would steer M1's spec toward copying.

**Checks.** They run against the PR branch. The scripts are posted, collapsed, in the PR description, so
