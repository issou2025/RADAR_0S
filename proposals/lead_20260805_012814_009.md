## Project Understanding
You need assistance with: 
**Checkout: app still shows Free after a successful Stripe payment, and repeat checkouts created two separate Stripe customers**

*Project description:*
## Symptom

On the `validation` environment, after paying for Tier 1 with a Stripe test card and being redirected back to Settings:

1. The app still shows the account on the **Free** plan (this is *after* #192's fix, which retries `/api/billing/me` on `?checkout=success` specifically to ride out a webhook race — so this isn't just the race the retry was built for; something is stopping the plan from ever flipping).
2. Checking out a second time created a **second, separate Stripe customer** for what should be the same account — both show an Active Tier 1 subscription, in the same sandbox, same billing email, different `Customer ID`s (`cus_V0qWuBnUZKiYhA` created "Aug 4" ~8:21 PM, `cus_V0rZSHpNMmlzaS` created ~9:25 PM).

## What the code says should happen

- `api/billing.py`'s `create_checkout()` reads the account's existing `Subscription.provider_customer_id` and, right after creating the Checkout Session (synchronously, *before* payment even completes), persists whatever customer id Stripe returned — specifically so a second checkout reuses the same customer (`api/billing.py` ~L228-236, comment: "the user may abandon checkout, and next time we want to reuse the same provider customer rather than create a second").
- `already_subscribed` (`subscription_is_live(row.status)`) is supposed to hard-block a second checkout once the first one is live — that block only lifts if `row.status` was never updated to `active`/`trialing`/`past_due`.
- The plan only ever changes in the DB via the `/api/billing/webhook` handler (`api/billing.py` `webhook()` → `src/billing/subscriptions.apply_update()`), driven entirely by Stripe's webhook deliveries.

Given that, two independent Stripe customers for one checkout flow — plus the plan never updating — both point at the same underlying cause: **the local `Subscription` row for this account isn't holding the state the code expects it to.** Ranked by likelihood, from reading the code (not confirmed against the live environment):

1. **The webhook never reached the app**, or isn't correctly configured on `validation` — `docs/BILLING.md`'s setup section requires a webhook endpoint registered in the Stripe dashboard (`.../api/billing/webhook`) with a matching `STRIPE_WEBHOOK_SECRET`, subscribed to `checkout.session.completed` / `customer.subscription.*`. If that's missing or misconfigured for this environment, `Subscription.status` never leaves whatever it started as, so the plan stays Free and `already_subscribed` never blocks a repeat checkout. This alone explains symptom (1); it doesn't fully explain (2), since `provider_customer_id` gets written independently of the webhook (see above) — *unless* the row it was written to isn't the row being read back later.
2. **Two different `UserInfo` accounts share this email** (e.g. a local-password account and a Google-OAuth account both using `rui.jf.narciso@gmail.com`, or an old test account). Each has its own `Subscription` row and its own empty `provider_customer_id` until first checkout, so checking out once per account would legitimately mint two Stripe customers — and if the one currently signed into Settings isn't the one that has a subscription applied, it would show Free even with the other paid. Worth checking `SELECT * FROM userinfo WHERE email = 'rui.jf.narciso@gmail.com'` (or the admin dashboard's user search from #194) for duplicates.
3. **The `validation` environment's `db` volume didn't persist** across one of the several redeploys of the `:validation` image during this session's testing (see docker-compose.yml.example's `./db:/app/db` mount) — if the Subscription row was lost between the two checkout attempts, the second would read `provider_customer_id` as empty again and create a new customer, same as first-ever checkout.

## Ask

Investigate against the actual `validation` deployment (not something I can check from here):
- Is the Stripe webhook endpoint actually configured and receiving deliveries for this sandbox account (check Stripe dashboard → Developers → Webhooks → delivery attempts/logs)?
- Does `SELECT * FROM userinfo WHERE email = '<the test email>'` return more than one row?
- Did the `./db` volume actually persist across the validation redeploys during this testing session?

Depending on what's found, this may turn out to be pure environment/config (no code change needed) — but if the webhook *was* delivered and applied to the *correct* single account and the app still shows Free / still created a duplicate customer, that's a real bug in `create_checkout`/`apply_update`/`resolve_row` worth chasing further, and this issue should be updated with those findings before anyone starts coding a fix.
