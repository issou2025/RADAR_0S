# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Ed25519 availability across platforms, a Linux key-import bug, and pluggable key algorithms for agent ids**

*Project description:*
Agent ids are bare Ed25519 keys. This issue records where Ed25519 is and isn't available across the platforms Atomic runs on, one bug that probably affects Linux users today, and a proposal to make the key algorithm pluggable. It came out of ontola/atomic-plugins#54, where plugin iframes are to generate a short-lived Ed25519 key with WebCrypto.

## 1. Ed25519 in WebCrypto, per platform

MDN's browser-compat-data lists `generateKey`/`sign`/`importKey` with Ed25519 as shipped in **Chrome/Edge 137, Firefox 129 and Safari 17**; mobile and webview builds follow their desktop engines.

| Platform (Tauri engine) | Ed25519 | Notes |
|---|---|---|
| macOS (system WebKit) | ✅ Safari 17+ | **Tested on macOS 26.6 / WebKit 21624** in `WKWebView`, inside a sandboxed null-origin iframe: Ed25519 generates and signs, P-256 works, `localStorage` throws `SecurityError` (as expected). On older macOS, installing a newer Safari also updates the system WebKit that apps embed. |
| iOS (system WebKit) | ⚠️ iOS 17+ | The app's `IPHONEOS_DEPLOYMENT_TARGET` is **14.0**, so iOS 14–16 lack it. |
| Android (System WebView) | ⚠️ WebView 137+ | The app's `minSdk` is **24** (Android 7). Chrome/WebView updates for Android 7 stopped in late 2023, well before 137. Android 8/9 get up to 138, which is enough. |
| Windows (WebView2) | ✅ | Chromium, updates itself. |
| Linux (WebKitGTK, libgcrypt) | ⚠️ present, buggy | See section 2. I didn't find which WebKitGTK version added Ed25519, so older LTS distributions may lack it. |

Also tested in Chromium 152, in a `srcdoc` iframe with `sandbox="allow-scripts allow-modals"` (what `AppFrame` uses): `isSecureContext` true, Ed25519 works, storage throws. A real frame loaded by URL, and Firefox, were not tested.

**Suggestion:** raise the minimums to iOS 17 and Android 8 (`minSdk 26`), or give frames on older engines a fallback.

## 2. Bug: some users' keys can't be imported on Linux (WebKitGTK)

WebKit PR https://github.com/WebKit/WebKit/pull/72772 (in review as of 2026-09-23) describes a libgcrypt-backend bug. When a key component starts with a zero byte, WebKit extracts 31 bytes instead of 32. As a result:
- about **0.8%** of Ed25519 `generateKey` calls fail;
- **1 in 256** valid keys fail `importSpki`/`importPkcs8`.

`browser/lib/src/CryptoProvider.ts` imports the user's private key with `importKey('pkcs8', …)`. So on the **Linux Tauri app** (and GNOME Web), roughly 1 in 256 users probably can't load their key. This is inferred from the PR and the code; not reproduced.

Possible workarounds until the WebKit fix ships:
- import through JWK instead of PKCS#8, if that path avoids the bug (not checked);
- fall back to signing with the Rust/WASM implementation when the import fails;
- retry key generation on failure.

## 3. Hardware key stores mostly can't do Ed25519

Software Ed25519 is fine everywhere that matters for embedded agents: `ed25519-dalek` (no operating system needed), libsodium (an ESP-IDF component), Monocypher, wolfSSL. The exception is **Mbed TLS**, the default in many embedded SDKs: it has no Edwards curves, and EdDSA is only on its roadmap.

But keys held in hardware are mostly **P-256**:

| Key store | Ed25519? |
|---|---|
| Apple Secure Enclave | P-256 only among classical curves; ML-DSA exists for post-quantum |
| Android Keystore | Ed25519 since Android 13 (KeyMint v2); StrongBox chips typically P-256 |
| Microchip ATECC608 | P-256 only |
| NXP SE050 | ✅ Ed25519 |
| TPM 2.0 | I couldn't confirm EdDSA in the spec; TPMs in the field typically offer NIST P-256/P-384 |

So a phone, laptop or IoT device that wants its agent key locked in hardware usually can't be an `atomic:agent` today.

## 4. Proposal: pluggable key algorithms in agent ids

Today, `atomic:agent:<key>` is a bare 32-byte Ed25519 public key, `lib/src/agents.rs` uses `ed25519_dalek` throughout, and neither the id nor the `x-atomic-*` headers name an algorithm.

**Proposal:**
- **The bare form stays Ed25519, forever,** so every existing id stays valid.
- **New algorithms get an explicit segment:** `atomic:agent:<alg>:<key>`, for example `atomic:agent:p256:<33-byte compressed key>` for hardware-backed keys.
- **Post-quantum keys are too large for an id.** An ML-DSA-44 public key is 1,312 bytes. Use a hash in the id: `atomic:agent:mldsa44-sha256:<hash>`. The key travels in `x-atomic-public-key` (or in the commit), and the verifier checks it against the hash. Still self-certifying, no lookup.
- **Signature formats don't change.** The signed message stays the same; the verifier picks the algorithm from the id. Everything that references agents inherits the new algorithms: ACLs, commit signers, the proxy's connections, delegations and capabilities.
- **Alternative:** a multicodec/multikey prefix, as `did:key` uses. More interoperable, but less readable and harder to tell apart from existing bare ids.

**What's needed now:** agree the id format and route all id parsing through one function, in `atomic_lib`, `@tomic/lib` and Flutter. P-256 itself can be implemented when someone needs hardware-backed keys.
