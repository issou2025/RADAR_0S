## Goal

Episode state has accumulated enough special-case behavior that the same episode can mean different things depending on whether the app just refreshed, relaunched, advanced a queue, finished playback, or passed through automation.

Before implementing fixes, **produce a concrete design/implementation plan for the state model and transition ownership. Do not begin implementation until that plan has been written and reviewed against the findings below.** The intent is to avoid adding another round of local patches to `WiltedMacModel`.

The plan should explicitly identify:

1. Which durable record is authoritative for each dimension of episode state.
2. Which transitions must be atomic.
3. Which state may be ephemeral/in-memory only.
4. How state is reconstructed after relaunch.
5. How failed/interrupted work is represented and recovered.
6. How "finished listening", "hidden/retired from Larder", "dismissed from feed re-admission", and "delete local media" differ.
7. What existing tests will change and what new integration tests are required.
8. A migration/backward-compatibility strategy for existing local stores.

Prefer separate orthogonal state dimensions over a single giant lifecycle enum. The problem is not that download, preparation, playback, and visibility are separate concepts; the problem is that ownership and transitions between them are inconsistent.

## Review findings

### P0/P1: automation can report a failed download as successful

`WiltedAutomationCoordinator.drain()` treats `operations.startDownload()` returning normally as a successful download and increments its completed count. It also expects thrown failures to reach its retry/recovery logic.

The real adapter in `WiltedMacModel.startClaimedDownload()` starts `downloadEpisode()` and waits for its task, but `downloadEpisode()` catches transfer failures internally, updates UI/store state to failed, and returns normally. That means automation can:

- count a failed transfer as downloaded;
- skip its bounded retry behavior;
- report an inaccurate final automation result.

Recovery is also inconsistent: the downloader persists `.failed`/`.cancelled`, while `unfinishedPodcastDownloads()` only returns `.queued` and `.downloading`, despite coordinator comments saying failed work can be resumed later.

**Required direction:** the underlying download operation needs a real result contract, ideally an `async throws` operation used by both manual UI and automation. UI presentation must not consume errors needed by orchestration.

Decide explicitly whether an automatic download failure is retryable immediately, retained for relaunch reconciliation, or terminal until user action.

### P0/P1: successful preparation is reconstructed from a journal that is written best-effort

`WiltedMacModel.preparationState(...)` only considers an episode prepared when there is a successful terminal preparation journal entry whose revision matches the current ready revision. This is a reasonable requirement if the journal is authoritative proof of preparation.

But `PodcastPreparationPipeline.prepare()` commits the prepared artifacts first and writes the terminal journal separately. `journalTerminal()` saves with `try?`, so failure of that authoritative write is silently ignored. After the pipeline returns, `WiltedMacModel` explicitly overwrites the row in memory with `.prepared(summary:)`.

This creates a split-brain state:

1. prepared audio/transcript can be committed;
2. terminal proof can fail to persist or the process can exit between those operations;
3. the current process may still show Prepared;
4. a later refresh/relaunch reconstructs state from durable records and may no longer consider it prepared.

**Core contradiction:** the journal is authoritative when reading status but best-effort when writing status.

**Required direction:** successful preparation must have a durable, transactional outcome record tied to the produced revision. Progress/event logging may remain best-effort, but the success record that controls readiness cannot.

Conceptually the store needs durable evidence equivalent to:

> episode X has successful prepared artifact revision Y, produced under processing policy Z / pipeline version V

Do not rely on a post-reload in-memory `.prepared` override to compensate for missing durable state.

### P1: natural completion has different persistence semantics depending on queue position

If another episode is already queued, `PlaybackController.handleBackendCompletion()` writes completion and advances to the next queued episode. The model reloads rows but does not dismiss the finished episode.

If the finished episode has nothing queued behind it, `WiltedMacModel.handlePodcastPlaybackFinished()` writes/observes completion and then calls the dismissal/removal path.

`dismissPodcastEpisode()` is destructive state cleanup, not merely a visibility toggle. It removes the episode record plus queue, download, speed, artwork, revision, transcript, and playback records, while retaining a dismissal marker and preparation history. Media bytes are intentionally left on disk.

Thus the persistence result of "I listened to this episode to the end" changes according to queue layout.

Restoring a dismissed prepared episode intentionally returns it as not downloaded and not prepared, so dismissal is not an undoable visibility operation either.

**Required direction:** separate these concepts and define them independently:

- finished listening / played history;
- active Larder visibility or retirement;
- dismissal that prevents feed refresh from re-admitting the episode;
- local media deletion/reclamation.

Automatic retirement after completion is fine if desired, but it must be consistent and must not erase durable listening history as a side effect.

### P1: the library can present an episode as prepared/ready even when its audio file is gone

`loadLibrary()` maps persisted download `.completed` to `.completed` presentation state and derives preparation from revision/journal records. `readyRevision()` returns stored revision metadata and a URL but does not establish that the media file currently exists.

The playback controller checks the file later and throws `podcastMediaUnavailable`, so playback itself has a guard, but the library can still present a stale ready state and enable playback until the user discovers the missing file.

The failure path also does not clearly repair the durable availability state.

**Required direction:** distinguish historical preparation success from current local-media availability. A useful state/presentation is:

> Prepared · Local audio missing — Download again

Do not erase valid preparation history merely because local bytes disappeared.

Reconcile file existence at appropriate boundaries (startup/reconciliation, relevant store snapshot construction, and after a playback-open failure), without introducing full-file hashing on every render.

### P1/P2: pipeline fingerprint changes can revoke otherwise usable prepared state too broadly

The preparation fingerprint incorporates source hashes and the contents of Python files from Wilted/speech-stack, not just the explicit semantic version. Startup then calls `invalidateStalePodcastPreparations()` when the fingerprint differs.

That invalidation clears prior preparation journals and can schedule reset/forced-redownload recovery. Because a successful ad-removal run can replace the original downloaded source with the prepared artifact and delete the old source file, a fingerprint change can turn a previously successful prepared episode into work requiring a fresh download.

This means "implementation changed" can effectively become "existing artifact is no longer prepared," even when the old artifact is still perfectly playable and there is no known correctness defect in it.

**Required direction:** distinguish:

- prepared successfully with an older pipeline;
- eligible/recommended for reprocessing;
- invalid/unsafe artifact that must no longer be used.

Existing successful artifacts should remain playable unless a specific compatibility/correctness rule says otherwise. Use explicit invalidation for known-bad pipeline versions rather than treating every fingerprint difference as loss of readiness.

### P2: state reconstruction performs repeated broad reads and decoding

`loadLibrary()` reconstructs each episode by separately looking up ready revision, playback, transcript, and preparation state. Several store methods fetch broad tables and then filter in Swift. Library reconstruction also calls `preparationRuns(limit: Int.max)`, and `preparationRuns()` fetches/decodes journal records before grouping them.

Multiple lifecycle events then reload the entire library. The code already contains comments acknowledging repeated reloads around download completion.

This is both a scaling concern and an architectural smell: the UI model is assembling a state snapshot itself from many independent store reads.

**Required direction:** design a store/service-level episode library snapshot that performs scoped/batched reads once, indexes by episode/revision, and returns a coherent projection. Detailed preparation history should be loaded on demand for Prep/debugging rather than decoded to decide every Larder badge.

## Architectural concern

`WiltedMacModel` currently compensates for gaps between durable and current-process state in several places:

- preserves in-memory preparation state when a store reload would regress a queued/running row;
- persists off-peak jobs separately in preferences;
- explicitly reapplies `.prepared(summary:)` after a durable reload;
- contains special-case playback-finished retirement behavior;
- coordinates download claims, preparation admission, and presentation messages.

Each workaround addresses a real symptom, but together they mean the answer to "what state is this episode in?" lives across store records, journals, task dictionaries, user defaults, and UI overrides.

The planning phase should consider extracting clear responsibilities such as:

- a download operation/service with typed results;
- a durable preparation-job/outcome service;
- an episode lifecycle/retirement service;
- a store-provided coherent library snapshot;
- a thinner `WiltedMacModel` that issues commands and renders resulting state.

Do not do a broad rewrite just for aesthetic reasons. Preserve useful existing mechanisms such as revision matching, playback generation guards, bounded automation retries, and transactional store operations where they already work.

## Required integration/regression tests

The implementation plan must include end-to-end or assembled-component tests for at least these cases:

- [ ] A download fails through the real `WiltedMacModel` -> automation adapter. It is not counted as downloaded and the intended retry/recovery policy actually occurs.
- [ ] A preparation reaches artifact commit but the process exits/fails before its terminal status write. Relaunch reconstructs one coherent, recoverable state; it must not silently oscillate between Prepared and Not Prepared.
- [ ] An episode naturally finishes with another queued item versus with nothing queued. Listening history and retirement semantics are consistent by design.
- [ ] A prepared episode's local media file disappears. The Larder reports unavailable local media, disables/recovers playback appropriately, and retains valid preparation/listening history.
- [ ] A pipeline implementation/fingerprint change occurs without a known artifact incompatibility. Existing prepared audio remains valid/playable while reprocessing eligibility is represented separately.
- [ ] Refresh/relaunch while preparation is queued, running, cancelled, failed, or completed reconstructs the expected durable state.
- [ ] Restore/dismiss semantics are explicitly tested independently from played/completed semantics.
- [ ] Existing-store migration tests cover any new durable state records/fields.

## Definition of done

- Episode state after relaunch is derived from durable records without needing UI-only overrides to manufacture success.
- Automation receives the real success/failure result of a download.
- Historical preparation success, current artifact availability, listening completion, and Larder visibility are distinct concepts.
- Natural playback completion has deterministic semantics independent of whether a successor happened to be queued.
- Existing prepared artifacts are not invalidated solely because implementation source changed unless an explicit invalidation rule requires it.
- The Larder cannot advertise an episode as playable when its local media is missing.
- Status reconstruction is batched/scoped enough that library size does not multiply full-table reads per episode.
- Integration tests cover the real component wiring, not only mocked coordinator behavior.
