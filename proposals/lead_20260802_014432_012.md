**Authors:**

## **Summary**

Agentic-security repositories are targeted by an abuse pattern that code review
does not catch: not malicious code, but **social engineering of trust**.
Someone opens a plausible issue or a small, correct PR whose real purpose is to
attach their own product to the credibility of the project, then cites that
association elsewhere. Every individual item looks reasonable. The pattern is
only visible in the author's cross-repository behaviour.

WS4 is a high-value target for exactly this. "Referenced in a CoSAI
workstream" is worth manufacturing.

This RFC proposes documenting a **reporting** control for it, as a WS4 Runbook:
when a pull request or an issue is opened, publish a small number of factual,
publicly-observable signals about the author's GitHub account, so a maintainer
can decide how much scrutiny the item deserves. The control never blocks,
closes, or auto-rejects anything, and it forms no opinion about the person. It
counts public behaviour against published thresholds. A human decides.

This is not a design proposal. It is running in production today on
[microsoft/agent-governance-toolkit](https://github.com/microsoft/agent-governance-toolkit)
(MIT) and on eight repositories in the
[agentrust-io](https://github.com/agentrust-io) organisation. The detection
scripts are open source. This RFC offers the pattern, the thresholds, the
failure modes, and the reasons for some deliberately unpopular design choices.

A companion PR adds the workflow to this repository, so WS4 can see it fire on
its own next issue rather than take my word for the description:
**PR: #157**

## What actually happens, concretely

### Trigger

`pull_request_target: [opened]` and `issues: [opened]`. Once, when the item is
opened. Maintainers (resolved from GitHub RBAC, Maintain or Admin, not from a
hardcoded roster of handles) and known bots are skipped. There is also a manual
`workflow_dispatch` against any username, which is how you investigate an
account without waiting for them to open something.

### What is measured

Twelve signals over four groups, every one of them a count or a ratio over the
public GitHub API. No private data, no third-party data broker, no model
inference about the person.

**Account shape**

| Signal | Fires at |
|---|---|
| `repo_velocity` | >0.2 repos/day with 10+ repos (MEDIUM); >0.5/day with 15+ (HIGH) |
| `new_account_burst` | <90 days old with 20+ repos (HIGH); <180 days with 30+ (MEDIUM) |
| `following_farming` | following:follower >5:1 with 100+ following (MEDIUM); >20:1 (HIGH) |
| `zero_followers` | 0 followers with 5+ public repos (MEDIUM) |

**Repository patterns**

| Signal | Fires at |
|---|---|
| `governance_theme_concentration` | >50% of repos governance/security themed, 5+ repos (MEDIUM) |
| `recent_repo_burst` | 15+ repos created in 90 days (HIGH) |
| `awesome_fork_burst` | 3+ awesome-list forks inside 72 hours (HIGH) |
| `fork_burst` | 5+ forks inside 72 hours (MEDIUM) |
| `batch_repo_naming` | 3+ same-suffix repos inside 48 hours, all <10 stars (MEDIUM/HIGH) |
| `feature_overlap` | a young repo matching 3+ (MEDIUM) or 4+ (HIGH) of 6 defined capability buckets |

**Issue spray**

| Signal | Fires at |
|---|---|
| `cross_repo_spray` | issues in 5+ distinct repos inside 7 days (HIGH) |
| `cross_repo_spread` | issues across 8+ distinct repos total (MEDIUM) |
| `self_promotion_spray` | 3+ issues promoting own repos across 2+ orgs (MEDIUM); 5+ across 3+ orgs (HIGH) |
| `credential_citation` / `credential_laundering` | citing this repo's merges in issues in 1+ other repos (MEDIUM); 3+ (HIGH) |

**Credibility**

| Signal | Fires at |
|---|---|
| `thin_credibility` | a repo <60 days old with <5 stars promoted into 1 org (MEDIUM); 2+ orgs (HIGH) |
| `coordinated_promotion` | 3+ thin repos promoted to overlapping org sets, Jaccard >=0.6 on 50%+ of pairs (HIGH) |

Aggregation: two or more HIGH gives HIGH. One HIGH, or three or more MEDIUM,
gives MEDIUM. Otherwise LOW.

`awesome_fork_burst` is the one worth calling out. Credibility-farming accounts
fork curated "awesome" lists to pad a profile with plausible-looking
repositories. Legitimate developers rarely fork several curated lists in
72 hours. Forks that have an outgoing PR to their parent are excluded, because
those are real contributions.

`self_promotion_spray` is the signal that does the actual separating. A
specification contributor filing tracking issues across 15 repositories trips
`cross_repo_spray` and looks identical to a spammer on volume alone. The
difference is whether the issues reference the author's own repositories.

### What gets published, and to whom

This is the part I want WS4 to push on, because it is a deliberate choice that
costs us something.

**Public, on the item, at MEDIUM or above:** one comment containing risk levels
only, a three-row table, plus a `needs-review:MEDIUM` / `:HIGH` / `:UNKNOWN`
label. The comment is idempotent, so a re-run edits it instead of stacking.

**Published nowhere:** the per-signal detail. The report underneath names which
signals fired and with what numbers. That detail is not posted as a comment,
not written to the job summary, and not uploaded as an artifact. The job
discards it.

Publishing a scored dossier about a named person, under a standards-body
banner, on the repository they just opened their first issue on, is a worse
outcome than the spam it defends against. False positives are real. A public
accusation is not reversible.

**How a maintainer gets the detail:** they run the same MIT-licensed tool
themselves against the same handle. It reads only public API data, so anyone
can reproduce or contest any result.

```bash
python scripts/contributor_check.py \
  --username <handle> \
  --repo cosai-oasis/ws4-secure-design-agentic-systems
```

One correction to a claim it would be easy to make and that I want on the
record instead: on a **public** repository there is no maintainer-only channel
inside GitHub Actions. Run logs, job summaries, and artifacts are readable by
anyone. "Only maintainers see the detail" cannot be implemented with Actions on
a public repo. What is actually true is narrower and worth stating plainly: the
detail is published to nobody, and is reproducible on demand by anybody with a
token, maintainers included. If WS4 wants genuinely maintainer-restricted
output, that needs a channel outside Actions, and I do not have a good answer
for it yet.

### The line this control does not cross

The tool does not decide. It does not close, block, or mark anything as spam.
It does not judge the contribution: a HIGH-risk author can be right and a
LOW-risk author can be wrong, and the risk level says nothing about whether the
issue or PR is any good. It does not use a model to form an opinion about a
person. Every signal is a documented count against a documented threshold, and
the code is readable.

That distinction is the whole point of proposing it here. An automated system
that produced a judgment about a contributor's intent, at a standards body,
would be indefensible. One that surfaces "this account created 41 repositories
in 90 days and has promoted 8 of them into other organisations" is just showing
the maintainer public facts they could have looked up, at the moment they need
them.

There is a maintainer allowlist upstream. By design it can only soften a HIGH
auto-flag to MEDIUM. It cannot mark anyone LOW, it does not bypass code review,
and it does not apply at all when a deliberate-abuse signal is present, so a
listed account cannot be whitewashed.

## **Drawbacks**

**It scores people, and WS4 would be doing it under the CoSAI name.** Even
"MEDIUM" attached to a first-time contributor's issue is a cost paid by that
contributor. Some of them will be new developers with thin profiles and nothing
wrong with them. `zero_followers` and `new_account_burst` fire on a genuine
newcomer.

**False positives have a known shape.** Specification and protocol
contributors trip the cross-repository signals as a normal part of their work.
Volume signals are dampened for accounts with established organic credibility,
and the deliberate-abuse signals block that dampening, but it still gets people
wrong.

**`pull_request_target` is a sharp tool.** It runs with a write-capable token.
Anything it checks out must be pinned to an immutable SHA and no untrusted PR
code may run before it in the same workflow. The proposed workflow pins by SHA.
This is a real footgun for anyone copying the pattern carelessly, and the
Runbook should say so loudly.

**It is a point-in-time check** that runs once at open and never re-evaluates.

**It adds a dependency** on an external repository's action, pinned by SHA,
which someone then has to bump deliberately.

## **Alternatives**

**Do nothing and rely on review.** This is the status quo, and it works for
code. It does not work for this pattern, because each item is individually
reasonable. The cost of doing nothing is that a workstream's name becomes a
citation in someone's marketing.

**Manual investigation only.** Ship the CLI in a Runbook, no automation. Fully
avoids the public-labelling cost. Depends on a maintainer thinking to look,
which in practice means it happens after the problem, not before.

**Block or auto-close at HIGH.** Rejected. The false-positive rate does not
support enforcement, and an automated system that turns away contributors at a
standards body is the wrong shape regardless of accuracy.

**Publish the full signal detail publicly.** Rejected, for the reasons above.
Worth revisiting only if WS4 concludes that transparency about *why* an account
was flagged outweighs the harm of a public dossier. I can see that argument and
do not agree with it.

## **Unresolved questions**

**1. Does WS4 want to run this, or only document it?** Running it means CoSAI
publishes risk labels on contributors' issues. That is a governance decision
for the chairs, not a technical one. The Runbook is useful either way.

**2. Comments are not covered, and I want help deciding whether they should
be.** Today the check fires on PR-open and issue-open only. Someone who never
opens anything and only comments is never screened, and comment-only product
placement is a real pattern.

I checked whether this is technically possible. It is, with caveats:

* `issue_comment` fires on comments on both issues and PRs, from the default
  branch, in the base repository, which is the right execution context.
* **Token scope needs empirical confirmation.** Whether the token is
  write-capable for comments on pull requests from forks has to be tested
  before relying on it to post or label. I have not run that test.
* **Rate limit is the hard constraint.** One profile check costs tens of API
  calls, several against the Search API, which is capped at
  [30 requests per minute](https://docs.github.com/en/rest/search/search)
  authenticated. `GITHUB_TOKEN` is capped at
  [1,000 requests per hour per repository](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
  Checking every comment would exhaust that on one busy thread.
* **Noise makes the naive version unusable.** A risk comment in reply to every
  comment is worse than no control.

The shape that seems workable is first-time-commenter-only, result cached per
account for some window, writing a label rather than a new comment. I have not
built it. If WS4 thinks comment coverage matters, I will, and I would rather
design it with input than guess.

**3. Are the thresholds right for a standards-body repo?** They were tuned on
AI-governance project repos, where the base rate of product placement is high.
A workstream repository has different traffic. `governance_theme_concentration`
in particular is close to useless here, since almost everyone legitimately
participating in WS4 has governance-themed repositories.

**4. Is there a maintainer-only output channel worth building?** See above: not
achievable inside Actions on a public repo. If someone knows a clean pattern, I
would like to hear it.
