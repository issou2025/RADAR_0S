# 1. Three constraint levels

## A. HARD — must not be violated
These are product-level requirements, not suggestions:

- Final Android result must visually follow the Issue #4 Final Baseline as a whole.
- Platform: Android 16, Kotlin + Jetpack Compose as the primary UI stack.
- Target motion path: 120Hz; do not hard-code 60Hz timing or intentionally fall back to a 60Hz animation path.
- No crash on major interactions.
- No default Material ripple / white pressed flash.
- Dock must not cover readable page content.
- Dock must remain a floating glass navigation system with a distinct moving selected state; do not replace it with standard Material BottomNavigation / icon tint only.
- Glass must visibly interact with the backdrop; a plain opaque/white/translucent capsule is not acceptable.
- If a local fix makes the result farther from the Final Baseline, reject that fix.

Only these HARD items are blockers by themselves.

## B. TUNABLE — starting values, not prison bars
The detailed sizes, alpha values, blur radii, displacement, magnification, highlight strength, spring timing, etc. in `final_design_spec.yaml` are **initial production values**.

They may be adjusted when necessary to match the Final Baseline on the real device.

Rules for tuning:
- keep the same visual role and hierarchy;
- preserve the intended proportion and material behavior;
- do not use a numerical value as an excuse to produce a visibly worse result;
- if the baseline image and an old numeric value disagree, the baseline image wins;
- changes should stay local and explainable, not become a redesign.

## C. IMPLEMENTATION FREEDOM — developer decides
The developer may choose the internal implementation that best achieves the HARD requirements and 120Hz target.

Allowed freedom includes:
- exact Compose component decomposition;
- Canvas vs GraphicsLayer usage;
- AGSL/RuntimeShader pass structure;
- RenderEffect usage;
- SDF/path strategy;
- state-holder architecture;
- Pager implementation details;
- SurfaceView / TextureView / SurfaceControl choice for video compositing;
- shader pass consolidation, sampling resolution, caching, and lifecycle optimizations.

Do **not** reject a valid implementation merely because it does not match an earlier conceptual pipeline name.

# 2. Required product behavior

## Dock
Required outcome:
- floating track with 4 equal tabs: Home / Movies / Series / Profile;
- selected state is a distinct liquid/glass Bubble, not only icon tint;
- Bubble follows swipe/page progress continuously;
- Track and Bubble visually belong to the same material system;
- ends are rounded/full/continuous, never sharp or arrow-like;
- no milky white slab that dominates the page;
- no content overlap.

The exact internal layer graph is not mandated.

## Liquid Glass
Required outcome:
- background remains recognizable;
- center is relatively stable/clear;
- edges/endcaps carry more optical activity;
- motion produces visible but controlled refraction/re-imaging and highlight movement;
- no rainbow/neon/fantasy glow;
- no static white outline pretending to be refraction.

The exact blur/displacement/magnification values are tunable.

## Motion
Required outcome:
- Bubble and page swipe feel mechanically linked;
- movement includes directional deformation, not simple teleport/tint swap;
- dynamic light follows motion;
- timing is frame-time based, not fixed `1/60`.

The exact phase durations may be tuned if needed to improve the final result.

---

# 3. Performance contract

Final target:
- 120Hz-capable motion on the real Android 16 test device;
- no deliberate 60Hz cap/path;
- no repeated 60Hz state updates on a 120Hz display.

`8.33ms` is a **performance target/budget**, not a reason to block all implementation work before real-device profiling.

Optimization may change implementation details, sampling strategy, shader passes, and update regions, but should not remove the core visual identity.

Intermediate builds may be marked:
`Implemented / Pending 120Hz device verification`

Final acceptance still requires real-device confirmation.

---

# 4. Layout safety contract

All root scrolling pages must reserve bottom content space from one shared calculation.

Required behavior:
- Dock never covers readable titles, metadata, controls, or the last content row;
- bottom inset must include Dock height + Dock bottom gap + system navigation inset + content safety space;
- pages should share the same inset source instead of custom per-page Spacer hacks.

The exact computed value may adapt by device/window inset; the old fixed `112dp / 188dp` values are reference baselines, not mandatory constants on every device.

---

# 5. Visual regression rule

Before submitting a UI change, compare the **whole result** against Issue #4 Final Baseline.

Reject the change if it solves a local bug by causing any of these regressions:
- removes the Track;
- removes the Bubble;
- converts selection to icon tint only;
- introduces a giant circular selected button;
- turns the Dock into a white/milky capsule;
- introduces sharp/arrow ends;
- worsens content overlap;
- removes perceptible backdrop interaction;
- makes the product look more like generic Android navigation.

The goal is not “changed more code”. The goal is “closer to the baseline”.

# 6. Development workflow

1. Read `design/final_design_spec.yaml`.
2. Read/view Issue #4 Final Baseline image.
3. Implement the complete visual system, not one symptom at a time.
4. Use YAML values as starting production tokens.
5. Tune values when real rendering requires it, while respecting HARD constraints.
6. If the current Dock architecture is fundamentally incompatible, replace it.
7. Build and test the integrated result.
8. User performs Android 16 real-device verification.

Do not stop at “shader exists”, “Bubble exists”, or “build succeeds”. Those are implementation facts, not visual completion.

---

# 7. Technology direction

Primary stack:
- Kotlin
- Jetpack Compose
- AGSL / RuntimeShader where useful
- GraphicsLayer / RenderEffect where useful
- Media3 / ExoPlayer for playback

These are the preferred native Android tools, but the developer retains freedom over the exact internal composition as long as the HARD requirements are met.

---

# 8. Definition of Done

Final completion requires all of the following:
- overall UI is recognizably the Issue #4 Final Baseline design;
- Dock geometry/material is correct in spirit and proportion;
- Liquid Bubble exists and moves with page progress;
- backdrop interaction is visibly present;
- no content is obscured by Dock/Mini Player;
- no white flash/ripple regression;
- no major interaction crashes;
- 120Hz-targeted path works on the real test device.

If the visual result is still obviously a generic Android bottom navigation, it is not done.
