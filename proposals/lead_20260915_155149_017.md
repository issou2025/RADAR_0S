### 2. `onetaskgraph task status set <source>:<native-id> <category>`

- **What it writes.** The status of one existing task, and nothing else. Title, content, labels,
  metadata, dependencies, `delivers`, `delivered_by`, project membership and comments stay as they
  were.
- **Output under `--json`.**
  - Success prints a document naming the qualified `id`, the resulting `status` as the store reads it
    back (`category` and `name`), and the `delivered` outcomes from §3.
  - Failure prints the failure document every other verb writes, and exits non-zero.
- **Refusals, each by name:**
  - an id that is not qualified;
  - an unknown source;
  - a task that does not exist;
  - a category disabled for that source, in the wording a copy uses for that refusal;
  - a source that cannot write a status.
- **Plugin API.** A new `TaskSource` method whose default refuses as unsupported, the way
  `write_task`'s default does (`crates/onetaskgraph-plugin-api/src/source.rs`). Document it in
  `docs/plugin-protocol.md` beside the other writes, and expose it in both SDKs.
- **Per plugin.**
  - `local-md` rewrites only the record's `status`.
  - `github-projects` writes only what the category's target needs:
    - a column target sets the item's `Status` option;
    - a closed target closes the issue with the mapping's state reason;
    - a column category written onto a closed issue reopens it.

    It never changes the issue's title, body or labels.
  - `in-memory` supports it.
  - `linear` implements it or refuses it by name as unsupported, whichever its write support already
    implies.

### 3. The `delivers` relation, and the propagation the store owns

A task can name the tasks it **delivers**: finishing it finishes them. The store keeps each delivered
task's status in step with its deliverers. This is the contract, stated literally.

**The fields.** Model them on how `repositories` and `onetaskgraph.depends_on` are held today
(`Repository::METADATA_KEY`, `DependencyEdge::RECORDED_KEY`). Where the Rust types sit is your call
under "Keep the api crate still", and `scripts/check-contract-inventory.sh` must agree with it.

- **`delivers`** is a list of task ids on a task, with no repeats, empty by default.
  - A qualified entry `<source>:<native-id>` names a task in any source.
  - A bare native id names a task of the same source.
  - `task show` and `task list` print every entry qualified, in JSON and in the rendered output.
- **`delivered_by`** is the reverse list on a delivered task: the qualified ids of every task that
  delivers it. It is empty by default and **owned by the store**. No source record and no copy
  supplies it.
- **Where they are stored.**
  - `local-md`: front matter keys `delivers:` and `delivered_by:`.
  - `github-projects`: reserved metadata keys `onetaskgraph.delivers` and `onetaskgraph.delivered_by`
    in the issue's existing `<!-- onetaskgraph.metadata -->` block. Neither is ever returned among the
    caller's free metadata, just as the two existing reserved keys are not.
  - `in-memory` holds both. `linear` holds both, or refuses a write carrying either by name.
- **Refused where a record is read or written**, naming the task and the entry:
  - an entry that is not a task id;
  - an entry naming the task itself;
  - a repeated entry.

**A copy.**

- An entry naming a member of the copied set is rewritten to the destination's id for that member.
- Every other entry is carried through as a qualified id.
- A copy never takes `delivered_by` from its source. It keeps the destination item's own
  `delivered_by`, including on a total replacement.
- The copy report counts the rewritten entries.

**The back-reference.** Whenever the store writes a task's `delivers`, by copy or by any other write,
it keeps every delivered task's `delivered_by` in step:

- the deliverer's qualified id at the destination is added to each task its `delivers` names;
- it is removed from each task a previous `delivers` named and the new one does not.

Maintaining `delivered_by` changes nothing else on the delivered task. On `github-projects` only the
metadata block of the body changes, and the rest of the body stays byte-identical.

**The propagation rule.** Every write of a task that has a non-empty `delivers`, or whose previous
`delivers` was non-empty, re-evaluates each task it delivers and each task it **dropped** (named by
the previous `delivers` and not by the new one). That covers a copy that writes it and
`task status set` on it. A write that leaves the deliverer's status unchanged re-evaluates too, so a
retried write re-fires the rule.

1. **What each deliverer counts as.** Read the delivered task's `delivered_by`, including the deliverer
   just written and excluding a deliverer that just dropped it, and classify each deliverer by its
   category:

   | deliverer category | counts as |
   | --- | --- |
   | `queued`, `in-progress` | a claim |
   | `done` | finished |
   | `todo`, `cancelled`, `unknown` | a release |
   | `draft`, `backlog` | nothing |
   | read by its source as **not found** | nothing, and it is removed from the ticket's `delivered_by` on this same write |

2. **The result, over every remaining deliverer, checked in this order. The first branch that matches
   decides:**
   - `done` when every deliverer is `done` or `cancelled` and at least one is `done`. A `cancelled`
     deliverer releases its claim and never counts as completion. It only stops blocking a sibling's
     completion, because a cancelled node is one a manager idled as redundant or misdirected;
   - otherwise `in-progress` when any deliverer is `in-progress`;
   - otherwise `queued` when any deliverer is `queued`;
   - otherwise `todo` when any deliverer releases or is `done`. So every deliverer `cancelled` gives
     `todo`, and so does one `done` beside one at `todo`, `backlog` or `unknown`;
   - otherwise `todo` when **no deliverer remains** (every one dropped the ticket or was not found).
     The claim is released: a ticket at `queued` or `in-progress` returns to `todo`, and one at `todo`
     is `unchanged`;
   - otherwise, when every remaining deliverer is `draft` or `backlog`, no write.
3. **Whether the delivered task is written.** Only when it currently reads `todo`, `queued` or
   `in-progress` and the result differs from what it holds. It is written through the status-only
   write of §2, so nothing but its status changes. A delivered task at `draft`, `backlog`, `unknown`,
   `done` or `cancelled` is **left alone**: a claim never accepts, reopens or un-defers an item on a
   person's behalf.
4. **The report.** Each verb that writes a deliverer reports one entry per delivered task it evaluated,
   in a `delivered` list:
   - `ticket`, the qualified id;
   - `deliverer`, the qualified id;
   - `outcome`, one of `written`, `unchanged`, `left` or `failed`;
   - `from`, the category the ticket read;
   - `to`, the category written, present only when `written`;
   - `failure`, the failure document every other verb writes, present only when `failed`;
   - `pruned`, the qualified ids of deliverers read as not found and removed from the ticket's
     `delivered_by` on this write, present only when non-empty.

   A ticket re-evaluated because the deliverer dropped it is reported the same way, with that
   deliverer as `deliverer`. The rendered output says the same in words. `copy`'s report carries the
   list beside its per-item outcomes.
5. **A failure.** A delivered task that cannot be read or written, a deliverer unreadable for any
   reason other than not found (a transport failure, a source the configuration does not name) is
   `failed` for that ticket. The rule never guesses past it. The deliverer's own write still lands,
   and the verb exits `4` (`EXIT_PARTIAL`). A deliverer read as not found is never a failure: step 1
   counts it as nothing and prunes it.

**Documents.** `docs/plugin-protocol.md` states the fields on the wire and the rule, the README and
`docs/local-md.md` show `delivers` in a record, and `SCHEMA_BUNDLE_VERSION` moves as that repository's
recorded decision requires.

## Why

In the user's words: "when the dag starts everything in that graph goes to queued and then as is
already happening they go to in progress once the node is actually running + completed once it's
merged. this will prevent another manager picking up already in flight follow-ups or other tickets in
general, that are planned in a dag but are not running yet."

On where the relation belongs, also in the user's words: "delivers should be a otg responsibility.
That's generally useful for users of one task graph to be able to represent that one ticket solves
another ticket and that the other ticket should be closed once the solving ticket is closed. one
pipeline just handles the connection of that state to the dag".

Several managers share the same boards. An agent sent to pick up accepted tickets selects `Todo`, and
the store has no category for "claimed, not started" that does not collapse into `Todo` or
`In Progress`. A ticket worked by a plan task on another board has no relation today that would move
it, so it looks available the whole time it is being worked.

  - On `github-projects`, neither appears among the caller's free metadata.
  - An entry that is not a task id, names its own task, or repeats is refused by name.
- **A copy.**
  - A `delivers` entry naming a member of the copied set arrives as the destination's id, and every
    other entry arrives qualified.
  - A copy never takes `delivered_by` from its source and keeps the destination's, including when it
    replaces an existing item whole.
  - The rewritten entries are counted in the copy report.
- **The back-reference.** Writing a task's `delivers` adds its qualified destination id to each
  delivered task's `delivered_by`, and removes it from a task a previous `delivers` named. Nothing else
  on the delivered task changes, and on `github-projects` the body outside the metadata block is
  byte-identical.
- **The propagation rule.** Every row of the §3 table and every branch of the result rule is proven
  through the real binary:
  - a delivered task follows a single deliverer through `queued`, `in-progress` and `done`;
  - a deliverer at `todo`, at `cancelled` and at `unknown` each returns it to `todo`;
  - a deliverer at `draft` or `backlog` writes nothing;
  - with two deliverers:
    - the ticket is `in-progress` while either runs, including one `in-progress` beside one
      `cancelled`;
    - it is `queued` for one `queued` beside one `todo`;
    - it is not `done` while one deliverer is `done` and the other is `todo`, `queued` or `backlog`;
    - it is `todo` when both are `cancelled`;
    - it is `done` once both are `done`, or one is `done` and the other `cancelled`;
  - a delivered task at `draft`, `backlog`, `unknown`, `done` or `cancelled` is reported `left` and its
    status is unchanged;
  - a re-copy that leaves the deliverer's status unchanged re-evaluates, writing a ticket whose status
    had drifted and reporting a ticket in step as `unchanged`;
  - **a deliverer that no longer exists.** With a ticket's `delivered_by` naming a deliverer whose
    record was deleted, writing the remaining deliverer applies the rule over that deliverer alone.
    The ticket's entry reports the deleted one under `pruned`, the ticket's `delivered_by` no longer
    names it, and the verb exits `0`. A deliverer in a source the configuration does not name is
    instead `failed`, with exit `4`, and stays in `delivered_by`;
  - **a dropped ticket.** Rewriting a deliverer's `delivers` without a ticket removes the
    back-reference and re-evaluates that ticket, reported with the dropping deliverer as `deliverer`.
    With no deliverer left, a ticket at `queued` or `in-progress` returns to `todo`, one at `todo` is
    `unchanged`, and one at `draft`, `backlog`, `unknown`, `done` or `cancelled` is `left`. With another
    deliverer still `in-progress`, the ticket stays `in-progress`.
- **Across two sources.** A journey drives a `local-md` task delivering a task on a `github-projects`
  source served by the HTTP fixture, through `project copy` and `task status set`. The ticket's

  - A delivered task whose write the destination refuses, for example a board lacking `Queued`, is

you touched, the lint that reads your diff — and nothing wider. The repository's own
automation runs the full bar downstream on the change this work becomes: a `pre-push`
hook where that repository publishes locally, the host's required checks where it

anyway. That is measured rather than estimated: one node in this workstream spent about

a diff-scoped run reports in two.

**Pick those checks from your change, and take the narrowest scope each one supports.**
One test module over the whole suite; the lint over your diff over the lint over the
tree. A repository's own fast deterministic tier is a fine choice when it is what
exercises your change — its `just --list` says which recipe that is — and a poor one when
you reached for it because it was the widest thing available. When a check you ran
reports something, fix that and run **that check** again; nothing here asks you to re-run
its neighbours to confirm, and a wider tier cannot re-check a finding it never made.

**A dispatch that changed nothing tracked owes none of them.** When your deliverable is a
document, a report, or an answer, there is no changed code for those checks to exercise
and you are complete without them — decide that from what the repository shows, never
because running them is slow or inconvenient. `git status` reporting nothing to commit is
then a correct and complete outcome, not a problem to solve by writing a file nobody
asked for.

**Never signal a process you did not identify by PID, and a PID you got from a pattern is
still a pattern kill.** Several managers share this host, and their dispatches, drivers,
publications and test servers run under the same few binary names — `just`, `node`,
`python`, `onepipeline-api` — so a kill by name knows nothing about *whose* work it
matched. The distinction is the tool rather than the pattern: `pgrep` and `ps` **read**,
and either spelling of them is fine, `pgrep -x` included; `pkill` **signals**, and it is
never the answer here, in any spelling. `-x` is the trap, because it reads as the careful
one — `pkill -f 'just gate'` at least needs a narrowing pattern, while `pkill -x just`
takes every `just` on the machine. Reading the table first and piping the pids into `kill`
is no way around it: that is the same pattern kill with more steps.

Two workers reached that place from different directions on 2026-08-24, while another
manager's dispatch had been live over an hour. One ran `pkill -TERM -x just`. The other
ran `ps -eo pid,args | grep 'onepipeline-api serve' | awk '{print $1}' | while read pid;
do kill "$pid"; done` — which obeys the letter of every paragraph below and does the same
damage, because `just dag-ui` and the e2e suites both spawn that server and a pytest run's
were alive at that moment.

**The one process you may signal is one you started yourself, so capture its PID as you
start it:**

    cmd & MYPID=$!
    kill "$MYPID"

Anything you did not start belongs to somebody. Read what it is, report what you found,
and leave it running.

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or
`publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

That has wedged four workers here, and then two more workers and the manager itself in one
night: seven instances of one defect. A crozier corpus audit waited in `until ! pgrep -f
'scripts/fetch-corpus.sh'` with no fetch running at all — the only two matches were its own
polling shell and the manager's diagnostic shell — and waited until it was interrupted. A
`check-plan-bar-conflict` dispatch waited on `! pgrep -f "llmlint-judge.sh"`, whose negation
could never become true, and was cancelled and killed; its replacement then reached for
`pkill -f` against three patterns, which is not a wait at all but the same self-match with a
signal attached, and is refused above. And the manager, an hour after instructing a worker

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.

**To ask whether a process is running at all, match the executable, not the command line.**
`pgrep -x onepipeline` matches process *names* exactly — the binary, not its arguments — so
the shell doing the asking, whose own name is `bash`, cannot match it however the pattern
is spelled. Where the binary name is not distinctive enough to identify what you mean
(`just`, `node` and `python` run everything), read the process table instead and drop the
one self-match that form has:

    ps -eo pid,args | grep -v grep | grep 'lint-llm-diff'

Both of those are **reads**, which is what makes `-x` safe here and forbidden the moment
the tool signals. The replacement for the worker wedged above reached for `pkill -f "just
gate"`, `pkill -f "just check"` and `pkill -f "nx run"` while another manager's run was
live. Read to learn what is running, report what you found, and signal nothing you did not
start.

**One sentinel and one log per invocation, and look before you launch one.** That pair is a
shape rather than two literal paths. Several dispatches run on this host at once and they
share `/tmp`, so a second worker writing `/tmp/check.log` writes into the first one's — and
`until [ -f /tmp/check.exit ]` returns immediately on somebody else's exit file, reporting
their result as yours. Name both after the invocation (`/tmp/check.$$.log`, or the node
id), and, before starting it, check whether its sentinel path is already in use by another
invocation; if so, choose a different invocation-specific pair. This path-ownership check
does not prohibit concurrent checks or judged tiers. Three workers collided on shared names
today and not one of the three failures read as what it was: two
