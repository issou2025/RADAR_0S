# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat(skills): vendor-neutral secrets access layer**

*Project description:*
## Why this exists

Provisioning a real GTM automation stack surfaced a class of failure that no Lisa skill currently prevents: **the same credential existing in more than one store.**

Concretely, across two days of work on a downstream project:

- An API key lived in both a secrets manager and the OS keychain. A sync that would have reconciled them was flagged once as `would update` and never applied, so the two silently diverged.
- Both values authenticated. They were **two live credentials**, not one stale copy — and the difference is not visible from either side.
- Pruning "duplicates" then deleted the one that differed, leaving a working credential recorded nowhere until it was tracked down and revoked.

Every one of those steps looked reasonable in isolation. The failure was structural: nothing owned the rule that a secret lives in exactly one place, so nine scripts each grew their own env-then-keychain resolver and drift became inevitable.

## What good looks like

**For the person operating a project:** one place to put a credential, and an error that tells them what is actually wrong when resolution fails — not a silent empty value.

**For an agent working in a repo:** a single call to obtain a secret, with no decision to make about where to look, and metadata describing what the secret is for so it can orient without guessing.

**For whoever owns the vendor relationship:** confidence that a leaked or rotated credential has exactly one home to fix, and a check that reports when that stops being true.

## Scope

Add `lisa-secrets-access`, a vendor-neutral access layer following the established `lisa-atlassian-access` pattern. Every skill or script needing a credential delegates through it rather than reading a keychain, an `.env`, or a provider CLI directly.

Config in `.lisa.config.json`:

```json
{
  "secrets": {
    "provider": "bitwarden",
    "bootstrap": { "sources": ["env", "keychain"], "key": "BWS_ACCESS_TOKEN" },
    "require": ["ATTIO_API_KEY"]
  }
}
```

Four design choices, each of which had an obvious-looking alternative that was rejected:

- **No map of secret IDs.** Copying a UUID per secret is the same duplication in a smaller costume. Lookup is by name.
- **No list of expected names by default.** The provider already scopes what a machine account may see, so that set *is* the permitted set; restating it duplicates a boundary already enforced. `require` is optional and, when present, asserts rather than merely filters.
- **Environment resolves first**, so CI injection wins and a scheduled run never touches a local store.
- **Never writes.** Writing secrets or their notes needs an authority a CI credential should not hold.

Usage metadata is read from the provider's own description field — Bitwarden `note`, 1Password notes, AWS `Description` — because a note travels with the secret and therefore cannot drift from it, which is the property a config file lacks. When empty, infer purpose from the name, **mark it inferred, and report the gap**: a silent fallback that works well enough guarantees the notes stay empty forever.

## Acceptance criteria

```gherkin
Scenario: the environment wins over the provider
  Given a secret exists in the configured provider
  And the same name is set in the environment
  When a caller resolves that name
  Then the environment value is returned
  And the provider is never contacted

Scenario: a missing name fails usefully
  Given a caller requests a name the provider does not hold
  When resolution runs
  Then the error names which secrets are visible
  And states that a key must be the exact environment variable name

Scenario: require asserts rather than filters
  Given secrets.require lists a name
  And that name does not resolve
  When verification runs
  Then it fails at startup rather than at point of use

Scenario: describe never leaks a value
  When a caller describes a secret
  Then the usage note is returned
  And no part of the secret value appears in the output

Scenario: doctor reports a credential in two stores
  Given a secret is readable from both the provider and a local cache
  When doctor runs
  Then it reports two live credentials rather than a duplicate
```

## Out of scope

- Writing, creating or rotating secrets. Read-only by design.
- Managing the rotating-credential writer. An OAuth refresh token that the issuer replaces on each use needs a separately scoped writer and exactly one process holding that loop; that is its own concern.
- Implementations for 1Password, AWS Secrets Manager and Vault. The dispatch table documents them and the resolver fails with a clear message naming where to add one.

## Technical approach

- `plugins/src/base/skills/lisa-secrets-access/SKILL.md` — the contract, following `lisa-atlassian-access`.
- `plugins/src/base/skills/lisa-secrets-access/scripts/resolve-secret.mjs` — the resolver, as a **CLI rather than a library** because callers are polyglot: Python scripts, shell and TypeScript all need the same answer, and a subprocess is the only interface all three share without triplicating the logic.
- Operations: `get`, `list`, `describe`, `verify`. `list` and `describe` can never emit a value.
- In-process caching only. A disk cache would recreate the problem this exists to remove.

## Validation journey

Verified against a live Bitwarden Secrets Manager project holding ten secrets:

1. `list` returns ten names, no values.
2. `get ATTIO_API_KEY` returns a value whose hash matches the one CI injects.
3. `ATTIO_API_KEY=x get ATTIO_API_KEY` returns `x`, confirming environment precedence.
4. `describe HANDWRYTTEN_API_KEY` returns the stored note including its API gotchas.
5. `get NOPE` lists the visible names and explains the naming rule.
6. `verify` reports resolves / name-shape / note-present per secret.
