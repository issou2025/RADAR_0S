## Executive assessment

This week moved SkillJury from a broad “trust methodology” idea toward a more concrete product thesis: **SkillJury should become a provenance-first trust and lifecycle-risk layer for mutable agent skills, with directory discovery serving mainly as distribution.**

The strongest new product evidence was not a growth metric. It was a failure of reproducibility: the visible `flutter-app-size` recovery record points to historical source identity `flutter/skills`, which now resolves upstream to `flutter/agent-plugins`, while SkillJury’s stored record does not preserve the exact evaluated commit, path, checksum, or scanner version needed to prove what the historical audit actually evaluated.

That makes immutable provenance capture—not a prettier score or larger catalog—the highest-leverage prerequisite for trustworthy drift detection.

## Product and trust audit

### Evidence for the narrowed hypothesis

1. **Discovery/popularity is becoming infrastructure rather than a defensible product.** `skills.sh` ranks from anonymous CLI installation telemetry and automatically lists installed skills; it also explicitly warns that it cannot guarantee every listed skill’s quality or security.
2. **Skill artifacts are becoming more mutable at runtime/distribution time.** Microsoft Agent Framework now supports discovering and loading Agent Skills directly from MCP servers, allowing centrally hosted skills to change without an application redeploy.
3. **Current security research is lifecycle-aware, not merely static-scan-aware.** SkillSec-Eval models repository admission, retrieval, planner selection, execution, and later skill evolution as distinct attack surfaces.
4. **SKILL.md itself is part of the supply chain.** Recent work shows semantic content can manipulate discovery, selection, and governance decisions even without conventional malicious binaries.
5. **Dependency provenance is emerging as a missing primitive.** Recent work applying SBOM-like analysis to more than a million skills argues that skill identity, versions, dependency graphs, and lockfile-like records are currently too implicit.

### Evidence against the current implementation

- The public recovery catalog has aggregate counts for 4,274 skills and 784 sources but only 25 complete browsable skill records.
- The snapshot is dated Jul 18 and grows less credible as a current ranking every day live sync remains unavailable.
- Review volume, submissions, saves, and conversion remain unavailable because Supabase is inactive.
- GA4 exists, but property-side navigation/event behavior is not accessible through current connected tools, so the methodology experiment still lacks trustworthy behavioral measurement.
- Legacy security audit statuses are not reproducible against exact immutable artifacts because evaluated commit SHA, skill path, checksum, and scanner version were not stored.
- The `flutter-app-size` test demonstrates real source identity/content drift and shows why an old pass/warn result must not silently imply current-upstream validity.

## Security audit

### Strengths
- Current production responses retain CSP, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, strict referrer policy, and restrictive camera/microphone/geolocation permissions.
- Transactional routes and scheduled writers were previously made provider-safe rather than repeatedly hammering the restricted database.
- Trust methodology explicitly avoids absolute safety claims.

### Highest-risk trust gap
Security findings are currently attached to logical records, not immutable evaluated artifacts. A status such as `pass` cannot be strong evidence once upstream identity/content has changed unless SkillJury can prove the commit/path/checksum and scanner version it evaluated.

The trust model should therefore treat provenance mismatch or missing provenance as a first-class state, not as a minor metadata omission.

## Market and ecosystem movement

This week materially strengthened the provenance thesis:
- `skills.sh` has standardized cross-agent skill installation and popularity telemetry, reducing differentiation from basic discovery/ranking.
- Microsoft shipped production-ready Agent Skills for .NET and then direct MCP-hosted skill discovery, making centralized skill evolution a normal distribution pattern.
- Recent research independently converges on lifecycle security, semantic supply-chain attacks, evolving skill stores, dependency graphs, provenance, rollback, and lockfile-like records.
- Developer discussion increasingly treats MCP, CLI tools, and Agent Skills as complementary layers, which implies SkillJury should evaluate the composed trust boundary rather than treating a skill as an isolated README-like artifact.

No credible evidence reviewed this week justifies competing on raw directory size, generic reviews, or cosmetic scoring.

## Strategic decision

**Continue, but narrow again.**

Working thesis for the coming week:

> SkillJury is a provenance-first trust ledger for agent skills. It should tell a developer exactly which artifact was evaluated, where it came from, what it can do, what it depends on, what changed, and whether the old trust conclusion still applies. Directory discovery is the acquisition layer, not the moat.

The product should not claim reproducibility for legacy records that cannot be reproduced.

## Highest-leverage actions for the coming week

### Urgent fixes
1. Keep issue #22 open and aggregate recurrences silently unless impact changes. The next technical experiment must inspect production-equivalent emitted CommonJS + ESM app-render artifacts or use a controlled Next.js version change with focused RED/GREEN regression coverage.
2. Keep recovery mode intact while Supabase remains inactive. Do not reactivate write/auth flows piecemeal.

### Strategic decision
Define immutable provenance as a prerequisite for every newly ingested trust conclusion. Minimum identity should include canonical repository identity, immutable commit SHA, exact skill path, deterministic artifact checksum, evaluation timestamp, scanner/tool identity + version, dependency/capability evidence, and an explicit stale/unknown state.

### Cheap experiments
1. Implement the provenance schema/manifest for **one newly captured skill whose current upstream commit can be pinned end-to-end**. Do not retrofit a legacy SHA.
2. Produce one static trust dossier from that manifest and prove that changing the upstream artifact invalidates or marks the conclusion stale.
3. Once GA4 navigation behavior is verifiable, measure whether visitors who inspect provenance/trust evidence are more likely to open the upstream repository or another skill detail page. Do not add measurement code before issue #56’s duplicate-pageview question is resolved.

## Success criteria for next week

A successful week is not “more pages.” It is:
- one trust record whose evaluated artifact can be independently reproduced from immutable evidence;
- a deterministic stale/changed/unknown rule when upstream differs;
- regression coverage that prevents a trust conclusion from surviving a checksum/commit mismatch;
- preview + production verification if any product code ships;
- no degradation of the recovery catalog;
- no fabricated analytics or legacy provenance.

## Measurement reality

Available and trustworthy now:
- deployment health;
- runtime error/5xx signals;
- route usability;
- static snapshot coverage;
- repository/deployment history;
- upstream source evidence.

Not currently trustworthy/available enough for product claims:
- review conversion;
- submissions/saves;
- current install/ranking freshness;
- GA4 client-side navigation behavior/property-side engagement;
- exact provenance for historical legacy audits.

## Final weekly decision

**Continue, narrow, and prioritize provenance capture over catalog expansion.**

The week produced a useful falsification: a version-drift dossier cannot be trustworthy if the original evaluated artifact was never pinned. The next product milestone is therefore not the dossier UI itself; it is the immutable evidence layer that makes the dossier true.
