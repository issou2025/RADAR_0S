# Project Proposal — Unknown

## Project Understanding
You need assistance with: 
**Task state is not trustworthy during a swarm: workers lack the tools, the gate is repo-wide, and the board does not survive the session**

*Project description:*
Task state was the least trustworthy signal in a long swarm session. By the end I was reading `git log`, `gh issue list`, and branch diffs to work out what was actually done, and treating the task list as decoration. Five distinct problems, all observed in one Phase 0 → Phase 1 build.

## 1. Workers do not actually have the task tools

`agents/worker.md` declares `TaskGet`, `TaskList`, `TaskCreate`, and `TaskUpdate`. In practice they were absent from every spawned worker's tool roster. Three separate workers reported it unprompted:

> `TaskGet`/`TaskUpdate` aren't in my tool roster — I'll keep reporting task completions to you by message as instructed.

> `TaskUpdate`/`TaskList`/`TaskGet` are not available in my tool roster (confirmed again this session), so I can't mark task 11 done on the board myself.

This is the load-bearing failure. The dispatch model in `agents/orchestrator.md` says *"Workers self-claim subsequent tasks via TaskList"* — that cannot happen. It degrades silently to the orchestrator hand-transcribing status from chat messages, which is exactly where the board drifts out of sync with reality.

Either the tools should genuinely reach workers, or the docs should stop describing self-claiming and the orchestrator should own the board explicitly.

## 2. The completion gate is repo-wide, so unrelated tasks cannot be closed

`task-completed-gate.sh` runs the full test suite. Early in a project that means *no task can ever be marked complete*, regardless of whether it is finished.

Concretely: task 1 was "bootstrap the toolchain" and task 11 was "write the docs". Both were done. Both were refused:

```
[task-completed-gate.sh]: Tests failing. Fix tests before completing: Bootstrap toolchain and repo scaffolding
[task-completed-gate.sh]: Tests failing. Fix tests before completing: Docs, ADR, and the two human runbooks
```

The suite was red because the project had no test files yet — the task that would add them was #7, still open. So the gate blocked closing a docs task on the state of a test suite that did not exist. The board sat wrong for hours as a direct result.

A gate that cannot distinguish "this task broke the build" from "the build is red for reasons predating this task" trains people to ignore it.

## 3. The task list does not survive the session

A session limit killed six workers at once. The eleven decomposed tasks vanished with the session. Everything else survived because it was on disk or in git — `context.md`, `checkpoint.json`, the branches.

`/pds:swarm` treats decomposition as a real phase with real cost, and then stores the output somewhere strictly more fragile than every other artifact it produces. On restart I rebuilt all eleven by hand from `context.md`.

If checkpointing exists precisely so a swarm can be resumed, the task graph belongs in it.

## 4. Nothing links a task to the work

The board holds a subject and a description. It does not hold the branch, the issue, the PR, or the commits. So the questions actually being asked during a swarm — *is task 13 merged? which branch is it on? did that PR close it?* — are unanswerable from the board.

I ended up maintaining that mapping by hand in `checkpoint.json` and in GitHub issue comments, which is duplicated state that immediately goes stale.

## 5. Malformed `TaskCreate` fails silently

I mis-nested XML in a `TaskCreate` call. It succeeded, and produced a task whose *subject* was the entire malformed payload — several hundred lines, description included. No validation, no warning.

A subject that long is never intentional and would be cheap to reject.

## Suggestions, roughly in value order

1. Fix worker task-tool access, or remove self-claiming from the docs. The current gap is worse than either resolution because it fails quietly.
2. Scope the completion gate to the task, or let it be overridden with a reason. Failing that, distinguish a pre-existing red build from one this task caused.
3. Persist the task graph into `.claude/swarm/checkpoint.json` alongside the phase.
4. Add optional `branch`, `issue`, and `pr` fields to a task.
5. Reject implausible subjects — a length cap would have caught mine.

## Context

Observed across a full Phase 0 → Phase 1 build: 19 tasks, 8 workers, one session-limit crash, one watchdog-interrupted worker recovery. PDS 5.1.1.

For what it is worth, the parts that held up were the ones written to disk. `.claude/swarm/context.md` was genuinely excellent — every worker read it and built to it, and the amendment sections at the bottom worked well as a way to override earlier decisions without rewriting history. The problem is specifically the in-memory task board next to it.
