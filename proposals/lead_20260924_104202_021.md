# [Roadmap] NX_MCP 2026 Q4, with H1 2027 outlook

> **Updated:** 2026-09-24 · **Next refresh:** early January 2027
> **Scope:** Q4 2026 is planned in detail; H1 2027 is direction, not commitment.
> This issue is pinned. Each quarter gets a new issue; the previous one is closed with a link.

**North star.** An agent should be able to change a real Siemens NX model *and prove
the change is correct*, without arbitrary code execution. Every capability we add
serves that loop:

**inspect → mutate → measure → compare with intent → repair or stop**

We grow the certified surface only as fast as we can verify it on real NX.

## TL;DR

- **Q4 theme: ship `0.2.0`, then close the verification loop in `0.3.0`.**
- `0.2.0` is blocked on **evidence, not features**. The current commit has not passed
  a full acceptance run on any NX build yet (see [Evidence](#where-we-are-evidence)).
- `0.3.0` adds units and measurement (bounding box, volume, distance), so an agent can
  confirm `20 × 10 × 12.5 mm → 2500 mm³` through MCP instead of trusting "NX returned success".
- Feature breadth (arc/circle, hole, fillet/chamfer, pattern) and parametric editing
  follow in H1 2027, one coherent group per PR, in **both** bridges.

## Q4 2026

### M1 — `0.2.0`: certified foundation

**Goal:** the existing 16 tools pass a fresh acceptance run on a tagged commit,
through each bridge, on at least one supported NX build.

- [ ] Python bridge: take the same `bridge.lock` as the C# bridge, use a per-writer temporary descriptor, refuse a live descriptor with the invalid-token probe (#9)
- [ ] Configurable `run_journal` arguments, used by README, `real-nx.yml` and the restart test (#8)
- [ ] Hosted-CI parity check between `nx_bridge.py` and `NxMcpGuiBridge.cs` (#9)
- [ ] `nx_status` reports `bridge_implementation` (additive; protocol stays v1)
- [ ] Runtime probe writes a versioned evidence JSON: NX release and build, embedded Python, bridge, accepted `run_journal` switches, commit, OS (#9)
- [ ] Fresh acceptance + restart at the release candidate: Python batch on NX2506
- [ ] Fresh acceptance + restart at the release candidate: C# GUI on NX2206
- [ ] `CONTRIBUTING.md`, PR template with an evidence section, NX validation-report issue form, `SECURITY.md`
- [ ] `RELEASE.md` checklist and `CHANGELOG.md`; tag `v0.2.0`

**Parity check scope:** command names; required parameters and optional defaults;
mutation set (it decides undo marks and rollback); protocol version, 1 MiB message
limit and 5 s receive deadline; `CERTIFIED_TOOL_NAMES`. The check must fail loudly
when it cannot parse the C# source, so a refactor cannot silently disable it.

**Exit criteria**

- Evidence JSON and JUnit reports exist for both cells above, at the same tag.
- Adding a command to one bridge only fails hosted CI.
- A contributor on another NX build can reproduce the run from documentation alone.
- The version moves from `0.2.0.dev0` to `0.2.0` only after all of the above.

### M2 — `0.3.0`: the verification loop

**Goal:** an agent can check numerically, through MCP alone, that a sketch/extrude
produced the intended solid.

**Contract first.** One short design issue settles these before any code:

- the units of returned values;
- the coordinate system;
- exact or approximate bounding box;
- tolerances;
- accepted ID kinds;
- error codes.

The 0.1 implementations in `tools/measure.py` and `tools/feature_tree.py` are
reference material, not the contract.

- [ ] Inspection contract issue
- [ ] Part units and counts: `nx_get_part_info`, or `units` added to `nx_status`
- [ ] `nx_get_bounding_box`, `nx_measure_volume` (or `nx_get_mass_properties`), `nx_measure_distance`, in both bridges
- [ ] `real_smoke` asserts numbers: `20 × 10 × 12.5 mm`, `2500 mm³`, one body
- [ ] Independent check: exported STEP measured outside NX, reusing the separate-environment pattern of the USD validator
- [ ] MCP tool annotations (`readOnlyHint`, `destructiveHint`) on every certified tool
- [ ] `nx-modeling` skill: verification uses measurements instead of existence checks
- [ ] New skill for interactive GUI sessions: shared work part, `state_dir` on both sides, undo versus discard-close, calls deferred behind dialogs (#9)
- [ ] `docs/compat/nx2206.md`: measured behaviour and workarounds on that build (#9)

Part units come first because `nx_status` does not report them today, so the skill
has to ask the user before using any dimension on an existing part.

**Exit criteria**

- The canonical block is created and verified end to end through MCP on real NX.
- Real-NX acceptance fails on a wrong dimension, not only on a missing file.
- Every measurement result carries an explicit unit.

## H1 2027 outlook

Direction only. Order may change with evidence and contributor interest.

**`0.4` — core mechanical features.** Promotion order:

1. sketch arc and circle;
2. hole;
3. fillet and chamfer;
4. linear and circular pattern;
5. revolve;
6. boolean operations.

Each group gets a tracking issue and lands in both bridges together. Each group is
verified with the `0.3` measurement tools. Target workflows: a plate with patterned
holes, a revolved shaft, a bracket with fillets and holes.

**`0.5` — parametric editing.**

- List, read and update expressions.
- Edit supported feature parameters, and report regeneration failures explicitly.
- A model revision token, so an agent notices that a human edited the part in the GUI
  and re-inspects before its next mutation.

**Scenario suite.** Grows out of `real_smoke`. Each scenario is a task statement plus
deterministic geometry assertions, like SWE-bench's hidden tests. Checks include
bounding box, volume, body/feature/hole counts and hole positions. Assertions run in
the real-NX workflow. An LLM judge never replaces a check NX or the STEP can answer.

**Surface scaling**, once the certified surface passes about 30 tools:

- tool groups the client enables (compare the GitHub MCP server's toolsets, and the
  compact profile explored in #5);
- read-only MCP resources for session and part state;
- view capture, GUI bridge first.

**Later / exploration:** assembly inspection before assembly mutation; drawings and
PMI; additional NX builds as contributors bring runners.

## Capability maturity

"Implemented", "tested" and "certified" are different claims. This table makes the
levels explicit. The idea is borrowed from Kubernetes' alpha → beta → GA feature
graduation.

| Level | Where | Requires | Exposed |
| --- | --- | --- | --- |
| Legacy | `tools/` | nothing beyond mock tests | `NX_MCP_ENABLE_EXPERIMENTAL=1`, both processes |
| Preview *(proposed, RFC 3)* | certified modules | typed contract, fake-NX and failure-path tests, both bridges, parity check | opt-in flag, both processes |
| Certified | default `tools/list` | the above + real-NX acceptance with numeric assertions on a supported build, docs | default |

The current rule: a tool is certified only when both bridges implement the same
contract. The sidecar advertises one list whichever bridge is connected. A tool
missing from one bridge would be listed and then fail.

## How we work

- **Contract first.** New certified tools, bridge protocol changes, or more than about
  500 lines of non-test code need an issue or RFC before the PR. Very large PRs will
  be split along agreed boundaries before review.
- **Evidence in every NX-facing PR:**
  - NX release and build;
  - bridge implementation;
  - commit;
  - the commands that were run;
  - results.

  The PR template asks for this.
- **Real-NX CI runs only trusted refs** on the maintainer's self-hosted runner, never
  PR code. Contributors running their own NX installations submit evidence through the
  validation-report form. These reports are informative, not required checks. We keep
  test failures separate from runner or licence problems.
- **AI-assisted contributions are welcome.** Say so in the PR. The human author stays
  accountable for every line and must have actually run the validation they report.
- **Clean-room documentation.** Skills and docs are written in contributors' own words
  and validated on real NX. Nothing is transcribed from Siemens documentation or
  videos. The repository and CI artifacts never contain NX binaries or assemblies,
  licence files, tokens, descriptors or customer parts.
- **Labels:** `area/{bridge,gui,tools,inspection,compat,skills,ci,docs}`,
  `kind/{bug,feature,rfc}`, `real-nx-required`, `help wanted`, `good first issue`.
- **Review:** we aim for a first response within three working days. Ping after a week.

## Not now

- **Full NXOpen coverage.** The surface is designed around verifiable agent workflows,
  not API breadth.
- **Arbitrary Journal or code execution as a way to add capabilities.** It remains an
  explicit, disabled-by-default escape hatch.
- **Remote or network-exposed bridges.** The security model is loopback plus a
  per-session token.
- **Teamcenter-managed sessions (`run_journal -pim`).** Native parts only.
- **CAM and CAE.** Also broad assembly or drawing automation before the part-level
  verification loop is done.
