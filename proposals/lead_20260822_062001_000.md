## Notes before starting

### Products, releases, variants, and outputs form a chain

A product holds releases, a release holds variants, a variant holds outputs. The walkthrough runs the four in order. Model them as four resource groups on one namespace and document the order.

### Variant and output creation are asynchronous

Both return a request ID. Poll `GET Get Outputs Request` or `GET Get Upload Request` until it finishes. Reuse the polling pattern from `client.model_derivative.wait_for_translation`.

### Uploads and downloads are signed URLs

`POST Get Upload URLs` and `GET Get Signed Download URL` behave like the OSS signed flow. Reuse the OSS helpers.

### Rules need reading before modelling

`POST Evaluate Rules` and `POST Validate Rules` take a rule document. Read [Rules](https://aps.autodesk.com/en/docs/informed-design/v1/rules/) first and decide whether to type it or pass a dict.

## How it fits the client

Follow the shape that `client.issues` already uses:

- `src/autodesk_platform_sdk/services/informeddesign/operations.py` holds one `Operation` per endpoint and a `BASE` constant.
- `schemas.py` holds the Pydantic request and response models.
- `__init__.py` holds the service class with a sync method and an async method for each operation.
- Mount `client.informed_design` in both `client.py` and `async_client.py`.
- Add `cli/commands/informeddesign.py` and register it on the `aps` group.
- Add `tests/test_informeddesign.py` with mocked transports.
- Add the row to the services table in `README.md`.
