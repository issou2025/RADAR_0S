# Project Proposal — Quantity Takeoff

## Project Understanding
You need assistance with: 
**spike(mobile): native iOS/Android app, plausibility and mobile-first design**

*Project description:*
### What

A spike, no implementation: how plausible a **native CheevoVault app for iPhone and Android** is, and a first mobile-first design.

**Not a web wrapper.** No WebView / PWA shell / Capacitor around the site: a real mobile project with native navigation (tab bar, stacks, gestures, pull to refresh), its own screens designed for a phone, talking to the same backend.

**Scope decided by the owner (2026-11-16): a personal app, for the owner only, for now.** No store, no other users, no public sign-in. That removes the store fees and reviews and most of the auth work; the spike says what it would take to open it to everyone later, but does not plan for it.

**When:** only once the site is in a stable enough version. From then on every feature has a second client to keep in step, so starting while the web still changes a lot doubles the work.

The spike answers:

1. **Stack.** Likely Expo (React Native + TypeScript), since the team already writes React/TS. Compare against Flutter / Swift+Kotlin only briefly and say why not.
2. **Installing it without the stores.** The owner has an **iPhone 13** and is on Windows with no Mac. Leaning (2026-11-16): **sideload with a free Apple ID through SideStore** (or AltStore), a new build about **once a month** when the web has changed enough, not in step with every web release.
   - A free Apple ID signs for **7 days**; SideStore re-signs on the phone in the background (no PC needed after setup), AltStore needs AltServer on the PC on the same Wi-Fi. If a refresh is missed the app just will not open until one tap re-signs it; nothing is lost. Max 3 sideloaded apps; iOS Developer Mode on.
   - The unsigned IPA is built on a **GitHub Actions macOS runner** (no Mac at home; check the repo's macOS minutes, an Expo iOS build is ~15-30 min, fine monthly).
   - The data is always fresh (it comes from the server); a new build only brings new screens. **EAS Update** (OTA JS updates) could even ship small UI changes without reinstalling: check it works with a sideloaded build.
   - Fallback if the weekly re-sign gets annoying: the paid Apple Developer Program (signing lasts a year, TestFlight, push notifications).
   - Android, if ever: an APK installed from the file manager, free and no expiry.
3. **Auth for one account.** No credentials in the app: an APK/IPA can be unpacked. Proposal: a personal token (long random value) in a server env var mapped to the owner's user id; `requireSession()` also accepts `Authorization: Bearer <token>` (constant-time compare through `src/lib/secrets.ts`), so every route works unchanged; the token is typed once in the app and kept in the OS secure storage (`expo-secure-store`); rotating the env var revokes it. Admin routes keep their own locks (`requireAdmin`) and stay out of the app. Opening it to others later means a real token flow (sign-in, refresh, Steam OpenID and RA linking via in-app browser + deep link).
4. **What can be shared with the web.** `src/types/`, the pure utils (`dates.ts`, `streaks.ts`, `vaultScore.ts`, `gameRef.ts`…) and the translations (plain data) could live in a shared package (workspace). What cannot: every component (`ui/` is DOM + Tailwind), Framer Motion, recharts.
5. **Backend.** The ~106 route handlers in `src/app/api/` are the API the app calls. Check `proxy.ts`, CORS and rate limits against a non-browser client; the app never calls a platform directly and never holds an RA key or NPSSO.
6. **Mobile-first design.** On the design canvas (`docs/design-process.md`), in the site's visual language (slant, mark, display italics, themes): home/vault, library, game page with achievements, streak, rankings, profile. Which screens a phone needs on day one (the MVP) and which stay web-only (admin, heavy settings).
7. **Phone-only value**: push notifications (ties to the "Notifications" **ask first** item in `docs/roadmap.md`), widgets (streak, last unlock), offline read of the last data. Check what each needs with sideloading (push on iOS needs the paid program).
8. **Effort and upkeep.** A rough estimate in sessions for the MVP; how versioning, CI and the "the welcome follows the app" style rules extend to a second client.

Deliverable: a doc under `docs/` (verdict, stack, install path per phone, auth plan, MVP scope, effort) plus a design entry in `docs/designs.md` with the canvas link.

### Why

The owner would love to use CheevoVault from their phone with an interface made for it, not the responsive site. It is big, so first know whether it is affordable. **Low priority**: to pick up when the site is stable, nothing else is pending and there are spare sessions in the week.
