*Project description:*
## Objective

After the current governance/documentation convergence has stabilized, prove Pantheon on one real architecture-agency task before adding further ontology, Roles, Rites, governed Spaces or broad product abstractions.

The first vertical is deliberately narrow:

```text
CCTP + DPGF/DQE + contractor quote
-> governed ACT / pre-contract review
-> source-linked findings
-> human professional decision
```

The goal is not to demonstrate that an LLM can summarize or compare documents. The goal is to demonstrate that the existing Pantheon architecture produces a review that is materially safer, more traceable and more useful to an architect than an ordinary assistant workflow.

## Why this issue exists

Pantheon already contains substantial doctrine and implementation around:

- Case / Affaire and Situation intake;
- document identity, versions and source authority;
- architecture document review;
- CCTP / quote comparison;
- Evidence candidates and human decision gates;
- Hermes external execution;
- Pantheon governance / policy / bounded persistence;
- Cockpit governed projection;
- document structural-analysis qualification;
- real-environment Project Anatomy qualification.

The current risk is no longer primarily missing conceptual coverage. The risk is that Pantheon architecture and doctrine advance faster than demonstrated professional value.

This issue therefore changes the validation question from:

> Is the architecture internally coherent?

to:

> On a representative architecture task, does Pantheon actually prevent mistakes, preserve the right source/version/authority distinctions, reduce reconstruction effort, and produce a review an architect would choose to use?

## Expected finding shape


## Qualification dimensions

Do not use a single abstract AI score.

Measure at least:

### 1. Coverage

- known material findings detected;
- known findings missed.

### 2. Noise

- false-positive findings;
- duplicate findings;
- findings that are technically true but professionally useless.

### 3. Provenance

- every material claim resolves to the correct source document;
- exact version/index is visible;
- page/clause/structural locator is preserved where available;
- derived extraction never silently replaces the source.

### 4. Version and authority safety

- superseded/non-applicable documents do not silently control the answer;
- the system exposes uncertainty when authority/currentness is unresolved;
- a newer filename/index does not automatically become contractual authority.

### 5. Governance safety

- findings remain candidates until professionally reviewed;
- no automatic compliant/non-compliant verdict from document matching alone;
- no contractor selection/rejection;
- no automatic contract, OS, payment or transmission effect;
- missing evidence produces a bounded refusal/uncertainty state rather than invented certainty.

### 6. Professional usefulness

Human review should answer:

- Would an architect actually use this review?
- Does it reduce time spent reconstructing context?
- Does it expose useful issues that may otherwise be missed?
- Are proposed contractor/client questions directly usable after review?
- Does the system make the important uncertainty easier to see rather than merely producing more text?

### 7. Effort

Record at least qualitatively, and quantitatively where practical:

- manual setup required;
- manual source/version correction required;
- number of review interventions before usable output;
- avoidable repeated clarification;
- rework caused by false positives or bad source selection.

The product test is not merely `workflow completed`.

The stronger question is:

> Would the agency prefer to run this review through Pantheon again on the next comparable case?

## Harness ratchet / failure-to-constraint loop

Every meaningful failure observed during the vertical must be classified before changing prompts or adding architecture.

Use the strongest justified correction layer:

```text
one-off/local context problem
-> task/context correction

recurring judgement/procedure problem
-> existing method/guide owner

objective recurring check
-> deterministic sensor / test / validator / schema where appropriate

action that must be impossible without authority
-> existing policy / permission / contract boundary

source information lost or distorted upstream
-> parser / adapter / normalization owner

already structurally enforced rule
-> remove redundant narrative restatement where safe
```

Compact principle:

```text
one recurring failure -> strongest justified enforceable constraint
```

The ratchet is an engineering/product discipline, not by default a new Role, Rite, governed Space, workflow engine or ontology layer.

## Cockpit acceptance posture

The Cockpit should project professional attention, not internal ontology.

A successful first vertical should be able to present something conceptually like:

```text
Affaire X — lot couverture

3 points require review
- one CCTP item has no matching priced quote item
- one contractor exclusion conflicts with the selected review baseline
- one quantity differs from the DPGF

Baseline used: DCE / CCTP index <X> / DPGF index <Y>

- inspect sources

```

The user should not need to invoke `ARGOS`, `THEMIS`, a Rite, PDP/PEP terminology or Task Contract fields manually for ordinary use.

Those mechanisms may explain why a result is gated, but the primary UX vocabulary should remain professional.
