# Dynamic UI cards in Crew: speed and interactivity

Research date 2026-11-01. Read-only: no app code, no PRs, no server or profile config changed. Probes ran only on `crew-test` (model `gpt-6.1-sol`), via `Tests/chat_probe/run.sh a2ui`, 4 turns, n=1 per prompt.

## Verdict

**Speed.** A recipe card takes about 29 s from send to visible card, and 22 s of that is Crew showing "Preparing card…" while the model streams ~1,300 tokens of A2UI JSON. Crew only renders a card after `message.complete`. The biggest win is Crew-only: render the surface progressively from the open fence. On the measured turns that would have shown the card header at about 14.9 s instead of 29.0 s (recipe) and about 8.4 s instead of 16.5 s (pancakes). A one-line skill change (components before the data model) should pull the header up to about 1 s after the fence opens (estimate). Next come fewer tokens per card through template components (`Recipe`/`Ingredients`), then dropping the `skill_view` round trip with Hermes' `skills.auto_load` (profile config, 2.7 to 5.2 s before the first token when it fires). For data cards (weather), tool round trips dominate: 28 of 36 s happened before the first token, and Crew can't speed that up.

There is also a reliability bug: "Give me a recipe for köttbullar for 4" produced **no card**. The model called `skill_view chef` and wrote 3 KB of markdown, because the skill's description doesn't mention recipes. This is a skill-only fix.

**Interactivity.** Stay declarative and native. Crew's pinned A2UI Swift package already has everything a servings adjuster or a slider-driven chart needs: a reactive data model (any change rebuilds the tree), two-way bound `Slider`/`TextField`, `formatString` `${…}` interpolation with nested function calls, and a public `FunctionImplementation` hook for custom catalog functions. What's missing is arithmetic (the basic catalog has none) and bindable props on Crew's own `Chart`/`Table`/`KeyValue` (their schemas declare plain types, so bindings don't resolve). Both are Crew-only changes plus skill text, with no Hermes work. A sandboxed WKWebView for model-written HTML/JS is the only way to get "anything goes", but it is slower to generate, a second renderer with its own security surface, and a step backwards in looks. Even Anthropic's HTML visuals don't render on its iOS and Android apps. Defer it.

**Recommended plan (smallest first):**

1. Skill fix: trigger on recipes; components before data model. *Skill only.*
2. Progressive surface rendering. *Crew only* (reverses the "no partial JSON healing" line in PLAN.md Decisions, so it needs a new Decisions line).
3. A `calc` function, plus bindable `Chart`/`Text` values: covers servings scaling and sliders → charts. *Crew + skill.*
4. A `Recipe`/`Ingredients` template component with a built-in servings stepper: faster to write and nicer to use. *Crew + skill.*
5. Optional Hermes levers: `skills.auto_load: [crew-ui]` per profile, `/fast`. *Hermes profile config.*
6. Only if a real need shows up: an `html` fence in a locked-down WKWebView. *Crew + skill.*

## Part 1: Where the time goes today

### How a card is produced and rendered (code)

- **Production.** The bot has the `crew-ui` skill (`Sources/Profile/crew-ui.SKILL.md`, v6, 14,627 bytes), installed by the Rich UI switch. The model decides whether to call `skill_view crew-ui`, then writes prose plus one ```` ```a2ui ```` fence: a JSON array of `createSurface`, optional `updateDataModel`, and `updateComponents` (A2UI v0.9, catalog `crew/v1`). It's plain transcript text, with no tool call for the card itself.
- **Rendering.** `SurfaceStore.sync` (`Sources/Chat/A2UI/SurfaceStore.swift`) skips any turn with `status == .streaming` (`guard turn.status != .streaming …`). It feeds each finished fence whole to the package's `MessageProcessor`. While streaming, `SurfaceBlock` shows "Preparing card…". The fence becomes a code block as soon as it opens, because CommonMark runs an unclosed fence to the end of the document (read from `MarkdownBlocks.swift`, not run in the app).
- **The renderer tolerates partial trees.** `NodeResolver.resolveNode` returns `nil` for a missing child id, and `SurfaceViewModel` rebuilds the tree on every component or data change (`swift/core/Sources/A2UICore/Models/SurfaceViewModel.swift`, `setUpSubscriptions`). Feeding a growing component list is therefore safe.

### Where the time goes

1. **The client waits for the whole surface.** About 22 s of "Preparing card…" on the recipe (6.5 to 29.0 s) and about 12 s on pancakes. This is the largest share, and Crew alone can fix it.
2. **The model writing JSON token by token.** Generation runs at about 57 tok/s, and a recipe card is about 1,300 tokens. Half the characters are structure, and the data model goes first, so the header comes late (13 to 14 s in).
3. **Tool round trips.** Each LLM call costs about 2.5 to 5 s before useful output. `skill_view crew-ui` fired on 2 of 3 card turns in the same session. For the weather card, search and extract plus their LLM turns took 28 s of 36 s. That's inherent to fetching data.
4. **Not triggering at all.** The skill description is "Use for checklists, tables, charts, maps, forms, carousels." A plain recipe prompt didn't match, so the model looked for a `chef` skill instead (1 of 1 tries).

## Part 2: More dynamic, interactive cards

### What Crew's A2UI stack can already do (pinned commit `4ca7353`, 2026-10-13)

- **Spec.** Crew speaks v0.9 (also registered as v0.9.1). The [roadmap](https://a2ui.org/roadmap/) (updated June 2026) lists v0.9.1 as stable, v1.0 as a release candidate targeted at Q4 2026, and the SwiftUI renderer as Alpha with v0.9, v0.9.1 and v1.0 support.
- **Data model and bindings.** `{"path": "/x"}` binds any `Dynamic*` property, and input components write back (two-way). Templates iterate arrays with relative paths. A data change rebuilds the tree, so it's reactive without a round trip (`a2ui_protocol.md` v0.9.1, "Two-way binding", "Reactivity").
- **Functions and expressions.** The basic catalog functions are `required, regex, length, numeric, email, formatString, formatNumber, formatCurrency, formatDate, pluralize, openUrl, and, or, not` (`specification/v0_9/catalogs/basic/catalog.json`). `formatString` interpolates `${/path}`, `${relative}` and nested named-argument calls like `${formatNumber(value:${/x}, …)}`. **There is no arithmetic**, and the expression parser handles only paths, literals and calls (`swift/core/Sources/BasicCatalog/Functions/ExpressionParser.swift`).
- **Custom functions.** These are allowed by spec (`v0_9_1/docs/a2ui_custom_functions.md`) and by the Swift API: `FunctionImplementation { api; evaluate(arguments:context:) }` registered in a `Catalog`. Crew passes `functions: V09BasicCatalog.functions` in `CrewCatalog.swift`, so adding its own is a one-place change.
- **Why Crew's components aren't bindable.** `NodeResolver.classifySchema` decides per property from the component's JSON schema: `$ref` `DynamicNumber`/`DynamicString`/`DynamicValue` is resolved (path or call), while a plain `{"type": "number"}` is a literal. `crewSchema` declares plain types for `Chart`, `Table`, `KeyValue` and the others, which is why the skill says "plain values, no {"path"} bindings".
- **What v1.0 adds** (`specification/v1_0/docs/evolution_guide.md`):
  - inline `components` and `dataModel` in `createSurface`
  - `@path`/`@call` prefixed directives
  - `Slider.steps`
  - `@index`
  - `ValidationResult`
  - `openUrl` gated by `requiresUserActivation`
  - mixable catalogs
  - `callAgentFunction`/`callRendererFunction`: a typed renderer-to-agent RPC, the "server round trip" tier
  - an `instructions` field in catalogs
- **Security constraint for anything Crew adds.** Functions are evaluated during render and on every data change, so they must be pure and side-effect free. The draft [user-initiated functions proposal](https://github.com/a2ui-project/a2ui/blob/main/specification/proposals/user_initiated_functions.md) (2026-08-05) exists because `openUrl` could fire on render.

**Pattern.** The industry splits into (a) declarative data plus a whitelisted catalog plus client-side bindings (A2UI, ChatKit, the template side of Vercel) and (b) sandboxed web code (MCP Apps, ChatGPT apps, Claude visuals, Gemini). Only (a) renders natively, and (b) is slower to generate where numbers exist (Gemini: a minute or more) and weaker on mobile (Claude visuals: web and desktop only). Nobody ships a general expression language in a declarative spec yet. A2UI's answer is "catalog functions", and its Express spec reserves syntax for future math.

### Options for Crew

**A. Declarative reactive bindings plus a small safe calculator (recommended core).** All Crew + skill.

- Register two pure functions in `crew/v1`:
  - `calc(expr: string, …named numeric args) -> number`: a tiny recursive-descent evaluator over `+ - * / ^ ( )`, `min max round floor ceil abs`, numbers and named args. No loops, no strings, no side effects. Limits of 256 chars and depth 32.
  - `series(expr, var, from, to, step) -> [number]`: at most 500 points, for chart data.
- Use them anywhere a `Dynamic*` is accepted, including inside `formatString`.
- Basic `Slider` (bound to `/servings`, `/rate`, …) and `TextField variant:number` already write the data model. Override `Slider` so it snaps to integers when `min`/`max` are integers, because v0.9 has no `steps`.

Servings adjuster in plain A2UI with one Crew function (sketch, unverified):

```json
{"id":"servings","component":"Slider","label":"Servings","min":1,"max":12,"value":{"path":"/servings"}},
{"id":"item","component":"CheckBox","value":{"path":"done"},
 "label":{"call":"formatString","args":{"value":"${formatNumber(value:${calc(expr:'q*s/b', q:${qty}, s:${/servings}, b:${/base})}, maximumFractionDigits:1)} ${unit} ${name}"}}}
```

The data model gains structured `{qty, unit, name}`, which the skill must teach. Cost: more tokens per ingredient, and fiddly syntax for the model.

**B. Native chart bound to the data model.** Crew + skill.

- Change `Chart`'s schema so `labels`, `values` and `series[].values` accept `DynamicValue` (a path or a `call`). Keep plain arrays valid so old cards still render.
- Example: `"values": {"call":"series","args":{"expr":"p*(1+r/100)^t","var":"t","from":0,"to":{"path":"/years"},"step":1,"p":{"path":"/principal"},"r":{"path":"/rate"}}}` with three Sliders above it.
- Swift Charts re-renders on each data change; animate with `.animation(.smooth, value:)`.
- Needs a short spike to confirm `resolveDynamicValueBinding` returns arrays through Crew's `node.array(for:)`. That's a guess from reading `NodeResolver.swift`, not run.

**C. Template components (best UX for the common case).** Crew + skill.

- `Ingredients` (or a full `Recipe`): `{"servings": {"path":"/servings"}, "baseServings": 4, "groups": [{"title":"Meatballs","items":[{"qty":250,"unit":"g","name":"beef mince"}]}]}`.
- It draws a HIG `Stepper` for servings and scales quantities natively, with fractions (½, ¼), sensible rounding and pluralisation.
- The model writes less than in A (speed lever #4) and can't get the math wrong.
- This is the Vercel/ChatKit "model fills data, app owns UI" pattern.

**D. Sandboxed WKWebView fallback.** Crew + skill. Defer.

- The model writes an ```` ```html ```` fence (self-contained, Claude-visuals style). Hermes' Desktop-only `::preview{file=}` needs host file fetches that can vanish from history (`docs/generative-ui.md` §2).
- Lockdown:
  - `WKWebsiteDataStore.nonPersistent()`
  - a `WKContentRuleList` blocking all network loads
  - navigation cancelled in `decidePolicyFor`
  - no `allowsContentJavaScript` for remote content
  - one `WKScriptMessageHandler` `send(text)` mapped to the hidden `prompt.submit`, on a user gesture only
  - a height bridge and a size cap
- Costs:
  - Generation is several times larger than JSON (guess).
  - A second renderer inside a `LazyVStack`, which hurts scroll performance.
  - It looks like a web page in a Liquid Glass app.
  - Hermex/Desktop show it as code.
  - Anthropic doesn't render its own HTML visuals on mobile.

**E. Server round trips via actions.** Already works: a button sends `<a2ui-action>` as a hidden turn and the bot replies with `updateDataModel`. It's fine for "recompute with real data", but at 3 to 30 s per tap it's wrong for sliders. A2UI v1.0's `callAgentFunction` would formalise it, but Hermes has no endpoint for it, so it would need Hermes core work. Not recommended.

### Recommendation and layered plan

Each step stands alone and ships behind the existing Rich UI skill version bump.

1. **Skill v7: triggers and ordering.** *Skill only.* Add recipes to the description (57-char string above), and put `updateComponents` before `updateDataModel` in every example. No Crew change.
2. **Progressive rendering.** *Crew only.* Partial-JSON healing for the open ```` ```a2ui ```` fence (port of the Python SDK's reader), render while streaming, disabled until complete. Add a PLAN.md Decisions line replacing "render when the fence closes … no partial JSON healing".
3. **`calc` + `series` functions, bindable `Chart` and `Text`.** *Crew + skill* (teach one calculator example). Covers "charts from sliders" and a basic servings adjuster. Unit tests evaluate fixtures with slider values changed.
4. **`Ingredients`/`Recipe` template with a servings Stepper.** *Crew + skill.* The polished servings adjuster plus fewer tokens.
5. **Hermes levers.** *Hermes profile config; ask the user first.* `skills.auto_load: [crew-ui]` set by the Rich UI switch (`PUT /api/config?profile=`), and optionally exposing `/fast`.
6. **A2UI v1.0 migration** when it goes final (Q4 2026 target). *Crew + skill.* Inline `createSurface`, `@path`/`@call`, `Slider.steps`.
7. **WKWebView `html` fence.** *Crew + skill.* Only for a concrete need that steps 3 and 4 can't express.

### Gaps and open questions

- **Card state isn't persisted.** Slider and checkbox state lives only in the in-memory `MessageProcessor` for that `ChatView`. Ingest replays only the transcript, so a reload or a second device shows the original values (read from `SurfaceStore.swift`; not tested). Interactive cards make this more visible. It may overlap with the concurrent pinned-cards work, so it's left out of this plan on purpose.
- **Small sample.** Measurements are n=1 per prompt on one model; tok/s and tool timings vary per run. Re-run `Tests/chat_probe/run.sh a2ui` with `A2UI_PROMPT=…` to repeat. The analyzer scripts are in this scratchpad (`timeline.py`, `components.py`).
- **Unverified items.** `skills.auto_load` was read in the local Hermes checkout (`ae3f9f9`, 2026-10-13), not on the server's version. `/fast` provider support for `gpt-6.1-sol` is unknown.
