## TL;DR

**2.0 is not tag-ready.** Six new blockers, none of them fixed by any of the sixteen in-flight PRs. Four of those sixteen PRs carry their own regressions. Two PRs collide in a way that silently destroys one of them if merged carelessly. Independently, #146 alone blocks the tag — `ash.config.version` still reads `2.0-beta1`.

The good news: **no version-specific defect exists** anywhere in 14 → 19beta2. Every confirmed finding is version-independent SQL logic. The risk in this release is logic, not portability.

## 1. New blockers (not among the 21 known issues)

| ID | What breaks | Where |
|---|---|---|
| **B1** | **`ash.compare()` fabricates regressions on byte-identical load.** `aas()`/`timeline()` upgrade a `rollup_1h` read to minute grain via `rollup_1h_minutes`; `top()` never does, and `compare()` delegates both windows to `top()`. That is the textbook latency-regression signature, on unchanged load, and `compare()` has no `source` column to reveal it. `compare(dimension => null)` reports 600 on both sides — the two modes of one function contradict each other. | `sql/ash-install.sql:4470`, `:4608`, `:4699-4707` |
| **B2** | **Two of pg_ash's own cron jobs deadlock each other.** `rollup_cleanup()` deletes the rows `rotate()`'s completeness gate (the #81 guard) requires. Rotation then fails permanently and `ash.sample` grows unbounded — the exact failure the ring exists to prevent. Because `rotate()` returns text on the failure path, **pg_cron records SUCCESS** and `ash.status()` exposes no failure metric. Reachable with stock 30-day retention via the README's own "increase raw retention" runbook. | `:1428` vs `:3258` vs `:2943` |

Passing `ash.status().raw_retention_start` *still* raises (the reader floors `since` to the minute before the guard runs). Following the error's own printed advice returns **0 rows**. With `ash.start()`'s 1s default, `raw_start` lands mid-minute 59/60 of the time — this is the default path, not an edge case. | `:3527`, `:3430` |

**#131 and #150 both rewrite the same four single lines** — the catalog comments for `aas`/`timeline`/`top`/`compare` at `:5755-5764`. A careless `-X ours` / `-X theirs` **silently discards one PR's entire documented contract with no conflict marker to notice.** #131 also inserts its hour-alignment guard at `:4472`, *inside* #150's replaced `:4452-4507` block, and #150 changes which calls can reach that guard at all. **This merge must be hand-derived, never resolved automatically.**

Other collisions: #123↔#150 splices two rewordings together and git merges it *clean* (re-read after merging). In `.github/workflows/test.yml`: #123↔#150 (add/add at line 3712), #129↔#152 (taking one side silently reverts only a rename), #140↔#152, and #140↔#159 (mixed checkout pin, not textual).

### Test-quality red flags

Four PRs ship an assertion that passes with the bug present:

- **#129** — `assert v_slots = array[0, 2]` passes on unpatched `main`; N=3 is precisely the value where the old and new formulas agree. The genuinely novel behaviour (N>3) has no coverage.
- **#131** — CI is green on a regression that hard-errors the documented investigation flow, because the test step contains **no zero-argument call anywhere**.
- **#150** — the riskiest change (the `v_exact_query` widening) has no test at all.
- **#123** — the 553× perf cliff has no assertion.

**#135 is the counterexample and the shape to aim for:** it exists to convert a gate that *could not fail* into one that does, and it was mutation-tested three ways.

## 3. Release gate — what is still uncovered

`CLAUDE.md` demands a fully clean comprehensive pass before tagging. Honest accounting of what these audits did **not** cover:

- **Fresh install + regression per PG major** — missing entirely for **15, 16, 17**; cron path missing for **19beta2**. (`demos/Dockerfile` does `FROM postgres:19`, which does not exist — only `postgres:19beta2`.)
- **Upgrade chain + idempotent re-apply + schema equivalence per major** — run only on PG 18.3. This surfaced a gap in the CI check itself: the COL snapshot orders by `attname` and omits `attnum`, so it is blind to column-ordinal divergence.
- **Degraded mode without `pg_stat_statements`** — zero evidence. No-cron got heavy incidental coverage; no-pgss got none.
- **New 2.0 features exercised behaviourally, one per surface** — the audit hunted defects; it did not run a systematic per-feature pass.
- **Demo/docs reproducibility (`make -C demos record`)** — not covered, and the regenerated GIF has had **no human visual review**, which the merge rules require.
- **Three known release blockers remain open and independently gate the tag:** #146 (prerelease stamping — `ash.config.version` still reads `2.0-beta1`; you cannot tag 2.0 with a beta stamp), #137 (design blocker), #139 (benchmark suite).
- **REV review + explicit owner approval per PR.** Green CI is not merge approval.

Per the gate: any finding means file, fix, and re-run the **whole** suite. A partial re-run does not satisfy it.

## 4. The visual harness (replaces `demos/`)

A replacement for `demos/` was built and runs end to end: `make all` → **161 s from nothing** (database, seed, 8 stills, GIF + MP4), versus ~9 minutes before, **with no Docker requirement**.

Why the old one had to go: `demos/record.sh` hard-requires a local Docker daemon *and* a Docker Hub pull, which is why assets could only ever be regenerated on one laptop. It also used blind `sleep 3.8`-style choreography, and still installs from `devel/sql/ash-install.sql`, which the 2.0 release stamp emptied (#138).

Architecture — deliberately two mechanisms:

- **Stills** → a stdlib-only ANSI→SVG renderer. No terminal, no browser, no timing; byte-identical output, so images are diffable in a PR and `make check` is a real gate.
- **Animation** → tmux + asciinema + agg, with an **OSC-2 prompt sentinel** replacing blind sleeps. The escape rides the same pty byte stream as the output, so it is non-racy by construction (verified 40/40 on random output sizes).

VHS was evaluated and **rejected as an engine** — it drives headless Chromium, and adopting a browser-dependent engine to fix an "only runs on my laptop" problem reintroduces the defect. Its visual spec (chrome, geometry, palette) was adopted wholesale.

Both halves share one seeder, one frozen incident window, one theme and one vendored font, so stills and GIF show digit-identical numbers while remaining independently re-runnable.

**The harness is on branch `agent/visual-harness` and open as draft PR #178.** Verified to work from its real in-repo location: `make -C demos doctor` resolves all three tiers plus the local and Docker backends, and `make -C demos check` re-renders all 8 fixtures byte-identically.

Unproven (its own honest list):

- **Never run on Linux/GNU userland**, and `demo.yml` has never executed. Written to the portability rules (no `sed -i`, no `date -d`, bash 3.2-safe) and clean under BSD userland, but the first Linux run is a genuine risk.
- The **pg_cron scheduling path is exercised by nobody** — the harness drives `ash.take_sample()` itself.
- Only PG 18 tested (`ASH_PG_MAJOR=14 ASH_BACKEND=docker make stills` is the whole command for others).
- `make all` is 161 s, not the 120 s target; 76 s of that is a real-time recording.
- Rendered SQL shows unexpanded `$STORM_SINCE` / `:'UNTIL'` — keeps images deterministic but is not copy-pasteable. `now() - interval '30 minutes'` would read better.

## 5. Recommended environment: **x86_64 Linux**

1. **That is where the unproven risk lives.** The harness ran only on macOS; its Linux/GNU path and `demo.yml` have never executed. Working on Linux surfaces those on day one rather than at merge time.
2. **CI is `ubuntu-latest`,** and `demo.yml` downloads `agg-x86_64-unknown-linux-gnu` — that URL is wrong on arm64 Linux *and* on macOS. x86_64 specifically.
3. **pg_cron works natively.** On the maintainer's Mac the cluster pins `cron.database_name`, so the cron path is only reachable through Docker.
4. **Native Docker** — the still-missing PG 15/16/17 matrix runs far faster without a VM.

Caveat: macOS (bash 3.2 + BSD userland) was the stricter authoring environment, so macOS-clean is usually Linux-clean — but GNU/BSD differences cut both ways. **Smoke the harness on macOS once before shipping**, since that is the maintainer's machine.

Setup: any PG 14–19 via Docker, plus one local cluster where you control `cron.database_name`. Needed CLI: `tmux`, `asciinema`, `agg`, `ffmpeg`, `gifsicle`, `psql`, `pgbench`, `docker`, `gh`, `python3`.
