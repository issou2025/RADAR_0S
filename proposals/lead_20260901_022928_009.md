# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**.gitignore: unanchored directory patterns silently swallow unrelated trees, and the kit offers no guidance but "skip"**

*Project description:*
## What's wrong

The kit's only guidance on generating a project `.gitignore` at scaffold time is two lines: a clause in the repo-creation checklist telling the agent to add "a sensible `.gitignore`," and an anti-pattern warning against generating "a 500-line `.gitignore` with every possible language." Neither says anything about how generated `.gitignore` content actually behaves — specifically, that a bare directory pattern (`lib/`, `build/`, `target/`) matches at **any depth**, so a per-language section silently ignores files in a completely unrelated tree. The only alternative the kit offers to "don't paste every language" is "pick one stack hint… or skip" — a *narrower* file, never a *scoped* one.

This is not a github-issues-only path. `github_only_profile.md` is also the repo-provisioning reference when planning = `linear` (`linear_planning.md:32`: "**GitHub repo provisioning** — same as `github_only_profile.md` stage 1 steps 1–3 and 5; skip the project board step"), so the same two lines govern both backends.

Two things this shows that a reviewer would not guess:

- **Line 87 `lib/` sits in the Python section** (setuptools block: `downloads/`, `eggs/`, `lib/`, `lib64/`, `parts/`, `sdist/`, `var/`, `wheels/`) — and `lib/` is the canonical source directory of every Dart/Flutter package. A Python build-artifact line was set to ignore the project's own Flutter source tree.
- **Line 146 `target/` sits under the Python section's `# PyBuilder` block**, not the Rust section. A reviewer auditing "the Rust section" for Rust-owned paths would not find the line that ignores `target/`.

**The repair.** `echosphere/.gitignore` now carries this header, verbatim:

```
# Based on https://www.toptal.com/developers/gitignore/api/dotenv,rust,python,flutter
# Diverged at ops M1 R5 (ECH-21): the template's unanchored directory patterns
# swallow new-tree files (proven: `lib/` ignored modeling/lib/*.jl). The Flutter
# section is scoped to app/**, the Python section to bridge/** (their future
# homes per docs/ARCHITECTURE.md § Workspace map), and the remainder anchored.
```

The fix landed as a squashed-in commit (`chore(ops): anchor .gitignore template sections to their future homes`, `[ECH-21 AC2]`) inside squash-merge `047b0a7` — *"chore(ops): close bootstrap residuals — hygiene files, security surfaces, evidence (#16)"*. Its body records the pins it asserted: `modeling/lib/x.jl` un-ignored; `target/x`, `firmware/target/x`, `.env` still ignored; `app/lib/main.dart` and `bridge/src/*.py` not swallowed.

## Why it matters

An unanchored generated `.gitignore` fails by omission. A file matched by a stray `lib/` or `target/` line never appears in `git status`, never gets staged, and never enters a diff — so nothing downstream reports it. That includes the cascade's own review surface: `pr-review.md`'s rubric is defined entirely over the diff (it pre-filters a changed-path list and hands the same list to every reviewer), and a file that was never tracked is never in one. There is no red build, no failing check, no review finding.

**Scope honestly: in echosphere no file was actually lost.** No `.jl` file was ever committed to that repo, and `app/` and `modeling/lib/` are still-planned trees — `modeling/lib/x.jl` was a *probe path* used to prove the behavior, not a tree that went missing. The trap was caught proactively, mid-cascade, because someone thought to test it. That is the argument for fixing it in the kit rather than against: the generated file was already on a collision course with the project's primary Flutter source directory, from bootstrap, and the only thing that stopped it was one operator's curiosity at ops M1 R5. The next run gets the same generated file and may not probe.

The cost asymmetry is what makes it worth a rule: anchoring costs one character per line at generation time; discovering the omission later costs a mid-cascade repair, and discovering it after content lands costs whatever was silently never committed.

## Proposed change

**`.claude/skills/scaffold/references/github_only_profile.md`** — the two lines above.

- **Line 77's anti-pattern bullet** carries the real fix. The guidance stops at "pick one stack hint… generate that"; extend it to say the alternative to a 500-line `.gitignore` is a **scoped** one, not merely a narrower one: anchor every directory pattern (`/build/`, not `build/`), leave only genuinely any-depth entries (`.env`, editor/OS junk) unanchored and mark them as deliberate in a comment. Worth naming the cross-section trap explicitly — the offending line is usually in a *different* language's section than the tree it swallows.
- **Line 18's checklist clause** should point at that bullet rather than restating it.

One ordering constraint the fix must respect: **scaffold runs before blueprint**, so at the moment the `.gitignore` is generated there is no `ARCHITECTURE.md` and no declared tree layout. So the two halves of the discipline land in different phases — *anchoring* needs no tree knowledge and belongs at scaffold; *scoping a language section to that language's directory home* needs a layout and belongs later. (Note also that the kit's architecture template names that section `## Project Structure`, not "Workspace map" — the latter is a heading `echosphere` coined locally — and the template marks it optional: "ONLY if non-obvious." So the rule should not assume a workspace map exists.)

**`.claude/rules/cbk-conventions.md`** — add a portable section stating the discipline: anchor by default; mark deliberate any-depth exceptions in a comment; scope per-language sections to that language's directory home once one is declared; and require a commit body that changes a `.gitignore` to state its pin assertions (which paths became un-ignored, which stayed ignored), since a `.gitignore` diff is otherwise unreviewable.

There is working prior art to lift from: the vendored copy in the `you-are-hear` project already carries exactly this section — `## .gitignore anchoring trap`, sitting between `## Dependency settle-window` (line 299) and `## Methodology` (line 347). The kit's own `cbk-conventions.md` has that identical adjacency (settle-window at 299, Methodology at 320) and zero occurrences of "gitignore," so the section drops into the same slot unchanged. That copy also carries a Dart/Flutter-specific note worth keeping — an unanchored `lib/` is catastrophic in that ecosystem.

**`.claude/skills/scaffold/references/bootstrap_checklist_template.md:20`** — the line "created with README, .gitignore, MIT license" should point at the new conventions section, so the checklist doesn't read as "any `.gitignore` counts."

No reviewer sweep is needed: `grep -rn "gitignore" -i .claude/agents/` exits 1, so no shipped reviewer restates this guidance. Worth recording that fact *inside* the new section, since the next hygiene-focused reviewer author will otherwise have no cue to pick it up.
