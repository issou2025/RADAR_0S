## What

Make every `onetaskgraph` verb that fails under machine output (`--json`, or `--set output=json`) say
**why** it failed in a document a caller can branch on. Today it cannot: `crates/onetaskgraph/src/main.rs`
turns every failure into one prose line on stderr (`fail()` prints `onetaskgraph: <message>`) and exit
`1`. The source's own error kinds — `SourceError` in `crates/onetaskgraph-plugin-api/src/error.rs`:
`config`, `auth`, `refused`, `rate-limited`, `unavailable`, `malformed` — exist inside the store and
never reach a caller of a failing command. `onepipeline`'s settlement write-back is that caller. It spawns
`project show`, `task list` and `project copy`, and it cannot tell a refusal that will never change,
like `status unknown is disabled for source plans; set status_mapping.unknown …`, from a rate limit or
an unreachable store. So today it retries both on a timer, forever.

### The contract this node lands

This is stated literally, once. `op-refusal-not-retried` and `op-incremental-projection` in
`onepipeline` restate it from here.

**When.** A verb run with machine output that exits `1` (`EXIT_FAILURE`) writes **exactly one JSON
document to stdout**, and nothing else goes to stdout. The stderr line and the exit code stay exactly
what they are today. A usage failure (exit `2`: an unknown flag, or a malformed `--set`) writes no
document. That covers every verb whose failure passes through the machine-output path, including
`project show`, `task list`, `task show`, `project copy`, `task copy` and `document copy`.

**Shape.**

```json
{"failure": {"class": "refused", "kind": "refused", "source": "plans",
             "message": "the source refused the request: status unknown is disabled for source plans; …",
             "retry_after_seconds": null}}
```

- `class`, a string from a **closed** vocabulary:
  - `"refused"` means the store or a source declined the request, and repeating it unchanged cannot
    alter the answer;
  - `"transient"` means the request got no ruling a caller could act on.
- `kind`, a string from an **open** vocabulary. When a source's error caused the failure, it is that
  `SourceError`'s own `kind`, verbatim. Otherwise it is the store's own name for the failure in
  kebab-case, for example `no-such-item`, `stale-origin`, `unknown-source`, `not-writable`.
- `source`: the configured source name the failure came from, or `null` when none did.
- `message`: the same text the stderr line carries, without its `onetaskgraph: ` prefix.
- `retry_after_seconds`: a non-negative integer when a rate limit named a wait, otherwise `null`.

**The class mapping, made once, in the store.**

| cause | class |
| --- | --- |
| `SourceError::RateLimited` | `transient` |
| `SourceError::Unavailable` | `transient` |
| `SourceError::Refused`, `Config`, `Auth`, `Malformed` | `refused` |
| any failure no source caused (an id that names nothing, a stale origin, an unknown or unwritable source, a bad page token …) | `refused` |
| a failure that wraps another (a destination that could not be built, a copy that could not be undone) | the class and kind of the failure it wraps |

**Partial answers keep their shape.** Exit `4` already writes the query response with an `errors`
array, and each entry carries the source's `SourceError`. Each entry of that array gains the same
`class` field, computed by the same mapping, and nothing else about exit `4` changes. A caller then
classifies a partial answer and a failure the same way.

**One source for every copy of this.** The document is a Rust type deriving `JsonSchema`, emitted as a
root of the bundle `onetaskgraph schema` prints, which is what both SDKs are generated from and what
`crates/onetaskgraph/tests/e2e/machine.rs` validates output against. The mapping is one function, and
every caller of it (the failure document and the partial `errors` entries) calls that function rather
than restating the table. `README.md`'s *Exit codes* section documents the document and points at the
schema root rather than restating the fields.

Read this repository's `AGENTS.md`, `crates/AGENTS.md` and `sdks/AGENTS.md` first; each is binding.
Releases are cut by `release-plz` from the squash subject, so this node's title is a `feat`.

## Why

The user keeps running out of GitHub's GraphQL allowance, and the settlement write-back is what spends
it: *"I seem to keep running out of GitHub GraphQL quota and agents are saying it's the write-back
onetaskgraph copy to GitHub Projects. I thought we already optimized it."* The user agreed that a store
**refusal** should not be retried on a timer. Measured on this host, one write-back attempt costs about
94 points, and a refused projection retried every 60 seconds costs about 5,600 points an hour from one run
holding one failed node. Four runs did exactly that, for up to eleven hours. The board never receives
the refused write either way, so those retries bought nothing. The allowance has to stay free for the
reads that matter: `just plans`, `just check-plan`, `just copy-plan`, and a second run on the same
token. The engine can stop retrying only once the store says which failures are refusals, and the brief
puts that classification at the boundary that knows it.

## Acceptance criteria

- A verb that exits `1` while JSON output is selected — by `--json`, by `--output json`, or by the
  configuration's own output setting through `--set` or its `ONETASKGRAPH_` variable — writes exactly
  one JSON document to stdout, and nothing else; a verb whose output is text writes none.
  The document is an object whose single member `failure` holds:
  - `class`: `"refused"` or `"transient"`;
  - `kind`: the causing `SourceError`'s own kind, or the store's kebab-case name for a failure no source
    caused;
  - `source`: the configured source name, or `null`;
  - `message`: the stderr text without its `onetaskgraph: ` prefix;
  - `retry_after_seconds`: a non-negative integer, or `null`.

  Its stderr line and exit code are what they were before this change. A usage failure (exit `2`)
  writes no document.
- `class` follows the mapping above for every row: `rate-limited` and `unavailable` are `transient`;
  `refused`, `config`, `auth`, `malformed` and every failure no source caused are `refused`; a wrapping
  failure takes the class and kind of the one it wraps. The mapping is declared in one function that
  both the failure document and the partial answer's `errors` entries use.
- Each entry of an exit-`4` partial answer's `errors` array carries `class`, and that response is
  otherwise unchanged.
- The failure document is a root of the bundle `onetaskgraph schema` prints. The generated SDK models
  reflect it wherever this repository generates them from that bundle, and the repository's contract
  and SDK drift checks agree with the bundle.
- End-to-end tests spawn the compiled binary and assert its exit code, stdout and stderr for at least:
  - a refusal from a real source: a `project copy` into a `github-projects` fixture board whose
    `status_mapping` disables the status an item carries, answering `class: "refused"`;
  - a rate-limited answer from the fixture board's limiter, answering `class: "transient"` and the
    wait, when the limiter names one;
  - a source that cannot be reached, answering `class: "transient"`;
  - a failure no source caused, such as an id naming nothing, answering `class: "refused"`;
  - a partial `--json` read, whose `errors` entries carry `class`.

  Each of those stdout documents validates against the schema the binary itself emits, and at least
  one of the cases is driven under each of the three ways JSON output is selected, so a selection
  mode that still answers prose on failure fails here.
- `README.md` documents the failure document beside the exit codes, pointing at its schema root.
- The checks that exercise this change are green over the finished tree: the `crates/onetaskgraph`
  end-to-end modules this node adds or touches (including `machine.rs` and `failures.rs`), the unit
  tests of the modules it touches, the protocol and contract checks that read the schema bundle, the
  SDK tests over any regenerated models, clippy over all targets, and the judged lint over this node's
  diff. Nothing is skipped, and every suppression this node's diff writes is site-scoped, answers a rule genuinely misapplied at that site, and carries its reason, as the operational appendix permits — none silences a finding the change has not answered.
- Every claim the dispatch makes about the finished work, including what it verified and the evidence
  for it, is true of the tree as it finally stands.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.
