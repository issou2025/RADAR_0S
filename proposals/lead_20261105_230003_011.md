## Summary

A file attached to a shared Markdown note or shown on a shared canvas must be available to every current member, on desktop and phone. The file bytes stay end-to-end encrypted. The server stores ciphertext in a share-scoped blob store and serves it only to accepted members of that share.

Each attachment gets a fresh random file key. The file key encrypts the file and is wrapped to the shared note key for each note epoch. When membership changes, the owner rotates the note key as today and the remaining members receive wraps for the current epoch. Removing a member stops future server access; it cannot take back a file the member already downloaded.

Adding a file uploads a separate shared copy. Existing private attachments do not become shared silently. Ordinary files stay capped at 10 MiB; PDFs whose bytes begin with %PDF- may be up to 50 MiB, as in #43. The shared canvas refusal is removed only after the member-checked file path works.

Locked notes remain unshareable. If a member later puts a shared attachment in a locked note, Kanso makes a new private, sealed copy with a new file ID under the rule accepted in #44. It never puts a shared file-key wrap in a locked note.

## How it works for the user

### Sharing attachments already linked from a shared note

A shared note can already contain private file links from before this feature. Other members cannot read those account-private files. When the owner opens the shared note after upgrading, Kanso shows:

> **Attachments to review**
> This note links to 3 files that haven't been shared. Choose which files to share with everyone in this note.
> [Review files]

The review lists each file's name, type and size, plus whether its bytes are present on this device. Nothing is uploaded until the owner chooses **Share selected**. **Keep private** closes the review and leaves the existing links as unavailable placeholders to other members. The owner can return to the review later.

After confirmation, Kanso encrypts and uploads each selected file, then replaces its private file ID with a new share-scoped file ID in the shared note or canvas. It does not delete the owner's private copy. If the owner has no bytes on this device, the row says:

> The file isn't on this device. Open Kanso on a device that has it, then try again.

On a phone the same review and choice appear in the shared note. The rows show per-file upload progress and can be retried. Whether iOS and Android can continue these uploads after Kanso is suspended is *(unverified)* and must be settled by device testing.

### Adding a file from desktop or phone

In a shared Markdown note, **Attach file** opens the normal file picker. In a shared canvas, **Add image** or **Add file** adds a file card. Kanso checks the actual bytes and type before upload. It refuses an ordinary file over 10 MiB and a valid PDF over 50 MiB:

> This file is 12 MB. Ordinary attachments can be up to 10 MB.

> This PDF is 52 MB. PDFs can be up to 50 MB.

The member sees the upload progress. Kanso encrypts the file, uploads its ciphertext, and only then commits the attachment record and reference to the shared note. If the connection drops, the attachment remains **Waiting to upload** on the adding device and can be retried. The upload starts again from the beginning. It is not presented to other members as a complete file before the server has it.

For an allowed add, the shared editor inserts the existing Markdown attachment link form with a share-scoped file ID, or adds that ID to the canvas file card. Other members see the attachment arrive with the shared-note update.

Who may add files is an owner decision below. The UI must not imply that a View or Comment member can upload.

### Opening a file on another member's device

Text edits continue syncing if a file is not downloaded. A missing image or card shows a placeholder with progress:

> **Still arriving**
> 3.2 MB of 8.4 MB
> [Retry]

A transient error says:

> Couldn't download this file. Check your connection and try again.
> [Retry]

Kanso downloads in the background while the shared note is open, verifies each encrypted chunk, decrypts only after authentication succeeds, and marks the file ready only when the complete file verifies. Partial or malformed bytes are never shown. Desktop and phone use the same states. Tapping an image opens the image viewer. Tapping a PDF opens the PDF reader. Other files show their name and size and can be handed to another app using the existing attachment sheet.

If the user is offline, the last downloaded copy remains available. A new file shows **Waiting for a connection**. Reconnecting retries without blocking text and canvas sync. A removed member receives no new file bytes; the normal not-found response does not reveal whether a particular share file still exists.

### Removing a link, stopping a share, or deleting a note

Removing one Markdown link or canvas card removes only that reference. When no live reference in the shared note or canvas points to the file, Kanso writes a tombstone. Other members stop seeing it as soon as that update arrives; the server then deletes the ciphertext. Kanso does not delete an object that is still referenced elsewhere in that same share.

Stopping the share or permanently deleting its note makes every blob unavailable at once and queues all its server objects for deletion. Kanso's server-side cleanup may finish asynchronously. Members who already downloaded or exported a copy may keep it; neither the server nor the owner can recall it. The proposed Trash behavior is to stop sharing immediately and require a new share if the note is restored; the owner must answer question 11.

### Member changes

When the owner adds a member, the shared-note epoch changes as it does today. The owner's device unwraps each live file key and wraps it to the new note key for the new epoch. The new member can open files that are still linked. An invited, not-yet-accepted person cannot download them.

When the owner removes a member, the new epoch contains wraps for the remaining members only. The server checks current accepted membership for every download and refuses the removed member. A member may keep any bytes and keys already downloaded. Whether Kanso should also re-encrypt every live file after removal is an owner question below.

### Locked notes

The existing message remains:

> Locked notes, and notes in locked notebooks, can't be shared.

A locked attachment cannot be added to a shared note while it is sealed. The user must unlock it and choose to share a copy. If a shared attachment is later linked from a locked note, Kanso downloads it while the member still has access, creates a new file ID, seals a copy with the locked note's file-key flow, and changes the locked note's link to that new ID. The locked note stores no share ID, NoteKey, shared FileKey, or shared-file wrap. The confirmation says:

> This attachment will be copied into the locked note.

### The pieces to add

#### File identities, keys and encrypted data

Use random share-scoped IDs in the existing file:<22 URL-safe characters> wire shape (cloud/src/protocol.ts:41-54). The local reference can keep the existing file:… form, but resolution must use the containing share ID as part of the key. The same file ID must never resolve through the private account-file route. Keep a separate local shared-blob cache and index; do not insert shared attachments into the private account sync documents or private blobs table.

Add a versioned shared-file manifest map as a root Yrs map in each encrypted shared note or canvas CRDT, not as a JSON fence in Markdown. A proposed entry is:

    file_id -> {
      v: 1,
      name: filename,
      content_type: MIME type,
      plaintext_size: u64,
      chunk_size: 65536,
      chunk_count: u32,
      file_key_wraps: { decimal_epoch: base64url(73-byte wrap) },
      OCR: optional extracted text, if the owner approves encrypted OCR sync
    }

The manifest, filename, type, size, OCR text and annotation metadata travel only inside collaboration envelopes encrypted with NoteKey. Names and types are therefore not exposed to the server.

For each file, generate an independent random 32-byte FileKey. The proposed v1 container is:

    header = 0x01 || u32be(65536) || nonce_prefix(16 random bytes)
    chunk_count = floor(plaintext_size / 65536) + 1
    encrypted_chunk_i = XChaCha20-Poly1305(FileKey, nonce_prefix || u64be(i), AAD, padded_plaintext_chunk)
    AAD = "kanso-shared-file" || 0x01 || lp(share_id) || lp(file_id) || u64be(plaintext_size) || u32be(65536) || u32be(chunk_count) || u32be(i) || u32be(logical_chunk_length)

Each nonce is the 16 random prefix bytes followed by the big-endian chunk index. All chunks before the last carry 65,536 bytes. The final chunk is padded with zero bytes to the next 4 KiB boundary; an empty final chunk pads to 4 KiB. Exact-size multiples of 65,536 include one additional padded final chunk. The encrypted manifest gives members the exact plaintext length and chunk count. The server sees the chunk count and ciphertext size, which reveal an approximate size but not the exact length or MIME type. Each chunk authenticates the file identity, total size, chunk size, index and count, so truncation, reordering and cross-file substitution fail verification. A full ciphertext SHA-256 digest detects transport errors; it is not a plaintext content ID. The server checks the framing, byte counts and digest but cannot authenticate the plaintext. Here lp uses the existing two-byte big-endian length prefix.

Wrap the FileKey with XChaCha20-Poly1305 under a separately derived key:

    wrap_key = HKDF-SHA256(NoteKey[epoch], salt = lp(share_id) || lp(file_id) || u32be(epoch), info = "kanso/v1/shared-file-key")
    wrap_AAD = "kanso-shared-file-key" || 0x01 || lp(share_id) || lp(file_id) || u32be(epoch)
    wrap = 0x01 || nonce(24 random bytes) || XChaCha20-Poly1305(wrap_key, nonce, wrap_AAD, FileKey)

Do not reuse the lock-file-key AAD or public ShareKey from crates/kanso-sync/src/share.rs:100-125. The encrypted manifest carries the epoch-specific wrap. On each epoch rotation, rewrap all live FileKeys to the new NoteKey before committing the new-epoch snapshot. Removed members have old wraps but no current server authorization; remaining members receive the new wraps.

#### Shared-file protocol and server storage

Add share-scoped blob routes under /v2/collab/shares/{share_id}/files/{file_id}. Proposed operations:

| Operation | Behaviour |
|---|---|
| PUT /files/{file_id} | Stream one complete encrypted container to a staging object; require an accepted member and the chosen add role. Enforce the ciphertext maximum, digest and quota. A retry with the same ID and digest is idempotent; a different digest is refused. |
| GET /files/{file_id} | Stream the complete encrypted object only to a currently accepted member. |
| DELETE /files/{file_id} | Idempotently tombstone an unlinked file. A tombstoned ID cannot be reused. |

These routes are proposed, not current endpoints. Each request authenticates the account/device and verifies accepted membership and active share status; writes also check the current epoch and approved add role. After the streamed PUT, recheck authorization and quota before marking the object complete, so a member removed mid-upload cannot publish it. Never return an object to an invitation or non-member. Return the same not-found response for a non-member and an absent file.

Store blobs in a share-specific R2 namespace or binding, separate from account files. Use share ID plus random file ID as the object key; never expose a public R2 URL. Store only ciphertext, its length and digest, the opaque IDs, the uploader account/device, share owner for quota, and timestamps. The server sees the existing membership and role list, file identifiers, ciphertext sizes, uploader, request times and quota use. It does not see file names, MIME types, plaintext, OCR, PDF text or keys.

No cross-share content-hash deduplication. Repeated references inside one note reuse the same file ID. A copy into another share gets a new ID, FileKey and ciphertext. Random IDs and per-file encryption avoid revealing that two shares contain equal files.

Proposed: attribute shared bytes and count to the share owner's file quota, kept separate from the owner's private file documents but included in displayed account file use. Charge only completed ciphertext to storage quota; discard and expire staging objects after failed uploads. Enforce per-share and per-owner storage limits and upload rate limits. Owner quota attribution is still awaiting the owner's choice.

The ordinary 10 MiB limit is checked on the client from the actual bytes. The server cannot know whether end-to-end encrypted bytes are a PDF or an ordinary file. It can enforce the maximum ciphertext size needed for a 50 MiB PDF plus the container overhead, and it can apply share and account quotas. A modified client could upload an ordinary file larger than 10 MiB but no larger than that PDF ceiling. This limitation must be visible in the owner decision below.

#### Sync and local storage

Keep file bytes out of the shared-note text update stream. A file upload completes before the CRDT publishes its manifest reference. A crash between upload and reference leaves an unreferenced object for garbage collection. On download, sync reads the encrypted manifest, schedules referenced files, fetches the encrypted container, verifies and decrypts each chunk, then atomically installs a complete local cached file. An interrupted or corrupt transfer is discarded and retried from the beginning; no partial file is shown. A failed file download never stops shared text/canvas sync.

Use a separate local shared-file cache keyed by share ID and file ID. Store the encrypted container at rest; unwrap the FileKey from the existing local collab key vault only when opening, keep plaintext temporary and app-private, and delete temporary plaintext when the viewer closes. Mark file state as waiting, downloading, ready, failed or revoked; share progress through the Rust/mobile bridge. Do not report local attachment quota as shared server usage. A removed member or stopped share cannot make new server fetches; cached copies stay governed by the owner choice below. Downloaded copies can also be exported.

#### References, unlinking and garbage collection

Use shown_file_ids to collect references from Markdown links and canvas cards. Store one manifest/object per file ID, even if a Markdown note links to it more than once or multiple cards show it. Deleting one of several references does not delete the blob.

When the last reference disappears, the client writes an encrypted manifest tombstone and sends the authenticated DELETE. The server makes the ID unavailable immediately and deletes the R2 object asynchronously. Retries are idempotent. If an offline concurrent edit restores a reference after tombstoning, it must attach as a new file ID and upload again; a tombstoned ID is never revived. A periodic collector deletes staging or completed objects with no committed manifest after a grace period. Stop-share and owner note deletion revoke all routes immediately and enqueue every share blob for deletion. The server never tries to infer references from encrypted note text.

The share is the GC boundary for now. If future Kanso features share one ciphertext across multiple shares, they must add an explicit reference count and a separate retention design first.

#### Search, OCR and PDF annotations

Search never goes to the shared-file server. Each member decrypts only files referenced by a shared note they can currently open and builds a local search index scoped by share and file ID. The normal note search continues to index the note text. Do not mix shared-file rows with private-file OCR or with locked-note search results.

For images, run the existing OCR path on an eligible device. Recommend storing OCR text in the encrypted shared-file manifest so other members can search it locally, including devices without an OCR engine. The local FTS index is a rebuildable private cache; the OCR source remains end-to-end encrypted in the shared CRDT. Text size limits and conflict behaviour need owner approval in the question below. Sealed files are never offered to OCR.

For PDFs, use the #43 PDF reader and 50 MiB file limit. Index extracted PDF text locally for search. Highlights, comments and ink belong to the shared note, not to the PDF bytes. In a shared Markdown note, use the #43 annotation data and page links in the shared body. In a shared canvas, store the same annotation records in the canvas CRDT, keyed to the shared PDF file ID. Another member opening that file sees the shared annotations; downloading the PDF alone does not carry them. The PDF bytes remain unchanged.

Whether image and scanned-PDF OCR text should sync encrypted between members or be rebuilt on each device is an open question. Text-layer PDF extraction remains local, as in the current implementation. The answer should follow #43 and the owner's answer to question 7 below.

#### Locked notes and private APIs

The existing share check remains authoritative. No locked note or note in a locked notebook gets a collaboration share key, file manifest, OCR result, API response, search hit or blob cache entry. A locked attachment is never accepted by the shared-file upload route.

Copying a shared file into a locked note uses the #44 path: download it while the user has access, create a private file document with a new ID, seal it with the lock key, put its ownership record in kansoFiles, and rewrite the locked note reference. The shared file ID and wrap do not go into the locked note. If the file cannot be fetched, the copy does not happen.

The local REST API and MCP need member-aware attachment operations. Reuse the caller's existing local API read/write grant. A read operation must name both the shared note and file, confirm the local account is an accepted member, confirm the file is referenced by that note, and then use the shared-file engine. An add requires the note write grant plus the add role approved below. Never return a NoteKey, FileKey, wrap, private file path, or server object URL. Keep the current private attachment tools unchanged for private files. Extend the Rust bridge and Flutter bridge with progress and retry operations.

## Security and privacy

**Threat model.** The Worker, R2 operator, a network observer, an unaccepted invitee and a removed member must not learn file plaintext or keys from stored data or a new download. The server is trusted to enforce member access and quotas, but it can observe timing and size. A current accepted editor can read the shared note and files by design and can save or export them. A device already holding a FileKey or plaintext may retain it after removal.

**Encryption.** File content uses a fresh random FileKey per file. FileKey wraps are separately authenticated for share ID, file ID and epoch using that epoch's NoteKey. The shared note's signed encrypted envelope protects the manifest. File chunks authenticate their position and identity so chunks cannot be swapped between files or replayed in a different order. Keys stay in zeroizing Rust key types; logs and Debug output redact them.

**Server visibility.** The server sees share and opaque file IDs, the accepted membership/roles, uploader account and device, time, ciphertext size and ciphertext digest. It may infer that a share transferred a large object at a particular time. It cannot inspect file name, content type, MIME, image pixels, PDF pages, OCR, annotations or FileKey. There is no cross-share content deduplication or public object URL.

**Member removal.** Existing collaboration rotates NoteKey and stops future writes from removed members. This proposal extends server fetch checks to files. It cannot revoke a downloaded file or make the removed member forget an old NoteKey. Re-encrypting each active file after removal raises the cost and still cannot retract a file already saved. The recommended baseline is to keep the encrypted blob and deny future fetches; the owner decides below.

**Unlinking and deletion.** An encrypted CRDT cannot be parsed by the server to discover that a file became unlinked. A member client must send an authenticated tombstone. The server immediately refuses new fetches for that ID and then deletes the object. A malicious editor can upload unwanted data within server quotas or lie about its local reference check, so quota/rate limits and owner visibility matter. The server must never accept a client-provided URL or arbitrary object path.

**Device storage.** Keep the share blob cache encrypted at rest. Store only wrapped FileKeys with shared note state; unwrap them in memory for an authorized view. Temporary plaintext needed by a viewer stays in the app's protected temporary area and is removed when closed. The exact iOS/Android temporary-file protections are *(unverified)*.

**Locked-note boundary.** Shared files live in a separate cache and cannot be resolved from locked-note APIs. The copy into a locked note has a different ID and is sealed with the lock-key container. Property tests must prove that link conversion, OCR, search, export, MCP and error paths cannot return the original or sealed bytes while locked.

## Choices and trade-offs

These are recommendations for the owner to consider, not decisions. Effort is stated to make the trade-off concrete; effort does not select the recommendation.

1. **Removed-member files.** Keep current ciphertext and deny new downloads, matching the existing “keep what you had” collaboration rule; or re-encrypt every live file with a new FileKey after removal and replace the blob. Recommend keeping current ciphertext and enforcing membership on every fetch: it matches the note's existing epoch semantics, avoids transferring every large file, and does not imply that Kanso can recall saved copies. Estimate: 2–3 days for rewrap and access tests; 6–10 more days for blob replacement and retries.
2. **Who may add.** Owner-only upload is simple and limits quota abuse; any Edit member can add, which matches the current meaning of editing shared content. Recommend any Edit member, with visible uploader attribution, rate limits and owner quota controls, so file cards do not have a surprising owner-only exception. Estimate: 1–2 days for role/UI checks either way.
3. **Quota attribution.** Charge the share owner, charge each uploader, or give each share its own quota. Recommend the share owner's quota, shown separately as shared storage, because the owner controls the share's lifetime and can stop it. Keep uploader identity for audit and abuse limits. Estimate: 2–3 days for accounting and settings UI; no added effort should decide the owner.
4. **Deduplication.** Global plaintext hash dedup saves space but reveals equality and complicates authorization. Share-local dedup is possible but still adds refcount and unlink races. Recommend no content-based dedup; reuse an existing ID only for repeated references inside the same share. This is the clearest privacy boundary. Estimate: 1 day to keep random IDs; 3–5 days for per-share dedup and GC.
5. **Unlink deletion.** Keep unlinked ciphertext until the share stops, or tombstone it as soon as the final local reference is removed and garbage-collect the object. Recommend immediate server inaccessibility followed by asynchronous deletion, with a short grace period only for incomplete uploads. This makes “remove” meaningful while avoiding synchronous R2 cleanup in the edit path. Estimate: 3–4 days for tombstones, idempotent delete and GC.
6. **Existing links.** Upload old private files automatically, leave them private, or ask the owner to review and select. Recommend explicit review and confirmation; attachment links can contain sensitive data and an old shared note did not grant permission to share them. Estimate: 3–4 days for review, retry and reference replacement.
7. **OCR and PDF text.** Keep all OCR and extracted text local on each device, or sync bounded OCR text inside encrypted shared metadata while rebuilding only the local index. Recommend syncing image OCR and scanned-page OCR, following #45's shared search precedent; keep text-layer PDF extraction and FTS indexes local. Keep synced text bounded so one file cannot exceed the collaboration snapshot budget. Estimate: 3–5 days for encoding, limits and local index rebuild; PDF-page annotation data already follows #43.
8. **Local API/MCP.** Keep shared files out of local tools, add separate member-aware tools, or let private file IDs flow through existing private routes. Recommend separate member-aware read/add operations using the caller's existing local API grant. Private routes cannot prove share membership and must not serve these IDs. Estimate: 2–4 days for server, tool schemas and permission tests.
9. **Non-PDF size enforcement.** Reveal a server-visible size/type class, cap every shared file at 10 MiB, or keep the 10 MiB ordinary / 50 MiB PDF split client-side while the server permits the PDF ceiling. Recommend the client-side split and server-wide PDF ceiling to preserve MIME privacy and #43 PDF support; disclose that a modified client can upload a 10–50 MiB non-PDF. Estimate: 1–2 days for server/client limits; a server-visible class would need a protocol/privacy review.
10. **Local cache after membership is lost.** Erasing Kanso's cache limits casual access on that device but cannot delete an exported copy. Keeping the cache matches current collaboration semantics. Recommend keeping already downloaded files available on that device and blocking new fetches, so removal means future collaboration stops but does not pretend to recall prior access. Estimate: 1–2 days for retained-cache tests; 2–3 more for a purge option.
11. **What should moving a shared note to Trash do?** Keep sharing active while the note is recoverable, or stop sharing and revoke server access when it enters Trash. Recommend stopping the share immediately and requiring the owner to share again if they restore the note; a trashed note should not keep serving files to members. Estimate: 1–2 days for the Trash/restore lifecycle and cleanup tests.

## What this costs

The estimated build is about 56 developer-days, or 11–13 weeks for one developer who knows the codebase, including review and desktop/mobile integration. The encrypted container, epoch rewrap, Worker routes and phone lifecycle are the main work.

There is a new share-scoped cache and server accounting path alongside private file sync; reuse is limited to chunk verification, the existing account quota concepts, shared-note membership, and the PDF reader. The feature also needs new collaboration-manifest compatibility, migration UI for old links, local API/MCP access, and explicit unlink/unshare cleanup.

No new dependency is assumed. If implementation needs one, compare its maintenance and licence before adding it.

## Open questions for the owner

Each recommendation is a proposal only. The owner should choose an option or adjust it; no choice is made here.

1. **What happens to files when a member is removed?**
   - Keep the ciphertext and deny future fetches; rewrap active FileKeys for the new epoch. Previously downloaded copies remain.
   - Re-encrypt every live file under new FileKeys and replace the server blobs; previously downloaded copies still remain.
   - **Recommendation:** keep ciphertext and enforce member-only fetches, matching current collaboration removal semantics.
   - **Cost:** 2–3 days for the first option; 8–13 days for re-encryption, replacement, retries and recovery.

2. **Who can add a file?**
   - Only the owner.
   - Any member with the Edit role.
   - **Recommendation:** any Edit member, matching the role's existing content-edit capability.
   - **Cost:** 1–2 days for role checks, controls and messaging either way; editor uploads also need rate limits.

3. **Whose quota pays for shared files?**
   - Share owner's account quota.
   - The account that uploaded each file.
   - A separate per-share quota that does not count toward an account.
   - **Recommendation:** charge the share owner and show shared usage separately, with uploader identity retained for abuse controls.
   - **Cost:** 2–3 days for accounting and UI; a third quota model needs additional settings and enforcement.

4. **Should the same bytes be deduplicated?**
   - No content-based dedup; one random ID per shared copy.
   - Deduplicate only inside one share.
   - Deduplicate across accounts or shares by a content hash.
   - **Recommendation:** no content-based dedup; repeated links in the same note reuse the same ID.
   - **Cost:** 1 day for no dedup; 3–5 days for per-share references and GC; cross-share dedup also needs privacy review.

5. **When should an unlinked blob be deleted?**
   - Make it unavailable immediately and delete asynchronously after the last reference tombstone.
   - Keep it until the owner stops sharing the note.
   - Keep it for a fixed recovery period after unlink.
   - **Recommendation:** immediate server denial and asynchronous deletion, with only a short grace period for incomplete uploads.
   - **Cost:** 3–4 days for tombstone, retries, race handling and GC.

6. **How should existing private attachments be migrated?**
   - Upload every linked file automatically.
   - Leave all old references private with no migration action.
   - Show a review and let the owner explicitly select files to share.
   - **Recommendation:** review and explicit selection. Sharing is a new disclosure, so the owner must see the file list before upload.
   - **Cost:** 3–4 days for review, retries and reference replacement.

7. **Should OCR text sync to other members?**
   - Rebuild image OCR and scanned-PDF OCR locally on each device; keep text-layer PDF extraction local.
   - Sync bounded image and scanned-page OCR inside the encrypted shared manifest; rebuild the local search index on each device; keep text-layer PDF extraction local.
   - Sync image OCR only; rebuild scanned-PDF OCR locally and keep text-layer PDF extraction local.
   - **Recommendation:** sync image and scanned-page OCR as encrypted shared metadata, following #45's cross-device search approach; keep extracted search indexes local.
   - **Cost:** 3–5 days plus a chosen text cap; large OCR payloads need chunking and must fit collaboration snapshot limits.

8. **How may local API and MCP read or add shared files?**
   - Keep shared files unavailable to local API/MCP.
   - Add member-aware read/add tools under the caller's existing read/write grant.
   - Add new API-key grants dedicated to shared files.
   - **Recommendation:** member-aware operations under existing grants, checking the joined share and file reference for every call.
   - **Cost:** 2–4 days for tools/routes and security tests; new grants also need key setup and migration UI.

9. **How should the server enforce the ordinary 10 MiB limit without seeing MIME type?**
   - Allow a server-visible type or size class, leaking that classification.
   - Cap all shared files at 10 MiB, including PDFs.
   - Let clients enforce 10 MiB for ordinary files and 50 MiB for valid PDFs; server enforces the PDF-size ciphertext ceiling plus quota.
   - **Recommendation:** client-side type split and a server-wide PDF ceiling, preserving MIME privacy and the #43 PDF limit. A hostile client can exceed the ordinary-file client cap up to the PDF ceiling.
   - **Cost:** 1–2 days for limits; a server-visible classification needs protocol and privacy review.

10. **When a member leaves or is removed, what happens to the local shared cache?**
    - Keep already downloaded files available on that device; block future server fetches.
    - Erase Kanso-managed cached files and keys when membership is lost; exported or copied files remain.
    - Offer a setting to clear shared caches.
    - **Recommendation:** keep what the member already had, matching the existing collaboration removal rule, while blocking future fetches and making clear that copies cannot be recalled.
    - **Cost:** 1–2 days for retained-cache behavior and tests; 2–3 more days for revocation-driven purge and a setting.

11. **What should moving a shared note to Trash do?**
    - Keep sharing and serving files while the note is recoverable from Trash.
    - Stop sharing immediately, revoke server fetches and delete server blobs; restoring the note requires the owner to share it again.
    - **Recommendation:** stop sharing on Trash. A note in Trash should not keep serving shared files; restoring does not silently restore access for other people.
    - **Cost:** 1–2 days for Trash/restore lifecycle handling and deletion tests, included in build step 6.
