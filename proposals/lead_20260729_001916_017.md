# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**uitest.py crashes with UnicodeEncodeError when the focused control contains a non-ASCII glyph**

*Project description:*
## What happens

`native/tools/uitest.py state` crashes whenever the app's reported state contains a
non-ASCII character. In practice this is any time a detail view is focused, because the
Play button's label contains `▶` (U+25B6):

```
Traceback (most recent call last):
  File "native\tools\uitest.py", line 104, in <module>
    sys.exit(main())
  File "native\tools\uitest.py", line 65, in main
    print(json.dumps(state(), indent=2, ensure_ascii=False))
  File "C:\Python314\Lib\encodings\cp1252.py", line 19, in encode
    return codecs.charmap_encode(input, self.errors, encoding_table)[0]
UnicodeEncodeError: 'charmap' codec can't encode character '\u25b6' in position 182:
character maps to <undefined>
```

## Cause

[`native/tools/uitest.py:65`](native/tools/uitest.py#L65):

```python
print(json.dumps(state(), indent=2, ensure_ascii=False))
```

`ensure_ascii=False` passes the glyph straight through to `stdout`, which on Windows
defaults to the ANSI codepage (cp1252) and cannot encode it. The pipe read itself is fine
— `_send` already decodes UTF-8 — so this is purely the console encoding on the way out.

## Reproduce

1. Launch the app with `EB_UITEST=1`.
2. Navigate to any item's detail view, so the focused control is **▶ Play**.
3. `python native/tools/uitest.py state`

## Why it matters

It breaks the harness exactly where automation needs it most. Any scripted flow that
polls `state` while a detail view is up dies mid-run, and the failure looks like a harness
or pipe fault rather than an encoding problem, which sends you looking in the wrong place.

The workaround is `PYTHONIOENCODING=utf-8`, but that has to be remembered at every call
site.

## Suggested fix

Reconfigure the stream in `main()` so it holds regardless of the caller's environment:

```python
sys.stdout.reconfigure(encoding="utf-8", errors="replace")
```

`errors="replace"` keeps it from failing on a console that genuinely cannot render the
glyph. `sys.stderr` is worth the same treatment.
