## Summary

Add a shell for **OpenHarmony / HarmonyOS 5–6**, `frust-shell-ohos`, so a Frust app can run on Huawei phones and tablets and on other OpenHarmony devices.

Research says this is **feasible**, and most of it can be built and compile-gated **today, with no device and no version-pin change**. Only the runtime proof needs real HarmonyOS hardware.

Status as of `main` @ 654f7acb (2026-10-05). Every claim below was re-checked against the source tree, the vendored crate sources and upstream tags on that date.

## Where things stand

### What already works (re-probed 2026-10-05, rustc 1.98.1, no OHOS SDK)

`cargo check --target aarch64-unknown-linux-ohos -p <crate>`:

| Crate | Result |
|---|---|
| `frust-gpu`, `frust-engine`, `frust-render`, `frust-core`, `frust-plugin` | ✅ clean |
| `frust-text`, `frust-widgets`, `frust-shell-common` | ❌ `failed to run custom build command for yeslogic-fontconfig-sys v6.0.1` |

### Rendering has no compute requirement
`frust-engine` uses only vertex and fragment shaders. [`ENGINE_REQUIRED_DOWNLEVEL_FLAGS`](https://github.com/frust-rs/frust/blob/654f7acb9757ebcfdc91ef001dcade8eabb23917/crates/frust-render/src/tier.rs#L50) is empty, and the engine targets the GLES3/WebGL2 feature level. The old blocker (vello needed compute shaders and storage buffers, which meant Vulkan only) went away when vello was removed.

### GPU backend on OHOS: GLES now, Vulkan later
- **GLES/EGL works on the current pin.** In wgpu-hal **30.0.1** the GLES backend accepts `Rwh::OhosNdk` ([`gles/egl.rs` L935, L1262 @ v30.0.1](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/gles/egl.rs#L935)), added in [gfx-rs/wgpu#7085](https://github.com/gfx-rs/wgpu/pull/7085).
- **Vulkan is not in 30.0.1.** [gfx-rs/wgpu#9908](https://github.com/gfx-rs/wgpu/pull/9908) ("hal/vulkan: add OpenHarmony surface support", `VK_OHOS_surface`) was merged to trunk on 2026-07-24, but it is **not in the v30.0.1 tag**: `wgpu-hal/src/vulkan/instance.rs` has 0 OHOS references at the tag and 13 on trunk. It will ship in **wgpu v31**, which has not been released. ⚠️ The trunk CHANGELOG lists #9908 under v30.0.0, which is wrong. Check the tag's source, not the changelog.
- **No pin change needed.** Backends are chosen per target in [`crates/frust-gpu/Cargo.toml`](https://github.com/frust-rs/frust/blob/654f7acb9757ebcfdc91ef001dcade8eabb23917/crates/frust-gpu/Cargo.toml#L29). OHOS triples are `target_os = "linux"`, so they already match the `all(unix, not(target_vendor = "apple"))` row and get `vulkan`. That has no effect until v31. Adding a `[target.'cfg(target_env = "ohos")'.dependencies]` row with `gles` is a feature-routing change, not a version bump. Keep `gles` to OHOS only.

## Known blockers (in-tree, fixable now)

1. **Font discovery: fontique has no OHOS backend.** fontique 0.11.1 (through parley 0.11.1) enables `yeslogic-fontconfig-sys` for `cfg(any(target_os = "linux", target_os = "freebsd"))`. OHOS reports `target_os = "linux"` but has no fontconfig. Fix:
   - turn parley's `system` font feature off for `cfg(target_env = "ohos")` in `crates/frust-text/Cargo.toml`;
   - build the collection with `system_fonts: false`, the same approach already used in [`context.rs` L933–938](https://github.com/frust-rs/frust/blob/654f7acb9757ebcfdc91ef001dcade8eabb23917/crates/frust-text/src/context.rs#L933-L938);
   - fill it by scanning `/system/fonts` (HarmonyOS Sans) and/or from app-bundled fonts via `TextContext::register_fonts`;
   - later, contribute an OHOS backend to fontique upstream ([linebender/parley](https://github.com/linebender/parley)).
2. **The facade would pull in the desktop shell.** The [`frust` facade's target predicate](https://github.com/frust-rs/frust/blob/654f7acb9757ebcfdc91ef001dcade8eabb23917/crates/frust/Cargo.toml#L123) only excludes `android`, `ios` and `wasm32`. On OHOS it would pull in `frust-shell-desktop` and winit. It needs `target_env = "ohos"` added.

## Proposed approach

- **Use the Android shell as the template:** direct FFI, a continuous frame loop, **no winit**.
- **FFI:** raw [`ohos-sys`](https://github.com/openharmony-rs/ohos-sys) 0.9.x (XComponent, native_window, native_vsync, hilog, rawfile and inputmethod are behind features, with an API-level feature matched to the target device) inside a sanctioned-unsafe `napi_glue` module. Use [`napi-ohos`](https://github.com/ohos-rs/ohos-rs) 1.2.x for calls between ArkTS and Rust. The higher-level ohos-rs wrappers are pre-1.0 and thinly documented, so the shell won't build on them.
- **Surface:** add `frust-gpu` `create_ohos_surface` and a `frust-render` surface-created-from-OHOS-window path, next to the existing [`create_android_surface`](https://github.com/frust-rs/frust/blob/654f7acb9757ebcfdc91ef001dcade8eabb23917/crates/frust-gpu/src/lifecycle.rs#L290). Use [`raw-window-handle` 0.6.2 `OhosNdkWindowHandle`](https://docs.rs/raw-window-handle/0.6.2/raw_window_handle/struct.OhosNdkWindowHandle.html).
- **Host:** an ArkTS template (`EntryAbility` plus an `XComponent` page, hvigor, `oh-package.json5`) that loads the Rust `.so`.

## Risks / open questions

- **GLES on OHOS gets little upstream testing.** wgpu#7085 was merged with crashing examples and no CI. [gfx-rs/wgpu#6543](https://github.com/gfx-rs/wgpu/issues/6543) (GLES fails to instantiate on the OHOS emulator) was closed as *not planned*. We found no report of wgpu-GLES running on a HarmonyOS 5/6 device, so the first device run may hit wgpu-hal EGL bugs that need upstream fixes.
- **Hardware:** we don't own a HarmonyOS 5/6 device. Supply is mostly in China; the EU MatePad 2026 models are the nearest retail option. The DevEco emulator is Windows-only, its Vulkan support is unconfirmed, and cloud device farms are geofenced.
- **Toolchain:** DevEco Studio is Windows/macOS only. Getting the OpenHarmony SDK on a Linux host and setting up the clang linker wrappers hasn't been tested. Account and licensing requirements for signing HAPs have not been checked.
- **HarmonyOS vs OpenHarmony drift:** the consumer line is HarmonyOS 6 / API 23 (the "NEXT" label has been retired). `ohos-sys` API-level features default to 10. The Flutter OHOS fork shows one build can serve both, but nobody has verified that for Rust.
- **Fonts:** the `/system/fonts` scan would be our own code with no upstream precedent, and nobody has checked the HarmonyOS 6 font paths on a device. Bundled fonts are the guaranteed fallback.
- **Accessibility:** AccessKit has no OHOS backend. This would be a documented limitation, not a task.
- **wgpu 31 timing** is up to upstream, and the bump has to go through the engine gate suite on every shipping backend.

### Decisions needed
- [ ] Font strategy: `/system/fonts` scan + bundled fonts in-tree now, upstream fontique backend later (recommended), or something else.
- [ ] Device: buy or borrow a HarmonyOS 5/6 device for Phase 2. Phases 0–1 don't need one.
- [ ] Plugin substrate: ship without `frust_plugin::ohos` (the iOS and web shells set the precedent) and add it only when a plugin needs the napi env or ability context.
