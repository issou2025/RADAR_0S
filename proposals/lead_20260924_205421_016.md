# Strix integration: pentest the apps you build inside a workspace

## What is Strix

**Repo:** https://github.com/usestrix/strix · **Docs:** https://docs.strix.ai · Apache 2.0

Strix is an open-source AI penetration testing tool. It runs a team of specialised AI agents inside a Docker sandbox (`ghcr.io/usestrix/strix-sandbox`) equipped with an HTTP intercepting proxy (Caido), a real browser, a shell, and a Python sandbox for writing exploits.

It is **dynamic, not static**. A normal scanner reads source and says "line 42 looks like SQL injection". Strix runs the app, sends real attack traffic at it, and proves the bug by exploiting it — so a finding arrives with a working reproduction instead of a guess. It covers the OWASP Top 10: injection, broken access control, XSS, SSRF, business logic flaws.

**Targets:** a live app URL, a GitHub repo URL, a local directory, a domain/IP, or an API spec (OpenAPI/Swagger/Postman).

**Scan modes:** `quick` (minutes, built for CI), `standard` (30–60 min), `deep` (1–4 hours, and Strix's own default).

**Needs:** Docker, and an LLM API key (`STRIX_LLM` + `LLM_API_KEY`, LiteLLM format). Runs headless with `strix -n`, returning exit codes for automation, and writes a structured event stream to `strix_runs/<run>/events.jsonl`.

## Why add it to kube-coder

A workspace user builds an app and runs it on `localhost:3000`. Today nothing in kube-coder tells them whether that app is safe to expose. This closes that gap, and does it in a way a standalone CLI cannot.

**1. The find-then-fix loop is the real product.** Strix proves a vulnerability. kube-coder is already sitting on the repo, an agent orchestrator, isolated worktrees (#701), a review queue, and a push-PR flow. So:

```
Strix finds it  →  agent fixes it in a worktree  →  human approves the diff  →  PR
```

All of that already exists. Running the Strix CLI by hand gives you the first box only. **This loop is the reason to build it here.**

**2. It fits the existing shape.** We already ship Playwright MCP for browser automation and e2e flows. This is its security sibling — same instinct, same surface, aimed at a different question.

**3. Zero setup for the user.** The workspace already knows which apps are running and on which ports (`/api/apps`). The user picks one from a list instead of configuring a security tool.

**4. Phone-first fits naturally.** A scan is long-running and its output is a short list of decisions — exactly the shape that suits the mobile app and push (#685). Start a scan from the desktop, get pushed when it finds something critical, triage from a phone.

**5. Findings become durable.** Scan results land in the workspace rather than a terminal someone closed.

## Recommended approach

### Architecture

A scan is a long-running job that emits a stream of events and a set of findings. That is a shape kube-coder already handles twice, so the new module composes both rather than inventing a third:

- **Execution + streaming** — the pattern from `hypervisor_session.py`: run the CLI over pipes in machine-readable mode, normalise into our canonical event stream, push onto the existing `/api/events` SSE firehose. Strix already writes `events.jsonl`, so this is tailing a file, not scraping a terminal.
- **Lifecycle** — the pattern from `boards/runs.py`: `running` / `done` / `stopped` / `interrupted` plus its reclaim-orphans-at-boot sweep, so a scan whose process dies is marked `interrupted` rather than sitting at `running` forever (#462's failure mode).

Deliberately **not** a Hypervisor adapter (a scan is not a conversation) and **not** a tmux task (there is no terminal to scrape).

### Keep the execution backend behind one seam

```
scans.py ──> ScanBackend ──> LocalStrixBackend    (v1 — subprocess in the pod)
                        └──> RemoteRunnerBackend  (later — a dedicated scan host)
```

Everything above the seam — the API, the UI, the event stream, the findings model, the fix loop — is backend-agnostic. Moving Strix off-pod later becomes a backend swap instead of a rewrite. See *Later changes* below.

### Request flow

```
  Web / Mobile
      │  POST /api/scans  {port: 3000, mode: "quick", budget: 5, model: "..."}
      ▼
  server.py ──> scans.ScanManager.create()
      │            ├─ resolve_target(port)  →  http://<docker-gateway>:3000
      │            ├─ enforce budget + model allowlist
      │            └─ spawn LocalStrixBackend  →  strix -n --target … --max-budget …
      │
      ├─ returns {scan_id} IMMEDIATELY (never blocks on the scan)
      │
      ▼
  tail strix_runs/<run>/events.jsonl
      │  normalise → canonical events
      ▼
  /api/events (existing SSE firehose)  +  /api/scans/<id>/stream
      │
      ▼
  Web live view · Mobile live view · push on completion / critical finding
```

## Things to keep in mind

### 1. Never assume the target address — resolve it

Inside the Strix sandbox, `localhost` means *the sandbox*, not the workspace. The user's app is reachable at the Docker bridge gateway, not at `localhost`.

```
❌  target = "172.17.0.1:3000"        # breaks the day Strix runs anywhere else
✅  target = resolve_target(port)     # discovers the gateway at runtime
```

Discover it at runtime (`ip route` → `default via`). `172.17.0.1` is the conventional value, not a guarantee. **A wrong address does not error — it produces a clean report against nothing**, which is the worst possible failure for a security tool. This is also the exact seam that makes a future scan-runner cheap.

### 2. Budget cap — mandatory, and the user controls it

- `--max-budget <usd>` on **every** invocation, no exceptions, enforced server-side.
- Default mode is `quick`. Strix's own default is `deep` (1–4 hours) — never let the bare default through.
- Show the time cost beside each mode in the picker.
- Render live spend during the run; Strix reports it.
- A `quick` scan against a near-empty target still burns ~900K input tokens. A frontier model costs roughly **20×** a cheap one for the same work. Default to a cheap model and make the cost visible before the user commits.

### 3. Strix needs its own API key, separate from the workspace assistant key

A `deep` scan is 1–4 hours of continuous LLM calls. Run on the workspace's shared key it can exhaust that key's budget and **silently break the OpenRouter/Claude assistant for everyone using the workspace**.

Strix gets its own key with its own cap. v1 can use Strix's `~/.strix/cli-config.json` (`chmod 600`), which needs no `ProviderKeysManager` change; a Settings-UI path can follow in Phase 3.

### 4. Model is a fixed list, not free text

Strix ships a recommended-model list and warns when the configured model is off it. **A weak model does not fail loudly — it misses vulnerabilities.** Offer only models from Strix's list, sourced from `strix.models` in values.yaml, and default to a cheap one.

### 5. Latency — high priority

The scan itself is irreducible. What is winnable is **time-to-first-signal**:

- **Pre-pull `ghcr.io/usestrix/strix-sandbox` at pod boot.** This is the single biggest win. On a fresh workspace the image cache is empty, so the first scan sits silent for minutes while a multi-GB image downloads — which reads as a hang and gets killed.
- **Stream, don't poll.** Tail `events.jsonl` onto the SSE firehose; findings appear as they are confirmed.
- **Return a scan id immediately.** Never block a request on a scan.
- Targets: status visible in **<1s**, first agent activity within **~30s** with the image warm.

### 6. Network policy

- **v1 (in-pod):** no change required. The sandbox reaches the app through the Docker bridge — that is not pod egress.
- **Cross-pod / in-cluster targets:** blocked by the egress policy (pod CIDR `10.244.0.0/16`, service CIDR `10.245.0.0/16` denied). Out of scope, and correctly so — a tool built to attack things should not reach other tenants.
- **Cilium footgun:** an `allowCIDRs` entry inside a denied range is a **silent no-op**. Narrowing `deniedCIDRs` is the supported route. Do not "open" anything the easy way; it will look like it worked.
- **Future scan runner:** `templates/networkpolicy.yaml` denies all ingress except from the `ingress-nginx` namespace, explicitly so that *"workspaces should never talk to each other"*. A runner needs a `namespaceSelector` exception — that touches the tenant isolation boundary and belongs in its own issue with its own review.

### 7. Local folder scans are not supported in v1

Strix bind-mounts a local source directory into its sandbox. With `dind` as a sidecar the daemon has its own filesystem, so the mount resolves against the wrong root and Strix receives an **empty directory** — then honestly reports "no vulnerabilities found". Silent, no error.

Upstream fix is open but unmerged: [usestrix/strix#1328](https://github.com/usestrix/strix/pull/1328) (`STRIX_REQUIRE_MOUNT_FREE`).

**So v1 ships running-app and GitHub-repo-URL targets only. Local folder scanning is omitted from the UI, not offered with a warning.**

### 8. Gate it loudly

`strix.enabled` must `fail` at template render unless `build.mode == "buildkit"`. The Docker dependency should be a clear install-time error, never a mysterious first-scan failure.

### 9. Memory

Sandbox + Caido + browser + concurrent agents, on top of code-server. The `dind` sidecar defaults to `limits: memory 4Gi`, and concurrent Board runs already OOM a 4GiB workspace — with cgroup counters resetting afterwards, so the OOM is invisible in the UI. Raise limits deliberately when `strix.enabled`, and treat an abrupt scan death as a suspected OOM.

### 10. Only ever scan what the user owns

Strix generates real attack traffic. In-workspace targets are the user's own app, which is why this scope was chosen. Scanning a deployed kube-coder instance is a different activity belonging in CI against staging — never against the live shared cluster. Separate issue if wanted.

## UX requirements

### Web

- **Pick the target from a list**, sourced from `/api/apps` — port, pinned name, and `status: running`. Never make the user type a path or an address.
- **Mode picker shows the time cost**: `quick ~5 min` / `standard ~45 min` / `deep 1–4 hrs`. The cost is part of the choice.
- **Budget prefilled and editable**, with live spend rendered during the run.
- **Model dropdown** from the allowlist, cheap default, with a one-line note that stronger models find more.
- **Live view, not a spinner.** Agent activity and findings stream in as they are confirmed.
- **Findings sorted by severity**, each with a working reproduction and a **Fix this** button.
- **Never show a bare "0 vulnerabilities."** Always say what was reached and scanned — given how many failure modes here produce a clean-looking empty result, an unqualified all-clear is misleading.
- **Empty and blocked states are explicit**: no running apps → say so and link to Applications; `strix.enabled=false` → say why and what to change.

### Mobile

- Lives under **Mission Control**, beside Board — both answer "what needs me?"
- **Scan list** as the landing screen: target, status, findings count, spend.
- **Starting a scan must work from the phone** — target/mode/budget in one sheet, with form state persisted so switching apps mid-entry doesn't reset it (the RunsPanel defaults problem; don't repeat it).
- **Live progress on the phone**, not a frozen screen — a multi-hour job must show it is alive.
- **Push on scan complete and on first critical finding**, routed through the #685 dedupe rules (seen-rule + cooldown, `collapseId`/`tag`/`ttl`). A scan that finds nothing should not push twice.
- **Tapping a push deep-links to `ScanDetail`**, including from a cold start.
- **44pt touch targets**, safe-area insets, and a readable finding detail on a phone screen — reproductions are long; make them collapsible rather than a wall.
- **Triage from the phone**: approve a fix, dismiss a finding, stop a runaway scan. Reading-only would waste the surface.

## Later changes, when needed — a separate machine for Strix

The better end state on a shared cluster is one hardened **scan-runner host** with Docker, shared by all workspaces, with `RemoteRunnerBackend` talking to it.

```
┌─ WORKSPACE POD ──────┐         ┌─ SCAN RUNNER ─────┐
│                      │         │                   │
│  user's app  ◄───────┼─scans───┤       Strix       │
│  :3000               │         │                   │
│  kube-coder ──"scan ─┼────────►│  • one machine    │
│               this"  │         │  • hardened       │
└──────────────────────┘         └───────────────────┘
```

**What it fixes:** no privileged `dind` in any tenant pod; scans stop competing with the workspace's own memory; the sandbox image is pulled once and shared, removing first-run latency for everyone; one key and one budget enforced centrally.

**What it costs:** a service to build and operate (TLS, auth, tenant isolation, result routing, queuing), and an exception in the workspace ingress policy — which is the tenant isolation boundary and needs its own security review.

**What it does not fix:** local folder scans. A remote machine can never see workspace files, so that limitation becomes structural rather than a bug.

**Build it when** more than a couple of workspaces want scans, or when privileged `dind` on tenant pods is ruled out. Not before — and with the backend seam in place from v1, it is a swap rather than a rewrite.

## Acceptance criteria

**Server**
- [ ] `POST /api/scans` returns a `scan_id` in under 1s and never blocks on the scan.
- [ ] Target address is resolved at runtime; no hardcoded gateway IP anywhere in the tree.
- [ ] A scan rejects a model outside the allowlist and a missing/zero budget, with a clear error.
- [ ] A scan whose process dies is marked `interrupted`, not left `running` — verified across a pod restart.
- [ ] Helm render fails with a readable message when `strix.enabled=true` and `build.mode != buildkit`.
- [ ] The sandbox image is present before the first user-initiated scan.
- [ ] Local folder targets are not offered by any endpoint.

**Web**
- [ ] Target picker lists only running apps from `/api/apps`; no free-text address entry.
- [ ] Mode picker shows the time estimate; budget is prefilled and editable; live spend renders during the run.
- [ ] Findings appear during the scan, not only at the end.
- [ ] A completed scan with no findings states what was reached and scanned — never a bare "0 vulnerabilities".
- [ ] `strix.enabled=false` renders an explanatory state, not a broken page.

**Mobile**
- [ ] Security appears under Mission Control in the drawer, beside Board.
- [ ] A scan can be **started** from the phone, not just viewed — and the form retains typed values when the app is backgrounded.
- [ ] Live progress updates on the phone while a scan runs.
- [ ] Push fires on scan complete and on first critical finding, deduped per #685, and does not double-fire.
- [ ] Tapping the push opens the right `ScanDetail`, including from a cold start.
- [ ] Finding detail is readable on a phone: collapsible reproduction, 44pt targets, safe-area respected.
- [ ] A running scan can be stopped from the phone.

**End to end**
- [ ] Start an app on a port, start a `quick` scan against it from the web, watch findings stream in, receive the completion push on the phone, open the finding from that push.
