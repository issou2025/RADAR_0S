# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**hooks: bash_windows_path_guard message misattributes trailing-backslash-escaped-quote breakage**

*Project description:*
## Symptom

`hooks/bash_windows_path_guard.py` blocked a Bash command in a life-os session with:

> Blocked: unquoted Windows path `E:\automation\life-os\.claude\skills\general\conversations\` in a Bash command — Git Bash strips backslashes in unquoted word-splitting context, so this would actually run as `E:automationlife-os.claudeskillsgeneralconversations`. Use forward slashes (`E:/automation/life-os/.claude/skills/general/conversations/`) or quote the path (single or double quotes).

The flagged path visibly *is* wrapped in double quotes in the source command, so the message reads as wrong or confusing — the reader has no way to tell why a quoted-looking path was rejected as unquoted.

## Root cause

The full blocked command was:

```
ls "E:\automation\life-os\.claude\skills\general\memory\" 2>/dev/null; echo "---"; ls "E:\automation\life-os\.claude\skills\general\conversations\" 2>/dev/null
```

The **first** path ends `memory\"` — a trailing backslash immediately before the closing double-quote. Inside bash double quotes, `\"` is an escaped literal `"`, not a quote-closer, so that first quoted string never actually closes. The quote parity shifts for the rest of the line, and by the time bash reaches the second path, it lands genuinely unquoted and gets its backslashes stripped.

Verified two ways:

1. Real Git Bash:
   ```
   $ bash -c 'set -x; echo "E:\automation\life-os\.claude\skills\general\memory\" TESTMARKER "E:\automation\life-os\.claude\skills\general\conversations\"'
   + echo 'E:\automation\life-os\.claude\skills\general\memory" TESTMARKER E:automationlife-os.claudeskillsgeneralconversations"'
   E:\automation\life-os\.claude\skills\general\memory" TESTMARKER E:automationlife-os.claudeskillsgeneralconversations"
   ```
   The second path's backslashes are stripped exactly as the guard's message warned.

2. The guard's own `_safe_mask()` already models this correctly (`hooks/bash_windows_path_guard.py:75-84` — a backslash inside `in_double` consumes the following character, including `"`, without closing the string). Running `find_unsafe_drive_paths()` on the exact command above returns only the second path as the hit, matching real bash.

So **the guard's detection is correct and it did its job** — it caught a command that would have silently run against the wrong path. The gap is purely diagnostic: the message names the downstream symptomatic path, not the actual defect (the trailing backslash on the *first* path's closing quote), leaving no one — human or model — able to tell what to actually fix.

Triggering context, for reference: life-os's `.claude/skills/_shared/bootstrap.md` Step C tells the skill to do "the harness's native non-recursive directory listing" on the private `memory/`/`conversations/` dirs. On Windows Claude Code this got realized as a raw `Bash` `ls` using Windows-style backslash paths with a trailing `\` before the closing quote — a generic, easy-to-repeat footgun, not specific to life-os.

## Proposed approach

1. In `hooks/bash_windows_path_guard.py`, when a drive-letter path match is immediately followed by `\"` inside what looks like an intended-but-broken quoted segment (i.e., a backslash sits directly before the quote character that would otherwise close the string), detect that specific shape and report the *root-cause* path/position, not only the cascaded symptomatic one. At minimum, when this shape is detected, add a distinct clause to the block message explaining the actual mechanism: "a trailing backslash immediately before a closing `\"` escapes the quote instead of closing it, shifting quoting for the rest of the command" — so the fix is legible even when the downstream flagged path isn't the one that needs changing.
2. Add this pattern to `global-CLAUDE.md`'s "Recurring gotchas" section (Windows paths + Git Bash) as its own bullet, since it's a generic bash quoting trap that can bite in any hand-written or model-generated Bash command referencing a Windows directory path ending in `\`, not just inside this hook.
