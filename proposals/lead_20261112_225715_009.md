# Project Proposal — Structural Drawings

## Project Understanding

**Wayfinder map: Live VBT v1**

*Project description:*
## Destination

Two deliverables.

1. A v1 build spec, ready to hand to an implementing agent, for live rep-by-rep barbell VBT that is functional without the Criterion: XR Stations that track the bar and give feedback on the phone, a local Host with an iPad web UI, and a functional gate between delivery phases that needs no GymAware. The data model leaves room for future jump, IMU, and mocap Recordings.
2. A validation protocol with pass criteria against GymAware, backed by a collected Reference Dataset. It does not gate the build; the user validates when they need to.

## Notes

**Domain.** Exploratory R&D at the OSU Human Performance Collaborative. Not under an IRB, except that any Session comparing against the Criterion (GymAware) falls under the lab's existing IRB approval for validation research. Vocabulary is in `CONTEXT.md`; use its terms.

**Skills.** Grilling tickets: call the grilling and domain-modeling skills, and update `CONTEXT.md` as terms resolve. Research tickets: the research skill, fired as subagents. Prototype tickets: the prototype skill. Task tickets: drive alone where possible, otherwise hand the user a precise checklist.

**Hardware.**
- Several iPhone XR: A12, 3 GB RAM, single 12 MP wide camera with OIS, 1080p slo-mo formats at 120 and 240 fps. iOS 18 is their last OS, so iOS 26-only APIs (locked frame duration, genlock) are unavailable.
- One iPhone 17 Pro: the reference camera. Never develop or benchmark Station software against it; it hides XR performance problems.
- One iPad: opens the Host's web UI.
- GymAware: the Criterion.
- Samsung S10 and S22: not used in v1.
- Apple: the user's personal Apple Developer account.

**Lifts.** Back squat, front squat, bench press, deadlift (straight bar or trap bar).

**Decided before the map** (don't reopen without new evidence):
- Native Swift Station app, deployment target iOS 18.
- AprilTag 3 (C library, BSD-2) on the bar end for tracking, with full pose from per-device intrinsics.
- Rep logic lives in a pure Swift package shared by the app and a macOS replay CLI.
- The live value is the stored value. Replay flags disagreements; it never overwrites what the Participant saw. Every derived value records its algorithm version.
- Raw data is never discarded: video, per-frame timestamps, device ID, calibration version.
- Session model: one Recording per Station per Session. Each Set carries its Participant, load, Station, and start and end time within that Recording.
- Host stack mirrors `hpc-open-wearables`: FastAPI, Postgres, Celery/Redis, React web UI served to the iPad.
- Stations, Host, and iPad sit on an isolated router with no internet route. Live feedback never depends on the network.
- Capture target 1080p at 120 fps, pending the XR benchmark.
- Delivery phases: Phase 0 groundwork, Phase 1 one Station with no Host, Phase 2 Host plus several Stations. Phase 2 starts when Phase 1 passes the functional gate, which needs no Criterion (re-scoped 12 Nov 2026: the system must be functional before, and without, GymAware validation).

**Methods.** Agreement analyses use repeated-measures Bland-Altman limits of agreement, CCC, MAE/RMSE, proportional bias, and TOST equivalence against an a priori SESOI. Never correlation alone.

**Data handling.** Participant video and Criterion data stay on local machines. Never commit them to git and never upload them to cloud services, including cloud coding sessions.

## Decisions so far

<!-- one line per resolved ticket: [ticket title](issue URL): one-line gist -->
- [iOS capture pipeline](https://github.com/Michael-Dial/hpc-vbt-live/issues/2): one capture session, a bi-planar 4:2:0 data output feeding both an HEVC AVAssetWriter and tag detection, with a per-frame timestamp sidecar; needs nothing from iOS 26; XR format list, storage, and 60-minute stability go to the XR benchmark.
- [AprilTag on iOS](https://github.com/Michael-Dial/hpc-vbt-live/issues/3): vendor the C sources as a C target in the shared Swift package; take a 90 mm tag36h11 on a centred end-cap mount into the benchmark (tagStandard41h12 as comparison), viewed along the bar axis from 2.0 to 2.5 m, detecting in a window around the last detection; no published A12 timing exists.
- [GymAware definitions, export, and alignment](https://github.com/Michael-Dial/hpc-vbt-live/issues/4): the lab has the tethered GymAware with the iPad app and Cloud; rep thresholds are unpublished and there is no MPV output; export per-rep CSV; align Sets by wall clock and Reps by index, confirmed by concentric durations (no bar tap); mean-velocity error against motion capture is about 0.02 to 0.06 m/s.
- [Apple developer setup and installing on the XRs](https://github.com/Michael-Dial/hpc-vbt-live/issues/14): paid membership; Station bundle ID `edu.osu.hpc.vbt.station` (separate from the Flutter HPC VBT app); install directly from Xcode for development and the benchmark, with TestFlight through the `app-store-release` workflow as the second route; one XR registered and a probe installed and launched on it; each further XR needs Developer Mode and one registering build.
- [Rep-logic structure and regression testing](https://github.com/Michael-Dial/hpc-vbt-live/issues/13): rep logic takes per-frame bar samples and is streaming only, one code path for live and Replay (ADR 0001); the Station logs a Bar Track so Replay runs from it by default, or from video; a Regression Run happens on the user's MacBook; same Algorithm Version must reproduce live values and a changed Rep count fails the run; numeric thresholds go to the validation protocol; only aggregates leave `data/`.

Waits on [XR benchmark](https://github.com/Michael-Dial/hpc-vbt-live/issues/5), which sets the thermal and power constraints. The first tag mount, needed for the benchmark, is now [Bar-end tag mount](https://github.com/Michael-Dial/hpc-vbt-live/issues/18).
- **Analytics.** Load-velocity profiles, velocity-loss summaries, and exports to the lab's analysis pipeline. Waits on [Metric definitions per lift](https://github.com/Michael-Dial/hpc-vbt-live/issues/7) and [Data model and storage](https://github.com/Michael-Dial/hpc-vbt-live/issues/12).
- **Container Services sync.** Pushing data from the Host to OSU Container Services. In scope, but only after v1 works fully self-hosted, and it needs its own decision on participant video.
