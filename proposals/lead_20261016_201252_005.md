## Project Understanding

**FROST: ZIP 2005 quantum-recoverable keys (dkg-2), member backup string, signing transport from sk**

*Project description:*
## Problem Statement

A FROST group's funds in zkool are not quantum recoverable, even when they sit in the Ironwood pool. [ZIP 2005](https://zips.z.cash/zip-2005) lets an Ironwood note be recovered after a discrete-log break only if its viewing key was derived in a way the Recovery Statement can check. For a key whose spend authority comes from a DKG, the only such derivation is the `use_qsk` branch, where `rivk` is a hash of `(ak, nk)` keyed by a quantum intermediate key. Our frost accounts take `nk` and `rivk` from a throwaway broadcast account and only swap in the group `ak`, so their `rivk` satisfies neither branch. A member who does everything right today, including moving funds to Ironwood, still loses them the day Orchard is switched off.

A FROST member also has no compact backup. A regular account is a 24-word phrase; a frost account is only recoverable through the full account export, which until #1335 did not even carry the key package.

## Solution

New FROST groups derive their viewing key as ZIP 2005 specifies for FROST: `sk` is the Orchard key of the broadcast account the group already shares, `nk` and `qsk` derive from it, and `rivk` derives from `(qk, ak, nk)`. Only `rivk`, and therefore the group address, changes; signing, proving and sync are untouched. Each member can back up their whole state as one short `zkfrost` string, 68 bytes, and restore it with the group's UFVK alone, with no peer addresses, because the signing transport is reworked so that a member never needs to know the other mailboxes after the DKG. Existing groups keep working unchanged, can produce the same backup string for device loss, are told plainly that their notes are not recoverable, and get a one-action upgrade that creates the recoverable sibling account from the same shares and a one-action sweep that moves the funds into it, in the Ironwood pool.

## User Stories

1. As a member of a new FROST group, I want the group address to be quantum recoverable from the first payment, so that funds the group receives in the Ironwood pool survive a future discrete-log break.
2. As a member of a new FROST group, I want every participant to arrive at the same group address, so that money sent to the address we agreed on is money we can all see and spend.
3. As a member running an older app during a DKG with members on the new app, I want the DKG to stop with a clear error instead of completing with a different address on my device, so that nobody pays into an address only some of us hold.
4. As a member of any FROST group, I want to sign transactions exactly as before, so that the recoverability work costs me nothing in day-to-day use.
5. As a member of any FROST group, I want to export my share as one short string, so that I can back it up like a seed phrase, on paper or in a password manager.
6. As a member restoring on a new phone, I want to type my backup string and paste the group's viewing key, and get my frost account back with its balance, so that losing a device does not mean losing my seat in the group.
7. As a member restoring on a new phone, I want to be able to sign in the next session without collecting the other members' mailbox addresses, so that a restore does not depend on everyone else doing something.
8. As a member restoring, I want the restore to refuse a string that does not belong to the group whose viewing key I pasted, so that a mix-up between two groups is caught before I rely on the account.
9. As a member restoring a legacy group, I want the restore to recreate the legacy account with its old address and notes, so that funds already received there stay visible and spendable.
10. As a member restoring an upgraded group, I want both the legacy and the recoverable account back from one string, so that I do not need two backups per group.
11. As a member of a legacy FROST group, I want the app to tell me that the group's funds are not quantum recoverable, so that I know action is needed while every member is still reachable.
12. As a member of a legacy FROST group, I want a single action that creates the recoverable sibling account from our existing shares, so that we do not have to run a new DKG.
13. As a member of a legacy FROST group, I want every other member's upgrade to produce the same new address as mine, so that we can give out one address.
14. As a member of an upgraded group, I want one action that sweeps the legacy balance to the new address in the Ironwood pool as a normal signing session, so that the funds actually become recoverable.
15. As a member of an upgraded group, I want the warning to stay until the legacy balance is zero, so that creating the sibling account is not mistaken for finishing the job.
16. As a member of any group, I want Orchard-pool notes on a recoverable account to be flagged too, so that I know a payment that arrived in the wrong pool still needs moving.
17. As a member, I want the backup string of a legacy account to be presented as a device-loss backup only, so that I do not believe it protects the funds against the quantum scenario.
18. As a member, I want the full account export to keep working and to carry the new key material, so that a full copy of my wallet stays a complete backup.
19. As a member, I want my backup string to work on any network the group lives on, so that I do not need to know which chain the string was made for.
20. As a member acting as coordinator, I want to run a session without a stored public key package, so that a coordinator who restored from a string can still aggregate.
21. As a member, I want a group member on a new app to be able to coordinate a session that members on an older app can still take part in, so that a group can upgrade one phone at a time.
22. As an operator of a headless zkool server, I want the same operations exposed over GraphQL, so that integration tests and automated custody can run them.
23. As a developer, I want the derivation checked against the published `use_qsk` test vectors, so that a change in the ZIP before NU6.3 is caught by a failing test rather than by lost funds.
24. As a developer, I want a per-account derivation version stored and carried in the backup string, so that a future revision of the derivation can be introduced without breaking older accounts.

## Implementation Decisions

**Assumptions.** Mailbox addresses are exchanged out of band and stay private to the group. Participants are honest during the DKG. These are the conditions under which no message authentication, equality-check round or sealed-contribution round is added to the DKG. `sk` and `qsk` are never placed inside a memo, because Orchard note encryption is not quantum-safe; the out-of-band address exchange is the sole channel through which `sk` is agreed.

**Derivation.** `sk` remains the Orchard spending key of the broadcast account, itself derived from the mnemonic the DKG builds over the n mailbox addresses, unchanged since the first DKG. For a dkg-2 account: `nk = H^nk(sk)`; `qsk = truncate_32(PRF^expand_sk([0x0C]))`; `qk = BLAKE3.derive_key("Zcash ZIP 2005 qk-derivation v1", qsk, 32)`; `rivk = ToScalar(PRF^expand_qk([0x0D] || ak || nk))`; the FVK is `ak || nk || rivk`. `ak` keeps its even-y normalisation. The internal-scope `rivk` follows from the existing ZIP 32 rule and needs no change. The legacy formula, `rivk = H^rivk(sk)`, is kept as the version-0 and version-1 builder. No upstream crate offers these functions; they are implemented in a new keys module of the FROST crate from the BLAKE2b, BLAKE3 and Pallas primitives already in the dependency tree.

**Generations.** Three DKG generations exist and must coexist in one build: dkg-0, before message signing, with no round-0 key and unsigned messages; dkg-1, from message signing to now, with a random ed25519 key and the legacy `rivk`; dkg-2, this spec. `dkg_params` gains a `dkg_version` integer column added idempotently with default 1, and a one-time update sets 0 where the account has no round-0 peer row. `dkg_params` gains a nullable `sk` blob, written for dkg-2 accounts when the frost account is created. The FVK builder is the only code that branches on the version. Signing reads only the key package, the public key package, the sighash and the randomizer, and the Orchard circuit accepts any `rivk`, so signing, proving and sync have no version branch.

**Round-0 version.** The round-0 message carries the derivation version next to the ed25519 public key. When a peer's version differs from ours, `collect` fails the DKG with a new terminal status that names the peer and both versions; the app shows it and tells the user to update. Older builds cannot parse the longer payload and never advance past round 0, which is the intended failure.

**Signing transport, all groups.** Three compatible changes to the signing protocol so that a member needs no peer addresses after the DKG. The signing-time broadcast account is rebuilt from `sk` as a view-only account whose unified address carries only the Orchard receiver; it is the same account the address hash produces, so the on-chain address is unchanged. The coordinator's mailbox address is appended to the signing-package message as a trailing field; the legacy bincode decoder ignores trailing bytes, so older builds keep reading the package and keep resolving the coordinator through the stored addresses, while new builds prefer the field. Each member appends its verifying share to its commitments message as a trailing field; the coordinator rebuilds the public key package from the t participating shares after checking they interpolate to `ak`, and falls back to the stored package when a share is missing. The ed25519 message key stays random; a restored member has none and sends unsigned messages, which the existing dkg-0 compatibility path already accepts, and must not sign with a new key because peers verify against the key published in round 0.

**Backup string.** One bech32m string with human-readable part `zkfrost`, 68 bytes of payload: format version (1 byte, value 1), participant id (1), threshold t (1), group size n (1), signing share (32), `sk` (32). No network identifier and no mailbox seed. Any frost account can export it, including dkg-0 and dkg-1 accounts, whose `sk` is rederived from the stored addresses. The string is sensitive to the same degree as the share: it is shown and copied the way a seed phrase is.

**Restore.** Inputs are the string and the group's UFVK. `ak` is taken from the UFVK; `nk` and `rivk` are recomputed from `sk` and `ak` under the legacy formula and under the ZIP 2005 formula and compared with the UFVK's own. A legacy match creates a dkg-0 account; a ZIP 2005 match creates a dkg-2 account; no match is an error naming the mismatch. The new account gets the key package rebuilt from the share, id, t and `ak`, the `dkg_params` row, `sk` when version 2, a fresh random mailbox, and the birth height set to the Orchard activation height so that a rescan finds the notes. A member of an upgraded group restores twice with the two UFVKs. No peer addresses, round-0 keys or public key package are required; the stored-address path stays empty for the restored member and the new transport covers it.

**Legacy upgrade.** An action on a dkg-0 or dkg-1 frost account creates a second frost account, version 2, from the same key package, public key package and `sk`, with the ZIP 2005 FVK and its new address, and records the pairing. The legacy account is unchanged. All members obtain the same new address because the derivation is deterministic. The sweep is an action on the legacy account that plans a self-send of the full spendable balance to the sibling's Ironwood address through the existing migration planner's fee-only transfer, so the output lands in the Ironwood pool, and runs it as an ordinary FROST signing session.

**Recoverability flag.** An account-level state computed from the notes, not stored: a legacy frost account with a non-zero balance, and any frost account holding spendable Orchard-pool notes, is flagged "not quantum recoverable". The flag drives the upgrade and sweep prompts and clears on its own when the condition no longer holds. The same computation applies to non-FROST accounts for Sapling and Orchard-pool notes, but only the FROST surface is built here.

**API contract.** The app API and the GraphQL schema gain, in matching shape: export of the backup string for an account; restore from string and UFVK, returning the new account id and version; upgrade of a legacy frost account, returning the sibling id; sweep of a legacy frost account into its sibling, returning the signing session handle the existing signing flow reports on; the recoverability state in the account listing. The account export gains `dkg_version` and `sk`, with the import accepting files without them.

**Pages.** The frost account's keys page shows the backup string with the sensitivity warning, and for a legacy account the device-loss-only note. The restore page accepts a `zkfrost` string and a UFVK. The frost account page shows the flag, the upgrade action on a legacy account, and the sweep action once the sibling exists. The DKG page shows the version-mismatch error.

## Testing Decisions

A good test drives the system through a seam a user or an integrator would use and asserts only what they would observe: addresses, balances, a signature that verifies, a transaction that mines, an error message. Tests do not inspect intermediate protocol state or private database columns except where the seam is the database itself.

**Seam 1, the regtest GraphQL stack.** The existing Python harness with its DKG participant class driving `zkool_graphql` on a local zebra chain, as in `test_dkg.py`, `test_dkg_2_of_3.py` and `test_frost.py`. New tests, through the new mutations:
- a three-participant dkg-2 DKG completes and all three report the same address, which differs from the legacy derivation for the same parameters;
- a signing session over the new transport from that group spends an Ironwood note and the receiver's balance changes;
- one participant exports its string, a fresh headless wallet restores from the string and the group UFVK with no addresses entered, and a signing session with that wallet as a participant and then as coordinator succeeds;
- the restore rejects the string with a UFVK from another group;
- a group restored from the legacy fixture upgrades, every participant reports the same sibling address, the sweep mines into the Ironwood pool, and the flag reads false afterwards and true before;
- a session where only the coordinator carries the new trailing fields and the other participants' messages lack them completes, standing in for a mixed-build group.

**Seam 2, the Rust library.** Unit tests run by `cargo test --lib`:
- the derivation against the frost-tools `use_qsk` vectors, and the FVK builder for versions 0 and 2 from the same `(sk, ak)`;
- `zkfrost` encode and decode round trip, and rejection of a wrong checksum, wrong prefix or wrong length;
- restore into an in-memory database for a legacy UFVK and a dkg-2 UFVK, following the in-memory pattern of the existing database and export tests;
- round-0 `collect` with a peer version that differs fails with the mismatch status;
- the signing messages with trailing fields decode under the previous struct shape, and the previous bytes decode under the new one;
- the account export round-trips `dkg_version` and `sk`, extending the tests added in #1335.

The existing legacy fixtures and their DKG and signing tests remain and must keep passing unchanged; they are the regression guard for dkg-0 and dkg-1.

## Out of Scope

- The Recovery Protocol itself. The ZIP defines only the statement; nothing can be built until the protocol exists.
- Message authentication in the DKG, an equality-check round, a sealed-contribution round, or adoption of COCKTAIL-DKG. These address a dishonest participant or a leaked address set, both excluded by the stated assumptions.
- Rotating a member's mailbox address after the DKG, or changing the DKG-time transport.
- Flagging Sapling and Orchard-pool notes on non-FROST accounts, and the general "move everything to Ironwood" prompt the ZIP asks wallets for.
- A Flutter UI test for the new pages; they ship with manual verification and a UI test follows as the send-flow one does.
- Deriving the ed25519 message key from a seed, or any change to how unsigned messages are treated.
- Hardware-wallet FROST members.

## Further Notes

ZIP 2005 is Proposed and zcash/zips#895 is still open. The `0x0C` and `0x0D` domain tags and the BLAKE3 context string could still move before NU6.3; the version column and the vector test are the absorbers. There is no upstream API yet: zcash/orchard#475 is the legacy constructor and is named as incompatible with recoverability, and ZcashFoundation/frost#1094 waits on the ZIP.

The ZIP is explicit that for FROST the threshold protects nothing against a quantum adversary, since every member holds the same `qsk` and `ask` becomes computable from `ak`; it recommends moving FROST funds to a post-quantum threshold pool once one exists. The flag introduced here is the first instance of a warning the app will carry for a long time.

Suggested delivery order, each a PR that keeps the suite green: the derivation module and vector test with the version and `sk` columns and the new FVK builder behind the round-0 version; the signing transport changes; the backup string with export, restore and their tests; the upgrade, sweep and flag with the legacy-fixture test; the pages. The first PR changes nothing on the wire, so it can merge ahead of a decision on timing for the rest.
