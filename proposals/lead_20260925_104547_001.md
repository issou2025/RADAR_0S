# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**product/worktree: auto-follow Working Head + scoped / variant / live collaboration demo**

*Project description:*
## Product problem

Recent hands-on acceptance of **Modeling / Drawing / Render** exposed the same UX failure in several places:

> MonkeyHub currently leaks internal candidate / branch plumbing into ordinary user work.

The system already knows exact source revision, candidate lineage, task ownership, dependencies and artifact bindings. A person should not have to remember:

- which candidate is the newest;
- which branch a Drawing is bound to;
- whether Render is looking at yesterday's candidate;
- which candidate to continue after an Agent finishes;
- whether a newer compatible working result already exists.

That is machine bookkeeping.

The normal user mental model should be:

> **I am working on the current project. MonkeyHub follows the latest valid working state automatically.**

Candidates / branches remain necessary internally for speculation, rollback and parallel execution, but they should become visible only when the user actually needs to compare, fork, freeze, recover or resolve concurrent work.

# Core product rule

> **People operate the project; the system manages candidates.**

Default behavior:

~~~text
Project
  ├─ Accepted / committed source
  └─ Current Working Head   ← ordinary user follows this automatically
~~~

The UI should not require a user to understand candidate IDs or manually select the newest branch after routine work.

Candidate / branch controls should be **progressively disclosed**, not permanently placed in the main workflow.

---

# 1. Auto-follow the current valid Working Head

For ordinary work, Modeling, Drawing, Render and Board should resolve their source automatically from the current project working line.

Example:

~~~text
r182
 ↓ Agent edit
r183
 ↓ human direct edit
r184
 ↓ accepted working continuation
r185
~~~

Normal workspace behavior:

~~~text
Modeling  → current working source
Drawing   → compatible current working source
Render    → compatible current working source
Board     → live/current source where configured
~~~

Do not ask the user to manually choose `candidate-183`, `candidate-191`, etc. merely because the implementation stores them separately.

## Explicit exceptions

A source selector becomes visible only when the user intentionally requests something like:

- compare A vs B;
- keep A and explore B;
- continue from an older revision;
- freeze a Drawing / Render to an exact revision;
- inspect history;
- resolve a concurrent conflict;
- recover an interrupted branch.

---

# 2. Distinguish LIVE / FROZEN / STALE instead of candidate picking

Reuse the source/update policy direction already described in #254.

A project-linked workspace/artifact should expose ordinary states such as:

~~~text
LIVE
  follows the latest compatible Working Head

FROZEN
  intentionally pinned to an exact retained revision

STALE
  source advanced; this representation/artifact is older
~~~

Examples:

~~~text
Drawing / Section A
LIVE · current with r205

AI Render 07
STALE · generated from r201
[new source r205 available]

Competition board
FROZEN · r198
~~~

Cheap deterministic projections may refresh automatically.

Expensive / ambiguous outputs may become STALE and follow their own rerun policy.

The user should reason about **current / stale / frozen**, not internal candidate IDs.

---

# 3. Candidate Graph stays internal by default

Existing candidate lineage remains useful for:

- speculative execution;
- exact-base validation;
- rollback;
- history;
- recovery;
- experiments;
- Agent branches.

Do not delete or flatten it.

But do not make the ordinary user manage it as a primary navigation model.

Conceptually:

> **Candidate Graph = internal speculative execution history.**

It may be exposed inside History / Advanced / Compare when useful.

# 4. Add an explicit Project Worktree Graph for concurrent work

Future multi-Agent work needs a different user-visible concept:

> **Worktree Graph = who/what is currently working from which exact project source, on what scope, and whether those lines can reconcile.**

This is not a second canonical project store.

Prefer a derived/project-runtime projection over existing:

- exact base revision / Stage / candidate refs;
- task/job identity;
- Agent / human owner;
- declared read/write scope;
- current retained result;
- dependency impact;
- status;
- merge/reconcile/conflict state.

Conceptual row:

~~~text
Worktree
  worktree_id
  task_id
  owner / agent
  base_revision
  current_head
  read_scope
  write_scope
  status
  source bindings
  dependency impact
  reconcile status
~~~

Project · accepted r182

├─ Main working line
│   └─ r187 · CURRENT
│
├─ Panny · Render task
│   base r187

~~~

This graph should answer:

1. What is the current project head?
2. What work is running right now?
3. What exact source did each task start from?
4. What scope can each task modify?
5. Which results are ready?
6. Which work is stale?
7. Which branches can reconcile automatically?
8. Where is human judgement actually required?

# 5. Automatic reconcile when scopes do not conflict

The long-term Harness should be able to recognize independent work.

Example:

~~~text
Agent A
write: structure/*

Agent B
write: representation/drawing/*

Agent C
read: design/*
write: representation/render/*
~~~

These should not require a person to manually select and merge candidate IDs merely because they ran concurrently.

Where exact ownership/dependency rules establish compatibility, reconcile automatically through the existing project authority.

Human-visible conflict should be reserved for meaningful overlap, e.g.:

~~~text
Agent A → write wall_17
Agent B → write wall_17
~~~

Then surface:

> Two active worktrees modify the same authoritative scope.

Do not silently choose a winner.

Do not implement a generic Git merge over project JSON.

# 6. Workspace behavior

## Modeling

Default:
- open current valid Working Head;
- after an Agent candidate becomes the accepted/current working continuation, follow it automatically;
- preserve current UI selection/view when safely compatible;
- do not require explicit candidate dropdown interaction for routine continuation.

History / Compare:
- user may inspect old candidates;
- viewing an old candidate must not silently move the Working Head;
- explicit "Continue from here" creates/activates an intentional worktree/fork.

## Drawing

Default:
- follow current compatible design source;
- regenerate semantic architectural base when source advances;
- retain valid representation-only dressing;
- mark invalid anchors/stale representation explicitly.

Do not make a user manually bind every drawing to the newest candidate.

## Render

Default:
- inherit current compatible design source and camera/view where available;
- cheap preview follows LIVE source;
- selected/final expensive render may become STALE rather than silently changing;
- source candidate IDs are advanced details, not normal workflow.

## Board / Publish

Use existing LIVE / FROZEN / STALE semantics for linked artifacts and selected presentation results.

---

# 7. Do not create another source of truth

This issue must reuse existing owners.

Do **not** introduce:

- a second project branch database;
- a parallel candidate store;
- a new Drawing/Render project authority;
- UI-local "current branch" truth that can disagree with Runtime/P036;
- duplicate task/job state.

The Worktree Graph should be reconstructable from authoritative retained project/task/runtime facts wherever possible.

If a small retained worktree record is genuinely required for identity/intent that cannot be reconstructed, first document exactly what fact has no existing owner.

# 2026-09-24 — Demo-first revision: three collaboration semantics

The Worktree Graph should not assume every concurrent branch means the same thing.

Architecture has at least three distinct collaboration needs. V0 should demonstrate all three with one small fixture before expanding the runtime.

The purpose of this demo is not to reproduce Git, Revit, Rhino Worksession, Unreal Multi-User or USD. Those are reference patterns. MonkeyHub must keep its own project authority, semantic identity and dependency model.

## Mode A — Scoped composition worktrees

Use when several people / Agents own different parts of the same project and the outputs should compose into one current project.

~~~text
Master project
├─ facade
├─ core
├─ interior
└─ representation / analysis workers
~~~

This is the useful intent behind Rhino Worksession / linked-model workflows, but the file must not become the long-term ownership boundary.

Why file-based collaboration is insufficient:

- architectural responsibility rarely equals one file;
- cross-file dependencies are not explicit;
- one design decision can affect several files;
- a file boundary does not explain whether two changes semantically conflict;
- users must manually reload and remember which linked file is current;
- the composed project is weaker than the individual file ownership model.

MonkeyHub should make semantic scope the collaboration boundary.

~~~text
Master Working Head r120
│
├─ WT-facade
│  base r120
│  write: envelope/facade/*
│
├─ WT-core
│  base r120
│  write: circulation/core/*
│
└─ WT-interior
   base r120
   write: interior/unit/*
~~~

All worktrees read the same composed project context.

V0 behavior:

- exact base revision per worktree;
- explicit read / write scope;
- non-overlapping scopes reconcile automatically;
- dependency overlap may escalate even if object IDs differ;
- same-authoritative-scope writes become a visible conflict;
- no generic JSON/text merge.

Long-term rule:

> Ownership follows the task / semantic scope, not a permanent file partition.

---

## Mode B — Variant worktrees for parallel design exploration

Use when several people / Agents intentionally solve the same problem in different ways.

These worktrees must not continuously merge with each other.

~~~text
Facade Study
base = r120

├─ Variant A
├─ Variant B
├─ Variant C
└─ Variant D
~~~

They share one exact evaluation context:

~~~text
same base revision
same surrounding project
same camera / section / crop
same scale
same lighting where relevant
same evaluator inputs
same budget / constraints
~~~

This is closer to a USD VariantSet / design-study branch than to ordinary merging.

Introduce or reuse a lightweight source-bound ReviewContext:

~~~text
ReviewContext
  source_revision
  camera / view
  section / crop
  visible scope
  scale
  evaluator set
  optional environment / lighting
~~~

The comparison UI should show A | B | C | D from the same angle / same drawing condition / same evaluation conditions without a person manually matching each one.

This is also the natural container for later OCBA / sequential allocation experiments:

~~~text
same State
→ independent Variant Worktrees
→ comparable rollout results
→ evaluator
→ allocator decides which variants receive more budget
~~~

V0 behavior:

- Explore alternatives creates sibling Variant Worktrees from one exact base;
- variants remain isolated during exploration;
- each remains source-bound and reproducible;
- Compare automatically uses one ReviewContext;
- user may retain / reject / select a direction;
- only explicit continuation advances the relevant project scope;
- candidate IDs remain implementation detail.

---

## Mode C — Live transaction worktree

Use when several people / Agents are editing one composed project state at the same time and the desired experience is closer to Revit worksharing / Unreal Multi-User.

Do not assume the old production pattern must remain:

~~~text
Architect A permanently owns floor 3
Architect B permanently owns floor 4
Architect C permanently owns facade file
~~~

The durable concept should instead be:

~~~text
actor
+ task
+ exact base
+ semantic lease / write scope
+ transaction stream
+ validation
~~~

People and Agents are both actors.

Useful Revit lesson:

- one shared project authority;
- local / temporary editing context;
- fine-grained edit ownership / borrowing;
- synchronize accepted edits into the shared project;
- reload the latest accepted changes.

Do not copy the idea that worksets should map permanently to people. MonkeyHub should use task-scoped semantic ownership.

Useful Unreal lesson:

~~~text
durable project / source control
        +
live transaction session
~~~

A live session is not canonical authority by itself.

For V0, do not build full networked real-time editing. Demonstrate the semantics locally:

- two actors attach to the same Working Head;
- operations appear as typed transactions;
- compatible transactions compose into the current view;
- overlapping writes show a lease / conflict state;
- accepted transactions materialize into a new immutable State revision;
- reopen can rebuild from durable State rather than session memory.

Long-term rule:

> Task-scoped semantic leases instead of permanent person-scoped model partitions.

# Demo acceptance: UI first, infrastructure second

This is an interaction / architecture proof, not a distributed-systems project yet.

V0 may:

- run all actors locally;
- use deterministic worker identities;
- reuse existing retained State / Candidate / Task records;
- use a read-only Worktree Graph plus minimal actions;
- avoid networking, presence avatars, chat and generic merge UI.

But it must not fake the semantics:

- exact base must be real;
- Current Working Head must be real;
- scopes must be explicit;
- Variant comparison must truly share one ReviewContext;
- LIVE / FROZEN / STALE must derive from real source bindings;
- conflict must come from actual overlapping authority / dependency, not a hard-coded demo label.

The first product question is:

> Does this collaboration model feel substantially clearer than manually choosing candidates / branches / linked files?

If yes, deepen the runtime. If no, revise the interaction before building distributed collaboration.
