**[Bug]: GetSetArgument can loop forever on a malformed file: its walk has no end-of-tape check**

*Project description:*
### What happened?

A malformed `.ifc` loads normally, and then the first geometry call never returns. `OpenModel` succeeds and `StreamAllMeshes` spins at full CPU until it is killed. No API misuse is needed: the file alone does it.

This is a robustness report, not a claim that these files are valid or should parse. They should fail rather than hang.

It can come from real files too. A real 190 KB Archicad export, truncated at every 101st byte, hung on 16 of 1888 cuts, all inside the unit definitions, all at `IfcCache.cpp:313`. The same cuts also segfaulted on 553 and aborted on 52, which I have not investigated. A 2 MB Revit export, truncated the same way at every 1009th byte, had no hang or crash in 2015 cuts.

**Mechanism** (line numbers on `main` at `50153fad`):

- `IfcLoader::GetSetArgument()` (`IfcLoader.cpp:519`) reads one byte as "set begin" without checking it (`:524`), then loops on `while (depth > 0)` with no end-of-tape check (`:526`).
- At the end of the tape, `IfcTokenStream::Forward()` clamps `_readPtr` to the tape size, and `Read<char>()`, which has no bounds check, returns the byte one past the end.
- gdb, attached twice a few seconds apart, shows the same frame both times: `depth` = 1, `_readPtr` equal to `_currentSize`, and that byte = `0x00`. So it hits `default:`, logs, and loops with no state change.
- That byte is uninitialised heap (`new uint8_t[chunkSize]`). `0x08` is `SET_END`, so the outcome at the end of the tape depends on uninitialised memory. In my runs it was always `0x00`; with `MALLOC_PERTURB_=247`, which fills new memory with `0x08`, the reproducer terminates. I only measured Linux with GCC 13, and Node for the npm build.

**When it does not hang.** It is not "any non-list". A `$` or a nested list returns without a log line. Most single references return after about four log lines, but one whose id contains the byte 5 or 7 (`#5`, `#7`, `#263`) still spins. A string, number or enum in a list slot depends on its length bytes, which get read as tokens, and on the file's size. The reliable cases are the ones above: the cursor left on a line's closing `)`, or a line with an unbalanced `(`.

**Related work I found:**

- #1788 fixed this same loop at one call site, with the comment at `IfcCache.cpp:268`. Almost all of the 70 `GetSetArgument()` calls in `IfcCache.cpp`, `IfcGeometryLoader.cpp` and `IfcGeometryProcessor.cpp` trust the token.
- #2150 / #2151 bounded the tokenizer's end-of-file scans, but not these walkers.
- `GetSetListArgument` (`:562`) and `ArgumentOffset` (`:616`) have the same `while (true)` shape with no end check.

**`GetSchema()` now reaches this too, and that part is on me.** The `GetSetArgument()` call in `GetSchema()` came from the fix I suggested in #2302, and #2316 correctly merged it: it also fixes the crash on a missing `FILE_SCHEMA`. I did not consider a `FILE_SCHEMA` that is not a list. On `main`, `FILE_SCHEMA();` hangs in `GetSchema()` on every size I tried (0.9 KB to 11 MB), where `0.78` returned IFC2X3. `FILE_SCHEMA('IFC4');` hung on small files and on 3 of 8 real models I tried (10.8 to 11 MB), and returned on the other 5, again depending on bytes. This is native only: nothing in the library calls `GetSchema()` except its test, and the wasm API does not. Such a header is not valid Part 21 and I have seen no exporter write one, so it is minor, but `GetSchemaTestNoFileSchema` does not cover it and a test for it would hang CI.

**A direction that worked here.** On a scratch native build of `0.78`, making `IfcTokenStream::Read<T>` throw at the end of the tape turned these hangs into an immediate failure (about 0.15 s, an uncaught exception in my harness) and left five valid real models unchanged. It also made 697 of the 1204 truncated-file runs that previously completed fail. I did not measure its cost on a hot path or try it in wasm, so treat it as a data point, not a proposal.

### Version

npm `web-ifc` 0.0.78 and tag `0.78` (`4310503d`), and `main` at `50153fad` (2026-11-01), natively. Node v24 and a native build (GCC 13) on Linux; not a browser. `main` was tested natively only.

### Relevant log output

```
[error] [GetSetArgument[]) unexpected token
```

On the 900-byte reproducer that line repeats about a million times a second (about 70 MB/s). On larger models it is slower, since evaluating `GetCurrentLineExpressID()` for the log call scans all lines (about 150 k lines/s on a 2 MB model), and that happens even with the log level off. Memory stays flat.

### Anything else?

Not tested: other platforms and compilers, the multithreaded wasm build, wasm outside Node, and each of the 70 call sites individually. I did not diagnose the segfaults and aborts in the truncation sweep.
