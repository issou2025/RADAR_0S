# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Linux: libssh2 is shipped as libssh2.so but libgit2.so needs libssh2.so.1, so a packaged app cannot load libgit2**

*Project description:*
**Version:** git2dart_binaries 1.14.0 (libgit2 1.9.7, libssh2 1.11.1), `linux/` artifacts. Same in 1.13.0.

## What happens

`libgit2.so` asks for libssh2 by its SONAME, but the file is shipped under its development name:

```
$ readelf -d linux/libgit2.so | grep ssh2
 (NEEDED)  Shared library: [libssh2.so.1]
$ readelf -d linux/libssh2.so | grep SONAME
 (SONAME)  Library soname: [libssh2.so.1]
```

The dynamic linker resolves a `NEEDED` entry by file name. Flutter's Linux plugin install step (`install(FILES ${bundled_libraries} DESTINATION lib)`) copies the file as it is named. So a built bundle contains `lib/libssh2.so` and nothing named `libssh2.so.1`:

```
$ cd build/linux/x64/release/bundle/lib && LD_LIBRARY_PATH=. ldd libgit2.so | grep ssh
	libssh2.so.1 => not found
```

`git2dart`'s loader can preload libssh2 by absolute path, but it resolves that path from the pub cache. That cache exists on a developer's machine and not on an end user's. So this works under `flutter run` and `flutter test`, and only fails in a packaged application. It looks like the Linux counterpart of #14.

## Where it comes from

`.github/actions/build-linux/action.yml`:

```sh
cp /tmp/libssh2/install/lib/libssh2.so /tmp/export/libssh2.so
```

`install/lib/libssh2.so` is the unversioned development symlink. Copying it follows the link, so the bytes are the real library under the wrong name.

## Two possible fixes

1. **Ship it as `libssh2.so.1`** (copy `install/lib/libssh2.so.1`, and list that name in `linux/CMakeLists.txt`'s bundled libraries). This is the minimal change.
2. **Link libssh2 and OpenSSL statically into `libgit2.so` on Linux**, as `fc80f9f` did for macOS. I think this is the better one, for a second reason. OpenSSL 3.0.15 is built from source as a shared library, but it is not shipped. So `libgit2.so` and `libssh2.so` also need `libssl.so.3` / `libcrypto.so.3` from the user's system, and the OpenSSL that actually runs is whatever the distribution has, not the one in `openssl-provenance.json`:

   ```
   $ readelf -d linux/libgit2.so | grep NEEDED
    [libssl.so.3] [libcrypto.so.3] [libssh2.so.1] [libz.so.1] [libc.so.6]
   ```

   A static build would remove both the file-name problem and the runtime dependency on a system OpenSSL 3. Windows already bundles its own OpenSSL runtime (#20).

## Our workaround, in case it helps anyone else

We rename the file in the bundle before packaging (`mv lib/libssh2.so lib/libssh2.so.1`). Don't use `patchelf --replace-needed libssh2.so.1 libssh2.so lib/libgit2.so`. It makes the library load, but rpm then derives `Requires: libssh2.so()(64bit)` from the edited `NEEDED` while still deriving `Provides: libssh2.so.1()(64bit)` from the unchanged SONAME. The result is an rpm that nothing can satisfy.
