### Steps to reproduce

1. Create a Flutter Windows app using `media_kit`/`media_kit_video` (a `Texture`-backed video widget). Full minimal repro below.
2. Open a network video stream into a `Video` widget.
3. After playback has started, remove the `Video` widget from the tree via `setState` (same `Scaffold`, same route — **no `Navigator.pop()` involved**).
4. Compare what Flutter thinks it painted (captured via `RenderRepaintBoundary.toImage()`) against what is actually presented on screen by the OS (captured externally via `PrintWindow`/`PW_RENDERFULLCONTENT`, or simply look at the window).

### Expected results

The window should display the new frame (the `Text` widget that replaced `Video`).

### Actual results

Flutter's internal render tree is correct — `RenderRepaintBoundary.toImage()` immediately after removal shows the expected content (`Text('CE TEXTE DEVRAIT ETRE VISIBLE A L'ECRAN')` under an `AppBar` titled "Video retiree"). But the actual window, as presented by Windows, shows **stale/incorrect content that never updates again** — in our latest run, solid black (the video's last frame), in earlier runs of the same repro we also observed the window showing pixels belonging to a **completely unrelated application** (confirmed via NVDA's screen-recognition feature, which reads the literal displayed pixels). The window never recovers: minimizing/restoring and resizing the window do not help. The app keeps running and processing normally (not hung — `Process.Responding == true`, and the internal render tree keeps updating correctly on further `toImage()` calls), only the on-screen presentation is broken.

This matches the symptom historically reported in #78648 ("Drawing in Texture() buffer on Windows causes viewport corruption on other widgets in screen"), which was closed as fixed via engine PR #25193 back in 2021. We are reproducing this (or a very similar regression) on current `stable` (3.44.8) — so either a regression, or an unfixed edge case of the same underlying issue.

### Isolation done so far (rules out media_kit / GPU-specific causes)

Tested each of these independently; the corruption persists in **every** case:
- The underlying `Player` is **never disposed** (`player.dispose()` never called) — only the `Video` widget is removed from the tree.
- Using `Offstage` (widget stays mounted, `State` never disposed) instead of fully unmounting the widget — still corrupts, as soon as the video's layout size goes to `0x0`.
- No `Navigator.pop()` at all — same route, same `Scaffold`, just a `setState` swapping the body.
- `VideoControllerConfiguration(enableHardwareAcceleration: false)` (media_kit's software rendering path instead of Direct3D/ANGLE) — still corrupts.

So the common factor is specifically: **a `Texture`-backed widget changing presence/size in the tree**, independent of the plugin's disposal logic or GPU backend choice.

// pubspec.yaml: media_kit: ^1.1.11, media_kit_video: ^2.0.1
import 'package:flutter/material.dart';
import 'package:media_kit/media_kit.dart';
import 'package:media_kit_video/media_kit_video.dart';

late final Player player;
late final VideoController videoController;

void main() {
  MediaKit.ensureInitialized();
  player = Player();
  videoController = VideoController(
    player,
    configuration: const VideoControllerConfiguration(enableHardwareAcceleration: false),
  );
  runApp(const MyApp());
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});
  @override
  Widget build(BuildContext context) => const MaterialApp(home: Repro());
}

class Repro extends StatefulWidget {
  const Repro({super.key});
  @override
  State<Repro> createState() => _ReproState();
}

class _ReproState extends State<Repro> {
  bool _showVideo = true;

  @override
  void initState() {
    super.initState();
    _run();
  }

  Future<void> _run() async {
    await Future<void>.delayed(const Duration(seconds: 2));
    player.open(Media('https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8'));
    await Future<void>.delayed(const Duration(seconds: 5));
    // From here on, the window stops presenting new frames on Windows.
    setState(() => _showVideo = false);
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text(_showVideo ? 'Video visible' : 'Video retiree')),
      body: _showVideo
          ? Video(controller: videoController)
          : const Center(child: Text("THIS TEXT SHOULD BE VISIBLE ON SCREEN")),
    );
  }
}

### Context

We hit this in a real app ([iptv_player](https://github.com/nael-sayegh/iptvplayer), an accessibility-focused IPTV player) where closing a video-playing screen (`Navigator.pop()`, triggered by pressing Escape) reliably left the window frozen on stale content on Windows — confirmed via NVDA's screen-recognition feature reading pixels belonging to an unrelated application. This forced us to work around the bug by launching an external video player process instead of using Flutter's own video widget on Windows, since no in-app mitigation (listed above) resolved it. Happy to provide more logs/repros if useful — this was found via fairly extensive isolation testing, not a one-off observation.
