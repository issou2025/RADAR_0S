## Required implementation contract
### Persistent destination capability
- Native channel launches `ACTION_OPEN_DOCUMENT_TREE` and requests read/write + persistable grants only.
- Persist durable tree capability as device/platform state under app-private `state/backup_destination.json` (or the narrow equivalent established by `AppDirectories`), not SQLite product data and not inside `.csebackup`.
- Stored state must be bounded/non-secret capability metadata such as tree URI, granted flags, safe display name and last validation time; do not store arbitrary file bytes.
- Revalidate persisted permission + tree availability on use/restart. Revoked/missing => fail closed, explain and offer re-selection. No silent fallback that falsely claims an external verified backup succeeded.

### Verified external backup export
1. Existing `createBackup` first produces its current verified internal `.csebackup`; do not alter package format.
2. Copy/stream that exact package into the authorized tree/`Şefim` child with a deterministic collision-safe name (`sefim-backup-<UTC>.csebackup`, suffix if necessary).
3. Never overwrite an existing document.
4. Flush/close destination, reopen it and verify exact byte size + SHA-256 against the internal source.
5. Report external success only after verification.
6. On failure, delete only the exact document created by that operation; never touch prior valid backups.

### Restore source
- Enumerate only direct `.csebackup` children of the configured authorized folder.
- Selecting one must feed the bytes through the existing protected internal import/staging verification boundary before `preflightBackup` / `restoreBackup`.
- No direct restore from arbitrary external URI/handle.
- Existing #503 safety-before-restore/newer-live-data protections remain unchanged.

### UI
- Memory/Backup page exposes configured-folder state, first selection, change/re-authorize and unavailable/revoked states without turning the screen into a storage manager.
- Existing share/save fallback stays visible/reachable.
- User-facing success must distinguish internal backup creation from successfully verified external-folder copy.

## Failure model that must be covered
- folder not configured;
- permission revoked;
- tree missing/unavailable;
- disk/write error;
- partial document;
- byte-size mismatch;
- SHA-256 mismatch;
- filename collision;
- restart/update with persisted grant;
- malformed/corrupt destination-state file;
- unsupported platform call.

All fail closed without deleting prior backups or mutating live product data.
