# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Simplify development documents into contract-first two-person handoffs**

*Project description:*
Supersedes #22.

## Problem Statement

LocateMY 当前的 Development Documentation Package 规范把学生工作包设计成版本锁定、可审计的 PDF 发布套件。Authentication & Session 试点因此产生了 Manifest、Feature Guide、多个 Data Contract、文档 ID、版本号、校验和、Locked Source Set、Generation Gate、Development Release 和 Invalidated 生命周期。

这些机制没有解决两名学生协同开发最重要的问题：一个 Owner 到底需要调用另一个 Owner 的什么 Interface，以及必须向对方提供什么 Interface。现有 AUTH-001 一类标识主要描述动作和可观察语义，却没有给出公开 import 位置、Dart 声明、输入输出类型、失败类型、状态变化或调用顺序。实施者还必须在 Capability ID、Requirement ID、Acceptance ID 和 Interface ID 之间反复翻译。

现有设计边界也存在直接冲突：高层设计规则禁止语言级符号、参数和 DTO，但两名 Owner 若不知道跨模块公开声明的确切格式，就无法真正独立实现、使用 fake Adapter 验证并在最后稳定集成。

本项目只有两名学生，开发文档在派工后很少修改，Git 已能保存历史。当前套件的发布治理成本和阅读成本明显高于它提供的协作价值，需要改为单份、契约优先的开发说明。

## Solution

把每个 owning Feature 或 shared module 的 Markdown 设计升级为唯一的开发协作契约（Development Contract）。它同时服务设计协调、实施和联调；PDF 只是同一内容的等价导出，不再生成平行的 Feature Guide、Package Manifest、Calculation Specification 或 Data Contract PDF。

每份契约先说明双方职责，再分别列出“需要调用的 Interface”和“必须提供的 Interface”。凡被另一个 Owner 使用的 Interface，都必须固定真实的公开入口和声明级格式，包括输入、输出、失败、状态、副作用、权限及调用顺序。Module 内部实现仍由 Owner 决定。

每个 Module 只提供一个供其他 Owner import 的公开入口。提供方先提交并合入声明级 Interface，消费者随后可以针对相同 Interface 使用 fake Adapter 并行开发。生产实现、消费实现和少量跨模块验收都通过同一 seam 验证。

删除文档版本、checksum、Manifest、Locked Source Set、Generation Gate Report、Development Release 和 Invalidated 状态机。Git 与普通 PR 保存历史；公开 Interface 变更只需提供方说明影响、消费方确认，并在同一 PR 更新声明、契约和相关测试。

同步修改设计总规范、Feature/shared module 模板、人类交付规范和相关 ADR。以 Authentication & Session 重写单份代表性开发协作契约及 PDF，把旧的四份 PDF 套件移入历史文档区域。

## User Stories

1. As a student implementer, I want one document for my assigned Module, so that I do not need to reconstruct the task from several PDFs.
2. As a student implementer, I want the first page to state the outcome, Owner, dependencies and definition of done, so that I can start with the correct mental model.
3. As a student implementer, I want human-readable names before short IDs, so that I can understand a requirement without decoding AUTH-0X-style identifiers.
4. As a student implementer, I want a dedicated “需要调用的 Interface” section, so that I immediately know what another Owner must supply.
5. As a student implementer, I want a dedicated “必须提供的 Interface” section, so that I immediately know what other Modules expect from me.
6. As a consuming Owner, I want the exact public import location, so that I do not import another Module’s internal files.
7. As a consuming Owner, I want declaration-level Dart members and types, so that my code can compile against the agreed Interface.
8. As a consuming Owner, I want every input’s type, nullability, unit and constraint, so that I do not guess the caller contract.
9. As a consuming Owner, I want every return variant explained, so that I handle success, absence and failure correctly.
10. As a consuming Owner, I want failures represented as distinguishable results, so that I do not parse messages or collapse different recovery paths.
11. As a consuming Owner, I want state changes and side effects documented, so that I know what remains true after a call completes.
12. As a consuming Owner, I want ordering and lifecycle constraints documented, so that I do not invoke a valid operation at an invalid time.
13. As a consuming Owner, I want permissions and account isolation stated at the Interface, so that I cannot accidentally expose another account’s data.
14. As a consuming Owner, I want a minimal invocation example, so that the intended use is immediately visible.
15. As a consuming Owner, I want a fake Adapter to satisfy the same Interface as production, so that I can work before the provider is complete.
16. As a providing Owner, I want one public entry point for my Module, so that callers cannot couple themselves to internal implementation files.
17. As a providing Owner, I want all consumers named, so that I can judge the impact of an Interface decision.
18. As a providing Owner, I want Interface declarations agreed before implementation starts, so that parallel branches do not invent incompatible shapes.
19. As a providing Owner, I want freedom over private files, helpers, Widgets, state management and SDK mapping, so that the contract does not become an implementation blueprint.
20. As a providing Owner, I want performance, cancellation, caching and concurrency included only when another Owner depends on them, so that the Interface stays small.
21. As a Module Owner, I want one deep Interface rather than many pass-through surfaces, so that callers learn less and implementation knowledge remains local.
22. As a Module Owner, I want a typed, Module-specific result model rather than a mandatory global Result wrapper, so that failure semantics fit the domain without creating a shallow abstraction.
23. As a database-accessing Owner, I want the exact table, View or RPC fields I use, so that I can implement data access without searching unrelated schemas.
24. As a database-accessing Owner, I want CRUD, RLS and account rules beside those fields, so that persistence code respects security boundaries.
25. As a non-database-consuming Owner, I want only the public Dart data model, so that I do not become coupled to another Module’s persistence schema.
26. As a Flutter composition Owner, I want public Widget inputs, callbacks and navigation intents specified when they cross ownership, so that independently built UI Modules compose correctly.
27. As an Owner consuming a View or RPC, I want its exact name, parameters and returned row shape, so that backend and Flutter work agree.
28. As a student implementer, I want implementation stages after the Interface sections, so that contractual dependencies guide the work order.
29. As a student implementer, I want named scenarios such as “离线恢复会话” rather than AT codes in the main text, so that tests describe recognizable behavior.
30. As a student implementer, I want clear blocking items in the same document, so that I know what is missing without reading a separate Gate Report.
31. As a student implementer, I want large formulae and schemas linked to their authority but relevant inputs repeated locally, so that the document is complete enough without copying an entire catalog.
32. As a project owner, I want only four readiness checks, so that incomplete collaboration contracts are caught without a release bureaucracy.
33. As a project owner, I want Owner, dependency order, Interface formats, relevant data rules and joint acceptance known before development, so that parallel work begins safely.
34. As a project owner, I want Git and PR history to record changes, so that document-specific versions and checksums are unnecessary.
35. As a project owner, I want both affected Owners to confirm a public Interface change, so that one side cannot silently break the other.
36. As a project owner, I want the Interface declaration, development contract and related tests updated in the same PR, so that code and documentation do not drift.
37. As a project owner, I want stable human-readable PDF names, so that team members can find the current contract without interpreting package IDs or versions.
38. As a project owner, I want old package PDFs removed from the active handoff area, so that obsolete process artifacts do not appear current.
39. As a design AI, I want permission to define declaration-only public Interfaces and data types, so that I can specify collaboration without implementing student code.
40. As a design AI, I want the prohibition on function bodies, Widget implementations, migrations and test implementations preserved, so that students still write all executable behavior.
41. As a reviewer, I want every cross-Owner Interface checked for location, declaration, inputs, outputs, failures, side effects, order and permissions, so that “Interface complete” has an objective meaning.
42. As a reviewer, I want the final PDF compared with its Markdown source, so that export does not omit or alter contractual content.
43. As a reviewer, I want a developer walkthrough, so that document usability is measured by whether a student can identify the actual collaboration seam.
44. As a providing Owner, I want tests against the real Adapter, so that the implementation proves it satisfies the public Interface.
45. As a consuming Owner, I want behavior tests against a fake Adapter, so that my Module remains independently testable.
46. As both Owners, I want only a small number of cross-module flow tests, so that joint behavior is proven without duplicating each Module’s internal suite.
47. As a future maintainer, I want engineering delivery terminology kept out of the LocateMY product glossary, so that product language is not polluted by documentation mechanics.
48. As a future maintainer, I want one ADR to explain the contract-first handoff choice, so that the simplified process and its trade-off remain understandable.
49. As an Authentication & Session implementer, I want its public session Interface expressed in exact Dart-level terms, so that Application Shell, Account Privacy and Account Center can integrate without guessing.
50. As an Authentication & Session consumer, I want authenticated, unauthenticated, verification-required, unavailable and failure results distinguishable, so that private UI cannot be opened from an ambiguous session fact.

## Implementation Decisions

- The canonical engineering delivery artifact is the Development Contract. It is the existing owning Feature/shared module Markdown enhanced for implementation collaboration, not a new product-domain concept.
- The Development Contract Markdown is authoritative for its Module’s cross-Owner collaboration. A single PDF with equivalent content is exported for human reading.
- One implementation assignment produces one PDF. Separate Manifest, Feature Implementation Guide, Calculation Specification and Data & Dataset Contract PDFs are removed.
- PDF is no longer governed as an independently versioned release artifact. Git commits and PRs provide history.
- Document IDs, document versions, checksums, generator versions, Locked Source Sets, Generation Gate Reports, Development Release approval and Invalidated lifecycle states are removed.
- A Development Contract has the following fixed reading order: task outcome; responsibilities and dependency order; Interfaces the Owner must call; Interfaces the Owner must provide; directly used data; recommended implementation order; joint integration and acceptance scenarios; internal implementation freedom; blockers and authoritative references.
- The first page must make the task outcome, Owner, dependencies and definition of done understandable.
- The body uses human-readable feature, Interface and scenario names. Requirement IDs are removed. Capability and Interface IDs may appear only as secondary references and in an optional final traceability table.
- Every cross-Owner Interface receives a contract card containing: human-readable name and optional ID; Owner and consumers; public import location; declaration-level Dart shape or exact View/RPC call format; inputs and constraints; outputs and meanings; typed failures and caller handling; state and persistence effects; ordering and lifecycle; permission/account isolation; a minimal invocation example; and a contract scenario usable with a fake Adapter.
- Performance, cancellation, concurrency, caching and similar characteristics are added only when observable by or required by another Owner.
- Every Module exposes one public entry point to other Owners. The entry point may export the minimum set of required declarations. Consumers may not import internal implementation files.
- The public Interface is a complete caller contract, not merely a Dart interface keyword. It includes declarations, invariants, ordering, errors, required configuration and any cross-Owner performance characteristics.
- Declaration-only Dart Interfaces, public data types, public Widget inputs/callbacks, navigation intents and exact View/RPC contracts are permitted design output. Function bodies, Widget implementations, private helpers, SDK mapping, SQL migrations and test implementation remain prohibited AI output.
- Every Interface used by another Owner must be exact regardless of whether it represents domain data, UI composition, navigation, callbacks, streams, storage access, a View or an RPC.
- Module-internal Supabase SDK Adapters, repositories, private Widgets and implementation seams are not specified unless they themselves cross ownership.
- Results and failures are typed so consumers can distinguish every required response. The standard does not mandate a global Result wrapper; each Module uses the smallest result model that communicates its actual contract.
- Only the Owner that directly accesses a database object receives its schema fields, nullability, keys, permissions and CRUD/RLS rules. Other Owners consume the public Module data model rather than the persistence schema.
- Large formulae and schema catalogs keep their existing authority. The Development Contract links them and repeats only the inputs, fields, units, bounds and rules necessary for the assigned work.
- Before parallel implementation, the providing Owner submits and merges the public entry point and declaration-level Interface in a small contract-first change. Both branches then use that exact seam.
- Readiness is reduced to four checks: ownership/dependency order is clear; every cross-Owner Interface is complete; relevant data and permission rules are complete; joint Interface-level acceptance scenarios are complete.
- Missing readiness information is recorded as a blocker in the owning document. It does not generate a separate report or partial publication lifecycle.
- A public Interface change requires the provider to explain reason and impact, the consumer to confirm, and one PR to update the declaration, Development Contract and affected tests. The PDF is then re-exported without introducing a document version.
- Providing Owners prove real Adapters satisfy the Interface. Consuming Owners test their behavior using fake Adapters at the same seam. Both Owners maintain only the cross-module flow tests needed for collaboration.
- PDF presentation keeps Chinese text searchable and copyable, prevents declarations and important table rows from being cut across pages, and places call/provide Interface sections near the front. Complex publication preflight and page-count budgets are removed.
- Diagrams are optional. A single simple diagram is added only when ordered cross-Owner interaction cannot be explained clearly with short numbered steps.
- Markdown and PDF use the same stable, human-readable basename without package IDs or version suffixes.
- The design entry documentation, Feature template, shared-module template and human handoff standard are revised to reflect the single Development Contract model.
- The existing high-level-boundary ADR is revised where it prohibits all language-level symbols, parameters and DTOs. It continues to protect Module-internal implementation freedom.
- The version-locked PDF package ADR is superseded by a new contract-first two-person handoff ADR.
- The Authentication & Session owning design becomes the representative pilot: it must expose exact caller-facing session declarations and results for Application Shell, Account Privacy and Account Center, while keeping Supabase SDK details internal.
- Authentication & Session is re-exported as one human-readable PDF. The current Manifest, Guide and two Data Contract PDFs are removed from the active handoff area and retained only as historical material.
- This specification supersedes Issue #22.

## Testing Decisions

- The highest acceptance seam is: given an owning Feature Markdown whose cross-Owner Interface design is complete, export one equivalent Development Contract PDF from which either student can accurately identify what to import, what to call, what to provide, every input/output/failure meaning, and how the two Modules integrate.
- Tests and reviews assert external contract and document behavior rather than template, converter or PDF-renderer internals.
- Authentication & Session is the representative fixture because it coordinates session state, Application Shell gating, Account Privacy lifecycle and Account Center identity display.
- A structural review verifies the fixed section order and confirms that both “需要调用” and “必须提供” sections appear before implementation stages.
- An Interface completeness review verifies public location, declarations, input constraints, result variants, failures, side effects, lifecycle/order, permissions, invocation example and fakeable scenario.
- A dependency review proves consumers import only the provider’s public entry point and do not depend on internal implementation files.
- A provider-side contract test proves the real Adapter satisfies the declared Interface and required result semantics.
- A consumer-side behavior test uses a fake Adapter implementing the same Interface; it must not require the real provider implementation.
- Cross-module tests cover only consequential joint flows. For the pilot these include session restoration and gating, registration/verification outcomes, logout with privacy closure, and switching from account A to account B.
- Data checks verify that only the directly accessing Owner receives persistence details and that downstream consumers receive only public Module types.
- A Markdown-to-PDF comparison confirms that declarations, tables, human-readable scenario names and blockers are not omitted or semantically altered.
- PDF checks are limited to readable/searchable Chinese text and unbroken declarations/tables. Whole-binary snapshots, checksum verification, bookmarks and publication lifecycle checks are removed.
- Manual acceptance includes a walkthrough in which a student identifies the first implementation action, public import, callable members, provided members, result/failure meanings and joint integration scenarios without consulting the previous package PDFs.
- Existing prior art includes the Authentication & Session owning design, the system Interface registry, Feature/shared module templates, human handoff template and current cross-module acceptance scenarios. These are revised rather than surrounded with a parallel workflow.

## Out of Scope

- Implementing Authentication & Session application behavior, Widget bodies, Supabase SDK adapters, migrations or tests.
- Designing private files, helpers, state-management choices, internal repositories, retry algorithms or test organization.
- Introducing a global Result abstraction or forcing identical failure types across unrelated Modules.
- Changing LocateMY product capabilities, formulas, geographic meanings, data ownership or RLS policy semantics.
- Rewriting the product knowledge base or adding delivery-process terminology to the product glossary.
- Generating separate calculation, dataset, Manifest, Gate Report, review or release PDFs.
- Building a general-purpose document versioning, checksum, invalidation or release-management system.
- Prescribing a PDF rendering library, CI provider or visual theme.
- Bulk rewriting every existing owning design in the first implementation; the Authentication & Session pilot and reusable standards/templates are the required scope.
- Writing compilable implementation bodies on behalf of either student.

## Further Notes

- The key trade-off is explicit: the project gives up artifact-level release auditing in exchange for a much smaller, directly usable collaboration contract suited to a two-person student team.
- “Interface” includes everything a caller must know, not only a type declaration. Exact declarations are necessary but insufficient without failure, ordering, permission and side-effect semantics.
- The one-public-entry rule is intended to create a deep Module: a small caller surface hiding substantial implementation behavior.
- The contract-first code change remains student-authored. Allowing design AI to define declaration-only surfaces does not transfer implementation work from the students.
- Git history is sufficient because these documents are expected to change rarely, and any actual Interface change already requires a reviewed code change.
- Human-readable prose is primary. Short IDs remain optional navigation aids and must never be the only way a student understands a responsibility or scenario.
