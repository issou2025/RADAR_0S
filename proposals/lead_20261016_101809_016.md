## Problem Statement

A developer who wants to use simllms today cannot install it. `cargo add simllms` and `pip install simllms` both fail: the library is functionally complete for its v1 scope — Chat, streaming, Structured Output, Image Generation, the Capability Gate — but nothing has ever reached a registry, so evaluating it means vendoring a git checkout. The version number that a release would carry is also unstated in truth: it lives in four places with no mechanism keeping them equal, so the first Release could ship a Rust crate and a Python wheel with different numbers — precisely the promise the spec made against ("versions move in lockstep, single version source").

The maintainer's failure mode is asymmetric and permanent. A release cut by hand can produce a package with an empty registry page, missing license files, or two registries disagreeing about the version — and neither registry lets a taken version number be reused. One mistake consumes a number forever, on a line that has never run before.

## Solution

One act — pushing a tag — produces a **Release**: the same version number on crates.io and PyPI, prebuilt wheels for a stated platform set, an sdist, and a GitHub Release whose notes come from the changelog and state which Catalog **Snapshot** the package was built against.

The version number has exactly one **Authoritative Version** home; every other copy is derived, and a machine check keeps the derived copies honest on every PR. Before anything is published, the artifacts themselves are installed and inspected at a single seam — the published artifact — so a green pipeline means "the package is complete and behaves as documented", not "the build step exited zero". The whole line can be exercised end to end without publishing anything, so the first real Release is not also the first test.

## User Stories

1. As a developer evaluating simllms, I want `cargo add simllms` to work, so that I can try the library in five minutes instead of pointing at a git checkout.
2. As a Python developer, I want `pip install simllms` to hand me a prebuilt wheel, so that I never need a Rust toolchain to use the library.
3. As a Python developer on an ARM Linux server, I want an aarch64 wheel, so that installation doesn't silently fall back to compiling Rust on a machine that cannot.
4. As a maintainer, I want one place that declares the version number, so that the two packages cannot drift and I don't have to remember four files.
5. As a maintainer, I want that declaration to appear in a PR diff, so that a version change is reviewed like any other change instead of being minted by a tag.
6. As a user, I want the reported package version to come from the compiled binary, so that the number I print at runtime is the number that was actually built.
7. As a CI job, I want a check that every derived copy equals the Authoritative Version, so that a change to the changelog that forgets the version fails immediately.
8. As a maintainer, I want pushing a tag to be the only act needed to ship, so that release day involves no local build that could differ from CI's.
9. As a maintainer, I want the release to refuse a tag that isn't in the main branch's history, so that what ships is always reviewed code.
10. As a maintainer, I want the release to refuse pre-release suffixes for now, so that we don't grow a "promote an rc to final" procedure we don't yet need.
11. As a maintainer, I want the release to stop when the changelog has no section for the tag's version, so that we never ship a number with no written account of what changed.
12. As a first-time publisher, I want the human-only steps (registry account, publisher bindings, approval environment) written down in their required order, so that I don't discover a missing binding after burning a version number.
13. As a maintainer, I want to run the entire release line without publishing, so that the first real Release rides machinery already proven on main.
14. As a reviewer of a release run, I want artifacts installed and inspected before publication, so that packaging mistakes surface as a red job rather than as a bad package on PyPI.
15. As a user, I want the published package to carry the license files and the third-party attribution, so that the vendored Snapshot's MIT obligation travels with the code that uses it.
16. As a user arriving from a registry search, I want the registry page to show a README, so that a search hit explains what the library is.
17. As a developer looking for a gateway for one specific provider, I want provider names among the package keywords, so that simllms appears in that search.
18. As a maintainer, I want one approval gate before anything reaches a registry, so that a mistyped tag push cannot publish.
19. As a maintainer, I want publication to run sequentially with the Rust crate first, so that a Python-side failure leaves a state I can reason about.
20. As a maintainer, I want a half-failed Release repaired by a **Forward Fix**, so that we never attempt to erase what the registries keep forever.
21. As a user, I want the GitHub Release to state the platform list and the Catalog Snapshot's date, so that I can judge how current the Gate's answers are before I rely on them.
22. As a Python user, I want the docs to say which configuration options are Rust-only in this version, so that I learn the gap from documentation and not by hunting for a missing keyword argument.
23. As a future maintainer, I want the publication-auth decision and the version-source decision recorded as ADRs, so that nobody "fixes" the deliberate oddities — a pyproject with no version field, a publish job that must not become a reusable workflow.
24. As a security-conscious maintainer, I want no long-lived registry token stored in the repository, so that a leaked secret cannot publish our packages.
25. As a maintainer, I want the environment name used by the workflow and the bindings declared registry-side asserted to match, so that a rename on one side cannot quietly break publication later.

## Implementation Decisions

**Authoritative Version.** The workspace version in the root manifest is the single source. The Python binding crate sits outside the root workspace on purpose (ADR-0001), so it cannot inherit that version and becomes the only derived copy to write. The Python project metadata declares its version as dynamic and reads it from the binding crate; the extension module exposes a compile-time version string, and the pure-Python layer re-exports it as the package version instead of holding its own literal. Net effect: four static copies become one authoritative plus one derived, with the rest derived at build time. The release workflow never rewrites repository content — a human changes the Authoritative Version and the diff shows it.

**A check family, not scattered assertions.** The task-runner crate gains a family of checks built as pure functions over file contents, with filesystem writes kept in a thin shell: version-sync drift, "the changelog has a dated section for this version", "the tag equals the Authoritative Version", and configuration self-consistency. CI's PR gate runs the same family that the release job runs, so there is one vocabulary for "the repo is releasable". The Rust-only API inventory is asserted the same way — derived from the actual public surface rather than hand-maintained prose that rots.

**Release trigger and shape.** Publication is triggered by a version tag, plus a manual dispatch with a dry-run input. No comment or pull-request-event triggers: registry-side policy forbids them and they are the dangerous shapes anyway. The line is verify → build matrix → artifact smoke → publish, with build and publish in separate jobs passing artifacts, so the approval gate stops publication without wasting a rebuild. Publication happens in the release workflow file itself, never in a reusable workflow, because trusted publishing rejects callers that reach it through one — this constraint is non-obvious and must be recorded so it isn't refactored away.

**Trusted publishing on both registries.** OIDC for everything, so no long-lived token lives in the repository. The bindings are exact: repository, workflow file name, and one shared approval environment name, asserted for consistency by the check family. crates.io requires one publish performed with a short-lived API token before a trusted publisher can be configured at all; PyPI accepts a pending publisher and creates the project on first upload. That asymmetry dictates the order of human steps: verify account email → create the approval environment → bind PyPI's pending publisher → one-time token publish of the crate from the checked-out tag → revoke the token → bind crates.io's publisher.

**Platform set.** abi3 for the oldest-supported Python means one wheel per platform covers every supported interpreter. Built: manylinux x86_64 and aarch64 with the base image explicitly pinned (an unpinned default drifts and silently narrows compatibility), macOS x86_64 and arm64 as separate wheels rather than a combined universal binary, and Windows amd64. An sdist is published alongside, generated through the Cargo packager so version-control-ignored local directories cannot ride into it. Not built: musl variants, Windows arm64.

**Failure semantics.** Sequential publication, Rust crate first, stop on first failure with a human deciding. A half-failed Release is repaired by a Forward Fix — the next number — never by yank automation. The yank procedure exists only as a written runbook step.

**Package self-description.** Both packages use an explicit include whitelist rather than an exclusion list, so a mistake fails by missing content (loud, caught by the smoke checks) instead of by shipping extra files (silent). Registry pages render the English README while the repository default stays Chinese. The description remains provider-agnostic — a list of six providers would rot as the set changes — and the provider names live in keywords instead. License metadata uses an SPDX expression plus license files, and the third-party attribution ships inside both packages.

**Release notes.** The changelog is the single source; the GitHub Release body is English, carries that changelog section, one line listing the wheel platforms, and one line with the Catalog Snapshot's date read from the vendored snapshot's own metadata (date plus upstream commit), which is what makes a Gate answer's currency checkable.

**Version semantics after this.** New public API surfaces land as a minor bump (the Python capability and parity work is therefore 0.2.0, not 0.1.1); patches are for fixes. Reaching 1.0.0 is tied to P1 landing — tool calling is the point at which the request and response shapes stop moving.

**Docs produced with the line.** A release page in the documentation site covering the human-only steps, the tag procedure, the Forward Fix policy, and the post-release changelog step; two ADRs — publication authentication with its environment binding and one-time token prerequisite, and the Authoritative Version with its derived-copy shape.

## Testing Decisions

A good test here asserts an observable property of an artifact or a configuration, never a workflow step's internals — step ordering, action inputs, and job names are free to change.

**Primary seam: the published artifact.** One seam serves local verification, dry-run, and real publication, so all three paths prove the same claim. Against an unpacked crate and a wheel installed into a clean environment: the version equals the Authoritative Version and the tag; the reported version originates from the binary rather than a source literal; license files and the third-party attribution are present inside the package; the README renders as package content; a Gate refusal against a text-only model raises the typed Capability error with no network involved; the request-debug helper renders an outbound body without credentials. Nothing about publication waits for this to pass except the publish job itself.

**Secondary seam: the check family as pure functions.** Table-driven, in-memory: given a version and a set of file contents, the checks decide "consistent" or name the drift. No toolchain, no filesystem, no network — this is where changelog-section and tag-match logic lives.

**Third seam: configuration self-consistency.** The environment name used by the release workflow, the bindings the runbook tells a human to configure, and the docs' claims about which surface is Rust-only must agree. This seam exists specifically for the known failure mode "someone renamed an environment and publication now 403s", and for documentation drift.

**The platform matrix is verified by artifact inventory, not by running tests on every platform.** A wheel for a target we did not build should fail; building everywhere is out.

Prior art: the workspace test suite is hermetic (no live providers, no network, no Python toolchain) and the wire layer is tested with mockito against local mock servers, asserting only outbound JSON and inbound reply shapes. Release tests follow the same discipline at a higher seam. Live-provider smoke remains manual and environment-gated and never runs in the release path.

The seam set above was reviewed and confirmed with the maintainer in the 2026-10-16 design session; the existing v1 seams (Gate legality, Dialect translation) are untouched by this spec.

## Out of Scope

- The Python parity gaps — eight Rust client methods never bound (custom authentication headers, DashScope region, Zhipu international, default headers, retry policy, stream timeouts, runtime model refresh, structured warning visibility) and the untyped shape of the capability-override argument. Tracked separately for 0.2.0 with its own spec; this spec only documents the gap honestly.
- A typed Python view of the Catalog, Capabilities, and Capability Source.
- musl, Windows arm64, and universal2 wheels; any mirror or private-registry publishing.
- Yank automation, rollback, or re-publishing a taken version.
- Pre-release version flow.
- Generated changelogs or release-please-style automation; the changelog stays hand-written and bilingual-aware.
- Anything from P1 onward: tool calling, the quick-judgement module, file upload, MCP, embeddings, speech.
- Changes to the Dialect layer, the Gate, or the Catalog's content.

## Further Notes

- Both package names were re-checked on 2026-10-16 and are still free on both registries (the v1 spec verified them on 2026-10-15).
- One premise from the roadmap's first draft was wrong and is corrected here: Python callers could already declare capability overrides — the binding parses the mapping and rejects unknown keys — so the real Python gap is the unbound configuration methods plus warning visibility, not the override path. The roadmap's engineering-debt entry is rewritten to match.
- Sequencing is load-bearing: the tag must be cut only after the release line is on main and dry-run green, and the one-time crates.io publish must be run from a checkout of that tag, so the hand-published content and the tagged commit are the same commit.
- The first real Release burns a version number irreversibly; that is why dry-run, artifact smoke, and the approval gate are all required rather than optional.
- Tracked as five tickets in dependency order: the documentation-honesty slice and the version-source slice have no blockers and can run in parallel.
