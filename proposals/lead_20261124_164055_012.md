# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Phase 3: architecture boundaries the gate enforces (Flutter layers, daemon modules, platform services)**

*Project description:*
Part of the agent-driven development migration (Phase 3 of 6). Builds on Phase 1 (#41) and Phase 2 (#51). Work lands on the integration branch `dev/SDD-rework` and draft PR #49; `main` is not updated until the repository is ready for the new methodology.

## Problem Statement

PiFrame's architecture exists only as a convention, so agents (and people) cross layers without noticing, and agents copy whatever they see:

- In the Flutter app, the domain layer is supposed to be plain models, but some domain files import Flutter, `dart:io` or the data layer. Some data-layer files reach up into the app shell (for the app version and the harness mode) or into a feature. 29 feature and shared-widget files call raw I/O and platform plugins directly (`dart:io`, `http`, `ffi`, links, file dialogs, the window, drag and drop, the embedded browser), which also makes those widgets hard to test without a real desktop.
- In the daemon, modules depend on each other freely and there is one cycle: `server` and `remote` import each other (through the auth code).
- Nothing in the gate notices any of this, so every new change can make it worse.

## Solution

The layers become rules the gate enforces, and the existing violations are fixed in this phase:

- One boundary check, in the guardrails module like the other gate checks, reads the imports of Dart and TypeScript sources and fails on any import that breaks the layer rules, with a message that says how to fix it.
- Flutter: the domain layer is pure Dart; the data layer never imports features, shared widgets or the app shell; shared widgets never import features, the app shell or the data layer; features never use raw I/O or platform plugins directly but go through small services in the data layer; only the app shell and the entry points use the harness. Features may import each other (not restricted in this phase).
- Daemon: no cycles between modules, ever, and a committed table of which module may import which; a new module dependency needs the maintainer's approval.
- Shared packages never import the apps. Tests are exempt.
- The check lands first with a baseline listing every current violation; each fix removes its entries; at the end of the phase the baseline is empty, and the mechanism stays for exceptions the maintainer approves.

## Implementation Decisions

- **Integration.** Work lands on the Phase 1 integration branch and its draft PR; `main` is untouched.
- **Boundary check (guardrails module, pure, no I/O).** Input: tracked source files with paths and contents, the layer rules, the daemon allowed-dependency table and the baseline. Output: `{ ok, problems }` (the shape the other docs and design checks use), each problem naming the file, the import, the rule and the fix. Dart `import`/`export` lines and TypeScript `import`/`export … from` (and dynamic `import()` with a literal) are read; relative paths and `package:pi_frame/` paths are resolved to repository paths. A thin adapter reads the tracked files and runs it as a step in `check`, `verify` and `ci` (CI workflow kept in parity).
- **Flutter rules** (by folder under the app's `lib`):
  - domain → only domain and pure Dart packages; no Flutter, Riverpod, `dart:io`, data, features, ui, app.
  - data → domain and I/O packages; not features, ui, app.
  - ui → domain, the theme package, Flutter; not features, app, data.
  - features → domain, data providers, ui, other features; not `dart:io`, `dart:ffi`, `ffi`, `http`, `web_socket_channel`, `win32`, nor the platform plugins (window manager, file selector, URL launcher, desktop drop, local notifier, Windows webview).
  - app → anything.
  - harness → imported only from app and the entry points.
- **Daemon rules.** Module = first folder under the daemon's `src` (root files are their own module). No cycles between modules (hard rule). A committed allowed-dependency table, derived from today's graph minus the cycle; a module edge not in the table fails. Test folders and `*.test.ts` are exempt.
- **Packages rule.** Nothing under `packages/` imports from `apps/`.
- **Baseline.** A committed list of `{ file, import }` violations; a listed violation passes; a stale entry fails naming the entry to delete; the list starts with every current violation and is empty at the end of the phase; the mechanism stays. The baseline, the rules/table and the check (module and adapter) are guarded paths.
- **Daemon cycle fix.** The auth code moves from the server module into a new top-level `auth` module; server and remote both depend on it; server may depend on remote. No behaviour change.
- **App runtime values.** App version and harness mode move from the app shell into a runtime folder in the data layer; the app shell imports them from there.
- **Domain and data fixes.** Smallest move per file that follows the rules: the domain helper that builds UI text keeps only values and the text moves to the feature that shows it; the user-facing error mapping moves into the data layer; domain models use pure-Dart annotations; the notification watcher's dependency on a feature moves down into domain or data. No behaviour change.
- **Platform services.** In a platform folder of the data layer, one small service per kind of I/O: links, file dialogs, window, drag and drop, embedded browser, HTTP, files and processes. Each is an interface plus a real implementation exposed through a Riverpod provider. Existing data services are reused where they already cover the need. Features read the providers; no feature or shared widget imports raw I/O or a platform plugin afterwards.
- **Docs.** AGENTS.md conventions name the rules and the check (AGENTS.md stays ≤100 lines and passes its map check); the developer verification docs describe the check, the baseline and how to add an approved exception.

## Testing Decisions

- **What a good test is here:** tests call public interfaces and assert on outputs. For the check: problems returned for in-memory files, not regexes or helpers. For features: what the feature asks a service to do (via a fake), not how the service is wired. Expected values come from hand-written fixtures.
- **Seam 1, the guardrails module (`node --test`, in-memory files):** a domain file importing Flutter / `dart:io` / data fails; data importing features / ui / app fails; ui importing features / app / data fails; a feature importing `dart:io`, `http`, `ffi`, `win32` or a platform plugin fails; feature → feature passes; harness imported outside app and entry points fails; relative and `package:pi_frame/` imports resolve the same; a daemon module cycle fails naming the loop; a module edge missing from the table fails; packages → apps fails; test files are ignored; a baselined violation passes; a stale baseline entry fails naming the entry. The step list and guarded-path tests cover the new step and files; the CI parity test stays green.
- **Seam 2, the new platform services (existing Flutter widget and unit tests):** each feature that moves its I/O behind a service gets a fake of that service via provider overrides; tests assert the feature's interaction with the service (for example "clicking the link asks the link service to open this URL"). Features that already have widget tests switch to the fakes.
- **Behaviour-preserving moves** (daemon auth module, runtime values, domain fixes) are covered by the existing suites passing unchanged and by the boundary check passing with their baseline entries removed.
- **Prior art:** the Phase 1–2 guardrails tests (step list, escape-hatch audit, approval, doc links, agent map, design tokens), the CI parity test, the Flutter widget tests that already override providers, and the daemon module tests.
