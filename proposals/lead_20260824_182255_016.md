# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat(scope): delivery provenance belongs in a post-merge receipt, not the committed artifact**

*Project description:*
Delivery provenance currently lives in the completed xBRIEF. That placement is why every code-bearing story needs a second PR after its work merges, and the second PR is why we have been buying cheaper CI for a class of change that may not need to exist.

Split from #3679, which kept the route and recovery defects. This issue owns the boundary question, and it is the thing #3680 and #3631 are actually waiting on.

## The constraint that forces the second write

`evaluateDeliveryGate` requires a non-null `mergeCommit`, refreshes `origin/<deliveryBranch>`, and runs `git merge-base --is-ancestor`. Introduced by `4dab160f` on 2026-08-02.

A PR's own squash commit does not exist before that PR merges, and cannot be an ancestor of the refreshed remote ref. So **no formulation that still means "this artifact's own PR was delivered" can be both truthful and pre-merge-satisfiable.** Accepting a predicted SHA, the PR head, or an assume-validated flag would erase exactly the distinction the ancestry gate exists to make.

Requiring that post-merge fact inside a file on the delivery branch therefore makes a second branch mutation architectural rather than incidental.

## The question was never singular

`CompletionProvenance` has fourteen fields (`packages/core/src/scope/delivery-evidence.ts:44-60`) and they do not share a home.

**Cleanly derivable after merge** — `implementationCommit`, `prNumber`, `prBase`, `mergeCommit`; plus `repository` and `deliveryBranch` from local remote and policy rather than from a stamp; and a delivered `disposition` / `handoffState` computable by ancestry.

**Derivable only with a changed meaning** — `deliveryCommit` is today the remote tip observed at verification, not necessarily the merge commit. The historical tip at an arbitrary local `verifiedAt` is not reconstructible from current forge state.

**Not derivable at all** — `verifiedAt`, `verifier`, `completedSessionId`; explicit non-delivery dispositions; and `deployed` / `uatVerified`, which the source forbids inferring from Git in three separate comments (#3041).

Making the whole object mandatory duplicates forge facts while still failing to prove the local assertions.

## Forge-only derivation is not the answer either

A live query is not a durable provenance system. PR association can be absent for direct pushes, altered by history or import strategy, unavailable offline, or lost in a forge migration. `verifiedAt` and the observed delivery tip are point-in-time facts that querying later cannot recreate.

ADR-002 already describes extracting GitHub behind a `ForgeProvider` contract, so hard-coding "ask GitHub forever" would add migration debt against a direction the repo has already chosen.

## Proposed shape

**The pre-merge artifact carries intent, not a delivery claim.** A worker can truthfully commit repository identity, scope id, candidate PR number, PR base, head SHA, intended delivery branch, expected terminal disposition, and a state such as `pending_delivery`. It must not say `delivered`. The non-derivable assertions — `deployed`, `uatVerified`, explicit non-delivery dispositions, verifier identity — stay in the artifact, because no reconciler can produce them.

**Post-merge delivery facts go to a provider-neutral, append-only receipt**, keyed by repository identity, scope id, artifact blob hash, and PR/head identity, and hash-bound to the committed artifact. A post-merge reconciler — merge webhook, merge queue job, or the existing `swarm:finalize-cohort` closer — records the actual merge SHA, delivery ref and tip, provider event time, and verifier version.

A Git-native implementation can use a namespaced ref or notes ledger so the receipt travels with the repository without rewriting the delivery branch. A service-backed implementation can use the same schema and export or import it.

**DONE verifies both** — the intent-bearing artifact is on the delivery ref, and a matching receipt proves ancestry.

Under human-merge policy no worker can satisfy a "the future merge happened" gate before merging. The correct move is to give that gate to a durable post-merge owner, not to have the worker manufacture foreknowledge.

## A separate pre-merge intent check

Two critics split on this and both were right about their own point. The intent shape should be checked before merge, and `verify:completed-tracked` should not be the thing that checks it — that verb answers the #3264 / #3476 land question, and widening it makes a land detector into a stamp-quality detector.

So: a separate pre-merge check for intent shape, leaving the land verb answering land.

## What this is not

**Not a repair of `verify:completed-tracked`.** Presence-only is the question that verb was built for, answered correctly.

**Not blocked on volume.** Post-gate compliance is already 88.4% — 168 of 190 artifacts since 2026-08-02, against 1 of 1122 before. The mechanism works. This issue is about what it costs, not about whether it is being followed.

## Constraints on any implementation

- **Bind #3675 first.** Ancestry is reachability and same-SHA counts, and `mergedAt: "supplied"` is synthesized whenever `--merge-commit` is passed. Until merge identity is bound to the story, any stamp-quality requirement can be satisfied by feeding `origin/master`.
- **Non-code-bearing scopes legitimately have no provenance.** `evaluateDeliveryGate` returns `ok: true` with `provenance: null` for them, and `scope:fail` stamps nothing by design. Neither may be made to fail.
- **Historical corpus is advisory.** 1122 pre-gate artifacts carry no provenance and never will. Grandfather by date, as `doctor/checks.ts` already does for pre-#2862 open items.
- **Do not weaken ancestry** to make a pre-merge stamp possible. That is the distinction worth keeping.

## Acceptance

- [ ] Delivery facts and completion assertions are separate records with stated durability contracts
- [ ] The pre-merge artifact can be written truthfully by a worker before its PR merges, and does not claim delivery
- [ ] Non-derivable assertions remain committed in the artifact
- [ ] A provider-neutral receipt schema exists, hash-bound to the artifact, with a Git-native implementation that does not rewrite the delivery branch
- [ ] A post-merge reconciler writes the receipt without a human-opened PR
- [ ] A separate pre-merge intent check exists; `verify:completed-tracked` still answers only the land question
- [ ] Non-code-bearing and `failed` completions pass unchanged
- [ ] Pre-2026-08-02 artifacts are advisory, not red
- [ ] CHANGELOG `[Unreleased]` line

## Why this gates other work

If the reconciler writes a ref instead of opening a PR, most of the leftover lifecycle PR class stops existing. #3680 would then be buying a Greptile carve-out for a population that is disappearing, and #3678's non-required-job skips become a transitional saving rather than permanent infrastructure. #3631's chore-lane work is downstream of the same question.
