# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Beta tester mode: a Settings toggle and a one-time token**

*Project description:*
Supersedes the badge half of #48 (its options A and B), and covers something #48 never
did: **the web app**.

## Why this instead

The Pages web build has no beta buttons and can't have them — it's built without
`TIMEFLOW_BETA`, and the alternatives were a second deploy at `/TimeFlow/beta/` (public
URL, and it shares its IndexedDB with the real app) or a separate origin (more setup).
The connect-code flow agreed on #48 needed a browser hop, so it couldn't help the web app
either.

A toggle turns any build into a tester build at runtime. One mechanism, three platforms,
and the URL-scheme worry from #48 disappears with it.

## How it works

1. `announce` (which already runs in the portal's Worker, per recipient, with the mail
   binding) mints a **one-time code per tester per round** and puts it in that tester's
   release email. Only its hash is stored.
2. **Settings → Beta testing** → paste the code. The app calls
   `POST /beta/connect {code}`, which spends the code — same conditional
   `UPDATE … WHERE claimed_at IS NULL … RETURNING` the portal's sign-in links use — and
   returns a long-lived **device token** plus the tester's handle (`Tester A4F2`).
3. The token goes in secure storage (Keychain / Keystore / WebCrypto). From then on the
   app shows the two app-bar icons **driven by the toggle, not by `BETA_FEEDBACK`**, with
   the tasks badge from `GET /beta/summary`.
4. Tapping an icon asks for a **30-second single-use handoff link**
   (`POST /beta/handoff`) and opens that. The portal swaps it for the normal session
   cookie and strips it from the address bar, so the long-lived token never travels in a
   URL and nothing reusable lands in browser history.

Email sign-in is untouched. It stays the way into the portal from any other computer, and
it's how a tester resends themselves a code.

## The code is one-time, and that's the point

A forwarded or breached email is worthless once the tester has connected. More
importantly, **silent theft becomes loud theft**: if someone claims the code first, the
tester gets "already used" and says so, and both the console and the tester's own portal
page show when it was claimed and by what browser. A reusable token would let a thief and
a tester coexist indefinitely with nobody finding out.

Consequences, both handled without the developer in the loop:

- **More than one device.** The connected app gets **Add a device**, minting a 10-minute
  code for the next one. The portal also offers **Resend my beta token** behind email
  sign-in.
- **Reinstalls and cleared browser storage.** Same self-service resend.

## What the device token can and cannot do

The token is **tester-scoped, not round-scoped** — a code proves "I am this tester", so a
second round's announcement needs no reconnecting and the badge follows the tester across
rounds. Its powers are deliberately small:

- Read the tester's rounds and steps; report results and findings.
- **Never** payment details, **never** the tester's name or email (the app only ever
  learns the handle), and **never** NDA acceptance — that needs the browser session, so a
  stolen token can't agree to anything on anyone's behalf.
- Listed and revocable: "TimeFlow on Pixel 8a — connected 16 Oct, last used 2 minutes
  ago", on the tester's portal page and in the console, with Revoke beside each.
- `401` when the tester leaves the pool; the app forgets the token rather than retrying.

**Proof of possession is deliberately deferred.** Binding to a device *id* would be
theatre — the id travels with the token, so whoever steals one has both. The real version
is a keypair generated on first connect, public key sent with the claim, requests signed
thereafter; Workers can verify it with `crypto.subtle.verify`, so the portal's half is
easy and the cost is signing code on three platforms. The upgrade is additive: the app
starts sending a public key, the portal stores it, and verification turns on once every
live token has one. Nothing has to be re-emailed.

## Per platform

- **Web (the reason this exists).** Show the Beta testing section when
  `betaFeedback || kIsWeb`, so the public Pages build gets it with no second deploy and
  iOS/Android store builds stay exactly as they are — no reviewer ever sees it. Needs CORS
  on `/beta/*` for the Pages origin; on web, "secure storage" is browser storage, so the
  web token gets a shorter life and switching the toggle off must delete it.
- **Android.** Nothing special; Keystore via `flutter_secure_storage`.
- **Apple.** Keychain via the same package, resolved through SPM (no `pod install`). A
  `mac` issue for the TestFlight build will follow once the Dart lands, as #49 did.

## What the portal side provides

`POST /beta/connect`, `POST /beta/handoff`, `GET /beta/summary`, plus the one-time code in
the announcement mail, the device list, revocation and the reuse tripwire. Bearer only on
`/beta/*`, cookie never accepted there — as already agreed on #48. Tracked in
`docs/next-dev-cycle.md` in RinseRepeatLabs/tester-pool.

## Acceptance

- [ ] A tester pastes the emailed code once and the two icons appear, with a badge showing
      required steps left, in a **store** web build and in beta mobile builds.
- [ ] A second attempt to use that code fails, and the attempt is visible to the tester
      and in the console.
- [ ] Tapping an icon opens the portal already signed in, with no reusable value left in
      the URL or in history.
- [ ] The toggle off deletes the token; Revoke in the portal kills it from the other end.
- [ ] An NDA-gated round the tester hasn't accepted shows no badge and sends them to the
      browser to accept.
- [ ] iOS and Android **store** builds show no Beta testing section at all.
