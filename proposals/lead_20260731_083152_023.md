## Findings

### Playwright Test belongs in the repository

Official Playwright Test provides isolated browser contexts, resilient role/label locators, tracing, screenshots, videos, responsive emulation, request interception, and pixel comparison through `toHaveScreenshot()`.

Source:

- https://playwright.dev/docs/test-snapshots
- https://playwright.dev/docs/ci
- https://playwright.dev/docs/test-webserver
- https://www.npmjs.com/package/@playwright/test

Current stable package inspected on 2026-07-31: `@playwright/test` 1.62.0, Apache-2.0.

Playwright warns that screenshot output varies across operating system, browser version, hardware, headless mode, and related rendering inputs. Baselines must therefore be generated and checked in one pinned environment, with explicit review when updated.

### Official Playwright MCP is useful for exploration

Microsoft maintains `microsoft/playwright-mcp`. It exposes browser control through structured accessibility snapshots and supports screenshots, persistent or isolated browser profiles, existing-browser attachment, origin controls, output directories, and local or HTTP transport.

Source:

- https://github.com/microsoft/playwright-mcp
- https://github.com/microsoft/playwright-mcp/blob/main/packages/extension/README.md

The maintainers explicitly distinguish the interfaces:

- CLI + skills is generally more token-efficient for high-throughput coding agents;
- MCP is useful when persistent browser state, rich page introspection, or a long exploratory loop outweighs schema and snapshot context cost.

This makes Playwright MCP an optional operator/agent research tool, not the CI proof surface.

### Browserbase is useful as an occasional hosted adapter

Browserbase maintains a hosted and self-hostable MCP server backed by Browserbase and Stagehand. Its tools cover session start/end, navigation, action, observation, and extraction. Browserbase documentation names market research, testing, data extraction, monitoring, and user-journey testing as supported use cases.

Sources:

- https://github.com/browserbase/mcp-server-browserbase
- https://docs.browserbase.com/integrations/mcp/introduction
- https://www.browserbase.com/pricing

Current free-plan limits inspected on 2026-07-31:

- one browser hour per month;
- 15-minute maximum sessions;
- three concurrent browsers shown on the pricing page;
- three included Agent runs;
- seven-day session-data retention.

This is enough for occasional design sweeps and difficult hosted-page research. It is too quota-dependent to become the required repository gate. Any paid capacity increase still requires operator approval under `STENSIBLY.md`.

## Decision

Use three separate layers.

### Layer A — canonical repository proof

Add `@playwright/test` as a reviewed development dependency and run Chromium against fixture-only local routes.

Required controls:

- repository-owned configuration and tests;
- a tiny local static server with no credentials;
- fail every unexpected external request;
- deterministic wide and narrow viewports;
- keyboard-only task flows and focus assertions;
- console and page-error collection;
- screenshots and traces stored only from fictional public fixtures;
- Chromium first; Firefox/WebKit become evidence-driven additions;
- exact dependency and browser versions through the committed lock and CI environment;
- no live API, login state, cookies, analytics, or private payloads.

### Layer B — exploratory local browser work

Allow Playwright CLI or Playwright MCP for manually directed research, QA, and test generation.

Default controls:

- isolated profiles unless an exact logged-in task requires operator browser attachment;
- explicit allowed/blocked origins;
- no unrestricted file access;
- no retained credentials or copied private content;
- record source URL, inspection date, task, evidence class, applicable lesson, and limits in #615 or its durable index;
- screenshots supplement findings but do not replace source attribution or task evidence.

### Layer C — optional hosted research

Use Browserbase only when remote execution, session replay, hosted observability, or difficult site behavior materially helps.

Default controls:

- stay inside the free plan unless separately approved;
- one bounded research question per session;
- use fresh isolated contexts unless persistence is required;
- no operator impersonation, contact, purchase, submission, or publication;
- no private accounts or secret-bearing pages in retained hosted sessions without an explicit reviewed need;
- record minutes, sources, findings, limitations, and any upstream defect.

## Research protocol

Browser-based market research should produce an evidence packet rather than an unstructured browsing transcript:

- research question and target audience;
- source list and date;
- ordinary navigation path attempted;
- wide and narrow observations;
- accessibility-tree or semantic observations;
- screenshots only where they clarify a finding;
- concrete praise, friction, fatigue, discoverability, speed, trust, and delight signals;
- applicable Stensibly experiment;
- adopt, adapt, test, or reject disposition;
- robots, terms, login, rate, and evidence limitations.

Do not bypass access controls, CAPTCHAs, paywalls, robots restrictions, or site terms for market research.

## First implementation slice

- add `@playwright/test` 1.62.x as a development dependency;
- add a repository static fixture server for `site/`;
- add a Chromium-only Playwright configuration;
- verify `/labs/` route rendering and registered variants;
- exercise side-by-side comparison;
- exercise Quiet Control keyboard and narrow-screen behavior;
- fail on external requests, browser page errors, or unexpected console errors;
- attach reviewable wide/narrow screenshots and traces;
- run the suite in canonical CI and retain public fixture-only artifacts for seven days;
- document browser installation cost, CI time, update path, and removal path.

Do not block this first slice on committed pixel baselines. Add `toHaveScreenshot()` only after one exact CI environment has produced stable evidence and the update workflow is reviewed.

## Upstream and operator-owned repository opportunities

After two owned repositories use the same controls, extract the generic pieces rather than copying them indefinitely:

- secure fixture-only static server;
- unexpected-network fence;
- console/page-error collector;
- responsive viewport matrix;
- screenshot and trace artifact convention;
- public-fixture leakage scan;
- reusable GitHub Actions browser-install/cache step;
- evidence manifest schema.

Potential destination: a small operator-owned browser-evidence toolkit or shared workflow repository. Keep Stensibly-specific tasks and status semantics in Stensibly.

Open upstream issues or pull requests only for reproducible defects or generally useful missing behavior in Playwright, Playwright MCP, Browserbase MCP, or Stagehand. Preserve a minimal reproduction, exact versions, expected/observed behavior, and privacy-safe evidence.
