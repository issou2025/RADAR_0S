# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Support apps that draw with game engines (SpriteKit first)**

*Project description:*
A starting point for supporting apps that draw their UI through a game engine. This records the options surveyed on 2026-11-01 so the next session doesn't start from scratch. It's exploratory, not a committed plan. The tool details are from memory and haven't been checked against current releases; check versions and licenses before building on any of them.

## Why game engines break the usual approach

A game draws into one Metal/GL surface, so the accessibility tree shows a single full-screen view with nothing inside it. That causes three problems:

1. **Finding things:** there are no labels, so `tap_element`, `wait_for_element` and landmarks have nothing to match.
2. **Knowing state:** the score, the level or whether a dialog is open never appears in any tree.
3. **Input timing:** engines read touches once per frame. A very short tap, a held virtual joystick or a multi-touch gesture can be missed even when the coordinates are right.

## How other frameworks handle it

**1. Reading pixels (works on any app).** Sikuli, Airtest's image matching, the Appium images plugin (OpenCV template matching) and OCR. It needs nothing from the app, but it breaks across resolutions and animation, and says nothing about state. Every serious game testing tool keeps it only as a fallback.

**2. A test SDK built into the game's debug builds (the main industry answer).**
- **AltTester** (formerly AltUnity, for Unity): a server inside the game exposes the GameObject hierarchy, component properties and method calls, and injects input from inside the engine. Python, C# and Java clients. I believe the SDK is GPL with a commercial option.
- **Poco** (NetEase Airtest): SDKs for Unity3D, Cocos2d-x, Cocos-JS, UE4 and Egret, with one Python client and one hierarchy format. Apache-2.0. The broadest open-source coverage.
- **Unreal:** the Automation Driver (Slate/UMG UI only), Gauntlet (runs sessions across devices), and the Remote Control API plugin (UObject properties and functions over HTTP/WebSocket in dev builds). Remote Control is good for setting game state, not for finding UI.
- **GameDriver:** commercial, covers Unity and Unreal.
- **Godot:** no standard. The editor's remote debugger can inspect a debug build's live scene tree, and GdUnit4 runs tests inside the engine, but there's no device automation protocol.

**3. The engine's own accessibility support (nothing for quern to build).** Newer Unity versions (2023.2 and later, I believe) have an accessibility hierarchy that feeds VoiceOver and TalkBack. Apple publishes Unity plugins that include an accessibility one. SpriteKit nodes can carry accessibility properties. When a game uses these, quern's existing tree works as it is.

**Also:**
- **Frida** (for example, frida-il2cpp-bridge for Unity) can inspect a game with no SDK. It works on simulators and debuggable Android builds; physical iOS needs the app re-signed. Powerful but fragile.
- **Flutter** has the same one-canvas symptom but already sends a semantics tree to accessibility, and has the Dart VM service. Quern already detects Flutter projects.

## Proposed order for quern

1. **Detect canvas apps and fall back to vision.** When the tree is one large childless element, `get_screen_summary` should say so rather than showing nothing. `tap_element(label=...)` could fall back to OCR through the existing `server/device/vision_ocr.py`, which today only aims web-content hit-tests. Then add template matching ("tap this image") and frame-diff waiting through the existing settle logic. This works with every engine.
2. **Bridge to Poco and AltTester.** Speak their existing wire protocols over the port forwarding quern already does, and convert their hierarchy into quern's UI tree. Then `tap_element`, `wait_for_element` and landmarks work on game objects unchanged.
3. **Unreal Remote Control for setting state**, alongside the plist and app-state tools: jump straight to a game state instead of playing your way there.
4. **Better input for games:** press duration, continuous drag paths and multi-finger gestures, for virtual joysticks and hold-to-charge actions. Overlaps #243 and #252. Engine-side input through a bridge avoids coordinate mapping entirely.
5. **A log convention:** games print structured state lines, and quern's log capture plus a `wait_for_log` lets agents synchronize on them. Any engine, a few lines in the game.

Deferred: Godot (we'd have to write the addon) and GameDriver (commercial).

## First engine to explore: SpriteKit

Chosen 2026-11-02 and measured the same day on an iOS 27.0 simulator. The full results are in [the findings comment](https://github.com/quern-dev/quern/issues/601#issuecomment-6595158731). In short:

- **SpriteKit already reaches quern's tree.** Text labels appear automatically. Any node with `isAccessibilityElement` and `accessibilityLabel` set appears with the right type, and its frame stays current while it moves. `tap_element` lands on both. Building elements yourself on the view (`SKView.accessibilityElements`) has no effect, so no in-app package is needed.
- **Gaps:** a node has no `accessibilityIdentifier`, so nodes can only be matched by label. Labelling a text node hides its text unless `accessibilityValue` is set too. Quern refuses to tap a moving node (`obstructed`, `reason: moving`).

Recommended next steps:
1. **Docs:** a short guide to annotating SpriteKit nodes for quern (which also makes the game usable with VoiceOver).
2. **Tapping a moving target:** an opt-in on `tap_element` that taps the latest frame, or predicts the position, instead of refusing. Needs a design decision.
3. **Detecting a canvas:** when the screen is an SKView with nothing annotated, say so and point to the guide, then to the OCR fallback.
4. **Not yet measured:** the WDA path on a physical device, nested accessible nodes, and how many shipped SpriteKit games annotate their nodes.
