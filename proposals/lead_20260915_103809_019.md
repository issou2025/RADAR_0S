# backup create --verify accepts raw SQLite .db WAL/SHM families

## Observed

On OpenClaw 2026.9.4, a full archive containing a SQLite database named `cron-log.db` reports `verified: true` while retaining the raw main file, `cron-log.db-wal`, and `cron-log.db-shm`. The same synthetic database named `.codex/state_5.sqlite` goes through native SQLite snapshot capture, restores the committed WAL row, and has no sidecars in the restored tree.

The test used only synthetic data, an isolated HOME, state/config roots and temporary directory. A connection stayed open after a committed WAL write, with `wal_autocheckpoint=0`; no concurrent write was required to expose the capture distinction. This does not demonstrate corruption, but raw sequential file capture is not the SQLite online-backup consistency guarantee.

## Minimal reproduction shape

1. Create an isolated state directory with a minimal valid config and workspace.
2. With Python sqlite3, open `<state>/cron-log.db`, set `PRAGMA journal_mode=WAL` and `PRAGMA wal_autocheckpoint=0`, create a simple table, insert a witness row, and commit. Keep that connection open.
3. Run native `openclaw backup create --output <outside-state-directory> --verify --json` under the isolated HOME / OPENCLAW_STATE_DIR / OPENCLAW_CONFIG_PATH.
4. Inspect archive members before closing the connection.

Observed archive members: `cron-log.db` (4,096 bytes), `cron-log.db-wal` (12,392 bytes), and `cron-log.db-shm` (32,768 bytes). Result: `verified: true`.

Control: repeat with `.codex/state_5.sqlite`. Native creation, independent verification and fresh-target restore pass; the witness row survives and no sidecars remain.

## Source contact

`src/infra/backup-sqlite-snapshot.ts`, `resolveSqliteBackupDatabasePath`, recognizes only `.sqlite` and its sidecars in the installed version and current upstream source inspected on 2026-09-15 UTC. Generic `.db` files do not enter the native snapshot plan. The backup docs describe SQLite capture and sidecar rejection more broadly than this suffix boundary.

## Requested resolution

Discover supported SQLite databases by safe file identity/header checks rather than assuming `.sqlite` is the only extension, and route supported families through the existing snapshot/verification path. Fail closed on unsupported SQLite capabilities or inconsistent/orphan sidecars. Preserve package-content, ownership, exclusion, symlink/alias and canonical role checks. Do not classify arbitrary non-SQLite .db files as databases based solely on extension.

Please add synthetic regression coverage for committed WAL data with `.db`, `.sqlite`, `.sqlite3`, and extensionless names; ordinary non-SQLite `.db` files; orphan/mismatched sidecars; excluded/package paths; and canonical ownership failures. Verification should not label a raw live SQLite family as a safe consolidated snapshot. Clarify the documented capture boundary if some files intentionally remain opaque.
