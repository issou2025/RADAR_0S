# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Automation harness silently disables opponent detection (ctypes prototype pollution)**

*Project description:*
## Summary

While verifying PR #1011 on this dev machine, opponent detection in the Opponent Deck Spy (`MTGOpponentDeckSpy`) never fired: `utils/find_opponent_names.find_opponent_names()` returned `[]` inside the running app, even with a window titled `... vs. <player>` visible on screen.

The same call from a **standalone** Python process — including one that had constructed a `wx.App` and was calling from a worker thread, i.e. the same shape as the real poll path — returned the player name correctly.

## Evidence

An in-app probe showed the split is inside `pygetwindow`, not in our code:

- raw `EnumWindows` via `ctypes` **succeeded** in-process: 318 hwnds enumerated, `GetLastError() == 0`
- `pygetwindow.getAllTitles()` in the **same process and same thread** returned **0 titles**

So the window handles are reachable from the app process; `pygetwindow` is the layer dropping them.

## Why it matters

`find_opponent_names()` is the only trigger for opponent detection (`widgets/frames/identify_opponent/handlers/polling.py::_poll_worker`). If it returns `[]`, the tracker sits on "no active match" forever and the whole feature is silently dead — no error, no log line at warning level or above.

## Important caveat — NOT confirmed as a user-facing bug

A screenshot from a real user shows opponent detection **working**, so this is not reproducing universally. It may well be specific to this dev machine or to how the app was launched during verification (e.g. under `--automation`, or the WSL/`/init` interop launch path used by `automation/run_app_from_wsl.sh`, or a `pygetwindow` version/`pyobjc`-style backend quirk). This issue is filed so the investigation is not lost, not because the shipped app is known to be broken.

## Suggested investigation

- [ ] Reproduce: run the app normally (installed build) vs `main.py --automation` vs launched through `/init` interop, and compare `find_opponent_names()` results
- [ ] Check whether the automation launch path affects window-station / desktop association, which would explain an empty enumeration from one API but not another
- [ ] Read `pygetwindow`'s MSW implementation to find which filter drops the windows (visibility? title length? `IsWindowVisible`?) and whether it swallows an exception
- [ ] Decide whether to drop `pygetwindow` for a direct `ctypes` `EnumWindows` + `GetWindowTextW`, which the probe proved works in-process and removes a dependency from the one code path the feature depends on
- [ ] Add a log line (warning, not debug) when a poll enumerates zero windows entirely, so a user hitting this is diagnosable from logs
