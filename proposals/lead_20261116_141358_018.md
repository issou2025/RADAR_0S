## Finding (verified against the official docs)
The emulator supports per-camera video files natively, no kernel modules needed:
`emulator -camera-back videofile:<file> -camera-front videofile:<file>`
Source: developer.android.com/studio/run/emulator-commandline — `-camera-back/-camera-front` modes include `videofile:<filename>` ("The emulator uses a video for the camera output"), alongside `emulated`, `environment` (virtual scene), `webcam<n>`, `imagefile:<filename>`, `none`.

Fallback if videofile does not work on the CI emulator version: v4l2loopback + ffmpeg streaming a test video into /dev/video10, with `-camera-back virtualscene -camera-front webcam0` — proven pattern in the wild (TRIfA bobtests_linux.yml).

## Acceptance
1. Two distinct test videos feed the two cameras in the CI emulator (front = one video, rear = a different one). Videos generated in-workflow with ffmpeg (no binary blobs in the repo); each labelled so front vs rear is unmistakable on sight.
2. The emulator-screenshots workflow (and the smoke test, if it touches the camera) uses the videofile feeds instead of `-camera-back emulated -camera-front emulated`.
3. PROOF in CI: a run whose screenshots/recording show different moving content on front vs rear at the same moment — the dual preview shows both at once, so one screenshot of the main screen proves it; a recorded video whose extracted frames differ between front circle and back area proves the recording path too. Check the video actually keeps moving (loops, or long enough for the take) — a frozen last frame is not a stream.
4. If videofile cannot be made to work on the CI emulator, record exactly what was tried and the emulator's error, and say so — do not silently fall back to the test pattern.
