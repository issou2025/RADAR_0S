# Project Proposal — Structural Drawings

You need assistance with:

*Project description:*
## Problem Statement

Projects using domain_error need reusable guidance that matches their installed major version and their own architecture. The package does not currently publish a discoverable, portable flutter-domain-errors skill with a supported installation command. Personal or project-specific rules can also impose conventions that do not belong in a universal package skill.

Installation, automatic selection, and instruction quality are separate concerns. A successful installation does not prove that a client will select the skill automatically, and an explicitly invoked test does not prove the dependency-based trigger.

## Solution

Publish flutter-domain-errors in this public repository using the portable SKILL.md format and distribute it through the existing skills CLI. Make it eligible for implicit invocation for relevant Dart/Flutter work when the applicable package directly depends on domain_error. Confirm dependency presence and the resolved major before applying version-specific rules.

Support current 3.x and the agreed next-major interface with maintained rules, scenarios, examples, and migration guidance. Recognize older or unknown majors without silently upgrading them or applying incompatible examples.

## User Stories

1. As a Dart developer, I want the guidance to apply to pure Dart projects so that the skill is useful without Flutter-specific application layers.
2. As a Flutter developer, I want package-specific guidance selected during relevant work so that I do not need to repeat the error-handling contract in every request.
3. As a user, I want dependency detection based on the applicable package manifest so that a comment or an unrelated sibling package does not activate the rules.
4. As a monorepo contributor, I want version selection scoped to the package being changed so that one package's dependency does not control another package's code.
5. As a user of a path or Git dependency, I want the actual resolved API inspected so that the skill does not assume a hosted release's shape.
6. As a 3.x user, I want valid 3.x examples so that installing the skill does not require a package upgrade.
7. As a next-major user, I want guidance for the agreed capture and composition interface so that new capabilities are used consistently.
8. As a legacy user, I want the unsupported major identified clearly so that incompatible migration is not performed automatically.
9. As an application maintainer, I want existing architecture, naming, and state-management conventions respected so that a package skill does not redesign my application.
10. As a developer, I want examples for domain errors, raw-error mapping, result handling, observation, and composition so that common scenarios have executable references.
11. As a developer, I want sync/async and late-stream error limits explained so that I place capture at the correct execution point.
12. As a maintainer, I want reporting guidance that distinguishes diagnostics from business decisions so that observers do not change outcomes or expose sensitive context.
13. As a user, I want a standard npx installation command so that I do not need a custom installer or a separate npm package.
14. As a user, I want project-local and optional global installation documented so that I can choose the scope deliberately.
15. As a maintainer, I want selection tested with both matching and non-matching projects so that automatic use is supported by evidence.
16. As a contributor, I want versioned examples checked against the package so that instructions do not drift after releases.

## Implementation Decisions

- Use skill-creator to produce a self-contained portable skill. Keep essential rules in the entry point and route substantial examples or version-specific detail to maintained references.
- Publish the skill in this repository under the agreed name flutter-domain-errors. Use the existing skills CLI rather than building or publishing a custom npm installer.
- Describe the actual automatic-use condition precisely. Keep implicit invocation enabled where a client supports such policy metadata; do not set explicit-only invocation.
- Before applying rules, inspect the nearest applicable package manifest, direct production or development dependencies, resolved version, overrides, and source when needed. Do not activate solely for a transitive dependency or a textual mention.
- Support 3.x and the next major with separate, verified contracts. For unsupported or unclear versions, report the mismatch and inspect the source before making version-dependent recommendations; do not upgrade automatically.
- Cover feature error roots, stable identifiers, equality and diagnostic context, raw-error mapping, result branches, capture routing, observer/reporter failures, mapper failures, sync/async limits, late stream errors, and next-major composition.
- Keep application-layer recipes optional. Do not require a state-management library, repository return convention, version suffix convention, barrel layout, or personal/company architecture.
- Preserve existing project instructions and untouched legacy code. Provide migration guidance without treating installation as authority to migrate a project.
- Distinguish safe structured reporting from arbitrary error strings. Examples must not assume diagnostic text is suitable for remote publication.
- Keep installation, selection, and behavioral validation separate. Report only the clients and versions actually exercised; do not promise a universal forced trigger without client support.
- Preserve any pre-existing personal skill and unrelated installed skills. Test installation in isolated projects rather than modifying the user's global setup.

## Testing Decisions

Validate metadata and references, then exercise realistic requests and projects without naming the skill in the automatic-selection prompt. Test example behavior through each supported package major's public interface.

- [ ] The published source is discoverable and installable by the documented npx command in a clean project.
- [ ] Project-local installation and explicitly requested global scope behave as documented without replacing unrelated skills.
- [ ] Positive selection cases include direct hosted dependencies, applicable path/Git dependencies, and relevant development-dependency usage.
- [ ] Negative selection cases include no dependency, a textual mention, a transitive-only dependency, an unrelated sibling package, and unrelated work.
- [ ] Resolved 3.x and next-major examples compile and pass focused behavior checks against the correct API.
- [ ] An unsupported major does not trigger a silent upgrade or incompatible implementation.
- [ ] Examples preserve error identity, callback ordering, observer isolation, mapper failure behavior, and the selected sync/async contract.
- [ ] Content and selection tests do not rely on project-specific paths, private services, credentials, or a particular application architecture.
- [ ] Validation results distinguish installation success, automatic selection, example execution, and untested client compatibility.
- [ ] The package documentation includes the installation command and supported-version policy.

## Out of Scope

- A custom npm CLI or separate npm publication.
- Hooks or mandatory client integrations that force selection on every request.
- Full behavioral support for domain_error 2.x in the first published skill.
- Automatic dependency installation, package upgrades, global setup changes, or migration of untouched code.
- Imposing a particular state-management or application architecture.
- Claiming every compatible client has been tested.
