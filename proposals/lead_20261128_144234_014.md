**Document how to retrieve a Datadog event from an Event Explorer URL in the datadog skill**

*Project description:*
## Problem

When a user copies a Datadog Event Explorer URL (e.g. `https://us5.datadoghq.com/event/explorer?...&event=AwAAAaIgUPAo...&live=true`) and hands it to an agent, the agent has no reliable way to retrieve the specific event via the Datadog API. Investigation against the live US5 Datadog API confirmed:

- The `event=` URL parameter is a base64-encoded opaque stream key. Decoding it yields a stream UUID and a binary stream uid — both internal Datadog identifiers that are **not** indexed by the Events API and do not appear in API responses.
- The `from_ts` / `to_ts` parameters, when `live=true` and `refresh_mode=sliding` (the common case for a copied link), are the **view window the user was looking at when they copied the link**, not the event's trigger time. They slide to "now" on every page load.
- The API-retrievable identifier is the event's numeric `evt.id` (visible in the UI under Event Attributes → `evt` → `id`), which is **not present in the URL** in any encoding.

## Proposal

Add a section to `skills/datadog/SKILL.md` documenting:

1. That the `event=` URL parameter is an opaque stream key and should not be base64-decoded looking for an API ID.
2. That `from_ts`/`to_ts` with `live=true` are a sliding view window, not the event trigger time.
3. The reliable path: ask the user for the numeric `evt.id`, then `GET /api/v1/events/{evt.id}`. Note that the v2 single-event endpoint frequently 404s for monitor alerts and containerd events.
4. A brittle fallback: search the v2 Events API by trigger time + title.
5. A quick-reference table of URL fields vs API-retrievable fields.

## Verification

Tested against the live US5 Datadog API (`api.us5.datadoghq.com`):

- `GET /api/v2/events/{uuid-from-url}` → `404 "No event matches that event_id."`
