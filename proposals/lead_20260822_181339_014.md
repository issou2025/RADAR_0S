## Explore intent

Investigate which current Scheduled-Agent governance and mapped Skill conditions are actually deterministic predicates that should be moved from natural-language Agent interpretation into executable validators/classifiers, while preserving genuinely semantic judgment for Lead/Reviewer/Executor.

The goal is not to add more governance. The goal is the opposite: reduce correctness-critical prose, reduce repeated context loading, and make mechanically decidable answers reproducible by code/tests instead of relying on the Agent to remember and re-interpret increasingly detailed instructions.

Observed default-branch baseline: `1d6bd5523fa933c543e2858f52003139043d873f`.

## Creation evidence / current friction

Current `main` contains several governance and Skill sections whose conditions are already expressed like executable pseudocode: exact counts, set membership, tuple validity, SHA equality, timestamps, ordering, state combinations, event provenance, and finite result tables. These conditions are repeatedly consumed by Agents as natural-language instructions even though the desired answer is deterministic.

Concrete adjacent evidence already exists:

- #133 shows that prose-defined/test-only runtime preconditions can be semantically correct yet still fail to enforce the real execution path; it specifically investigates executable cardinality/runtime enforcement.
- #83 identified a similar Human-authority gap: the semantic predicate already exists in code/tests, while executable evidence-acquisition procedure remained too dependent on Agent rediscovery.
- #111 investigates recurring mechanical mutation recovery that should be executable by the owning role instead of repeatedly escalating for rediscovery.
- `.github/scripts/archive_pr_linkage.py`, archive automation, and compatibility helpers demonstrate the repository already benefits from deterministic repository-owned checks where Agent judgment is unnecessary.

This Explore is broader but must not duplicate those issues. It owns the **systematic boundary/inventory question**: which natural-language governance/Skill rules should remain semantic instructions and which should become executable, reusable, tested decision surfaces.

## Working principle to test

A candidate rule should be considered for executable enforcement when its answer can be derived primarily from operations such as:

```text
if / and / or
== / !=
count / cardinality
set membership / set difference
sort / deterministic tie-break
SHA/revision equality
timestamp/event ordering
finite state/result table
structural parsing/validation
```

Conversely, rules that require interpretation of meaning, intent, materiality, feasibility, architecture trade-offs, requirement satisfaction, or whether behavior semantically changed should normally remain Agent/role judgment, possibly supported by executable evidence collection.

This is a hypothesis for investigation, not a pre-approved implementation design.

## Required investigation

1. Inventory deterministic-looking conditions across the current authoritative surfaces, at minimum:
   - `agents/AGENTS.md`;
   - `agents/workflow.md`;
   - `agents/roles/*.md`;
   - every mapped `agents/skills/*/SKILL.md`;
   - `openspec/config.yaml` where mechanical validation rules are repeated operationally.
2. For every candidate, classify it as one of:
   - **Executable**: result should be determined mechanically;
   - **Hybrid**: script gathers/classifies structural evidence, Agent decides semantic/material meaning;
   - **Semantic**: should remain role judgment.
3. Identify duplicated deterministic predicates across shared governance and multiple Skills. Determine the single correct ownership surface so extracting them reduces context instead of introducing another synchronized copy.
4. Prioritize correctness-critical candidates. Evaluate at minimum:
   - workflow/cardinality/dispatch and routing validity;
   - Human decision/approval provenance;
   - exact-head Reviewer PASS and required CI/gate matching;
   - merge preconditions and PR non-closing linkage;
   - Invocation Exit / external asynchronous-wait evidence;
   - terminal/interrupted-finalization classification;
   - premature-close recovery structural predicates;
   - required deferred-tracker structural integrity;
   - exact-revision strict-validation evidence;
   - temporary branch safe-delete predicates;
   - Skill-local checkpoint/readiness/recovery state that is mechanically decidable.
5. For hybrid cases, define the exact split. Examples to evaluate:
   - script enumerates newer Human comments and provenance; Agent decides whether content is material;
   - script reports which OpenSpec/Skill paths and structural declarations changed; Reviewer decides whether meaning/responsibility materially changed;
   - script verifies tracker existence/linkage/routing once Lead has semantically classified an obligation as required separate follow-up.
6. Identify natural-language sections that could be deleted or materially shortened after executable extraction. Estimate the context reduction by authoritative surface and mapped Skill; do not optimize for line count at the expense of clarity or provenance.
7. Define the desired Agent interaction contract for executable checks. Prefer a small result vocabulary such as `PASS / FAIL / INDETERMINATE` plus machine-readable reasons/evidence rather than requiring the Agent to recompute predicates from prose.
8. Determine how authoritative current input reaches each validator. A correct classifier over stale/incomplete/non-authoritative input is not sufficient. Separate:
   - evidence acquisition/completeness/provenance;
   - deterministic classification;
   - semantic interpretation;
   - mutation authorization.
9. Determine runtime feasibility for each proposed executable surface. Do not assume Scheduled Agents can invoke repository-owned code merely because a Python file can exist in the repository; consume #133/#137 findings and prove the actual invocation/tool boundary before proposing live enforcement.
10. Preserve SSOT for workflow topology. `agents/workflow.md` is currently the sole topology authority and current governance prohibits a second DAG/registry. If action-transition lookup should become executable, investigate a design where machine-readable and Human-readable representations do not become two independently maintained authorities.
11. Define regression strategy. Tests must exercise the executable boundary actually consumed by the runtime/action where feasible, not merely a parallel test-only model that can drift from Agent execution.
12. Determine whether executable helpers belong in one shared governance module, action-local helpers, progressively loaded references, existing application modules, or another minimal ownership layer. Avoid a generic framework unless demonstrated reuse requires it.
13. Produce a staged migration order that minimizes scope and allows prose removal only after the executable path is demonstrated and tested.

## Natural-language judgment that should likely remain

The Explore must explicitly protect semantic work from over-mechanization. At minimum evaluate retaining role judgment for:

- Explore root cause, feasibility, alternatives, trade-offs, and `PROPOSAL_READY` meaning;
- whether a new Human-reserved commitment or material scope/behavior trade-off appears;
- semantic proposal/spec/design/task traceability and requirement satisfaction;
- implementation conformance to approved behavior beyond mechanical file/check evidence;
- meaningful regression-test adequacy;
- implementation-vs-specification finding classification when meaning is involved;
- material semantic change;
- whether maintenance/friction is materially worth a new change;
- whether substantive Human input materially affects the current decision/gate.

## Constraints

- This Issue is an inventory/boundary Explore, not authorization to immediately rewrite all governance or Skills.
- Do not duplicate or absorb the narrower remediation owned by #133, #83, #111, or #137. Reuse their evidence and define clear ownership/relationship.
- Do not create a central workflow engine, second workflow DAG, hidden lifecycle state, lock/lease/heartbeat/retry counter, or generic orchestration framework merely to make predicates executable.
- Do not replace semantic role judgment with brittle keyword/text classifiers.
- Do not treat executable output as trustworthy unless required current authoritative input and completeness/provenance are established.
- Do not keep the old full prose algorithm indefinitely after an executable SSOT is proven merely for reassurance; the desired outcome includes context reduction and removal of duplicate normative logic.
- Keep Scheduled Task bootstrap/prompt context thin. Repository governance should describe when/how to obtain authoritative evidence and consume the executable check, not restate the full algorithm in every role/Skill.
- Prefer smallest sufficient ownership and progressive disclosure.
- Preserve current WIP=1 / finish-first semantics. This Issue remains `Change: unset` queued pre-activation work while #133 or another formal workflow owns WIP.

## Decision-complete exit criteria

Explore is complete when Lead can state from current authoritative governance and durable evidence:

1. a complete-enough inventory of deterministic, hybrid, and semantic conditions across shared governance and mapped Skills;
2. which predicates provide the highest correctness/context-reduction value when made executable;
3. the exact evidence-acquisition versus classification versus semantic-judgment boundary for each high-priority candidate;
4. the narrowest SSOT/ownership model that avoids duplicated classifiers or a second workflow DAG;
5. actual runtime/tool feasibility for consuming the proposed executable surfaces;
6. the staged migration order and bounded first proposal scope;
7. which existing governance/Skill prose can be removed or shortened after each migration stage;
8. regression coverage that exercises the real consumption boundary rather than only a parallel model;
9. how `PASS / FAIL / INDETERMINATE` outcomes are consumed without Agent recomputation or override;
10. why the resulting design reduces both correctness risk and invocation context rather than merely adding another validation layer.
