*Project description:*
## Why

The website should show how AngularLynx performs, with charts. I looked for numbers to chart, and there aren't any we can use:

- Nobody has published a like-for-like mobile benchmark of Lynx against React Native, Flutter, NativeScript, Ionic/Capacitor or Angular Native.
- Lynx's "2–4× reduction in launch times" ([launch post](https://lynxjs.org/blog/lynx-unlock-native-for-more)) is for pages ByteDance moved from its own web pages to Lynx, not from React Native, and comes with no method. The same post calls Lynx only "competitive" on iOS. The rival data promised in [lynx-family/lynx#45](https://github.com/lynx-family/lynx/issues/45) in March 2025 hasn't been posted.
- The precise Lynx vs React Native numbers that circulate (420 vs 720 ms cold start, 28 vs 45 MB, 59.8 vs 54.3 FPS) go back to two blog posts from March 2025 that reuse the same Lynx numbers against different frameworks. We can't use them.
- The side-by-side Lynx and React Native repos on GitHub publish no results. One of them shows `Math.random()` as its memory figure.

The only figure that lines up today is engine size, read from each project's published Android artifacts (arm64-v8a, uncompressed): Lynx 4.2.0 10.2 MB, React Native 0.88.1 with Hermes 11.8 MB, Flutter 3.47 11.8 MB, NativeScript 9.1.1 27.2 MB. Compressed, Lynx and React Native are level: 3.59 MB against 3.50 MB for their two main libraries.

So we measure it ourselves, publish the apps, the harness and every raw sample, and chart whatever it shows. Nothing like it exists yet, so it would become the reference for Lynx.

## The test app

[Software Mansion's KMP vs React Native study](https://swmansion.com/blog/we-built-the-same-app-in-kmp-and-react-native-here-s-what-we-found) is the best current method, and its React Native app is public: [software-mansion-labs/launchperf-poke-rn](https://github.com/software-mansion-labs/launchperf-poke-rn) (MIT; Expo 54, React Native 0.81.5). It's a Pokémon list with two tabs, a detail screen and favourites, where each row loads its Pokémon's types. It marks two points:

- **First frame:** `reportInitiallyDrawn()`, when the root layout mounts
- **Fully drawn:** `reportFullyDrawn()`, when the first page of the list renders

On Android it calls `Activity.reportFullyDrawn()`; on iOS it emits an `os_signpost` event. Its SpaceX twin, `launchperf-rn`, no longer loads, because the SpaceX API is gone.

Port it screen for screen, with one change for every app: the data comes from a local server with recorded PokeAPI responses and images, not pokeapi.co, so network time stays out of "fully drawn".

| Angular Native | A port made with `create-expo-app --template @ng-native/template` (Expo SDK 58), built in release with `expo run:ios` and `expo run:android` |

Second round: NativeScript Angular, Ionic Angular on Capacitor, and Flutter.

## What AngularLynx needs first

- **A way to report "fully drawn".** Add `reportFullyDrawn()` to the runtime, with a shell module that calls `Activity.reportFullyDrawn()` on Android and emits an `os_signpost` event on iOS. Apps want it anyway: Android's startup tools (Macrobenchmark, logcat's `Fully drawn` line) measure time to full display from it. Update the public skill in the same PR.
- **R8 on.** The Android template's `build.gradle.kts` has `isMinifyEnabled = false`, since R8 "is off until Lynx's keep rules are verified" ([native-app-builds.md](https://github.com/Blotch-Smart-Frames/AngularLynx/blob/master/investigations/native-app-builds.md)). Without it the APK carries XElement's Guava and media3 unshrunk, so a size comparison isn't fair to us. Verify the keep rules, turn R8 on, and leave out the XElements an app doesn't use.
- **The real size of a new app's bundle.** `ng add`'s comment and the production-build docs say a new app's bundle is "already about 1 MB", but the minimal `element-view` example builds to 370,729 bytes (160 KB gzipped). Measure a fresh `npm create angular-lynx` app, and fix whichever is wrong.

## Rules for a fair run

- Release builds only. Lynx apps run in a release shell, never in Lynx Explorer, as React Native never runs in Expo Go. Android builds use R8 and an arm64-v8a split; iOS builds are exported Ad Hoc or for the App Store.
- Physical devices only for published numbers. The iOS Simulator and the Android emulator are for checking the harness.
  - iOS: my iPhone 14 Pro.
  - Android: needs a physical phone, ideally a budget one, where Lynx's first-frame claims should show most, and a mid-range one.
  - Software Mansion used a Pixel 7, Motorola Edge 60, Huawei P40 Lite, iPhone 13 mini, iPhone 16 and iPhone 17.
- At least 10 runs per app, device and cold or warm start (30 is better), alternating apps run by run rather than in blocks. Record battery level, thermal state and OS build with each run.
- Report the median and p90, and commit every raw sample as CSV. Pin and list every version.

## What to measure

| Metric | Android | iOS |
| --- | --- | --- |
| Time to first frame | `adb shell am start -S -W` (TotalTime) | xctrace App Launch |
| Time to fully drawn | `reportFullyDrawn()` in logcat | The `os_signpost` event |
| Memory | `dumpsys meminfo` PSS at 1 Hz | xctrace Memory Footprint |
| Frame rate and dropped frames, during a scripted scroll | Flashlight, with Perfetto FrameTimeline for jank | xctrace Animation Hitches |
| CPU | `simpleperf stat` | xctrace CPU Profiler |
| Size | `bundletool get-size total` for an arm64 device spec | Xcode's App Thinning Size Report |
| Rendering throughput | Mount 1,500 and 5,000 views, texts and images, as in [reactwg/react-native-new-architecture#123](https://github.com/reactwg/react-native-new-architecture/discussions/123), and Angular Native's 1,000-row bench for Angular against Angular | Same |

Also measure first frame and frame pacing while the JavaScript thread is busy, where Lynx's two threads should make the difference. Callstack's [dual-thread demo](https://www.callstack.com/blog/visualizing-the-dual-thread-model-of-lynx-js) blocks the JavaScript thread for 10 s. Smooth scrolling on an idle phone won't show one: React Native already holds about 59 FPS there.

## Where it goes

- **`benchmarks/` at the root,** outside the npm workspaces, so Expo and Flutter never touch the monorepo build. It holds an app folder per framework, the fixture server, the harness scripts, and `results/` with the CSVs.
- **The website:** a performance section on the home page and a methodology page in the docs.
  - The charts use TanStack Charts' React adapter (`@tanstack/charts/react`; `packages/ui` already depends on `@tanstack/charts`) and read the committed CSVs.
  - Each chart names the device, OS, versions, date and run count.
  - Every metric we measure goes on the page, including any where AngularLynx isn't ahead.
- **Not on the website:** Lynx's "2–4×", and any figure from rutvikbhatt.com, pkgpulse or posts like them.
