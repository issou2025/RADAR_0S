# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**cleanup-fleet-all: escalation must tear down worktrees/branches, not just park them**

*Project description:*
## What & why

`/cleanup-fleet-all` escalates an issue after a failed build/validate round by parking the branch "for a human to look at later" — but nothing ever tears down the worktree or branch that build round created, and nothing enumerates leftover state across the fleet when the run finishes. On the 2026-07-30 overnight run (35 merged / 12 escalated / 0 failed), every one of the 12 escalated lanes parked without teardown:

- 11 stray worktrees (`app-launcher-wt-687..690`, `automation-wt-90..93,95`, `home-automation-wt-575`, `local-llm-hub-wt-451` — the last two as dead unregistered dirs after a partial teardown)
- ~10 stray branches, all 0 commits ahead of `main` (only uncommitted probe edits)
- the `automation` primary left checked out on `docs/94-audit-documentation-findings` with 6 dirty files — a worker building in the primary, the same violation class #515 exists to close
- the `local-llm-hub` primary parked on `chore/449`

Roberto had to order a manual fleet-wide wipe the next morning. This is the teardown-side companion to #515: #515 mandates worktree isolation on the *create* side so a build agent never edits a live primary; this issue is that an escalation never tears its worktree back down, so mandating worktree creation (once #515 lands) will only turn today's dirty-primary incidents into tomorrow's stray-worktree pile — same root failure, one step later in the lifecycle.

## Current state

- `.claude/skills/cleanup-fleet-all/SKILL.md:16` — "a second failure escalates the issue — the branch is left as-is for a human to look at later via `/issue-finish`, never force-merged." No teardown, no GitHub comment.
- `.claude/skills/cleanup-fleet-all/SKILL.md:112-118` (step 8, post-flight) — for `status: "escalated"` it only runs `dirty_tree_check.py check ... --mode built --expect-branch <branch>` against that repo's **primary** checkout. It never runs `git worktree list`, never checks for sibling `<repo>-wt-*` dirs, never checks for stray non-main branches. Checking primaries only is exactly what let 11 worktrees slip through undetected.
- `.claude/skills/cleanup-fleet-all/SKILL.md:161` (hard rules) — "Max 2 build/validate rounds per issue. A second failure escalates — it never force-merges and never silently drops the issue from the final report." Silently dropping *from the report* is guarded against; silently leaving worktree/branch state behind is not mentioned at all.
- `.claude/workflows/cleanup-fleet-all.js:100-150` (`processIssue`) — every `return { ..., status: 'escalated', ... }` (lines 118, 146, 149) returns straight from a failed build/validate round with no fourth step. The file's own header comment states the script "owns zero Bash/filesystem access by design — every repo-mutating action happens inside a spawned agent, never here," so a teardown step belongs as another `agent()` call in this chain, not orchestrator-side Bash.
- `skills/_lib/worktree_claim.py:521` and `:435` already expose `remove-worktree` (reparse-safe junction teardown, `remove_worktree()` at line 362) and `release` (idempotent claim release) subcommands — the primitives this issue needs already exist and are proven (used by `codebase-audit` step 8b's self-heal). Nothing currently calls them from the escalation path.
- `skills/_lib/dirty_tree_check.py:95-111` (`gather`/`cmd_check`) only ever inspects the single repo path it's pointed at — current branch, porcelain-clean, commits-ahead. It has no notion of sibling worktree directories or of "other branches in this repo besides the one I'm told to expect."
- Nothing today posts the escalation reason back onto the GitHub issue itself — the failure feedback and branch name only ever reach the console/Slack final-summary block (`SKILL.md:136-147`). The open issue is meant to be the durable escalation record but currently carries none of the context a human would need days later.

## Scope

- `cleanup-fleet-all`'s escalation path (`.claude/workflows/cleanup-fleet-all.js`, `.claude/skills/cleanup-fleet-all/SKILL.md`).
- The orchestrator's final post-flight verification (`SKILL.md` step 8/10) — extend it to enumerate residual worktree/branch state fleet-wide, not just check the primaries of merged/escalated repos.
- Investigate whether `/cleanup-fleet`'s easy-tier `❌ failed` path (`.claude/skills/cleanup-fleet/SKILL.md:257`, "branch left for inspection") shares the same no-teardown, no-comment gap — see Constraints below. `/cleanup-fleet`'s hard-tier `📋 review` parking is intentional (a human is expected to run `/issue-finish` on it) and is **not** in scope — don't touch that path.
- Not in scope: re-litigating #515's worktree-mandate design, or `codebase-audit` step 8b's self-heal (already worktree-aware and already tears down via the same primitives — worth a quick sanity check but no changes expected).

## Proposed approach

1. **Add an `escalate()` step to `processIssue` in `cleanup-fleet-all.js`**, invoked on every path that currently `return`s `status: 'escalated'`. It should be a dedicated `agent()` call (consistent with the script's zero-Bash-here design) that:
   - Posts a `gh issue comment` on the issue with the failure feedback (build `reason` or validator `feedback`, whichever fired last) and the branch's HEAD SHA if it has any commits ahead of the default branch (a WIP marker for whoever picks it up later) — this is the durable artifact per this issue's title; the branch/worktree is not.
   - Always runs `skills/_lib/worktree_claim.py remove-worktree` (if the build ran in a worktree) and `release` (idempotent either way), deletes the local feature branch, and confirms the primary checkout is back on a clean default branch — never leaves a repo the way the 2026-07-30 run did.
   - This mirrors the shape `executePrompt` already uses for shipping; add an `escalatePrompt(issue, build, reason)` alongside `buildPrompt`/`validatePrompt`/`executePrompt`.
2. **Extend the orchestrator's final verification** (`SKILL.md` step 8, after all buckets finish) to, per touched repo: `git worktree list`, a scan for sibling `<repo>-wt-*` directories next to it, and `git branch` for non-default local branches — and if any survive, **fail loud**: append it to the final report as its own escalation-worthy line (not folded into a clean-looking `✅`/`📋` status), same "no silent pass" discipline the global CLAUDE.md already requires of health/verification gates. This is the check that would have caught all 11 stray worktrees before Roberto had to.
3. **Cross-link, don't duplicate #515**: #515 is "never build in the primary" (create-side); this issue is "always clean up after yourself" (teardown-side). Reference both ways once both are filed.
4. **Check `/cleanup-fleet`'s easy-tier `❌ failed` branches** (SKILL.md:257) for the same gap — no GitHub comment, no teardown — and, if confirmed, fix it in the same PR (small, same shape). Leave hard-tier's intentional `📋 review` parking untouched.

## Acceptance criteria

- [ ] Every `cleanup-fleet-all` escalation posts a `gh issue comment` with the failure reason and WIP SHA (if any) before returning.
- [ ] Every `cleanup-fleet-all` escalation tears down its worktree (`remove-worktree`), releases the claim, deletes the local branch, and leaves the primary on a clean default branch — verified, not assumed.
- [ ] The orchestrator's final verification enumerates `git worktree list` + sibling `<repo>-wt-*` dirs + non-default local branches across every repo touched in the run, and fails loud (surfaced in the final report) if anything remains.
- [ ] `/cleanup-fleet`'s easy-tier `❌ failed` path is either confirmed already clean or fixed to match, in the same PR.
- [ ] `SKILL.md` no longer describes escalation as just "the branch is left as-is" without qualifying that it's torn down first and the issue comment is the durable record.

## Constraints worth knowing

- Reuse `skills/_lib/worktree_claim.py`'s existing `remove-worktree` / `release` subcommands (reparse-safe `.venv` junction teardown already solved there) — never hand-roll a second teardown path.
- The workflow script (`cleanup-fleet-all.js`) is deliberately Bash-free; any repo-mutating teardown action belongs inside a spawned `agent()`, matching how build/validate/execute already work — don't add orchestrator-side `git`/`gh` calls to the `.js` file itself.
- The final worktree/branch enumeration, by contrast, is read-only and belongs in the orchestrator `SKILL.md` step (Bash/`git` directly), same as the existing `dirty_tree_check.py` post-flight calls — don't spawn an agent just to run `git worktree list`.
- This depends conceptually on #515 landing (worktree-mandated builds) but isn't blocked on it — today's escalations already sometimes land in a worktree whenever `try_acquire` falls back to `MODE=worktree` because the primary is already claimed, which is exactly how the 2026-07-30 run produced 11 of them despite #515 not yet being merged.
