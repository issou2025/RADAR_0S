## Summary

The MCP server stays. What should change is the transport it currently uses to reach Revit.

Today each tool in `revit_mcp/server.py` is a thin wrapper that POSTs to an HTTP endpoint served from *inside* the Revit process by `AsyncHttpServer`, marshalled onto the UI thread by an IronPython `IExternalEventHandler`. pyRevit 7 already provides that transport. Replacing it removes the crash in #2 without changing the MCP server, the tool surface, or any client configuration.

The environment this was diagnosed on is **pyRevit 7.0.0.26237+2139, Revit 2025 (25.5.0.57)**. That version exposes a 15-tool MCP server for Revit:

```
get_context            list_revit_instances   inspect_elements
run_query              run_modify             get_run
get_skill              list_skills            capture_view
show_elements          navigate_revit_link    list_automation
run_automation         lookup_pyrevit_api     lookup_revit_api
```

`run_query` / `run_modify` are the direct equivalents of what `AsyncHttpServer` + `ExternalEvent` are hand-rolling today.

## Three layers, different verdicts

"The MCP server" names two different things here â€” the tool surface, and the machinery that reaches Revit. Keeping the first while replacing the second is the whole proposal:

| layer | verdict |
|---|---|
| `revit_mcp/server.py` â€” stdio MCP server, tool surface | **Stays exactly as it is.** Standards-compliant; verified locally with a clean `initialize` handshake, correct `serverInfo`, all 13 tools listed. |
| `HttpListener` + token + port scan inside Revit | **Replace.** pyRevit's host already does this, and each piece became a distinct failure mode. |
| IronPython `IExternalEventHandler` marshalling | **Replace.** This is the #2 crash. |

The MCP server is the product. The in-Revit transport is an implementation detail of how it reaches Revit, and that detail is what needs replacing.

## Why the current transport is the wrong shape

The in-Revit bridge exists to carry agent requests to Revit. But it bought a list of new failure modes, and every one has now materialised:

| bridge component | failure it introduced |
|---|---|
| `HttpListener` inside the Revit process | port range 40001-40010, bind conflicts, no transport on failure |
| shared-secret token in `~/.revit_mcp/instances/*.json` | silent 401, stale tokens, discovery failure reported as "no Revit" (#3) |
| port scan (`server.py:74-104`) | wrong-instance binding, 10 sockets per discovery call |
| second interpreter + `pip install -e .` | `mcp>=1.0.0` vs `mcp.server.mcpserver` import crash; `"env": {}` wiping `PATH` (#3) |
| `SESSION_BINDING_FILE` on a different path than its producer | binding never persists (#3) |
| IronPython `IExternalEventHandler` for UI-thread marshalling | **the crashes (#2)** |
| floating WPF HUD with a 400 ms `DispatcherTimer` | extra dispatcher thread inside Revit; `Topmost` + `AllowsTransparency` + `DropShadowEffect` over the DirectX viewport |
| `GEMINI.md`, 3 example configs, 2 hook scripts, 5 phantom tools | config drift; agent calls non-existent tools (#3) |

None of that exists to give the agent Revit access. It exists to re-create what the host already provides.

The engine row is a correctness problem, not a nicety: `get_context` reports

```

"default_syntax": "Not available: f-strings, type annotations, ... walrus (:=)."
```

whereas `revit_execute_python` accepts arbitrary code with no engine parameter and no syntax check, so an agent writing an f-string gets a bare `SyntaxError` with no hint that a 3.12 engine is available. Verified live on the reporter's machine.

## Proposed shape

The goal: **keep the MCP server, replace the transport underneath it.** The agent still talks MCP over stdio to a `revit_*` tool surface. What changes is that those tools stop being HTTP requests into a hand-rolled listener inside Revit, and start being calls into pyRevit's built-in host.

```
agent  â”€â”€MCP/stdioâ”€â”€>  revit_mcp server (UNCHANGED, stays)  â”€â”€>  pyRevit MCP host
                                                                        â”‚
                                                                        â””â”€> Revit, safely
```

1. **Keep `revit_mcp/server.py` as the MCP server.** The tool surface stays where it is â€” `revit_ping`, `revit_execute_python`, `revit_capture_screenshot`, `revit_set_busy`, etc. Clients change nothing; `python -m revit_mcp` and all client configs keep working. No deprecation, no migration.
2. **Change what each tool calls.** Today a tool POSTs to `http://127.0.0.1:<port>/api/execute`. Instead it delegates to the host's `run_query` / `run_modify`. The tool contract is preserved; only the implementation underneath changes.
3. **Delete the Revit-side transport** that the host replaces: `AsyncHttpServer`, the `HttpListener`, the bearer token, the 40001-40010 port scan, `instance_<port>.json`, and the `session_binding.json` cache.
4. **Delete the IronPython `IExternalEventHandler`** (`RevitExecutionHandler`, `ExecutionTask`). This is the #2 crash. Nothing in the extension should call `ExternalEvent` for script execution any more.
5. **Keep the HUD, and narrow it to what only it can do:** `PickObject` on request, screen snip + markup, busy/idle indicator. Those are human-in-the-loop interactions the host does not expose.
6. **Hard constraint on the HUD: it must not own Revit-side script execution.** It may request a pick and display state; it must not `exec()` agent code through an `ExternalEvent`. This is the one non-negotiable requirement, or #2 survives the refactor.
7. **Do not call `PickObject` from `Execute()`.** Per #2, either route it through a mechanism that cannot throw into Revit's frame, or hold `revit_request_user_selection` out of the MVP until it can be shown to be safe.
8. **Keep the current HTTP bridge as an explicitly-labelled fallback** for clients or setups where the host is unavailable â€” not as a path the agent is instructed to fall back to (that is GEMINI.md rule 13).

Net effect: same MCP server, same tools, same client configs â€” a much smaller Revit-side footprint, and no `ExternalEvent` in the request path.

## Scope of this proposal

**Not proposed:** removing `revit_mcp` as an MCP server, deprecating the stdio entry point, or changing the tool surface or client configuration. Clients keep talking MCP to the same tool names. Everything here is behind that interface.

**Proposed:** replacing the in-Revit transport those tools currently use â€” the `HttpListener`, the token/port-scan/instance-file machinery, and the IronPython `ExternalEvent` â€” with calls into pyRevit's host.

If that distinction is not the intent being proposed here, this issue should be closed as a misunderstanding.

## Interaction with `mcp-server-for-revit-python` (Routes-based)

There is already a second Revit-MCP extension in circulation, [mcp-servers-for-revit-python](https://github.com/mcp-servers-for-revit/mcp-server-for-revit-python), which uses the pyRevit **Routes** API instead of a hand-rolled listener. Both can be registered in the same client at the same time. Worth stating explicitly what does and does not conflict:

| | in-Revit transport | port | requires a ribbon click |
|---|---|---|---|
| this extension | hand-rolled `HttpListener` | 40001-40010 | yes |
| `mcp-server-for-revit-python` | pyRevit Routes | 48884 | no (Routes is a global pyRevit service) |
| pyRevit built-in agent host | local named pipe | n/a | no |

**No pyRevit Routes change is needed for the two to run concurrently.** Routes is a single global listener started once from `[routes] enabled = true`; this extension never registers a route and never touches it. The two are independent.

The real problem is tool-surface overlap in the agent, not a runtime conflict:

| `mcp-server-for-revit-python` | this extension |
|---|---|
| `execute_revit_code` | `revit_execute_python` |
| `get_revit_model_info` | `revit_get_active_model` |
| `get_revit_view` | `revit_capture_screenshot` |
| `get_selected_elements` (pending) | `revit_get_selection` |
| `launch_revit`, `open_document`, `save_document`, `sync_with_central` | â€” |

MCP namespaces both servers, so nothing breaks mechanically, but an agent handed both surfaces will pick between two ways to run Python in Revit â€” one of which currently crashes the host (#2). Note also that the Routes-based extension has capabilities this one lacks (`launch_revit`, document open/close/save, `sync_with_central`).

If the consolidation above is pursued, or if the Routes path is adopted instead, note that `startup.py` there uses `routes.API('revit_mcp')` and this package is also named `revit_mcp`. That is an import-collision risk inside Revit's IronPython namespace, so adopting Routes would want a distinct API name. Not a prerequisite for #2/#3, only for a future consolidation.

## Counterargument â€” why the current transport is defensible

@AndreyStartsev may reasonably reply:

- The bridge works with **any** MCP client, including ones pyRevit does not support. Delegating to the host may narrow that.
- pyRevit's MCP host is new and its API surface could change or be dropped, so building on it is its own risk.
- This is MIT, self-contained, with no dependency on pyRevit internals â€” genuinely valuable for non-pyRevit users, who have no host available.

That argument is legitimate and is why this is filed as a discussion rather than a bug. It is also why item 8 above keeps the current bridge as a fallback rather than proposing its removal.

What the counterargument does not cover is the transport specifically: `ExternalEvent` marshalling of script execution kills the host (journal 1337, a plain agent query, no UI interaction). That part is #2, and it is independent of where the script execution ends up.
