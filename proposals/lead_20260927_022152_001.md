# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Revit: a 2 km² import takes 76 to 117 minutes in every supported Revit — get it under 5 minutes**

*Project description:*
**Host:** Revit 2025, 2026 and 2027. **This is not a Revit 2025 edge case.** Both measurements below are from Revit 2027.

A free-tier order of about 2 km² takes **76 to 117 minutes** to import in Revit 2027. Most of that time is spent inside single commits during which Revit reports "not responding". A curator reads that as a crash. Revit 2025 is slower still on the subdivision steps (#249, folded in below).

**The target: under 5 minutes** for a full import with every layer included, in each of 2025, 2026 and 2027. The platform's own build time for the order is the fallback ceiling. The data is already prepared and local, so the import should not be slower than building it. Today's 76 minutes is about 15 times over the target.

**What a 15× cut means:** tuning cannot close the gap on its own. The drape alone takes 42 minutes. In Revit 2025, one subdivision covering the whole order takes about 9 minutes by itself on a bare terrain (#249). So meeting the target in 2025 needs a different representation for at least that kind of layer, not a faster version of the current one. Phase 2 has to weigh representation changes, not only the order of cuts and how commits are grouped.

This issue replaces #249, which covered one step in one Revit version. It is the umbrella for the whole import: measure every step in every version, then plan and land the improvements. **Nothing is implemented here.**

## What #249 established (Revit 2025, folded in)

On the MPB 1.4.0 order (74,855 points), with terrain, land use, land cover and water:

- The land-cover commit took 970 s before #250 and 1,783 s on #250's branch. That is one run each, and two runs of one configuration have differed by up to about 1.8×. Revit 2026 and 2027 took 150 s and 178 s for the same commit.
- **In 2025, cost tracks how much of the toposolid a subdivision covers**, not how many subdivisions share a commit. A single 5-vertex grass ring covering the whole order took **526.5 s** alone on a bare terrain.
- Three levers were probed: commit per cut, land cover first, and both combined with largest first. None met the acceptance line. Land cover first, the best of them, merged as #256 (873 s against 999 s, inside run-to-run noise).
- `SlowStepNotice`'s later-layer wording was corrected (#251, #254).

A full 2025 import of either order has **not** been measured. Road surfaces and the drape, the two largest steps in 2027, have not been timed in 2025 at all.

## Phase 1: measure everything, in all three versions (agent work, no human needed)

An agent runs this on this machine. The scratch harness runs any commit's code in a real Revit beside the install slot, unattended and without taking focus.

1. **The full import of `4276ef78`, once per version (2025, 2026, 2027), every layer checked.** Record every step, every commit and the gaps between commits. The import log times every commit. The Revit journal keeps each transaction's commit seconds after the log beside the zip is overwritten. If 2025 never finishes a step, record the step, the elapsed time at the cut-off and the journal's last activity, and treat that as the measurement. It is not a failed run.
2. **Each import option in isolation.** Run every layer in the checklist alone, with its prerequisite (terrain), per version, so that each step's cost is its own and not the result of what came before it. At minimum:
   - terrain
   - terrain plus each polygon layer
   - terrain plus the drape, with and without the polygon layers
   - planting
   - context buildings
   - the IFC link
   - contours
   - the hazard layers, where a bundle carries them
3. **Split plugin time from Revit time** inside the three largest steps (drape retype loop, road surfaces, planting). Use a profiler trace, not only the log. The drape's 20 to 30 minutes of retyping happen *outside* its commit, in API calls the plugin makes, and that is the most tractable part.
4. **Record variance.** Run each isolated measurement at least twice, and don't report a gain smaller than the spread between runs.
5. Post the results here as one table: every step, every version, in seconds, with the commit each run was built from.

### Iteration speed

The target is minutes per experiment, not an hour and a half.

- **Explore in two versions at once, and gate in three.** Revit 2025 has its own subdivision cost. Revit 2026 and 2027 share the typed-subdivision drape path and measured close to each other in #249. Explore in **2025 and 2027 in parallel processes**, and run 2026 only at checkpoints and at the end.
- **Checkpoint projects.** For each version, save a project once it has the terrain and all subdivisions. An experiment on the drape, planting or the view then opens a copy of that project instead of re-cutting 400 subdivisions first. Revit upgrades a project to a later version but cannot save to an earlier one, so keep one checkpoint per version.
- **Run only the steps under test**, with `ImportLayerChoice.Only([...])`. The full import runs only at a checkpoint.
- A probe in a scratch copy is fine for finding a lever. What merges goes through the normal build, tests and PR.

## Research track: are we building this plugin the right way?

This runs alongside Phase 1 and is a large part of the effort, not an appendix. The Revit plugin grew one step at a time, and some of its slowness may come from the approach rather than the code. Before Phase 2 commits to levers, survey how a modern, fast Revit add-in is built. Use primary sources: Autodesk's API documentation and "What's New" notes for 2025–2027, the Revit API forum and blog posts by Autodesk engineers, and well-maintained open-source add-ins. Compare what they do with what this plugin does. Each question gets an answer with a source, or a stated "unknown".

**Revit API performance**
- What does a commit actually cost, and what controls it?
  - Regeneration, `TransactionGroup.Assimilate` versus separate commits, and `SubTransaction`.
  - Failure-handling options and preprocessors.
  - Whether warnings raised during a commit add cost.
- Batch creation APIs versus one call per element: for example `NewFamilyInstances2` for planting, the batch overload of `ChangeTypeId`, and batch parameter writes.
- What changed in toposolids and subdivisions from 2024 to 2027: typed subdivisions, their cost model, any newer API for splitting or subdividing, and what Autodesk says about subdivisions at scale.
- What else could carry roads, land cover and the photograph with no toposolid relation rebuild: DirectShape, floors, filled regions, decals, material painting, or a link. Weigh each for curator value, not only speed.

**Responsiveness and architecture**
- Can the import window live on its own UI thread, so it stays live and shows the current step while Revit's thread sits in a commit? Or is the staged `ExternalEvent` model the ceiling?
- Is idling, external events or an external command the right driver for a long-running import today?

**Where the work happens**
- Could the heavy geometry be prepared *outside* the curator's Revit? For example, the platform could build an `.rvt` or a Revit family with a headless cloud Revit such as Autodesk Platform Services Design Automation, and the plugin would place it. That moves work to the platform and changes cost and licensing, so it is a maintainer and platform decision. Record the answer, but don't route the work here.

**Development workflow**
- Multi-version builds for 2025, 2026 and 2027 from one project: the API NuGet packages and community SDKs and templates.
- Reloading an add-in without restarting Revit.
- In-Revit test runners, compared with the scratch harness.
- Profiling inside Revit (dotnet-trace, PerfView, Revit's own tools).
- Anything that makes one experiment cost minutes rather than an hour.

**Output:** a findings document written with the repo's research skill, cited here. It should have one section per question, each ending with what it means for this plugin: *keep*, *change*, or *measure in Phase 1*. A finding that says "change" and touches architecture becomes its own issue.

## Phase 2: plan the improvements from the numbers and the research

These are hypotheses to test in Phase 1, not decisions, and the research track may add to them or replace them. Each one names the constraint it touches.

- **Imagery drape (56 to 67%).**
  - Under smooth shading every subdivision gets its own material, anchored to its own corner ([ADR 0008](https://github.com/mantleplace/mantleplace-dcc/blob/main/docs/adr/0008-revit-drape-is-anchored-to-the-smooth-shading-origin.md)). That per-subdivision cost is real, but three things are worth measuring:
    - What each ~3 s retype actually spends its time on.
    - Whether a subdivision could be **created on its imagery type** in its own polygon step. That would drop a second relation rebuild over the whole terrain, the way the terrain is already created on the imagery type.
    - Whether per-change regeneration can be deferred.
  - The smooth-shading commit (141 to 422 s) runs *after* 400 subdivisions exist. Measure it before they are cut.
- **Road surfaces (25%).** 344 subdivisions in one commit, with 1,247 reported overlaps. Measure how the commit scales with overlap versus count, and whether roads cut before or after the other layers (or in several commits) change 2026 and 2027 even though they did not change 2025's land cover.
  - Clipping or merging published polygons stays ruled out: the plugin applies them verbatim. Changing that would be a platform decision, not a plugin shortcut.
- **Planting (7%).** About 17 ms per instance, with one `NewFamilyInstance` and three parameter writes by name for each. Measure batch creation (`NewFamilyInstances2`), parameters looked up once rather than by name per instance, and a larger chunk size (`ImportChunking.ElementsPerTransaction`, now 200).
- **The site IFC is read twice**, once to copy the buildings out and once to link it (about 105 s). Measure opening it once.
- **Site context view (57 to 72 s)** for one view and one filter is suspicious. Find what it waits on.
- **Terrain density.** `SlowStepNotice` records a decision that the plugin does not make the import faster, and that refused decimation, point sampling and skipping the boundaries. **This issue reopens that decision.** The refusal of decimation *inside the plugin* stands: it is also the thin-client boundary. Whether the platform should publish a surface sized for Revit is a question for the platform, and it is out of scope here.

- **Representation changes, which are maintainer decisions.** The 5-minute target probably needs at least one. Each must be measured before it is chosen:
  - Roads, or a whole-order land-cover ring, drawn as something other than a toposolid subdivision. The candidates are elements that do not make Revit rebuild the terrain's relations at commit.
  - The photograph carried by the terrain alone, with the subdivisions drawn over it, instead of one anchored material per subdivision.
  - Which layers start checked in the import window. The slowest optional layers could default to off, so the default import meets the target and a curator opts into the rest knowing the cost.

  Each one changes what the curator gets, so none lands without the maintainer's call. None of them may compute a placement value locally.

Each lever that survives Phase 1 becomes its own issue, linked from here, sized to one PR.
