*Project description:*
## Intent

Reassess Mosaic's production build-size policy **from first principles**, rather than presuming all seven bespoke blocking metrics are necessary. Replace early-stage and repeatedly extended byte-budget machinery with the smallest maintainable industry-standard Vite/PWA performance workflow, **even if this means deleting or replacing the current guard**. Optimize for consistently smooth mobile/PWA UX, safe offline updates, fast ChatGPT-first feature delivery, and long-term simplicity. **Research/planning only; no code or budget-change authorization yet.**

**Distinct from #592:** #592 owns the secure, quota-safe GitHub CI → validated artifact → **no provider deployment before acceptance** → Vercel Preview delivery, build-input parity, alias and approvals. This issue owns **what size/performance acceptance should mean**, which tools should implement it, historical budget-policy debt, saved metrics and scheduled optimization audits. #592 must not be blocked indefinitely on an arbitrary 7/7 migration requirement; maintain the currently accepted guard until any replacement is separately approved and verified.

## Why revisit the original decision?

- [PR #1 (2026-09-20)](https://github.com/carlers/mosaic-life-tracker/pull/1) introduced a five-metric size budget inside a **63-file** multi-domain infrastructure/PWA/cache/workflow PR. Original stated aim: avoid unexpected app/precache growth. It was not proven as the optimal sustained governance scheme.
- [PR #122 (Sep 28)](https://github.com/carlers/mosaic-life-tracker/pull/122) already had to rebaseline after TodoMate/photo/sync feature growth and restore about 5% aggregate headroom.
- [PR #228 (Oct 3)](https://github.com/carlers/mosaic-life-tracker/pull/228) achieved real loading optimization and added two more mandatory metrics: Vite initial/Home static-import closure gzip, taking the guard from five to seven. A useful *measurement* need not imply a blocking **byte ceiling** on that metric.
- [PR #390](https://github.com/carlers/mosaic-life-tracker/pull/390) fixed a 416-B false size regression caused by commit-message metadata, not a changed app bundle. [PRs #548](https://github.com/carlers/mosaic-life-tracker/pull/548), [#583](https://github.com/carlers/mosaic-life-tracker/pull/583) and [#750](https://github.com/carlers/mosaic-life-tracker/pull/750) documented same-tree GitHub/Vercel effective-output size divergence. [PRs #677](https://github.com/carlers/mosaic-life-tracker/pull/677), [#724](https://github.com/carlers/mosaic-life-tracker/pull/724) show +14 B gzip byte-golf and +2 B violation prompting a +8 B exception.
- Current `npm run build` bundles type checking, Vite compile, PWA/SW semantic verification, artifact fingerprinting and all seven budget failures. It is not obvious that *successful app building* should itself require every aggregate-size policy to pass.
- Current `scripts/check-service-worker.mjs` already verifies offline shell, static app-chunk coverage, bounded same-origin precache references, update activation semantics and precise `mosaicBytes` progress weights; **preserve this correctness contract**. Vite PWA/Workbox offers `maximumFileSizeToCacheInBytes` per precached asset; Vite already exposes compressed output sizes and chunk warnings. Those native capabilities may remove some need for bespoke numeric rules. They **do not** replace total PWA install/update budget measures or offline correctness validation.
- As the app grows via new features and future integrations, globally prohibiting growth in *lazy/deferred* bundles is not necessarily a user-meaningful performance policy. Startup, a representative authenticated Home visit, update/install payload and interaction responsiveness are different problems.

## External patterns inspected / candidate evaluation

1. [Vite's build options](https://vite.dev/config/build-options.html): built-in per-chunk size warnings/gzip reporting. Baseline option, **not a whole-site performance guarantee**.
2. [Vite PWA FAQ](https://vite-pwa-org.netlify.app/guide/faq) + [Workbox](https://vite-pwa-org.netlify.app/workbox/): precache entry size limit and generated SW verification, **not a total update/install cap**.
3. [Size Limit](https://github.com/ai/size-limit) + [@size-limit/file](https://github.com/ai/size-limit): well-established **minimal file/glob size gates** and optional PR comments, in built apps and libraries. Would avoid bespoke raw/gzip budget code if only a small number of hard file metrics are retained. Its library usage by [Nano Stores](https://github.com/nanostores/nanostores/blob/main/package.json) is real but **not** an exact comparable PWA architecture.
4. [rollup-plugin-visualizer](https://github.com/btd/rollup-plugin-visualizer): simple opt-in treemap/JSON diagnostics; a [real React/Vite PWA starter](https://github.com/azamaulanaaa/react-pwa-starter) uses it without bundling seven custom byte limits into `vite build`. A starter is only illustrative, not industry prevalence proof.
5. [BundleMon](https://github.com/LironEr/bundlemon): size groups/CI/PR/history, but dependency on GitHub integration/optional hosted reporting and no automatic Vite route closure/SW semantics. Compare local-only implementation burden to benefits before choosing.
6. [BundleStats](https://github.com/relative-ci/bundle-stats): useful Vite package/module diff diagnostics; may be overkill for each acceptance. Distinguish standalone local CLI from hosted RelativeCI.
7. [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md): supports per-page resource/performance budgets and warn/error assertions, but authenticated Mosaic Home and offline PWA scenarios require trustworthy fixtures and repeatability; appropriate as targeted/periodic diagnostic initially, **not another obligatory every-Preview browser gate**.

**No tool migration decision yet.** Original #592 recommendation "BundleMon top candidate" is not binding. Evaluate dropping old constraints vs tracking them as warning-only; 7/7 numerical parity is not a legitimate prerequisite if that defeats the purpose of redesign.

## Proposed minimal end state (hypothesis to test, not preapproved policy)

- **Must pass for every deployable candidate:** existing functional/tests/security/Scratch correctness, Vite/TypeScript build, PWA policy/precaching checks and exact accepted artifact. No Vercel provider POST for a red candidate—#592 owns this.
- **Size visibility at acceptance:** one existing-artifact comparison showing **initial/entry load**, **total shipped JS/CSS**, **PWA precache and update-change footprint** (where measurable), and major dependency/chunk growth; compare same effective Scratch/GIPHY/toolchain profile. This can initially be *informational* except for demonstrably necessary hard limits.
- **Hard stops only when justified by actual UX or platform constraints:** e.g. an excessively large initial-load payload, a significant accidental heavy dependency, or Workbox's per-file precache limit. Select the *fewest* hard assertions that defend real risks; use normal tooling and deliberate headroom. Do not blindly use 1 B, 1 KiB, 5%, 10%, or any universal arbitrary grace. **The existing seven ceilings remain in force until a measured, explicitly reviewed cutover.**
- **Twice-weekly non-deployment audit:** consume accepted build metrics snapshots if possible; examine growth trends and use a local-only visualizer or BundleStats **on demand**. Optional monthly seeded/device loading and PWA update checks. No arbitrary new deploys, paid platform, obligatory SaaS, ChatGPT external approvals or auto budget resets. GitHub schedule is approximate; Monday/Thursday is not a literal fixed 72-hour period.
- **Separate build from policy:** consider `npm run build` for compiling/validating product correctness, a `size:report` diagnostic script/tool on the produced output, and only required `size:check` thresholds in predeploy acceptance. Do not rebuild solely to run size checks, and do not ship analyzer reports into `dist`/precache.

## Implementation plan / stop-go acceptance criteria

**D0 — zero-deployment historical baseline & requirements audit:** From PR #1 and current `dev`, inventory what each metric was intended to prevent; distinguish size-policy failures vs wrong effective config vs genuine PWA/startup regression, including known PR #390 false metadata, #548/#583/#750 hosted variance, notifications growth, and initial/Home improvements in #228. Establish current output, comparable run-to-run variance, PWA install/update behavior and whether any real user slowdown was *predicted* by existing caps. **Test necessity, don't assume it**.

**D1 — local-only alternatives spike (no code promotion):** On one exact safe artifact and historical fixtures, compare: (A) native Vite/PWA + light report only; (B) `@size-limit/file` for 1–3 outcome-based hard checks + visualizer on demand; (C) BundleMon or BundleStats only if demonstrably simpler. Assess GitHub integration, artifact reuse, full change-over code/lockfile/config/tests/dependencies, costs, repeatability, no-provider quota use, long-term maintenance. Include 2 realistic features with legitimate growth and 2 deliberate regressions; report which tool catches *meaningful problems* with lowest toil. Include workbox total/update vs per-entry measurement nuance. **Prefer fewer gates, not numerical 7/7 equivalence**.

**D2 — policy decision and explicit approval:** Propose hard/warn/report split, performance justification, thresholds from measured data and accepted real device/browser baselines, rollback path, and changes to `PROJECT_REFERENCE.md §24.14`, budget file, tests and `AI_WORKFLOW.md`. Preserve PR approval process; no silent cap inflation or waiver. Coordinate exact interface with #592's prebuilt artifact and trusted approval gate. **Do not remove current guard until replacement policy accepted.**

**D3 — bounded rollout:** Add new reporter in shadow alongside seven-budget checks without new provider deployments; compare several accepted candidates and representative old failure fixtures; then perform owner-approved atomic cutover to approved minimal guard, remove obsolete test/docs/byte-golf machinery, validate reproducibility + PWA offline/update progress + source-artifact identity + CI and Preview. If a useful intended regression slips, rollback.

**D4 — evidence-based retrospective:** Measure Preview-to-test time, budget-only repair cycles, number of provider deployment creations on red, actual UX/startup/update size and incidents over several releases; adjust only on evidence. #592's quota-safe delivery success is tracked **separately** from this issue's reduced budget toil.
