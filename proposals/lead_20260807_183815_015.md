## Goal

Close the gap between the current CSE Codex Loop and Fatih's accepted operating contract: after one approved Issue starts, the system must continue without repeated user `d` messages until the Issue reaches a true terminal state.

Current verified gaps:
- The installer deliberately registers `CSE Codex Loop` Disabled and there is no narrow, repository-owned operator activation entrypoint.
- The worker stops after local validation, independent Codex review, commit/push and Draft PR creation with `READY_FOR_FATIH`; it does not finish the approved Issue.
- Issue #371 has a valid `cse-bridge-task:v1` body plus the latest trusted `CSE_BRIDGE_APPROVED` and `CSE_LOCAL_GATE_REQUEST`, but no `RUNNING` marker appeared after the scheduled trigger window.

Implement a fail-closed terminal-completion controller boundary:

1. Add an explicit repository-owned activation entrypoint for the already-installed Windows Scheduled Task. It must:
   - require the existing dedicated-control-clone configuration and exact task name;
   - refuse activation unless the task action, principal, runner path, config, repository role and current `origin/master` admission are valid;
   - run one read-only Codex smoke before enablement;
   - enable the task only after every acceptance check passes;
   - never install credentials, elevate privileges, modify the production repository, or silently weaken task settings;
   - be idempotent and report a data-minimal status.

2. Extend successful publication so the same deterministic host can complete the approved Issue without another user `d`:
   - keep implementer, host validation and independent read-only reviewer gates unchanged;
   - after publication, verify the PR belongs to the exact repository/base/branch and exact published head SHA;
   - transition the PR out of Draft only after those checks;
   - squash-merge only that exact approved head with no force, branch deletion or bypass;
   - verify the merged result from GitHub before posting PASS;
   - close the Issue only after verified merge if GitHub has not already closed it;
   - use a terminal success marker distinct from the former pre-merge `READY_FOR_FATIH` state;
   - any head drift, mergeability ambiguity, review failure, API error or repository mismatch must stop fail-closed as `NEEDS_HUMAN` or `FAILED` with no merge.

3. Preserve human-on-exception behavior:
   - `review_needs_human`, unresolved second review, merge ambiguity, head drift, protected-branch refusal and any unsafe state stop without merge;
   - ordinary successful Issues do not require a user continuation message;
   - do not automatically create or prioritize new product Issues in this task.

Add deterministic mocked tests for activation admission/rejection/idempotency and for exact-head ready/merge/verify/close success plus every fail-closed boundary above. Update the operator documentation with the one-time activation and rollback/disable path.

Validation class: release-critical orchestration control plane, not mobile release.
Retry budget: one primary implementation and at most one exact correction.
Time budget: 75 minutes hard stop.
No merge of this bootstrap PR by the worker currently under modification; publication remains Draft PR so the existing controller cannot self-authorize its own new merge power. A separate trusted GitHub review must merge this bootstrap once. After that, Issue #371 is the live terminal-completion acceptance.
