## Premise

The original Light Herder is not software. It is Dave Blair's physical optical rig: real cameras on rotating, sliding shafts pointed at stacked monitors through a 45° 50/50 beam splitter, hardware video switchers/keyers, matrix routers, frame-delay boxes, and analog hue/contrast/brightness/saturation knobs. There is no download, manual, MIDI map, preset file or app store listing anywhere on the site or in the build log. "Parity" therefore means: every capability the rig gives its operator has a lightherder equivalent the board can drive, within the hard constraints below.

Sources (untrusted data, facts only): thelightherder.com (61 posts, 2003–2026), the build log at walkswithdave.tumblr.com (tag `videofeedbackkineticsculpture`, 473 posts; the Aug 2026 4K schematic and the Apr 2024 Phase 4 schematic), Hackaday 2021/2024/2026 with Blair's own comments, Make: "Freaky Fractals HD Video Feedback Machine" (the only build guide), cdm.link 2026, video descriptions on Vimeo/YouTube. Cited below as **site**, **log <date>**, **HA26**, **Make**.

## Hard constraints

Owner-set; they override parity wherever the two conflict:

- Stay true to Blair's model: cameras watch monitors ONLY (recursive-only); external light (files, capture, patterns) enters via the switcher/mix, never as a camera target.
- The nanoKONTROL2 board + window-close are the ONLY inputs (keyboard input was deleted 2026-09-01). Dead buttons are fine; bind only real equipment; control overflow fails loudly at load.
- Two deploy targets, BOTH on every landed stage: the TV binary at `/home/a/lightherder/lightherder` (build release from the landed HEAD, copy to `lightherder.new`, sha256 both sides equal, `mv lightherder lightherder.prev` then `mv lightherder.new lightherder` — rename, never overwrite in place; preserve owner/mode; never touch `run-lightherder.sh`; never launch or restart anything on the TV) and the GitHub Pages web build (automatic on push to main). A stage is not done until the installed TV file's sha equals the built artifact's; state both shas in the result.

A parity feature that needs a control the board cannot express is recorded as a gap with that note, not a reason to add keyboard input. The factory map today uses all 8 faders, all 8 rotaries, and every transport button but one (marker-prev, CC 61); 8 of the 24 knobs are off the map (`src/midi.rs:132-136`). Any stage that says "board: page 2" depends on stage 5.

## (c) Increments

Ordered by value; each is one worker job, independently landable and testable. Unambiguous gaps first.

- [x] **2. Momentary cut on marker-prev (CC 61).** While held, the focused monitor shows the focused input (or, with no inputs, the focused camera) whole and nothing else; release restores the prior crosspoints and releases fader pickup. Acceptance: a command test proves down/up round-trips the routing exactly; overlay and card show it; the button lamp lights while held.
- [x] **3. Frame delay, engine + config.** Per-camera `delay` in passes, 0–30, default 0, backed by a history ring of monitor banks; the 2 GiB bank cap counts the ring. Acceptance: GPU test that a seed lit on pass 0 reaches the delayed monitor exactly `delay + 1` passes later, and `delay = 0` is pixel-identical to today. Config only; board binding lands in stage 6.
- [ ] **1. The rig preset: the 4K rig's topology as ONE graph (owner 2026-09-02: model only the 4K rig; an HD-resolution input is sampled into the bank, "upsampled", so resolution is not a topology concern and the HD-only variants are dropped). Order: lands after stages 2–3; a worker armed on it MUST read the owner's newest comments on this issue via botq-issue-brief for corrections to the graph below.** Nodes: cameras A, B, 3; monitors upper-A, lower-A, upper-B, lower-B, rotating; switchers A, B, C, D (two inputs, one program each; the original's cut/crossfade). Optical (the only camera edges): camera A sees upper-A directly and lower-A through the 50/50 glass (0.5/0.5), camera B likewise for structure B, camera 3 sees the rotating monitor only. Electrical: Switcher A = {In1 camera A, In2 camera B feed}; Switcher B = {In1 camera B, In2 Switcher C program}; Switcher C = {In1 camera A feed, In2 Switcher D program}; Switcher D = {In1 camera 3, In2 seed input (external, via the switcher only)}; each structure-A monitor selects In1 = camera A direct or In2 = Switcher A program, independently per monitor; structure-B monitors likewise from camera B / Switcher B; the rotating monitor shows the camera B feed; per-camera frame delay sits right after the camera (stage 3 supplies it; 0 until then). Representation: if the routing matrix already expresses a switcher's program exactly, do NOT add a second mixing mechanism — but the preset must NAME the switchers and the per-monitor In1/In2 selects so that a board control on "Switcher A" moves exactly the rig's crosspoints (one implementation, no drift). Acceptance: `--preset <name>` validates; the "every shipped preset settles without clipping" GPU test covers it; a unit test asserts the flattened taps of each monitor against the graph above (e.g. upper-A on In2 with Switcher A at 100% In2 reads camera B and nothing else); README lists the preset and its controls.

- [ ] **4. V/H flip.** `flip_x`/`flip_y` on `Framing`, composed into the affine. Acceptance: the pan-direction GPU test run mirrored; config round-trips; `deny_unknown_fields` still holds. Config only; board binding lands in stage 6.
- [ ] **5. A second knob page on the board.** One button (candidate: cycle, with `help` moving to a held-chord, or a free select-row button when the graph is small) toggles faders/rotaries between page 1 (today's map) and page 2; page switch releases pickup; overlay draws the live page; `midi.toml` gains `page`. Acceptance: unit tests on paging + pickup; overlay snapshot test. This is the control-overflow stage: without it the 8 off-map knobs and stages 3, 4, 7, 8 stay config-only.
- [ ] **6. Page 2 factory map.** Bind key threshold/softness/hue/tolerance, bloom radius, delay, flip x/y, per-channel gain on page 2. Acceptance: card prints both pages; every `Knob::ALL` entry is reachable from the factory map or has a stated reason.
- [ ] **7. Source reversal.** A button swaps the focused monitor's two strongest crosspoints (A↔B). Acceptance: command test on a 2-source row; no-op with one source.
- [ ] **8. Quantized rhythmic switching.** Period mode: a latch toggles the focused monitor between its two strongest sources every N passes, N from a page-2 rotary, quantized to the tempo. Acceptance: unit test that routing alternates on the exact pass boundary; stops cleanly on reset. Pattern mode (push-button sequences) is a follow-on stage once period mode is in use.
- [ ] **9. Sensitivity curve.** `midi.toml` fader `curve` (0 = linear, 1 = flat middle), applied to brightness and contrast by default. Acceptance: unit test of the mapping's endpoints and midpoint; pickup still catches through the curve.
- [ ] **10. Colour temperature.** One monitor knob shifting the white point along the Planckian locus inside the existing 3×3 matrix. Acceptance: GPU test that grey stays grey at identity and warms/cools at the ends without a luma change.
- [ ] **11. Sharpness.** Per-monitor unsharp mask in the front panel (one extra 4-tap read). Acceptance: GPU test that identity is pixel-exact and a positive value raises edge contrast on the seed's rim.
- [ ] **12. Web external input.** The Pages build accepts a `<video>` element or `getUserMedia` as an `Input` so `external` and `webcam` presets run in the browser, entering via the send only. Acceptance: `?preset=webcam` shows the camera on monitor 1 in Chrome; native path unchanged.
- [ ] **13. Per-path frame rate.** Per-camera `divider` (1, 2, 3) so a path steps every Nth pass, reproducing the 24/30 fps stutter without changing the global tempo. Acceptance: GPU test that a divided path holds its frame for N passes.
