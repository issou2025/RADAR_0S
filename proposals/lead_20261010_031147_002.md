## Can a local GUI be built for Linux, Windows, macOS, iOS and Android?

**Yes.** This is what the design was for: the core is a portable library with a plain C interface, and a GUI is a separate program on top of it.

- **One codebase for all five.** The plan recommends Flutter, which builds for every one of those platforms and can call the core directly. (Qt is the alternative if you care more about desktop than phones.)
- **What exists today:** the core and the terminal client, on Linux only.
- **What each platform needs:** Windows needs a small port of a few Linux-only calls. macOS, iOS and Android need build settings and testing, not redesign.

## Do you need a Mac, or to pay for anything, to build?

**No Mac, and no cost, to build.** GitHub's build machines include macOS and Windows and are free for public repositories like this one. Every platform's build can run there automatically. Your Mac virtual machine would only be useful for trying the result by hand.

**The cost is in app stores, not in building:**

| Platform | Free way to give it to people | Paid way |
|---|---|---|
| Linux | Download | none needed |
| Windows | Download. Windows shows an "unknown publisher" warning the first time | A code-signing certificate removes the warning |
| Android | Download the app file directly (sideload) | Google Play, a one-time fee |
| macOS | Download. Each user has to approve an unsigned app by hand once | Apple Developer Program, about $99 a year |
| iOS | None that works for other people. A free Apple account can put it on your own phone for 7 days at a time | Apple Developer Program, about $99 a year |

So everything except iOS can be shipped for free. iOS for other people needs Apple's yearly fee, which is their rule and not something the code can get around.

## Is a browser GUI possible?

**Yes, but it's the hardest client to build and the least secure one.** You guessed right that it needs custom work.

1. **Browsers can't make the kind of connection the server uses.** A web page can only use WebSockets. The server needs a second way in that carries the same protocol over a secure WebSocket. That part is modest.
2. **The encryption has to run in the browser.** Rewriting it in JavaScript would mean two copies to keep correct, which is where security bugs come from. The better route is compiling the existing core to WebAssembly, which the libraries it uses already support. Real work, but not a rewrite.
3. **There's a trust problem that can't be fully fixed.** An installed app is installed once. A web page is sent fresh on every visit, so whoever hosts it could at any time send a version that steals your keys. Signal has no web client for this reason. It can be reduced (you host the page yourself; an installable web app that only updates when asked) but not removed.

**My recommendation:** build it last, after the desktop and phone apps, and label it as the convenient client rather than the secure one.
