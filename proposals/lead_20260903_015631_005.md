That gate has now been passed. A single day of interactive work (the #113–#118

wedged the instance until a human clicked. This issue records them as the evidence

## The observed signatures

All captured live from the v1 `window-inventory-timeout-fallback` notice, which
worked exactly as designed — it turned a silent hang into an actionable window list
every time.

**1. Virtual memory warning — WEDGED the instance**

```
class_name: #32770
title:      (Revit memory warning)
```
Raised mid-run while several script-created scratch documents were open. Blocked the
idle loop: `execute_script` returned `pending`, `list_instances` kept answering (the
documented liveness probe). Needed a human click on **Close**.

Downstream of issue #31 (memory growth across create/write/close cycles), so
auto-dismissing it treats a symptom — but leaving it wedges an unattended session
indefinitely.

**2. "Project Not Saved Recently" — WEDGED the instance**

```
class_name: #32770
title:      "Project Not Saved Recently"
buttons:    Save the project | Save the project and set reminder intervals
            | Do not save and set reminder intervals | Cancel
```
Timer-driven, so it can fire at any moment including between runs, and it fired
*during* an in-flight `Document.Close` call. Needed a human click.

Note for allowlist design: two of its four buttons mutate persistent Revit settings.
An auto-dismiss that picks the wrong one silently changes the user's configuration.
`Cancel` is the only non-mutating choice, which makes this dialog a good argument for
per-signature button selection rather than a blanket `WM_CLOSE`.

**3. Autodesk trial banner ("24 DAYS LEFT") — NOT a wedge, verified**

Sits over the Revit window and looks exactly like the two above. Registration,
`execute_script`, and a full 11-minute tier-2 suite all ran straight through it.
Worth an explicit non-entry in the allowlist so nobody "fixes" it: `caveats.md`
already records a prior session mistaking it for a wedge, and this is the second
time it has been suspected.

## One alternative explanation, tested and ruled out

Before filing this it was worth checking whether these modals are really *outside*
`DialogBoxShowing` at all, or merely intercepted and answered with a result the
dialog could not accept — a much cheaper fix than a Win32 allowlist.

`DialogSuppressionHandler` answers every intercepted dialog with
`DialogResultDefaults.TaskDialogCancel`, verified live (PR #128) to be genuinely
`TaskDialogResult.Cancel == 2`. But Cancel is only a meaningful *answer* for a dialog
that offers Cancel:

```
TaskDialogResult:  None=0  Ok=1  Cancel=2  Retry=4  Yes=6  No=7  Close=8
```

So a `TaskDialog` offering only `Close` (8), or only `Yes`/`No` (6/7), might
plausibly ignore the override and display anyway. **Tested against Revit 2027 — it
does not.** Three dialogs raised from a script and answered by the handler:

```
offers Cancel (control)  -> handler sent 2 -> Show() returned Cancel(2), never displayed
offers ONLY Close        -> handler sent 2 -> Show() returned Cancel(2), never displayed
offers ONLY Yes/No       -> handler sent 2 -> Show() returned Cancel(2), never displayed
```

`OverrideResult` is not validated against the button set: it suppresses the dialog
and returns the value whether or not that button exists. **So the cheap explanation
is dead, and v2 is genuinely needed** — the wedging modals are never intercepted at
all, exactly as §07 assumes. Recorded in PR #128.

## Scope when it is built

Per §07 v2, unchanged in direction:

- Extend the existing v1 window-enumeration pass (background thread — the UI thread
  is blocked by definition) to match an allowlist of title/class signatures and act
  via `WM_CLOSE` or a simulated click on a **named** button.
- Allowlist, never a blind "close anything modal" heuristic: §07 already says
  misfiring on a legitimate window is worse than leaving it to the v1 diagnostic, and
  signature 2 above shows why — two of its buttons change persistent settings.
- Record every auto-dismissal as a §01 diagnostic in `notices[]`, the way
  `dialog-auto-answered` already does for the framework path, so a dismissal is never
  silent.

## Correction to an earlier claim, recorded so it is not repeated

During the session I repeatedly cited the `#32770` window class as evidence these
dialogs are outside `DialogBoxShowing`. That reasoning is wrong: `#32770` is the
generic Win32 dialog class, and Revit's own `TaskDialog`s — which the handler *does*
intercept — report it too. The actual evidence is that the v1 inventory only fires
*"on an `execute_script` timeout with no `DialogBoxShowing` event fired"*, so the
notice's existence is the proof. Same conclusion, but the stated reason was not
support for it.

Relatedly, `dev-environment.md`'s "UI automation is a dead end here" refers to
driving Revit *externally* via `prlctl exec` under Session 0 isolation. In-process it
demonstrably works — the v1 notice enumerated ~60 windows with titles and classes
from the background thread while the UI thread was blocked — so the mechanism v2
needs is already proven to run.
