## Motivation

The Revit add-in chooses its broker (Local vs Remote) **once, at startup**, from the `MCPBRIDGE_BROKER_MODE` env var (`MCPBridgeApplication.BuildDiscoveryOptions()`). That has two costs we hit live:

1. **Changing mode means clearing env vars and relaunching Revit from a clean shell.** A leftover `MCPBRIDGE_BROKER_MODE=remote` silently forced a fresh `--mode local` install into remote mode: Revit's ribbon showed `Connected to broker at 10.211.55.2:56777` (the Mac dev broker) while a local client's `list_instances` saw nothing — two different brokers. Diagnosing it took a full broker/rendezvous investigation. (Mitigated partly by the install-time warning in #184 / `Get-RemoteBrokerModeWarning`, but that's a band-aid.)
2. **No in-app reconnect.** When the broker is restarted or re-elected, the add-in's retry loop doesn't always pick it up promptly (we've seen re-election need an MCP request to nudge it). There's no user-facing "reconnect now."

We decided **against** a "both brokers concurrently" / shared-broker approach — it over-optimizes for this project's Mac+Parallels dev setup. A ribbon switch keeps the connector cleanly **Local by default** and makes the **Remote/Mac-broker case an explicit, visible dev choice**, and it doubles as the reconnect tool we already need.

## Proposed design

### 1. Config-driven mode (not startup-env-only)
- New `%LOCALAPPDATA%\Connectors\Revit\bridge-config.json`, e.g. `{ "brokerMode": "local" | "remote", "sharedRoot": "\\\\Mac\\connectors" }`.
- `BuildDiscoveryOptions()` precedence becomes **config → env var → default Local**. The ribbon switch writes the config, so it's authoritative; `MCPBRIDGE_BROKER_MODE` stays a fallback for the existing dev launchers (`dev-tooling/launch-revit-discovery.bat`, `install-mac.sh`, `docs/quickstart.md`).
- Remote still requires a UNC `sharedRoot` (existing `BrokerDiscoveryOptions.Remote()` validation).

### 2. Runtime switch + reconnect in `BridgeHost`
`BridgeHost` currently holds `_discoveryOptions` in a `readonly` field, runs a worker-thread connection loop (`RunConnectionLoop`) that re-discovers + retries with backoff, and already has `RefreshVersionStatus()` re-running discovery on demand — good precedents.
- `SwitchTo(BrokerDiscoveryOptions)` — tear down the current connection and reconnect against new options, **no Revit restart**. A mode switch is a deliberate re-registration; decide whether `InstanceId` is preserved or regenerated (lean: preserve on plain reconnect, regenerate on mode switch — TBD in design).
- `Reconnect()` — force **immediate** re-discovery (re-read `broker.json`, picking up a restarted/re-elected broker) instead of waiting out the backoff. This is the reconnect tool.
- Mind the thread lifecycle: no races between `Stop()`/the worker thread and a switch; `Stop()` must stay non-throwing.

### 3. Ribbon UX — make it clear when the Mac broker is in control
- A **Local ⇄ Remote** toggle and a **Reconnect** button (extend the existing status ribbon in `MCPBridgeApplication.CreateStatusRibbonButton` / `MCPBridgeStatusCommand`).
- Status shows the **active mode** prominently, with a visible **REMOTE (Mac broker)** indicator when remote, so during development it's unambiguous which broker owns the session.

## Testing
- **Unit** (Pester/xUnit as appropriate): config parsing + the config → env → default-Local precedence in `BuildDiscoveryOptions`; `Remote()` UNC validation.
- **Live, on both Revit 2025 and 2027** (no fake integration tier — real socket/ExternalEvent against real Revit): switch Local→Remote→Local without restart; `Reconnect()` after a broker restart re-attaches; `list_instances` reflects the active broker.
