*Project description:*
## Idea

A Home Assistant integration for this container, plus a good-looking dashboard card: the scanner model as an image (unless configured otherwise), the scan buttons with the names from the container configuration, the state of the scanner and the toolchain like the web UI shows it, a download button for the last scanned document, and a link to the web UI. Published through HACS. Brainstormed by the maintainer on 2026-10-10.

## What the container already offers (after #101)

- `GET /api/actions`: the actions with their labels (RENAME_GUI_*), enabled flags (DISABLE_GUI_*) and accepted parameters
- `POST /api/scanner/scanto` with `target`, optional `resolution`, `mode`, `source`; returns a job id
- `GET /api/jobs`, `GET /api/jobs/<id>`: job state (`queued`, `scanning`, `waiting_for_rear`, `scanning_rear`, `converting`, `done`, `failed`), pages, file and OCR copy with download URLs
- `POST /api/jobs/<id>/rear`: rear pages for a specific job
- `GET /api/scanner/status`: `scan`, `waiting`, `ocr`, `reachable`; queue counts come with #125
- `GET /api/file-list?limit=1`: newest file; `GET /api/file/<name>/download`
- optional `API_TOKEN` (bearer or `X-API-Token`)

## Options for the integration

**A. Custom integration (Python, `custom_components/brother_scanner`) talking to the REST API.** Best user experience: config flow (host, port, token, poll interval), one device per container with model name and image, entities created from `/api/actions`. Polling every few seconds is cheap; the API is local.

**B. MQTT discovery published by the container.** No HA code: the container announces its entities on an MQTT broker and HA creates them. Needs an MQTT broker and a publisher in the container; no card, no download. Could be a later addition for people who already run MQTT, not the first step.

**C. No code: HA's built-in `rest` sensors, `rest_command` services and a YAML card.** Works today for the basics (status sensor, scan button) and could ship as a documented example in the README right away, but no model image, no dynamic buttons, no download.

Recommendation: A, with C as a documented quick start until A exists.

## Entities for option A

Sensors
- `sensor.<name>_state`: idle / scanning / waiting_for_rear / converting / ocr (derived from status and the latest job), with attributes: job id, pages, waiting_until
- `sensor.<name>_last_scan`: file name of the newest PDF, attributes: size, timestamp, download URL, OCR copy URL
- `sensor.<name>_ocr_queue`: pending count (#125), attributes: in progress, failed, holding
- `sensor.<name>_last_job_state`, `sensor.<name>_last_error`
- diagnostic: container version, API token configured, reachability check interval

Binary sensors
- `binary_sensor.<name>_scanning`, `_waiting_for_rear_pages`, `_ocr_running`, `_reachable` (device class connectivity), `_problem` (last job failed or OCR failed)

Buttons and controls
- one `button` per enabled action, named after the container's labels; pressing triggers the action with the current select values
- `button.<name>_scan_rear_pages` enabled only while a job waits for rear pages (uses `POST /api/jobs/<id>/rear`)
- `select.<name>_resolution`, `select.<name>_mode`, `select.<name>_source` with the options from the device capabilities (the container would expose them in `/api/actions` from `scanimage -A`), defaults from the container
- `number.<name>_rear_page_wait` once #124 allows changing settings over the API

Services and events
- `brother_scanner.scan` with `target`, `resolution`, `mode`, `source`, `wait`; returns the job id (response data)
- `brother_scanner.scan_rear` with `job`
- `brother_scanner.download_last_scan` to a path, for automations (e.g. move to paperless)
- events `brother_scanner_scan_started`, `_scan_done`, `_ocr_done`, `_scan_failed`, fired when the polled job state changes; optional webhook from the container later (`NOTIFY_WEBHOOK_URL`, pairs with the existing Telegram/inotify triggers) so events arrive without polling

Device
- device info: manufacturer Brother, model from `MODEL`, configuration URL = the web UI, suggested area
- model image: shipped with the integration for the common models (MFC-L2700DW and friends, ADS-1x00W, DS-940DW) with a generic fallback, overridable by URL in the options flow

## The card (option A, HACS "plugin")

- custom Lovelace card `brother-scanner-card` in its own repository (HACS requires one repository per category), JS/Lit, built with the usual card tooling
- layout: model image (or configured image), name, state line with icon (like the web UI's smiley / hourglass / spinner / brain), the action buttons in the configured order and labels, the rear-page button while waiting, a "last scan" row with download (link to the container's download URL, or through an integration-provided HA endpoint so the token stays server side), and a link to the web UI
- card editor: pick the device, hide image, image URL, which buttons, compact mode
- graceful states: container unreachable, scanner unreachable, token missing

## Publishing

- integration repository `ha-brother-scanner` with `hacs.json`, `manifest.json` (version, `iot_class: local_polling`), `README`, GitHub releases; HACS default-repository submission later, custom repository first
- card repository `brother-scanner-card` with `hacs.json` (`render_readme`), released as a single JS bundle
- `brands` submission for icon and logo
- CI: hassfest and HACS validation actions for the integration, build and lint for the card
- versioning tied to the container's API version (`/api/actions` could carry an `api_version`)

## Open questions

- Download through HA (keeps the token hidden and works from outside the LAN via HA) versus a direct link to the container (simpler): the integration could register an HA HTTP view that proxies the download.
- Should the container push state changes (webhook or MQTT) in addition to polling? Polling at 5 s is fine for the UI; a webhook would make automations immediate.
- Capabilities for the selects: the container should expose the device's option lists (`scanimage -A` parsed at startup) in `/api/actions`.

## Not in scope here

The container API itself (#101) and the queue counts (#125) are prerequisites and are tracked separately.
