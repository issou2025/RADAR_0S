# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Step 5: deploy the merged site — hourly rebuild, frontend fold-in, live-mode Worker wiring**

*Project description:*
## Problem Statement

`live-political-analysis` just merged with `mypolitik`'s frontend
(`frontend/`), and the merge decision (session of 2026-08-29) settled that
`mypolitik`'s frontend is the surviving interactive architecture going
forward, while PolitikKu's Python pipeline stays the trusted data backend.
Right now the two halves have two separate, unreconciled deploy stories:
the Python pipeline publishes once a day to GitHub Pages
(`.github/workflows/daily.yml`); `frontend/` has its own Cloudflare
Workers deploy config (`wrangler.jsonc`) that has never been wired into
this repo's CI at all and currently only knows about `mypolitik`'s old
domains (`mypolitik.xyz`, `mypolitik.krackeddevs.com`), not
`politikku.my`. Nobody visiting `politikku.my` today sees any of the
merged frontend work, and the site's daily-only refresh cadence means a
Return Trigger (a news cycle, a State Election Signal, a Projection swing
worth noticing) that happens mid-day doesn't show up until the next day's
batch.

## Solution

Reconcile the two halves into one deploy story (Step 5 of the merge plan,
settled by session discussion, see ADR 0013):

1. GitHub Pages keeps serving the whole site — both the existing
   Python-rendered PolitikKu pages and `frontend/`'s static assets, folded
   into the same daily publish, at a new subpath so neither disturbs the
   other during the Step 4 transition (old pages retired one at a time,
   only once their new-view replacement exists — not this spec's concern).
2. The daily batch becomes an hourly batch, so Sentiment and the Projection
   are never more than an hour stale for a Return Trigger — still fully
   static, no new hosting model.
3. Election-night live mode is the one genuinely dynamic piece and gets its
   own Cloudflare Worker + KV, addressed via Cloudflare's own `workers.dev`
   subdomain (no DNS change to `politikku.my` — a branded
   `live.politikku.my` address is deliberately deferred, tracked in issue
   #133, not part of this spec).

## User Stories

1. As a site visitor, I want the Sentiment score and Seat Projection to be
   at most an hour stale, so that a same-day Return Trigger is reflected
   without waiting for tomorrow's batch.
2. As a site visitor, I want the existing PolitikKu pages (homepage,
   landing, MP profiles, bills tracker, projection, learn pages) to keep
   working exactly as before, so that this deploy change is invisible to
   me unless I go looking for the new frontend.
3. As a site visitor, I want to reach `frontend/`'s map/Politicians
   directory/Dewan table on the live `politikku.my` site, so that I can
   actually use the interactive features the merge was supposed to bring.
4. As a site visitor during a live election count, I want the live-results
   panel to show current counts without a full page reload, so that I can
   follow the count as it happens.
5. As the maintainer, I want the hourly rebuild to cost nothing new, so
   that this change doesn't reopen ADR 0002/0007's zero-cost-by-default
   framing.
6. As the maintainer, I want `frontend/`'s static assets served from
   GitHub Pages rather than requiring a second host for the whole site, so
   that I don't have to manage a Cloudflare account/DNS just to show the
   merged frontend.
7. As the maintainer, I want the live-mode Worker to require no DNS change
   to `politikku.my`, so that this deploy work carries zero live-site risk
   and doesn't block on issue #133's branded-domain question.
8. As the maintainer, I want a single, high-level way to verify this whole
   change (one workflow run, checked end to end), so that I'm not stitching
   together confidence from several disconnected small checks.
9. As the maintainer, I want the existing daily pipeline's other guarantees
   (a bad PolitikKu-page render doesn't take down the whole site;
   `deploy-pages` only replaces the live site with a good build) to keep
   holding once the frontend fold-in step and hourly cadence are added.
10. As an orchestrating agent, I want each executor's task scoped to a
    single git worktree on its own branch, so that concurrent work by
    multiple agents in this repo cannot silently clobber another agent's
    uncommitted changes (per this session's earlier branch-collision
    incident).
11. As an orchestrating agent, I want each executor's "done" report backed
    by a real, independently-reproducible verification step (a test run, a
    workflow dry-run, a diff), so that I'm not trusting a self-report (per
    `docs/agents/deepseek-agent.md`'s existing rule).
12. As a future contributor reading `wrangler.jsonc`, I want to see the
    Worker still serves `mypolitik`'s original domains
    (`mypolitik.xyz`/`mypolitik.krackeddevs.com`) unless KrackedDevs asks
    otherwise, so that this merge doesn't unilaterally break a domain that
    isn't this project's to retire.
13. As a developer running `frontend/`'s existing local dev server, I want
    the frontend to keep working locally exactly as before, so that this
    deploy change doesn't regress the local dev workflow used to build
    Step 4's new views.
14. As a site visitor whose browser blocks cross-origin requests by
    default, I want the live-mode Worker's API responses to carry correct
    CORS headers for `politikku.my`'s origin, so that the live-results
    panel actually loads data instead of silently failing.
15. As the maintainer, I want the frontend's data-fetching code and
    asset references to work correctly when served from a subpath instead
    of a domain root, so that folding `frontend/` into the existing Pages
    site doesn't break relative links, fonts, or data fetches.
16. As the maintainer, I want a documented, named reason for every
    deviation from the previous deploy model, so that a future maintainer
    reading the ADRs understands why the site isn't purely static anymore
    (ADR 0013) and why the batch got faster (this spec).

## Implementation Decisions

- **Pages artifact fold-in**: the daily Actions workflow's existing "build
  the Pages artifact and deploy" steps are extended with one new step that
  copies `frontend/`'s static assets (no build step — this is intentional,
  per `frontend`'s existing "no bundler" convention) into the artifact
  directory at a new subpath (not the site root — the root stays owned by
  the existing PolitikKu landing page per ADR 0011, unaffected by this
  spec). This keeps the fold-in a pure copy, not a build step, matching
  `frontend`'s own no-build-step convention.
- **Cadence**: the workflow's schedule trigger changes from once daily to
  once hourly. Every existing step's `continue-on-error` behavior is
  preserved as-is — a bad render on any individual page still doesn't take
  the rest of the site down, now just checked hourly instead of daily. The
  "archive the dated permalink" step's Malaysia-day dating logic is
  unaffected — multiple runs within the same Malaysian day correct that
  day's row, exactly as the workflow's existing concurrency-group comment
  already describes for same-day re-runs.
- **Live-mode Worker becomes reachable from the Pages origin**: the
  Worker's `/api/live/:electionId` endpoint gains explicit CORS headers
  scoped to `politikku.my`'s origin (not a wildcard). The Worker's existing
  asset-serving configuration and its existing `mypolitik.xyz`/
  `mypolitik.krackeddevs.com` custom-domain routes are left in place,
  untouched — this spec adds reachability from the new origin, it does not
  remove the old ones, since retiring KrackedDevs' own domains isn't this
  project's call to make unilaterally.
- **Live-mode addressing**: the frontend's live-mode data-fetching code
  changes from a same-origin relative path (which only worked when the
  Worker served the whole site itself) to an absolute URL pointing at the
  Worker's `workers.dev` subdomain. A branded `live.politikku.my` address
  is explicitly out of scope here (see Out of Scope; tracked in issue
  #133).
- **Subpath base-path correctness**: any of the frontend's asset
  references or data-fetch calls that assumed the app runs at a domain
  root are corrected to work from the new subpath. This is scoped to
  path-correctness only — no visual/design changes.
- **Worker deploy automation**: a new, separate CI job runs `wrangler
  deploy` for `frontend/` whenever its own files change, gated on a
  Cloudflare API token being present as a repository secret. Provisioning
  that token is a real account-owner action (Cloudflare account access)
  that no agent can perform — the job is written to fail clearly and
  explain why if the secret is absent, not to silently no-op.

## Testing Decisions

A good test here checks real, external behavior — does the published site
actually work — not internal implementation details of any one script.

- **Primary seam (single, highest-level)**: the composed daily workflow,
  run by hand (`workflow_dispatch`) on a branch, checked against the
  resulting Pages artifact and the deployed result. This one seam is
  expected to demonstrate all three changes together: the hourly-cadence
  config is valid and the workflow still completes; the artifact contains
  both the existing PolitikKu pages and the folded-in frontend assets at
  their expected paths; the live-mode fetch call in the deployed frontend
  successfully reaches the Worker's `workers.dev` URL and gets a
  CORS-correct response.
- **Existing seam, extended not replaced**: `frontend/public/worker.test.mjs`
  (`node --test`) — add cases for the new CORS headers on
  `/api/live/:electionId`. The existing Johor/election-generalization
  cases it already covers are untouched.
- **Existing seam, unaffected**: `tests/test_live_poller.py` — stays green
  as a regression check; nothing in this spec touches the poller.
- **New, narrow seam**: a lightweight smoke-check (a script or an
  additional workflow step) that asserts the Pages artifact actually
  contains the expected folded-in frontend files after the copy step —
  kept as a simple existence/shape assertion, not a new test framework.
- **Full local regression**: `pytest` run in full before any branch here
  is merged, per this repo's existing verification discipline.

## Out of Scope

- The branded `live.politikku.my` domain and the DNS migration it would
  require — deliberately deferred, tracked in issue #133.
- Building the new frontend views (seat projection, bill tracker,
  sentiment digest, FACT/MODEL trust pattern) — that's Step 4, already
  spec'd separately in `docs/design/mypolitik-new-views-spec.md`, and has
  its own bills-export prerequisite already shipped.
- Retiring any of the four old Python-rendered pages — explicitly gated on
  Step 4's new-view replacements existing first, per the already-amended
  Step 4 plan.
- Any change to how Sentiment/Projection are computed — only how often the
  existing computation runs.
- Backlog features (MP/DUN notifications, gamification, community
  sentiment polling, interactive sandbox) — undesigned, not part of this
  merge phase.
- Deciding whether `mypolitik.xyz`/`mypolitik.krackeddevs.com` should keep
  serving traffic long-term — that's KrackedDevs'/the maintainer's call to
  make separately, not implied one way or the other by this spec.

## Further Notes

**Orchestration plan** (the user runs 2 Antigravity CLI sessions — "agy" —
plus this Claude Code session as a dispatchable helper, with the current
Claude Code session acting as orchestrator, per the working pattern
established earlier this session):

- **Claude Code helper — CI/workflow track**: the daily workflow's cadence
  change, the frontend fold-in copy step, the new smoke-check, and the
  separate Worker-deploy CI job. This is mechanical, spec-pinned
  YAML/shell work with a clear existing pattern to follow (the workflow's
  own existing `continue-on-error`/step-ordering conventions) — Sonnet
  default per `docs/agents/model-effort.md`, no escalation trigger hit.
- **Antigravity worker (agy) — frontend base-path and live-mode addressing
  track**: correcting the frontend's asset references and data-fetch calls
  for subpath hosting, and switching the live-mode fetch call to the
  Worker's absolute `workers.dev` URL. JS/TS work, which is exactly why
  this goes to an Antigravity worker rather than the DeepSeek loop
  (`docs/agents/model-effort.md`'s DeepSeek allowlist excludes JS/TS).
  Verification requires actually loading the app in a browser from the new
  subpath — a visual/functional check, escalate that worker's effort per
  trigger 1 if anything looks visually off, not by default.
- **Orchestrator (this session) — Worker CORS change directly, not
  delegated**: adding the CORS headers to the Worker is small but
  security-relevant (getting the allowed-origin scoping wrong is a real
  correctness/security mistake, not just a style choice) — per
  `docs/agents/model-effort.md` trigger 3, this is done by the orchestrator
  directly rather than dispatched.
- **Isolation**: each track gets its own git worktree on its own branch
  before work starts, per the branch-collision incident earlier this
  session (multiple agents `git checkout`-ing in one shared working
  directory silently clobbered each other's uncommitted state). No track
  starts work in the shared main directory.
- **Verification discipline**: every track's "done" report is
  independently re-run by the orchestrator (real `pytest`, real
  `workflow_dispatch` or local simulation, real diff of changed files) —
  not accepted on narrative alone, per `docs/agents/deepseek-agent.md`'s
  existing rule and this session's own practice on Steps 3 and 6.
