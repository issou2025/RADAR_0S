## 1. Purpose

Firebase work is currently spread over five open issues, written at different times against different application identities and build models. None of them owns the cross-cutting invariants (which build uses which Firebase project, how that is verified, which credentials may exist where) or the ordering between them. This issue establishes one architecture, one configuration source of truth, and one sequence covering:

- Android and iOS;
- staging and production;
- Firebase application registrations and client configuration;
- FCM client integration and the backend push-registration lifecycle;
- APNs integration and iOS signing entitlements;
- backend notification delivery;
- open-source build compatibility;
- configuration verification and credential governance.

## 6. Preservation of historical registrations

- Historical Firebase registrations are **preserved**. They are not deleted, replaced, renamed or reconfigured by this workstream.
- Retirement requires a separate, **explicit authorization** after an audit of their consumers. Their historical use (including earlier acceptance testing and any external consumer) has not been fully documented.
- Observation from the backend source: the backend sender addresses messages by Firebase project and installation ID (`Message(fid=...)`, configured by `FIREBASE_PROJECT_ID`), not by application registration. This is evidence about the backend only; it is not a substitute for the consumer audit.
- New registrations are **additive** and are completed and verified before any retirement is even considered.

## 7. Build-flavor-driven Firebase configuration

- Firebase client configuration is selected by **build flavor**, not by Android build type. (The build-type mapping in #28, `debug -> staging`, `release -> production`, predates the flavor model of #65 and is obsolete: a debug build of the production flavor exists.)
- Android: `android/app/src/<flavor>/google-services.json`.
- iOS: a per-flavor `GoogleService-Info.plist`, selected by a variable in `ios/Flutter/Flavor-<flavor>.xcconfig` next to the bundle ID.
- There must be **no generic fallback**: no `android/app/google-services.json`, no `android/app/src/main/google-services.json`, and no unflavored iOS plist.
- Manual replacement of configuration files between builds is not acceptable.
- The Firebase client configuration for the iOS native default app comes from the plist. Dart-define based Firebase options (a second configuration source, used on the historical branch) are not carried over.

## 8. Static configuration registry and verification (D2)

A static, version-controlled registry records, per platform and flavor:

- expected Firebase project ID and project number;
- expected Firebase application ID;
- expected Android `applicationId` / iOS bundle ID;
- the path of the client configuration file;
- the Firebase mode: `required` or `disabled` (see section 12).

Requirements:

1. The registry **follows** the environment selected by `config/build/<env>.json` and the flavor. It never selects, defaults or infers the environment. `lib/config/build_config.dart` and the build files are not changed to accommodate it, and no second environment selector is introduced.
2. The registry reuses the identity matrix of `tool/verify_artifact.sh matrix` for the native identities instead of copying them.
3. Verification fails, with a message naming what is wrong and never a secret value, when:
   - a required configuration file is missing, or a generic fallback file exists;
   - the file's project ID, project number, app ID or package / bundle ID differs from the registry;
   - the registry's package / bundle ID differs from the actual native identity of the flavor;
   - the Firebase project does not agree with the flavor's environment.
4. Verification runs at three levels:
   - **Source:** before a build (tool and CI).
   - **Built artifact:** the generated Android resources and the IPA's embedded plist match the registry (an extension of `tool/verify_artifact.sh` / `tool/verify_ipa.py`).
   - **Provenance:** the build manifest (`tool/build_manifest.py`) records the Firebase project and application ID.
5. The `build-variants` workflow exercises all five variants without any signing credential.
6. The verifier also rejects credential material anywhere in the repository (see section 13).

## 9. Android and iOS FCM registration lifecycle

The functional specification is Issue #27; the implementation exists only on the historical branch `sziller/firebase-installation-work` (6 commits on a base 151 commits behind `development`). That branch is a **reference, not a merge candidate**: it targets legacy identifiers, per-build-type Android configuration, Dart-define iOS options, an `http://` API default and an older reset flow.

The migration into the current baseline must preserve:

- the authoritative path **Firebase init -> FCM registration -> native registered-FID callback -> authenticated `POST /auth/push-registration`**; a raw `FirebaseInstallations.getId()` is never uploaded;
- the separation of the **callback-confirmed FID** from the **last backend-confirmed FID**, and rotation (POST new, persist, best-effort DELETE old);
- registration on login, session restoration, token refresh and app resume; `DELETE /auth/push-registration/{fid}` before logout / reset teardown, never blocking it;
- failure isolation: Firebase or registration failure must not affect authentication, wallet, DLC retrieval or signing; no retry loops;
- `platform` exactly `android` / `ios`; FIDs redacted in logs;
- state scoped by backend environment and JWT subject (the API base URL comes from `BuildConfig`).

Out of scope here: receiving or displaying pushes, notification-driven signing, notification payload semantics (a later phase; see section 15).

## 11. Backend notification delivery and end-to-end acceptance

The backend part (authenticated push-registration API, persistence, Firebase Admin sender, semantic dispatch; backend issues #296, #298, #300) is implemented. Its contract is **unchanged** by this workstream.

Requirements and cautions:

- Each backend environment must use the matching Firebase project (`FIREBASE_PROJECT_ID`) with its own server-side identity.
- The backend cannot tell which Firebase project a client FID belongs to. A FID from the wrong project fails at send time and may be treated as unregistered. This is why the build-time verification of section 8 is required, not optional.
- The sender currently sends no APNs or Android-specific options (no `content-available`, no priority). Reliable background wake-up of an iOS or Android signer is **not** supported yet and is outside this workstream.
- End-to-end acceptance per platform: authenticate against staging -> FCM-registered FID -> `POST` returns 200 -> active registration row -> restart refreshes the same row -> logout/reset `DELETE` returns 204 and the row becomes inactive -> the controlled smoke send (`scripts/send_push_smoke.py` in the backend) returns an accepted Firebase message ID. Acceptance on both platforms is required before production enablement. Firebase acceptance is not proof of visual delivery on the device.

## 12. Optional Firebase operation for open-source builds

The open-source user must be able to modify and rebuild the application with their own configuration.

- A fork supplies its own client configuration files and edits the registry for its own identities and Firebase project, **or** declares Firebase `disabled` in the registry.
- The mode is **explicit** in the registry; it is never inferred from a file merely being present or absent.
- In `disabled` mode the build succeeds without any Firebase configuration, initializes nothing, makes no registration call and sends nothing to a Firebase project. This is verified on the built artifact.
- Official builds are always `required`: a missing or mismatching file fails the build, with no fallback.
- The Firebase SDK may remain linked (inert) in v1; a variant without the SDK is not part of this workstream.
- The official client configuration files are not a license to register against Cadena's Firebase projects. A fork's build must not silently reuse them; the verifier checks identity agreement, and the documentation says what a fork must replace.

## 13. Credential separation, verification and governance

Firebase **client** configuration (version-controlled under D1):

```text
google-services.json, GoogleService-Info.plist,
Firebase project ID / number, application ID, client API key, sender ID
```

These are client configuration, not authorization to send notifications.

**Never** in the repository, the application, a workflow, a log, an artifact or a chat:

```text
Firebase Admin / service-account credentials and private keys
server OAuth credentials
APNs provider private keys (.p8) and APNs certificates
Android keystores, key.properties, Apple signing keys and certificates
JWTs, passwords, mnemonics, seeds
```

Governance:

- **D1 requires a security review** before official client configuration files are committed. The review covers at least: file contents contain only client configuration; Google Cloud API-key restrictions (package / bundle ID) are applied by an authorized operator; no private material is present.
- The verifier rejects service-account JSON, private-key blocks and `.p8` content anywhere in the repository.
- Existing registrations and credentials are preserved until their dependencies are known; retirement or rotation needs explicit authorization.
- Credential custody for provider-side keys stays with the authorized operators (see #110); this workstream documents identifiers, not secrets.
- No change to application identities, signing configuration, `CADENA_SIGNING`, the iOS hosted-signing workflow or the authorization gate is part of the planning stage.
- Dependency changes (for example `firebase_core`, the native Firebase SDKs and the lockfile) require an issue-scoped justification and the verification of CLAUDE.md section 4. Wallet-secret handling, signing and cryptographic semantics are not touched.
- Documentation of the Firebase role, the credential boundary and the maintainer / fork procedure is part of the deliverables.
