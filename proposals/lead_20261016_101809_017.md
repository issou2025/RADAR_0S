## Problem

Testing the iTerm2 backend through a real stdio MCP revealed three security/contract issues. Tested upstream SHA: `6d6216ffdeb5d2649dbd50a8ecf62edec4163122`, macOS arm64, iTerm2 3.7.4beta1, Python SDK iterm2 2.13, MCP SDK 1.25.0.

### 1. False completion of a quiet command

Run this in a separate test session:

```json
{"name":"execute","arguments":{"session_id":"<explicit-test-session-id>","command":"sleep 6","wait":true,"timeout":4,"watch_for":"prompt"}}
```

The actual result was `Completed (stability) in 1.8s` before the process had finished (the call's wall time was about 2.46 s). An independent fixture recorded the start and completion state locally; completion was absent when the response was returned and appeared later.

Expected behavior: silence does not prove that a process has finished. Prompt detection requires a confirmed fresh shell prompt; otherwise the result should be timeout/inconclusive. Silence must have an explicitly indeterminate result rather than `Completed`. It is also important not to accept the previous prompt state immediately after sending a command. The SDK JSON-decodes values returned by `async_get_variable`: `isAtShellPrompt` is a boolean, not a string.

### 2. Errors are returned as successful MCP results

After closing an own test session:

```json
{"name":"read","arguments":{"session_id":"<closed-session-id>","lines":20}}
```

The response is `Session not found`, but `isError=false`. Validation and backend errors have the same problem.

Expected behavior: return a `CallToolResult` with `isError=true`; a timeout means that waiting has stopped, not that the process was stopped. Broadcasts need per-target `sent/skipped/failed` results; otherwise a retry may execute a command that was already sent.

### 3. Implicit binding to the current/first session

When `session_id` is omitted, the iTerm backend may select the current/first session. In automation with multiple windows, this risks sending input to the wrong session.

Expected behavior: addressable operations must require an explicit non-empty `session_id` or explicit non-empty `targets`, with no focus-based fallback. Listing and creating new windows/sessions are separate cases. This changes the previous contract, so an explicitly enabled upstream strict mode would also be acceptable, but strict binding is mandatory for our use case.

## Local fix verification

The local changes add typed backend errors, MCP `isError`, mandatory addressing, and remove completion based on screen stability. A prompt is accepted only after an observed False → True transition following command submission; per-target broadcast results were also added. A screen change alone is insufficient: it may be command echo while the old `prompt=True` state is still present. If the transition for a short command is missed between polls, the result is conservatively timeout/inconclusive rather than a false success.

- Focused suite: 129 passed, including 25 safety regressions.
- Live iTerm2 smoke test: missing target, empty broadcast, and unknown ID → `isError=true`; explicit execute/read work; quiet prompt → timeout/error; silence → inconclusive/error.
- A successful short live command was verified with `watch_for=output`. The successful prompt branch was verified by unit tests; no live prompt success without Shell Integration is claimed.
- Isolation of two own sessions, interactive input, ANSI/Unicode, arrow keys, and Ctrl+C were separately verified through a real MCP.
