## Problem

Kitty is being built by one person coordinating many models, tools, workflows, services, and partial product surfaces. The recurring failures are not just coding defects. They include:

- contradictory authority and unclear sequencing;
- visible capabilities that are not genuinely usable;
- expensive experiments without firm stop conditions;
- lost or duplicated work across agents and branches;
- difficulty explaining friction after the fact;
- architecture and documentation drift;
- too much raw agent output and too many consequential decisions pushed back to Jacob;
- model and tool choices based on reputation rather than Kitty-specific evidence.

## Candidate leverage systems

### 1. Mission compiler / authority linter

Generate one machine-readable current-work view from the roadmap, active mission, queue, branches, PRs, and blocking dependencies. Fail when there are two simultaneous "current priorities," unauthorized work, duplicate branches, or a task whose prerequisites are unmet.

Output should answer only:

- what is active;
- what is blocked and why;
- what may start next;
- what must not start;
- which document is authoritative.

### 2. Prompt compiler

Jacob states the desired outcome in ordinary language. The compiler reads canonical project state and emits a short task card containing scope, dependencies, budget, acceptance, evidence, branch, and stop rule. It rejects conflicting or duplicate work rather than creating another giant prompt.

### 3. One-tap friction capture

Add a private dogfood control that captures the current route, viewport, screenshot, visible state, console/network errors, recent actions, and Jacob's short voice/text note. Produce a ready-to-triage evidence bundle so Jacob does not have to reconstruct what happened.

### 4. Failure museum

Maintain a compact regression corpus from real failures: clipped mobile dialog, raw 500, dead-looking action, fake success, duplicate launcher, lost receipt, conflicting mission, RunPod readiness timeout, provider unavailable, merge conflict, and stale documentation. Every relevant release replays the applicable failures.

### 5. Chaos UX lab

Deliberately inject latency, timeout, 401/403/404/500, unavailable provider, partial stream, malformed response, process restart, offline mode, and exhausted budget. Verify Kitty remains honest, understandable, recoverable, and fail-closed.

### 6. Builder flight recorder and replay

Record every mission's inputs, authority, branch/base SHA, model/tool calls, commands, state transitions, artifacts, costs, retries, failures, and approvals in a replayable event bundle. Resume from the last proven checkpoint rather than starting over or narrating uncertain state.

### 7. Experiment budget governor

Every paid or potentially expensive experiment receives a hard envelope: token budget, dollar budget, GPU minutes, retry count, deadline, success evidence, and kill condition. Exceeding the envelope requires explicit approval. No silent fallbacks to a paid provider.

### 8. Model tournament and routing bench

Build Kitty-specific golden tasks for planning, coding, debugging, UX critique, review, research, summarization, and browser operation. Periodically compare models on correctness, evidence quality, runtime, and cost. Route work to the cheapest model that clears the required threshold instead of choosing by hype.

### 9. Repo archaeologist

Combine static dependency mapping, runtime import/route tracing, test coverage, recent commits, and entrypoint execution to classify modules as live, dormant, duplicate, orphaned, or unknown. Produce a deletion/merge/document queue with confidence and evidence.

### 10. Change-impact graph

Map user journeys to routes, components, services, schemas, and tests. A PR automatically knows which journeys and service states it must rerun. This reduces giant universal test prompts while preventing narrow tests from missing user-visible regressions.

### 11. Capability quarantine and maturity contract

Every capability has one state: `proven`, `preview`, `developer-only`, `blocked`, or `hidden`. Only proven capabilities appear as normal product actions. Preview surfaces disclose limitations. Blocked or unproven capabilities cannot masquerade as shipped UI.

### 12. Shadow and canary mode

Run new routing, classification, memory, or workflow logic beside the current system without affecting the user. Compare decisions and outcomes, then expose the change only to a controlled preview. One action rolls back to the previous proven version.

### 13. Jacob taste memory

Store approved and rejected screens, interaction patterns, terminology, density, colors, typography, and reasons. Product Studio and design agents must cite this taste library when proposing work. The goal is to learn Jacob's preferences without freezing them into a rigid style.

### 14. Synthetic user panel plus real-user bridge

Maintain a bounded panel for phone-only use, first-time use, cognitive overload, low-connectivity, dependency failure, accessibility, and expert operation. Treat it as hypothesis generation, never as a substitute for real users. When Kitty is stable enough, run small real-user sessions against the same journeys and compare findings.

### 15. Decision expiry and assumption monitor

Important decisions record assumptions, evidence, owner, consequences, and a review trigger. Surface decisions when their assumptions change—for example, provider availability, model capability, Figma plan, architecture, or product priority—rather than letting old ADRs silently govern new conditions.

### 16. Separate Kitty from the operator cockpit

Keep the normal product focused on Jacob's life and creative work. Put Builder state, provider health, budgets, traces, queues, and developer controls in an explicit operator surface. No internal machinery leaks into ordinary tasks merely because the backend capability exists.

### 17. Weekly evidence brief

Produce one short evidence-grounded report covering:

- what actually became usable;
- what regressed;
- current spend and waste;
- unresolved decisions;
- stale or contradictory authority;
- the single highest-leverage next action.

No activity theatre, commit counts, or long status narration.

## Selection rubric

Promote only experiments that:

1. remove recurring work from Jacob;
2. prevent an observed class of failure;
3. produce inspectable evidence;
4. reuse existing infrastructure;
5. have a bounded proving slice;
6. can be removed if they do not help;
7. do not create another queue, authority source, or autonomous merge path.

Score candidates by expected hours saved per month, user harm prevented, implementation cost, ongoing maintenance, and reversibility.

- Keep Jacob's required input to one consequential choice or less.
- Stop or remove the experiment if it fails to create measurable leverage.
