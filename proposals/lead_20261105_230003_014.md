# Private backend repo — implementation plan

**Status:** Approved concept → phased implementation plan

Move the Firebase backend (`backend_strava/`: Cloud Functions, Firestore rules and indexes) out of this public repo into a private sibling repo, `bike_setup_tracker_backend`. Future backend work (e.g. #17 cloud sync) stays private. The Flutter app stays the primary public portfolio piece.

Rationale, option comparison and the code facts behind the decisions: see the brainstorm comment on this issue.

## Resolved open questions

| Area | Decision | Rationale |
|---|---|---|
| A. Scope | **Move the whole folder** (A2) | Self-contained (23 tracked files, own `firebase.json`/`.firebaserc`/`package.json`); nothing in `lib/` or `test/` imports it. Future features like #17 stay private |
| B. Mechanism | **Separate sibling private repo, no link** (B1), named `bike_setup_tracker_backend` | A submodule's pointer bump is recurring pain and gives anonymous clones a dangling link for no build benefit. The name is broader than "strava" because the folder already hosts subscriptions and #17 widens it |
| C. History | **Leave public history alone** (C1) | Non-destructive; a rewrite conflicts with the `CLAUDE.md` rule against rewriting LFS history. Future features are what must stay private. The one fork (`gaoypChina`) is accepted |
| D. Seeding | **`git subtree split --prefix=backend_strava`** (D1) | Built into git, keeps the 46 backend commits and blame, and does not modify the public repo |
| E. Deploy / CI | **Manual deploys** (E1). `backend_test.yml` and the two deploy tasks move to the new repo | Secrets (8, all in Secret Manager, bound by name), `.firebaserc`, project id and region are unchanged. No new credentials |
| E′. Deploy proof | **Skipped now; fix issues at the next real deploy** (user decision) | No known risk: nothing deployed changes, only the folder's location. If the first deploy from the new repo fails (`npm ci`, `firebase use`, auth), fix it then |
| F. Contract | **No contract document; a `CLAUDE.md`/`AGENTS.md` pointer instead** (revises F1) | A markdown interface doc has to be maintained constantly and drifts. The code on both sides is the contract, and agents can read the private repo from the sibling folder and the GitHub link. The pointer carries the repo URL, the "sibling folder next to the main checkout" convention, and a reminder to add it as a working directory |
| Branches | **`main` and `dev` in the new repo**, like this repo | Same workflow as the app; the CI triggers already target both |
| G. Reviewers | **No recruiter-specific changes** | The Flutter app is the primary goal. No README showcase, no on-request-access line |
| H. Design docs | **Keep #40, #41, #43 public** (H1) | Architecture is not a working system, and the history is public anyway |
| I. Tracking | **Public repo stays the single tracker** (I1); the private repo gets a tiny `CLAUDE.md`/`AGENTS.md` pointing here | Matches the "GitHub Issues are canonical" rule; no split backlog |
| Machines | Clone the backend repo next to the app on **both Windows and macOS** | Deploys happen on Windows; releases are cut on macOS |
| Secret scan | **Skipped** (user decision) | User is confident no shared secrets are in the history. If one ever turns up, rotate it; do not rewrite history |

None. This is repository structure only; the app binary and the deployed backend are unchanged.

## Acceptance criteria

- `bike_setup_tracker_backend` exists as a private repo containing the former `backend_strava/` content at its root, with its history, and has `main` and `dev` branches (default `main`).
- Its CI (Jest on Node 24) runs and is green.
- The public repo no longer contains `backend_strava/`, the backend workflow, or the deploy tasks, and `git grep backend_strava` finds only historical references (issues, old comments), not live paths.
- `CLAUDE.md`, `AGENTS.md` and `CONTEXT.md` describe where the backend lives and how to find it: repo link, sibling-folder convention, and the app files that call it. No separate contract document is maintained.
- #17's path mention points to the new repo.
- No Dart code, `pubspec.yaml`, deployed function, secret, or Firebase project setting changed.
