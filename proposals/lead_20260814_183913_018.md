## What it is

`NS_Impact_Point` — a hit landing on a target. It goes first because enemies
already land hits, so it is immediately visible in the sandbox, and because it
exercises the whole convention at once.

The conventions document states what done means:

- it spawns on an enemy hit
- **changing a row in `DT_ElementVisuals` changes it with no asset edit**
- the debug display shows the instance count capping with twenty Brutes attacking
- it disappears at 4000 cm and does not come back

That second one is the point of the whole arrangement. One system serves all
eight damage types by reading its two colours from the table, so a Demonic hit
and a Void hit are the same asset with different rows. Eight shapes times eight
damage types is 64 assets built the wrong way and 8 assets plus 8 rows built this
way.

## It must set an effect type

`FXT_Enemy`, built in #555. Nothing in Niagara is culled by default, and the
conventions document is explicit that a system with no effect type "is not
reviewable and should not be committed".

## THE BLOCKER, and it is why this issue exists rather than a pull request

**A Niagara system cannot be authored from an editor Python script.** That was
established by probing the engine rather than assumed, on 2026-08-14:

- `NiagaraSystemFactoryNew` and `NiagaraEmitterFactoryNew` exist, so an empty
  system asset can be created.
- **Nothing exposed to Python can populate its emitter stack.** There is no
  Niagara editor library, no Niagara subsystem, and no function library for
  adding a module, setting a module input, or adding a renderer.
- The 56 `NiagaraExt_*` types the engine exposes are data types — schemas,
  topology, summaries. `NiagaraExternalEditContext`, which sounds like the entry
  point, is a plain struct with no methods at all.

The authoring operations exist, but only through the editor's Model Context
Protocol server, in the `NiagaraToolsets.NiagaraToolset_System` toolset, whose
own description is "System, emitter, and module creation and modification".

So this needs one of:

1. **The editor's Model Context Protocol server connected**, which is how the
   toolset is reached. It is enabled in `Cataclysm.uproject` and available when
   the editor is running and the connection is live.
2. **Authoring the system by hand in the editor**, and pinning its settings with
   an automation test afterwards, the way #555 pins the effect types.

Option 1 keeps the project's convention that an asset's definition is reviewable
text. Option 2 does not, and would make this the first authored asset with no
script behind it — worth deciding deliberately rather than by default.
