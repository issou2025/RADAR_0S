## Revised product definition

Drawing is **not** MonkeyHub's replacement for Revit / AutoCAD construction-document authoring.

It is the 2D representation side of the same semantic project state:

> **State is the only architectural authority. Drawing is a semantic vector projection plus editable 2D scene dressing.**

Board remains the main thinking / review surface. Formal construction-document review can stay in Board. Drawing exists when the user wants to make a plan / section / elevation **look and read like an architectural drawing**, while keeping every projected architectural object traceable to the same source state.

Useful shorthand:

```text
Board   = think / compare / review
Arch    = edit architectural state
Drawing = semantic 2D projection + vector dressing
Render  = 3D visual dressing
Publish = final composition / delivery
```

---

# Core principle: no second source of truth

MonkeyHub should not insert Revit / CAD as an intermediate authority:

```text
State
 ├─ Arch
 ├─ Drawing
 ├─ Render
 ├─ Fab / analysis
 └─ optional Revit / DWG / IFC / other export
```

Not:

```text
State → Revit → DWG → Drawing
```

External professional tools may remain valuable executors / interoperability targets, but they do not become the owner of architectural truth.

Multiple representations are allowed.

> **Multiple architectural authorities are not.**

---

# Kill manual CAD-layer logic in the core

Traditional CAD layers often answer a question the semantic state already knows:

```text
A-WALL
A-DOOR
A-FLOR
A-FURN
...
```

In MonkeyHub, an object already has stable identity, semantic meaning and dependencies.

Example:

```text
wall_042
  semantic_kind = wall
  material = concrete
  base = level_02
  top = level_03
  relations = ...
```

So the internal Drawing system should not require the user to manage:

- A-WALL / A-DOOR / A-FLOR style layers;
- layer visibility as the primary way to decide what appears;
- duplicated layer-based identity;
- manual layer reassignment after model changes.

Instead:

> **Query semantics, not layer names.**

Layer mappings may still be generated inside an export adapter when a downstream DWG / office standard requires them. They are compatibility output, not project authority.

---

# Drawing as a semantic View Compiler

The base drawing should be compiled from exact project state.

```text
Canonical semantic state
        ↓
      ViewSpec
 plan / section / elevation
 level / cut / depth / crop / scale
        ↓
Semantic Projection Compiler
        ↓
     2D Scene Graph
```

A vector in the projected scene should remain traceable to its source:

```text
vector_018
  source_ref = wall_042
  semantic_kind = wall
  projection_role = cut
  view_ref = plan_L02
```

So clicking a projected wall is not selecting an anonymous line. It is selecting the 2D projection of `wall_042` in that view.

---

# Graphic rules should be semantic + view-dependent

Lineweight / visibility / linestyle should derive from object meaning **and its relationship to the current view**, not from a user-managed layer string.

Example:

```text
wall + cut by view        → heavy
wall + projected beyond  → medium
furniture                → light
overhead object          → dashed
background context       → faded
```

The same wall may render differently in plan, section and elevation without being copied into different layers.

Likewise hatches / fills should preferably be driven by semantic / material / view rules, with representation-only overrides allowed when the user wants a specific graphic treatment.

---

# Drawing is the 2D equivalent of scene dressing

The useful product analogy is closer to **D5 for architectural drawings** than to AutoCAD.

Base:

```text
exact plan / section / elevation projection
```

Then add editable representation assets:

```text
+ people SVG
+ trees SVG
+ furniture silhouettes
+ vehicles
+ entourage
+ poche / hatch
+ arrows / labels
+ graphic shadows
+ annotation
+ other vector assets
```

All should remain editable as vector objects where practical.

Typical interaction:

```text
Generate / choose person SVG
→ preview
→ drag into section
→ scale / flip / move / restyle
```

or:

```text
User: add a few people and trees here
→ Codex selects / generates vector assets
→ places them as editable objects
→ user moves / deletes / mirrors / restyles them
```

Agent output should therefore be **editable scene objects**, not a newly flattened image.

---

# Representation-only assets are not design state

A person / tree / vehicle / graphic shadow inserted for drawing presentation is representation-only by default.

Example:

```text
tree_svg_17
person_svg_08
car_svg_03
```

These must not silently become architectural objects in StateRecord.

If the user explicitly decides that a representation asset now expresses real design intent (for example, a specific retained existing tree or a proposed landscape object), that should require an explicit promotion path:

```text
Drawing asset
  ↓ explicit user/design intent
design proposal
  ↓ accept
State
```

Never infer promotion just because something appears on a drawing.

---

# Board owns drawing review

Board remains the natural surface for:

- reviewing construction documents;
- markup / clouds / notes;
- comparing revisions;
- source-aware comments;
- linking one drawing / detail / model view to another;
- turning a review comment into a bounded design task;
- consultant / owner / external review.

A construction drawing produced by Revit / AutoCAD / an external LDI / another tool can simply arrive in Board with exact source / revision identity.

MonkeyHub does **not** need to rebuild the entire Revit / AutoCAD authoring stack merely to review and control it.

Conceptually:

```text
professional tool / external deliverable
        ↓
      Board
review / compare / annotate / task
        ↓
design or agent action
        ↓
updated deliverable
        ↓
      Board
```

This issue should not absorb Board review into Drawing.

---

# Relationship to external CAD / BIM

Revit / AutoCAD / IFC / DWG remain optional projections / executors / exchange targets.

Examples:

```text
semantic state → Revit category / family mapping
semantic state → IFC entity mapping
semantic state → DWG layer mapping
semantic state → Drawing vector projection
```

The mapping may be lossy or format-specific, but the source object identity and project authority remain upstream in MonkeyHub.

This means a traditional DWG export can still emit:

```text
A-WALL
A-DOOR
...
```

without making those layers part of MonkeyHub's core design logic.

# First vertical slice

Do not start with dimensions, sheet management or a mini-Revit.

Prove the actual user-facing representation loop:

```text
exact accepted design source
        ↓
one plan or section ViewSpec
        ↓
semantic vector projection
        ↓
semantic lineweight / hatch / visibility
        ↓
insert one SVG person / tree manually
        ↓
Codex places a small set of editable SVG assets
        ↓
user manually adjusts them
        ↓
close / reopen
        ↓
change one design object in State
        ↓
regenerate base projection
        ↓
retain valid representation-only dressing
        ↓
explicitly flag broken / orphaned anchors
```

The key proof is:

> **Base architecture regenerates from State; representation intent remains editable and durable without becoming architectural truth.**

# Product significance

The point is not:

> AI can draw a plan.

The point is:
