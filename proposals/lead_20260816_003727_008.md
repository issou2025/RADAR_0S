# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[Impeller] A blurred `TextStyle` shadow detaches from its glyph when the same single-glyph run is painted more than once**

*Project description:*
## Steps to reproduce

1. Run the code sample below on iOS or Android (default renderer, i.e. Impeller).
2. Look at the first block of text, `'11\n3\n3'`.

No scrolling, animation, or interaction is needed. The artifact is present in the very first frame and is stable and deterministic.

## Expected results

Each line's blurred shadow is drawn behind that line's glyph, as it is for every other line.

## Actual results

On the second `'3'`, the shadow is **detached**: it is painted as a free-floating black `3` roughly one glyph-width to the left, and the real `'3'` is left with no shadow at all. The shadow is not duplicated — it is displaced.

With more repeats the error accumulates: with `'3\n3\n3\n3\n3'` each successive occurrence drifts further, ~1 glyph-width per repeat.

The two control blocks in the sample render correctly, which isolates the trigger:

| text | repeated run | result |
|---|---|---|
| `'11\n3\n3'` | `'3'` — **one glyph** | **broken** |
| `'111\n33\n33'` | `'33'` — two glyphs | correct |
| `'11\n9\n8'` | none | correct |

## What I was able to narrow down

Things that are **not** required — the artifact persists with all of these changed:

- **Scale/transform** — happens at scale 1.0 with no `Transform` or `FittedBox` anywhere.
- **`textAlign`** — `start`, `center` and `end` are all affected.
- **One paragraph vs. many** — a single multi-line `Text` and a `Column` of one-line `Text` widgets both show it.
- **Digits** — `'BB\nA\nA'` fails the same way, so it is not digit- or `tabularFigures`-specific.
- **Font** — the sample above uses the default platform font. I first hit this in a production app using a different font, so it is not font-specific.
- **Build mode** — the sample above is a debug build (release is not supported on the simulator), but the original report that led me here was a user screenshot from a **release TestFlight build on a physical iPhone 17 Pro running iOS 26.6**, so this is not debug-only or simulator-only.

Things that **are** required:

- **A blur.** `blurRadius: 0` renders correctly. `1`, `2`, `5` and `10` all fail.
- **A single-glyph run.** Any repeated run of two or more glyphs is fine.
- **Repetition.** The same single-glyph run must be painted at least twice. The first occurrence is usually correct and later ones drift.

Adding any zero-width character to the run makes it multi-glyph and the artifact disappears with **no layout change at all** — measured glyph x-range was identical to the broken version, to the pixel. `U+2060` WORD JOINER, `U+200B` ZERO WIDTH SPACE and `U+200C` ZWNJ all work. This is a usable workaround but obviously a hack.

## Renderer

Reproduces on:

- iPhone 17 simulator, iOS 26.5, Impeller (Metal) — log confirms `Using the Impeller rendering backend (Metal).`
- Android 16 (API 36) emulator, Impeller (Vulkan)

I could not A/B against Skia on iOS because `FLTEnableImpeller=false` is ignored on 3.47 and the fallback is gone. Rendering the same construct through `flutter_tester`, which rasterizes with Skia, produces no detached shadow — though that uses the test box font on a CPU raster, so I would treat it as suggestive rather than conclusive.

Given #126106 ("Investigate if we should cache text shadows in the glyph atlas as well", closed completed), a glyph-atlas cache keyed on glyph identity seems like a plausible place for this to live: it would explain why only *repeated* runs go wrong, why *single-glyph* runs are special, and why the error accumulates per repeat.

Same trigger by the sound of it, but it was closed without diagnosis because the sample depended on third-party packages. This issue is a dependency-free deterministic repro for what I believe is the same bug.
