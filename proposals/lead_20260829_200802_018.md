# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**swarm: mutable DAG owned by an Opus conductor, executed per-node in VMs**

*Project description:*
Amends #4781. Decisions 3 and 5 stand; decision 8 (Qwen conducts) is reversed and decision 9's swappability is what makes that reversible.

## Decided

1. **Opus plans.** The conductor is an Opus agent session with repo access, not a cheap API model. The cost objection is understood and accepted: Opus is on subscription and already runs in a guest. Revisit if per-task planning cost proves worse than measured.
2. **The DAG is mutable at the orchestration level, not inside a durable workflow.** The conductor owns the graph and reshapes it while work runs. Individual nodes execute as pinned units underneath.
3. **Limited escalation to Fable.** A bounded path for a node that Opus cannot resolve. Bounded means an explicit cap, not a fallback that any stuck node can reach.
4. **Everything executes in VMs.** Conductor and nodes alike are EmberVM guests. No planning or execution in the monolith process.

## Why point 2 is the load-bearing one

I raised this as the biggest unwritten risk and the decision answers it.

The pin exists because #4618 proved a durable workflow reading mutable state recovers wrongly; PR #4633 moved the retry bound into a pinned step record so replay could not see a different value than the original execution. Decision 3 (mutable plans) collides with that head-on **if the mutable graph lives inside the DBOS workflow**: on crash recovery, reading "current plan" recreates #4618, and reading "the version pinned at my start" means runtime add and discard cannot steer a running workflow, so the central promise quietly does not hold.

Putting mutation at the orchestration level dissolves it. The conductor holds the graph; each node is dispatched as its own durable unit with its own pinned inputs; the orchestrator reconciles graph against reality. Nothing durable ever reads mutable state mid-replay, because the durable units are per-node and their inputs are fixed at dispatch.

The consequence, stated plainly so nobody is surprised: **`implement_then_review` stops being the engine.** Today it is one monolithic workflow whose Python control flow IS the DAG (`swarm/workflows.py`, `node_key="implement"` / `"push_gate"` / `"review"`, with the same shape hardcoded again as a literal list with literal `deps` at `swarm/view.py:487-540`). This is a rewrite of that layer, not a refactor of it.

## Work, roughly in dependency order

- [ ] **Attribute storage must survive a write first.** #5417: DBOS workflow attributes replace rather than merge, so approving a push gate destroys the pinned plan. Versioned plan revisions cannot be built on a field that any writer blindly overwrites. Prerequisite, not a side quest.
- [ ] **A typed channel from an agent turn to the server.** There is none today: verdicts are a regex over the last lines of prose (`swarm/policy.py:101`, failing closed to "unparseable"), and an agent-written JSON file only reaches the server because the shim sweeps untracked files into the turn diff (`projects/embervm/runtimes/claude/shim.py:217-221`). A declared turn artifact `(path, schema)` validated server-side at ingestion, with validation failure a retryable turn outcome. One mechanism serves the conductor's graph edits and retires the verdict regex.
- [ ] **`swarm/mcp.py` DAG tool surface.** `add_node`, `discard_node`, reshape, following the per-domain pattern (`agent_sessions/mcp.py`, `cluster/mcp.py`). Built as MCP from the start per decision 9, so the conductor stays swappable and a CLI delegate is nearly free.
- [ ] **Per-node durable execution.** Each node its own unit with pinned inputs; an orchestrator reconciling the conductor's graph against what has run. Replaces the `implement_then_review` control flow.
- [ ] **`view.py` builds nodes from the graph** rather than from a literal three-element list.
- [ ] **Discard refusal.** Decision 5: a node that acted can never be silently discarded. Refuse when the dispatcher armed it, when `read_branch_head` shows the branch moved against the recorded baseline, or when recorded activities claim a write. The claim may only ever force a refusal, never permit a discard.
- [ ] **Per-node `max_cost_usd` admitted against the pin at add time.** #4781 decision 13, and the only spend control that can work: cost is observable only between turns (`swarm/steps.py:89`), so a runtime cap cannot interrupt work but an admission check needs no in-flight visibility. Relevant to #4784, and more urgent now that the planner itself is Opus.
- [ ] **Bounded Fable escalation**, with the cap explicit and recorded.
- [ ] **Conductor recording** per decision 10: task text, shape built, every edit, and whether the plan later had to grow. This is the feedback loop that makes an Opus conductor defensible or kills it.

## Open

- Does under-delivery get detected? Decision 7 makes under-calling the safe failure, but a run that planned one read node for a task that meant a repo change completes green and nothing marks "did less than asked". Same false-green class fought elsewhere in this repo. Decision 10's recording should carry a delivered-versus-asked judgment.
- What bounds the Fable escalation, concretely: attempts, cost, or node count.
