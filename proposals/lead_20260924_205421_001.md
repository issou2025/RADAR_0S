## Do NOT reuse mechanically: `rft.revit.column_place_ties.place_ties`

This function assumes a COLUMN host: it reads
`host_element.Location.Point`/`HandOrientation`/`FacingOrientation` as its
own origin/axis convention. Every footing placement adapter in this repo
(`footing_mesh.py`, `footing_dowels.py`) instead uses `_footing_origin`
(the footing's own bounding-box centre) and `_to_world_point` -- a
DIFFERENT, already-established convention, because a footing
`FamilyInstance` does not necessarily expose `HandOrientation`/
`FacingOrientation` the same way a column does (unverified either way --
flag it, don't guess). Build a NEW footing-specific placement function
that:
- reuses `resolve_tie`'s PURE geometry output (the rectangle's own
  corner/edge points, footing-local mm)
- converts those points via `_footing_origin`/`_to_world_point`
  (footing_mesh.py's own pattern), not via a column's Location/orientation
- uses `norm = XYZ.BasisZ` for the closed horizontal loop (matching
  `column_place_ties`'s own convention for a HORIZONTAL loop plane --
  this one detail IS safe to reuse, since dowel_tie sits in a horizontal
  plane exactly like a column tie does; this is DIFFERENT from
  `footing_dowels.py`'s `XYZ.BasisY`/per-bar norm, which is for a BENT
  bar in a VERTICAL plane -- do not conflate the two, this exact mistake
  was caught once already in this project's history)
- places one closed-loop `Rebar` per level in `dowel_tie_ladder`'s own
  ladder, hosted on the SAME footing as everything else
