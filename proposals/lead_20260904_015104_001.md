# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Design: service-hosted primary so every MCP client is a secondary and updates restart one known process (PRD §05)**

*Project description:*
## Problem

PRD §05's singleton model makes the primary whichever client process happens to win the lock. Live on 2026-09-03 this made a routine update hard to complete: the primary belonged to a client nobody was restarting, "restart your client" was true only for the owning client, and a client's window close did not end its server processes. Stale-image self-eviction (see the companion issue) removes most of the pain, but the ownership question remains: no single process is *the* server that an installer, a Status window, or a person can point at and restart.

## Proposal (design only for now)

In local mode, install the primary as a per-user logon scheduled task (or a Windows service for AllUsers scope) that runs `mcp-server --mode local --primary-only` continuously: binds, writes `broker.json`, never takes the lock-or-proxy decision. Client-spawned processes become secondaries always (they still race the lock for robustness when the task is not running, so a fresh install with no task still works). The installer gains `Restart-PrimaryTask` after a broker swap, so an update is: swap exe → restart task → every client's next call proxies to the new primary. The Status window's `MCP Server` line can then name the task and its state.

## Questions to settle
- Does a stdio-spawned secondary reconnecting to a restarted primary preserve the MCP session the client expects, or does the client need one reconnect regardless?
- Remote mode (Mac broker): unchanged — the Mac side already runs its broker deliberately.
- AllUsers scope: service vs per-user task; token/`broker.json` ownership under SYSTEM.
- Failure mode when the task is stopped/disabled: fall back to today's race (already in the code), plus a Status hint.

## Prior art in the repo
`revit/dev-tooling/launcher-agent.ps1` already runs a logon task in the interactive session and starts the broker there for the dev loop (`*.startbroker`), which is a working prototype of "the primary lives in a known process".
