### 5.2 `run_pipeline.sh` reports success after a total failure

This is the most dangerous bug in the repository.

When the run above crashed and both `detect.py` and `report.py` died with `FileNotFoundError`, your script printed:

```
========================================
✅ Pipeline Finished Successfully
========================================
```

Nothing ran. Nothing was produced. The script announced success anyway.

The cause is that `run_pipeline.sh` has no `set -e`, no exit-code checks, and no `exit` on failure. I grepped for all three and found zero occurrences. Bash carries on past a failed command by default, so the final `echo` always runs.

An automation script whose success message is unconditional is worse than having no script at all, because it turns a loud failure into a quiet one. Anyone running this from a scheduled job, from CI, or in front of an audience would walk away believing it worked.

Two lines fix it:

```bash
#!/bin/bash
set -euo pipefail    # stop on the first error, on undefined variables, and on pipe failures

IMAGE_DIR="${1:-./images}"

if [ ! -d "$IMAGE_DIR" ]; then
    echo "Error: input directory not found: $IMAGE_DIR" >&2
    exit 1
fi
```

With `set -e` the script stops at the first failing step and returns a non-zero exit code, which is what every tool that calls it expects.

### 5.3 The safety report says zero violations while people are detected

This is the most important technical finding in the review, and I want you to sit with it for a moment.

`report.py` and `api/main.py` both classify detections using hardcoded exact strings:

```python
if cls_name == "Person":
    persons += 1

if cls_name.startswith("NO-"):
    violations += 1
```

If the model's class names do not match those strings character for character, both counters stay at zero, nothing raises an error, and the report is written as though the site were fully compliant.

I reproduced this. Running your pipeline on your own five test images gave me:

```
Image                Persons  Violations Rate (%)
test1.jpg            0        0          0
test2.jpg            0        0          0
test3.jpg            0        0          0
test4.jpg            0        0          0
test5.jpg            0        0          0
```

while the JSON file written by the very same function contains:

```json
{
    "image": "test1.jpg",
    "persons_detected": 0,
    "violations_detected": 0,
    "violation_rate_percent": 0,
    "detections": [
        { "class": "person", "confidence": 0.91, "bbox": { ... } },
        { "class": "person", "confidence": 0.71, "bbox": { ... } }
    ]
}
```

Two people detected at 91% and 71% confidence, drawn correctly with bounding boxes in the annotated output image, and the compliance summary reports zero people, zero violations, zero percent. Across all five images there were 10 detections, every one of them a person, and every row of the report read zero.

In my case this happened because the stand-in model uses `"person"` rather than `"Person"`. Your real model may well use the capitalised name and work correctly today. **That is not the point I am making.** The point is the failure mode. A one-character difference in a class name — from a retrain, from a new dataset version, from a different export — turns your safety monitor into a system that reports perfect compliance for every image, with no error, no warning, and nothing in the logs. For a system whose whole purpose is catching workers who are not wearing protective equipment, silently failing toward "everything is fine" is the worst possible direction to fail in.

The same logic is duplicated across two files, so any fix has to be applied twice, and that duplication is part of the problem.

Here is what I want you to do:

1. Move the class logic into one shared module that both `report.py` and `api/main.py` import. Do not keep two copies.
2. Validate the class names against the model at startup and stop loudly if they are wrong:

```python
PERSON_CLASS = "Person"
model_classes = set(model.names.values())

if PERSON_CLASS not in model_classes:
    raise SystemExit(
        f"Expected class '{PERSON_CLASS}' not found in model. "
        f"Model classes: {sorted(model_classes)}"
    )
if not any(c.startswith("NO-") for c in model_classes):
    raise SystemExit(f"No 'NO-*' violation classes in model: {sorted(model_classes)}")
```

Six lines turn a silent wrong answer into an immediate, explicit error.

3. Log a warning whenever an image produces detections but zero persons. That combination is almost always a bug rather than a real result.

### 6.1 The annotated image URL is hardcoded to port 8000

In `api/main.py`:

```python

```

I ran your API on port 8021 and the response still pointed at port 8000, so the dashboard would show a broken image. Build the URL from the incoming request instead, and it works on any host and port:

```python
from fastapi import Request

    "annotated_image_url": str(request.url_for("output", path=output_filename)),
```

I verified this works with your existing `StaticFiles` mount — the returned URL reflects whatever port the server is actually running on.

### 6.2 The dashboard runs in debug mode bound to every interface

```python
app.run(host="0.0.0.0", port=5000, debug=True)
```

Here is what your own startup log printed on my machine:

```
 * Running on http://192.168.1.15:5000
 * Debugger is active!
 * Debugger PIN: 135-541-007
```

`debug=True` enables the Werkzeug interactive debugger, which exposes a browser console capable of executing Python on the server. It is protected by the PIN you can see printed above, but Flask's own documentation describes it as a major security risk and says not to run the development server or the debugger in production. Combining it with `host="0.0.0.0"`, which makes the port reachable by anyone on the local network, is the part that turns a development convenience into an exposure.

```python
app.run(host="127.0.0.1", port=5000, debug=False)
```

Use `debug=True` only while developing locally, and never together with `0.0.0.0`.

### 6.3 The API returns 500 with a traceback for a non-image upload

What I measured:

|---|---|---|
| Valid image | 200 with correct JSON | Correct |
| No file | 422 | Correct |
| Text file instead of an image | **500 with a traceback** | 400 with a clear message |

### 6.4 The model is loaded at import time

`model = YOLO(MODEL_PATH)` at module level in `api/main.py` means the server dies during startup when the weights are missing, which after a fresh clone is always. Put the existence check from 5.1 before it so the message is useful.

### 6.5 You never pin the execution device

No call in `detect.py`, `report.py`, or `api/main.py` passes `device=`, so ultralytics picks the hardware itself. On any machine with a GPU these scripts quietly move to CUDA, which contradicts the "runs locally on CPU" item in the Definition of Done. Define it once and pass it everywhere:

```python
DEVICE = "cpu"
results = model(image, conf=CONF, iou=IOU, device=DEVICE)
```

This is the same issue I saw in Week 1, in a new project.

### 6.6 The pipeline runs the model twice over the same images

`detect.py` loads the model and runs inference to draw boxes. `report.py` loads the model again and runs inference over the same folder to build the JSON. `run_pipeline.sh` calls both, so every image is processed twice and the model is loaded twice.

A single pass produces both outputs, because `results[0]` already holds everything you need:

```python
results = model(str(img), conf=CONF, iou=IOU, device=DEVICE)[0]
cv2.imwrite(str(OUTPUT_DIR / img.name), results.plot())   # annotated image
# build the JSON from results.boxes in the same loop
```

That halves the work, and more importantly it removes the possibility of the image and the report disagreeing because two separate runs produced them.

### 6.7 The violation rate can exceed 100%, and your README shows it

```python
rate = 0 if persons == 0 else round((violations / persons) * 100, 2)
```

One worker missing both a hardhat and a vest produces two `NO-*` detections against one `Person`, which gives 200%. Your README publishes an example of this without comment:

| Image | Persons | Violations | Violation Rate |
|------|---------|------------|----------------|
| test2.jpg | 4 | 5 | 125% |

A "rate" above 100% tells the reader the metric is not measuring what its name claims. You have two honest options:

- Rename it to what it actually is, `violations_per_person`, which may legitimately exceed 1.
- Or compute real compliance by associating each `NO-*` box with the `Person` box it overlaps, using IoU or centre containment, and then counting **non-compliant workers** instead of violation boxes. That is the more useful number for a safety report and it is good practice with bounding-box geometry.

Note as well that the `persons == 0` branch returns a rate of 0 even when violations were detected, which once again reads as "compliant" when the truth is "unknown."

### 6.8 `conf=0.65` is hardcoded in three files

The same magic number sits in `detect.py`, `report.py`, and `api/main.py`. Changing the threshold means editing three files and hoping you did not miss one.

Your commit message says you raised it to 0.65 to "eliminate duplicate detections." That is the wrong lever. Duplicate boxes on the same object are removed by non-maximum suppression, controlled by `iou`, and when the duplicates carry *different* class labels — which is likely here, since a head can be predicted as both `Hardhat` and `NO-Hardhat` — the parameter you want is `agnostic_nms=True`. Raising `conf` does hide duplicates, but only by discarding every lower-confidence detection, including real violations you wanted to catch. In a safety system a missed violation is precisely the error you cannot afford.

Put both values in one place and expose them:

```python
parser.add_argument("--conf", type=float, default=0.5)
parser.add_argument("--iou", type=float, default=0.45)
```

The Definition of Done asks for detections above 0.5, so make 0.5 the default and tune from the command line rather than by editing source.
