# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Keep the per-install id and city out of crash reports**

*Project description:*
Crash reports carry a **stable per-install identifier** and the **city** of every crash. Neither is needed to fix a bug, and both contradict what users were told.

Measured on a live event in this project's Sentry organisation ([#889](https://github.com/simonoppowa/OpenNutriTracker/issues/889)):

```
user.id  : 36-character UUID   ← stable across launches, ungated by sendDefaultPii
user.geo : { country_code, city, region }
user.ip_address : null          ← the IP itself is correctly withheld
```

The consent label promises *"**anonymous** crash reports … No food log, weight, or personal data is included"*, and [#874](https://github.com/simonoppowa/OpenNutriTracker/issues/874) made that label the basis of an Art.6(1)(a) consent. [#894](https://github.com/simonoppowa/OpenNutriTracker/issues/894) decided the data is **pseudonymous, not anonymous** — a persistent identifier makes every crash from one installation linkable to every other — and that the fix is to remove the identifier rather than to describe it.

## The work

**1. Strip the identifier, client-side.** Add a `beforeSend` hook in `lib/core/utils/sentry_config.dart` that clears `event.user`. That also restores an existing public claim instead of requiring a third correction of it: the README's *"no user or device identifier"* becomes true for Sentry again. Pin it with a test alongside the existing `sentry_config_test.dart` cases, which already pin `enablePrintBreadcrumbs` and `sendDefaultPii`.

**Known cost, accepted deliberately:** `user.id` is what powers Sentry's *users affected* count. Without it you cannot tell one installation crash-looping from a hundred installations hitting the same bug.

**2. Chase `user.geo`, server-side.** A client hook **cannot** remove it — the client never sends it. Relay derives it from the connection IP at ingest, and #889 established the organisation's *Prevent Storing of IP Addresses* setting does not cover it. The candidate is an **Advanced Data Scrubbing** rule under Security & Privacy. **Verify against a real event rather than assuming it worked** — the same method that found this in the first place.

**3. Correct the consent label.** Drop *"anonymous"*. Say what is actually sent and what is not.
