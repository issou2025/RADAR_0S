# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Associated Domains entitlement points at a placeholder domain that can never resolve**

*Project description:*
Found while producing the first TestFlight build.

Both entitlements files declare:

```
com.apple.developer.associated-domains = ["applinks:tideandseek.invalid"]
```

`.invalid` is a **reserved TLD** (RFC 2606) guaranteed never to resolve. So universal links cannot work, and the entitlement is inherited scaffolding rather than a feature.

Files: `apps/mobile/ios/Runner/Release.entitlements`, `apps/mobile/ios/Runner/DebugProfile.entitlements`

## Why it matters beyond tidiness

It is a capability the App ID must carry and the provisioning profile must match. It contributed to the first `flutter build ipa` failing with *"requires a provisioning profile with the Associated Domains and Push Notifications features"* — the capability is enabled on the Bundle ID, so the build works, but the app is claiming an entitlement it cannot use.

It also affects App Review: an app declaring associated domains that resolve to nothing is a question waiting to be asked.

## Decide which

**If universal links are wanted** — a shared voyage code opening the app from a link is the obvious use, and would be a genuinely nice way to join a voyage — then a real domain is needed, plus an `apple-app-site-association` file served from it.

**If not**, remove the entitlement from both files and drop the capability from the Bundle ID (`34RUABFBY4`).

Note that the voyage-join flow currently works by six-digit code and QR, neither of which needs associated domains, so removal is the smaller change and loses nothing today.

## Acceptance

- [ ] Either a real domain with a valid AASA file, or the entitlement removed from both files
- [ ] The Bundle ID's capabilities match what the app actually declares
- [ ] A release build exports without needing that capability, if removed
