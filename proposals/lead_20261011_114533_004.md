## Summary

Apple shipped **[Core AI](https://developer.apple.com/documentation/coreai)** with iOS/macOS 27 (WWDC26) as its new framework for running neural-network models on Apple silicon. This issue looks at whether the Apple backend (`mobile_back_apple`, which uses Core ML today) should adopt it, and answers the "check if we should keep using CoreML or move to CoreAI" item of #1177.

**Recommendation: keep Core ML for the Apple backend and don't move to Core AI yet. Choose the framework per workload:**

| Workload | Recommended path | Why |
|---|---|---|
| Classic models (MobileNetV4, MobileDet, MOSAIC, MobileBERT, EDSR) | **Stay on Core ML** | Core ML runs on every iOS version the app supports. Core AI needs iOS 27 and converts from PyTorch only, and MobileDet and MOSAIC are TF models. Third-party data shows Core AI only on par with Core ML for CNNs on iPhone. Open Core AI bugs silently return wrong results on the Neural Engine (ANE). |
| int8 on the ANE (A17 Pro / M4 and later) | **Core ML W8A8** | Apple's guide shows W8A8 at 1.3–2.5x faster than FP16 on iPhone 15 Pro. We already generate `mobilenetv4_w8a8.mlpackage`. |
| Stable Diffusion | **Core ML via Apple's [`ml-stable-diffusion`](https://github.com/apple-aiml-research/ml-stable-diffusion)** (`CPU_AND_NE`) | It is ANE-optimized and converts the text encoder, UNet and VAE decoder separately. Core AI has no SD or UNet recipe, and its diffusion runtime prefers the GPU even on iOS. |
| LLM (Llama 3.2 1B) | **Core AI spike (experimental)**, with LiteRT + Metal as the baseline | Core ML has no ANE path for LLMs: Apple's own Core ML Llama recipe targets the GPU. Core AI ships an ANE-targeted iOS LLM recipe and an engine that takes token IDs, but open bugs block it (below). |

**What blocks Core AI as an MLPerf backend today.** The first two are open GitHub issues filed by third parties, with no Apple response yet.
1. **The process crashes after exactly 16,384 output `NDArray` allocations** ([coreai-torch#75](https://github.com/apple/coreai-torch/issues/75)). The crash can't be caught, and reloading the model doesn't help. One image classification v2 performance run (at least 60 s at about 1 ms per inference) would hit it.
2. **Default (ANE) specialization silently returns wrong results** for argmax, fp16 outputs, QDQ multiply and per-block int weights (#116, #115, #112, coreai-models#279).
3. **No way to pin a compute unit.** You can only set a "preferred" unit, which falls back to the others.
4. **Swift-only async API, no iOS Simulator support, PyTorch-only conversion, iOS 27 and later only.**

Apple's own position: Core ML is **not deprecated**. At the WWDC26 ML & AI lab: *"it's not a call to migrate off… Core ML works. It is supported"*, while Core AI *"is where we're investing for… modern AI generative models."*

Proposed next steps are at the end.

## 1. What Core AI is

Sources: the [Core AI docs](https://developer.apple.com/documentation/coreai), WWDC26 sessions [324 "Meet Core AI"](https://developer.apple.com/videos/play/wwdc2026/324/), [325](https://developer.apple.com/videos/play/wwdc2026/325/), [326](https://developer.apple.com/videos/play/wwdc2026/326/) and the [ML & AI Group Lab (8016)](https://developer.apple.com/videos/play/wwdc2026/8016/).

- **Platforms:** iOS, iPadOS, macOS, tvOS, visionOS, watchOS and Mac Catalyst, all **27.0 and later**.
- **API:** Swift only. The docs list no Objective-C, C or C++ interface; Core ML has an Objective-C API. `AIModel`, `InferenceFunction` and `NDArray` are Swift structs. Loading (`AIModel(contentsOf:)`) and `run(...)` are `async`. `encode(inputs:states:outputViews:to:)` onto a `ComputeStream` is synchronous and can target your own `MTLCommandQueue`.
- **Model format:** `.aimodel`, which is portable and holds one or more named inference functions.
- **Tensors:** `NDArray` (read-only by default, with `mutableView` for writes). Image inputs and outputs use `CVMutablePixelBuffer`.
- **Specialization:** the first load specializes the model for the current device, which is slow for large models. The result is cached in `AIModelCache`. `AIModel.specialize(...)` pre-warms it, and a `.persistent` policy keeps it. **The cache is always invalidated on an OS update.**
- **Ahead-of-time compile:** `xcrun coreai-build compile` produces one `.aimodelc` per device architecture, chosen at runtime via `AIModel.deviceArchitectureName`. It only supports Apple Intelligence-capable devices (A17 Pro or later, M1 or later), and some specialization still runs on the device ([docs](https://developer.apple.com/documentation/coreai/compiling-core-ai-models-ahead-of-time)).
- **Compute units:** `SpecializationOptions.default` (auto), `.cpuOnly`, or `init(preferredComputeUnitKind:)` with `.cpu`, `.gpu` or `.neuralEngine`. The preferred option "maximizes use of the specified compute unit kind, falling back to other allowed compute units". `allowedComputeUnitKinds` is get-only. **There is no equivalent of Core ML's strict `.cpuAndNeuralEngine` or `.cpuAndGPU`.**
- **Generative-model features:** stateful `run(inputs:states:)` for KV caches, dynamic shapes with `expectFrequentReshapes`, and concurrent runs (`InferenceFunction` is `Sendable`). LLMs can also run through Foundation Models' `LanguageModelSession`.
- **Tooling:** [coreai-torch](https://github.com/apple/coreai-torch) (conversion), [coreai-optimization](https://apple.github.io/coreai-optimization) (compression), [coreai-models](https://github.com/apple/coreai-models) (recipes and a Swift package), Xcode model viewer, Core AI Instruments and debug gauge, and the Core AI Debugger app.
- **Integration requirement:** Xcode needs the Metal Toolchain component to build projects that bundle `.aimodel` files.
- **Scope:** the Core AI docs send non-neural-network models (trees, tabular) to Core ML. The Core ML docs now say: "If your app integrates AI models using the latest architectures and inference techniques, see Core AI." Core ML has **no deprecation markers** (checked on `CoreML` and `MLModel`).

## 3. Core ML side: the references from #1177

### 3.1 Stable Diffusion: [`ml-stable-diffusion`](https://github.com/apple-aiml-research/ml-stable-diffusion)
- **Repo status:** `apple/ml-stable-diffusion` now redirects to the **`apple-aiml-research`** org. That org's profile says repos "may not receive ongoing feature development after initial release. Issues, pull requests, and discussions are disabled." The last code change was 2025-07 (PR #368), and the last release is 1.1.1 (2024-05). **It's frozen, but usable.**
- **Supported models:** SD 1.4, 1.5, 2.0-base, 2.1-base, SDXL (and an SDXL-iOS 768x768 variant), and SD3-medium. SD3 is CPU+GPU only.
- **Pipeline:** each component converts separately (`--convert-text-encoder`, `--convert-unet`, `--convert-vae-decoder`). Shapes are static (77 tokens).
- **ANE attention:** `SPLIT_EINSUM` (the default) and `SPLIT_EINSUM_V2`, which is "10-30% improvement for mobile devices". Recommended for iPhone/iPad: **`CPU_AND_NE`**.
- **Compression:** palettization with `--quantize-nbits {2,4,6,8}` (at least 6-bit recommended) and mixed-bit palettization (about 4-bit). `--chunk-unet` is required for the ANE on iOS if weights aren't 6-bit or lower.
- **W8A8 on A17 Pro / M4:** mixed W8A8/W8A16 UNet via per-layer sensitivity analysis. It needs calibration data and a few GPU hours. No latency is published.
- **Published latency** (SD 2.1-base, 512x512, 20 steps, 6-bit, `CPU_AND_NE`, `SPLIT_EINSUM_V2`, iOS 17 beta): iPhone 13 Pro Max **10.4 s**, iPhone 14 Pro Max **7.9 s**, iPad Pro M2 **7.0 s** end to end. SDXL-iOS (4.04-bit) on iPhone 15 Pro Max: 31 s.
- **Requirements:** iOS 16.2 / macOS 13.1 or later (iOS 17 for the memory improvements), A14 / M1 or later, `coremltools>=8.0`.

### 3.2 Transformers and LLMs on Core ML
- **[Deploying Transformers on the ANE](https://machinelearning.apple.com/research/neural-engine-transformers)** (2022), with its code in [`ml-ane-transformers`](https://github.com/apple-aiml-research/ml-ane-transformers):
  - Use the (B, C, 1, S) channels-first layout. Replace `nn.Linear` with 1x1 `nn.Conv2d`.
  - Split heads into single-head attention, and keep reshapes and transposes to a minimum.
  - The last axis should be contiguous and 64-byte aligned.
  - distilbert ran up to 10x faster with 14x less memory.
  - It is **encoder-only**, with no KV-cache or decoder guidance. The repo is frozen; the last real commit was 2022.
- **[On-device Llama 3.1 with Core ML](https://machinelearning.apple.com/research/core-ml-on-device-llama)** (2024):
  - It **targets the GPU, not the ANE**: "We use a Mac with M1 Max and specifically target the GPU…".
  - Techniques: stateful KV cache (`MLState`, iOS 18 / macOS 15), fused SDPA (a GPU kernel), int4 per-block quantization ("optimized for the GPU"), and flexible shapes.
  - Result on M1 Max: ~33 tok/s decode. There are no iPhone or ANE numbers.
- **Conclusion:** none of these sources gives a Core ML path for running Llama 3.2 1B on the iPhone ANE. Apple's documented Core ML LLM route is the GPU. A 1B fp16 model (about 2.5 GB) would also need chunking or 4-bit-or-lower palettization plus ANE-style rewrites, with no guarantee it stays on the ANE.

### 3.3 int8 / W8A8 ([coremltools quantization performance guide](https://apple.github.io/coremltools/docs-guides/source/opt-quantization-perf.html))
- "In newer hardware with **A17 Pro or M4** chips… there is increased throughput possible for int8-int8 compute on Neural Engine."
- Use activation quantization only when the model runs fully or mostly on the ANE. On the ANE, prefer per-channel scales over per-block.
- **Latency in ms**, iPhone 14 Pro → iPhone 15 Pro:

  | Model | FP16 | Weight-only (post-training) | W8A8 (QAT) |
  |---|---|---|---|
  | MobileNetV2 | 0.48 → 0.49 | 0.45 → 0.44 | 0.27 → **0.20** |
  | ResNet50 | 1.52 → 1.38 | 1.49 → 1.50 | 0.94 → **0.77** |
  | MobileViTv2 | 1.38 → 1.36 | 1.43 → 1.37 | 1.18 → **1.03** |

  Weight-only is roughly latency-neutral. On the 15 Pro, W8A8 is **1.3–2.5x faster than FP16**. Note that these W8A8 numbers come from quantization-aware training (QAT).
- **Importing already-quantized models:**
  - PyTorch's built-in quantization (per-tensor and per-channel) is picked up automatically during conversion ([docs](https://apple.github.io/coremltools/docs-guides/source/opt-conversion.html)).
  - Activations can also be quantized directly on an `.mlpackage` with `linear_quantize_activations` (calibration data needed).
  - **TFLite is not a supported source format**, and the ONNX converter is frozen ([FAQ](https://apple.github.io/coremltools/docs-guides/source/faqs.html)). TFLite int8 models therefore can't be imported; re-quantize from PyTorch or float instead.

### 3.4 coremltools status ([repo](https://github.com/apple/coremltools))
- The latest stable release is **9.0** (2025-11-11). The latest pre-release is `9.1.dev1` (2026-08, on PyPI only). PyTorch support goes up to 2.7 (2.8 on main).
- The newest deployment target is still **iOS26/macOS26**; **there is no iOS 27 target** and no 10.0 beta. My reading, not stated by Apple: the iOS 27-generation work went into Core AI tooling.
- Development continues: 60+ commits since 2026-05, active issues, no deprecation notice and no mention of Core AI.

### 3.5 ANE features by generation ([guide](https://github.com/freedomtan/coreml_to_ane_hwx/blob/main/docs/GUIDE_ANE_FEATURE_SUPPORT_BY_GENERATION.md))
- **`DoubleInt8`** (2x int8 MAC throughput) first appears in **H16 (A17 Pro / M4)**. This matches Apple's W8A8 guidance: no int8 compute gain on earlier chips.
- **1D Winograd** first appears in **H17**. 2D Winograd isn't real on any chip through H19.
- **FP8 (E4M3) activations** first appear in **H18**. Neither public toolchain appears to give a way to target FP8 on the ANE:
  - coremltools has no FP8 activation quantization.
  - Core AI's FP4/FP8 activation presets need macOS 27.2 or later and are GPU-path presets.

## 4. Core AI side

### 4.1 Conversion: [coreai-torch](https://github.com/apple/coreai-torch) ([docs](https://apple.github.io/coreai-torch/main/))
- **Versions:** v0.4.3 (2026-09-25); releases roughly monthly since v0.4.0 (2026-06-09). It requires Python 3.11 or later, `torch>=2.8` and `coreai-core==1.0.0b3`.
- **Input:** the only input is **PyTorch** (`torch.export` ExportedProgram → `TorchConverter` → `to_coreai()` → `.aimodel`). There is **no TFLite, ONNX or Core ML (`.mlpackage`) import** and no migration tool from coremltools.
  - [Ultralytics](https://docs.ultralytics.com/integrations/coreai/) confirms an `.mlpackage` can't be converted.
  - MobileDet SSD and MOSAIC would need PyTorch ports plus accuracy re-validation.
  - MobileNetV4 (timm), MobileBERT (HF) and EDSR have PyTorch sources.
- **Where conversion and running work:** conversion works on **macOS 26 or Linux x86_64**; macOS 27 isn't needed. Running a model and AOT compilation need macOS/iOS 27 and Xcode 27.
- **Ops:** about 150 supported ATen ops, including topk, argmax, SDPA and `pixel_shuffle`. There is no `torchvision::nms`. Custom lowerings and inline Metal kernels are possible.
- **Image inputs:** `TorchConverter` emits tensors only. Pixel-buffer inputs need the lower-level authoring API (`ImageSpec`).
- **Precision:** there is no precision flag; it follows the exported graph's dtype. The ANE accepts **fp16, int8 and int16 only**, so fp32 falls back to GPU/CPU. Even a Python float literal creates an fp32 constant.
- **Placement reporting:** v0.4.3 added a compute-plan report showing each op's device and why the ANE was rejected.
- **Format churn:** assets built with v0.4.0 fail to load from OS 27 beta 2 onward ([v0.4.1 notes](https://github.com/apple/coreai-torch/releases/tag/v0.4.1)).
- **Export-host sensitivity:** one third party saw the same recipe produce a 2.2x slower artifact after the export host moved from macOS 26 to 27 ([write-up](https://github.com/john-rocky/apple-silicon-llm-bench/blob/main/methodology/coreai-export-lowering.md)). Treat `.aimodel` files as pinned build artifacts.

### 4.2 Compression: [coreai-optimization](https://apple.github.io/coreai-optimization) (`coreai-opt`)
- **Weights:** INT2/4/8, FP4/FP8, palettization (1–8 bits) and pruning.
- **Activations:** INT8/FP8, by post-training calibration or QAT. Per-channel and per-block granularity.
- **Input:** PyTorch only. Pre-quantized TFLite or ONNX models can't be imported.
- **int8 execution:** whether int8 activations actually run as int8 on the ANE isn't stated explicitly. The closest statement is that an INT8 LUT "allows the runtime to use the faster W_INT8-A_INT8 execution path where available".

### 4.3 Recipes and runtime: [coreai-models](https://github.com/apple/coreai-models)
Tagged 1.0.0 on 2026-10-02; PRs are not accepted.
- **LLMs:**
  - **No Llama recipe.** SmolLM2 is routed through the qwen2 path. Llama 3's `rope_type: "llama3"` scaling needs a small patch: the macOS path asserts default RoPE, and the iOS `RoPECache` silently ignores the scaling.
  - Closest iOS recipes: qwen3-0.6b, smollm2, olmo2-1b.
  - **The iOS recipe targets the ANE:**
    - Fully static shapes; default context 4096.
    - Graphs specialized per cache length and query length.
    - Separate prefill and decode functions.
    - The KV cache is passed as inputs (the caller writes the new K/V back).
    - 4-bit palettized weights, fp16 compute.
    - The Swift runtime specializes it with `preferredComputeUnitKind: .neuralEngine`.
  - The macOS recipe uses the GPU, dynamic shapes, INT4 per-block weights and a stateful KV cache.
  - **Published numbers are perplexity only.** There are no tok/s or time-to-first-token figures.
- **Swift package** (iOS/macOS 27):
  - `InferenceEngine.generate(with: [Int32], ...)` **takes raw token IDs**, which fits our SentencePiece/MMLU data path.
  - The `llm-benchmark` CLI already measures prepare/specialization time, cache hit, prompt tok/s (time to first token) and decode tok/s at temperature 0.
- **Diffusion:**
  - **No Stable Diffusion or UNet recipe.** Only DiT/flow models: FLUX.2 klein 4B (iOS, 4-bit), Sana Sprint (macOS) and Wan.
  - All diffusion components load with `preferredComputeUnitKind: .gpu`, even on iOS.
- **Vision:** EDSR (`edsr_r16f64_x2`, fp32 by default, static 16x16 or dynamic) and YOLO. No compute unit or performance numbers are published.
- **ANE authoring rules** (from the repo's [`skills/model-authoring` reference](https://github.com/apple/coreai-models/blob/main/skills/skills/model-authoring/references/neural_engine_rules.md)):
  - Layout: BC1S; `nn.Linear` becomes 1x1 conv, otherwise it may fall back to the CPU.
  - Precision and shapes: fp16 only, no fp32 literals, fully static shapes. Keep iOS models under 2 GB.
  - Attention: per head (there is no fused SDPA on the ANE). The mask uses -40000 instead of -inf. Precompute RoPE outside the graph.
  - Decode: chunked prefill of 64, because q=1 decode drifts in fp16.
  - Placement: pin the ANE at compile time with `coreai-build --preferred-compute neural-engine`. The documented failure mode is "Neural Engine model compiles but runs on CPU".

### 4.4 Known Core AI issues (blockers for MLPerf use)
All are open, all were filed by third parties, and none has an Apple response so far.

| Issue | What happens | Impact on MLPerf Mobile |
|---|---|---|
| [coreai-torch#75](https://github.com/apple/coreai-torch/issues/75) (2026-08-30) | The process crashes after exactly **2^14 = 16,384 output `NDArray` allocations**, so the maximum number of inferences is floor(16384 / num_outputs). It hits every compute unit, the SIGTRAP can't be caught, and reloading the model leaks ANE threads without resetting the count. | **Blocker.** IC v2 needs at least 60 s and 1,024 queries; at ~1 ms per inference that is about 60k inferences. Full-dataset accuracy runs (ImageNet val) exceed the cap too, and the count adds up across benchmarks in one app session. My reading (unconfirmed): LLM decode returns per-layer K/V outputs every step, so the cap arrives after a few hundred tokens. A possible workaround, pre-allocated `outputViews`, is untested. |
| [coreai-torch#116](https://github.com/apple/coreai-torch/issues/116) (2026-09-18) | `argmax` is wrong with default specialization on iPhone 17 Pro: 198,442 of 409,600 pixels differ. CPU-only is correct. | MOSAIC outputs a per-pixel class map ([`ade20k.cc:147-165`](https://github.com/mlcommons/mobile_app_open/blob/978419f6/flutter/cpp/datasets/ade20k.cc#L147-L165)), so it is directly affected. |
| [coreai-torch#115](https://github.com/apple/coreai-torch/issues/115) (2026-09-18) | FP16 model silently returns wrong outputs with default specialization on iPhone 17 Pro. CPU-only, GPU-preferred and FP32 are correct. A follow-up comment narrows it to fp16 `topk` on the ANE lane returning 16-bit indices packed two per int32. | Affects any fp16 model on the ANE, including SSD postprocessing. |
| [coreai-torch#112](https://github.com/apple/coreai-torch/issues/112) (2026-09-14) | QDQ multiply returns scale-dependent wrong values on the ANE. The reporter says Core ML has the same behaviour. | Affects W8A8 models. |
| [coreai-models#279](https://github.com/apple/coreai-models/issues/279) (2026-09-22) | Per-block int weight quantization silently produces wrong output on the ANE: cosine 0.367 vs 0.999 on the GPU. | Rules out per-block int quantization on the ANE; palettization works. |
| [coreai-torch#51](https://github.com/apple/coreai-torch/issues/51) (2026-07-23) | MobileNetV3 shows an fp16 numerical discrepancy on the ANE (Linear followed by Hardswish, about 3.9% relative L2 error). | Accuracy risk for MobileNet-family models. |

Other constraints:
- **No iOS Simulator support:** the Swift package fails to compile for the Simulator with "no such module 'CoreAI'" ([coreai-models#49](https://github.com/apple/coreai-models/issues/49)). Ultralytics notes the same, so Core AI tests must run on real devices.
- **No way to pin a compute unit**, so a delegate called "ANE" can't be guaranteed to run on the ANE.
- **No Apple statement on run-to-run determinism.**

### 4.5 Published performance data
**Apple:** no Core AI vs Core ML comparison has been published. Session 324 only says "blazing fast inference across the CPU, GPU, and Neural Engine".

**[Ultralytics](https://docs.ultralytics.com/integrations/coreai/)** (third party): YOLO26n FP16 on a Mac mini M4 running macOS 27.0, end-to-end ms:

| Task | Core ML CPU+ANE | Core AI ANE-preferred |
|---|---|---|
| Detect | 7.6 | **2.8** |
| Segment | 9.2 | **5.1** |

- **On iPhone 17 Pro, Core AI is only on par with Core ML.** In Ultralytics' words: "level with Core ML for the full pipeline rather than ahead". Semantic, depth and CPU-only inference were slower, and FP16 assets were about twice the download size.
- So Ultralytics keeps Core ML as the default in its iOS SDK and Flutter plugin.

**[apple-silicon-llm-bench](https://github.com/john-rocky/apple-silicon-llm-bench)** (third party, beta-era builds, mixed sessions): Qwen3-0.6B decode on iPhone 17 Pro:
- Core AI: about 117–122 tok/s on the ANE (static shapes) and about 193 tok/s on the GPU.
- Core ML: about 38 tok/s.
- Treat these as directional only. They do suggest LLM is where Core AI has a real advantage.

## 6. Mapping to the #1177 checklist

- [ ] **LiteRT + Metal for Llama 1B and SD:** still worth doing. It's the only path that works the same below iOS 27, and it serves as the baseline.
- [ ] **Llama 1B and SD on the ANE via Core ML:**
  - **SD: yes**, via `ml-stable-diffusion` components (`CPU_AND_NE`, `SPLIT_EINSUM_V2`, 6-bit palettization).
  - **Llama: no.** Apple's Core ML LLM path is the GPU, so the ANE route for LLM is Core AI (see the next step).
- [ ] **Optimize existing models (NHWC vs NCHW):** unchanged by this investigation. The ANE wants channels-first layout under both frameworks.
- [ ] **Quantized TF/TFLite/PyTorch models to Core ML:**
  - TFLite: not possible. ONNX: frozen.
  - PyTorch per-tensor and per-channel quantization: converted automatically.
  - Otherwise use `coremltools.optimize` (`linear_quantize_activations`).
  - The W8A8 gain is real only on A17 Pro / M4 and later.
  - Quick win: benchmark the existing `mobilenetv4_w8a8.mlpackage`.
- [ ] **Core ML vs Core AI:** **keep Core ML.** Run Core AI as an LLM-only experiment until #75 and the ANE correctness issues are fixed.

## 7. If we add Core AI later: integration notes
- **Location:** put it **inside `mobile_back_apple`** rather than a new top-level backend.
  - It's the same vendor, it reuses the list tag, xcframework and Xcode project entries, and the per-benchmark backend selection from #1164 already covers the user-facing choice.
  - A new top-level backend touches about 8 places (`*.mk`, `Makefile`, `list.in`, `flutter.mk`, `ios.mk`, pbxproj, dummy xcframework), as the `litert-ios` branch shows.
- **Building on older toolchains and OS versions:**
  - Guard the code with `#if canImport(CoreAI)` so it still builds with Xcode 26.
  - Mark it `@available(iOS 27, *)` and weak-link the framework so the backend still loads on iOS 15–26.
- **Exposing it to the app:** `mlperf_backend_matches_hardware` returns a different settings pbtxt on iOS 27, with Core AI delegates plus LLM and SD entries. `mlperf_device_info_t` has no OS version, so the backend has to check it itself.
- **Bridging:** a Swift shim (`@objc` or `@_cdecl`) that blocks on the async calls, or `encode` on a `ComputeStream` backed by our own `MTLCommandQueue` for a synchronous path.
- **Toolchain and CI:**
  - It needs the Xcode 27 SDK. Bazel is 6.6, and rules_swift / rules_apple come pinned through TF 2.18.
  - The `apple-xcode27` CI leg is still `continue-on-error`.
  - Without simulator support, Core AI tests need devices.
- **Model distribution:**
  - Either `.aimodel` files (specialized on the device, which can take minutes for LLM/SD, and must happen outside the timed region and be cached), or one `.aimodelc` per architecture (A17 Pro or later only, with an MD5 per architecture).
  - The cache is invalidated on every OS update.
  - Pin conversion-tool versions, because of the format churn.
- **Accelerator reporting:** delegates can only say "prefer ANE"/"prefer GPU". Use the coreai-torch compute-plan report to document actual placement.
