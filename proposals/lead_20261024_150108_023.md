# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Node-level retry attempts are not observable in the run steps API (only final attempt kept, attempt count only in logs)**

*Project description:*
## Summary

The engine's node retry loop (A-1, `WorkflowEngine` node execution: `max_retries`/`retry_delay`) retries on exceptions/timeouts and logs each attempt (`Node '<name>' exception attempt=N/M`), but the run steps API keeps only the **final** attempt's `WorkflowStep`. There is no way for an API consumer to see how many attempts a node actually took, or that intermediate attempts failed.

Two consequences:

1. **Observability gap** — ops/GUI cannot surface "node X failed twice then succeeded", which matters for reliability dashboards (PRD-level requirement: retryable errors must be visible).
2. **Business failures are not retried** — `node.execute()` returning `NodeResult(status=FAILED)` breaks out of the retry loop (`break` on success-or-node-FAILED), so only uncaught exceptions/timeouts retry. That is reasonable as-is, but it means nodes like `python_repl` (which wrap runtime exceptions into a FAILED result) never get engine retries even with `max_retries > 0` — inconsistent with what the retry config implies.

## Current behavior

- Steps API (`GET /api/runs/{id}` → `steps[]`): one entry per node, final attempt only
- Attempt evidence only in webserve.log warnings: `attempt=N/M`

## Suggested options

- Record attempts on the step (e.g. `step.attempt = attempt + 1`, plus optional `step.attempt_errors: []`), and/or
- Append one step entry per attempt (mirrors n8n), and/or
- At minimum, include an `attempts` counter in the run events stream (`NODE_START`/`NODE_END` already fire per attempt? — if not, fire per attempt) so SSE consumers can count retries

Also consider: a per-node opt-in flag `retry_on_business_failure` so node types that wrap runtime errors (python_repl) can participate in engine retries.
