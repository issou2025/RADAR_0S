# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Tekla 2026 grid still refused for level labels of three or more words (EL +99.350 BOB)**

*Project description:*
## What

The Tekla 2026 bridge maps a two-word grid label to one native token (`2nd Floor` → `2nd_Floor`, #428/#429) but still refuses the whole grid when any label has three or more words. Level labels such as `EL +99.350 BOB`, `EL +103.000 TOS` are the normal way detailers name levels, so a common grid lands with no grid at all.

Seen on 2026-11-07 (pawellisowski/floless.app#3272): FloLess 0.169.0, AWARE 0.174.0, Tekla Structures 2026.0. Exports → Send to a CAD app → Tekla, a 137-member model into an empty Tekla model. All 137 members were created; the grid came back as

```json
{"id":"grid:model","kind":"structural-grid","status":"unsupported","code":"tekla-grid-label-token-unsupported",
 "message":"Tekla native Grid requires each label to be one token; resolved Tekla 2026 additionally supports exactly two control-free tokens …"}
```

with every axis and level `unsupported-parent`.

## Cause

`TeklaGridEnvelopeContract.IsSupportedTwoTokenLabel` accepts exactly one ASCII space. The mapping itself (`Replace(' ', '_')`, collision-safe `~<pos>-<attempt>` retries, ≤ 40 UTF-16 units, transactional `tekla-grid-label-tokenized` warning carrying `{id, family, authoredLabel, nativeLabel}`) produces one whitespace-free token whatever the word count, the same native grammar class already proven live for `2nd_Floor`. The two-word limit was a conservative "live-proven authored grammar" boundary from the #429 plan, not a Tekla limit on the native token.

## Expected

On resolved Tekla 2026, accept any label of N ≥ 2 non-empty, control-free words separated by single ASCII spaces (still no leading/trailing/repeated/non-ASCII whitespace), map it with the same deterministic allocation, and list it in the `tekla-grid-label-tokenized` warning. `EL +99.350 BOB` → `EL_+99.350_BOB`. Blank labels, other whitespace and the 40-unit bound keep today's unsupported result. Prove it live on Tekla 2026 (parent read-back and child-plane label match, as #429 did) before release.

## Why here, not in FloLess

Tokenizing is Tekla-specific. FloLess's canonical labels go to IFC, Revit, Rhino and SketchUp too, so FloLess rewriting them would lose the authored name everywhere else, and it would duplicate the bridge's collision-safe allocation and its mapping record. FloLess (pawellisowski/floless.app#3272) now reads this refusal as a listed omission with the offending labels named, so the send no longer reads as unverified; this issue is what would let the grid actually arrive.

Cross-reference: #428, #429, pawellisowski/floless.app#3272.
