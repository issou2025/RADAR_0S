## Objective and coordination

Implement the shared-automation portion of PiesP/.github#1. Make TypeScript the primary language for maintained browser tooling without introducing another runtime, reducing the existing supported Node matrix, or giving shared automation consumer release/merge authority.

This issue owns `browser-core` changes and the reusable contract. Consumer-specific policy, build orchestration, and migrations belong to the companion issues linked from the tracker. Land shared changes first, validate one consumer, then roll out full immutable SHAs; do not require all consumers to change in the same PR.

## 1. Inventory, ownership, and runtime-specific checks

- [ ] Inventory public commands, private helpers, hooks, Action code, workflow inline logic, tests, and subprocess callers. Record each retained language/runtime and why it is needed. Keep a concise catalog in existing development/automation documentation rather than a new registry.
- [ ] Keep ordinary development tools in `scripts/` and distributable unprivileged automation in `automation/`; do not expose tooling through runtime package exports or create a new published package/task framework.
- [ ] Cover every Node-direct TypeScript implementation and its tests with the appropriate Node module-resolution/type-check configuration, including erasable-only syntax where required by the existing runtime execution contract. Preserve separate browser/bundler checking. Actual runtime execution does not replace type checking.
- [ ] Verify commands on the official manifest pin and the existing compatibility jobs. Do not assume features available on the official runtime also exist on every supported Node branch. Avoid adding `tsx`/`ts-node` or upgrading engines merely to simplify migration.
- [ ] Keep Git hooks as minimal adapters when necessary; move substantive policy into tested TypeScript. Preserve arguments, working-directory behavior, exit statuses, and hook opt-in behavior. Ordinary helper imports must not start processes or perform writes.

## 2. Preserve bootstrap ordering while minimizing JavaScript

- [ ] Draw the setup sequence explicitly: runner-provided Node -> runtime selection -> pinned Node/pnpm installation -> optional dependency installation -> consumer tool execution.
- [ ] Treat `resolve-runtime.mjs` as a pre-runtime exception unless execution on every actual bootstrap environment proves that conversion is safe. It cannot depend on the runtime it selects or installed project dependencies. Document the smallest supported bootstrap contract and a concrete review trigger.
- [ ] Convert other `.mjs` helpers to TypeScript only after their actual callers/runtime order are checked. In particular, verify where `consumer-impact` executes before renaming its file or changing its invocation. A bounded compatibility exception is preferable to increasing supported-runtime requirements.
- [ ] Retain `install-dependencies: 'false'` as the existing way to prepare Node/pnpm before dependency-free checks. Preserve exact manifest selection, numeric compatibility overrides, caching, locked installs, and the single runtime owner.
- [ ] Update Action metadata, documentation, test imports, and consumers of renamed CLIs together. Do not add an arbitrary executable-command, URL, path, ref, or secret input to make a helper reusable.

## 3. Extract and test security validation without moving trust

- [ ] Compare the inline OSV result validators with the three consumers' Python validators and write down their actual input/output and trust differences before choosing common code. Similar-looking code is not evidence of identical contracts.
- [ ] Put genuinely shared parsing/validation in a small unprivileged TypeScript module with explicit inputs. Keep scan selection, baseline/head authority, workflow permissions, and artifact policy in callers. Do not run PR-controlled helpers in a secret-bearing context.
- [ ] Establish positive and negative fixtures through the real CLI/wrapper before replacement: malformed/empty/truncated input, wrong roots and required structures, mixed valid/invalid data, and scanner failure. Preserve strict duplicate-key/non-finite-number rejection wherever the current caller requires it; plain last-key-wins parsing must not silently weaken a consumer contract.
- [ ] Preserve existing same-file protections, output cleanup/replacement behavior, failure propagation, and resource limits for callers that have them. A failed validation must not publish a success output or clean scan summary.
- [ ] Make the helper available from the correct independently pinned trusted source. Do not solve extraction by importing unchecked candidate artifacts or by adding project dependency installation to privileged jobs.
- [ ] Remove duplicated inline Python and its Python-only callers only after equivalence is established. If a safe, proportionate TypeScript replacement is not ready, document the exact temporary Python exception and keep that migration visibly incomplete rather than lowering validation.

## 4. Share only stable mechanics and tool metadata

- [ ] Consolidate repeated process execution, GitHub output handling, version/digest data reading, or downloader verification only when at least two real callers have matching contracts. Use small modules, not a generic workflow engine.
- [ ] Replace source/comment scraping of tool versions with one authoritative structured representation where needed. Keep existing manifest-owned pins authoritative, preserve the minimum release age and exact digest checks, and keep tool-specific policy in the appropriate owner.
- [ ] Keep consumer path-to-test policy local. Shared Git extraction may be reused, but must retain rename source/destination coverage, type changes, NUL-safe names, event-specific boundaries, and conservative unknown/error handling.
- [ ] Preserve consumer-impact semantics: unknown/unavailable/unrelated bases and source-reference ambiguity remain impactful; reviewed automation-only/development-only changes retain their intended behavior. Do not alter runtime notification routing just because a helper changes language.

## 5. Rollout and regression evidence

- [ ] Run focused unit/CLI/Action-contract tests, the applicable existing `pnpm verify`, and existing official/compatibility CI jobs. Include dependency-install-disabled setup and a clean bootstrap without `node_modules`.
- [ ] Verify no permission, secret, event, concurrency, required-check-name, trusted-base, or consumer publication policy changes are hidden in the refactor. Shared automation stays unprivileged.
- [ ] Validate one companion consumer against the new full 40-character automation SHA at that consumer's final source revision. Record old/new automation pins and rollback instructions. Do not automatically update runtime `packages/core` gitlinks when only automation changes.
- [ ] Supply the stable contract and validated pin to the other consumer issues. This issue owns core implementation and pilot evidence; the cross-project tracker owns completion of the remaining rollout.

## Definition of done

All audited surfaces have an implemented or justified-exception disposition; portable maintained logic is TypeScript; remaining pre-runtime/compatibility JavaScript is small and documented; shared validators have meaningful failure tests; runtime-appropriate checking and current compatibility coverage pass; and one consumer integration is verified. Record exact tested/landed commits, commands/results, language/runtime counts under the tracker method, and every blocked/not-run check. A required unexecuted integration check is not a pass.

No runtime-library redesign, new npm publication, dependency/toolchain upgrade, mass consumer rewrite, live settings change, release/tag/deployment, or scanner-status change is included. Do not remove safety checks or keep two handwritten implementations to claim completion.
