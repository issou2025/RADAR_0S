## User story

As a product repo owner, I want an approved-asset registry I can declare in DESIGN.md and a check that reads it, so that unapproved logos and product icons are caught the day I declare the registry, with no further triage.

## Background

IDN-1 and IDN-2 are L1 controls with no script and no detail files, and `validate.py:587` already grandfathers IDN-1 as "planned but unbuilt". Both relabel to `hybrid` and both build.

The registry they read does not exist anywhere: not in `.dx/design.json`, whose ten keys are `essence, colour, typography, tokens, tone, motion, layout_system, components, guardrails, overrides`; not in the DESIGN.md template; not in `standards/`; not as any allowlist file.

Rather than accept the gap, the check is built now and grades N/A until a product declares a registry. That is the honest-inert pattern CMP-1 already uses with `coverage: "complete"`. The gap closes the day someone declares one, with no further triage.

The registry's shape follows the precedent the existing keys already set: a `## Approved assets` section in DESIGN.md, projected to an `approved_assets` key in `.dx/design.json`, exactly how `layout_system` and `components` already work. `identity-scan.py` then reads it the way `component-manifest.py` reads `coverage`. One precedent note to carry forward: inertness cuts both ways in the triage. IDN-1 and IDN-2 build while LAY-1 accepts, both under an N/A-everywhere premise. What decides is cost and false-positive risk, not the N/A gate. `identity-scan.py` is small and clean and its gap self-closes on declaration; `layout-scan.py` would be roughly 200 new lines with a proven false-positive class. Cite cost, never the N/A gate alone, when using either call as precedent.

## Acceptance criteria

### A declared registry reaches the check

- **Given** a DESIGN.md carrying a `## Approved assets` section
- **When** `generate-design-json.py` runs and `checks/identity-scan.py` follows
- **Then** `.dx/design.json` carries an `approved_assets` key and the check reads the declared set from it, the way `component-manifest.py` reads `coverage`

### An unapproved logo asset is reported

- **Given** a declared registry, and a component named to match `*Logo*` or `*Lockup*` whose `src` or import path resolves outside the declared set
- **When** the check runs
- **Then** it reports `ERROR <file>:<line> [IDN-1]`

### The check is honestly inert before a registry exists

- **Given** a repo that declares no approved-asset registry
- **When** the check runs
- **Then** it grades N/A for IDN-1 and IDN-2, reports no findings, and does not report a pass either

### Legitimate icons and inline SVGs are never candidates

- **Given** a bare inline `<svg>` outside any `*Logo*` or `*Lockup*` component, and a `lucide-react` import
- **When** the check runs against a repo with a declared registry
- **Then** neither is reported, because IDN-1 never flags a bare inline SVG and IDN-2 is scoped to the product-icon family only

### The stale grandfather entry is removed

- **Given** `identity-scan.py` has shipped
- **When** `validate.py` runs
- **Then** IDN-1's `SKILL_WIRING_GRANDFATHERED` entry is gone and no check reports IDN-1 as planned but unbuilt

### 6. How CMP-1's honest-inert actually works in code, and where the spec sends you to the wrong file

With that straight, the mechanism being copied is `run_validate()` at `:203`: it reads `coverage` from the manifest with a `partial` default at `:224`, runs the import diff only when `coverage == "complete"` (`:227`), and otherwise `print`s a single `INFO <manifest path>: partial manifest (generated: <date>)` line at `:231` to `:233` saying the diff was not run, appends nothing to `errors`, and falls through to the silent exit 0 at `:479`. `checks/README.md:307` states the contract in prose. ### 7. ast-grep, with the rules measured on this machine

Spec section 10 commits every new rule to ast-grep, and spec section 12 moves the existing matching layer there too. `ast-grep 0.44.1` is installed at `/opt/homebrew/bin/ast-grep` and the harness declares it nowhere: `git grep ast-grep` over `plugins/dx-harness` on `main` returns nothing. **How the harness provisions it is #152's call, and this issue reuses whatever #152 lands.** Do not invent a second invocation path or a second provisioning story.

Three rule shapes were run against fixtures on this machine, so these are measurements and not predictions:

- The relational rule that expresses the whole inline-`<svg>` narrowing in one place works: `rule: {pattern: '<svg $$$A>$$$B</svg>', inside: {kind: function_declaration, stopBy: end, has: {field: name, regex: "Logo|Lockup"}}}` matched the `<svg>` inside `function SiteLogo()` and did **not** match the one inside `function Badge()` in the same file. `stopBy: end` is required to climb past the intervening JSX and return statements.
- Arrow-function components need a second variant: the same rule with `kind: variable_declarator` matched `export const BrandLockup = () => (<svg>...)` and skipped `export const Plain`. Two variants, not one.
- Import specifiers come back as metavariables: `ast-grep run -p 'import $A from "$P"' -l tsx --json` on a file importing both `lucide-react` and `@/assets/brand/tfx-lockup.svg` returned both with `$P` bound to the specifier, which is all the bare-specifier test in block 8 needs.

One negative measurement worth recording so nobody loses an hour to it: a bare attribute pattern (`-p 'src=$V'`) matches nothing, because a JSX attribute is not a valid standalone parse. Use a rule of `kind: jsx_attribute` with `regex: '^src='`, which was measured returning the one `src="/brand/other-logo.svg"` attribute in the fixture, or match the element (`<$T $$$A />`) and filter attributes in Python.

### 8. Judgment calls this issue has to make

**Proposed (not in the spec): keep the spec's registry shape, change only the value type.** Spec section 11 (lines 768 to 777) proposes the `## Approved assets` section in DESIGN.md projected to `approved_assets`, and explicitly says the implementation effort can adjust it, because nothing else depends on which shape wins. Keeping it, for four reasons the alternative fails:

1. An approved asset is a **path inside a product repo**. The per-product table shape TYP-1 uses (`standards/controls/typ-1.md:28`, verified: the `## Per-product registered brand wordmark` heading with its four-column table at `:30` to `:34`) works because a typeface name is a portfolio fact, resolvable without the product checked out. A file path is not. A harness-held table of product file paths goes stale the moment a product moves a file, and the harness cannot see the move.
2. Spec section 11's own CMP-9 ruling (lines 760 to 766) draws exactly this line: portfolio-wide library-name knowledge is harness-held, product-specific facts are not. Asset paths are product-specific.
3. `identity-scan.py` must read the target repo tree anyway to resolve `src` and import paths, so reading the declaration from the same tree costs nothing.
4. Measured in block 5: the DESIGN.md route already projects the right key. The generator edit is a declaration, not surgery.

**Proposed (not in the spec): an asset entry is a path and nothing else.** A repo-relative path, or a directory prefix if it ends in `/`. Rejected: a content hash (the harness installs nothing, DESIGN.md is hand-authored, and a hash turns a human file into a lockfile while making every legitimate re-encode of the same mark a finding); a display name (the check resolves paths, so a name is a second field synced to nothing); an allowed-usage field (that is the container-colour, gloss, and wordmark territory the spec keeps with the evaluator). Directory-prefix support is what lets one bullet mean "the family", which is precisely what IDN-2 needs.

**Proposed (not in the spec): the product-icon family is defined by path shape, not by a library denylist.** A reference is a candidate for IDN-2 only when its specifier is a **path into the repo**: it starts with `./`, `../`, `~/`, `@/`, or `/`. A **bare package specifier** (anything else, so `lucide-react`, `@radix-ui/react-icons`, `react-icons/fa`) is never a candidate, under any registry state. Note the one ambiguity: `@/` exactly, meaning `@` followed by `/`, is a path alias, while `@scope/name` is a package. Defining it this way satisfies the spec's "`lucide-react` imports are never candidates" **by construction**, with no list of icon libraries to maintain and no chance of the next icon library being missed.

**Proposed (not in the spec): three ways a candidate is admitted for IDN-1, only the first of which admits an inline `<svg>`.**

1. The enclosing component's identifier matches `*Logo*` or `*Lockup*`, case-insensitively (block 7's two rule variants). This is the only gate that admits an inline `<svg>`, per the spec's narrowing.
2. The file's basename matches `*logo*` or `*lockup*`, so `components/brand/logo.tsx` exporting a default `Logo` is caught. Same treatment as (1). This costs one string test and catches the most common real spelling.
3. An `src` string literal or import specifier whose resolved basename matches `*logo*` or `*lockup*`, or which sits under a declared `logo` prefix, **wherever it appears**. This catches `<Image src="/brand/tfx-lockup.svg">` inside a component named `SiteHeader`, which is the realistic miss if only (1) applies. It admits the reference, never an inline `<svg>`.

**Proposed (not in the spec): a known limitation, stated rather than hidden.** A product icon rendered from a generated TypeScript module holding path data (this repo's `@/components/ink-icons.generated`) has no asset path to resolve, so the static check cannot reach it and it stays with the evaluator. Say so in `standards/controls/idn-2.md`; do not paper over it with a heuristic.

### 10. Wiring, and why it is safe to wire immediately

Giving IDN-1 and IDN-2 `enforced: partial` plus `script: checks/identity-scan.py` makes them "claimed" for `[WIRING-SYNC]` (`validate.py:579` to `:610`), which then requires the script to actually run in `package.json` prebuild or `.github/workflows/ci.yml`, or to sit on `WIRING_EXEMPT` (`:572` to `:576`) with a documented reason. Separately, `validate.py:997` to `:1008` errors if a `script:` path does not exist on disk, so the catalogue edit and the new file must land in one commit.

The obvious move is to copy CMP-1 all the way and add a `WIRING_EXEMPT` entry, because CMP-1 has one: `validate.py:575` reads `"checks/component-manifest.py": "validates a product's .dx/component-manifest.json; this repo has none to validate"`. **Do not copy that part.** The reason CMP-1 needs the exemption is mechanical, not philosophical: `component-manifest.py` takes the manifest path as a **required positional argument**, prints usage and exits 1 with no arguments (`:465` to `:468`), and errors `file not found` and exits 1 when handed a path that is not there (`:205` to `:207`). Wiring it into prebuild on a repo with no manifest would fail the build. That is why it is exempt.

`identity-scan.py` has no such problem, because it takes source paths and looks the registry up for itself. On a repo with no registry it prints `INFO` and exits 0.

**Proposed (not in the spec): wire it into `check:python` (`package.json:10`) and the matching CI step, and add no `WIRING_EXEMPT` entry.** This repo declares no registry, so the check prints its `INFO` lines and exits 0 on every build, which exercises the inert path continuously and for free, and proves constraint 1 on every commit rather than in a test only. The exemption route instead buys a second written inertness claim that someone has to remember to delete later, which is the exact shape of problem this effort exists to remove. Two couplings if you disagree and take the exemption anyway: `validate.py:570` to `:571` requires `WIRING_EXEMPT` to stay in sync with the "Wiring status" prose at `checks/README.md:342`, so both move together; and the dead-exemption check (`:643` to `:655`) only catches an entry whose script has vanished or is claimed by no control, so an entry that stays technically accurate is never reported and nothing will ever prompt its removal.

`detect.py` registration is optional and separate: it is hook-only by design (`checks/README.md:38` to `:45`). If you register it, put it in the `--all` profile and report it skipped when no `approved_assets` key exists, mirroring how `component-manifest` is skipped when no manifest exists. Not in the curated hook profile: a check that grades N/A everywhere has nothing to say on a file edit.

## Data model

Three shapes: the section a person writes, the key a machine reads, and the N/A semantics that sit between them.

### 1. The `## Approved assets` section in DESIGN.md

An h2 heading, one guidance comment, one bullet per family. Exact markdown:

```markdown
## Approved assets
<!-- Cites: IDN-1 (logos and lockups), IDN-2 (the product-icon family).
     Machine-read by checks/identity-scan.py; keep the bullets exact.
     Paths are repo-relative. A path ending in / is a directory prefix and
     admits everything under it. Delete a bullet and that control grades
     N/A; delete the section and both do. -->
- logo: assets/brand/tfx-lockup.svg
- icons: assets/icons/product/
```

- The heading is exactly `## Approved assets`, sentence case, h2. `heading_to_key()` lower-cases before lookup, so `## Approved Assets` reaches the same key, but the template writes the sentence-case form.
- Two field keys, and only two: `logo` (IDN-1's declared set) and `icons` (IDN-2's product-icon family). One key per control is what lets one script grade two controls with two independent N/A gates.
- **Several assets in one family** use a JSON array literal, which `coerce_value()` (`:119`) already coerces to a list: `- logo: ["assets/brand/tfx-lockup.svg", "assets/brand/tfx-mark.svg"]`. Comma-separated bare strings are **not** supported; that would be a new convention and the array form already exists.
- `<!-- ... -->` comments never reach the projection (`strip_comments()` at `:105`), so the guidance above costs nothing downstream.

**Proposed (not in the spec): where the section goes in the template.** After `## Components` and before `## Guardrails`, so the machine-read sections (`Layout system`, `Components`, `Approved assets`) stay contiguous. Note that #148 proposes inserting `## Quality bar` after `## Voice & Tone`; the two placements do not collide, but the second issue to land still edits the same file.

### 2. The `approved_assets` key in `.dx/design.json`

Type: an object whose keys are family names and whose values are each **either a string or a list of strings**.

```json
{ "approved_assets": { "logo": "assets/brand/tfx-lockup.svg", "icons": "assets/icons/product/" } }
```

**Proposed (not in the spec): the check normalises a bare string to a one-element list; the generator is not changed to always emit arrays.** This is the one place this issue diverges from the shape the Design assets section above sketches, and it diverges because that sketch does not match the generator's measured behaviour: a `- logo: <path>` bullet projects as a string, not as a one-element array (block 5). Two ways to close the gap, and the string-tolerant reader is the better one:

- Force authors to write `- logo: ["assets/brand/tfx-lockup.svg"]` even for one asset. Correct, ugly, and it makes the common case the awkward case.
- Accept both and normalise in `identity-scan.py`. The generator stays untouched apart from the `SECTION_MAP` declaration, the one-asset bullet reads like every other DESIGN.md bullet, and the many-asset bullet uses a coercion that already exists.

Take the second. A value that is neither a string nor a list of strings (an integer, a nested object) is not a declaration: treat that family as undeclared, emit a `NOTE`, and grade it N/A.

Additive only: the existing ten keys and their types do not change, no new header key joins `generated_from`, `generated_at`, `catalog_version`, and `standards/schema.json` is untouched (it describes `catalog.yaml`, not `design.json`).

### 3. What one asset entry holds

One string. Either a repo-relative file path (`assets/brand/tfx-lockup.svg`), or a directory prefix ending in `/` (`assets/icons/product/`) that admits every file beneath it recursively. Nothing else: no hash, no display name, no allowed-usage field (block 8 gives the reasoning for each rejection).

A candidate matches an entry when its resolved repo-relative path equals a file entry, or begins with a directory entry. Path resolution is normalised (`./`, `../`, and the `~/` and `@/` aliases collapse to repo-relative) before comparison, and comparison is exact after normalisation, never a substring test.

### 4. N/A semantics, stated per control rather than per section

This is the honest-inert contract and it must not be collapsed to "the section is missing".

| State of `approved_assets` | IDN-1 | IDN-2 |
|---|---|---|
| key absent (no section, no DESIGN.md, or a comment-only section) | N/A | N/A |
| `{"logo": "..."}` | graded | N/A |
| `{"icons": "..."}` | N/A | graded |
| `{"logo": [...], "icons": "..."}` | graded | graded |
| `{"logo": []}` (an explicit empty array) | graded, empty set | N/A |
| a bare string (a prose-only section) | N/A plus a `NOTE` | N/A plus a `NOTE` |
| present but not an object (a list, a number) | N/A plus a `NOTE` | N/A plus a `NOTE` |

Two distinctions carry the weight:

- **Absent means N/A. Present-but-empty means graded with an empty declared set.** `- logo: []` is a declaration: it says this repo has no approved logo asset, so every candidate resolves outside the declared set and every candidate is a finding. It is not the inert case and must not be reported as one.
- **The gate is per control, not per section.** A repo may declare `logo` and not `icons`; IDN-1 then grades and IDN-2 stays N/A. Nothing about the section's presence is allowed to switch a control on when its own family is undeclared.

A comment-only section produces no key at all, because `section_value()` returns `None` after comment stripping (`:156` to `:171`), which `parse_sections()` then omits. That is the same as absent, deliberately.

## Error contract

Five outcomes. They are deliberately different channels and must not be collapsed into each other.

### 1. An unapproved asset: `ERROR`, exit 1

**ERROR, not NOTE.** IDN-1 and IDN-2 are `tier: L1` with `waiver: documented` (`catalog.yaml:959` and `:977`). L1 findings are meant to block: spec section 11 (line 740) states the L1 rule plainly, and `checks/README.md:147` states the portfolio behaviour. Emitting a NOTE would leave two L1 controls unenforceable while the catalogue claimed `enforced: partial`, which is precisely the "claims automated enforcement that no automation delivers" drift class `[WIRING-SYNC]` exists to catch (`validate.py:584` to `:586`). A NOTE here would replace one dishonesty with another.

Emit through `checklib.emit_error(rel, lineno, ctl, found, suggest)` (`checklib.py:109` to `:113`). Call the helper; do not format the string by hand, because `detect.py`'s `_FINDING_RE` (`detect.py:100` to `:103`) reverse-parses that exact shape and the two are documented as changing together. `found` names the unresolved path or the inline mark; `suggest` names the declared set the candidate failed against.

### 2. A claimed waiver: annotated, still `ERROR`, still exit 1

Both controls are L1, so an inline `dx-waive IDN-1` or `dx-waive IDN-2` comment **does not suppress the finding**. It downgrades the line to carry a `[waiver-claimed]` marker beside the control id and still exits 1, exactly as `token-audit.py` does for TOK and COL (`checks/README.md:147`; the marker regex pattern is `token-audit.py:134`). `_FINDING_RE`'s optional second bracket group already accommodates it. The scanner never silences an L1 violation; a human closes the loop in a decision record, which `waiver-reconcile.py` then reconciles (`checks/README.md:221` to `:228`).

Consequence worth stating in the detail file: an inline `<svg>` inside a `*Logo*`-named component in a repo with a declared `logo` set is a finding no waiver can silence. The remedy is to move the mark into an approved asset file and reference it. That is what "no inline redraws" means (`catalog.yaml:963`).

### 3. No registry declared: `INFO`, exit 0, and never a pass

The honest-inert outcome, copying `component-manifest.py:231` to `:233`. One line per control that is N/A, naming the control id and why, printed to stdout, appended to no error list, exit 0:

```
INFO identity-scan: no approved-asset registry declared (.dx/design.json has no approved_assets.logo); IDN-1 graded N/A, not passed
INFO identity-scan: no approved-asset registry declared (.dx/design.json has no approved_assets.icons); IDN-2 graded N/A, not passed
```

**Proposed (not in the spec): the exact wording, and that the line says "graded N/A, not passed" in so many words.** The spec fixes the behaviour, not the string. Saying it out loud is what makes the check honest instead of merely quiet: a silent exit 0 is indistinguishable from a clean pass, and CMP-1's precedent is a printed line for exactly that reason. It must not begin with `ERROR`, or `detect.py` will parse it as a finding.

### 4. A candidate that cannot be resolved: `NOTE`, exit 0

A dynamic `src={logoSrc}`, a template literal, or a specifier that resolves to nothing on disk, inside a candidate component in a repo that **has** declared a registry. Follow `contrast.py`'s established "unresolvable, never silent" channel (`contrast.py:23`, `checks/README.md:209`): a `NOTE` naming the file, the line, and the unresolved expression, and exit 0. It never passes silently and it never raises a false `ERROR`. This is the single largest false-positive class the check has, and the NOTE channel is where the portfolio already puts it.

### 5. A tool failure: `ERROR`, exit 1, never a silent skip

A missing or unrunnable ast-grep binary, or an ast-grep invocation that fails, is a tool failure and must be loud. Print one `ERROR` line naming what could not be run and exit 1. Do not exit 0: a static check that silently skips its own matching layer is worse than the "planned but unbuilt" state this issue removes, because it looks like a pass. The exact provisioning behaviour is #152's to define and this issue inherits it.

A missing or malformed `.dx/design.json` is **not** a tool failure: it means no registry, so outcome 3 applies. Read it with `detect.py:145` to `:162`'s discipline, where a missing file, unparseable JSON, a non-object document, or a wrong-typed key all yield "nothing declared" and never a crash.

## Hard constraints

1. **The check ships inert and must never fail a repo that has declared no registry.** No registry means N/A and exit 0, for both controls, always. This is the honest-inert pattern from spec section 14 (lines 900 to 902), and breaking it turns a ceiling-raising build into a portfolio-wide outage.
2. **N/A is reported, never implied.** An `INFO` line per N/A control, printed. A silent exit 0 is indistinguishable from a pass and is not acceptable output for this check.
3. **Never flag a bare inline `<svg>`.** An inline `<svg>` outside a `*Logo*` or `*Lockup*` name match is not a candidate in any registry state. Four files in this repo depend on it, including `components/foundations/brand-icon-set.tsx`.
4. **`lucide-react` and every other general icon library are never candidates.** Enforce it through the bare-package-specifier rule, not a maintained denylist.
5. **The container-colour, gloss, and wordmark clauses stay with the evaluator.** `catalog.yaml:984` and `:985` are IDN-2's judgment half. Do not attempt them statically and do not delete them from the control.
6. **Nothing is installed or configured in the target repo.** No ast-grep config, no rule file, no dependency entry, no lockfile change. Rules live in the harness. This is the defining constraint of a static check (spec section 14) and `detect.py` depends on it.
7. **Every rule rides ast-grep**, per spec sections 10 and 12, using whatever provisioning and invocation #152 lands. Do not add a second matching engine and do not fork the provisioning decision.
8. **No new control enters `catalog.yaml` through this issue.** IDN-1 and IDN-2 already exist. The permitted edits to them are `enforced:`, `script:`, `detail:`, and whatever `verify:` text #150 owns. No new id, no new `fails_when` clause.
9. **The catalogue edit and the script land together.** `validate.py:997` to `:1008` errors on a `script:` path that does not exist on disk, and `[WIRING-SYNC]` (`:579`) errors on a claimed script that runs nowhere. A split commit leaves `main` red.
10. **Do not delete IDN-1's `SKILL_WIRING_GRANDFATHERED` entry without naming IDN-1 in a skill or agent file in the same commit.** IDN-1 is currently named in none, so the deletion alone converts a suppressed orphan into a `[SKILL-SYNC]` error (`validate.py:716` to `:722`).
11. **An L1 waiver never silences.** `dx-waive IDN-1` or `dx-waive IDN-2` annotates the line and still exits 1 (`checks/README.md:147`, spec line 740). Do not add suppression.
12. **The existing ten `.dx/design.json` keys and their types do not change**, and `standards/schema.json` is not touched: it describes `catalog.yaml`, not `design.json`. In particular, do not introduce a `coverage` field into the catalogue in an attempt to follow the spec's wording literally; that field belongs to the product's `.dx/component-manifest.json` and appears nowhere in `catalog.yaml` or `schema.json` today (Technical context, block 6).
13. **The quality bar never blocks and its anchors never become findings.** `approved_assets` and `quality_bar` are two unrelated declarations that happen to share a file and a generator; do not let this check read, grade, or fail on anything belonging to the quality bar.
14. **When citing this issue as precedent, cite cost, never the N/A gate alone** (spec lines 650 to 654). LAY-1 is accepted under the same N/A-everywhere premise, and the distinction is script size and false-positive risk.
