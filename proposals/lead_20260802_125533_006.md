# Project Proposal — Autocad Drafting

## Project Understanding
You need assistance with: 
**[Epic]: RPC streaming — genuine incremental delivery, honest error contract, composable stream links**

*Project description:*
### Executive Summary

We want RPC streaming (`@procedure ... -> T[]`, `stream()` on the generated client) to actually deliver items incrementally, with mid-stream failures signaled honestly and observable through the same composable-link mechanism every other call kind already has, because today "streaming" is a wire-format-compatible illusion — the entire response is buffered server-side before the first byte is sent, no mid-stream error signal exists at all, and `stream()` bypasses the client's `RpcLink` chain entirely so logging/retry/auth-refresh links are silently inert for it. This epic exists to solve the gap between what the framework's own docs claim ("streaming... shipped... no code change needed") and what the code actually does.

### Strategic Intent

The intent of this epic is to make RPC streaming genuinely incremental end-to-end — server production to client consumption — with an honestly-specified, implementable mid-stream error contract, and full participation in the client link chain, instead of the current buffered-but-labeled-streaming state.

### Problem Statement

- **Users get no early data.** A `@procedure foo() -> Bar[]` today produces the entire result set server-side before any bytes reach the client, identical in effect to a plain unary call — the `stream()` API promises something the implementation doesn't deliver, which is misleading and, for genuinely large or slow-to-produce result sets, defeats the actual point of choosing a streaming API.
- **No mid-stream failure signal exists, and the documented one can't work.** `docs/design/rpc-transport.md` describes a "trailing content-type chunk" that isn't realizable over HTTP, and the alternative (an HTTP trailer) is invisible to browser `fetch()` entirely — so even after fixing incremental delivery, there was no correct spec to implement against until this epic's first ticket.
- **Streaming calls are invisible to the link chain.** Every configured `RpcLink` (logging, batching, validation, retry, auth-refresh) silently does nothing for `stream()` calls — a user who wires up observability and then calls a streaming procedure gets no logs and no explanation why not.
- **Impact:** developers building on streaming procedures get worse behavior than they're told to expect (no incrementality, no error visibility mid-stream, no observability) — a correctness and DX gap that specifically undermines trust in a framework whose other guarantees (schema-first types, generated clients, deterministic wire contracts) are otherwise taken seriously.

### Desired Outcome

- A `@stream`-marked procedure delivers items to the client as they're produced, provably (timing-based test against the real generated server, not a hand-rolled fixture).
- A mid-stream failure is signaled via a correctly-specified, implementable in-band mechanism and surfaces to the client as a real error, not a truncated/ambiguous stream.
- `stream()` runs through a composable `RpcStreamLink` chain, so existing link authors (logging, batching, retry) can support streaming calls the same way they already support unary/batch ones.
- The documentation accurately reflects what the code does, closing the "shipped, no code change needed" inaccuracy this epic's scoping uncovered.

### Scope (In / Out)

### In Scope
- Correcting the mid-stream error wire-format spec in `rpc-transport.md`/`streaming-rpc-links.md` (#281).
- A `@stream` schema directive + stream-shaped `ProcedureRegistry` trait method, non-breaking for existing non-`@stream` procedures (#282).
- Genuinely incremental `cratestack-axum` sequence-response encoding via `Body::from_stream`, plus fixing `IdempotencyService`'s response-buffering conflict with streaming (#283).
- A TypeScript `RpcStreamLink` chain (`streamLinks` option, `createLoggerStreamLink` reference implementation) and a hand-rolled CBOR-seq boundary-scanner client-side decoder, ported from the existing Rust client's algorithm (#277).

### Out of Scope
- WebSocket subscriptions (`@@subscribe`) — separate, pre-existing, unrelated roadmap item (epic #207, ticket #183).
- Dart/Flutter client changes to match the new server wire behavior — filed separately if needed once #283 lands, not blocking this epic.
- `OpExecutor` consolidation (idempotency/ratelimit/audit unification) — explicitly deferred elsewhere pending WS/subscriptions, per `rpc-transport.md` §4; not touched by this epic.
- REST/gRPC-Web streaming parity.

### Key Assumptions

- The chosen CBOR tag number for the error sentinel (finalized in #281) will not collide with a future IANA-assigned tag — validated against the registry before merge, not assumed.
- `axum`/`hyper`'s current versions (0.8.9 / 1.10.1, confirmed) support everything needed for `Body::from_stream` with proper cancellation semantics on client disconnect — needs verification under load in #283, not just a happy-path test.
- No existing production consumer depends on today's buffered-but-labeled-streaming behavior in a way that a genuinely incremental response would break (e.g. assuming the whole body arrives in one read). Flagged as a risk, not fully validated — check before #283 ships.

### Constraints

- **Breaking-change surface must stay minimal.** #282's trait-signature change must not alter behavior for any procedure not explicitly marked `@stream`.
- **Browser `fetch()` compatibility is non-negotiable** for the client half (#277) — this is exactly what ruled out the HTTP-trailer error mechanism in #281.
- Each ticket ships as its own reviewable PR, in dependency order (#281 → #282 → #283 → #277) — no ticket starts implementation before its blocking predecessor merges, given how expensive a wrong wire-format decision would be to unwind after client and server both implement against it.

### Risks

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| Wrong CBOR tag choice collides with a future IANA assignment | Low | Medium (wire-format break) | Validate against the registry in #281 before any implementation starts |
| `Body::from_stream` cancellation doesn't actually stop server-side item production on client disconnect | Medium | High (resource leak under load) | Dedicated test in #283, treated as a primary acceptance criterion, not an afterthought |
| `IdempotencyService`'s streaming conflict is discovered to need more than a bypass (e.g. a product requirement for idempotent streams) | Low | Medium (scope growth in #283) | #283 explicitly picks and documents one approach rather than deferring the decision |
| CBOR boundary-scanner ported to TypeScript has a subtle correctness bug (indefinite-length items, tag edge cases) | Medium | High (silent data corruption, not a loud failure) | #277 tests against real Rust-encoder-produced fixtures, not hand-constructed bytes |
