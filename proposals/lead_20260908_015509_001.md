# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**"Attempted to write protected memory" in RevitSessionSetup: Test Explorer re-injects per session, and the Revit parallel limit is never applied**

*Project description:*
**Package:** Nice3point.TUnit.Revit 2026.1.1 (TUnit 1.44). The engine code paths below were also checked in the versions `main` pins (TUnit 1.65.68, Microsoft.Testing.Platform 2.3.3).
**Revit:** 2026, Windows 11, .NET 8, Visual Studio 2022 with *Use testing platform server mode*.

## Summary

`BeforeTestSession hook failed: Attempted to write protected memory.` (as in #103) is not a diagnosis. `Injector.InjectApplication` wraps the whole core load in a catch-all that rethrows every exception except `FileNotFoundException` as an `InvalidOperationException` with that fixed text. Subscribing to `AppDomain.FirstChanceException` around the call shows what is actually thrown. Two independent problems came out of that; the first produces the message, the second is silent.

### 1. Visual Studio Test Explorer runs many test sessions in one process

Test Explorer in server mode keeps the test host process alive between clicks and sends a new `testing/runTests` request for every run. Microsoft.Testing.Platform mints a new `SessionUid` per request (`PerRequestTestSessionContext`), and TUnit keeps one `TUnitServiceProvider` per session uid, so every run executes the `Before(TestSession)` / `After(TestSession)` pair again. `RevitApiTest` injects in the first and ejects in the second. Revit's core cannot be loaded into a process twice: the second `RevitSessionSetup` throws whether or not the first session ejected. So the first run in a fresh host passes and every later one fails.

**Reproduction without Visual Studio** (attached `mtp-client.ps1`, a minimal JSON-RPC client that does what Test Explorer does: `initialize`, `testing/discoverTests`, then N `testing/runTests` in the same process):

```
.\mtp-client.ps1 -Exe .\bin\Release.R26\MyTests.exe -Runs 2
run 1 finished in 16s : passed=1
run 2 finished in 0s  : error=1
[Setup Failure] BeforeTestSession hook failed: Attempted to write protected memory.
```

### 2. The parallel limit is never applied

`RevitThreadExecutor.OnTestRegistered` sets `RevitCountParallelLimit`, but TUnit's `TestExecutorAttribute<T>.OnTestRegistered` only calls `SetTestExecutor` / `SetHookExecutor`; it does not forward `ITestRegisteredEventReceiver` to the executor it creates, and the engine only collects event receivers from attributes, arguments and the class instance (checked in TUnit 1.44 and 1.65.68). `TestContext.Current.Parallelism.Limiter` is `null` for every Revit test. All tests are scheduled at once, marshal onto the one Revit thread, and interleave at every `await`; in my suite one test observed another test's elements because their `TransactionGroup`s nested.

## Proposed fix

PR to follow:

- inject once per process and eject once when the test application finishes, through an `ITestHostApplicationLifetime` that the package registers via a `build/*.props` `TestingPlatformBuilderHook` item, the same way TUnit.Engine registers its own hook. `AfterRunAsync` runs after the last session in both the console host and the server host, and it is the last point where the dispatcher on the Revit thread still accepts work: `AppDomain.ProcessExit` is too late (the WPF dispatcher aborts queued work once runtime shutdown has started), ejecting from another thread throws, and not ejecting stalls the host in Revit's native teardown;
- `[ParallelLimiter<RevitCountParallelLimit>]` on `RevitApplicationTest`, inherited by every Revit test. TUnit's generator copies the attribute onto each derived test class, and the engine keys limiter semaphores by type, so one limit covers all Revit tests.

Until the injector exposes the real exception, I would also suggest wrapping the inner exception instead of replacing it: the fixed message cost this investigation most of its time.
