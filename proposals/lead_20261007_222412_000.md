# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**IFC4X3: IfcSurfaceCurveSweptAreaSolid gets no geometry when StartParam/EndParam are written as IFCPARAMETERVALUE(...)**

*Project description:*
## What happened?

In IFC4X3, `StartParam` and `EndParam` moved up to `IfcDirectrixCurveSweptAreaSolid` and their type changed from `IfcParameterValue` to the select `IfcCurveMeasureSelect`. Files therefore write them as typed values, for example `IFCPARAMETERVALUE(0.)`, where IFC4 files wrote `0.`.

For an `IfcSurfaceCurveSweptAreaSolid` written that way, web-ifc returns no geometry and logs:

```
[WEB-IFC][error][GetRefArgument()] unexpected token type, expected REF 42
```

The same solid with plain numbers (the IFC4 form) is tessellated. I would expect the IFC4X3 file to give the same geometry as the IFC4 one.

Two small hand-written files (47 lines each, no third-party data) and the probe are included at the end of this issue. They are identical except for `FILE_SCHEMA` and these two arguments:

```
IFC4:   #42=IFCSURFACECURVESWEPTAREASOLID(#32,#13,#52,0.,1.5707963267949,#40);
IFC4X3: #42=IFCSURFACECURVESWEPTAREASOLID(#32,#13,#52,IFCPARAMETERVALUE(0.),IFCPARAMETERVALUE(1.5707963267949),#40);
```

The directrix and reference surface follow what the Revit exporter writes: an `IfcTrimmedCurve` on a 2D `IfcCircle`, and an `IfcSurfaceOfLinearExtrusion` of that curve.

Both files pass IfcOpenShell 0.8.5 validation (schema and where rules, no issues), and IfcOpenShell tessellates both.

| | IFC4 file | IFC4X3 file |
|---|---|---|
| web-ifc 0.0.77 | 88 triangles | 0, `expected REF 0` |
| web-ifc 0.0.78 | 92 triangles | 0, `expected REF 42` |
| IfcOpenShell 0.8.5 | 292 triangles | 292 triangles |

(`node probe.mjs surface_curve_swept_ifc4.ifc surface_curve_swept_ifc4x3.ifc`, default settings.)

**Where it might come from.** I have not built web-ifc to confirm this, so please take it as a guess. In `IfcGeometryProcessor.cpp` (case `IFCSURFACECURVESWEPTAREASOLID`, around lines 1031-1043 at 40fad28), `StartParam` and `EndParam` are read only when the next token is `REAL`. A typed value starts with a label token, which `GetTokenType()` consumes without stepping back, so the following `GetRefArgument()` for the reference surface lands on the wrong token. If that is right, the fix would need to accept the typed form. Since `IfcCurveMeasureSelect` is `IfcLengthMeasure` or `IfcParameterValue`, a file could also write `IFCLENGTHMEASURE(...)` there. I have not seen that in the wild, though.

**Effect on a real file.** In the Autodesk "Snowdon Towers Sample Architectural" exported from Revit as IFC4X3_ADD2, 12 elements get no geometry for this reason:

- 4 `IfcLightFixture` wall sconces, which reach the solid through an `IfcMappedItem`;
- 8 `IfcBuildingElementProxy` bleacher slab edges.

In a copy of that file I replaced only the typed parameters of the 18 `IfcSurfaceCurveSweptAreaSolid` instances with plain numbers. All 12 elements then come back, with non-zero area: 6204 elements with geometry before, 6216 after, through `@thatopen/fragments` 3.4.8 with its default settings (with web-ifc 0.0.77 and 0.0.78). IfcOpenShell 0.8.5 produces geometry for all 12.

Earlier this year we also had round duct fittings missing in a Revit IFC4X3 HVAC export, with the same `expected REF 0` message. I no longer have that file, so I cannot confirm it is the same entity, but it looks likely.

**One question, separate from the bug.** With the IFC4 file, the swept profile comes out turned 90 degrees compared with IfcOpenShell. The 0.2 m side of the 0.2 x 0.1 rectangle is vertical in web-ifc and horizontal in IfcOpenShell:

| | x | y | z |
|---|---|---|---|
| web-ifc 0.0.78 | -0.001 .. 2.05 | -0.001 .. 2.05 | -0.1 .. 0.1 |
| IfcOpenShell 0.8.5 | 0 .. 2.1 | 0 .. 2.1 | -0.05 .. 0.05 |

The handler has a `TODO: the plane is not being used now`, so I suspect this is a known limitation and not a new bug. Is that right?

```js
// Probe for the web-ifc reports in this folder.
//
//   npm i web-ifc@0.0.78        (or 0.0.77)
//   node probe.mjs surface_curve_swept_ifc4.ifc surface_curve_swept_ifc4x3.ifc
//
// Prints, per file, the triangles web-ifc returns for the proxy #46 and the
// error lines it logs.

import fs from 'node:fs'
import path from 'node:path'
import * as WebIFC from 'web-ifc'

const errors = []
for (const k of ['log', 'warn', 'error']) {
  console[k] = (...a) => {
    const s = a.join(' ')
    if (s.includes('[error]')) errors.push(s.slice(0, 160))
  }
}

const api = new WebIFC.IfcAPI()
api.SetWasmPath(path.join(process.cwd(), 'node_modules', 'web-ifc') + path.sep, true)
await api.Init()

for (const file of process.argv.slice(2)) {
  errors.length = 0
  const modelID = api.OpenModel(new Uint8Array(fs.readFileSync(file)))
  const mesh = api.GetFlatMesh(modelID, 46)
  let triangles = 0
  for (let i = 0; i < mesh.geometries.size(); i++) {
    triangles += api.GetGeometry(modelID, mesh.geometries.get(i).geometryExpressID).GetIndexDataSize() / 3
  }
  api.CloseModel(modelID)
  process.stdout.write(`${file}: ${triangles} triangles${errors.length ? `; ${[...new Set(errors)].join(' | ')}` : ''}\n`)
}
process.exit(0)
```
