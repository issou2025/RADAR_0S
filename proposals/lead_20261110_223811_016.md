# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[security] Release pipeline: `v*` tags are unprotected and release.yml publishes :latest / GH Packages / npm from any branch or commit**

*Project description:*
**Saiku version:** `development` @ `39c00634f` (origin/development, 2026-11-10)
**How are you running Saiku?** Built from source — applies to the launcher JAR, the Docker image (`ghcr.io/spiculedata/saiku`) and WAR deployments; see *Impact* for per-mode notes.
**Environment:** GitHub Actions on `spiculedata/saiku`; repository settings as reported by the review on 2026-11-10 (re-confirmed read-only via `gh api` while drafting this issue). Not a runtime finding — nothing here depends on JDK, browser or datasource.

## Severity

**MEDIUM** — any repository collaborator with push access (or anyone holding a collaborator's token, PAT or a compromised dev machine) can publish a release of arbitrary content under Saiku's name: the `ghcr.io/spiculedata/saiku:latest` and semver image tags, the module jars on GitHub Packages, the `@concepttocloud/saiku-embed*` npm packages, and (on the tag path) a public GitHub release with JAR/dist assets. Every artifact gets a *truthful* Sigstore/SLSA attestation (#1992) that says "built by `release.yml`", so provenance verification does not catch it — the attestation records the ref the attacker chose. It is not HIGH because it needs an account that already has write access (no outsider path), and the merge queue / required `ci` check still protect `development` and `main` themselves. It is not LOW because the blast radius is every downstream consumer of `:latest`, and nothing in the repo (no tag ruleset, no environment, no ancestry check in the workflow) makes the release path distinguishable from a normal push. CWE-284 (Improper Access Control), CWE-829 (Inclusion of Functionality from Untrusted Control Sphere) for the dispatch-from-branch path.

## Description

`release.yml` is the single publishing path for every Saiku artifact (docs/releasing.md:10-17). It is meant to run only for a release cut by the Gitflow process in `.agents/skills/cut-release/SKILL.md`: version bump on `development`, `release/X.Y.Z` branch, PR to `main`, then a `v*` tag on the merged `main` HEAD. The workflow, however, has no idea any of that happened. It trusts two things only:

1. **The `v*` tag push.** There is no ruleset or protection on tags. The API lists exactly one ruleset for the repository, `development merge queue` (target `branch`), and no tag-targeted ruleset; `gh api repos/spiculedata/saiku/branches/main/protection` shows `required_pull_request_reviews: null`, `enforce_admins.enabled: false`, `restrictions: null` and only the `ci` status check; `development` is the same except `enforce_admins.enabled: true`. Any collaborator can therefore `git push origin v4.99.0` pointing at **any commit at all** — a feature branch, a dangling commit, a rewritten history — and the `push` trigger fires with full repository secrets.
2. **The `workflow_dispatch` `tag` input.** `Resolve version` (release.yml:88-100) regex-validates `INPUT_TAG` and then uses the string purely for *naming* (`jar_name`, `dist_name`, image tags). The checkout at :42 uses the branch the operator picked in the "Run workflow" dialog. Nothing checks that the named tag exists, that it points at the checked-out commit, or that the commit is on `main`. A dispatch of `tag=v4.99.0` from `feature/anything` builds `feature/anything`, pushes it to GHCR as `4.99.0`, `4.99` **and `latest`** (release.yml:343-345), runs `mvn deploy` to GitHub Packages at whatever `<version>` the branch's POM declares (:271-293), and publishes the embed npm packages at whatever version `saiku-ui/package.json` declares (:508, :576). Only the GitHub release page itself (`release` job, :381) and the docs PR (`docs-changelog`, :635) are skipped.

Because #1992 added keyless attestations, both paths produce provenance that is *correct* — it faithfully records `refs/heads/feature/anything` or `refs/tags/v4.99.0` as the source. The documented consumer check (docs/releasing.md:140-147) pins `--signer-workflow .../release.yml` and `--source-ref refs/tags/v<version>`; a maliciously pushed tag passes both. Signing does not substitute for controlling *what may be signed*.

There is also no GitHub environment on the publish jobs (`gh api repos/spiculedata/saiku/environments` returns none), so there is no required-reviewer gate and no secret scoping between "build" and "publish" beyond the job-level `permissions:` blocks.

## Steps to reproduce

**Preconditions:** an account with `write` (collaborator) on `spiculedata/saiku`, or its token. No admin needed. Nothing has to be merged.

**Path A — tag push from an arbitrary commit (publishes everything, including the GitHub release page):**

1. ```bash
   git clone git@github.com:spiculedata/saiku.git && cd saiku
   git checkout -b evil origin/development
   # any change at all, e.g. a one-line backdoor in saiku-launcher or the Dockerfile
   git commit -s -am "#0 - totally legitimate"
   # Do NOT push the branch. Tag the dangling commit and push only the tag:
   git tag v4.99.0
   git push origin v4.99.0
   ```
2. Observe `release.yml` run on `refs/tags/v4.99.0`. The `jar`, `deploy-packages`, `docker`, `release`, `npm-embed-build`, `npm-embed-publish` and `docs-changelog` jobs all run.
3. `docker pull ghcr.io/spiculedata/saiku:latest` now returns the attacker's image; `gh attestation verify oci://ghcr.io/spiculedata/saiku:4.99.0 --repo spiculedata/saiku --signer-workflow spiculedata/saiku/.github/workflows/release.yml --source-ref refs/tags/v4.99.0` **passes**.

**Path B — `workflow_dispatch` from a feature branch (publishes images + GH Packages + npm; skips only the release page):**

1. Push any branch: `git push origin evil`.
2. ```bash
   gh workflow run release.yml --ref evil -f tag=v4.99.0
   ```
3. Observe: `docker` pushes `ghcr.io/spiculedata/saiku:4.99.0`, `:4.99` and `:latest` from the `evil` tree; `deploy-packages` runs `mvn deploy` for every reactor module at the branch's POM version (overwriting nothing only if the version is new — GitHub Packages otherwise rejects, but an attacker simply bumps the POM); `npm-embed-publish` publishes `@concepttocloud/saiku-embed@<branch version>` if that version is not yet on the registry.

## Expected behaviour

- A `v*` tag can only be created by a maintainer (or only by the release automation), and only on a commit that is already on `main`.
- `release.yml` refuses to publish anything unless the commit it is building is the one the tag points at **and** that commit is an ancestor of `main`.
- `workflow_dispatch` is a re-run/repair path for an existing tag, not an alternative way to mint a release from any branch.
- The jobs that hold publishing credentials (`packages: write`, `NPM_TOKEN`, `contents: write` for the release, `id-token: write`) run inside a protected GitHub environment with required reviewers, so a second human must approve before anything leaves the runner.
- `main` requires a PR review and `enforce_admins` is on, so the "commit on `main`" precondition is itself meaningful.

## Actual behaviour

- Any collaborator can push `v*` tags to any commit; no ruleset exists for tags.
- `workflow_dispatch` builds the selected branch HEAD, validates only the *format* of the `tag` input, and publishes `:latest`, semver image tags, GitHub Packages jars and the npm embed packages from it.
- No GitHub environment exists; no human approval sits between "workflow started" and "artifact public".
- Provenance attestations are generated for whatever was published and verify successfully against the documented commands.
- `main` has no required reviews and `enforce_admins=false`; `development` has no required reviews.

## Impact

Who: every consumer of Saiku's published artifacts, and Saiku's own demo/preview infrastructure that pulls from GHCR. A single compromised collaborator credential (phished PAT, leaked `gh` auth, malicious IDE extension on a maintainer laptop) is enough — no code review, no merge.

Per published artifact / deployment mode:
- **`ghcr.io/spiculedata/saiku` image** (Docker users, `docker run ghcr.io/spiculedata/saiku:latest`): **affected on both paths.** `:latest` and the semver tags are overwritten with attacker content; `docker pull` on any host tracking `:latest` picks it up. The demo path (`promote-green.yml`, `:development-green`) is *not* touched by `release.yml`, so demo.saiku.bi is unaffected unless the attacker chose to also push to `development`.
- **GitHub Packages Maven artifacts** (`maven.pkg.github.com/spiculedata/saiku`, consumed by saiku-cloud and embedders via `<dependency>`): **affected on both paths.** A new version appears with a valid-looking publisher; a downstream `mvn` bump to it pulls attacker jars.
- **npm `@concepttocloud/saiku-embed` / `saiku-embed-react`**: **affected on both paths** whenever the branch's `saiku-ui/package.json` version is not already on the registry (the publish job's `npm view` idempotency check, release.yml:612-616). Published with `--provenance`, so npm's UI shows a green provenance badge pointing at the attacker's run.
- **GitHub release assets** (`saiku-<v>.jar`, `saiku-dist-<v>.zip`, SBOMs, `SHA256SUMS`): **affected on the tag path only** (release job is `push`-only). Launcher-JAR and WAR users who download from the Releases page get the attacker build with matching checksums and valid attestations.
- **Preview hosts** (`preview-env.yml` / `/preview`): not affected — they pull per-PR `pr-<n>` / `sha-*` tags from `docker.yml`, never `:latest`.
- **Launcher JAR / WAR / Embedded in saiku-cloud:** consumers of the above; the finding is about how the artifacts are produced, so the mode only determines which of the artifacts above you consume.

Containment that *does* exist today: `development` and `main` cannot be pushed to directly (required `ci` check, merge queue), so the attacker's code never has to be on a protected branch — which is precisely the gap.

## Suggested fix

Layered; do all of 1–4, 5 is strongly recommended.

**1. Tag ruleset (repository Settings → Rules → Rulesets → New tag ruleset).**
- Target: tags, pattern `v*` (include `refs/tags/v*`).
- Rules: *Restrict creations*, *Restrict updates*, *Restrict deletions*. Bypass list: the Repository admin role only (or a dedicated release GitHub App if you move tagging into automation). Collaborators with `write` can then no longer push `v*` tags. Equivalent API call, for the record:
  ```bash
  gh api -X POST repos/spiculedata/saiku/rulesets --input - <<'JSON'
  {"name":"release tags","target":"tag","enforcement":"active",
   "conditions":{"ref_name":{"include":["refs/tags/v*"],"exclude":[]}},
   "rules":[{"type":"creation"},{"type":"update"},{"type":"deletion"}],
   "bypass_actors":[{"actor_id":5,"actor_type":"RepositoryRole","bypass_mode":"always"}]}
  JSON
  ```
  (`actor_id: 5` is the built-in *Admin* repository role; adjust if you want *Maintain*.)

**2. Make `release.yml` verify the ref it builds, on both triggers.** Replace the bare checkout in the `jar` job and extend `Resolve version`:
```yaml
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          # Always build the TAG, never "whatever branch the dispatcher picked".
          ref: ${{ github.event_name == 'workflow_dispatch' && format('refs/tags/{0}', inputs.tag) || github.ref }}
          fetch-depth: 0   # needed for the ancestry check below

      - name: Resolve version
        id: meta
        env:
          EVENT_NAME: ${{ github.event_name }}
          INPUT_TAG: ${{ github.event.inputs.tag }}
        run: |
          set -euo pipefail
          ... (existing shape validation) ...
          # The tag must exist, must be what we checked out, and must be on main.
          TAG_SHA="$(git rev-parse --verify "refs/tags/${REF_TAG}^{commit}")"
          HEAD_SHA="$(git rev-parse HEAD)"
          if [ "$TAG_SHA" != "$HEAD_SHA" ]; then
            echo "::error::checked-out commit $HEAD_SHA is not ${REF_TAG} ($TAG_SHA)"; exit 1
          fi
          git fetch --no-tags origin main:refs/remotes/origin/main
          if ! git merge-base --is-ancestor "$TAG_SHA" origin/main; then
            echo "::error::${REF_TAG} ($TAG_SHA) is not reachable from main — refusing to release"; exit 1
          fi
```
Carry the same `ref:` into the `docker` (:305) and `npm-embed-build` (:514) checkouts — or better, have them depend on `needs.jar.outputs.ref_tag` and check out `refs/tags/${{ needs.jar.outputs.ref_tag }}` so all three jobs provably build the same commit. Also consider dropping `type=raw,value=latest` for pre-release tags (`v4.99.0-rc1` currently matches the regex and would move `:latest`).

**3. Put the publishing jobs behind a protected environment.** Create environment `release` (Settings → Environments) with *Required reviewers* (two maintainers), *Prevent self-review*, and deployment branches/tags limited to `v*` tags. Then on `deploy-packages`, `docker`, `release` and `npm-embed-publish`:
```yaml
    environment: release
```
Move `NPM_TOKEN` and `DOCS_SITE_PAT` from repository secrets into that environment's secrets so they are not even *available* outside it. The `jar` and `npm-embed-build` jobs (untrusted lifecycle) stay environment-less and credential-less, as #1993/#1992 already intended.

**4. Branch protection on `main` and `development`** (Settings → Branches, or convert to rulesets):
- `main`: require a pull request with ≥1 approving review, dismiss stale approvals, **enable "Do not allow bypassing the above settings"** (`enforce_admins`), keep the `ci` required check and `strict: true` (up-to-date branch).
- `development`: require ≥1 approving review (the merge queue already re-runs `ci`; this closes the "a collaborator merges their own PR" path noted in release.yml:115-118's own comment about v4.5.1).

**5. Optional, stronger: tag from automation only.** Have a `cut-release` workflow (dispatch, environment-gated) create the tag via the API from `main`'s HEAD, and give *only* that workflow's App identity bypass on the tag ruleset. Humans then never push tags at all, and `.agents/skills/cut-release/SKILL.md` step 5 becomes "dispatch the workflow".

Document the new rules in `docs/releasing.md` (operator section) and update `.agents/skills/cut-release/SKILL.md:19-23`.

## Acceptance criteria

- [ ] A collaborator with `write` but not `admin` gets `! [remote rejected] v9.9.9 (refusing to create tag: ...)` when pushing a `v*` tag (tag ruleset active, verified with a non-admin test account).
