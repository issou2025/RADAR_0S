# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**fix(reply)!: let a note applied with nothing driving be withdrawn**

*Project description:*
## What

Make a manager note sent to a run nothing is driving withdrawable by the receipt the engine returned, just like a note sent to a driven run.

**The invariant.** Every note the engine accepts is named by a durable envelope id and its index, and the sender learns that id from the receipt. That holds whether the run's driver applied the envelope or the reply applied it directly. A carried note not yet composed into a dispatch can be withdrawn by that name.

### Where it breaks today (onepipeline `origin/main` `25448122`)

- **The direct-apply path never numbers the envelope.**
  - `reply` in `src/driver.rs:4486-4697` gets `Accepted::NothingIsDriving(lock)` from `engine::accept` (`src/engine.rs:1431`). With nothing claimed and unanswered (`:4510`), it applies the edit itself and never calls `channel.submit`.
  - It journals the operations at `:4622-4636` through `engine::commits_of` (`src/engine.rs:6256`). The note record is built by `note_record` (`src/engine.rs:8061-8079`) with `envelope: None, index: None`.
  - The queued path stamps identity with `from_envelope` (`src/engine.rs:5793-5813`). The direct path skips it.
- **The receipt has no id to give.** The result is `Submitted::AppliedHere` (`src/driver.rs:4052`, `:4695`), mapped to `ReplyOutcome::AppliedHere { verdict }` (`src/verbs.rs:910`). `Receipt::reply()` answers `0` for it (`src/verbs.rs:965`).
- **Withdrawal cannot find the note.**
  - `withdrawal::validate` (`src/withdrawal.rs:61-64`) finds an envelope only through `ChannelState::commands_of` (`src/channel.rs:2433`), so it refuses with "the run holds no envelope".
  - Its `Reached::Carried` branch (`:91-103`) also matches `Held.sent == Some((id, index))`. `Held.sent` (`src/note.rs:771`, filled at `:895`) is `None` for these notes.

### The change

1. **Record the directly applied envelope** in the run's command record under the next envelope id, the same 0, 1, 2… numbering the queue uses, together with its commands and the answer it was given. Then `ChannelState::commands_of(id)` finds it, and a later driver adopting the run never applies it a second time.
2. **Stamp its notes** with that envelope id and each note's index, as the queued path does through `from_envelope`. Then `note-delivered` and the carried `Held.sent` name the note.
3. **Return the id in the receipt.** This is the public contract below.
4. **Withdrawal then works through its existing code:** a carried note from such an envelope, not yet composed into a dispatch, is withdrawn whether or not a driver runs by the time `withdraw-note` is sent.

### The public contract (high-cost, approved by the manager; stated once in `src/verbs.rs` and `docs/contract-divergences.md` entry 64)

```rust
pub enum ReplyOutcome {
    // ...
    AppliedHere {
        /// The envelope's durable id in the run's command record.
        reply: u64,
        /// The verdict half that rode along, if one did.
        verdict: VerdictHalf,
    },
    // ...
}
```

- `Receipt::reply()` returns that `reply` for `AppliedHere`, and the reply's JSON `reply` field carries it instead of `0`. The `state` and `commands` words are unchanged (`applied`).
- `Answered { reply: 0 }` for a verdict written straight to the run's record is unchanged.
- Update entry 64 of `docs/contract-divergences.md` and the doc comments on `ReplyOutcome` (`src/verbs.rs:890-930`) that say a direct apply has "no identifier to name". Those comments and entry 64 are the one statement consumers read.

### What it must not touch

- No change to `withdraw-note`'s syntax, to the queued and driven paths' receipts, or to the numbering of envelopes the queue already assigns.
- The ticket also lists `src/engine.rs`'s refusal of an outstanding admitted note on recovery (`unanswered_note`, `:5556`, used inside `recover_queued`). That location is mis-copied: it concerns a queued envelope whose driver died, not direct application. Leave it alone.

## Why

A manager who notes a run nothing is driving, for example before adopting it, gets an "applied" receipt but cannot take the note back. Stale guidance then reaches the node's next dispatch unless someone starts a driver first, and no message names that workaround. Withdrawal is a promised part of carried notes. Making it hold on every submission path keeps steering reliable whether or not a driver is running, and gives the receipt an id that means what its documentation says.

## Goals

- A note applied to a run with nothing driving is withdrawable, by the envelope id and index its receipt names, until a dispatch is composed with it.
- A reply applied with nothing driving returns its envelope's durable id in `reply`, and the documented receipt contract says so.
- A directly applied envelope is applied exactly once, including after a driver later adopts the run.

that an assertion can fail means making it fail, reading the message, and reverting;
proving that a message used to say nothing means quoting the run from before the change.
A citation of a run taken before a change, or of a failure induced on purpose as evidence,
is correct evidence — provided the citation says which it is. One node of this host was
failed for exactly that: its own criteria required its assertions be observed failing, and
the resulting-tree property above was read as forbidding the citation that requirement
produces.

**A commit that cannot affect a check leaves that check's evidence standing.** *Could have
invalidated it* is a condition, and a commit that fails it does not reach the claim — so a
run taken before a later commit is still evidence for the tree after it, provided the
report names that commit and says why it is inert for that check. What decides it is what
the check reads, never what kind of change the commit is. A comment-only or
documentation-only commit to content a check does not read is inert for that check; the
same comment is not inert for a check that reads comments, which a judged lint does, so
that one is re-run or named as not re-checked. A commit touching anything a check reads is
not inert for it, however small. Two dispatches of one node, about 45 minutes each, were
refused over nothing but a comment-only final commit after their cited check runs, with no
change in whether either tree was correct, and the manager had to send *re-run after every
commit* three separate times to get past it: read as absolute, the conditional rule above
is one no worker can meet, because every commit comes after the last run.

The ordering demand this replaces — that the report come after everything else, and that
anything found later be repaired and the whole report written again — is **withdrawn**. It
failed six of fourteen nodes in one workstream, each with complete committed work, a green
deterministic tier, and no acceptance criterion found unmet, and two of those carried an
escalated warning about it in their own task and failed anyway. A bar finished work
cannot clear teaches everyone to route around the thing that enforces quality; the
property above is what that demand was serving, and it is what survives.

### State the bar in `## Acceptance criteria`, not only here

A judge reads this node's `## Acceptance criteria` and its own review bar. Where the
criteria are silent about something the bar demands, it imports the demand and applies its
own reading of it — and finished, gate-green work has been failed twice that way: once for
running the gate's parts separately, and once for never having *"provided a final verified
completion report"*, a demand in neither the task nor the shared completion clause.

So every demand this node will be held to is stated as a criterion of its own, including
the two the bar makes of every implementation dispatch:

- the behavior this node adds is **proven end to end** by a test or journey that drives the
  real interface, rather than by inspection;
- every claim the dispatch makes about the finished work — what it verified, and the
  evidence for it — is **true of the tree as it finally stands**.

Criteria state properties of the finished tree; the commands that produce them belong in
this section. Whether the criteria answer every demand their own bar — or this appendix —
makes of them is read by `just review-plan <source:project>`, which spends a judged turn
on it and judges it by meaning: criteria that state a demand in their own words answer it,
and no criterion is refused for failing to use a particular phrase. Nothing reads it
deterministically any more, because the phrase matching that did refused wordings the same
review had just asked for.
