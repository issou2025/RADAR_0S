**CI: stop a merge-queue run as soon as the queue drops it**

*Project description:*
**Ready for coding:** yes.

Parent initiative: #4054

## What will be true

When the merge queue drops a pull request, its CI run stops within about a minute. Its runners are then free for live runs.

Words used here:

- **Merge queue:** GitHub's queue on `main`. It tests each pull request together with the newest `main` and the pull requests ahead of it. One such test is a **group**. Each group has its own short-lived branch (for example `gh-readonly-queue/main/pr-4280-…`) and its own `CI` run (event `merge_group`).
- **Required check:** a check that must pass before a pull request can merge. `main` has 10 of them.
- **The queue drops a group** when a required check of the group fails, or when the queue takes out a pull request ahead of it and builds the group again. Then it deletes the group's branch.
- **Dead run:** a `CI` run whose group the queue has already dropped. Its result no longer counts. But its jobs still wait for runners and still use them.
- **Heavy runners:** our own runner pool `meho-runners-ci-heavy` (6 runners). In `.github/workflows/ci.yml`, only 7 jobs use it:
  - the 4 unit-test shards `Python unit shard 1/4` to `Python unit shard 4/4`, in every pull-request, merge-queue and `main` run;
  - the 3 coverage shards `Python coverage (SonarCloud, shard 1/3)` to `Python coverage (SonarCloud, shard 3/3)`, only on pushes to `main`.

## Why it matters

Measured read-only with the GitHub Actions API, for the 24 hours up to 2026-10-21 15:52 UTC:

- **The trigger.** From 08:13 to 10:52 UTC, 31 merge-queue runs failed in their first minute. In all 31, the job `Go (golangci-lint + go test)` failed at its `govulncheck` step (the Go vulnerability scan). The scan had found a new issue in the Go standard library. #4692 fixed it (build with Go 1.26.10 for GO-2026-6809).
- **The queue was fast.** It dropped each of these groups within 0.3 to 1.3 minutes. 14 times it took the pull request out of the queue, and 17 times it built the group again.
- **The runs did not stop.** Their other jobs kept waiting for runners and kept using them, for a median of 131 minutes after the drop and up to 197 minutes. Example: #4280 left the queue at 08:30:13 UTC, but its run [39569626368](https://github.com/evoila/meho/actions/runs/39569626368) went on until 11:47 UTC.
- **They held the runners.** From 08:13 to 11:56 UTC, dead runs used 73 percent of the heavy runners. Up to 112 heavy jobs waited at the same time.
- **Almost half of the queue's runner time was wasted.** Dead runs used 1,017 of the 2,317 heavy runner minutes of all merge-queue runs in these 24 hours (44 percent). 971 of these minutes came from the 31 runs in the morning. On the main runner pool the share was the same: 1,582 of 3,587 minutes.
- **The longest runs were dead runs.** 26 merge-queue runs took longer than 78 minutes, up to 198 minutes (for example [39574953389](https://github.com/evoila/meho/actions/runs/39574953389): 158 minutes). All 26 were dead runs from the morning. Merge-queue runs that passed took at most 78 minutes.

Why the runs keep going:

- `ci.yml` never cancels a merge-queue run. `cancel-in-progress` is off for `merge_group`, on purpose: when a check of a live group is cancelled, the queue drops that group.
- Each group has its own branch. So a new group never replaces the run of an old group.
- GitHub does not stop a run when the queue drops its group.

**Expected gain:** on a day like 2026-10-21, about 1,000 heavy and 1,600 main runner minutes. Dead runs end about a minute after the drop, not after a median of 131 minutes. On a day without a broken check, the gain is small: about 50 heavy runner minutes, from groups that the queue builds again.

## What to build

Scope: only `.github/workflows/ci.yml`. The dead runs above were measured for the `CI` workflow only.

Rules:

1. **Only merge-queue runs.** The new behaviour runs only when the event is `merge_group`. Never in pull-request runs or in pushes to `main`: a pull-request run must still show every failing job.
2. **(a) A failed job cancels the rest of its run.** When a job of a merge-queue run fails, and that failure makes a required check fail, cancel the rest of that run. The queue drops the group in that case anyway.
   - Today this is true for every job of a merge-queue `CI` run except `CLI API snapshot freshness`. That job is not a required check. Its failure alone does not drop the group, so it must not cancel the run.
   - Cancelling a run (`POST /repos/{owner}/{repo}/actions/runs/{run_id}/cancel`, or `gh run cancel`) needs the `actions: write` permission on the job token. Give it only to the job that cancels. The workflow-wide `permissions: contents: read` stays.
3. **(b) A watchdog job stops a dead run.** Add one small job on a GitHub-hosted runner (`runs-on: ubuntu-latest`). About once a minute, it asks GitHub if the run's own merge-queue branch (`github.ref_name`) still exists: `GET /repos/{owner}/{repo}/branches/{branch}`.
   - GitHub answers `404` ("Branch not found"): cancel the run.
   - Any other answer or any error (for example a timeout, `403`, `429` or `5xx`): do nothing, and keep the run alive.
   - The watchdog ends, with success, as soon as all other jobs of its run have finished. It checks this before it checks the branch. So it never cancels a run that passed after the queue merged the group and deleted its branch.
   - It never fails, and it is not a required check.
   - It can also do rule (a), by looking at the jobs of its own run in the same loop. Or each job does rule (a) in a last step with `if: failure()`.
4. **Keep the concurrency setting** and its comment for merge-queue runs as they are (`cancel-in-progress: ${{ github.event_name != 'merge_group' }}`).
5. **Keep the API calls low:** at most about 2 calls a minute per run. GitHub allows the job token 1,000 API calls an hour per repository, and all workflow runs share this limit.

Checked on 2026-10-21: `GET /repos/evoila/meho/branches/<branch>` answers `200` for a live queue branch, and `404 Branch not found` for the branch of the dropped run 39569626368.

## How to test

- [ ] One pull request goes through the merge queue and merges. Its `CI` run is not cancelled, and all required checks pass.
- [ ] A merge-queue run with one failing job (for example a test pull request with a step that fails only when the event is `merge_group`): the rest of the run is cancelled within about a minute after the failure, at most 2 minutes.
- [ ] A pull request is taken out of the queue by hand while its run is going: the run stops within about a minute, at most 2 minutes.
- [ ] A pull-request run with one failing job still runs all other jobs to the end.
- [ ] `concurrency:` and its comment are unchanged.

## What else is affected

- Nothing changes for pull-request runs and for runs on `main`.
- If a live merge-queue run is cancelled by mistake, its pull request leaves the queue and must be queued again. The automation that merges our pull requests already puts a dropped pull request back in the queue.
- The watchdog keeps one GitHub-hosted runner busy while its run goes. The queue builds at most 4 groups at once. So this is at most about 4 of the 20 hosted jobs that the organisation can run at the same time (#4641).

Related: #4626 also changes `ci.yml` (fewer runner jobs per run). Whichever pull request merges second rebases.
