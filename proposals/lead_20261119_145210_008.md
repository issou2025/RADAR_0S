## Goal

Ship Ooga Chat to the Apple App Store and Google Play as its own mobile app, while the web app at **ooga.chat** stays the one product and the one codebase. The store apps are thin native shells around that web app. Nothing in the web app is rewritten for them.

This issue is a requirements discussion, not an implementation ticket. Nothing here is built or decided yet. @w-s-bitcoin and @rules-without-rulers: please mark up the requirements and add to the wish list at the bottom.

## Core recommendations

1. **Use Capacitor for the iOS shell.** It is the native runtime from the Ionic team, and it is the part of "Ionic" we actually need. Ionic Framework itself is a UI component kit; we would not adopt it, because Ooga Chat already has its own native OBL look.
2. **Use a Trusted Web Activity (TWA) for the Android shell**, generated with Bubblewrap or PWABuilder. A TWA runs the live site full screen in the phone's own Chrome, so voice, sign-in and cookies behave exactly as they do in the browser. It needs only the web manifest from #657 and one small verification file served from ooga.chat.
3. **Keep the web app as the single source of truth.** Both shells load the deployed ooga.chat. A web deploy updates the store apps without a store release, and there is no second copy of the UI to keep in step.
4. **Keep the shells out of the page.** They live in their own directory with their own `package.json`, as `worker/` does today, so the root stays free of npm dependencies and the page stays vanilla JavaScript under the existing content policy.
5. **Prove voice on real phones before anything else.** A short spike on a physical iPhone and a physical Android phone, over mobile data, decides whether this plan holds. [#767](https://github.com/OogaBoogaX/oogaboogaland/issues/767) (voice stuck on JOINING over mobile data) must be fixed first, because the shell inherits it.
6. **Treat Apple review as the main risk, not the tooling.** A shell that only shows a website is the classic rejection under guideline 4.2 (minimum functionality). The store build needs a short list of things the browser cannot do; see the requirements below.

## Framework research

"No changes" below means no changes to the web app's own code.

| Option | What it is | No changes to the web app? | Verdict |
|---|---|---|---|
| **Capacitor** | Native iOS and Android projects around the system web view, with a large plugin set (push, deep links, splash, status bar) | Yes, when the shell loads the live site. Plugins are optional and can be feature-detected | **Recommended for iOS.** Fallback for Android |
| **Trusted Web Activity** (Bubblewrap, PWABuilder) | Android only. The installed app is the live site in Chrome, verified by Digital Asset Links | Yes. Needs the manifest and an `assetlinks.json` file | **Recommended for Android** |
| PWABuilder iOS package | Generates a plain Swift web view project | Yes | Workable, but it is a one-off template we would then maintain by hand. Capacitor gives the same shell with upkeep and plugins |
| Tauri (mobile) | Rust-based shell, strong on desktop; mobile support is newer | Yes | Not recommended: a Rust toolchain and a thinner mobile plugin set, with no gain for a mobile-only wrapper |
| Cordova | Capacitor's predecessor | Yes | Not recommended: legacy, and Capacitor replaces it |
| React Native or Flutter with a web view | A full app framework hosting one web view | Yes | Not recommended: a second runtime to carry for no benefit |
| Commercial wrapper services | Hosted build of a web view shell | Yes | Not recommended for now: closed tooling and a recurring fee. Cost: TBD |

Three findings that shape the requirements:

- **Loading the live site is a trade-off on iOS.** Capacitor's own docs describe its remote URL setting as meant for development, and Apple reviewers look harder at shells that are only a remote page. The alternative is to bundle the built app inside the shell, but then the page runs from a different origin than ooga.chat, and sign-in cookies, the content policy and the API calls would all need backend changes. Loading the live site is the only route that truly leaves the app alone, so the 4.2 answer has to come from native extras, not from bundling.
- **iOS has no TWA equivalent.** On iPhone the shell is always the system web view, which is the same engine as Safari but a separate process with its own microphone and audio session rules. Voice with the app in the background is unreliable there, and #657 already says installation grants no background microphone. The store app should promise the same.
- **Sign-in inside a web view is not a given.** Some identity providers refuse embedded web views, and the recommended pattern is the system sign-in sheet. That sheet does not share cookies with the web view, so using it would need a small hand-off step from the backend. On Android the TWA avoids the question, because it is Chrome.

## Draft requirements

**Must have**

- One web app. No fork, no store-only UI, no change to the island page.
- Feature parity with ooga.chat at release: listening, Join Voice for verified contributors, reactions, the native panels, The Commons.
- Voice works on a physical iPhone and Android phone, on Wi-Fi and on mobile data, with the microphone permission prompt and its purpose text.
- Sign-in with GitHub and X completes inside the app and survives a relaunch.
- Links to ooga.chat open the app (universal links on iOS, app links on Android).
- Account deletion reachable inside the app (Apple requires it; `DELETE /api/me` already exists).
- A way to report and block people, and a published contact, for chat and voice. Both stores require this for user-generated content.
- Store listings: name, icons, screenshots, privacy policy, data disclosure forms, age rating.
- The shell adds no analytics and no tracking, in line with the repository's privacy rules.

**Decisions needed**

| # | Question | Why it matters |
|---|---|---|
| 1 | Who owns the Apple and Google developer accounts, and are they organization accounts? | Signing keys, legal name on the listing, and enrolment checks all follow from this |
| 2 | Do we add Sign in with Apple? | Apple guideline 4.8 expects an equivalent privacy-focused option beside third-party sign-in such as GitHub and X. #650 currently says GitHub and X only, with no account linking |
| 3 | What happens to Feed the Oogas in the store builds? | Both stores restrict in-app donations and digital payments. Options: hide it, or link out to the browser |
| 4 | Which native extras carry the 4.2 case on iOS? | Candidates: push notifications, deep links, share sheet, lock-screen audio controls |
| 5 | Is a moderation process in place before submission? | Reviewers test report and block, and expect someone to act on reports |
| 6 | Same release for both stores, or Android first? | The Android TWA is far less work and far less review risk |
| 7 | Where do the shells live: this repository or a new one? | #650 keeps everything in one repository until a stable shared boundary exists |
