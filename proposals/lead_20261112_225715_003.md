# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Testing: unify discovery, isolate fixtures and measure coverage**

*Project description:*
Follow-up from the 7.1 pre-release documentation review (#3969). `docs/testing.md` described this consolidation plan as "proposed". It is not implemented, so it is tracked here instead of in the as-is docs. The testing policy in `docs/testing.md` ("Repository testing policy") stays in the docs; this issue is the work to make the repository follow it.

## Current gaps

- CI selects C# tests by class-name allowlists (`FullyQualifiedName~...` filters in `build/Modules/TestConfigurationsModule.cs`) for `pyRevitLabs.UnitTests` and `pyRevitExtensionParserTester`. Renaming a class silently drops coverage, and a new regression test needs a build-pipeline edit.
- `pyRevitExtensionParserTester` has far more test classes than the filter selects. Some excluded tests track mutable DevTools layouts and titles, others need Revit assemblies.
- Host-free Python discovery in CI is `dev/scripts/test_standalone_*.py` only. `test_check_config_api.py` and `test_check_py3_compat.py` are not run by CI.
- `revit-integration.yml` launches Revit on pushes to `develop`, which the policy does not allow.
- Tests carry no `Level` / `Environment` metadata, no validator checks for undiscovered suites or suites selecting zero tests, and no coverage is measured.
- Hosted Python tests (`pyrevit.unittests`) have no documented local procedure, no aggregated result report, and several DevTools buttons mix assertions with demos.
- Test builds can deploy into the active clone's `bin/`, so a running Revit can block them.
- The Python (`pyrevit.extensions.genericcomps`) and C# (`pyRevitExtensionParser`) parsers disagree on components not listed in `layout`.

## 1. Unify discovery and execution

- Provide discoverable host-free and local Revit selections, with manual checks documented separately. Local development and CI share the host-free selection rules; CI never executes the Revit selection. Start by including all `dev/scripts/test_*.py` modules in the host-free group and removing automatic Revit execution from the existing workflow.
- Inventory every first-party test project and module with its command, required runtime, fixtures and CI status. Add a discovery check that fails when a new suite has no execution group. Keep vendored dependencies out of the inventory.
- For C#, replace class-name allowlists with the required `Level` and `Environment` metadata and optional network/elevation capabilities. Select all `HostFree` tests for CI and keep every Revit API test in the local `Revit` selection. Triage excluded failures first (stale expectation, product defect or missing dependency) and record temporary exclusions with a reason and a tracked follow-up.
- Separate three responsibilities: test projects own capability metadata using their framework's category/trait mechanism; shared selection rules own framework selection and capability filters and discover projects beside their modules; the build runner executes a requested profile and publishes results without enumerating test classes.
- Network and elevation requirements need provisioned CI environments rather than silent omission. Validate discovery so an expected project or selection returning zero tests fails visibly.

Done when a new host-free test runs locally and in CI without editing an allowlist, and every excluded suite has an explicit execution path.

## 2. Preserve module ownership and isolate fixtures

- Keep C# suites beside their owning modules. Moving one is optional and must solve an ownership or fixture problem (update project references, solution membership, build paths and docs together).
- Keep `dev/scripts/test_*.py` discoverable as host-free suites, `build/tests/` beside the pipeline, and `pyrevit.unittests` importable for hosted commands until the runner and package dependencies are decoupled. DevTools command scripts become thin launchers for shared suites or explicitly labelled manual checks.
- Replace parser fixtures that depend on the changing DevTools extension with small dedicated extension fixtures, keep one smoke test for the real DevTools layout, and define the intended Python/C# layout contract tested by both parsers against shared cases.
- Move reusable assertions out of ribbon scripts into the shared suite, and separate automated tests, interactive checks and examples in the ribbon. Make test builds independent of deployment into the active clone's `bin/`.

Done when each suite has one owning location, fixtures are deterministic, ribbon launchers share the automated assertions, and host-free tests can build while Revit is open.

## 3. Restore and measure coverage

- Execute the existing excluded tests before adding more tests of the same behavior (parser, layout, metadata, icon and runtime coverage).
- Document local hosted execution with deterministic project and family fixtures, shared between individual buttons and `Run All Tests`. Record a local Revit-year and engine matrix (IronPython 2, IronPython 3, CPython). Keep Revit execution out of CI.
- Publish JUnit/TRX results with passed, failed and skipped counts by suite, framework, Revit year and engine. Aggregate hosted results across modules instead of overwriting one report, fail on missing or empty expected suites, and distinguish expected capability skips from unavailable required fixtures.
- Collect C# and host-free Python line and branch coverage per module, excluding vendored and generated code. Establish baselines before setting thresholds, then guard coverage of changed behavior. Hosted lifecycle tests must also verify CPython reload and repeated execution in Revit.

Done when CI shows which API-free module/framework combinations ran, unexpected coverage loss is visible, and local Revit results record year/engine combinations separately (load/signing smoke checks apart from functional hosted tests).
