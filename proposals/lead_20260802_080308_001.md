## Summary

## Root cause — the same fragile trick, failing two different ways

Neither project references the Revit API. Both instead `<Compile Include="..\StingTools\...">` selected plugin sources directly, on the assumption those files stay Revit-free. The `StingTools.Clash.Tests.csproj` comment states the intent outright: *"avoiding the need for Revit DLLs on the test host."*

The assumption is unenforced, and it broke in two distinct ways:

1. **Clash.Tests has no Revit shim at all** (`TestHelpers/` contains only `StingLogShim.cs`). `c98500b5a` was a bulk mechanical pass adding `using` directives across 163 files; it added `using Autodesk...` to four of the five included Clash sources at once. Nothing in that commit was wrong for the *plugin* — it simply had no way to know four of those files were load-bearing for a Revit-free test project.
2. **Routing.Tests hand-rolls a fake Revit namespace** in `TestHelpers/RevitStubs.cs`, implementing "only the public surface area touched by AStarSolver / AcoRefiner / VoxelGrid / ConduitRouteEngine". When `ConduitRouteEngine.cs` grew `Autodesk.Revit.DB.Structure` and a `Document` reference, the shim did not grow with it.

`RevitStubs.cs` carries this comment:

> *"Everything else throws NotImplementedException so accidental drift surfaces loudly rather than silently breaking under a pure-logic test."*

That reasoning holds for drift in a **method body** — a `NotImplementedException` at runtime is loud. It does not hold for drift in a **type or namespace**, which fails at *compile* time and takes the entire project's 41 tests offline. The mechanism designed to make drift loud is the mechanism that made it silent.

Separately, and worth stating because the two get conflated: **executed test cases** today total **1,017** (1,015 passed, 2 failed), because `[Theory]` + `InlineData` expands one declared method into many cases. Declared-methods and executed-cases are different metrics; `CLAUDE.md` uses the former, `dotnet test` reports the latter. Whichever is chosen, it should exclude the 97 that cannot run.

## Why this is worth an issue rather than a quiet fix

A coverage number that includes tests which cannot execute is worse than a smaller honest one. It is the same failure mode as an empty list standing in for an error: a confident, plausible, wrong answer. Anyone reading "774 test methods" reasonably concludes the clash kernel and the routing solver are under test. They have not been since May.

There is also no CI gate catching it — a project that fails to build is not distinguishable from one that was never run, unless something explicitly asserts that all nine projects compile.

## Suggested direction (not done here)

1. **Correct the `CLAUDE.md` headline** to the runnable figure, and note the exclusion, so the number stops overstating.
2. **Make the breakage loud.** A CI step that builds all nine test projects and fails on any that do not compile turns a two-month silence into a red build on the offending commit.
3. **Then** decide per project whether to repair the shim, extend the `<Compile Include>` set with the missing Revit-free dependencies, or give these projects a real Revit reference like the plugin has. That is a design call, not a mechanical fix, which is why it is out of scope here.

## Not in scope

**The compile errors are deliberately not fixed in this issue.** Repairing them means either extending `RevitStubs.cs` to track the real Revit surface (which re-arms the same trap) or restructuring how these projects consume plugin source — a decision worth taking on its own, with the CI gate in place first so the next regression is caught in minutes rather than months.
