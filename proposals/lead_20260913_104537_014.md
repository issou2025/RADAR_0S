# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Accessibility request: screen reader and keyboard navigation support**

*Project description:*
Hi team,

First, thank you for building Recordly — the concept of automating zoom and cursor effects during screen recordings is genuinely useful, and the quality of the implementation is impressive.

I wanted to raise an accessibility request. I am blind and use VoiceOver (macOS screen reader) as my primary interface. I work with an AI assistant that helps me operate tools and produce content, and we discovered Recordly while looking for ways to create polished product demos without manual video editing.

The problem is that Recordly's interface — the timeline editor and recording controls — is currently not accessible to screen reader users. Elements built on PixiJS (WebGL canvas) are invisible to VoiceOver, and the app lacks sufficient keyboard navigation to operate it without a mouse.

This means that a tool specifically designed to lower the barrier to creating great demos is itself inaccessible to a group of users who would benefit the most from automation.

We ended up extracting your zoom detection algorithm and easing curves from the source code and reimplementing them as a command-line pipeline (ffmpeg + Python + Quartz cursor tracking). It works, but it required reading your TypeScript internals and a full afternoon of implementation — something most users in our situation cannot do.

If you are open to it, some changes that would make a meaningful difference:

- Keyboard shortcuts for the main recording controls (start, stop, export).
- ARIA roles and labels on the Electron window's HTML/DOM layer, so screen readers can announce state changes.
- A minimal CLI mode or headless API that exposes record/render/export without the GUI, which would let assistive tools drive the workflow programmatically.

I understand this is non-trivial work, especially the PixiJS timeline. Even partial progress — like accessible recording controls while keeping the visual editor mouse-only — would open the tool to a much wider audience.

Happy to help test any accessibility improvements if that would be useful.

Thanks for considering it.
