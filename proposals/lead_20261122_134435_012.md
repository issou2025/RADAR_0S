# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Unify design-system press/hover feedback on M3E state layers**

*Project description:*
## Problem Statement

Across the Flutter design system and product surfaces, press and hover feedback still mix Material defaults, custom InkWell alpha values, and Material 3 Expressive (M3E) state layers. After removing legacy GhostButton / custom context menus / OutlinedMetaChip, remaining custom tappable surfaces (segmented bar segments, list-detail destinations, split list rows, facet candidate rows, and many feature InkWells) still feel inconsistent. Maintainers want one interaction model without writing collaboration docs and without a hard architecture ban on InkWell.

## Solution

Unify interactive-state and press feedback onto the M3E model already shipped in `material_3_expressive`: `M3EInteractionState` priorities and `M3EStateOpacity` tokens (hover 8%, focus 10%, pressed 10%, dragged 16%). Prefer package controls (`M3EButton`, `M3EIconButton`, `M3EChip`, `M3ECard`, `M3EFab`, menu APIs) or `M3ETappable` (optional material ink) for custom surfaces. Keep **press-only corner-radius morph** on SplitList-style segmented rows as a deliberate product exception. Enforce the outcome through component behavior tests and migrations—not AST forbid-lists or new engineering prose docs.

## User Stories

1. As a library browser, I want every tappable control to darken or ripple the same way on hover and press, so that the UI feels coherent.
2. As a keyboard user, I want focus rings (or focus fill when rings are not the modality) to follow M3E rules, so that I can see which control is active.
3. As a mouse user on desktop, I want hover feedback at the standard 8% state layer, so that hover is visible but not louder than press.
4. As a touch user, I want pressed feedback at the standard 10% state layer or InkSparkle splash, so that taps feel responsive.
5. As a settings user tapping a split-list row, I want the row corners to morph only while pressed, so that segmented lists keep their expressive press affordance.
6. As a settings user releasing a split-list row, I want the corner radius to return to the resting segmented shape, so that the list structure stays readable.
7. As a catalog user switching comic/series segments, I want segment hover/press to use M3E opacities, so that the capsule bar matches other controls.
8. As a metadata editor using the wide list-detail rail, I want destination hover/press to use M3E state layers, so that navigation items match the rest of the shell.
9. As a reader opening a page-image context menu, I want the menu and its items to use the M3E menu path already adopted, so that chrome stays consistent.
10. As a history user deleting a record, I want the delete control to be an M3E icon button with standard ink, so that it matches toolbar icons.
11. As an author-detail user managing links, I want chips to be M3E chips with standard delete affordances, so that chip interaction matches metadata chips elsewhere.
12. As a developer adding a new tappable row, I want an existing design-system surface or `M3ETappable` pattern to copy, so that I do not invent new overlay alphas.
13. As a developer reviewing a PR, I want failing widget tests when press morph or state opacity contracts regress, so that I catch interaction drift without reading a guide.
14. As a design-system maintainer, I want package M3E widgets used directly when they fit, so that we do not grow wrapper layers.
15. As a design-system maintainer, I want custom surfaces that cannot use a stock widget to share one tappable primitive, so that state tracking stays consistent.
16. As a FAB / scroll-to-top user, I want press scale only on FAB-class controls, so that lists and navigation do not shrink on tap.
17. As a reduced-motion user, I want press morph and springs to respect disable-animations, so that motion does not fight accessibility settings.
18. As a focus user after a pointer click, I want focus not to stick on the control, so that keyboard chrome does not linger after mouse use.
19. As a filter/sort sheet user, I want rows eventually to share the same press feedback as settings rows or M3E list patterns, so that side sheets do not feel like a second UI kit.
20. As a Widgetbook reviewer, I want Lab cases to exercise hover, press, focus, and keyboard activation for migrated controls, so that visual acceptance covers interaction states.
21. As a window-chrome user, I want the close button to keep its error-tinted overlay exception, so that destructive window actions stay distinct.
22. As an agent implementing this work, I want a shrink-only exception list described in code comments near the exception sites (not a gate), so that I know what must not spread.
23. As a product owner, I want no new collaboration/ADR write-up required for this pass, so that delivery stays in code and tests.
24. As a maintainer, I want feature-level bare InkWell migrations to be opportunistic after design-system surfaces are fixed, so that high-traffic DS controls land first.
25. As a developer, I want pressed feedback to be either splash-or-fill, not both stacked at full pressed opacity, so that press does not look muddy.
26. As a catalog grid user, I want card press to continue using M3E card ink, so that cards stay aligned with the package.
27. As a pagination user, I want page buttons to keep `M3ETappable` plus tab state-layer tokens, so that pagination matches tabs.
28. As a calendar user, I want day/month/year cells to keep `M3ETappable` state layers, so that the date picker matches M3E.
29. As a QA engineer, I want tests to assert observable colors/radii/semantics rather than private field names, so that refactors do not flake.
30. As a future contributor, I want SplitList press morph preserved and not copied onto segmented bars or nav destinations, so that morph stays a list-row signature only.

## Implementation Decisions

- Scope is the design system interaction model and its high-traffic expressive surfaces first; feature InkWell cleanups follow the same patterns but are secondary.
- Single source of truth for opacities and state priority is the M3E package interaction foundation (`M3EStateOpacity` / `M3EInteractionState`), not app-local constants.
- Prefer direct M3E package widgets when they fit; do not add one wrapper per widget.
- Custom tappable surfaces use `M3ETappable` (with optional material ink / state-layer overlay). Do not introduce new ad-hoc overlay alpha literals.
- Press feedback patterns:
  - Standard controls: hover/focus overlay + InkSparkle pressed splash; no press scale.
  - Custom surfaces: state-layer fill from M3E opacities (optional material ink); no press scale by default.
  - FAB class only: state layer + press scale (~0.95) with expressive spatial press spring.
- **Press-only corner-radius morph** remains on SplitList-style segmented rows (and settings tiles that report press into that row). Morph must not spread to `ExpressiveSegmentedBar`, `ExpressiveNavDestination`, chips, or generic feature rows.
- SplitList may keep an InkWell or equivalent for hit-testing/highlight reporting as long as resting/pressed radii still morph only while pressed and any painted overlay uses M3E opacities.
- Desktop window close control may keep error-role overlay coloring and suppressed focus fill as a named exception at the call site.
- Pointer activation should continue to drop focus after pointer gestures so keyboard focus chrome does not stick.
- Reduced motion: morph/springs honor disable-animations; jump or shorten rather than inventing a second visual language.
- **No new collaboration documents or ADRs** for this work; encode contracts in tests and brief code comments at exception sites only.
- **No hard architecture/AST gate** forbidding InkWell globally; do not add allowlist scanners that fail CI on every remaining InkWell.
- Migration order (implementation guidance): (1) `ExpressiveSegmentedBar` segment feedback, (2) `ExpressiveNavDestination`, (3) SplitList overlay token alignment while preserving morph, (4) facet multi-select candidate rows, (5) opportunistic feature/shared InkWell rows toward design-system / `M3ETappable` patterns.
- Testing seam (confirmed): **design-system / Lab widget tests** that assert external interaction behavior (state-layer strength, press-only morph, focus/unfocus). Existing motion/decoration and component tests are the preferred prior art; extend them rather than inventing a new architecture suite.

## Testing Decisions

- Good tests assert what the user can observe: resting vs pressed corner radii on split rows; hover/press overlay strength consistent with M3E opacities; presence of M3E controls after migrations; keyboard focus ring vs pointer unfocus behavior where already covered.
- Do not assert private implementation type names as the primary contract (for example “must not contain InkWell”) unless that is the user-visible API under test.
- Modules under test: design-system expressive segmented bar, nav destination, split list row / settings tile shell press morph, pagination/calendar/`M3ETappable` surfaces already on the M3E path, plus regression coverage for recently migrated buttons/menus/chips.
- Prior art: design-system boundary tests stay for dependency portability only; interaction contracts belong with existing design-system and MD3E widget/motion tests (for example effects decoration / split row morph, segmented indicator springs, scroll-to-top FAB behavior).
- Promote new interaction contract tests into the existing fast-track manifests only when they meet gate promotion rules.

## Out of Scope

- Writing or updating collaboration/engineering prose docs or a new ADR solely for this interaction scheme.
- Adding a hard CI architecture gate or shrink-only InkWell forbid-list scanner.
- Spreading press corner-radius morph beyond SplitList-style segmented rows.
- Replacing M3E package internals or forking `material_3_expressive`.
- Visual redesign of colors, typography, or layout unrelated to interaction states.
- Reader page-image fidelity, navigation routing, or domain behavior changes.
- Mandatory one-shot cleanup of every feature InkWell in a single change set (secondary, opportunistic).
