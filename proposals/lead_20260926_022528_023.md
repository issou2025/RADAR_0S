# Using Claude Code: Spending your effort
Author: Thariq Shihipar | Published: Sep 25, 2026 | Reading Time: 8 min

What effort really is and when to use which level in Claude Code, from my own tests of three builds and a deep dive into Terminal-Bench 3.0 on Opus 5.5 and Fable 5.1.

One of the best parts of our newest Claude models is how they respond to effort without breaking the prompt cache in Claude Code, but I’ve received a lot of questions on this from users. What is effort really, and when do you use which effort level? Why do we need effort at all?

To answer this, I decided to do a deep dive into the evals and do my own tests of effort across normal work.

At a high level, I found that effort was a great way of modulating how much verification and edgecase testing Claude did and how much of its own judgement it used. Extra effort gave better results in domains where verification and edgecase testing was more useful like hardware, code review, and security.

For normal software engineering, I’m running a loop of getting the model to interview me then implementing on low effort, reviewing what it built, and then running verification on high effort.

## WHAT IS EFFORT?
At a high level, effort gives the model an approximation of how much compute you want it to spend on the task. It’s somewhat related to your modeling of the difficulty of the task.

Think of it this way, if someone asked you to do something in 12 hours straight, you might assume they just want you to do it and try very hard. If someone asked you to do the same task in 1 hour, you’d try to get them the best version that meets their task and then expect to iterate from there.

Or, you might push back and say the task requires at least 3 hours and then work for 3 hours to deliver it.

You should think of effort in the same way. Claude will always try and do your task reasonably, but higher effort will involve Claude taking more independent action for judgement and verification.

## EFFORT CURVES
Fable 5.1 and Opus 5.5’s effort curves are our best yet: at each level, there is an uptick in benchmark scores and tokens consumed.

Terminal-Bench 3.0, the same 70 tasks for every model (the 4 GPU tasks are left out). Opus 5.5 ran about three weeks later, with responses capped at 128k tokens and no GitHub or PyPI access; Opus 5’s max is its effort-120 run.

## BUILDING WITH EFFORT
The best way to understand how models work is to run experiments. I tried doing the same tasks at several different effort levels on Opus 5.5 to understand the work it would do.

### Underspecified build task
If I ask Claude to “build a personal fitness and workout tracker app,” effort changes dramatically how fleshed out the app is, but also results in Claude making more choices along the way. At low effort, the fitness app is just a log and a simple graph. At higher effort levels the app is more complex with additional detail. At max effort there’s a heat chart.
- Low: 1.5 min
- Medium: 4 min
- High: 11 min
- Max: 67 min
If I wanted a simple base to iterate from, low effort would get it done. Max effort would be if I wanted Claude’s best one shot.

### Lightly specified design task
Redesign the /config menu in Claude Code:
- Low effort (1 min): interactive sketch conveying the idea.
- Max effort (28 min): polished mockup looking very much like Claude Code with flow walkthroughs.

### Highly specified build task
Interview in-depth about fitness app, then give spec: models behaved much more similarly across effort levels (Low 16m, Medium 22m, High 33m, Max 79m).

### Takeaways
For regular software engineering:
1. Give Claude a spec and ask it to interview me about any details I’m missing
2. Implement it on low effort
3. Review to make sure it got the gist of it correct, iterate on low effort as needed
4. Verify and test on high effort

## HOW EFFORT LEVELS IMPACT OUTPUT ON DIFFICULT TASKS
Terminal-Bench 3.0 problems:
Higher effort is best for tasks with lots of hidden edge cases.
Example: html-js-filter (XSS sanitizer):
- Low effort (2 min): 1/5 pass. Wrote filter in one pass, tested against single page.
- High effort (33 min): 5/5 pass. Adversarially reviewed first draft, read installed parser source, tested clean test cases, ran standard XSS suite, wrote random-document fuzzer.

Error Analysis: Increasing effort tends to reduce failures due to missing edgecases (purple blocks), but DOES NOT FIX when the model has the wrong approach (blue blocks).
- Fable 5.1 at low: 140 passed, 40 bug tests missed, 45 misread requirement, 31 wrong/incomplete fix, 32 got domain rule wrong, 25 wrong reading.
- Fable 5.1 at max: 214 passed, 14 bug tests missed, 26 misread requirement, 10 wrong/incomplete fix, 24 got domain rule wrong, 47 wrong reading.

Problem areas where effort helps (Fable 5.1 low -> top):
- Security: 64% -> 87%
- Hardware: 34% -> 75%
- ML: 54% -> 73%
- Science: 41% -> 61%
- Software: 43% -> 56%
- Media: 18% -> 30%
- Operations: 12% -> 22%

Opus 5.5 Case Studies:
- mvcc-lsm-compaction: 0/5 low -> 4/5 xhigh (reproduced crash first, randomized test, verified test failed on half-fixes).
- cli-2ph-simplex: 0/5 low -> 5/5 high (tested on random problems against brute-force solver, timed bigger ones, reworked search).
- gsea-proteomics: 0/5 low -> 4/5 high (tested two data preps, noticed list changed, investigated why).

Rule of Thumb:
- Low: quick in-the-loop responses (brainstorming, sketching, mechanical edits).
- Medium: regular software engineering (new feature implementation).
- High: verification & edge cases (bug fixes in brownfield codebases, code review).
- Max: fully autonomous operations (end-to-end build & verification, security audits).

# Getting the most out of Opus 5.5 in Claude and Claude Code
Author: Addy Osmani | Published: Sep 22, 2026 | Reading Time: 9 min

Try this first:
1. Hand over the whole task. Say what "done" looks like and when you want it to stop and ask. Then let it work.
2. Delete "think carefully" lines. Opus 5.5 already thinks before every reply.
3. When a long run ends, read what it needs from you first.

1. How to ask:
- Give the whole task in one message: whole task, finish line ("every endpoint uses new client, old client deleted, tests pass"), and when to stop ("only if test fails for unexplained reason").
- Stop telling it to "think hard" / "think step by step": always thinks internally; removing prompt padding cuts time-to-first-token.
- Design work: Name the styles you DON'T want. Generic instructions like "avoid generic look" fail. Specific negative lists work ("no cream background, no italic accents, no 01/02 labels, no pill buttons").

2. Steering a long run in Claude Code:
- CLAUDE.md rule: "When a step doesn't need my input, keep going. Put status notes in the same message as your next action. Stop and ask only when you can't continue without me, or before anything destructive: deleting data, force-pushing, or changing anything outside this repository."
- Split big work across subagents: Give each service to its own subagent, check evidence before accepting, finish with one table.
- Keep task list in a file: Context fills and auto-compacts; a checklist in TASKS.md survives compaction and keeps state visible.

3. Checking the result:
- Read what it needs from you first: End every run with three headings: Blocked on me, Changed, Found.
- Ask Opus 5.5 to review diff: Lowest effort Opus 5.5 caught more bugs than Opus 5 at high effort with fewer false alarms.
- Ask it to mark what it couldn't confirm: "Mark anything you couldn't confirm, and say where you looked."

4. Claude apps & Projects:
- "Once you have answered something, treat that answer as done. Focus on what I'm asking now, and don't go back over an earlier answer unless I ask about it." Prevents model from repeatedly re-analyzing past chat history.
- Never ask it to reproduce internal reasoning in the reply (can trigger flags). Ask "explain why in three sentences".

5. Speed:
- Fast mode (/fast): 2.5x speed at 2x price ($8/M in, $40/M out). For synchronous interactive sessions only.

# What a task costs on Opus 5.5
Author: Addy Osmani | Published: Sep 25, 2026 | Reading Time: 21 min

Key Token Economics:
- List prices: Input $4/M, Output $20/M, Cache read $0.20/M (5% of input price!). Output tokens are 100x the cost of cache reads.
- Every turn resends the entire conversation so far:
  * 20k -> 120k context across 40 turns = 2.8M input tokens ($1.62 at 90% cache vs $11.20 uncached).
  * The cheapest turn is the one you don't need: provide test/build checks so the model catches errors on turn 1 rather than turn 10.
- Effort levels:
  * Default on Opus 5.5 is MEDIUM (one level below Opus 5's default of High).
  * At given level, Opus 5.5 thinks more per turn than Opus 5, especially at xhigh/max.
  * Medium for day-to-day clear scope. Raise to High when medium stalls. Low for mechanical edits across files.
  * High effort adds ~$0.40 in output tokens; a 10-turn retry loop costs the same, so High pays for itself if it saves one retry.
- What breaks the prompt cache:
  * Pauses exceeding TTL (5 min on API key; 1 hour on subscription).
  * Changing tool definitions / connecting/disconnecting MCP servers.
  * Modifying system prompt mid-session.
  * Model switches.
  * Changing effort on cloud gateways.
- Compaction economics:
  * Compacting at 150k context costs ~$0.25 (read + output summary + fresh write). Saves ~$0.025/turn. Pays off in ~10 turns.
  * Compact at natural breaks while cache is warm; never compact right before finishing.
  * Keep CLAUDE.md under 200 lines. Use deferred tool definitions.
- Subagent model allocation:
  * Search, log reading, file lookup -> cheap models (Sonnet, Haiku, Flash).
  * Code edits, judgement calls -> Opus 5.5.
  * Avoid "opusplan" inversion (Opus plans, Sonnet writes code) for non-trivial code: keeping code edits on Opus 5.5 at low/medium effort yields better results than Sonnet.
  * Escalate to Fable 5.1 when Opus on xhigh fails twice on the same problem.

## Detailed Findings across the 7 Core Dimensions

### 1. Effort Levels & Compute Modulation
* **The Core Mechanism**: Effort is an approximation of compute and thoroughness, directly steering the volume of thinking tokens, file inspections, tool invocations, and edge-case verification before returning to the user.
* **The Asymmetry of Effort**:
  * **Where Effort Wins**: Tasks dominated by hidden edge cases—hardware design (Verilog/FPGA pass rate jumps 34% → 75%), security audits (64% → 87%), complex algorithms/ML (54% → 73%), and storage engine compaction (`mvcc-lsm-compaction` jumps 0/5 to 4/5).
  * **Where Effort Fails**: Architectural flaws and incorrect conceptual approaches. Increasing effort does not fix a wrong reading of a problem; it merely makes the model reason deeply along the flawed path.
* **Effort Level Calibration**:
  * **Low**: Fast in-the-loop interactions, sketching, spec interviews, mechanical renames across files.
  * **Medium**: The new **recommended default for Opus 5.5** for all everyday feature development.
  * **High**: Brownfield debugging, complex multi-layer refactors, and adversarial code reviews.
  * **Max**: Fully autonomous one-shot building or mission-critical security auditing.
* **The 4-Stage Feature Loop**: Spec Interview → Implement at Low Effort → Human/Agent Review → Verify at High Effort.

### 2. Prompting Discipline & Style Constraints
* **"Say What Done Looks Like, Then Let It Cook"**: A single prompt must combine the entire goal, explicit observable completion criteria, and precise stopping boundaries (only stop for destructive actions or inexplicable test failures).
* **Elimination of "Think Hard" Rituals**: Opus 5.5 natively reasons internally on every turn. Prompt padding like "think carefully" or "think step by step" adds latency to first token without improving benchmark scores.
* **No Internal Reasoning Dumps**: Requesting the model to reproduce its raw internal reasoning in the user reply can trigger safety refusals; request concise explanations ("explain why in three sentences") instead.
* **Negative Constraints for Design**: Open-ended prompts produce generic default tropes (cream background, italic accents, pill buttons, monospace labels). Providing an explicit negative list of forbidden styling patterns forces fresh, high-quality aesthetics.

### 3. Steering, Stops, and Settled Answers
* **CLAUDE.md / AGENTS.md Stop Rule**: Explicitly steer the agent: *"When a step doesn't need my input, keep going. Put status notes in the same message as your next action. Stop and ask only when you can't continue without me, or before anything destructive: deleting data, force-pushing, or changing anything outside this repository."*
* **Settled Answers Directive**: In long multi-turn sessions, Opus 5.5 re-analyzes prior turns unless told: *"Once you have answered something, treat that answer as done. Focus on what I'm asking now, and don't go back over an earlier answer unless I ask about it."* This prevents quadratic latency degradation in complex threads.

### 4. Context Engineering & "Unhobbling"
* **80% System Prompt Reduction**: Strip rigid, prescriptive prompt rules that conflict with user intent or codebase idioms.
* **Judgement Over Rules**: Replace rigid bans ("never write comments") with contextual guidance ("match surrounding comment density, naming, and idiom").
* **Interface Design Over Examples**: Expressive parameter schemas and self-documenting enums guide tool use far more cleanly than verbose few-shot examples.
* **Rich References Over Markdown Plans**: Code, test suites, and HTML mockups provide higher fidelity than abstract markdown task specs.

### 5. Tool Use, Deferred Loading, and Skills Architecture
* **Deferred Tool Loading**: Tool definitions should be loaded on demand via tool search/discovery (`search_tool_bm25`) rather than bloating upfront context.
* **Skills as Modular Folders**: Skills must be structured as folders (`SKILL.md` hub with `references/`, `scripts/`, `gotchas/`) rather than flat monolithic text.
* **High-Signal Gotchas**: The "Gotchas" section is the most valuable part of any skill, capturing hard-won operational edge cases.
* **On-Demand Session Hooks**: Ephemeral safety hooks (`/careful` to intercept destructive bash commands; `/freeze` to constrain file edits during debugging).

### 6. Caching Economics & Cache Preservation Discipline
* **Token Cost Ratio**: On Opus 5.5, cache reads are $0.20/M (5% of input price), while output is $20/M (100x cache read price).
* **Cache Hit Rate is Dominant**: Maintaining 90–96% cache hits is the primary cost driver.
* **Cache Invalidation Traps**: Mid-session MCP changes, dynamic system prompt edits, model switches, and pauses exceeding TTL (5 min on API keys; 1 hr on subscriptions) invalidate the cache. The tool schema and system prompt prefix must remain strictly static.

### 7. Compaction Strategy & Durable Task State in Files
* **Compaction Economics**: Compacting at 150k tokens costs ~$0.25 and saves ~$0.025 per subsequent turn, breaking even in ~10 turns. Never compact right before task completion.
* **Preserving Durable Task State**: Because context auto-compacts and drops older turns, the agent must keep its active task checklist in a file (`TASKS.md` or the tracking issue body) rather than relying on session memory.
* **Model Tiering**:
  * Routine search, logs, and lookups → Cheap models (Flash, Sonnet, Haiku).
  * Implementation, complex refactoring, and code review → Opus 5.5.
  * Avoid the "opusplan" inversion (Opus planning + Sonnet coding) for non-trivial code.
  * Two-strike escalation to Fable 5.1 when Opus on xhigh fails twice.
