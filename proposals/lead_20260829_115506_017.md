# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**MODULES: resident services — spawn once, stream events over stdin**

*Project description:*
**What problem would this solve?**

Every module command today is a fresh subprocess: startup, each `[[events]]` hook, each action (`src/module/runtime.rs`). That is the right default — a module can't leak, hang the server, or hold state it shouldn't — but it makes one class of module needlessly expensive: anything that reacts to *many* events and keeps a small amount of state between them.

Concrete case: an agent-usage widget (session / weekly rate-limit meters, tokens by day and model — the thing omarchy's bar shows for Claude Code and Codex). The natural trigger is `pane.agent_status_changed`, because that is exactly when the numbers move. With four agents running, one hook firing per status change means two process spawns per event (the hook, then `luvus bar push` to call back), each re-reading its caches from disk, each rebuilding its view of the world from `LUVUS_MODULE_CONTEXT_JSON`. A Python hook adds ~30 ms of interpreter boot on top. None of that work is the module's actual job.

There is no sanctioned alternative. A startup hook that simply never exits *almost* works, but:

- it pins one of the 32 `Running` slots forever (`MAX_IN_FLIGHT`);
- its stdout is capped at 64 KiB and then dropped, so `module log` goes blind;
- nothing stops it on `module disable`, `module unlink`, or server stop — it is orphaned;
- nothing restarts it if it crashes;
- it never learns that its settings changed (hooks re-read env on every spawn; a resident process can't).

**What would you like to happen?**

A `[[services]]` manifest table: a process luvus spawns **once**, supervises, and talks to over stdio.

```toml
[[services]]
id = "collector"
command = ["bin/agent-usage", "serve"]
events = ["pane.agent_status_changed", "workspace.created"]   # optional; default: all
restart = "on-failure"                                        # always | on-failure | never
platforms = ["linux", "macos"]
```

Half of it already exists. `App::emit_event` publishes every lifecycle event to `events.subscribe` subscribers as sequenced `{"event","sequence","data"}` frames *before* it fans out to hooks. The missing half is a process luvus owns, and delivery that doesn't require the module to open the socket. The framing I'd propose: **stdio is a third UHP transport** — `protocol/README.md` already says sockets and named pipes are transports only.

*Lifecycle.* Spawned where startup hooks run (link, enable, server start), cwd = module root, same env as hooks minus per-target context (a service asks for state; it isn't invoked *against* anything). luvus keeps the `Child`. On disable / unlink / server stop: close stdin (EOF = polite stop), wait 2 s, SIGTERM, wait, SIGKILL (`TerminateProcess` on Windows), with a drop guard so a panic can't orphan it. On exit: log the code, restart per policy with backoff (1 s doubling to 30 s; five crashes in a minute → mark failed in `module info`, stop). Services have their own small cap and don't count against `MAX_IN_FLIGHT`.

*stdin → service.* NDJSON, one frame per line. Event frames are byte-for-byte the existing UHP event schema — `publish_event` already builds each line as an `Arc<str>`, so fan-out to services is handing the same `Arc` to one more writer. Filtered by the manifest `events` list. Plus two control frames luvus needs: `module.settings_changed` (with the new values) and `service.lag {dropped, after_sequence}` when the service doesn't drain — a bounded writer channel, drop-oldest, never blocking the app thread; the sequence tells the service exactly what it missed so it can resync by querying.

*service → stdout.* Two steps, two PRs:

1. **Logs only.** Lines go to a per-service ring buffer shown by `module log <id>`, replacing the 64 KiB cap. The service calls back over the socket like any hook — but holds its connection, so a compiled service produces zero forks per event.
2. **stdio as UHP.** A stdout line that parses as `{"id","method","params"}` is dispatched exactly as a socket request, attributed `source = "module:<id>"`, response written back on stdin. The service never touches the socket, and luvus gains a principal for every module request — which is what per-module permissions would need later. Needs the request dispatch in `ipc/api.rs` factored out of the connection loop; that refactor stands on its own.

*Trust.* Same level as hooks — modules are unsandboxed either way. What changes is that a service can't hold the app thread: stdin writes happen on a writer thread, stdout is drained by a reader thread, and the app only ever sees `AppEvent`s. Identity env stays non-overridable.

**Why it's worth having in core**

- It's the difference between "a module can react to events" and "a module can be a live component": a usage meter, a CI watcher, a port scanner, an MQTT bridge, a language-server-style helper — anything that is naturally a loop, not a script.
- It removes the incentive to write the daemonizing-startup-hook hack, which is already possible today and has every failure mode listed above.
- It's additive. Nothing about `[[events]]`/`[[actions]]`/`[[startup]]` changes; the fire-and-forget model stays the default and the right choice for most modules.
- The Go/Rust/compiled module story gets a reason to exist beyond `buzz`. Today a compiled module pays a build step to save 30 ms per hook; with services it pays it to become resident.

**Alternatives**

A module can't do this itself — the lifecycle is the part only core can own. The workaround (startup hook that daemonizes and reads `luvus uhp events`) is what this replaces.

**Where it lands**

| File | Change |
|---|---|
| `src/module/manifest.rs` | `Service` struct, `services: Vec<Service>`, validation (argv, `events` ⊆ `KNOWN_EVENTS`, restart enum, platforms) |
| `src/module/runtime.rs` | `ServiceSupervisor`: spawn, writer/reader threads, backoff, stop ladder |
| `src/app/modules.rs` | start on startup/enable, stop on disable/unlink, status for `module info` |
| `emit_event` | services fan-out after `publish_event` |
| server stop path | stop services before the socket closes |
| `src/ipc/api.rs` | (step 2) factor request dispatch for the stdio reader |
| `protocol/uhp/v1`, website docs, `skills/luvus-module/SKILL.md` | the table and the frames |
| `examples/modules/` | a service example |

Step 1 is roughly 400–500 lines of Rust plus tests; a `sh -c 'while read l; do …; done'` fake service tests spawn / stop / restart hermetically, following `startup_hooks_run_once_and_again_after_re_enable`.

I'm happy to implement this — step 1 as a docs/ plan and a PR, step 2 once the shape has survived contact with a real service. Mostly looking for a yes/no on the direction and on `[[services]]` vs. another name before writing code.
