### Problem or use case

`WebviewController` provides `openDevTools()`, but there is currently no API to prevent end users from opening WebView2 DevTools themselves.

WebView2 enables DevTools access by default, so users may be able to open DevTools through keyboard shortcuts such as F12 or Ctrl+Shift+I, or through  the context menu's "Inspect" item when default context menus are enabled via  setDefaultContextMenusEnabled(true).

When WebView is used as an application rendering surface rather than as a general-purpose browser, applications may want to disable these DevTools entry points for end users.

A common example is keeping DevTools available during development while disabling end-user access in release builds.

### Proposed behavior or API

Add a controller method that allows applications to enable or disable user access to WebView2 DevTools.

For example, to keep DevTools available during development but disable them in release builds:

```dart
import 'package:flutter/foundation.dart';

await controller.setDevToolsEnabled(!kReleaseMode);
```

A possible API could be:

```dart
/// Enables or disables the user's ability to open WebView2 DevTools.
///
/// This controls user-facing DevTools entry points such as keyboard
/// shortcuts and the relevant context-menu action.
Future<void> setDevToolsEnabled(bool enabled);
```

The implementation could use WebView2's `AreDevToolsEnabled` setting.

Expected behavior:

- Passing `false` prevents users from opening DevTools through WebView2's user-facing entry points.
- Passing `true` enables those entry points again.
- The method should follow the same lifecycle and error-handling conventions as other `WebviewController` methods.
- This setting should not be treated as a security boundary.

One point I would like the maintainer's input on is how the existing `openDevTools()` method should behave while DevTools access is disabled. Today, the native implementation calls `OpenDevToolsWindow()` and always reports success, so if WebView2 ignores the call while DevTools are disabled, the Dart call would complete without error and without opening a window.

Possible options:

- (a) Leave `openDevTools()` unchanged and document that it may have no effect while DevTools are disabled.
- (b) Make `openDevTools()` throw a `PlatformException` while DevTools are disabled, so callers can detect it.
- (c) Keep allowing `openDevTools()` to open DevTools programmatically, if WebView2 permits it, so apps can still offer an explicit developer-only entry point.

My preference would be (a), but I am happy to follow the project's preferred behavior.

### Compatibility and defaults

This would be an additive API and should not change the behavior of existing applications.

DevTools should remain enabled by default, matching the current behavior and WebView2's default.

The plugin would only change `AreDevToolsEnabled` when an application explicitly calls the new API.

Therefore:

- existing applications would continue to behave as they do today;
- no migration would be required;
- no existing public API signatures would need to change;
- applications could opt in to disabling DevTools when needed.

`AreDevToolsEnabled` is part of WebView2's settings API, so the feature should map directly to the underlying WebView2 capability.

### Alternatives considered

I considered adding this as an initialization-only option instead of a runtime controller method.

An initialization-only option would make sense if DevTools access were expected to remain fixed for the lifetime of the WebView. However, a controller method would be more flexible for applications that want different behavior between development and release builds or need to change the setting at runtime.

I am open to using an initialization option instead if that better matches the project's API design.
