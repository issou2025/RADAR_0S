*Project description:*
## Summary

Integrate the functional intent of PR #12 ("Fix dart2wasm standalone exports") into `main`, then harden `wasm_ffi` so it is clean, testable, and compatible with the current stable Dart/Flutter toolchains.

As of 2026-09-02, the current stable toolchains are Dart 3.13.x and Flutter 3.47.x. The implementation should validate against the current stable channels and avoid unnecessarily raising the package's minimum SDK beyond what the code/dependencies actually require.

This issue is intentionally self-contained so an autonomous coding agent can execute it without requiring additional design decisions.

## Context

Current `main` is `wasm_ffi 2.3.0` with:

- Dart SDK constraint `^3.10.8`
- standalone Wasm support
- Emscripten/JS-glue support
- `dart:js_interop` based WebAssembly interop

PR #12 is currently open and mergeable, but has no CI status attached to its head commit. It fixes a real `dart2wasm` runtime incompatibility:

- standalone Wasm exports are surfaced as JavaScript `JSFunction` values under `dart2wasm`
- current code discovers/casts them using Dart `Function` assumptions
- current standalone `lookupFunction()` bypasses the normal `NativeFunction -> asFunction()` marshalling path
- this can cause function lookup/invocation failures at runtime even when compilation succeeds

PR #12 also adds marshalling support needed for correct native signatures, including pointer and 64-bit/pointer-sized argument handling.

Related existing issue: #8 ("Supported when compiling Flutter with --wasm?").

Downstream motivation includes `vm75/sweph.dart`, which needs reliable standalone Wasm function lookup and typed FFI calls when the Dart/Flutter application itself is compiled with `dart2wasm`.

## Goal

Make `wasm_ffi` reliably support standalone WebAssembly libraries from both:

1. normal Dart/Flutter web builds, and
2. Dart/Flutter web builds compiled with `dart2wasm` / `flutter build web --wasm`

while preserving existing Emscripten behavior and the public API as much as practical.

The result should be release-ready: analyzable, formatted, tested, buildable, and validated in a real browser runtime.

## Required implementation scope

### 1. Review and integrate PR #12

Use PR #12 as the primary implementation reference, but do **not** blindly merge it.

Rebase/re-implement the necessary changes onto current `main`, keeping only changes required for correctness, maintainability, tests, examples, and documentation.

At minimum, verify and integrate the following concepts from PR #12 where still applicable:

- identify standalone Wasm function exports using JS interop semantics such as `typeofEquals('function')`, rather than Dart `value is Function`
- preserve exported WebAssembly functions as `JSFunction` values
- route standalone `lookupFunction<T, F>()` through the same typed path as:
  - `lookup<NativeFunction<T>>()`
  - `NativeFunctionPointer.asFunction<F>()`
- allow the marshalling/invocation layer to handle both:
  - ordinary Dart `Function` targets where appropriate
  - JavaScript `JSFunction` targets under `dart2wasm`
- add a web-specific invocation path for `JSFunction` without introducing package-local code generation or annotation/build-runner requirements
- preserve correct conversion of Dart arguments/results to JS/Wasm values
- preserve pointer binding to the correct `Memory`
- correctly handle native 64-bit values and pointer-sized values that require JavaScript `BigInt`
- correctly handle:
  - `Int64`
  - `Uint64`
  - `IntPtr`
  - `UintPtr`
  - `Size`
  - `Pointer<T>`
  where relevant to wasm32/wasm64 marshalling
- preserve existing Emscripten module support

Prefer a clean direct solution. Do not reintroduce the earlier annotation/builder/generated-wrapper approach that preceded PR #12 unless a current Dart limitation makes it strictly necessary and this is demonstrated in the issue/PR.

### 2. Eliminate current test/runtime gaps

PR #12 notes that `dart test` fails at baseline because some package code imports web-only `dart:js_interop` APIs.

Do not leave this as a known baseline failure.

Restructure imports/tests as needed so platform-specific code is isolated correctly and the project's supported test commands are deterministic.

Acceptable approaches include conditional imports/exports, web-specific test targets, or separating VM-safe units from browser-only integration tests.

Do not "fix" this by broadly skipping tests or suppressing failures.

### 4. Validate against current stable Flutter

- `flutter build web`
- `flutter build web --wasm`

A successful build is **not** sufficient by itself. The implementation must also exercise runtime function lookup/invocation in a browser.

### 5. Add runtime regression coverage

Add or improve automated browser/runtime coverage so the original failure cannot silently return.

The test fixture should expose a small native library with representative functions. Reuse the existing example fixture where practical rather than creating a parallel framework.

Cover at least:

- standalone Wasm module loading

### 6. Error handling

Replace brittle null-check/cast failures in the affected lookup/invocation path with intentional exceptions where practical.

Failures should identify the operation/symbol sufficiently for a developer to diagnose:

- missing export
- symbol exists but is not a function
- unsupported marshalling/signature
- unavailable browser-only invocation path

Do not swallow JavaScript/WebAssembly exceptions.

### 7. CI hardening

The repository currently only has a publish-oriented workflow. It does not provide a dependable PR validation gate, and the existing publish workflow's path check should also be reviewed for correctness for this root package.

Add/update CI so pull requests and pushes to `main` validate the library without publishing.

CI should use supported stable toolchains rather than pinning an unnecessarily old SDK.

Required CI gates:

- dependency resolution
- formatting check
- `dart analyze`
- VM-safe unit tests
- web/browser tests required by this issue
- pure Dart `dart2wasm` compilation/runtime validation
- Flutter example:
  - `flutter build web`
  - `flutter build web --wasm`
- package validation:
  - `dart pub publish --dry-run`

Use caching where simple and safe, but do not make CI complexity part of the product design.

Publishing must remain non-destructive during this issue: do not automatically publish a package release merely because the implementation lands.
