# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Test corpus: a deterministic revision chain of one model for ifc-git flows**

*Project description:*
## What

A deterministic **revision chain** of one real IFC model — a committed base plus N derived revisions, each applying one declared, realistic change — together with a manifest pinning the expected diff for every step.

Part of #8038. Needed before any ifc-git flow can be tested honestly.

## Why the current corpus cannot test versioning

`tests/models/manifest.json` catalogues 182 files and 1.14 GB, and none of it is a version history. Every entry is a standalone model. The only base/head pair in the repo is `apps/viewer/public/samples/building-architecture.ifc` and its `-rev-b` variant, derived by `tools/demo-kit/derive-variants.mts` — two revisions of a 226 KB sample, built for the tours walkthrough rather than for versioning.

That is enough to exercise `diff`. It is not enough to exercise anything ifc-git claims:

- `log`, `rebase` and `revert` need a chain, not a pair.
- Compare-and-swap on a head needs two deliveries that share a parent.
- The **GUID-agnostic** claim needs a re-export that regenerates every `GlobalId` while changing nothing semantically. Nothing in the corpus does this, and it is the single most important case: it is what real authoring tools do on every from-scratch export, and it is exactly what a naive implementation gets wrong.

The diff engine's own test suite has the same shape — 2,315 generated oracle cases across nine corpora, all synthetic, plus exactly one test that touches a real model (`buildFingerprints.typeObjects.real.test.ts`). Parity is well covered; behaviour against real exporter output is covered once.

## Proposal

A generator at `tools/ifc-git-corpus/`, following the established pattern of `tools/demo-kit/derive-variants.mts`: derive from committed base bytes, never modify the base, and **self-verify every declared change by running the real diff engine during generation**.

Base: `apps/viewer/public/samples/building-architecture.ifc` — already committed, already the demo kit's base, 226 KB, no licensing question.

Revision classes, each chosen to exercise one thing ifc-git has to get right:

| Rev | Change | Exercises |
| --- | --- | --- |
| `r00` | the base, unmodified | first commit, `parents: []` |
| `r01` | one property value in one property set | change localisation: exactly `pset:<Name>` on one element |
| `r02` | one element moved | placement/geometry change with data unchanged |
| `r03` | one element added | `added` |
| `r04` | one element deleted | `deleted` |
| `r05` | one element's `Name` changed | `attr:core` only |
| `r06` | a classification added | component **key presence**, not an "empty" hash |
| `r07` | **re-export: every `GlobalId` regenerated, new header timestamp, nothing semantic changed** | **GUID-agnostic identity — must produce NO commit** |
| `r08` | byte-identical re-save | empty diff — must produce NO commit |
| `r09` | a type object's property set changed, occurrences untouched | the #8040 class: types tracked, not only occurrences |
| `r10` | one element split into two | split/merge claims |
| `r11` | a **shared** property set edited | the localisation payoff: one node change, N element markers |

`r07` is the one that cannot be faked by a synthetic fixture, and the one that would have caught the defect recorded in #8038 §6.1 — node-hash v0 hashes the entity `key` into the `element` node, so a re-GUID changes every element address.

Determinism comes from `uuidFromSeed` + `uuidToIfcGuid` (`@ifc-lite/encoding`), so `r07`'s fresh GUIDs are reproducible and the manifest's SHA-256 pins are real pins rather than decoration.

## Deliverables

1. `tools/ifc-git-corpus/derive-revisions.mts` — the generator.
2. `tools/ifc-git-corpus/revisions.json` — committed manifest: per revision, its parent, declared change class, SHA-256, and the **measured** diff (counts, changed component keys, affected `GlobalId`s).
3. Generated `.ifc` files are **not committed**. They are reproducible from the base, so the manifest is the artifact and the bytes are regenerated on demand — consistent with the repo's "fixtures are catalogued, not committed" rule, and it keeps ~2.7 MB of derived bytes out of git.
4. A test that regenerates the chain and checks it against the manifest, skipping cleanly when the base or built `dist/` is absent.

## Out of scope

- **Real authoring-tool revisions.** A chain of genuine successive exports from Revit or ArchiCAD would be better evidence than anything derived, and cannot be fabricated. Worth obtaining separately; this issue delivers what can be built now and states its own limits.
- Multi-megabyte scale chains. The scale question belongs with the performance work, against `ara3d/ISSUE_053_20181220Holter_Tower_10.ifc` (177 MB) and `various/O-S1-BWK-BIM architectural - BIM bouwkundig.ifc` (343 MB).
- Federation chains across several repositories.

## Honest limitation

A derived chain tests ifc-git against **our own** idea of what a revision looks like. It proves the machinery handles the change classes above; it does not prove real exporters only produce those classes. `r07` narrows that gap because regenerated GUIDs and a moved timestamp are what real tools actually do, but the gap does not close without real successive exports.
