*Project description:*
## What & why

The Energy tab's solar-forecast card is currently overestimating generation. The real array has **two orientations**: ~90% of panels face south at 15° tilt, and two panels face north at a -15° tilt (mounted the opposite way). The forecast model only supports a single tilt/azimuth for the whole array, so the north-facing panels are being modeled as if they matched the south-facing majority — a north-facing panel produces much less than a south-facing one at the same tilt, so the estimate skews high. Fix the model to reflect the real physical layout, and evaluate whether pulling from PVGIS (the EU JRC's official solar radiation/PV performance API) would make the estimate more realistic than the current Open-Meteo source.

## Current state

- `src/pv_system_config.py:33-40` — `PvSystemConfig` holds exactly **one** `kwp` / `tilt_deg` / `azimuth_deg` / `performance_ratio` tuple for the entire array, loaded from `config/pv_system.json` (gitignored; `config/pv_system.sample.json` is the committed template).
- `src/pv_forecast.py:66-153` — `fetch_pv_forecast()` makes a single Open-Meteo `global_tilted_irradiance` (GTI) request at that one tilt/azimuth and scales it by the one `kwp` and `performance_ratio` (`expected_W = kwp · GTI/1000 · performance_ratio`). There is no concept of multiple sub-arrays.
- `docs/pv-forecast.md` documents the model and already made this trade-off once, deliberately: "The dedicated `pvgis` sister repo is the more faithful PV-estimate path; this card deliberately stays self-contained and approximate (the source chosen for issue #39)." It also has a calibration table showing how to translate a PVGIS `loss` % into this model's `performance_ratio` — i.e. PVGIS is already used indirectly today, just as a one-time tuning input, not a live source.
- Sister repo `E:\automation\pvgis` already computes a PVGIS-based estimate for this same house (`.env`: `HOME_PEAKPOWER_KW` / `HOME_TILT_DEG` / `HOME_AZIMUTH_DEG` / `HOME_LOSS_PCT`) — single orientation there too, as far as this repo's docs reference it.

## Proposed approach

Two parts, sequenced so the accuracy bug isn't blocked on the larger source question:

**1. Multi-sub-array support (fixes the immediate bug, no new data source needed).** Extend `PvSystemConfig` / `config/pv_system.json` from one flat tuple to a list of sub-arrays, each with its own `kwp` / `tilt_deg` / `azimuth_deg` (e.g. `[{"kwp": 7.9, "tilt_deg": 15, "azimuth_deg": 0}, {"kwp": 0.9, "tilt_deg": 15, "azimuth_deg": 180}]` — note: a panel "tilted -15° facing north" and "tilted +15° facing the 180°/north azimuth" are the same physical panel under Open-Meteo's tilt≥0 + azimuth convention; the config should normalize to one signed convention rather than accepting negative tilt). Fetch GTI per sub-array (check whether Open-Meteo's API accepts repeated `tilt`/`azimuth` params in one call, or needs one call per sub-array) and sum each sub-array's weighted Wh into the total. Migrate `config/pv_system.sample.json` and the real (gitignored) `config/pv_system.json` to the new shape; keep the single-tuple shape loadable too (treated as one sub-array) so existing configs don't silently break.

**2. Evaluate PVGIS as a data source.** PVGIS's `seriescalc`/`PVcalc` tools return **typical/historical** irradiance (a representative year), not a live day-ahead forecast for a specific real date — a real mismatch with this card's yesterday/today/tomorrow use case. Before building, decide which of these PVGIS actually fits:
   - a **calibration feature** (e.g. a debug/admin view comparing "PVGIS says your annual/typical output is X" against what the current `performance_ratio` implies, to help tune it) — lower risk, complements the existing calibration table in `docs/pv-forecast.md`;
   - a **full source swap** for the live forecast — only viable if PVGIS also exposes forward-looking data suitable for "tomorrow," which needs verifying against the actual API before committing;
   - or **staying on Open-Meteo GTI** for the live card and treating PVGIS purely as an occasional cross-check, not a live dependency.

   Either way, per sub-array PVGIS call, same weighting approach as above, and no hard dependency on the sister `pvgis` repo (this Energy tab stays self-contained, per its existing convention) — call the PVGIS HTTP API directly if pursued.
