# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**IfcSurfaceCurveSweptAreaSolid ignores ReferenceSurface: non-circular sections are rolled 90° (Revit slab edges, light fixtures)**

*Project description:*
### Summary

`SurfaceCurveSweptAreaSolidProcessor` orients the section with a rotation-minimising frame and does not read attribute 5 (`ReferenceSurface` / `FixedReference`). The doc comment in `rust/geometry/src/processors/swept/surface_curve.rs` says that the exact roll of a non-circular section "is not modelled (no such case is known in the wild)". Here are two such cases, from a Revit export of Autodesk's public *Snowdon Towers* sample.

Both directrices are planar circular arcs. Even so, the section comes out rolled 90° about the tangent:
- for a slab edge, the profile's width and height are swapped;
- for a wall sconce, the shape collapses to about a quarter of its area.

The same happens in the hosted viewer at ifclite.com and in `@ifc-lite/geometry` 8.0.2 (and 7.6.0).

### Reproduction

### Expected (ISO 10303-42, repeated in the IFC4 / IFC4.3 documentation)

> The orientation of the SweptArea as it sweeps along the Directrix is precisely defined by an IfcCartesianTransformationOperator3D with attributes: LocalOrigin as point (0,0,0), Axis1 as the normal N to the ReferenceSurface at the point of the Directrix with parameter u, Axis3 as the direction of the tangent vector t at the point of the Directrix with parameter u.

### Proposed fix (PR ready, see below)

Keep the processor and the sweep as they are, and build the per-sample frame from attribute 5 instead of the rotation-minimising frame:

- **Axis1 by reference type:**
  - `IfcSurfaceOfLinearExtrusion`: Axis1 = t × ExtrudedDirection, which is the surface normal ∂S/∂u × ∂S/∂v with the directrix running along the swept curve. ExtrudedDirection is rotated by the surface's Position.
  - `IfcPlane`: Axis1 is the plane normal (its Position's +Z) with the component along t removed.
  - `IfcFixedReferenceSweptAreaSolid`: Axis1 is the FixedReference with the component along t removed.
- **The other two axes:** Axis2 = t × Axis1, the same handedness as the current RMF frame, so `sweep_profile_along_frames` and the winding are unchanged.
- **Placement:** the reference is read in the solid's frame and rotated by the solid's Position, like the directrix.
- **Fallbacks:** an empty slot 5, any other surface type, or a sample where the reference is parallel to t keep the current RMF frame. Circular profiles, such as the duct elbows from #1485, are unaffected.

Validated two ways:
1. **Python prototype of the same frame**, on the attached file:
   - slab edge #99: bounding box identical to IfcOpenShell to the millimetre (6.383 × 3.251 × 0.254), centroids 0.8 mm apart;
   - sconce #135: 0.707 × 0.933 × 0.187 against 0.705 × 0.933 × 0.187, centroids 6 mm apart.
2. **The Rust patch, built against `main` (fc6eceba) on the pinned nightly.** All of `rust/geometry` passes: 3083 tests, 0 failed. So do the `mesh_determinism` manifests, with no re-pin needed. It also adds unit tests for the three references, plus an integration test with a neutral fixture (`tests/fixtures/surface_curve_reference_roll.ifc`, a Revit-style trimmed circle in degrees, `IfcSurfaceOfLinearExtrusion` along −Z, asymmetric profile).

We are happy to open the PR if you agree with the approach.

### Note: the authoring model differs (a separate exporter issue)

In Revit itself, these elements do not match the ISO result either. Read from Revit's own solids, the slab edge stands upright (0.254 wide × 0.203 tall) and the sconce is a narrow cone, 0.406 m tall. So the Revit exporter appears to write a `ReferenceSurface` that does not describe its own geometry. That is a problem for the exporter, and we can report it there separately.

The file itself is valid (`ifcopenshell.validate --rules` reports no issues), and ifc-lite should render what the file encodes. After this fix, ifc-lite matches IfcOpenShell on these files, not the view in Revit.

### Context

We ran into this while comparing web IFC engines element by element against IfcOpenShell on real models. None of the other web engines we tested gets these elements right yet either.
