# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Add a `widgetbook test` command to run selected scenarios**

*Project description:*
Coding agents and developers need a quick way to check that new or changed stories still render.
Today that means running `flutter test` on `test/widgetbook_test.dart`, which has three gaps:

- It runs the whole catalog; `--plain-name Button` also matches `IconButton`, and test names don't map to the `.stories.dart` file that was just edited.
- A new story only exists after `build_runner` has run; if it hasn't, the story is silently not tested and the run is green.
- Its output has to be scraped to find out which scenario failed and where its snapshot is.

`widgetbook test` wraps `flutter test` to close these gaps.

## Command

```sh
widgetbook test [--path <file|folder|glob>]... [--filter <Component[/Story[/Scenario]]>]... \
  [--no-snapshots] [--no-build-runner] [--target <test file>] [-- <flutter test args>]
```

It runs in the Widgetbook project directory (the current directory) and:

1. Runs `dart run build_runner build`, unless `--no-build-runner` is passed.
2. Resolves `--path` and `--filter` into one `--name` regex.
3. Runs `flutter test <target> [--name <regex>] [--dart-define=WIDGETBOOK_SNAPSHOTS=false] [<pass-through args>]`, streaming its output.
4. Exits with a code and message that say what went wrong (see below).

## Selecting scenarios

| Flag | Selects | Repeatable |
|---|---|---|
| `--path` | `.stories.dart` files, folders (every `*.stories.dart` below), globs | yes |
| `--filter` | `Component`, `Component/Story` or `Component/Story/Scenario`; `*` matches a whole level | yes |

```sh
widgetbook test                                             # whole catalog
widgetbook test --path lib/src/counter.stories.dart
widgetbook test --path lib/src/buttons/ --path 'lib/**/avatar*.stories.dart'
widgetbook test --filter Counter
widgetbook test --filter Counter/Default
widgetbook test --filter "Counter/Default/Loading • Dark Mode"
widgetbook test --filter '*/Default'                        # every component's Default story
```

- Everything matched by any `--path` or `--filter` runs (union); no `--path` and no `--filter` runs everything.
- Each level matches a whole name, so `Button` does not match `IconButton`.
- `--path` is resolved to component names by statically analyzing the stories files, as `widgetbook coverage` does (`ShallowAnalyzer` + `ComponentCollector`), including a `ComponentMeta(name: ...)` override.
- Globs are expanded by the CLI, so quoted patterns behave the same on every shell.
- Test names are `"<Component> <Story> <Scenario>"`, so the selection becomes one anchored, escaped regex, e.g. `--filter Counter/Default` becomes `--name '^Counter Default '`.
  Repeated `--name` flags are ANDed by `flutter test`, so multiple selections must be combined into a single alternation (`^(Counter|Avatar) `).
- Names containing spaces can make the regex match a few extra scenarios.
  That is acceptable: the selection may run more than needed, but never less.
- Component folders are not part of test names, so `--filter` cannot select by folder; `--path` covers that.

## Other options

- `--no-snapshots` passes `--dart-define=WIDGETBOOK_SNAPSHOTS=false` (#2084): scenarios still build and run, but no PNG or JSON is written.
  Snapshots stay on by default; on a small selection they are cheap, and agents can look at the PNGs.
- `--no-build-runner` skips the `build_runner` step, e.g. when `build_runner watch` is already running.
  On an up-to-date project the step is a ~2s no-op, so it is on by default.
- `--target` sets the test entry file, defaulting to `test/widgetbook_test.dart` as created by `widgetbook init`.
- Arguments after `--` are passed to `flutter test` unchanged.

## Errors and exit codes

Each case gets its own exit code and a message that names the cause:

| Situation | Detected by | Message |
|---|---|---|
| A `--path` matches no file | file check / glob expansion | `lib/x.stories.dart not found` |
| A file declares no component | static analysis | `lib/x.dart declares no Widgetbook component (expected a .stories.dart file with const meta = Meta(...))` |
| Selection matched no test | `flutter test` exits with 79 | `Component "Counter" (lib/x.stories.dart) ran no scenarios; its generated code may be stale. Run without --no-build-runner.` |
| All matched scenarios are skipped | skipped count | `All scenarios of "Counter" are excluded via excludeFromTests` |
| `build_runner` fails | its exit code | its output, then stop before testing |
| A scenario fails | `flutter test` exit code | `flutter test` output |
| The project's `widgetbook` version does not support a flag | `pubspec.lock` | `--no-snapshots requires widgetbook >= <version>` |

The CLI is installed globally while `widgetbook` comes from each project's pubspec, so the version check prevents a define from being silently ignored.

## Implementation notes

- A `CliCommand<TestArgs>` with `test_args.dart`, registered in `CliRunner`, following `coverage`.
- `ExecutableManager.runFlutter` buffers output via `ProcessManager.run`; this command needs a `ProcessManager.start`-based helper that streams output, returns the exit code and forwards Ctrl-C to the child process.
- Tests inject a `ProcessManager` and assert the exact `build_runner` and `flutter test` invocations for each flag combination, plus the error cases.
- Check what happens when `build_runner build` runs while `build_runner watch` is running; if they conflict, detect the watcher and skip the build step.
- Docs: a `docs/cli/commands/test.mdx` page and an entry in `docs/cli/index.mdx`; `docs/agentic/*` should use `widgetbook test --path <file>` in the self-correct loop instead of plain `flutter test`.

## Later

Not part of the first version:

- `--reporter json`: one entry per scenario with its path, result, error, snapshot PNG/JSON paths and accessibility violation count, built from `flutter test --reporter json` and the snapshot JSON.
- `--changed [--base <ref>]`: select the stories files changed against a base ref.
- Delete the existing snapshot files of the selected scenarios before running, so no stale PNG/JSON is left behind.

Making accessibility violations fail a scenario is a separate change in `AccessibilityConfig`; this command only reports them.
