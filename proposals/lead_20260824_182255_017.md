**[Bug]: browser.use_gateway is silently stripped by the tools picker, breaking the managed (Nous/Browser Use gateway) connection**

*Project description:*
### Bug Description

Two changes landed independently and now conflict. Selecting "Browser Automation" in hermes tools silently drops browser.use_gateway from config, but the Browser Use CLI harness still reads that exact key to decide whether to connect through a managed gateway or spawn Browser Use locally. Once the key is gone, the harness gets neither a managed CDP endpoint nor autospawn, and falls through to hunting for a local Chrome install, which fails outright on any headless host with no local browser.

Root cause: tools/browser_use_cli.py:506-520 reads browser.use_gateway to distinguish a managed gateway connection from a direct local Browser Use instance. The tools picker's _set_selection() in hermes_cli/tools_config.py:4419-4456 runs section.pop("use_gateway", None) whenever the Browser Automation section is (re)selected, unconditionally removing the key browser_use_cli.py depends on. These appear to be diverging commits: 7e04718ec3 introduced/relied on use_gateway; a later change around 7f83d3808c / b10c5a8084 had the picker stop writing it, without updating the reader to match. No test currently exercises browser.cloud_provider: nous end-to-end through _resolve_backend_cdp(), which is likely why the mismatch shipped.

(Separately, working as intended, noted for anyone tracing the path: tools/browser_tool.py:833 remaps cloud_provider: nous to the browser-use provider for registry lookup, since Nous isn't a standalone provider, it's Browser Use with a Portal token attached.)

No traceback to attach, this is a silent misconfiguration, not a crash.

Duplicate check: searched open and closed issues for use_gateway, cloud_provider nous, browser_use_cli, and managed gateway browser. No existing issue covers this.

### Steps to Reproduce

Steps to Reproduce
Configure a managed browser backend, e.g.:
yaml
   browser:
     cloud_provider: nous
     backend: browser-use
     use_gateway: true

with the browser-browser-use plugin enabled. 2. Run hermes tools and (re)select "Browser Automation", or otherwise trigger the picker's _set_selection() for the browser section. 3. Inspect config: use_gateway is gone. 4. Call browser_exec. Instead of using the managed CDP endpoint, it searches for a local Chrome install and fails on any host without one.

### Expected Behavior

Reselecting "Browser Automation" in hermes tools should not remove use_gateway, or browser_use_cli.py should resolve managed-vs-local some way that doesn't depend on a flag the picker can silently delete. Either way, browser_exec should keep using the managed CDP endpoint after running the picker, with no manual config repair needed.

### Actual Behavior

After (re)selecting "Browser Automation" in hermes tools, browser.use_gateway is removed from config.yaml. browser_exec then fails to reach the managed gateway and instead searches for a local Chrome installation, which fails outright on a headless host with none installed. The only way to recover is to manually restore the key: hermes config set --force browser.use_gateway true.
