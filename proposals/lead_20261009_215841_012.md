## Tested flow ledger for #7536

Which product flows have been tested end to end on this branch, how, by whom, and with what result. Sub-issue of the work ledger #8493. The runbook for running each flow: `dev/docs/runbooks/upgrade-and-flow-testing.md`.

This body holds the templates, rules, the upgrade matrix, the custom and product flows, prerequisites, an area index, findings and the log. Each area's full table is a pinned comment, linked from **Areas**.

## How to use this ledger

Copy a template into a comment on this issue. Keep it short; the coordinator copies the result into the row.

**1. Claim a row**

```text
claim <ROW-ID>
planned: <YYYY-MM-DD>
tool: <vd:… | api:… | wr:… | ul:… | e2e:… | sql | manual | cli>
```

**2. Report a result**

```text
result <ROW-ID>: <✅ | ❌ | 🟡>
tested by: <@handle | lane:<id> (model)>
date: <YYYY-MM-DD>
commit: <sha or branch@sha>
prereqs: <P ids used>
evidence: <screenshot or recording for UI | run id, report path or commit otherwise>
failing ids: <ids, only for ❌ or 🟡>
notes: <one line>
```

**3. Add a new flow**

Add a PF row, or a row under **Beyond the UI** if the UI cannot reach it. Never as a comment.

**4. Release a claim**

```text
release <ROW-ID>
reason: <why>
```

**Rules**

- A row is ✅ only with evidence: a commit, a run id or a report path, and the date.
- **Tested by** names who ran it: a person (`@handle`) or an agent lane (`lane:<id>`, model). An agent row is re-checked by a person before release.
- Compare runs by failing ids, never by counts. A ❌ row links the fix lane or issue.
- Security findings are never described here: write "fix pending" and keep details private.
- **Claiming:** comment `claim <row id>`. The row's Status becomes 🙋 and its Tested by cell gets `⏳ @handle` or `⏳ lane:<id>` plus the date. A claim with no update in 48 h lapses and the row returns to ⬜.
- **Evidence:** UI flows need a screenshot or recording, attached in a comment and linked from the row. API, worker and data flows need a run id, report path or commit. Usage, metering, retention and isolation rows need exact counts (`sql`), never a screenshot alone.
- A ❌ lists its failing ids (finding ids below) as well as the fix lane or issue.
- Rows are tested on a fresh head stack, and again on upgraded stores (P7) where the row names an upgrade step. Never on the developer's own dev stack: one worktree and slug per flow round.
- Never name a customer.

**Legend:** ✅ passed · ❌ failed · 🟡 partial · ⏳ running · 🙋 claimed · 🔧 fixing or building · ⬜ not yet tested

### Upgrade matrix detail

The UP rows above are the headline cells; the UM rows below spread them across deployment, tenant count, data shape and tier. A UM row that names an UP id refines it: report on the UM row and the coordinator updates the UP row. Upgrade findings keep the `UPG-0xx` ids in Findings.

Each cell boots origin/main on its own `upgradelab_<cell>` stores, seeds it, sends traffic through the cut, switches the same stores to head (api first, worker after; **the worker runs the upgrade**), settles and judges the invariants. Runbook §3. Tool: `ul:<cell>`.

**Tiers.** S: 1-4 orgs, ~12 projects, ~40 users, 2,000 traces / 10,000 spans over 2 months, every product kind 1-3 times. M: 10 orgs, 100 projects, 500 users, 250k traces / 1.5M spans. L: 100+ orgs, 20,000 projects, 200,000 users, 500k traces / 5M spans (nightly snapshot, CI only). XL: L × 20 by tenant clone, ~100M spans (manual runner).
**Data shapes.** `typical` (every kind the old release can hold, plus jobs queued at the cut); personas (P33-P36); overlays `upcast-events`, `held-tenants`, `queued-jobs-v1`, `operator-damage`, `wide-traces` (50k-span traces, 1 MB attributes).

Columns: **Ingest** every OTLP, collector, log and metric post answered 2xx during the switch (N1, N2) · **API** every route serves from boot (no holds, ruling 2026-10-09); a Postgres read ahead of the schema answers `upgrade_in_progress` (503, `Retry-After: 10`) and succeeds on retry; a pending ClickHouse column reads as its typed default (N2) · **Drain** head's worker resumes the jobs queued at the cut and drains to baseline (N4) · **Projections** read models caught up and every seeded kind reads back (I5, I6) · **Rollback** origin/main on head's schema passes the HTTP smoke, re-upgrade reconciles (nightly).
