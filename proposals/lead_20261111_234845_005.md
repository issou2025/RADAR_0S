## 0. Mission — do not turn this into another report-only audit

GP must use this issue as the durable work queue and knowledge-transfer record. The objective is not to produce a large count of findings. The objective is to remove real correctness, safety, performance, and integration defects from the shared MiniAndroid runtime and prove that real APKs consume the repaired behavior.

For every item GP must:

1. Re-read the current `main` HEAD and current source before acting. Old line numbers and old patches are leads, never proof of current state.
2. Locate the exact implementation, declarations, callers, ownership rules, build target, and runtime reachability.
3. Reconcile prior reports/issues and commits before changing code. Do not duplicate or re-implement landed work.
4. Classify the claim honestly: `CONFIRMED`, `REPRODUCED`, `PARTIAL`, `PENDING`, `BLOCKED`, `FALSE_POSITIVE`, `DUPLICATE`, or `SUPERSEDED`.
5. For confirmed defects, explain the semantic contract, root cause, smallest generic fix, compatibility risks, and regression tests.
6. Implement fixes in coherent batches. Do not leave isolated helper patches disconnected from the authoritative runtime.
7. Build using the repository's canonical build. Run focused tests, the full test suite, opcode/DEX probes, and the required real-APK regression battery.
8. Prove the fix is reached through the actual production execution route and consumed by at least one real APK where applicable.
9. Update this same issue after every meaningful wave with commit SHA, changed files, exact test commands, expected/observed results, artifact hashes, and remaining blockers.
10. Never claim success from compilation, a unit test, APK parsing, process exit code, or a non-white screenshot alone.

**Core architecture law:** MiniAndroid supports different execution routes (ordinary Views, AndroidX/Fragments, Compose, JNI/native, libGDX, SDL, EGL/GLES, hybrid apps). Do not force all apps through one fake linear pipeline. Fix shared semantic primitives at the first divergence, preserve route-specific contracts, and prove the resulting app-visible behavior.

## 2. Severity and evidence vocabulary

Use these labels on every finding:

- `CONFIRMED`: source semantics prove the defect; include exact source and contract.
- `REPRODUCED`: a discriminating test or real APK demonstrates the failure.
- `IMPLEMENTED`: code change exists, not a claim of correctness by itself.
- `TESTED`: exact test command and observed result recorded.
- `OBSERVED`: runtime trace/UI evidence exists.
- `PARTIAL`: some paths fixed; enumerate remaining paths.
- `PENDING`: not yet verified or integrated.
- `BLOCKED`: concrete external prerequisite with evidence.
- `FALSE_POSITIVE`: explain the mistaken assumption.
- `DUPLICATE`: point to the canonical finding.
- `SUPERSEDED`: newer code/contract replaces this item.

Severity:
- **P0:** memory corruption, OOB, UB, invalid DEX acceptance causing unsafe reads, interpreter semantic corruption on reachable path.
- **P1:** process crash from malformed input, broken exception/stack semantics, resource exhaustion, broken lifecycle/render route, native lifetime hazards.
- **P2:** correctness/performance degradation with bounded scope.
- **P3:** maintainability/diagnostic debt; never mix with correctness claims.

Every finding must have: ID, status, severity, file/function/line at reviewed SHA, source/semantic contract, exact trigger, impact, root cause, proposed patch, regression test, integration route, and evidence.

## 4. Additional audit areas GP must discover independently

Do not limit the audit to the table above. The following areas are required because they are common sources of false success, cross-app failures, and state corruption in a compact Android runtime.

### 4.1 DEX and class-linker semantics
- Header/map-list consistency, endian handling, alignment, signed/unsigned LEB128, MUTF-8 decoding, string/type/proto/field/method index validation.
- Code-item register/ins/outs sizes, instruction width, payload alignment, packed/sparse switch payloads, fill-array-data, try/catch handler lists, debug info, annotations, encoded arrays.
- Method/field resolution by exact descriptor, class-loader identity, interface/default method order, bridge/synthetic methods, access flags, static-vs-instance rules.
- Wide register pair integrity, invoke argument word count, range invokes, result pseudo-register lifetime, move-result adjacency, exception edges, monitor enter/exit.
- Class initialization state machine, recursive initialization, initialization failure persistence, static field default values.
- DEX version compatibility, multidex ordering, secondary DEX class injection, duplicate descriptors, cross-APK class identity.

### 4.2 Interpreter and execution control
- PC bounds and instruction-boundary validation before fetch/decode.
- Every opcode's exact operand order, width, signedness, overflow behavior, floating-point semantics and exception conditions.
- Integer division/remainder corner cases, shift masking, NaN, signed zero, infinities, float/double conversions and Java rounding.
- Branch offsets relative to correct PC; goto/if/switch target alignment and target-instruction validation.
- Return-value type checks, wide-pair preservation, invoke recursion, stack cleanup, pending exception propagation and uncaught exception reporting.
- Unimplemented instructions must not silently advance into operand words.
- Fuel/instruction budgets, recursion limits, loop detection and cancellation must not corrupt interpreter state.

### 4.3 Heap, object identity and GC-like ownership
- Object handle stability, object ID reuse, stale handles, cross-engine isolation, array/object field lifetime.
- Vector/map reallocation assumptions, iterator vs pointer/reference invalidation, aliasing, snapshots and restore.
- Primitive/object arrays, multidimensional arrays, descriptor classification, covariance, bounds, null checks and store checks.
- String interning, UTF-16 storage, equality/hashCode, substring/concat, char/codepoint conversions.
- Collection shadows must have one consistent source of truth and match Java iteration/modification behavior.

### 4.4 JNI and native ABI
- JNI local/global/weak refs, handle validity, method/field ID identity, pending exceptions, modified UTF-8, primitive arrays and critical access release modes.
- DirectByteBuffer capacity/address/ownership, byte order, slices/duplicates, read-only state and cleaner/release semantics.
- Native library load order, dependency resolution, symbol visibility, duplicate SONAMEs, constructor/destructor calls, dlopen flags and unload lifetime.
- JNI ABI widths, alignment, struct packing, calling conventions, variadic calls, pointer-width handling on x86/x86_64.
- Native callbacks into Java, thread attachment/detachment, exception propagation across C ABI boundaries.

### 4.5 Android lifecycle and framework contracts
- Application/Activity/Service/Receiver/Provider lifecycle and process identity.
- Intent resolution, task stack, launchMode, PendingIntent identity/flags, URI grants, permissions and provider authority resolution.
- Context identity, resources/configuration/density/locales, theme inheritance and package boundaries.
- Handler/Looper/MessageQueue ordering, delayed messages, Choreographer/frame callbacks, cancellation and background thread behavior.
- View attach/detach, focus, input dispatch, click/touch state, layout invalidation, measure/layout/draw ordering.
- Fragment attach/host/manager/state transitions and saved state.
- ViewTree owner propagation and Compose lifecycle integration.

### 4.6 Rendering and native graphics
- Surface/Canvas/Bitmap/Drawable/Paint/Path/Region semantics and framebuffer bounds.
- EGL context/surface lifecycle, GLES state, texture uploads, shader/program behavior, blending, viewport, scissor, framebuffer completeness.
- Native renderer route selection and whether the app actually consumes the native graphics backend.
- Distinguish a working compute shader from a working graphics rasterization path; do not label SwiftShader compute success as app graphics success.
- Frame synchronization, dirty regions, resize, rotation, density, pixel format, premultiplication and alpha.

### 4.7 Resources, storage and security
- Binary XML/ARSC parsing, resource ID/package/type/entry identity, qualifiers, density and locale fallback.
- Asset path normalization, zip traversal, duplicate names, compressed/uncompressed size limits, decompression bombs and CRC.
- SQLite transaction, cursor, type affinity, statement lifecycle, locking, package-specific databases and persistence.
- File sandbox path traversal, symlink behavior, permission checks and multi-package isolation.
- Avoid shell execution on APK-controlled paths. All input sizes and decompression ratios must be bounded.

### 4.8 Determinism and multi-engine correctness
- Global/static state shared between engine instances.
- Thread safety and reentrancy of caches, JNI registries, native library maps and diagnostics.
- Stable ordering for deterministic reports and screenshot goldens.
- Reset/teardown between APKs; ensure one APK's state cannot contaminate the next.
- Repeat-run byte identity and baseline pin preservation.

## 5. Mandatory repair workflow (each wave)

### Phase A — Baseline and source proof
- Record `git rev-parse HEAD`, branch, dirty state, build compiler/version, canonical build command and binary SHA-256.
- Confirm the source line and all call sites on that exact SHA.
- Identify the relevant AOSP/DEX/JVM/AndroidX/Compose contract and record the exact semantic rule.
- Reproduce the pre-fix failure with a minimal synthetic DEX/unit probe or real APK.

### Phase B — Generic implementation
- Fix the root primitive, not a named app.
- Keep the patch minimal and local unless the root requires an architectural change.
- Add a regression test that fails before and passes after.
- Add malformed-input and boundary tests for parsers/memory-sensitive code.
- Preserve deterministic behavior and existing APIs unless a deliberate compatibility correction is required.

### Phase C — Integration and validation
- Build the canonical runtime from a clean state.
- Run focused tests and full `make test` (or the current authoritative test command).
- Run ASan/UBSan where feasible; use leak checking for ownership candidates.
- Run opcode/DEX coverage probes and test every affected branch.
- Run the canonical golden battery, including unaffected anchors.
- Run real APKs through the actual production route (not a shadow-only unit route).
- Capture runtime traces, exception state, ViewTree/provenance, layout/measure state, frame deltas, screenshots and hashes.
- Repeat at least 3 times for deterministic claims.
- Cross-test at least one second APK from a different app family for every generic fix.

### Phase D — Evidence and closure
- Record exact before/after command, exit status, test count, binary SHA, source commit, screenshot SHA, report SHA, and trace excerpts.
- State what the test does NOT prove.
- Mark partial paths and blockers explicitly.

## 6. Acceptance criteria

The master audit is not complete until:

1. All P0 candidates are either fixed and tested or explicitly refuted with source/semantic proof.
2. All P1 candidates are classified and the reachable defects are fixed or blocked with concrete evidence.
3. The DEX parser rejects malformed offset/count arithmetic safely without process crash or wrong-entry reads.
4. Every supported opcode has an exact semantic test; unsupported opcodes fail loudly and do not desynchronize PC.
5. No raw native pointer is dereferenced without a documented lifetime/ownership guarantee and validation strategy.
6. Direct-buffer allocations have explicit ownership and release tests; leak checks show no growth across repeated APK lifecycle runs.
7. C++ exceptions do not silently disappear or corrupt DEX frame/exception state.
8. Compose/View rendering tests prove actual app content, not only lifecycle success or default background.
9. At least five distinct small real APKs/games display their own real UI/content through one integrated main-runtime binary, with 3-run evidence and no golden regressions.
10. The main runtime consumes integrated contributor work; isolated patches and no-push branches do not count as integrated.
11. All remaining optimizations are backed by profile data and cannot regress semantic behavior.
