## Problem Statement

Watchdog is public on GitHub but cannot yet be adopted, deployed or relied on by anyone except its author. An audit in October 2026 scored it 0.5 to 2 out of 5 on legal, install, release, docs, community and operations readiness.

- **No license.** Without a LICENSE file the public repository is all-rights-reserved: no one may legally use, modify or self-host it.
- **No deployable artifact.** There is no container image, no production compose file, no published release. Running Watchdog means cloning the repository and reproducing the developer toolchain (nix, just, lefthook).
- **No releases or versions.** There are no tags, no changelog, no version in the app or API, and no upgrade procedure. A self-hoster has nothing to pin and no way to know what changed.
- **Unsafe defaults for a first install.** The example env file ships a placeholder secret of valid length, the first admin is created by temporarily opening signup, and invitation links are written to process logs.
- **No operator documentation.** There is no configuration reference, no backup and restore procedure (including the vault master key, without which stored credentials are unreadable), and no upgrade or reverse-proxy guide.
- **No error visibility.** Errors are logged but reported nowhere. The browser has no root error boundary and no recovery when a deploy replaces code chunks that an open tab still references.
- **Third-party data terms are unaddressed.** Caps call providers whose terms differ (some public tiers ban commercial use; some require attribution). Breach-data Caps return leaked credentials and carry the highest legal exposure.
- **No contributor path.** There is no CONTRIBUTING guide or code of conduct, and the git hooks install only inside the nix shell, so an outside contributor first meets the gates in CI.

This spec absorbs the remaining parts of the platform readiness spec (#61): the container image, error reporting and browser resilience, and env metadata. Readiness (#286) has shipped.

## Solution

Make Watchdog a project someone else can legally use, install in one command, upgrade safely, operate and contribute to.

- License the code under AGPL-3.0 with a contributor license agreement, so it is open source and commercial licensing stays possible.
- Publish versioned container images for the web app and the worker, with a production compose file, migrate-on-start and a CI image scan and smoke test.
- Release with versions, tags, a changelog and an SBOM; show the version in the app, API and CLI.
- Ship safe first-install defaults and a first-admin bootstrap command.
- Publish an operator guide: configuration reference generated from the env schema, backup and restore including the vault key, upgrade and reverse-proxy setup.
- Report errors through an optional sink behind the logger, add a root error boundary and stale-chunk recovery.
- Publish a Cap register with each Cap's credential, tier, commercial-use terms and attribution; breach-data Caps ship disabled until the operator opts in.
- Add a contributor guide, code of conduct and a non-nix setup path.

## Implementation Decisions

- **Decided by the owner:** AGPL-3.0-only with a contributor license agreement (license grant, not assignment, adapted from the Apache Individual CLA with an explicit relicensing clause, plus a corporate variant), collected by a CLA bot on pull requests with the owner and bots allowlisted. Breach-data Caps ship disabled by default with an operator opt-in. Self-host first.
- **Notices.** Every package declares its license. A generated third-party notices file lists dependency licenses; a gate fails on a newly added dependency with a license outside an allowlist (permissive, weak copyleft and AGPL-compatible).
- **Image.** One multi-stage image definition with web and worker targets, digest-pinned base images, a non-root user and no dev dependencies. A shared entrypoint runs migrations under a Postgres advisory lock unless a kill switch is set; the worker target skips migrations by default. The container exits non-zero when migrations fail. A production compose file runs web, worker, Postgres and object storage with healthchecks on liveness and readiness.
- **CI.** A container job builds both targets, scans them (pinned scanner, fails on high and critical findings, with a reviewed ignore file), and runs a smoke test that starts the image against real Postgres and object storage and polls readiness.
- **Releases.** Release automation driven by conventional commits creates a release pull request with the version bump and changelog; merging it tags the release, publishes images to the GitHub container registry and attaches an SBOM. The version is embedded at build time and exposed in the app footer, the readiness response and `wd --version`. Data compatibility promise: migrations are forward-only and every release can upgrade from the previous minor release.
- **Safe defaults.** Startup validation rejects known placeholder secrets and secrets shorter than a minimum, for the auth secret and the vault master key. A CLI or worker command creates the first instance admin. Invitation links are no longer logged.
- **Env metadata.** Each env field gets a description and a sensitive flag without changing parsed types. A generator writes the example env file (secrets blank) and the configuration reference; a drift check fails when either is stale.
- **Operator guide.** Backup and restore scripts and docs for Postgres, the object store and the vault key; an upgrade procedure; a reverse-proxy and TLS example; production object-storage CORS.
- **Error reporting.** An optional sink behind the logger with a vendor-neutral interface tested with a fake sink; the first implementation is Sentry's SDK, off unless configured, and it reuses the logger's redaction. A root error boundary, an unhandled-rejection listener that reports through the same path, and a one-time reload on chunk-load failure guarded by a session flag.
- **Cap register.** Each Cap declares provider, credential, tier, commercial-use note and attribution requirement in its metadata. A generator writes the Cap register into the docs from that metadata, and the UI shows attribution where required. Breach-data Caps carry an opt-in flag the operator sets in configuration, and the UI explains what enabling them means.
- **Contributor path.** CONTRIBUTING (including the CLA and why), a code of conduct, a declared and documented non-nix setup that installs the hooks, and a short pull request template variant for outside contributors.

## Testing Decisions

- The container smoke test in CI is the test seam for the image, entrypoint and compose file: it must reach readiness and serve the sign-in page.
- A deliberately failing migration in a test image must stop the container.
- Startup validation has unit tests for placeholder and short secrets.
- The env generator and Cap register generator each have a drift check that runs in CI.
- The error sink is tested with a fake sink: an error-level log event and an uncaught failure reach it, and redaction removes secrets.
- The chunk-reload guard is tested so it reloads once and never loops.
- Release automation is tested by a dry run on a branch before it is enabled on main.
