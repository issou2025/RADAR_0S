*Project description:*
## Problem Statement

Brickit has six active Flutter Locales today. An external translation agent can inspect old draft data, but it cannot safely add Portuguese to the real, Snapshot-backed catalog: there is no way to pin work to accepted source evidence, supply all translated values within backend limits, preserve ARB structure, prove Contract Validity, or produce a Brickit change that compiles.

A new Locale is more than a translated ARB file. Brickit must also expose the Locale through its runtime selection and regenerate its localization Dart. Letting an agent submit arbitrary ARB bytes, file paths, Dart patches, or Git operations would make a seemingly useful translation feature able to damage the Source Contract or the checkout.

The MVP needs one safe, agent-driven path from the accepted Baseline Snapshot to a reviewable Portuguese proposal. A developer, not Blabla or the agent, remains the actor that creates a Brickit branch and pull request.

## Solution

Add a deep **Locale Proposal** module inside the Localization Sync Module. It lets an agent with the existing project-scoped proposal authority create or resume a Portuguese proposal against one immutable Baseline Snapshot, obtain the source messages it must translate, submit bounded translation batches, and finalize the proposal only when the complete Catalog Document is faithful and valid.

For this MVP, Portuguese is one canonical Locale:

- catalog code: `pt`
- label: **Portuguese**
- catalog document locale: `pt`
- default Runtime Locale Mapping: Brazilian Portuguese, `pt-BR`

Brazilian Portuguese is the default content locale for generic Portuguese; it is a Runtime Locale Mapping, not a second Blabla Locale. Portugal receives the same deliberately shared Portuguese Catalog Document. A future Portuguese-for-Portugal catalog is a separate Locale Variant only when we intentionally author different content.

Finalization returns a durable, reviewable Locale Proposal and a deterministic delivery artifact. The artifact contains the derived Portuguese Catalog Document, its exact source evidence and manifest, and the fixed Runtime Locale Mapping required by Brickit. A Repository Adapter running in a developer's checkout applies only those recognized changes, runs Flutter localization generation, verifies the resulting change set, creates a local branch, and prints the pull-request command. Blabla and the agent never receive Git credentials, push a branch, or open a pull request.

When the proposal branch lands, a later Source Snapshot may establish the actual Locale Binding only if its Portuguese Catalog Document and binding match the delivered proposal. A proposal never makes a new Locale active before Git contains it.

## User Stories

1. As a translation agent, I want to discover the active project's accepted source snapshot and its Portuguese proposal status, so that I do not translate against obsolete or ambiguous source text.
2. As a translation agent, I want to create or resume one Portuguese Locale Proposal, so that retries never duplicate a large translation job.
3. As a translation agent, I want each message identifier, source value, source metadata needed for translation, and source fingerprint from immutable evidence, so that I translate the exact catalog Git accepted.
4. As a translation agent, I want to send translations in bounded batches, so that a complete Portuguese catalog can be created safely without relying on one oversized request.
5. As a translation agent, I want each staged value tied to the source fingerprint it answers, so that a changed source cannot silently receive an old translation.
6. As a translation agent, I want clear diagnostics for duplicate, missing, malformed, or contract-invalid values, so that I can repair the proposal instead of guessing which content was discarded.
7. As a translation agent, I want an ordinary empty value rejected as incomplete, so that the proposal never turns source fallback into a hidden shipped output.
8. As a translation agent, I want to record an Intentional Blank with a reason when it is genuinely required, so that every empty Portuguese output remains deliberate and explainable.
9. As a translation agent, I want the server to derive Portuguese ARB structure and metadata from the Source Snapshot rather than trusting my raw file, so that I cannot accidentally alter message identifiers, placeholders, globals, or unknown metadata.
10. As a project owner, I want a Portuguese Locale Proposal to stay distinct from active Locales and Locale Bindings until Brickit accepts it, so that Blabla never claims a locale Git has not yet published.
11. As a project owner, I want agent-authored values to retain agent provenance rather than becoming Translator Confirmations, so that a human confirmation remains meaningful.
12. As a project viewer, I want to read a proposal's source snapshot, completion state, diagnostics, and proposed Locale identity, so that I can review what the agent is asking Brickit to adopt.
13. As a developer, I want a deterministic delivery artifact with a fixed Portuguese Runtime Locale Mapping, so that the adapter changes only the new catalog, the known runtime-locale registration, and Flutter-generated output.
14. As a developer, I want the Repository Adapter to refuse a dirty or structurally drifted checkout before writing, so that a locale proposal cannot absorb unrelated Brickit changes.
15. As a developer, I want Flutter localization generation to succeed before any local branch is created, so that a proposal cannot reach review with generated localization code broken.
16. As a developer, I want the adapter to stop at a local branch and print a pull-request command, so that my own Git credentials and review process remain the only route into Brickit.
17. As a project owner, I want the later Portuguese Source Snapshot to activate the Locale Binding only when it matches the delivered proposal, so that an arbitrary Unbound Locale File cannot become an active locale.
18. As a maintainer, I want the proposal to remain readable after its source snapshot stops being the Baseline Snapshot, so that evidence and failed attempts are durable even though only a current proposal may be delivered.
19. As a maintainer, I want a later `pt-PT` catalog to be modelled as a separate Locale Variant rather than silently changing the shared Portuguese content, so that variant history and release output remain honest.

## Implementation Decisions

- **Locale Proposal** is the new domain term. It is not a Source Proposal, which remains limited to an existing source-language value, and it is not an Unbound Locale File, which is Git evidence without setup.
- The Locale Proposal module is a deep module within the Localization Sync Module. Its external interface is limited to creating or resuming a proposal, reading its source template and progress, staging a bounded translation batch, finalizing it, and reading the durable proposal or delivery artifact. It hides Snapshot evidence lookup, message completeness, ARB construction, Contract Validity, provenance, idempotency, and lifecycle checks.
- The existing Agent API is the public adapter. A token must have the existing `read` and `propose` scopes; proposal operations remain project-scoped, authenticated, rate-limited, and auditable through that adapter. No broad writer or export authority is added.
- Proposal identity is the project, pinned Baseline Snapshot, canonical Locale code, and Runtime Locale Mapping. Repeating the same request resumes the proposal; a different source snapshot creates a distinct proposal rather than overwriting historical evidence.
- Portuguese is represented as one canonical Locale with code `pt`, label Portuguese, Catalog Document locale `pt`, and default Runtime Locale Mapping `pt-BR`. The agent cannot choose another code, path, region, or arbitrary source edit for this MVP.
- The agent provides only target message values and explicit blank reasons. The module derives message identifiers, Catalog Document ordering, metadata ownership, document globals, source fingerprints, and the Portuguese ARB from immutable source evidence.
- Staging is bounded by both member count and byte size. Duplicate message identifiers, values outside the pinned source catalog, and attempts to alter source-side information are rejected. A finalized proposal requires every source message exactly once.
- Every non-empty value is validated with the existing ICU and Message Signature rules. A target-only argument, malformed ICU, or plural/select value without `other` prevents finalization. An empty value is permitted only through an Intentional Blank with a non-empty reason.
- Agent-authored translations carry agent provenance and do not create Translator Confirmations. They are proposed output, not a claim that a human has affirmed every Portuguese value.
- A proposal becomes stale for delivery when its pinned Baseline Snapshot is no longer the current Baseline Snapshot. It remains readable, but the agent must create or resume a proposal against current source evidence before delivery.
- The delivery artifact is immutable and contains the derived Portuguese Catalog Document, source snapshot identity, content hashes, Locale descriptor, and a constrained request to register the `pt-BR` Runtime Locale Mapping. It is not a general patch format and never accepts arbitrary file paths or Dart source from the agent.
- The Repository Adapter is the only delivery adapter. It applies the recognized Portuguese catalog and runtime-locale registration in a local Brickit checkout, regenerates Flutter localization output, verifies the expected generated surface, creates a local branch, and stops. It never pushes, opens a pull request, or lets Blabla hold Git credentials.
- A Locale Binding is established only after Git contains the proposal's exact Portuguese Catalog Document. The activation path checks the delivered proposal identity, binding path, canonical `pt` locale declaration, and the later Source Snapshot before exposing Portuguese as active translation or release work.
- This vertical slice must use the existing Catalog Document codec, Source Snapshot evidence, Contract Validity rules, API-token authentication, and Repository Adapter seam. It must not revive the legacy draft translation tables, change-set export path, or create a parallel release implementation.

## Testing Decisions

- Test the feature through the public Agent API and Repository Adapter seams. Tests assert observable proposal, artifact, and delivery outcomes rather than proposal-table internals.
- Use compact public API integration fixtures for authorization, proposal idempotency, source pinning, bounded batch staging, duplicate and missing message diagnostics, explicit blank provenance, and stale-source rejection.
- Reuse the existing Catalog Document, ICU, Message Signature, Source Snapshot, and public API-token test patterns as the lower-level oracles. Do not duplicate their parser and authorization tests inside proposal tests.
- Assert that finalization derives a Portuguese Catalog Document with the same message identifiers, order, source-owned metadata, and required globals as its pinned source evidence, while only target values and `@@locale` differ as the Locale Contract requires.
- Assert that malformed ICU, a target-only argument, a missing `other` arm, a duplicate identifier, an unknown identifier, an ordinary blank, and a missing source value all leave no deliverable artifact.
- Assert that an agent token lacking either `read` or `propose`, a revoked token, or a token for another project cannot read or mutate the proposal.
- Exercise the real Brickit fixture: a complete Portuguese proposal produces `intl_pt.arb`, registers the default `pt-BR` Runtime Locale Mapping, and causes Flutter localization generation to succeed. The generated delegate must resolve Portuguese by language code without adding a second Portuguese catalog.
- Exercise delivery in a disposable Brickit checkout. Assert that a clean valid checkout yields only the catalog, known runtime-locale registration, and generated localization changes; a dirty relevant checkout, generator failure, unexpected generated interface change, or stale proposal writes nothing and creates no branch.
- Assert that delivery stops before remote Git activity and emits the information needed for the developer to inspect and open the pull request.
- Exercise observation after a simulated landed commit: the matching later Source Snapshot establishes the Locale Binding and exposes Portuguese as active; a mismatched or arbitrary unbound Portuguese file remains an Unbound Locale File and does not activate.
- Keep the existing full backend suite, web typecheck/test/build, and Brickit generation pass as required verification. The decisive MVP oracle is a real Portuguese proposal that generates successfully in a clean Brickit checkout.

## Out of Scope

- A separate Portuguese-for-Portugal Locale Variant, regional copy divergence, locale fallback policy beyond the one shared Portuguese catalog, or automatic migration from `pt` to a regional code.
- Automated translation quality scoring, translation-memory suggestions, machine-output approval, or a human review workflow beyond durable provenance and normal pull-request review.
- Direct GitHub access, branch pushing, pull-request creation, or Git credentials for Blabla or the agent.
- General locale-management UI, arbitrary new-language creation, arbitrary ARB paths, or arbitrary Dart modifications.
- Completing English Source Proposal editing, structured Message Segment editing, Dictionary work, Code Context UI, or a general release dashboard.
- Broader cutover of the existing Brickit catalog. This is a contained Portuguese proof before any production migration sequence.

## Further Notes

- This is the closest complete MVP loop: agent API -> immutable Portuguese Locale Proposal -> validated delivery artifact -> local Repository Adapter -> Flutter generation -> developer-owned pull request.
- The existing target Catalog Workspace remains useful for later human refinement, but it is not the authority or delivery path for this agent-driven locale addition.
- CLDR treats `pt-BR` as the default content locale for generic Portuguese. The shared catalog is therefore correctly named Portuguese with canonical code `pt`; its Brazilian default is stated as Runtime Locale Mapping rather than hidden as a second locale.
- After this specification is accepted, split it into end-to-end tracer-bullet tickets: proposal module and Agent API, deterministic artifact and activation, Repository Adapter delivery, then the real Brickit proof.
