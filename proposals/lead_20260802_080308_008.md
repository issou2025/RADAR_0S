# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Add named role registry to ask_openrouter (one-shot A2A CLI)**

*Project description:*
## Problem Statement

When Claude consults the OpenRouter peer through `ask_openrouter.py`/`ask_openrouter.ps1`, the tool has exactly one built-in persona: a skeptical adversarial reviewer, applied automatically whenever `--system` is omitted. That persona is well suited to pressure-testing a plan, but wrong for other things Claude legitimately wants from the peer — e.g. asking it to propose an implementation with a concrete code example. Today, getting anything other than the adversarial persona means Claude has to freehand a `--system` string inline, per call, with no record of what wording was used or why. That produces inconsistent prompts across sessions and gives the tool's maintainer no single place to see what personas exist or refine their wording over time.

## Solution

Add a small named-role registry to the one-shot A2A tool. Each role bundles a short description of its responsibilities with the system prompt that expresses them. Claude picks a role by name per invocation (`--role`/`-Role`) instead of writing a system prompt from scratch every time. The existing adversarial-reviewer behavior becomes the first registered role and stays the default — nothing changes for existing callers that pass neither `--role` nor `--system`. A second role, `implementation_advisor`, is added for the concrete case that motivated this: asking the peer for an approach that includes a real code example instead of prose-only advice. The raw `--system` escape hatch is kept for one-off system prompts that don't warrant a named role.

## User Stories

1. As Claude invoking the one-shot tool, I want to select a named role instead of writing a system prompt inline, so that my intent for the call is expressed consistently and is easy to audit later.
2. As Claude invoking the one-shot tool, I want the previous default behavior (adversarial reviewer) preserved exactly when I pass neither `--role` nor `--system`, so that existing workflows (e.g. `/grilling`) keep working unchanged.
3. As Claude invoking the one-shot tool, I want an `implementation_advisor` role that asks the peer to ground every suggestion in a concrete code example, so that I get something more directly reusable than freeform advice when comparing or borrowing implementation approaches.
4. As Claude invoking the one-shot tool, I want the `implementation_advisor` role to explicitly instruct the peer to say what's missing rather than invent unstated files/APIs/dependencies when the pasted context is insufficient, so that I don't receive plausible-looking but fabricated code.
5. As Claude invoking the one-shot tool, I want the `implementation_advisor` role's output framed as a suggestion for me to review, not verified/executable code, so that I don't treat the peer's output as safe to apply without judgment.
6. As Claude invoking the one-shot tool, I want passing both `--role` and `--system` in the same call to fail with a clear error, so that a stale or mistaken automation doesn't have one flag silently overridden by the other.
7. As Claude invoking the one-shot tool, I want passing an unrecognized `--role` value to fail with an error listing the valid role keys, so that I can immediately correct a typo instead of unknowingly falling back to some default.
8. As Claude invoking the one-shot tool, I want role validation to happen before any node subprocess is started or any network call is made, so that a bad `--role` value fails fast and cheaply.
9. As the person maintaining this tool, I want the adversarial-reviewer system prompt to exist in exactly one place in the codebase, so that migrating it into the registry can't silently drift from what callers currently get.
10. As the person maintaining this tool, I want role selection logic centralized in one function shared by the CLI and (indirectly) its PowerShell wrapper, so that a future third role or a change to the precedence rule doesn't need to be reimplemented in multiple places.
11. As a PowerShell caller of `ask_openrouter.ps1`, I want a `-Role` parameter that forwards to the underlying Python script, so that I get the same role-selection capability from the wrapper as from calling `ask_openrouter.py` directly.
12. As a PowerShell caller, I want the wrapper to do no role validation of its own, so that error messages for invalid input are consistent regardless of whether I called the `.ps1` or the `.py` directly.
13. As the person maintaining this tool, I want the debate-mode system prompt (`DEBATE_SYSTEM_PROMPT`) and its structured JSON protocol left completely untouched by this change, so that the multi-round debate coordinator's behavior can't regress as a side effect.
14. As the person maintaining this tool, I want documentation (README and the hybrid-workflow doc) updated to list the available roles, what each is for, and that roles apply only to one-shot mode (not debate mode), so that future sessions of Claude don't have to rediscover this by reading source.
15. As the person maintaining this tool, I want the documentation to state the trust-boundary assumption plainly — pasted project context and peer-generated code are both untrusted input that must be reviewed, never blindly executed or applied — so that this isn't left as an implicit, easy-to-forget assumption.
16. As the person maintaining this tool, I want role keys treated as a stable, case-sensitive naming surface, so that a future rename is understood as a breaking change for any caller referencing a role by name.
17. As a future contributor adding a third role, I want a single obvious place (the registry) to add it and a single function whose behavior determines precedence, so that adding a role doesn't require touching argument-parsing logic in more than one place.

## Implementation Decisions

- A new `roles` module is added alongside the existing `common` package (same location tier as `config.py`, `peer_client.py`, etc.). It defines:
  - A frozen `Role` value type with exactly two fields: `responsibilities` (a short human-readable description of what the role is for) and `system_prompt` (the actual text sent to the model). No `name` field — the registry's dict key is the sole identifier, avoiding a key/field consistency problem. No `output_contract` field — nothing in this change enforces or consumes output shape, so a field for it would be unused metadata; if a real enforcement mechanism is designed later, the field can be added then.
  - A `ROLES` registry mapping role key → `Role`, seeded with two entries:
    - `adversarial_reviewer` — the existing skeptical-reviewer system prompt, migrated verbatim (word-for-word) from its current location so today's default behavior is provably unchanged, not just "similar."
    - `implementation_advisor` — a new system prompt instructing the peer to (a) include a concrete code example for every suggestion, grounded only in whatever context was actually provided in the prompt, (b) explicitly state what's missing rather than invent unstated files/APIs/dependencies when context is insufficient, (c) frame its output as a suggestion to be reviewed, not verified or executable code, and (d) stay concise (no rhetorical framing, no restating the problem before showing code).
  - A `DEFAULT_ROLE` constant identifying which registry key is used when the caller specifies neither `--role` nor `--system`.
  - A single function, `resolve_system_prompt(system, role)`, that is the sole place resolution/precedence logic lives:
    - Both `system` and `role` provided (both non-`None`) → raises an error (mutual exclusivity, not silent override).
    - Only `system` provided → returned as-is, unchanged (existing escape-hatch behavior for one-off prompts).
    - Only `role` provided → looked up in `ROLES`; unknown key raises an error whose message lists the valid keys.
    - Neither provided → resolves `DEFAULT_ROLE` from the registry (this is what preserves today's default exactly).
    - This resolution happens before any node subprocess is started or network call made.

  Signature (encodes the resolution contract precisely; came out of the design discussion, not a literal prototype run):
  ```
  def resolve_system_prompt(system: str | None, role: str | None) -> str: ...
  ```

- The one-shot CLI script's existing hardcoded adversarial-system-prompt constant is removed from that script; the script imports the role registry instead, so the prompt text has exactly one source of truth. The script gains a `--role` argument and calls `resolve_system_prompt(args.system, args.role)` to obtain the final system prompt string, which then flows into the existing (unmodified) call path exactly as today's `--system` value does. Errors raised by `resolve_system_prompt` are caught at the CLI boundary, written to stderr, and result in a non-zero exit — matching the script's existing error-handling shape for peer-call failures.

- The PowerShell wrapper gains a `-Role` parameter that is forwarded to the underlying script as `--role` when supplied, with no independent validation — validation and precedence logic live only in the Python layer, so the two entry points can't disagree about what's valid.

- Debate mode (the multi-round coordinator and its structured-JSON system prompt) is explicitly untouched: it does not import or depend on the new roles module, and its own system prompt continues to live where it already does. Roles apply to one-shot mode only.

- Documentation updates: the tool's README usage section for one-shot questions gains a description of `--role`/`-Role`, the two registered roles and when each is appropriate, and a note that roles don't apply to debate mode. The hybrid-workflow doc's prompting-principles section gains the same role list plus an explicit statement of the trust-boundary assumption (pasted context and peer output are both untrusted and must be reviewed before reuse).

## Testing Decisions

A good test here exercises `resolve_system_prompt`'s observable behavior (inputs → returned string or raised error), not how the registry dict is laid out internally. This mirrors the existing precedent in this codebase's `test_agent.py`, which tests `_validate_model_id` — a small pure function — directly by calling it with representative valid/invalid inputs and asserting on acceptance or the specific exception raised, with no subprocess or network involved.

New/changed test coverage:
- `resolve_system_prompt(None, None)` returns exactly the current adversarial-reviewer text (a direct regression check against today's behavior, not just "a" role).
- `resolve_system_prompt(None, "implementation_advisor")` returns that role's system prompt.
- `resolve_system_prompt("custom text", None)` returns `"custom text"` unchanged.
- `resolve_system_prompt("custom text", "implementation_advisor")` raises (mutual exclusivity).
- `resolve_system_prompt(None, "not_a_real_role")` raises, and the error message contains the valid role keys.
- A check that the debate-mode system prompt module has no dependency on the new roles module (guards against the two concerns merging later by accident).

No new subprocess/node-level test is added: the path from a resolved system-prompt string to the actual OpenRouter call is existing, already-covered plumbing (`test_integration.py`, `test_openrouter_executor.py`) that this change doesn't alter — the CLI just now computes that string differently before handing it to the same unmodified call path. This is also the single seam confirmed with the user for this change: `resolve_system_prompt` is the only new unit under test.

## Out of Scope

- Any change to debate mode, its coordinator, or its structured-JSON system prompt.
- Enforcing or validating that a role's output actually matches an "output contract" (e.g. verifying returned text contains a code block) — the `implementation_advisor` role is an instruction to the model, not a guarantee, and this change adds no execution/compile validation of returned code.
- Role versioning, snapshot-testing role prompt text over time, or any semver-style compatibility policy for role keys beyond the plain statement that renaming a key is a breaking change.
- An automated PowerShell test harness for the wrapper script (none exists today; this change relies on the Python-level tests plus manual verification of the wrapper's forwarding).
- Adding roles beyond the two described here.
- Any sanitization or filtering of pasted project context for prompt injection — this change documents the existing trust-boundary assumption but does not add new safeguards against it.
- Updating the pointer doc in other projects (e.g. the Haikyuu project's copy of the hybrid-workflow reference) — its description of default (no-flag) behavior remains accurate as-is since that behavior is unchanged.

## Further Notes

This design was pressure-tested with the OpenRouter peer itself via `ask_openrouter.ps1` (adversarial-reviewer role) before being finalized here; several of the decisions above (dropping `output_contract`/`name` as unused fields, making `--role`/`--system` mutually exclusive rather than silently overriding, wording the `implementation_advisor` prompt to avoid implying a guarantee, centralizing resolution in one function, and validating before any network call) came directly out of that review round.
