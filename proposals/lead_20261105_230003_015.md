# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Home takeover backend for the W22 family (webOS 7.x / 8.x)**

*Project description:*
### Context

I bought an **LG 43UQ81003LB** (W22 family, Realtek, reports webOS **7.6.0**, firmware `04.60.90`, build `HE_DTV_W22A_AFADATAA`). I'd like Cinema++ to be the Home there, as it is on my webOS 9/10 TVs. Branch `webos22` already opens the `homeStatusSupported` gate for 7.x/8.x behind `allowExperimentalHome`; the lifecycle itself does not yet work on this family and this issue tracks the backend needed to finish the job.

### What I found on the TV

- Home app `com.webos.app.home` is **native** (`type: native`, `main: /usr/bin/com.webos.app.home`, 54 KB ARM ELF). It loads QML modules from `qml/UserInterfaceLayer/Containers/MainView.qml` (and a `MainView_WEE.qml` variant). No writable layout XML and no Flutter assets, so the webOS 9 (`home_layoutShelfView.xml` under `/mnt/lg/cmn_data/manifest/`) and webOS 10 (overlay on `data/flutter_assets`) paths do not apply.
- LG Input Hook is already in place via the Homebrew Channel path (`/media/developer/apps/usr/palm/services/org.webosbrew.inputhook.service`, injected into `lginput2` by `/var/lib/webosbrew/init.d/60-inputhook`). Keybind `773` (Home key) already works with `action: exec` or `action: launch` to redirect the Home key to another app. Verified end-to-end.
- HBC `startup.sh` runs at `core-boot-done` as root and reads init hooks in `/var/lib/webosbrew/init.d/`, which Cinema++ already uses (`50-tvweb`, `56-cinemapp-ledstrip`, `57-cinemapp-service`).

### Proposal: hook-based "takeover" for the W22 family

A file-level overlay is not available. The equivalent user-visible behaviour (TV boots into Cinema++, Home key opens Cinema++, LG Home never appears) can be reached with two coordinated hooks rather than a QML rewrite:

1. **Home key**: write `/home/root/.config/lginputhook/keybinds.json` with `{"773": {"action":"launch","id":"io.github.ihtisham1211.nativetv","params":{"screen":"home"}}}` on takeover; back up and restore the previous content on release.
2. **Boot activity**: install a `/var/lib/webosbrew/init.d/55-cinemapp-home` that, after `core-boot-done` and a short settle, launches Cinema++ via `luna-send -i -n 1 luna://com.webos.applicationManager/launch '{"id":"io.github.ihtisham1211.nativetv","params":{"screen":"home"}}'`. Removed on release.
3. Optionally, a small **home watcher** (polling or SAM subscription) that, while takeover is active, re-launches Cinema++ when LG Home ends up in the foreground. There is already `home-watcher.sh` in the Cinema (webos-launch-home) repo that does this on webOS 5; same contract would do here.

Cinema++ already has a `home` tab and `screen=home` param in `cinemapp-home-key`, so the UI side is a no-op.

### Changes required in this repo

- **`home_screen_manager.cpp`**: new path `writeStateWebos22()`/`removeStateWebos22()` that manages the hook+activity pair and keeps a back-up of the previous keybind JSON. `supported22()` returns true if the lginputhook service is installed; `mounted22()` returns the current state of the keybind + activity.
- **`home_takeover_manager.cpp` / `home_takeover_lifecycle.cpp`**: branch on `startsWith(version, "7.")` or `"8."` to skip mount/overlay steps and only drive the hook path. Release follows the same branch.
- **Install/uninstall of the app itself**: when Cinema++ is removed the HBC should remove the boot activity; the current install.sh adopt/retire path is a good hook point.
- **`/api/home/startup`**: wire it so the user-visible "Open on power on" toggle on the Home tab in the dashboard writes the boot activity.

### Validation (what to rerun on the TV)

- Takeover on → reboot → Cinema++ opens by itself.
- Press Home while on Netflix → Cinema++ opens.
- Takeover off → reboot → LG Home opens; keybind and activity are gone (verify with `ls /var/lib/webosbrew/init.d/` and `cat /home/root/.config/lginputhook/keybinds.json`).
- Remove Cinema++ app → boot activity disappears, keybind reverts (adopt/retire path).

### Why not a QML overlay

The Home binary is native C++; its QML lives under `/usr/palm/applications/com.webos.app.home/qml/`. A bind-mount on `MainView.qml` would replace the launcher UI but not its event model (the binary expects the QML to expose a specific set of properties and signals: `topArea`, `shelfList`, `editMenuLoader`, `settingPopup`, etc.). Reimplementing all of that is a much larger surface than a hook and is not reversible as cleanly.
