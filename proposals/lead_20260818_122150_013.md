## Why this is being raised

#905 and #906 ask Backend to host `https://app.badabhai.in/.well-known/assetlinks.json` so Android App Links verify and a shared invite opens the worker app. #906 describes it as a do-it-now slice because "the server is live".

Tracing it, that ask cannot be satisfied as a merged repo change today, and the blocker is a deployment gap rather than the file itself:

- `https://app.badabhai.in` is **payer-web's** origin — `apps/payer-web/src/app/i/[code]/page.tsx` documents that exact URL and already implements the `/i/<code>` landing page.
- **`GAP-XC-06`** (`docs/payer-agent/GAP_REGISTER.md`, **P1**): *"`apps/payer-web` is built by no workflow and deployed by none; `staging-cd.yml:172` skips the Next apps"* — needs *"a deployment path... Decide hosting (Vercel / container / Lightsail), add the pipeline, set `PAYER_API_URL` + CORS origin."*
- `apps/payer-web/next.config` says the same in its own header: *"the portal is not deployed by any workflow today — GAP-XC-06"*.
- The only nginx in the repo is `infra/docker/proxy-harness/nginx.conf`, explicitly *"Never a production config"*.

So there is **no repo-managed pipeline** to add a `.well-known` file to. Either payer-web is deployed by hand outside CI (then hosting assetlinks is a server action, not a PR), or `app.badabhai.in` is served by something not in this repo (then the `/i/<code>` page is not live either, and #905's deliverable 2 is unmet in production for the same reason).

## The decision needed (DevOps / infra)

1. **What serves `app.badabhai.in` today** — and if it is payer-web, how it got there, since no workflow deploys it.
2. **The hosting target** for payer-web: Vercel, a container on Lightsail beside the API, or static export behind the existing edge.
3. **The pipeline** — GAP-XC-06's actual deliverable: build + deploy payer-web, `PAYER_API_URL`, CORS origin, and TLS/HSTS termination (the portal deliberately omits HSTS today because TLS terminates at the edge).

## What that unblocks immediately

Once a deploy path exists, hosting the two files is small and lands in `apps/payer-web/public/.well-known/` (Frontend-owned; raise there, or fold into the same PR by agreement):

- `assetlinks.json` — must be **200, `application/json`, no redirect** (Android is strict).
- `apple-app-site-association` — **no extension**, and must still be `application/json`. Next.js `public/` will likely serve an extensionless file as `application/octet-stream`, so this needs a `headers()` rule in `next.config` and should be verified against the running origin, not assumed.

Then `#906`'s verification runs: `adb shell pm verify-app-links --re-verify com.badabhai.workerapp` → `app.badabhai.in: verified`.

## One security call to make explicitly, not by default

`apps/worker-app/deeplinks/well-known/assetlinks.json` currently lists **only the debug signing SHA-256**, and #906 states the debug fingerprint should stay in the array after Play launch (*"do NOT drop the debug one while still sideloading for QA"*).

`assetlinks.json` is a **trust delegation from the production domain to a signing key**: any build signed with that key can claim App Links on `app.badabhai.in` and receive invite URLs. Debug keystores live on developer laptops, are not rotated, and are frequently shared or committed.

Worth a deliberate decision rather than inheriting it:
- ship debug-only now for sideload QA, and **remove it** when the Play App Signing key is added; or
- keep both permanently and accept that the debug key is production-trusted; or
- use a dedicated QA signing key that is not the shared debug keystore.

This is a hosting/security posture question, which is why it sits here rather than in #905.
