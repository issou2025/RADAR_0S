# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**dependants.txt is read by nothing and wrong where it has content; maintain, delete, or mark it**

*Project description:*
`dependants.txt` sits at the root of BHoM and BHE repositories as the apparent counterpart to `dependencies.txt`. It is read by nothing, and where it has content that content is wrong. Anyone who trusted it would be misled.

This is the same shape as several findings from the BHoMBot migration audit: **something that looks like a mechanism, is not wired to anything, and would mislead a reader who assumed it worked.** The audit's examples were BHoMBot's `null-handling` check (reports Neutral, implementation unreachable), its versioning fast-fail (reads a path nothing writes), and its `IncludedDLLs.txt` (three different paths, none matching the reader).

## What was measured

| Repo | `dependants.txt` contents | Actual dependents, derived from `dependencies.txt` |
|---|---|---|
| `BHoM/Revit_Toolkit` | **empty** | **17** |
| `BuroHappoldEngineering/Revit_UI` | one entry (`BuroHappold_Revit_Toolkit`) | **14** |

Actual dependents were computed by inverting `dependencies.txt` across the 100 repositories in the installer manifest: 413 edges, 96 repos with at least one edge.

**Nothing reads it.** No reference to `dependants` anywhere in `CI_Toolkit/.github` or `CI_Toolkit/tools`, and none in the BHoMBot source. So it is not feeding a check, a build, or a report.

Both repos also ship `core.txt` alongside it in at least one case, which suggests this family of root-level manifest files accumulated over time rather than being designed as a set.

## Why leaving it is the worst option

The file is not inert in the way an unused variable is inert. It is **addressed to a human**, at the root of the repository, with a self-describing name, in a location where a developer looking for "who depends on me" would reasonably look first. An empty `dependants.txt` in `Revit_Toolkit` reads as "nothing depends on this", which is the opposite of true for a repo with 17 dependents.

That matters more now than it did. CI builds the repo under test and its dependencies, not its dependents, so a developer changing a high-fan-out repo has to know about downstream impact from somewhere. The guidance for that is currently a central page. If someone checks the file at hand instead, they get a wrong answer with no indication that it is unmaintained.

## Three options

### 1. Maintain it, generated rather than hand-written

Derive each repo's `dependants.txt` from the inverted `dependencies.txt` graph and keep it current.

**Cost.** Needs a generator and a scheduled job with write access across both orgs, producing commits in ~96 repositories whenever the graph changes. That is a new cross-org write mechanism, which is the pattern the BHoMBot migration is removing. It also adds commit noise to every repo each time a `dependencies.txt` changes anywhere upstream.

**What it buys.** The information lives where a developer looks, per-repo, with no central page to find. Transitive versus direct would need deciding: `Revit_Toolkit` has 17 transitive dependents but fewer direct ones, and the two answer different questions.

### 2. Delete it from every repo

Remove the file fleet-wide and rely on the central guidance.

**Cost.** A change to ~96 repositories, though a trivial and reviewable one. Loses the per-repo discovery point entirely, so discovery depends on the central page being found. That is already a known weakness of the current guidance and this would make it the only route.

**What it buys.** No misleading artefact. The graph has exactly one source of truth, `dependencies.txt`, and anything derived from it is derived at the point of use rather than cached in ~96 places where it can go stale.

### 3. Leave it, and mark it as unmaintained

Keep the files but add a header line saying the contents are not maintained and pointing at the real source.

**Cost.** Still a change to ~96 repositories, so the same distribution problem as option 2 for none of the benefit. Leaves a file that must be explained rather than trusted, and the header will itself go stale or be stripped by anyone editing the file by hand.

**What it buys.** Cheapest to reason about, and reversible. Preserves the possibility of option 1 later without committing to the machinery now.

## Not recommending one

The choice turns on whether per-repo discovery is worth a cross-org write mechanism, which is a question about how the fleet is administered rather than about this file. Recording it because leaving it undecided is the one outcome with no argument in its favour.
