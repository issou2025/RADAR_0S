# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[design] Decouple model integration from the engine**

*Project description:*
## Problem

Integrating a model into the engine, or adjusting how an already-integrated
model is driven, requires cutting an engine release even when the change
contains **no engine code**.

## The two kinds of model change

Model integration work falls into two buckets:

**Bucket A: data and certification.** Preset routing that composes *existing*
policy classes (schema sanitizer, prompt/content/response policy, reasoning
codec, cache policy), a price-table entry, and a capability certificate
asserting what the model actually supports on the wire. All of this is
declarative. None of it changes engine behaviour for any other model.

**Bucket B: engine code.** A genuinely new policy, codec or sanitizer class,
because no existing class expresses the model's wire contract.

Bucket B belongs in the engine and should ride an engine release. Bucket A is
the common case, and it should not. Today both do.

## Cost of the current coupling

- **Release cadence is driven by model onboarding rather than by engine
  change.** Releases carry no engine delta, which makes the version line a poor
  signal of what actually changed.
- **Version drift downstream.** Consumers that pin the engine by tag end up
  spread across engine versions purely as a side effect of when each model was
  onboarded. For any consumer that compares results across models, "which
  engine version did this run on" becomes a per-model question instead of a
  constant, and every difference then needs its own justification.
- **Often two releases per model**, as ADR 0002 already records: integration
  tests pass, release, a live run surfaces a model-specific failure pattern,
  the fix is to re-route to a policy class *already in tree*, release again.
  Both releases ship zero engine code.

## What already exists

This is not a from-scratch request. The seam is half open:

- **Preset overlay.** `--presets-file` / `RunConfig.engine.presets_file`, loaded
  and validated at `tolokaforge/core/llm/presets.py:176`, failing loud on
  unknown policy names. Documented in `docs/ADD_NEW_MODEL.md` under "Adding a
  model without an engine release".
- **Pricing overlay.** `observability.pricing_overlay_path`, applied at
  `tolokaforge/dx/cli/main.py:655` via `pricing.reload_pricing()`.
- **Report-side pricing override.** The results collector accepts an explicit
  pricing file instead of the bundled table.
- **ADR 0002** (`docs/adr/0002-external-model-registry.md`) diagnosed exactly
  this problem and chose the overlay as the mechanism.

So the run path can already consume an out-of-tree model registration. In
practice it is not used, and the reasons are structural.

## What still couples model integration to the engine

1. **Certification lives inside the engine test suite.**
   `tests/integration/llm/registry.py` is engine-repo code, and
   `docs/ADD_NEW_MODEL.md` makes it a mandatory gate ("No PR merges a model
   change without all six passing"). A model therefore cannot be certified
   without an engine-repo PR, and that PR is what drags the release along. This
   is the load-bearing coupling: the overlay removes the *preset* dependency but
   not this one, so the release happens anyway.

2. **The documented default points at `main`.** The pre-flight table in
   `docs/ADD_NEW_MODEL.md` routes the price table, the certificate registry and
   the preset file to `main`, justified as "shared". The overlay appears further
   down as an alternative. The release path is the documented happy path and the
   seam is the exception, so integrators reasonably take the former.

3. **The auto-integration workflow emits engine commits.**
   `.github/workflows/integrate-model.yml` checks out an engine-repo branch,
   fills the in-tree price table during the probe stage, and commits the
   integration back to that branch. Its output shape is an engine commit, so
   automation reinforces the coupling rather than relieving it.

4. **No packaged, pinnable form.** An overlay is a loose file path each operator
   carries and keeps in sync by hand. Nothing bundles preset routing, pricing
   and certificate into a single installable, versioned artifact, so there is no
   way to pin "model data vN" the way an adapter can be pinned.

5. **Overlay runs are not reproducible from the run record.**
   `write_engine_run_state()` (`tolokaforge/core/engine_run_state.py:33`)
   persists the overlay **path**, not its content or a fingerprint. The
   effective model data of a completed run cannot be reconstructed from the
   pinned wheel plus the run state.

6. **The bucket boundary is undeclared.** Nothing tells an integrator up front
   whether a candidate falls in bucket A or B, so the safe default is to open an
   engine PR regardless.

## Proposal

Complete the split along the boundary ADR 0002 already drew, and finish what it
deferred.

- **Promote ADR 0002 from Proposed to Accepted.** Its Option 2 shipped, yet the
  ADR still reads `Status: Proposed`, which leaves the seam looking
  experimental and discourages use.
- **Implement ADR 0002 Option 3: an entry-point group for model data**, mirroring
  `tolokaforge.adapters`. Model data becomes an installable package consumers
  pin, not a path they pass. Avoid the failure mode already open against the
  adapter registry in #544 (silent last-wins on duplicate names): a model-data
  registry must fail loud on collision rather than silently shadow.
- **Move certification out of the engine test suite**, or give it an out-of-tree
  entry point, so certifying a model does not require an engine-repo PR. This is
  the single change that decides whether the rest of the seam is usable.
- **Fold pricing into the same artifact**, so one pin covers preset routing,
  pricing and certificate instead of three separately-overridden files.
- **Invert the `docs/ADD_NEW_MODEL.md` pre-flight table**: out-of-tree is the
  documented default, `main` only for bucket B. Add an explicit "which bucket am
  I in" pre-flight check so the answer is known before any work starts.
- **Record the resolved model-data fingerprint in `engine_run_state.json`**, not
  just the overlay path, so out-of-tree runs stay auditable.
- **Teach the auto-integration workflow to emit a model-data artifact** instead
  of an engine commit whenever the candidate is bucket A.

Explicitly **not** in scope: policy, codec and sanitizer *classes* stay engine
code. ADR 0002 deferred the sidecar-Python-module escape hatch (its Option 4)
and that deferral still looks right. The goal is narrower: a model that needs no
new class should need no new engine version.

## Relationship to other work

- **#622** (Milestone 15, runner wheel split / `tolokaforge-core` extraction) is
  a different axis and **not** a prerequisite. That issue is about the import
  graph and lists `core.llm.*` among the shared subsystems to untangle. This
  issue needs no import-graph refactor: `core.llm.*` stays exactly where it is
  and only data plus certification move out. The two can proceed independently.
- **#353** (pricing table location alignment) overlaps on the price file and
  should land with or before the pricing part of this.
- **#544** (adapter entry-point silent last-wins) is the pitfall to avoid when
  introducing a second entry-point registry.
- **#633** touches the same auto-integration workflow.

## Acceptance criteria

- [ ] A bucket-A model change can be registered, certified, priced and evaluated
      **without any commit to this repo and without a new engine version**.
- [ ] That model data is installable and pinnable as one versioned artifact, and
      collides loudly rather than silently.
- [ ] `engine_run_state.json` lets a reader reconstruct which model data a
      completed run resolved.
- [ ] `docs/ADD_NEW_MODEL.md` documents the out-of-tree path as the default and
      states the bucket boundary as a pre-flight decision.
- [ ] A bucket-B change still fails the out-of-tree path loudly and is routed to
      an engine PR, as today.
