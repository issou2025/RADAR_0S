# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat(make): domain-partitioned make interface with interactive workflows and self-healing prerequisites**

*Project description:*
## Context & Problem Statement

FoodSavr's developer CLI experience currently suffers from several key friction points:
1. **Flat Target Explosion**: Running `make help` outputs an overwhelming list of 33+ targets, mixing daily development drivers (`run-dev`, `test`) with low-level setup and infra scripts (`setup-fork`, `setup-event-policy`, `infra-github-plan`, `social-auth-setup`).
2. **Fragile Parameter Inputs**: Targets require memorizing and passing obscure environment variables (`PROJECT_ID`, `WEB_APP_ID`, `ENV`, `RELEASE_TOPOLOGY`), failing with cryptic errors when omitted.
3. **Missing Pre-Flight Self-Healing**: Setting up a new environment or provider crashes on missing cloud prerequisites (e.g., Terraform plan fails with HTTP 403 because `apikeys.googleapis.com` is disabled before import, or Firestore databases are uninitialized).
4. **Hardcoded Identity Leakage**: Hardcoded defaults (`JoachimTislov/foodsavr`, `my-foodsavr-store`) risk exposing the owner's deployment or breaking when run on contributor forks.
5. **UI & Friction Drain**: Humans spend too much time navigating cloud web consoles, while agents risk overstepping into infrastructure mutations.

---

## Guiding Philosophy & Scope

* **Automate Everything (Even Single-Run Tasks)**: The entire solution is designed as a modular framework on top of GitHub to get the best of both worlds—where automation and setup are standardized, and every provider component (GitHub, Google Cloud, Firebase, Supabase) can be switched out or replaced cleanly.
* **Radical Overhead Reduction**: The explicit goal of automation is to eliminate development and operational overhead so that both humans and agents can focus squarely on product, code quality, and user experience.
* **Unbounded Agent Capability, Focused Mission**: Agents can do virtually anything, but their mission here is automating infra/operational friction away so human creativity and agent implementation remain centered on product UX.
* **Scope Boundary (Explicit Non-Goal)**: While migrating to a new platform or provider can technically be automated, **live platform/data migration is strictly out of scope** due to its excessive blast radius.

---

## Core Architectural Decisions

### 1. Makefile as a Thin Router
* Preserve `Makefile` as a lightweight, zero-dependency front-door router (providing universal shell tab-completion).
* All parsing, interactive menus, and domain logic delegate to a structured Python controller (`scripts/dev.py` or modular domain scripts), avoiding messy GNU Make bash scripting.

### 2. Standardized 6-Domain Taxonomy
Partition all developer commands into six explicit domains:
1. **`app`**: Local app development, emulators, builds, and compilation (`dev`, `build-web`, `build-apk`, `serve`).
2. **`quality`**: Testing, static analysis, code formatting, and translation checks (`check`, `test`, `analyze`, `fmt`, `locale`).
3. **`provider`**: Backend cloud infrastructure, hosting channels, databases, App Check, and IAM (`status`, `setup`, `plan`, `apply`, `rules`).
4. **`repo`**: Git repository operations, worktree creation, branch hygiene, and pre-push validation (`worktree`, `push`, `hooks`, `branches`).
5. **`agent`**: Autonomous CI harness operations, status, quota headroom, and audit ledgers (`status`, `usage`, `audit`, `sync`).
6. **`setup`**: Guided developer onboarding, tool dependency probing, and configuration verification (`wizard`, `probe`, `verify`).

### 3. Filtered `make help` Overview
* `make help` displays **only** primary domains and essential daily commands (under 10–12 entries).
* Specific granular sub-targets (`<domain>-*` such as `setup-branches`, `infra-gcp-*`, `social-auth-*`) are excluded from the main help overview.
* Sub-targets are discoverable via domain-specific help (e.g., `make help domain=provider` or `make provider-help`).

### 4. Numbered Selection Engine (No Free-Text Typing)
* Replace all free-text input and slash prompts (e.g., `(setup/operations) [setup]:` or pasting project IDs) with standardized 1-based numbered menus:
  ```text
  FoodSavr:
    1) setup
    2) operations
  Select [1 - setup]: 
  ```
* Supports single-keystroke default selection on `<Enter>` and lists auto-discovered cloud projects/environments.

### 5. Access-Adapted Identity & Isolation
* The interface dynamically adapts to the human's actual authenticated access across VCS (`gh`) and cloud (`gcloud`, `firebase`).
* Automatically defaults to the owner's repository for the owner, and to the contributor's fork for external contributors, without hardcoding or leaking upstream deployments.

### 6. Provider Lifecycle & Minimal Abstraction
* **Define "Provider"**: An abstraction managing external backend services supplying app capabilities (`auth`, `documents`, `hosting`, `storage`, `appCheck`) per ADR 0005 (Firebase, Google Cloud, and spec-ahead for Supabase/Self-Hosted).
* **Transparent Forwarding**: Do not over-abstract native `firebase` and `gcloud` CLIs. Forward a simplified, reliable wrapper that keeps the human in control.
* **Frictionless Non-Secrets**: Non-secrets and client configs (`webAppId`, web client API key, project numbers, hosting URLs) require zero manual confirmation—they are written automatically to `deploy/instance.yaml`, `lib/firebase_options.dart`, and `android/app/google-services.json`.

### 7. Hard Interactive TTY Barrier against Agentic Mutation
* **Enforce ADR 0003 / ADR 0008**: Mutating cloud, infrastructure, and app-setup commands (`provider apply`, `provider setup`, `secrets rotate`) strictly require an authentic interactive human TTY (`sys.stdin.isatty() == true` and `is_unattended_agent_env() == false`).
* If called by an autonomous agent or via headless piping, mutating targets fail fast with an explanatory error, strictly preventing unintended agentic infrastructure mutation.
* Read-only analysis and verification commands (`check`, `test`, `provider status`, `provider plan`) remain fully executable by agents and CI runners via environment variables/flags.
* Safe local bootstrapping (stubs, SDK configs, formatting) self-heals automatically within granted access limits.

## Acceptance Criteria

1. **Clean Overview**: `make help` displays only the 6 core domains and primary daily commands; all `<domain>-*` targets are hidden from the default listing.
2. **Domain Discovery**: Running `make help domain=<domain>` displays the granular sub-targets for that domain.
3. **Numbered Selection**: Interactive prompts throughout setup and provider commands use 1-based numbered lists with single-stroke defaults on `<Enter>`.
4. **Caller-Adaptive**: Running on a fork automatically operates on the fork's identity without targeting or exposing upstream deployments.
5. **Self-Healing Bootstrapping**: Running provider setup on a new project pre-enables required APIs (`apikeys`, `firestore`, etc.), registers missing Web/Android apps, and syncs manifest and client config files without manual copy-pasting or 403 crashes.
6. **Agent Mutation Guard**: Attempting to invoke mutating provider/infra commands from an unattended agent environment or headless pipe immediately halts with an exit code and human-only notice.
7. **Agent Verification Support**: Read-only verification targets (`check`, `test`, `provider plan`) remain non-interactively executable via command arguments or environment variables.
8. **Explicit Non-Goal Enforcement**: Migration of live databases or active cloud providers is strictly excluded from implementation scope.
