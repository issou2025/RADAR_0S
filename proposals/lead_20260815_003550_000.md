# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**ci-versioning attributes the whole closure when subject resolution yields zero assemblies, failing a PR with 1,056 findings that are not its own**

*Project description:*
Observed on a real production pull request, `BHoM/BHoM_Adapter` PR 416, run `31844962538`, 2026-08-14.

`ci-versioning` failed the pull request with **1,056 findings, none of which belong to the repository under test**, having examined **none of its types**. That is the check doing the opposite of its purpose. It reported another 22 repositories' defects against a diff that changed one comment.

The only reasons this is not currently causing harm are that the check is non-blocking and that it had never actually run on that repository. Both of those protections disappear at enforcement.

## The measurement

```
Attribution: whole closure, 99 namespace prefix(es)
Classification: real/DeclaringTypeNotLoaded=642, real/NoMethodEvent=394, real/NoOverloadFound=10, real/SignatureResolved=10
Coverage: 0 subject type(s) across 0 subject assembl(ies), checked against the previous dataset version; 75 assembl(ies) loaded; 1 FromJsonDatasets entry point(s) invoked
```

- `--subject-assemblies` was passed `D:\a\BHoM_Adapter\BHoM_Adapter\Build` and resolved **0 subject assemblies**.
- With no subjects, attribution fell back to the **whole closure, 99 namespace prefixes**.
- **1,056 findings**, spread across **22 namespaces belonging to other repositories**: ETABS, GSA, CFD, CarbonQueryDatabase, Excel and others.
- **Zero** findings match `BH.oM.Adapter` or `BH.Engine.Adapter`. Not a low count. Zero.

The failure surface presented to the author is 52 annotations plus `... and 1006 more failures (see artifact)`, none of them actionable by them.

## The action is not broken in general

The same action at the same ref, on `BuroHappoldEngineering/Revit_MechanicalPlumbing_Tool` run `31841555571` the same day, resolved **3 subject assemblies and 208 subject types across 17 namespaces** and attributed correctly. So this is something about how the subject set is derived for a particular repository shape, not a general fault.

## What I could not establish

**Why `Build\` yielded nothing for this repository is not determined**, and the obvious explanations do not hold:

- Both repositories declare `<OutputPath>..\Build\` in every project file.
- The `Build primary repo` step **succeeded in both**, 13.4s here against 39.1s on the working case.
- Naming does not obviously disqualify it: of the four projects, `Adapter_Engine` and `Adapter_oM` carry conventional suffixes.

One difference is visible and its relevance is untested: the working repository carries an `altConfigs.txt` and built five `Release*` configurations, this one carries none and built once. Whether the subject scan depends on that path is not something the run log answers, and the log does not enumerate what landed in `Build\`. **Reproducing with a directory listing of `Build\` immediately before the runner call is the cheapest next step** and I have not done it.

## What hid this, which matters as much as the defect

**The previous run on this repository skipped.** Run `30096926588`, 2026-07-24, logged `No relevant files changed — check skipped` and reported `ci-versioning: success`.

So the green on that repository was vacuous, and there has never been a real versioning result on it. This defect has been latent since onboarding and was only visible because a pull request happened to touch a file the check watches.

This is the silent-vacuous-pass class arriving on a production repository, which the migration audit recorded as a risk in the checks themselves. It is worth stating plainly: **a skipped check and a passing check are indistinguishable in the merge UI**, so the population of repositories in this state is invisible without deliberately measuring it.

## Why this is urgent relative to enforcement rather than today

At enforcement, every repository whose subject set resolves empty will fail its first real pull request with a wall of other repositories' defects. The author cannot fix any of them. The likely outcome is that the check gets bypassed or removed, which costs more than the check was ever worth.

Two things are needed and they are separable:

1. **Fix the subject resolution**, or fail loudly when it resolves zero subjects rather than silently widening to the whole closure. Widening on empty is the specific behaviour that turns a configuration problem into a thousand-item false report. A hard error saying "no subject assemblies resolved" would have made this a one-line diagnosis.
2. **Count the affected population** before the enforcement register counts anything. Any repository where `ci-versioning` has never genuinely executed is a candidate, and that is the same population that produces garbage on day one of enforcement.

Item 1 is the defect. Item 2 is tracked separately and is not a prerequisite for fixing it.

## Not to be confused with

This is not the attribution-filter work already closed, and not the `TryGetValueFromSource` finding. Those concern which findings are real once subjects are known. This concerns the case where **no subjects are known at all** and the code proceeds anyway.
