# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**feat(github-projects): add missing board status options safely**

*Project description:*
## What

Ticket: https://github.com/nickderobertis/onetaskgraph/issues/1312 — *safely upsert configured board
status options*. Severity **critical**.

**Root cause (from the ticket).** The GitHub Projects adapter
(`crates/onetaskgraph-github-projects/src/lib.rs`) reads and writes configured board statuses but
has no guarded operation that adds missing configured options while preserving every existing
option id and assignment. GitHub's `updateProjectV2Field` takes `singleSelectOptions` as the field's
whole option list, and options sent without their ids are re-minted, clearing every item's status:
adding `Deferred` by a hand-written mutation without ids cleared the follow-ups board, while adding
`Queued` with ids preserved 420 plan statuses. The crate documents that nothing in it calls
`updateProjectV2Field`; this change deliberately introduces the one guarded call, and the module
documentation says so and why.

**The accepted fix, and its operator surface (approved by the manager).**

`onetaskgraph sources status-options <source> [--apply]`

- **Without `--apply`** it reads the named `github-projects` source's board `Status` field and prints
  which options this source's `status_mapping` (and shipped defaults) name that the board lacks, and
  changes nothing.
- **With `--apply`** it adds only the missing configured options: the mutation sends every existing
  option with its existing id, name, color and description unchanged, plus the missing ones, and
  leaves unconfigured options untouched.
- **Guarded.** Before the write it snapshots the field's options and every item's status assignment;
  after the write it reads both again and verifies every pre-existing option id and every item's
  assignment is unchanged. If GitHub reports drift, it refuses — exits non-zero — printing the
  recovery data: the snapshot of item ids and their option names and ids from before the write.
- **Refused by name.** A source that is not `github-projects`, an unknown source, and a board with
  no `Status` field.
- `--json` renders the plan and the outcome as a document; the CLI's own documentation describes the
  verb.

Nothing in this plan calls the verb; this host's plan-store adoption only documents it for
operators.

## Why

The user asked to "pick up accepted follow ups … get all the accepted and plan them as a single dag." Every ticket in this plan was verified with evidence by a follow-up run, then read by the user and moved to `Todo` with its fix chosen, so it is a known failure in a tool this harness runs on that the user has decided to have fixed.

Adding one required status option to a board by hand has already wiped every item's status on the

`Deferred`). The user wants a tool that makes that addition safe instead of a hand-composed
mutation.

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or
`publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.
