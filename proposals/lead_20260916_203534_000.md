# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**interaction: Stage 1 elevation datums and stacked-mass relationships**

*Project description:*
## Why

MonkeyArch manual modeling is now intentionally a **Stage 1 steering layer**, not a Rhino/SketchUp replacement. The remaining missing basic control is vertical design reference: an architect must be able to place one mass above another, work against meaningful elevations, and adjust heights without introducing premature Wall/Floor/BIM semantics.

Current product direction:

```text
Study / Board / uploaded sketch
        ↓
Agent proposes Stage 1 massing
        ↓
user corrects massing by hand
        ↓
accepted Stage 1
        ↓
next-stage reasoning
```

For that workflow, `Level / elevation / datum` is more important than expanding Rotate/Scale into a complete CAD suite.

Related: #138 retires the old top-level Frame panel but explicitly keeps Level/Grid/Datum semantics; this issue defines the concrete contextual replacement use case. Do not restore the old Frame product surface.

---

## Product rule

> **A Level is a spatial reference datum, not automatically a floor/storey object.**

Stage 1 geometry may remain generic mass/volume/boundary/void geometry. Referencing an elevation must not classify a mass as Wall/Slab/Room or force BIM structure.

Examples:

```text
Ground        +0.000
Podium Top    +4.500
Upper Mass   +13.500
Roof Ref     +16.000
Site Low      -1.200
```

A volume may bind to a datum, another mass, or an explicit numeric elevation without those references becoming architectural object identity.

---

## Minimum interaction

### 1. Contextual elevation readout

When a supported mass / face / object is selected, show the vertical facts needed for Stage 1 steering, e.g.:

```text
Base Z     +4.500 m
Top Z     +13.500 m
Height       9.000 m
```

Do not require opening a specialist Frame dialog.

### 2. Datum snap / numeric override

Support deliberate actions such as:

- set base to an existing reference elevation;
- set top to an existing reference elevation;
- type an exact base/top Z or height;
- drag vertically with datum snapping;
- preserve the selected vertical constraint while typing an override.

Transient drag remains local preview; one deliberate completion uses the existing typed model/draft path.

### 3. Stacked mass relationship

Support the basic Stage 1 case:

```text
Mass B
  sits_on / base follows top(Mass A)

Mass A height changes
        ↓
Mass B remains stacked deliberately
```

The first implementation may use the repository's existing dependency/reference vocabulary rather than introducing a new `sits_on` schema if an existing relation can express it correctly.

Important: this relationship is optional. A mass with explicit Z coordinates must remain valid without being forced onto a Level/Grid hierarchy.

### 4. Small datum surface

Provide only the minimal user-facing controls required to:

- inspect useful elevations;
- create/name a simple reference elevation when needed;
- choose one as a base/top reference;
- see the reference in the viewport while using it.

Do not recreate the retired Frame editor, grid-management panel or a full Revit Levels workflow.

---

## Architecture boundaries

Reuse existing Level/Datum/frame/runtime capabilities where they already own these facts.

```text
pointer / numeric input
      ↓
local Stage 1 interaction
      ↓
explicit elevation/reference intent
      ↓
existing typed draft / dependency patch
      ↓
Canonical project path
```

Rules:

- Canonical State remains authority;
- datum overlays are projections;
- no client-only relation masquerades as retained truth;
- no automatic Wall/Slab/Floor classification;
- no per-pointer Agent call;
- exact-base / candidate / undo semantics stay unchanged;
- #138 may retire the old Frame UI while the underlying datum reader remains available to this interaction.

## Acceptance

- [ ] A user can stack one generic mass above another without creating Wall/Floor semantics.
- [ ] Base Z, Top Z and Height are visible and numerically editable for supported Stage 1 geometry.
- [ ] A mass can snap/bind to a reference elevation intentionally.
- [ ] A deliberately stacked upper mass follows the lower mass when the referenced top elevation changes.
- [ ] A free mass can remain at explicit coordinates with no Level binding.
- [ ] No global rule claims every Stage 1 object must be placed by Level/Grid.
- [ ] Drag preview is transient; completion uses the existing retained model path.
- [ ] Undo/redo and exact-base protections still work.
- [ ] The normal MonkeyArch UI does not resurrect the old Frame/Massing/Program specialist surfaces.

## Non-goals

- BIM storeys;
- automatic floor generation;
- automatic wall/slab classification;
- complete grid authoring;
- structural levels;
- full Rhino/Revit coordinate-management UI;
- changing Stage semantics globally.

## Definition of done

A user can receive a Stage 1 massing proposal from Study/Board/Agent, correct its vertical composition in seconds, and continue designing without learning a CAD/BIM datum-management workflow.

> **Stage 1 needs reliable spatial references, not premature building-object ontology.**
