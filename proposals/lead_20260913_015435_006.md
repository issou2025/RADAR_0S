# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**feat(gui): integrate desktop_updater for signed auto-updates**

*Project description:*
## Goal

Add Sparkle-style auto-updates to the Flutter desktop app (`apps/gui-flutter`) using [`desktop_updater`](https://pub.dev/packages/desktop_updater) (^3.1.6).

Users should get verified in-app updates on macOS / Windows / Linux without manual reinstalls, with release metadata and artifacts authenticated via pinned Ed25519 keys.

## Context

- Package: [desktop_updater 3.1.6](https://pub.dev/packages/desktop_updater) (Flutter desktop: Linux, macOS, Windows)
- Update flow (schema v3):

  ```text
  app-archive.json -> release.json -> app.zip / installer artifact
  ```

- Clients fetch exact URLs and verify artifact length + SHA-256 before install.
- App identity today:
  - macOS `PRODUCT_BUNDLE_IDENTIFIER`: `top.mixar.app`
  - Linux `APPLICATION_ID`: `top.mixar.app`
  - Windows default from pubspec `name`: `gui_flutter` (likely needs an explicit `--package-id` / `expectedPackageId` of `top.mixar.app` so platforms agree)
- App support dir already used for `library.db` / settings — recovery store should live under the same support root.

## Behavior

- On desktop launch (after engine/host bootstrap is healthy), check for updates against a hosted `app-archive.json`.
- Show update UI via package widgets (`DesktopUpdateWidget` / dialog) or a thin Forui-aligned custom surface driven by `controller.state`.
- Support optional updates (soft prompt, skip/defer) first; mandatory / support-policy modes can follow once hosting + signing are solid.
- Before native install handoff, persist a pending-install marker via an app-owned `UpdateRecoveryStore` (file-backed under application support) and verify completion on next launch.
- Fail closed on signature / hash / package-id mismatch — never install an unverified artifact.

## Implementation direction

1. **App dependency + config**
   - Add `desktop_updater: ^3.1.6` (and `path_provider` if not already used for the recovery path).
   - Add `desktop_updater.yaml` at the Flutter app root with `updates.baseUrl` pointing at the Mixar update host.
   - Generate / pin `trustedReleasePublicKeys` via `dart run desktop_updater:release keygen` (or adopt existing 3.0 keys if any); commit public `desktop_updater.keys.json` only — keep private key material out of the repo.

2. **Controller wiring**
   - Construct `DesktopUpdaterController` with:
     - `appArchiveUrl`
     - `expectedPackageId` matching the published `release.json` `packageId` per platform
     - `trustedReleasePublicKeys`
     - `recoveryStore` under `{applicationSupport}/desktop_updater/…`
   - Mount updater UI near existing app chrome without fighting the custom title bar / Forui patterns; keep error feedback concise (toast/snackbar where custom UI is used).

3. **Release / publish pipeline**
   - Add `dart run desktop_updater:release doctor` + `publish --platform {macos,windows,linux}` to release docs/CI.
   - Decide upload provider vs manual upload of `dist/desktop_updater` artifacts.
   - Back up / restore signing keys for CI via `release keys export|import` and secrets (`DESKTOP_UPDATER_KEY_BUNDLE_PASSPHRASE`).
   - Align Windows package id with macOS/Linux (`top.mixar.app`) rather than pubspec `gui_flutter` unless there is a strong reason not to.

4. **Platform trust (app-owned)**
   - macOS: Developer ID + hardened runtime + notarize/staple before packaging.
   - Windows: Authenticode when publisher trust is required; zip and/or Inno artifacts as needed.
   - Linux: direct-ZIP only for this package release; preserve Unix executable modes in update zips.

## Acceptance criteria

- [ ] Desktop builds depend on `desktop_updater` and construct a controller with pinned keys + recovery store.
- [ ] Update check works against a real or staging `app-archive.json` host.
- [ ] Download → verify (size + SHA-256 + signatures) → stage → install/relaunch path works on at least one primary platform (prefer macOS or Windows first).
- [ ] Pending-install recovery survives relaunch after a successful update.
- [ ] Private signing material is documented for CI/humans and is not committed.
- [ ] Publish/doctor commands documented for Mixar release process.

## Out of scope

- AppImage / deb / rpm / Flatpak / Snap store delivery (explicitly outside `desktop_updater` 3.1 Linux scope; Linux zip path is preview/candidate-only).
- Mobile / web update channels.
- Shipping mandatory / support-policy / fresh-install policy modes in the first cut (optional updates only unless trivial).
- Replacing engine/host versioning or FRB transports.
