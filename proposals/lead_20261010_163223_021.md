*Project description:*
## What

Change `just follow-ups-answer-comments` so one pass reads the board's issues and comments **once**. The gathering is one plan-store copy, by query, into an immutable per-snapshot local Markdown source. Every later step works from that copy:
- the real run after a dry run;
- the pre-launch `check-gathering`;
- the dispatched feedback-mode agent and its response checks;
- `settle`.

**After the snapshot, the board is written (replies, ticket copies, priority, the one withdrawal), and the only board read is one batched verification at `settle`.** The one exception is the named, counted fallback the store makes when a write's cached ids are missing or stale.

This node builds on `aio-adopt-comment-copy`. That node put on this host a plan store offering:
- copy `--comments --no-link` by query, which writes each item and its comments into a local-md root exactly at the version it read, recording it in `onetaskgraph.copied_version`, with each comment's board id in `origin.id`;
- `Task.version` change tokens;
- the per-host cache, which `aio-adopt-comment-copy` turned on for `followups`, `hellopatient-followups`, `plans` and `hellopatient`;
- `--expect <version>` writes, which send only their mutation;
- `task comment add --json`, which returns the created comment's id and URL;
- a batched `task show-many`.

The store's own docs at the pinned release state that contract. This node renders no board item or comment itself. Every read and write goes through the store's ordinary verbs.

Files involved:
- `orchestrator/follow_up_comments.py`: `gather`, `select`, `render`/`write_feedback`, `settle`, `reply_urls`, the CLI, and the module docstring, which states the rules.
- `scripts/follow-ups-answer-comments.sh` and `scripts/follow-up-env.sh`, which configure the snapshot source.
- `orchestrator/follow_up_tickets.py`: `check-gathering` (`gathering_on_board`), `read_gathering`, `check-responses` (`responses_unanswered`, `replies_posted`), `re-estimate`, `board-status`, `copy`, the withdrawal, and the quoted-comment grammar.
- `scripts/follow-ups.sh`, as far as its `--comments` path needs.
- `templates/follow-up-task.md.j2`'s feedback mode.
- `AGENTS.md`'s follow-ups section.
- The journeys and tests the criteria name.

### Where the repeated reads are today

- A `--dry-run` runs the narrowed `task list` plus one `task comment list` per item, then writes nothing. The real run re-does the whole query.
- `check-gathering` re-reads every quoted issue's record and comments.
- The feedback-mode template tells the agent to read each issue with `task show` and its comments with `task comment list`.
- `re-estimate` recounts the comments on the board.
- `check-responses` re-reads the replies, both inside the dispatch and at `settle`.
- `reply_urls` looks each reply up again.
- Every store write reads its target first: ISSUE before ADD_COMMENT, UPDATE_FIELDS or UPDATE_ISSUE.

All of these go away.

### The snapshot contract

Every step that reads or writes a snapshot holds to this agreement. It is declared **once**, in `orchestrator/follow_up_comments.py`: the constants, the snapshot source's name and configuration, the one writer, the one reader, and the docstring section that states it. `follow_up_tickets.py`, the scripts and the template reach it only through that module, or through the paths, source name and lines it writes. A test reconciles each feedback file against `snapshot.json` and the snapshot source, and fails as soon as they differ.

1. **Where it lives.** `<drafts root>/feedback/.snapshots/<stamp>/`.
   - `<stamp>` is the board query instant in `STAMP_FORMAT` (`YYYYMMDDTHHMMSSZ`), with `-<n>` added when two gatherings share a second.
   - The leading dot keeps the directory out of the run-id grammar.
   - The directory is staged under a temporary name and renamed into place whole.
2. **`items/`** is a local-md source root: **the snapshot source**. It is configured, for every process that reads it, under the one source name the module declares (`snapshot`), as `ONETASKGRAPH_SOURCES__SNAPSHOT__PLUGIN=local-md` and `…__CONFIG__ROOT=<snapshot dir>/items`. Only the gathering's own copy writes it: one `task copy --to snapshot --comments --no-link`, either by the narrowed query (unscoped) or by the ids an `--issue`/`--run` pass reads. Nothing writes it afterwards. Each item there:
   - carries `onetaskgraph.origin` naming its board item, and `onetaskgraph.copied_version` naming the board `version` it holds;
   - carries the item's comments, each with `origin.id`, the board comment id replies name.

   The cache refreshing, this pass's own writes, and `cache clear` cannot change it.
3. **`snapshot.json`** (`schema: 1`) is the authoritative record of the pass. It holds:
   - `queried_at`: RFC 3339, the instant every watermark, boundary and feedback stamp derives from;
   - `board`, `boards`, `named_board`;
   - `scope` (a run id or `null`) and `issue` (a qualified id or `null`);
   - `starts`: per board, its start instant and where it came from;
   - `store`: the store's version line;
   - `dry_run`;
   - `items`: one entry per item, `{id, snapshot_id, version, title, owner, host, url}`. `id` is the board's qualified id, `snapshot_id` is the item's qualified id in the snapshot source, and `version` is the copied version;
   - `boundaries`: each recorded run's boundary instant or `null`, and whether this gathering computed it;
   - `selection`: per run, its chosen comments in order, each `{issue, comment, last_changed, body_sha256}`;
   - `left`: each left-out comment, as `{issue, comment, reason}`.
4. **`launched.json`** is absent until a launch claims the snapshot. It is written exclusively (`open("x")`) **before** any feedback file, holding the claim instant and whether the launch was fresh or `--from`.
5. **`<drafts root>/feedback/pending.json`** is the one host-wide record of settle writes that did not certainly land. It is not per snapshot, so the next pass finds it whatever it gathers. Each entry is `{snapshot, run, item, write, state, snapshot_version, seen_version, intended, parts, error, recorded_at}`:
   - `write` is one of `ticket-copy`, `priority` or `withdrawal`;
   - `state` is one of:
     - `withheld`: the batched read showed a person's edit since the snapshot, so nothing was written;
     - `failed`: rejected, or the response does not show the intended value;
     - `partial`: some parts landed;
     - `unknown`: the outcome was lost;
   - `parts` is the write's `result.parts` from the store, where one was attempted.

   Each entry also records `intended`: the value of every field the write sets. Recovery follows one rule, applied in the next pass's settle straight after its single batched read:
   - **Already applied: cleared, never repeated.** If the read shows the board holding every intended value, the entry is removed without sending the mutation again. This applies to an `unknown` write that in fact landed, and to a `partial` or `failed` one whose remaining fields the board already holds.
   - **Not, or only partly, applied: retried on the unapplied fields only.** Otherwise the entry is resolved to the fields still missing, and the retry is an `--expect` write of only those fields. This applies to an `unknown` write the read shows did not land, or landed only in part.
   - **A conflict is surfaced, not written.** If the read shows a person changed one of those fields since the entry's `seen_version` (or, for `withheld`, since its `snapshot_version`), the entry is surfaced as a conflict. It is kept and not written.
   - **Removal.** An entry is removed only when the read shows every intended value applied, or the retry's own mutation response shows its remaining parts landed. A retry whose response is rejected, partial or lost updates the entry under the same states and stays pending.
6. **Feedback files**: `feedback/<run>/<snapshot stamp>.md`.
   - Each names its snapshot directory on one marker line beside its `FEEDBACK_BOUNDARY` line.
   - Under each quoted issue, it names the issue's board id, its `snapshot_id` and its version on one line.
   - Each quoted comment carries its id, author, URL, last-changed instant and body, as today.

   `read_gathering`'s grammar, `render` and the template change together.

### The dry run → real run hand-off (rulings carried over)

- **`--dry-run`** gathers, writing the snapshot including its `items/` copy, and prints the selection and then the exact command `just follow-ups-answer-comments --from <absolute snapshot dir>`. It writes nothing to the board, and no feedback file, `boundary.txt` or watermark. It launches nothing.
- **`--from <dir>`** launches from that snapshot with **no board request** before its launches. It is refused beside `--since`, `--run`, `--issue`, `--to` and `--dry-run`; `--detach` is allowed. It is refused, with nothing written and each refusal naming the fresh `--dry-run` to run instead, when:
  - the snapshot is malformed;
  - it is already consumed (naming the first launch's instant);
  - it is older than `SNAPSHOT_LAUNCHABLE_FOR`, one named `timedelta(hours=24)` constant;
  - a later, overlapping snapshot of the same board family has since been launched. An unscoped snapshot overlaps all; two scoped ones overlap on the same run.
- **It is never refused because the board or the cache moved after the snapshot.** The launch answers exactly the versions `selection` records, from the snapshot source.
- **A plain run** gathers, writes a snapshot and launches from it through the same path, with no second read.
- Nothing picks up a "latest" snapshot by itself.
- At the launch, not the dry run, the recipe writes the needed `boundary.txt` files, then the feedback files, then the plan.

### Reads and writes after the snapshot

- **Every read of a snapshot item** goes to the snapshot source, through the store's local-md reads (`task show snapshot:<id> --json`, `task comment list snapshot:<id>`), never to the board or the cache. That covers `check-gathering`, the feedback agent, and `check-responses` in the dispatch. These reads send no network request at all.
- **The feedback agent** posts replies with `task comment add <board id> --expect <snapshot version> --json`. It records the reply's id and URL from that response in the run's response account; nothing looks a reply up. Its other work is local: it edits ticket records and validates them. It no longer runs `board-status`, `copy`, `re-estimate` or the withdrawal. `check-responses` in the dispatch reads the response account and the snapshot source only.
- **`settle`** makes the pass's single board read first. It is one batched, unpinned `task show-many` over every issue the pass replied on (the runs' ticket items) and every item named in `pending.json`. That read verifies each reply and gives every pending entry the board's current values, so the recovery rule in item 5 of the contract decides each one: cleared, retried on its unapplied fields, or surfaced.
- **Settle's writes, straight after the read.** Using that read's values, `settle` makes every write whose rule depends on a value a person may change. Each write is `--expect <the version the read returned>`, field-scoped, so it sends only its mutation and only the fields it changes. The writes go item by item, straight after the read, retrying the pass's own pending entries first and then this pass's writes, so each item's window between the read and its mutation is as short as practical. The writes are:
  - the **priority re-estimate**, computed from the snapshot's comments plus this run's own replies, never a board recount. If the read shows a priority that differs from the stored estimate, the person's priority stands, and nothing is written;
  - the **one withdrawal** (a status write), only when the read shows the item still at `Proposal`;
  - **ticket copies back**, only for tickets whose record changed, sending only the changed fields. If the read shows a ticket's board item changed since its snapshot version by anything other than this pass's own replies (a person's edit), the copy is **withheld**: not written, and recorded `withheld`.
- **Each settle write is verified from its own mutation response**, the store's `result`, with no extra read:
  - a write whose every part `landed` with the intended values is done;
  - a rejected write, or one whose response does not show the intended value, is recorded `failed`, with the error;
  - a ticket copy with some parts landed is recorded `partial`, naming which parts;
  - a lost response is recorded `unknown`.

  No write is retried within the pass.
- **Pending work.** A pass that ends with any entry in `pending.json`, its own or carried over, ends with the recipe's final status saying **needs attention** and listing each entry, never reading as fully done. The next pass, whatever it gathers, handles every pending entry first, by the contract's recovery rule (item 5), against the values its batched read shows. An entry the board already holds is cleared without repeating the mutation. Only unapplied fields are retried. A person's change to one of those fields is surfaced as a conflict, not written.
- **The residual race, an accepted exception.** Neither backend offers a conditional write. So a person's edit to a field a settle write sets, landing in the seconds between the batched read and that item's mutation, is overwritten. Edits before the read are caught and withheld, and edits to fields the write does not set are never touched. Today's flow carries the same class of window between its pre-write read and its write. The module docstring states this exposure in those words.
- **Store fallback.** When a write's cached ids are missing (after `cache clear`) or rejected as stale, the store makes one read, then the write. The recipe names each such fallback in its output and counts it in the budget's telemetry. The realistic pass has none.
- **Where the board gives an item no `version`** (a Linear board whose token is still unproven), the copy and the writes still work, but `--expect` has no version to state. Each write there takes the store's own pre-write read, and the recipe's output names it. This is an accepted exception recorded in the plan.

### Watermark, boundary and the answered-version rule (carried over)

- The watermark moves only in `settle`, and only when all of these hold:
  - the snapshot is unscoped;
  - every launched run was checked sound, which means every reply was posted and verified. Pending ticket, priority and withdrawal writes do not hold it, because `pending.json`, not the comment gathering, drives their retry. A failed or unknown reply makes its run unsound and holds the watermark, as today;
  - it moves to `queried_at` minus `OVERLAP`, for every board in `boards`;
  - it never moves backward.

  A dry run never moves it.
- A boundary is computed when the snapshot is gathered, exactly as `run_boundary` computes it today, and carried on the feedback file's boundary line. A feedback file's stamp is the snapshot's query instant.
- **A reply answers the version its gathering quoted.** This is stated once, in the module docstring's "answered" reason, and decided from this host's local response accounts. A reply mapped to a quoted version older than the comment's current one leaves the comment unanswered. A reply with no local account keeps today's time rule. Nothing stored on the board changes shape.

### What must not change

- A dry run writes nothing to the board and moves no watermark.
- Feedback mode's bounds stay: answer only the quoted comments, touch only their issues' tickets, and use the one withdrawal exception. Settle now performs the ticket copy and the withdrawal on the dispatch's behalf, under the same bounds. The one exception is recovery: settle also retries or clears the entries `pending.json` already holds from earlier passes, which may name unquoted issues, and writes to them only those entries' `intended` values.
- The routing reasons and their order are unchanged.
- `--run` and `--issue` list no board.
- Every existing budget's threshold is unchanged.


## Why

A dry run exists to show what the real run will do. Today the real run asks the board again and can answer a different set of comments from the set the preview showed. When the real run answers exactly what the preview listed, from a copy nothing else can change, a person can check what will be posted on their behalf before anything is posted. A change on the board between the two steps is picked up by the next pass, not acted on without notice.

Each board read spends part of an allowance that every session on every host shares: GitHub's hourly GraphQL points for the `followups` board, and Linear's limit for Hello Patient's routed tickets. The same command runs on several hosts sharing one board token, so one pass has to fit a small share of it. Today a pass reads the same issues and comments up to four times, reads each write's target again before writing, and re-reads its own replies. Reading once into a local copy, writing without pre-reads, and verifying in one batch brings a realistic pass from hundreds of points to tens.

Neither saving may cost correctness. A comment written or edited after the snapshot must still be answered by a later pass. A person's priority, status or ticket edit made before settle reads the board must never be overwritten, and the seconds-long window between that read and each write is stated as an accepted exception, never hidden. A write that did not certainly land must never silently vanish.

## Additional info

**Contract discipline.** The snapshot contract and the read and write rules above are fixed for this run. They are declared in `orchestrator/follow_up_comments.py` and imported by every other reader. runnable by a worker, and a dispatch is never held to one having passed. That holds on a
retry too. A `checks-failed` retry — a re-dispatch onto the same branch carrying the

**Never signal a process you did not identify by PID, and a PID you got from a pattern is
still a pattern kill.** Several managers share this host, and their dispatches, drivers,

matched. The distinction is the tool rather than the pattern: `pgrep` and `ps` **read**,

never the answer here, in any spelling. `-x` is the trap, because it reads as the careful
one — `pkill -f 'just gate'` at least needs a narrowing pattern, while `pkill -x just`
takes every `just` on the machine. Reading the table first and piping the pids into `kill`

**The one process you may signal is one you started yourself, so capture its PID as you

    kill "$MYPID"

Anything you did not start belongs to somebody. Read what it is, report what you found,

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or
`publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

**A process must finish inside the turn that started it.** Backgrounding is how you wait

you no sign of that, because it succeeded and the turn then ended normally. The loss

signal, with the whole run to pay for again. It bites hardest where it is most tempting,

threaten the turn — here the judged lint tier and a whole test tier, which are the two

result on the next one.
