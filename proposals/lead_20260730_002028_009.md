# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**feat(robot): add phone-only Robot configuration**

*Project description:*
## Summary

Add a **phone-only Robot** configuration to the existing Android Robot app. This configuration runs entirely on the phone:

- no ESP32/XIAO controller;
- no BLE controller connection;
- no servo or carousel;
- no PIR sensor;
- no external buttons, LEDs, buzzer, or other Robot hardware;
- no simulated or fake physical dispense records.

The same Robot APK must support both hardware-assisted and phone-only installations. During Robot onboarding, the user chooses whether this device has controller hardware. A guarded Settings flow allows changing that choice later, for example if hardware is added or removed.

Phone-only Robot wakes its face for scheduled doses or normal screen/touch interaction. At dose time it presents medication instructions and records digital actions such as **Taken**, **Snooze**, **Skip**, missed-dose acknowledgement, or caregiver-help actions through the same local-first dose history and backend synchronization used by the normal Robot.

## Product decision

Use one Robot app and model hardware as an orthogonal device capability:

```text
Robot cloud/connectivity mode
  - local
  - cloud-mounted

Robot hardware mode
  - hardware-assisted
  - phone-only
```

Do not introduce a separate phone-only APK, flavor, package name, or app-store release. Hardware capability must not be encoded as a compile-time build profile.

This issue does **not** require combining the existing local and cloud-mounted deployment configurations into one production configuration. It requires that whichever Robot APK is deployed can choose hardware-assisted versus phone-only behavior at runtime.

## Feasibility and hard limits

This is feasible while Android is running.

The app cannot power on a fully shut-down phone. A phone-only Robot deployment must assume:

- the phone remains powered on;
- the phone is normally connected to power;
- Dosey remains the foreground kiosk/home experience, or the user can return to it;
- scheduled Android wake behavior is best effort unless the device is provisioned as a managed dedicated device and exact-alarm requirements are satisfied.

No camera, microphone, proximity sensing, or motion sensing is needed. There is no automatic person-presence detection. Wake triggers are only:

1. a scheduled dose event;
2. the user waking/tapping the phone.

## Goals

- One Robot APK supports hardware-assisted and phone-only configurations.
- Onboarding clearly asks whether controller hardware is attached.
- Phone-only composition does not initialize, scan for, connect to, monitor, or report health for a BLE controller.
- Phone-only Robot never displays controller-offline errors as though missing hardware were a fault.
- Dose schedules wake the Robot face and present an actionable dose experience.
- Phone-only actions include Taken, Snooze, Skip, and the existing applicable missed/help flows.
- Actions persist locally first and synchronize through the existing backend path.
- History identifies that no physical dispense occurred.
- A guarded Settings flow supports switching hardware mode safely.
- Existing hardware-assisted Robot behavior remains unchanged.
- No fake controller movement, command session, servo completion, visible-dose proof, or physical inventory decrement is created in phone-only mode.

## Non-goals

- Waking a powered-off phone.
- Camera-based presence detection.
- Always-on microphone or hotword detection.
- Simulating physical dispensing.
- Automatically marking a dose taken.
- Treating a notification delivery as proof the dose was seen or taken.
- Removing hardware-assisted Robot support.
- Resolving the staged BLE state-machine blockers tracked in #79.
- Redesigning the Personal app or household model.

## Current architecture to preserve

The current application intentionally separates display wake from physical movement:

- External PIR currently emits `WAKE_FACE` over BLE.
- `DoseyShell` routes that event to Robot Face and controls an awake window.
- Scheduled reminders already exist independently of controller movement.
- `RobotFaceController` derives dose states from schedule, history, and controller state.
- `ControllerLifecycleService` owns physical movement and its audit/inventory safety boundary.
- `DoseActionService` and `DoseLogRepository` own medication outcomes.

Phone-only mode must preserve this separation. It should bypass the physical-controller path rather than impersonate it.

## Recommended design

### 1. Persisted hardware capability

Introduce an explicit domain value such as:

```dart
enum RobotHardwareMode {
  hardwareAssisted,
  phoneOnly,
}
```

Requirements:

- Persist the choice in device-local Robot configuration.
- Do not infer it from BLE availability, connection state, build flavor, simulator state, or cloud state.
- Do not silently fall back from hardware-assisted to phone-only when BLE fails.
- Require an explicit selection during new Robot onboarding.
- Define migration behavior for existing Robot installations: preserve them as `hardwareAssisted` unless the product has explicit evidence otherwise.
- Expose a read-only capability through app dependencies so UI and services branch from one source of truth.

Keep hardware mode independent from local/cloud-mounted access. A cloud-mounted Robot may be phone-only or hardware-assisted; the same is true for local Robot unless product policy later narrows that combination.

### 2. Composition and dependency isolation

At app composition time:

#### Hardware-assisted

Keep the existing path:

```text
FlutterBluePlusBleGateway
  -> BleControllerGateway
  -> ControllerHealthSupervisor
  -> ControllerLifecycleService
  -> RobotFaceController
```

#### Phone-only

Do not construct:

- `FlutterBluePlusBleGateway`;
- `BleControllerGateway`;
- controller health supervision;
- physical command repository/session lifecycle solely for movement;
- `ControllerLifecycleService` for dispense movement;
- Bluetooth permission/setup requirements.

Do not use `SimulatedControllerGateway` in production phone-only mode. Simulation means test/demo behavior and would create misleading controller semantics.

Prefer an explicit capability-aware Robot Face dependency boundary over nullable checks scattered across screens. For example, expose a dose-interaction coordinator with distinct physical and digital implementations:

```text
RobotDoseInteraction
  - HardwareDoseInteraction
  - PhoneOnlyDoseInteraction
```

The phone-only implementation records medication outcomes but has no movement methods or controller stages.

### 3. Phone-only dose state machine

At a due dose:

```text
scheduled
  -> doseApproaching
  -> doseReady
  -> user action
```

Available actions:

- **Taken** — user explicitly confirms the medication was taken.
- **Snooze** — record the snooze and schedule the next prompt according to existing policy.
- **Skip** — explicitly record a skipped dose, including any existing confirmation/safety copy.
- **Ask for help** — retain existing caregiver-help behavior where available.
- **Missed-dose acknowledgement** — retain existing missed-dose safety workflow.

Phone-only mode must not pass through these physical stages:

- dispense requested;
- command sent;
- firmware accepted;
- movement started;
- servo completed;
- dose visible after movement.

Taken remains explicit user testimony. The UI must not imply that the phone dispensed or verified medication.

### 4. Dose log and backend semantics

Reuse the established dose-log event model where its meaning is accurate:

- `doseTakenConfirmed`;
- `doseSnoozed`;
- `doseSkipped`;
- `caregiverHelpRequested`;
- `doseMissed`;
- `doseMissedRecognized`;
- existing early/late/already-taken outcomes where policy permits.

Do not create:

- `controllerDispenseSucceeded`;
- controller command sessions/events;
- physical visibility confirmation;
- movement-driven inventory mutations.

Before implementation, map the current sync contract to confirm that these outcome events already reach the backend for mounted Robots. If event provenance is not represented, add a narrow source field such as `hardware-assisted`, `phone-only`, or `personal` only if backend consumers need to distinguish them. Do not fork a second phone-only history system.

Offline behavior:

- write actions to the local database first;
- render the local result immediately;
- synchronize when connectivity returns through the normal Robot backend path;
- never block Taken/Snooze/Skip solely because the cloud is temporarily unavailable;
- preserve conflict/idempotency rules already used by dose history.

### 5. Inventory semantics

Phone-only Robot cannot prove a package or carousel slot changed.

Recommended policy:

- Do not mutate carousel or controller-managed inventory.
- If the existing prescription inventory model decrements on explicit Taken confirmation independent of controller movement, retain that behavior only where it represents user-managed supply accurately.
- Keep controller/carousel inventory and general medication supply conceptually separate.
- Add tests proving phone-only actions cannot quarantine slots, create needs-review movement state, or consume guided-carousel positions.

The implementation session must inspect `DoseActionService` preconditions before choosing the exact reuse point. Current `recordRobotFaceVisibleAndTaken` expects movement/visibility proof and should not be reused unchanged for phone-only confirmation.

### 6. Scheduled wake and display behavior

#### Baseline deployment

- Keep the Robot app foregrounded.
- Keep the phone connected to power.
- Use the existing screen-awake gateway to keep the display active or dimmed while charging.
- Represent sleep primarily as a dim/sleepy Robot Face, not process suspension.
- At dose time, transition the face to `doseApproaching`/`doseReady`, brighten the display, play configured audio, and hold an awake window.
- A normal screen tap/user wake returns to the active Robot Face.

#### Android wake path

Extend scheduling so a scheduled dose can request a wakeup alarm where policy allows. The wake path should:

1. wake the CPU at the scheduled dose time;
2. surface the Dosey activity through a permitted alarm/notification path;
3. call existing `setTurnScreenOn(true)`/`wakeScreen` behavior;
4. route directly to the current due-dose Robot Face;
5. create no medication outcome until the user acts.

Android constraints:

- A wakeup alarm does not itself guarantee the display turns on.
- Exact alarm access must be checked with `AlarmManager.canScheduleExactAlarms()`.
- `SCHEDULE_EXACT_ALARM` may require user-granted special access.
- Full-screen intents must only be used if the dose reminder legitimately qualifies as an alarm-like urgent event and deployment policy permits it.
- Do not build around arbitrary background activity launches or unrestricted foreground-service starts.

For the strongest unattended deployment, plan a follow-up managed-kiosk setup:

- device owner / fully managed device;
- Dosey as persistent home activity;
- lock-task allowlisting;
- stay-on-while-plugged-in policy;
- boot recovery and alarm rescheduling.

Do not make device-owner provisioning a hidden requirement for the first phone-only implementation. Clearly document the reliability difference between managed kiosk and ordinary app deployment.

Official Android references:

- Dedicated devices: https://developer.android.com/work/dpc/dedicated-devices
- Lock task: https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode
- Alarm scheduling: https://developer.android.com/develop/background-work/services/alarms
- Exact-alarm changes: https://developer.android.com/about/versions/14/changes/schedule-exact-alarms
- Background activity limits: https://developer.android.com/guide/components/activities/background-starts

### 7. Onboarding

Add a Robot setup step with plain wording, for example:

> Does this Robot have a Dosey controller attached?

Options:

- **Phone only** — reminders and dose check-ins run on this phone. No medication is physically dispensed.
- **Controller hardware** — connects to the Dosey controller for physical movement and optional presence wake.

Behavior:

- Explain that the choice can be changed later in guarded Settings.
- Phone-only selection skips Bluetooth permission, controller discovery, pairing, heartbeat, and controller qualification screens.
- Hardware-assisted selection preserves all current setup and safety checks.
- Cloud mounting/account restoration remains a separate step and must not be described as hardware pairing.
- Add accessibility semantics and clear confirmation copy because this choice changes safety behavior.

UI work should be handled through the existing designer workflow rather than implemented as a mechanical form.

### 8. Guarded Settings change

Add a Settings flow that shows the current hardware mode and consequences of changing it.

#### Hardware-assisted -> phone-only

Before switching:

- require explicit confirmation;
- prevent the switch while a command is active or physical outcome is unresolved;
- stop scanning/reconnection and close controller services cleanly;
- preserve all historical controller audit records;
- leave unresolved physical inventory/review state visible for manual resolution;
- remove controller-offline status from the active face after re-composition.

#### Phone-only -> hardware-assisted

Before enabling:

- require explicit confirmation;
- request Bluetooth permissions only then;
- run controller setup/discovery/qualification;
- do not mark the mode active until setup succeeds, or represent a clear setup-incomplete state;
- never silently return to phone-only because setup fails.

Because composition currently occurs near application startup, choose one explicit strategy:

1. persist the new mode and require an app restart/re-entry; or
2. introduce a narrow re-composition coordinator.

For the first implementation, a confirmed mode change followed by controlled app restart is safer and lower risk than hot-swapping BLE/controller dependency graphs.

### 9. Robot Face behavior

Phone-only mode should retain normal expressive states that do not imply hardware:

- idle;
- sleepy;
- dose approaching;
- dose ready;
- waiting for user confirmation;
- missed;
- error for real schedule/storage/sync failures.

It must not show:

- controller offline;
- reconnecting controller;
- servo error;
- carousel movement;
- physical dispensing animation/copy;
- instructions to troubleshoot absent hardware.

Introduce capability-aware copy and actions without flattening the existing Robot Face design. UI/interaction changes belong to the designer lane.

### 10. Build, permissions, and release behavior

- Continue producing one Android Robot artifact for a given deployment configuration.
- Do not add a phone-only flavor.
- Do not require Bluetooth permission during startup or onboarding when phone-only is selected.
- Keep Bluetooth manifest declarations if the same artifact supports hardware-assisted mode; runtime permission requests must be capability-gated.
- Add CI/widget coverage proving both hardware selections compile and compose from the same Robot build.
- Document that phone-only does not mean powered-off wake support.

### 11. Backend and mounted access

Cloud mounting and hardware capability are independent:

- A cloud-mounted phone-only Robot restores mounted access through the same restoration-only contract.
- Backend dose-history sync uses the same authenticated/anonymous mounted association as the normal Robot.
- Losing mounted authorization must block cloud writes or surface sync status according to existing policy, but must not invent physical controller errors.
- Local Robot remains usable without Appwrite; local phone-only actions stay local unless/until a supported sync path is configured.

Before implementation, verify whether hardware capability needs backend persistence. Recommended default:

- local device setting is authoritative for composition;
- backend may receive capability metadata for fleet/support visibility;
- backend metadata must not remotely and silently switch physical safety mode.
