## 1. The Real Role: What This Person Actually Does

This is not a "build ML models" or "design strategy" role. It is an **operations data analyst embedded in a global returns/reverse-logistics or compliance function** (likely Worldwide Returns & ReCommerce or an operations quality team). The daily work is:

- **Morning:** Check dashboards for overnight exceptions, triage urgent data failures.
- **Mid-morning:** Run SQL validation queries against Redshift/Andes tables, investigate broken records.
- **Afternoon:** Classify exceptions (delivery disputes, losses, suspected theft), escalate to Loss Prevention or carrier claims.
- **Late afternoon:** Update Power BI dashboards, respond to stakeholder asks, document fixes.
- **Ongoing:** Automate recurring manual work, maintain reporting pipelines, train teammates.

Amazon job postings for this exact profile describe it as: "Use data and analytics to identify operational gaps, drive business decisions… discover patterns of risks, abuse… Write SQL queries and leverage data to surface gaps" .

## 2. The Real Tools (What They Actually Are at Amazon)

### Amazon Redshift
**What it is:** Amazon's petabyte-scale cloud data warehouse. It stores structured operational tables (shipment records, driver rosters, audit logs) that analysts query with SQL. It uses columnar storage and massively parallel processing to handle large analytical queries fast .

**How the analyst uses it:** Writing SELECT queries against tables like `shipment_tracking`, `driver_roster`, `audit_exceptions`. Joining tables, filtering by region, aggregating counts. This is the primary database they live in all day.

### Amazon QuickSight
**What it is:** Amazon's native business intelligence (BI) service for building dashboards and visualizations. It connects to Redshift, S3, Athena, and other sources. It has an in-memory engine called SPICE for fast dashboard loading .

**How the analyst uses it:** Building operational dashboards showing audit pass rates, exception trends by region, and delivery dispute counts. Sharing dashboards with ops managers who check them every morning.

### Amazon S3
**What it is:** Object storage that serves as the data lake foundation. Raw data (logs, exports, staging files) lands here before being processed into Redshift or queried via Athena .

**How the analyst uses it:** Occasionally pulling raw exports or log files that haven't made it into the warehouse yet.

### Amazon Athena
**What it is:** A serverless query service that runs SQL directly against data in S3. No infrastructure to manage. Good for ad-hoc queries on raw/staging data .

**How the analyst uses it:** When a data source isn't in Redshift yet, they query the S3 file directly with Athena to check something quickly.

### Andes
**What it is:** Amazon's internal data lake/catalog system. It stores exabytes of data and serves as the enterprise data catalog. Analysts reference Andes tables to find and access operational datasets .

**How the analyst uses it:** Looking up table schemas, finding which Andes table contains the driver roster or shipment events they need to join against.

### Excel
**What it is:** Still used for quick pivots on small extracts, packaging findings for non-technical stakeholders, and ad-hoc reconciliation when a full SQL query is overkill.

**How the analyst uses it:** Pasting a 50-row exception list into Excel to add notes before sending to ops managers who won't open SQL.

### Power BI
**What it is:** Microsoft's BI tool. The resume explicitly says Power BI, not QuickSight. Some Amazon teams (especially those supporting acquired entities or specific operational functions) standardize on Power BI.

**How the analyst uses it:** Building the operational dashboards that stakeholders actually open. Connecting to Redshift, creating measures with DAX, scheduling refreshes.

## 3. A Real Day (Hour by Hour)

### 8:30 AM — Dashboard Check

The analyst opens their Power BI dashboard. Overnight data refreshed at 6 AM. They scan for red flags:

- **Audit pass rate by region:** NA is at 98%, EU at 94%, APAC at 100%.
- **Exception count:** 47 records flagged, up from 12 yesterday.
- **EU spike:** 23 of the 47 exceptions are from EU, all with the same pattern: "Delivered but scan_time is NULL."

They drill into the EU exceptions. The driver IDs are all D-447. They pull the raw records with SQL:

```sql
SELECT record_id, tracking_id, carrier, scan_status, scan_time, pod_photo, driver_id
FROM raw_shipment_tracking
WHERE region = 'EU'
  AND scan_status = 'Delivered'
  AND scan_time IS NULL
  AND promised_date >= CURRENT_DATE - 1;
```

Result: 23 records, all carrier DHL, all driver D-447, all missing scan_time.

### 9:30 AM — Ops Standup

The analyst joins a 15-minute call with the EU operations manager and a logistics coordinator. They share the finding: "D-447's deliveries from yesterday have no scan timestamps. The carrier's feed might be broken."

The ops manager asks: "Are these actually delivered or lost?"

The analyst says: "Can't confirm yet. I'll check if the carrier sent any scan event at all, and cross-reference with customer claims."

### 10:00 AM — Deep Investigation

Back at the desk. First, check if DHL sent *any* scan data for these tracking IDs:

```sql
SELECT r.record_id, r.tracking_id, r.scan_status, r.scan_time, c.carrier_scan_event
FROM raw_shipment_tracking r
LEFT JOIN carrier_scan_feed c ON r.tracking_id = c.tracking_id
WHERE r.driver_id = 'D-447'
  AND r.promised_date >= CURRENT_DATE - 1;
```

Result: The carrier feed shows scan events exist, but the `scan_time` field wasn't populated in Amazon's table. **This is a data pipeline issue, not a delivery failure.** The carrier did scan the packages; the integration dropped the timestamp.

Second, check customer claims for these tracking IDs:

```sql
SELECT tracking_id, COUNT(*) AS claim_count
FROM customer_claims
WHERE tracking_id IN (SELECT tracking_id FROM raw_shipment_tracking WHERE driver_id = 'D-447')
GROUP BY tracking_id;
```

Result: Zero customer claims. The packages were delivered. The problem is purely data quality.

**Classification:** Data pipeline failure — carrier integration dropped `scan_time`. Not a loss, not a theft.

### 11:00 AM — Root Cause and Fix

The analyst traces the pipeline. The EU carrier integration has a mapping table that translates DHL's event codes to Amazon's internal status codes. The mapping for "delivered" was recently changed, and the new mapping doesn't populate `scan_time`.

They document the finding, create a ticket for the data engineering team to fix the mapping, and add a **validation rule** to catch this specific pattern in the future:

```sql
-- New validation check: Delivered but scan_time NULL for known carrier
SELECT record_id, tracking_id, 'EU_DHL_MISSING_SCAN_TIME' AS issue
FROM raw_shipment_tracking
WHERE carrier = 'DHL'
  AND region = 'EU'
  AND scan_status = 'Delivered'
  AND scan_time IS NULL;
```

### 12:00 PM — Handle a Fraud Escalation

An ops manager forwards a customer complaint: "Package marked delivered, customer says never received. Driver ID looks weird."

The analyst pulls the full record:

```sql
SELECT *
FROM raw_shipment_tracking
WHERE tracking_id = 'T-99123';
```

Result:
- Status: Delivered
- POD photo: No
- Scan time: 2024-03-15 23:47 (unusual — late night)
- Driver ID: D-999
- Customer claim: "Not received"

They check the driver roster:

```sql
SELECT driver_id, driver_name, active_status
FROM driver_roster
WHERE driver_id = 'D-999';
```

Result: **No rows.** D-999 is not a valid driver in the roster.

They run a pattern check:

```sql
SELECT driver_id, COUNT(*) AS dispute_count
FROM raw_shipment_tracking
WHERE customer_claim = 'Not received'
  AND scan_status = 'Delivered'
  AND pod_photo = 'No'
GROUP BY driver_id
HAVING COUNT(*) > 2;
```

Result: D-999 has 7 disputes in the last 30 days.

**Action:** Escalate to Loss Prevention with the evidence chain (invalid driver ID, no POD, multiple disputes, late-night scan). This matches Amazon's real Loss Prevention workflow — LP investigates driver theft patterns and escalates to law enforcement when confirmed .

### 2:00 PM — Update the Dashboard

The analyst updates the Power BI dashboard to reflect today's findings:

- EU exception count corrected (23 were pipeline failures, now classified as "Data Issue — Resolved")
- Fraud escalation logged (1 new case)
- Audit pass rate recalculated: EU back to 99% after excluding pipeline failures

They also add a new card to the dashboard: **"Invalid Driver ID Exceptions"** so ops managers can see this pattern without waiting for a complaint.

DAX measure added:

```dax
Invalid Driver Exceptions =
CALCULATE(
    COUNTROWS(validated_shipment_tracking),
    validated_shipment_tracking[data_quality_flag] = "Invalid Driver ID"
)
```

### 3:30 PM — Stakeholder Follow-Up

The EU ops manager asks: "Can we get a list of all D-447 deliveries from last week? I want to confirm with the carrier that they actually scanned them."

The analyst runs:

```sql
SELECT record_id, tracking_id, promised_date, scan_status, scan_time
FROM raw_shipment_tracking
WHERE driver_id = 'D-447'
  AND promised_date BETWEEN CURRENT_DATE - 7 AND CURRENT_DATE
ORDER BY promised_date;
```

Exports to Excel, adds a note about the pipeline issue, sends to the ops manager.

### 4:30 PM — Documentation and Handoff

The analyst updates the SOP for EU carrier integration validation. Adds:

- **New check:** `EU_DHL_MISSING_SCAN_TIME` — run daily, alert if count > 5.
- **Escalation path:** Data engineering ticket for mapping fix.
- **Stakeholder notification:** Ops manager, EU region.

They also add a note to the team wiki: "D-999 is a fraudulent driver ID. Escalated to LP on 2024-03-15."

### 5:00 PM — End of Day

The analyst checks the dashboard one last time. EU is at 99%, the pipeline fix ticket is in the engineering queue, and the fraud case is with Loss Prevention.

Tomorrow's priority: Follow up on the DHL mapping fix and check if any new D-999 records appeared.

## 4. The Real Queries (What They Actually Write)

### Daily Validation Query (Runs Automatically)

```sql
-- This view is created once, queried daily by Power BI or scheduled email
CREATE OR REPLACE VIEW daily_audit_exceptions AS
SELECT
    record_id,
    tracking_id,
    region,
    carrier,
    driver_id,
    promised_date,
    scan_status,
    scan_time,
    pod_photo,
    customer_claim,
    CASE
        WHEN scan_status IS NULL THEN 'MISSING_STATUS'
        WHEN scan_status = 'Delivered' AND scan_time IS NULL THEN 'DELIVERED_NO_SCAN_TIME'
        WHEN scan_status = 'Delivered' AND pod_photo = 'No' THEN 'NO_POD'
        WHEN customer_claim = 'Not received' AND scan_status = 'Delivered' THEN 'CLAIM_VS_DELIVERED'
        WHEN driver_id IS NULL AND scan_status = 'Delivered' THEN 'MISSING_DRIVER_ID'
        ELSE 'OK'
    END AS exception_type
FROM raw_shipment_tracking
WHERE promised_date >= CURRENT_DATE - INTERVAL '7 days';
```

### Driver Fraud Pattern Query

```sql
-- Flag drivers with multiple disputes and no POD
SELECT
    driver_id,
    COUNT(*) AS total_deliveries,
    SUM(CASE WHEN customer_claim = 'Not received' THEN 1 ELSE 0 END) AS disputes,
    SUM(CASE WHEN pod_photo = 'No' THEN 1 ELSE 0 END) AS no_pod_count,
    ROUND(
        100.0 * SUM(CASE WHEN customer_claim = 'Not received' THEN 1 ELSE 0 END) / COUNT(*),
        2
    ) AS dispute_rate_pct
FROM raw_shipment_tracking
WHERE scan_status = 'Delivered'
  AND promised_date >= CURRENT_DATE - 30
GROUP BY driver_id
HAVING COUNT(*) > 10
   AND SUM(CASE WHEN customer_claim = 'Not received' THEN 1 ELSE 0 END) > 2
ORDER BY dispute_rate_pct DESC;
```

### Invalid Driver ID Check

```sql
-- Join to roster to find drivers not in the system
SELECT
    r.record_id,
    r.tracking_id,
    r.driver_id,
    r.promised_date,
    'INVALID_DRIVER' AS issue
FROM raw_shipment_tracking r
LEFT JOIN driver_roster d
    ON r.driver_id = d.driver_id
WHERE r.driver_id IS NOT NULL
  AND d.driver_id IS NULL
  AND r.scan_status = 'Delivered';
```

### Audit Pass Rate Calculation

```sql
-- Overall and by region
SELECT
    region,
    COUNT(*) AS total_records,
    SUM(CASE WHEN audit_status = 'PASS' THEN 1 ELSE 0 END) AS passed,
    ROUND(
        100.0 * SUM(CASE WHEN audit_status = 'PASS' THEN 1 ELSE 0 END) / COUNT(*),
        2
    ) AS pass_rate_pct
FROM validated_shipment_tracking
WHERE promised_date >= CURRENT_DATE - 30
GROUP BY region
ORDER BY region;
```

## 5. Interview Questions and How to Answer Them (Real Amazon Style)

### Behavioral (STAR Format, Tied to Leadership Principles)

**Q1: Tell me about a time you found a data quality issue that others missed.**

> **S:** During my morning dashboard check, I noticed a spike in EU exceptions — 23 records marked "Delivered" but with no scan timestamp.
> **T:** Determine if this was a real delivery failure or a data problem.
> **A:** I ran a SQL join to the carrier scan feed and found the carrier *had* sent scan events, but Amazon's integration dropped the timestamp. I also checked customer claims — zero for these tracking IDs. I classified it as a pipeline failure, not a loss, and created a ticket for engineering to fix the mapping. I added a new validation rule to catch this pattern automatically.
> **R:** The 23 records were reclassified as data issues, not losses. The audit pass rate for EU stayed at 99% instead of dropping to 94%. The validation rule prevented future occurrences from going unnoticed.
> **Principle:** Dive Deep.

**Q2: Describe a time you automated a manual process.**

> **S:** The team was manually pulling exception reports from Redshift into Excel every morning, running VLOOKUPs, and emailing them to ops managers. It took about 2 hours daily and was error-prone.
> **T:** Reduce manual effort and eliminate errors.
> **A:** I created a SQL view that pre-classified exceptions, connected Power BI directly to that view with a scheduled refresh, and set up the dashboard to email a summary to ops managers at 7 AM. The manual Excel step was eliminated.
> **R:** Manual time dropped from 2 hours to near zero. The error rate went down because no human was copying and pasting. Ops managers got the data earlier (7 AM vs. 9 AM).
> **Principle:** Invent and Simplify.

**Q3: How do you handle a suspected fraud case?**

> **S:** An ops manager forwarded a customer complaint about a delivery. The driver ID looked unusual.
> **T:** Determine if this was a normal dispute or something more serious.
> **A:** I pulled the full record — no POD, late-night scan, customer claim. Then I checked the driver roster: the driver ID wasn't in the system. I ran a pattern query and found 7 similar disputes for that ID. I escalated to Loss Prevention with the evidence chain.
> **R:** Loss Prevention investigated. This matched their workflow for driver theft cases. I didn't resolve it myself — I routed it correctly with the data they needed.
> **Principle:** Bias for Action / Earn Trust.

**Q4: How do you standardize reporting across regions with different definitions?**

> **S:** NA, EU, and APAC defined "received" differently, so global reports were incomparable.
> **T:** Align the definition and update reporting.
> **A:** I met with regional ops managers to understand their definitions. We agreed on one: "received when scanned into the system." I updated the SQL views and Power BI templates to use that definition, documented it in the metric glossary, and trained the teams.
> **R:** Global reports became trustworthy. Regional numbers could be compared without caveats.
> **Principle:** Earn Trust.

**Q5: What would you do if the audit pass rate dropped from 100% to 90%?**

> First, I'd scope the drop: which region, which exception type, which time window. Then I'd check three things: (1) Did an upstream source system change? New fields, mapping changes, schema updates. (2) Did a manual process change? New staff, process edits. (3) Is the validation logic itself stale? Maybe a new carrier was added and the validation rules don't cover their data format. I'd fix the immediate issue and add a rule or mapping fix to prevent recurrence.

### Technical

**Q6: What SQL techniques do you use for data validation?**

> `LEFT JOIN` to find orphans (driver IDs not in roster), `GROUP BY + HAVING` for duplicates and pattern detection, `WHERE ... IS NULL` for completeness checks, `CASE` for classification. For driver fraud patterns, I use aggregation with `HAVING` to flag drivers with high dispute rates. Window functions aren't heavily used in this role — the analysis is more about classification and exception detection than ranking or time-series.

**Q7: How do you distinguish a lost parcel from a theft?**

> Lost in transit: delivered status but no carrier scan event, no POD, no customer claim pattern. The carrier lost it. Theft: delivered, no POD, customer claim, and either an invalid driver ID or a repeated pattern (same driver, multiple disputes, unusual scan times). I classify based on data signals, not assumptions. The classification determines the routing: lost → carrier claim; theft → Loss Prevention escalation.

**Q8: What's the difference between Redshift and Athena, and when do you use each?**

> Redshift is the data warehouse — structured tables, optimized for repeated analytical queries, connects directly to Power BI and QuickSight. Athena is serverless SQL on S3 — good for ad-hoc queries on raw or staging data that hasn't been loaded into Redshift yet. In this role, I used Redshift for daily validation and reporting, and Athena when I needed to check a raw export before it was processed.

**Q9: How did you measure the 80% manual reduction?**

> Baseline: I tracked hours per week spent on manual exception reporting and Excel reconciliation — about 10 hours. After automation (SQL view + Power BI scheduled refresh + email), the manual time dropped to about 2 hours (only handling edge cases the automation couldn't classify). Reduction = (10 − 2) / 10 = 80%. I documented the before/after steps and time logs.

**Q10: What tools did you use, and what didn't you use?**

> Used: SQL (Redshift), Power BI, Excel, Python for simple automation scripts, S3 for raw exports, Athena for ad-hoc queries. Did not use: QuickSight (the team standardized on Power BI), SageMaker or ML models (not part of this role), Glue/EMR (those are engineering tools, not analyst tools in this context).
