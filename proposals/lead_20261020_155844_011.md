## Problem

An operator running an Archon node on a headless host, reached over SSH, has one interactive surface: the `archon`/`keymaster` CLI. The CLI is good for scripting and single actions, but poor for browsing state:

- Seeing what a wallet holds (identities, aliases, issued and held credentials, dmail, polls, groups) means chaining `list-*` and `resolve-*` commands and piecing the results together by hand.
- The CLI has about 150 commands. The only way to find one is `--help`, so you have to know roughly what you're looking for before you can find it.
- Node health (Gatekeeper status, queue depths, mediator progress) is visible in Grafana, which needs a browser. From an SSH session the only option is individual API calls.

The browser wallets and demo clients cover the browsing case, but only where a browser is available. The MCP server covers agents, not people.

## Constraints

- The CLI stays the scripting and automation surface. A terminal UI would be in addition to it, not a replacement.
- `tests/wallet/ui-capability-parity.test.ts` tracks which Keymaster capabilities reach each UI surface. A new interactive surface has to either reach parity or record each omission there with a reason (#935).
- It must work against a remote Keymaster over HTTP (`@didcid/clients`), not only an in-process wallet. That is the headless-node case.

## Open questions

- Who is the primary user: node operators, wallet holders, or both? The answer decides whether this is a status and browsing tool or a full wallet.
- Which actions, if any, belong in it rather than in the CLI?
