# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Contact import is offered on Android but READ_CONTACTS is never declared**

*Project description:*
The contact import feature is offered on Android but cannot work there, because `READ_CONTACTS` is never declared in the merged manifest.

## Symptom

On Android the user taps "Choose from Contacts", either from the buddy list import action or from the profile photo source sheet, and immediately gets a permission error with no way to resolve it. No permission dialog appears, and Contacts never shows up in the app's entry in system settings, so the user cannot grant it manually.

## Cause

`isContactImportSupported` in `lib/shared/utils/contact_import_support.dart` returns true for `TargetPlatform.android`, so both entry points offer the feature.

`ensureContactPropertyAccess` in `lib/features/buddies/data/services/contact_photo_loader.dart:23` then calls `FlutterContacts.permissions.request(PermissionType.read)` on the Android branch.

But `READ_CONTACTS` is declared nowhere:

- `android/app/src/main/AndroidManifest.xml` declares no CONTACTS permission of any kind. A `git log -S"READ_CONTACTS" --all -- android/` over the full history returns nothing, so it has never been declared. Contact import has never worked on Android.
- `flutter_contacts` 2.3.1, the resolved version in `pubspec.lock`, ships an `android/src/main/AndroidManifest.xml` containing an empty `<manifest>` element with no `uses-permission` entries, so the manifest merger contributes nothing either.

Android denies a runtime request for an undeclared permission immediately, without showing a dialog. `ensureContactPropertyAccess` returns false and the caller shows `profilePhoto_error_contactPermission` or `buddies_message_contactPermissionRequired`.

iOS is unaffected: `NSContactsUsageDescription` is present in `ios/Runner/Info.plist:140`, and the iOS picker runs out of process, so it returns the chosen contact's properties without the app holding a permission at all.

## Why a permissionless picker is not the fix

`FlutterContacts.native.showPicker` is permissionless on Android only when called with no properties. From `ShowPickerImpl.kt` in flutter_contacts 2.3.1:

```kotlin
if (properties.isEmpty()) {
    postResult(result, Contact(id = contactId, displayName = readDisplayName(pickedUri)).toJson())
    return@execute
}
if (!Permissions.hasReadPermission(context)) {
    return@execute postError(result,
        "showPicker(properties: …) requires READ_CONTACTS on Android. …")
}
```

The picker is an `Intent.ACTION_PICK`, which grants a temporary read on the single chosen contact's URI. With empty properties the plugin reads `DISPLAY_NAME` through that grant. With any properties it needs a full `ContactsContract` projection, which is the permission boundary.

So a permissionless Android flow would return the display name only: no email, no phone, no photo. That is useless for the profile photo path, which wants only a photo, and it would make buddy import silently produce records with blank contact details on Android while iOS fills them.

## Fix

Declare the permission in `android/app/src/main/AndroidManifest.xml`:

```xml
<uses-permission android:name="android.permission.READ_CONTACTS" />
```

`ensureContactPropertyAccess` already does the right thing; it was correct code sitting on a missing manifest entry, so no logic change is needed there.

Two follow-on items:

1. A guard test. The Dart platform gate and the XML manifest are two artifacts in two languages with nothing linking them, which is exactly how they drifted. A test should assert that whenever `isContactImportSupported` admits Android, the manifest declares `READ_CONTACTS`.

2. A permanently denied permission becomes reachable for the first time. On Android 11 and above, dismissing the dialog twice denies it for good and the request returns instantly, landing the user back on the same dead-end message. The snackbar should offer a Settings action wired to `FlutterContacts.permissions.openSettings()`.

## Note for the Play production access work

Branch `ericgriffin/google-play-production-access-2a5330` currently documents contacts access as iOS only, in the `PRIVACY.md` permission table and in section 5.8 and the 3.2 Data safety row of `docs/developer/play-production-access.md`. Those statements become wrong once this is fixed and need updating when that branch lands.

`READ_CONTACTS` is a dangerous permission but not a restricted one, so it adds review scrutiny and a Data safety obligation without requiring a Permissions Declaration Form.
