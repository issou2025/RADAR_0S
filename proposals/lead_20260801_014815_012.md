**A conflicted PR runs zero validation and gh pr checks still exits 0**

## Summary

A pull request that GitHub cannot merge runs none of its `pull_request` validation, and nothing tells the author. `gh pr checks` exits 0 and prints all pass or skip, so the PR reads as fully green while roughly 28 workflows have never executed on it.

This is not a duplicate of #4080 or #4099. Those two explain why plugin PRs conflict. This one is about what a conflict costs after it happens: silent loss of the entire validation suite, with a green-looking signal on top.

## Measured on PR #4124

`gh pr view 4124 --json mergeable,mergeStateStatus` reports `CONFLICTING` and `DIRTY`. The conflict surface is the two parity manifests and nothing else, which puts it in the largest bucket #4080 already measured.

Every workflow run recorded against the branch, from `gh run list --branch rjmurillo/eval-provider-provenance --limit 200 --json event`:

| Event | Runs |
|---|---|
| `pull_request_target` | 17 |
| `dynamic` (Copilot app) | 8 |
| `pull_request` | 0 |

Zero. Not one `pull_request` event across 41 commits. `Python Tests` never ran. `PR Validation` never ran. Neither did any of the other workflows that trigger on `pull_request`.

## Why the push trigger does not cover it

Most of the heavy workflows list `push` alongside `pull_request`, which reads at a glance like branch pushes are covered. They are not. `.github/workflows/pytest.yml`:

```yaml
on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main
```

The `push` trigger is pinned to `main`, so a feature-branch push fires nothing. All validation for a feature branch arrives through `pull_request`, and GitHub cannot raise that event for a PR whose merge commit it cannot compute. Conflict therefore removes the whole suite rather than degrading it.

## The signal is worse than absent

`gh pr checks 4124` exits 0 and prints:

```
Apply Labels                             pass
Cursor Bugbot                            skipping
Dependabot (GitHub Actions and Python)   skipping
Renovate                                 skipping
CodeRabbit                               pass
semgrep-cloud-platform/scan              pass
```

Every entry is a pass or a skip, and the exit code is success. The checks that would have failed are not listed as pending or missing, because they were never created. An author reading this output, or automation reading that exit code, concludes the PR is validated. Nothing in the output distinguishes "everything passed" from "almost nothing ran."

## Impact observed

PR #4124 accumulated 41 commits over two days while the author believed each push was validated. Two defects that the suite would have caught surfaced only when a later push happened to trip a local pre-push gate:

1. A markdown fence with no opening delimiter in `.claude/skills/context-optimizer/SKILL.md`, which made the following heading render as code.
2. The generated Copilot mirrors of the same file carrying the identical defect.

Neither is severe. That is the point: they sat undetected not because they were subtle but because nothing was looking.

## The detection already exists

`scripts/invoke_pr_maintenance.py:288` already does exactly the right check:

```python
has_conflicts = pr.get("mergeable") == "CONFLICTING"
```

The gap is placement, not capability. That check runs in a maintenance pass, not in the loop an author is actually in. The pre-push hook runs a large local validation suite and never asks GitHub whether the PR it is about to update can be merged at all.

## Candidate directions

Not a recommendation; any of these is cheap next to the cost of a silently unvalidated PR.

1. **Report mergeability after a push.** When a push updates a branch with an open PR, query `mergeable` and print a warning when it is `CONFLICTING`. Cheapest option, no gate semantics, no new failure mode.
2. **Make the absence loud rather than the conflict.** Compare the set of checks present on the PR against the set of workflows that declare `pull_request`, and report the difference. This catches every cause of a missing check, not only conflicts, including a workflow that failed to enqueue.
3. **Treat `gh pr checks` exit 0 as insufficient anywhere it gates.** Any consumer of that exit code should also assert `mergeable != CONFLICTING`, otherwise green means "nothing ran" just as readily as "everything passed."

## Acceptance criteria
