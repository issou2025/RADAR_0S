# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Naval missions: map context menu + panel assign (Patrol/Blockade/Beachhead/Defend)**

*Project description:*
## Summary

Human players cannot assign **naval missions** (`NavalMissionOrder`: Patrol, Blockade, Beachhead, Defend) from the player app. The player manual and actions appendix document fleet mission controls on `UNIT30001`, and the order engine / turn resolver / Full AI already support missions—but the live naval panel and map fleet markers offer **Move / organize / train only**. This blocks core naval play (interception, port pressure, invasion staging) and is **high priority**.

## Environment

- Player app (Flutter), in-game naval flow on branch `dev` (investigation baseline ~`2396ea63e`)
- Surfaces: map human fleet markers (`MAP10001` / `map-widget.md`), `UNIT30001` Naval Units panel
- Related: `NavalMissionOrder`, `validateNavalMission`, `suggestNavalMissionOrders`, `applyNavalMissionOrders` (resolution); draft path has `applyNavalMoveOrderForPlayer` but **no** human mission draft apply + bus event

## Steps to reproduce

1. Start or load a human Great Power game with at least one **sea-going** fleet **at sea** (split from Home Fleet and undock if needed).
2. Tap the **human fleet marker** on the map.
3. Observe: `UNIT30001` opens tile-scoped (or full panel); row actions include Move / Split / Locate (and Transfer where eligible)—**no mission assign**.
4. Open Naval Units from the empire rail and expand a sea-going at-sea fleet: same gap—mission is **display-only** (e.g. None / current enum label).
5. Optionally compare: AI and order-suggestion tests can stage `NavalMissionOrder`; the human UI cannot.

## Expected behavior

1. **Map (primary shortcut):** Tapping a **human fleet marker** offers a **context menu of currently available missions** for the selected fleet (see availability rules below). Choosing a mission stages a draft `NavalMissionOrder` (with required targets where applicable). Choosing **Cancel pending** removes a staged mission when one exists—not a “set mission to None” resolution order.
2. **Panel parity:** `UNIT30001` exposes the same mission assign / cancel-pending path so players not using the map shortcut can still issue missions.
3. **Missions in scope (v1):** Patrol, Blockade, Beachhead, Defend. **Join Home Fleet is out of scope** for v1 (capital dock + `DLG40001` Transfer remain the player path).
4. **Move xor mission:** A fleet may have a pending **move** or a pending **mission**, never both. Applying one replaces/clears the other for that fleet (mirror existing move-clears-mission draft behavior).
5. **Draft feedback:** Fleet row (and map draft projection consistency where already used for missions) shows a pending line, e.g. `On mission: Patrol` / `Blockade → <province display name>` / `Beachhead → <province display name>`.
6. **Costs:** Missions are free; disabled or rejected options show a **plain-language primary reason**.
7. **Resolution:** On Next turn, staged missions apply via existing movement/mission resolution (no new combat formulas).

### Mission availability (careful gating)

Menu entries appear only when legal **now** for the chosen fleet under current game, topology, diplomacy, and draft orders. Prefer **hide or disable with reason**—product should not offer dead-end taps that only fail later.

| Control | Show / enable when |
|---------|-------------------|
| **Patrol** | Fleet is human-owned, **not** Home Fleet, **at sea**, and not blocked by draft xor rules (or replacing move is allowed on confirm per implementer UX, but end state is xor). |
| **Defend** | Same as Patrol (at-sea non-Home). Distinct from “no mission.” |
| **Blockade** | Same base gates **and** there is **at least one legal blockade target** (see targets). |
| **Beachhead** | Same base gates **and** there is **at least one legal beachhead target** (see targets). **No exceptions**—beachhead **always** requires a hostile coastal province target. |
| **Cancel pending** | Human draft already contains a `NavalMissionOrder` for this fleet. Removes that pending mission only. |

**Home Fleet:** never offered at-sea missions.  
**In port (non-Home):** at-sea missions not offered (must undock first).  
**Multi-fleet marker:** if multiple fleets share a location scope, player must **select which fleet** before mission options for that fleet (or menu is per-fleet after selection)—do not apply one mission to all fleets blindly.

### Target rules (product-locked)

**Blockade target (required):**

- Province owned by a faction the player is **at war with** (enemy).
- Province is **adjacent** to the fleet’s **current sea zone** (topology P↔S edge from current `seaZoneId` to that province).
- Not the player’s own province; not unowned/missing.
- UI only offers provinces that pass this filter. Confirm stages `NavalMissionOrder` with `mission: blockade` and `targetProvinceId` set.

**Beachhead target (required — no exceptions):**

- Province is **hostile** (owner is a faction the player is **at war with**).
- Province is **coastal** relative to the fleet: has a P↔S adjacency to the fleet’s **current sea zone** (same adjacency family as blockade coastal contact; refine wording in SPEC if “coastal” needs an extra port/terrain gate beyond topology adjacency).
- `targetProvinceId` **must** be set on the order. UI and **validator must reject** beachhead without a legal target—today’s looser validator is a **gap to fix** as part of this work.
- UI only offers legal hostile coastal candidates; no “Beachhead with no province.”

**Patrol / Defend:** no province target.

## Proposed fix (not implemented)

### Root cause / hypothesis

Mission **simulation and AI** were built without a **human draft + map/panel commit path**. Fleet marker intentionally opens the naval panel only; panel never grew mission actions. Beachhead target rules in GDD are stronger than current order validation.

### Suggested change

1. **Draft wiring:** Add session bus event (e.g. `NavalMissionRequestedEvent`) and `applyNavalMissionOrderForPlayer` (replace mission for fleet; clear pending naval move for same fleet; cancel-pending removes mission entry). Shell listener next to naval move.
2. **Validator/SPEC alignment:** Enforce beachhead **requires** legal hostile coastal `targetProvinceId`; optionally tighten blockade adjacency in validator to match UI product rule (UI must already filter adjacency).
3. **Availability helper:** Shared pure function (logic/orders) listing legal mission kinds + targets for a fleet given game/topology/draft—consumed by map menu and panel (single source of truth).
4. **Map UX:** On human fleet marker tap, show **context menu** of available missions (+ Cancel pending when applicable). Multi-fleet scope: select fleet first. Target-required missions open a short target picker (adjacent war enemies / hostile coastal only) before emit.
5. **Panel UX:** Same assign + cancel-pending + pending line on `UNIT30001` for parity.
6. **UI docs:** Update `SPEC/ui/naval-units-panel.md`, `map-widget.md` (or overlay/menu component spec); new dialog/screen ID via **`document-app-ui`** if a modal is introduced (e.g. target picker / mission menu host).
7. **Manual:** **`update-game-manual`** for Ch. 13 and appendix so entry points match map context menu + panel; note Join Home Fleet remains dock/transfer.
8. **Tests:** Unit tests for availability + draft xor + beachhead reject without target; widget tests for menu gating; positive/negative panel/map paths.

## Suggested acceptance criteria

- [ ] Given a human non-Home fleet **at sea** with no pending move, when the player taps its map fleet marker, then a **context menu** lists only **available** missions (Patrol/Defend when base gates pass; Blockade only if ≥1 adjacent war-enemy province; Beachhead only if ≥1 hostile coastal legal target) and **Cancel pending** only if a draft mission exists for that fleet.
- [ ] Given multiple fleets at one marker, when the player opens the mission menu, then they select a **single fleet** before mission options apply to that fleet only.
- [ ] Given the player chooses **Patrol** (or Defend), when confirm/select completes, then draft contains a `NavalMissionOrder` for that fleet with the correct mission and **no** `NavalMoveOrder` for that fleet; the naval panel shows a pending mission line.
- [ ] Given the player chooses **Blockade**, when they pick a province, then only **adjacent provinces owned by factions at war** with the player are offered; the order includes `targetProvinceId`; illegal targets are not offered.
- [ ] Given the player chooses **Beachhead**, when they pick a province, then only **hostile (at war) coastal** provinces legal for the fleet’s sea zone are offered; the order **always** includes `targetProvinceId`; beachhead without target is **rejected** by validation (no exceptions).
- [ ] Given a pending mission, when the player chooses **Cancel pending**, then that fleet’s draft mission is removed and no resolution mission remains for it.
- [ ] Given a pending move for fleet F, when a mission is staged for F (or vice versa), then the draft ends with **only one** of move or mission for F.
- [ ] Given Home Fleet or a fleet **in port**, when the mission menu is considered, then at-sea missions are **not** available.
- [ ] Given `UNIT30001`, when viewing an eligible at-sea fleet, then the player can assign and cancel-pending missions with the **same availability rules** as the map menu (panel parity).
- [ ] Given implementation lands, when UI surfaces change, then `document-app-ui` obligations are met for any new dialog/menu ID/spec/Widgetbook binding.
- [ ] Manual: Given player-visible naval mission UX ships, when implementation merges, then `docs/manual/13-mastery-of-the-seas.md` and `docs/manual/16-appendix-actions.md` describe map context menu + panel entry points and do not claim unshipped Join Home Fleet UI as the primary human path (dock/transfer documented instead), or non-update is justified in the PR.
