## Project Understanding
You need assistance with: 
**Create the typed auth exception hierarchy and guardAuth**

*Project description:*
## Context & Objective

**Background:** Issue #177 established the project's error-handling contract for storage: `lib/core/error/` holds a sealed `RepositoryException` hierarchy, and every repository method wraps its storage call in `guardPersistence`, so no `IsarError` ever escapes `data/`. `CLAUDE.md` states the rule bluntly — "A layer above catching an `IsarError` is the same leak as importing one."

Authentication needs the identical treatment for a different reason. Supabase throws `AuthApiException`, `AuthRetryableFetchException` and friends; `sign_in_with_apple` throws `SignInWithAppleAuthorizationException`. If either type reaches `application/`, the layer arrow is violated and swapping the backend becomes a cross-layer rewrite.

Auth failures differ from storage failures in one way that matters: **several of them are normal.** A user dismissing the Apple sheet is not an error state, a mistyped OTP is not a crash, and being offline is a recoverable condition with a specific piece of Hebrew copy attached. A single opaque `AuthException` would force the UI to string-match to tell these apart. Hence a sealed hierarchy the presentation layer can `switch` over exhaustively, with the analyzer flagging the switch when a case is added.

`guardAuth` mirrors `guardPersistence` and must catch `Object`, not `Exception`, for the same reason: some platform channel failures surface as `Error` subtypes, and an `on Exception` clause silently misses them.

**Objective:** `lib/core/error/auth_exception.dart` defines a sealed `AuthException` with five concrete cases, and `lib/core/error/guard_auth.dart` provides `guardAuth` / `guardAuthStream` that classify any backend throw into one of them. No Supabase or Apple exception type is reachable above `data/`.

**Why Now:** `SupabaseAuthRepository` (#L9) wraps every one of its calls in `guardAuth`, and the `AuthRepository` contract (#207) already documents these types by name. Must land before #L9.

## Technologies & Approach

| Concern | Technology / Package | Version | Notes |
|---|---|---|---|
| Sealed hierarchy | Dart `sealed class` | SDK ^3.13.2 | Exhaustive `switch` in presentation; analyzer flags an unhandled new case. Matches `RepositoryException` |
| Stack-trace preservation | `Error.throwWithStackTrace` | dart:core | Same technique `guardPersistence` uses — rethrows the typed exception carrying the original trace |
| Classification input | Duck-typed inspection of the caught object | — | The guard must **not** import `supabase_flutter`, so it classifies on `runtimeType.toString()` and message content rather than `on AuthApiException` clauses |

**Approach summary:** Sealed hierarchy over an error-code enum, because the presentation layer branches on these to pick Hebrew copy and an exhaustive `switch` is what stops a new failure mode from silently rendering a blank sheet. The guard lives in `lib/core/error/` alongside `guardPersistence` rather than in the auth feature, because `lib/core/` is where cross-cutting error handling already lives and a second location would fragment it.

The classification-without-importing constraint is the one awkward part: `lib/core/` may not depend on `supabase_flutter`. Resolved by having the guard accept an optional `AuthException Function(Object)? classify` hook that `SupabaseAuthRepository` supplies from inside `data/`, where the Supabase types *are* importable. The guard's own default classification handles only the generic cases.

## Implementation Plan

### Step 1 — Define the sealed hierarchy

**File:** `lib/core/error/auth_exception.dart`

**API Contract:**
```dart
/// Typed failures the auth backend may produce.
///
/// Sealed, so presentation can switch exhaustively and the analyzer flags the
/// switch when a case is added. Implements [Exception] rather than extending
/// [Error]: every case here is a runtime condition a caller may reasonably
/// handle, not a programming bug.
///
/// Deliberately import-free — `domain/` may not see Supabase or Flutter, and
/// these types are part of the contract `AuthRepository` declares.
library;

sealed class AuthException implements Exception {
  const AuthException(this.message);

  /// Developer-facing description. Not localised, so it is never UI copy —
  /// presentation switches on the *type* and supplies its own Hebrew string.
  final String message;
}

/// The user dismissed the Apple sheet or backed out of the OTP screen.
///
/// **Not an error.** Callers must return the UI to its prior state silently;
/// showing a snackbar here is a bug.
final class AuthCancelledException extends AuthException {
  const AuthCancelledException([super.message = 'Sign-in cancelled by user']);
  @override
  String toString() => 'AuthCancelledException: $message';
}

/// The device could not reach the auth backend.
///
/// Distinguished from [AuthBackendException] because it is the one failure the
/// user can act on, and because it is expected: this is an offline-first app
/// and a user may well be signing in from a supermarket basement.
final class AuthNetworkException extends AuthException {
  const AuthNetworkException([super.message = 'Auth backend unreachable']);
  @override
  String toString() => 'AuthNetworkException: $message';
}

/// The submitted one-time code was wrong or had expired.
final class InvalidOtpException extends AuthException {
  const InvalidOtpException([super.message = 'Invalid or expired code']);
  @override
  String toString() => 'InvalidOtpException: $message';
}

/// The credential being linked already belongs to a different account.
///
/// Thrown by `linkApple` / `linkEmail`. The caller must offer an explicit
/// choice — sign in to the existing account and discard local data, or cancel
/// — and must never resolve it silently, because either branch loses data.
final class CredentialAlreadyLinkedException extends AuthException {
  const CredentialAlreadyLinkedException([
    super.message = 'Credential already linked to another account',
  ]);
  @override
  String toString() => 'CredentialAlreadyLinkedException: $message';
}

/// Anything else the backend reported.
///
/// [cause] is the original failure, kept so a log or bug report can show what
/// the backend actually said. Callers must not type-check it — it is an
/// implementation detail of whichever backend is wired in.
final class AuthBackendException extends AuthException {
  const AuthBackendException(super.message, [this.cause]);
  final Object? cause;
  @override
  String toString() =>
      'AuthBackendException: $message${cause == null ? '' : ' ($cause)'}';
}
```

**Logic / Behaviour:**
- Mirror `repository_exception.dart` exactly in shape: `sealed` base with a `message`, `final class` cases, a `toString()` on each.
- Only `AuthBackendException` carries a `cause`, matching how only `PersistenceException` carries one.
- Every case gets a default message so a throw site can be a bare `const AuthCancelledException()`.

**Integration:**
- Thrown by: `SupabaseAuthRepository` (#L9), via `guardAuth`
- Switched over by: `SignInSheet` (#L13) to pick Hebrew copy
- Declared by: `AuthRepository` (#207) doc comments

### Step 2 — Implement the guards

**File:** `lib/core/error/guard_auth.dart`

**API Contract:**
```dart
import 'package:fantastic/core/error/auth_exception.dart';

/// Runs [body], converting any auth failure into an [AuthException].
///
/// [operation] names the call site — `'SupabaseAuthRepository.signInWithApple'`
/// — so an exception reaching a log identifies its origin without a trace.
///
/// [classify] lets the caller map backend-specific exception types the way
/// only `data/` can: this file may not import `supabase_flutter`, so the
/// repository passes a closure that *can*. Returning null from [classify]
/// falls through to the default classification below.
Future<T> guardAuth<T>(
  String operation,
  Future<T> Function() body, {
  AuthException? Function(Object error)? classify,
});

/// Stream counterpart, for `AuthRepository.watchAuthState()`.
///
/// Guards both a synchronous throw while [body] builds the stream and an error
/// delivered on the stream afterwards, so `authStateProvider` (#L10) surfaces
/// either as `AsyncValue.error`. Identical in shape to
/// `guardPersistenceStream`.
Stream<T> guardAuthStream<T>(
  String operation,
  Stream<T> Function() body, {
  AuthException? Function(Object error)? classify,
});
```

**Logic / Behaviour:**
- `catch (error, stackTrace)` on **`Object`**, not `Exception`. This is the same trap `guardPersistence` documents: platform-channel failures from `sign_in_with_apple` can surface as `Error` subtypes, and `on Exception` silently misses them.
- Classification order, first match wins:
  1. `error is AuthException` → rethrow unchanged (never double-wrap, matching `_asRepositoryException`).
  2. `classify?.call(error)` → use it if non-null.
  3. `error is SocketException` **by name check** — the guard cannot import `dart:io` types into a file that must stay web-safe, so test `error.runtimeType.toString() == 'SocketException'` or a `ClientException` message containing `'Failed host lookup'` → `AuthNetworkException`.
  4. Fallback → `AuthBackendException('$operation failed', error)`.
- Rethrow with `Error.throwWithStackTrace(typed, stackTrace)` so the original trace survives — copy the exact technique from `guard_persistence.dart`.
- `guardAuthStream` returns `Stream.error(...)` for a synchronous build failure and uses `handleError` for post-subscription errors, exactly as `guardPersistenceStream` does.

**Integration:**
- Used by: every method of `SupabaseAuthRepository` (#L9), which supplies the `classify` closure mapping `AuthApiException` codes to `InvalidOtpException` / `CredentialAlreadyLinkedException` and `SignInWithAppleAuthorizationException(canceled)` to `AuthCancelledException`
- Sits alongside: `lib/core/error/guard_persistence.dart`

**File:** `test/core/error/guard_auth_test.dart`

**What to test:**

**Test doubles needed:** none — throw plain `Object`s and a custom `Error` subclass directly.

## Testing Requirements

#### Happy Path
- [ ] Success path returns the value and never enters the catch
- [ ] Stream path forwards all values in order

#### Edge Cases
- [ ] An already-typed `AuthException` passes through unchanged
- [ ] A thrown `Error` (not `Exception`) is still caught — the regression this guard exists to prevent
- [ ] `classify` returning null does not swallow the failure

#### Error / Failure Handling
- [ ] `AuthBackendException.cause` holds the original object
- [ ] Stack trace of the rethrown exception matches the original throw site
