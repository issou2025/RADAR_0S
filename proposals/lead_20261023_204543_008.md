## Summary

- **One React Native app for iPhone, iPad and Android phones and tablets, released together.** It
  is an **Expo** app with development builds (no Expo Go), on the New Architecture (Fabric and Turbo
  Modules on Hermes). It needs iOS/iPadOS 17 and Android 10 (API 29) or later. The screens are React Native; **everything
  that decides anything is Rust.**
- **Kanso's logic is shared, not ported.** The store, sync, end-to-end encryption, locked notes,
  live collaboration, search, links, properties and query views, Markdown rendering, math and
  diagrams, canvas ink and AI all run as the same Rust crates the desktop app uses. They reach
  JavaScript through **UniFFI** bindings generated by **uniffi-bindgen-react-native**.
- **First, move logic out of the desktop app.** `kanso-app` is a binary crate with about 150
  modules. Lock sessions, account flows, sync scheduling, wiki links, daily notes and templates
  live there, mixed with GPUI. A new UI-free crate, **`kanso-engine`**, takes that logic. The desktop
  app and the mobile app both call it, so a rule is written once and holds on every platform.
- **A thin, typed facade crate, `kanso-mobile`,** is the only thing the bindings see. It's a few
  objects (`Library`, `Session`, `Sync`, `Renderer`, `Ink`, `Ask`) and callback interfaces for
  events. It is built as an XCFramework for iOS and as `.so` libraries per ABI for Android.
- **Native where the platform matters, React Native everywhere else:**
  - The Markdown editor is a native text view (TextKit 2 on iOS, `EditText` on Android), with
    highlighting computed in Rust, so autocorrect, dictation, IME composition and accessibility
    behave exactly like every other app. These were the GPUI spike's unknowns.
  - The preview is the same HTML the desktop's published pages use (`kanso_render::html`, styled
    to match the preview), shown in a WebView.
  - The canvas draws with React Native Skia, from Rust-computed stroke outlines, with native
    Pencil and stylus capture.
- **Security is the desktop's:**
  - Locked notes are sealed with the same `kanso_sync::lock::LockKey`.
  - Secrets live in the iOS Keychain and the Android Keystore, behind the same seam the desktop
    uses (`crates/kanso-app/src/services.rs`).
  - Face ID, Touch ID and Android BiometricPrompt unlock notes through a biometric-protected key.
  - Nothing the server can read changes.


## Why React Native over the Rust core

The mobile spike (PR #28, closed and its branch deleted; its findings are recorded here) ran
Kanso's phone UI on `gpui-pre-mobile` in the iOS Simulator. A release build with only the store and
core was 17.8 MB zipped. Its verdict was "not yet; keep React Native as the plan of
record":

- autocorrect was hard-coded off;
- IME marked text and dictation couldn't be tested;
- accessibility is experimental in the fork;
- gpui-kit has no navigation stack, sheets, swipe actions, long-press, pull to refresh, haptics,
  or native share and document pickers.

A notes app lives or dies on text input and platform feel. React Native gives native text views,
navigation, sheets, gestures, accessibility, share extensions and widgets on both platforms. And
because the Rust core is shared through bindings, choosing React Native costs no duplicated logic.

Plain React Native in JavaScript is rejected: it would reimplement the store, sync, crypto and
merge rules, and two implementations of end-to-end encryption are two places to get it wrong.

Native Swift plus Kotlin apps are also rejected: they would mean two UI codebases. UniFFI could
still bind Swift and Kotlin from the same facade if one platform ever needs it, so this choice
can be reversed cheaply.


## How it works for the user


### Phone

- **Library:** notebooks, tags, pinned, recent, tasks, Canvases, and trash, as on the desktop
  sidebar. A search field sits on top.
- **Note list:** grouped by date like the desktop list, with pull to refresh (sync now), swipe
  actions (pin, move, trash), long-press for multi-select, and the same sort and filter as the
  desktop.
- **Note:** opens in **Preview**. Tap **Edit** (or double-tap the text) to type in Markdown.
  - A keyboard accessory bar holds `#`, `-`, `[ ]`, `**`, link, image, `[[`, indent and outdent,
    and undo.
  - Live syntax highlighting, with tables and lists continued like the desktop editor
    (`crates/kanso-app/src/list_edit.rs`, `table_format.rs`).
  - Wiki-link and tag completion.
  - Properties appear in a collapsible section above the text.
- **Capture:**
  - a **+** button;
  - the iOS Share Sheet and Android share target (text, links, images, PDFs);
  - a home-screen widget (new note, voice note, today's daily note);
  - iOS Shortcuts and App Intents.
- **Locked notes:** a locked note shows its title (if the title isn't sealed) and a lock. Face ID
  or the lock password opens it. It locks again after 10 minutes, the same `AUTO_LOCK` as the
  desktop (`crates/kanso-app/src/locked.rs:47`), and also when the app goes to the background.
- **Sync:** you sign in once with any method the account supports (username, passkey, Apple,
  Google or GitHub; see issue #32). A new phone is approved from a signed-in device, or with the
  recovery key.


### iPad and Android tablets

- Three panes like the desktop (library, list, note) that collapse to two or one as the window
  narrows: Split View, Stage Manager, foldables.
- A hardware keyboard gets the desktop's shortcuts: ⌘N, ⌘F, ⌘K, ⌘[, ⌘], ⌘1–3 and so on.
- **Apple Pencil and styluses:**
  - **Canvases** (issue #45) open full-screen, where the Pencil draws, fingers pan and zoom,
    and the palm is ignored.
  - **Inline sketches** in notes and **PDF ink** (issue #43) use the same input.


### Things the mobile app doesn't do

- No local REST API or MCP server. Phones can't host agents.
- No ACP agents (issue #46), since phones don't run local agents.
- No plugins at first (issue #37).
- No Kanso Dev flavour on devices: test builds go through TestFlight and Play internal testing.

### `kanso-engine`: moving the logic out of the desktop app

Today `kanso-app` has no `lib.rs`. Logic and GPUI are mixed in modules such as `locked.rs` (1,646
lines), `notebook_lock.rs`, `account_flow.rs`, `services.rs` (sync scheduling and the Keychain
seam), `wikilinks.rs`, `journal.rs`, `due.rs`, `smart_paste.rs`, `code_lang.rs` and the editor's
list and table helpers.

**The rule:** anything that decides something (what to save, seal, sync, show or refuse) moves
into `kanso-engine`, with no GPUI dependency. `kanso-app` keeps only views, windows and AppKit
glue, and calls the engine. The desktop app is the first user of the engine, so the refactor is
tested by the existing desktop test suite before mobile depends on it.

What moves, and what it becomes:

| From `kanso-app` | Into `kanso-engine` |
|---|---|
| `locked.rs`, `notebook_lock.rs` (`LockKeys`, `AUTO_LOCK`, `seal`, unlock bookkeeping) | `lock::Session`: keys in memory, the auto-lock clock driven by the caller's clock, seal and unseal of notes and notebooks |
| `services.rs` (sync after edit, periodic sync, the Keychain and backend seams) | `sync::Scheduler`, plus a `Secrets` trait (desktop: macOS Keychain; mobile: the native module above) |
| `account_flow.rs`, `account_words.rs` | `account::Flow`: sign-up, sign-in, recovery, password change, device approval (#32), without views |
| `wikilinks.rs`, `note_link.rs`, `tag_complete.rs` | `links`: resolution, completion candidates, rename rewriting |
| `journal.rs`, `due.rs`, `reminders.rs` (rules only) | `daily`, `tasks`: daily notes, templates, due dates |
| `list_edit.rs`, `table_format.rs`, `markdown_edit.rs` (pure text edits) | `edit`: Enter in a list, Tab in a table, wrap selection; pure `(text, selection) -> Edit` |
| `code_lang.rs` grammar choice | `highlight`: Markdown and code spans for a range of text |
| `ask.rs` retrieval (with #40) | already in `kanso-ai`; the engine owns eligibility (locked, trash, `#ai-exclude`) |

Every moved module keeps its tests and property tests. A move is done when the desktop behaves
identically, the same tests pass, and `kanso-engine` builds for `aarch64-apple-ios`,
`aarch64-apple-ios-sim`, `aarch64-linux-android`, `armv7-linux-androideabi` and `x86_64-linux-android`.


### `kanso-mobile`: the facade

A small crate with `#[uniffi::export]` items only. JavaScript never sees the store, the sync
engine or a key.

- `Library::open(path, secrets: Box<dyn Secrets>) -> Library`: opens the database in the app
  container (iOS: the App Group container, so the Share Extension and widgets can add notes;
  Android: `filesDir`).
- `Library`:
  - `notes(query) -> Vec<NoteRow>`, `note(id) -> NoteView`, `save(id, base_rev, body) -> Saved`,
    `create(...)`, `trash(id)`, `notebooks()`, `tags()`;
  - `search(text) -> Vec<Hit>`, `properties(id)`, `query_view(source) -> Table`.
- `Session` (locks): `unlock(password)`, `unlock_with_biometrics()`, `lock()`,
  `is_unlocked(note)`. JavaScript never receives a `LockKey`, only booleans and the unlocked
  text of the note it opened.
- `Sync`: `sign_in(method)`, `approve_device(request)`, `start()`, `sync_now()`, `status()`;
  shared notes through `kanso-collab`.
- `Renderer`: `preview_html(id, theme) -> String`, `highlight(text, range) -> Vec<Span>`,
  `math_svg`, `diagram_svg`, all through `kanso-render`'s one QuickJS engine
  (`crates/kanso-render/src/js.rs`).
- `Ink`: `outline(stroke) -> Path` (perfect-freehand in Rust, issue #45), `apply(op)`,
  `merge(a, b)`.
- `Ask` (issue #40): questions over notes through agent-runtime and `kanso-ai`, streamed through
  a callback.
- Callback interfaces (Rust → JavaScript): `LibraryObserver::changed(ids)`,
  `SyncObserver::status(s)`, `LockObserver::changed(note)`, `AskObserver::chunk(text)`.

**Threads:** every call that touches the database, the network or QuickJS is `async` on the Rust
side and runs on Rust's own threads. Hermes's JavaScript thread never blocks. Rust owns a small
pool: the store thread, the sync thread, the QuickJS thread `kanso-js`, and an ink worker.

**Errors:** typed Rust enums map to TypeScript error classes. A failure never crashes the app;
a Rust panic is caught at the facade boundary, logged, and returned as an error.


### Bindings: uniffi-bindgen-react-native

[uniffi-bindgen-react-native](https://github.com/jhugman/uniffi-bindgen-react-native) (Mozilla and
Filament, [announced December 2024](https://hacks.mozilla.org/2024/12/introducing-uniffi-for-react-native-rust-powered-turbo-modules/))
generates TypeScript and JSI C++ from UniFFI definitions, plus a Turbo Module that installs them.
It supports objects with garbage-collected lifetimes, sync and async calls in both directions, and
callback interfaces. The runtime is published as `@ubjs` packages.

**Risk, stated plainly:** its docs say the project is "still in early development, and should not
yet be used in production" ([docs](https://jhugman.github.io/uniffi-bindgen-react-native/)).
Recent 0.31 pre-releases fixed a leaked buffer on async returns. The mitigations:

- pin the exact version and upgrade deliberately;
- keep the facade small, so the generated surface is small;
- cover the bindings with tests that run in Hermes (the project's JSI test player) for every
  facade function;
- keep a fallback path, so the facade can be bound by hand through a C ABI and a Turbo Module if
  the generator blocks the work. The facade's shape doesn't depend on the generator.


### The editor

- **A native text view, not a WebView editor and not React Native's `TextInput`.**
  - `TextInput` can't style ranges well enough for live Markdown highlighting at length.
  - A CodeMirror WebView handles IME, dictation, accessibility and selection as web content,
    which is the weakest kind on mobile.
  - A native text view gets all of them from the platform.
- **Highlighting comes from Rust:**
  - The engine's `highlight` returns spans for the visible range plus a margin.
  - The text view applies them as attributes (iOS) or spans (Android), incrementally on each edit,
    off the main thread, and cancelled when a newer edit arrives.
  - The theme's syntax colors come from the same theme files (`themes/`).
- **Edits that the desktop editor does** (continue a list on Enter, indent with the accessory bar,
  tables) come from `kanso-engine::edit`. They are applied as one native undo group.
- **Saving:** the desktop's autosave rule (600 ms after the last change,
  `crates/kanso-app/src/editor.rs:85`) runs in the engine. It saves with the note's revision as
  the base, so a sync that changed the note meanwhile becomes the same conflict flow as on the
  desktop.


### The preview

A WebView showing `kanso_render::html` output, the same pages publishing produces. Since #42 those
pages match the desktop preview's typography, code highlighting, checkboxes and quotes.

- **Locked down:** no JavaScript in the WebView (`javaScriptEnabled = false`), no network
  (pages are self-contained; attachments are inlined as data URIs, as exports do), and every link
  tap intercepted. Note links navigate in the app, web links open in the system browser, and
  `kanso-audio:` and PDF links (#38, #43) open their viewers.
- **Interactive bits** (task checkboxes, query tables refreshing, the audio player) are native
  overlays or re-renders driven by the engine, not scripts in the page. Rejecting JavaScript in
  the preview is a security choice: the page shows note content, which is untrusted.


### Canvas and ink

The canvas format, renderer and merge rules are the ones in issue #45, and the pen capture is the
table above.

- The live stroke draws on a React Native Skia surface
  ([@shopify/react-native-skia](https://shopify.github.io/react-native-skia/)) from points the native
  capture module delivers.
- Finished strokes go to Rust. `Ink::outline` returns the perfect-freehand polygon that the desktop
  draws too, so ink looks identical everywhere.
- Predicted points are drawn for one frame and never stored.


### Sync, sharing and background work

- `kanso-sync` and `kanso-collab` are pure Rust (`ureq`, `rustls`, `tungstenite`, `yrs`).
  - Certificates: on Android, use the platform's trust store through `rustls-platform-verifier`
    instead of the bundled `webpki-roots` (`Cargo.toml`), so user-installed and enterprise CAs
    behave like other apps.
  - On iOS, use the same verifier, which uses the Security framework.
- **Foreground:** sync after edits and periodically, with the desktop's timings
  (`SYNC_AFTER_EDIT`, `crates/kanso-app/src/services.rs:30`).
- **Background:** iOS `BGAppRefreshTask` and Android `WorkManager` run a bounded sync (pull,
  merge, push, within the OS's time budget).
- **Push notifications wake sync, in the first release.** See "Push notifications" below.
- Live collaboration on shared notes works in the foreground and pauses in the background.


### Push notifications

A note edited on the Mac should already be on the phone when the phone is picked up. The sync
server tells the phone's OS to wake Kanso; the phone then syncs the usual way. The push itself
carries nothing.

- **Registration.** After sign-in the app asks for the platform push token (APNs on iOS, FCM on
  Android) and sends it with `PUT /v2/account/devices/<device_id>/push` (`{platform, token,
  environment}`), authenticated by that device's session. It's stored on the device's existing
  `sessions` row (`cloud/migrations/0002_accounts.sql`, new nullable columns `push_platform`,
  `push_token`, `push_environment` and `push_updated_at` in a new migration). Signing out, revoking
  the device, expiry, recovery and rekeying clear it, along with the session. `DELETE` on the same
  path turns pushes off. Tokens are refreshed whenever the OS issues a new one.
- **What triggers a push.** A successful `push` in `cloud/src/sync.ts` that changed at least one
  document wakes every other active device on the account that has a token. A change to a shared
  note (`collab`) wakes the members' devices the same way. The device that made the change is
  never woken.
- **What a push contains.** Nothing about the library: no note IDs, titles, counts or account
  name.
  - iOS: a background push (`apns-push-type: background`, `apns-priority: 5`, payload
    `{"aps":{"content-available":1}}`).
  - Android: a high-priority FCM data message with an empty body, which starts an expedited
    `WorkManager` sync.
  - Visible notifications are not part of this; share invitations stay in the app.
- **Coalescing.** At most one push per device every 30 seconds. A burst of edits is one wake-up,
  and the device fetches everything on that one wake. The Worker keeps the last push time per
  device and sends the trailing one with `waitUntil` or a Durable Object alarm *(choose in the
  step)*.
- **Sending from the Worker.**
  - FCM's HTTP v1 API takes an OAuth token minted from a service-account key (signed JWT, cached
    for its hour).
  - APNs uses token auth: an ES256 JWT from the `.p8` key, refreshed every 20–60 minutes as Apple
    requires. APNs only speaks HTTP/2, and whether a Worker's outbound `fetch` reaches it over
    HTTP/2 is *(unverified)*. Step 8 checks this first. If it can't, a small push relay
    (a container or VM holding only the APNs key) takes `{token, environment}` from the Worker
    over an authenticated channel and nothing else.
  - The keys are Worker secrets (`APNS_KEY_P8`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `FCM_SERVICE_ACCOUNT`),
    set with `wrangler secret put`.
  - A token the service reports as gone (APNs 410, FCM `UNREGISTERED`) is cleared.
- **Limits, stated plainly.**
  - iOS throttles background pushes and doesn't deliver them to an app the user force-quit, so
    sync on open and `BGAppRefreshTask` stay.
  - Android may defer work for apps in restricted standby buckets.
  - Push makes sync faster; it never makes sync correct.
- **Privacy.** Apple and Google learn when this device's library changed, not what. The setting
  "Wake this device when notes change elsewhere" is on by default and turns pushes off for this
  device (the token is deleted from the server).


### Locked notes and secrets

- **The lock key never leaves Rust.** `Session` keeps it in memory, zeroized on lock, as
  `LockKey` already does (`crates/kanso-sync/src/lock.rs:142`).
- **Biometric unlock:** after a password unlock, the user may allow Face ID, Touch ID or
  BiometricPrompt. A random wrapping key is stored as a biometric-only Keychain or Keystore item,
  invalidated when biometrics change. It wraps the lock key at rest on that device only, never
  synced and never in backups (`ThisDeviceOnly`).
- **Auto-lock:** after 10 minutes, and on entering the background. The app switcher's snapshot
  shows a blurred cover while a locked note is open.
- **Attachments:** pictures and files in locked notes are sealed once issue #44 lands. Until then,
  attaching to a locked note is refused on mobile, as on the desktop.
- **Data protection:** the database and attachment files get iOS `NSFileProtectionCompleteUntilFirstUserAuthentication`,
  so sync can run in the background after the first unlock. Android uses its default file-based
  encryption.
- **Not in device backups.**
  - iOS: the library folder is marked `isExcludedFromBackup`, which covers iCloud and computer
    backups.
  - Android: `android:allowBackup="false"`, plus `dataExtractionRules` that exclude everything from
    cloud backup and device-to-device transfer.
  - The server already holds the end-to-end encrypted copy, and a backup would be one more place
    notes live.
  - A user without sync loses their notes with the phone. The app says so once, on first launch
    and in Settings › Sync, and offers sync (free on their own server).


### Voice, AI and imports

- **Dictation** uses the platform's on-device recognizers, which are fast, small and private.
  **Recordings** (issue #38) can use Parakeet through `kanso-voice` on devices that can carry the
  model. ONNX Runtime's mobile builds and the model's size and speed on phones are measured in
  step 12; Parakeet is off by default on phones.
- **Ask your notes:** `kanso-ai` on agent-runtime, whose HTTP layer is pluggable and
  runtime-agnostic, with the API key in the Keychain or Keystore. No ACP agents.
- **Imports:** a shared file or the document picker feeds `kanso-import` (Evernote, Apple Notes
  export, Obsidian vault zip, Markdown).


### Builds, CI and size

- **Rust:** `cargo` targets per platform. `xcodebuild -create-xcframework` for iOS (device and
  simulator), and `cargo-ndk` for Android ABIs. The release profile is the spike's: `opt-level =
  "z"`, fat LTO, `strip`, `panic = "abort"`.
- **The React Native app** lives in `mobile/app/`: Expo (current SDK, New Architecture, Hermes),
  TypeScript strict, Expo Router for navigation.
  - **Development builds and continuous native generation** (`expo prebuild`). Expo Go can't load
    custom native code, so it isn't used.
  - The `ios/` and `android/` folders are generated, not committed. Every native change goes
    through a config plugin in `mobile/app/plugins/`, so a fresh prebuild always reproduces the
    projects.
  - **Native modules use the Expo Modules API** (Swift and Kotlin): the Markdown text view, pen
    capture, secure storage, biometrics and the push token.
    - The secure storage module is Kanso's own, not `expo-secure-store`, because secrets go to
      Rust, never to JavaScript.
    - Library modules are used where they hold no secrets: `expo-notifications` for push tokens and
      permission, `expo-sharing`, `expo-document-picker`, `expo-image-picker` and `expo-camera`.
  - **The Rust bindings** are a local package built by uniffi-bindgen-react-native (a Turbo Module
    with the XCFramework and the `.so` libraries). Expo's autolinking picks it up in prebuild.
    uniffi-bindgen-react-native's docs don't mention Expo *(unverified)*. Step 4 proves the
    package builds and runs in an Expo development build on both platforms before anything else
    depends on it.
  - **Extension targets:** the share extension and widgets are added by config plugins (a community
    plugin such as `@bacons/apple-targets` for iOS, or Kanso's own) *(choose in step 10)*.
  - **Builds run in Kanso's own GitHub Actions** (`expo prebuild`, then `xcodebuild` and Gradle),
    not EAS Build, so signing keys and certificates stay in GitHub's protected environment, as the
    desktop's do.
  - **No over-the-air JavaScript updates (EAS Update).** Every app change ships through the App
    Store and Google Play. An OTA channel would be a second way to deliver code to everyone's
    notes, beside the stores and the desktop's signed feed.
- **CI:** a macOS job builds the XCFramework and the iOS app for the simulator; a Linux job builds
  the Android libraries and APK. Rust tests run as today. Binding tests run in Hermes. End-to-end
  flows run with Maestro on a simulator and an emulator.
- **Device tests before each release, by hand on real devices:**
  - IME composition (Japanese and Chinese), dictation and autocorrect;
  - VoiceOver and TalkBack;
  - Pencil latency;
  - background sync.
- **Size:** the spike's release iOS app was 17.8 MB zipped with only the store and core. The full
  core adds QuickJS with MathJax and Pele, resvg/usvg, Yrs and the crypto crates. Target an
  install size under 40 MB without the voice model *(to measure)*.
- **Distribution:** TestFlight and the App Store, and Play internal testing and Google Play.
  - Kanso uses its own end-to-end encryption, so App Store Connect's export compliance needs
    `ITSAppUsesNonExemptEncryption` answered truthfully. The annual self-classification report
    applies *(confirm the exact obligation for the owner's jurisdiction)*.
  - Sign in with Apple is offered, which Apple's guideline 4.8 requires once Google or GitHub
    sign-in appear in an App Store app.


## Security and privacy

| Threat | What stops it |
|---|---|
| A lost or stolen phone | Device passcode and file protection; locked notes sealed with the lock key; biometric wrapping keys that are `ThisDeviceOnly` and invalidated when biometrics change; auto-lock on background; the account's device list can sign the phone out remotely (existing per-device sessions) |
| Another app reads Kanso's data | iOS sandbox and App Group; Android app-private storage; nothing in shared storage; no exported content provider |
| JavaScript gets a key | Keys never cross the facade: `Session` returns booleans and plaintext of opened notes only; the native secure-storage module returns secrets to Rust, not to JavaScript |
| Note content runs code | Preview WebView with JavaScript off, no network, intercepted links; Markdown rendered by Rust; SVG from Kanso's own renderer |
| A malicious shared item (share sheet) | Imported as data through `kanso-import`'s caps and parsers; never opened automatically |
| Screenshots and the app switcher | A blurred cover over locked notes when backgrounded; Android `FLAG_SECURE` on locked-note screens |
| Backups leak secrets | The library is excluded from iCloud, computer and Google backups and from device-to-device transfer; Keychain and Keystore items are device-only |
| Push notifications leak activity | Pushes are content-free and coalesced; Apple and Google see only that this device's library changed; tokens are tied to a device session and cleared with it; a setting turns pushes off per device |
| A stolen APNs or FCM key | Lets the holder send empty wake-ups to Kanso devices, nothing else: a push carries no data and triggers only an ordinary authenticated sync. Keys are Worker secrets, rotated in each provider's console |
| A network attacker | TLS with the platform verifier; end-to-end encryption unchanged; certificate pinning is not added (it breaks enterprise CAs, and E2E already protects content) |
| A compromised dependency in the JS ecosystem | A small, pinned dependency set; lockfile reviews; no JS-side crypto or storage; anything that decides runs in Rust |
| The bindings generator misbehaves | Pinned version, Hermes binding tests, a hand-binding fallback |

What the server sees doesn't change: a phone is one more device with its own session.


## Choices and trade-offs

| Decision | Chosen | Rejected because |
|---|---|---|
| UI framework | React Native (New Architecture) | GPUI mobile: text input, accessibility and platform features not ready (PR #28). Native Swift and Kotlin: two UI codebases. Flutter: Dart plus an FFI layer, with no gain over RN for this app |
| Logic | Rust crates via UniFFI | A JavaScript rewrite duplicates crypto, sync and merge rules |
| Sharing logic with the desktop | A new `kanso-engine` crate used by both apps | Copying logic into the mobile facade would let the two apps drift |
| Bindings | uniffi-bindgen-react-native, pinned, with a hand-binding fallback | Hand-written JSI for everything is slower to build and easier to get wrong |
| Editor | Native text views with Rust highlighting | `TextInput` can't highlight at length; a WebView editor gets weaker IME, dictation and accessibility |
| Preview | Locked-down WebView with Kanso's HTML | Rebuilding Markdown as RN components duplicates the renderer and drifts from desktop and published pages |
| Canvas | Native capture + React Native Skia + Rust outlines | PencilKit and Jetpack Ink draw differently and need format conversion (decided in #45) |
| Dictation | Platform on-device recognizers | Parakeet on every phone is a large download; kept optional for recordings |
| App tooling | **Expo with development builds and prebuild** (owner's decision) | Plain React Native CLI: committed native projects that drift, and hand upgrades of React Native each release. Expo Go: can't load custom native code |
| Builds | Own GitHub Actions | EAS Build would hold the signing keys outside GitHub's protected environment |
| OTA updates | None | EAS Update is a second code-delivery channel beside the stores |
| Push | Content-free wake-ups from the Worker, in v1 | Polling only (slow); pushes with content or note IDs (leaks to Apple and Google) |
| Device backups | Excluded | Backups are another copy of notes outside Kanso's encryption model |

## Decisions

Made by the owner on 2026-10-23:

1. **React Native with Rust bindings**, reusing as much Rust logic as possible. The UI is React
   Native; the logic is the shared Rust core.
2. **iPad is part of the mobile app**, not a separate project (from the canvas decisions, #45).
3. **Pen input is native capture feeding Kanso's one renderer**, not PencilKit or Jetpack Ink (#45).
4. **Minimum OS: iOS/iPadOS 17 and Android 10 (API 29).**
5. **Phones and tablets ship together** in the first release. Canvases follow #45.
6. **Expo**, with development builds and continuous native generation. Builds run in Kanso's own
   CI, with no OTA updates (see "Builds, CI and size").
7. **The library is excluded from iCloud and Google backups.** Keychain and Keystore secrets are
   device-only.
8. **Push notifications wake sync in the first release** (step 8b), content-free.
9. **PR #28 (the GPUI spike) is closed and its branch deleted.** Its findings are recorded in "Why
   React Native over the Rust core".


## Open questions for the owner

1. **Crash reporting** (the owner is deciding). The needs are fixed either way: a crash report
   must never contain note text, titles or file names, and nothing is sent without the user's
   choice. The options:
   - **On-device symbolicated crash logs the user chooses to send, with no third-party SDK**
     (recommended). Uses MetricKit's `MXCrashDiagnostic` on iOS and
     `ApplicationExitInfo` / tombstones on Android, uploaded to the Worker only when the user taps
     Send.
   - **A self-hosted Sentry-compatible server** with the SDK scrubbing everything but stack
     frames.
   - **App Store Connect and Play Console's built-in crash reports**, which only cover users who
     opted into sharing with Apple or Google.

   Step 13 implements whichever is chosen.
