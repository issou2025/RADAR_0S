- `schemas/skill_manifest.schema.yaml` owns Skill-oriented declaration/admission identity through `skill_id`.
- `schemas/workflow_manifest.schema.yaml` may carry `capability_id` plus optional `skill_manifest_ref` to the admitted Skill declaration.

### Correct identity boundary

```text
Capability Slot != Capability
Capability Slot = abstract replaceable function / binding target

Capability = governed unit under the uniform Capability Passport
Skill / Tool / Prompt / Resource may be Capability primitives
Skill manifest = Skill-oriented declaration / admission material
Capability Passport != runtime binding
```

`skill_manifest_ref` proves an explicit Skill admission/reference relationship. It does not by itself create a mandatory abstract Capability layer above every Skill.

Identifier equality or difference alone establishes no admission, binding, activation or task authorization.

### pantheon-mvp

- `mvp_vertical/capability_manager.py` is an implemented bounded lifecycle seam for external capability/runtime operations; its naming and semantic level remain to be reconciled only if an executable failing scenario requires it.
- existing code already separates installed, enabled, activation scope, health, update, task authorization and technical receipt states.
- Agent Plugin normalization already preserves package version/digest and component identity/provenance without granting authority.
- Tool Card/Hermes inventory work projects catalogue/runtime observations without becoming authority.
- existing Execution Admission remains the sole task/run legitimacy seam and must not be duplicated by Capability admission.
- `policy_gate` remains the consequential-effect chokepoint.
- Hermes Runs observation already separates compatibility, safety qualification and Evidence posture.

### Pantheon-plugins / H boundary

- external adapters/plugins may supply implementations or observations;
- H remains authoritative for Project Anatomy source/adapter qualification;
- I may consume bounded compatibility observations but must not recreate PDF/IFC/Revit qualification.

## Tranche-I exit criteria

I may close only when:
1. Capability Slot, Capability Passport unit and runtime binding have unambiguous distinct responsibilities;
2. Skill/Tool primitives can participate without availability implying admission;
3. exact implementation/release provenance is sufficient for binding and observed compatibility;
4. bindings are replaceable and separate from dependency adoption;
5. admission is distinct from installation and task authorization;
6. activation is scope-bounded and distinct from task authorization;
7. compatibility is observation-backed and distinct from health/safety/Evidence;
8. existing Execution Admission remains the sole task/run legitimacy seam;
9. Cockpit projects states without owning them;
10. one representative vertical proves the whole chain;
11. no runtime-management responsibility has moved into Pantheon;
12. Next schemas/docs and MVP/plugin consumers agree on final semantics;
13. H ownership of source/adapter qualification is unchanged.
