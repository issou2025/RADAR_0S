# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[Enhancement] Foldable Android support in the native (universal) Android app — adaptive layout across folded / open / tabletop / book postures**

*Project description:*
## Goal

Make the native (universal) Android version of MeedyaConverter **fully support
foldable Android devices** — Samsung Galaxy Fold-style book foldables, flip
foldables, the newer landscape foldables and trifolds, and large-screen tablets.
"Fully support" means one adaptive app that:

- uses the **large unfolded (open) screen** for a genuine multi-pane layout,
- stays usable on the **small folded (cover) screen**,
- takes advantage of the **half-open postures** — "tabletop" (hinge horizontal:
  media on top, controls below) and "book" (hinge vertical: two side-by-side
  panes), and
- **re-flows live** as the device folds, unfolds, or is rotated, without
  restarting and without losing what the user was doing.

This is the Android sibling of the iPhone Duo (Apple foldable) request in #500;
the two should be planned together as "foldable support across both native apps".

## Important prerequisite — read this first

**There is no Android version of MeedyaConverter today.** This was checked
against the repository: it is a Swift package targeting macOS only
(`Package.swift` declares `platforms: [.macOS(.v15)]`), and there is **no Android
app** — no Gradle files, no Kotlin (`.kt`) sources, no `AndroidManifest.xml`,
nothing under an `app/` module.

So "fully support foldable Android" is **not** a tweak to an existing Android app.
It sits on top of a larger, currently-unstarted piece of work: **building a
native Android app for MeedyaConverter at all.** Treat this issue as the
"make the Android app adaptive to foldables" layer, which depends on that Android
app existing first. Two sensible ways to run it (mirrors #500):

1. **Umbrella now, split later** — keep this issue as the tracking item for
   "foldable Android support", and open a separate, earlier issue for "bring
   MeedyaConverter to Android (native, universal)" that this one depends on.
2. **Fold into the Android effort** — when an "Android app" issue is opened, build
   the foldable/adaptive requirements in from the start (far cheaper than
   retrofitting) and keep this issue as the foldable-specific acceptance checklist.

A decision on which is one of the open questions below.

## The good news: Android foldable support is mature and well-documented

Unlike the iPhone Duo (#500), where Apple's tooling and docs are still rolling
out, Android foldables have existed for years and Google's guidance is settled.
There is a clear, stable set of APIs to build against.

### Jetpack WindowManager (`androidx.window`) — how the app learns the fold state

- `WindowInfoTracker.windowLayoutInfo(...)` gives a stream of `WindowLayoutInfo`,
  which lists the current `DisplayFeature`s.
- A **`FoldingFeature`** is the display feature that describes a fold or hinge. Its
  properties drive the layout:
  - **`state`** — `FLAT` (opened out flat) or `HALF_OPENED` (partly folded).
  - **`orientation`** — `HORIZONTAL` or `VERTICAL` (which way the hinge runs).
  - **`occlusionType`** — `NONE` or `FULL` (does the hinge hide content behind it).
  - **`isSeparating`** — whether the fold splits the display into two logical
    areas the layout should treat as separate.
  - **`bounds`** — the rectangle of the hinge/fold, so content can be kept out of
    it and the two halves aligned to it.

### The postures to support

- **Folded / cover screen** — small, compact. A cut-down layout: pick a file,
  see job progress at a glance, quick actions.
- **Unfolded / flat (open)** — large, tablet-like. A real multi-pane layout that
  uses the width (e.g. source + queue list beside job detail and settings).
- **Tabletop** (`HALF_OPENED` + `HORIZONTAL` hinge) — device propped like a
  laptop. Natural for media: preview/output on the top half, controls and queue
  on the bottom half, aligned to the hinge.
- **Book** (`HALF_OPENED` + `VERTICAL` hinge) — held like a book. Two side-by-side
  panes.

### Adaptive layout, driven by window size classes

- Use **window size classes** (Compact / Medium / Expanded, for width and
  height), not hard-coded device checks or orientation, to decide navigation and
  content density. Foldables shift between these classes **instantly** as they
  fold/unfold, so the UI must react to size-class changes as normal live events.
- If the app is built in **Jetpack Compose**, use the Material 3 **adaptive**
  layouts — `NavigationSuiteScaffold` (navigation that moves between bottom bar /
  rail / drawer by size class), and the canonical panes `ListDetailPaneScaffold`
  and `SupportingPaneScaffold`. These already collapse to one pane when folded and
  expand to two when opened, and there is dedicated guidance for the newer
  **landscape foldables and trifolds**.

### App configuration and behaviour

- Declare the app resizeable (`android:resizeableActivity="true"`) and **do not
  lock orientation**.
- Handle configuration changes so the app **does not restart** when the device
  folds/unfolds or is rotated — keep the running conversion, form input,
  selection and scroll position across the change.
- Support **multi-window / split-screen**, which large screens and foldables use
  heavily.
- Optional, form-factor-specific: **rear-display mode** and **dual-screen mode**
  are available through WindowManager for devices that support them.

## Proposed scope for this issue (the foldable-adaptive layer)

Assuming a native Android app exists (or is being built in parallel):

1. **Unfolded (open) multi-pane layout** using window size classes + Compose
   adaptive scaffolds (or the View-system equivalent) — the headline "use the big
   screen" work.
2. **Folded (cover) compact layout** — a coherent small-screen layout.
3. **Tabletop and book half-open postures** — observe `FoldingFeature`
   (`HALF_OPENED` + hinge orientation) and split the layout across the hinge
   (media above / controls below for tabletop; two panes for book), keeping
   content out of the hinge `bounds`.
4. **Live re-flow across fold/unfold/rotate** with full state preservation (no
   restart, no lost work).
5. **Size-class-driven, never orientation- or model-driven** layout decisions.
6. **Verify on every posture** — folded, flat, tabletop, book — on the foldable /
   resizable emulators and on hardware when available.

## Acceptance criteria (draft)

- [ ] A native (universal) Android app for MeedyaConverter exists and builds
      (prerequisite — may live in its own issue; link it here).
- [ ] Unfolded: a real multi-pane layout that uses the width (adaptive scaffold),
      not a stretched phone layout.
- [ ] Folded: a coherent compact layout on the cover screen.
- [ ] Tabletop posture: content splits across the horizontal hinge (media top,
      controls bottom); nothing is lost behind the hinge.
- [ ] Book posture: two panes aligned to the vertical hinge.
- [ ] Folding, unfolding and rotating re-flows the layout live and preserves the
      user's state (running job, input, selection, scroll).
- [ ] No layout decision depends on orientation or a device allow-list; all
      adaptation is by window size class + `FoldingFeature`.
- [ ] Behaviour verified in folded, flat, tabletop and book states on the
      foldable/resizable emulators, then hardware.

## Tooling

- **Jetpack WindowManager** (`androidx.window`) — stable; `FoldingFeature`,
  `WindowInfoTracker`, `WindowLayoutInfo`.
- **Window size classes** and **Jetpack Compose Material 3 adaptive** layouts.
- **Android Studio foldable / resizable emulators** and the Fold/Flip/tablet
  virtual devices; `adb` can drive fold/unfold for testing. No "coming later"
  gap here — this can be built and tested today, once the Android app exists.

## Open questions / decisions needed

1. **Do we actually want a native Android app?** Foldable support only matters if
   we ship MeedyaConverter on Android at all. That is a strategic call, and a
   large one — the current engine is Swift and shells out to command-line tools
   (ffmpeg etc.). On Android that becomes either a bundled native library
   (ffmpeg via the NDK / an ffmpeg-kit-style dependency) or a **companion / remote
   app** that drives a Mac or the `serve` REST API rather than converting
   on-device. Confirm the appetite and the shape first.
2. **"Native (universal)" — what stack?** Kotlin + Jetpack Compose is the modern
   default and has the best foldable/adaptive story (this issue assumes it). Note
   if a cross-platform toolkit (KMP, Flutter, etc.) is intended instead, because
   it changes which adaptive APIs apply.
3. **Umbrella-vs-fold-in** — run this as the umbrella with a separate "Android
   app" dependency, or fold the foldable criteria into a future "Android app"
   issue? (See "Important prerequisite".)
4. **Scope on Android** — full on-device converter, or a companion/remote app? A
   companion is far more realistic near-term; the foldable-adaptive layout work
   applies either way.
