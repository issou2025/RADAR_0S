# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**[Bug]: Windows `list_windows` takes ~1.2 s per call on every version**

*Project description:*
**Describe the bug**

On Windows, every `list_windows` call over MCP takes about 1.2 s. It did not change between 0.21.0, 0.33.1 and 0.34.0, while `get_window_state` on the same window got 5–14x faster between those versions.

One call returned in 13 ms with the same result, so most of the 1.2 s looks like waiting rather than enumeration work. For comparison, `EnumWindows` plus reading each window's process image name takes 1–2 ms from Python (ctypes) on the same machine.

Clients that target a window by app name (Hermes Agent's `computer_use` does this) pay this 1.2 s on every capture.

**Measurements** (Windows 11 Pro 10.0.26200, release `windows-x86_64-binary.zip` builds, MCP stdio session to the embedded daemon, permission mode unrestricted, warm medians of 10 calls)

| cua-driver | `list_windows` | `list_apps` | `get_window_state` (same window) |
|---|---|---|---|
| 0.21.0 | 1163–1271 ms | 363–583 ms | 1263–1500 ms |
| 0.33.1 | 1176 ms | 380 ms | 176 ms |
| 0.34.0 | 1120–1238 ms | 457 ms | 89–272 ms |

Measured against Notepad, Slack, Discord and the Claude desktop app; `list_windows` was about 1.2 s in every case.

**To reproduce**

1. Start an MCP session with `cua-driver mcp` on Windows.
2. Call `list_windows` with no arguments 10 times and time each call.

**Expected behavior**

`list_windows` in tens of milliseconds, close to the cost of `EnumWindows`.

**Questions**

- Is there a fixed wait or timeout inside the Windows window enumeration (for example a per-window message such as `WM_GETTEXT` to a hung window, or a UI Automation call)?
- Is there an argument that skips the slow part when the caller only needs pid, window id, app name and title?
