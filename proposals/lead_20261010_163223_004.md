# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**ios-build: install a dev build on the iPhone from anywhere (local devicectl, or OTA link over Tailscale)**

*Project description:*
## Goal

A model-invoked skill, `ios-build`, that answers one sentence from the user: **"install this on my phone"**. It works whether the phone is on the same Wi-Fi as the Mac or out on 4G/5G.

The agent then does this:

1. **Phone reachable on the local network** → build and install directly (`xcrun devicectl`), like today.
2. **Phone not reachable** (cellular, different network, Mac at home) → build a development `.ipa`, serve it over HTTPS inside the user's Tailscale tailnet, and **hand the user an install link** they tap in Safari.
3. **First run on a machine** → walk through a one-time setup (Tailscale, HTTPS certificates, device registration), check each item and say exactly which one is missing.

## Why this needs a skill: "impossible" was wrong, but only for one route

An earlier investigation concluded that building to the phone away from home was impossible. That conclusion holds **for the `devicectl` / Xcode route only**, and it was measured:

- A Tailscale bridge (replaying the phone's Bonjour record on the Mac and relaying ports to the phone's Tailscale IP with `socat`) reaches the phone over cellular, but the phone answers the CoreDevice pairing port with a TCP **RST**. **iOS closes its developer pairing service when it leaves Wi-Fi**, so no tunnel can fix that route. `devicectl` reports the phone `unavailable`.

The route that works ignores pairing completely. **Over-the-air (OTA) install** via an `itms-services://` link is a plain HTTPS download, so cellular is fine. A development-signed build installs this way on any device listed in its provisioning profile.

**Measured on 2026-10-10:** an iOS app with three extensions (keyboard, share, widgets) was built on the Mac. The resulting 63 MB `.ipa` was installed on the phone **over cellular** from Safari, while `devicectl` showed the phone `unavailable`. It installed and ran.

## The recipe that worked

### 1. Build: development signing, generic device

```bash
xcodebuild build -project <App>.xcodeproj -scheme <Scheme> -configuration Debug \
  -destination 'generic/platform=iOS' -derivedDataPath build/DerivedData \
  -allowProvisioningUpdates
```

`generic/platform=iOS` means the phone does not need to be reachable at build time. `-allowProvisioningUpdates` renews the team profile without the user.

### 2. Check the phone is in the profile, or the install fails silently on the phone

```bash
security cms -D -i <App>.app/embedded.mobileprovision > /tmp/profile.plist
plutil -p /tmp/profile.plist | grep ProvisionedDevices -A 50   # must contain the phone's UDID
```

The UDID comes from `xcrun devicectl list devices`, or from the setup step. Never write it into a repository.

### 3. Package as `.ipa`

```bash
mkdir -p stage/Payload && cp -R <App>.app stage/Payload/
(cd stage && zip -qry ../App.ipa Payload)
```

Building with `build` and zipping `Payload/` was enough. No `archive` / `-exportArchive` was needed for a development build.

### 4. `manifest.plist` + an install page

```xml
<plist version="1.0"><dict><key>items</key><array><dict>
  <key>assets</key><array><dict>
    <key>kind</key><string>software-package</string>
    <key>url</key><string>https://<host>/App.ipa</string>
  </dict></array>
  <key>metadata</key><dict>
    <key>bundle-identifier</key><string><bundle id></string>
    <key>bundle-version</key><string><CFBundleShortVersionString></string>
    <key>kind</key><string>software</string>
    <key>title</key><string><App> dev <sha></string>
  </dict>
</dict></array></dict></plist>
```

```html
<a href="itms-services://?action=download-manifest&url=https://<host>/manifest.plist">Install</a>
```

Both URLs must be **HTTPS with a certificate iOS trusts**. A self-signed certificate does not work.

### 5. Serve inside the tailnet

Tailscale Serve provides a real certificate for `https://<machine>.<tailnet>.ts.net`, reachable only from the user's own devices.

**Trap, measured:** the Mac App Store build of Tailscale **refuses to serve a directory**:

```
Error: failed apply web serve: Path serving is not supported on macOS due to sandbox restrictions.
```

So serve the folder with a local static server bound to `127.0.0.1`, and proxy it:

```bash
TS=$(command -v tailscale || echo /Applications/Tailscale.app/Contents/MacOS/Tailscale)
python3 -m http.server <port> --bind 127.0.0.1      # run it under the user's process manager (e.g. Portly) if they have one
"$TS" serve --bg http://127.0.0.1:<port>
HOST=$("$TS" status --json | python3 -c "import json,sys;print(json.load(sys.stdin)['Self']['DNSName'].rstrip('.'))")
```

Before handing over the link, verify it from the Mac: `curl -sI https://$HOST/App.ipa` must return `200` and the right `content-length`.

### 6. Hand over

The user turns Tailscale ON on the phone, opens `https://<host>/` **in Safari** (`itms-services` does not work from other browsers), and taps Install. The app installs from the home screen.

## Decision flow

```
xcrun devicectl list devices
├─ phone "available (paired)" and tunnelState: connected → build for the device, devicectl install, launch
└─ otherwise → OTA route (steps 1-6), reply with the link
```

The direct route stays the default: it is faster, launches the app, and needs nothing from the user.

## First-run setup the skill must cover

Check each one and report the missing one by name. Do not report a vague "it does not work".

| Requirement | How to check | If missing |
|---|---|---|
| Tailscale on the Mac and on the phone, same tailnet | `tailscale status` lists a phone peer | install Tailscale on the phone, same account |
| MagicDNS + HTTPS certificates enabled in the tailnet | `tailscale serve` succeeds, `curl https://<host>/` has no TLS error | enable HTTPS in the Tailscale admin console (DNS page) |
| Phone registered in the Apple team, and Developer Mode on | the UDID is in `ProvisionedDevices` (step 2) | connect once by cable/Wi-Fi to Xcode so the device is registered, then enable Developer Mode (Settings → Privacy & Security, reboot) |
| Mac awake while the user is away | — | energy settings or `caffeinate`. Say it, because a sleeping Mac looks exactly like a broken link |
| Static file server available | `python3` present | any static server works |

## Relation to existing skills

- **`in-progress/test-on-phone`** already holds the Tailscale Serve recipe for dev **web** servers (CLI inside the app bundle, deriving the host). The OTA route reuses it. **Collision to design for:** `test-on-phone` runs `serve reset` and serves at `/`. If both use the root, one evicts the other. The iOS route should probably serve under a path (`--set-path /ios`), or the two skills should share one convention.
- **A local, unpublished `ios-device-build`** (Flutter + native Xcode, `devicectl` route only, rule: never commit signing identity) is the Wi-Fi half of this skill. `ios-build` should absorb it rather than sit next to it.
- Project-specific checks (for example, verifying an injected git sha before install) stay in the project's own skill or `CLAUDE.md`, per the portability rule.

## Open questions (not measured yet)

- **Does an OTA install preserve the app's data?** A `devicectl` dev install has been seen wiping app state. Whether OTA behaves the same is untested.
- **Caching:** if the URL is the same for every build, Safari or iOS may serve a stale manifest. Possible fix: one folder per sha (`/ios/<sha>/`) with the sha in the manifest `title`.
- **Cleanup:** how many `.ipa`s to keep, and whether to stop the server and serve after install.
- **Flutter:** `flutter build ios --debug` then the same packaging. Not tried.
- **Free Apple accounts (7-day profiles):** the device must be in the profile. Not tried.
- **Without Tailscale:** fall back to a third-party host (Diawi, Firebase App Distribution, TestApp.io, Loadly)? That uploads the binary to a third party, so it should be explicit and opt-in, never silent.
