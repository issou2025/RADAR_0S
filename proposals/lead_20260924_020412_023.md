# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat(coverage): search GitHub and Sourcegraph for witness shapes**

*Project description:*
## What

Search **GitHub** — its code search index over the whole corpus of public repositories,
and the repository trees of API publishers — and **Sourcegraph**'s public code search for
a registrable real-world witness of every outstanding shape, under Contract B, with every
call through the Contract C guard. This node owns three of the seven declared sources:
`github-code-search`, `github-publisher-trees` and `sourcegraph`. The sibling node
`search-registries` owns the other four, and between you the seven are covered.

**The key set** is every `FIXTURE` `gap` row in the six region files at the commit you
branch from. At plan time that is the 29 rows of the ranked backlog, all in
`docs/openapi-surface/schemas.md`; `evidence-contract` adds to it every row it demotes
from `limitations` for a generation verdict, and `census-grammar` adds every new `FIXTURE`
row its selectors produce. Derive the set from the region files rather than from any list
restated in prose — `RankedBacklogTests.region_rows` is the read the repository already
uses for it.

**What the previous searches did and did not do, so you do not repeat either.** Two
rounds stand in the tree. The authoritative issue #188 search queried five sources
including GitHub code search (`gh search code '"<keyword>" filename:openapi.yaml'` and
five sibling file patterns) and Postman; it settled many rows and its records are in each
region file's `### Witness search (issue #188)` table. The later wide scrape (crozier
#264–#266, `docs/openapi-surface/witness-scrape-wide/`) cloned publisher trees and
re-censused an APIs.guru snapshot, and its own README records that **GitHub API, search and
GraphQL calls and Postman were not used**; it ended with all 26 of its baseline keys
`search-incomplete`. So GitHub's index has been asked with keyword queries and has never
been asked with the method these shapes need.

**The method, which is the point of this node.** The 29 outstanding shapes are structural
conjunctions of the object model — `schema.oneOf>schema.type:primary=array&schema.items>schema.anyOf:sole-non-null-member`
and its twenty-eight siblings, listed with their selectors in
`docs/openapi-surface/witness-scrape-wide/keys.md`. No keyword expresses any of them. So:

- **Keyword queries find candidates, and nothing more.** Query GitHub's code search for
  the *ingredients* — the field spellings a document declaring the shape must contain, in
  both the JSON and the YAML spelling — across `openapi.yaml`, `openapi.yml`,
  `openapi.json`, `swagger.yaml`, `swagger.json`, `path:openapi`, and the `language:JSON`
  and `language:YAML` caps where a narrow query returns little. At least two distinct
  phrasings per shape, each recorded verbatim in a code span with the count it returned.
- **The census decides.** Fetch each candidate, parse it, and run that shape's selector
  over it with `scripts/openapi-surface-census.py`'s own engine. A candidate declares the
  shape when the census says so and never because a grep matched.
- **Publisher trees.** Beyond the index, walk the repository trees of API publishers that
  serve their own descriptions — the wide scrape did five (Adyen, Twilio, Kubernetes,
  MongoDB, GitHub) from local clones; widen that list from the publishers the registered
  corpus and the APIs.guru catalogue already name, and census every readable OpenAPI 3
  document in each. Record the tree, its commit and each document's digest.
- **Sourcegraph.** Its public code search on `sourcegraph.com` indexes public
  repositories on more than one code host, with its own query language, so it is a
  second text-queryable index rather than a copy of GitHub's. Ask it the same way: queries
  for the shape's ingredients in both the JSON and the YAML spelling, across the same
  document locations expressed in Sourcegraph's own file filters, at least two distinct
  phrasings per shape, and every result evaluated by the census exactly as a GitHub code
  search result is. It is not a GitHub API, so the 70% rule does not govern it: every
  Sourcegraph call goes through the guard's `sourcegraph` host, paced on Contract C's
  non-GitHub discipline.

**Screening and recording.** Every candidate the census confirms is screened on all three
corpus screens — licence under `docs/corpus-licensing.md`, immutable ref, and Fern's own
acceptance of the raw document — and each outcome recorded per candidate. You do **not**
register anything: `register-witnesses` does that, from your ledger.

**Your evidence, Sourcegraph's included, lives at
`docs/openapi-surface/witness-search-github/`**: the acquisition
manifests, the census output over every candidate, the per-candidate screen records, the
Contract C wait log, and a `candidates.tsv` naming every confirmed declarer with its keys,
its three screen outcomes and its disposition. Your region-file lines go in each key's own
`### Witness search` table. Touch no other node's evidence directory.

**Replacing the eight grant-blocked artifacts is a named objective of this node.** The
wide scrape found eight artifacts that declare an outstanding shape and lack an evidenced
publisher redistribution grant, which `docs/corpus-licensing.md` refuses outright, and
`docs/openapi-surface/witness-scrape-wide/candidates.md` records each with its keys and
its `witness-blocked` disposition. Between them they cover three keys:
`ref-pointer-unnamed-segment` (seven Codat artifacts) and
`annotated-ref-target-closed-object` and `annotated-ref-target-oneof` (the PandaScore one).
The user's ruling is to **find specifications with the correct rights to replace those
eight** — so for each of those three keys, finding a replacement is part of this node's
work: a real-world document declaring the same shape, carrying an evidenced
redistribution-compatible licence under `docs/corpus-licensing.md`, and accepted by Fern.

There is no publisher outreach in this plan and none contemplated later. The eight stay
recorded only as provenance — publisher, artifact, pinned ref, and exactly what licence
evidence is missing — and they never satisfy a key and never stop the search for one. A key
with no properly licensed witness after an exhausted search stays a `gap` and is escalated,
under the rule Contract B states.

### Contract B — what makes a search exhaustive for a shape, and where it is recorded

**Where it is recorded.** Two places, and the gate reconciles them.

- The **row's own region file**, in its `### Witness search` table: one line per
  `(key, source)`, carrying the source, both query phrasings verbatim in code spans,
  what each returned as a count, the candidates the census confirmed, and each
  candidate's three screen outcomes.
- The **per-source evidence directory**, `docs/openapi-surface/witness-search-<source>/`,
  holding the raw acquisition manifests, the census output over every candidate, the
  per-candidate screen records, and the quota-guard wait log Contract C names.

**A search for a shape is exhaustive only when all five hold.**

1. **Every source in the declared set was asked and answered.** The set for this plan
   is these seven: `apis.guru`, `jentic`, `github-code-search`,
   `github-publisher-trees`, `sourcegraph`, `postman`, `vendor-portals`. A source
   outside this set is not a declared source: a record naming one answers for no
   declared source and leaves no obligation outstanding, and no key's outcome cites it
   as searched or as still owed.
   **Answered** means one of two things, decided by what the source offers rather than
   by the searcher. A source that accepts a text query is answered when condition 2
   holds for it. A source that does not — a repository tree, a publisher's tree, a
   registry read by enumeration — is answered when the record names the tree or index
   and the immutable ref or page range it was read at, and lists every readable
   OpenAPI 3 document in it with the census-selector output over that document, or
   names the document with the measured reason it could not be read. A source that
   offers both is answered only when both hold for it: a tree the queries did not walk
   is an unread tree, whatever the queries returned.
2. **At least two query phrasings per shape per source that accepts a text query, no
   two of them the same string**, each recorded verbatim in a code span so it can be
   re-run as issued, each with the count it returned.
3. **A candidate is tested for the shape by parsing it and running the census
   selector** — `scripts/openapi-surface-census.py`'s own selector engine over the
   parsed object model — and never by a keyword grep. Keyword queries find candidates;
   the census alone decides whether a candidate declares the shape. This is what the
   29 outstanding shapes require: they are structural conjunctions no keyword
   expresses.
4. **Every candidate the census says declares the shape is screened on all three
   corpus screens** — licence (`docs/corpus-licensing.md`), immutable ref, and Fern's
   own acceptance of the raw document — with the outcome recorded per candidate.
5. **No line reads `unanswered` for a required source.**

**The outcome vocabulary, amended.** `witness-found`, `witness-blocked`,
`fern-rejected`, `none-found`, `search-incomplete`, and the new **`exhausted`** —
which is `none-found` over a search meeting all five conditions above. Only
`exhausted` licenses the statement that a shape has no registrable real-world
witness. A `none-found` over a search that does not meet the five reads
`search-incomplete`, exactly as today.

**A rate-limit cap is never `unanswered`.** `unanswered` is reserved for a source that
refused, errored, or does not exist. A bucket reaching its cap is not a source
declining to answer: the search waits for the reset and continues. Recording a source
`unanswered`, marking a key searched, or stopping a search because a bucket filled is
refused by the gate and is the failure this contract exists to prevent.

**What a probe may settle, which replaces routes 2 and 3 for generation verdicts.** A
locally authored probe settles a row **only** where that probe's own Fern measurement
shows non-generation under Contract A. Where Fern emits output derived from the shape,
no probe settles the row however the search ended: the row stays `gap`, carries its
full search record, and is escalated. Routes 2 and 3 survive only for non-generation
verdicts, and every row they settle now owes a Contract A artifact rather than a prose
verdict alone.

### Contract C — the rate-limit guard, its interface and its 70%-per-bucket wait rule

**Where it lives.** `scripts/rate_limit_guard.py`, imported by every script in this
repository that makes an HTTP call to GitHub, to Postman or to Sourcegraph, and readable from the
command line as `just quota-status`.

**This plan's code makes no GitHub GraphQL call of any kind.** Every GitHub call it makes
is REST: code search and repository search are `/search/code` and `/search/repositories`,
repository contents and git trees are `/repos/…/contents` and `/repos/…/git/trees`, and
nothing this plan does needs GraphQL for anything else. The reason is the guard's own
reading, and it was measured rather than assumed. A GraphQL `rateLimit` query is itself a
GraphQL call and spends a point of the bucket it reports: the manager measured this host's
token on 2026-09-23 at about 18:55 UTC and `used` rose on every read, the response
reporting `cost: 1`, `rateLimit(dryRun: true)` included. The one free source of that
figure, the `graphql` block of REST `/rate_limit`, was measured at the same moment
reporting `used: 0` while GraphQL's own `rateLimit` field and the `X-Ratelimit-Used`
header on a GraphQL POST both reported 1,274–1,279. So the GraphQL bucket has no reading
that is both free and accurate, and a guard covering it could not take even its first
reading without possibly spending past 70%. REST `/rate_limit` is free — GitHub documents
it as not counting against any limit — and accurate for the REST buckets. Leaving GraphQL
out is what lets the user's rule hold by construction, with no exemption for the guard's
own readings, no reservation to carry and no first-reading hole.

**The 70% rule is a guarantee about GitHub's REST buckets, and Postman and Sourcegraph
are paced instead.** The rule needs three figures — limit, used and reset — read freely and
accurately before each call, and only GitHub publishes them: `GET /rate_limit` reports
every REST bucket and does not count against any limit. So the percentage rule holds by
construction for GitHub `core`, `search` and `code_search`, and any other REST bucket
`/rate_limit` reports that a call of this plan spends in. The Postman endpoint this plan
uses — `POST https://www.postman.com/_api/ws/proxy` — publishes no quota figures at all,
and **this contract makes no claim about any Postman quota figure**: no limit, no used, no
reset, and no percentage. Postman runs under a separate, stated pacing discipline: a fixed
minimum spacing between requests, `429` and `Retry-After` honoured, exponential backoff on
repeated refusals, and never a retry into a refusal. A Postman refusal or throttle is a
wait exactly as a GitHub cap is — never a reason to mark a key searched, to record a
source `unanswered`, or to stop a search. Sourcegraph's public code search on
`sourcegraph.com` is not a GitHub API either, so the percentage rule does not govern it
and this contract claims no Sourcegraph quota figure: it runs on exactly the pacing
discipline Postman does, in a paced lane of its own, and a Sourcegraph refusal or
throttle is a wait on the same terms.

**The interface, fixed for this plan.**

- `RateLimitGuard(host, *, evidence_dir=None)` — `host` is `"github"`, `"postman"` or `"sourcegraph"`.
- `guard.acquire(bucket, *, cost=1)` — called immediately **before** every call. For the
  GitHub host, `cost` is the number of units that call spends in that bucket, which is 1
  for every call this plan makes; the guard reads that bucket's usage live and free, and
  admits the call only while `(used + cost) / limit <= 0.70`; otherwise it sleeps until
  the `reset` that refusing reading named and reads again once that reset has passed, for
  as long as that takes. It does not return while admitting the call would take the bucket
  past 70%, and it never raises for a bucket being full. Checking `used` alone is the bug
  the `cost` term spells out: a bucket at 69 of 100 has room for a call costing 1 and none
  for a call costing 2.
- For each paced host — Postman and Sourcegraph — `acquire` returns only once that
  host's declared minimum spacing since the guard's own last request to it has elapsed
  and any backoff a refusal from it opened has expired. It decides on no usage figure,
  because neither host publishes one to decide on, and it raises nothing for pacing: it
  waits, and the wait is recorded like any other. The two lanes are independent, so a
  wait on one never delays the other.
- **`acquire` refuses a bucket the guard does not cover, `graphql` by name**, raising
  `UnsupportedBucket` at once — before any reading, without waiting and without admitting.
  Such a call is a programming error in this repository, not a call to pace: the fix is to
  make the REST call instead, never to wait for a bucket the guard cannot read for free.
  `record` refuses a response from GitHub's GraphQL endpoint the same way, so a GraphQL
  call made without passing through `acquire` is a loud failure rather than an unaccounted
  spend.
- **Admission is a reservation, not a reading taken beside the call.** `acquire` holds
  a per-bucket lock across the live read, the admission decision and the caller's call,
  released by `record`, and reserves `cost` against the reading it admitted on until
  `record` replaces that reading with the response's own headers. So two callers inside
  one process are admitted in sequence and the second decides against a figure that
  already accounts for the first. Each paced lane holds the same lock across its spacing
  wait and its call, so two callers cannot collapse one interval.
- **The guard's own quota-reading calls spend nothing**, which is why the percentage rule
  is stated for GitHub's REST buckets and for nothing else: `GET /rate_limit` does not
  count against any limit, so no reading the guard takes can carry any bucket anywhere.
  One freshness policy covers every bucket the percentage rule governs, with no exception
  for any of them:
  - **Every admission is decided on a reading taken from the host inside that `acquire`**
    — never on a reading kept from an earlier call, and never on a counter the guard
    maintains, because between one response and the next call another holder of the
    shared token may have spent.
  - **The cap governs the guard's readings as well as the calls it admits**, and it does
    so at no cost: a reading spends nothing, so no reading of the guard's own takes a
    bucket past 70%, at the cap or anywhere else, and a fresh guard's very first reading
    is safe for that same reason whatever state it finds the bucket in. While a reading
    does not leave room for the guarded call's `cost`, the guard sleeps until the `reset`
    that reading named and reads again once it has passed, writing each such reading to
    the wait log as a probe. **Neither a guarded call nor a guard reading ever takes a
    GitHub bucket past 70% on this code's own spending**; spending by other holders of the
    shared token is outside that guarantee, as the next bullet but one states.
  - `record` is what a response's own `x-ratelimit-*` headers are for: closing the
    reservation, logging what the call actually cost, and honouring a `Retry-After`. They
    are never the basis of a later admission.
- **What the 70% is a guarantee about.** The guard bounds what *this repository's* code
  spends on the shared GitHub token and leaves the rest of every bucket as headroom for
  the other work on this host, which it cannot see and does not control. It is not a claim
  about the token's instantaneous total usage: an independent caller can spend between
  any two of the guard's readings, and that headroom is the answer to it. A consumer's
  criteria therefore state what the guard and the committed evidence hold, never what
  every process on the host did at an instant.
- `guard.record(response)` — called immediately **after** every call. For GitHub it folds
  in that response's own `x-ratelimit-*` headers and any `Retry-After`. For a paced host it
  starts that lane's next interval, and on a `429` or other refusal it honours
  `Retry-After` and opens the exponential backoff the next `acquire` on that lane waits
  out.
- `guard.waits()` — the structured record of every wait it made, written under
  `evidence_dir` so a recorded search can show it waited rather than skipped. A paced
  lane's spacing or backoff wait is recorded there as a GitHub cap wait is.
- Buckets: GitHub `core`, `search` and `code_search`, plus any other REST bucket
  `/rate_limit` reports that a call of this plan spends in. The guard has no `graphql`
  bucket, because this plan makes no GraphQL call. Neither Postman nor Sourcegraph has
  a named quota bucket either, because neither publishes one; each has one paced lane.
- **Usage is read live before every call** the percentage rule governs, never estimated,
  never cached across calls, because the token is shared with everything else on this
  host.
- **A refusal that the live reading disagrees with is GitHub's secondary (burst)
  limiter**, which no endpoint reports and which every retry extends. The guard backs
  off exponentially honouring `Retry-After`, and after its declared attempt budget
  raises `SecondaryLimit`. Handling that is to report the refused call and stop making
  it — never a tight retry, and never marking the key searched. A Postman or Sourcegraph
  refusal is handled the same way.

**The invariant every consumer of the guard restates.** A bucket reaching its cap is
never a reason to stop a search, to mark a key searched, to record a source
`unanswered`, or to conclude anything about the world. Waiting is the intended
behaviour and it is not a failure. The rule is per bucket, and a Postman or Sourcegraph
throttle or refusal is a wait exactly as a GitHub cap is.

## Why

The user's constraint is the reason this node exists and it is worth quoting: *"Do not
give up early on searching. A shape is never declared unwitnessed after a finite-corpus
sweep... `search-incomplete` is a reason to keep going, not a stopping point."* Twenty-six
keys have read `search-incomplete` through three rounds of work, and the cheapest way to
clear that has always been to declare the search over. The user wants the opposite: a
shape Fern generates from gets a real specification or it stays visibly unproven.

GitHub is the largest index of public OpenAPI documents anywhere and it has never been
asked the question these shapes actually pose. Sourcegraph is in the declared set for the
same reason, and a source in that set that nobody searches would let a key read as
exhausted while one of its required sources was never asked. And the shapes are worth the spend: all 29
are branches of `src/ir.rs`'s six type-lowering functions, the file the repository's own
join table calls *"still wholly unreached — all 235 of them"* by any committed golden.
Every one of them is a place where crozier and Fern could disagree and nothing in the tree
would notice.

## Acceptance criteria

- The key set searched is derived from the six region files at the branch point and
  contains every `FIXTURE` `gap` row in them; the derivation is recorded and reproducible.
- Every key carries a `### Witness search` line in its own region file whose
  `github-code-search` segment records queries covering that shape's own ingredients
  rather than repeating one of them: for every field spelling a document declaring the
  shape must contain, at least one query in the JSON spelling and one in the YAML
  spelling, put across the document locations this node's `## What` names rather than a
  single one of them, and at least two phrasings for the shape overall with no two
  recorded queries being the same string. The segment names the ingredients it derived
  from the shape's selector, so a reader can see which query covers which. Each query is
  recorded in a code span as the string that would re-issue it against GitHub unchanged,
  and each carries a recorded outcome: a result count, or a recorded non-answer carrying the status and the
  time recorded against it. No query is left without an outcome, no cell in that segment is
  empty, a placeholder or a `TODO`, and a segment whose queries cover one ingredient or one
  spelling satisfies none of this.
- Every key's `### Witness search` line carries a `sourcegraph` segment held to the same
  obligations as its `github-code-search` segment: queries covering that shape's own
  ingredients, for every field spelling at least one in the JSON spelling and one in the
  YAML spelling, put across the document locations this node's `## What` names as
  Sourcegraph's own file filters express them, and at least two phrasings for the shape
  overall with no two recorded queries being the same string; the ingredients named; each
  query in a code span as the string that would re-issue it against Sourcegraph unchanged;
  and each carrying a recorded outcome, a result count or a recorded non-answer carrying
  the status and the time recorded against it. No query is left without an outcome, no
  cell in that segment is empty, a placeholder or a `TODO`, and a segment whose queries
  cover one ingredient or one spelling satisfies none of this. Its results are held to
  every criterion below that governs the candidates a recorded query yielded — the one
  admitted reduction, the three dispositions, the outstanding failures and the candidate
  identity — exactly as GitHub code search results are.
- Every key's `github-publisher-trees` segment is answered in Contract B's second sense
  rather than by a query: it names the publisher set searched and, per publisher, the
  tree and the immutable ref it was read at, and every readable OpenAPI 3 document in
  those trees is listed with the census-selector output over it and its digest, or named
  with the measured reason it could not be read. A segment carrying queries alone
  satisfies none of this.
- The publisher set is a widening of the last round's rather than a repeat of it. The
  committed record states the rule by which it was derived from the publishers the
  registered corpus and the APIs.guru catalogue name as serving their own descriptions,
  lists every publisher that rule selects, and the set is a strict superset of the five
  the wide scrape walked — Adyen, Twilio, Kubernetes, MongoDB and GitHub. The derivation
  is reproducible from the committed record, and a set equal to those five satisfies
  none of this.
- No candidate is classified on the strength of a keyword match, and the committed record
  for each key accounts for every result its recorded queries and tree walks yielded. The
  one reduction admitted between the recorded results and the candidate list is
  deduplication by repository, path and digest, so that one document reached twice is one
  candidate; the record states that it is the only reduction applied. No result is dropped
  by a bound, a sample, a cap or any other rule, and a candidate list smaller than the
  recorded results can account for satisfies none of this.
- Every candidate in that list carries exactly one of three dispositions, and the number
  of dispositions equals the size of the list: the committed output of that shape's
  selector run through `scripts/openapi-surface-census.py`'s own engine over the parsed
  document, with the classification that output produced; a recorded parse failure,
  carrying the parser's own diagnostic over the bytes that were fetched; or a recorded
  acquisition failure, carrying what was attempted and the status recorded against it. The
  key's confirmed declarers are exactly those whose committed output declares the shape.
- A key carrying any parse or acquisition failure records each as outstanding rather than
  as an absence, so `final-reconciliation` reconciles that key as `search-incomplete`. Only
  a key whose every candidate carries a committed selector output is eligible to read
  `exhausted` at all — which is what makes an unevaluated result cost the exhaustion claim
  rather than disappear.
- No source line this node writes reads `unanswered` because a rate-limit bucket reached
  its cap, and no key is recorded as searched for that reason.
- Every GitHub call this node's own code makes is a REST call bracketed by the guard: a
  `scripts/rate_limit_guard.py` `acquire` on the bucket that call spends in, naming its
  cost, immediately before it, and a `record` of its response immediately after. The
  finished tree carries no GitHub call of this node's code outside that bracket, and no
  GitHub GraphQL call at all — the searches, the repository trees and the contents reads
  are `/search/code`, `/search/repositories`, `/repos/…/git/trees` and
  `/repos/…/contents`. Building and issuing the request between the two is what a
  consumer of Contract C does, and is not what this criterion refuses.
- Every Sourcegraph call this node's own code makes is bracketed the same way, by an
  `acquire` on the guard's `sourcegraph` host immediately before it and a `record` of its
  response immediately after, and the finished tree carries no Sourcegraph call of this
  node's code outside that bracket. Those calls are paced under Contract C's non-GitHub
  discipline — declared spacing, `429` and `Retry-After` honoured, exponential backoff,
  never a retry into a refusal — and no criterion of this node holds them to the 70% rule
  or records a quota figure for Sourcegraph.
- The committed wait log accounts for every bucket the recorded acquisitions touched —
  `core`, `search` and `code_search` — naming each wait's bucket, the reading that caused
  it and its duration, and for every wait on the Sourcegraph lane names that lane, its
  duration and its cause — the declared spacing, or a refusal with the backoff it opened —
  since Contract C claims no Sourcegraph quota figure. It carries no credential value.
- Any secondary-limiter refusal is recorded with what was refused and what was tried, the
  call is not retried tightly, and the affected key is not marked searched.
- `docs/openapi-surface/witness-search-github/candidates.tsv` names every confirmed
  declarer with its keys, its licence, ref and Fern screen outcomes, and its disposition,
  in a form `register-witnesses` can act on without re-deriving anything.
- Each of the eight redistribution-blocked artifacts from the wide scrape is recorded as
  provenance with its publisher, artifact, pinned ref and the exact licence evidence that
  is missing, and no key is recorded as witnessed or as searched on the strength of one.
- The three keys those eight declare — `ref-pointer-unnamed-segment`,
  `annotated-ref-target-closed-object` and `annotated-ref-target-oneof` — each carry, in
  this node's record, either a replacement candidate declaring the same shape with an
  evidenced redistribution-compatible licence and Fern's acceptance, or the recorded search
  that looked for one across this node's sources and what it found. No publisher is
  contacted and no criterion here rests on a grant being given, and this node does not
  conclude that no replacement exists — that reading needs both search nodes' sources and
  belongs to `final-reconciliation`, which escalates such a key.
- Each recorded query is re-runnable as written against the source it names, and each
  recorded candidate carries the identity a later reader can fetch it by: its source and
  the repository and path it was reached at always, and its pinned ref and digest wherever
  its bytes were fetched. A candidate carrying a parse failure carries both, since its
  bytes were fetched; a candidate carrying an acquisition failure carries instead the
  identity the search result itself reported and the recorded failure, which is the
  complete record for one whose bytes never arrived. So a later re-run of those queries and
  fetches against these same sources — `final-reconciliation`'s refresh of this record, or
  a later search round — can compare what is committed here with what that source then
  holds. That re-run is the named later comparison and whether it agrees is not this node's
  bar; this node's bar is the record's completeness in the sense above, with no empty,
  placeholder or `TODO` cell in any source, query, result, candidate or screen position.
- This node registers no corpus row, commits no golden, adds no `CORPUS.md` row, and
  changes no file under `tests/fixtures/`.
- An outcome of `exhausted` is recorded for a key only where this node's sources plus the
  sibling `search-registries` node's are all answered for it; where that is not yet true,
  the line records what this node found and leaves the key's overall outcome to
  `final-reconciliation`.
- The acquisition code this node adds or changes is proven end to end by an offline test
  tier that drives it against a real local HTTP server rather than a mock of the module
  or of its HTTP client, and that tier is part of the repository's deterministic gate. It
  proves at minimum: that an acquisition routes through the guard and waits rather than
  proceeding when the server reports a bucket over the cap; that a bucket reaching its
  cap produces a wait record and never an `unanswered` source line or a key marked

**A wait written against a full command line never ends, because one of those command
