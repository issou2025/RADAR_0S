# Project Proposal — Pdf To Revit

## Project Understanding
You need assistance with: 
**glTF/IFC export loses Revit transparency when the element→material binding fails, and never reads view/graphics (V/G) overrides**

*Project description:*
### Summary

First, thanks — the material pipeline is in better shape than the docs suggest. On a Revit 2024
project, `material_object_tag` / `scan_material_appearances` recovered **192 materials, 60 of them
with transparency > 0**, and `model_to_glb` emitted **37 `alphaMode: "BLEND"` materials whose
`baseColorFactor[3]` is exactly `1 − transparency`** (`Glass` 0.9, `Fassade - Glas` 0.75,
`Glass - Clear, Grey` 0.64, `Glass - Frosted` 0.55, …). Those bindings reach 438 glazing panels and
66 light-fixture glass panes. So graphics-tab transparency is read and exported correctly — this is
not an alpha-emission bug report.

Two gaps remain for consumers that treat the glTF as geometry+appearance data:

1. **View/graphics overrides (V/G) are not read at all.** A view that sets a category or an element
   to 50% transparency exports fully opaque. There is no research module, no `support-matrix.json`
   row, and no mention in the changelog for `VisibilityGraphics` / `OverrideGraphicSettings` /
   per-view transparency. (All "override" hits in the changelog are IFC *Export As* overrides.)
2. **When the element→material binding fails, the fallback throws away transparency.** The
   fallback is `category_material()` → `category_colour()` (`src/ifc/gltf.rs:640-664`), which
   hardcodes alpha per IFC type and otherwise `1.0`. On the same project:
   - 6,804 node primitives total, 580 transparent;
   - `Category IFCDUCTSEGMENT` 728, `Category IFCPIPESEGMENT` 488,
     `Category IFCLIGHTFIXTURE` 149, `Category IFCDOOR` 124, `Category IFCRAILING` 14,
     `Category IFCSTAIR` 8, `Category IFCWALL` 2, `Category IFCBUILDINGELEMENTPROXY` 1
     → ~1,500 primitives that can only ever be opaque or the hardcoded category alpha.
   - This overlaps the open element→material assignment issue (#1603); I am reporting it here
     because the *rendering consequence* is transparency loss, not just a missing colour.

A related small inconsistency: `category_colour()` **invents** alpha for `IFCWINDOW`/`IFCPLATE`
(0.45) and `IFCSPACE` (0.12). Those values are not in the file. For a viewer palette that may be
intentional, but the same function feeds the glTF/IFC data export, so a consumer cannot tell
"Revit says 45% opaque" from "rvt chose 45% for windows". See the downstream-consumer note below for
why that distinction matters to a CAD database.

### How YACR uses this crate

YACR (https://github.com/zenglanmu/yacr) is a Rust CAD viewer that imports `.rvt` by depending on
this crate, pinned exactly at `=0.17.0` (no fork, no patch). It calls `run_export(...)` +
`model_to_glb(&run.model)` and then reads the GLB as data: node world transforms become meshes,
`baseColorFactor` becomes the entity colour, and `alphaMode: "BLEND"` + alpha becomes an explicit
**opacity** attribute stored on the entity. That opacity is both rendered (transparent pass: 580 of
6,804 batches in the sample below) and plotted (PDF `/ca`), so it is database state rather than a
viewer tint: a lost material binding makes an element silently opaque, and a V/G override has no
representation — and no diagnostic saying it was dropped.

### Reproduction

1. Open the sample project with the default export path, write the GLB.
2. Count materials and node primitives by `baseColorFactor[3]`:
   - 212 glTF materials, 37 with alpha < 1.0;
   - 6,804 primitives, 580 with alpha < 1.0;
   - every primitive on a `Category IFC*` material is `a = 1.0` except `IFCSPACE` (0.12).
3. In Revit, create/observe a view with a V/G override that makes a category translucent
   (e.g. Walls → 50%); re-export. The override has no effect on any material or primitive.
4. For the binding gap, compare a type that draws with one material against an instance whose
   material is only in its own parameters: the former gets the material (and its alpha), the latter
   falls back to `Category IFC*`.

### Expected

- A documented, machine-readable statement of whether view/graphics overrides are part of the
  export contract (a `support-matrix.json` row plus a line in the glTF/IFC docs would be enough for
  consumers to state the boundary honestly).
- If feasible: read `OverrideGraphicSettings` transparency for the exported view and let it override
  the element/category alpha, with the same "no invented values" rule used for materials.
- Category fallback should not fabricate alpha for data exports, or should mark it (e.g. the
  material name already says `Category …`; an extras flag or a documented `alphaSource` would make
  it unambiguous).

`tests/element_materials.rs` checks material **names** through the IFC export, but no test asserts
the glTF alpha path — the transparency claim currently rests on the external IFC-scored probes
(RE-53). I can add `tests/gltf_material_alpha.rs`, corpus-free and deterministic:

- build `IfcModel { materials: vec![..], ..Default::default() }` with
  `MaterialInfo { transparency: Some(0.75) }` and an opaque sibling;
- `model_to_glb(&model)`, parse the JSON chunk with `serde_json` (already a regular dependency);

  `ifc_type = "IFCWINDOW"` and no material emits `Category IFCWINDOW` with alpha `0.45`, so the

No `Cargo.toml` change is needed: the upstream `[dev-dependencies]` already enables
`rvt = { path = ".", features = ["unstable-research"] }` for dev targets, and `serde_json` is
already a regular dependency.

I can also add a corpus-gated companion check in the style of `tests/element_materials.rs`
(`RVT_PROJECT_CORPUS_DIR`, skip when absent) that walks the sample project and asserts the
transparent-material count, so a future regression in `pbr.rs`/`gltf.rs` fails loudly.
