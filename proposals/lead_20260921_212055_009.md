# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**The flatten cache cannot be reached from inside a clip, so a scrolling list re-flattens every frame**

*Project description:*
**The architecture is to be agreed before anything is written.** This changes
how a clip reaches a draw command, which is a representation every consumer of
`FlattenedCommand` depends on.

## Observed

The flatten cache cannot be reached from inside any clip. Both halves are gated
on the same condition (`src/renderer/flatten.rs`):

```rust
// read
if parent_clip.is_none() && node.clip.is_none() && ...

// write
let should_cache =
    node.clip.is_none() && parent_clip.is_none() && world_transform.is_translation_only();
```

A container clips when it scrolls or when it is `Overflow::Hidden`
(`src/widgets/container/mod.rs:1741-1748`), and `text_input` clips its own text.
So every node inside a scroller is excluded, and measurement confirms it:
`examples/bench_list` with 5000 rows reports **`flatten: cache_rate=0.0%` in
fifty consecutive samples** across two builds, while the paint cache sits near
70% in the same runs.

**The guard is load-bearing, not conservative.** Each command carries the
*effective* clip — already intersected with every ancestor, in world
coordinates:

```rust
let effective_clip = match (parent_clip, &node_world_clip) {
    (Some(parent), Some(node_clip)) => Some(intersect_clips(parent, node_clip)),
    (Some(parent), None)            => Some(*parent),
    ...
```

and the reuse path shifts **every** command's clip by the scroll delta. Relax
the guard as it stands and a cached row inside a scroller carries the viewport's
clip baked in, so scrolling drags the viewport along with the row: the clip
stops cutting anything and the list paints straight through its scroller. That
is the first frame, not an edge case.

## Expected

A subtree that only translates is reused rather than re-flattened, including
inside a scroller — which is the case that translates most.

## Two changes, and only one of them is architectural

**A. The hazard is a mismatch, and it can be tested for directly.** The danger
is content translating by `(dx, dy)` while its inherited clip does not. Record
the parent clip in `CachedFlatten` beside the world transform, and reuse only
when

```
cached_parent_clip translated by (dx, dy) == current_parent_clip
```

- static `Overflow::Hidden`: `dx = dy = 0`, clips match — **reused**
- a clipped subtree moving as a unit with its clip — **reused**
- scrolling: content moved, viewport did not — **correctly rejected**
- a resized clip: shapes differ — **correctly rejected**

One field and one comparison. It does not help scrolling. It removes the half of
the restriction that guards against nothing.

**B. Scrolling needs the clip to stop being baked in.** Give commands a
reference to a clip rather than a resolved shape, resolve it when `render.rs`
reads `cmd.clip`, and a cached subtree no longer carries its ancestor's clip at
all — scrolling moves content while the clip entry stays put.

The blast radius is smaller than `.claude/skills/renderer/SKILL.md`'s *"Five
pipelines, so a change to clipping has to be checked in all of them"* implies:
`cmd.clip` is read in about six places, all in `src/renderer/render.rs`. If
resolution happens before those reads, the five pipelines and every shader see a
`PlacedShape` exactly as they do today.

## Prior art

Both of the obvious comparisons cache inside scrollers, and both do it by
separating the clip from the content rather than by shifting it.

- **Flutter** wraps a scrollable's children in `RepaintBoundary`, whose stated
  purpose is exactly this: *"it allows the scrolling to change the offset of the
  child picture without repainting the picture"*. Each boundary owns a `Layer`,
  so the clip is a different layer from the content and does not move with it.
  Flutter does not treat it as free — its own docs say that for children that
  are cheap to repaint it can be better not to add one, and flutter#103162 asks
  for them to be dropped when a scrollable cannot actually scroll.
- **Chromium** keeps four property trees — transform, clip, effect, scroll. A
  clip is a node in the clip tree that draw commands reference; scrolling
  updates a node in the transform tree and the clip node is untouched. That is
  option B in its mature form.

Links: https://api.flutter.dev/flutter/widgets/RepaintBoundary-class.html ·
https://github.com/flutter/flutter/issues/103162 ·
https://developer.chrome.com/docs/chromium/renderingng-data-structures

## What is missing before B is worth doing

**A measurement this repository does not have.** `AGENTS.md` asks for one
wherever performance is claimed, and what exists is a hand-scrolled run:
flatten averaged **74us against a GPU phase of 623us** — about a tenth of frame
cost — with a single 21ms outlier seen once and not reproduced. Scrolling felt
fine. That is not enough to justify changing a representation the whole renderer
reads.

Two guido runs in the same session polled 136k and 83k frames, because the
scrolling was done by hand, so their per-frame averages are not comparable to
each other either. There is no `criterion` setup and no `benches/`; `Headless`
renders offscreen but is a correctness harness, not a benchmark one.

So the honest order is: **A** now, a repeatable scrolling benchmark next, and
**B** only if the number it produces says so.

## Acceptance

For **A**, writable today: a test that a subtree under a static
`Overflow::Hidden` container is reused rather than re-flattened across two
frames — `tests/paint_cache_across_frames.rs` is the file that already watches
cross-frame reuse, and `record_flatten_cached`/`record_flatten_full` are what
count it. It fails today (the guard refuses) and passes with the delta check.
A second test must show a scrolling subtree is still **rejected**, or A has
reintroduced the bug it is avoiding.

For **B**, not writable until the benchmark exists, and that benchmark is its
own piece of work.

## Non-goals

- Not changing what any shader does with a clip.
- Not Flutter's per-child boundaries as an API — guido has no `RepaintBoundary`
  equivalent and this does not propose one.
- Not the paint cache, which refuses partial paints for a separate and
  documented reason (`docs/RENDERER.md`: a list that scrolls culls from its
  first scrolled frame onward).
