*Project description:*
## Is your feature request related to a problem? Please describe

The docs list test surfaces ([`docs/testing.md`](https://github.com/pyrevitlabs/pyRevit/blob/develop/docs/testing.md)) and release checks ([`docs/release-qualification.md`](https://github.com/pyrevitlabs/pyRevit/blob/develop/docs/release-qualification.md)). They don't say what a feature or PR has to be tested against. The knowledge is scattered:

- `release-qualification.md` has a "Languages and encodings" section covering UI language, decimal comma, non-ASCII paths and `user_locale`. It is only a release checklist, and contributors don't see it.
- `pyrevit-style.md` and `scripting/ironpython.md` cover f-strings and the coding line, but not the semantic differences between engines.
- `check_ipy2_compat.py` only rejects `**kwargs,`. `check_revit_api_compat.py` checks API surface, not behaviour changes.
- No page covers units. Metric, imperial and internal feet are not mentioned as a test case. The only unit remarks are in `agent-runtime.md` and `revit-api-compat.md`, and they are about the API.
- Other pitfalls were found only while reviewing PRs and testing live, and they never reached the docs. Examples:
    - IronPython 2.7: `500 / 180` is 2 without `from __future__ import division`.
    - IronPython 2.7: a non-ASCII character without a coding line is a `SyntaxError`.
    - IronPython 2.7: `io.open(..., encoding='utf-16')` silently returns an empty string.
    - IronPython 3.4.2: `print` without a console fails with `unknown encoding: codepage___0`.
    - IronPython 3.4.2: a script that leaves a Python worker thread running can end with `engine_error` and no traceback.

## Describe the solution you'd like

Add a "Test matrix and pitfalls" section to `docs/testing.md`. It would be a checklist an author or reviewer goes through for any feature, and `release-qualification.md` would link to it. Proposed axes:

| Axis | Cases |
|---|---|
| Engine | IronPython 2.7.12, IronPython 3.4.2, CPython 3.12. Integer division, `str`/`unicode`, `open()` encoding (CPython on Windows defaults to cp1252), `print` without a console, threads |
| Units | Project units metric, imperial and internal feet. Check that values, thresholds and displayed numbers go through `UnitUtils`/`ForgeTypeId`. Include area, volume, angle (radians) and rounding |
| Locale and text | Cyrillic, CJK and umlauts in element, parameter and family names, in paths and in output windows. Decimal comma. Look up by `BuiltInCategory`/`BuiltInParameter`, never by localized name |
| Revit year | Years on different .NET runtimes, and API deprecations that change behaviour (`ElementId` int to long, `DisplayUnitType` to `ForgeTypeId`) |
| Document state | No document open, a family document, a linked model, a workshared model with elements owned by others, design options, phases, a read-only or detached model |
| View and selection | The active view is a sheet, schedule or 3D view. The selection is empty, has one element or has many |
| Environment | Spaces and non-ASCII in the user name and clone path, per-user vs all-users install, light and dark theme, high DPI |
| Failure paths | The user cancels a dialog, a transaction fails or rolls back, a script errors halfway |

Each row should say how to reach the case (for example `pyrevit launch ... --language=<code>`, or a project units change) and what a pass looks like. Add the PR-review pitfalls above as a short "known traps" list per engine. When a pitfall can be linted, link the checker. When it can't, say so.

## Describe alternatives you've considered

- Keep it in `release-qualification.md` only. That reaches release testers, not authors, so bugs are found late.
- Put it in `AGENTS.md`. It is too long for conventions every agent needs, and it would duplicate the docs.
- Add more linters. That is worth doing for the parts that can be checked statically (Python 2 division, missing coding line, `ElementId(int)`), but the units, locale and document-state cases need a person or a live test.
