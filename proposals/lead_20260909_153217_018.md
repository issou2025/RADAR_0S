*Project description:*
## Summary

In `ai-incident-response-playbook-builder`, SSM Automation document generation silently produces **nothing** while reporting success. Observed live during an end-to-end deploy test: with `--output-format both`, **12 playbooks were generated but 0 SSM documents**. The run logged retry/failure warnings but completed "successfully" and uploaded only the playbooks.

This is **runtime (generation) behavior, not a deployment issue**, and it lives in the cross-platform Python (`src/generator.py`) — so it affects **both** the bash and PowerShell entry points equally. There is no PowerShell-specific fix; fixing `generator.py` fixes both platforms.

Pre-existing and unrelated to the model-id fix (#124): the model **invoke succeeds**; the failure is in parsing an empty/unparseable SSM response afterward.

## Where

`security/ai-incident-response-playbook-builder/src/generator.py`

- `generate_ssm_document()` retries `max_retries` times, then re-raises:
  ```python
  for attempt in range(max_retries + 1):
      try:
          response_text = invoke_bedrock(bedrock, model_id, prompt)
          return extract_json(response_text)
      except (json.JSONDecodeError, KeyError) as e:
          last_error = e
          if attempt < max_retries:
              print("    ⚠ SSM JSON parse failed (attempt ...), retrying...")
  raise last_error
  ```
- The caller in `main()` swallows the re-raised error:
  ```python
  except (json.JSONDecodeError, KeyError, Exception) as e:
      print(f"    ⚠ SSM document generation failed for {name}: {e}")
  ```

## Observed failure

Every SSM attempt failed with:
```
No valid JSON found in response: line 1 column 1 (char 0)
```
i.e. `extract_json()` received an empty or non-JSON string. The markdown playbook calls (a different prompt) all succeeded in the same run, so this is specific to the SSM prompt/response — not the model, region, or credentials.

## Two distinct problems

**A. SSM generation is actually failing (the real bug).** Likely prompt-shaped: `SSM_PROMPT` asks the model to "Return ONLY valid JSON for the SSM Automation document" (a full schemaVersion 0.3 Automation doc). The model appears to return an empty completion / refusal / prose / prose-wrapped JSON that `extract_json` can't recover, consistently enough that ALL docs failed. Root cause is not yet confirmed because the raw response is discarded on failure.

**B. A broad `except (..., Exception)` hides it.** Catching `Exception` (which already subsumes `json.JSONDecodeError` and `KeyError`) makes the failure non-fatal and nearly invisible: a user requesting `--output-format both` or `ssm` silently receives only half (or none) of the expected output, with a success-looking exit.

## Severity

Medium. Not a crash, and the primary output (playbooks) works — but a documented output format (`ssm` / `both`) silently produces nothing, and the broad catch keeps future failures here hidden too.

## Suggested direction (investigate, then fix)

1. **Diagnose first.** On SSM failure, log/persist the raw `response_text` plus the response `stop_reason` and token usage. This confirms the real failure mode (empty body? refusal? truncation at `max_tokens=4096`? prose-wrapped JSON?) instead of inferring "empty".
2. **Likely prompt/formatting fix.** Based on the diagnosis: strengthen the "JSON only, no prose" constraint, and/or raise/segment output if truncation is the cause, and/or make `extract_json` more tolerant of prose-wrapped JSON.
3. **Stop hiding it.** Narrow `except (json.JSONDecodeError, KeyError, Exception)` to the specific exceptions, and print an end-of-run summary (e.g. "N of M SSM documents failed") rather than only per-item warnings that scroll by — so partial failure is visible even if kept non-fatal by design.

## Acceptance criteria

- Running with `--output-format both` on a typical account produces SSM documents (not zero), OR failures are clearly surfaced in an end-of-run summary with enough diagnostic detail to act on.
- The catch no longer swallows unexpected exceptions via a bare `Exception`.
- Fix is in `generator.py` (cross-platform); no separate PowerShell change needed.
