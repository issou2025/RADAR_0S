# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[2.x] A4: iOS client for the 2.x server (Star printers, dedicated devices)**

*Project description:*
Related: epic #21 (Wubiq 3), #31 (M6 mobile agents), #20 (language comparison).

## Why
Users run Wubiq on Android devices dedicated only to printing, and they ask for an iOS version. Wubiq 3 (#31) already plans an iOS agent, but that is a long way off. This issue covers an **iOS client for the current 2.x server**, so iOS users can be served now.

## Feasibility (summary)
**The 2.x mobile client is thin**, so the port is feasible:
- The Android app (`BluetoothPrintManager` on top of `AbstractLocalPrintManager`, about 1,000 lines) talks to the server with plain HTTP commands and text parameters:
  `REGISTER_COMPUTER_NAME`, `REGISTER_MOBILE_PRINT_SERVICE`, `PENDING_JOBS`, `READ_PRINT_REQUEST_ATTRIBUTES`, `READ_PRINT_JOB`, `CLOSE_PRINT_JOB`.
- The **server** converts each page into the printer's command bytes (`MobileDevices` → `IMAGE_TO_ESCAPED`), and the client just writes those bytes to the printer.
- **No server changes are expected.**

**Apple platform constraints:**
1. **Bluetooth Classic requires MFi.** iOS has no generic SPP access. Classic-Bluetooth printers are reachable only through the External Accessory framework (iAP2):
   - The printer must be in **"Bluetooth (iAP)"** mode. Android needs **SPP**, so each printer is configured for one platform.
   - The app must declare the printer's protocol strings, and for App Store distribution the **manufacturer (Star) must submit the app to Apple for MFi approval**.
   - BLE and LAN printers don't need MFi.
2. **No background polling service.** iOS suspends apps in the background. Target model: a **dedicated device** with the app on screen, the screen kept awake (`isIdleTimerDisabled`), and **Guided Access** or MDM single-app mode locking the device to Wubiq. That matches how users run Android today.
3. **Distribution:** an Apple Developer account and Xcode on a Mac. Options: the App Store (review plus MFi), TestFlight for testers, or Apple Business Manager custom apps for fleets.

## Scope
- [ ] **Spike, first and decisive:** from an iPhone, print one job from the existing 2.x server to an SM-T300i in iAP mode using StarXpand (StarIO10). Confirm the External Accessory connection and the byte output (ESC/POS raster).
- [ ] **Spike: one printer for both platforms.** Confirmed: the SM-T300i in iAP mode does **not** work with Android (no SPP service: `find_rfc_slot_by_id unable to find RFCOMM slot`, see #22), so it serves one platform only. Test Star models that could serve iOS **and** Android without a mode switch, using the same app builds:
  - **BLE printers:** no MFi on iOS; StarXpand supports BLE on both platforms.
  - **Dual-mode Bluetooth (iAP + SPP at the same time):** check Star spec sheets for iOS + Android support with no mode setting.
  - **LAN/Wi-Fi printers.**
  Outcome: a recommended model list for mixed fleets, and printer setup documentation per model.
- [ ] **Decide the technology with v3 in mind** (see #20): native Swift, or Flutter if #20 favors Flutter for mobile. Then reuse it in #31.
- [ ] **Protocol layer:** port the 2.x HTTP conversation (register, poll, read job, close job) into a single module, so it can be replaced by the v3 protocol later.
- [ ] **Printing:** Star printers through StarXpand (MFi Bluetooth, BLE, LAN), using the same device definitions the server already knows (`Star Micronics 2/3/4 in`).
- [ ] **UI**, matching the refreshed Android screens: server configuration, printer and driver selection, advanced settings, start/stop, status.
- [ ] **Kiosk operation:** keep the screen awake, document the Guided Access / MDM setup, and automatically reconnect to the server and the printer.
- [ ] **MFi:** request Star's MFi submission for the Wubiq bundle ID, and add the protocol strings to `Info.plist`.
- [ ] **Distribution:** TestFlight for advanced testers, then the App Store or Apple Business Manager.
- [ ] **Documentation:** printer setup per platform (iOS: iAP mode; Android: SPP mode, ESC/POS emulation).

## Out of scope
- Background printing while the app isn't on screen (not possible on iOS for this use).
- Zebra and other brands. Zebra's iOS SDK also requires MFi; add them later if needed.
- Wubiq 3 features (submit role, AirPrint, share extension). Those stay in #31 / #32.

## Risks
- **Time for MFi approval through Star**, which blocks App Store release. TestFlight testing can start earlier.
- **Throwaway work when v3 arrives**, limited by isolating the protocol layer and choosing the technology with #20.
- **Mixed fleets:** a printer set to iAP won't work with Android devices, and one set to SPP won't work with iOS. Mitigation: the dual-platform printer spike above.
