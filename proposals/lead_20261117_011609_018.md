# WhatsApp Flows: forms in templates, with responses mapped to documents

## Problem Statement

A business that uses this app can send a customer only text, media, buttons, lists and templates. To collect structured information, such as a rating after a deal closes, a lead's company and budget, or a consent, an agent must ask questions one by one in the chat and copy the answers into the record by hand. The answers come back as free text, in any order, and nothing in the system knows they belong to a field.

WhatsApp Flows solve this on Meta's side: a business sends a form that opens inside WhatsApp, and the customer fills in screens of inputs. The app cannot use them today:

- A template that has a Flow button is synced with an empty button type, and the Flow ID is lost.
- A completed Flow comes back on the `messages` webhook as an `nfm_reply`. The app reads only button and list replies, so it saves an empty Message and the customer's answers are lost.
- There is no way to say which Flow a template opens, what data the form starts with, or what to do with the answers.

The obvious workaround is to ask users for their own endpoint URL and let them process the answers. That excludes every site whose plan does not allow Server Scripts, and it asks business users to write code to get a feedback form.

## Solution

A template author adds a **Flow button** to a WA Template, in the same template form they use today. On that button they choose:

- **the Flow** it opens, from the Flows synced from their WhatsApp account;
- **the screen** it opens on, and an **icon**;
- **Flow inputs**: the data the form starts with, filled from fields of the template's reference document (for example the customer's name, already typed in);
- **Response actions**: what happens when the customer submits. Either update the reference document, or create a new document (for example a Customer Feedback record linked to the Deal). Each action maps the form's answers to fields, and can have a condition so that different outcomes do different things.

When a customer submits, the app:

1. receives the answers on the webhook it already has, with no endpoint and no code;
2. stores them on the incoming Message and shows them in the conversation as labelled answers, with sensitive fields masked;
3. ties the response to the Message that sent the form, so it lands on the same reference document;
4. runs the template's Response actions;
5. fires the standard events, so Notifications, the core Webhook DocType, app hooks and Server Scripts can all react. Server Scripts are possible but never required.

Flows are built in Meta's Flow Builder. The app syncs them, shows their status and a preview link, and can push edited Flow JSON, publish and deprecate them from Desk. It does not try to be a form builder.

The app does not limit what Flows can do. Any Flow content works, including several outcomes, uploads, Flows that call the business's own endpoint, and prefilled first screens.

## Glossary

These terms extend the vocabulary in the shared UI's CONTEXT.md (Message, Bubble, Direction, Template, Host, Controller, Part, Chrome) and are used throughout:

- **Flow**: one `WA Flow` document, a form defined on Meta and synced here. Referenced by Meta's Flow ID.
- **Flow button**: a template button of type Flow. It names a Flow, an entry screen and an icon, and owns that button's Flow inputs and Response actions.
- **Flow outline**: what the app reads out of a Flow's JSON when it syncs it. It holds the screens, the entry screens with their declared data, the keys each `complete` action sends with the label and component type of each, and the sensitive keys. It is derived and never edited.
- **Flow inputs**: the data a Flow button sends for the first screen (`flow_action_data`), each value resolved from a field of the reference document.
- **Flow response**: the answers a customer submitted, stored on the incoming Message that carried them.
- **Response action**: one thing a Flow button does with a Flow response. It updates the reference document or creates a document, under an optional condition, through a field map.
- **Flow token**: the random identifier the app puts on every Flow send. It comes back with the response and is how a response is matched to its send.

## Implementation Decisions

### Gate: verify the Flow button contract against Meta first

Meta's documentation contradicts itself or is silent on parts of the Flow button contract. Build nothing that depends on these points until a live probe against a test WhatsApp Business Account has answered them. The probe creates Flow-button templates in each variant, reads them back, sends them in each variant, and completes them on Android and iOS while capturing the raw webhooks. Its results are recorded on this issue.

| Question | Docs say | Open because |
|---|---|---|
| `sub_type` on send | `"flow"` | the main open-source SDK (pywa) sends `"FLOW"` |
| `index` on send | `"0"` (string) | pywa sends an integer |
| Can the button component be omitted on send? | silent | only its fields are marked optional (`flow_token` defaults to `"unused"`) |
| `navigate_screen` | "required for navigate" and also "optional, defaults to the first entry screen" | contradictory |
| `icon` values | changelog only | pywa uses `DOCUMENT`, `PROMOTION`, `REVIEW`; absent from Meta's API reference |
| Categories allowed with a Flow button | examples use MARKETING only | UTILITY matters for feedback |
| Can a template reference a draft Flow? | silent | |
| How many Flow buttons per template, and in which combinations? | changelog says Flow plus other buttons is allowed | no limits documented |
| Does `GET` on templates return `flow_id`, `navigate_screen`, `icon`? | silent | sync depends on it |
| Is `flow_token` always inside `response_json`? | the `complete` action docs say yes | pywa logs a known iOS case where it is missing |
| Is `context.id` the wamid of the template message? | "message_id of flows request message" | not stated for templates |

### WA Flow (new DocType)

- One document per Flow per account, named by Meta's Flow ID. Fields: Flow ID, name, account, status (Draft, Published, Throttled, Blocked, Deprecated, mirrored from Meta), categories, Flow JSON version, endpoint URI (read-only, informational), Flow JSON, validation errors, preview URL with its expiry, and the Flow outline.
- Flows are synced, not authored here. The daily scheduler sync, the on-demand per-account sync and the `flows` webhook all update it through one sync path.
- Desk only: a code editor for the Flow JSON that uploads through the Flows assets endpoint and stores Meta's line-numbered validation errors, plus Publish and Deprecate actions. A published Flow that is edited goes back to Draft on Meta, and the status follows it.
- A Flow that Meta cloned to a new ID becomes a new WA Flow. Templates keep the Flow they were created with, as Meta does.
- Deleting a WA Flow that a template button links to is refused, as for every link.

### Flow outline

- One parser reads Flow JSON and produces the outline. Everything else (template validation, the mapping pickers, sensitive masking, answer labels) reads the outline and never parses Flow JSON itself.
- Entry screens are screens that no `navigate` action names as `next`. Each has its declared `data` keys and types (taken from `__example__`).
- Answer keys are the union of payload keys across every `complete` action. Each key carries the label and component type of the input that feeds it (followed through `${form.x}` and `${screen.S.form.x}`), so the UI can label answers and the mapping can check types. A key with no traceable input (a constant, such as an outcome name) is still listed, with type unknown.
- Sensitive keys are those in any screen's `sensitive` list, plus every password and passcode input.
- The outline is stored on the WA Flow when it syncs, so reading it costs no parse.

### Graph client

- The client gains the Flow calls the sync and the Desk actions need, and nothing more: list Flows for a business account, get one Flow (with preview and health status), list its assets and download the Flow JSON, upload Flow JSON, publish, and deprecate.
- Sending reuses the existing send-message call. Flow payloads are built by new builders next to the existing template and interactive builders.

### Webhook

- Dispatch gains the `flows` field. Status changes and creation events update the WA Flow's status. Endpoint and client health alerts and version-expiry warnings are logged to WA Log and fire a Notification event. Error-type names are normalised to one case, because Meta's samples and reference disagree.
- The incoming-message parser handles `interactive.type == "nfm_reply"`. It parses `response_json` into the Flow response, removes `flow_token` from it, and sets all Flow fields on the Message before submit (see Matching).
- The existing setup check for webhook subscription also reports whether the `flows` field is subscribed.

### WA Message (schema additions)

- Outgoing: `flow_token` (random, unique), `flow` (Link WA Flow), and for interactive sends the CTA text, the screen and the Flow input data.
- Incoming: `flow_response` (JSON), `flow` and `flow_template` (Link WA Template, the template whose button opened the Flow). The existing `reply_to_message` points at the send.
- `whatsapp_template` and `is_template` keep meaning "this Message was sent as a template". A Flow response is never marked as a template.

### Matching a response to its send

- First by `flow_token`, then by `context.id` against the outgoing Message's `message_id`. The second path is required from the start because of the iOS case.
- A matched response inherits the send's `flow`, `flow_template`, reference DocType and reference document, and its `reply_to_message` points at the send. Because the reference is already set, Append Actions leave it alone.
- An unmatched response is stored and shown, with `flow` left empty, and goes through Append Actions like any incoming Message. It runs no Response actions.
- Responses are not limited in number or age. Each is its own Message.

### WA Template Button (schema additions)

- `button_type` gains `Flow`. A Flow button row has: `flow` (Link WA Flow), `flow_screen`, `flow_icon`, `flow_action` (navigate by default; data_exchange allowed for Flows that call the business's own endpoint), `flow_inputs` (JSON), and `flow_response_actions` (JSON).
- Inputs and actions are JSON on the button row, not child tables. Frappe has no child tables inside child tables, and a separate table keyed by button position would break when buttons are reordered. The row owns its own configuration.
- The JSON shapes are fixed and validated on save:

```text
flow_inputs:            [{ key, source_field }]
flow_response_actions:  [{ action: "Update Reference" | "Create Document",
                           doctype,            # Create Document only
                           condition,          # optional Python expression
                           fields: [{ source, target_field }] }]
source:                 an answer key or dotted path from the outline
                        | one of: sender_phone, sender_name, reference_doctype,
                          reference_name, received_at, whole_response
```

- Template create builds the Meta button from the row (`FLOW`, text, `flow_id`, `flow_action`, `navigate_screen`, `icon`), with the field choices fixed by the probe.
- Template sync maps Meta's `FLOW` to `Flow` and links the WA Flow by ID. If that Flow has not been synced yet, it syncs that one Flow. Inputs and actions are local configuration, so sync never overwrites them.

### Template validation (on save)

- The Flow is synced and not Deprecated. The screen is an entry screen of the outline.
- Each input key is declared by the entry screen, and its source field exists on the reference DocType with a compatible type.
- Each target field exists on the target DocType (the reference DocType for Update Reference) with a type that can hold its source. Field checks reuse the Append Actions mapped-field validation and field-options picker, generalised from fixed slots to any source.
- Update Reference requires the template to have a reference DocType. Create Document rejects child-table and single DocTypes, as Append Actions do.
- A source key missing from the current outline is a warning, not an error, because older Flow versions still answer.
- The button label is limited to 25 characters.

### Sending

- Template sends add one button component per Flow button. It carries a new Flow token and the Flow inputs resolved from the reference document, in the same pass that resolves `{{variables}}`. The token is stored on the outgoing Message.
- A blocked Flow fails the send with a readable message (Meta error 132068). A throttled Flow (132069, ten sends an hour) fails the same way. Both become a Failed Message with the reason, as other send failures do.
- A new whitelisted `send_flow` method sends an interactive Flow message, guarded like `send_template` (host access guard, permission to read the reference). It accepts the Flow, recipient, CTA text, screen, input data and a draft mode for testing. It has no UI.

### Response actions

- They run in the incoming Message's `on_submit`, before Notifications, Webhooks and Server Scripts, which Frappe runs after the controller method. The existing Append Actions call happens after submit returns; the Flow path must not copy that ordering.
- Actions run in the order configured, each independently. A condition is evaluated with Frappe's safe evaluator against `response`, `doc` (the reference document) and `message`.
- Missing keys are skipped, never written as empty. Values are converted by target field type: Check from a boolean, Date from `YYYY-MM-DD`, Int and Float from numbers, Table MultiSelect from an array, text fields from an array joined by commas, JSON and Code from the whole response, Attach from an uploaded file.
- Writes run as the system with `ignore_permissions`, and each action logs its result to WA Log against the Message. A failing action is logged and skipped. The Flow response is never rolled back.
- Uploaded photos and documents arrive as media IDs. They are downloaded through the media endpoint and attached as Files to the target document. This depends on the open "media download on webhook" work. Until that lands, the IDs are stored and an Attach mapping is skipped with a logged warning.

### Conversation API and shared UI (`@whatsapp/ui`)

- `get_messages` returns, for a Flow send, the Flow's name and CTA. For a Flow response it returns the answers as an ordered list of label and value pairs, labelled from the outline, with sensitive values masked on the server. A Bubble never receives a masked value and never parses `response_json`.

```text
flow_answers: [{ key, label, value, masked: bool }]
```

- **MessageBubble** draws a Flow send as its body plus a disabled-looking CTA row with the Flow icon. It draws a Flow response as plain label and value lines on the Bubble's own surface: no nested card, no borders, with the Quote of the send above it. Labels use secondary ink and values primary ink. A masked value shows as a row of dots with no reveal. Labels sit in a fixed-width lane, so values line up across rows.
- **TemplateContent and TemplateButtons** draw a Flow button like other buttons, with its icon.
- **TemplateForm**: the button grid accepts type Flow. Choosing it opens the row's detail with three short groups, in this order:
  1. Flow, screen and icon.
  2. Flow inputs: one line per declared key, key on the left, field picker on the right. Shown only when the entry screen declares data.
  3. Response actions: a list where each action shows its kind and target in one line and expands to its field map.

  Pickers are filled from the outline and the target DocType's fields. Nobody types a key. The form's one primary action stays Save. Flow status is a small badge beside the Flow picker, and colour is used only for that badge.
- A new Part, **FlowButtonEditor**, holds that detail. It draws content, not its container, as CONTEXT.md requires for Parts, so the Host decides whether it sits in a grid row's detail, a dialog or a side panel. All user-facing strings are Chrome props with English defaults.
- The template controller exposes the selected Flow's outline and the reference and target field options. Nothing else in the UI fetches.
- CONTEXT.md gains the glossary terms above. A Flow is not a Render kind, because Render kind is derived from MIME type alone.

### Code shape

- New behaviour goes in new, single-purpose modules, not in the existing large ones. Flow sync, the outline parser, response matching and the Response action runner each get their own module. Each file stays under about 300 lines, with public entry points at the top and helpers below.
- The outline, the Flow response and a Response action are small classes, each with one job. No base class or registry until a second concrete use exists.
- Comments only for facts the code can't show: Meta's quirks (the iOS missing token, the case mismatch in error names) and the ordering constraint in `on_submit`. Nothing that restates code.

### CRM (Host)

- The CRM `validate` hook on WA Message must keep a reference that is already set on incoming Messages, as it already does for outgoing ones. Otherwise its phone lookup moves a Flow response off the Deal that sent the form.
- The template selector in the record's WhatsApp tab lists Flow templates like any other; it needs no change beyond rendering the Flow button.
- CRM automation can add a "Flow completed" trigger by checking `flow_response` in its existing WA Message `on_update` handler. This is optional and separate from this work.

## Testing Decisions

- **One seam.** The backend is driven through its public entry points: the webhook handler, `send_template`, `send_flow`, WA Template save and sync, and WA Flow sync. Only the WhatsApp Graph client class is mocked, as the existing webhook and template tests already do. Assertions are on the payload handed to the client and on the documents that exist afterwards: Messages, Flows, templates, updated and created records, and WA Log entries.
- **A good test** states behaviour a user would notice. For example: "a response to a Flow sent from a Deal updates that Deal and is attached to it", or "a response without a flow token is still matched by its context". Tests never assert on private helpers or on how the outline is stored.
- **Modules covered:**
  - Flow sync: status mapping, outline produced from real Flow JSON samples (several terminal screens, nested expressions, pickers, sensitive keys), and cloned Flows.
  - Template create and sync with Flow buttons: payload shape as settled by the probe, and Meta Flow buttons round-tripping without loss.
  - Template validation: entry screen, input types, target field types, stale keys as a warning.
  - Send: button component with token and resolved inputs, blocked and throttled failures recorded on the Message.
  - Webhook: `nfm_reply` parsed, matched by token, by context and unmatched; reference inherited; Flow fields set before submit.
  - Response actions: update, create, conditions, skipped missing keys, type conversion, isolated failures, and the ordering that lets a Server Script see the result.
  - `get_messages`: labelled and masked answers.
  - The `flows` webhook field: status change, alerts, expiry warning.
- **Fixtures** are trimmed copies of real Meta payloads captured by the probe, not hand-written guesses.
- **Prior art:** the webhook handler tests (incoming messages, statuses, template status updates, read receipts, reactions), the WA Template tests for create and sync payloads, the WA Account tests for append-action field validation, and the conversation API tests for `get_messages` with access guards.
- **UI** is verified through Storybook stories in `ui-dev`, using realistic content (a deal-feedback Flow with a 1–5 rating, a comment and a follow-up date, and a lead-qualification Flow with a masked passcode). Stories cover TemplateForm with a Flow button, FlowButtonEditor empty and filled, and MessageBubble for a Flow send, a response, a masked response, and a response to an unknown send. @whatsapp/ui has no unit-test runner, and this work does not add one.

## Out of Scope

- **Hosting a Flow data endpoint** (data exchange: request decryption, key generation and registration per phone number, health pings, the 421, 427 and 432 responses). Flows that use the business's own endpoint are supported; serving one from this app is a later phase.
- **A visual Flow builder** in this app. Meta's Flow Builder remains the editor. This app syncs, previews, edits raw JSON, publishes and deprecates.
- **Response actions for interactive Flow sends.** Their responses are stored and shown only. Nothing in the design prevents adding actions later.
- **Prefilling list or object inputs** (for example Dropdown options built from a child table). Scalar inputs only. The input shape leaves room for it.
- **The Flows Metrics API.** Meta deprecated it on 30 April 2026. Health comes from the `flows` webhook instead.
- **A "Flow completed" trigger in CRM automation.** It can follow separately.
- **An endpoint URL field** for users to receive answers. The core Webhook DocType covers external delivery.

## Further Notes

- **Business verification.** Meta requires a verified business with high message quality to send Flows. A send refused for that reason must surface Meta's message on the Failed Message, not a generic error.
- **Reading responses in Server Scripts.** After Submit on WA Message runs as Guest, because the webhook request has no session. Scripts that write other documents need `ignore_permissions`. The feature's documentation must say so; the webhook is not switched to run as Administrator.
- **Version freezes.** Meta freezes old Flow JSON versions (5.0 and earlier are frozen). The stored JSON version and the expiry-warning event make this visible. The app does not migrate Flow JSON.
- **Published Flow edits.** Meta's documentation conflicts on whether a published Flow can be edited or must be cloned. Sync treats both as normal: an edit changes status, and a clone produces a new Flow.
- **Sources.** Meta's Flows documentation under developers.facebook.com: business-messaging/whatsapp/flows (guides: flowjson, components, sendingaflow, flows-templates, receiveflowresponse, flowswebhooks, lifecycle, flowsapi, versioning, bestpractices; reference: error-codes) and the Flows changelog. Cross-checked against the pywa SDK.
