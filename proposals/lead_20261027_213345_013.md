# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[RESEARCH-ONLY][TOOL-EVAL] Measure diagnostic speedup for IDM, Notepad++ x64, and WinRAR without changing MiniWin**

*Project description:*
# Objective: Evidence-only evaluation of external diagnostic tools for IDM, Notepad++ x64, and WinRAR — no MiniWin implementation changes

## 1. Mission

Conduct a rigorous, reproducible, Linux-agent-compatible experiment to determine whether existing open-source tools, upstream source code, conformance tests, binary-analysis utilities, filtered runtime traces, and automated test techniques can substantially reduce the time required to understand and diagnose MiniWin compatibility failures for exactly these three target applications:

1. Internet Download Manager (IDM), using the existing pinned corpus version.
2. Notepad++ x64, using the existing pinned portable version and, where useful, its existing installer target.
3. WinRAR x64, using the existing pinned installer and installed payload where available.

This is an **investigation and measurement issue only**.

The objective is to discover whether these techniques produce a measurable practical advantage over our current workflow. We want evidence that could justify adopting some techniques later—not a proposal to change the project architecture now.

The experiment must answer these questions:

- Do the existing and candidate tools reveal information that MiniWin's current scripts and traces do not already reveal?
- Can they identify a real, reproducible failure earlier?
- Can they distinguish the first root cause from downstream crashes?
- Can they determine whether a problem is in the PE loader, delay-import resolver, API contract, process creation, installer, GUI lifecycle, filesystem, registry, or input simulation?
- Can they reduce trace sizes without losing the evidence required to diagnose a problem?
- Can existing Wine/ReactOS source and tests replace hours of manual investigation with a small, targeted conformance test?
- Can any tool be used effectively in our actual Linux, preferably unprivileged, agent environment?
- How much time does every approach actually save or cost?
- Are any promising suggestions false positives, irrelevant, Windows-only, too costly, or already covered by existing MiniWin functionality?

**Final deliverable:** a detailed evidence report posted as a comment on this same GitHub Issue. It must answer each investigation item individually, including negative and blocked results. Do not implement the proposed tools or fixes during this experiment.

## 2. Non-negotiable scope and safety rules

### 2.1 No product or architecture changes

Do not:

- Refactor `src/loader/loader.c` or any other runtime source.
- Change the MiniWin execution backend or the intended project architecture.
- Integrate Wine or ReactOS as MiniWin's product execution backend.
- Add Wine, ReactOS, Ghidra, LIEF, or any other external framework to the MiniWin runtime.
- Implement or modify Win32 APIs to make these applications work.
- Add capability packs, application-specific workarounds, compatibility shims, or new permanent execution paths.
- Change the existing test criteria merely to make a target pass.
- Modify `plugins/*.tsv`, `plugins/status.tsv`, `tests/corpus/manifest.tsv`, loader code, runtime code, or existing experiment records.
- Change project dependencies, build configuration, or tracked documentation.
- Create follow-up Issues, child Issues, pull requests, or commits as part of this investigation.

Wine is permitted only as an external reference implementation and tracing environment. ReactOS and both projects' source code are reference material. They are not proposed as runtime dependencies for MiniWin.

### 2.2 Permitted operations

You may inspect source code and existing evidence, run current tests, execute the three targets under the existing MiniWin harness, and install or use small diagnostic tools in an isolated user-space environment when necessary.

Temporary scripts and downloaded tools must live under `/tmp` or the existing ignored cache directories. Do not add generated programs, installers, archives, downloaded source trees, raw traces, screenshots, or other test artifacts to tracked Git files.

Use existing tools first. Do not install a large toolchain merely because it exists. Before downloading a tool, establish which specific unanswered question it is supposed to answer.

No paid APIs, paid services, external cloud VMs, administrator/root access, or new hosted infrastructure are required. Do not assume access to a Windows host.

### 2.3 Safe handling of application binaries

Use the exact versions and SHA-256 pins in the existing corpus unless there is a specific reason to compare another version. Do not silently substitute an installer, a different architecture, or a file from an unofficial mirror.

Do not execute an artifact if its hash is unverified. Keep installer runs in the existing isolated MiniWin sandbox workflow. Use a separate disposable Wine prefix if Wine reference runs are possible.

Do not use real IDM accounts, passwords, tokens, private download URLs, or user data. If testing IDM downloading becomes possible, use a small file served from a local loopback HTTP server rather than downloading arbitrary Internet content.

Retain large raw evidence locally only as necessary. In the final Issue comment, provide concise excerpts, exact commands, hashes, file paths, tool versions, and summary metrics. Never claim success merely because a process returned zero, a single screenshot exists, or an executable was parsed successfully.

## 6. Static PE analysis experiment matrix

The aim is to determine whether multiple independently implemented tools reveal new, reliable information about our real target binaries.

For all three applications, perform the following investigations wherever the appropriate files are present and hash-verified.

### S01 — Architecture and PE header agreement

Compare `guest_profile.py`, `file`, and at least one independent parser.

Record:

- PE32 versus PE32+.
- Machine type.
- Optional-header details.
- Subsystem.
- Entry-point RVA.
- Image base.
- Section count and section table.
- Parsing errors or inconsistent interpretations.

Does independent agreement increase confidence? Does any parser discover a real disagreement that affects MiniWin diagnosis?

### S02 — Normal imports

Extract each imported DLL and symbol name.

Compare the output of:

- Existing `guest_profile.py`.
- `pefile`, if available.
- LIEF, if available.
- `llvm-readobj --coff-imports`, if available.
- GNU `objdump -p`, where its output is adequate.

Report counts of DLLs, named imports, ordinal imports, missing symbol names, malformed entries, and disagreements.

Do not treat the mere existence of an imported API as evidence that the application actually calls it during the tested scenario.

### S03 — Delay-load imports and `.didat`

Explicitly test whether available tools correctly enumerate delay-load descriptors, associated DLLs, symbols, INT/IAT information where available, and the relationship to relevant PE sections.

Pay particular attention to WinRAR because an earlier experiment recorded a delay-import/self-resolver frontier. Verify whether the current binary actually has the structure under investigation.

Use LIEF's delay-import functionality and any working independent parser or LLVM utility. Record limitations if a tool cannot display this information.

Answer: which tool offers the clearest evidence with the least manual work?

### S04 — Sections, relocation, TLS, resources, and load configuration

Test whether parser outputs expose section boundaries and the structures needed to investigate loader failures.

Inspect, when supported:

- Relocation directory.
- TLS directory and callbacks.
- Resource directory.
- Debug directory.
- Load configuration.
- Exception/unwind metadata.
- Relevant PE flags and section permissions.

Do not investigate a feature that the binary does not use without identifying a concrete reason.

### S05 — Embedded strings and runtime clues

Use `strings` and available binary utilities to look for useful indicators such as:

- DLL names and API names.
- Dynamic loading references.
- Installation path strings.
- Runtime/compiler markers.
- Installer signatures.
- Managed-runtime indicators.
- Error messages or diagnostic messages.
- Relevant UI, file, registry, or process-operation strings.

Measure how much useful information this gives beyond imports and `guest_profile.py`.

String matches are clues, not proof that a code path executes.

### S06 — Compiler and runtime classification

Determine what can actually be established about native versus managed code, CRT choice, embedded runtimes, compiler families, and external runtime dependencies.

Use the PE CLR directory/metadata where relevant. Only invoke .NET-specific tools if a target is genuinely managed or a concrete dependency requires them.

Do not infer that an application is C#, VB.NET, VB6, or native C++ solely from its user-interface appearance or a generic DLL import.

### S07 — Dynamic resolution and import-table anomalies

Search for indications of:

- `LoadLibrary`/`LoadLibraryEx` use.
- `GetProcAddress` use.
- Delay-load helpers and resolver behavior.
- Import-table mutation.
- Installer-specific unpacking or custom resolving.
- Dynamically loaded DLL names that static analysis cannot resolve.

Determine which of these are supported by static evidence alone and which require runtime traces.

For WinRAR, test whether inspection of the delay-import data explains the observed resolver behavior or whether execution evidence is still required.

### S08 — Dependency graph and missing prerequisites

Build a small temporary report of direct dependencies for each target. Resolve only as far as the tools can do reliably.

Compare the information from `guest_profile.py` against the independent parsers.

Differentiate:

- Imports actually present in the file.
- Direct dependency files found in the package.
- APIs MiniWin claims to provide.
- Runtime-loaded modules observed in execution.
- Dependencies that remain unknown.
- Dependencies that may simply never be exercised.

Avoid unbounded recursive analysis and large dependency dumps. Keep the report small, structured, and reproducible.

### S09 — Installer versus installed payload comparison

Where both artifacts exist, analyze the installer and installed executable separately.

For each application, determine which dependencies and clues belong to the installer, which belong to the installed program, and which appear only in unpacked or generated payloads.

Use the existing sandbox and `install_contract.py` where possible.

This test must prevent us from mistakenly treating a successful installer launch as a successful launch of the application itself.

### S10 — Parser speed and correctness benchmark

For each viable parser or tool, measure:

- Execution time.
- Peak memory if easy to collect.
- Output size.
- Number of useful fields recovered.
- Parser errors.
- Agreement with the other independent parsers.
- Manual intervention required.

Use the same exact binary hash for comparable runs.

A tool that produces a larger report is not automatically better. It must either answer an additional useful question or make an existing question measurably faster to answer.

### T06 — Relay include/exclude filtering

Inspect the current Wine source and test the relay filtering mechanism in an isolated, disposable prefix.

The source contains handling for registry values under `HKCU\Software\Wine\Debug`, including:

- `RelayInclude`
- `RelayExclude`
- `RelayFromInclude`
- `RelayFromExclude`

Determine the exact accepted value formats from the installed source/version and use an appropriately isolated prefix.

Test at least:

1. Unfiltered trace.
2. A narrow inclusion filter around a small, relevant set of functions.
3. An exclusion filter that removes high-volume irrelevant activity.
4. A caller-module filter, where supported.
5. A combined-filter experiment if it adds value.

Do not modify the user's normal Wine prefix or assume all relay events come from the target process.

Record output bytes, line counts, useful target-relevant events, relevant-call retention, and whether filtered traces actually reduce diagnostic time.

If a filter cannot be configured or does not retain the required events, say so and provide the observed evidence.

### T07 — First-divergence identification

For each executable that reaches a meaningful execution point, attempt to identify the earliest failure that can be proven from the available trace.

Separate:

- First observed error.
- First unsupported or unresolved API, if explicitly reported.
- First invalid state transition.
- First crash or exception.
- Last known successful operation.
- Subsequent errors likely caused by the initial failure.

Do not equate the final crash location with the original root cause.

### T08 — Trace parsing quality

Inspect the existing parser, if available, for call/return pairing, thread ID reuse, nested calls, multiline arguments, module-load events, and unusual return formats.

Create small temporary parser tests using real observed log samples or existing fixtures. Do not modify the tracked parser.

Answer whether parser inaccuracies can change a conclusion about IDM, Notepad++, or WinRAR.

### T09 — System-level tracing with `strace`

If `strace` is available and permitted, test a bounded invocation that observes selected process, file, or network system calls from the reference execution.

Use it only to answer questions about operating-system-level activity such as child process creation, file access, or local networking.

It does not directly provide a complete Windows API trace. Do not present `strace` output as evidence that a specific Win32 API was called.

Record its incremental diagnostic value and overhead. Skip it if blocked by container restrictions.

### T10 — Trace data size and storage budget

For every trace approach, calculate:

- Raw output size.
- Parsed summary size.
- Number of lines/events.
- Unique relevant API names.
- Number of irrelevant or duplicate-heavy events identified.
- Time from beginning the run to obtaining the useful answer.

Where possible, compare the same question answered from raw and filtered traces.

The objective is a smaller, auditable evidence package, not an arbitrarily truncated log that loses the information needed to identify the root cause.

## 14. How results must be classified

Use these statuses consistently:

- `CONFIRMED_USEFUL` — new, reproducible information was obtained that materially improved the investigation.
- `PARTIALLY_USEFUL` — the tool helped, but an important limitation remains.
- `NO_NEW_INFORMATION` — the evidence was already available or the tool did not improve the result.
- `NO_GAIN` — the tool added cost or noise without a useful improvement.
- `CONTRADICTED` — the tool or hypothesis was contradicted by observed evidence.
- `BLOCKED_ENVIRONMENT` — the test could not run because of an established environment limitation.
- `NOT_APPLICABLE` — the tool or test does not apply to the actual binary or execution path.
- `NOT_TESTED` — not attempted; explain why and what evidence is still needed.

Do not turn `BLOCKED_ENVIRONMENT`, `NOT_APPLICABLE`, or `NOT_TESTED` into pass results.

## 15. Decision rubric

Score each meaningful tool or method against this rubric:

- **0 — No value:** no usable result, irrelevant, or no measurable benefit.
- **1 — Marginal:** small convenience, redundant confirmation, or weak clues requiring similar manual effort.
- **2 — Useful:** saves meaningful manual work or produces an actionable reproducible test or diagnostic result.
- **3 — Material:** demonstrably reduces investigation time, trace size, repetition count, or uncertainty by a substantial amount while retaining the evidence needed for the conclusion.

For each score, cite the exact experiment and the comparison baseline. A score is an assessment, not a substitute for the evidence.

At the end, answer all of the following directly:

1. Which methods should be considered useful for this Linux agent environment?
2. Which tools were not worth their setup or execution cost?
3. Which tools were unavailable because of genuine environment constraints?
4. Which method most reliably identified the first failure?
5. Which method produced the greatest reduction in trace volume without losing essential evidence?
6. Which method best linked a real failure to an upstream implementation or conformance test?
7. Did any tool identify information missing from our current scripts?
8. Did any tool merely repeat information that `plugin_run.sh`, `guest_profile.py`, `install_contract.py`, or the existing logs already provide?
9. Did any tool produce a false positive, misleading assumption, or unreliable result?
10. Which exact target-specific question is still unanswered after this experiment?
11. What is the measured difference in time, number of runs, or output volume for each fair A/B comparison?
12. Is there enough evidence to justify considering a later adoption of any technique, or is the current workflow already sufficient?

The final recommendation must follow the results. It may conclude that a tool is not worthwhile.
