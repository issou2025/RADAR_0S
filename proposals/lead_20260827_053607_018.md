# Objective

Make the left half of the implementation diagram work cleanly:

```text
setup.md
  ↓
CASE
  ↓
INITIALISE / RUN
```

Do not redesign PyAnsys as a new platform. Reuse the code and probes that already work, then extract reusable helpers only where real repetition proves they are needed.

# Core rule

The implementation agent should understand scientific intent from `setup.md` and use existing PyAnsys tools to carry it out.

The default should be:

```text
read setup
→ inspect parent/live state
→ make the smallest required changes
→ read back/verify
→ save case
→ initialise/run using the simplest robust mechanism
```

# 1. Audit by behaviour, not directory aesthetics

Review the current reusable modules and setup scripts.

Classify useful behaviour as:

```text
KEEP REUSABLE
EXTRACT WHEN REPEATED
THIN EXPERIMENT WORKFLOW
LEGACY ONE-OFF
PROBE/DEBUG
```

Do not rename/move modules just to create a cleaner-looking package tree.

# 2. Keep a small connection layer

Reuse/consolidate the current connection helpers so an implementation workflow can:

- connect to the requested Fluent endpoint;
- check whether the session is reachable/usable;
- inspect what is actually loaded;
- never treat server/connection ID as case identity.

No experiment logic belongs in connection code.

# 3. CASE workflow

Use the existing Fluent state-machine principle:

```text
load parent
→ inspect
→ enable/create parent dependency
→ reacquire
→ set child
→ read back
→ continue
→ save
→ reload/check critical state when needed
```

The implementation agent may use existing probes such as live settings exploration when a deep path is uncertain.

Do not invent a universal case compiler unless repeated experiments demonstrate that one is actually needed.

# 4. Reuse before abstracting

Existing helpers/scripts may remain the implementation mechanism.

When a new experiment repeats generic logic already seen in multiple scripts, move that repeated logic into `src/pyansys_fluent/`.

Rule:

> abstraction is earned by repeated working behaviour, not created in anticipation.

New experiment-specific scripts/workflows should be thin and should not reimplement generic connection, mutation, verification or save logic.

# 5. Do not require a second experiment schema

`setup.md` is the scientific authority.

Do not require `experiment.yaml`, a universal execution spec, generic compiler or broad receipt schema by default.

If a specific automation later needs machine-readable configuration, introduce the smallest config needed for that workflow and keep it derived from / consistent with `setup.md`.

# 6. Run strategy

Support the mechanisms already useful in the repository rather than enforcing one universal runner.

Choose the simplest robust method for the experiment, e.g.:

```text
direct Fluent iterate
Fluent-native journal/batch
Python-supervised blocks when the experiment genuinely requires decisions between blocks
```

The skill should decide based on experiment needs rather than a categorical prohibition or requirement.

# 7. Minimal implementation evidence

The workflow must be able to state:

- parent case/state used;
- intended controlled change;
- critical readback/verification result;
- case artifact written;
- run method and requested budget;
- whether initialization/run started/completed/failed where observable;
- checkpoint/data artifact locations when relevant.

This can be compact JSON/text/output. Do not build a general receipt framework unless downstream use proves it necessary.

# 8. Tracer-bullet execution rule

Treat this issue as direction for real implementation work, not a mandate to refactor all of PyAnsys in one pass.

Each meaningful refactor should come from either:

- the next real selected experiment exposing a painful/repeated seam; or
- clearly duplicated working behaviour already present in multiple scripts.

If a proposed abstraction cannot point to a concrete repeated use, leave the current working code alone.

# 9. Tests

Add small tests only around reusable code that is actually introduced/refactored, such as:

- path/config parsing;
- scoped state comparison;
- artifact naming/provenance;
- checkpoint validation;
- server-ID-not-case-identity regression.

Live Fluent verification can remain integration/manual where required.

# Acceptance criteria

- [ ] A selected `setup.md` can be implemented without creating another campaign monolith by default.
- [ ] Existing reusable connection/state helpers are reused or simplified rather than replaced wholesale.
- [ ] Deep Fluent changes follow inspect → mutate → reacquire → readback.
- [ ] New reusable abstractions come from repeated working code.
- [ ] No mandatory universal `experiment.yaml`/compiler/receipt framework was introduced.
- [ ] The implementation workflow can reliably produce a verified case and start/run it using an appropriate mechanism.
- [ ] Project conclusions remain outside PyAnsys.
- [ ] No broad refactor was performed without a real experiment or demonstrated repetition motivating it.
