# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Spec: error-as-data streams (ResultStream)**

*Project description:*
Consolidates the [Wayfinder: error-as-data streams](https://github.com/JakesMD/mallard/issues/1) map and its resolved tickets (#2–#16, #18).

## Problem Statement

Mallard lets one-shot async work report failures as data: a `Task` runs and gives back a single `Result`, so the code stays on the success track or the failure track and never has to catch anything. Much of a real app is not one-shot, though. Firestore snapshots, auth state, location feeds and websocket messages are all streams, and mallard has nothing for them.

So developers are back to raw Dart streams. Errors come through as untyped stream error events. A `throw` inside an `async*` generator ends the stream for good. An `await for` rethrows and cancels the source. The typed failure modelling they rely on for Tasks disappears the moment data starts arriving over time. Building a value from several live sources (for example a batch rebuilt from its info, tasks, containers and ingredients streams) means writing your own `StreamGroup.merge` and accumulator code, and chaining a stream off a Task (fetch the user, then listen to their profile) means wiring subscriptions by hand. On the Bloc side, `mallard_bloc` only covers Tasks, so stream-backed cubits manage their own subscriptions, cancellation and error handling. That package also has a mislabelled generic order on `TaskCubitMixin`, and a `request` that leaves the cubit stuck `inProgress` when a Task throws.

## Solution

A new core type, **ResultStream** (`ResultStream<S, F>`): a cold, deferred source that emits a sequence of Results when run. Failures are ordinary data events and never end the stream. It is modelled on `Task`:

- **Ways in** are factories. Use `ResultStream(() => ...)` for streams you write yourself, `ResultStream.attempt(run:, handle:)` to wrap third-party streams and turn their error events into typed Failures, `ResultStream.fromTask` to make a Task a one-shot stream, and `succeed` / `fail` / `fromResults` as test stubs.
- **The way out** is `run()`, which returns a `Stream<Result<S, F>>` and fires the new `Mallard.onStreamSuccess` / `onStreamFailure` callbacks once per emitted Result.
- **Operators** are Task's operators applied to each event, plus a few stream-specific ones: switch-latest `chainStream` / `thenAttemptStream`, opt-in `untilFailure`, `restartWhen` for restarting a failed or closed source, a `transform` escape hatch, and a combine-latest `combine` on records of 2–6 ResultStreams.
- **Task interop:** `Task` gains `chainStream` / `thenAttemptStream`, so a stream can hang off a one-shot fetch.
- **short.dart** gets a `ResStream` extension type using the `ok`/`err` vocabulary.
- **mallard_bloc** gets a `ResultStreamCubitMixin` that drives the existing `TaskBlocState` from a live stream. It also aligns `TaskCubitMixin` to `<S, F>` and makes `request` handle untyped throws.

Core changes are additive (non-breaking). The mallard_bloc changes are breaking and ship as 0.1.0.

## User Stories

### Creating result streams

1. As a mallard user, I want to wrap a stream I write myself (`async*` or `StreamController`) that already yields Results, so that I can use mallard operators on it.
2. As a mallard user, I want to wrap a third-party `Stream<T>` (e.g. Firestore snapshots) and turn each of its error events into a typed Failure through a `handle` function, so that the stream's errors become data.
3. As a mallard user, I want a wrapped third-party stream to keep going after it emits an error, so that sources that recover on their own (e.g. a snapshot listener after a network blip) are not lost.
4. As a mallard user, I want a factory that throws inside `attempt` to become one Failure followed by close, so that setup errors are typed like any other failure.
5. As a mallard user, I want `run()` never to throw synchronously, so that I can always pass it straight to `StreamBuilder`, `emit.forEach` or `await for`.
6. As a mallard user, I want a ResultStream to be cold, with each `run()` building a fresh pipeline, so that I can run the same ResultStream more than once and restart it by hand.
7. As a mallard user, I want `run()`'s output to be broadcast exactly when the source is broadcast, so that the ResultStream doesn't change how the source subscribes.
8. As a mallard user, I want cancel, pause and resume on `run()`'s subscription to pass through every operator to the source, so that I control the lifecycle and get backpressure.
9. As a mallard user, I want the docs to tell me my factory must return a fresh (or broadcast) stream on every call, so that I don't get "already listened" errors on a second run.
10. As a mallard user, I want to turn a Task into a one-shot ResultStream with `ResultStream.fromTask`, so that a fetch-once value can take part in a combine.

### Errors and failures

11. As a mallard user, I want Failures to be non-terminal whether they come from the source or from an operator such as `ensure`, so that one bad event doesn't kill a live feed.
12. As a mallard user, I want errors that have no `F` to become (raw error events in a hand-built stream, exceptions thrown in operator callbacks, a `handle` that throws) to come out of `run()` as plain stream errors, so that bugs stay visible, the same as with `Task.run()`.
13. As a mallard user, I want later events to keep flowing after an operator callback throws, so that a single bug on one event doesn't silently end the stream.
14. As a mallard user, I want to opt in to stopping at the first Failure with `untilFailure()`, which emits that Failure and then closes and cancels the source, so that I can treat a stream as fail-fast when I need to.
15. As a mallard user, I want `untilFailure()` to ignore untyped stream errors, so that only typed Failures stop it.
16. As a mallard user, I want Failures to keep their original exception and stack trace through every operator, so that logging and crash reporting still have the root cause.

### Per-event operators

17. As a mallard user, I want `convert`, `convertFailure`, `convertBoth`, `ensure`, `recoverWhen` and `apply` on ResultStream, with the same names and signatures as on Task, so that I don't have to learn anything new.
18. As a mallard user, I want `then`, `thenAttempt` and `chain` to run their async step once per Success, one at a time and in input order, so that output order is predictable and I get backpressure.
19. As a mallard user, I want Failures to pass straight through async steps and keep their place in the order, so that the event sequence stays truthful.
20. As a mallard user, I want `transform(StreamTransformer)` as an escape hatch for stream-specific behaviour (distinct, take, debounce, rxdart transformers) that keeps me inside ResultStream, so that mallard doesn't need its own filter/distinct/take operators.

### Restarting

64. As a mallard user, I want `restartWhen` on any ResultStream to restart the source after a Failure or a close, so that a feed that dropped (e.g. a websocket) comes back without my wiring it by hand.
65. As a mallard user, I want `onFailure(failure, attempt)` and `onClose(attempt)` callbacks that return `FutureOr<bool>`, so that I decide per case whether to restart, and can `await` a delay inside for backoff.
66. As a mallard user, I want `attempt` to count consecutive restarts and reset to 0 on any Success, so that I can give up after N tries.
67. As a mallard user, I want the Failure that leads to a restart hidden by default (`hideFailure = true`), so that a restart doesn't flash an error in the UI, with `hideFailure: false` to see it straight away.
68. As a mallard user, I want the Failure from giving up to always reach downstream, so that I never lose the final error.
69. As a mallard user, I want a restart to be invisible (no event, no new callback, no cubit state change), so that downstream code needs no changes.
70. As a mallard user, I want an `onFailure` / `onClose` that throws to give an untyped stream error and count as "don't restart", so that bugs stay visible.
71. As a mallard user, I want the listener cancelling never to restart, and untyped errors never to trigger a restart, so that only typed outcomes drive it.
72. As a short.dart user, I want `ResStream.restartWhen({onErr, onClose, hideErr})`, so that restarting matches the short vocabulary.

### Dependent chaining

21. As a mallard user, I want `chainStream` to switch to a new inner ResultStream on each outer Success (e.g. auth user → that user's profile stream), so that I always listen to the stream for the latest value.
22. As a mallard user, I want an outer Failure to cancel the current inner stream and be emitted, so that I never see inner data for an upstream value that is no longer valid.
23. As a mallard user, I want a chained stream to close only after the outer stream and the last inner stream have both closed, so that no data is cut off.
24. As a mallard user, I want `thenAttemptStream(run:, handle:)` to build a third-party stream from each Success with `attempt` semantics and switch-latest behaviour, so that I don't have to wrap it in `ResultStream.attempt` inside `chainStream` myself.

### Combining

25. As a mallard user, I want to combine 2 to 6 ResultStreams that share a failure type with `(a, b, c).combine(((a, b, c)) => Value(a, b, c))`, so that I can rebuild a view model from the latest value of each source.
26. As a mallard user, I want a combined stream to wait until every source has emitted before it emits a combined value, so that the builder always gets a complete record.
27. As a mallard user, I want a source's Failure to be emitted once, and Successes from other sources to be held while any source's latest Result is a Failure, so that I never get a value combined from stale data.
28. As a mallard user, I want the combined value to be emitted again once the failing source recovers, so that the view heals by itself.
29. As a mallard user, I want a Failure that arrives before every source has emitted to be emitted straight away, so that early errors aren't hidden.
30. As a mallard user, I want the combined stream to close once every source has closed, or straight away if a source closes without ever emitting, so that I'm never left waiting on a stream that can't produce a value.
31. As a mallard user, I want cancelling a combined stream to cancel every source, so that no subscriptions leak.
32. As a mallard user, I want a builder that throws to give an untyped stream error while later events keep flowing, so that combine follows the same rule as `convert`.
33. As a mallard user, I want to nest a combine inside `chainStream` to pass an upstream value (e.g. a selected batch id) into the sources, so that dependent combines need no extra API.
34. As a mallard user, I want to nest combines to go beyond 6 sources, so that large view models are still possible.

### Task interop

35. As a mallard user, I want `Task.chainStream` to start a ResultStream from a Task's Success (e.g. fetch the current user once, then listen to their profile), so that one-shot and live work chain fluently.
36. As a mallard user, I want `Task.thenAttemptStream` to wrap a third-party stream built from a Task's Success, so that the headline Firestore case is a single call.
37. As a mallard user, I want a failing upstream Task to emit its Failure (with its exception and stack trace) and then close the stream, without building the inner stream, so that `emit.forEach` and `await for` don't hang.
38. As a mallard user, I want every `run()` of a Task-started stream to re-run the Task, so that the stream stays cold.

### Global callbacks

39. As an app developer, I want `Mallard.onStreamSuccess` / `onStreamFailure` to fire once per Result emitted from `run()`, so that stream outcomes reach my analytics and logging.
40. As an app developer, I want stream callbacks kept separate from `onTask*`, so that busy feeds don't flood my task analytics, and I can still point both pairs at the same sink if I want.
41. As an app developer, I want inner runs (async steps, chained Tasks and streams, combine sources, an upstream Task) not to fire callbacks, so that each outcome is reported once, by the outermost `run()`.
42. As an app developer, I want untyped stream errors to fire no Mallard callback, so that the callbacks only ever see typed outcomes, as with Tasks.

### Testing helpers

43. As a test author, I want `ResultStream.succeed(value)` and `ResultStream.fail(value, [exception, stackTrace])`, which emit one Result and close, so that I can stub repositories the same way I do with `Task.succeed` / `Task.fail`.
44. As a test author, I want `ResultStream.fromResults(iterable)` to emit each Result in order and then close, so that I can stub a sequence of Successes and Failures.
45. As a test author, I want `emitsInOrder([Success(1), Failure('x')])` to work on `run()`'s output, so that I need no mallard-specific matchers.

### short.dart

46. As a short.dart user, I want a `ResStream<S, F>` extension type whose callbacks take and return `Res` and whose parameters use `onOk` / `onErr`, so that streams match the short vocabulary.
47. As a short.dart user, I want `convertErr` and `untilErr` instead of `convertFailure` and `untilFailure`, so that the names match `isErr` / `asErr`.
48. As a short.dart user, I want `ResStream` entry points (`ResStream(...)`, `attempt`, `fromTask` taking a short Task, `succeed`, `fail`, `fromResults` taking Res values), so that I never need the long types.
49. As a short.dart user, I want short `Task` to gain `chainStream` and `thenAttemptStream` returning `ResStream`, so that the Task bridges work in the short vocabulary too.
50. As a short.dart user, I want `(a, b).combine(...)` on records of `ResStream`s with the same call site as core, so that combining reads the same in both vocabularies.
51. As a short.dart user, I want only the short types exported, with core `ResultStream` and its `combine` extensions hidden, so that the two vocabularies don't clash.

### mallard_bloc

52. As a Flutter developer using Cubits, I want a `ResultStreamCubitMixin<S, F>` that subscribes the cubit to a ResultStream, so that I don't manage subscriptions by hand.
53. As a Flutter developer, I want the stream mixin to reuse `TaskBlocState`, emitting `inProgress` and then `completed` for each event, so that my existing UI switches on status keep working.
54. As a Flutter developer, I want calling `subscribe` again to cancel the old subscription and switch to the new stream, so that changing the selection simply works.
55. As a Flutter developer, I want untyped stream errors to go to `addError` (and so `BlocObserver.onError`) while the state stays the same and the subscription stays live, so that bugs are reported without breaking the screen.
56. As a Flutter developer, I want the last Result to stay as the state when the source closes, so that the UI keeps showing the final data.
57. As a Flutter developer, I want `unsubscribe()`, `isSubscribed` and automatic cancellation on `close()`, so that I control the subscription and nothing leaks.
58. As a Flutter developer, I want the cubit to go back to its state from before `inProgress` if the stream ends or I unsubscribe before the first event arrives, so that a spinner never hangs.
59. As a Flutter developer, I want `TaskCubitMixin.request` to catch an untyped throw from `task.run()`, pass it to `addError` and restore the previous state, so that the cubit never gets stuck `inProgress`.
60. As a Flutter developer, I want `TaskCubitMixin` to take `<S, F>` like the rest of mallard, so that its type arguments go in the same slots as `Task` and `TaskBlocState`.
61. As a Flutter developer upgrading mallard_bloc, I want a changelog migration note for the generic swap and the `request` behaviour change, so that I can upgrade safely.

63. As a mallard user, I want dartdoc on every new public member, using `{@template}` / `{@macro}` like Task does, so that short.dart and IDE hovers show the same docs.

## Implementation Decisions

### Domain

- **ResultStream** is already defined in CONTEXT.md ("a deferred asynchronous source that, when run, emits a sequence of Results, carrying Failures down the stream as data rather than as stream errors"). No new domain terms. `ResStream` is a vocabulary alias, not a new term.

### Core: the ResultStream type

- A new class `ResultStream<S, F>`, a sibling of `Task`. It is not an extension type and not an extension on `Stream`. It wraps a factory `Stream<Result<S, F>> Function()` and is exported from the core library next to `Task`.
- **Factories (the only ways in):**
  - `ResultStream(Stream<Result<S, F>> Function() run)`: for hand-built sources. A factory that throws gives one untyped stream error, then close. Raw error events in the source pass through as untyped errors.
  - `ResultStream.attempt({required Stream<S> Function() run, required F Function(Object e) handle})`: each data event becomes a Success. Each error event becomes `Failure(handle(e), e, s)` and the stream continues. A factory that throws becomes one Failure, then close. A `handle` that throws gives an untyped stream error.
  - `ResultStream.fromTask(Task<S, F>)`: emits the Task's single Result and closes, re-running the Task on each `run()`.
  - `ResultStream.succeed(S)`, `ResultStream.fail(F, [Object? exception, StackTrace? stackTrace])`: one event, then close.
  - `ResultStream.fromResults(Iterable<Result<S, F>>)`: emits each Result in order, then closes. An empty iterable just closes.
  - There is no `Stream.toResultStream` instance extension. It was dropped because it captured a single-subscription stream that couldn't be re-run.
- **`run()`** returns `Stream<Result<S, F>>`, never throws synchronously, and calls the factory at `run()` time (not on listen). Each call builds a fresh, independent pipeline. The output is broadcast exactly when the source is. It fires `Mallard.onStreamSuccess(value)` / `Mallard.onStreamFailure(value, exception, stackTrace)` for each emitted Result. Untyped errors fire nothing.
- **Lifecycle:** cancel/pause/resume from the listener pass through every operator to the source subscription(s). ResultStream holds no resources of its own. Operators that close early (`untilFailure`) cancel the source. Multicasting is left to Dart (`.run().asBroadcastStream()`). There is no share/replay operator.
- **Inner runs don't report.** Operators compose on the underlying factory, not on the public `run()`, so inner and chained streams, Tasks and combine sources don't fire callbacks. This is the same way `Task.chain` uses the inner Task's private run today.

### Core: operators (all return a new ResultStream and are applied to each event)

- **Synchronous, same names and signatures as Task:** `convert`, `convertFailure`, `convertBoth({onSuccess, onFailure})`, `ensure({check, otherwise})`, `recoverWhen({check, then})`, `apply(Result<S2, F2> Function(Result<S, F>))`. Failures keep their `exception` / `stackTrace`. A callback that throws becomes an untyped stream error and later events keep flowing.
- **Async, same names and signatures as Task:** `then(FutureOr<Result<S2, F>> Function(S))`, `thenAttempt({run, handle})`, `chain(Task<S2, F> Function(S))`. These run once per Success, **sequentially**, like `asyncMap`: one at a time, output in input order, with backpressure. Failures pass through and keep their place in the order.
- **`chainStream<S2>(ResultStream<S2, F> Function(S))`**, with switch-latest semantics:
  - each outer Success cancels the current inner stream and subscribes to the new one;
  - an outer Failure cancels the inner stream and is emitted;
  - it closes once the outer stream and the last inner stream have both closed.
  
  It is hand-rolled, with no deps.
- **`thenAttemptStream<S2>({required Stream<S2> Function(S) run, required F Function(Object e) handle})`**: the same switch-latest rules as `chainStream`. It is equivalent to `chainStream((s) => ResultStream.attempt(run: () => run(s), handle: handle))`.
- **`untilFailure()`**: emits every event up to and including the first Failure, then closes and cancels the source. Untyped errors pass through and don't stop it.
- **`restartWhen({FutureOr<bool> Function(F failure, int attempt)? onFailure, FutureOr<bool> Function(int attempt)? onClose, bool hideFailure = true})`**: an operator on any ResultStream (so it composes with `attempt`, `thenAttemptStream`, `chainStream` and each source of a `combine`). It cancels the source and calls the factory again. An assert requires at least one callback; leaving one out means that trigger never restarts.
  - **Triggers:** a Failure while the source is live, or the source closing. Listener cancel never restarts. Untyped errors are not triggers and pass through.
  - **No policy surface:** no delay, backoff or max-attempts parameters. Callers `await` a delay inside the callback.
  - **`attempt`** is the number of restarts so far in the current streak (0 on the first ask), reset by any Success (including ones flowing during a `hideFailure: false` decision). It lives per `run()`.
  - **`hideFailure` (default true):** a Failure is held until the callback decides. If it returns true, the Failure is dropped and the source restarts. If false, the Failure is emitted; the Failure from giving up always reaches downstream. Hidden Failures never fire `Mallard.onStreamFailure` (log inside `onFailure` if needed). With `hideFailure: false` the Failure is emitted straight away and source events keep flowing during the decision.
  - **Hold mechanism:** with `hideFailure: true`, the hold is done by pausing the source subscription (not by queueing), so order and a waiting close come for free: held events and the close arrive after the decision (false flushes them, true cancels the source and drops them).
  - **One decision at a time:** further Failures during a pending decision don't call `onFailure` again. A close during a pending Failure decision is dropped if that decision is true, and asks `onClose` only after a false.
  - **Callback throws:** an untyped stream error, treated as false. The stream carries on, or closes if it was a close.
  - **Throwing factory on restart:** an untyped error, then close.
  - **Lifecycle:** a restart while the listener is paused resubscribes the source paused (pause counts nest, so a user pause survives). A cancel during a pending decision means no restart and no emission. Output is broadcast iff the first factory source is (known at `run()` time); multiple listeners share one restart.
  - **Combine / chainStream:** restarts inside `chainStream` or on a `combine` source emit no Failure and no stale combine. On a combined stream, `restartWhen` restarts every source, so place it on each source instead.
  - **Visibility:** the restart itself is invisible: no event, no Mallard callback, no cubit state change.
  - **Not supported / caveats:** re-listening to a broadcast output after its last listener left; an `onClose` that always returns true with no delay loops forever.
  - Prototype: local branch `prototype/restart-when`, about 110 lines over a `StreamController`, 20 checks passing.
- **`transform<S2, F2>(StreamTransformer<Result<S, F>, Result<S2, F2>>)`**: the only escape hatch. There are no built-in filter, distinct, take, merge, zip or scan operators.
- There is no `thenStream`, no `ResultStream` → `Task` conversion, and no separate retry/repeat operator (`restartWhen` covers it).

### Core: combine

- One **named** extension per record arity from 2 to 6 (e.g. on `(ResultStream<A, F>, ResultStream<B, F>)`), each with a `combine<S>(S Function((A, B)) builder)` method returning `ResultStream<S, F>`. The extensions must be named so that short.dart can hide them.
- **Semantics:** combine-latest. Each slot remembers its latest Result. Nothing is emitted until every slot has emitted once (there are no seeds; add one upstream via `transform`).
- **Failures (emit, then hold):** a Failure is emitted once. While any slot's latest Result is a Failure, Successes from other slots are held and never combined with stale data. When the failing slot emits a Success, a combined value is emitted. A Failure that arrives before all slots have emitted is emitted immediately.
- **Failure type:** all sources share `F`. Mismatched sources are aligned first with `convertFailure`.
- **Builder:** returns a plain value. If it throws, that becomes an untyped error and later events keep flowing. For a fallible step, follow the combine with `.then` / `.ensure`.
- **Closing:** the combined stream closes once every source has closed, or immediately if a source closes without ever emitting.
- **Lifecycle:** cold. `run()` runs every source. Cancel/pause/resume pass to all sources. The output is broadcast only if every source is. Untyped errors from any source pass through.
- **Callbacks:** these fire once per combined event, from the outer `run()` only.
- **Upstream values:** nest the combine inside `chainStream` (or `Task.chainStream`). There is no combine-specific chaining form. Go beyond 6 sources by nesting combines.

### Core: Task additions

- `Task.chainStream<S2>(ResultStream<S2, F> Function(S))` and `Task.thenAttemptStream<S2>({required Stream<S2> Function(S) run, required F Function(Object e) handle})` both return `ResultStream<S2, F>`. If the Task succeeds, the inner stream is built from the value. If the Task fails, its Failure (with exception and stack trace) is emitted and the stream closes without building the inner stream. Each `run()` re-runs the Task.
- **Callbacks:** only `onStream*` fire, including for the Task Failure that cuts the stream short. The upstream Task is an inner run, so no `onTask*` fires.

### Core: Mallard callbacks

- Add `static void Function(dynamic success) onStreamSuccess` and `static void Function(dynamic failure, Object? exception, StackTrace? stackTrace) onStreamFailure`. They default to no-ops and have the same signatures as `onTask*`. `onTask*` doesn't change. There is no source identity / `MallardEvent`.

### short.dart

- `ResStream<S, F>`: an extension type over core `ResultStream`, built like short `Task`. Converting `Stream<Result>` to `Stream<Res>` is a zero-cost cast.
- **Entry points:** `ResStream(Stream<Res<S, F>> Function())`, `ResStream.attempt({run, handle})`, `ResStream.fromTask(Task)` (taking short Task), `ResStream.succeed`, `ResStream.fail`, `ResStream.fromResults(Iterable<Res<S, F>>)`.
- **Operators** keep the core names, with Res in and out: `convert`, `convertBoth({onOk, onErr})`, `ensure`, `recoverWhen`, `apply`, `then`, `thenAttempt`, `chain`, `chainStream`, `thenAttemptStream`, `transform` (taking `StreamTransformer<Res, Res>`), `restartWhen({onErr, onClose, hideErr})`, and `run()` returning `Stream<Res<S, F>>`. Renames: `convertFailure` becomes `convertErr`, `untilFailure` becomes `untilErr`, and `restartWhen`'s `onFailure` / `hideFailure` become `onErr` / `hideErr`.
- Short `Task` gains `chainStream(ResStream Function(S ok))` and `thenAttemptStream({run, handle})`, both returning `ResStream`.
- `combine` is redeclared for records of 2–6 `ResStream`s, returning `ResStream`.
- The export hides core `ResultStream` and the named core `combine` extensions (next to the existing `Result` and `Task`). `Mallard.onStreamSuccess` / `onStreamFailure` are re-exported unchanged.

### mallard_bloc

- **Generic order:** `TaskCubitMixin<F, S>` becomes `TaskCubitMixin<S, F> on Cubit<TaskBlocState<S, F>>`, with `request(Task<S, F>)`. The old mixin was effectively mislabelled. `TaskBlocState`'s `toString` currently prints `<$F, $S>` and is corrected to `<$S, $F>` in the same pass.
- **`TaskCubitMixin.request`:** the existing guard (ignore while in progress) stays. It remembers the state from before `inProgress`. If `task.run()` throws, it calls `addError(error, stackTrace)` and restores that state instead of staying `inProgress` and rethrowing.
- **New `ResultStreamCubitMixin<S, F> on Cubit<TaskBlocState<S, F>>`**, separate from `TaskCubitMixin` (a cubit uses one or the other). It reuses `TaskBlocState` unchanged, with no new state or status.
  - `subscribe(ResultStream<S, F>)` cancels any live subscription and remembers the current state. It emits `inProgress(state.result)`, runs the stream, and emits `completed(result)` for each event. There is no in-progress guard (it switches to the latest stream).
  - Untyped errors go to `addError`. The state stays the same and the subscription stays live.
  - Source closes: nothing is emitted and the subscription is cleared. If no event arrived since `subscribe`, the remembered state is restored.
  - `Future<void> unsubscribe()` cancels and leaves the state unchanged. As above, it restores the remembered state if no event has arrived yet.
  - `bool get isSubscribed`. A `close()` override cancels the subscription.
  - Global callbacks need nothing here (they fire from `run()`).

### Versioning, changelog and docs

- **mallard core: 1.1.0.** It is additive and non-breaking. The changelog lists ResultStream, its factories, operators and combine, the Task stream bridges, the `onStream*` callbacks and short.dart `ResStream`.
- **mallard_bloc: 0.1.0** (breaking). It requires the new core version. Changelog entries: `ResultStreamCubitMixin`, and a migration note for (a) swapping the type arguments on `TaskCubitMixin` and (b) `request` now catching untyped throws (reported via `addError`, previous state restored).
- **README (core):** a ResultStream section covering:
  - ways in and out;
  - failure vs untyped-error semantics and the `async*` `throw` caveat;

## Testing Decisions

- **One seam: core ResultStream's public API.** Each test builds a ResultStream (or a Task bridge / combine), calls `run()`, and asserts on the emitted stream with `package:test` matchers (`emitsInOrder`, `emitsError`, `emitsDone`). Success and Failure are Equatable, so expected values are plain Results. Global callbacks are checked by assigning recording functions to `Mallard.onStreamSuccess` / `onStreamFailure` / `onTask*` and resetting them in `setUp`.
- **Good tests check external behaviour only**: what `run()` emits, in what order, when it closes, which callbacks fire, and what happens to the source subscription (observed via a `StreamController`'s `onListen` / `onCancel` / `onPause` / `onResume` hooks and `hasListener`). Never assert on private fields or internal stream plumbing.
- **Coverage to aim for**, by area:
  - Restart: restart on Failure and on close, `attempt` count and reset, `hideFailure` true/false, give-up Failure emitted, hidden Failures firing no callback, one decision at a time, close during a pending decision, callback throws, cancel during a pending decision, pause/resume across a restart, inside `chainStream` and on a `combine` source.
  - Factories: factory-throw behaviour, attempt error-to-Failure while continuing, `handle` throwing, `fromTask`, `succeed` / `fail` / `fromResults`.
  - Run behaviour: cold re-run, broadcast-iff-source, no synchronous throw from `run()`.
  - Operators and errors: each sync operator per event, callback throws as untyped errors with flow continuing, exception/stack-trace preservation, sequential ordering of async steps.
  - Chaining: `chainStream` / `thenAttemptStream` switch-latest (inner cancelled on new Success and on Failure, close timing), `untilFailure` (includes the Failure, cancels the source, ignores untyped errors), `transform`.
  - Combine: wait-for-all, emit-then-hold, early Failure, recovery, close rules including a source closing empty, cancellation of all sources, builder throws.
  - Task and callbacks: `Task.chainStream` / `thenAttemptStream` (Task Failure emitted then close, inner not built), callbacks firing once per outer event and never for inner runs or untyped errors, `onTask*` not firing for stream runs.
- **Prior art:** the existing Task test suite (`package:test` + `test_beautifier`, callbacks reset in `setUp`, a fake `StackTrace.fromString`) is the template. ResultStream tests go in a new test file next to it, in the same style.
- **Not tested:** short.dart `ResStream` and short Task bridges (a thin zero-cost wrapper over the tested core), and mallard_bloc (no test suite exists today and none is added here). Both were explicitly left out of the test seams.

## Further Notes

- Dart caveats to keep in mind while implementing:
  - a `throw` inside `async*` ends that generator;
  - `StreamTransformer.fromHandlers(handleError: ...)` is the natural primitive for turning error events into data and carrying on;
  - exceptions thrown in listener callbacks go to the zone, not `onError`;
  - broadcast streams silently drop events that have no listener.
- Research notes from the wayfinder live on the `research/error-as-data-streams` branch (`docs/research/`).
- The motivating cases were a `Batch` view model combined from four Firestore streams, and an auth user → profile stream chained off a one-shot fetch.
