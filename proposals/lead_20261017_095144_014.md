*Project description:*
# P0 — Headless CLI / Internal Dispatch Control Entry

**Status:** PLANNED / NOT IMPLEMENTED  
**Parent architecture owner:** #806 (stable Headless API/SDK, remains canonical; do not create a competing SDK)  
**Priority:** P0 enabling slice, scheduled with #1191/#1193 safety dependencies; do not displace ongoing owners or imply readiness to auto-run.  
**Product intent (Owner, 2026-10-17):** Nerelan must be usable like Codex through both a desktop GUI and CLI. More importantly, authorized internal agents/long-lived schedulers must invoke the same governed Goal/Task/Run lifecycle **without a mouse or browser**, while users can inspect/approve through Desktop. **Unified AI resource management, cost-aware routing, verifiable results remain core product value.**

## Concrete trigger / evidence

The supported Windows launcher/trusted client opens the local UI at `127.0.0.1:4173`, Task API `:8766`, Model Control `:8765`. Direct terminal reads of private Task APIs without a client capability returned `401 local_client_session_required`: **the security policy correctly rejects an arbitrary local caller**. The live host currently creates a private high-entropy local-session capability, hands it through anonymous stdin to the native trusted client, and uses it to forward browser requests. This is a real boundary under #384, not a bug to delete.

An authorized owner can create/plan/approve/launch through the trusted browser. Requiring that graphical automation to perform everyday programmatic dispatch, however, obstructs Nerelan's multi-day unattended operation. **Do not expose, copy, recover or inject the browser's private client capability to make CLI work.** Nor should an owner-activated window be interpreted as blanket permission to replay historical work.

## Architectural decision / permanent invariants

```text
Desktop GUI ────────────────┐
CLI (human/script) ─────────┼──> ONE authenticated Control Plane
Internal Scheduler/Agent ───┘    (one policy, one TaskStore, one Goal/Run state machine)
                                  │
                                  ├── owner identity / explicit delegated scopes
                                  ├── authorization window / lease / budgets / quota
                                  ├── capability + repository + workspace admission
                                  ├── idempotency, durable receipts, restart fencing
                                  ├── structured activity, result, evidence, audit
                                  └── executor adaptors (OpenCode, Codex, Claude Code…)
                                         │
                                  Magpie-first provider/usage source (#1170),
                                  not an alternative lifecycle authority
```

The local GUI stays a review/oversight/configuration client. The CLI is a **thin client**, never another agent engine, TaskStore, database, scheduler, policy evaluator, model-account switcher, or quota bypass. The internal coordinator uses trusted in-process/host IPC/capability-checked operations instead of simulating GUI clicks or trusting localhost alone. Backend policy is evaluated for every caller, not only the frontend.

## Security and authority design required before implementation

1. Inventory current `trusted_host`, `trusted_client`, `local_client_session`, `task_service`, `cli.py`, Goal/Run operations, and `unattended_coordinator`; choose a **mature supported** OS-local/IPC mechanism (e.g. Windows named pipes or authenticated host-owned local endpoint) under #361 reuse gate, then write a threat model. Reuse existing auth boundaries from #384 and current durable semantics from #806. No blanket bypass of `X-Nerelan-Client-Capability` or CORS/Origin checks.
2. Define **separate principals**: (a) interactive local owner CLI (authenticated to OS/session, capable of requesting approvals but not silently minting them); (b) limited system scheduler/Agent identity, restricted to specifically approved Goal/task IDs, repository/workspace, allowable operations, executor/binding, time window, quotas and concurrency. Same backend admission and audit contract, different scopes.
3. Host owns capability issuance/rotation/revocation; prevent leakage through argv, environment inherited by executors, renderer state, URL/query string, SQLite task evidence, logs, crash dumps or GitHub comments. Reject arbitrary same-machine subprocess callers without authorization, not just external-network callers. Deny stale/replayed/scoped-mismatch requests and malformed input. Fail closed when host unavailable.
4. Every state-changing request uses revision/CAS, idempotency identity, exact goal/task/window/attempt binding and durable operation receipt. Detect owner window expiry, machine restart, stale claims, external jobs with unverified receipts; an unauthenticated `nerelan run resume` or a surviving queued row grants no execution authority. Explicit `UNKNOWN/WAITING` rather than fabricated success.
5. Use the same quota/budget/cost admission as #1193; provider/source truth from #1170. Do not auto-spend account subscriptions, switch identities, renew authorization, merge PRs or start remote GPUs as a side effect of querying CLI status.
6. Local-first and loopback-only by default. Remote SSH/multi-machine/API publication is **not** solved by opening `:8766` or using the browser token; future remote/multi-user auth is separately scoped under #806.

## Delivery slices (Owner preference: Nerelan itself executes; supervisor audits)

**CLI-0 — provider-free mapping / design and threat-model.** Document exact existing routes, identities, and which behaviors are already supported vs missing, including #384 auth and #1191 recovery; define the narrow IPC contract and tests before edits. Explicit no-op status/test fixtures.

**CLI-1 — shared versioned application/control contract.** Thin typed request interface for `goal create/inspect/plan/approve/launch`, `task list/inspect`, `run status/watch/stop`, `doctor`, `window status`; unsupported lifecycle verbs must return typed NOT_SUPPORTED rather than false-green. Semantics follow #806 TaskStore/GoalService and existing tests.

**CLI-2 — authenticated CLI entrypoint.** Windows runnable `nerelan` command plus `--json`, sane exit codes, bounded timeout, sanitized stdout/stderr, IDs and structured evidence. Illustrative *future* usage (not a claim of implemented commands):

```sh
nerelan status --json
nerelan goal create --file goal.json --json
nerelan goal plan <goal-id> --json
nerelan goal approve <goal-id> --json
nerelan goal launch <goal-id> --window <window-id> --json
nerelan task list --json
nerelan run watch <run-id> --json
nerelan run stop <run-id> --json
```

**CLI-3 — host-internal authorized autonomous dispatch.** Scheduler/Agent calls same controlled service directly with scoped runtime authority; no GUI automation, no endpoint authentication bypass. Frontend and CLI observe the **same** state transition, IDs, receipts and validation records.

**CLI-4 — Windows real-host dogfood and restart fencing.** Through real owned local host, prove GUI and CLI feature parity for one small provider-free Goal, then one approved quota-bounded live task; explicitly prove denial after authority expiry/restart and orphaned-claim hold. Continue #1191 long-run task only after recovery prerequisites hold.

**CLI-5 — SDK + optional remote access.** Defer larger Python/TS SDK and remote transport to #806; do not broaden this P0 slice without priority reevaluation.

## Deterministic acceptance and observable evidence

- [ ] CLI can inspect local authenticated state with **no desktop window running** and without using/printing trusted-client secret.
- [ ] A scoped, explicitly owner-approved CLI Goal can proceed through draft→plan→approve→launch with persistent Goal/Task/Run IDs shared with GUI (provider-free acceptance first).
- [ ] Internal scheduler can dispatch the same authorized Goal without opening or clicking a browser; TaskStore/run/evidence and CLI/GUI projections agree.
- [ ] No-capability, wrong-capability, expired-capability, other local process and wrong-origin attempts rejected; no shortcut around #384. Never assume `localhost + absent Origin` proves identity.
- [ ] Authorization scopes for goal/repo/workspace/operation/executor/binding/window/time/concurrency/budget are enforced server-side; privilege-looking JSON fields cannot mint authority.
- [ ] Duplicate/retried `goal create` or `launch` calls are idempotent; disconnect/crash/restart cannot silently duplicate model run/PR/publication.
- [ ] `HOLD_ORPHANED_CLAIMS`, stale receipt, expired window, quota exhausted and `UNKNOWN` cases fail closed and surface repairable diagnostic codes, no actual model dispatch.
- [ ] Machine-readable status/exit codes + structured sanitized event stream can be consumed from PowerShell/CI/Agent with no secret leakage.
- [ ] Windows host + CLI acceptance run includes exact code SHA, authentic Task/Run IDs, real gateway/model usage if live, relevant test logs; distinguish execution started from completion, verification, review and merge.
- [ ] Before any landing: isolated worktree, exact-head CI/state-gate, genuinely independent review verdict and repository governance-compliant merge. No overlap with active #1191/#1193/#1170 source ownership.

## Dependencies and anti-duplication

- #806 is **canonical product contract**, this is a narrow P0 implementation/handoff child, not a replacement.
- #384 is local-client identity/auth; **preserve its protections**.
- #1191 is reboot recovery / multi-day JEV dogfood; blocked recovery claims must remain fenced.
- #1193 is quota/admission gate; CLI cannot route around it.
- #1170 owns Magpie-first resources; CLI must not build another model gateway.
- #289 owns generic run operations/triggers; #357 owns desktop shell; these are peer consumers, not duplicate dispatch logic.

**Implementation status on creation:** SPEC FIXED / NO SOURCE CHANGE / NO NEW EXECUTION AUTHORITY. Explicit user authorization for this design priority is **not** permission to access secrets, invoke uncontrolled models, or use a system-level elevated identity.
