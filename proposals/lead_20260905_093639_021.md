*Project description:*
## Goal

Investigate the current MARP development ecosystem and design a **proper agentic development workflow/harness** that can support Claude Code, ChatGPT/Codex, GitHub Copilot, and future coding agents across the MARP repositories.

This is a **research and planning task**, not an implementation task. Do not begin modifying the MARP repositories to install the harness until the proposed workflow has been reviewed with Isaac and approved.

The workflow should preserve the part of our current process that has worked well, especially the way the design of the Picture Mosaic Reviewer has been worked through in [`MARP_API` issue #68](https://github.com/MarineAppliedResearch/MARP_API/issues/68): investigate the existing system, surface assumptions and ambiguities, discuss them with Isaac, revise the design based on those answers, and only then allow the agent to go off and implement the settled design.

**Do not assume that GitHub issues are the correct long-term design/specification mechanism.** Issue #68 is an example of the *interaction loop*, not necessarily the artifact we want to keep using. A major part of this task is to investigate and recommend the proper agentic flow and the proper artifacts for requirements, plans, assumptions, decisions, tests, and implementation state.

# Desired development interaction

We do **not** want maximum unattended autonomy.

The goal is to make agents extremely fast once a design has been settled, while keeping important product and architecture decisions human-guided.

The process we want to preserve is approximately:

**investigate -> surface assumptions -> iterate with Isaac -> settle requirements/design -> implement autonomously -> present tests -> Isaac reviews tests -> run verification -> Isaac reviews evidence -> create PR only when approved**

A better agentic workflow may express these stages differently. Part of this task is to research the best current way to implement this process with modern agent tooling.

## Critical rule: assumptions must be surfaced

Agents currently make too many plausible but incorrect assumptions.

A material assumption must not silently become an implementation decision.

During planning, the agent should identify things such as:

- behavioral assumptions
- product/UI assumptions
- scientific/data-meaning assumptions
- database/data-model assumptions
- API-contract assumptions
- architectural assumptions
- performance/concurrency assumptions
- security/permission assumptions
- destructive-operation assumptions
- cross-repository integration assumptions

These should be resolved with Isaac before implementation where they could affect intended behavior or architecture.

Trivial local coding choices that clearly follow an established repository pattern do not need to become questions.

If a new material assumption is discovered during implementation, the process should provide a clean way to return to the design/decision loop instead of guessing.

---

# Test-first human acceptance loop

A major requirement is that implementation should **not immediately become a pull request**.

After implementation, the agent should be able to present a test/verification package for review, including as appropriate:

- tests added or changed;
- what requirement each test is intended to prove;
- important edge cases;
- regression coverage;
- known verification gaps;
- manual/interactive test steps;
- browser/UI test artifacts;
- screenshots, recordings, traces, or reports where useful;
- performance/concurrency/integration verification where relevant.

Isaac should be able to review the tests and say, for example, “you are missing this case” or “that test does not actually prove the requirement,” before the final verification/PR step.

Then the agent runs the approved verification and presents the actual results.

PR creation should remain a deliberate human-approved step unless we later explicitly change that policy.

# Multi-agent requirement

The harness should be designed for **multiple agents and multiple model families**, not just one interactive Claude Code session.

Investigate how to support patterns such as:

- multiple implementation agents working on independent tasks;
- one task/issue per isolated branch or worktree;
- independent local environments when appropriate;
- cross-repository changes;
- implementation agents and independent reviewer/test agents;
- Claude reviewing Codex work, Copilot reviewing Claude work, etc.;
- CI and automated verification between agent stages;
- dependency awareness between parallel tasks;
- preventing two agents from independently making conflicting architectural assumptions;
- handling shared API/data-contract changes safely;
- deciding which stages can run in parallel and which need synchronization/human gates.

The objective is **parallel execution after assumptions are settled**, not several agents inventing incompatible interpretations of MARP at the same time.

# Determine the proper planning/design artifact

One of the explicit goals of this issue is to answer:

**What should replace the ad-hoc use of a GitHub issue as the evolving design record?**

Issue #68 worked because the interaction was iterative and decisions were progressively clarified, but the issue itself was chosen mainly because we did not yet have a better agentic workflow.

Investigate current agentic-development practices and recommend the appropriate mechanism for maintaining, during a task:

- the current understood requirements;
- open assumptions/questions;
- decisions already made;
- proposed implementation plan;
- affected repositories/interfaces;
- acceptance criteria;
- test plan;
- implementation/verification status.

The desired artifact should be easy for Isaac to inspect and edit, easy for agents to consume, resistant to stale assumptions, and suitable for both small and large tasks.

Consider whether different artifacts are appropriate for temporary task planning versus durable architecture/product decisions.

---

# Learning from corrections

The harness should make repeated human corrections accumulate into a better environment.

When Isaac corrects an agent, determine how the workflow should decide whether that correction belongs in:

- the current task specification;
- permanent architecture documentation;
- an ADR;
- `AGENTS.md` or another shared instruction file;
- a path-specific rule;
- a test;
- a linter or structural constraint;
- CI;
- a hook/permission rule;
- an issue/task template;
- another durable artifact.

The same avoidable mistake should become less likely after it has been corrected once.
