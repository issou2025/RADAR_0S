# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Simplify BeLib PR approval: i5 preview OK → chat merge request, without solo-owner JSON comments**

*Project description:*
## Owner request — 2026-11-05 JST
The current Draft PR workflow requires manually authored structured `BELIB-SOLO-REVIEW v1` and `BELIB-SOLO-RELEASE v1` comments before a merge can enter production CD. The owner finds this workflow unnecessarily cumbersome and wants normal BeLib UI changes to follow: **Codex implementation + exact-HEAD CI/independent review → physical i5 browser on isolated test/preview environment → owner confirms OK and explicitly requests "mergeして" in chat → guarded normal PR merge → current production CD + post-deploy readback**. An explicit current-PR owner request must not be inferred from earlier approvals.

## Current evidence
- Source of the active gate: `scripts/deploy/release_gate.py` (`_verify_solo_owner_policy`, `_verify_pr_review`), with `scripts/deploy/test_release_gate.py`.
- Current documented policy: `docs/runbooks/release.md` § Frontend CI/CD handoff / Solo-owner comment format.
- Active exact-HEAD candidates, e.g. PR #93 and #98, currently report a HOLD for owner-authored comment pairs despite green candidate CI/review.
- Merely merging a PR without revising the release validator may leave the CD handoff rejected. **Do not delete validators or skip CD gates to fake success.**

## Implementation objective
Replace the *manual structured solo-owner comment pair* with a low-friction, auditable single-maintainer merge authorization path. Define how exact-PR/exact-HEAD owner intent reaches the authorized merger and how production CD validates it without relying on untrusted agent-authored GitHub comments. A deliberate authenticated owner's GitHub merge is potentially usable as one signal, but an agent using an owner-attributed token is **not** by itself proof of human approval: avoid silently upgrading a bot merge to owner acceptance. Preserve a verified separate independent review/check and revocation/changes-request semantics. Do not add multiple new human steps or a new generic approval service.

## Acceptance
- For normal UI-only changes, no manual GitHub JSON comment copying/posting by the owner. The owner's flow is: view physical-i5 isolated preview with correct revision → state OK / request merge in chat → normal merge by an authorized actor.
- Before merge, verify exact current PR head, required CI green, real independent review PASS/no unresolved high findings, correct target branch, no blocking review or material conflict, and physical-i5 preview evidence or an explicit owner-approved exception. Merger must verify that this PR/head is the one accepted in the current request. Never treat preview or test success as permission to deploy unauthorized protected changes.
- After merge, the existing CD path must accept the newly authorized pathway, validate the exact `main` merge SHA and PR head checks, and perform normal production handoff/readback. Prevent false-success when CD skips/rejects.
- DB migration, auth/permissions, private books/R2, irreversible deletion, credentials, billing, shared infra or risky production effects retain separate protected approval and safe rollback; this issue alone grants no such changes.
- Update `scripts/deploy/release_gate.py`, meaningful tests (positive/negative/stale-head/unauthorized-bot/failed-review/revocation), `docs/runbooks/release.md`, and exact required CI. Keep branch protection and required checks; no unsafe bypass or force-push.
- Draft/PR candidate first; independent review and explicit owner merge request are prerequisites to merging *this gate-change PR* itself. Verify the resulting CD on a later eligible merge; do not claim production acceptance from PR CI alone.
