# Project Proposal — Flutter App

You need assistance with: 
**[M13][Investigation] Define host-neutral UI environment, locale, direction, and user-scale propagation**

*Project description:*
## Context

Accepted M8 provides international text shaping/bidi and explicit `StylePreferences` for high contrast and reduced motion. Accepted M13 is responsible for production platform profiles.

A platform/profile audit shows a missing neutral **environment** contract. Current public state does not name:

- active locale/language preference;
- left-to-right versus right-to-left UI layout direction;
- user text/UI scaling distinct from raster/DPI scale;
- platform appearance/color-scheme preference;
- pointer/hover capability facts where adaptive controls need them.

Text shaping support alone is not application localization or UI-direction propagation.

Mature declarative frameworks treat these as inherited environment facts. SwiftUI exposes locale and layoutDirection through environment values, and layout direction affects view layout:
https://developer.apple.com/documentation/swiftui/environmentvalues
https://developer.apple.com/documentation/swiftui/layoutdirection

Flutter similarly resolves application locale and uses localization data to establish directionality:
https://docs.flutter.dev/ui/internationalization

## Goal

Define the smallest host-neutral environment vocabulary and propagation/invalidation model needed by RunenUI's supported desktop, embedded and real-time 0.1 profiles.

The framework should expose facts; it should **not** become a translation-catalog/message-formatting product unless a later decision proves that necessary.

## Required questions

1. Which facts belong in one environment contract versus existing `StylePreferences`?
2. Locale representation:
   - language;
   - script;
   - region;
   - fallback/resolution policy.
3. UI layout direction:
   - inheritance;
   - explicit subtree override;
   - interaction with bidi text;
   - logical Start/End versus physical Left/Right layout vocabulary.
4. User text/UI scale:
   - distinct from raster scale/DPI;
   - whether typography only or broader control metrics;
   - bounded accessibility behavior.
5. Appearance and accessibility preference facts:
   - light/dark/system preference;
   - high contrast remains mandatory preference authority;
   - reduced-motion authority remains the accepted StylePreferences path;
   - determine whether a platform/user **focus-indicator visibility / always-show-focus** preference is required by #286 and, if so, expose it as an explicit neutral fact rather than a hidden platform heuristic;
   - theme selection remains application/theme policy rather than hidden framework branding.
6. Input capability facts:
   - hover availability;
   - coarse/fine pointer;
   - touch/controller presence;
   - whether these belong here or in a separate adaptive-input query contract.
7. Headless deterministic construction and override.
8. Host change invalidation and trace.
9. Native winit/platform mapping on Windows/macOS/Linux.
10. Embedded/game host injection without ambient OS reads.
11. Interaction with #289 adaptive/container queries.
12. Interaction with standard-control sizing and accessibility.
13. Whether localized shortcut display belongs to this environment while command binding remains M11.
14. Surface-safe-area / content-inset facts:
   - whether supported desktop/full-content and embedded/game surfaces can expose logical regions obscured by platform chrome, display cutouts or host-reserved UI;
   - whether one logical edge-inset fact is sufficient or whether non-rectangular/display-feature occlusion is actually required by a declared 0.1 profile;
   - whether ordinary window content bounds/root constraints already remove the need for a framework fact on each supported host;
   - subtree propagation/override and interaction with #289 adaptive layout if a neutral fact is justified.
   Do not add mobile/web safe-area parity without profile evidence.

## Non-goals

- no ARB/Fluent/ICU message catalog mandate;
- no application string translation store in runtime;
- no device-name or "mobile/tablet/desktop" categorization;
- no DPI/raster-scale conflation;
- no automatic theme branding;
- no ambient global mutable locale.
