### Why this matters

The documentation treats this module as executing code, not as a specification to be read:

- `contract/OVERSIGHT-CONTRACT.md` and `overseer.md` step 4: *"Re-detect server-side gate (`merge_authority.py:detect_server_side_gate`) — **R9.1.1: never use a cached result for a merge decision.**"* A rule forbidding cached results presupposes the function is *called*. An LLM re-deriving the answer from source each cycle is not what R9.1.1 describes, and the property it guarantees — a fresh, deterministic read of live server state — is not delivered.
- The module has unit tests asserting exact behaviour. Those tests pass and prove the library is correct. They say nothing about what the pipeline does, because the pipeline does not run the library.
- This is the **archetype** of the pattern already recorded in `research/sessions/2026-08-04-controls-that-never-fire.md` — *"absence must be affirmed, not inferred"* — at the highest-stakes point in the system: the merge decision itself.

If an LLM approximating tested Python is the intended design, then the tests, the contract language, and the "never use a cached result" rule are all misleading about what actually enforces the gate. If it is *not* the intended design, then the merge-authority matrix has never run in production.

### The question this issue must answer

**Is the library intended as executable code, or as a specification the agent reads and applies?**

Both are defensible architectures. What is not defensible is the current state, where the artifacts assert one and the runtime does the other. Specifically:

- **If executable:** every entry point needs an invocable, statically-allowlistable surface — the `bootstrap/*.sh` wrapper pattern (`--app <role>`, variable text via `--body-file`, mint/revoke internal). The agent files must invoke those wrappers rather than saying "call `function(...)`", which is not an executable instruction for an agent that can only issue shell commands.
- **If specification:** the tests are testing a model of the system rather than the system; the contract's execution-flavoured language (`never use a cached result`, `re-detect`) must be rewritten to describe what the agent is actually required to do; and there needs to be some check that the agent's reading matches the code, because nothing currently detects divergence between the two.

### Scope beyond the merge matrix

The same question applies to every entry point in the module and to any similarly-invoked library: `decide_merge_authority`, `detect_server_side_gate`, `check_register_completeness`, `bounce_count`, `record_pr_bounce`, `has_human_approval`, `detect_human_hold_directive`, `route_embargo`. `#1356` covers the bounce specifically; this issue is the general case.

Worth checking as part of this: whether `scripts/automation/lib/pr_readiness.py` (the one real importer) is itself invoked at runtime, or is in the same position.

### Residual checks not yet done

- The probe searched for `python3 -c` specifically. **Other invocation forms should be ruled out** — `python3 <script>`, `python -m`, a venv interpreter path, or invocation from inside a `bootstrap/`/`scripts/` shell script that then imports the module. The absence of any wrapper and of any non-test importer makes this unlikely, but it has not been exhaustively excluded and should be before the conclusion is treated as settled.
- The HOS overseer log covers only 2026-08-12 → 08-13 (size-bounded/rotated). The CPS overseer log covers 2026-06-29 → now with the same zero result.
- Consumer projects beyond `hos` and `cps` were not examined.
