## Engineering-loop contract

Each iteration owns **one unblocked ticket** and must preserve an accurate record:

1. **Orient:** Re-read repo `AGENTS.md`, `CONTRIBUTING.md`, current `main` SHA, ticket, active branches and relevant tests. Verify that upstream has not already resolved the issue.
2. **Claim:** Record the issue being worked and the base SHA. Skip claimed or blocked work; do not edit the same branch from two concurrent iterations.
3. **Specify:** Document trigger, observable failure, expected behavior, affected interface/seam, acceptance test, out-of-scope.
4. **Red:** Reproduce with a failing test where a suitable public seam exists. Do not invent private-method tests or fake green.
5. **Green:** Implement the minimum vertical slice using existing module interfaces and types.
6. **Verify:** Run targeted tests, static analysis, contract/integration checks, and real-device checks when required. Distinguish `PASS`, `FAIL`, `NOT_RUN`, and `BLOCKED`. A committed test without a runner is `NOT_RUN`.
7. **Review:** Standards axis: `AGENTS.md`, `CONTRIBUTING.md`, existing contracts, blast radius. Spec axis: acceptance criteria, missing behavior, scope creep. Address failures before continuing.
8. **Record:** Commit only to isolated development branch where authorized, add issue comment with SHA, command/output, risks, next blocker. Never silently merge into `main`.
9. **Repeat:** Choose the next independent unblocked ticket; otherwise report the blocking dependency instead of making up progress.

**Stop rule:** If a deterministic failure repeats, stop the affected slice and create/record a diagnosis. Infra-only failures allow one bounded retry. No override of security policy, no destructive test on personal devices, no secrets in source or comments, no data-loss migration without backup and rollback. No fake sandbox success based only on process exit code.

## Program route and proof gates

| Milestone | User-visible outcome | Gate |
| --- | --- | --- |
| M0: Reproducible engineering baseline | A developer can run targeted tests on forked branches and see truthful results | Current SHA and executable test commands; no unverified success claims |
| M1: Host correctness and plugin integrity | Web entry points follow chosen Local/SSH/Relay host; valid npm archives install while altered archives reject | Widget + pure/integration tests; remote/device result separated |
| M2: Runtime recovery and safety | Crashes do not silently corrupt retained state and sandbox claims match enforcement; native phone policy tested at execution path | Crash, policy-bypass, and rollback scenarios; device gates where required |
| M3: Portable user state | Exported sessions and local workspace can be recovered after uninstall or APK re-sign without relying on lost app-private keys | Fresh-install import fixture, integrity and confidentiality checks, rollback |
| M4: Multi-host capability evidence | Feature availability, session list size, and connection failure semantics documented across Local/SSH/Relay | Capability matrix and measured payload profile |
| M5: Remote-First decision | Quantified comparison of an isolated thin-client build with existing bundle | APK size, startup, feature completeness, maintenance and compatibility measurements |
| M6: Release qualification | Reproducible build, documented known limitations, license/branding review and required device tests | No release without explicit approval |

## Dependency policy

- M1 Web and OHOS work is parallel; neither branch blocks the other.
- M2 security/crash studies can begin once test method is specified, but device-dependent claims remain blocked until a device is available.
- Portable implementation is blocked on state-inventory/key-recovery decision.
- Remote-First implementation decision is blocked on host capability evidence and an actual build-size measurement.
- Release is blocked on all relevant verification, including real-device checks.
