## Summary

BIMCraft's architecture suits AI-assisted development. It already relies on:

- every feature being a command;
- one place for validation, with rollback;
- a core with no UI;
- strict lints;
- tests that drive the UI as a user does.

The **guidance for agents** and the **file layout** don't scale, though. `CLAUDE.md` is a single 10,000-word file loaded in full every session, and it grows with each feature. Six source files are between 3,400 and 5,700 lines. The full test run takes about 12 minutes, most of it one test.

At today's rate, approaching Revit feature parity would overflow an agent's context window before the code itself became unmanageable. This issue proposes changes so the project stays maintainable with AI as it grows.

## What already works well (keep it)

- **Everything is a command** (`ALL` in `commands.rs`), so a feature is a new command plus a test, not edits scattered across files.
- **Validation lives in one place.** `Model::check` runs after every command and the engine rolls back on failure, so a mistake in one feature can't quietly corrupt the model.
- **The core has no UI.** Most logic is testable without a window, and the UI is a thin layer that changes the model only through `Session::execute`.
- **Lints enforce the rules.** No `unwrap`/`panic`/`unsafe`, `-D warnings`, and a sweep of hostile input over every command. An agent's mistakes show up as failures, not as hidden bugs.
- **Tests behave like a user** (egui_kittest: clicks, keys, labels), and drawing and IFC output are tested through their actual output: PNG pixels and STEP references. This is what lets AI-written changes be trusted.

## The problems

### 1. `CLAUDE.md` is one ever-growing file

About 80% of `CLAUDE.md` describes individual features in detail: walls and joins, roofs and the straight skeleton, masses, phases and design options, structure and MEP runs, families, graphics and templates, schedules, and the updater's Windows, AppImage and macOS internals.

Every agent session pays for all of it. An agent fixing a schedule filter still loads the macOS updater's `hdiutil` sequence and the straight-skeleton rules for roofs.

- Each feature adds a paragraph or more. At Revit-parity breadth this file would be hundreds of thousands of tokens: it wouldn't fit, and long before then it would crowd out the code being changed.
- There is no short map saying which module handles what. Agents find their way by grepping, which spends context on every task. In practice they often skip the long file once it's too big to keep in context.
- Rules (must never be broken) and descriptions (helpful background) are mixed together, so the rules get less attention.

### 2. Files too large to read in one go

At 3,000–6,000 lines (roughly 40k–80k tokens each), the large files can only be worked on by searching and reading slices. That's workable today, but it means agents edit code they have seen only partly.

- `commands.rs` collects every command in every domain in one file. It will keep growing, linearly with features.
- The two `tests.rs` files are the same pattern, and UI tests have only started moving into `tests/<area>.rs` (`dock.rs`, `browser.rs`, `autosave.rs`, `mep.rs`, `structure.rs`).
- A recent example from this repo: a scripted edit to `ui-egui/src/lib.rs` that searched for a marker string matched an identical doc comment 2,500 lines earlier. It duplicated half the file before the build caught it. Smaller files make that kind of slip both less likely and easier to spot.

### 3. The test loop slows as commands are added

The hostile-params test sweeps every command with every hostile input, so its cost grows with the number of commands. It is already about 11 minutes.

- A slow loop pushes agents (and people) to run only a filtered subset, or to skip the full run before a PR.
- Fast, complete feedback is what keeps AI-written code honest. This test is valuable and should stay; it just needs a fast tier.

### 4. Nothing checks pull requests automatically

CI on every PR is already a roadmap item. It becomes more important when work arrives as stacked PRs that are rebased before merge, as #19, #21, #26 and #28 just were. Each rebased commit should be checked again automatically.

## Could AI maintain BIMCraft at Revit feature parity?

**Mostly yes, if the structure above is kept. The limit is verifying results, not context size.**

- **Fits the pattern well:** another element kind, schedule field, IFC mapping, family category, ribbon tool or annotation type. Each is a command, a validation rule and tests in a few modules. AI can do this kind of work well and indefinitely, as long as a task only needs a few files.
- **Needs a human design owner:**
  - work that cuts across everything: worksharing and merging files, linked models, joins and cleanup between element kinds;
  - the performance architecture: GPU rendering (there is still no GPU acceleration), incremental validation and caching;
  - fidelity to Revit's behaviour.

  AI can implement these, but deciding the design and judging whether the result looks and behaves right needs someone who checks drawings and real projects.
- **Realistic scope:** Revit has decades of work behind it. Full parity is unlikely. Parity on the workflows people actually use (architecture, structure, documentation, MEP basics, IFC exchange) is reachable. The roadmap should say which subset is the target.
- **What makes AI maintenance safe** is test-first development with output-level assertions, plus human PR review. Neither should be relaxed as the project grows.

## Proposal

In order of impact on AI maintainability:

### 1. Split `CLAUDE.md` into layers (about a day, no behaviour change)

- **Root `CLAUDE.md` (aim: 2,000–3,000 words).** It holds:
  - the rules, as now (never crash, everything is a command, ids and GUIDs, validate in one place, clean-room, a core without UI, a thin UI, updates only through `crates/update`, test first);
  - the checks to run before finishing;
  - the conventions (units, axes, languages);
  - a module map: one line per module saying what it owns, e.g. `walls.rs`: wall outlines, joins and caps.
- **A `CLAUDE.md` inside each crate or area,** holding the detailed write-ups now in the root file. Claude Code loads a folder's `CLAUDE.md` only when files there are touched, so an agent working on schedules never loads the updater's details. Suggested split:
  - `crates/core/CLAUDE.md`: model, commands, validation, geometry conventions;
  - areas within core where the text is long: walls and roofs, phasing and options, massing, families, structure and MEP runs, graphics and templates, schedules, IFC;
  - `crates/ui-egui/CLAUDE.md`: palettes and docking, canvas and click handling, tests;
  - `crates/update/CLAUDE.md`: the update and install sequences for each platform.
- **`docs/` for long design notes,** opened when needed. `docs/autosave.md`, `docs/performance.md` and `docs/disciplines.md` already follow this.
- **Guard it with a check** (a test or CI step) that fails if the root `CLAUDE.md` passes a word budget, so it doesn't grow back.

### 2. Split the largest files by area (mechanical but large; one PR per file)

- `commands.rs` → `commands/{mod, walls, openings, roofs, floors, views, annotation, families, schedules, phasing, massing, structure, files}.rs`. `ALL` stays the single list.
- `model.rs` → element structs separate from the `Model` queries, grouped by area.
- `ui-egui/src/lib.rs` → ribbon, menus, view tabs and the app shell in separate modules (`dock.rs`, `browser.rs` and `settings.rs` already show the pattern).
- `tests.rs` (core and UI) → `tests/<area>.rs`, finishing the move the UI tests started.
- **Target:** no file needs more than about 2,000 lines read to change it safely.
- **Timing:** do each split immediately after a merge, one PR per file, so open PRs aren't conflicted for long.

### 3. A fast test tier

- Parallelise the hostile sweep across commands, and/or add a quick mode that samples commands, with CI always running the full sweep.
- Document per-area test filters (e.g. `cargo test -p bimcraft-core walls`) in each area's `CLAUDE.md`, so an agent can verify its change in seconds and run the full suite before the PR.

### 4. CI on every pull request (already on the roadmap)

- fmt, clippy and tests on Linux, Windows and macOS, plus IfcOpenShell validation, shellcheck and actionlint.
- Required before merge, including on rebased stacks.

### 5. Short decision records for cross-cutting choices

A page per decision: element ids and GUIDs, docking, autosave, CPU rendering now with GPU later, and so on. Each states the choice, the alternatives rejected, and the constraints that must hold. This stops a later agent from "simplifying" something that was deliberate. `docs/autosave.md` and `docs/performance.md` are good models.

## Definition of done

- Root `CLAUDE.md` ≤ ~3,000 words, with a module map; the rest lives in per-crate or per-area `CLAUDE.md` files and `docs/`, with nothing lost.
- No source file over ~2,500 lines.
- A documented quick test command that runs in under a minute; the full suite runs in CI on every PR.
- Decision records exist for the existing cross-cutting systems.
