## Confirmed documentation discrepancies to review

1. `docs/PRD.md` near lines 31, 38 and 298 still describes Python 3.10 in the current-looking CI/install matrix, whereas the published package requires Python >=3.11. Determine whether these sections are historical snapshots or current guidance; date/label historical content, and update current claims. Link #697 rather than duplicating its document edits.
2. `docs/PRD.md` near line 90 says SQLAlchemy <2.2, while `pyproject.toml` currently allows <2.3. Resolve through #774 and then align the PRD's current guidance, or mark the PRD version as historical.
3. `docs/SUPPORT_MATRIX.md` states that shipped types compile and separately records reflection and value round-trip limitations. Ensure summary language cannot be mistaken for a promise that every type reflects or returns native Python values. Preserve documented BLOB/CLOB, BIT/empty binary, and CUBRIDdb DECIMAL constraints.
4. `docs/SUPPORT_MATRIX.md` Alembic row (around line 113) says 'the whole upgrade is atomic by default' alongside `transaction_per_migration=True`. Check the actual Alembic implementation/tests and revise the wording to distinguish atomicity of a revision from a multi-revision upgrade, **only if the current claim overstates the tested contract**.
5. Review current-facing ORM, driver/server compatibility, and feature-support statements for conflation of: implemented vs tested; compile vs reflection vs binding vs value round-trip; supported versions vs tested combinations; recommendation vs deprecation; current policy vs historical evidence.

## Recurrence prevention (required)

The fix is not complete when the current prose is corrected. Prevent the same categories of mistakes from reappearing in future agent-generated changes.

### 1. Establish canonical sources and ownership
- [ ] Identify the canonical source for current Python/SQLAlchemy dependency bounds (package metadata), tested combinations (CI matrix plus run evidence), feature limitations (tests and reviewed support matrix), and driver recommendation/deprecation policy (reviewed support docs). Document ownership and update order without duplicating the source of truth.
- [ ] Mark PRD/roadmap and old release matrices as dated snapshots when appropriate. Current-facing pages must link to the canonical support matrix rather than maintain independent copies of version facts.

### 2. Automated consistency checks (targeted, not brittle)
- [ ] Extend existing repository/documentation tests, if present, to parse package metadata and check structured current-support declarations; include project dependencies AND dev/pycubrid extras. Do not compare free-form translated prose by exact string.
- [ ] Check that canonical/generated docs are synchronized through the existing generation process and that doc-only changes use lightweight CI.
- [ ] Add regression fixtures for previously observed errors: Python 3.10 incorrectly presented as current minimum, SQLAlchemy bound/support disagreement, and deprecated extras conflated with driver deprecation. Prefer structured assertions or targeted checks over global keyword bans.
- [ ] For support-claim changes not automatically checkable (e.g. ORM behavior, LOB, transactional atomicity), require linked test/run evidence or an explicit limitation/untested qualifier in the PR description.

### 3. Agent and reviewer guardrails
- [ ] Update AGENTS.md only after checking existing rules, with a short mandatory checklist: separate official/recommended/deprecated; compiled/reflected/bound/round-tripped; implemented/tested/supported; current/historical; per-version/per-driver results vs blanket claims.
- [ ] Require agents to inspect existing issues/PRs, identify the canonical source and affected translated/generated docs, and avoid inventing new support guarantees from tests merely being present.
- [ ] Require a focused reviewer checklist for changes to README, SUPPORT_MATRIX, DRIVER_COMPAT, CONNECTION, PRD, packaging metadata or release notes. Human review is needed for semantic claims; automation does not prove runtime correctness.

### 4. Verify the prevention works
- [ ] Add positive and negative regression cases: a legitimate historical 3.10 statement must be allowed; a current 3.10 minimum claim must be flagged; a deprecated extra statement must be allowed; declaring the supported CUBRIDdb driver deprecated must be flagged in current docs.
- [ ] Record the CI job(s), sample failures, and successful clean run on the candidate SHA.
- [ ] Confirm the added checks are scoped to relevant changed files and do not trigger the full live DB matrix for documentation-only edits.
- [ ] Document the rule owner and how to update checks when the supported version or driver policy intentionally changes.

**Acceptance gate:** Do not close #780 solely on documentation edits. Close only when the corrections and proportionate prevention checks/guidance are merged and verified. If a proposed check is not feasible, record the reason and a concrete review control rather than adding a fragile test.
