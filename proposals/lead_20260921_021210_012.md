# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**[system] A .env tier line without `export` never reaches a bot session: the tier loop skips `set -a`**

*Project description:*
## Summary
`start-bot.sh` builds each session's env file by writing four bare `. <tier>` lines and then wrapping **only** `bot.conf` in `set -a`. So a tier `.env` line written as `KEY=value` instead of `export KEY=value` becomes a shell variable in the pane shell and is *not* inherited by `exec claude` or its MCP servers — a silently unauthenticated integration, indistinguishable from a missing credential. The fix is four characters of placement: wrap the tier loop in `set -a` / `set +a` the way `bot.conf` already is. Bundled with it are five one-line config-surface items that each make the framework assert something untrue.

## Evidence

**Lead item — the export gap.**
- `lib/start-bot.sh:158-176` — the writer. The tier loop emits bare source commands:
  ```sh
  BOT_ENV_FILE="$BOT_DIR/.tmux-env"
  ...
  while IFS= read -r _sb_env_tier; do
      [ -n "$_sb_env_tier" ] || continue
      printf '. %q\n' "$_sb_env_tier" >> "$BOT_ENV_FILE"
  ```

- `lib/start-bot.sh:181-184` — `set -a` is opened and closed around `bot.conf` alone, with the reason stated in the comment: *"set -a auto-exports every assignment so vars reach `exec claude`."* The tier loop above it gets no such wrapper.
- `lib/start-bot.sh:221` — `CLAUDE_CMD=". '$BOT_ENV_FILE'; exec $CLAUDE …"`. The pane shell sources the file and then `exec`s, so only *exported* names cross into the CLI and the MCP children it spawns.
- Why the values usually arrive anyway, and when they do not: `lib/start-bot.sh:54` calls `source_env_tiered` (`lib/lib-common.sh:390-411`), which routes every tier through `parse_env_file` — and that helper always `export`s (`lib-common.sh:383`). A **newly created** tmux server inherits that parent environment, which masks the defect. A session created inside a **surviving** per-bot tmux server does not: the pane gets the server's environment, and `.tmux-env` is then the only path — which is precisely the belt it exists to be. So the exposure is a keepalive restart, a `/reload`, or any re-session after a credential was added or rotated.
- Measured on the host, 2026-09-20 (key names only, never values): one fleet's tier `.env` carries `plain:VERCEL_AUTOMATION_BYPASS_SECRET` alongside `export:GITHUB_PAT` and `export:NOTION_TOKEN`; the host and root tiers each carry two more plain-assigned token lines. The composed `.tmux-env` for a worker on that fleet contains exactly four bare `. <tier>` lines followed by `set -a` / `. …/bot.conf` / `set +a`.
- The same var is a *declared requirement*: that fleet's `projects.yaml` records `bypass_env: VERCEL_AUTOMATION_BYPASS_SECRET` for its preview-tier project, with the comment *"this records that the project REQUIRES it, so a fresh box knows before someone hits the wall."* `grep -rn bypass_env claudlobby/ lib/ library/ documentation/` in the checkout returns **zero hits** — `config.py:253` carries `preview` as an opaque `dict[str, Any]` and nothing reads inside it (#993). `creds-reconcile` correspondingly reports the var as a shape-2 orphan: a value with no equipped consumer.
- Two more framework facts that make this the onboarding shape rather than a drifted one: `claudlobby/commands/_helpers.py:65-66` documents that both `VAR=value` and `export VAR=value` occur in the wild and that `env-migrate` writes the bare form; `claudlobby/composer.py:3182-3185` writes `export VAR=` stubs, so a hand-added or migrated line is the one at risk and the scaffolded one is not.

## Why this matters
The lead item's failure mode is the one the estate is worst at seeing: a credential that is *assigned* and not *equipped* produces an unauthenticated MCP server or a deaf integration, which returns real-looking data rather than an error. It is the same silent-downgrade class as an empty token, arriving by a different route, and no door can distinguish them — `creds-reconcile` says "no consumer", `validate` says nothing, and the bot reports success.

It also removes the point of a declared requirement. A fleet wrote down that its preview-tier project *requires* a bypass secret so that "a fresh box knows before someone hits the wall"; the value was then placed in a form the session cannot see, and nothing reads the declaration either. The fresh box hits the wall.

The five bundled items are individually trivial and collectively expensive: they are five places where a reader who trusts the framework's own words is sent to investigate something that is not there — a missing bot, a non-existent MCP server, a deprecated tier that is load-bearing, a validation that does not happen — and they land inside a warning wall where the real defects also live.

## Proposed fix
1. **`lib/start-bot.sh:173-176` — wrap the tier loop.** One `printf` before and after the loop, mirroring `:182-184`:
   ```sh
   # after
   printf 'set -a\n' >> "$BOT_ENV_FILE"
   while IFS= read -r _sb_env_tier; do
       [ -n "$_sb_env_tier" ] || continue
       printf '. %q\n' "$_sb_env_tier" >> "$BOT_ENV_FILE"
   done < <(env_tier_present_files "$BOT_DIR" "${FLEET_NAME:-}")
   printf 'set +a\n' >> "$BOT_ENV_FILE"
   ```
   Extend the comment above the loop to say *why*: a tier file may legally use either `KEY=value` or `export KEY=value` (`_helpers.py:65-66`), so the writer must not depend on the author's choice. Keep the `bot.conf` wrapper separate rather than merging the two into one `set -a` region — the Telegram-token block between them (`:197-203`) must stay outside it, since it deliberately `unset`s an empty value.
2. **B1 — `claudlobby/validator.py:1256-1258`.** Resolve the reference across fleets before warning, and warn only when it resolves nowhere on the host:
   ```python
   if bot.reports_to and bot.reports_to not in fleet.bots:
       if not _bot_exists_on_host(bot.reports_to, paths):        # paths._iter_fleet_dirs
           report.warnings.append(
               f"bot '{bot_name}': reports_to '{bot.reports_to}' names no bot in this fleet "
               f"or any other fleet on this host")
   ```
   A cross-fleet coordinator then validates clean, which is what `config.py:759-783` already rules it to be.
3. **B2 — `claudlobby/validator.py:678-684`.** Branch the consequence on the declaring surface:
   ```python
   if not req.secret:
       consequence = "the server or tool will start with this unset"
   elif req.origin.startswith("mcp/"):
       consequence = "MCP server will start and serve ANONYMOUSLY (unauthenticated), not fail"
   else:
       consequence = "the CLI or tool call runs unauthenticated at use time and fails there"
   ```
4. **B3 — `claudlobby/composer.py:2161-2186`.** Make the resolution declared rather than ambient: add an optional fleet field `claudron_bin` (schema + `known_values` + `documentation/fleet-yaml-schema.md`), prefer it, and fall back to the composed unit's own `Environment=PATH` — which the composer already writes — before `shutil.which`. Scope the WARN to that run-host PATH so the three doors stop warning about a condition they cannot observe.
5. **B4 — `lib/lib-common.sh:390-411`.** Make `source_env_tiered` a consumer of the door one file over, so the order exists once as `env-tiers.sh` claims:
   ```sh
   source_env_tiered() {
       while IFS= read -r _t; do
           [ -n "$_t" ] && parse_env_file "$_t"
       done < <(env_tier_present_files "${BOT_DIR:-}" "${FLEET_NAME:-}")
   }
   ```
   Move the root-tier deprecation notice into `env_tier_rows`' caller-visible output (or drop it): as a per-boot stderr line it is noise in the one log an operator reads during a boot incident, and it advises a move that has already been made.
6. **B5 — `lib/lib-common.sh:10`.** Correct the index line to `load_bot_conf — source bot.conf (NOT validated; see #1350)` so it stops asserting a control that does not exist. Whoever lands #1350 makes the original wording true and can restore it.

Dependencies: item 1 is independent. B2 touches the same `validator.py` block as the empty-MCP-secret issue — land that one first or take its rebase. B3 partially delivers #681 (consolidating the three `shutil.which("claudron")` probes); do the consolidation there, the declared field here. B5 is a comment-only precursor to #1350. Reading `projects.yaml`'s `bypass_env` as a checkable requirement is **#993's**, not this issue's.

## Rollout & risk
Risk: **low-medium.** Item 1 makes *more* variables reach the session; the risk is not absence but surprise — a tier file containing a bare assignment that was previously inert now takes effect, including an inert bare `KEY=` that will now export an empty value and, under shell semantics, beat an upstream real one. Before rolling, read the tier files' **key names and export form** (never values) on the host and confirm no bare `KEY=` empty stub exists at a less specific tier than a real value.

Rollout, per the `canary-rollout` protocol: land items 2–6 (report/text/compose only) first. For item 1, restart **one** bot, diff its `.tmux-env` against the previous copy, confirm the pane's `claude` process carries the expected names, and watch its `data/events/*.jsonl` and pane for a clean boot before the fleet. B3 changes composed bytes for vault-wired bots — `generate --bot <name>` and `diff` first.

Backout: every item is an independent revert. Item 1's artefact is regenerated at each boot, so reverting the script and restarting restores the previous `.tmux-env` exactly.

## Out of scope
- **Reading `projects.yaml` requirements** (`bypass_env` and the rest of the `preview` block). That is #993's deliverable and it is a different mechanism: a checkable declaration, not an export. This issue only fixes why the value cannot reach a bot even when it is present.
- **`MANAGER_TMUX` vs `reports_to`** (#1257 / #475). B1 fixes the *wording*; the load-bearing half — a sub-manager's `report-back.sh` sending to itself — is that issue's and must not be touched here.
- **Consolidating the three `claudron` PATH probes** (#681) and **validating `bot.conf`** (#1350). B3 and B5 are the parts that fit in this PR; the mechanisms belong to those issues.
- **Retiring the root `.env` tier.** B4 drops a duplicated order and a misleading notice; deciding the tier's future is a config-surface decision with its own migration.
- The specific wrong turn: **merging the tier region and the `bot.conf` region into one `set -a` block.** It reads as the tidier edit and it swallows the Telegram-token block at `:197-203`, whose whole purpose is to `unset` an empty `TELEGRAM_BOT_TOKEN` — inside `set -a` the intermediate `_tg_tok` also exports, and an empty token silently kills the inbound bridge with the bot still reporting "Listening". The second wrong turn is "fixing" this by rewriting the tier files to use `export`: that repairs one host and leaves the framework producing the same trap for the next one, and `env-migrate` will write bare lines again.
