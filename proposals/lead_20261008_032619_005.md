## Case study

External project: https://github.com/kanumuri9593/Baton

Baton is a local execution control plane for people and coding agents. It manages runnable targets, dev-server and Flutter/React Native sessions, git worktrees, simulators/devices, logs, network evidence, screenshots, proof bundles, and an MCP surface over the same daemon state.

This makes Baton a useful **case study for a broader AI coding-runtime problem**:

> As coding agents gain direct control over local runtimes and debugging evidence, secrets and PII can cross the agent boundary without ever being committed to source control.

This issue does **not** propose that Redact Secret build or maintain a Baton-specific adapter. Baton is being recorded because its implementation makes several recurring exposure paths concrete and inspectable.

## Observed sensitive-data paths

### 1. Ignored local configuration is copied into alternate worktrees

Baton supports running a target from the current checkout, an attached worktree, or a Baton-owned worktree.

Its checkout implementation intentionally searches the source checkout for local configuration such as:

- `.env*`
- `*.local.json`
- names beginning with `secrets`
- `google-services.json`
- `GoogleService-Info.plist`
- files referenced by Flutter `--dart-define-from-file`

and copies those files into the selected or Baton-owned worktree.

Relevant source:
- https://github.com/kanumuri9593/Baton/blob/main/src/core/checkouts.ts

The product motivation is understandable: a detached or agent-owned worktree often cannot run without local configuration that is intentionally gitignored.

The security consequence is also clear:

```text
developer checkout
  .env.local
  secret-bearing config
        |
        | copy
        v
agent/tool-owned worktree
        |
        v
runtime process
```

This increases the number of plaintext-at-rest locations and can extend secret lifetime beyond the original checkout.

Potential failure modes include:

- abandoned Baton-owned worktrees retaining copied secret files;
- attached agent worktrees receiving local files that the agent did not previously possess;
- cleanup failure leaving duplicated plaintext under tool-owned directories;
- debugging tools, indexing systems, backups, or other processes observing the copied material.

### Redact Secret relevance

This exposes a product problem larger than Baton:

**Can an agent runtime receive only the secrets required for a specific run without duplicating the source secret file into every worktree?**

A generic direction worth researching is an authority-backed runtime-release contract:

```text
trusted source / captured mapping
           |
           v
redact-secret-vault authority
           |
           | project
           | checkout
           | target
           | session
           | purpose
           | expiry / budget
           v
approved runtime fields
           |
           +--> process environment
           |
           +--> narrow temporary materialization when unavoidable
```

Important boundary:

- Redact Secret should **not** become a general-purpose secret manager.
- The external runtime remains responsible for process and worktree lifecycle.
- `redact-secret-vault` would own capture/mapping/grants/lifetime where reversible handling is used.
- planned `restore` would own reconstruction after successful preflight, not authorization or persistence.

The preferred end state, where technically possible, is **no plaintext secret-file copy at all**.

---

### 2. Process stdout/stderr and diagnostics become agent-readable evidence

Baton supervises child processes and retains bounded logs per session. The same daemon state is exposed to human CLI/HUD clients and to MCP tools such as `read_logs` and `diagnose`.

Relevant source:
- https://github.com/kanumuri9593/Baton/blob/main/src/core/session-base.ts
- https://github.com/kanumuri9593/Baton/blob/main/src/mcp/index.ts

This produces another common AI coding-runtime boundary:

```text
application process
      |
      | stdout / stderr / diagnostic
      v
runtime controller
      |
      v
MCP / coding agent / LLM
```

A source repository may contain no credential at all while the running application logs:

- connection strings;
- authorization headers;
- signed URLs;
- session identifiers;
- database errors containing credentials;
- customer PII/PHI;
- payload fragments;
- third-party SDK diagnostics.

### Redact Secret relevance

This maps directly to existing core capabilities.

A product-generic evidence filter could treat runtime logs as an outbound sink:

```text
raw runtime logs
      |
      v
redact-secret core
      |
      v
safe diagnostic text
      |
      v
agent / model / run history
```

Irreversible redaction should be the default. Reversible capture is only justified when a trusted human/debug destination has a concrete need to reveal a value later.

Research questions:

- How much diagnostic usefulness survives redaction?
- Should structured log fields be preferred over free-text rewriting when available?
- Can one policy protect both live streaming and persisted run history?
- What must be removed from error objects and metadata as well as human-readable text?

### 3. Network inspection exposes especially sensitive material

Baton can collect HTTP request information and expose request details to MCP clients.

Its shared network model includes:

- URI;
- request/response headers;
- cookies;
- request body;
- response body;
- status/timing information.

Relevant source:
- https://github.com/kanumuri9593/Baton/blob/main/src/core/types.ts
- https://github.com/kanumuri9593/Baton/blob/main/src/mcp/index.ts
- https://github.com/kanumuri9593/Baton/blob/main/src/daemon/network.ts

This is a high-value debugging feature and also a high-value sensitive-data surface.

Typical examples include:

```text
Authorization: Bearer <credential>
Cookie: session=<credential>
Set-Cookie: ...
POST /customer
{ email, phone, SSN, health data, ... }
```

The critical point is that the model-facing tool may not need the original values to diagnose most failures.

### Redact Secret relevance

This is a strong candidate for a generic **agent evidence boundary**:

```text
runtime network capture
        |
        v
header/body-aware redaction
        |
        v
sanitized request evidence
        |
        v
agent / LLM
```

Potential product directions to research:

- secret/credential filtering in headers, URI query values, cookies, and bodies;
- PII-aware body filtering under an explicit PII profile;
- preserving HTTP structure and debugging context;
- separating metadata that is always safe from payload fields requiring inspection;
- preventing raw bodies from entering model context by default.

Reversible handling should remain exceptional and destination-bound.

---

### 4. Proof bundles can persist leaked runtime evidence

Baton has a `proof` workflow that can gather runtime state into durable artifacts. Current proof concepts include:

- session state;
- logs;
- network summaries;
- screenshots;
- per-cell evidence;
- packaged proof bundles.

Relevant source:
- https://github.com/kanumuri9593/Baton/blob/main/src/daemon/proof.ts

This illustrates a broader issue:

> Agent-generated verification evidence can become a new persistence layer for secrets and PII.

Even if exposure to the model is temporary, a proof bundle, debugging archive, run history, or generated artifact may persist the sensitive value much longer.

### Redact Secret relevance

Evidence should ideally be sanitized **before persistence**, not only when displayed later:

```text
runtime
   |
   +--> log
   +--> network
   +--> diagnostic
          |
          v
      sanitize
          |
          v
      proof artifact
```

Questions to research:

- Should proof artifacts contain only already-sanitized evidence?
- Can a tokenized proof retain controlled human-debug capability without embedding plaintext?
- How should screenshots be treated, since text redaction alone does not protect visual exposure?
- Should persisted evidence have a stricter policy than live interactive evidence?

## Where the existing Redact Secret products fit

### `redact-secret` core

Best fit:

- irreversible secret filtering for logs/diagnostics;
- filtering HTTP textual evidence;
- optional PII profiles where appropriate;
- preventing raw sensitive values from reaching agent/model context.

Core should remain side-effect free and should not learn Baton-specific concepts.

### `redact-secret-vault`

Best fit where reversible workflows are actually needed:

- short-lived capture/mapping lifecycle;
- source/capture binding;
- sink/path grants;
- expiry/revocation;
- use budgets;
- server/current-policy authorization;
- optional persistence under the vault's own qualified profiles.

Baton or another runtime should supply trusted runtime context. A model-provided claim such as "I need this secret for debugging" must never become authority.

Potential runtime context worth studying:

- project identity;
- checkout identity;
- target identity;
- runtime session/process identity;
- purpose;
- requested destination/field;
- human approval where applicable.

### planned `restore`

The planned repository should remain the reconstruction component:

```text
tokenized approved output
        |
        v
build restore plan
        |
        v
vault authority preflight
        |
        v
bulk consume / resolve
        |
        v
one-pass reconstruction
```

It should not store secrets, decide policy, or become Baton-aware.

---

## What Redact Secret should NOT claim to solve

This case study must not imply that Redact Secret secures Baton as a whole.

Out of scope:

- Baton daemon authentication;
- localhost threat model;
- MCP permission design;
- process sandboxing;
- child-process tree cleanup;
- worktree ownership correctness;
- simulator/device isolation;
- filesystem permissions;
- arbitrary malicious local code.

Those remain Baton/runtime responsibilities.

Our narrower claim would be:

> Redact Secret can reduce unnecessary plaintext propagation across runtime-input and runtime-evidence boundaries when the host provides an integration point.

## General pattern extracted from Baton

The useful product abstraction is not "Baton adapter".

It is:

### Agentic Development Runtime Sensitive-Data Boundary

```text
             trusted developer environment
                        |
        +---------------+----------------+
        |                                |
        v                                v
 runtime inputs                     runtime outputs
 env/config                         logs/network/proof
        |                                |
        v                                v
 scoped release                   redact before agent
        |                                |
        +---------------+----------------+
                        |
                        v
                 coding-agent loop
```

This pattern potentially applies beyond Baton to:

- IDE-integrated coding agents;
- agent-created worktrees;
- local execution supervisors;
- DevPod-like environments;
- Docker Compose development workflows;
- CI/sandbox agents;
- MCP-based runtime/debugging tools;
- future autonomous coding systems.

## Outcome expected from this issue

No Baton code is required.

The desired result is a documented example showing that the Redact Secret ecosystem can address a real emerging problem:

**AI coding agents increasingly consume and persist runtime data that contains secrets and PII, while local development tools increasingly duplicate or materialize secret-bearing configuration for isolated agent workspaces.**

Baton gives us a concrete implementation to study. The product opportunity is the reusable sensitive-data boundary, not the vendor-specific adapter.
