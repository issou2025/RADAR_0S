## Bounded acquisition target

Establish a deterministic, reviewable inventory for every non-default ref that records at minimum:

- exact branch/ref name and immutable head SHA at observation time;
- association with an open PR, merged PR, closed-unmerged PR, active issue/lane, automation/validation purpose, or genuinely unassociated ref;
- independently resolved merge base plus ahead/behind status against the then-exact protected default tip;
- exact changed-path summary sufficient to identify source/docs/workflow/schema/package writer overlap without copying repository content into the evidence;
- last commit identity/time as an observation signal only, never as automatic deletion authority;
- lifecycle classification such as `ACTIVE_WRITER`, `STACKED_DEPENDENCY`, `RETAINED_AUDIT_OR_INCIDENT`, `SUPERSEDED_RETAINED`, `UNCLASSIFIED`, or `RETIREMENT_CANDIDATE`;
- bounded rationale and owning PR/issue/reference for the classification; and
- evidence timestamp/version so a stale inventory cannot be reused as a permanent lease claim.

Classification must fail closed on ambiguity. A branch is **not** a retirement candidate merely because it is old, diverged, named `tmp`, has no open PR, or looks superseded. Exact path overlap, PR association, active writer evidence, stack ancestry, incident/provenance value and rollback/recovery needs must be evaluated first.

## Retirement safety contract

Any future retirement mechanism must:

- begin with read-only/dry-run inventory and produce an explicit candidate set;
- never delete or rewrite protected refs, active PR heads, stacked predecessors, unresolved source/docs writers, evidence needed for an active incident/audit, or a ref whose ownership is ambiguous;
- require an auditable reason that a candidate is merged, normally superseded, or otherwise no longer authoritative for any active source/docs/workflow/schema/release surface;
- preserve exact head SHA and owning history in the evidence before deletion so later diligence can distinguish intentional retirement from lost history;
- make branch deletion a separate explicit governed action, never an implicit side effect of inventory generation;
- avoid force-update, destructive rebase, hidden history rewrite, or deletion merely to "free" a writer lane;
- define operator recovery/recreation guidance where Git object retention is not a sufficient operational guarantee; and
- prove idempotency and bounded failure behavior if automation is eventually introduced.

A `RETIREMENT_CANDIDATE` classification is evidence for review, **not approval to delete**. Normal GitHub governance and then-live permissions remain authoritative for any mutation.

## Acquisition / control objective

A buyer or new maintainer should be able to answer reproducibly:

1. Which branches can still modify each commercially material source/docs/workflow/schema/release surface?

4. Which refs are genuinely safe to consider for retirement, and what evidence supports that conclusion?
5. Has branch hygiene changed since the previous evidence snapshot without silently invalidating writer-safety assumptions?

The output should be machine-readable and content-bounded; it must not expose credentials, DSNs, prompts/results, provider data, arbitrary commit bodies beyond what is necessary for stable identity, or private incident content.
