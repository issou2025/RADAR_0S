### WHAT TO LOOK AT

**A checklist, not a script. Skip what does not apply and say you skipped it. Follow anything that
smells, even if it is not listed.**

1. **Correctness and failure modes** — especially anything that **fails silently, or reports success
   for something it did not actually verify.** A check that passes because it checked nothing is the
   single most valuable thing you can find here.
2. **Tests** — do they exist, do they run, do they assert anything real? **Can any of them pass
   vacuously** — empty fixture, skipped case, a filter that matches nothing, an assertion on a value
   the test itself computed?
3. **CI** — what actually runs, what is *required* to merge, and what is **green by absence** because
   nothing was required.
4. **Security** — secrets in the tree or in logs, file and directory permissions, anything privileged,
   command injection and unquoted expansion, path traversal, dependency supply chain. **Note who can
   write what, especially for anything that runs as root or as a daemon.**
5. **Error handling and the ergonomics of failure** — when it breaks, does the message say what
   happened and what to do? Are exit codes meaningful and consistent?
6. **Docs versus reality** — does the README describe the code that exists **today**? Name anything
   that documents a flag, path, command or behaviour that is gone or renamed.
7. **Structure and maintainability** — dead code, duplication, oversized functions or files, unclear
   boundaries, things that are hard to change safely.
8. **Dependencies** — currency, pinning, deprecation, anything unmaintained.
9. **Consistency across the surface** — naming, flag spelling, error phrasing, exit codes. *A tool
   that is inconsistent with itself is a tool nobody can predict.*
10. **Performance and cost** — hot paths, anything quadratic, and **any external API or rate-limit
    budget being spent carelessly.**
11. **Reproducibility** — can someone build, test and run this from a clean checkout by following the
    docs alone? Try it if you can.
12. **Whatever surprised you.** Keep a running "I did not expect this" list. *It is often the most
    useful section.*

### HOW TO WRITE A FINDING

**Each one carries: a one-line claim · severity · the evidence · why it matters · a suggested
direction.**

- **Evidence means `file:line`, or the literal command and its output.** Never a description where the
  command would do, and **never a claim you did not actually run.**
- **A suggested direction, not a patch.** You are not fixing it and you may not have the context to
  choose between two fixes. Say what the options look like.
- **Rank by severity and put the worst first.** Do not pad.
- **Prefer a few high-confidence findings to many speculative ones** — then add a short
  `WORTH A LOOK` tail for the uncertain ones, clearly marked as uncertain.

### !! A REQUIRED SECTION: `WHAT I COULD NOT CHECK, AND WHY` !!

**An audit that reports only what it found reads as complete.** Every report must end with this
section: what you could not build, could not run, had no credentials for, could not understand
without context, or ran out of time on.

***`UNMEASURED` is a real verdict and it beats silence.*** *A gap you name is a gap someone can close;
a gap you omit is one everybody assumes is clean.*

### One practical warning

**Never pipe a verification into `head`, `tail` or `grep` and then read `$?`** — the exit code you get
is the pipe's, not the command's. Run it alone, read the code, then filter for display.
