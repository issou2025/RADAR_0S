# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: workflows — scenes as data, FTS grouping, the patch list, headphones, comps in a stack, the golden session**

*Project description:*
Spec collapsed from the wayfinder map #16 (22 decisions, 2026-09-14). The workflow spec's rules (`docs/spec/session/workflows.md`, tracey `flow.*`) are the requirements; this issue is the buildable plan that satisfies them. Every decision below links to the ticket that made it.

## Problem Statement

Editing and mixing a project in the session window today works only on the reference drum session. Scenes are hand-written Rust functions matching literal track names; the three "presets" hide tracks while scenes only size them; REAPER's track groups, take lanes and comp areas are invisible to the facade, so nothing can comp a kit or gang a performer's arm; inputs are set track by track with nothing above the session to say where they come from; every performer's headphone mix is wired by hand; the golden session is a Python script that drifts from the template it is supposed to prove; and CI is red for reasons unrelated to any change, so nothing gates a flow that loses its verification. An engineer tracking a band, a player looking at the tablet, a producer switching the vocal language, or an agent asked to build any of these flows has no reliable shape to work against.

## Solution

Make the session window a control surface over REAPER's own data model, on REAPER and on daw-standalone alike, driven by data the dynamic template owns:

- Scenes become a data table resolved by one engine in the dynamic template, keyed by taxonomy, following the DAW mode per instrument and audience, regrouping rows by performer while tracking, and rendering to committed pictures.
- Grouping is provided by an FTS watcher for the booleans and by REAPER VCA groups for the faders, allocated deterministically from the top of the range.
- The patch list is an album-level styx file resolved through a studio profile, applied to every session's inputs as one undo step, with a per-session override.
- Headphone buses are template tracks created by apply; the cue send is the record of who played what; the performer row is a control surface over those sends.
- Comps are REAPER's named comps in a stack (COMP → EDIT → TUNE); the hit list is stretch markers; folder items are views over the children's takes; every instrument's comp, edit and align flow is the kit's landing with a different folder in the kit's place.
- The golden session is the template applying itself to a fixture album through the real apply path, in Rust, with its RPP and every scene picture committed and a test per golden rule.
- CI is green on main and gates every `flow.*` rule that has lost its verify.

## Implementation Decisions

### Scenes as data (#28)

- One engine in the dynamic template owns scenes. The window's hand-written scene functions and the three presets retire once every scene, expressed as data, reproduces its render fixture byte-identical. Scenes own show and hide; there is no preset layer.
- Rust first: a static table of Facet-derived `Scene` values in a new dynamic-template scenes module; the styx file, its schema and the user and session override layers are a later step. The resolve function carries layering semantics (append by slug, replace) now, tested with in-code fixtures.
- Types: `Scene { name, slug, instrument, modes, audience (engineer | player), group_by (arrangement | performer), spec (the flow rule ids it implements), default effect, rules }`; `Rule { selector, effect, optional arrange and mixer overrides }`; `Selector { group path (prefix match), kind, role (bus | leaf), rank (all | topmost-per-instrument), performer, layer, channel, multi-mic, arrangement, name }` — taxonomy first, `name` only for a user's own one-off folders, no negation; `Effect { size (minimum | compact | normal | working | focus), fold (open | small | collapsed | hidden) }`. Rules are ordered, last match wins, the scene's default covers the unmatched.
- Every template-created folder and track carries a taxonomy kind in its ext-state (Process, Verb, Compress, FX, MIX BUS, Drum Kit, Guide, Keyflow, Headphones, the VCAs); selectors match kinds, never names, for those.
- Class-to-pixel tables live in the same definition, separately for row height and strip width, plus the focus parameters; the window's settings become consumers of them.
- Output is a row list, `Row { target: Track(guid) | PerformerHeader(performer), depth, size, fold }`; the window renders it as-is, the REAPER applier walks it, skips headers, and applies show, compact and size to real tracks.
- `group_by: performer` synthesises one header row per performer under each instrument folder, identity from the Performer dimension else the headphone bus, ordered by the patch list once it exists (an ordering function is injected). Engine invariant: a stereo pair's half is always a rail. Common prelude, overridable: Guide and Keyflow collapsed in every scene; Write and Produce open Keyflow.
- Follow-mode: the default for (mode, instrument, audience) is the one scene declaring all three, two claiming the same triple is a validation error, a scene with no mode is recall-only. The instrument is the selected track's, else the shown scene's, else Drums. Modes without a default leave the current scene alone. A window carries an audience setting, default engineer.

### FTS grouping (#30, amended)

- Watcher provides the booleans: the rig gang (performer × source kind: input, arm, input monitoring) and the layer gang (a layer's channels arm together). REAPER VCA groups provide fader-follows-folder and one VCA per language. Which folders get a VCA lead is derived from routing: a folder whose children route past it to a bus gets one; a folder that sums its children gets nothing.
- The language switch writes the active language once; the watcher sets the language VCAs' mute from it. Amendment: whether a VCA lead's mute reaches its followers in REAPER is unverified and standalone says no, so the first commit is a REAPER test; if it does not propagate, the switch mutes through the mute gang on the same FTS slot on both backends. Mute propagation through whichever family is a facade behaviour standalone implements in its engine.
- Slots are assigned from 128 downward, deterministically from the template (language VCAs first, then folder VCAs in golden order), named with an `FTS` prefix and the purpose, which is also how the watcher recognises its own slots on a project it did not create. First commit: a REAPER test that names slot 128 and reads it back; fallback starts the walk at 64.
- Facade round-trip in the daw repo, tagged before the watcher: a per-family group-flag setter (track, slot, family, lead | follow | none), wrapped in daw-control, implemented on REAPER over its family mask and on standalone with track grouping widened to 128 slots and every family; the file writer emits group flags so round-trips keep groups.
- The echo guard is idempotence: the watcher computes desired state and writes diffs. One module in the dynamic template extension over the facade's track events, in-process against standalone and inside REAPER alike. Language VCA membership is a projection of the Language dimension, re-derived on every track event.

### The patch list (#29)

- Styx from day one, Facet types, a schema, a round-trip test. One shape: performer → source kind → channel or mic → input role; kits are the drummer's rig of kind drums keyed by piece and mic; basses a rig of kind bass keyed by channel; headphone buses listed the same way with who each is for; MIDI sources are entries. On load it lowers to flat (selector, role) entries using the scene `Selector` vocabulary. Two entries on one role is a validation error unless the profile marks the role shared.
- Album file found by walking up from the project's directory to the first directory holding one. Studio profile in the app config directory, the active one a per-machine setting defaulting to the hostname; the profile owns the role vocabulary (an inputs table of role → device channel or MIDI device and channel, an outputs table of bus role → output pair), with an optional patchbay endpoint per role that patchbay uses to build and verify the profile; apply never needs patchbay. An unknown role shows as unresolved.
- Session copy and override in project ext-state: the full text last applied with profile name and timestamp, and a partial document in the same schema whose entries replace by key and cannot delete.
- Apply is manual, one undo step, inputs only; arm and monitoring belong to the gangs. Unpatched tracks and unused entries are view states counted on the apply span. Never auto-apply; the view shows stale with a diff. Edits in the view write the album file by default and the override behind a visible "for this session" toggle.

### Headphone buses and performer identity (#31)

- Apply creates one track per bus under the HEADPHONE MIXES monitor bus, named `HP <performer>`, `HP Engineer`, `HP Producer`, `HP Broadcast`, kind and performer ids in ext-state, hardware output from the profile; it never deletes one. A bus may be for a group.
- A performer's bus receives their own source tracks directly, every instrument bus and the vocal bus at unity, and the Guide folder; never the master. Engineer and Producer receive the mix bus plus talkback; Broadcast the mix bus only. Talkback mics send to every performer bus and the engineer's, never the mix. Every cue send is post-FX pre-fader.
- The send is the assignment; when both exist the Performer dimension wins and the watcher rewrites the send. The performer row is a synthetic header row from the scene engine showing the rig, the gang toggles, the "me" and "band" levels and the bus output; "more of me" and "the band" are gang controls over sends written as diffs; the row's only own state is which performer it is.

### Folder items (#27, from the prototype)

- Sum rule: min of mins and max of maxes per column and per role; never a mean. Colour layering: an outer envelope of everything in the dim track colour, then toms, snare and kick opaque on top in the role colours, kick last. At the Channel level the fold groups by side instead of role, L and R in their own shades as one stereo waveform.
- Cache: one picture per (folder revision, mute mask, take, zoom bucket, style, rule), replayed like the docked stack's cache; zoom is in the key because the fold is on a column grid. Muted leaves the sum and bumps the revision; hidden stays in and replays from cache.
- Lane layout: one lane per take, each the take's folder item, and a comp lane on top built from regions, unchosen stretches dimmed with crossfade wedges. Bleed is gated by the piece's hit list when one exists.
- Peaks come from the existing take-peaks RPC on both backends; the REAPER backend's peak shim (hardcoded rate and channel count, ignores offset and rate, wrong buffer layout) is fixed as part of wiring it. Record preview: while a folder's armed sources record, the window accumulates the 30 Hz meter stream into a column buffer, folds it per the rule, and replaces it with real peaks when the take lands; window-side only.

### Comps and hits (#35, #36, #37, #38, #39; map rule)

- Comps are REAPER's named comps in a stack: COMP from the take lanes; EDIT from COMP, the working copy every edit lands on; TUNE from EDIT for vocals, holding retuned audio. Take lanes and COMP are never edited; re-comping makes a new COMP and EDIT. A group comp writes one comp area per source track with identical regions; a piece taken out is that track's regions differing. The folder's comp lane is a view over the sources' comp areas.
- The hit list is stretch markers on the EDIT comp's items on every mic of the piece; detection writes them as one undo step, re-detection replaces them, hand-placed hits are the same thing, slip and nudge are marker moves. Trigger velocity is measured from the piece's audio at the marker when the trigger is rendered, cached nowhere. The trigger track is a MIDI item into signal-sampler, one note per hit, rewritten when a hit moves, blended on the piece's Sum.
- The edit scene and the docked stack fold from the same taxonomy (a piece is the multi-mic group under Drum Kit; a bass or percussion layer, a guitar channel, a vocal part take the piece's place) and read the DAW's item and time selection. The editor's engines are kept; their write path moves from a patched project file to live facade item edits as one undo step to every mic. The project-file path stays for the standalone editor only.
- Alignment references: the kit's reference take; L channel for a guitar double; the lead's Main EDIT comp for the active language for vocals. Phrase boundaries for vocal crossfade snapping come from gaps in the lead's Main pitch blobs.
- The daw round-trip for lanes (tagged before comping lands): lanes read on the REAPER backend, a lane writer, a comp-area type parsed and written, named comps, standalone parity; the two project-file loaders' disagreement on lane fields is fixed on the way.

### Growing a part and defaults (#37)

- L/R is the Channel dimension for guitars; DBL stays a vocal Layer: a Channel shares a chain, a Layer has its own. Double, add an arrangement, add a layer, add a source are session actions over the facade in the architect action idiom, one undo step each, inserting the missing folder level only when a level gains its second member, naming new tracks from the template's dimension vocabulary; items and routing untouched. Source defaults are applied once at creation by the grow actions and by the golden builder; nothing re-applies.

### Vocals and MIDI (#38, #39)

- Language becomes a taxonomy dimension (EN, ES, PT, All), read from the name or inherited from a Language folder, at source level under Performer and Layer. The active language is project ext-state with two projections: the vocal scenes' common prelude hides sources of other languages, and the watcher sets the language VCAs. A performer's mix track is a plain folder with Main and DBL folders and one source per language under each, parent sends on; no VCA for the mix track.
- The MIDI count-in is the guide's, heard on the headphone buses, with REAPER's pre-roll set to match; standalone counts with the same engine. MIDI takes are take lanes; COMP is one MIDI item; the dock's roll writes to the EDIT item through the daw MIDI service. A printed synth keeps its MIDI as a layer named MIDI.

### The golden session (#34)

- Rust only; both Python writers retire at the end of the first landing. The builder composes the config-derived template tree with a fixture patch list and fixture song shape through the real apply path (bus creation, grouping, kinds, inputs). GUIDs are derived from each node's path hash; synthetic media is generated deterministically into an uncommitted fixtures directory; FX chains are written by name at default state with no plugin state.
- The built RPP is committed and a test asserts builder output equals it; scene pictures are committed at one size and compared on every run; one test per golden rule walks the built tree and the maximal-template checklist is regenerated from those tests. Shapes land in order: reproduce today's writers; Guide, Keyflow and the monitor buses; vocal languages, VCAs and choir; keys, synths and percussion; the orchestra.

### Scenes per instrument

- Drums: Drum Tracking, Drum Tracking Overview, Drum Editing (Edit default), Drum Mixing, Drum Advanced, Drum FX, Drum Overview, Buses (the existing scenes become data). Bass: Tracking, Tracking Overview (player), Comping, Editing, Mixing. Guitars: Tracking, Tracking Overview (player), Editing, Mixing, Balance, FX. Vocals: Vocal Tracking, Vocal Comping, Lead Vocal, Lead Vocal FX Edit. Keys and synths (one bus): Keys Tracking, Keys Editing, Keys Mixing. Percussion: Tracking, Comping, Editing, Mixing. Every scene carries the flow rule ids it implements.

### CI (#40, #45, #33)

- The checks workflow checks out the daw and processor siblings at pinned refs on the self-hosted runner; the lockfile's unused-patch trailer is compared as a sorted set rather than with `--locked`; main is format-checked. Three pre-existing test failures on main are fixed (one is a test asserting on absence where the component now hides). The tracey step then fails the build when a `flow.*` rule marked implemented has no verify, and reports the open count, runnable locally as `just daw-flows`.

## Testing Decisions

- A good test drives the real gesture through the daw facade and reads the project back through the same facade. It asserts on project state (inputs, sends, group flags, comp areas, stretch markers, MIDI notes, folder structure) and on rendered pictures, never on the window's internals or on how an engine got there. Every scenario has a negative control (the unarmed folder shows nothing; the moved source is untouched; Broadcast has no talkback).
- One gesture seam: the facade's service traits. Scenario tests run in-process against daw-standalone for the fast loop (the session facade's existing memory-link bootstrap is the prior art) and inside REAPER through the reaper-test harness for parity on the flows that touch lanes, comps, groups and named slots. The window is never driven directly; the dock and the row planner are covered by the pictures and by the facade state they write.
- Three pure-data seams: the scene engine's resolve (row list in, row list out; committed PNG fixtures through the existing bench, direct row-list assertions where a picture is overkill); the golden builder (committed RPP equals output; one tree-walk test per golden rule); Facet round-trips for the patch list, the profile and the scene types.
- Byte-identical is the standard: the golden RPP, every scene PNG, and `daw-verify` on the reference session. A scene resolving to zero visible rows fails its fixture.
- Every execution ticket lands: a render fixture, a scenario test, `r[impl]` on the code and `r[verify]` on the test for the rule ids the ticket names. Prior art: the existing daw-ui and expression-editor test crates, the bench's scene renders, the session facade's standalone bootstrap tests, the dynamic-template tests directory.

## Out of Scope

- The Render service and everything on it: stems per bus, print-through bounces, render presets, the mastering handoff (#44, deferred; its research is attached there). The vocals per-language render landing waits on it; nothing else does.
- Session-wide editing (tempo map and time-signature edits, moving markers and regions, section operations, ripple, item operations); a written cross-surface undo rule and a visible history; importing an unsorted multitrack; the click and guide cues while a band tracks; automation; guitar reamping; cue mixes carried across an album. All recorded as fog on the closed map.
- The orchestra's own spec (divisi, seating, spot mics, scoring to picture); only its golden shape lands. Bass mixing beyond the folder, bus and rack. Which performers sing the BGV parts and the choir. Default scenes for Master, Live, Video and Scoring.
- The styx file for scenes and its user and session layers (the Rust table comes first). The daw round-trip that would let the checks workflow drop the sibling patches (a runner with the siblings is the chosen baseline).

## Further Notes

- Execution runs one worktree and one PR per ticket into main, subagents sharing one cargo target directory, exactly as the map decided. Cross-repo work (the group-flag setter, the lanes round-trip, the REAPER peak shim fix, the MIDI writes) lands in the daw repo first behind the local `[patch]`, is tagged, and is bumped here; a ticket that needs it says so as a blocking edge.
- Two REAPER facts gate two decisions and are each ticket's first commit: whether slots 65 to 128 can be named, and whether a VCA lead's mute reaches its followers. Both have a written fallback.
- The research that informed the map is on main under `docs/research/` (take lanes, item peaks, track groups, render); the folder-items prototype stays on its `prototype/folder-items` branch as a primary source.
- Every decision here links to its ticket on the map (#16); a ticket's comment is the authoritative wording where this spec compresses it.
