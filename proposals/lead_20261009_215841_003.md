# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Wi-Fi as the primary Transport: first-come claiming, Secure Channel, retire USB**

*Project description:*
## Problem Statement

The display has three ways in, and none of them is right for day-to-day use. USB needs a cable. BLE works, but its range is short and it needs a phone nearby with a live link, even though the device is now reliably on Wi-Fi: it keeps a Saved Network, Rejoins it at boot, and syncs the Wall Clock. Pairing also needs the GP22 button, and GP22 is the board's BOOTSEL button, which shouldn't double as a user control.

## Solution

Wi-Fi becomes the primary Transport. BLE shrinks to onboarding and recovery, and USB is removed.

- An **Unclaimed** device (one with no Bond) accepts the first phone that pairs over BLE, with no button involved. That Pairing **Claims** the device: it persists the Bond and generates a random **Link Key**, which the app fetches over BLE.
- The phone then sends `WIFI`. After that, the app finds the device on the LAN over mDNS and talks to it through a **Secure Channel**: a Noise `NNpsk0` handshake keyed by the Link Key, then ChaCha20-Poly1305 frames carrying the same line protocol.
- BLE only advertises when it's needed: when the device is Unclaimed, has no Saved Network, or has had no DHCP lease for more than 2 minutes.
- A **Factory Reset** puts the device back to Unclaimed. It's triggered by holding Button A (GP12) for 5s, or by the `RESET` Command.

## User Stories

1. As an owner, I want a brand-new device to pair with my phone without pressing anything, so that setup is just "open the app".
2. As an owner, I want a Claimed device to refuse any other phone, so that a stranger in BLE range can't control it or read its secrets.
3. As an owner, I want to control the display over my home Wi-Fi from anywhere in the house, so that I'm not limited to BLE range.
4. As an owner, I want Wi-Fi control to be encrypted and authenticated, so that someone else on my LAN can't read or forge Commands.
5. As an owner, I want the app to find the device on the LAN automatically even if its IP address changes, so that I never type an address.
6. As an owner, I want the app to fall back to BLE when the device can't reach Wi-Fi (new router, changed password), so that I can give it a new network without a reset.
7. As an owner, I want to hold a physical button to Factory Reset the device, so that I can recover it if I lose my phone or reinstall the app.
8. As an owner, I want to Factory Reset from the app, so that I can hand the device to someone else without touching it.
9. As an owner, I want the grid to show progress while I hold the reset button, and letting go early to cancel, so that I can't wipe it by accident.
10. As a developer, I want the Wi-Fi Transport to run the same `run_session` as BLE, so that Transports can't drift in behaviour.
11. As a developer, I want BLE off whenever Wi-Fi is healthy, so that the embassy#7081 Wi-Fi+BLE concurrency risk is rarely exercised and the attack surface is smaller.
12. As a developer, I want USB CDC removed, so that there's less firmware and no unauthenticated Command path. Debugging stays on defmt/RTT.

## Implementation Decisions

**Buttons and reset**
- GP22 (BOOTSEL) has no role. The Bondable Window and `pairing_window.rs` are removed, and ADR-0002 is superseded.
- Button A on GP12 is active low, the same configuration as GP22. Holding it for 5s triggers a Factory Reset, with a fill-up progress bar on the grid; releasing it early cancels. A short press does nothing for now and is reserved for cycling clock faces (Phase 2).
- A Factory Reset wipes **everything**: the Bond, Link Key, Saved Network, TZ Rule and any persisted display settings. Then the device reboots Unclaimed.
- `RESET` replaces `UNPAIR` as a remote Factory Reset with the same effect. It's available on every Transport.

**Claiming (supersedes ADR-0002)**
- Unclaimed means no Bond. While Unclaimed, the first Pairing is persisted as the Bond and the device becomes Claimed. This is trust on first use.
- When a device is Claimed it generates a 256-bit Link Key from the RP2350 TRNG and persists it next to the Bond. It's regenerated only by a Factory Reset.
- While Claimed, any BLE link whose encryption isn't against the stored Bond is disconnected before a Session starts. This closes the transient-pairing gap that ADR-0002 accepted. That gap can't be accepted any more, because BLE now hands out the Link Key.
- `KEY` returns the Link Key, hex encoded. It's the **only Transport-restricted Command**: it works over BLE and is refused on any other Transport. `CONTEXT.md` has to say this explicitly, since the glossary otherwise describes Commands as Transport-agnostic.
- The Link Key is stored in plaintext in the `settings.rs` map (new `Key::LinkKey`). The reasoning is the same as ADR-0004: physical access already lets someone reset the device and take it over.

**Wi-Fi Transport and Secure Channel**
- The device runs a TCP server on the LAN and advertises it over mDNS as `_automata._tcp`.
- Handshake: `Noise_NNpsk0_25519_ChaChaPoly_SHA256`, with the Link Key as the PSK. After the handshake, each Command or reply line travels as one length-prefixed AEAD frame. A wrong or missing Link Key fails the handshake, and no Session starts.
- One Session at a time. A newly authenticated connection **replaces** the existing one, because phones waking from sleep leave dead sockets behind. Sessions close after 5 minutes idle.
- The Wi-Fi Transport adapts frames to the `Read`/`Write` traits so `run_session` is unchanged, apart from knowing enough about its Transport to refuse `KEY`.
- A new ADR records why this is Noise with a PSK and not TLS. `embedded-tls` is client-only. The only no_std TLS 1.3 server is a v0.1 PSK-only fork (GatoPSKTLS) with no forward secrecy. Dart's `SecureSocket` doesn't expose TLS-PSK. Noise `NNpsk0` gives forward secrecy and has a spec with test vectors.

**BLE on/off**
- BLE advertises only when the device is Unclaimed, has no Saved Network, or has had no DHCP lease for more than 2 minutes. It stops once there's a lease **and** no BLE connection is active, so an onboarding Session isn't cut off. "Off" means not advertising; whether the BT core can be powered down at runtime is something to check, and doesn't change the decision.

**App**
- The pairing screen drops the "press the button" step. After the OS bonding dialog, the app sends `KEY` and stores the Link Key in `flutter_secure_storage`.
- Transport selection: Wi-Fi whenever the device is reachable, trying the cached IP from the `WIFI` `OK <addr>` reply first, then mDNS. BLE is used only when the device is advertising. Off the LAN there's no control, and that's accepted (no cloud relay).
- iOS needs the Local Network permission and `NSBonjourServices` (`_automata._tcp`) in `Info.plist`.
- The `UNPAIR` control becomes a `RESET` control with a confirmation step.

**USB**
- `usb.rs` and the USB CDC stack are deleted. This is the last slice, so the dev path keeps working until Wi-Fi is proven end to end.

**Migration**
- None. After flashing the first build of this phase, Factory Reset the device by hand and claim it again.

## Testing Decisions

- Test external behaviour: a Command line in, a reply line and state out. The same seams as before.
- Host-tested (firmware `[lib]`):
  - `RESET` and `KEY` parse and dispatch, including `KEY` being refused off BLE.
  - The Noise handshake and frame codec, against the published Noise test vectors where they apply, plus a wrong-PSK rejection.
  - The BLE advertise/stop rule as a pure function of (claimed, saved network, time without lease, BLE connected).
  - The Factory Reset hold-progress state machine as a pure function of press and release timings.
- Host-tested (Dart): Noise handshake and frame codec interoperating with the same vectors, and the Transport-selection logic.
- Checked by hand: claiming a fresh device, a second phone being refused, Wi-Fi control end to end, router change with BLE fallback, Button A reset (hold and cancel), `RESET`, and that the device runs with USB removed.

## Out of Scope

- TLS, certificates, or any cloud or remote (off-LAN) access.
- More than one phone, or more than one Bond or Link Key.
- MQTT or Home Assistant. They can come later as another Transport over the same Session.
- Encrypting secrets in flash at rest (ADR-0004 reasoning).
- Migration code for existing devices.
- Display features: Phase 2 (analog face, night dimming) is a separate PRD.

## Further Notes

- Glossary additions for `pico_w_display/CONTEXT.md`: Claimed/Unclaimed, Link Key, Factory Reset, Secure Channel. Bondable Window and USB are removed. Command list: `UNPAIR` becomes `RESET`, plus `KEY`.
- Supersedes ADR-0002. New ADRs: Noise over TLS, and first-come claiming with refusal of non-Bonded links. Link Key plaintext storage is either a new ADR or an extension of ADR-0004.
- ADR-0001's embassy#7081 risk shrinks but doesn't go away: both radios still run together during onboarding and recovery.
