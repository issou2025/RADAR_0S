# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**feat(copy): land section links on each destination's own heading anchors**

*Project description:*
## What

Make onetaskgraph's copy carry a section link onto the destination's own way of addressing a heading, as a
general feature of the copy rather than anything specific to budgets or to ai-orchestrator. Today, in
`crates/onetaskgraph-core/src/engine/copy.rs`, `rewrite_references` and `substitute` have three gaps:
- They rewrite a referent's location only in **documents**.
- They recognise a reference only as the referent's exact location string.
- They carry any `#fragment` after it byte for byte (`delimited_at`), as they do a same-record `#slug`.
So a section link reaches a GitHub issue or a Linear record pointing at a fragment nothing there answers to.

Change the copy so that, for every body it writes, each section link in the authored form below is
written in the destination's section form. The bodies are documents, tasks, project descriptions, public
projections, and comments carried on copy.
- **Reference recognition.** From a local-md source, a path relative to the referring record's own file
  names the referent it resolves to, in addition to the absolute location recognised today. This is a
  general local-md feature.
- **Fragment translation.** The `#<slug>` after a rewritten reference, and a same-record `#<slug>`, are
  written in the destination's form below for the counterpart heading whose slug is `<slug>`.
- **Unknown slugs.** A fragment naming no heading of its referent is carried verbatim and counted as
  unresolved in the copy's per-record report, never guessed.
- **Provenance.** A rewritten task or project body's template provenance is restamped by the same rule
  documents follow today, so a regenerate still reproduces the pre-copy content.

**Recognition of a link already in a tracker's form.** A body copied out of a GitHub Projects or Linear
source holds its section links in that source's form, written by an earlier copy or by hand. Each is
recognised as naming its referent and its heading, so it is translated like an authored link and never
carried verbatim to a destination where it would point at the wrong tracker or nowhere.
- *Mechanism: the copy's reported locations, read by each destination kind's form entry in reverse.*
  The referent set stays what `named_referents` reads today: the records of the body's own project at the
  source, each with the location that source reports for it. Each kind's form entry (below) also parses its
  own form back into a reported location and a heading, and a link is a reference when the location it
  parses to is a referent's reported location (or the body's own record's, for a same-record link). The
  `onetaskgraph.copies` links, `onetaskgraph.copy_locations` and the origin keys are not used to recognise a
  reference; they keep their one job, finding the referent's counterpart at the destination, unchanged.
- *GitHub.* `https://www.github.com/<owner>/<repo>/issues/<n>` and the canonical `https://github.com/…`
  spelling, with or without `#user-content-<slug>` or `#<slug>`, name the referent whose reported location is
  that issue's canonical URL; a same-record `#user-content-<slug>` names a heading of the body's own record.
  The heading is the one whose slug is `<slug>` under the GitHub slug rule, repeats included. Cost: none,
  because the reported locations are read already.
- *Linear.* `<record URL>#heading-<slug>-<id8>` names the referent whose reported location is `<record
  URL>`, and its heading is the one of that referent whose stored id begins with `<id8>`; the `<slug>` part
  is not relied on. Cost: none in requests, because the Linear plugin selects the record's editor state in
  the reads `referents` already makes of each project, task and document; it adds only bytes to those
  answers.
- *Heading identity across trackers.* A recognised heading is carried as its text and its position among
  the headings of that text in its record, never as a slug string, because the slug rules of GitHub and
  Linear differ; the destination link names the counterpart heading with the same text and position.
- *A link to a record outside the referent set* (another project, another repository's issue) is a real
  URL that works from anywhere and is left as it is, as today.
- *Ancestry.* A chained copy resolves at each hop because each hop's counterpart is one recorded hop
  away; the two-hop limit `Referent::keys` documents is about finding counterparts, is unchanged, and is
  not reached by a chain that copies the whole project at each hop.
- *Round trip to local-md.* From a GitHub or Linear source to a local-md destination, a recognised link is
  written in the authored form below, relative to the destination record's file, so a project copied
  local-md -> github-projects -> linear -> a second local-md store ends with every section link equal to
  the original authored one. Each hop's anchor markup is stripped on read, as the GitHub entry states, so
  none reaches the next tracker.
- *Idempotence.* A repeated copy of an unchanged project writes nothing, at every hop and from every
  source kind: the comparison that decides a write is made on the translated body, so a body whose links
  are already in the destination's form is unchanged.

**Each destination's section form (a contract; the spike `spike-section-links` established the GitHub and
local-md entries from the real trackers, and the manager the Linear entry from Linear's own stored state and
copied link).** Choose the form in one place in `onetaskgraph-core`, one entry per destination kind,
so changing one destination's form changes that entry and its journeys' expectations and nothing else.
- **GitHub Projects (an issue body).** The issue page gives a heading no `id`, so neither `#<slug>` nor
  `#user-content-<slug>` lands on a plain issue.
  - *Anchor markup.* The GitHub destination writes `<a id="<slug>"></a>` on its own line immediately before
    every heading of each body it writes (GitHub stores it as `id="user-content-<slug>"`). It strips exactly
    that markup when it reads a body back, so a read through the store returns the body as it was authored.
    `<a name>` does not work on an issue page, so it is never used.
  - *Cross-record link.* `https://www.github.com/<owner>/<repo>/issues/<n>#user-content-<slug>`. On the
    canonical `github.com` host a link clicked inside GitHub (issue to issue, which is how a design document
    is read) opens its target at the top, because GitHub's in-app navigation ignores the fragment. The
    `www.github.com` host is answered with a 301 to `github.com`, the browser keeps the fragment, and the
    link lands both when opened directly and when clicked inside an issue. This rests on undocumented
    GitHub behaviour, so the live journey below re-observes it.
  - *Same-record link.* `#user-content-<slug>`.
- **Linear issue and Linear document: one named decision, `linear_section_form`, Linear's own heading link.**
  Linear stores each heading of a record as a node of the record's editor state carrying an `id`
  attribute, a UUID Linear assigns when the record is written: a document's `contentState` and an

  API and never opened in a browser already carry them (issue TES2-773's five headings carry

  `### Budget demo-quota-seconds` heading of the plain spike document

  `…/document/<doc slug>#heading-budget-demo-quota-seconds-e1544ca7`, whose 8 hex characters are the
  first 8 of that heading's `id`.
  - *Cross-record link.* `<counterpart record URL>#heading-<Linear's slug of the heading text>-<first 8
    hex characters of the heading's id>`. The heading is found in the counterpart's stored editor state
    by its position among the headings of the same text, repeats included: a link to `budgets-1` names
    the second heading whose text is `Budgets`.
  - *Same-record link.* The record's own URL with that fragment.
  - *Linear's slug rule.* Establish it from the stored state and from Linear's own copied links, never
    by assumption: case, punctuation (`Step 2.b: retry (once)`) and repeats. Only one of
    Linear's own copied links is in hand, for `### Budget demo-quota-seconds`, so derive the rule for the

    the copied links replace the derived expectations they cover.
  - *Where the ids come from: one read-back of each Linear target record, and no more.* The Linear
    plugin already takes what Linear stores from each write's own mutation answer
    (`issueCreate`/`issueUpdate`/`documentCreate`/`documentUpdate`). The copy selects the record's
    editor state in that same answer and decodes the heading ids from it, so a record written in this
    copy is read back at no added request. The copy writes each target before the records that link to
    it. A target this copy does not write, linked from a record it rewrites, is read once per copy. A
    link whose target's ids are unknown when its record is first written (a same-record link on
    creation, or a target written later in the same copy) is written in the follow-up write the copy
    already sends when Linear rewrote that record, and otherwise in one update of that record that the
    copy's report counts.
  - *No anchor markup.* The copy writes no anchor markup into a Linear body, which Linear would render
    as visible text.
  - *A link it cannot address.* When the counterpart's stored state holds no heading of that text at
    that position, or no state is returned, the copy keeps the counterpart record's URL with no
    fragment and counts the link unaddressable in the per-record report, as the form does today.
  - Keep this decision one isolated entry, so that a single amendment from the manager switches it if
    the user's clicks show the form does not land in Linear's web app.

**The authored section-link form (a contract between this plan's nodes; never change it unilaterally).**
In a document, task, project description or comment held in a local-md source, a section link is a
Markdown link whose destination is `<path>#<slug>`:
- `<path>` is the referent record's file, written relative to the directory of the referring record's own
  file (for example `../tasks/<task file>.md` from `.plans/documents/<doc>.md`). The referent's absolute
  location, which is today's form, stays recognised too. The spike found that an absolute path resolves in
  neither GitHub's file view nor a VS Code preview, which is why the relative path is the authored form.
- `<slug>` is GitHub's heading slug of the target heading's text: lowercased; every character that is not
  a letter, a digit, a space, `-` or `_` removed; each space replaced by `-`; the n-th repeat of a slug in
  one record suffixed `-<n>` (the second `## Budgets` is `budgets-1`). GitHub's file view and VS Code
  agree on this rule, the repeat suffix included.
- A link to a heading in the same record is `#<slug>` alone.
- For a budget heading `### Budget <id>`, the slug is `budget-<id>`, which `orchestrator/plan_budgets.py`'s
  `budget_anchor` states.
- The authored form carries no anchor markup (`<a id>`, `<a name>`): a Linear body renders such a line as
  visible text. Anchor markup a destination needs is the copy's to write.

The producer is ai-orchestrator's design-document template (node `budget-link-form`). The consumer is
onetaskgraph's copy (node `onetaskgraph-section-links`), whose README becomes the authority for the
form and the slug rule. Node `adopt-section-links` adds the journey that goes red when the two drift.
A worker who finds the form wrong raises a proposal with `$ORCHESTRATOR_ASK_MANAGER` and keeps building
against it; the manager decides whether to amend it.


## Why

A person approving a plan reads a design document's one-minute Budgets summary and clicks through to a
budget's detail (its workload, evidence and command) to judge whether the number is sound. Today every such
link lands at the top of a long task issue on GitHub, and nowhere useful on Linear, which makes that check
tedious enough to skip. The same is true of every other section link a plan carries between its records,
on whichever tracker it lands. Fixing it in the copy fixes it for every consumer of the plan store, and
for every kind of record, at once.

## Goals

- A section link copied from a local-md source to a GitHub Projects destination lands on the counterpart heading, both when opened directly and when clicked inside another GitHub issue.
- A section link copied to a Linear issue or document is written in Linear's own heading-link form, naming the stored id of the heading it targets, with no anchor markup in the Linear body. Each Linear target record is read back at most once per copy, from the write's own answer where this copy wrote it. Linear's form stays one decision that a single amendment can switch.
- Section links in documents, tasks, project descriptions, public projections and carried comments are all re-pointed and translated, not only documents.
- A section link already in a GitHub or Linear form is recognised as naming its referent and heading, so a copy from any of local-md, GitHub Projects and Linear to any of them, same kind included (board to board, team to team), writes it in the destination's form; a chain of copies ending in local-md gives back the authored links, and repeating an unchanged copy writes nothing.
- A reference written relative to the referring local-md file is recognised as naming its referent.
- A body read back from a GitHub destination is the authored body, free of the anchor markup the copy wrote.

### Operational notes for this host

**Run only the checks that exercise what you changed.** The tests that cover the code
you touched, the lint that reads your diff — and nothing wider. The repository's own
automation runs the full bar downstream on the change this work becomes: a `pre-push`
hook where that repository publishes locally, the host's required checks where it
publishes remotely. Neither is waiting for you to have run it first, so running it here
spends twenty to forty minutes of this dispatch learning what the merge path reports
anyway. That is measured rather than estimated: one node in this workstream spent about
84 minutes on three rounds of everything its repository could run, to reach lint findings
a diff-scoped run reports in two.

**Pick those checks from your change, and take the narrowest scope each one supports.**
One test module over the whole suite; the lint over your diff over the lint over the
tree. A repository's own fast deterministic tier is a fine choice when it is what
exercises your change — its `just --list` says which recipe that is — and a poor one when
you reached for it because it was the widest thing available. When a check you ran
reports something, fix that and run **that check** again; nothing here asks you to re-run
its neighbours to confirm, and a wider tier cannot re-check a finding it never made.

**A dispatch that changed nothing tracked owes none of them.** When your deliverable is a

**A publication check runs downstream, so no worker can run it and none is judged on it.**
The host's required checks and a repository's `pre-push` gate run on the change this
work becomes, after this dispatch settles: downstream publication checks are not
runnable by a worker, and a dispatch is never held to one having passed. That holds on a
retry too. A `checks-failed` retry — a re-dispatch onto the same branch carrying the

acceptance checks: the repair of what the refusal named, proven by the checks the task

retry has settled. One retry that fixed and locally verified the failing test its

**Never signal a process you did not identify by PID, and a PID you got from a pattern is
still a pattern kill.** Several managers share this host, and their dispatches, drivers,
publications and test servers run under the same few binary names — `just`, `node`,
`python`, `onepipeline-api` — so a kill by name knows nothing about *whose* work it
matched. The distinction is the tool rather than the pattern: `pgrep` and `ps` **read**,
and either spelling of them is fine, `pgrep -x` included; `pkill` **signals**, and it is
never the answer here, in any spelling. `-x` is the trap, because it reads as the careful
one — `pkill -f 'just gate'` at least needs a narrowing pattern, while `pkill -x just`
takes every `just` on the machine. Reading the table first and piping the pids into `kill`
is no way around it: that is the same pattern kill with more steps.

manager's dispatch had been live over an hour. One ran `pkill -TERM -x just`. The other
ran `ps -eo pid,args | grep 'onepipeline-api serve' | awk '{print $1}' | while read pid;
do kill "$pid"; done` — which obeys the letter of every paragraph below and does the same
damage, because `just dag-ui` and the e2e suites both spawn that server and a pytest run's
were alive at that moment.

**The one process you may signal is one you started yourself, so capture its PID as you

    cmd & MYPID=$!
    kill "$MYPID"

Anything you did not start belongs to somebody. Read what it is, report what you found,
and leave it running.

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against the judged lint tier's script, `scripts/fetch-corpus.sh`,
or `publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

That has wedged four workers here, and then two more workers and the manager itself in one
night: seven instances of one defect. A crozier corpus audit waited in `until ! pgrep -f
'scripts/fetch-corpus.sh'` with no fetch running at all — the only two matches were its own

script, whose negation could never become true, and was cancelled and killed; its replacement then reached for

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.

**To ask whether a process is running at all, match the executable, not the command line.**
`pgrep -x onepipeline` matches process *names* exactly — the binary, not its arguments — so
the shell doing the asking, whose own name is `bash`, cannot match it however the pattern
is spelled. Where the binary name is not distinctive enough to identify what you mean
(`just`, `node` and `python` run everything), read the process table instead and drop the
one self-match that form has:

    ps -eo pid,args | grep -v grep | grep 'lint-llm-diff'

Both of those are **reads**, which is what makes `-x` safe here and forbidden the moment
the tool signals. The replacement for the worker wedged above reached for `pkill -f "just
gate"`, `pkill -f "just check"` and `pkill -f "nx run"` while another manager's run was

**One sentinel and one log per invocation, and look before you launch one.** That pair is a

their result as yours. Name both after the invocation (`/tmp/check.$$.log`, or the node

**Commit a coherent working piece the moment it works.** A dirty worktree does not
