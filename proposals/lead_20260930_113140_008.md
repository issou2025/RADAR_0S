# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**UI interoperability lab: observe, reconstruct, compose, render, and recapture across Mitosis, A2UI, json-render, Builder, and Nx**

*Project description:*
## Status and publication boundary

This is a **public integration / conformance epic** for building a deterministic UI interoperability laboratory around existing external standards and tools.

Public purpose:

> Demonstrate that Rosetta can preserve and evaluate correspondence across independently maintained UI representations without inventing a new Rosetta-specific UI ontology, schema family, or component language merely because translation work is difficult.

The first implementation should use external standards and their own rigorous syntax as far as they can carry the problem:

- Playwright + Web Platform APIs for observable rendered behavior;
- Vercel `json-render` for schema-constrained generative approximation, rendering, image/video projections, and A2UI experimentation;
- Builder.io Mitosis for framework-neutral component source/IR and cross-framework code generation;
- A2UI for agent-facing declarative composition against approved catalogs;
- Builder Content / Builder SDKs as an optional external visual-composition and multi-renderer proving surface;
- Nx for repository scaffolding, project/task graphs, caching, affected execution, generators, migrations, Playwright/Storybook integration, and repeatable developer ergonomics;
- existing Rosetta Run / Action / Observation / Evaluation / Receipt semantics only where those generic contracts already fit.

### Explicit semantic restraint

**Do not create a Rosetta UI Composition IR, Rosetta-specific scrollytelling ontology, Rosetta component schema, or new Core UI primitive in this epic.**

If a requirement cannot be represented adequately by the selected external syntaxes, first:

1. prove the gap with a concrete fixture;
2. test whether another maintained external standard can represent it;
3. record the translation loss explicitly;
4. only then route any proposal for new Rosetta semantics through separate governance.

A human-readable sentence such as “maintain geographic continuity while narration advances” is not an acceptable machine contract when the same behavior can be represented as executable component structure, bindings, scroll state, layout, animation timing, and assertions.

This public epic may define deterministic mappings, profiles, fixtures, version pins, loss reports, and conformance evidence. It must not disclose or standardize generalized hidden correspondence discovery, candidate ranking, adapter synthesis, or other protected operational machinery.

## Why this matters

Rosetta currently has mature specifications and a growing integration backlog, but it needs a compact, visible demonstration of its core value:

**interoperability across representational systems with provenance and bounded evidence about what survived translation.**

The UI domain is unusually suitable because:

- the source and target can both be rendered;
- their behavior can be exercised under the same browser scenarios;
- visual and structural outputs can be recaptured;
- differences can be measured rather than merely argued;
- multiple independent standards already provide useful, complementary abstractions.

The same work also directly supports Entif's near-term UI engineering and the clean-room redesign of ETR-2026-07 without making that publication the owner of the interoperability architecture.

## Recommended implementation order

The dependency order is intentionally not “build every adapter, then integrate.”

1. **#1662 thin tooling scaffold** — add only enough Nx/Playwright generator/orchestration support to avoid copy-paste infrastructure.
2. **#1659 one-reference / one-viewport capture** — freeze a bounded source scene.
3. **#1660 one json-render approximation loop** — prove that the frozen evidence can drive a useful schema-constrained reconstruction and recapture.
4. **#1467 one Mitosis reconstruction** — express the accepted behavior as a portable component and prove one generated target.
5. **#1152 one A2UI custom-catalog surface** — compose the accepted component through A2UI and compare official/current rendering with json-render's A2UI path.
6. **#1467 second Mitosis target + #1659 narrow viewport** — establish that the proof is not accidentally single-renderer/single-viewport.
7. **#1661 Builder lane** — add Builder Content / Visual Editor / multi-SDK evidence only after the local open path is working.
8. **Second materially different reference** — only then generalize generators/catalog helpers and expand the reference corpus.
9. **Editorial consumption** — after #1657 and the interoperability primitives are credible, use the reference corpus and accepted components to inform the fresh ETR-2026-07 design process.

At every stage, stop and revise the representation if the next adapter requires inventing a Rosetta UI dialect merely to bridge an avoidable mismatch.

## Architectural thesis

The first-wave system should look approximately like this:

```text
reference website
      |
      v
Playwright + browser observations
      |
      v
json-render candidate approximation
      |
      v
render + Playwright recapture
      |
      v
accepted reconstruction evidence
      |
      v
Mitosis source / MitosisComponent IR
      |
      +----------------------+----------------------+
      |                      |                      |
      v                      v                      v
framework targets      A2UI catalog seam      Builder adapter
      |                      |                      |
      v                      v                      v
render + recapture      A2UI surface/render    optional visual edit
      |                      |                      |
      +-----------+----------+----------------------+
                  |
                  v
          fidelity / loss evaluation
                  |
                  v
        bounded Rosetta evidence/receipt
```

The exact route between json-render and Mitosis is deliberately experimental. The first proof should compare the simplest deterministic options rather than pre-ordaining a new abstraction layer.

## Division of labor

### Playwright / browser APIs

Own observable facts:

- screenshots;
- scroll positions;
- viewport dimensions;
- element geometry;
- visible text/state;
- computed style needed for reconstruction;
- transforms / opacity / filters / clipping where inspectable;
- sticky/fixed behavior;
- Web Animations state where exposed;
- ARIA/accessibility state where relevant;
- user interactions and resulting state changes.

Observation artifacts are evidence. They are not a new UI ontology.

### json-render

Own rapid schema-constrained approximation and rendering experiments:

- generate candidate specs from frozen observations;
- render through one or more supported targets;
- render A2UI natively through `@json-render/core`;
- produce images/contact sheets where useful;
- use Remotion to project scroll-space choreography into a deterministic inspection timeline;
- provide a fast “can we represent this behavior?” workbench.

json-render specs are external-format artifacts, not Rosetta Core truth.

### Mitosis

Own portable component implementation:

- candidate `.lite.tsx` / `.lite.jsx` source;
- pinned `MitosisComponent` / `MitosisNode` JSON;
- framework generation;
- component state, bindings, lifecycle, events, styles, slots, children, props and target-specific escape hatches;
- reproducible target builds and runtime fixtures.

Mitosis is authoritative for its own compiler IR.

### A2UI

Own agent-facing composition:

- surfaces;
- component/catalog selection;
- application data;
- bindings;
- actions;
- progressive updates.

A2UI should generally instantiate **accepted components** rather than receive a lossy translation of every CSS declaration or Mitosis hook. Detailed implementation behavior stays inside the component implementation.

### Builder SDK / Content

Optional proving surface for:

- visually authored composition;
- custom component registration;
- Builder Content JSON as another existing external UI representation;
- human visual correction loops;
- multi-framework SDK rendering.

Builder cloud/editor access must not be required for the canonical local conformance path.

### Nx

Own developer ergonomics and orchestration:

- integration/reference/renderer/fixture scaffolding;
- project graph;
- task graph;
- caching;
- affected execution;
- migrations;
- Playwright and Storybook integration;
- deterministic conformance pipelines.

Nx does not own UI semantics.

### Rosetta

Own only what Rosetta already legitimately owns:

- identity of source/target artifacts;
- version/profile identity;
- transformation provenance;
- bounded mapping correspondence;
- explicit unsupported/loss conditions;
- observations;
- evaluations;
- receipts.

## First vertical slice

Use **one bounded scrollytelling scene from _The Road Was Long: A Voice from Ukraine_** as the first end-to-end fixture.

Reference:
https://story.internal-displacement.org/the-road-was-long-a-voice-from-ukraine/index.html

The first slice should prove:

1. capture one desktop viewport deterministically;
2. retain the source screenshots/trace and browser-observable state;
3. generate one json-render approximation;
4. render and recapture it;
5. iterate until the bounded scene meets declared observable invariants;
6. express the accepted implementation as a Mitosis component;
7. generate at least one web target and recapture it;
8. expose the accepted component through an A2UI custom-catalog entry;
9. render one A2UI surface through the official/current A2UI web path;
10. render the same A2UI fixture through json-render's A2UI support where practical;
11. compare results structurally and behaviorally;
12. emit a machine-readable loss/unsupported report;
13. generate a contact sheet and human-readable reference analysis from the frozen fixture;
14. only after the one-viewport path is credible, add a narrow/mobile viewport;
15. only after two substantially different reference experiences fit without schema invention, generalize the tooling.

## Fidelity model

Do not use “render succeeded” as the success criterion.

Evaluate dimensions separately where applicable:

- structural fidelity;
- content fidelity;
- spatial/layout fidelity;
- interaction fidelity;
- temporal/scroll fidelity;
- responsive fidelity;
- accessibility/semantic fidelity;
- visual similarity.

No single aggregate score is required for first release.

The harness should allow a dimension to be:

- exact under declared tolerance;
- equivalent under declared invariant;
- approximated;
- unsupported;
- not evaluated.

The representation of those statuses should reuse existing Rosetta evaluation/receipt semantics where possible rather than create UI-specific Core kinds.

## Determinism rules

1. Live reference capture is a refresh operation, not normal CI.
2. CI consumes frozen fixture inputs.
3. Pin browser/tool versions for a conformance run.
4. Pin external protocol/library versions in profile metadata.
5. Use fixed viewports, locale, color scheme, reduced-motion setting, timezone, and relevant browser context.
6. Do not introduce random animation state or time-dependent content into deterministic fixtures.
7. Derived outputs from frozen inputs must be reproducible.
8. Tool upgrades invalidate stale baselines unless explicitly migrated.
9. LLM assistance may propose reconstruction code/specs, but accepted artifacts become checked-in inputs; ordinary conformance does not regenerate semantic decisions from an LLM on every run.

## Nx execution model

The first-wave workspace should prefer official Nx plugins and ordinary commands before custom executors.

Expected pattern:

```text
reference:refresh
  -> frozen observations

json-render:build
  -> json-render:e2e
      -> json-render:fidelity

mitosis:parse/generate
  -> target:build
      -> target:e2e
          -> target:fidelity

a2ui:catalog
  -> a2ui:render
      -> a2ui:e2e
          -> a2ui:fidelity

all fidelity artifacts
  -> conformance report
```

Independent target branches should run in parallel where possible. Expensive deterministic outputs should be cacheable. `nx affected` should prevent unrelated adapters/targets from rebuilding.

## Storybook posture

Storybook is a specimen cabinet, not the canonical UI format.

Use it to expose accepted reusable component states and fixture variants for human inspection and interaction testing. Prefer one dependable primary Storybook surface first rather than multiplying Storybooks across every generated Mitosis target.

## Success condition

The first public demonstration should be able to show:

> A sophisticated third-party interaction was observed through browser evidence, approximated in one external generative UI syntax, reconstructed as a cross-framework component through another external compiler IR, exposed through an agent-facing declarative UI protocol, rendered through independent implementations, and compared against its source behavior without Rosetta inventing a new universal UI language.

## Non-goals

- a new Rosetta UI ontology;
- a new Rosetta component schema;
- a universal visual-design language;
- arbitrary framework-source reverse engineering;
- pixel-perfect cloning as the only success measure;
- scraping and republishing third-party assets without rights;
- making Builder cloud services mandatory;
- making json-render, Mitosis, A2UI, Builder, AG-UI, MCP, or Nx authoritative outside their own domains;
- treating build/typecheck success as behavioral equivalence;
- exposing generalized private correspondence-discovery or adapter-synthesis machinery.
