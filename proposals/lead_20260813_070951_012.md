# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Move local identity, keys and application capability custody into `greenwaysd`**

*Project description:*
Parent: #49

## Goal

Make `greenwaysd` the only owner of Greenways **installation-local** private-key custody, provider credentials, node identity, local application approvals and durable local capability decisions.

Hestia remains the owner of human/agent profiles, private-office rooms, invitations, membership, mandates, exact-root approvals, source mandates and room application grants.

## Authority model

Distinguish:

```text
Greenways profile/node custody
  local installation and provider keys held by greenwaysd

local client identity
  desktop · cli · browser-bridge · developer process authentication

local application approval
  exact package/version/publisher/manifest/lock decision on this installation

local capability grant
  exact permission for that installed app to request a Greenways operation

Hestia room authority
  imported room membership, source mandate and member-specific room app grant
```

A local client role is never Hestia membership. A local application approval is necessary but never sufficient for room access.

## Daemon custody responsibilities

- create, unlock, rotate and revoke local node/application identities;
- use operating-system keystores or hardware-backed handles where available;
- retain provider credentials without projecting them to clients;
- sign only typed local Greenways subjects;
- issue bounded local browser sessions;
- store local app approvals, capability grants, revocations and receipts;
- verify pinned Hestia authority imports and preserve exact Hestia roots;
- support local recovery without exporting ordinary private-key material through IPC.

## Hestia boundary

`greenwaysd` must not mint or reinterpret:

```text
room descriptors
room membership
membership epochs
agent mandates
source mandates
room application grants
human exact-root approvals
```

Those are Hestia records and decisions. Greenways OS may hold verified projections needed for routing and execution.

## Closed operations

Examples:

```text
identity.status
identity.public-card
node.enrol.prepare
node.enrol.complete
node.revoke
application.approve
application.revoke
capabilities.check
provider.invoke
hestia.import.status
hestia.room.check
vault.lock
recovery.status
```

Do not expose private-key export, credential reads, arbitrary signing, generic secret lookup, caller-selected room policy or unrestricted Hestia record mutation.

## Browser boundary

The Chrome extension authenticates through an exact Native Messaging manifest and OS-user-protected local bridge. A successful connection yields only an expiring browser session bound to the exact extension, local node, browser profile/device and connection generation.

No persistent Greenways root, provider credential or reusable Hestia room bearer token remains in extension storage.

## Acceptance criteria

- All current Keyring responsibilities have a daemon-side destination and migration plan.
- Private keys and provider credentials never appear in Flutter, extension messages, Hestia room records, logs or public receipts.
- Every signing operation revalidates its complete typed subject immediately before use.
- Local node, local client, local application and provider authority can be revoked independently.
- Hestia room authority can be revoked independently without modifying local app installation state.
- Browser disconnection destroys the active browser session without changing local identity or Hestia membership.
- Restart recovery preserves local grants and receipts without making interrupted approvals ambiguous.
- Conformance proves clients cannot select arbitrary keys, expand local authority or substitute Hestia roots.
