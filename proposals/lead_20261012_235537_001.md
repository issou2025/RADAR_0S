**pyRevit 7.0: concurrent tool calls get each other's results, and list_families ignores contains/limit**

*Project description:*
### Tool name

All tools that need the Revit API context (measured with `execute_revit_code`), and `list_families`

### What happened?

Two things I found while testing the server against pyRevit 7.0. I ran my tests on a clone at `40af5a7` (before the phase-1 server rewrite); the extension code under `revit_mcp/` is identical to current `master`, and I checked by reading `master` that neither point has changed.

**1. Concurrent tool calls get each other's results.**

pyRevit Routes keeps a single module-level `RequestHandler` / `ExternalEvent` for every request thread, so when two API-context requests are in flight together only some handlers run and every waiting client receives the same response, all with HTTP 200. The calls that follow come back shifted by one until the server has been idle for a few seconds. I reported the root cause upstream with a minimal repro: pyrevitlabs/pyRevit#3752.

Through this server it is easy to hit, because MCP clients issue tool calls in parallel. Six simultaneous `execute_revit_code` calls, each appending its own id to a file and printing it:

```
request 0 was told: ran 3
request 1 was told: ran 3
request 2 was told: ran 3
request 3 was told: ran 3
request 4 was told: ran 3
request 5 was told: ran 3
payloads that actually executed inside Revit: ['3', '4']
sent 6, executed 2, correct answers 1
```

Four model edits were skipped while their callers were told they succeeded.

Until Routes is fixed, the CPython side can protect itself by letting one request through at a time. In my clone a single `asyncio.Lock` around the HTTP calls was enough (on `master` that would be `_send`): after it, five parallel tool calls each got their own answer in live Revit. It does not cover two separate server processes pointed at the same Revit, or a call that timed out on the client and is still running inside Revit.

**2. `list_families` never applies `contains` / `limit`.**

The tool sends both as query parameters, but the handler is `def list_families(doc, request)` and stops at a hard-coded 50, so they have no effect. pyRevit Routes 6.x dropped the query string entirely; 7.0 forwards query parameters as keyword arguments, but only those the handler declares (undeclared ones are silently dropped). Declaring them makes the filter work on 7.0:

```python
@api.route("/list_families/", methods=["GET"])
def list_families(doc, request, contains=None, limit=50):
    ...
    try:
        limit = max(1, int(limit))
    except (TypeError, ValueError):
        limit = 50
    needle = contains.lower() if contains else None
    ...
        if len(families) >= limit:
            break
        ...
        if needle and needle not in (family_name + " " + type_name).lower():
            continue
```

With that change `list_families(contains="door", limit=3)` returned only the two matching types. On pyRevit 6.x the parameters still never arrive, so a path parameter or a POST body would be needed there.

### Steps to reproduce

1. Open any project with the extension loaded (pyRevit 7.0, Routes on).
2. From an MCP client, issue several `execute_revit_code` calls in the same turn, each printing a different token — or POST them concurrently to `/revit_mcp/execute_code/`.
3. Compare each response with the token that call sent.
4. For the second point: call `list_families` with `contains` set to something specific and note that the result is the same unfiltered first 50.
