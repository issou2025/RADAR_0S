## Request

Matt asked (voice memo, 2026-10-26 12:58Z, paraphrased by the filing actor) to investigate packaging the existing Flutter dashboard as an Android app, with whatever platform hooks or bindings are needed so the user can set it as the phone's **default assistant**. Explicitly **out of scope**: any always-on listening or custom wake-word engine. The app should only answer the system assistant trigger.

## Why

The dashboard already runs as a Flutter web app with walkie (voice memo) recording to actors. On Android, the default-assistant role is what the system invokes for:

- long-press power / home gesture assistant trigger
- the Bluetooth headset assistant button (Matt's Powerbeats Pro "b" button hold sends the standard HFP/AVRCP assistant trigger)

So a dashboard build registered as the default assistant gives a one-button, hands-free path into a walkie message to root with no microphone service running in the background.

## Investigation scope (proposal, not implementation)

1. Flutter Android target: what the current dashboard needs to build as an APK/AAB (platform folder, auth/token flow against the rusa server, which web-only dependencies break).
2. Assistant hooks: which Android surfaces are needed to be eligible for the assistant role (`RoleManager.ROLE_ASSISTANT`, a `VoiceInteractionService` / `VoiceInteractionSessionService` plus `ACTION_ASSIST` handling), minimum API level, and how the Flutter side is launched straight into walkie recording with audio routed from the connected headset.
3. Headset trigger: confirm the Bluetooth assistant button reaches the default assistant on Android, and note any OEM caveats.
4. Distribution: sideload vs Play internal track, signing, and how a dev build is installed on Matt's phone.
5. Interaction with the existing walkie transcription work (#662) and the recognizer-only decision.

Deliverable: a written proposal on this issue with the recommended minimal path, the risks, and a size estimate, for Matt's go/no-go before any implementation PR.
