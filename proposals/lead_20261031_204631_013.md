*Project description:*
## Problem Statement

Reading books in English or Spanish is one of the best ways to learn a language, but today the experience is fragmented. When the reader hits an unknown word or expression, she has to leave the book, open a dictionary or translator, type the term and hope the translation fits the context. Idiomatic expressions ("kick the bucket") go unnoticed because each word on its own looks familiar. And the vocabulary she runs into is lost: there is no record of what she looked up, in which sentence, in which book, nor of passages worth re-reading.

## Solution

An Android EPUB reader that looks and feels like an e-reader (pages you turn, a fixed dark theme, comfortable fixed typography), built for language study:

- While the reader reads, the AI analyzes the text in the background and **underlines** words that are hard for her level (CEFR) and idiomatic expressions. Tapping an underline shows the translation into the reader's native language (PT-BR by default) and a short note.
- **Every word** in the text is tappable and shows a **contextual** translation (taking the surrounding sentence into account).
- Every tap automatically feeds a local **Learning Glossary**, with the context sentence and a way back to the book.
- Passages can be **marked for re-reading**, with an optional note, and revisited in a dedicated list.
- Reading is **never blocked** by the AI: text appears immediately, underlines arrive later, and the book stays readable offline.

## Implementation Decisions

### Context and platform
- Personal / portfolio project, single user. No user authentication or multi-tenancy; the architecture must not prevent adding them later.
- MVP platform: **Android**, locked to portrait. Nothing should prevent iOS later; desktop and web are out.
- Monorepo with three areas: Flutter app, FastAPI backend, docs.
- Tooling: Flutter pinned via fvm to 3.47.9 (stable); Python 3.14 managed by uv; Riverpod for state; drift + SQLite for persistence; EPUB and HTML parsing packages in the app; Pydantic, openai-agents and pytest in the backend; flutter_lints in the app.

### App language and translation language
- The app UI is in **English** in the MVP (only locale). UI strings go through Flutter's localization tooling with a single English resource file, so more UI languages in v2 are additive.
- Reading languages (the books) are English and Spanish.
- The reader picks a **native language** in settings; every translation and note from the AI is produced in it. Default: **PT-BR**. The native language is a request parameter on both endpoints, not hardcoded in the backend prompts.

### Native rendering (no WebView)
- The EPUB is rendered **natively in Flutter**: each chapter's XHTML is parsed and turned into custom rich text. No WebView, no JS engine.
- Preserved: italics, bold, headings, section breaks, images (scaled to fit, on their own page when needed). Ignored: all of the book's CSS (fonts, colors, sizes). Tables and footnotes become plain text in the MVP.
- Fixed typography and theme (not user-configurable): background `#121212`, text `#E0E0E0`, bundled Literata font (OFL), ~18sp, 1.5 line height, comfortable margins. The system font scale is ignored. Dotted amber underline for difficult words, solid teal underline for idioms. Re-reading marks use a subtle background tint.

### Text model: chapter → paragraph → token
- Each paragraph has a stable identity: (book, chapter, paragraph index) + text hash.
- The **app tokenizes** each paragraph with a Unicode regex that handles apostrophes ("don't"), hyphens, ¿¡ marks and accents. Tokenization runs once per chapter and is memoized.
- Every location in the book (progress, re-reading marks, glossary occurrences, AI terms) is expressed in **token coordinates** (chapter, paragraph, token index), never as a page number, so nothing is lost when pagination changes.

### Pagination engine
- Per-chapter pagination based on text measurement: paragraphs are flowed into the screen's content area, and when one doesn't fit it is split at the last line that fits. The split point is converted to a token index.
- A page is a list of fragments `(paragraphId, tokenStart, tokenEnd)`.
- The page map is persisted, keyed by (book, chapter, screen size, typography version).
- Computation runs on the UI thread in batches across frames: pages near the current position first, then the rest of the chapter.
- Navigation: `PageView` with horizontal swipe and slide animation; narrow side margins (~8% each side) without text act as back/forward tap zones. Taps inside the text area always belong to words.
- Progress indicator: "page X of Y in chapter" + book percentage computed by paragraph count.

### Per-word interactivity
- Each token becomes a span with its own tap recognizer. Recognizers only exist for mounted pages and are disposed when pages leave.
- Text renders immediately without underlines. When a paragraph's analysis arrives (from cache or network), **only that paragraph** is rebuilt, via a per-`paragraphId` provider.
- Tap → translation. Long-press → start of a re-reading selection.

### AI analysis (reading session)
- The unit of analysis is the **paragraph**, not the visual page.
- On each page shown, the app requests analysis of the current page's paragraphs + the next page's (prefetch) **in a single batch**.
- ~400ms debounce after a page turn; requests for abandoned pages are cancelled.
- Deduplication: paragraphs already cached or in flight (same hash) are not resent.
- Permanent local cache keyed by (paragraph hash, CEFR level, native language), since highlights depend on the level and translations on the native language.
- AI failures never block reading: they fail silently and are logged. No retry queue; when the paragraph is shown again with a connection, analysis is requested again.
- The reader's CEFR level for the book's language and her native language are sent with every analysis request.

### API contract (FastAPI backend)
- Every route requires an `X-API-Key` header with a fixed token configured on the server. No server-side cache.
- **`POST /analyze`**: takes the book language, CEFR level, the target (native) language and a list of paragraphs; each paragraph carries `paragraphId`, hash and its already-indexed token list. Returns the found terms grouped by `paragraphId`. Each term has: `start` and `end` (inclusive token index range), `surface` (exact text of the tokens), `lemma`, `type` (`word` | `phrase` | `idiom`), `translation` (in the target language) and `note` (short explanation, in the target language).
- **Backend validation**: terms with out-of-range indices, an inverted range, or a `surface` that doesn't match the tokens in the range are dropped before responding.
- **`POST /translate`**: takes the book language, the target (native) language, the word (or token range) and the context sentence. Returns `translation`, `lemma` and `note`.
- The app caches translations by (lemma, sentence hash, native language).

### Agents (OpenAI Agents SDK)
- Two simple agents, with no tools, no handoffs and no agentic loop:
  - **AnalyzerAgent**: input = tokenized paragraphs + language + CEFR; typed (Pydantic) output with the list of terms per paragraph.
  - **TranslatorAgent**: input = word/range + sentence + language; typed output with translation, lemma and note.
- A small "mini"-family model, configurable via environment variable.
- HTTP routes depend on an injectable "agent runner" interface so tests can use fake agents.

### Tap UX and bottom sheet
- Tap on an underlined term: opens the bottom sheet with the translation and note that already came with the analysis, without a new call.
- Tap on a word inside an underlined expression: shows the whole expression, with a "just this word" button that calls `/translate`.
- Tap on a plain word: the bottom sheet opens immediately with a loading indicator and calls `/translate` (using the cache when available).
- Offline with no cache: "no connection" message.
- Every case records into the glossary.

### Local persistence (drift + SQLite, single database)
- **Library**: imported books (internal file path, metadata, cover, detected/overridden language, progress in token coordinates).
- **Settings**: CEFR level per reading language; native language for translations (default PT-BR).
- **`glossary_entries`**: unique by (lemma, language); stores type (word/phrase/idiom), total counter, first and last tap dates.
- **`occurrences`**: one per distinct tap; stores translation, the native language it was translated into, context sentence, book and location in token coordinates. A repeated tap on the same passage only increments the entry's counter.
- **Re-reading marks**: book, start and end in token coordinates, a copy of the text, optional note and date. Single color.
- **Analysis cache**: keyed by (paragraph hash, CEFR level, native language).
- **Translation cache**: keyed by (lemma, sentence hash, native language).
- **Page maps**: keyed by (book, chapter, screen size, typography version).

### Re-reading marks
- Custom selection: long-press starts it, dragging extends it with live highlighting, and on release an action bar shows "Mark for re-reading" / "Cancel". The selection may span paragraphs but is limited to the current page in the MVP.
- A per-book "Re-reading" screen lists passages and notes; tapping one jumps to its page.
- Marks are never sent to the AI.

### Glossary screen
- List with search, filters by language and by book, sorting by most recent or most tapped.
- Each item shows the lemma, the translations found and the context sentence; the reader can navigate to an occurrence in the book and delete entries.

### Deployment
- During development the backend runs locally and is reached over the home Wi-Fi.
- Once usable, a cheap deploy (Fly.io, Railway or Render), protected by the fixed token.

### Build order
1. Reader without AI: import, parse, tokenize, paginate, swipe, theme/typography, tap opening an empty bottom sheet.
2. Backend + `/translate` + glossary recording taps.
3. `/analyze` + cache + prefetch + underlines.
4. Re-reading marks + "Re-reading" screen.
5. Polish: table of contents, progress, glossary screen with filters, deploy.

Each step ends with something usable on the phone.

## Testing Decisions

### What makes a good test here
- It tests **external behavior** through the module's public boundary, not internal details. Tests must not break when the implementation is refactored without changing behavior.
- Deterministic: fixed screen size, controlled clock, no real calls to OpenAI or the network.

### Test seams (agreed)
1. **Backend through the HTTP boundary**: tests call `POST /analyze` and `POST /translate` via FastAPI's test client, with the agents replaced by fakes through the agent runner interface. They cover:
   - contract shape and grouping by `paragraphId`;
   - dropping invalid terms (out-of-range index, inverted range, mismatched `surface`);
   - rejection without `X-API-Key` or with a wrong key;
   - multi-word expressions and repeated words in the same paragraph.
2. **Reader engine in the app (EPUB → pages)**: input = sample EPUB + fixed screen size; output = chapters → paragraphs → tokens → pages (fragments with token ranges). They cover:
   - tokenization (apostrophes, hyphens, ¿¡, accents);
   - preservation of italics, bold and headings;
   - discarding the book's CSS;
   - page breaks at the right token index;
   - no token lost or duplicated across pages;
   - terms crossing a page break;
   - extraction of the table of contents and language.
   Runs as a widget test, because it depends on real text measurement.
3. **Reading session in the app (orchestration + persistence)**: fake HTTP client, fake clock and in-memory drift. They cover:
   - current + next page batched per page turn;
   - debounce (flipping quickly produces a single request);
   - deduplication by hash and cache usage;
   - cancellation of abandoned requests;
   - AI failure having no effect on reading;
   - recording taps into `glossary_entries` / `occurrences` (including a repeated tap on the same passage, which only increments the counter);
   - creating and listing re-reading marks;
   - progress saved and restored in token coordinates.

### Outside automated tests
- The visual UI (bottom sheet, gestures, colors, animations) is verified manually on the device. Targeted widget tests only if a regression shows up.
- Prompt quality is assessed by a manual script that runs a few sample paragraphs in English and Spanish against the real AI, for human inspection.

### Prior art
- New repository with no existing tests. These will be the first and set the pattern.

## Out of Scope

- DRM-protected EPUBs (Kindle, Kobo, etc.).
- iOS, desktop and web in the MVP.
- Configurable scroll vs. pagination, user font/theme settings, light mode.
- Re-reading selections spanning pages; multiple mark colors.
- Words marked as "already known" no longer being highlighted.
- Spaced repetition (SRS) / flashcards; the data model is already prepared for it.
- Exporting the glossary to CSV/Anki.
- Bundled offline dictionary (translation always goes through `/translate` + cache).
- App UI in languages other than English (v2). Strings are already externalized, so adding locales is additive.
- User authentication, multi-tenancy, billing, server-side cache.
- Retry queue for failed analyses.
- Fidelity for complex layouts (tables, floats, advanced CSS).

## Further Notes

- Decisions were made in a question-and-answer design session (Q1–Q28) on 2026-10-31.
- Isar and Hive were rejected: original development of both has stopped and they only survive as community forks. Hive (key-value) is also a poor fit for the glossary's relational queries.
- Analyzing per paragraph, decoupled from the visual page, is the decision that lets pagination change or be recomputed without losing the cache, marks or glossary.
- The biggest technical risk is native pagination with per-word taps. That's why it's the first step, before any AI integration.
- This spec can be broken into tickets per build-order step (e.g. with `/to-tickets`).
