## Correct meaning of “Schema A validates Schema B”

Do **not** ordinarily validate schema document B as a payload instance of application schema A. Required process:

1. Validate A and B independently against the Draft 2020-12 meta-schema and repository structural rules; use explicitly supported, pinned resource resolution. Full resource-graph support remains tracked in #8.
2. Compare declaration inventories and qualified identities.
3. Normalize reviewed equivalent representations without deleting constraints.
4. Recursively compare normalized declaration semantics.
5. Execute A and B over the same generated and recorded instance corpus, including instances derived from both lanes.
6. Stop on any differing verdict, unsupported validation feature, unresolved reference, missing evidence, or violated recorded valid/invalid expectation.

A finite corpus gives bounded behavioral evidence, **not proof of universal equivalence**. Zero corpus divergences must not silently waive unexplained structural discrepancies. Recorded acceptance fixtures are independent test evidence; generated fixtures remain downstream outputs. Neither is a third schema authority.

## Protobuf projection and permanent compatibility ledger

Generate from approved data IR plus reviewed projection metadata: messages, enums, scalar mappings, repeated fields, valid-key maps, nested messages, explicit presence, representable oneofs, packages/namespaces, comments/source pointers, and request/response envelopes.

`idl/protobuf.lock.json` is reviewed projection metadata. Never derive field numbers from declaration order, alphabetical order, or hashes.

```text
existing field -> preserve its number
new field      -> allocate the next available permitted number; append to lock
renamed field  -> require explicit rename metadata; preserve number
removed field  -> emit reserved number AND old name; retain permanently in lock
```

Keep message/enum identities and enum numeric mappings stable; validate collisions, reserved ranges/names and incompatible changes. Regeneration must be deterministic. Any one-time migration from authored Proto must preserve the existing reviewed numbers and identities.

## Representational losses are explicit, reviewed, and enforced

Arbitrary JSON objects; `if/then/else`; some unions/intersections; additional/unevaluated-property policy; regex/numeric/format constraints; dependent schemas; dynamic references; and missing/null/empty/default distinctions may not map exactly to Protobuf. Never silently weaken them.

Example proposed delta record:

```json
{
  "id": "rpc-receipt-protobuf-flattened-state",
  "sourcePointer": "#/$defs/RpcReceipt",
  "projection": "protobuf",
  "reason": "Protobuf cannot encode the JSON Schema conditional state machine",
  "runtimeValidatorRequired": true,
  "reviewed": true
}
```

The supplied `RpcReceipt` example flattens success/error state semantics; the shared semantic validator must enforce them at runtime. An unrecorded loss stops generation. A `reviewed: true` literal alone is not approval: require exact reviewed scope, provenance, compatible source digests, and executable negative fixtures. A required runtime validator must actually run on every applicable ingress/egress path; merely generating its symbol is insufficient.

## Full gRPC / Connect generation

Generate gRPC from generated-and-locked `.proto` services/descriptors, not independently from JSON Schema. Data shapes alone cannot determine unary/server-stream/client-stream/bidi behavior, read-only semantics, idempotency, retryability, transactions, auth, organization scope, rate limits, deadlines, or offline write policy. Require authored operation metadata.

Example operation record:

```json
{
  "operationId": "accounts.watch",
  "input": "WatchAccountRequest",
  "output": "AccountEvent",
  "rpcKind": "server_stream",
  "idempotency": "safe",
  "auth": "user_or_org",
  "writePolicy": "direct",
  "timeoutMs": 30000,
  "http": {"method": "GET", "path": "/v1/accounts/{accountId}/events"}
}
```

Example target service:

```proto
service AccountsService {
  rpc GetAccount(GetAccountRequest) returns (GetAccountResponse);
  rpc WatchAccount(WatchAccountRequest) returns (stream AccountEvent);
  rpc UploadEvidence(stream EvidenceChunk) returns (UploadEvidenceResponse);
  rpc Synchronize(stream SyncFrame) returns (stream SyncFrame);
}
```

One explicit operation inventory should drive service methods/descriptors, Connect definitions, supported HTTP transcoding annotations, Rust tonic/prost clients and server traits, Go/Dart clients, TypeScript Connect or gRPC-Web clients, test vectors and mocks. Check each target's transport/streaming capability; reject unsupported combinations instead of silently degrading them. Evaluate Connect for browser clients while preserving service identity and JSON/binary conformance. HTTP dispatch remains method + path; query/headers/body are validation inputs, not hidden operation selectors.

## tRPC is a TypeScript adapter, not a new backend or authority

Generate input/output validators, procedure names, query/mutation/subscription classification, canonical error mapping, context requirements, operation metadata, telemetry names, transport adapters and typed clients.

```text
generated/trpc/
  accounts.schemas.ts
  accounts.meta.ts
  accounts.router.ts
  accounts.client.ts
  accounts.errors.ts
  accounts.test.ts
```

Conceptual adapter (illustrative, not claimed executable output today):

```ts
export const accountsRouter = router({
  getAccount: protectedProcedure
    .meta(operationMeta.accountsGet)
    .input(GetAccountInputSchema)
    .output(GetAccountOutputSchema)
    .query(({ input, ctx }) => ctx.rpc.call("accounts.get", input)),
  updateAccount: protectedProcedure
    .meta(operationMeta.accountsUpdate)
    .input(UpdateAccountInputSchema)
    .output(UpdateAccountOutputSchema)
    .mutation(({ input, ctx }) => ctx.rpc.call("accounts.update", input)),
});
```

`protectedProcedure` and runtime policy hooks require explicit reviewed implementations. Do **not** invent business logic, authorization decisions, database transactions, secret access, payment effects, undeclared retry policies, or middleware order. Rust-backed adapters call the canonical generated RPC/HTTP client; they do not implement a second TypeScript backend. Preserve declared rate-limit, telemetry and auth metadata without introducing forbidden runtime dependency edges.

1. Run TypeSpec ↔ independently authored JSON Schema parity.
2. Verify a passed receipt for the exact input revision/closure.
3. Export/verify approved Contract IR.
4. Compile and validate operation/API IR.
5. Generate Proto files.
6. Verify compatibility with `protobuf.lock.json`.
7. Run Buf formatting checks.
8. Run `buf lint`.
9. Run `buf build` / descriptor compilation.
10. Run `buf breaking` against an immutable previous-release baseline.
11. Generate gRPC and Connect clients/server surfaces.
12. Generate tRPC adapters and Zod validators.
13. Compile every declared generated-language target with pinned toolchains.
14. Run shared positive/negative/boundary wire fixtures across languages.
15. Run corresponding sibling `*-test` repository suites at recorded revisions.
16. Fail when committed generated output differs from clean regeneration.

Missing suites/toolchains/baselines, unsupported target semantics, stale receipts and skipped mandatory checks cannot be reported as green. Keep generated files separate from authored authorities and ship `generated/README.md` explaining regeneration and no manual edits.
