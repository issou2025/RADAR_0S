# Make SSO real: OpenID Provider, server-side sessions, native login

## Why

Today all three apps share one credential database and one JWT issuer, but there is no single sign-on. Each app renders its own login form and posts the password to `POST /auth/login` (Resource Owner Password Credentials, the grant OAuth 2.1 removed). Users reuse one password, but they do not share a session: signing in to calendar does not sign in to the tracker web app, and signing out of one does not sign out of the others.

Phase 0 closed the authorization holes that made this dangerous. What remains is the protocol and session layer. This issue covers **Phases 1–3** of the auth roadmap, plus the small Phase 0 leftovers.

Target end state:

- One login screen, served by Legacy Auth, reached by redirect from every app.
- Web apps hold an `httpOnly` session cookie; tokens never touch JavaScript.
- Logging out of one app logs out of all of them.
- Mobile uses the system browser with PKCE, and still supports passkeys.
- Legacy Auth is a standards-compliant OpenID Provider, so it can later federate to Google/Entra/Okta without touching the apps again.

### What Phase 0 already did (do not redo)

**legacy-auth** (`eb9daa7`, `f66257a`, `ca29fb6`)

- `iss` from `JWT_ISSUER` and `aud` (array of allowed apps) on access tokens — `backend/src/jwt.ts`.
- `POST /auth/login` and passkey login accept an optional `audience` (`calendar` | `tracker`); it is refused with 403 when the user lacks that scope. Without it, `aud` lists every scoped app.
- Refresh tokens remember the app (`app` claim) and the scope is re-checked on every refresh; losing the scope ends those sessions.
- Atomic refresh claiming (`claimRefreshToken` in `backend/src/db.ts`), plus a 30s reuse grace (`REFRESH_REUSE_GRACE_SECONDS`) so parallel refreshes do not sign the client out.
- CORS allowlist via `CORS_ALLOWED_ORIGINS` — `backend/src/cors.ts`. Unset still means `*`, with a startup warning.
- Failed-login throttling per username and IP with `429` + `Retry-After` — `backend/src/throttle.ts`. `TRUST_PROXY` only trusts `X-Forwarded-For` from a private peer.
- `auth_events` audit table for sign-in, refresh failures, password/passkey changes, and admin user changes — `backend/src/db.ts`.
- Passkey registration can no longer steal a `credentialId` owned by another account.
- README no longer documents the removed `locked` status; the schema still drops the column.

**legacy-calendar** (`4ed5145`)

- ES256 tokens now require `type: "access"`, the expected `iss` (`AUTH_ISSUER`, defaults to `AUTH_HOST`), `"calendar"` in `aud`, **and** `scopes.calendar`. The scope bypass is closed.
- HS256 is accepted only for this server's own passkey tokens (`scope: "calendar"`), so a Legacy Auth refresh token cannot pass as a session.
- Passkey register/delete requires a session, not an API token.
- JWKS URI and issuer are configurable; tests sign ES256 against a local JWKS.

**legacytracker** (`5be63eb`)

- `jwtVerify` pins `issuer: AUTH_ISSUER`, `algorithms: ["ES256"]`; `type` must be `access`; `aud` must contain `tracker`; scope is still checked first so a scope-less account gets 403 rather than 401.
- `AUTH_JWKS_URI`, `AUTH_ISSUER`, `CORS_ALLOWED_ORIGINS` env vars (the JWKS URL was previously hardcoded).
- API tokens are revoked when the tracker scope is lost.

## Phase 0 leftovers (small, do first)

- [ ] **Client sends `audience`.** calendar, tracker web and Flutter should pass `audience: "calendar"` / `"tracker"` at login and passkey login. Right now every token carries `aud: ["calendar","tracker"]`, which keeps the cross-app replay window open even though both resource servers now check scopes. Update `legacy-calendar/src/frontend/src/services/API.ts`, `legacytracker/src/web/src/api/auth.ts`, `legacytracker/src/client/lib/src/data/network/auth_service.dart`.
- [ ] **Make `audience` required at the OP** once all clients send it, and delete the "every scoped app" fallback in `resolveAudience`. Old mobile builds break at this point — see the rollout note below.
- [ ] **Set `CORS_ALLOWED_ORIGINS` in production** for all three services. The default is still `*` with a warning. Add it to the deployment manifests, not just `.env.example`.
- [ ] **Refuse to boot with a placeholder `JWT_SECRET`.** Calendar already does this (`FORBIDDEN_JWT_SECRETS` in `env.validation.ts`); legacy-auth should match, and should refuse to boot without `JWT_PRIVATE_KEY` in production (today it silently generates an ephemeral key and invalidates every token on restart).
- [ ] **Audit retention.** `auth_events` has no pruning or admin view. Define retention (e.g. 180 days), add a prune job, and consider an admin endpoint.
- [ ] **Throttle state is in-memory.** Fine for one container; if the API ever runs more than one replica the limits multiply. Note this in the README or move counters to Postgres.
- [ ] **Scope freshness.** `scopes` and `role` are snapshotted into the token for up to `ACCESS_TOKEN_TTL_SECONDS` (900s). If instant revocation matters, add a `token_version` claim per user checked by resource servers, or an introspection endpoint. Decide, don't leave it implicit.

## Phase 1 — Legacy Auth becomes an OpenID Provider

Do not hand-roll the protocol. Spike **`node-oidc-provider`** first (mature, OpenID-certified) and confirm it runs on Bun, including `jose` interop and the existing ES256 key from `keys.ts`. Fallback: run the OP as a Node sidecar in the same image, or use a framework-free certified implementation. Hand-rolling `/authorize` + `/token` is the highest-risk option and should be rejected unless the library genuinely cannot work.

### 1.1 Scope model

Replace the boolean pair with real scopes. Keep the `scopes` object in tokens for one transition period so the resource servers can migrate without a flag day.

| Scope | Meaning | Derived from |
|---|---|---|
| `openid` | OIDC identity | always |
| `profile` | `username`, `role` claims | always |
| `calendar.read` / `calendar.write` | Calendar API access | `scopes.calendar: true` |
| `tracker.read` / `tracker.write` | Tracker API access | `scopes.tracker: true` |
| `admin` | Admin API + console | `role: "admin"` |
| `offline_access` | Issue a refresh token | requested |

- [ ] Add `app_scopes` (or widen `scopes`) so read/write can be granted separately later. Do not assume they stay paired.
- [ ] Access tokens carry the RFC 9068 `scope` string **and** the legacy `scopes` object until both resource servers stop reading it.
- [ ] Resource servers must assert the scope they need (`calendar.read`), not just the audience.

### 1.2 Client registry

New table, seeded and managed through the admin API.

```sql
CREATE TABLE oidc_clients (
  client_id                  text PRIMARY KEY,
  client_secret_hash         text,                 -- NULL for public clients
  name                       text NOT NULL,
  redirect_uris              text[] NOT NULL,      -- exact match, no wildcards
  post_logout_redirect_uris  text[] NOT NULL DEFAULT '{}',
  backchannel_logout_uri     text,
  allowed_scopes             text[] NOT NULL,
  is_public                  boolean NOT NULL DEFAULT false,
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now()
);
```

Initial clients:

| `client_id` | Type | Redirect URIs | Scopes |
|---|---|---|---|
| `calendar-web` | confidential (BFF) | `https://calendar.legacy-group.tech/auth/callback` | `openid profile calendar.read calendar.write offline_access` |
| `tracker-web` | confidential (BFF) | `https://tracker.legacy-group.tech/auth/callback` | `openid profile tracker.read tracker.write offline_access` |
| `tracker-mobile` | public (PKCE) | `com.legacy.legacytracker:/oauth2redirect` | `openid profile tracker.read tracker.write offline_access` |
| `auth-console` | confidential (BFF) | `https://auth.legacy-group.tech/auth/callback` | `openid profile admin offline_access` |

- [ ] Admin endpoints: create/rotate/disable a client. Rotating a secret must not invalidate existing refresh tokens immediately; decide on a grace period.
- [ ] Store only the secret hash (same treatment as refresh tokens in `db.ts`).
- [ ] Reject unregistered `redirect_uri` with `invalid_request`; never fall back to the first URI.
- [ ] Do **not** add a client-management UI in the first iteration; the admin API is enough.

### 1.3 Endpoints

- [ ] `GET /.well-known/openid-configuration` — `issuer`, `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`, `jwks_uri`, `end_session_endpoint`, `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code","refresh_token"]`, `code_challenge_methods_supported: ["S256"]`, `scopes_supported`, `claims_supported`, `id_token_signing_alg_values_supported: ["ES256"]`, `token_endpoint_auth_methods_supported: ["client_secret_basic","none"]`, `backchannel_logout_supported: true`.
- [ ] `GET /authorize` — renders the existing login UI when there is no OP session, otherwise issues a code. Supports `prompt=login|none`, `max_age`, `login_hint`, `state`, `nonce`.
- [ ] `POST /token` — `authorization_code` and `refresh_token`. `client_secret_basic` for confidential clients, `none` for public ones.
- [ ] `GET /userinfo` — returns `sub`, `preferred_username`, `role`. Bearer access token with `openid` scope.
- [ ] `GET|POST /logout` — RP-initiated logout with `id_token_hint`, `post_logout_redirect_uri`, `state`.
- [ ] Keep `/.well-known/jwks.json` exactly as is; the key must not change or every existing passkey-relying surface breaks.
- [ ] Publish the endpoints in `openapi.ts` as well, so `/docs` stays truthful.

### 1.4 Claims

Access token (RFC 9068, header `typ: at+jwt`):

```json
{
  "iss": "https://auth.legacy-group.tech",
  "aud": "calendar",
  "sub": "8f14e45f-...",
  "client_id": "calendar-web",
  "scope": "openid profile calendar.read calendar.write",
  "username": "alice",
  "role": "admin",
  "scopes": { "calendar": true, "tracker": false },
  "sid": "session-id",
  "jti": "...",
  "iat": 1783774116,
  "exp": 1783775016
}
```

ID token:

```json
{
  "iss": "https://auth.legacy-group.tech",
  "aud": "calendar-web",
  "sub": "8f14e45f-...",
  "nonce": "...",
  "auth_time": 1783774000,
  "amr": ["pwd", "user_presence"],
  "acr": "urn:legacy:loa:1",
  "sid": "session-id",
  "at_hash": "...",
  "iat": 1783774116,
  "exp": 1783774716
}
```

- [ ] `aud` on the access token is the **resource** (`calendar`, `tracker`), not the client id. The BFF requests the resource it will call.
- [ ] `amr` must distinguish `pwd` and `webauthn` so downstream policy can require passkeys later.
- [ ] Keep `sid` stable for the life of the browser session so back-channel logout can target it.
- [ ] Do not put `role`/`scopes` in the ID token; they belong in the access token (and `/userinfo`).

### 1.5 Browser session at the OP

- [ ] `oidc_sessions` table: `id`, `user_id`, `auth_time`, `amr`, `expires_at`, `revoked_at`, `ip`, `user_agent`, `last_seen_at`.
- [ ] Cookie: `__Host-legacy_session` — `Secure; HttpOnly; Path=/; SameSite=Lax`, **no** `Domain` attribute.
- [ ] Idle timeout (e.g. 14 days) and absolute timeout (e.g. 30 days); surface both in the discovery doc? No — keep them internal, but document them.
- [ ] Session list + "sign out other sessions" in the console (nice-to-have; do it after the flow works).
- [ ] Rotate the session id on authentication (fixation defence).

### 1.6 Logout

- [ ] RP-initiated: clear the OP session, then redirect only to a registered `post_logout_redirect_uri`.
- [ ] Back-channel: `POST` a signed `logout_token` (`iss`, `aud`, `iat`, `jti`, `events`, `sid`/`sub`) to every client with a `backchannel_logout_uri`. Retry with backoff; log failures.
- [ ] Token endpoint must reject refresh tokens whose session was revoked.
- [ ] Add `sid` to every token derived from the session.

### 1.7 Security requirements (acceptance-blocking)

- [ ] PKCE `S256` only; reject `plain`.
- [ ] Authorization codes: single use, 60s TTL, bound to `client_id` + `redirect_uri` + `code_challenge`, hashed at rest.
- [ ] Exact `redirect_uri` matching; reject fragments in redirect URIs.
- [ ] `state` round-tripped; `nonce` required for `openid` and echoed in the ID token.
- [ ] `Cache-Control: no-store` + `Pragma: no-cache` on token and userinfo responses.
- [ ] No tokens in query strings or fragments.
- [ ] `X-Frame-Options: DENY` / `frame-ancestors 'none'` on `/authorize` (clickjacking).
- [ ] Login CSRF protection on the HTML form (double-submit or origin check).
- [ ] Constant-time secret comparison; secrets hashed at rest.
- [ ] Rate-limit `/authorize` and `/token` the same way as `/auth/login`.
- [ ] Audit events: `oidc.login`, `oidc.code.issued`, `oidc.token.issued`, `oidc.refresh.reuse`, `oidc.logout`.
- [ ] Distinguish refresh **reuse outside grace** from a legitimate retry and revoke the whole token family on reuse. The current grace window (`claimRefreshToken`) has no family concept, so a stolen token replayed inside 30s silently yields a new, long-lived session.
- [ ] Run the OpenID Foundation conformance suite against the Basic OP profile before calling it done.

### 1.8 Retire ROPC

- [ ] Mark `POST /auth/login` and the passkey login endpoints deprecated once the OP flow ships.
- [ ] Keep them for exactly one release cycle, then remove. While they exist, they must still honour `audience`.
- [ ] Removing them is a breaking change for any un-updated mobile build. There is **no minimum-version enforcement** in the tracker app update mechanism today — add one, or keep ROPC indefinitely for old clients with `audience` required.

### 1.9 Acceptance criteria

- [ ] A test client can complete Authorization Code + PKCE end to end from discovery alone.
- [ ] A token minted for `calendar` is rejected by tracker and vice versa (already true in Phase 0; keep the test).
- [ ] A token without `scopes.calendar` cannot read calendar data.
- [ ] `GET /logout` ends the OP session and the refresh token stops working within one access-token TTL.
- [ ] Back-channel logout reaches both BFFs in under 5 seconds.
- [ ] No endpoint returns a token in a URL.
- [ ] Existing passkeys still authenticate (RP ID unchanged).

## Phase 2 — Server-side sessions (BFF) for the web apps

Goal: the browser holds only an `httpOnly` cookie. This is what makes SSO real and removes tokens from `localStorage`.

There is no Redis in any repo. Use Postgres for the session store — it is already a dependency and the volume is trivial. Do not use in-memory sessions without sticky routing.

### 2.1 Shared design

- [ ] Session table per app: `id` (hash of the cookie value, not the value), `user_id`, `access_token`, `refresh_token`, `access_expires_at`, `refresh_expires_at`, `created_at`, `last_seen_at`.
- [ ] Cookie: `__Host-<app>_session` — `Secure; HttpOnly; Path=/; SameSite=Lax`.
- [ ] CSRF: `SameSite=Lax` **plus** an `Origin`/`Sec-Fetch-Site` check on state-changing methods. Do not rely on SameSite alone.
- [ ] Proxy the API under the app's own origin (`/api/*`) so there is no CORS and no preflight. Alternatively set `CORS_ALLOWED_ORIGINS` and `credentials: true`, but same-origin is simpler and safer.
- [ ] Refresh server-side, with a single-flight lock per session so parallel requests do not burn the refresh token.
- [ ] On `401` from the API, clear the cookie and redirect to `/auth/login`.
- [ ] Logout: clear the cookie **and** call the OP `/logout`, so back-channel logout is not the only path.

### 2.2 legacy-calendar (NestJS, Express adapter)

- [ ] Add session middleware + store (`connect-pg-simple` or a small custom store).
- [ ] Replace `localStorage` token handling in `src/frontend/src/stores/session.ts`; the SPA calls same-origin endpoints only.
- [ ] Socket.IO auth currently reads the bearer token — switch it to the session cookie (`auth-identity.service.ts` already unifies HTTP and sockets, so this is one place).
- [ ] File uploads and avatars keep working through the BFF.
- [ ] Guest invite links must not require a session (keep the existing guest path untouched).

### 2.3 legacytracker web (Fastify)

- [ ] `@fastify/cookie` + session store; remove the refresh token from `localStorage` (`src/web/src/stores/session.ts`, `src/web/src/lib/storage.ts`).
- [ ] WebSocket auth: cookie-based handshake, with an explicit origin check.
- [ ] The device-token flow stays as is — it is a separate credential class and must not be routed through the BFF.
- [ ] `X-API-Token` support stays; personal API tokens are unaffected by cookie auth.

### 2.4 legacy-auth console (Vue)

- [ ] Move `frontend/src/stores/auth.ts` off `localStorage`. The console is served from the same origin as the OP, so this is the simplest of the three.

### 2.5 Acceptance criteria

- [ ] No `localStorage` or `sessionStorage` entry contains an access or refresh token in any web app (`grep` should come back empty).
- [ ] Signing in to calendar, then opening tracker web, does not show a login form.
- [ ] Signing out of calendar ends the tracker web session within one TTL.
- [ ] An XSS that can run script cannot read a token (cookie is `HttpOnly`).
- [ ] Cross-site `POST` to a state-changing route is rejected (CSRF test).
- [ ] Session survives a server restart.

## Phase 3 — Native login and optional federation

### 3.1 Flutter

- [ ] Replace the in-app password form with `flutter_appauth` (or `openid_client`) using `ASWebAuthenticationSession` on iOS and Chrome Custom Tabs on Android. Never a WebView — WebViews break passkeys and are blocked by Google's OAuth policy.
- [ ] PKCE with a claimed-HTTPS redirect (preferred) or the custom scheme already implied by the Android asset links.
- [ ] Store tokens in `flutter_secure_storage` (Keychain / EncryptedSharedPreferences), not `SharedPreferences`.
- [ ] Keep device tokens exactly as they are for the background tracking engine (`services/device-auth.ts`); they are exchanged from a user JWT and are independent of the OIDC session.
- [ ] Passkeys: keep them as an authentication method **at the OP**. The native app should not implement its own WebAuthn ceremony; it opens the OP in the system browser, which already has the asset links.
- [ ] Handle `prompt=none` failure gracefully (show the browser, do not fail silently).

### 3.2 Optional, only if there is demand

- [ ] **DPoP** on mobile refresh tokens (RFC 9449) — makes a stolen refresh token useless without the device key.
- [ ] **Social federation** (Google/Apple) at the OP, with explicit account-linking rules: link only on verified email, never on username.
- [ ] **MFA for `admin`** — TOTP or a second passkey, enforced by `acr`/`amr` at `/authorize`.
- [ ] **Password reset + email verification** — currently missing entirely and arguably a bigger user-facing gap than SSO. Requires an SMTP or transactional-email dependency.
- [ ] **SAML inbound** only if an external organisation requires it; do not use SAML between your own apps.

## Rollout

1. Deploy the OP alongside ROPC. Register clients. Nothing changes for users.
2. Move the calendar SPA to the BFF behind a feature flag. Soak for a week.
3. Move the tracker web app. Soak.
4. Move the console.
5. Ship the Flutter release using the system browser. Enforce a minimum supported version before removing ROPC.
6. After one release cycle with no ROPC traffic, delete `/auth/login` and the passkey login endpoints, make `audience` mandatory, and drop the `scopes` object from tokens.

Each step must be independently revertible. The OP session and ROPC can coexist indefinitely if the mobile rollout stalls.

## Out of scope

- Replacing Legacy Auth with Keycloak/Zitadel/Auth0. The OIDC surface makes that swap mechanical later; it is not needed now.
- Multi-tenancy, per-tenant branding, SCIM.
- Third-party developer clients. The client registry supports them, but nothing should be exposed publicly without a separate review.
- Removing passwords entirely. Passkeys become primary; passwords remain the recovery path until a real recovery flow exists.

## Open questions

1. Does `node-oidc-provider` run cleanly on Bun today, or do we ship a Node sidecar? (Spike first; this decides the schedule.)
2. Should `calendar.read` / `calendar.write` be separable, or is one scope per app enough?
3. Is instant permission revocation a requirement? If yes, add `token_version` or introspection before Phase 1 ships.
4. Do we need a password-reset flow before SSO, given there is no email dependency at all?
5. Can the tracker enforce a minimum app version? ROPC removal depends on it.
6. Stay on `auth.legacy-group.tech` as the passkey RP ID forever? Moving it later forces every user to re-enrol passkeys.
