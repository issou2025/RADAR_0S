This **supersedes the part of S-2026-09-23-b** that says a reference family is never a generation input and that no value from one enters a generated family. The owner is now asking for exactly that, for the parameter definitions.
2. **How it is done without breaking what does not move:**
   - The public repo is never a copy of eVolve content (rule 6: the repo is public and a push is not retractable; hard rule 3: no third-party bytes built into the product).
   - The eVolve parameter definitions are therefore **extracted from the owner's own copy into a shared-parameter file that stays private**: the private repo and `samples/`, never committed here. It is **supplied at generation time as user input**, the same way a user's own `.rfa` is loaded (S-2026-08-10-c leaves that lane unaffected).
   - What lands in this repo is only the generic, content-free machinery: read any user-supplied family's shared parameters and entity schema; write a shared-parameter file; apply it at build.
3. **"Understand how these families are generated":** a development study of the library's structure (parameter sets, shared parameters, extensible-storage entity schema, nesting, naming, types, formulas). Detailed findings that name eVolve content stay private; public records carry aggregate, content-free facts only.
4. **"/loop to constantly update it for any errors":** a self-paced, in-session loop (no Routines, no approval prompts: S-2026-08-10-b) that regenerates families with the eVolve parameter file, validates them, compares them against the reference anatomy, and fixes what it finds (S-2026-09-22-a).
