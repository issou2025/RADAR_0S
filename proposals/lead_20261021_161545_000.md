## Research Findings

### Summary
The banner in the screenshot comes from `RevitWebhookService.SubscribeAsync`, which throws when `RevitWebhooks:CallbackBaseUrl` is empty (`Services/RevitWebhookService.cs:34-39`). `appsettings.json:26-28` ships that value as `""`.

**What the user is missing:** a public, internet-reachable URL that APS can POST `adsk.c4r` callbacks to, ending in `/api/revit-webhooks`. For local development that means a tunnel:

1. Run `ngrok http 5271`.
2. Run `dotnet user-secrets set "RevitWebhooks:CallbackBaseUrl" "https://<your-ngrok-domain>/api/revit-webhooks"`.
3. Restart the app.

The **Add demo receiver** row in the screenshot (`https://localhost:7191/api/revit-webhooks/demo-receiver`) is an *outgoing* target. The app calls it itself, so localhost works there. It does not replace the *incoming* APS callback URL, which localhost cannot be.

**Root cause is missing documentation.** The README never mentions the Revit Webhooks module or this key. Issue #25's plan had a README task (TASK 8: "document `RevitWebhooks:CallbackBaseUrl`…"). Its implementation review marked that task **NOT DONE**, and PR #30 was merged anyway. A secondary UX gap: the page reports the missing setting only *after* the user fills the form and clicks **Subscribe**.

**Recommended fix:**
1. Finish the README work: setup steps, config key, ngrok, restart, re-sign-in, limitations.
2. Optionally warn on page load, disable **Subscribe** while the key is unset, and make the exception message more actionable.

### Key Discoveries
- **Where the error comes from.** The guard is the first statement of `SubscribeAsync` (`Services/RevitWebhookService.cs:34-39`). The page shows it through `catch (InvalidOperationException ex) { _errorMessage = ex.Message; }` (`Components/Pages/RevitWebhooks.razor:531-534`, bar at `:33-38`).
- **How the key is bound.** `services.Configure<RevitWebhookOptions>(configuration.GetSection("RevitWebhooks"))` (`Extensions/AutodeskServiceExtensions.cs:29`). The only in-repo documentation of the expected value is a code comment, `// Public base URL that APS calls back, e.g. "https://<ngrok-url>/api/revit-webhooks"` (`Models/RevitWebhookOptions.cs:5-7`).
- **How the callback URL is built.** `{CallbackBaseUrl}/model-publish` or `/model-sync` (`Services/RevitWebhookService.cs:83`). These map to `[Route("api/revit-webhooks")]` + `[HttpPost("model-publish")]` / `[HttpPost("model-sync")]` (`Controllers/RevitWebhooksController.cs:9,18-24`). The value must therefore end in exactly `/api/revit-webhooks`; a trailing slash is trimmed at `:34`.
- **APS cannot reach localhost.** APS Webhooks docs say the callback must be reachable from the internet ("A `localhost` address is not reachable by the Webhooks service"). It must return 2xx within ~7 s, and it is not verified when the hook is created. So a localhost value would *not* fail at Subscribe time; events would just never arrive. Sources: [Configuring Your Server](https://aps.autodesk.com/en/docs/webhooks/v1/tutorials/configuring-your-server), [Event Delivery Guarantees](https://aps.autodesk.com/en/docs/webhooks/v1/developers_guide/event-delivery-guarantees/).
- **ngrok can forward to the plain HTTP port.**
  - `Program.cs:29-43` exempts `/api/revit-webhooks` from the custom HTTPS redirect "to allow ngrok HTTP forwarding".
  - The `https` launch profile listens on `https://localhost:7191;http://localhost:5271` (`Properties/launchSettings.json:17`).
  - So `ngrok http 5271` works. `ngrok http https://localhost:7191` also works.
- **A restart is required.** `RevitWebhookService` injects `IOptions<RevitWebhookOptions>` (`Services/RevitWebhookService.cs:20`), which does not pick up config changes after startup.
- **A changed tunnel URL breaks existing subscriptions.**
  - Existing hooks are reused only if their callback URL equals the current one (`Services/RevitWebhookService.cs:166-183`), and APS does not allow editing a hook's callback URL.
  - If the tunnel URL changes, existing subscriptions keep pointing at the dead URL. The user must unsubscribe and subscribe again.
  - ngrok now gives every free account one stable `*.ngrok-free.dev` dev domain, which avoids this.
- **What fails next, once the URL is set.** These are the checks in the order the user will meet them, and they belong in the docs:
  1. A stored 3LO refresh token is required. Without one the error is "Sign in again…" (`Services/RevitWebhookService.cs:41-45`). The token is saved only during sign-in (`Controllers/AuthController.cs:97`), so users who signed in before the module existed must sign in again.
  2. The AEC Data Model extraction must be `SUCCESS`, so the model has to be a *published* RCW model (`Services/RevitWebhookService.cs:68-74`).
  3. Hooks are created with a 2-legged `data:read data:write` token (`Services/APSAuthenticationService.cs:122-125`, called at `RevitWebhookService.cs:80`).

### Detailed Findings

#### Configuration surface
- **`appsettings.json`.**
  - `RevitWebhooks` has only `CallbackBaseUrl: ""` (`appsettings.json:26-28`).
  - The optional `ExtractionPollSeconds` (30) and `ExtractionTimeoutMinutes` (60) exist only as class defaults (`Models/RevitWebhookOptions.cs:8-9`), consumed at `Services/RevitWebhookProcessor.cs:19,190-191`.
- **User secrets** are already enabled: `UserSecretsId` 917f7e38-92f4-4af8-8aeb-5228523de101 (`aps-dotnet-blazor-samples.csproj:10`). `dotnet user-secrets set` works without `init`.
- **Environment variable form:** `RevitWebhooks__CallbackBaseUrl`.
- **The older webhook flow uses a different, full-URL key.**
  - `Webhooks:CallbackUrl` (`<ngrok-url>/api/webhooks/version-added`) is documented at `README.md:100-101,115,134` and read at `Tools/RevitModelTools.cs:335-339`.
  - `RevitWebhooks:CallbackBaseUrl` is a *base* URL. The two keys look alike but are not interchangeable, and the README must make that explicit.

#### README gap (main deliverable)
- **No mention of the module anywhere.** A grep for `RevitWebhooks`, `revit-webhooks` and `CallbackBaseUrl` in `README.md` finds nothing.
  - The intro says "five key capabilities" (`README.md:12-18`), and the usage list has five workflows (`:31-40`). Revit Webhooks is in neither, though the Home card (`Components/Pages/Home.razor:78-91`) and nav link (`Components/Layout/NavMenu.razor:18`) exist.
- **Prerequisites.** These list ngrok only "to receive publish completion callbacks" (`README.md:60`). The enabled-APIs list (`:50-54`) omits the AEC Data Model API and the Webhooks API.
- **Config and deployment sections.** The config JSON and the `dotnet user-secrets` examples (`README.md:84-116`) and the deployment notes (`:128-136`) don't include `RevitWebhooks:*` or the `/api/revit-webhooks` redirect exemption.
- **Known limitations.** The section (`README.md:138-145`) lacks every item issue #25's TASK 8 listed:
  - the in-memory queue is lost on restart;
  - extraction latency;
  - `model.sync` baseline behaviour;
  - `revit.link.modified` is not implemented;
  - refresh tokens are stored in plaintext in `Data/revit-webhook-tokens.json` (`Services/RevitWebhookTokenService.cs:11,35`);
  - refresh tokens expire after ~14 days;
  - AEC DM data-out billing.
- **Outgoing event contract.** It is undocumented:
  - the envelope `version: "1.0"` and the `x-revit-webhook-signature` header (`Services/RevitWebhookDispatcher.cs:15-16`);
  - the log-only demo receiver `POST /api/revit-webhooks/demo-receiver` (`Controllers/RevitWebhooksController.cs:26-34`).

#### Revit Webhooks page UX
- **No upfront check.** `OnInitializedAsync` (`Components/Pages/RevitWebhooks.razor:293-322`) does the auth and project redirects, refreshes the store and loads models. It doesn't check configuration.
  - The **Subscribe** button is disabled only while subscribing or with no model selected (`:129-136`).
  - The page has no `IOptions`/`IConfiguration` inject (`:7-12`). No Razor component in the repo reads config directly.
- **Existing patterns for a page-load banner:**
  - Persistent Info bar with `AllowDismiss="false"` (`Components/Pages/Chat.razor:539-544`).
  - Precondition Warning bar on this same page, "No Revit Cloud Worksharing models found…" (`RevitWebhooks.razor:72-74`).
  - Role-check banners (`Components/Pages/Settings.razor:23-28`).
- **How to expose the setting to the page.** Either inject `IOptions<RevitWebhookOptions>` in the page, or add a read-only member to `IRevitWebhookService` (`Services/IRevitWebhookService.cs:5-25`), e.g. `bool IsCallbackConfigured` / `string? CallbackBaseUrl`. The second keeps the page free of config, as today.
- **Demo receiver URL.** `AddDemoReceiverTarget` builds its URL from `NavigationManager.BaseUri` (`RevitWebhooks.razor:464-470`), which is why it shows `https://localhost:7191`. That is fine for an outgoing target, since `RevitWebhookDispatcher` posts server-side via `IHttpClientFactory` (`Services/RevitWebhookDispatcher.cs:13,126`). It can confuse users into thinking the incoming callback is covered (see the screenshot), so a short hint near the targets section would help.

#### Service-level validation and tests
- **Easy to unit test.** The guard runs before any dependency is touched (`Services/RevitWebhookService.cs:34-39`; the first other dependency use is `tokenService` at `:41`). A test can construct `RevitWebhookService` with `null!` for every dependency except `Options.Create(new RevitWebhookOptions { CallbackBaseUrl = ... })` and the logger, following:
  - `AgentToolContextTests.cs:6-36`, `null!` deps with `Assert.Throws<InvalidOperationException>` + `Assert.Equal` on the message;
  - `ApsSamples.Tests/RevitWebhookProcessorTests.cs:48`, `Options.Create(new RevitWebhookOptions {...})`.
- **Test framework.** xUnit 2.9.3 with hand-written fakes and no mocking library (`ApsSamples.Tests/ApsSamples.Tests.csproj:12-16`). There is no `RevitWebhookServiceTests.cs` yet.
- **Possible extra validation, same guard location:**
  - reject a non-absolute URL;
  - reject a `localhost`/`127.0.0.1` host with a message that APS can't reach it and a tunnel such as ngrok is needed;
  - optionally warn if the value doesn't end with `/api/revit-webhooks`.
  - Today a localhost value passes the guard silently and events never arrive.

### Open Questions
- **Scope (assumption).** The issue is a "how do I configure this?" question. I assume the expected outcome is (a) answering it, by finishing the README work left undone in #25 TASK 8, and (b) the small UX improvement so the page explains the requirement before the user clicks **Subscribe**. The Plan stage can drop (b) if a docs-only change is wanted.
- **Validation strictness (assumption).**
  - Rejecting `localhost`/`127.0.0.1`/`::1` callback hosts seems safe, since APS documents they're unreachable.
  - I would *not* require `https`: APS docs don't state that HTTPS is required, though all examples use it.
  - Requiring the `/api/revit-webhooks` suffix might be too strict for reverse-proxy setups, so warn rather than reject.
- **Restart vs hot reload.** Switching `IOptions` to `IOptionsSnapshot`/`IOptionsMonitor` would avoid the restart, but that's a behaviour change beyond this issue. I assume the README will just say "restart the app".
- **Auto-deriving the URL (rejected).** Falling back to `NavigationManager.BaseUri` when it isn't localhost was considered and rejected. The OAuth `Forge:CallbackUrl` is localhost-based, so users browse via localhost, and an explicit setting is clearer.
- **Unverified web facts.** The APS docs pages are client-rendered and were read through a reader proxy, so the quotes (7-second window, localhost wording, `data:read data:write` scopes) should be spot-checked before they are copied into the README verbatim.
- **Related config drift (out of scope, possibly worth separate issues).**
  - `appsettings.json:13` has `Forge:AutomationActivity`, but code and README use `Forge:RevitAutomationActivity` (`Services/RevitAutomationService.cs:21`, `README.md:94,112`).
  - The README config example omits the required `SsaApp:ClientId`/`ClientSecret` (`Extensions/AutodeskServiceExtensions.cs:112-114`).
  - `README.md:135` and `Program.cs:32` refer to `/da`, but the controller route is `api/da` (`Controllers/RevitAutomationController.cs:11`).
  - `/api/webhooks` (the older `Webhooks:CallbackUrl` flow, `Controllers/WebhooksController.cs:9,18`) is not exempt from the HTTPS redirect. An HTTP-forwarded ngrok callback there would get a 301.
