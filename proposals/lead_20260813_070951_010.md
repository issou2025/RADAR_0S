**[proposal] Introduce the Base Image host-mediated semantic slice**

*Project description:*
## Goal

Introduce an evidence-backed Base Image semantic slice and its first Web-host vertical implementation.

Image is a fundamental GUI presentation primitive, but Proto UI does not currently have a cataloged Image prototype, an image-resource protocol, or a portable way to project source, loading state, fitting behavior, and non-text accessibility semantics. The result should establish that foundation without turning Template into a raw native-property/event escape hatch.

This issue includes the current research and a recommended technical direction. The direction is a **working proposal**, not permission to silently freeze unresolved semantics. A maintainer semantic checkpoint is required before the implementation surface is finalized.

> [!IMPORTANT]
> **Claiming guidance:** this is an advanced architecture task intended primarily for Proto UI core contributors and organization members.
>
> A contributor who is actively working toward core-contributor responsibility may ask to take it, but should expect a high bar: the work crosses spec governance, Core/Module/Host Capability design, adapter target selection, asynchronous resource lifetime, accessibility, tests, and public documentation. Please comment with a short design assessment and proposed delivery slices before starting. Do not open a full implementation PR until a maintainer confirms the semantic boundary.

## Why this is not a thin `<img>` wrapper

Proto UI Template v0 describes children inside a host-created Root and intentionally exposes only portable structural/style input for ordinary nodes:

- `spec/contracts/C-TEMPLATE-0001.yaml`
- `packages/core/src/spec/template.ts`

Adding `src`, `alt`, Web loading attributes, and native load/error handlers directly to ordinary Template props would create a Web-shaped property/event channel and weaken the existing host boundary.

Base Textarea provides the closest repository precedent:

- `spec/prototypes/P-BASE-TEXTAREA.yaml`
- `spec/contracts/C-TEXT-CONTROL-0001.yaml`
- `spec/decisions/D-TEXT-CONTROL-PROJECTION-0001.yaml`
- `spec/host-caps/HC-TEXT-CONTROL-0001.yaml`
- `packages/modules/text-control/`
- `packages/prototypes/base/src/textarea/`
- `internal/records/2026-08-02-text-control-host-boundary.zh-CN.md`
- `internal/records/2026-08-02-host-surface-projection.zh-CN.md`

Textarea demonstrates that a leaf prototype can declare a portable static requirement, let the adapter choose one physical host target, synchronize it through a bounded lease, preserve host-owned behavior, and return empty Template children. The same pattern is currently the strongest fit for Image.

## Research summary

### Base UI and Radix UI

Base UI and Radix expose Image as part of an Avatar family:

- Base UI Avatar: https://base-ui.com/react/components/avatar
- Radix Avatar: https://www.radix-ui.com/primitives/docs/components/avatar
- Radix implementation: https://github.com/radix-ui/primitives/blob/main/packages/react/avatar/src/avatar.tsx

The reusable findings are:

- a small image-loading state machine such as `idle | loading | loaded | error`;
- the loaded image and fallback are separate parts;
- arbitrary fallback content may be shown while loading or after error;
- delayed fallback can avoid a flash on fast/cache hits;
- changing the source must reset and re-evaluate the current request.

These libraries primarily specify **Avatar composition**, not a general cross-host Image primitive. Proto UI should therefore avoid making Avatar fallback policy intrinsic to Base Image.

### HTML and accessibility

Relevant references:

- HTML `img`: https://html.spec.whatwg.org/multipage/embedded-content.html
- WAI Images Tutorial: https://www.w3.org/WAI/tutorials/images/
- APG accessible names and descriptions: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/

Important conclusions:

- an informative image needs an author-provided text alternative;
- a decorative image needs explicit null/decorative semantics;
- a functional image obtains its functional name from the owning control/link context rather than describing its pixels;
- complex images require a longer description outside a short alternative;
- Web `alt` is one host projection of these semantics, not the portable API itself;
- Image is normally a non-interactive semantic object, not a keyboard widget.

Representative host APIs:

- Android ImageView and ScaleType:
  - https://developer.android.com/reference/android/widget/ImageView.html
  - https://developer.android.com/reference/android/widget/ImageView.ScaleType.html
- Jetpack Compose image loading/customization:
  - https://developer.android.com/develop/ui/compose/quick-guides/content/load-images
  - https://developer.android.com/develop/ui/compose/graphics/images/customize
- SwiftUI Image / AsyncImage:
  - https://developer.apple.com/documentation/swiftui/image
  - https://developer.apple.com/documentation/swiftui/asyncimage
- Flutter Image / BoxFit:
  - https://api.flutter.dev/flutter/widgets/Image-class.html
  - https://api.flutter.dev/flutter/painting/BoxFit.html
- React Native Image: https://reactnative.dev/docs/image
- Qt Quick Image: https://doc.qt.io/qt-6/qml-qtquick-image.html
- Windows Image source/stretch:
  - https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.controls.image.source
  - https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.controls.image.stretch

The shared portable intersection is relatively small:

- a source reference resolved by the host;
- asynchronous request/loading outcome;
- a physical image presentation surface;
- contain/cover/fill-like fitting behavior;
- alignment/position;
- semantic label or decorative exclusion;
- bounded lifetime and replacement behavior.

Caching, request headers, CORS/referrer policy, responsive Web candidates, fetch priority, decode scheduling, downsampling, bitmap memory, animated-frame control, EXIF behavior, color space, and platform image objects vary substantially. They should not be promoted into the first portable contract merely because one host exposes them.

## Recommended architecture

### 1. Introduce a host-mediated Image View domain

The current recommendation is a contentless, single-target Base Image protocol:

1. The prototype statically declares a host-owned image-view requirement.
2. The adapter resolves it before first render.
3. A mixed-lifetime Image View module connects the logical instance to a host lease.
4. The lease receives portable patches and reports normalized facts/events.
5. The protocol renderer returns `null`; it does not render authored children.
6. Root visual intent projects to the physical image view.
7. Raw host targets, native events, native error objects, and platform image instances never enter prototype payloads.

The initial Web profile should materialize exactly one `HTMLImageElement`. React and Vue may collapse logical boundary and physical image target. A Web Component adapter may keep the custom-element boundary and use an inner `img` as the presentation/a11y/image-resource target, following `C-HOST-SURFACE-PROJECTION-0001`.

Passing Web Component, React, and Vue tests on the Web host proves a cross-adapter Web profile only. It must not be described as completed multi-host conformance.

### 2. Proposed entity chain

Names/IDs are proposed and must be checked against the catalog before authoring:

- `K-IMAGE-0001` — Image is a host-decoded visual resource domain.
- `D-IMAGE-PROJECTION-0001` — fetching/decoding/caching and the physical image view remain host-owned.
- `C-IMAGE-VIEW-0001` — portable source, request generation, loading facts, fitting, accessibility, and lease lifetime.
- `HC-IMAGE-VIEW-0001` — host can lease one physical image view.
- `M-IMAGE-VIEW-0001` — module owns normalized status and current-request reconciliation.
- `P-BASE-IMAGE` — `base-image-root` and `asImageRoot`.
- `T-IMAGE-VIEW-0001` and `T-BASE-IMAGE-0001` — contract and prototype evidence.

Do not create empty entities just to complete the list. A coherent smaller chain is preferable if repository analysis shows that knowledge or decision content belongs in an existing entity.

### 3. Proposed portable surface

A starting point for discussion:

```ts
type ImageLoadingStatus = 'idle' | 'loading' | 'loaded' | 'error';

type ImageSourceRef =
  | { kind: 'uri'; uri: string }
  | { kind: 'asset'; key: string };

type ImageFit = 'contain' | 'cover' | 'fill' | 'none' | 'scale-down';

interface ImageRootProps {
  source?: ImageSourceRef;
  alternativeText?: string;
  decorative?: boolean;
  fit?: ImageFit;
  position?: 'center';
  labelledBy?: string;
  describedBy?: string;
}
```

This shape is not yet normative:

- `uri` is the minimum source kind needed by the first Web profile.
- `asset` should be included only if the resolution owner and app/package namespace can be specified portably; otherwise defer it without closing the source descriptor to future extension.
- `position` may begin with `center`, but its coordinate/keyword model must be decided before expansion.
- Proto UI should choose explicit fitting semantics rather than inherit incompatible host defaults. Current recommendation: default to `contain`.
- `alternativeText` and `decorative` express semantic intent; Web `alt` is an adapter projection.

Expected prototype exposes:

- state: `loadingStatus`;
- event: `loadingStatusChange`;
- event: normalized `load`;
- event: normalized `error`.

The first contract should avoid exposing a host error message unless there is a stable, privacy-safe portable error classification.

### 4. Required request-generation behavior

The protocol needs explicit asynchronous replacement rules:

- no source resolves to `idle`;
- accepting a new non-empty source starts a new logical request and reports `loading`;
- success for the current request reports `loaded`;
- failure for the current request reports `error`;
- source replacement invalidates the previous request generation;
- late success/error from an invalidated generation must be ignored;
- detach/dispose revokes listeners and host references and prevents later emissions;
- synchronous/cache-hit completion must still produce a deterministic observable sequence;
- equivalent prop synchronization must not restart a settled current request unnecessarily.

Current v0 recommendation is to clear the previous visible resource when the source changes. “Keep the previous image until the replacement is ready” is useful, but should become an explicit later replacement policy rather than accidental host behavior.

“Loaded” should mean that the host has a displayable image result for the current request, not that every byte/frame of every possible animated format has been downloaded. The exact Web event mapping and any decode-before-reveal policy must be recorded.

### 5. Accessibility boundary

The semantic checkpoint must define at least:

- informative image: a non-empty alternative or resolvable naming relationship is required;
- decorative image: explicitly excluded from the semantic tree; Web uses `alt=""`;
- functional image: the surrounding Button/Link owns the functional name and the image is normally decorative;
- complex image: short alternative plus a description relation or a later Figure/Description family;
- contradictory input such as `decorative: true` plus a non-empty alternative must fail, warn, or follow one documented precedence rule;
- Base Image does not become focusable or clickable merely because a host image view supports pointer events.

### 6. Keep Avatar as a later composition

After Base Image is stable, a separate Base Avatar proposal may define:

```text
Avatar.Root
├── Avatar.Image     -> consumes the Image View protocol/status
└── Avatar.Fallback  -> consumes family context and Presence/delay policy
```

Avatar owns fallback composition and optional delay. Base Image should not own arbitrary fallback children, initials, skeletons, or presence policy.

## Required design questions

The proposal/implementation must answer or explicitly defer:

1. Is `Image View` the correct domain name, or should the contract distinguish resource loading from visual projection?
2. Is source a single URI-only v0 value or an extensible JSON descriptor?
3. What constitutes source equality and when does a request generation restart?
4. Does `loaded` mean fetch complete, decode complete, first displayable frame, or host-selected readiness?
5. Should Web use native load readiness directly or an explicit `decode()` gate?
6. Is the recommended replacement policy “clear previous” correct for v0?
7. Which fit/alignment values form a genuinely portable intersection, and what is Proto UI's default?
8. How are intrinsic dimensions exposed, if at all? Are authored width/height resource hints distinct from layout styling?
9. How are informative, decorative, functional, and complex-image semantics validated and projected?
10. Which target receives presentation, a11y, resource properties, and normalized events when the logical boundary is split?
11. What behavior remains host-owned for caching, downsampling, animation, orientation, color, and memory pressure?
12. Can a host-neutral fake capability prove lifecycle/state semantics before adding a second real host?

## Delivery checkpoints

### Checkpoint A — semantic proposal

Before implementation, post or PR an evidence-backed proposal containing:

- entity/relationship graph;
- source and loading-state model;
- request-generation and stale-event rules;
- fitting/alignment table across representative hosts;
- accessibility matrix;
- host-owned versus Proto-owned responsibility table;
- Web target/surface mapping;
- explicit non-goals and open questions;
- intended executable test paths.

A maintainer must approve or request revisions at this checkpoint.

### Checkpoint B — host-neutral protocol

- Core types and static declaration.
- Image View module and host capability.
- Fake-host tests for status sequence, replacement, stale events, lease rebinding, detach, and dispose.
- No Web type or tag in portable declaration metadata.

### Checkpoint C — Web vertical slice

- Web `HTMLImageElement` host implementation.
- Web Component, React, and Vue adapter wiring.
- split boundary/surface/a11y projection coverage;
- cache-hit, source replacement, failure, and lifecycle integration tests.

### Checkpoint D — Base Image and projections

- `base-image-root` and `asImageRoot` with reusable frozen static requirements.
- Draft catalog entities and executable mappings.
- API/types exports and package surface.
- docs/demo showing informative, decorative, contain, cover, loading, error, and source replacement cases.
- generated projections updated through their generators.

## Acceptance criteria

- [ ] The semantic checkpoint is approved by a maintainer before the public protocol surface is finalized.
- [ ] Applicable existing spec entities, recent records, implementation paths, tests, and docs are traced before new entities are authored.
- [ ] Base Image uses a portable static requirement and one bounded host lease; Template gains no generic native property/event channel.
- [ ] The portable declaration contains no Web tag, DOM type, UIKit/Android/Flutter class, or other concrete host materialization.
- [ ] Request generations have deterministic `idle/loading/loaded/error` behavior and suppress stale completion.
- [ ] Equivalent updates, source replacement, synchronous/cache-hit completion, detach, target replacement, and dispose have executable coverage.
- [ ] Informative and decorative accessibility semantics are validated and projected correctly.
- [ ] Fit semantics and defaults are explicit and covered by tests.
- [ ] Web Component, React, and Vue use one physical `img` per instance and preserve the correct boundary/surface ownership.
- [ ] Native events and platform error objects do not leak into prototype event payloads.
- [ ] Cross-adapter Web evidence is described accurately and not presented as multi-host conformance.
- [ ] Public package exports, docs, demos, catalog relations, and generated projections remain consistent.
- [ ] Relevant focused tests, `check:prototype-catalog`, `check:agent-doc`, type checks, and proportional workspace tests pass.

## Out of scope for the first slice

- Avatar fallback/initials/delay behavior.
- Skeleton, spinner, retry UI, progress UI, or live-region announcements.
- Image upload, editing, crop tools, zoom/pan, lightbox, gallery, carousel, or image maps.
- Making Image a Button, Link, drag source, or focus target.
- Responsive Web `picture/srcset/sizes` syntax.
- Web-only CORS, referrer policy, fetch priority, and element timing guarantees.
- General request headers, authentication, cache policy, prefetching, or offline storage.
- Custom decoder registration, raw bytes/streams, platform image objects, bitmap memory control, animated-frame control, EXIF/color-space policy, or GPU texture ownership.
- Base Avatar or any design-language Image/Avatar projection before Base Image semantics stabilize.
- Claiming non-Web host conformance without a real second-host implementation or an explicitly limited host-neutral harness.
