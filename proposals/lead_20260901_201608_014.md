# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**[enhancement] Expose bounded realtime action timing and input-lease handoff semantics**

*Project description:*
## Problem

Runtime integration profiles can truthfully declare `realtime`, `bounded-input`, and `input-lease`, but `StepRequest` currently carries only the action and lifecycle cursor. There is no portable way for a provider to advertise the action hold/settle window, report that a command was consumed before the deadline, cancel an obsolete command, or hand the input lease to a supervised operator/CUA path.

For movement and combat actions, a command that is shorter than the game\'s input sampling window can produce no movement while still looking like a successful step. Supervisors then compensate with repeated turns, dodges, or jumps instead of switching to a different route or a bounded manual handoff.

## Proposal

Add an opt-in, versioned realtime-control capability with:

- descriptor-level timing contract: minimum/maximum hold, settle deadline, simulation quantum and clock source;
- per-step bounded deadline/quantum and a typed consumed/expired result;
- cancellation/preemption fencing for commands that are no longer valid;
- explicit input-lease acquire, renew, release and preempt operations bound to the same target/session identity;
- post-action readback linked to the timing receipt.

The contract must remain learner-neutral and must not expose generic OS automation. Providers that do not support realtime timing keep the current schema.

## Acceptance criteria

- Synthetic realtime fixtures cover short-window expiry, normal consumption, cancellation and lease preemption.
- A stale lease or deadline cannot mutate the target.
- The host returns a typed outcome when the action was not consumed and never retries it implicitly.
- Python, Rust, C# and C++ SDKs validate identical timing/lease fields.
