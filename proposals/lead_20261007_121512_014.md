## Approved parent-plan excerpt for this phase
Split the reusable managed CI into three parts: a read-only `validate` entry point, caller-owned test jobs, and a `publish` entry point. Each test job starts with a literal checkout of the validated SHA and a HEAD check, and ends with a pinned `attest` composite action. `publish` runs a read-only verify job and then a status-only job, which is the only job anywhere with `statuses: write`. The verify job selects the current-attempt attestations by strictly parsed artifact name and validates each against the exact `managed-ci-attestation/1` schema. It checks them against a literal expected set from the default-branch caller; each entry is `{attestation_id, job_name, needs_key}`. It requires the jobs API conclusion of each expected job name to be `success` and every declared needs entry to be `success`. Before writing anything, the status job independently checks that the forwarded inputs, target SHA and nonce equal the dispatch event, and writes no status on any mismatch. Otherwise it feeds `needs.verify.result` into today's unchanged status builder. A validation failure or correlation mismatch writes no status, any verify or preparation failure writes failure, and only a fully verified run writes success. Attestations are untrusted correlation claims; trust comes from the default-branch composition and API job conclusions. The existing workflows, the dispatch validator (including its rerun and freshness rules) and the driver stay unchanged. Stages: attestation library and action; the workflow entry points with contract and composition tests; adopter docs; a human-run SHA-pinned release and cross-repo probe; then the llm-dialectic#1383 amendment.

### Plan steps
1. Context (verified in source): `.github/workflows/managed-ci.yml` inlines the dispatch validator (job `validate-managed`, read-only, outputs target_sha/pr_number/managed_nonce/matrix), sharded `exact-head-shard` legs that check out the validated SHA and verify HEAD before installing, the `exact-head` literal aggregate, and `publish-exact-head`. That last job is the only `statuses: write` job; it reads `needs.exact-head.result` and its decision is extracted to `tests/fixtures/managed_ci/publisher.py`. Callee scripts come from `job.workflow_repository@job.workflow_sha` (`ci/managed/`), and attempt-suffixed artifacts are retained across reruns (`ci_shard_verify.py` selects among attempts). The driver (`managed_ci.py`) reads only the caller's `ci.yml` readiness markers and correlates runs by run-name and the status description `nonce=..;run_id=..;attempt=..;result=..`. The split must preserve all of these.
2. Attestation schema (stage 1): add `ci/managed/attestation.py` with a versioned JSON record. The record must be a JSON object of at most 16 KiB with exactly these keys and no others (unknown fields are rejected): `schema` (exactly the string `managed-ci-attestation/1`), `attestation_id` (string matching `[a-z0-9][a-z0-9._-]{0,63}`), `job_name` (non-empty string of at most 256 characters), `target_sha` and `head_sha` (lowercase 40-hex strings), `run_id` and `run_attempt` (positive JSON integers, not strings or booleans), `repository` (an `owner/name` string) and `job_status` (string, advisory only). The artifact name is `managed-ci-attest-<attestation_id>-attempt-<run_attempt>`, parsed with the anchored regex `^managed-ci-attest-([a-z0-9][a-z0-9._-]{0,63})-attempt-([1-9][0-9]{0,5})$`, which splits unambiguously at the last `-attempt-`. Each artifact contains exactly one `attestation.json`. The `write` subcommand fails non-zero without writing on a malformed SHA or a `git rev-parse HEAD` mismatch, and otherwise emits the record. A pure `verify(...)` function returns success or failure with reasons.
3. Attest composite action (stage 1): `.github/actions/managed-ci-attest/action.yml` takes the inputs `target_sha`, `attestation_id` and `job_name`. It fetches `ci/managed` from `github.action_repository` at `github.action_ref`, and fails closed when either is empty or the ref is not a 40-hex commit SHA (tags and branches are rejected). It then runs `attestation.py write` and uploads with `if-no-files-found: error`. Callers place it last in the job with the default `if: success()`. Every adopter use, like the reusable workflow uses, is pinned to a full commit SHA, with the release tag only as a trailing comment.
4. Security contract (what is trusted and why). The trust root is the default-branch caller, which managed dispatch executes, so PR code cannot change it. That caller declares four things literally: (a) each expected test job's first steps check out `needs.validate.outputs.target_sha` and assert `git rev-parse HEAD` equals it before any install or test step, as `managed-ci.yml` does today; (b) the expected set; (c) `needs` on validate and every expected job; (d) the permissions (test jobs `contents: read`). Pass/fail authority is the Actions jobs API conclusion of the expected job name in the current attempt, plus the caller-evaluated `toJSON(needs)` results. PR code can influence neither. The attestation artifact is written inside a runner that has executed PR-head code, so it is an untrusted claim. PR code can forge, alter or suppress it, and it does not prove that the pinned writer ran or that `head_sha` is true. The publisher uses it only for correlation and accounting: a declared identity reached its final step in this run and attempt naming the validated target. A missing, duplicate, extra or mis-bound record fails the run. It mainly catches misconfiguration (a wrong ref, a missing attest step or a stale artifact). The head binding rests on (a), which the contract tests check in the fixture caller and the docs require. Like today's model, none of this proves test quality: PR-controlled tests can exit 0.
5. Verifier rules (stage 1). `verify(expected, artifacts, api_jobs, needs_results, run_id, run_attempt, target_sha, repository)`: (1) `expected` must be a non-empty JSON array of at most 256 objects with exactly `attestation_id`, `job_name` and `needs_key` (valid id, non-empty name, valid job key). Ids and job names must be unique, otherwise fail. (2) Artifact selection: take artifact names matching `managed-ci-attest-*`. Any name that fails the anchored regex fails. Names whose parsed attempt is lower than the current `run_attempt` are ignored as retained history; a higher attempt fails. Only current-attempt artifacts are considered. (3) Record schema: each selected artifact must contain exactly one record that is valid under step 2's schema, checked before any binding comparison. A missing or unsupported `schema` value, a missing, extra or wrongly typed field, non-JSON content, a non-object or an oversized file all fail. (4) Within the selected set: the record's attestation_id and run_attempt must equal the values parsed from the artifact name. A duplicate id (two artifacts or records) fails, an id not in `expected` (extra) fails, and a missing expected id fails. (5) Per expected entry: the record's `job_name` must equal the expected `job_name`; `target_sha` and `head_sha` must equal the validated target; `run_id`, `run_attempt` and `repository` must equal the publisher's own. (6) The API job is looked up by the trusted expected `job_name` in `GET /repos/{repo}/actions/runs/{run_id}/attempts/{run_attempt}/jobs` (all pages). Exactly one job must match, with `conclusion == 'success'`; failure, cancelled, skipped, timed_out, null or ambiguous all fail. (7) `needs_results` must be a non-empty JSON object whose values are objects with a string `result`. Every result must be `success`, and every expected `needs_key` must be present. Malformed input fails. (8) An unavailable API or a malformed page fails. Success requires every rule to pass. The record's self-reported `job_status` is never trusted.
6. Validate entry point (stage 2): add `.github/workflows/managed-ci-validate.yml` (`workflow_call`). Its inputs are the four forwarded dispatch inputs only. Its single job keeps `validate-managed`'s read-only permissions, `if:` routing, concurrency group and forwarded-equals-event check, and its validator step is byte-identical to the one in `managed-ci.yml`, enforced by a contract test. Outputs: target_sha, pr_number, nonce, run_id (`github.run_id`), attempt (`github.run_attempt`).
7. Publish entry point (stage 2): `.github/workflows/managed-ci-publish.yml` (`workflow_call`) contains two jobs, mirroring today's split between `exact-head` and `publish-exact-head`. Inputs: the four forwarded dispatch inputs, `target_sha`, `nonce`, `validation_result`, `needs_results` (the caller passes `${{ toJSON(needs) }}`) and `expected_attestations` (a literal in the default-branch caller). Job `verify` has `if: always()` plus routing and `inputs.validation_result == 'success'`, and only `actions: read` and `contents: read`. It checks out `ci/managed` from `job.workflow_repository@job.workflow_sha` (failing closed on an empty context), downloads `managed-ci-attest-*` artifacts into per-artifact directories, pages the jobs API, runs `verify`, and ends with a literal `test "$VERIFY_RESULT" = success`. Job `publish` has `needs: verify`, `if: always()` plus the managed routing expression, and only `statuses: write`. It runs no repository code and downloads nothing. Its inline step first runs a correlation guard, a new verbatim-extracted block `MANAGED_CI_SPLIT_STATUS_GUARD` with fixture `tests/fixtures/managed_ci/split_status_guard.py`. The guard works independently of verify and writes no status (exit 0 with a message, like today's invalid-correlation path) unless every check passes: each forwarded input equals the matching `github.event.inputs` value; the supplied `target_sha` equals the event's `expected_head_sha`; the supplied `nonce` equals the event's `managed_nonce`; and `validation_result` is `success`. Only after the guard passes does it call the verbatim `build_status_request` block with `test_result = needs.verify.result`. A correlation rejection is therefore a no-write outcome, distinct from preparation errors. Once the guard passes, any checkout, download, API or verifier failure, or a skipped or cancelled verify job, yields `failure` on the guarded target. The status context, description and target_url are unchanged.
8. Rerun semantics (validator and driver unchanged). `validate_dispatch` (copied verbatim into validate) authorizes an execution only when the intent is at most 15 minutes old (and no more than 5 minutes in the future), and either the record's run pair equals the executing run and attempt, or the record is the driver's completed no-status retry and the execution is exactly the next attempt of that same run. Consequences for the split layout: (a) the only supported in-run recovery is that authorized no-status retry within the freshness window. Validate passes in attempt N+1, and every expected job must run and attest in attempt N+1. Retained attempt-N artifacts are ignored by name-based selection, so a `Re-run all jobs` retry verifies, while a retry that carries over expected jobs from attempt N fails as missing. (b) Any other rerun is rejected by validate and writes no status, exactly as today: after a published success or failure, with a stale intent, or with a skipped or unmatched attempt. (c) Ordinary recovery after a failure status remains the driver's fresh managed dispatch (a new run at attempt 1). No lifecycle change is in scope, and the docs promise reruns only under (a).
9. Expected set: v1 accepts only a literal declared in the default-branch caller. Routed-matrix adopters (llm-dialectic) declare the full managed-dispatch cell set literally; routing under a managed dispatch must select that set, and every cell attests (`attestation_id: unit-${{ matrix.cell }}`, `job_name` equal to the rendered cell name, `needs_key` equal to the matrix job key). Computed expected sets are out of scope (see caveats).
10. Legacy compatibility (stage 2): `managed-ci.yml`, `managed-ci-ordinary.yml`, this repository's `ci.yml`, the `ci/managed` shard scripts, `V2_FEATURE_MARKERS`, run-name and the status format all stay unchanged. The driver needs no change because the split caller keeps the same readiness literals in its own `ci.yml`.
11. Contract tests (stage 2): extend `tests/test_workflow_contract.py` with a fixture split caller `tests/fixtures/managed_ci/split_caller.yml`. It has validate, a services job, a matrix job and publish, all pinned by 40-hex SHA. Assert: (1) validate and publish are `workflow_call` with exactly the documented inputs; (2) across all split callee jobs, only the publish status job holds `statuses: write`, and verify holds only `actions: read` and `contents: read`; (3) the validator block is byte-identical to `managed-ci.yml`, the publisher block byte-identical to the extraction fixture, and the status-guard block byte-identical to its new fixture; (4) the status job runs the guard before the builder, its `test_result` is literally `needs.verify.result`, it has `if: always()`, and it has no checkout or download step; (5) routing guards keep an all-empty dispatch out; (6) in the fixture caller, every expected test job's first steps are the literal `ref: ${{ needs.validate.outputs.target_sha }}` checkout followed by a HEAD check before install or test steps, its last step is attest, it has `contents: read` only, publish `needs` covers validate and every `needs_key`, and the caller passes literal `expected_attestations` and `toJSON(needs)`; (7) the attest action rejects a non-SHA ref and uploads with `if-no-files-found: error`. Status-step tests drive the extracted guard plus builder with a recording request stub. With a valid tuple, verify results success, failure, cancelled and skipped yield exactly one success or failure request on the event SHA. A well-formed but mismatched `target_sha`, a mismatched `nonce`, any forwarded input differing from the event, or a non-success `validation_result` yields zero requests. Rerun composition tests use the existing `tests/fixtures/managed_ci/dispatch_validator.py` extraction: an authorization record for the driver's completed no-status retry passes `validate_dispatch` for attempt N+1, and its outputs then feed `verify` with retained attempt-N plus complete attempt-N+1 artifacts, which succeeds. With carried-over jobs it fails as missing. A stale intent, an unmatched attempt and a rerun after an attached or completed record with a different attempt are rejected by `validate_dispatch` before any verifier call (no status). Keep every existing test green.

### Execution strategy recommendation (v1)
- `topology_source`: `approved-plan-v1`
- `strategy`: `staged`
- `staging_feasibility`: `safe`
- `rationale`: The work changes the trust gate and spans this repository plus another repository, so it separates cleanly. The attestation library and action are inert until a publisher consumes them. The new workflows are additive and leave the existing single-job gate untouched. Docs follow the stable contract. Release, probe and the llm-dialectic migration are human-owned and depend on a merged, SHA-pinned artifact. The issue also asks for decompose-only review of each stage before implementation.

#### `scope_items`
- `scope-attest`
  - `requirement`: Provide a pinned attest composite action that asserts the checked-out HEAD equals the validated target SHA and uploads an attestation naming target SHA, run ID, attempt, job and matrix-cell identity and the job result.
  - `acceptance_criteria`:
    - The action refuses to attest and writes no artifact when HEAD differs from target_sha.
    - The artifact record contains target_sha, run_id, run_attempt, attestation_id, job_name and job_status in a versioned schema.
    - The action loads its scripts from its own pinned repository and ref and fails closed when that context is empty.
    - The action rejects any action ref that is not a 40-hex commit SHA.
- `scope-verify`
  - `requirement`: Implement the fail-closed attestation verifier that decides publish success from a default-branch-declared expected set, the attestations, the jobs API conclusions and the caller's needs results.
  - `acceptance_criteria`:
    - The verifier fails for missing, duplicate, extra, foreign-SHA, foreign-run or foreign-attempt attestations.
    - The verifier fails when any attested job's API conclusion is not success, including skipped, cancelled and null.
    - The verifier fails when the expected set is missing, empty or malformed, or when the API listing is unavailable.

  - `requirement`: Provide a read-only reusable validate entry point that runs today's dispatch validation and outputs target_sha, pr_number, nonce, run_id and attempt.
  - `acceptance_criteria`:
    - The validate workflow is workflow_call with only the four forwarded dispatch inputs and read-only permissions.
    - Its validator block is byte-identical to the one in managed-ci.yml, enforced by a contract test.
    - It outputs target_sha, pr_number, nonce, run_id and attempt.
- `scope-publish`
  - `requirement`: Provide a reusable publish entry point, the only job with statuses: write, that publishes final-ci/exact-head success only when the verifier passes, failure otherwise, and nothing when validation failed.

#### `caveats`
- Attestations are written in runners that have executed PR-head code, so they are untrusted correlation and accounting claims, not proof that the pinned writer ran or that HEAD was the target. The head binding rests on the default-branch caller's literal checkout and early HEAD check, and the outcome on the API job conclusion. As today, PR-controlled tests can still exit 0.
- The publisher cannot inspect the caller's workflow text, so the literal-checkout requirement is enforced by docs, the template and the fixture contract tests, not at runtime. It is still governed by default-branch review.
- Expected sets computed from job outputs (for example a route job's matrix) are excluded from v1. Routed adopters must declare the full managed-dispatch cell set literally.
- Job-name matching depends on GitHub's rendered job names for reusable-caller matrix cells. The stage-4 probe must confirm the exact rendering before adopters rely on it.
- Reruns are bounded by the unchanged validator: only the driver's completed no-status retry (the next attempt of the same run, within 15 minutes of the intent) is authorized, and it must re-run every expected job. Every other rerun writes no status, and recovery is a fresh managed dispatch. Broader rerun support would be a separate lifecycle change outside this issue.
