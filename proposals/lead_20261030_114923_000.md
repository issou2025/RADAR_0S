# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat: rebase on upstream 1.0 with a bounded fork layer for the eight local actions**

*Project description:*
## Problem Statement

This fork and upstream diverged at `5a65afc` (2026-09-16, upstream v0.5.0). Upstream has since shipped 133 commits, including a 1.0 release that rewrote the action pipeline, added 53 tools, and added a policy layer, a batch supervisor and an updater. This fork has shipped 55 commits that add eight actions upstream does not have.

Both directions were considered and one is now decided (`adr/0001`):

- Merging the fork into 1.0 produces 50 conflicted files concentrated in exactly the files the fork edited most. That is a rewrite plus 50 resolutions.
- Staying on the v0.5.x trunk and hand-porting upstream fixes keeps the fork on an architecture upstream no longer maintains, and every security fix has to be re-derived against code that no longer looks the same.

The fork's value is eight actions and the Revit behaviour behind them, not its architecture. It should sit on the maintained base, not fork it.

## Solution

Upstream 1.0 is the base. The fork becomes a bounded layer on it.

- Base: upstream commit `760bb7c` (v1.0.0 plus eleven post-release fixes), recorded as a full SHA.
- The eight fork actions are rewritten against the upstream contracts by remapping contracts, keeping behaviour (`adr/0002`).
- Fork code lives only in `src/RevitModelMcp.Core/Fork/`, `src/RevitModelMcp.Addin/Fork/` and `server/revit_model_mcp/fork_actions.py` (`adr/0005`).
- The fork touches upstream files at seven named dispatch hooks plus one Python registration line, bounded at 80 changed lines.
- Writes are read-only by default, expressed through the upstream policy (`adr/0003`).
- `revit_batch` is deleted in favour of upstream `revit_run_actions` (`adr/0004`).
- Revit 2020 is ported on 2022–2027 first, then restored as a required follow-up (`adr/0006`).
- The site generator is kept, the translated prose is dropped (`adr/0007`).

The eight actions, all confirmed absent from upstream:

`revit_create_floor`, `revit_create_level`, `revit_export_element_ids`, `revit_merge_phases`, `revit_rebuild_model_ids`, `revit_reset_element_ids`, `revit_set_phase`, `revit_set_view_lighting`.

## User stories

1. As a maintainer, I merge an upstream release into the fork and the conflicts appear only inside the seven hooks.
2. As a maintainer, I add a ninth fork action by adding one file under `Fork/` and one Python tool, without touching the seven hooks.
3. As a maintainer, I read the fork layer and see only fork code, never a modified copy of upstream code.
4. As a maintainer, a change that pushes the fork past 80 changed lines or past 7 hooks fails a check.
5. As a user, I install the fork and every action tool refuses with a read-only error until I change the policy.
6. As a user, I install the fork and the eight fork actions behave exactly like upstream actions: same dry run, same verification block, same error shapes.
7. As a user, I call `revit_run_actions` with a fork action in its steps and it runs inside the same undo step as upstream actions.
8. As a user, I call a fork action with `dry_run` and get a verification block without touching the model.
9. As an agent, I get a structured refusal when the model is read-only, not a missing tool.
10. As a user, I get the 53 upstream tools without the fork having reimplemented any of them.
11. As a maintainer, `revit_batch` is gone and `revit_run_actions` is the only batch tool.
12. As a maintainer, the tool manifest is derived from the registry and a drift check fails when it disagrees.
13. As a maintainer, the fork states which upstream commit it is based on, in one place, as a full SHA.
14. As a maintainer, the activity panel shows a fork action's title and summary in the same shape as an upstream action.
15. As a maintainer, I run the local gate suite and know whether the fork still fits its budget.
16. As a user, the model rebuild still refuses MEP system members, still excludes sketch lines, and still answers the duplicate-name dialog.
17. As a user, the element id export still produces the same workbook columns.
18. As a maintainer, the site's tool pages are generated from the registry, so a new fork action appears without hand-editing.
19. As a maintainer, I can see which upstream commits are in the base and which are not, without reading git log.
20. As a user on Revit 2020, the release notes tell me the gap and its date, instead of failing at load.

## Implementation decisions

**Base and branch.** A branch from `760bb7c`. The identity work already in the working tree predates this base and is replayed on it, not carried across (the installer, the bundle manifest and the release workflow all changed upstream).

**The seven hooks.** All in fallback branches, so upstream code keeps its own path:

| # | File | Anchor |
| --- | --- | --- |
| 1 | `src/RevitModelMcp.Core/Control/ActionJobParser.cs` | `IsAction` |
| 2 | `src/RevitModelMcp.Addin/Control/ActionCommandExecutor.cs` | the `Unknown action` arm |
| 3 | `src/RevitModelMcp.Addin/Control/ActionVerifier.cs` | `CaptureBefore` |
| 4 | `src/RevitModelMcp.Addin/Control/ActionVerifier.cs` | `CaptureAfter` |
| 5 | `src/RevitModelMcp.Core/Activity/ActionSummaryBuilder.cs` | the `_ =>` arm |
| 6 | `src/RevitModelMcp.Core/Activity/ActivityTitleBuilder.cs` | the `Phrases` dictionary |
| 7 | `src/RevitModelMcp.Addin/Application.cs` | `SupportedCommands` |

Plus, on the Python side, the action step union and one registration call in `fork_actions.py`.

**Why a registry.** Adding one action the upstream way touches eleven files. Eight actions is roughly ninety edits, each a fresh conflict site. The registry costs seven hooks once.

**Verification fields.** Upstream `ActionFacts` already reports elements, ids, category, bounding box, family, type, level, parameter, value, storage type, owner, requested dependents and still-present. The fork appends only its difference: name, elevation in millimetres, four phase fields, two reassignment flags, the remaining-source count, and the lighting block. No second verification model.

**Naming.** Zero fork renames except the forced `revit_batch` removal. `revit_set_view_lighting` matches upstream's own `revit_set_view_visibility` convention. `revit_export_element_ids` does not collide with `revit_export` or `revit_export_nwc`, where `export_element_ids` is a parameter name.

**Intake ledger.** The per-commit ledger and its gate were built for the trunk model. They stop governing the base and become reference material for reading what upstream shipped. The rhythm becomes: once per minor release, read the upstream range, then merge.

**Order of work.** The tracer action proves the seam before anything else is ported: `revit_set_view_lighting` touches every contact point and its logic is the most self-contained. Then `create_level`, `create_floor`, `set_phase`, `merge_phases`, `element_id_register`, `reset_element_ids`, and finally `rebuild_model_ids`, whose size is roughly the previous five together.

## Testing decisions

- **Seam behaviour.** With an empty registry the product behaves byte for byte like upstream 1.0. The upstream Python suite does not move.
- **Surface consistency.** A check derives the tool manifest from the registry and fails when the manifest, the action vocabulary, the supported-command list or the Python step union disagree.
- **Budget.** A check counts changed lines in the seven hook files against the base and fails above 80, and fails if a fork edit appears outside them.
- **Contract tests.** Each ported action gets a Core parser test and a Python action test, following the shape of the existing ones.
- **Compilation.** The C# build is verified by Windows CI. The local machine cannot build it: the SDK pinned by `global.json` is not installed.
- **Real Revit.** Reserved for the tracer action and for the rebuild, which is the one action whose correctness cannot be established from contracts alone.

## Out of scope

- Revit 2020 in the same change as the port (`adr/0006`); it follows as a required, dated step.
- Re-translating upstream documentation (`adr/0007`).
- Reimplementing the upstream policy layer, updater, store build or batch supervisor. They arrive with the base.
- Opening pull requests against upstream. Upstream is the base, not the destination.
- Changing upstream's own defaults beyond the fork's installer and shipped policy.

## Further notes

The working tree already contains identity isolation, a tool-manifest fix, an intake gate and a ledger. All of it is uncommitted and predates this base. The identity part must be redone against the new installer, which upstream extended with a policy file.

Upstream's own test baseline on a clean checkout is 1120 passed and 7 failed; the seven failures need the .NET 10 runtime, which this machine does not have. That number is the floor, not a regression signal.

The cost of this direction is permanent divergence: upstream fixes do not reach the fork layer, and the fork layer does not reach upstream. The rhythm in `adr/0001` is the only mitigation, and it is a discipline, not a guarantee.
