## P0 — «владелец не мясной прокси»: обязательная цель и критерии приёмки (07.11.2026)

**User story:** «Я пишу задачу человеческим языком в ChatGPT и принимаю принципиальные решения. Я НЕ пересылаю вручную готовый промпт из ChatGPT в ZCode/Z AI, ответ ZCode в ChatGPT, логи CI, статусы PR, handoff, команду сжатия /compact или следующий кусок контекста. Если такой перенос обязателен для штатного рабочего цикла, оркестрация ещё НЕ готова».

**Предпочтительный поток без ручной эстафеты:** owner → ChatGPT (формализовать критерии) → GitHub Issue/task contract → существующий agent runner (OpenCode либо поддерживаемый ZCode CLI) → GitHub PR/CI/структурированный checkpoint → ChatGPT читает результат из GitHub → owner принимает только требуемое GO/NO-GO. Нельзя подразумевать автономную подписку UI ChatGPT на GitHub-события: инициирование чтения результата через новую реплику владельца допустимо, *пересылка текста не допустима*. Полностью push-уведомления — отдельный этап с проверкой инструментов.

**Что нужно устранить (в проверяемом MVP):**
1. **Copy-paste task**: задание рождается как Issue/task contract и считывается исполнителем по ID/URL, не перепечатывается оператором в окно агента.
2. **Copy-paste result**: агент оставляет в PR/Issue machine-readable checkpoint: task_id, exact repo/base/head SHA, changes, тесты PASS/FAIL/BLOCKED/NOT_TESTED, ссылки на CI/artifacts, blocker и next owner decision. ChatGPT читает этот источник самостоятельно.
3. **Copy-paste logs/CI**: агент/ревью берут нужные точечные логи и CI через GitHub; ссылки/SHA вместо вставки гигабайт логов.
4. **Ручное сжатие контекста**: использовать встроенное auto-compaction ZCode, если оно срабатывает и подтверждено, либо session handoff с новой сессией; никогда не считать естественно-языковое «сделай /compact» выполнением UI slash-команды. В критическом незавершённом процессе сохранять корректную транзакцию, а не прерывать её ради сжатия.
5. **Повторная постановка**: перед продолжением агент считывает сохранённое состояние из GitHub и проверяет SHA/тесты, не просит пользователя пересказывать предыдущую переписку.
6. **Оператор только на границе полномочий**: подтверждает merge, stable, release, изменения инфраструктуры, железа или доп. расходов. Один owner GO не даёт автоматически следующего. При блокере — краткая развилка, не запрос «принеси мне отчёт от другого агента».

**Оценка результата:** ручные переносы текста/отчётов между ИИ **0 на демонстрационном task**; реальных сознательных owner GO — сколько требуется, учитывать отдельно; сценарии stale SHA, повторный webhook, offline ZCode, отмена, limit exceeded и ошибочная авторизация должны завершаться безопасным STOP. Зафиксировать before/after в количестве ручных пересылок, токенах (или NOT_AVAILABLE), стоимости (включая различие Z.AI Coding Plan vs API) и ресурсах/времени.

**Reuse first — запрет создавать лишний продукт:** прежде чем писать bridge, исследовать и испытать (a) OpenCode c Z.AI Coding Plan и GitHub integration, (b) имеющийся ZCode headless CLI с --prompt/--json в заведомо безопасном read-only режиме, (c) существующие GitHub Actions/webhook, Hooks, auto-compaction; Symphony/Gas Town рассматривать как альтернативы, а не зависимости. Собственный оркестратор разрабатывать **только при доказанном незакрытом gap**. Не переносить эту логику в Keenetic/Entware или KAS Web, не увеличивать обязательные зависимости core.

**Статус:** цель и acceptance записаны; не заявлять, что уже реализовано или что GitHub Actions может пользоваться Coding Plan без дополнительного платежа: это требует практического подтверждения.

## UPDATE 07.11.2026 — REUSE FIRST, отменить предположение о разработке с нуля

После проверки существующих open-source решений **сначала интегрировать готовое, а не писать собственный оркестратор**. До положительного proof/сравнения альтернатив нельзя начинать кастомный bridge. Первичный текст ниже — исходный scope, этот update имеет приоритет при противоречиях.

**Обнаруженные готовые варианты:**
1. **OpenCode** — официальный GitHub агент (issue_comment `/opencode`, `/oc`; PR workflow, runs в Actions), официальный **Z.AI Coding Plan** provider; можно также подключить ChatGPT Plus в OpenCode, но это отдельные лимиты модели и не подразумевает встроенное выполнение задач из UI ChatGPT. Источники: https://opencode.ai/docs/github/ , https://docs.opencode.ai/docs/providers/ .
2. **ZCode CLI — уже есть headless интерфейс**: исходники содержат `zcode --prompt`, `--output-format`/`--json`, `--mode`, `app-server`/`agent-server`, `--cwd`, resume/continue; репозиторий https://github.com/zai-org/ZCode/blob/main/apps/zcode-cli/packages/cli/src/run.ts ; публичный опыт headless Coding Plan: https://github.com/zai-org/feedback/issues/907 . Важно: **headless --prompt по умолчанию задаёт режим yolo (DEFAULT_HEADLESS_PROMPT_MODE)**! Никаких автоматических запусков без проверки и явного безопасного режима `--mode plan` в read-only пилоте; рабочие permissions надо аудировать. Подтвердить доступность двоичного `zcode` в фактической Windows-инсталляции, работу логина Z.ai Coding Plan, формат результатов и границы прав. Отдельный bare `app-server` может иметь ограничения с account registry по #907 — сначала `--prompt`.
3. **Symphony** — готовый orchestrator spec и reference (Codex App Server + Linear) https://github.com/openai/symphony ; оценить reuse лишь если нужен отдельный долгоживущий supervisor, не переписывать с нуля.
4. **Gas Town** — мультиагентная память и handoff, но, вероятно, чрезмерно для 1 ZCode исполнителя: https://github.com/gastownhall/gastown .

**Решение по приоритету POC**: (1) подтвердить `zcode --help`, `zcode --prompt "..." --mode plan --json` на фактической версии Windows в отдельном тестовом каталоге, **без мутаций KAS и без секрета в stdout**; (2) проверить OpenCode локально с уже оплачиваемым Z.AI Coding Plan; (3) только если облачная GitHub Actions-интеграция действительно может работать в рамках уже оплаченной квоты и разрешённых секретов — тестировать OpenCode GitHub интеграцию; (4) если эти варианты не покрывают handoff, добавить минимальный glue через GitHub, без создания альтернативного agent runtime. На каждую стадию отдельный owner GO, если она включает установку, секреты, платный API, workflow или запись.

**Экономический критерий**: не требовать новой подписки, не подменять Coding Plan общим платным Z.ai API, замерять списание фактической квоты; сохранять CI/PR safety gates. **Открытый вопрос**: есть ли техническая и договорная возможность использовать Coding Plan API-ключ из GitHub-hosted runner; до проверки НЕ считать это фактом.

**Пересмотр DoD**: для успеха достаточно конфигурации/adaptation существующих решений, без написания собственных планировщика, чат-системы, memory engine или новой платформы. Если готовый инструмент решает 80–100% проблемы без неприемлемых расходов, зафиксировать решение и НЕ строить bridge.

## Решение владельца — 07.11.2026
**GO на поэтапный proof/integration готовой Agent Orchestration для KAS; custom implementation только после доказанного gap**, чтобы убрать владельца из роли ручного транспорта ChatGPT ↔ Z AI/ZCode. Начать с минимального проверяемого рабочего вертикального среза; не строить автономную «фабрику агентов» без доказанной пользы.

**Связано:** #420 (экономия токенов), [docs/agent-token-efficiency.md](https://github.com/saymer-alt/keenetic-auto-setup/blob/main/docs/agent-token-efficiency.md), [AGENTS.md](https://github.com/saymer-alt/keenetic-auto-setup/blob/main/AGENTS.md). Существующие Proof Before Build, STOP/GO, safety gates и экономия токенов действуют без изменений.

### Проблема / измеримый результат
Сегодня владелец вручную:
1. Пишет задачу ChatGPT и переносит сформированный контракт в ZCode.
2. Копирует ответ/логи ZCode обратно в ChatGPT.
3. Инициирует /compact или новую сессию; синхронизирует handoff и статус GitHub.
Цель: на одном реальном небольшом KAS Issue добиться цикла **постановка → выполнение → доказательство → ревью**, где не требуется копировать текст задания или результат между чатами. Владелец участвует только в первоначальной постановке, необходимых разрешениях и конечном решении. При невозможности полностью автоматического запуска — честно показать, что остаётся ручным.

### Концепция
```
Owner → ChatGPT (план / review / owner decision)
                ↕ GitHub Issue / PR / Actions / SHA — source of truth
        Local KAS agent bridge (thin, opt-in)
                ↕ supported ZCode hooks / scheduled tasks / proven CLI if available
              Z AI / ZCode (triage, patch, tests)
```
**Не допускать циклического общения двух LLM без человека / предохранителей**. Не создавать публичный endpoint или отдельный постоянно работающий сервер на этапе MVP. Одна активная ограниченная задача, остальные не исполняются автоматически.

### Факты платформы, требующие проверки перед разработкой
- Официальный ZCode Hooks API поддерживает `SessionStart`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop` и др., JSON stdin/stdout, ограничения по перезапускам Stop. **Project-level hooks в .zcode конфиге не выполняются**; варианты — установленные plugin hooks либо user-level config с явным opt-in. Источник: https://zcode.z.ai/en/docs/hooks (проверено 07.11.2026).
- ZCode Automations выполняются **локально, только пока ПК включён и приложение открыто**; их наличие не доказывает API/headless запуск из ChatGPT/GitHub Actions. Источник: https://zcode.z.ai/en/docs/automations (07.11.2026).
- ZCode Subagents могут работать в отдельных контекстах, но **не являются доказательством удалённого программного управления главной сессией**. Источник: https://zcode.z.ai/en/docs/subagents (07.11.2026).
- У ZCode / Coding Plan и Z.ai API **не подтверждено одинаковое тарифицирование/списание квот**. Никаких автоматических платных API-запросов до проверки и отдельного GO.
- ChatGPT в текущем рабочем процессе умеет читать/изменять GitHub через подключённый инструмент, **но это не постоянный daemon / двусторонняя подписка на события**. Автозапуск исполнителя исследовать отдельно.

### Acceptance / Definition of Done
1. Демонстрация на одном реальном небольшом, не production KAS Issue: ChatGPT создаёт task contract; ZCode получает его по проверенному механизму; агент прикладывает SHA/tests/evidence в GitHub; ChatGPT читает результат из GitHub без пересылки пользователем текста/логов.

4. Короткая документация установки, восстановления и полного отключения (opt-in; default off), журнал событий без секретов, тесты. Отдельный Draft PR, никаких автоматических merges.
