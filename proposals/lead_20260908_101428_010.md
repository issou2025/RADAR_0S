# Application Dock redesign — left-edge auto-hide sidebar

## Title

As a Fredo desktop user, I can see every open app in a left-edge icon sidebar that appears only when I move the mouse to the left edge, so that I always know what is open and can switch/restore/close apps without a dock permanently covering my windows.

## Problem / Why now

The current "open applications" surface is a **bottom-docked tray** (`role="region"`, `aria-label="Open applications"`) that appears **only when a window is minimized/floated** and then permanently occupies the bottom of the desktop until dismissed. Consequences:

- With all windows in normal float/maximize state there is **no visible dock at all** — a user cannot see at a glance which apps are open or switch between them without first minimizing something.
- When it does appear it is a large bottom tray that **covers desktop content and must be manually dismissed**, which fights the maximized-window workflow (feature windows open maximized by default).
- The tray duplicates Restore/Focus/Close actions that belong in a compact, always-reachable switcher.

The desktop is the primary surface of the product; the open-apps affordance is a core desktop-chrome element, so its placement/behavior should follow the established auto-hide convention (hidden at rest, edge-peek reveal) rather than a minimize-only interruptive tray.

**Override note (important for downstream agents):** Issue #2821 asked for an app drawer that appears on minimize (bottom-docked tray with Restore/Focus/Close — covered in the `window-manager` durable suite F-16..F-19). This spec **intentionally REPLACES that drawer**: the bottom minimize-triggered tray is REMOVED and superseded by a single left-edge auto-hide icon sidebar that lists every open app. Do NOT re-follow the #2821 minimize-triggered-bottom-tray acceptance criterion; it is superseded here. The window lifecycle (minimize/restore/focus) semantics themselves are unchanged.

## Intended users

Fredo desktop users — the person running feature windows (Mission Monitor, Query Viewer, Run CLI, Stepper Probe, …) who minimizes/floats/stack windows and needs a persistent, non-occluding way to see what is open and to switch, restore, or close apps.

## Proposed behavior / Scope

On the desktop, replace the bottom-docked "Open applications" tray with a **left-edge auto-hide icon sidebar** that is the single open-apps surface:

- A slim vertical strip of **icons** docks at the **left edge** of the desktop.
- **At rest it is fully hidden** — it covers no window and no content; a maximized window stays full-bleed edge-to-edge.
- Moving the pointer to the **left screen edge** reveals the sidebar; it stays visible while the pointer is near the edge / over the sidebar and **slides away when the pointer leaves** (transient edge peek — no pinning).
- It lists **every open app** (normal, floating, minimized) as an **icon only**; **hovering an icon reveals that app's name**.
- **Clicking an icon focuses that app's window**, restoring it if minimized.
- A **hover-reachable close affordance** remains so an app can be closed from the sidebar (parity with the removed drawer's Restore/Focus/Close actions: click = restore/focus, hover action = close).

Scope boundary: desktop chrome / open-apps surface in `apps/ui/src/features/home/components/` and any shared window-system read surface it consumes (reads the open-window list; does NOT change the window engine).

## Success metrics

- A user can see every open app at a glance by peeking the left edge — no need to minimize a window first.
- The dock covers nothing at rest: maximized windows keep the full workspace (edge-to-edge), so the "drawer occupies the bottom" complaint is gone.
- Click-to-switch / restore and hover-to-close remain fully reachable, so the removed bottom tray's capabilities are preserved (no action regression).

These are qualitative desktop-UX outcomes; no quantitative usage metric exists for chrome behavior. Measurable proxy: the bottom minimize-triggered tray is gone (zero references), one left-edge auto-hide dock exists, and every open app (including minimized) appears in it.

## Acceptance criteria

- [ ] **1. Replace the bottom drawer with the left-edge dock:** with ≥1 window open (including at least one minimized), the desktop shows NO bottom-docked "Open applications" tray; instead a vertical icon sidebar at the left edge lists every open app (normal + floating + minimized). When no window is open the sidebar is hidden at rest.
- [ ] **2. Auto-hide edge peek (never covers content at rest):** the sidebar is fully hidden and non-interactive at rest — a maximized window is full-bleed (edge-to-edge, not indented) and desktop/window content at the left edge is reachable by the pointer. Moving the pointer to the left edge reveals the sidebar; moving the pointer away (off the sidebar and off the edge zone) hides it again.
- [ ] **3. Icons + name on hover:** each open app is represented by its icon only; hovering an icon shows the app's name (label/tooltip); the name clears when the pointer leaves the icon.
- [ ] **4. Click = focus + restore; hover = close:** clicking an icon of a minimized/backgrounded app brings that window to front and restores it (topmost, saved geometry); clicking the icon of the already-top window is a no-op (no duplicate, no flicker). A close action reachable on hover closes only that app — window removed, its icon drops from the sidebar, other entries remain; closing the last app leaves a clean desktop and a consistent empty-peek state.
- [ ] **5. Edge/negative + hygiene:** (a) many open apps (≥6) — the sidebar scrolls/clips gracefully with no dead input and no entry lost; (b) rapid open/close/minimize interleaves leave no stale/missing entries and no duplicate frames; (c) the sidebar is token-native (theme CSS vars, `tint()` hover/name surfaces, no hardcoded hex/rgba, Chakra v3) and readable in light + dark presets; (d) while hidden it never swallows pointer input meant for desktop/window content.
- [ ] **6. No regression:** window lifecycle (open/close/minimize/restore/focus/maximize) and z-order behave exactly as before (own-kernel #2807 semantics); the launcher/search (`| APPS`, Ctrl+Space) and desktop-chrome (clock/LED) surfaces are unaffected; webview console clean (no `Error:`/`Uncaught`/`Maximum update depth exceeded`); `pnpm --filter @fredo/ui build` green (+ Rust `cargo check` zero warnings if the Rust side is touched).
