# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: static landing page at the web root, Flutter web app under /app**

*Project description:*
## Problem Statement

MYOS links from the owner's TikTok and Instagram bios open straight onto a login screen. A curious visitor — a would-be Lifter, a Coach, or someone who just saw a post — gets no idea what MYOS is, cannot tell that Android and iPhone apps are coming, and has no way to reach the team. Bio traffic arrives on phones, mostly inside TikTok/Instagram in-app browsers, where the Flutter web bundle takes seconds to paint and Google sign-in is blocked by Google (`disallowed_useragent`), so the first impression is a slow loader and, sometimes, a broken button.

## Solution

A small, fast, static landing page served at the site root, before the Flutter web app. It says what MYOS is for Players and Coaches, shows Google Play and App Store badges marked "Coming soon", tells the story behind the name, and lists contact details in the footer. The navbar has the MYOS logo, an AR/EN toggle and **Log in**. The hero offers **Start free**, which opens registration in the web app.

The Flutter web app moves under `/app/`. Every URL that works today keeps working: old paths redirect to `/app/<same path>` with the query string kept, and no server or email link changes. Signed-in visitors who land on `/` go straight into the app. The page matches the app's theme exactly and weighs under ~300 KB on first load.

Web only: the Android app keeps going straight to login when signed out.

## Implementation Decisions

**Architecture (new ADR 086: "Static landing page at the web root; Flutter web app under /app")**
- The landing page is a separate static site (HTML, CSS, a small inline JS), kept in its own top-level folder in the repo. No framework, no bundler, no outside network sources; it must satisfy the existing CSP.
- The Flutter web app is built with base href `/app/` and served under `/app/`. The Android app is unchanged.
- The web deploy script assembles one output: landing page at the root, Flutter build under `/app/`, a single Cloudflare Pages redirects file. One Pages deploy, same project, same preview flag.
- Same origin is required (the landing page reads the app's stored theme, language and sign-in presence). Issue #132 is amended: the owned domain serves the landing page at `<domain>/` and the app at `<domain>/app`, with no `app.` subdomain.

**Links are never changed**
- Server-sent links (password reset, etc.), the forced-update flow and everything else keep their current URLs. Cloudflare redirect rules send each existing app path (`/login`, `/register`, `/google-signup`, `/forgot-password`, `/reset-password`, `/update-required`, `/splash`, `/home`, `/onboarding`, `/player-setup`, `/coach/*`, and every other route in the app router) to `/app/<same path>`, keeping the query string. The SPA fallback under `/app/*` serves the Flutter index. Unknown root paths fall to the landing page.
- Google sign-in authorized origins are unchanged (same origin, different path).

**Signed-in skip, theme and language handoff**
- On load, the landing page checks whether the app's stored sign-in token entry is present (the app's secure-storage token key on web). If it is, it immediately replaces the location with `/app/`. Only presence is checked; the token is never read or decoded.
- Theme: the page uses the app's color tokens and fonts exactly (MYOS light and dark palettes; Inter, Playfair Display, IBM Plex Sans Arabic). Mode follows the app's stored theme choice (`settings.theme_mode`: light/dark/system) when present, otherwise the system setting. The landing page has no theme toggle.
- Language: default is the stored logged-out display-language choice (the app's `mayos.display_language` key) if present, else the browser language (`ar*` → Arabic, `en*` → English), else Arabic. The navbar toggle writes the same key in the format the app already reads, so the app opens in the same language. Arabic sets `lang="ar" dir="rtl"` and the layout mirrors through logical CSS properties.
- All copy for both languages lives in the page and swaps without a reload.

**Page structure**
- Navbar: MYOS logo (links to `/`), AR/EN toggle, **Log in** → `/app/login`.
- Hero: the same gym wallpaper, white lockup and tagline as the splash, so the HTML loader opens into the page. Primary button **Start free** → `/app/register`. Google Play and App Store badges using the official artwork for the current language, each with a "Coming soon" mark. While "coming soon" they render as non-navigating elements with `aria-disabled` and announce "coming soon". A single config value per store switches each to a real link.
- For Lifters: 3–4 short lines with icons.
- For Coaches: 3–4 short lines with icons, plus **Become a MYOS coach** (a `mailto:` to the business email with a pre-filled subject) and an Instagram link.
- The name story.
- Footer: business email, Instagram, TikTok, privacy policy (the API's existing `/privacy` page), ©.
- Contact values are held in one place in the page: email `ahmedtamerhejazi@gmail.com`, Instagram `@ahmedtvmer`, TikTok `@ahmedforges`.

**Performance budget**
- Under ~300 KB transferred on first load, including the hero image (compressed WebP with a JPEG fallback only if needed) and fonts (self-hosted, subset, `font-display: swap`, only the weights used). Inline critical CSS. No JS needed to paint.

**Analytics**
- PostHog, using the same project key as the web build, is loaded after first paint and captures only these events: `landing_start_free`, `landing_login`, `landing_coach_contact`, `landing_store_badge` (property `store: google_play | app_store`). No session recording, no autocapture. If the key is absent, the page works without analytics.

**In-app browser hint (Flutter login screen)**
- On web, when the user agent is a known in-app browser (TikTok, Instagram, Facebook), the login screen shows a short hint near "Continue with Google": "To sign in with Google, open this page in your browser." The Arabic copy is in standard register. Username/password login is unaffected.

**Design direction** (from the frontend-design pass)
- Spend the boldness in one place: the name story. It's a typographic moment set in Playfair Display (Arabic in IBM Plex Sans Arabic), with the Greek word μῦς as the large visual element and the mouse/muscle meaning beneath it.
- Everything else stays quiet: start-aligned text (left in English, right in Arabic), generous whitespace, the app's accent blue used only on the primary action and links.
- Lifters and Coaches sit as two side-by-side columns on wide screens and stack on phones. Avoid identical rounded "SaaS cards", numbered markers, ALL-CAPS eyebrow labels, and "→" on buttons.
- Motion: one orchestrated page-load moment only. The lockup and tagline settle in from the splash loader state, then the hero actions fade in. On top of that, simple feedback on taps and hover. No per-section scroll fade-ins. Everything is turned off under `prefers-reduced-motion`.
- Mobile first: the target is a phone in an in-app browser. Use a 16 px side gutter, no horizontal scroll, and tap targets of at least 44 px.

## Testing Decisions

Good tests check behavior someone can observe (what URL a path ends up at, what the visitor can click, what the page weighs), not how the markup or scripts are structured.

- **Seam 1: assembled deploy output** (pytest, alongside the existing suite in `tests/`). Run the assembly step into a temp directory with a stub Flutter build. Assert:
  - the landing page is at the root;
  - the Flutter build is under `/app/`, with base href `/app/`;
  - the redirects file sends every route the app router declares (read from the router so new routes can't be missed) to `/app/<same path>` with the query string kept, and has the `/app/*` SPA fallback.

  After deploy, a curl check against the preview deploy confirms that old `/reset-password?token=x`, `/login` and `/coach/roster` URLs land on `/app/...` and the root serves the landing page.
- **Seam 2: landing page as a black box** (pytest over the built folder). Assert:
  - total first-load weight is under the budget, with no outside origins;
  - the link targets: Log in → `/app/login`, Start free → `/app/register`, the coach `mailto:` with subject, Instagram, TikTok, privacy;
  - both languages have every copy slot filled;
  - the four event names are present, and the badges don't navigate while "coming soon".

  The language toggle, RTL mirroring, theme pickup, signed-in skip and reduced motion are verified by hand in a browser on the preview deploy, with screenshots in the PR (no JS test runner is added).
- **Seam 3: Flutter login screen** (widget test, prior art: `auth_flow_test`). The in-app-browser hint appears for TikTok, Instagram and Facebook user agents on web, and not for normal browsers or Android.
- The existing Flutter and backend suites must stay green. No router route paths change.

## Out of Scope

- A waitlist or "notify me" email capture.
- A coach application form or self-serve Coach invites (spec #153 stays unqueued).
- Screenshots or videos of the app on the page.
- A theme toggle on the landing page.
- Any landing page inside the Android app, and any store or web links in the Android app (ADR 023).
- Buying or wiring the owned domain (#132 does that; this spec only amends its layout to `<domain>/app`).
- Changing any server email links or app routes.
- SEO work beyond a correct title, meta description, Open Graph tags and `lang`/`dir`.

## Further Notes

- Name etymology was checked: Greek μῦς (gen. μυός) means both mouse and muscle. Latin *musculus*, "little mouse", is the source of English *muscle*.
- The iOS app does not exist yet, and Android is in closed testing, so both badges really are "coming soon".
- The business email and handles are public by design. Keep them in one place so they can be swapped (e.g. for a domain email after #132).
- Domain glossary: Player (لاعب) and Coach (مدرب). The marketing copy says "lifters" for the audience, which matches the "Lifter" plan name.
