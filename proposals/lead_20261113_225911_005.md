**Windows desktop app: local Azure CLI integration and private, local-first simulation**

*Project description:*
## Goal

Implement a Windows desktop application with functionality comparable to the existing web application, integrating with the user's locally authenticated Azure CLI. Keep topology data, captured Azure configuration, routing calculations and saved scenarios on the user's machine rather than uploading them to a simulator-hosted service.

This issue tracks future implementation; it does not authorize implementation, deployment or changes to Azure resources now.

## Motivation

- Reuse local `az login` authentication, tenant and subscription access for convenient Azure discovery/import.
- Allow organizations to inspect sensitive networking configurations without sending those configurations to an external simulator backend.
- Support offline modeling, troubleshooting and replay of previously captured configurations.

## Functional scope

- Preserve the existing VWAN, Hub & Spoke and Full Hybrid experiences: visual topology editing, route maps, effective/learned/advertised routes, routing preferences, failure scenarios, path exploration and asymmetric-routing detection.
- Reuse the existing TypeScript routing engines, validation and UI wherever practical; avoid a separate implementation of routing semantics.
- Preserve native topology JSON import/export and compatibility with the web application, including archived regression scenarios from #98.
- Integrate local Azure CLI discovery/collection, reusing the existing collector/capture formats where suitable. Import collected data through the same validation/review flow.
- Show the active Azure cloud, tenant and subscription and require deliberate scope selection before collection. Support expired sessions, MFA/Conditional Access failures, insufficient permissions and partial captures with actionable errors.
- Keep Azure collection read-only. Missing CLI/authentication must not silently trigger installation, login, permission elevation or resource changes.

## Privacy and trust boundary

The intended guarantee is **no automatic upload of topology/configuration data or credentials to a simulator-operated or other third-party service**. This is not a claim that Azure integration never uses the network: explicit discovery necessarily communicates with the selected Azure identity and management endpoints under the organization's policies.

- Routing and analysis run locally; do not require the hosted simulator/API.
- Use local Azure CLI credentials through supported mechanisms; never upload credentials, persist access tokens in topology files, or include them in logs/crash reports.
- Package required UI/runtime assets locally. Modeling and file import/export must work without CDN dependencies or network access.
- Disable telemetry, feedback, cloud synchronization, crash uploads and topology sharing by default. Any later outbound integration needs explicit, informed opt-in and a documented destination/data inventory.
- Save topology/capture files only to deliberate local destinations; document filesystem permissions, retention, sensitive diagnostics and any user-selected synchronized/network folders.
- Constrain the desktop-to-process bridge to supported read-only operations, validate arguments and avoid shell-command construction from topology/import data.

## Implementation decisions to resolve

- Evaluate a Windows desktop host (for example Tauri, Electron or a native/WebView2 host) against UI reuse, secure local-process integration, enterprise deployment, offline support, runtime dependencies and maintenance.
- Define supported Windows/Azure CLI versions, executable discovery, packaging/signing, installation/uninstallation and controlled update behavior.
- Document which web features are available unchanged, adapted or intentionally unavailable; no implied cloud-resource deployment capability.
