**What this is**

The Revit plugin's next feature set, settled in a grilling session on 2026-09-17 against a Claude research report on add-in features and against the tree as it stands. This issue is the spec: the rules the work runs under, the facts it rests on, the items in build order, what waits on the platform, and what is deferred. Each Phase A item is a child issue linked below; each deferred item is its own issue so it can be picked up later.

**Why now**

The first users work in Revit. The roadmap's sentence saying the Revit plugin takes no headline features in this window was stale and is retired in PR #146, which also adds the glossary entries this plan uses: *site model*, *context building*, *foliage type*.

**Rules every item runs under**

- **The thin-client line, stated for geometry.** Realising published geometry in a Revit primitive is application: placing a family at a published point, copying a published extrusion, cutting a published polygon as a subdivision. Computing new geometry or classes from published data is derivation and is refused at review: buffering a centreline by a width, tiling a drape, classifying land cover into a material, bucketing trees by height, thinning a set. Everything on the refused side is a platform request (Phase B) and the add-in waits for the field.
- **Two phases.** Phase A consumes only what MPB 1.0.x publishes today. Phase B is the list of fields the platform must publish, each written with the add-in behaviour that consumes it; those requests are filed on the platform's own tracker and described here, never cited.
- **The persona for tie-breaks** is the visualiser at an architecture practice building site context for a concept model, presenting in a real-time renderer.
- **Renderer keyword names are host-owned.** The table from a published `subtype` to a material-name keyword lives in `MantlePlace.Revit.Core`, tested headlessly. It is Revit rendering knowledge, like the smooth-shading anchor, not a landscape binding.
- **Renderer-neutral output.** The add-in writes real Revit elements, sized as published, with names a renderer can recognise, and never writes a renderer's own storage: no Twinmotion substitution entity, no Enscape asset link. Linking a family to a renderer's asset is the curator's step. Decided when #174 was closed; whether a renderer's substitution keeps each tree's size is #183.
- **Attribution is pass-through.** The add-in writes the manifest's attribution text verbatim and carries only the attributes the manifest ships. It never makes a licensing decision.
- **One build, compiled against Revit 2025's API.** No 2026-only member (typed subdivisions, negative subdivide offset, cut-void stability) is used, by reflection or otherwise. Features degrade to 2025 behaviour on every host.
- **Stamp discipline extends to every element kind.** Each element the import creates carries `Mantle Place <Kind> {stem}/{token}` in its Comments parameter, and the reuse / refuse / create table of ADR 0004 applies per kind. Update-in-place is Unreal's remedy and does not cross over.
- **Scalability.** The add-in imports everything the bundle publishes. Work is chunked per transaction with progress and cancel. Costs are measured and tabled per element kind on the largest bundle available. A bundle that breaks Revit is a bug to fix, not a size to refuse. Bundles range from 1 km² to 64 km² today and will go beyond.

**Facts the plan rests on** (measured on `main` at 7b568ed and on the bundles in the local cache)

- The import is synchronous on Revit's main thread, one transaction per step, no progress, no cancel. `SlowStepNotice` recorded that as a decision, with the drape retype at 409 s and the site boundaries at 610 s on an 80,372-point toposolid. A 20,164-point bundle imports in about a minute. The cost scales with terrain size and sits inside single commits.
- Trees are DirectShapes on `OST_Planting` with no parameters and no stamp. Roads are unmaterialed DirectShape polylines with no stamp; width and class are parsed and unused.
- Buildings are a linked IFC only. That IFC carries one `IfcBuildingElementProxy` with its own `IfcExtrudedAreaSolid` per building, plus one `IfcGeographicElement` for context terrain, and no property sets. The building glb is one merged mesh with one node, so per-building elements cannot come from it without splitting.
- `vector.layers` ships `building` (footprints, `height` mostly null), `road`, `road_splines` (width, class, name), `water` (stream centrelines, `LineString`), `land_use` where the area has any, and `land_cover` (`subtype`: forest and its like). All GeoJSON in lon/lat, projected by the reader under `HPS-45`. The published schema pins no layer names.
- `attribution.sources[]` carries text, license and URL per source. `licensing.vector` is an ODbL derivative database; everything else is a produced work.
- `hosts.revit.georeference.origin` carries lon and lat. No `SiteLocation`, view, filter, Project Information, or ExtensibleStorage write exists today.
- The plugin has built an 80,372-point toposolid through `Toposolid.Create`, so the import-side point threshold does not gate the API path. The platform already decimates the Revit DXF.
- The drape is 4767 × 4733 px at 0.3 m on the 2 km² bundle. Nobody has yet observed it soft in a render.

**Definition of done, per item**

Headless tests for every Core decision; one real import in Revit 2027 from the `main` local-install slot, reported with the stamp the deploy script printed; the three-version check at release only.

**Phase B: what the platform must publish** (filed on the platform's tracker, described here)

- Pinned vector layer names, in the schema or the spec, so a reader keying on `land_use` or `land_cover` is reading a contract and not a convention.
- Water and road polygons in the vector layer, so the add-in can cut them as subdivisions with a "Water" material and an asphalt material. Streams as centrelines render nothing useful.
- A `foliage_type` column per tree point, closed vocabulary, so shrubs get their own family.
- A time zone in `hosts.revit.georeference`, so `SiteLocation` is complete without deriving one from longitude.
