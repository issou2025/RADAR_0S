# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[proposal] - flutter create templates ship outdated dependency versions and require manual built-in Kotlin migration**

*Project description:*
### Use case

When creating new projects with the latest stable Flutter (`flutter create`), the generated templates are already out of date, so every new project needs manual fixes right after creation:

1. The project still needs the manual "Migrate to built-in Kotlin" steps (https://docs.flutter.dev/release/breaking-changes/migrate-to-built-in-kotlin/for-app-developers), even though it was generated seconds ago by the Flutter tool itself.
2. Default dependency versions in the templates are behind pub.dev:
   - App: `cupertino_icons: ^1.0.8` (latest: `^2.0.0`)
   - Plugin: `plugin_platform_interface: ^2.0.8` (latest: `^2.1.8`)
   - Plugin (web): `web: ^1.0.0` (latest: `^1.1.1`)
3. `flutter create --template=package` generates no `example/` app, unlike plugins.

Is your feature request related to a problem?

Yes. Every new app/plugin/package starts in an outdated state. Developers have to (a) manually apply the built-in Kotlin migration to a brand-new project, (b) manually bump dependency constraints, and (c) manually create an example app for packages. This is repetitive, easy to forget, and gives a poor first impression of the "latest" template. It also makes pub.dev scoring worse for packages that ship without an example.

Question: why doesn't `flutter create` generate the built-in Kotlin configuration by default? Since the template is fully controlled by the Flutter tool, I would expect a fresh project (app and plugin) to already be in the migrated state. If there is a technical reason (AGP/Gradle minimum versions, compatibility with older plugins, etc.), it would be helpful to document it in the migration guide.

Requested changes:
- Generate the built-in Kotlin setup by default in app and plugin templates.
- Update template dependency defaults to the latest versions (and ideally add a CI check so they don't drift behind in the future).
- Generate a minimal `example/` for `--template=package` (or add a flag such as `--with-example`).


Describe the alternative solutions you’ve considered:

- Manually applying the built-in Kotlin migration after every `flutter create`.
- Running `flutter pub upgrade --major-versions` after creating a project, which fixes dependency constraints but must be repeated for every new project.
- Manually running `flutter create example` inside the package folder to add an example app.
- I'm not aware of any package on pub.dev that solves this, since it is about the defaults of the `flutter create` command itself.

### Proposal

Update the `flutter create` templates so that a freshly generated project is already up to date and needs no manual fixes:

1. App and plugin templates generate the built-in Kotlin configuration by default (per https://docs.flutter.dev/release/breaking-changes/migrate-to-built-in-kotlin/for-app-developers), so no migration is needed on a newly created project.

2. Template dependency defaults match the latest published versions:
   - `cupertino_icons: ^2.0.0` (currently generates `^1.0.8`)
   - `plugin_platform_interface: ^2.1.8` (currently generates `^2.0.8`)
   - `web: ^1.1.1` (currently generates `^1.0.0`)
   Ideally a CI check or test fails when a template's constraint falls behind the latest version on pub.dev.

3. `flutter create --template=package` generates a minimal `example/` app, as plugins already do. If changing the default is undesirable, add an opt-in flag such as `--with-example`.

Example of the expected result after `flutter create --template=plugin my_plugin`:

    dependencies:
      flutter:
        sdk: flutter
      plugin_platform_interface: ^2.1.8
      web: ^1.1.1

and an Android project that is already on built-in Kotlin, with no manual migration steps required.

This must be provided by Flutter directly. The defaults are part of the templates inside the `flutter` tool (`flutter create`), so a pub.dev package cannot change what the command generates.
