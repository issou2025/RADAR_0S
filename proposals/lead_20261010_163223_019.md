# Project Proposal — Permit Drawings

## Project Understanding
You need assistance with: 
**feat(copy)!: carry comments, skip items unchanged since the last copy, and copy by query**

*Project description:*
## What

Add three general capabilities to the plan store's copy, plus the per-item **change token** they and the next node's cache rest on. Everything here is general: it holds for every source plugin the store ships, not for one caller.

Where it lands: the plugin API crate (`crates/onetaskgraph-plugin-api`: `Task`, `Comment`, `Capabilities`), the engine's copy (`crates/onetaskgraph-core/src/engine/copy.rs`), the three plugins (`onetaskgraph-github-projects`, `onetaskgraph-linear`, `onetaskgraph-local-md`), the CLI (`crates/onetaskgraph/src/cli.rs`, `main.rs`, `render.rs`), `onetaskgraph schema`, both SDKs, and the docs (`README.md`, `docs/plugin-protocol.md`, `docs/local-md.md`, `docs/metadata.md`, `AGENTS.md`'s journey inventory). The loopback GitHub and Linear fixtures in `crates/onetaskgraph-e2e-support` must model what the token keys on: they answer issue `updatedAt: null` today.

### The contract this node lands (other nodes restate it from here)

It is declared once, in the plugin API crate and the CLI's report types, and published through `onetaskgraph schema`. The generated Python SDK models, the TypeScript SDK and `docs/plugin-protocol.md` derive from it. Keep the existing drift gates (`surface.rs` and the SDK generation checks) reconciling each copy, and add a gate wherever a new member has none.

1. **Change token.** `Task` gains an optional member `version` (string). The JSON of `task list`, `task show`, `task show-many` and every list, search and `--commented-since` result carries it.
   - Two equal versions of one item from one source mean nothing has changed in its title, body, status, priority, labels, project fields, metadata, edges, or comments. For comments that covers additions, edits and deletions.
   - A source that cannot promise all of that for an item leaves `version` absent.
   - The value is opaque to callers. The store itself must be able to tell, for two versions of one item from one source, whether they are equal, which one is later, or that they cannot be compared. The next node's cache depends on that ordering.
   - **GitHub Projects** builds the token from data its existing list, search and detail queries can select at no extra request: the issue's `updatedAt`, the ProjectV2 item's own `updatedAt` (a project field or status change moves that, not the issue's), and the issue's `comments { totalCount }` (which covers a deleted comment). A change kind none of these moves is either keyed on a signal that does move, or leaves the token absent. The kinds are a new, edited or deleted comment, a body or title edit, a label change, and a project field or status change.
   - **Linear** returns no token until its live lane proves which change kinds `Issue.updatedAt` covers. Where the proof is incomplete, the token stays absent, which means always read.
   - **local-md** returns a digest of the task file's bytes.
   - `docs/plugin-protocol.md` states, per plugin, the change kinds its token covers and what it keys on. The token is gated as §6 requires, so an older plugin that sends no token is read as "no token".
2. **Comment origin.** `Comment` gains an optional member `origin`: `{task: "<source>:<native task id>", id: "<native comment id at the origin>", author: string|null, created_at: RFC 3339|null, updated_at: RFC 3339|null, url: string|null}`. It is present only on a comment a copy wrote, and it names the comment at its origin. On the second hop of a chained copy it still names the first origin.
   - local-md stores the origin natively. A copied comment there takes the origin's id, author and times, and the format change follows `docs/local-md.md` and the plugin protocol's compatibility rules for older parsers.
   - GitHub and Linear cannot set a comment's author or time, so there the store carries the origin in a hidden marker inside the comment body. It strips that marker from `body` on read and reports it as `origin`. That marker is used only on destinations that cannot store the origin natively.
3. **`--comments` on `task copy` and `project copy`.** The flag is opt-in. Without it, copy reads, writes and costs exactly what it does today, and the existing no-comment journeys keep holding for the flagless form. With it, the copy keeps the destination's comments in step with the source's, in either direction (board → local-md, local-md → board, and board → board), by one symmetric rule:
   - The copy makes the destination's copies of the source's comments match the source. It adds new ones, edits changed ones, and deletes those whose origin comment is gone.
   - A comment native to the destination is never edited or deleted by a copy.
   - A source comment that is itself a copy of a destination comment is never sent back.
   - So copying a local item back to its board origin carries only the comments written locally, as new board comments, and never edits or deletes the board's own comments.
   - The copy report gains, per item, `comments: {added, edited, deleted, unchanged}` (integers), present only under `--comments`.
4. **The previous-copy record and skip-if-unchanged.** Each copy writes the reserved metadata key `onetaskgraph.copied_version` on the **destination** item, holding the source `version` it copied (and, under `--comments`, the token covers the comments it carried). A `--comments` copy also writes the reserved key `onetaskgraph.copied_with_comments`, the boolean `true`; a flagless copy removes it. A `--comments` copy never skips an item whose destination record lacks it, so a copy that adds `--comments` over an unchanged source still carries the comments. Each copy also writes the reserved key `onetaskgraph.copied_destination_version`: the destination item's own `version` as the copy left it, computed over the item excluding that key. A later copy skips an item only when the source's current `version` equals `onetaskgraph.copied_version` **and** the destination's current `version` equals `onetaskgraph.copied_destination_version`, so an edit or deletion of copied content at the destination is restored by the next copy. The destination's version comes only from reads the copy already makes of the destination; this check adds no request to either end. A destination-native comment added since the copy also makes the item not skipped: the copy re-reads the source, leaves the native comment alone, and reports `unchanged` with `skipped: false` if nothing else differs. A later copy that already holds the source item's current `version` from a listing in hand, equal to the destination's recorded one, does not read that item's body or comments from the source. It reports the existing `unchanged` action with a new member `skipped: true`; an `unchanged` decided by comparison reports `skipped: false`. An item with no token is read and compared as today. `docs/metadata.md`'s count of reserved keys and its drift gate move with the new keys.
5. **Copy by query.** `task copy --to <dest>` accepts, in place of ids, the same narrowing `task list` takes (`--source`, `--commented-since`, `--metadata KEY=VALUE`, repeatable). It copies what that query matches, and the query's own results are the token in hand for the skip. Within one invocation each item's comments are read from the source at most once, including the reads `--commented-since` makes to confirm a match. Ids and a query together are refused.
   **A copy is a consistent snapshot of what it read.** A copy into a local-md source writes the item and its comments exactly at the `version` the copy read: the body, fields, metadata and comments it writes all come from that one read, never mixed with a newer one. It records that version in `onetaskgraph.copied_version`. The store keeps no history, so when an item changed after its listing, the copy reads and records the later version, never the superseded listing one. Each request of the copy's read selects the token's parts at no extra cost; when they disagree across the item's requests, the copy re-reads that item once, and if the parts still disagree it writes nothing for that item and reports it as an error. This holds for every source: one without a token, such as Linear today, reads an item and its comments in one request where they fit, and otherwise detects a change between its requests from what each one returns, with the same one re-read and the same per-item error. So a copy by query into a fresh local-md root is how a caller takes an immutable snapshot of board items, and nothing in the store writes to that root afterwards unless the caller copies into it again. ai-orchestrator's follow-up gathering uses exactly that.
6. **`--no-link`.** It writes nothing at all to the source: no `onetaskgraph.copies` link and no other write. The counterpart is found on the next copy by the destination's own `onetaskgraph.origin`. The report's `link` member says `skipped`. This is what lets a board → local copy leave the board untouched.

**Version class: breaking.** The new public fields on `Task` and `Comment`, which are constructible structs, and the new `CopyLink` word are a break of the public Rust API. So the title carries `!`, and release-plz cuts the next minor (0.3 → 0.4) under this repository's pre-1.0 rule. The node that links this release in `onepipeline` is titled breaking for the same reason.


## Why

Every read of a GitHub or Linear board spends part of an allowance that every session on the host shares: GitHub's hourly GraphQL points and Linear's per-user request limit. When it runs out, every manager's board work stalls. Today a caller that wants to work from a local copy of board items and their comments cannot get one from the store. Copy never carries a comment, and a re-copy reads every item at both ends even when nothing changed. So callers either re-read the board for every step or render their own copies outside the store, which then drift from it.

Carrying comments with their origin identity lets a caller work locally and still reply to the right comment on the board. Skipping unchanged items, decided from tokens the store already receives in the listing, makes a repeat copy cost only its listing. These are general store features, so every consumer gets them without writing its own workaround. Trade-offs are weighed against one rule that outranks cost: a skip must never serve data that has changed.


## Acceptance criteria

- `version` is present on GitHub Projects and local-md items in the JSON of `task list`, `task show`, `task show-many` and `task list --commented-since`, and absent on Linear items unless its live lane proves full coverage. Loopback journeys in `crates/onetaskgraph-e2e` change one GitHub item at a time, by each change kind the contract's item 1 lists, in turn: a new comment, an edited comment, a deleted comment, a body edit, a title edit, a status change, a priority change, a label change, a project field change, a metadata change and an edge change (a dependency added and one removed). For each kind, the journey asserts one of two outcomes, whichever `docs/plugin-protocol.md` states for that plugin: either the item's listed `version` changed, the store compares the new version as later than the old one, and an untouched item's `version` did not change; or, for a kind the plugin documents as uncovered, `version` is absent on that plugin's items. No journey may observe two equal versions of one item across a change of any listed kind. The loopback fixtures model issue `updatedAt`, ProjectV2 item `updatedAt` and comment `totalCount` for this. Tests over the store's version comparison show that it answers `equal` for two equal versions, `later` and `earlier` for the two orders of a version taken before and after a change, and `incomparable` for versions of different items, of different sources, for a value the plugin cannot parse, and for two different local-md digests. The credentialed GitHub and Linear live journeys assert the same change kinds against the real services. Whether the live services agree is the merge path's credentialed lane to report, not this node's bar.
- `task copy --comments` and `project copy --comments` carry comments in each direction: GitHub board → local-md, Linear → local-md, local-md → GitHub board, local-md → Linear, and board → board (a loopback GitHub board → a loopback Linear board, and a loopback GitHub board → a second loopback GitHub board). Journeys over the real binary, on the loopback boards and on local-md over both source boundaries, prove that:
    - each copied comment carries `origin` naming its origin task and comment id, author, created and updated instants, and URL;
    - a local-md copy of a board comment stores those values natively and reads back with the board's own comment id in `origin.id`;
    - a board copy of a local comment, and a board → board copy of a board comment, reads back with the marker stripped from `body`;
    - on a chained copy (GitHub board → local-md → second board, and GitHub board → second board → local-md), the second hop's comments carry an `origin` that names the first origin's task, comment id, author, instants and URL, never the intermediate source's;
    - a re-copy after the source comment is edited edits the copy, and after it is deleted deletes the copy, on every direction above, the board → board one included;
    - a comment native to the destination is never edited or deleted;
    - a copy-back to the origin, from the first hop and from the second hop of a chain, creates only locally written comments and never echoes the origin's own;
    - the report's per-item `comments` counts match what was written.
- Without `--comments`, every existing copy journey and the request counts in `copy-cost.txt` and `docs/plugin-protocol.md`'s cost table are unchanged, and the no-comment journeys still prove that a flagless copy neither reads nor writes a comment at either end.
- A copy writes `onetaskgraph.copied_version` on the destination item, and a `--comments` copy also writes `onetaskgraph.copied_with_comments: true`. A re-copy by query of board items unchanged since the last copy reports each one `unchanged` with `skipped: true`, and the loopback's recorded requests show no request for those items beyond the listing pages. After any one of the change kinds in the first criterion, including a deleted comment, a priority change, a metadata change, an edge change and a project status change, the next re-copy re-reads and re-copies that item and no other. An item from a source with no token is read and compared as before. A journey copies board items without `--comments`, then copies them again with `--comments` while the source is unchanged: the second copy reads each item's comments, writes them, and reports their counts in `comments.added`, never `skipped: true`. A third `--comments` copy over the unchanged source then reports every item `skipped: true`. A `--comments` copy followed by a flagless copy over the unchanged source may skip. A copy also records `onetaskgraph.copied_destination_version`, and a skip requires the destination unchanged since the copy as well as the source. Journeys over an unchanged source show:
    - into local-md and into a loopback board destination, editing a copied comment at the destination, and separately deleting one, makes the next `--comments` copy re-read the item from the source and restore the comment to the source's text, never skipping it;
    - adding a destination-native comment makes the next copy not skip the item, leaves that native comment untouched, and reports the item `unchanged` with `skipped: false`;
    - a further copy over the untouched destination then skips again;
    - the loopback's request log shows that the destination check makes no request of its own: a skipped re-copy into a board destination sends only the source's listing pages and the destination reads the copy already makes to find each counterpart, and a skipped re-copy into local-md sends no board request beyond the source's listing pages. A further journey makes a `--comments` copy, changes the source item's comments, makes a flagless copy that advances `onetaskgraph.copied_version` and removes `onetaskgraph.copied_with_comments` from the destination, as the journey asserts, and then makes a `--comments` copy over the now-unchanged source: that copy reads and writes the changed comments, never skipping, and the destination's comments match the source's.
- `task copy --to <dest>` with `--source`, `--commented-since` and `--metadata` copies exactly what `task list` with the same narrowing returns, and is refused when ids are also given. A journey shows that within one such invocation each item's comments are requested from the source at most once, counting the `--commented-since` confirmation, when the board does not change during the copy. The one re-read the consistency rule makes for an item that changed mid-copy is the only exception, and the next criterion's journey counts it.
- A copy into a local-md root writes each item and its comments from one consistent read of its source, records the version of that read in `onetaskgraph.copied_version` where the source gives one, and never writes a mix of revisions, from every shipped source. The `version` an item's listing named is what the skip compares against; when the item changed after its listing, the copy writes and records the later version it actually read, never the superseded listing version, and never content older than that version. Journeys of a copy by query with `--comments --no-link` into a fresh local-md root change an item at each point the copy reads it, and in each the copy either writes the body, fields, metadata and comments of exactly one source revision, as the source's own state at that revision shows, or writes nothing for that item and reports it as an error, never a partial item:
    - From a loopback GitHub board, a hook changes the item between the listing and its detail read, and between the detail read and its comment page reads (a comment edited, a comment added, and the body edited). Each written item's `onetaskgraph.copied_version` names the revision it holds.
    - From a loopback Linear board, which gives no token, the same hook points are exercised on an item whose comments span more than one page.
    - From a local-md source, the item's file is rewritten between the copy's reads.
    Two further GitHub journeys pin the re-read down. In one, the item changes once between the detail read and its comment reads and then stays put: the copy makes exactly one re-read of that item, as the loopback's request log shows, writes the item at the later revision, and reports it copied. In the other, the hook changes the item again during the re-read: the copy makes exactly one re-read, writes nothing for that item, reports it as an error, and copies every other item normally.
    A further journey changes a comment and the body on the GitHub board after a copy finishes, has a second process read the changed items from the board, and asserts that the local-md copy is byte-identical to what it was before. A follow-on copy into the same root is the only thing that changes it.
- `--no-link` sends no write request to the source: the loopback's recorded requests hold none. The report says `link: skipped`, and the next copy finds the counterpart by its origin and reports it `unchanged` or `updated`, never `created`.
- On a loopback GitHub board of 80 items, 20 of which match a narrowed query (commented since an instant and metadata-filtered) and carry 1 to 5 comments each, with a page size that makes the listing span at least 4 pages, the loopback's recorded requests show both of these: a re-copy by query with `--comments --no-link` into local-md, with nothing changed on the board, sends no request beyond the listing pages; and a `--comments` copy after 5 of those items changed reads no unchanged item, and reads each changed item's detail together with its first comment page in the same request, batched as the plugin's multi-item detail read allows. No separate comment request is made for an item whose comments fit that first page, and a further comment page is the only extra request an item can cause. The journeys record both counts, with their listing, detail and comment-page requests and points, as telemetry files under the crate's `budget_runner` telemetry directory, for `otg-source-cache`'s budget to report in its breakdown. This node registers no budget.
- `onetaskgraph schema` publishes `version`, `origin`, the `comments` counts, `skipped` and the `skipped` link word. The Python SDK is regenerated from it, the TypeScript SDK's hand-written `CopyOptions`/`copyFlags` offer `comments`, `noLink` and the query narrowing, and each SDK's own tests drive a `--comments` copy. `README.md`, `docs/plugin-protocol.md`, `docs/local-md.md` and `docs/metadata.md` state the new behaviour, every sentence that said a copy never touches a comment is rewritten to say this holds without `--comments`, and their drift gates pass.
- The tests of every crate and SDK this change touches pass, formatting and clippy are clean, and the judged lint over this node's diff is clean, on the finished tree.
- Every claim the dispatch's report makes about what it changed, verified and measured is true of the tree as it finally stands.

### Operational notes for this host

**Run only the checks that exercise what you changed.** The tests that cover the code
you touched, the lint that reads your diff — and nothing wider. The repository's own
automation runs the full bar downstream on the change this work becomes: a `pre-push`
hook where that repository publishes locally, the host's required checks where it
publishes remotely. Neither is waiting for you to have run it first, so running it here
spends twenty to forty minutes of this dispatch learning what the merge path reports
anyway. That is measured rather than estimated: one node in this workstream spent about
84 minutes on three rounds of everything its repository could run, to reach lint findings
a diff-scoped run reports in two.

**Pick those checks from your change, and take the narrowest scope each one supports.**
One test module over the whole suite; the lint over your diff over the lint over the
tree. A repository's own fast deterministic tier is a fine choice when it is what
exercises your change — its `just --list` says which recipe that is — and a poor one when
you reached for it because it was the widest thing available. When a check you ran
reports something, fix that and run **that check** again; nothing here asks you to re-run
its neighbours to confirm, and a wider tier cannot re-check a finding it never made.

**A dispatch that changed nothing tracked owes none of them.** When your deliverable is a
document, a report, or an answer, there is no changed code for those checks to exercise
and you are complete without them — decide that from what the repository shows, never
because running them is slow or inconvenient. `git status` reporting nothing to commit is
then a correct and complete outcome, not a problem to solve by writing a file nobody
asked for.

**A publication check runs downstream, so no worker can run it and none is judged on it.**
The host's required checks and a repository's `pre-push` gate run on the change this
work becomes, after this dispatch settles: downstream publication checks are not
runnable by a worker, and a dispatch is never held to one having passed. That holds on a
retry too. A `checks-failed` retry — a re-dispatch onto the same branch carrying the
merge path's refusal and `onevcs`'s evidence — is judged on its task's stated local
acceptance checks: the repair of what the refusal named, proven by the checks the task
names, and never by the downstream check passing again, which can only happen once the
retry has settled. One retry that fixed and locally verified the failing test its
refusal named was failed for not re-running the required check, which left finished
work unpublished and its dependents skipped until a manager published it by hand.

**Never signal a process you did not identify by PID, and a PID you got from a pattern is
still a pattern kill.** Several managers share this host, and their dispatches, drivers,
publications and test servers run under the same few binary names — `just`, `node`,
`python`, `onepipeline-api` — so a kill by name knows nothing about *whose* work it
matched. The distinction is the tool rather than the pattern: `pgrep` and `ps` **read**,
and either spelling of them is fine, `pgrep -x` included; `pkill` **signals**, and it is
never the answer here, in any spelling. `-x` is the trap, because it reads as the careful
one — `pkill -f 'just gate'` at least needs a narrowing pattern, while `pkill -x just`
takes every `just` on the machine. Reading the table first and piping the pids into `kill`
is no way around it: that is the same pattern kill with more steps.

Two workers reached that place from different directions on 2026-08-24, while another
manager's dispatch had been live over an hour. One ran `pkill -TERM -x just`. The other
ran `ps -eo pid,args | grep 'onepipeline-api serve' | awk '{print $1}' | while read pid;
do kill "$pid"; done` — which obeys the letter of every paragraph below and does the same
damage, because `just dag-ui` and the e2e suites both spawn that server and a pytest run's
were alive at that moment.

**The one process you may signal is one you started yourself, so capture its PID as you
start it:**

    cmd & MYPID=$!
    kill "$MYPID"

Anything you did not start belongs to somebody. Read what it is, report what you found,
and leave it running.

**A wait written against a full command line never ends, because one of those command
lines is yours.** That is a different defect from the one above — it wedges your own
dispatch rather than somebody else's — and it is why `pgrep -f` cannot be waited on.
`pgrep -f` matches its pattern against every process's whole argv and excludes exactly one
process — itself — never the shell that invoked it. So any pattern naming the thing you are
waiting for is, by construction, a substring of the command line of the shell doing the
waiting: `until ! pgrep -f "just gate"` matches its own loop and never exits, and so does
the same loop written against `llmlint-judge.sh`, `scripts/fetch-corpus.sh`, or
`publish-branch`. That is a defect in the polling mechanism rather than a fact about gates,
so it applies to every wait you write.

That has wedged four workers here, and then two more workers and the manager itself in one
night: seven instances of one defect. A crozier corpus audit waited in `until ! pgrep -f
'scripts/fetch-corpus.sh'` with no fetch running at all — the only two matches were its own
polling shell and the manager's diagnostic shell — and waited until it was interrupted. A
`check-plan-bar-conflict` dispatch waited on `! pgrep -f "llmlint-judge.sh"`, whose negation
could never become true, and was cancelled and killed; its replacement then reached for
`pkill -f` against three patterns, which is not a wait at all but the same self-match with a
signal attached, and is refused above. And the manager, an hour after instructing a worker
about this, guarded a launch with `pgrep -f "publish-branch" && echo ABORT || launch`, whose
pattern was a literal substring of the launching shell's own command line: it aborted
unconditionally and then reported a publish as RUNNING that did not exist. That last one is
the evidence that matters most — a rule its own author reproduces an hour after issuing it
is a rule whose wording is the problem rather than its reader.

**Wait with a sentinel file.** Background the whole command you are waiting on — one
command, so that what you waited on is what you meant to run — and poll for a file only
that invocation can write:

    ( just test > /tmp/check.$$.log 2>&1; echo $? > /tmp/check.$$.exit ) &
    until [ -f /tmp/check.$$.exit ]; do sleep 20; done

**A process must finish inside the turn that started it.** Backgrounding is how you wait
on a slow command *within* one turn, which is why the launch and the wait sit together in
that example — both halves belong to the same turn. What does not survive is a background
process left running when the turn ends: nothing carries it across, and the launch gives
you no sign of that, because it succeeded and the turn then ended normally. The loss
shows up a turn later as a sentinel that never appeared and a recipe terminated by
signal, with the whole run to pay for again. It bites hardest where it is most tempting,
because a worker reaches for backgrounding exactly when a command is slow enough to
threaten the turn — here the judged lint tier and a whole test tier, which are the two
runs a node most needs to have made. So run a slow check in the foreground, or background
it and wait out its sentinel before your turn ends; never end a turn intending to read a
result on the next one.

**To ask whether a process is running at all, match the executable, not the command line.**
`pgrep -x onepipeline` matches process *names* exactly — the binary, not its arguments — so
the shell doing the asking, whose own name is `bash`, cannot match it however the pattern
is spelled. Where the binary name is not distinctive enough to identify what you mean
(`just`, `node` and `python` run everything), read the process table instead and drop the
one self-match that form has:

    ps -eo pid,args | grep -v grep | grep 'lint-llm-diff'

Both of those are **reads**, which is what makes `-x` safe here and forbidden the moment
the tool signals. The replacement for the worker wedged above reached for `pkill -f "just
gate"`, `pkill -f "just check"` and `pkill -f "nx run"` while another manager's run was
live. Read to learn what is running, report what you found, and signal nothing you did not
start.

**One sentinel and one log per invocation, and look before you launch one.** That pair is a
shape rather than two literal paths. Several dispatches run on this host at once and they
share `/tmp`, so a second worker writing `/tmp/check.log` writes into the first one's — and

**One suppression policy, and this is the whole of it.** A site-scoped `ignore` directive
is permitted where the rule is genuinely misapplied at that site **and** the directive
carries a substantive reason saying why. What is forbidden is silencing a finding you
have not answered so that a count moves. What you owe an account of is **every
suppression your own diff writes — added, moved or rewritten — and every one already
standing over a line that diff changes** — each with its site and its reason, in your
completion report, so the manager reads what you left rather than discovering it. Both
halves are decided from the diff alone: a directive line inside it, or a changed line
inside the region a directive covers. A file-scoped directive is outside both unless your
diff writes the directive itself — its region is every line of the file, so counting it
would make this file's own header a debt of every change that edits a word of it.
Suppressions elsewhere in the tree are not yours to inventory: this repository carries several hundred standing directives, and
a list of them would be longer than the report is read under while saying nothing about
the change under review.

That scope is stated because the sentence it replaces read two ways at once: its first

manager reads what you left* — was about this dispatch's own work, in the same breath. A

**`--no-verify` is not an acceptable response to a slow or inconvenient hook.** The hooks
are this repository's enforcement point — there is no CI — so bypassing one commits work
that nothing has checked, and nothing you run afterwards catches it: a check runs over

likely commit in a dispatch to be wrong. No check caught either one; the monitor caught

**Commit a coherent working piece the moment it works.** A dirty worktree does not
survive this dispatch: what is uncommitted when your last turn ends is what nothing
recovers — not a retry, not a recovery verb, not a manager reading the branch. So each

*The moment it works* is the moment you have seen it work: the checks that piece needs

which every dispatch carries, and go on working on whatever does not depend on the answer.

nothing can recover: a worker that reasoned about a frozen contract correctly, declined to
amend it unilaterally, named two options for its owner, and then stopped for three turns
lost about fifteen minutes of correct work and settled reporting `ahead of main: 0
commit(s)`.

**Draft a follow-up that can wait; never draft one that cannot.** Work you notice that

a list at the end of your last message instead, because nothing reads that list. A draft is

manager should act on now, goes over `$ORCHESTRATOR_ASK_MANAGER` immediately, as the

**A GitHub rate-limit refusal that `gh api rate_limit` disagrees with is the secondary

**Publication goes through the harness.** The session branch reaches its remote only
through `onevcs publish "$ONEVCS_SESSION"`, and its change request is lifted, landed or
kept for the user's review by the lifecycle after you settle. No `git push` of the session branch, no `gh pr create`
for it, no `gh pr ready`, no `gh pr merge`. Finish the branch, commit everything, leave
the tree clean, and report. Landing it is explicitly **not** yours to perform and **not**
part of your acceptance criteria. Two things are yours, and each only when this task's
own `## Additional info` — its own words above these notes — says so:

- **Only when the task's `## Additional info` says the change request may be published
  early**: `onevcs publish "$ONEVCS_SESSION" --draft [--title T] [--body-file PATH]` opens
  the session's change request as a draft, and a later `publish --draft` pushes new
  commits onto that same change request and never opens a second. Commit everything
  first — a dirty tree is committed for you, under a provenance you did not choose.

stands.** That is the property you are held to, and it says nothing about where your
report sits. This conversation does not end when you report — your supervisor keeps

**A claim about a check, a test, a lint run, or a commit that was not run or was not made
is false, and fails on its merits.** A report asserting a check passed on a commit where
no such run occurred is that case, and one node of this host's history was correctly

**Evidence deliberately about an earlier or induced state is not a false claim.** Proving
that an assertion can fail means making it fail, reading the message, and reverting;
proving that a message used to say nothing means quoting the run from before the change.

failed for exactly that: its own criteria required its assertions be observed failing, and
the resulting-tree property above was read as forbidding the citation that requirement
produces.

**A commit that cannot affect a check leaves that check's evidence standing.** *Could have
invalidated it* is a condition, and a commit that fails it does not reach the claim — so a
run taken before a later commit is still evidence for the tree after it, provided the
report names that commit and says why it is inert for that check. What decides it is what
the check reads, never what kind of change the commit is. A comment-only or
documentation-only commit to content a check does not read is inert for that check; the
same comment is not inert for a check that reads comments, which a judged lint does, so
that one is re-run or named as not re-checked. A commit touching anything a check reads is
not inert for it, however small. Two dispatches of one node, about 45 minutes each, were
