# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Build a blueyvatar app for iOS and Android**

*Project description:*
## Goal
Offer blueyvatar as a mobile app on iOS and Android so people can manage their avatars and profile from a phone, where most photos are taken.

## Why
- Taking and cropping a new picture, then making it the default, is a phone task.
- The avatar sync from #241 and the profile fields from #242 are most useful when they are one tap away.
- Store listings give the product more reach with the atproto audience.

## What the app should do (first version, for owner review)
- Sign in with any atproto account (same OAuth sign-in as the website; see #246 for wording that does not assume Bluesky).
- Show the person's avatars, with the default marked, and let them set the default, add alt text, set the rating, and delete.
- Take a photo or pick one from the library, crop it to a square, and upload it. Enforce the same limits as the site (plan image limits, PNG or JPEG size limits, R and X handling).
- Use an avatar as the avatar on the person's home server, with the same sync switch and undo as the website (#241).
- Edit the profile fields that exist on the site (including links, languages, and wallets from #242 once they ship).
- Show plan and billing status. Store rules on in-app purchases decide whether plan changes happen in the app or on the website (see Research).

## Research first (cite published sources; write "Unknown" where a source is silent)
1. **Framework.** Compare a cross-platform framework (for example React Native with Expo, or Flutter) with two native apps. Judge by: the team's existing TypeScript code and packages, atproto OAuth support on mobile, camera and image cropping libraries, and maintenance cost. Recommend one.
2. **atproto OAuth on mobile.** What the atproto OAuth profile says about native apps (redirect handling, client metadata, token storage), and which published libraries support it. The website uses a confidential web client, so a native client needs its own client registration.
3. **Store rules.** Read Apple's App Store Review Guidelines and Google Play's developer policies for: account sign-in requirements, user-generated content and reporting (the app shows user images), in-app purchase requirements for subscriptions, privacy labels and data-safety forms, and age ratings.
4. **Accounts and costs.** Developer program fees, who owns the store accounts, and the legal entity name to use.
5. **API.** Which existing endpoints the app can call, and which new ones it needs (upload, list, set default, delete). Prefer calling the user's own server through the OAuth session where the website already does, and the blueyvatar API where it does not.
6. **Content safety.** How the existing upload screening, ratings, and reporting flow reach the app, since store reviewers look for them.

## Decisions needed from the owner
- Cross-platform or native, after the research.
- Who owns the Apple and Google developer accounts, and under which name.
- Whether paid plans can be bought in the app (store rules may require in-app purchase) or only on the website.
- Which features must be in version 1.
- Whether to ship to TestFlight and Google Play internal testing first (recommended) and with whom (#215 early adopters).

## Work (after research and decisions)

3. Avatar list, upload with crop, set default, delete.

5. Accessibility pass (screen reader, large text, contrast) and localization setup.

7. Beta through TestFlight and Google Play internal testing; fix feedback.
8. Release and update the website and `/integrations` page.
