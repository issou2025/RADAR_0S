## Problem Statement

The ANDROMEDA Flutter app (`mobile_app/`) is a working Android app for monitoring and controlling the IoT drip-irrigation system, but it was built and polished without a verification pass against the approved design documents (`docs/blueprint-flutter-app.md`, `docs/blueprint-andromeda.md`, `docs/proposal.pdf`). A two-axis audit (Spec vs proposal/wireframe, Standards vs code smells) surfaced several safety-critical and correctness issues: valve status colors are reversed against the wireframe (a farmer could misread whether a valve is open), a realtime stream subscription leaks because a provider never disposes it, the valve command default duration is 0 instead of the specified 30s, config saves can silently diverge from the backend, an unsafe route cast can crash on null arguments, and a missing ConfigProvider means the spec's global settings feature doesn't exist.

The farmer user (main target) is non-technical and relies on the app reading correctly at a glance â€” these bugs erode that trust.

## Solution

From the user's perspective: the app behaves correctly and safely per the approved design â€” valve states display with the wireframe's color semantics (TERBUKA = red/danger, TERTUTUP = green/safe), valve commands always carry a sensible duration, saving a petak's konfigurasi either succeeds or visibly errors (never silently diverges), navigation never crashes on missing arguments, the app stops leaking connections in the background, and the global Pengaturan screen gets its spec'd ConfigProvider.

Under the hood: all of this is enforced at the **Provider layer** â€” the single testing seam â€” with the UI consuming state that is already correct.

## Implementation Decisions

- **Testing seam: the Provider layer.** All domain behaviour is tested at `DevicesProvider` and `DashboardProvider`, driven through **faked repositories** (repositories are injected into providers via constructor, so a test double implements the repository interface â€” no Supabase, no network, no widget tree). The UI becomes a thin consumer of already-tested state. This is the highest seam that captures the safety logic without spawning widget tests.
- **Valve colour/copy single source of truth.** Introduce one domain mapping (function on the valve-status type: `on`â†’danger/red/TERBUKA, `off`â†’success/green/TERTUTUP, `unknown`â†’grey) and have every screen and widget call it. The existing enum already declares the correct semantics; the bug is screens overriding it with literal colors. This mapping lives with the model and is covered at the Provider seam by unit-testing a small domain helper â€” no widget test needed.
- **Valve duration default = 30 detik.** Default selected duration in the dashboard UI becomes 30 (matching `SensorRepository.sendCommand` default and the blueprint's `VALVE_ON` default). Zero-duration sends become impossible from the UI.
- **DashboardProvider config handling.** `updateConfig` must notify success, and the UI must not mutate the provider-owned `SystemConfig` object in place. The provider owns the authoritative `config`; the screen edits a local draft and only applies via `updateConfig`, which sets state from the backend result on success and keeps the previous value (plus a surfaced error) on failure.
- **Null-safety hardening.** Remove the `dynamic config` in the dashboard; route arguments (`deviceId`) are validated and produce a safe error state instead of an unsafe cast crash.
- **DevicesProvider lifecycle.** Add `dispose()` that cancels the stored `StreamSubscription` from `getDevicesStream()`, and attach an `onError` handler so stream errors surface rather than crash.
- **ConfigProvider (spec gap).** Add the missing `ConfigProvider` (notification prefs + theme selection), wire it into `MultiProvider`, and back the Settings screen's toggles with it. This closes blueprint Â§State Management and task 3.3.
- **Repository error transparency.** Stop catch-all `â†’ null`/`â†’ {}` swallows in device/config repositories. Return typed failure (nullable + log, or throw) so callers can distinguish "empty" from "failed". The splash connectivity check uses the real result, not a guess.
- **Settings screen stability.** The connection check future is created once (not on every build) so the FutureBuilder doesn't flicker.
- **Splash determinism.** Replace busy-polling on the provider flag with a readiness event / direct await of initial load, then navigate once.
- **Remove dead/duplicate code** (unused `DeviceCard` duplicate, `LoadingOverlay`, `allDevices`, unused repository methods) as part of this pass where their removal is safe â€” but only items the audit proved unreferenced.
- No schema/API changes; the backend contract (devices, sensor_readings, pending_commands, system_config) stays as-is.

## Testing Decisions

- **What makes a good test here:** assert external behaviour at the Provider seam â€” state transitions (`loading â†’ ready/error`), the valve colour mapping (`on â†’ danger`), the duration default, config save success/failure keeping/diverging state, dispose cancelling subscriptions, and device online/offline classification. Never assert on internal fields or implementation details like how many times `notifyListeners` fired.
- **Modules tested:** `DashboardProvider` (load device, valve command with default duration, config update success/failure, chart range switching, dispose cancels subs), `DevicesProvider` (streams devices, latest readings, online/offline via heartbeat vs fallback, refresh error handling, dispose), and the domain valve-colour helper.
- **Test doubles:** faked `DeviceRepository`, `SensorRepository`, `ConfigRepository` â€” controllers that emit canned lists/streams and record calls. No Supabase, no timers beyond injectable clocks where needed.
- **Prior art:** the codebase currently has **no** meaningful tests â€” only a placeholder `widget_test.dart` (`expect(true, isTrue)`). So this spec establishes the seam from scratch. The blueprint's Â§12 and task 7.x define the intended test inventory; we start with the Provider seam and grow from there. (Building out the full blueprint test suite â€” model/service tests â€” is out of scope for this pass.)
