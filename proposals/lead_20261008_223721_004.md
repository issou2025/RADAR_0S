# Project Proposal — Dwg To Revit

## Project Understanding
You need assistance with: 
**Every block reference deep-copies its block's geometry, per instance and per layer (3.8 GB heap)**

*Project description:*
**Packages:** @mlightcad/three-renderer 1.7.4 (`AcTrGroup`), @mlightcad/cad-simple-viewer 1.7.4 (`AcTrView2d.handleGroup`), @mlightcad/data-model 1.15.2 (`AcDbRenderingCache`)

Memory for a drawing grows with *instances × parts × layers* instead of with the distinct blocks it holds. Three steps add up per `INSERT`:

1. The rendering cache hands out a [`fastDeepClone()` of the block template](https://github.com/mlightcad/realdwg-web/blob/0d3eb3be3c27a46ebc8158c348e4876d59ec91d2/packages/data-model/src/misc/AcDbRenderingCache.ts#L432-L442) for every reference (and again for [nested references](https://github.com/mlightcad/realdwg-web/blob/0d3eb3be3c27a46ebc8158c348e4876d59ec91d2/packages/data-model/src/misc/AcDbRenderingCache.ts#L686-L693)). [`AcTrGroup.fastDeepClone`](https://github.com/mlightcad/cad-viewer/blob/a39bab9b16892fa9d49101035579a022a03a8fc6/packages/three-renderer/src/object/AcTrGroup.ts#L658-L674) shares buffers only once the template is compacted.
2. Each clone [stores a bounding box per part](https://github.com/mlightcad/cad-viewer/blob/a39bab9b16892fa9d49101035579a022a03a8fc6/packages/three-renderer/src/object/AcTrGroup.ts#L890) up front, although they are only needed for picking.
3. [`handleGroup`](https://github.com/mlightcad/cad-viewer/blob/a39bab9b16892fa9d49101035579a022a03a8fc6/packages/cad-simple-viewer/src/view/AcTrView2d.ts#L3964-L3973) splits every block reference into one new group per layer.

**Measured** (on @mlightcad/data-model 1.14.12 / three-renderer 1.7.1; the code paths above are unchanged in 1.15.2 / 1.7.4): a 157 MB architectural detail drawing with about 72,000 block references holds 3.8 GB of JS heap once open (peak 4.7 GB). Of the sampled live allocations, about 800 MB sit under `AcDbRenderingCache.draw` (`fastDeepClone`/`copyGeometry` about 180 MB, `storeBoxes` about 120 MB) and about 180 MB in `handleGroup`'s per-layer groups. On machines with 8 GB of memory the tab runs out of memory. The drawing is customer data and cannot be shared.

**Reproduce**
Open a drawing whose blocks are inserted many times (façade or detail sheets), then take a sampling heap profile after the load: the allocations above dominate.

**Expected**
- Instances of one block share their template's geometry (a shared `BufferGeometry`, or an `InstancedMesh` with a per-instance matrix).
- Per-part boxes computed when picking first needs them, not for every instance up front.
- Per-layer groups referencing the shared geometry rather than copies.

**Workaround we use**
None that is safe to patch from outside. Dropping unused XData on the server saves 18 to 23 per cent of the heap on Revit exports, but not this.

Possibly related (closed): #159, #675, #683.
