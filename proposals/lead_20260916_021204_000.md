# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**stage-demo: progressively enrich one design from loose geometry to Stage-4 FEA-ready physical semantics**

*Project description:*
## Goal

Build one narrow vertical demo proving a core MonkeyHub principle:

> **Stage progression increases semantic and physical resolution only as the project needs it. Geometry does not have to be fully classified or physically specified at the moment it is created.**

The demo should take the **same retained design objects** from an early loose state through Stage 4, progressively attach semantics/material/physical properties, and finally compile a structural-analysis projection suitable for an FEA backend.

This is not a BIM conversion exercise and not a request to fully define the meaning of every MonkeyHub Stage globally. It is a concrete proof that the Stage system can support **progressive reality binding**.

---

# Core principle

A Stage is not merely a project-status label.

It represents the level of semantic commitment / reality correspondence that the project is ready to support.

Early:

```text
geometry
```

Later:

```text
geometry
+ architectural role
+ material identity
+ physical material properties
+ analysis role / assumptions
+ real-world evidence later
```

Do not force all future semantics into Stage 1.

Do not reinterpret an early generic face/solid as a trustworthy wall/slab/beam until the project or user commits that meaning.

---

# Demo object

Use one deliberately small fixture:

**small reinforced-concrete frame / pavilion**

Suggested geometry:

- 2–3 bays;
- 1–2 storeys;
- columns;
- beams;
- one slab or roof plate;
- simple supports;
- simple gravity load.

Keep the geometry small enough that the final structural result can be checked against a known/reference solution or independently reproduced.

The purpose is the Stage/semantic/analysis interface, not a production structural model.

---

# Demo Stage progression

The exact global Stage ontology can evolve later. For this demo, prove the following **progressive enrichment pattern**.

## Stage 1 — geometry without premature identity

Example:

```text
object A
  geometry = planar/solid geometry
  semantic role = unknown / coarse massing
```

At this stage the user can model spatially without answering:

- wall or slab?
- structural or non-structural?
- concrete or steel?
- exact physical parameters?

Requirements:

- geometry has stable MonkeyHub identity;
- provenance/history is retained;
- no fake physical properties are required;
- unsupported later capabilities remain unavailable rather than inventing defaults.

---

## Stage 2 — architectural / system role becomes explicit where needed

The same retained objects may now acquire roles such as:

```text
column-like member
beam-like member
floor/roof plate
non-structural enclosure
```

or the current repository's closest role vocabulary.

Important:

- identity survives from Stage 1;
- semantic enrichment is a patch/refinement, not object replacement;
- objects not relevant to the structural demo do not need forced structural semantics.

---

## Stage 3 — semantic material binding

Relevant members may be assigned a material family / specification identity, e.g.:

```text
material = reinforced concrete
```

This is **not yet equivalent to an FEA constitutive model**.

Separate:

```text
semantic material identity
```

from:

```text
physical property profile
```

A rendering/display material must not silently become structural material truth.

---

## Stage 4 — physical / analysis-ready semantics

The structural subset receives the additional information required by the structural-analysis capability.

For the first concrete-frame demo, this may include:

### physical material profile

```text
density
Young's modulus
Poisson ratio
compressive strength where relevant
thermal expansion only if the selected analysis needs it
```

Every property retains:

```text
value
unit
source/provenance
assumption/observed/specification status
conditions where relevant
uncertainty/range when supplied
```

### structural role / idealization

```text
beam / column / plate or equivalent analysis role
cross-section / thickness
connectivity
support/boundary assumptions
```

### analysis inputs

```text
load case(s)
load combination if needed
mesh/idealization policy
solver policy
```

Stage 4 does not mean every project object must contain all these fields.

Instead:

> **Stage 4 allows the project to carry this level of physical commitment; the FEA capability declares the exact prerequisites for the subset it consumes.**

---

# Capability prerequisite contract

Avoid a giant rule such as:

> `Stage 4 requires every object to have every physical property.`

Instead define a capability-readiness check, conceptually:

```text
StructuralAnalysisCapability
  required:
    structural role
    geometry/section sufficient for selected idealization
    physical material profile
    connectivity
    boundary/support conditions
    loads

  optional:
    nonlinear law
    reinforcement detail
    uncertainty distributions
```

The UI/runtime can then say:

```text
FEA unavailable:
- Column C03 has no physical material profile
- Beam B02 has no section
- supports not defined
```

rather than manufacturing assumptions silently.

---

# Material representation for the demo

Prove a minimal separation between:

```text
MaterialIdentity
```

and

```text
PhysicalMaterialProfile
```

Example:

```text
MaterialIdentity
  name: concrete
  family: concrete

PhysicalMaterialProfile
  domain: structural
  profile: demo-concrete-30MPa
  density: ...
  E: ...
  poisson: ...
  fc: ...
  provenance: fixture/source
```

Do not build the complete material library in this issue.

The first demo only needs one or two well-defined materials with explicit source and units.

The model must not invent physical values merely because the semantic material says `concrete`.

---

# Analysis projection

At Stage 4, compile an explicit projection rather than passing Canonical State directly to a solver.

Conceptually:

```text
Stage-4 Canonical Design State
        ↓
StructuralAnalysisCompiler
        ↓
StructuralAnalysisSpec@1
        ↓
FEA adapter / reference solver
```

`StructuralAnalysisSpec@1` should contain only the analysis facts required for this run, with exact source bindings back to MonkeyHub entities.

Example shape:

```text
analysis_id
source_project / exact revision
source_stage
members[]
  source_entity_id
  idealization
  geometry/section
  physical_material_profile_ref
nodes/connectivity
supports
loads
load_cases
analysis assumptions
mesh/solver policy
```

This is a **projection**, not a second Canonical State.

---

# FEA boundary for the first demo

Do not write a new general-purpose finite-element solver in this issue.

Use either:

- a small reference solver already suitable for the chosen fixture; or
- a temporary deterministic test adapter if necessary to prove the contract first.

The minimum end-to-end result should return structured evidence such as:

```text
analysis status
nodal displacement(s)
reaction(s)
member force / stress quantity appropriate to the fixture
solver/version
source revision
assumptions
```

A contour plot may be added later; structured evidence is the primary acceptance target.

---

# Stage transition semantics

The demo must prove that enrichment does not destroy earlier identity/history.

For one structural member, retain a trace like:

```text
Stage 1
entity_id = X
geometry only

Stage 2
entity_id = X
+ structural/architectural role

Stage 3
entity_id = X
+ semantic material

Stage 4
entity_id = X
+ structural physical profile
+ section / analysis assumptions
```

The same entity remains identifiable throughout.

Stage advancement should not rewrite earlier retained revisions.

Later Stage facts may refine current state while the historical earlier representation remains reproducible.

---

# Missing-information behavior

The demo is incomplete if it only works because every field is prefilled.

Prove at least these failures:

1. Stage 1 object cannot be sent to structural analysis solely because it has geometry.
2. Semantic `concrete` without physical profile is insufficient for FEA.
3. Physical material without section/idealization is insufficient for a beam/column analysis.
4. Missing supports or loads produces an explicit readiness failure.
5. The system never silently inserts arbitrary E/density/strength values.

---

# Relationship to Stage dependency authority

Later analysis semantics must not silently rewrite earlier protected design intent.

Example:

If structural preparation discovers that a Stage-4 analysis assumption is incompatible with a frozen earlier geometry/program decision:

```text
Stage 4 analysis preparation
    ↓
revision request / explicit proposed transition
```

not:

```text
silently resize Stage-2 architecture
```

This demo should reuse the existing Stage/revision authority model rather than create an analysis-specific mutation path.

# First implementation slice

1. Create one tiny retained concrete-frame fixture at Stage 1.
2. Advance the same exact entities through Stage 2/3/4 with explicit semantic enrichment records.
3. Add minimal semantic material + structural physical profile representation.
4. Add structural-analysis readiness validation.
5. Define `StructuralAnalysisSpec@1` (or repository-compatible equivalent).
6. Compile the Stage-4 fixture into that spec.
7. Send it through one bounded FEA/reference adapter.
8. Return structured analysis evidence bound to exact source entities/revision.
9. Save/reopen and prove Stage enrichment + analysis bindings survive restart.
10. Change one Stage-4 physical property (e.g. E/profile), rerun, and show that the analysis result changes while design geometry/identity remains the same.

## Definition of done

A reviewer can watch one small project evolve as:

```text
loose geometry
→ identified architectural/structural members
→ semantic material
→ sourced physical material profile
→ Stage-4 structural readiness

```

without losing entity identity, inventing missing physical facts, or turning the project into BIM at Stage 1.

The demo proves the larger principle:

> **MonkeyHub increases reality correspondence progressively with Stage, and physical analysis becomes available when the relevant subset has accumulated enough explicit semantics to support it.**
