# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**example: rebuild as a recipe browser with a viewport-aware preview stage, and give the app a real theme**

*Project description:*
## Problem Statement

The example app has one door, and it opens onto everything at once.

`PlaygroundPage` is 958 lines driving 58 settings fields across 20 features. For
someone evaluating the package it is excellent — every capability is reachable
from one screen, presets snap between states, and the feature list plus detail
pane already narrow 58 controls down to the handful a feature owns. For someone
who arrived because they searched for `mergedRows`, it is the wrong artifact
entirely: there is no minimal, self-contained, copy-and-paste block of code
anywhere in `example/`. The playground shows *that* a feature works. It never
shows *what you write to get it*.

Three specific gaps follow from that:

1. **No copyable recipe.** Every feature is demonstrated inside a page whose
   state is threaded through `PlaygroundSettings`. Lifting a working
   `FlutterTablePlus` call out of it means reading around 958 lines of
   playground scaffolding. `README.md` carries snippets, but snippets in prose
   are unexecuted and drift silently — this repo has no CI to catch that.

2. **No viewport story.** The package's most consequential layout behaviour is
   that it does *not* reflow — a table narrower than its content scrolls
   horizontally, with the header and scrollbar kept in step by
   `SyncedScrollControllers`. Nothing in the example shows what the table looks
   like at a phone width, so the one behaviour a reader most needs to see before
   adopting the package is the one behaviour the example never renders.

3. **The example app's own theme is unconsidered.** `main.dart` is
   `ThemeData(primarySwatch: Colors.blue, useMaterial3: true)` and nothing else.
   There is no dark mode, no typography decision, no colour decision. A table
   package's example is a shop window for a *visual* widget, and this one is
   dressed in the framework default. This is the maintainer's first-named
   complaint and is tracked here as a first-class axis, not a polish pass.

There is a fourth, quieter problem. The example currently has two entries in its
home list (`Playground`, `Tooltip anchors`), which reads as "this package does
two things". It does twelve.

## Solution

Build a **recipe browser** with a **viewport-aware preview stage** *beside* the
existing example, and keep the playground intact as one destination inside it.

**This is grown alongside, not swapped in.** The new shell arrives as an
additional entry in the current home list and stays there for the whole of the
work. Nothing existing is deleted, replaced, or rerouted while the shell is
being built: at every point the example still starts where it starts today, the
playground still opens the way it opens today, and the test suite is still
green. Retiring the old home list is a separate decision, taken by the
maintainer after the shell is built and judged — not a step inside building it.
The reason is not caution for its own sake: this is a large change to the only
artifact that demonstrates the package, and a rework that is additive can be
inspected at any point and abandoned at any point without a restoration.

**A recipe is one feature, one file, self-contained.** It imports Flutter, this
package, and the shared demo data — nothing else. It is short enough to read in
full and correct enough to paste into a real app unchanged. The app displays the
recipe's own source, read from the bundled file, so what is on screen and what
runs can never disagree.

**A recipe already has a name, a switch, and a knob set** — those live in
`settingsSpec`, which describes all 58 settings fields today and is held true by
a test that reads `PlaygroundSettings`'s source. Recipes attach to that
description rather than introducing a parallel taxonomy, and reuse
`FeatureDetailPane`, which already renders exactly one feature's controls and
nothing else.

**The preview stage owns the viewport.** A segmented control switches the
preview — and only the preview — between desktop, tablet, mobile, and an "all"
mode that shows the three side by side. The surrounding shell keeps its own
size, so knobs stay operable while the table is rendered at 390 logical pixels.

**Every one of the 58 settings survives.** They are re-homed, not removed: a
recipe exposes only the settings its feature owns, and the playground continues
to expose all of them. What is removed is screens, not options.

**The app chrome gets a real theme** — a deliberate palette, a typeface pairing,
and a light/dark pair — kept strictly separate from `TablePlusTheme`, which is
the package's own surface and is driven by the settings.

## Implementation Decisions

### Shell structure

- A single shell holds a category sidebar, a preview stage, a knob pane, and a
  source pane. Its three regions are laid out by available width so the shell
  degrades to a single column on a narrow window.
- Sidebar categories: **Recipes**, **Scenarios**, **Playground**. `Playground`
  is one destination in that list.
- **The shell is reached from the existing `HomePage` list, as an added entry.**
  `HomePage`, `PlaygroundPage`, and `TooltipAnchorPage` all keep their current
  routes and behaviour for the duration of this work. The shell reaching the
  playground through the sidebar and the home list reaching it directly are both
  live at once; that duplication is intended and is what makes every step
  reversible.
- `TooltipAnchorPage`'s content becomes a recipe as well. The standalone route
  is not removed at the same time — the recipe is added, both exist, and
  whether to drop the route is decided later against a working shell.

### Rollout: additive until a separate, explicit decision

- Every unit of work in this spec is expected to leave the example runnable and
  the suite green **with the current entry points untouched**. If a piece of
  work cannot be done that way, that is a finding to report rather than a reason
  to start deleting.
- Deleting the old home list, dropping the standalone tooltip route, and making
  the shell the app's home are one decision, taken once, at the end, by the
  maintainer. They are deliberately not distributed across the work.
- Consequence, accepted: for the duration, some features are reachable by two
  paths and a little code is duplicated. That cost is the price of being able to
  stop at any point.

### Reviewability: the work is inspected by running it

- This is a visual change to a visual artifact, and the agent doing the work
  cannot open a window — `flutter run` is the maintainer's to run. Tests going
  green is therefore necessary and not sufficient evidence that a piece of this
  is right.
- Each unit of work names, in the maintainer's terms, **what to look at and what
  it should look like**: which entry to open, what to click, and what should be
  on screen. A unit is not finished when its tests pass; it is finished when
  that has been looked at.
- Units are sized so that this looking is short. A unit whose visual check
  cannot be described in a sentence or two is too large and should be split.

### Recipes attach to the existing settings description — one seam

- `SettingFeature` in `settings_spec.dart` gains an optional field naming the
  recipe's source asset. `settingsSpec` already enumerates 20 features with a
  `switchId` and an `options` list per feature, and `settings_spec_test.dart`
  already holds it true against the 58 fields declared on `PlaygroundSettings`.
  Attaching recipes here means the recipe list, the recipe's knob set, and the
  recipe's related-feature notes all derive from a description that is already
  under test. No parallel catalogue is introduced.
- Features without a recipe asset (the pure-appearance groupings such as header
  borders) simply do not appear under Recipes. They remain reachable in the
  playground. Recipe coverage is therefore allowed to be a subset of features,
  and the absence of a recipe is a data fact rather than an omission.
- The knob pane for a recipe is `FeatureDetailPane`, unchanged in contract. It
  already renders exactly one feature's switch and options and nothing else, and
  already renders the feature's `Interaction` list with its citations. This is
  reuse, not a new widget.

### Recipe files

- One file per recipe under a recipes directory. Each is a self-contained
  widget: it constructs its own columns, holds its own local state, and calls
  `FlutterTablePlus` directly.
- **Import allow-list**: `package:flutter/*`, `package:flutter_table_plus/*`,
  and the shared demo data library. A recipe may not import the shell, the
  playground, or any settings type. This is what makes "copy-pasteable" a
  checkable property rather than a claim.
- Because of that rule, `Employee` and `RandomDataGenerator` move out of
  `playground/models` and `playground/utils` into a shared demo-data library
  that both the recipes and the playground import. The playground's behaviour is
  unchanged by the move.
- Recipes are driven by their feature's settings where that is natural, but a
  recipe must render correctly with default settings and no shell present. The
  shell passes settings in; it is not required for the widget to build.

### Source display

- Recipe source files are registered as Flutter assets and read at runtime with
  `rootBundle.loadString`. The source pane renders the file's real bytes.
- Hand-written snippet strings are explicitly rejected. This repo has no CI, so
  a snippet that drifts from the code drifts silently and indefinitely.
- Noted consequence, accepted: bundling `.dart` files as assets ships the
  recipe source inside the built app. That is correct for an example app and
  would be wrong for the package itself; the package bundles no assets and is
  unaffected.

### Viewport preview

- A `ViewportSpec` value type carries a name, a logical size, and a chrome
  policy (whether the shell's sidebar is shown at that width). The named
  viewports are desktop 1440x900, tablet 834x1112, and mobile 390x844.
- A `PreviewStage` widget takes a `ViewportSpec` and a child and constrains the
  child with **both** a `MediaQuery` size override and a matching `SizedBox`.
  **Corrected 2026-08-25, by measurement.** The two do different jobs, and the reason first given here was wrong. The package reads `MediaQuery` exactly once — for the text scaler, `flutter_table_plus.dart:585` — and never reads `MediaQuery.of(context).size`; it resolves its widths from its own `constraints.maxWidth`. So the `SizedBox` alone fully determines what the **table** does. The `MediaQuery` override is for the consumer code sharing the frame: a recipe or a scenario is entitled to branch on the reported size, and a phone preview handing it the host window's width would send that branch down the wrong arm with nothing on screen looking wrong. Both are still applied; the reason is the one above.

  From the prototype, the decision in its smallest form:

  ```dart
  MediaQuery(
    data: MediaQuery.of(context).copyWith(size: vp.size),
    child: SizedBox.fromSize(size: vp.size, child: child),
  )
  ```

- **Scale is 1.0 in the single-viewport modes.** When a named viewport is wider
  than the available stage, the stage scrolls rather than scaling, or scales
  with the factor rendered on screen — but the interactive modes are never
  silently scaled. The reason is specific to this package: drag selection is one
  viewport-local coordinate frame, with a `Listener` outside the body's
  horizontal `Scrollable` reading `event.localPosition`, and the rubber-band
  geometry and auto-scroll timer are written against that frame. Keeping scale
  at 1.0 means that frame is never questioned.
- **Device Wall** (the "all" mode) renders the three viewports side by side at a
  reduced scale and is wrapped in `IgnorePointer`. It is a layout-comparison
  view, not an operable one. Making it non-interactive removes the need to
  verify hit-testing, rubber-band geometry, and the auto-scroll timer under a
  transform — the risk is designed out rather than tested away.
- Device Wall and the 100,000-row scenario are mutually exclusive; the wall
  renders three tables at once and the scenario is a single-table performance
  claim.

### Rejected dependencies, and why

- **`device_preview`** wraps `runApp`, so the sidebar and knob pane would shrink
  along with the table. The requirement is to constrain the preview pane, not to
  simulate the app.
- **`device_frame`** draws a bezel by scaling the screen through a transform.
  Flutter's `Transform` does apply the inverse to hit testing, so pointer
  coordinates are likely correct — but "likely" is not a basis for putting the
  drag selection coordinate frame under a scale factor. A bezel may be added
  later as an opt-in on top of a working 1.0-scale stage.
- **`widgetbook`** would supply the sidebar, knobs, device frames, and theme
  switching for free. It is rejected because this repo already owns a settings
  description and control registry totalling roughly 1,050 lines that is under
  test; adopting Widgetbook would create a second knob system and leave the
  playground with nowhere to live. This is a budget trade-off rather than a
  technical one, and is recorded as such.

### App chrome theme

- A pure function from `Brightness` to `ThemeData` replaces the inline
  `ThemeData(primarySwatch: Colors.blue)` in `main.dart`. It defines a colour
  scheme, a typeface pairing, and surface treatments deliberately rather than by
  default.
- The app exposes a light/dark/system control. The table's `TablePlusTheme`
  follows the app brightness, which demonstrates a capability the package has
  and the example currently never shows.
- **The two themes stay separate.** `TablePlusTheme` is the package's surface
  and remains driven by the 58 settings; the app chrome theme is the example's
  own. A reader must be able to tell which colours the package controls. The
  chrome palette is therefore deliberately not the table palette.
- `scaledBy()` is built on `copyWith` and enumerates only the six sub-themes it
  scales. Nothing in this rework may reintroduce hand-listing of sub-themes.

### Settings: re-homed, never removed

- All 58 fields on `PlaygroundSettings` survive. The two-tier exposure is:
  a recipe shows its feature's `switchId` plus its `options`; the playground
  shows everything, exactly as it does today.
- `settings_registry.dart` and `settings_controls.dart` are reused unchanged in
  contract. Their existing invariant — the ids the description covers and the
  ids the registry can draw are the same set — continues to hold and continues
  to be the thing that keeps a control from vanishing.

## Testing Decisions

A good test here asserts a property of external behaviour and survives a
redesign of the thing it tests. This suite already works that way and the
existing comments say so explicitly: `feature_detail_test.dart` stopped counting
"25 switches, 12 dropdowns, 20 sliders" and now asserts that a feature shows its
own controls and nothing else. New tests follow that discipline — none of them
should assert a widget tree shape, a colour literal, or a pixel measurement that
a visual revision is entitled to change.

### Reusing the source-reading pattern

Dart has no reflection, so two existing tests put questions to the *source* that
cannot be put to the compiler: `settings_spec_test.dart` reads
`PlaygroundSettings`'s fields and compares them to what the description covers,
and `settings_id_test.dart` does the same for control ids. Two new invariants
use that same prior art:

- **Every recipe's source asset exists and is bundled.** A recipe naming a file
  that is absent, or present but not registered as an asset, must turn the suite
  red — otherwise the source pane renders empty at runtime with nothing to catch
  it.
- **Every recipe file's imports are inside the allow-list.** Read each recipe's
  import lines and assert they resolve only to Flutter, this package, or the
  shared demo data. This is what keeps "copy-pasteable" true. A recipe that
  reaches into the shell or the playground is the exact failure this guards.

### Modules under test

- **`settingsSpec` (extended).** The existing four tests continue unchanged —
  every field described exactly once, every interaction naming a real feature,
  no interaction without a citation, ids unique. Adding a recipe field must not
  perturb them, and the field count assertion of 58 is a deliberate tripwire
  that should be updated only alongside a real settings change.
- **`ViewportSpec`.** Pure data: named viewports carry the sizes claimed, and
  the chrome policy is a function of width. No pumping required.
- **`PreviewStage`.** One widget test: the child is laid out at the spec's size
  *and* reports that size through `MediaQuery`. Asserting only one of the two is
  the bug this test exists to prevent.
- **Device Wall.** Assert it renders three frames and that it does not deliver
  pointer events — a tap inside a wall frame must not reach a row.
- **App theme.** Pure function: light and dark both produce a `ThemeData`, the
  two differ in brightness, and the table theme derived alongside them follows.
  Do not assert specific colour values; assert relationships.
- **Shell navigation.** Selecting a recipe from the sidebar shows that recipe's
  knobs and no other feature's — the same property `feature_detail_test.dart`
  already asserts, applied at the shell level.
- **Recipes.** Each recipe pumps and renders a table. This is a smoke assertion,
  not a re-test of the library; the package's own suite owns feature behaviour.

### Prior art to follow

- `preset_bar_test.dart` sets an explicit `tester.view.physicalSize` and resets
  it in a tear-down. Every viewport-related test must do the same, and viewport
  tests must set a host size large enough that the widget under test is not
  silently clipped.
- `feature_list_test.dart` and `feature_detail_test.dart` document *why* they
  size the view the way they do, because the test font measures every glyph as a
  square of the font size and content is far wider under test than on screen.
  New widget tests inherit that hazard and should size for it rather than
  discovering it.
- `playground_columns_test.dart` is a characterisation test written before code
  was lifted out of the page. The move of `Employee` and `RandomDataGenerator`
  into a shared library should be preceded by the same move: characterise, then
  lift.

## Out of Scope

- **Changing the library.** This is an `example/` rework. No file under `lib/`
  changes. If the rework surfaces a package defect, it becomes its own issue.
- **The cutover itself.** Removing the current home list, dropping the
  standalone tooltip route, and making the shell the app's home are explicitly
  *not* part of this spec. They are a separate decision taken against a shell
  that already exists and has been looked at. Nothing here may delete an
  existing entry point.
- **Bezel/device-chrome rendering.** Explicitly deferred. A bezel requires a
  transform, and a transform puts the drag-selection coordinate frame in
  question. Revisit only on top of a working 1.0-scale stage.
- **Adding any dependency to `example/pubspec.yaml`.** `google_fonts` and
  `flutter_svg` are already there and may be used; nothing new is added.
- **Web deployment of the example.** Publishing the shell as a hosted demo is a
  reasonable follow-up and is not part of this.
- **README rewriting.** The README's snippets have the same drift problem the
  in-app source pane solves, but converting them is separate work.
- **Localisation.** The shell stays single-language.
- **Visual regression / golden tests.** The theme work is deliberately not
  pinned by goldens; the tests assert relationships, not appearance.
- **Recipes for every one of the 20 features.** Recipe coverage is a subset by
  design. Pure-appearance groupings stay playground-only.

## Further Notes

- **The prototype.** Four shell directions were prototyped and compared before
  this spec: a recipe browser, a Widgetbook adoption, a minimal augmentation of
  the existing playground, and a device wall. The recipe browser was selected
  with the device wall folded in as a viewport mode. The device wall on its own
  answers the viewport question and none of the feature-presentation question,
  which is why it is a mode rather than an option.

- **The playground is not the problem.** It is worth stating plainly, because a
  rework of this size reads as a verdict on what it replaces. The feature list,
  the detail pane, the search, the presets, and the settings description with
  its cited interactions are the strongest part of the example and are being
  *reused*, not rewritten. What is being fixed is that they were the only door.

- **Why "all 58 options" survives.** The maintainer's instinct that some things
  should be dropped is correct, but the thing to drop is screens, not options.
  Removing an option removes the ability to reproduce a reported combination.
  Removing a screen removes a place a reader can get lost. The rework removes
  two screens and zero options.

- **MAP obligation.** Per `docs/map/README.md`, the territory notes touched by
  this change should be opened and their `## Blast radius` treated as a
  checklist before the boundary is drawn — and if this work reveals a fact that
  holds outside the territory it was found in, an invariant note is part of the
  change rather than a follow-up. This is example-only work, so the expected
  outcome is that most territories are opened and nothing needs changing; not
  opening them is the failure the map exists to prevent.

- **Sequencing.** The shell and the viewport bar deliver the viewport
  requirement on their own, with only the playground hung off the sidebar. Each
  later stage — recipes, source pane, device wall, scenarios — is independently
  droppable if the work needs to be cut short. The one ordering constraint is
  that the shared demo data must be lifted out of `playground/` before the first
  recipe is written, since the import allow-list depends on it.

- **The riskiest assumption goes first.** The load-bearing guess in this whole
  rework is that a table constrained by a `MediaQuery` size override plus a
  matching `SizedBox` behaves as a genuinely narrow table — including that drag
  selection still works inside it, since that feature reads pointer positions in
  a viewport-local frame. That is provable with a preview stage and a hardcoded
  table, before any shell, any recipe, or any sidebar exists. If it fails there,
  almost nothing has been spent. It should not be discovered late.

- **Stopping is a supported outcome.** Because the work is additive and the
  cutover is deferred, abandoning after any unit leaves a working example plus
  however much of the shell was built, reachable from an extra home entry. There
  is no half-migrated state to restore from. This is stated so that stopping
  reads as a decision rather than a failure.
