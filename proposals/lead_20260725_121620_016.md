*Project description:*
## The repository has had no completed full-test run since 2026-07-23, by construction

This is not a dispatch-discipline problem and no fleet rule can fix it. The **scheduled nightly
is itself being destroyed**, so the project loses its only full test signal on any night with
concurrent activity — indefinitely, with nobody's behaviour at fault.

### Evidence

The last five `test.yml` runs, every one cancelled:

| run | created | trigger | outcome |
|---|---|---|---|
| 30145478392 | 07-25 05:16 | dispatch | cancelled |
| 30141465131 | 07-25 03:01 | dispatch (protected) | cancelled |
| 30141248301 | 07-25 02:53 | dispatch | cancelled |
| 30135536531 | 07-25 00:07 | dispatch | cancelled |
| **30069250206** | **07-24 05:22** | **schedule (cron)** | **cancelled** |

Last completed run: **29982196128, 07-23** (`failure`, 601 runtime failures — the baseline
everything is still measured against). That baseline is now two days stale and cannot be
refreshed.

### Mechanism

`test.yml` declares concurrency at **workflow level**:

```yaml
concurrency:
  group: rust-ci-${{ github.ref }}
  cancel-in-progress: true
```

Every trigger — cron and dispatch alike — lands in the **same** ref-keyed group, because
`github.ref` is `refs/heads/main` for both. So any dispatch cancels the nightly. A workflow-level
group cancels *every job in the run*, including `aggregate`, which is what writes
`MASTER_FAILURES`. Job-level concurrency cannot protect against it.

This is the same root cause as #2429's archive starvation, which was fixed by giving the archive
its own SHA-keyed, uncancellable workflow (`fa49405bd`). But that fix deliberately did **not**
address the ledger: `MASTER_FAILURES` is produced by the full run's `aggregate` job, not by the
archive job, so a cancelled `test.yml` still means no ledger. Naming that gap is why this issue
exists rather than a bullet on #2429.

### Why this is worse than it looks

`MASTER_FAILURES` is the only measurement of whether a campaign reduced red. Without it:

- no campaign can demonstrate a delta against the 601 baseline;
- a red named in the stale ledger may already be fixed, so lanes spend time re-fixing (this
  already happened: a lane found `sparse_dict::` was 101/0 at main before starting, because the
  ledger predated five fixes landed that afternoon);
- and a newly-introduced red is invisible until someone trips over it.

### Proposed fix — separate the two triggers into different concurrency groups

The interactive and scheduled uses of `test.yml` want opposite semantics, and one group cannot
express both:

- **dispatched** runs *should* supersede each other — a lane re-dispatching wants the newest, and
  ref-keyed `cancel-in-progress` is right for that;
- **scheduled** runs must never be cancelled — the nightly is the ledger, and there is no later
  run that recreates it.

Both are expressible without touching the shard fan-out:

```yaml
concurrency:
  group: rust-ci-${{ github.event_name == 'schedule' && github.sha || github.ref }}
  cancel-in-progress: ${{ github.event_name != 'schedule' }}
```

A scheduled run then sits in `rust-ci-<sha>` with cancellation off, while dispatches stay in
`rust-ci-refs/heads/main` with cancellation on. They are **different groups**, so a dispatch can
no longer cancel the nightly, and dispatches still supersede one another exactly as today.

Cost: the nightly and one dispatch may now run concurrently, bounded at two matrices. Previously
the "saving" was destroying the nightly, which is not a saving worth having. Dispatches still
cannot multiply among themselves, so this does not reproduce the runner-pool explosion that ruled
out SHA-keying the whole workflow in #2429.

### Alternatives considered

- **SHA-key the whole workflow unconditionally** — rejected in #2429: N distinct SHAs would mean
  N concurrent 11-job matrices.
- **A standalone `rust-ledger.yml` duplicating archive → shards → aggregate** — works, but
  duplicates ~500 lines of `test.yml`, and the duplicate would drift.
- **Extract the jobs into a reusable `workflow_call` workflow shared by both** — the clean
  long-term shape, but a structural refactor of the file the whole fleet depends on; worth doing
  deliberately, not at the same time as the minimal fix.

### Related

- #2429 — same root cause, archive half fixed; this is the ledger half it explicitly did not fix.
- The 07-23 ledger is a *snapshot*, not live state, and is stale in a known direction — always
  re-verify a named red before fixing it.
