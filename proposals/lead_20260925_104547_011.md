# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**[STRATEGY][CLAW][P0] Unified Claw surfaces — Web entry + Desktop Local Runner + Mobile Companion + optional Cloud Sandbox**

*Project description:*
## Product direction

Padiem Claw remains **web-first**, but the web surface is no longer required to own every execution environment.

The original product intent remains valid:

- ordinary consumers should be able to visit the Padiem website and experience Claw without understanding "agents", runtimes, terminals, or sandbox infrastructure;
- users should be able to start with chat, document work, Google Drive, Telegram, connected apps, automation, and other cloud-visible tasks directly from the web;
- stronger execution should appear progressively only when needed.

The revised architecture separates **entry experience** from **execution location**.

```text
                         PADIEM CLOUD
        account / chat / memory / tasks / connectors / policy
                              |
              +---------------+---------------+
              |               |               |
             WEB           DESKTOP          MOBILE
        primary entry     local worker      companion
              |               |               |
              +---------------+---------------+
                              |
                            CLAW
                              |
                  +-----------+-----------+
                  |                       |
             LOCAL RUNNER            CLOUD SANDBOX
             user's device         managed / BYOC
```

## Why this issue exists

The first Claw architecture intentionally emphasized browser access because consumer users may not understand or want to install an "AI agent". The web experience lets a user indirectly discover agent behavior:

```text
visit website
-> talk to Claw
-> create/edit documents
-> connect Google Drive / Telegram / other services
-> schedule or automate work
-> gradually discover stronger capabilities
```

This remains a strategic advantage and should not be discarded.

However, requiring the browser product to also solve safe multi-tenant arbitrary-code execution before Claw can feel useful has pulled the critical path into infrastructure-heavy sandbox work: nested virtualization, KVM, VPC/egress, metadata blocking, TTL/delete semantics, process-tree death, non-resurrection, secret isolation, etc.

Hermes Agent demonstrates a different useful pattern: install a local agent/runtime on the user's own computer and let that machine provide the execution environment. Its TUI/GUI is not the desired Padiem consumer experience, but the architectural separation between a headless runtime and multiple UI surfaces is relevant.

This issue records the product decision to combine both approaches rather than choosing "web only" or "installed only".

## Surface roles

### 1. Web — primary consumer entry

The web remains the default way to meet and use Claw.

Target web capabilities include:

- chat and memory;
- web research;
- connected-app work;
- Google Drive and document workflows;
- Telegram and messaging integrations;
- scheduled/recurring automation;
- cloud-side artifacts and approvals;
- task status and handoff to another execution surface.

Users should not need to understand Agent / MCP / runtime / shell / model/provider terminology to start.

### 2. Desktop — Claw Local Runner + full local execution

Desktop is the execution surface for work that requires the user's own computer.

Examples:

- files and folders;
- Git repositories;
- Python / Node / local tools;
- browser automation;
- local applications;
- document conversion;
- long-running development tasks.

Preferred connection shape:

```text
Claw Desktop / Local Runner
    -> outbound authenticated channel to Padiem Cloud
    -> receives signed bounded tasks
    -> executes only within granted capabilities/roots
    -> returns bounded evidence/results
```

No public inbound server or router port-forward should be required for the normal consumer path.

Reuse existing Padiem controls where practical:

- P01 approval and capability policy;
- selected-root filesystem boundaries;
- exact task/request fingerprints;
- process timeout/cancel/process-tree kill;
- safe evidence projection;
- secret redaction;
- network capability controls;
- explicit approval for elevated/high-risk actions.

### 3. Mobile — companion / controller, not a duplicate full desktop agent

Mobile should launch alongside or near Desktop for consumer completeness, but it should not duplicate every desktop execution primitive.

Primary mobile roles:

- chat / voice;
- camera/photo input;
- files and attachments;
- push notifications;
- approve/deny actions;
- task status;
- remote instruction to connected Desktop;
- cloud automation management;
- Drive/Telegram/connector work;
- results/artifact viewing.

Example:

```text
Mobile instruction
-> Padiem Cloud
-> connected Desktop Claw
-> local work
-> result / approval / notification back to Mobile
```

### 4. Cloud Sandbox — optional execution surface, not the launch blocker

Cloud sandbox remains important for:

- user device offline;
- scheduled/background execution;
- install-free users;
- mobile-only users;
- untrusted external repositories/code;
- disposable isolated workloads.

But Cloud M1 must no longer block the whole Claw consumer experience.

Current sandbox tracks such as #1405 remain valid. Managed options (Vercel Sandbox / E2B) and BYOC/self-host options (GCP, OCI, dedicated local KVM) remain research/implementation lanes, but are **execution options**, not the single required Claw runtime.

## Hermes / external-runtime adoption question

Run an adopt-first architecture review before rebuilding a complete desktop/local runtime from scratch.

Compare at minimum:

1. reuse current Padiem local execution primitives;
2. adapt selected Hermes Agent runtime concepts/components where licensing and architecture allow;
3. use Hermes or another headless runtime as a local execution backend behind Padiem UX/policy;
4. build only missing Padiem-specific local-runner layers.

Evaluation must cover:

- license and redistribution/fork posture;
- Windows/macOS support;
- installation/bootstrap/upgrades;
- headless API / WebSocket / JSON-RPC or equivalent;
- filesystem/process/browser/tool boundaries;
- skills and connectors;
- cron/background execution;
- local model support;
- telemetry/privacy;
- security model and privilege boundaries;
- fit with Padiem P01/capability approvals;
- ability to keep Padiem's consumer UX and product identity independent of the runtime.

Do not copy Hermes TUI/GUI as the product UI.

## Proposed priority

```text
P0  Web Claw consumer entry stays active
P0  Desktop Local Runner / Desktop app
P0  Cloud <-> Desktop task protocol and approvals
P1  Mobile companion
P1  Managed cloud sandbox (Vercel/E2B)
P2  GCP/self-hosted sandbox optimization
P2  OCI / dedicated local KVM fallback
```

This ordering may change after the architecture/adoption audit, but GCP/KVM research should not delay the Web/Desktop consumer path.

## Shared product model

The product should feel like **one Claw**, not four unrelated products.

```text
Web      = entrance
Desktop  = hands and feet
Mobile   = remote controller / companion
Cloud    = disposable remote workshop
```

Conversation, memory, tasks, approvals, connectors, artifacts, device presence and execution receipts should converge on shared cloud identity/state while preserving local-data and capability boundaries.

## Key UX requirement

When a web user requests a task that needs local access, the product should transition naturally:

> This task needs access to your computer. Connect this computer.

Then:

```text
[Connect my computer]
-> install/open Padiem Claw Desktop
-> login / pair
-> "This computer is connected"
-> user continues the same Claw conversation
```

Avoid developer terminology in the normal consumer flow.

## Non-goals for this parent issue

- no immediate final sandbox-provider selection;
- no requirement to make Mobile a shell/process executor;
- no requirement to expose model/provider/MCP configuration to ordinary users;
- no decision that Hermes must be forked or embedded;
- no abandonment of current web connectors or Cloud M1 work;
- no Production deployment authorized by this strategy issue alone.
