# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**audit: SORTENTSTABLE sort handles (group code 5) are counted as object handles, producing false `duplicate_handles`**

*Project description:*
## Summary

`audit` reports `invalid_dxf_handle_graph` with a long `duplicate_handles` list on files that contain a populated `SORTENTSTABLE`. The handles listed are not duplicated object handles — they are **sort handles**, which `SORTENTSTABLE` stores under group code **5** by design.

Tested with `OpenCADStudio-v2026.43-windows-x86_64-portable.exe` on Windows 11 x64, through `--serve`.

## Minimal reproduction (no drawing needed)

Three `TEXT` entities and one `SORTENTSTABLE`, built with `ezdxf`:

```python
import ezdxf

def build(path, with_sortents):
    doc = ezdxf.new("R2018")
    msp = doc.modelspace()
    ents = [msp.add_text(f"T{i}", dxfattribs={"insert": (i * 10, 0)}) for i in range(3)]
    h = [e.dxf.handle for e in ents]          # -> ['2F', '30', '31']
    if with_sortents:
        # sort handles drawn from the same value pool as the entity handles
        msp.set_redraw_order([(h[0], h[2]), (h[1], h[0]), (h[2], h[1])])
    doc.saveas(path)

build("no_sortents.dxf", False)
build("with_sortents.dxf", True)
```

Then run `audit` on each (`--serve`, `{"op":"open","path":...}` then `{"op":"audit"}`):

| file | `duplicate_handles` |
|---|---|
| `no_sortents.dxf` | **0** |
| `with_sortents.dxf` | **3** |

Three entities, three "duplicates".

## The object in question

This is the entire `SORTENTSTABLE` written by the script above:

```
  0
SORTENTSTABLE
  5
33            <- the object's own handle
330
32
100
AcDbSortentsTable
330
17            <- owner: the model space block record
331
2F            <- entity handle
  5
31            <- SORT handle for the entity above
331
30
  5
2F
331
31
  5
30
```

Inside `AcDbSortentsTable` the pairs are `331` (soft pointer to the entity) followed by `5` (the sort handle for that entity). Only the **first** group 5 in the record — the one before `100 AcDbSortentsTable` — is the object's own handle. The parser appears to treat every group 5 in the record as an object handle declaration, so each sort handle collides with the entity handle that happens to carry the same value.

## Expected

`duplicate_handles` should be empty for both files. A sort handle is a value in the entity-handle space by definition — it points at drawing order, it does not declare an object.

## Impact on real files

Six production drawings exported from Autodesk Revit, measured the same way (raw scan counting only the first group 5 of a `SORTENTSTABLE` as an object handle):

| drawing | declared handles | sort handles in `SORTENTSTABLE` | `audit` `duplicate_handles` | real duplicate object handles |
|---|---:|---:|---:|---:|
| A | 6,956 | 417 | 189 | **0** |
| B | 33,726 | 2,998 | 2,961 | **0** |
| C | 59,625 | 970 | 970 | **0** |
| D | 56,081 | 0 | **0** | **0** |
| E | 42,152 | 0 | **0** | **0** |
| F | 87,051 | 4,022 | 4,022 | **0** |

The correlation is exact: drawings whose `SORTENTSTABLE` is empty report zero, and the reported count tracks the number of sort handles. (A and B fall short of their sort-handle count because some of their sort handles do not collide with an existing entity handle.) Every one of these files has **zero** genuinely duplicated object handles.

Exporters that draw sort handles from the same value pool as entity handles therefore make `audit` flag thousands of entries on an otherwise clean drawing, which makes the `invalid_dxf_handle_graph` signal hard to trust.

## Suggested fix

When parsing `SORTENTSTABLE`, register only the group 5 that precedes `100 AcDbSortentsTable` as the object handle. After that marker, treat each group 5 as the sort handle belonging to the preceding group 331, and exclude it from the declared-handle set.

Round-tripping these files is otherwise lossless — entity counts, layers, block definitions, dimension measurements and the ANSI_949 code page all survived unchanged in my tests. Thanks for the tool.
