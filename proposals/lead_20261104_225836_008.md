## Background

Historically, Flutter has supported density adjustments through component-specific properties such as `isDense`, and through `VisualDensity`, which can be configured globally using `ThemeData.visualDensity`.

The new [Material 3 Expressive density guidelines](https://m3.material.io/foundations/layout/grids-spacing/density) describe a component-scaling system using density levels starting at `0`, with each negative step reducing component height by 4dp through adjustments to padding or dimensions.

While this is conceptually similar to Flutter's existing `VisualDensity` system, it is unclear how M3E component scaling is intended to be supported.

The existing M3E implementations appear to explicitly opt out of inheriting application-level density:

- flutter/packages#12832 — M3E `IconButton`
- flutter/packages#13084 — M3E `ElevatedButton`

Both use `VisualDensity.standard` in their generated defaults, and PR #13084 includes a test explicitly verifying that `ThemeData.visualDensity` is ignored.

Although developers can override density through component-specific styles, this requires configuring each component family independently.

## Questions

1. **Is there an existing plan for supporting M3E component scaling consistently across components?**
2. **Should M3E components respect an explicitly configured application-level density**, such as `ThemeData.visualDensity`, while retaining standard density as the default?
3. Should a new, theme-level component-scaling API be introduced for M3E?

## Related issue

- flutter/flutter#190578 — Discusses changing Flutter's default density to standard across platforms, but does not address whether M3E components should inherit explicitly configured theme-level density.
