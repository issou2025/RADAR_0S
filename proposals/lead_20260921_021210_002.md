**Revit: shrubs as their own Planting family, from the published foliage type**

**What to do**

- Read the `foliage_type` column in `TreePointsReader` by header name. `landcover.tree_points.foliage_type_vocabulary` names the vocabulary. A manifest without it has no column, and every point is a tree.
- Vocabulary `"1"` is `tree` and `shrub`. Map `shrub` to a Planting family of its own, and read any value the host does not know as `tree` (`spec/format.md` §4.4, a MUST). Never infer foliage type from `height_m` or `crown_radius_m`. The platform owns that classification.
- The shrub family is authored the way the tree family is (a developer command, height and crown radius per instance), stamped per row like the trees, with the same reuse / refuse / create table.
- The first host that reads the value lands the corpus case for the unknown-value rule. Propose it by pull request, since the corpus is maintainer-owned.

**Decisions** (settled in a grilling session on 2026-09-19)

- **Terms** (#195): a *tree point* is any published point of the tree layer. *Tree* and *shrub* name only its foliage type. `SiteTree` becomes `SiteTreePoint` and carries the foliage type.
- **Reading**:
  - An unknown value or an empty cell reads as `tree`. The log counts empty cells.
  - An unknown vocabulary id does **not** discard the column: known values keep their meaning and are mapped, and the log says once that the vocabulary is newer than the plugin. §4.4 now says this, in #180.
- **Family**: `Mantle Place Shrub`, a Planting family of its own (not a second type of `Mantle Place Tree`).
  - Geometry is a dome with no trunk, sized by `Shrub Height` and `Crown Radius`. `Tree Height` is not renamed, because a family already in a project is never reloaded.
  - The DirectShape fallback builds the same dome.
  - Each family decides its own fallback: a shrub family that fails doesn't pull the trees onto DirectShapes.
  - The shrub family is loaded only when at least one shrub will be created.
- **Authoring**: the same developer command writes both `.rfa`s, and its switch is renamed `MANTLEPLACE_AUTHOR_PLANTING_FAMILIES`. The shrub `.rfa` is committed as a binary (about 450 KB, approved).
- **Identity**: one stamp, `Mantle Place Tree {stem}/{build}/{row}`, on every tree point, shrubs included. The stamp identifies the row and the build, not the family. `TreeIdentity`'s doc comment says so in one sentence; there is no ADR.
- **Re-import after an older plugin**: the same build placed before this change has its shrubs as trees. Those rows are reused as they are (the step never modifies an element it didn't create), and the log counts reused rows whose foliage type disagrees with their family and names the Comments prefix to delete to rebuild them.
- **Checklist**: one box, relabelled **Planting** (was Trees). The `Trees` example text in the standard (HPS-51) changes with it.
- **Corpus**: the unknown-value case lands in this issue's PR, `appliesTo` Revit.
- **Also in the PR**: `revit/README.md`'s "one family only" line and `TreeFamily`'s "a foliage type waits for the platform" remark.
- **Unreal**: counterpart filed as #196.

**Done when:** headless tests for the column, the vocabulary (absent and unknown), the unknown value and the empty cell; one real import in Revit 2027 from the `main` install slot, reported with the deploy stamp.
