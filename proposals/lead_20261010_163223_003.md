## Problem Statement

An everyday Android user wants one convenient application for using compatible televisions and attached streaming devices, rather than separate disconnected experiences for remote control, phone-keyboard entry, media playback and live-screen display. Different television models, firmware, receiver protocols and Android versions offer different functions. A usable solution must therefore provide a consistent remote experience **without falsely suggesting universal compatibility**, and must clearly distinguish a **control target** from a **casting target** and **media casting** from **screen mirroring** (Q1–Q28, Q43–Q58).

## Solution

Provide a privacy-first Android app that discovers or manually connects to compatible televisions and streaming devices over local Wi-Fi, requests normal on-TV authorization as necessary, maintains saved devices, and exposes only supported/available remote commands and focused-field keyboard input. Allow the user to select media (photo/video/audio), optionally share a supported **direct media link** into the app, and send it to a separately identified **casting target** using compatible receiver mechanisms. Pursue independent live-screen mirroring with explicit Android capture consent, an active-sharing indicator, stop action, appropriate stream protection, and audio only where permitted and feasible. Investigate Wi-Fi Direct as an **optional additional transport**, never a prerequisite for existing LAN functions.

First explore implementation and hardware verification on a Samsung QN90B (2022 Tizen, reported firmware `T-PTMDEUC-1720.7`) with a Galaxy S24 FE. This first target is provisional and evidence-dependent, not a declaration of compatibility. Broader intended platforms include Android/Google TV, Roku, LG webOS, Fire TV and compatible external receivers. Release may be staged: only functions actually verified for advertised device/firmware combinations may be promised. Before finalizing an implementation plan, preserve the research/feasibility assessment of all four core feature groups (Q3, Q25, Q43, Q47, Q57).

## User Stories

### Connect, pair, save, recover and forget (US1–US13)

1. As an Android user, I want to discover compatible televisions on my current local Wi-Fi, so that I can select one without entering its address (Q7).
2. As an Android user, I want a clear list of detected devices, so that I can identify the intended TV or streaming device (Q7, Q12).
3. As an Android user, I want to enter a TV's IP address manually, so that I can try connecting when discovery does not find it (Q16).
4. As an Android user, I want understandable troubleshooting when discovery finds nothing, so that I can recover locally (Q16, Q58).
5. As an Android user, I want an ordinary TV-side pairing or authorization flow where required, so that I can grant permission without developer tools (Q7, Q17).
6. As an Android user, I want clear feedback if I deny or cancel TV pairing, so that no authorization is assumed (Q7, Q58).
7. As an Android user, I want to know whether a TV is connecting, connected, interrupted or unavailable, so that I understand command readiness (Q27).
8. As an Android user, I want my authorized TVs saved, so that I do not have to repeat setup every session (Q15).
9. As an Android user, I want to save multiple devices, so that I can switch among them (Q15).
10. As an Android user, I want reconnection after temporary interruptions where possible, so that normal control resumes conveniently (Q27).
11. As an Android user, I want manual recovery when reconnection fails, so that I am not trapped in a broken state (Q27, Q58).
12. As an Android user, I want to forget a device and delete its locally stored authorization details, so that it no longer remains in my app (Q52).
13. As an Android user, I want an explanation that forgetting a device may not revoke TV-side authorization, so that I do not mistake deletion for remote revocation (Q52).

## Implementation Decisions

### Accepted behavioral and product decisions (not technology selections)

1. **Compatibility is capability-specific.** A connected device can be partially compatible. Distinguish **verified compatibility** for a given model/software version from protocol-documented/expected, unknown/unverified and unsupported functions (Q6, Q53, Q57).
2. **Supported destinations include TVs and streaming devices.** A **control target** and **casting target** are separate selections; they may point to different endpoints and must not silently change together (Q12, Q46).
3. **Wi-Fi is the primary LAN path.** Discovery, manual-IP fallback, normal pairing, remembered device credentials, reconnection, troubleshooting and forgetting a device are in scope. Wi-Fi Direct is additional and experimental until verified; it must not gate LAN operation or be equated with Miracast (Q4, Q7, Q15–Q17, Q22, Q27, Q51–Q52).
4. **Use ordinary consumer authorization.** Debug/ADB-dependent paths may be optional advanced paths but not required for normal remote control. Secure communications, device identity and credential handling must be examined; copying community examples that turn off certificate verification is **not approved** (Q17, Q39; discovery §4.1).
5. **TV command support is per-device/per-command.** Navigation, selection, Home/Back, volume/mute, input, playback, power and app launching are offered only when compatible. Network wake can be limited by standby and protocol support (Q8, Q14, Q24).
6. **Keyboard input is focused-field and compatibility-scoped.** No arbitrary text injection into all TV applications. If the initial Samsung hardware cannot demonstrate a usable eligible input context, return to the user before narrowing the staged launch boundary; do not silently discard keyboard support (Q9, Q48).
7. **Media casting is separate from screen mirroring.** Investigate compatible Google Cast and DLNA/UPnP paths first; additional receiver protocols only where supported. Start with direct playback of user-selected media and eligible shared **direct media links**. Do not assume codecs, service credentials or formats transfer across receivers (Q10, Q18–Q19, Q44, Q49, Q54).
8. **Do not introduce unapproved media extraction/transcoding.** Arbitrary website video extraction, service integrations, DRM/authenticated-stream relaying and automatic transcoding are not accepted first-stage features. Unsupported media requires clear user-facing errors (Q19, Q49, Q54).
9. **Casting remains controllable.** Keep remote functions accessible alongside media playback functions, and restore access to an ongoing cast session after sender reconnection where possible; recognize that phone-hosted sources may disappear on disconnect (Q45, Q50).
10. **Independent live-screen mirroring remains a core objective.** Investigate native/standards-based receiving separately from MediaProjection capture plus encode/transport/receiver. Capture consent, active state, visible stop, reasonable stream protection and permitted audio are required. No DRM bypass or blanket Miracast promise (Q11, Q20–Q23, Q55).
11. **Smart View guidance is not independent mirroring.** On supported Galaxy hardware, optional user guidance or a tested public cast-settings handoff may be offered; do not claim UniRemote programmatically invokes undocumented Samsung mirroring APIs (Q34).
12. **TV-side receiver applications are optional.** Investigate built-in receivers/browser options before committing to a companion TV app. If one is necessary, disclose requirements and separately validate Samsung/Tizen packaging and distribution; phone-only ordinary LAN remote control must not depend on it (Q2, Q56).
13. **Initial device priority is provisional.** Samsung Tizen/QN90B is first for implementation exploration because physical equipment exists, not because third-party functions have been verified or other platforms excluded (Q13, Q29–Q33, Q43).
14. **Launch can be staged after cross-feature assessment.** All four feature groups are assessed prior to plan signoff; a remote-and-keyboard-first Play release is permissible only when its actual advertised functions are verified. Staged scope changes triggered by keyboard failure need renewed user agreement (Q3, Q25, Q47–Q48, Q57).
15. **Privacy and release constraints are product requirements.** No UniRemote account for core LAN operation, no ads at first launch, no automatic tracking/diagnostic upload, local/protected device records, minimal picker permissions, reviewable and redacted user-triggered diagnostic export, English-first localization-ready UI, accessibility and Play security/policy compliance (Q26, Q28, Q38–Q42, Q44, Q57–Q58).
16. **Development environments:** Windows and Linux are available. Do not schedule a separate exploratory prototype phase (Q35–Q36); the phone and TV already share Wi-Fi per user confirmation, so there is no standalone task merely to re-prove that baseline (Q37).

### Engineering choices deliberately left open

The discovery record **does not select** Kotlin vs other app language, UI framework, Android min/target SDK, concrete dependency versions, architecture/modules/adapters, individual TV protocol implementations, a specific mirroring transport/receiver, TV receiver distribution strategy, performance budgets or a definitive platform rollout order. Resolve these using official documentation, existing-source inspection, project constraints and later authorized implementation planning. No vendor or sample project is approved for direct code reuse. Review licensing and security before adopting third-party code.

### Proposed test seam (requires confirmation; not a previously accepted architecture decision)

Use the **highest user-observable device-session journey** as the primary functional seam: *discover or select target → request authorization → display capability status → perform supported action → survive failure/reconnect → forget device*. Exercise it against controlled protocol simulators/fake receivers where practical. Add only protocol-specific seams needed to validate distinct casting-target behavior, media-serving/rejoining and screen-capture consent/security. Real-device evaluation remains the separate final proof for **verified compatibility**. This proposes how to test behavior, **not** a module hierarchy, chosen framework or approved vendor integration.

| [Android Wi-Fi Direct](https://developer.android.com/develop/connectivity/wifi/wifip2p) and [P2P discovery](https://developer.android.com/develop/connectivity/wifi/nsd-wifi-direct) | Peer discovery/connection and relevant permissions are separate from upper-layer services. | Do not classify P2P discovery as confirmed TV control or Miracast support (Q22, Q51). |
| [Android 17 LAN permissions](https://developer.android.com/about/versions/17/behavior-changes-17) | Apps **targeting API 37+** face `ACCESS_LOCAL_NETWORK` runtime permission or suitable system-mediated discovery pathways. | Re-evaluate local-network discovery and permissions when deciding SDK/target support; no API 37 target selected here. |
| [Google Play target API policy](https://support.google.com/googleplay/android-developer/answer/11926878) | **As of 10 October 2026**, new **Android phone** apps and updates generally must target **Android 16 / API 36+** for Play submission (subject to policy exceptions/extensions). | This is a current release-policy floor, **not** a selection of UniRemote's `minSdk`; review policies again at submission (Q38, Q42, Q57). |
| [Google Cast Android sender guide](https://developers.google.com/cast/docs/android_sender/integrate) and [receiver media support](https://developers.google.com/cast/docs/media) | Sender, receiver app and codec support are separate; session discovery and playback can depend on receiver capability. | Separate control/casting targets, playback recovery and format handling; do not infer full-screen mirroring from Cast integration (Q18, Q46, Q49–Q50). |
| [Samsung Smart View receiver documentation](https://developer.samsung.com/smarttv/develop/extension-libraries/smart-view-sdk/receiver-apps.html) and [Seller Office](https://developer.samsung.com/tv-seller-office/guides/overview.html) | Receiver apps have their own requirements and distribution path; legacy default media player paths are not all still supported. | First validate modern Tizen receiver feasibility; an optional TV app cannot be assumed installable on QN90B (Q34, Q56). |
| [Roku External Control Protocol](https://developer.roku.com/dev/docs/external-control-api) | Although ECP documents SSDP and key commands (some require **Control by mobile apps** setting), it also explicitly says ECP commands **may not be sent from third-party mobile platforms**. | **Policy blocker** for conventional third-party Roku ECP control. Do not put Roku ECP in a committed rollout until an authorized path is established; keep the broad Roku ambition only as an investigation (Q12–Q13). |
| [OWASP MASVS Network](https://mas.owasp.org/MASVS/08-MASVS-NETWORK/) and [Google Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469) | Network and user-data protection are independent of home-Wi-Fi trust; Play disclosure must reflect actual SDK/network behavior. | No blanket TLS verification bypass, no invisible telemetry, and user-reviewable redacted diagnostics only if implemented (Q39, Q52, Q58). |

### Research-to-decision boundaries

- **Verified UniRemote interoperability on exact hardware: none yet.** QN90B/SmartThings and Galaxy Smart View operation are user reports of *Samsung's own apps*, not third-party UniRemote evidence.
- **Do not select dependencies based on example existence.** Re-evaluate protocol access, security posture, version compatibility, maintainer/licensing risks and usable UI before adopting code.
- **Keep Wi-Fi Direct, independent mirroring and TV receiver feasibility as separate technical gates.** A source showing a component of an end-to-end path is not proof of the entire path.
- **Do not silently relax security.** Community code may use insecure certificate workarounds; evaluate a defensible device identity and session-authentication method before selecting a transport.
- **Roku requires explicit policy resolution.** The new official reading strengthens the already-recorded Q13 Roku warning; it does not cancel the user's multi-platform vision.
- **Research is not an implementation authorization.** Product priorities, detailed technology selections, releases and testing approach still require the ordinary later phase decisions.

## Testing Decisions

1. **Behavior over implementation:** Assert observable user outcomes, failures, permissions, device state and target selection. Avoid tests that require a particular library, internal class structure or exact UI technology.
2. **Primary seam:** Repeat the discover/authorize/control/reconnect/forget journey against controlled simulated endpoints. Test normal, denied and cancelled pairing; saved device switching; manual-IP recovery; off/standby states; and stable UI status (Q7–Q8, Q14–Q16, Q27, Q52).
3. **Capability matrix:** Check supported, documented/expected, unverified and unsupported presentation **for each individual capability**; verify unsupported controls never appear as tested working commands (Q6, Q24, Q53).
4. **Input contexts:** Verify text delivery only into eligible focused TV fields. Check no focus, unsupported app, refused connection, and sensitive input contexts according to the supported protocol. On QN90B, keep context-by-context pass/fail evidence; do not infer keyboard availability from third-party code (Q9, Q48).
5. **Two-target behavior:** Verify the **control target** stays selected while a different **casting target** receives media; remote commands never migrate silently and playback controls address the receiver (Q45–Q46).
6. **Media:** Test picker-based photo/video/audio selection, granted/denied media access, supported and unsupported codecs, direct media links vs webpage links, receiver errors, interrupted/rejoined cast, and phone-hosted source loss. Do not assert transcoding (Q44, Q49–Q50, Q54).
7. **Mirroring:** Test consent granted/denied/revoked, visible sharing state, immediate stop, unauthorized viewer prevention, disconnection, optional audio limitation, protected/blank content handling, and whether a **real receiver** can present the stream. Screen capture alone does not pass the mirroring acceptance test (Q20–Q23, Q55).
8. **Wi-Fi Direct:** Test supported and unsupported P2P scenarios without breaking established LAN control, and explicitly distinguish peer connectivity from actual TV control/media services (Q22, Q51).
9. **Privacy/security:** Test local saved-credential lifecycle and deletion, appropriate authenticated connections/certificate policy, absence of automatic outbound diagnostics/telemetry, permission minimization, and reviewable redacted export without tokens, passwords, private identifiers or media contents (Q39, Q52, Q58).
10. **Accessibility and reliability:** Test readable connection/capability state, usable touch targets and control labels, predictable navigation, failures/recovery, background/foreground changes and interruptions on supported Android versions (Q24, Q27–Q28, Q41–Q42, Q57).
11. **Real-device verification:** On Galaxy S24 FE ↔ Samsung QN90B with firmware `T-PTMDEUC-1720.7`, record separately: third-party discovery, secure TV authorization, command-by-command control, eligible-field keyboard entry, local-media casting, independent screen mirroring, optional Smart View handoff and optional usable Wi-Fi Direct services. Record exact observed phone software/TV regional suffix when known. Neither the reported success of SmartThings nor built-in Smart View constitutes a passed UniRemote test (Q29–Q34, Q53, Q57).
12. **Evidence gate:** A public compatibility claim requires a passing UniRemote test on the named model/relevant firmware. Simulators, vendor API descriptions, open-source clients and Play listings inform candidate behaviors but **do not** substitute for hardware evidence. Recheck then-current Android/Google Play policies and optional Tizen Seller Office requirements before publication (Q53, Q57).
13. **Prior art:** Discovery identifies open-source Samsung remote examples, UPnPCast's HTTP/Range sender, CastVideos-android, ScreenStream and LG Power's fake-TV tooling as **possible testing references**. There is currently no UniRemote application implementation or existing test suite to reuse, and none of those projects is adopted by this spec.

The test-seam sketch above is **proposed for user review** as required by /to-spec; it does not quietly commit the project to a module structure or simulated endpoint protocol.

## Compatibility evidence and staged release gates

A **verified compatibility** claim is a specific pair of (device identity + relevant software/firmware) and a **tested capability**; it is not a badge attached to a whole brand. At minimum, record test date, test-device identification to appropriate non-sensitive granularity, phone OS/version, TV model/firmware, TV prerequisites, commands/fields/media or receiver used, outcomes and reproducible failures. Known baseline: user reports Galaxy S24 FE + Samsung QN90B (2022 Tizen), TV firmware `T-PTMDEUC-1720.7`, same home Wi-Fi, working SmartThings remote and built-in Smart View.

| Capability being claimed | Required evidence before public advertisement | Failure implication |
| --- | --- | --- |
| Samsung third-party remote | TV discovery or reliable manual selection, authorized connection, supported commands checked individually, stored/forgotten credentials, safe reconnection and failure handling on identified firmware | Advertise only the commands actually verified. |
| Samsung third-party keyboard | A repeatable *eligible focused input context* accepts text from UniRemote; record field and app, with unsupported contexts identified | If no usable context works, revisit the launch boundary with the user under Q48; do **not** silently remove keyboard. |
| Media casting | Selected file or direct link actually reaches the named receiver and decodes; remote and playback controls remain correctly targeted; incompatible format behavior is clear | Do not claim universal playback or automatic transcoding. |
| Independent mirroring | On-device capture is authorized and **the chosen TV or receiver actually displays live frames**; assess protected-content, stop state, audio restrictions and receiver availability | Built-in Smart View success or capture-only tests do not justify an independent-mirroring claim. |
| Wi-Fi Direct | Phone and relevant TV establish a usable P2P peer link **and** an appropriate control/media service can actually run over it | Do not list Wi-Fi Direct as functional merely from TV specifications. |
| Other TV platforms | Device/firmware-specific passing evidence **and** a permissible control interface, including vendor policy constraints | Do not infer platform-level compatibility from source examples. |
| Google Play Android app | Platform/target SDK compliance, secure/network behavior, permissions, accessibility, privacy/data-safety and evidence-aligned store description | Do not submit or market unsupported capabilities. |

**Release sequencing:** R1–R9 describe the product direction, **not** a commitment that every R group is in version 1. A reliable subset may ship when verified; the four feature groups must first be assessed, and unsupported/unreleased features must not be advertised as available (Q3/Q25/Q47/Q57). A separate Samsung/Tizen receiver store submission—if ever chosen—has its own approval gate.

**Testing approach requiring user confirmation:** High-level observable device journeys with simulated endpoints plus later authorized physical-device confirmation remain a recommendation from the /to-spec process, *not* an adopted architecture or permission to run a separate prototype. Work on /to-tickets and implementation stays unstarted.

## Out of Scope

For the initial approved product direction, the following are **not automatic requirements or promises**:

- Every TV brand, model, firmware, command, keyboard field, codec, app and audio source working universally, or an unsupported platform being labelled compatible (Q6, Q48, Q53).
- Requiring a UniRemote account, cloud backend or always-on internet for normal supported local-network remote controls (Q26).
- Mandatory TV-side companion installation for basic LAN remote control (Q2, Q56).
- Arbitrary webpage-video scraping, protected/DRM content bypass, authenticated/paywalled media relaying, YouTube/Netflix-specific integrations or unrestricted online stream extraction (Q54–Q55).
- Automatic transcoding or guaranteed playback of receiver-incompatible media (Q19, Q49).
- Claiming that Wi-Fi Direct automatically yields Miracast, TV remote protocol access or working screen mirroring (Q20, Q22, Q51).
- Treating Samsung Smart View guidance as an in-app, independently controlled UniRemote mirroring implementation (Q34).
- Separate exploratory feasibility prototypes that the user declined, or a new standalone test solely to verify the already-confirmed shared Wi-Fi setup (Q36–Q37).
- Selecting a definitive SDK, framework, transport, vendor protocol dependency, UI layout/theme customization model or later monetization strategy without further evidence/decisions (Q28, Q40–Q42; discovery §6).
- Shipping every researched capability simultaneously: incremental release is allowed **with evidence-backed claims** (Q47, Q57).
