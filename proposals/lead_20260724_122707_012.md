**Support the W3C Digital Credentials API to serve OpenID4VP sessions**

*Project description:*
## Goal

Let Yivi serve OpenID4VP presentation requests through the **W3C Digital Credentials API (DC API)**, so a website or app can request credentials via the platform credential chooser and have the OS route the request directly to Yivi — without relying on a custom scheme or universal link.

Today the only ways an OpenID4VP request reaches the wallet are:

- QR scanning (`yivi_core/lib/src/screens/scanner/widgets/qr_scanner.dart`),
- custom schemes `openid4vp://` / `eudi-openid4vp://` / `openid-credential-offer://` (`yivi_app/android/app/src/main/AndroidManifest.xml:57-69`), and
- universal links under `https://open.yivi.app/-/…` (`AndroidManifest.xml:44-49`, added in #545).

All three funnel into `Pointer.fromString` (`yivi_core/lib/src/models/session.dart:33`) — via a `HandleURLEvent` for links/intents (`yivi_core/lib/src/data/irma_repository.dart:225`, fed by native `YiviCorePlugin.java` / `IrmaMobileBridgePlugin.swift`) or `_foundQR` for QR (`yivi_core/lib/src/screens/scanner/widgets/qr_scanner.dart:112`) — producing a `SessionPointer` with `protocol == Protocol.openid4vp`. It is then validated and dispatched to the Go core (irmago) as a `NewSessionEvent` by `handlePointer` (`yivi_core/lib/src/util/handle_pointer.dart:12`). The actual OpenID4VP protocol execution (request fetch, `vp_token` production) lives in irmago; the Dart/native layers only parse the invocation URL and forward it.

The DC API is the direction of travel for cross-device and same-device presentation on the web (`navigator.credentials.get({ digital: … })`) and in native apps. It fixes the well-known problems of custom-scheme routing: any app can claim `openid4vp://`, producing a disambiguation sheet and enabling scheme hijacking. With the DC API the OS owns credential selection and only surfaces wallets that actually hold a matching credential.

## Scope

**In scope**
- Register Yivi as a Digital Credentials provider so it appears in the OS credential selector for OpenID4VP requests.
- Receive a DC API `openid4vp` request from the platform, run it through the existing OpenID4VP session flow, and return the `vp_token` response to the caller via the DC API (rather than an app-to-app redirect / `response_uri`).
- A credential-matcher so the OS only offers Yivi when the wallet holds a credential satisfying the request's `dcql_query`.

**Out of scope (track separately)**
- OpenID4VCI issuance over the DC API.
- Any relying-party / server-side documentation for verifiers.
- Deprecating the existing custom-scheme / universal-link entry points — they stay unchanged.

## Platform work

### Android — Credential Manager

Register as a Digital Credentials provider using Jetpack `androidx.credentials` + the credential-registry library (`androidx.credentials.registry:registry-*`):

- Publish the holdable credentials into the registry so the system matcher (a bundled WASM matcher) can decide whether Yivi satisfies an incoming `dcql_query`. This runs against a locally-registered snapshot of the wallet's credentials.
- Handle the provider entry point (`androidx.credentials.registry.provider` / `GET_CREDENTIAL` intent) in the native Android layer, hand the OpenID4VP request into the Flutter/Go session flow, and marshal the resulting `vp_token` back through `PendingIntentHandler.setGetCredentialResponse`.
- New native code lives alongside `MainActivity` in `yivi_app/android/…`; no new manifest intent-filters for schemes, but a provider `<service>`/registry declaration is needed.

### iOS

Track Apple's Digital Credentials / "Verify with Wallet" identity-document presentation path (iOS 26+ `ASCredentialProviderViewController` + Identity Documents). Same conceptual bridge into the OpenID4VP flow; scope and feasibility to be confirmed — may land in a follow-up.

## Core / Dart integration

The DC API delivers the same OpenID4VP request payload we already understand, so the goal is to converge on the existing pipeline rather than build a parallel one:

- Add a code path that accepts a DC-API-delivered OpenID4VP request and produces a `SessionPointer` (`protocol: Protocol.openid4vp`), reusing `Pointer.fromString`'s validation where possible.
- The response leg differs: instead of the wallet POSTing to a `response_uri` / opening a redirect, the `vp_token` must be returned synchronously to the platform API. Confirm how `irmago`/the Go core returns the OpenID4VP response and whether it can hand the token back to Dart/native instead of transmitting it itself.
- New native → Dart event (sibling to `HandleURLEvent`) carrying the DC API request and a response channel.

## Open questions

- Does the current `irmago` OpenID4VP server support the DC API request/response profile (`dcql_query`, unsigned/signed request objects, `openid4vp-v1` protocol identifiers) and returning the response to the caller rather than a `response_uri`? May need an upstream `irmago` change.
- Credential-matcher format: what does Yivi register so the OS matcher can evaluate `dcql_query` against IRMA/SD-JWT/mdoc credentials?
- Minimum supported OS versions and graceful fallback to the existing schemes on devices without DC API support.
