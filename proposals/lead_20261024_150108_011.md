# Project Proposal — Autocad Drafting

## Project Understanding
You need assistance with: 
**[Ticket]: Check fsp add and fsp upgrade --app on a real app pinned by git, from v0.22.1 to v0.23.0**

*Project description:*
### Type

Spike / Investigation

### Summary

Since 0.23.0 (#291) two commands change an app you already have:
- **`fsp add <feature>`** puts an optional feature of `fsp create` (storage, auth, http, ...) into the app: the pubspec lines, the feature's files, the shared files (`lib/app/startup.dart`, ...), then `flutter pub get`, `dart format`, `fsp gen` and `fsp test`. A shared file you changed is left alone, and the change to make is printed under `By hand:`.
- **`fsp upgrade --app`** moves the `ref:` of fespalier and of every companion package in `pubspec.yaml` to one release, prints the migration notes for the releases in between, then runs `flutter pub get` and `fsp gen`. It never moves an app back unless `--version` asks for it.

The tests cover a lot without the network:
- The plans (`add/plan.rs`, `upgrade_app.rs`) are pure functions with unit tests and golden files.
- The CLI tests run the binary against a stand-in `flutter` script and a made-up git pin.
- A test pins that adding every feature one at a time gives the app `fsp create --features` makes. CI's `create` job (its `add` case) formats, analyzes and tests such an app, but with this repository as the packages (`--local-packages`), not git.

No test has run these on an app pinned by git, with a real `flutter pub get`, across real release tags. This ticket is that check.

Expected result: a report on each case below, per operating system.

### Intent

Make sure a developer can add a feature to a real app, can recover when they have edited the shared files, and can move an app from one release to the next with the real tags, the real packages and the real notes. These are the claims of `docs/cli.md`, "fsp add" and "Moving the app's pins".

- `docs/cli.md`, "fsp add" (https://github.com/fespalier/fespalier/blob/main/docs/cli.md#fsp-add) and "Moving the app's pins" (https://github.com/fespalier/fespalier/blob/main/docs/cli.md#moving-the-apps-pins)

### Current Behavior

Checked by tests only:
- `fsp add`: the plan for each feature, the refusals, the pubspec edit (comments, quotes and order kept), the `By hand` output, and the commands that fail midway, against a stand-in `flutter`.
- `fsp upgrade --app`: the moves, the notes printed for each release, `--check` exit codes, `--json`, the refusal when a pin is newer than the `fsp`.
- `fsp add` of every feature in turn, then `dart format`, `flutter analyze` and `flutter test`, in CI, on a checkout.

Not checked:
- A real `flutter pub get` of an app pinned by git, after `fsp add`.
- An app whose `lib/app/startup.dart` was edited, in a real run.
- `fsp upgrade --app` across real tags (`v0.22.1` to `v0.23.0`), with the real packages and a real `fsp gen`.
- Windows.

### Expected Behavior

- **`fsp add <feature>`.** Prints each change as it writes it (`  edit   pubspec.yaml`, `  new    test/storage_test.dart`, `  update lib/app/startup.dart`), runs `flutter pub get`, `dart format` on the Dart files it wrote, `fsp gen` and `fsp test`, and ends with `✓ added storage`. The app then analyzes and tests clean.
- **A feature the app has already** is a note and nothing more: ``note: `storage` is in the app already``, then `nothing to add`.
- **A shared file you changed** is never overwritten. The change to make is printed as `+` and `-` lines under ``By hand: <file> (...). Make this change:``, before any command runs. Until you make it, the feature is not wired in and its test fails.
- **Refusals** write nothing.
- **`fsp upgrade --app`** moves every `ref:` of this repository's packages in `pubspec.yaml` to the release of the `fsp` that runs. Only the `ref:` values change. It prints the migration notes as soon as `pubspec.yaml` is written, then runs `flutter pub get` and `fsp gen`.
  - `--check` writes nothing and exits **3** when a ref would move, 0 when none would, 1 on an error.
  - `--dry-run` prints the moves and the notes and writes nothing.
  - With an `fsp` older than the app's pins it refuses (exit 1, nothing written), also with `--check` and `--dry-run`.

### Acceptance Criteria

- Tried on at least one of macOS, Linux or Windows, with a real Flutter and a network.
- Each case below is marked pass, fail, or not run, with what the command printed.
- The report lists the OS, the shell, `fsp --version`, `flutter --version` and `dart --version`.

### Out of Scope

- An app that takes fespalier from a checkout (`path:`) or a branch. CI covers the checkout.
- Every feature the cases do not name. CI's `create` job adds each one; try another if you have time.
- `fsp upgrade` without `--app` (it upgrades `fsp` itself).
- Any change to `fsp`.
