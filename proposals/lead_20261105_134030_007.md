## 3. Code findings to revalidate and resolve

### F1: Rest-day fallback

`WorkoutPlan.today()` returns the first plan day when no weekday matches. This can display a workout on an unscheduled day. Distinguish scheduled workout, explicit rest, no session scheduled, no plan, and unavailable/loading plan. Define behavior for multiple sessions in a day. Add regression tests before fixing it.

### F2: Partial Health integration

`HealthKitHealthService` requests steps, asleep sleep, active energy, and weight. `getTodayData()` currently populates steps and active energy but not `sleepHours`; `syncToday()` uploads only steps. The requested type list does not include VO2 max, resting HR, HRV, or workout records. Implement actual data handling before advertising those capabilities.

### F3: Misleading connection state

Authorization completion currently writes a persisted `connected: true`; another path derives connectivity from whether steps exist. A completed permission request is not proof that every read type is accessible. Apple does not expose individual read-denial status in the way this UI implies. Model request history, last successful read, returned-data availability, sync freshness, unsupported platform, and errors separately. Empty results mean no readable data, not necessarily denial. Do not label a permission as denied unless the API actually reports that state for that operation.

### F4: Missing health context in the coach

`buildContext()` includes profile, weight, strength plans/sessions, and nutrition, but not the proposed Apple Health recovery/cardiovascular summaries. Add a minimal, independently consent-filtered context. Never send a complete Health export to the model.

### F5: Output validation

`openai.ts` uses JSON mode (`response_format: { type: 'json_object' }`). Add schema-constrained responses where supported, then independent semantic validation. Preserve the existing propose/apply/dismiss architecture. Check model availability and supported parameters against current documentation/account access; do not assume a hardcoded model identifier is valid. Do not migrate API endpoints merely for novelty if the existing supported endpoint satisfies requirements.

### F6: Aggregation and synchronization risks to investigate

The health adapter directly sums returned step/energy samples and writes a timestamped steps upsert. Inspect source overlap, native aggregate APIs, database uniqueness, and retry behavior before calling it correct or claiming a confirmed duplication bug. Test repeat imports, concurrent retries, deletions, overlapping sources, and daily boundaries. `context.ts` also builds a UTC date for daily food queries; verify user-local-day behavior rather than silently changing nutrition semantics.

## 4. UI/UX specification: first implementation

### Visual system and navigation

Follow existing tokens and `.cursor/rules/apple-ios.mdc`. Current colors include light background `#F6F5F2`, light accent `#0F6E6B`, dark background `#121211`, dark surface `#1C1C1A`, and dark accent `#3AA8A4`. These are reuse starting points, not permission to scatter constants across widgets. Use existing typography, spacing, radius, elevation, and motion abstractions.

Use native-feeling Cupertino navigation and sheets, opaque content cards, restrained transitions, semantic colors, scalable text, VoiceOver labels, and at least 44-point phone interaction targets. Never encode state using color alone. Respect Reduce Motion. Check narrow phone layouts and large text. Watch controls must remain legible and practical during movement.

### Required screens and flows

1. **Home:** today’s session is the primary action; add a plain-language training check, data coverage/freshness, brief supporting factors, and a subjective check-in. Keep existing nutrition/protein summaries. No pseudo-precise readiness ring. Make rest/no-plan/offline states useful.
2. **Health overview/detail:** reachable from Home and Progress, not a new tab. Cards for available sleep, resting HR, HRV, estimated VO2 max, and recent runs. Include source, units, timestamp/window, sample coverage, and unavailable/stale states. Detail views explain what the number represents without diagnosis.
3. **Workout:** preserve strength flows; add running session details and a weekly view. Show interval sequence, total-duration calculation, effort guidance, and watch availability. A Norwegian 4x4 is an optional editable template, not a universal default prescription. Distinguish planned intervals from completed results.
4. **Watch handoff:** preview the planned session and represent unsupported, permission-needed, queued, scheduling-accepted, and failed states accurately. Do not say delivered or started based only on a local write. Verify which acknowledgement states Apple actually exposes before implementation. Do not promise an undocumented deep link or one-tap launch of Apple’s Workout app.
5. **Coach:** insights before conversation; contextual entry points such as reviewing a recent run or explaining a trend. Show “Data used for this answer,” limitations, and structured proposed-change previews. Apply and Dismiss must keep their existing meaning; never imply an unapplied change is saved.
6. **Progress:** retain body-weight history and consistency; add Running, Fitness, and Recovery sections within the screen. Distinguish estimated VO2 max from laboratory measurement and recorded peak HR from true maximum HR.
7. **Profile > Connections & Privacy:** separate device Health access, optional cloud summary sync, and optional third-party AI sharing. Explain recipients, categories, purpose, retention/deletion, and withdrawal. A decorative switch is not a permission implementation.
8. **Watch companion design:** Today, session detail, sync/offline status, and completion/review handoff. Custom live interval/timer screens are a later milestone; label them as future scope, not working MVP functionality.

### State inventory and prototype behavior

Cover populated, empty, loading, error/retry, stale, offline, no readable health data, partially populated health data, unsupported device/platform, AI-sharing off, and watch unavailable. Use a coherent demo scenario across screens, with every fixture view unmistakably marked Demo. Fixtures must not enter real accounts, telemetry, HealthKit writes, or AI requests. Keep demos in a debug/development path and out of ordinary production flows.

Build the clickable prototype in Flutter using provider overrides/repository fakes so the components are reusable. Avoid a separate web prototype that cannot be reused. Retain real existing behavior behind normal routes; gate unfinished additions. Capture light/dark screenshots and navigation notes if the environment supports them. State honestly when rendering or simulator checks cannot run.

## 5. Target technical architecture

```text
Flutter iPhone UI and existing feature repositories
  -> local health-summary repository / provenance and availability models
  -> existing health plugin where it correctly supports the operation
  -> typed Swift bridge (prefer Pigeon when appropriate) for missing capabilities
       -> HealthKit queries and WorkoutKit scheduling
       -> WatchConnectivity for app-owned plan/status exchange when needed

Native SwiftUI watchOS companion
  -> locally cached session and clearly defined synchronization states
  -> WorkoutKit/native Workout app path for the first structured-workout release
  -> later: custom HKWorkoutSession/HKLiveWorkoutBuilder execution

Existing Supabase authenticated services
  -> server-enforced sharing consent and minimized context
  -> deterministic constraints + OpenAI explanation/proposals
  -> semantic validation + explicit Apply/Dismiss + audited application
```

Keep pure domain models testable without HealthKit. Do not create a second competing Health data pipeline or watch-to-cloud upload path without an explicit need. Avoid claiming that background synchronization is immediate or guaranteed.

Recommended model responsibilities (adapt names to repository conventions):

- `HealthMetricSummary`: type, units, value, source/provenance, time window, sample count/coverage, freshness, and availability. Unknown is not zero.
- `TrainingSession`: preserve strength representation and add a typed running/interval representation instead of squeezing intervals into exercise reps.
- `IntervalPlan`: versioned ordered warm-up/work/recovery/cool-down segments, validated durations and total; do not accidentally append an extra recovery after the last work segment unless explicitly planned.
- `TrainingContext`: versioned goals, permitted recent summaries, subjective effort/soreness, coverage/limitations, and identifiers for evidence used. No unnecessary name, GPS, ECG, or unrelated records.
- `CoachProposal`: type, structured proposed diff, supporting evidence IDs, limitations, base plan revision, and approval/application state.

Prefer additive, backwards-compatible schema changes after inspecting migrations. Add an ADR explaining whether new summaries belong in existing `health_metrics` or a purpose-built table. Do not invent duplicate profile, goal, subscription, or workout tables when equivalent concepts already exist.

## 6. Health ingestion and quality requirements

Request only needed types, progressively and read-only unless a specific user-facing write requires authorization. Keep raw samples on-device by default. Persist only necessary derived data locally and exclude sensitive caches from inappropriate cloud backup.

Use appropriate HealthKit aggregate/source-selection semantics rather than blindly summing overlapping phone/watch samples. Sleep processing must account for overnight boundaries, time-zone changes, stages, overlaps, and in-bed versus asleep. Keep HRV measurement type explicit; do not mix incompatible HRV measures. Support incomplete nights and missing watch wear without inventing results.

For incremental imports, evaluate anchored queries including deletions and observer-triggered refresh with an explicit foreground refresh fallback. Store checkpoints only after successful local persistence. Repeated imports and retries must be idempotent. Define a stable key/source ID and recompute affected aggregates after deletion. Show stale data rather than silently treating it as current.

A recorded highest exercise HR is not automatically a calibrated maximum. An isolated sleep/HRV/VO2 estimate must not trigger an aggressive plan increase. Collect perceived exertion, fatigue/soreness, and relevant user limitations. Any training eligibility/progression policy needs a documented, reviewed basis and configurable limits, not an invented universal percentage rule.

## 7. Privacy, security, and coaching safety

- Keep this public issue and all repository artifacts free of real health exports, ECGs, GPS routes, actual personal measurements, health screenshots, credentials, or identifying demo records. Use synthetic fixtures only.
- Separate OS access from app cloud-processing consent and third-party AI consent. Default newly introduced cloud/AI health sharing off. Existing general coach consent must not silently expand to newly imported sensitive categories.
- Enforce consent at the server as well as the UI. For local-only processing, do not upload health payloads merely to have the server discard them. Re-check consent when queued uploads/AI calls execute. Withdrawal cancels pending transfers and stops future sharing; clearly disclose limits on recalling already transmitted data.
- Specify retention, export, deletion, backups, and provider handling. Minimize cached copies and clear user-specific local/watch data on logout/account switch. Account deletion must address account records, summaries, coach messages that contain health content, and pending work, with documented backup expiry.
- OpenAI and privileged Supabase credentials stay server-side. No secrets in Flutter assets, source control, screenshots, or logs. Audit error logging so provider responses cannot leak sensitive prompts/data.
- Require authentication, bounded requests, per-user quotas, cost ceilings, redacted observability, and timeouts/fallbacks. Keep basic dashboards/plans usable when AI is offline.
- Verify RLS/ownership across tables, views, storage, functions, and nested conversation/action IDs. Test with two distinct users plus unauthenticated requests; never authorize using user-editable metadata. Protect both reads and ownership-changing writes.
- Use schema validation plus semantic checks for AI output. Treat user text and imported notes as untrusted data, not instructions. Refuse unsupported action types. Validate plan freshness and use an atomic/idempotent application path so duplicate taps/retries cannot apply a change twice.
- Evidence references must point to actual supplied measurements. Missing data stays missing. Estimates and limitations must be visible. Do not diagnose, claim disease detection, or market readiness/sensor readings as clinical clearance.
- Live interval timing, stop/pause controls, and any defined offline prompts must not depend on GPT or connectivity. Build a reviewed response policy for symptoms or medical questions, without pretending the product monitors emergencies.
- Verify current Apple third-party AI and HealthKit rules and OpenAI processing/retention behavior. Do not equate `store: false` with zero retention. App Store privacy labels/manifests and policies must reflect the actual SDK/data flows.
- Before public release, obtain qualified privacy/regulatory review for intended markets, sensitive-data and cross-border processing, and any medical claims. Do not label the product legally compliant based only on implementation checklists.
