## Problem Statement

Developer tools leave a lot behind on disk: dependency folders, build output, download caches, model caches, old git worktrees and Docker data. On a machine with a few years of projects this easily reaches tens of gigabytes, spread over places nobody remembers.

Getting it back by hand is slow and risky. A developer has to know where each tool keeps its leftovers on each operating system, guess which ones are still in use, and then delete folders with commands that cannot be undone. One wrong path, one symlink that leads somewhere unexpected, or one folder that changed since they last looked, and real work is gone. Existing cleaners either cover one tool, or ask for trust they have not earned: they do not say why something is safe, and they delete permanently.

## Solution

`sweep` is a command-line tool and terminal screen for Windows, Linux and macOS that finds those leftovers and reclaims the space safely.

- `sweep scan` looks beneath the user's Roots and lists every Candidate with its Size, Last used, Kind and the Reason it is safe to reclaim. It changes nothing.
- `sweep clean --dry-run` writes a Plan: the exact list of Candidates one Clean will act on. Every Candidate is shown as picked or not picked, with the reason.
- `sweep clean --plan <file>` carries out exactly that Plan, re-checking every Candidate against the three Safety rules immediately before acting on it.
- `sweep` with no arguments opens an interactive screen to browse, pick, review and confirm, going through the same Plan and re-check.
- Candidates go to the operating system's trash. Delete is opt-in for a single run.

Three Safety rules can never be broken and no setting switches them off:

1. **Git rule**: sweep never touches a file git tracks, or a Worktree with uncommitted changes.
2. **Root rule**: sweep never follows a Link out of a Root and never touches a path outside the Roots.
3. **Fingerprint rule**: a Candidate whose Fingerprint no longer matches the Plan is a Skip.

## Implementation Decisions

Decided

- sweep is one Go module with a single binary named `sweep`, laid out as ADR-0001 describes: a domain that does no IO, adapters behind ports the domain features declare, a report package and an interactive screen that depend only on the domain, and a composition root that wires them by hand.
- The domain features are scan, plan, safety, clean and ecosystems. Only the trash adapter removes anything from disk, with one implementation per operating system.
- A Candidate is always a path, and always taken as a whole. A Scan does not descend into a Candidate.
- Roots come from the command line first, then configuration, then the current directory. A Scan also adds each known Shared cache as a Root of its own (ADR-0002), unless `shared-caches` is off or `--no-shared-caches` is given. Added Roots are shown in the output and written in the Plan. A location outside the home directory is never added.
- Each Ecosystem carries its Rules, and its Shared cache locations per operating system. Every Rule names one Kind from the fixed list (Dependencies, Build output, Cache, Models, Worktree) and carries a Reason. A Rule decides how finely a Shared cache is split into Candidates.
- How Rules are written (data files embedded in the binary, or one source file per Ecosystem plus a registry) is settled by a prototype and recorded in its own ADR. The judgement is how cleanly twenty changes could each add one Ecosystem without touching the same file.
- Last used is the newest modification among a Project's own files outside its Candidates. A Candidate with no Project takes the newest modification inside it. Access times are not used.
- Size is the disk space a Candidate occupies on its own, with each hard-linked file counted once.
- A Candidate is Stale when its Last used is older than the threshold, 30 days unless configured. Staleness decides the default Pick and never what a Scan finds.
- The default Pick is every Stale Candidate beneath the Roots the user gave. A Shared cache is never picked unless the user picks it. Every Candidate is reported as picked or not picked, with the reason.
- A Worktree is a Candidate only when it is a linked worktree, nothing in it is uncommitted or untracked, and its commits exist on a branch or remote. It is trashed like any other Candidate; sweep does not ask git to remove it.
- Docker data is reported by a Scan with its size and is never part of a Plan. The Docker adapter only reads.
- A Plan is a file listing the exact Candidates one Clean will act on, each with its Fingerprint, plus the Roots it was made from. A Clean acts on nothing that is not in the Plan.
- Immediately before acting on a Candidate, a Clean re-checks all three Safety rules. A Candidate that fails one is a Skip, reported with that rule, and nothing in it is touched.
- Trash is the default. Delete is chosen per run and cannot be made the default by configuration. A Candidate that cannot be trashed is reported as a failure and left in place; sweep never falls back to Delete.
- Trashed space is reported as moved to trash, never as reclaimed. sweep never empties the trash.
- Configuration holds exactly four things: default Roots, the Stale threshold, the Ignore list and the `shared-caches` switch. It cannot switch off a Safety rule.
- The interactive screen builds a Plan from the user's ticks and runs it through the same Clean as the command line. It has no removal path of its own.
- One script is the gate, and continuous integration runs exactly that script on Linux, Windows and macOS. The gate includes lint rules that fail when the domain imports anything outside the standard library and itself, and when a file removal call appears outside the trash adapter.
- The first Ecosystem built end to end is Node dependencies (`node_modules`), as the thin slice that proves scan, plan, clean, report and the Fixture together.
- The Ecosystems v1 aims to cover, each added as its own change once the first slice holds:
  - JavaScript: `node_modules`, the pnpm store, npm, yarn and bun caches, Next, Nuxt and Vite output.
  - Rust and Go: `target/`, the cargo registry, Go build and module caches.
  - Python: `.venv`, `__pycache__`, `.tox`, `.mypy_cache`, pip and uv caches.
  - JVM and .NET: `.gradle`, `~/.m2`, `bin/` and `obj/`, the NuGet cache.
  - Native and games: CMake build directories, Unity `Library/`, Bazel output.
  - Platform: Xcode DerivedData and simulators on macOS, Android build output and emulators.
  - Others: Hugging Face and Ollama model caches, `.terraform`, git Worktrees, and Docker data as report only.

Proposed defaults, to confirm or change when the work reaches them

- **Fingerprint contents**: the Candidate's identity on disk (so a folder replaced by another at the same path is detected), plus its entry count, total size and newest modification. A formal check of the Fingerprint rule is expected to show whether a gap remains between the re-check and the removal; its counterexample decides the final design.
- **Plan lifetime**: a Plan does not expire and is not tied to a machine by name. The Fingerprint rule already makes an old or foreign Plan skip everything that no longer matches.
- **Plan format**: JSON with a version field, so later versions can refuse or migrate an old Plan.
- **Other filesystems beneath a Root**: a Scan does not cross into another mounted filesystem unless it is given as a Root, and says where it stopped.
- **Configuration file**: TOML, in the operating system's standard per-user configuration directory.
- **Command line**: the standard library's flag handling, with subcommands. Revisit only if it becomes awkward.
- **Interactive screen**: an established Go terminal UI library, chosen when that work starts.
- **Exit codes**: zero when everything in the Plan was acted on, a distinct non-zero code when there were Skips or failures, another for usage errors.
- **Git rule at Scan time**: a path that a Rule matches but that holds git-tracked files is not a Candidate. The Clean re-checks this.

## Testing Decisions

A good test here checks what a user or a script can observe: what a Scan reports, what a Plan contains, and what is on disk after a Clean. It does not assert on internal types or call order. Expected values come from an independent source: `du` for Size, `git status` for the Git rule, and a file listing before and after for what survived. They never come from sweep's own output.

Seams, from highest to lowest:

1. **The binary against the Fixture.** The fixture tool builds a fake developer machine with known Candidates and Traps, and an answer key. Tests run the real `sweep` binary on it and compare `scan --json` with the answer key, Sizes with `du`, and the directory tree after a Clean with the expected survivors. Every Trap must still be there. This is the main seam, and it runs on all three operating systems. Scan, Plan, Clean, configuration, Pick and reporting are tested here.
2. **Domain features through their ports, with fakes.** Used only for what the first seam cannot force: a change that lands between the re-check and the removal, a trash that fails halfway, and path handling for the Root rule, which is also fuzzed (drive letters, `..` segments, UNC paths, very long paths).
3. **Port contract suites.** Each real adapter (files, git, trash per operating system) and its fake pass the same suite, so tests at the second seam can be trusted.
4. **The interactive screen at its own boundary.** Keys go in and rendered text comes out. The Plan it produces is then exercised through the first seam's path.

Traps the Fixture must contain at least: a leftover-looking folder that holds git-tracked files; a Worktree with uncommitted changes; a Link inside a Root that leads outside it; a leftover-looking folder outside every Root; and a Candidate that is changed between the Plan and the Clean.

The Fingerprint rule also gets a formal check: a model of plan-then-clean in which the property is shown to fail on a deliberately broken variant, and which is re-run when the clean feature changes.

There is no prior art in this repository yet. The first slice sets the pattern the later Ecosystems copy: one Fixture entry, one answer-key entry, and evidence that the scan output matches.

## Out of Scope

- Removing Docker data. v1 reports it only.
- Emptying the trash, or reporting on what is already in it.
- A mode that reports large folders no Rule recognises.
- Per-project settings files.
- Scheduling, background running or automatic cleaning.
- A graphical interface.
- Packaging for package managers and signed releases.
- Leftovers that are not developer leftovers: downloads, media, system caches.

## Further Notes

- Until trash by default works on all three operating systems and the formal check of the Fingerprint rule passes, a Clean is only ever run against the Fixture, never against a real directory.
- Scan speed is measured against `du` on a large Fixture once the first Ecosystems hold. No budget is set in v1.
- The glossary is the source for every term used here; a new concept is added there before code is named after it.
