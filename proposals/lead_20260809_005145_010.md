## Goal

Extend `/verify-closure <issue-number>` with a fail-closed, idempotent second invocation that recognizes explicit PO product confirmation and closes only the freshly revalidated Feature or Epic.

## User Story / Problem Statement

As the product owner, I want one brief GitHub confirmation to authorize a previously verified Feature or Epic to close, so that closure is consistent and auditable without asking me to repeat technical evidence or allowing an agent to make the product judgment.

## Business Value

- Completes the two-stage closure protocol without weakening the PO approval gate.
- Replaces error-prone manual closure with deterministic target, evidence, and freshness checks.
- Leaves durable evidence that explains who approved what, against which verified revision, and whether closure succeeded.
- Makes retries safe after partial GitHub API failures.

## Why

Story #232 owns read-only technical verification and the authoritative technical delivery summary. Without a separately gated continuation, the final state transition remains manual and inconsistent. This story adds only the approval-sensitive mutation phase and preserves the existing split between Codex technical verification and PO product judgment.

## Scope

- Extend the same `/verify-closure <issue-number>` command with a second-invocation continuation; do not introduce a separate close command.
- Find the latest authoritative, successful technical delivery summary created by the first phase and bind it to the repository, target number and type, and verified `main` SHA.
- Accept only an unambiguous confirmation comment authored by the repository PO, newer than that summary, and naming the same target and type.
- Immediately before closing, refresh repository identity, target number and type, open/closed state, latest authoritative summary, confirmation comment, current `main` SHA, and Feature/Epic-specific gates.
- Fail closed when evidence is missing, ambiguous, stale, mismatched, or cannot be refreshed.
- Close only the verified target, then post one formal closing-evidence comment. If close succeeds but posting evidence fails, a retry repairs the missing evidence without attempting another close.
- Exit cleanly on repeated invocations without duplicating the authoritative technical summary or formal closing evidence.
- Add deterministic command-contract and mutation-safety tests and update closure documentation.

## Out of Scope

- Re-running, weakening, or redefining the technical verification owned by #232.
- Making a product decision or posting confirmation on behalf of the PO.
- Inferring approval from reactions, edits to the issue body, Slack, chat, or any other out-of-band signal.
- Accepting generic approval text that does not identify the target type and number.
- Closing child stories, child Features, or any resource other than the command target.
- Changing story-level `/review`, `/merge`, or `/cleanup` behavior.
- Adding a compiled CLI, JSON mode, or new GitHub Project status.

## Command Surface

- First invocation (owned by #232): `/verify-closure <issue-number>` performs read-only technical verification and posts the authoritative technical delivery summary.
- PO response on the target issue:
  - Feature: `Product confirmed for Feature #<issue-number>.`
  - Epic: `Product approved for Epic #<issue-number>.`
- Second invocation: `/verify-closure <issue-number>` detects the fresh summary and valid PO response, revalidates mutation-sensitive state, and continues to closure.
- Input remains exactly one positive GitHub issue number; repository identity remains fixed to `LauraMardones/headless-pr-workflow` by the workflow contract.
- This is an assistant workflow command, not an `hpw` executable command. Process exit codes and CLI flags do not apply.

## Output Contract

GitHub evidence includes:

- The existing authoritative technical delivery summary from phase one, including its stable marker, target, type, and verified SHA as defined by #232.
- One formal closing-evidence comment after a successful close, with a stable marker that supports idempotent lookup.
- The issue's closed state.

Human-readable output includes:

- verified repository, target number and type;
- summary and confirmation evidence used;
- refreshed SHA and Feature/Epic gate result;
- close result and closing-comment result;
- blockers and the exact next action when closure does not occur;
- explicit no-op or repair result for an already-closed target.

No JSON output is required because `/verify-closure` is a Markdown assistant workflow command rather than a programmatic CLI.

## Decisions

### Continuation command shape — 2026-08-09
**Chosen:** Reinvoke `/verify-closure <issue-number>` — one command can recognize its prior authoritative summary and continue without adding another workflow surface.
**Rejected:** Add a separate close command — this would split one evidence chain across commands and duplicate target and freshness checks.

### PO confirmation wording — 2026-08-09
**Chosen:** Require one exact, target-specific sentence for each type — it is brief for the PO and deterministic for safe automation.
**Rejected:** Infer approval from free-form comments or reactions — those signals can be ambiguous, refer to another target, or change meaning out of band.

### SHA freshness — 2026-08-09
**Chosen:** Require current `main` to match the SHA in the technical summary — approval remains bound to exactly the evidence the PO reviewed.
**Rejected:** Close against a newer SHA without re-verification — unrelated-looking changes could invalidate evidence and would weaken the technical gate.

### Partial-failure ordering — 2026-08-09
**Chosen:** Close first, then post the formal result comment, with retry repair if commenting fails — the comment can truthfully record the close result and retries remain idempotent.
**Rejected:** Post a success comment before closing — it could claim a result that a later failed close mutation did not achieve.
