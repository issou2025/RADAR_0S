# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Pure-Rust replacement for the opt-in mimalloc allocator on the STEP read path**

*Project description:*
### What

Find a pure-Rust way to get the read-path speedup that `mimalloc` gives, so the bindings don't need a C allocator to be fast.

Reading STEP allocates once per attribute value. With glibc malloc, allocation and freeing are a large share of the parse. Swapping the global allocator to `mimalloc` (a C library, built through `libmimalloc-sys` and `cc`) cuts that cost substantially, but it breaks the repository's "pure Rust, no C++ in the dependency graph" rule. It also does not build for `wasm32-unknown-unknown`, and it keeps more memory resident.

`mimalloc` is now an **opt-in** cargo feature (`mimalloc`, off by default) on `openbim-ifc-py` and `openbim-ifc-capi` only. This issue is about replacing it with a Rust solution, or making it unnecessary.

### Evidence (measured 2026-09-24, openbim-step 0.7.0, ifc `5b78283`)

The IFC model read (`from_step_bytes`) on seven real IFC files, 18-109 MB. User-space instructions and cycles come from `perf stat`, taking the min of 5 runs on a shared 20-core VM.

```
file                        glibc cycles  mimalloc cycles   change   resident glibc -> mimalloc
arc_boe_archicad (76 MB)       20.71 G        14.53 G       -30%        356 ->  390 MB
arc_sfw_archicad              28.45 G        18.28 G       -36%        400 ->  445 MB
big100_synthetic (105 MB)     37.08 G        27.60 G       -26%        621 ->  704 MB
signs_ifc4x3 (38 MB)           7.18 G         5.52 G       -23%        193 ->  228 MB
tga_boe_ifc4_nova (18 MB)      5.92 G         4.28 G       -28%        138 ->  177 MB
tga_sfw_ifc4_nova (60 MB)     25.38 G        16.69 G       -34%        338 ->  436 MB
twp_sfw_ifc2x3_revit (109 MB) 34.16 G        23.04 G       -33%        501 ->  550 MB
```

- Instructions drop only 13-16%, but cycles drop 23-36%. The gain is mostly fewer allocator stalls, not less work.
- Resident memory after the read rises 2-28% on 5 of 7 files, because mimalloc keeps freed memory in its arenas.
- The multi-threaded `parse_parallel_with` (openbim-step 0.7.0) also scales better with mimalloc: at 16 threads it reaches 600-1000 MB/s against 450-700 MB/s with glibc. That points to glibc arena contention.

Harness: the `mb` model benchmark and `abstat.sh` from the openbim-step parse-limits investigation (openbimrs/step 0.7.0 release notes).

### Candidates to evaluate

1. **Allocate less instead of allocating faster.** Intern repeated strings (type names, enums, GUID-free text), use small-string storage for short values, and put a record's attribute `Vec`s in a per-model bump arena (`bumpalo`, pure Rust). This fixes the cause, and every host benefits, WASM included.
2. **Pure-Rust global allocators.** Examples: `rpmalloc-rs`-style ports and `talc`. Check maturity, thread scaling, fragmentation, and whether they build for wasm32. They must beat glibc on this workload to be worth anything.
3. **Arena per parse inside `ifc-model`.** Values live exactly as long as the model, so one arena drop replaces millions of frees. This needs a lifetime or ownership design that doesn't leak into the public API.
4. **Do nothing.** Document the opt-in feature as the answer for native hosts.

### Definition of done

- [ ] Every candidate is measured on the same seven files with the same harness: cycles, instructions, and resident memory against glibc and mimalloc.
- [ ] A written recommendation (an ADR if it changes a storage type), with the chosen change landed and the full gate green, or a documented "do nothing".
- [ ] If a pure-Rust option matches mimalloc within 10% on cycles without costing more memory, remove the `mimalloc` feature.
