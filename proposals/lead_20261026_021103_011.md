# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**The toolset: instance code, web, MCP, routine grants and a hub browser**

*Project description:*
Spec from [The toolset: what an instance can do, and how it gains more](https://github.com/jorgesolerrr/kinby/issues/161), the last spec of [kinby v1](https://github.com/jorgesolerrr/kinby/issues/516). ## Problem Statement

kinby can read and write files and run bash in its workspace, and it can change its own routines, skills and views. It cannot do much in the world outside that workspace. It can't search the web or read a page except by curling through bash, which asks every time. It can't use the MCP servers the rest of the ecosystem ships. It can't drive a website, so autonomous jobs like "check my job applications on LinkedIn every morning" are out of reach, and signed-in sites even more so. And it can't keep code of its own: a script it writes lives in a repository it doesn't own, any package it installs is lost when the container is recreated, and it can't turn a useful script into a tool, because a tool declares its own write flag and the gate would trust it.

## Solution

Every instance gets a base toolset for acting in the world, and governed ways to grow it.

- **Instance code.** Each instance keeps a Python project of its own that survives updates. The agent writes scripts there, installs packages, runs them, and can expose a function as an **authored tool**. The gate treats every call to an authored tool as a write until Jorge marks it read-only.
- **Web search and web fetch** are default tools. Search goes only to the backend Jorge chose (Brave by default). Fetch turns a page into Markdown, refuses private addresses, and asks only when the model built the URL itself.
- **MCP servers** come from the hub library. Jorge or Kinby adds one, an instance picks it, and every call to its tools is a write until Jorge trusts the server's read-only hints.
- **Routine grants** let a routine run a gated tool unattended once Jorge allows it there. Any edit to the routine revokes the grant.
- **A browser.** One browser service on the hub gives each turn a fresh browser. Signed-in **browser profiles** and a **vault** of site-bound credentials stay with the service and never enter the instance. When the agent meets a sign-in or a CAPTCHA it can't pass, it asks for a **takeover**, and Jorge drives the browser from the web app until it can continue.

Instance code and authored tools

## Implementation Decisions

Instance code and authored tools ([ADR 0109](https://github.com/jorgesolerrr/kinby/blob/main/docs/adr/0109-an-authored-tool-is-a-write-until-the-user-trusts-it.md))

- Each instance gets an instance-code directory: a `uv` project with a `pyproject.toml`, a lockfile and a venv. The image already has `uv`. The container entrypoint syncs the venv from the lockfile on start, so a recreated container gets back what the agent installed.
- Five new instance tools join `instance_tools(instance)`: `code_write(path, content)` and `code_delete(path)` take whole files under the instance-code directory and refuse paths outside it; `code_add_package(name)` runs `uv add`; `code_run(script, args)` runs a script with the venv's Python; `code_expose_tool(name)` registers an authored tool. All are write tools under the ordinary gate (ADR 0028). The writes go through the config change recorder as the routine and skill tools do.
- `code_run` reuses the shell tool's timeout and output cap. It builds the child environment from the container's, drops variables whose names match secret patterns (KEY, TOKEN, SECRET, PASSWORD, CREDENTIAL), and passes back the ones the project lists under a kinby table in its `pyproject.toml`.
- `code_expose_tool` validates in two stages: parse the module, then import it in a child process with the venv's Python and check that the named function has the tool shape the registry expects. Only then does it add the name to the project's list of exposed tools.
- The tool registry gains a third source beside `tools/*.py` and entry points: exposed functions in instance code, loaded at turn start in the venv's interpreter context. Their names are prefixed or checked against core names (ADR 0012) so an authored tool can't shadow a core or default tool. A failed load keeps the last valid set and shows a warning, as today.
- The gate gains one rule: a call to an authored tool is a write unless the instance's trust record marks it read-only. The trust record is an instance config file the agent's tools never write. Marking and unmarking go through a new contract method the web app and the approval card use, recorded as a config change made by the user.
- `code_delete` of an exposed tool's module and re-exposing a name check the config change history: the agent may only touch tools it exposed itself.
- A routine's code step may name an authored tool; the gate treats it the same way.

Web search and fetch ([ADR 0110](https://github.com/jorgesolerrr/kinby/blob/main/docs/adr/0110-web-reads-ask-only-for-a-url-the-model-built.md))

- Two new default tools, both read tools, in the defaults package beside files and shell: `web_search(query, count, domains)` and `web_fetch(url)`. The manifest can disable either, like the other defaults.
- Search backends sit behind one small Protocol, one module each for Brave, Tavily, Exa and SearXNG. The instance's config names the backend, Brave by default. The key's variable name is fixed per backend and filled from a hub secret. Without the key the tool is not offered and the instance reports pending setup for search. Results come back as title, URL and snippet.
- Fetch uses httpx and trafilatura, returns Markdown under a character cap, and states when the page looks JavaScript-only. A guard resolves every host, including on each redirect, and refuses loopback, private, link-local and unspecified addresses; it refuses URLs with userinfo. Output is wrapped in untrusted-content markers. The same marker helper wraps browser snapshot and text output.
- The gate gains the seen-URL rule for `web_fetch` and `browser_open`: the call is allowed when its URL appears in the thread's text so far (user messages, the routine prompt, tool results); otherwise it gets the ordinary write verdict for the mode. The turn keeps a set of seen URLs, extracted as messages and tool results arrive.

MCP servers ([ADR 0111](https://github.com/jorgesolerrr/kinby/blob/main/docs/adr/0111-mcp-servers-are-a-library-kind-whose-calls-are-writes.md))

- The hub library gains an MCP server kind. Its definition is a small file: a name, a transport (`url` with optional header variable names, or a `uvx` package and arguments), declared env variable names, and an include filter on tool names. Library validation refuses dangerous env keys and any transport other than these two.
- Picks gain the kind: an instance's `skills-lock.json` (or its successor for picks) records MCP server picks as pinned copies, and the existing library update and instance update flows carry them. Each pick holds a "trust read-only hints" flag the user sets, recorded as a config change.
- Adding to the library and picking go through the existing web app flows and through the home instance's hub tools (`library_*` and `instance_picks_set`), which ask in every mode.
- The instance connects to its picked servers with the Python MCP SDK at turn start (stdio servers started on first use and kept for the turn's life, or longer if cheap), and adapts each included tool into a kinby tool named `<server>__<tool>`. The adapter's write flag is true unless the pick trusts hints and the tool declares `readOnlyHint`.
- A server that fails to start or list tools leaves its tools out of that turn and raises an instance notice.

Routine grants ([ADR 0112](https://github.com/jorgesolerrr/kinby/blob/main/docs/adr/0112-any-edit-to-a-routine-revokes-its-grants.md))

- Grants are kept per instance in a store keyed by routine name and tool name, with when and from which approval. Any routine write, enable change, rename or delete clears that routine's grants, whether a client or an instance tool made it.
- The approval contract gains an "always allow in this routine" answer, offered only on approvals raised in a routine's turn. Channels offer it as an option too.
- The gate checks grants before the mode's verdict on a routine's turn, and never above the ceiling. Grants are listed and revoked through new contract methods the web app uses, under the routine's page.

Browser ([ADR 0113](https://github.com/jorgesolerrr/kinby/blob/main/docs/adr/0113-the-browser-is-a-hub-service-and-sign-ins-never-enter-the-instance.md))

- The hub runs a browser service container: Playwright's browser server on the headless shell, built from the kinby image or a small sibling, on its own Docker network with internet access and no route to the hub's or instances' networks. A filtering proxy or the service's own request interception refuses private addresses. The hub starts it on the first request and stops it after an idle period. It caps concurrent browser contexts (3 by default, configurable on the hub).
- The hub gains a browser route, reached the way intake is (ADR 0077): the instance presents its control token and asks for a browser for one turn. The hub returns a connect address and a short-lived token bound to that instance and turn. Profiles, the vault and takeovers are all keyed by the instance the token names.
- The instance side has one `BrowserService` Protocol (open a context with an optional profile, run one action, snapshot, fill a credential, request a takeover, close and save) and the browser tools built on it. The real implementation talks to the hub's route and the remote Playwright server; tests use a fake.
- Tools: reads `browser_snapshot(interactive, max_chars)`, `browser_text(ref)`, `browser_screenshot()`, `browser_scroll`, `browser_wait`; writes `browser_click(ref)`, `browser_type(ref, text)`, `browser_select(ref, value)`, `browser_press(key)`, `browser_upload(ref, path)`, `browser_fill_credential(ref, name, field)`, `browser_takeover(reason)`; and `browser_open(url, profile)` under the seen-URL rule. Snapshots use the accessibility tree with stable element refs; a ref that matches more than one element, or whose target is covered, fails with a reason. `browser_type` refuses password fields. Downloads are saved to the workspace's `downloads/`; uploads take workspace paths only.
- The context lives for the turn: opened on the first browser call, closed when the turn ends, and its storage state saved back to the profile it opened with. Profiles are stored by the browser service, per instance, as Playwright storage state, on a volume the instances never mount.
- The vault is a hub store, per instance, of entries holding a name, a site (origin), a username, a password and an optional TOTP seed, encrypted at rest with a hub key. `browser_fill_credential` sends the entry name and field to the service, which checks the page's origin against the entry's and fills it inside the page; the value never crosses to the instance. Hub contract methods let the web app add, edit and delete entries and list their names and sites; the home instance can only list.
- A takeover parks the turn as an approval does, with a new "takeover" kind of pending item that the sidebar, the needs-you list and channels show. The web app gets a takeover page that shows a CDP screencast the hub relays over its WebSocket and sends mouse and keyboard input back. Finishing (with "save as profile" and a name) resumes the turn; a deadline ends an abandoned takeover. The instance page can start a takeover with no turn, only to create a profile.
- The manifest gains `browser = true|false`, default false; only browser-on instances get the tools and the route.

Contracts and the web app

- New contract methods for: trust marks on authored tools, routine grants (list, revoke), vault entries (list, add, edit, delete), profiles (list, rename, delete), takeovers (start, input, finish), and the instance's toolset summary. Approval answers gain "always allow in this routine". Events gain the takeover pending item.
- The web app gains an instance "Toolset" section (default tools, search backend and its setup state, picked MCP servers with their trust flag, authored tools with their read-only marks, browser on or off), a vault and profiles section, a grants list under each routine, and the takeover page. All UI is built from shadcn components already in the registry.

## Testing Decisions

Good tests here go through the seams below and assert what a user or the model sees: gate verdicts, approvals, events in the thread, results returned to the model, and files left in the instance or the hub. They never assert on internal calls.

- **The turn seam (existing).** A turn driven by the scripted model, as in the gate, views and instance tools tests. Covered here:
  - instance code tools: writes recorded as config changes, paths outside the directory refused, `code_run` limits and env stripping, expose validation, the registry loading an authored tool next turn and keeping the last valid set when one breaks, the forced write and the read-only mark, deleting only the agent's own tools, an authored tool as a code step
  - web tools with HTTP faked at the httpx transport: each search backend's request and result shape, no tool without a key, the private-address and redirect guard, refused userinfo, untrusted markers, the seen-URL rule allowing a URL from a search result and asking for a built one
  - MCP tools against a small test MCP server written with the Python MCP SDK and started over stdio: tools named by server, the include filter, every call a write, trusted hints, declared env only, a failing server leaving the turn running with a notice
  - routine grants: allowed in their routine, revoked by any edit, not applied to a user's turn, never above the ceiling
  - browser tools against a fake `BrowserService`: reads allowed and writes asked, the seen-URL rule on `browser_open`, password fields refused, a fill only on a matching site, a takeover parking the turn and resuming it, a full cap failing with a clear error
- **The hub contract seam (existing).** Hub methods through a hub client, as in the home writes, secrets and library tests: the MCP server kind in the library and in picks, refused env keys, the home instance's hub tools asking for it; vault entries stored encrypted, listed without values, refused to the home instance for writes; profiles listed, renamed and deleted; the browser route issuing tokens bound to one instance and turn and refusing another instance's; routine grant listing and revoking; the takeover relay passing input and finishing.
- **The browser service adapter (new).** The real `BrowserService` implementation against a local test page served inside the check image, with Playwright's headless shell added to `docker/check.Dockerfile`: snapshots with refs and the cap, an ambiguous ref failing, typing refused in a password field, a vault fill on the matching origin and refused on another, profile state saved and loaded across two contexts, and a private address refused. These tests carry a marker so they run where the browser is installed, which `bun run check:linux` guarantees.
- Prior art: `tests/test_gate.py` (the scripted model and turn runner), `tests/test_instance_tools.py` (config changes), `tests/test_views.py` (new core tools and their contract), `tests/test_hub_home_writes.py` and `tests/test_hub_secrets.py` (hub contract and secrets), `tests/test_hub_library.py` (library kinds), `tests/test_notify.py` (an allow rule and channels).

## Out of Scope

- Image generation, file conversion and sub-agents.
- Provider-native search and fetch (Anthropic's or OpenAI's server tools).
- A domain allowlist or egress policy per instance.
- `npx` MCP servers and Node in the image.
- The home instance writing, exposing or running another instance's code; sharing authored tools through the library.
- Payment cards in the vault, and any purchase or payment flow.
- A password manager integration beyond the vault.
- Taking over the browser from a phone through a channel; the live view needs the web app.
- browser-use, Stagehand or agent-browser as the engine, a tool that runs page JavaScript, and a batch tool.
