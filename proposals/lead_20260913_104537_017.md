### `repo-fix-harness-excludes-bats` — Automated fix harness ./test.sh never runs the bats suites it is meant to verify

**Category:** `follow_up_issues` · **Band:** `defer`

**Triage:** impact `meta-harness` / `material` · trigger `common` · scope `limited` · reversibility `easy` · cost `moderate` · confidence `high` · guard `true`

**Uncertainty:** Whether maintainers intend `./test.sh` to stay bats-free (keeping it dependency-light) and instead want a second allowlisted harness is not recorded in ADR-030 or docs/decisions; the correct remedy (extend test.sh vs. add a harness entry) needs a maintainer decision.

**Verification capability:** environment `isolated-worktree` · harness `repository-test-suite`

## What is wrong

`scripts/workflows/lib/verification_capability.py:7-12` allowlists exactly one automated-fix harness:

```python
SUPPORTED_HARNESSES = {
    "repository-test-suite": {
        "environment": "isolated-worktree",
        "command": "./test.sh",
    }
}
```

and the fix runners default to the same command (`scripts/workflows/lib/run-opencode-fix.sh:16`, `scripts/workflows/lib/run-cursor-fix.sh:14`, `scripts/workflows/lib/run-fix-provider-cascade.sh:7`).

But `test.sh` never invokes `bats`. It sources only `scripts/checks/[0-9][0-9][0-9]-*.sh` (`test.sh:52-83`), and `scripts/checks/055-script-syntax.sh:27-29` explicitly states that `scripts/tests/*.bats` is excluded and "should be exercised via `bats`". The bats suites run only in CI, as a separate step (`.github/workflows/ci-tests.yml:121-128`).

## Why it matters

ADR-030 (`docs/decisions/adr-030-non-blocking-review-pipeline.md:215-224`) says the controller "replaces execution fields with immutable baseline/candidate exit codes" from the allowlisted harness and that this is the outcome evidence for an automated fix. For any defect whose regression test is a bats test — which is where essentially all behavioral coverage in this repository lives (`scripts/tests/` contains the mcp-prewarm, codespace-post-start, finding-priority, and provider suites) — the baseline and candidate `./test.sh` runs both exit zero regardless of whether the fix works or the regression test was written at all. The harness therefore certifies exit codes that are structurally incapable of failing for the class of defect being fixed. That is the "outcome theater" pattern AGENTS.md §Reviews and AP4 exist to reject, sitting inside the mechanism meant to prevent it.

Secondary effect: weekly/daily findings are pushed toward `verification_capability.environment: isolated-worktree` because it is the only band that reaches automated implementation, so a finding gets a real-looking harness receipt that proves nothing.

## Suggested fix

Pick one and record it:

1. Have `test.sh` run `bats scripts/tests/` when `bats` is on `PATH` (and `warn`/`fail` explicitly when it is not), matching the existing conditional pattern in `.github/workflows/ci-tests.yml:121-128`. This keeps one harness identity.
2. Or add a second allowlisted harness entry (e.g. `repository-bats-suite` → `bats scripts/tests/`) to `SUPPORTED_HARNESSES` and let findings select it, with the review prompts updated to describe both.

Either way, add a regression test asserting that a deliberately failing bats test makes the harness command non-zero.

### `repo-codespace-post-start-swallows-prewarm-output` — codespace-post-start discards MCP prewarm output, leaving an undiagnosable warning

**Category:** `follow_up_issues` · **Band:** `should-fix`

**Triage:** impact `dx-perf-doc` / `bounded` · trigger `common` · scope `limited` · reversibility `easy` · cost `trivial` · confidence `high` · guard `true`

**Uncertainty:** The volume and content of `open-design-mcp.sh --daemon-only` output on failure is not verified here, so a fix should re-emit only `mcp-prewarm:`-prefixed lines (as post-create already does) rather than all output, to avoid leaking unredacted daemon logs into the startup transcript.

**Verification capability:** environment `isolated-worktree` · harness `repository-test-suite`

## What is wrong

`scripts/codespace-post-start.sh:37-45` runs the readiness check with all output discarded:

```bash
if "$PREWARM" --readiness-only >/dev/null 2>&1; then
  log_info "Open Design readiness check completed."
else
  log_warn "MCP readiness check failed; OpenCode startup may require a retry."
fi
```

`scripts/mcp-prewarm.sh` writes a specific, machine-prefixed reason to stderr in every failure path — `Open Design readiness failed; launcher is missing or not executable: <path>` (line 171) and `Open Design readiness failed exit=%s elapsed=%ss; bridge was not started` (line 192). All of it is thrown away, so the user sees a warning that names neither the failing server nor the exit code.

The sibling hook already does this correctly: `scripts/codespace-post-create.sh:21-31` captures output and re-emits only `mcp-prewarm:`-prefixed lines to stderr on failure. The two hooks handle the identical failure differently.

## Why it matters

This is the interactive path — post-start fires on every container start/resume, whereas post-create fires once. Commit 9fa3f87 ("Add MCP startup diagnostics") and commit 4b578bc ("prewarm local MCP runtimes for Codespaces") exist so a maintainer can tell *why* MCP startup is degraded; the post-start hook defeats that for the most frequent trigger. It also reads as an AGENTS.md H8 violation: the failure is logged without enough detail to diagnose. A maintainer whose Open Design daemon is unhealthy must manually re-run `./scripts/mcp-prewarm.sh --readiness-only` to learn anything.

The existing test does not protect against this — `scripts/tests/codespace-post-start.bats:25-29` only greps the script for the literal string `MCP readiness check failed`, and stubs the prewarm command to `/bin/true` (line 12), so no test ever exercises the failure branch.

## Suggested fix

Mirror `codespace-post-create.sh:21-31`: capture `"$PREWARM" --readiness-only` output, and on non-zero exit re-emit lines matching `mcp-prewarm:*` through `log_warn` before the existing summary warning. Keep the hook non-fatal (`exit 0`). Add a bats case that stubs `CODESPACE_POST_START_PREWARM` with a script printing a `mcp-prewarm:`-prefixed reason and exiting non-zero, and assert the reason appears in the output.

**Evidence:**

- [`scripts/codespace-post-start.sh`](https://github.com/mikejmckinney/ai-repo-template/blob/4b578bc27eea7401384fa8aac2cf4c757f8851f0/scripts/codespace-post-start.sh)

### `repo-mcp-prewarm-exec-bit-dependency` — mcp-prewarm self-reexec through xargs depends on an exec bit test.sh only warns about

**Category:** `follow_up_issues` · **Band:** `should-fix`

**Triage:** impact `incorrect-behavior` / `bounded` · trigger `edge` · scope `isolated` · reversibility `easy` · cost `trivial` · confidence `high` · guard `true`

**Uncertainty:** How often a real consumer loses the exec bit is not measured. The known vectors are derived-repository creation, archive/zip export, and checkouts with `core.filemode=false`; none were exercised against this script, so the likelihood is reasoned rather than observed.

**Verification capability:** environment `isolated-worktree` · harness `repository-test-suite`

## What is wrong

`scripts/mcp-prewarm.sh:208-209` parallelizes package resolution by re-executing itself:

```bash
if printf '%s\n' "${servers[@]}" | xargs -r -P "$JOBS" -n 1 \
  "$SCRIPT_PATH" --run; then
```

`xargs` `execvp`s `$SCRIPT_PATH` directly, with no interpreter, so the script's own correctness depends on its filesystem exec bit — even when the caller invoked it as `bash scripts/mcp-prewarm.sh`. When the bit is absent, `xargs` exits 126 and the parent prints `mcp-prewarm: package resolution failed status=126; retry the prewarm command before starting OpenCode` (line 216), which is actively misleading: retrying will never help.

The repository's guard for this is weaker than the dependency. `scripts/checks/105-scripts.sh:10-17` treats a non-executable `scripts/*.sh` as `warn`, not `fail`, and `./test.sh` exits 0 on warnings (`test.sh:99-101`). `scripts/checks/010-required-files.sh:50` checks only `-f` for `scripts/mcp-prewarm.sh`. So the repository will pass verification in exactly the state where this script silently stops working.

The existing bats suite cannot catch it either: `scripts/tests/mcp-prewarm.bats:93` invokes `bash "$SCRIPT"`, which masks the parent's dependency on the exec bit while the child invocations still need it — the tests pass only because the committed file happens to be executable.

## Why it matters

Every package-resolution path in the Codespaces `postCreate` hook flows through this `xargs` call (`scripts/codespace-post-create.sh:23`). Derived repositories (`scripts/create-derived-repo.sh`), archive exports, and checkouts with `core.filemode=false` are the realistic ways the bit is lost; in all of them the failure is a confusing non-zero prewarm with an unactionable remediation message rather than an obvious permissions error.

## Suggested fix

Two independent, small changes:

1. In `scripts/mcp-prewarm.sh`, invoke the child through an explicit interpreter: `xargs -r -P "$JOBS" -n 1 bash "$SCRIPT_PATH" --run`. This removes the exec-bit dependency entirely.
2. Optionally promote `scripts/checks/105-scripts.sh` from `warn` to `fail` for scripts that are executed directly by lifecycle hooks, or at minimum for `scripts/mcp-prewarm.sh`.

While there, add `--run <server>` to `usage()` (`scripts/mcp-prewarm.sh:22-34`), which currently documents only `--readiness-only` and `--help` despite `--run` being a supported argument.

**Evidence:**

- [`scripts/mcp-prewarm.sh`](https://github.com/mikejmckinney/ai-repo-template/blob/4b578bc27eea7401384fa8aac2cf4c757f8851f0/scripts/mcp-prewarm.sh)
- [`scripts/checks/105-scripts.sh`](https://github.com/mikejmckinney/ai-repo-template/blob/4b578bc27eea7401384fa8aac2cf4c757f8851f0/scripts/checks/105-scripts.sh)

- [`scripts/codespace-post-create.sh`](https://github.com/mikejmckinney/ai-repo-template/blob/4b578bc27eea7401384fa8aac2cf4c757f8851f0/scripts/codespace-post-create.sh)

**Reproduction:**

1. Copy the repository to a scratch directory: `work=$(mktemp -d) && cp -r . "$work/repo" && cd "$work/repo"`

### `repo-triage-validators-unhandled-type-errors` — Triage validators raise raw AttributeError/TypeError instead of their intended errors

**Category:** `follow_up_issues` · **Band:** `defer`

**Triage:** impact `meta-harness` / `bounded` · trigger `fringe` · scope `isolated` · reversibility `easy` · cost `trivial` · confidence `high` · guard `true`

**Uncertainty:** Both inputs are produced by repository automation or an LLM under a schema prompt, so no observed occurrence is on record; the likelihood is reasoned from the fact that `validate-weekly-review.py` exists precisely because model output is untrusted.

**Verification capability:** environment `isolated-worktree` · harness `repository-test-suite`

## What is wrong

Two defensive guards in the weekly/fix triage library do not do what they appear to do.

**1. Unreachable type guard in `scripts/workflows/lib/route-fixable-findings.py:17-21`:**

```python
payload = json.loads(source.read_text(encoding="utf-8"))
findings = payload.get("findings")
if not isinstance(payload, dict) or not isinstance(findings, list):
    print("batch must be an object with a findings array", file=sys.stderr)
    return 1
```

`payload.get(...)` runs *before* the `isinstance(payload, dict)` check. If the batch file contains a JSON array or scalar, line 18 raises `AttributeError` and the intended message and `return 1` are never reached. The `isinstance(payload, dict)` clause is dead code (AGENTS.md H7) and the error handling is effectively absent (H8).

**2. Unhashable-key crash in `scripts/workflows/lib/verification_capability.py:31-34`:**

```python
if environment == "isolated-worktree":
    harness = SUPPORTED_HARNESSES.get(harness_id)
```

`harness_id` comes straight from model output via `validate-weekly-review.py:70-77`, which catches only `ValueError`. If a model emits `"harness_id": ["repository-test-suite"]` or an object, `dict.get()` raises `TypeError: unhashable type`, escaping the `except ValueError` and aborting the validator with a traceback instead of the intended `harness_id is not allowlisted` message.

## Why it matters

Both turn a recoverable schema rejection into an unhandled crash. For (2) the practical effect is that a weekly provider attempt dies with a Python traceback rather than a clean validation failure, which is harder to attribute during the provider cascade and produces worse diagnostics than the code was written to produce. Neither is a correctness risk to shipped fixes, but both are cheap to close and both currently have no test.

Also adjacent in the same file: `route-fixable-findings.py:26-27` silently `continue`s past any non-dict entry in `findings`, so a malformed entry disappears from both `findings` and `deferred_findings` with no record — a silent drop in a pipeline whose whole purpose is to account for every finding's disposition.

## Suggested fix

- Move the `isinstance(payload, dict)` check above the `payload.get("findings")` call in `route-fixable-findings.py`.
- In `validate_capability`, reject a non-`str`/non-`None` `harness_id` with a `ValueError` before the dictionary lookup (e.g. `if harness_id is not None and not isinstance(harness_id, str): raise ValueError(...)`).
- Record non-dict findings in `deferred_findings` with an explicit `routing_reason` instead of dropping them.
- Add unit coverage for a list-rooted batch, an object-valued `harness_id`, and a non-dict finding entry.

**Evidence:**

- [`scripts/workflows/lib/route-fixable-findings.py`](https://github.com/mikejmckinney/ai-repo-template/blob/4b578bc27eea7401384fa8aac2cf4c757f8851f0/scripts/workflows/lib/route-fixable-findings.py)
- [`scripts/workflows/lib/verification_capability.py`](https://github.com/mikejmckinney/ai-repo-template/blob/4b578bc27eea7401384fa8aac2cf4c757f8851f0/scripts/workflows/lib/verification_capability.py)
- [`scripts/workflows/weekly-review/validate-weekly-review.py`](https://github.com/mikejmckinney/ai-repo-template/blob/4b578bc27eea7401384fa8aac2cf4c757f8851f0/scripts/workflows/weekly-review/validate-weekly-review.py)

**Reproduction:**

1. Reproduce the unreachable guard: `printf '[]' > /tmp/batch.json && python3 -c "import sys; sys.path.insert(0,'scripts/workflows/lib'); sys.argv=['x','/tmp/batch.json','/tmp/out.json']; import runpy; runpy.run_path('scripts/workflows/lib/route-fixable-findings.py', run_name='__main__')" ; echo "exit=$?"`
