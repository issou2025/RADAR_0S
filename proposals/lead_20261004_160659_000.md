## Context

pyRevit CLI ships `pyrevit run`: it drives Revit through journal files — launches Revit, opens a model, runs a script and closes Revit with no user interaction. The alternative is **APS Design Automation** (cloud Revit without UI): simpler error/dialog handling, but it is paid, requires packaging the plugin as a UI-less AppBundle (no WPF / WebView2 / MCP), is harder to debug, and is not permitted in every company.

**Decision:** batch execution does **not** go into Core. It serves a narrow audience (BIM managers of large firms) and would weigh down the platform. It will be built later as a separate SDK extension (working name `AnalyseTool.Batch`) with two transports — local (journal files) and cloud (Design Automation) — and is a candidate for the paid tier of the open-core model.

The only thing needed **now** is that the pipeline engine and `CommandQueue` can be driven without any WebView2/UI dependency. That is worth doing anyway for architectural cleanliness and testability, and it lets Batch be built on top of the existing core with no rework.

## Now

- [ ] Headless entry point for the pipeline engine / `CommandQueue` with no UI dependencies (no WebView2, WPF, dialogs, `UIApplication`-only paths) — usable by a non-interactive transport the same way `AnalyseTool.Mcp.Bridge` uses the queue today (ProjectReference on Core + `InternalsVisibleTo`, zero Core changes per transport). Covered by a tier-1 (Revit-free) test where possible.

## Later (separate extension, not core)

- [ ] `AnalyseTool.Batch` extension built on the public SDK
- [ ] Local runner based on Revit journal files (open model → run pipeline → close, no user interaction; dialog/failure handling)
- [ ] Design Automation runner (UI-less AppBundle packaging)
- [ ] Paid tier gating via `ILicenseProvider`

## Rationale — why not in core

- Narrow audience; most users never need unattended runs.
- Both transports bring heavy, transport-specific concerns (journal generation, dialog suppression, process lifecycle, AppBundle packaging, APS auth) that don't belong in a headless platform core.
- Keeps Core small and lets Batch evolve / be licensed independently — consistent with the Core/Tools/App split and the extension model.
- The core only has to guarantee a UI-free entry point, which it should have regardless.
