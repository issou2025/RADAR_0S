# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Brand non-stable builds: qualification env, app-bar banner and a banded icon**

*Project description:*
Every build the CI produces is currently the same "environment": the app never
sets `ENV`, so `OcptConfigManager.env` falls back to `Environment.development`,
and nothing in the app or on the launcher icon tells a user whether they are
looking at a stable release or a pre-release/nightly build. We should make the
distinction visible, on the app bar and on the icon, and tie it to a single rule.

## The rule: stable → production, everything else → qualification

The version already tells the two apart. The `get-version` job in
`.github/workflows/build.yml` derives the version from `git describe`, and the
`verify-stable-schema-frozen` job already encodes the exact test we want: a
**stable** build is a final semver tag (`vX.Y.Z`, no hyphenated pre-release
suffix); **everything else** — a pre-release tag (`vX.Y.Z-rc.1`), a commit after
a tag (`0.1.0-3-g87a9b8d`), or an untagged commit (`0.0.0-87a9b8d`) — is
non-stable.

- Non-stable builds compile in `Environment.qualification`.
- Stable builds compile in `Environment.production`.

The environment is chosen at build time through `--dart-define="ENV=..."`
(`QUALIF` / `PROD`, the `parsedString` values of `Environment`), which
`AbstractConfigManager` reads via `String.fromEnvironment(Environment.envType)`.
The CI already passes `--dart-define=APP_VERSION=...` on every platform build, so
the version string that decides stable-vs-not is right there next to where the
new define has to go — the `get-version` job just needs to also emit the `ENV`
value (compute it once from whether the tag carries a pre-release suffix, exactly
as `verify-stable-schema-frozen` does), and each platform build forwards it as a
second `--dart-define`. This wants doing for every platform in the matrix (Linux,
Windows, macOS, Android, iOS), so the whole matrix carries the same rule.

Both `assets/config/qualification.yaml` and `assets/config/production.yaml` must
exist and load (today only `production.yaml`, `development.yaml`, `local.yaml`,
`default.yaml` and the intentionally-unused `staging.yaml` are present — a
`qualification.yaml` has to be added, even if it only overrides `default.yaml`
where needed).

## The app bar banner

The ACT toolkit already ships exactly the widget for this:
`actlibs/act_flutter_utility/lib/src/widget/env_banner.dart`.
`EnvBanner.displayAppBarBanner<OcptConfigManager>(child: …)` wraps a subtree with
a corner `Banner` reading the environment's short string (`QUALIF`, blue), and
returns the child untouched when the app is a release build in
`Environment.production` — so a stable release shows nothing, a qualification
build shows the banner, and there is no behaviour to write ourselves.

The natural single insertion point is `_EdgeToEdgeShell` in
`lib/ui/main_app/main_app_ui.dart`: it is already the one wrapper every route
passes through (edge-to-edge insets and the orientation policy live there), so
wrapping its subtree once banners every screen. The widget places the banner at
`BannerLocation.topStart`, which sits over the top toolbar as intended.

**Colour: use the ACT defaults as-is** (qualification = blue, development = red),
no OCPT tint — `EnvBanner` is consumed unchanged.

**The banner shows for every non-production environment, `development` included.**
`displayAppBarBanner` already does this: it only withholds the banner for a
release build in `Environment.production`, so a developer's or an agent's local
`development` run shows the red `DEV` banner in the app, and a qualification build
shows the blue `QUALIF` one. This is the wanted behaviour — no change needed.

## The banner on the icon

The CI's **qualification** builds carry a banner **on their launcher icon**, so a
qualification build is recognisable on the desktop / home screen without opening
it. **Only the CI's qualification builds get this** — a `development` or `local`
build is never produced by the CI and is not packaged with an icon, so it is out
of scope for the icon treatment (the in-app banner above already covers dev). The
stable (production) build keeps the plain mark.

Icons are generated from the branding masters in `assets/branding/icons/` by
`dart run icons_launcher:create` (configured by the `icons_launcher:` block in
`pubspec.yaml`), and the generated icons are committed. So this needs a
**second, banded set of masters** (a "QUALIF" corner ribbon over the existing
mark) and a way to select them for the qualification build:

- produce the banded PNG masters — ideally by extending `tool/generate_branding_icons.dart`
  so the ribbon is drawn from the same source rather than hand-edited, keeping the
  two icon sets in step. Follow the ACT banner convention (a `QUALIF` corner
  ribbon), so the icon reads the same way the in-app banner does;
- have the qualification build regenerate / swap in the banded launcher icons
  before packaging, per platform (Android adaptive foreground, iOS opaque master,
  the Debian package icon built by `.github/actions/flutter-debian`, Windows,
  macOS).

The exact packaging mechanics per platform want their own look — this is the
part that needs the most design and CI work.

Files that anchor this work: `.github/workflows/build.yml` (env + version rule,
already present in `get-version` and `verify-stable-schema-frozen`);
`assets/config/*.yaml`; `lib/managers/ocpt_config_manager.dart`;
`lib/ui/main_app/main_app_ui.dart` (`_EdgeToEdgeShell`);
`actlibs/act_flutter_utility/lib/src/widget/env_banner.dart` (used as-is, do not
edit the submodule); `tool/generate_branding_icons.dart`, the `icons_launcher:`
block in `pubspec.yaml`, and `.github/actions/flutter-debian`.
