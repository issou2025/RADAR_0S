## Problem Statement

Usisa is meant to help everyday smartphone owners in the Philippines, especially elderly people, tell whether a text, link or screenshot is a scam. Today it is unstable and untrustworthy:

- It gives **wrong verdicts and false alarms**. Normal family texts ("Hi Ma, pa-send ng pera"), genuine OTP messages and harmless promos get flagged. Words like "ok.salamat" or "report.pdf" are treated as links, and any web address containing "bdo" or "sss" looks fake.
- **Online checks fail.** Short links (bit.ly, tinyurl) are never followed, so Safe Browsing only sees the short address. Timeouts are too tight, every user shares one rate limit, and the free Render gateway sleeps. Every failure shows the same vague "Try again later".
- **Incoming SMS is never detected.** The default build has no SMS permission at all, and the SMS test build needs three hidden opt-ins and discards harmless texts silently.
- **The UI feels dull and confusing** for the people it's meant to protect.

## Solution

A rebuild inside the current Flutter project, with a brand-new UI and a reworked checking core.

- **Home:** four bright, icon-free tiles: **Scan a message**, **Check a link**, **Scan a screenshot**, **AI scan**. Below them is an **Auto SMS protection** card with a real switch. The first three tiles judge with the phone's own check plus an online link check. **AI scan** adds the AI. Every **Check** ends in exactly one **Verdict**: **Looks safe**, **Be careful**, **Dangerous** or **Couldn't check**. "Couldn't check" is never worded as safe.
- **Verdict screen:** the verdict, plain reasons, the **Real destination** behind short links, and **Send to family** and **Read aloud**.
- **Offline:** the phone still gives a real answer.
- **SMS:** incoming texts are checked automatically, with a notification only when something is wrong.
- **Sharing:** people can share a text, link or image into Usisa from any app.
- **Verdict quality** is measured against a labelled Philippine test set, and missing the targets blocks a release.

## Implementation Decisions

**Project and structure** (#15)
- Rebuild inside the current Flutter project. Keep the Android setup, the Kotlin SMS code and the gateway server.
- Delete every old screen, widget, theme file and old image asset, the seven UI-only packages (getwidget, hugeicons, flutter_spinkit, awesome_snackbar_content, cached_network_image, flutter_svg, animations), and the `manual` / `smsLab` flavor split. There is one build with SMS protection built in.
- Organise code by feature: app shell and theme, check, sms, history, learn, settings, and a small set of shared UI pieces.
- State management uses Flutter's `ChangeNotifier` with constructor-injected dependencies, as the kept code already does. No new state library.
- Add `flutter_tts` (Read aloud) and `share_plus` (Send to family). Share-into-Usisa uses a small native `ACTION_SEND` intent hook (text and images), following the existing notification-intent pattern in the main activity. Shared images are copied into app cache immediately.
- Bundle the chosen rounded geometric font as an asset; no runtime font download.
- App ID becomes `com.usisa.app`. One project release key, kept outside the repo and read through the git-ignored key properties file (#21).

**The Check pipeline** (#12, #15, #17)
- One entry point runs a Check from a **Check input** and returns a **Check result**.
- **Check input:** the content (text, or an image to read), its source (message, link, screenshot, share, SMS), and whether it is an AI scan.
- **Steps, in order:**
  1. extract text (OCR, screenshots only);
  2. phone check;
  3. online link check (gateway follows redirects, then Safe Browsing on every hop);
  4. AI, only when the input is an AI scan and consent is on;
  5. decide the verdict.
- **Check result:** the Verdict, up to 3 reasons, the real destination(s), the AI-highlighted evidence, and labels ("Checked on your phone", "AI couldn't look at this right now").
- Screens only display a Check result. Nothing in the UI decides a verdict.
- **The verdict decision is one pure function**, applying these rules in order:
  1. Any flagged hop, or a shortener-blocked link: **Dangerous**.
  2. **AI scan with an AI answer:** AI low / caution / high maps to Looks safe / Be careful / Dangerous. A *strong* local warning sign raises it by at most one step. *Weak* signs only add reasons.
  3. **Plain tiles, SMS checks, or an AI scan without an AI answer:** the phone check's verdict is final, including Looks safe.
  4. **Gambling ad** (AI `gambling_ad` sign or local detection): at least Be careful.
  5. App-opening links (`intent:` and other non-web schemes): Be careful.
  6. A link that couldn't be followed or checked, with no warnings: **Couldn't check**. A warning beats Couldn't check, and Couldn't check beats Looks safe.
- **Reasons:** at most 3, taken from the signals that decided the verdict. A mismatched AI quote drops only that reason.

**Phone check** (#8, #12, #15, #16)
- Rewritten from scratch in Dart, and shared by the app and the background SMS entry point. There is no Kotlin copy.
- Distinguishes **strong** signs (OTP/password request plus a link, a look-alike of a known brand domain, a prize-claim hook) from **weak** signs (urgency words, brand mentions, family money requests).
- Detects Gambling ads and Harmless promos.
- Normalises Unicode and works across line breaks.
- Link spotting in text is rewritten so that ordinary words with dots, file names and "data:" phrases are not links. Brand-domain checks compare registrable domains, not substrings.
- The known official-domain and shortener lists are carried over.

**Carried-over code** (#8)
- **Kept:** AI result validation (with the tolerant quote change), the AI and link clients with retuned timeouts, the gateway readiness probe, OCR, the history and settings stores, and the scan data classes.
- **Fix:** the settings store must fall back to defaults on corrupt data.
- **Change:** the history store must keep link results with each entry.

**Gateway** (#6, #8, #10, #15)
- **Short-link follower:**
  - GET only (HEAD is unreliable on shorteners); at most 8 hops, 2.5 s per hop, 6 s total; ports 80/443; at most 64 KiB read.
  - Follows HTTP 3xx, the `Refresh` header and `<meta refresh>`; never runs JavaScript.
  - SSRF guard: resolve DNS once and refuse private, link-local, metadata, NAT64, 6to4 and Teredo addresses, then connect to the checked IP. Bare-IP hosts get their own check, because the custom lookup is skipped for them in Node 24. Node's `blockList` is not relied on alone.
  - Stopping on a known shortener's preview page means the destination is unconfirmed.
  - The raw link and every hop go to Safe Browsing in one batch, and matches are checked against the set of URLs sent.
  - Caching: chains 10 minutes, clean results 5 minutes or less, failures 30 seconds or less.
  - Any failure returns "unresolved". Clean is reported only if every hop was followed.
- **AI request:** carries the text plus the real destination and redirect steps. The schema gains a `gambling_ad` warning code, and the quote check drops a bad sign instead of rejecting the whole answer.
- **Rate limiting:** counted per client using Render's forwarded client address.
- **Daily AI limit:** stays configurable; raise it for demos.
- **Operations:** client timeouts exceed server timeouts by a safe margin; `HOST=0.0.0.0` is documented for Render; Render deploys from `main` and the `codex/usisa-gateway` branch is retired.
- **Keep-alive:** cron-job.org pings `/healthz` every 10 minutes, with UptimeRobot as backup. The app sends one non-blocking `/healthz` ping when it opens, uses about a 10 s connect timeout, never auto-retries scan POSTs, and maps every timeout, non-200, HTML, oversized or stale response, or cancel to Couldn't check for links (or to the no-AI path for AI).
- **Consent:** one first-use consent covers both online calls. Declining means phone-only checks.

**Incoming SMS** (#5, #14, #17)
- **Setup:** one onboarding step requests SMS and notification permissions together; once granted, protection is on. On Xiaomi, Oppo, Vivo and Samsung, a follow-up step deep-links to the background-running settings.
- **On arrival:** join multipart messages, then run the phone check within seconds. There is no 15-minute silent expiry; a delayed check still notifies if the text is under 24 hours old.
- **Notifications:** only for Be careful or Dangerous. The title states the verdict; the sender is shown and the body is hidden on the lock screen. Tapping opens the Scan a message check for that text.
- **Storage:** harmless texts increment a daily count and store no content.
- **Status:** the home card and Settings share one switch. A revoked permission shows a "Scam text protection is off" banner with Fix.

**UI** (#11, #18, #19, #20; details in `DESIGN.md`)
- **Style:** indigo base with warm pastel accents, big rounded cards and geometric shapes, flat white bottom nav (Check, History, Learn, Settings). Icons are used sparingly and never boxed.
- **Home:** the four tiles carry no icons; each has its own colour and geometric motif. The SMS card has a switch.
- **Verdict screen:** a header in the verdict's colour, a white sheet with the action line, reasons, real destination, text-only Send to family / Read aloud buttons, a Learn link when relevant, and Ask AI to look closer when relevant.
- **History:** on by default; entries kept 30 days / 100 entries, encrypted on-device.
- **Learn:** Golden rules plus 8 topic cards, bundled offline, English and Filipino, sourced from public PH advisories, ending in Report a scam.
- **Settings:** one page of cards: Display, Protection, Online checks, History, About. No voice picker, no reset button.
- **Motion:** staggered entrance, press scale and a slow header drift, all disabled under reduced motion.

## Testing Decisions

Good tests check what a user or caller can observe (the verdict, reasons and labels a Check returns, what a screen shows, what the gateway answers) through the three agreed seams. They never test private helpers or internal call order. Each test uses fakes only at the seam's edges.

1. **The Check pipeline (Dart), the main seam.** Run a Check with fake gateway clients (link and AI), fake OCR and a fake clock.
   - One test per verdict rule (rules 1–6 above, the strong/weak one-step limit, at most 3 reasons, a dropped mismatched quote).
   - Phone-check behaviour on the hard cases: family money requests, OTP notices, promos, gambling ads, prize hooks, look-alike domains, dotted words, cross-line requests.
   - Prior art: the existing scan controller and AI flow tests, which already inject fakes.
2. **The gateway over HTTP (Node).** Start the real gateway with fake Safe Browsing, fake Groq, and injected DNS lookup and HTTP fetch.
   - Hop and time limits, internal-address refusal (including bare IPs and IPv6 transition ranges), meta-refresh following, shortener preview pages.
   - Batch Safe Browsing with set matching, caching windows, per-client rate limits, the `gambling_ad` schema, and tolerant quotes.
   - Prior art: the existing gateway and reputation tests built on the injectable gateway factory.
3. **The whole app on screen (Flutter widget tests).** Start the app with in-memory storage, a fake SMS bridge and a fake Check pipeline.
   - The four tiles; share intents landing on the right tile, filled in; the verdict screen (each verdict, Ask AI to look closer visibility, Learn link, Send to family, Read aloud).
   - History (default on, reopen as-was, delete, clear), Settings (text size, language, consent, SMS switch in sync with home), and the protection-off banner.
   - Prior art: the existing app-shell, UI layout and SMS UI widget tests.

**Quality bar** (#13)
- Build a test set of at least 300 distinct messages, labelled Scam / Gambling ad / Harmless promo / Normal by the agent with a one-line reason each.
- Sources: relabelled Yissuh rows (masked), existing fixtures, hand-written tricky harmless texts, PH advisory patterns, and Kaggle rows kept in their own attributed CC BY-NC-SA file.
- Split 70/30, with templates kept together. The evaluation runs through the Check pipeline seam.
- **Targets on the sealed 30%:**
  - false alarms on Harmless promo + Normal ≤ 5% (phone alone and combined);
  - zero Dangerous on Harmless promo + Normal;
  - Scams caught ≥ 90% combined / ≥ 75% phone alone;
  - Scams marked Dangerous ≥ 70% / ≥ 50%;
  - Gambling ads at Be careful or above ≥ 90%.
- Couldn't check is reported separately.
- **When it runs:** the phone-only evaluation on every change; the full evaluation with AI by hand before each release and after any prompt change. A miss blocks the release.

**Outside the seams**
- Android SMS delivery and background survival are covered by the existing on-device Kotlin instrumentation tests plus the real-phone checklist from #14: Samsung, Xiaomi and Oppo/Vivo via adb; delivery, a day idle, multipart texts, dual SIM.
- Development can fake incoming texts with `adb emu sms send`.

## Out of Scope

- Publishing on Google Play. Usisa ships as an APK for a school project, so Play's SMS permission policy does not apply.
- An iOS build.
- Large text for everyone by default (replaced by the text size setting).
- Automatically sending incoming SMS to the AI.
- A Read aloud voice picker, a "reset everything" button, and search or filters in History.
- Online updates to Learn content.
- The Filipino wording review and tuning the AI daily limit. Both are build-time follow-ups once the app's copy and real usage exist.
