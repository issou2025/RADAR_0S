## Project Understanding
You need assistance with: 
**Renderer, text extraction and Find lose the whole page when an inline image's EI is followed directly by a delimiter (`EI%comment`, `EI[] 0 d`): hayro's EI candidate check requires white space after EI; the edit reader accepts a delimiter**

*Project description:*
**Version:** pdfcraft-cli built from `main` @ `ec0a9650` · Windows 11 x64 · oracles: MuPDF 1.27.2 (PyMuPDF 1.27.2.3), pdftotext (xpdf) 4.00

### What happens

An inline image ends with the `EI` operator. When the byte after `EI` is a delimiter rather than white space, for example a comment (`EI%…`) or an array operand of the next operator (`EI[] 0 d`), hayro's lexer never considers that `EI` as the end of the image. It keeps looking for a later `EI`, finds none, and the renderer draws **nothing on the page**, text extraction returns nothing, Find and search-redaction find nothing.

The edit reader (`pdfcraft_content`) accepts a delimiter after `EI` and reads the page correctly, so Edit text shows the text that the page view doesn't draw.

MuPDF has the same gap ("syntax error after inline image", nothing drawn), so this is not a case where PdfCraft is alone. But the lexical rules make `EI%` two tokens, and PdfCraft's own two readers disagree on the same page.

### Steps

Save as `repro.py` and run it in an empty folder (Python 3, standard library only). It writes three one-page PDFs: a 16 × 4 mid-grey inline image scaled into (100,300)–(300,500), then the word `AFTER`. They differ only in the byte after `EI`:

```python
def pdf(path, content):
    objs = [b"<< /Type /Catalog /Pages 2 0 R >>", b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>",
            b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 612 792] /Resources << /Font << /F1 4 0 R >> >> /Contents 5 0 R >>",
            b"<< /Type /Font /Subtype /Type1 /BaseFont /Helvetica >>",
            b"<< /Length %d >>\nstream\n" % len(content) + content + b"\nendstream"]
    out, offs = bytearray(b"%PDF-1.7\n"), []
    for i, o in enumerate(objs):
        offs.append(len(out))
        out += b"%d 0 obj\n" % (i + 1) + o + b"\nendobj\n"
    x = len(out)
    out += b"xref\n0 %d\n0000000000 65535 f \n" % (len(objs) + 1) + b"".join(b"%010d 00000 n \n" % o for o in offs)
    out += b"trailer\n<< /Size %d /Root 1 0 R >>\nstartxref\n%d\n%%%%EOF\n" % (len(objs) + 1, x)
    open(path, "wb").write(bytes(out))

# a 16 x 4 DeviceGray image of mid-grey samples (0x80), scaled into (100,300)-(300,500), then the word AFTER
IMAGE = b"q 200 0 0 200 100 300 cm BI /W 16 /H 4 /BPC 8 /CS /G ID " + bytes([0x80] * 64) + b"\nEI"
AFTER = b"BT /F1 24 Tf 72 200 Td (AFTER) Tj ET"

pdf("ei_comment.pdf", IMAGE + b"%c\nQ " + AFTER)      # EI followed directly by a comment
pdf("ei_dash.pdf",    IMAGE + b"[] 0 d Q " + AFTER)   # EI followed directly by an array operand
pdf("control.pdf",    IMAGE + b" Q " + AFTER)         # EI followed by white space
```

### Suspected source

`vendor/hayro-syntax/src/content/mod.rs`, the `EI` candidate loop in `UntypedIter::next` (line ~245–256):

```rust
'outer: while let Some(pos) = find_needle(self.reader.tail()?, b"EI") {
    self.reader.read_bytes(pos)?;
    if self.reader.peek_bytes(2) == Some(b"EI") {
        // If the following character is not a whitespace character, then we are in a ASCII-85 stream.
        if self.reader.peek_bytes(3).is_some_and(|b| !is_white_space_character(b[2])) {
            self.reader.read_bytes(3)?;
            continue;
        }
```

An `EI` whose third byte is not white space is skipped as "inside the data". With no later `EI` in the stream, no candidate is ever accepted; the `BI` instruction is then returned without image data and the interpreter draws nothing more (the page's remaining operators are never reached). The same check is what makes `>EI` / `~>EI` work for hayro in #3108's mirror case, so it has a purpose; it just doesn't distinguish "glued to data" from "followed by a delimiter".

The edit reader's rule, `crates/content/src/lib.rs`, `end_of_image` (line ~307–321), accepts `EI` followed by white space, **a delimiter**, or the end:

```rust
&& data.get(i + 2).is_none_or(|b| is_ws(*b) || is_delim(*b))
```

ISO 32000-2 §7.2.3 (printed p.22): "The delimiter characters (, ), <, >, [, ], /, and % are special … Any of these delimiters terminates the entity preceding it and is not included in the entity." And (printed p.23): "A sequence of consecutive regular characters comprises a single token." So `EI%c` is the token `EI` followed by a comment, and `EI[]` is `EI` followed by an array. §8.9.7 (printed p.268) says where `EI` is expected after the data ("the EI operator is expected following optional white-space", NOTE 2) and nothing about what must follow it.

### Possible directions

- In the candidate check, treat a delimiter after `EI` like white space (accept the candidate and let the look-ahead validate it), keeping the rejection for a regular character (`EIQ`, `>EI`'s mirror). That is the rule the content crate already applies.
- PR #3563 (the content↔hayro differential test) can carry these two fixtures as rows; today they would be pinned as a divergence, after the fix they flip to agreement.
- Related: #3108 / #3259 are the mirror (no white space **before** `EI`); #3568 and #3565 are other places where hayro's lexer gives up on the rest of a page without a warning; #3438 changes the same loop for #3107 and should be sequenced with this.
