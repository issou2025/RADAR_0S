# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Site-local models discard all instancing metadata, so repeated geometry never collates**

*Project description:*
### Version

`main` at 271b83caa.

### Which surface

Geometry / CSG kernel

### Reproduction

Split out of #4103. That issue's attachment holds 10 `IfcFurnishingElement`
sharing one `IfcRepresentationMap`. #4103 fixes the reason their mesh buffers
differed, and after that fix the ten occurrences are byte-identical and
`collate_refs` groups them into 3 templates covering all 30 meshes, a 90%
reduction in the vertices that have to ship.

On the reporter's file it still groups nothing, because every mesh arrives with
`MeshData.instance == None`.

Measured on that file with the #4103 fix applied:

```
# as authored (IfcSite placement carries a 34 degree rotation)
templates=0 instanced_occurrences=0  flat=30  shared_verts=1562110

# same file, IfcSite placement translation and RefDirection neutralised
templates=3 instanced_occurrences=30 flat=0   shared_verts=156211
```

Nothing about the geometry differs between those two runs. The only difference
is which coordinate-space tier the model lands in.

### Cause

`rust/processing/src/element.rs:766-770`:

```rust
    let instance = if ctx.site_local_rotation.is_none() {
        mesh.instance_meta.take()
    } else {
        None
    };
```

and the same test four lines later drops `local_bounds` and `local_to_world`
(#1474). `site_local_rotation` is `Some` for every model in the `site_local`
tier, which `processor/mod.rs:1085-1096` selects whenever the `IfcSite`
placement has a non-identity TRANSLATION. So any model with a site offset,
which is most models out of Revit, discards its instancing metadata.

The stated reason is sound as far as it goes: `convert_mesh_to_site_local`
(`processor/site_local.rs:71`) re-transforms positions and origin AFTER
`instance.transform` was captured, so the captured transform would be stale.
`processor/mod.rs:1202-1206` refuses to arm the don't-bake plan for the same
reason and its comment names the follow-up:

> Extending instancing to site-local needs the renderer to instance in the site
> frame too; tracked as a follow-up.

This is that follow-up, now with a measured cost.

Two things are worth separating:

1. **The guard is wider than its reason.** `apply_inverse_rotation_in_place`
   (`site_local.rs:41-53`) early-returns on an identity rotation, so for a site
   placement that is a pure translation `convert_mesh_to_site_local` does not
   touch positions at all, and the captured transform is not stale. Those models
   lose instancing for nothing.
2. **A rotated site needs the transform composed, not dropped.** With
   `baked_k = R⁻¹ · M_k · canonical`, storing `R⁻¹ · M_k` as the transform
   yields `rel = R⁻¹ M_k M_0⁻¹ R`, which is exactly the relative transform the
   collator wants.

### What a fix has to solve

I spiked (2) alone. Groups then FORM but are refused: on the #4103 attachment
3 groups and 3 rejections, on `ISSUE_098_R8_F1_MAB_AR_M3_XX_XXX_MO_7000.IFC`
0 templates becomes 1324 templates / 6262 occurrences with 413 rejections. The
composition is directionally right and not sufficient: `collate_refs` is handed
`rtc = [0, 0, 0]` (`parquet_instancing.rs:206`) while the positions are both
RTC-subtracted and rotated into the site frame, so the reconstruction check runs
in the wrong basis.

`collate_refs_verified_in` already exists for exactly this ("the #3666
reconstruction check compares in a caller-supplied basis"), so the shape of the
fix is to hand it the site basis rather than to widen the drop.

Any fix also has to answer the renderer side, which is why the original comment
deferred it: the viewer has to instance in the site frame too, or the
occurrences it reconstructs land in the wrong place.
