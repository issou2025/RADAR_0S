# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[Feature] Android 登录后首次自动申请通知权限并联动开启推送**

*Project description:*
## Background / 背景

当前 Flutter App 的原生推送已经具备完整的 APNs / JPush 设备注册链路，但 Android 与 iOS 的通知权限申请时机不一致：

- iOS：登录后的首次启动会自动申请一次系统通知权限；用户授权即视为同意开启推送。
- Android：保持严格显式 opt-in。只有用户进入「设置 → 通知」并手动打开推送开关后，才会请求 `POST_NOTIFICATIONS`、初始化 JPush 并注册设备。

这导致 Android 新用户即使已经登录、且系统通知权限处于未授权状态，也不会主动看到通知权限提示；如果用户没有主动探索设置页，推送能力会长期处于关闭状态。

本 issue 希望将 Android 行为调整为：**用户首次进入 App 并完成登录后，如果本机尚未授权通知，则主动发起一次通知权限请求；若用户同意，则自动开启 App 内推送偏好并继续设备注册。** 同时要保持当前隐私约束：用户授权前不得初始化 JPush，也不得上传推送设备标识。

### 当前代码链路

扫描 `dev`（基线：`b5b0bf4e`）后，相关实现主要集中在：

- `apps/mobile/packages/forum_app/lib/src/push/push_service.dart`
  - `PushController.refresh()` 走 `_connect(request: false)`；
  - `enable()` 走 `_connect(request: true)`；
  - Android 当前只有 `request == true` 时才会写入 `push_enabled=true` 并请求系统权限；
  - iOS 已通过 `push_permission_requested` 做登录后首次自动申请的一次性门控。
- `apps/mobile/packages/forum_app/android/app/src/main/kotlin/tj/yourtj/forum_app/PushBridge.kt`
  - `requestPermission` 会在 Android 13+ 调用系统 `POST_NOTIFICATIONS` 运行时权限；
  - JPush 的 `JCollectionAuth.setAuth(..., true)`、`JPushInterface.init(...)`、设备 token 获取只发生在后续 `register` 阶段，因此完全可以做到“先请求系统通知权限，授权后再初始化 JPush”。
- `apps/mobile/packages/forum_app/lib/src/pages/settings/settings_page.dart`
  - 当前通知设置页开关仍是 Android 用户唯一主动触发 `enable()` 的入口。
- `docs/decisions/0019-native-push-providers.md`
  - 当前明确写着：Android SDK 和设备采集仅在用户于 Settings 中显式开启推送后启动；本需求会改变这一产品语义，因此实现 PR 需要同步更新 / supersede 该决策描述。

## Target Users / 目标用户

- Android 13+ 新安装用户，尤其是小米 / HyperOS、华为、荣耀、OPPO / ColorOS、vivo / OriginOS、三星 / One UI、Pixel 等常见 Android 设备用户。

## User Story / 用户故事

作为首次登录 YourTJ Android App 的用户，我希望在进入主界面后就能在合适的时机得知 App 可以发送私信、回复、关注等通知，并直接决定是否允许；如果我允许，推送应该自动完成开启，而不是还需要再次去设置页手动打开。

作为拒绝通知的用户，我希望 App 尊重我的选择，不要每次启动都重复弹系统权限，也不要因为通知权限被拒绝而影响其他功能。

## Scope / 范围

### 1. Android / OEM 调研结论

#### Android 13+ 共同行为

Android 13（API 33）起，非豁免通知使用 `POST_NOTIFICATIONS` 运行时权限：

- 新安装 App 默认无法发送通知；
- targetSdk 33+ 时，App 可以自行选择何时弹出系统权限框；
- 用户「允许」后才可正常发送通知；
- 用户「不允许」后，App 不应依赖反复弹权限框，应降级并提供设置入口；
- Google 官方建议在用户理解通知价值的上下文中申请；官方示例甚至直接给出“用户关注某个社交账号时”作为社交产品的合适触发点；也允许在登录后通过一个可关闭的解释界面再触发系统弹窗。

参考：
- https://developer.android.com/develop/ui/compose/notifications/notification-permission
- https://developer.android.com/training/permissions/requesting
- https://developer.android.com/design/ui/mobile/guides/home-screen/notifications
- https://source.android.google.cn/docs/core/display/notification-perm

#### 国产 / 常见 Android 厂商差异

对于标准 Android 13+ 设备，`POST_NOTIFICATIONS` 的核心授权模型由 Android 统一，OEM 不应该要求 App 为“发送通知”再实现一套独立的危险权限 API；差异主要落在 **通知展示策略、后台存活、通知渠道管理、厂商离线 push token 与系统设置入口**：

| 厂商 / 系统 | 权限申请层 | 需要关注的厂商差异 |
| --- | --- | --- |
| Pixel / AOSP | 标准 `POST_NOTIFICATIONS` | 作为基准行为；targetSdk 33+ 可自行选择申请时机 |
| 小米 / HyperOS | 标准 `POST_NOTIFICATIONS` | 官方 Android 13 适配文档同样强调 App 可自主选择申请时机；同时 HyperOS 对后台本地通知、通知分类等还有额外系统策略，因此“系统权限已给”不等于所有提醒形态都绝对可达 |
| 荣耀 / MagicOS | 标准 `POST_NOTIFICATIONS` | 荣耀 Android 13 适配指南同样使用标准权限；厂商 Push 仍需单独配置 Honor token / 服务端凭据 |
| 华为 / EMUI / 部分 Android 设备 | Android 侧仍遵循标准通知权限；离线送达依赖华为厂商通道 | 对未运行进程的稳定送达重点在 Huawei Push / JPush OEM adapter，而不是另造一层运行时“通知权限” |
| OPPO / ColorOS | 标准通知权限 + OPPO 厂商通道 | 权限允许与 OPPO 厂商离线通道配置是两层问题 |
| vivo / OriginOS | 标准通知权限 + vivo 厂商通道 | vivo 对本地通知 / channel 还有额外规则，服务端 channel 配置需与客户端 channel 对齐 |
| Samsung / One UI | 标准 `POST_NOTIFICATIONS` | 系统通知类别、弹窗 / 锁屏展示等由 One UI 设置继续细分 |

小米 Android 13 官方适配文档明确：target Android 13 后“应用自行控制”权限弹窗时机，并建议等待用户理解价值后再请求：
https://dev.mi.com/xiaomihyperos/documentation/detail?pId=1575

荣耀 Android 13 适配文档同样要求声明 `POST_NOTIFICATIONS`，并允许应用选择合适时机动态申请：
https://developer.honor.com/cn/docs/adaptation_guide/guides/google_t_compatibility_adaptation_guide

JPush 当前支持小米、华为、荣耀、OPPO、vivo、魅族、FCM 等厂商通道；这解决的是离线投递路径，不替代系统通知授权：
https://docs.jiguang.cn/jpush/practice/push_strategy

**结论：本需求不应为每个国产 ROM 编写不同的“请求通知权限”分支。** 权限请求继续走现有 `NotificationManagerCompat` + `POST_NOTIFICATIONS`；厂商差异留在现有 JPush OEM adapter、通知 channel 和真机验收矩阵中处理。

### 2. 国内外社交 App 的可借鉴模式

闭源 App 的“第一次具体在哪一屏弹权限”会随版本、地区、A/B 实验变化，公开帮助文档通常只保证通知设置结构，不应把某个版本的实测 UI 写成长期产品事实。稳定可借鉴的共性如下：

- **系统权限与 App 内通知偏好分层**：Reddit、Discord、X 等都保留 App 内通知设置，同时最终展示仍受 Android 系统通知设置控制。
  - Reddit：App 内可按通知类型开关：https://support.reddithelp.com/hc/en-us/articles/360043034552-How-do-I-opt-in-or-out-of-notifications
  - Discord：官方明确区分 App 内 notification settings 与 Android / iOS 系统级 notification settings：https://support.discord.com/hc/en-us/articles/218892547--Mobile-Notifications-Settings-101
  - X Android 权限说明：https://help.x.com/en/using-x/android-app-permissions
- **不建议“冷启动第一帧直接硬弹系统框”**：Android 官方设计规范建议先给通知价值上下文，再进入系统权限；可用 onboarding、卡片、bottom sheet 等可关闭的 App 内解释层，也可以在已有明确上下文时直接弹系统权限。
- **对社交产品最自然的时机是身份建立后**：未登录时没有私信 / 回复 / 关注等个性化通知价值；登录完成后已经具备清晰价值，因此“首次登录成功并进入主界面后”比“首次打开 App”更合理。

### 3. 建议产品流程

建议采用 **“登录后一次性自动触发 + 系统权限为主 + 必要时轻量 App 内 rationale”**，不要做重型 onboarding。

#### 新用户 / 从未请求过通知权限

1. 用户成功登录，主界面首帧稳定后触发一次 `PushController` 的权限检查；不要在登录 WebView / OAuth 回跳尚未完成时弹权限。
2. 若系统通知已允许：
   - 自动将 `push_enabled=true`；
   - 直接进入现有设备注册链路；
   - 不再展示任何权限说明弹窗。
3. 若系统通知未允许且此前从未主动请求过：
   - Android 13+：发起一次通知权限请求；
   - 用户选择「允许」后，再写入 `push_enabled=true` 并初始化 JPush / 获取 token / register device；
   - 用户拒绝或划走：保持 `push_enabled=false`，不初始化 JPush，不注册设备。
4. Android 12L 及以下：没有运行时 `POST_NOTIFICATIONS`；登录后可直接把“系统通知可用”视为通过，并开启 App 内推送偏好 / 注册设备；如果用户后来在系统设置手动关闭通知，则进入 denied 状态并引导设置。

#### 是否需要 App 内预弹窗

默认建议 **不额外堆一层自定义确认弹窗**，原因：

- 登录后本身已经提供了通知价值上下文；
- Android 官方明确说明如果不需要 rationale，可以直接请求系统权限；
- 现有产品已经在设置页提供详细的 JPush / 厂商处理说明，首次登录再复制一整套隐私文案会增加摩擦。

但如果产品希望提高授权解释度，可以采用非常轻量、可关闭的 bottom sheet：

> 开启通知，及时收到私信、回复和关注动态
>
> [开启通知] [暂不开启]

点击「开启通知」后才调用系统权限；点击「暂不开启」只记录本次跳过，不弹系统框。不要做不可关闭模态窗，也不要把“开启”设计成强诱导主按钮 + 隐藏拒绝入口。

### 4. 状态与持久化建议

建议将目前 iOS 专用的 `_permissionRequestedKey` 扩展成跨平台一次性门控，避免 Android 登录后每次 `refresh()` 都触发请求。

建议至少区分：

- `neverRequested`：登录后可以自动请求一次；
- `granted`：系统允许，App 内 push 偏好开启；
- `denied`：用户明确拒绝；不自动再次弹系统权限；设置页显示“系统通知已关闭”，点击后打开系统设置；
- `dismissed / undetermined`：如果系统允许“划走”而未做决定，本次不要连续再次弹；后续只在明确用户动作（例如设置页开启推送）时重试，或至少经过一个受控冷却周期；
- `revoked`：曾授权后用户去系统设置关闭；App 恢复前台时 `refresh()` 能感知并停止 / 注销设备。

不要仅用 `push_enabled` 一个 bool 同时表达“用户愿望”和“系统权限”；两者语义不同：

- App preference：用户希望 YourTJ 推送；
- OS permission：系统是否允许 YourTJ 展示通知。

现有 `PushChannelStatus` 已经区分 `disabled` / `permissionDenied` / `enabled`，实现时应继续利用这个状态机，而不是新建另一套平行 controller。

### 5. 隐私与 JPush 初始化顺序

必须保留 decision 0019 的核心隐私约束：

1. **先检查 / 请求系统通知权限；**
2. 用户授权后，才把 App 内推送偏好设为 enabled；
3. 然后才调用 `PushBridge.register`；
4. `register` 内才允许 `JCollectionAuth.setAuth(true)`、`JPushInterface.init(...)` 与设备 token 获取；
5. token 获取成功后才调用 `/api/forum/push/device/register`。

也就是说，“自动弹系统通知权限”不等于“自动在用户同意前初始化 JPush”。

### 6. 失败 / 边界场景

- 未登录：永远不自动申请通知权限。
- 登录流程尚在 OAuth / WebView / 系统浏览器回跳：不申请，避免与登录 UI 抢焦点。
- 用户拒绝：本次及之后普通启动不再自动弹；设置页保留重新开启入口。
- 用户曾允许、后从系统设置关闭：App resume 时识别并进入 `permissionDenied`，停止推送并注销已登记 token（沿用现有逻辑）。
- 服务端 native push 暂未配置：系统权限可以独立申请，但不能把状态伪装成 delivery ready；应显示 `serverDisabled`。
- 无 Google Play Services：不影响权限流程；Android 发送链路仍按 JPush + OEM adapter。
- 多账号切换 / logout：继续遵循现有 token owner 与注销逻辑；新账号不应继承上一账号的“设备已注册”状态。
- App 数据清空 / 重装：按全新用户处理，可以重新申请。
- Android 13 以下：不要尝试调用不存在的 runtime permission；只检查 `areNotificationsEnabled()`。

## Out of Scope / 不做什么

- 不在本 issue 中更换 JPush、重做后端 push provider 架构。
- 不为每个国产 ROM 单独实现一套权限请求 API。
- 不新增常驻前台服务、保活、自启动诱导或强制电池白名单。
- 不承诺系统权限允许后在所有 ROM 上 100% 实时送达；OEM 后台策略 / 厂商通道属于独立的投递可靠性问题。
- 不在首次请求时要求用户配置每个通知类别；类别级偏好继续留在设置页后续管理。

## Acceptance Criteria / 验收标准

- [ ] Android 13+：新安装、从未请求过通知权限的用户，在**成功登录并进入主界面后**自动触发一次通知授权流程，而不是必须先去设置页。
- [ ] 权限触发不会发生在未登录状态、登录 WebView / OAuth 回跳中或 App 首屏尚未稳定时。
- [ ] 用户点击系统「允许」后，`push_enabled` 自动变为 true，并继续执行 JPush 初始化、token 获取与 `/api/forum/push/device/register`；用户无需再手动打开设置页开关。
- [ ] 用户拒绝 / 关闭系统权限时，不初始化 JPush、不采集 / 上传 push token，App 其他功能不受影响。
- [ ] 用户拒绝后普通冷启动 / resume 不会反复自动弹系统权限；设置页仍可主动重试或跳转系统通知设置。
- [ ] 已授权用户不会重复看到首次权限提示。
- [ ] Android 12L 及以下不会调用 Android 13 runtime permission API，推送开启行为与系统 `areNotificationsEnabled()` 状态一致。
- [ ] 用户在系统设置撤销通知权限后，App resume 能进入 `permissionDenied`，停止推送并按现有规则注销设备。
- [ ] `serverDisabled`、`registrationFailed` 与 `permissionDenied` 仍保持不同状态，不把“系统权限已给”误显示成“推送已可达”。
- [ ] Android 端用户授权前 `JCollectionAuth.setAuth(true)` / `JPushInterface.init(...)` 不会执行。
- [ ] 设置页推送开关继续保留，且与自动授权后的状态同步；关闭开关仍能停止 / 注销推送。
- [ ] 补充单元 / 集成测试，至少覆盖：首次登录自动请求、允许、拒绝、已请求不重复、系统撤销、Android < 33、服务端未配置、logout / account switch。
- [ ] 在 Pixel / AOSP + 至少小米（HyperOS）、华为 / 荣耀、OPPO、vivo、Samsung 中做 Android 13+ 真机或等价设备验收；记录“系统权限弹窗、设置页状态、授权后设备注册”三项结果。
- [ ] 同步更新 decision / product docs，避免代码行为与 0019 继续冲突。
