# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**feat(launchd): package agent-worker and MCP-HTTP for macOS**

*Project description:*
## Problem

On Linux, a fresh install gets an autonomous background worker that executes long-running assistant tasks, plus an HTTP bridge that exposes the assistant's tools to other machines on the network — both installed automatically (behind their own opt-in switches) by the same script that sets up the API server and the vector store. On macOS, that same setup step only knows about three services: the API server, the vector store, and the nightly data sync. The worker and the HTTP bridge are not installed in a broken state — they are never mentioned at all.

This surfaced on a real second deployment: the operator's Mac was running the API, the vector store, and nightly sync for weeks with no autonomous worker, and nobody knew it was missing until someone went looking for it. Getting it running required reading another service's boot configuration as an improvised template, hand-authoring a new one over a remote session, and starting it by hand — none of which should be necessary for a service the platform already knows how to describe.

Separately, two of the Linux platform's self-healing watchdogs (for GPU health and network recovery) genuinely have no macOS equivalent, because they watch Linux-only hardware and drivers. That absence is correct, but today it looks identical to the worker's absence: silence. An operator can't tell "not applicable on this platform" from "just never built."

## Solution

Bring the macOS setup script's service catalog up to parity with the Linux one for every service that has a viable macOS equivalent: the autonomous worker and the HTTP tool bridge should each get a background-service definition, installed conditionally behind the same opt-in signal already used on Linux (off by default, so a fresh install stays exactly as inert as it is today; already-on hosts are unaffected since nothing here changes what's already loaded).

For the two watchdogs with no macOS equivalent, the setup script should say so out loud — printing, at the end of a run, which Linux services it installed, which it deliberately skipped, and why — rather than leaving a gap that only shows up when someone notices a missing process.

## Acceptance Criteria

- [ ] Given `LIFEOS_AGENT_WORKER_AUTOSTART` unset or false, running the macOS setup script shall install no worker service (matches today's behavior and the Linux default).
- [ ] Given `LIFEOS_AGENT_WORKER_AUTOSTART=true`, running the macOS setup script shall generate, install, and load a background-service definition for the autonomous worker, with its working directory, project path, and home directory substituted the same way the existing API service definition is.
- [ ] Given an MCP bearer token configured, running the macOS setup script shall generate, install, and load a background-service definition for the HTTP tool bridge; given no token, it shall skip it (matches the Linux conditional).
- [ ] The macOS setup script shall print an explicit "skipped" list naming the GPU and network watchdogs with a one-line reason (no macOS-equivalent hardware/driver) — not silence.
- [ ] Re-running the macOS setup script on a host where the worker and/or HTTP bridge are already loaded and running shall not unload, replace, or restart them if their generated configuration is unchanged.
- [ ] The Linux systemd setup script and its currently-running services are unaffected by this change — no criterion in this issue touches `setup-systemd.sh`'s installed units.

## Verification

- **Automated tests:** a shell test that runs the macOS setup script against a sandboxed `HOME`/`LaunchAgents` directory (no real `launchctl` calls) across the two opt-in flags on/off, asserting which service definitions get written and which are skipped-with-reason.
- **Manual checks:** on a real macOS host, toggle each opt-in flag and confirm `launchctl list | grep lifeos` matches the script's own printed summary.
- **Existing test suite:** must continue to pass; the Linux systemd path is untouched.

## Scope

**In scope:**
- New macOS service definitions for the autonomous worker and the HTTP tool bridge, generated and installed conditionally by the macOS setup script.
- The setup script printing which services it installed vs. deliberately skipped, and why.

**Out of scope:**
- Porting the GPU and network watchdogs to macOS — no viable equivalent exists; this issue only requires naming the gap, not closing it.
- The macOS auto-update path (tracked separately).
- Fixing how the existing macOS service definitions load environment variables (tracked separately — see the sibling issue on plist environment handling).

## Constraints

Behavior-preserving for an already-configured install. Both live deployments — a Linux/systemd host and a macOS/launchd host, each currently running — must be unaffected until their operator explicitly runs the new tooling. Installing or re-running setup must be idempotent and must never silently replace a working unit. Any new automation is opt-in, mirroring how Linux auto-deploy is gated behind an explicit enable flag. No existing test is weakened.

## Technical Context

- **Pattern to mirror:** `scripts/setup-systemd.sh:196-206` (agent worker, opt-in via `LIFEOS_AGENT_WORKER_AUTOSTART`, disables/stops the unit when the flag is off) and `:117-121,187-193` (MCP-HTTP, opt-in via presence of `LIFEOS_MCP_BEARER_TOKEN`) — same conditional shape to reproduce in `scripts/setup-launchd.sh`.
- **Current macOS install loop:** `scripts/setup-launchd.sh:73-86` (template → plist generation via `sed`), `:88-103` (`plutil -lint` validation), `:105-121` (copy into `~/Library/LaunchAgents`, with the existing chromadb skip-with-reason at `:114-116` as the precedent for the new "skipped and why" reporting).
- **Existing plist to model the new templates on:** `config/launchd/com.lifeos.api.plist.template` (full structure: `ProgramArguments`, `WorkingDirectory`, `EnvironmentVariables`, `KeepAlive`, log paths).
- **What the new services need to run:** `config/systemd/lifeos-agent-worker.service` (`ExecStart=__VENV__/bin/python -m api.services.agent_worker.worker`, restart-always) and `config/systemd/lifeos-mcp-http.service` (`ExecStart=__VENV__/bin/python __LIFEOS_DIR__/mcp_server.py --transport http`, restart-on-failure) — translate these into `com.lifeos.agent-worker.plist.template` and `com.lifeos.mcp-http.plist.template` under `config/launchd/`.
- **Existing launchd templates for reference on naming/placeholders:** `config/launchd/com.lifeos.crm-sync.plist.template`.
- **Constraints:** no new dependencies; keep the `__HOME__`/`__LIFEOS_PATH__`/`__VAULT_PATH__` placeholder convention from the existing templates rather than inventing a new one.
