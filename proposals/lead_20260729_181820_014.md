## Project Understanding
You need assistance with: 
**[Bug]: fs-safe reports EACCES as "path is not a regular file under root" (normalizePinnedWriteError catch-all, cf #72362)**

*Project description:*
### Bug type

Behavior bug (incorrect output/state without crash)

### Summary

`normalizePinnedWriteError` in `@openclaw/fs-safe` turns **every** unrecognized write error into one fixed message:

```js
function normalizePinnedWriteError(error) {
	if (error instanceof FsSafeError) return error;
	return new FsSafeError("invalid-path", "path is not a regular file under root", { cause: error instanceof Error ? error : void 0 });
}
```

That message is an assertion about the *path*, so a permission error is reported as a path error. An `EACCES` on a perfectly ordinary, regular, in-root file surfaces to the agent as `path is not a regular file under root`, which is false in every clause: the path is regular, it is a file, and it is under root.

This is the same masking mechanism reported in #72362 (closed 2026-05-01). That fix removed one *cause* (the `python3` dependency). The catch-all that made it undiagnosable is still present, and it now hides a different and more common errno class.

### Version

OpenClaw 2026.7.1-2 (0790d9f). Observed in the bundled `dist/secure-temp-dir-DMUMnweR.js`, region `node_modules/@openclaw/fs-safe/dist/root-errors.js`, called from two sites in the pinned-write path (`throw normalizePinnedWriteError(error)`).

### Reproduction

1. Point an agent at a workspace root.
2. Make one regular file in it unwritable by the agent's uid, e.g. `chown root:root file.txt && chmod 644 file.txt` while the agent runs as another user.
3. Ask the agent to edit that file.

Expected: something naming the permission problem, e.g. `permission denied`.
Actual: `path is not a regular file under root`.

### Why it costs real time

We hit this in production on 2026-07-24. A copy step had left workspace files group-unwritable, so every `edit` and `write` returned `path is not a regular file under root`. The message sent us to look for symlinks, path traversal, a mangled workspace root, and a corrupted file type. It was none of those, and the one word that would have ended it in seconds (`EACCES`) was already sitting in `error.cause`, discarded before the agent ever saw it.

The failure is also **self-inflicted-looking**: an agent told its path is invalid will usually try a *different path*, which is the wrong recovery. An agent told "permission denied" can say so and stop.

### Suggested fix

The `openForWrite` path a few hundred lines below already does exactly the right thing, mapping specific errnos to specific `FsSafeError` kinds and rethrowing what it does not recognize:

```js
if (isNotFoundPathError(err)) throw new FsSafeError("not-found", "file not found");
if (isSymlinkOpenError(err)) throw new FsSafeError("symlink", "symlink open blocked", { cause: err });
if (hasNodeErrorCode(err, "EISDIR")) throw new FsSafeError("not-file", "not a file", { cause: err });
throw err;
```

`normalizePinnedWriteError` could follow the same shape rather than collapsing everything:

- `EACCES` / `EPERM` → a `permission` kind, message `permission denied`
- `EROFS` → `read-only filesystem`
- `ENOSPC` → `no space left on device`
- anything still unrecognized → keep the current fallback, but include the underlying `code` in the message so the next person is not guessing

Even the minimal version, appending `error.code` to the existing message when present, would have turned our multi-hour diagnosis into a single glance. Happy to send a PR if the shape above looks right.
