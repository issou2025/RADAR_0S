## What changes for us

| Change | Effect here |
| --- | --- |
| **Sampling deprecated** — use the LLM provider API directly | Do not build it. We already have `Tools/Ai/` and `Microsoft.Extensions.AI`, which *is* the recommended path. |
| **Logging notifications deprecated** — use `stderr` for stdio, OpenTelemetry for structured | Already done the recommended way: `AnalyseTool.Mcp/Program.cs:18,107` write to stderr with a comment explaining why not stdout. Nothing to build. |
| **Roots deprecated** — use tool parameters / resource URIs | We never used them. |
| **`ttlMs` + `cacheScope` on `tools/list`** (SEP-2549) | Cheaper fix for #100 than a push channel — see the comment there. Also strengthens #84 P2. |
| **Tasks extension** — `tools/call` answers with a task handle, client drives `tasks/get`/`update`/`cancel` | #110 — the answer to #99, #102 and the 10-minute timeout workaround in #88. |
| **`structuredContent` may be any JSON value**, not only an object (full JSON Schema 2020-12, SEP-2106) | #111 — retires the array-rooted limitation documented in `Program.cs:230-253`, unblocks part of #89. |
| **Elicitation restructured** — `InputRequiredResult` + `requestState`, re-issued call instead of a held stream | The official mechanism for #106 — see the comment there. |
| **MCP Apps is now a formal extension** (SEP-1865) | Relevant to #71. UI templates are declared *ahead of time* so hosts can prefetch, cache and security-review them — a materially different threat model from generating HTML at call time. |
| **Stateless core** — `initialize` handshake and `Mcp-Session-Id` removed | Little direct effect: we are stdio against a single local Revit, and the SDK owns the handshake. |
| **Missing-resource error code `-32002` → `-32602`** | No effect: our wire uses its own string codes (`McpWire.Codes`) and we do not serve resources yet. |

## The direction of travel

Worth recording, because it argues against a design this backlog was drifting toward: the spec is
moving **away** from long-lived streams and server-initiated push, and **toward** self-contained
requests, explicit handles, and cache-freshness hints. Server-initiated requests are now allowed
*only while the server is actively processing a client request* (SEP-2260) — a user can never be
prompted out of nowhere.

So "build an unsolicited push channel through the bridge first" is the wrong opening move. Every
capability we actually want — progress, long operations, confirmation prompts, a fresh tool list —
has a request/response-shaped answer in this spec.
