## Signing: manual, one distribution certificate, profiles fetched by the API key

- One **Apple Distribution** certificate. Its private key is made by the account owner (a CSR from Keychain Access or openssl), never by CI; the exported `.p12` goes into the release environment as a secret with its password.
- Two **App Store** provisioning profiles, one per bundle ID, both on that certificate. CI downloads them by name through the App Store Connect API at build time (the key is already in the release environment), so a renewed profile needs no secret change.
- The build: `flutter build ipa --release` with an `ExportOptions.plist` (method `app-store-connect`, `signingStyle` manual, the two profiles by bundle ID), the certificate imported into a temporary keychain that the job deletes.

Not chosen: automatic signing with `-allowProvisioningUpdates` and the API key. On a fresh runner every run would create a new development certificate (the account allows only a few), and what gets signed with what depends on Xcode's choices rather than on the workflow.

## Upload: release.yml, stable channel, release environment

- A new `ios` job in release.yml, in the same environment as the other stable jobs (its secrets: the API key, the certificate), after the existing approval. It runs on the stable dispatch: the release itself and the rehearsal. TestFlight builds go to internal testers only, so a rehearsal's upload is not public either.
- Version and build: `CFBundleShortVersionString` is the workspace version, `CFBundleVersion` the release's build number (the one the desktop installers carry), so every upload is unique and increasing.
- Upload with `xcodebuild -exportArchive` with `destination` `upload` and the API key (`-authenticationKeyPath`, `-authenticationKeyID`, `-authenticationKeyIssuerID`), or `xcrun altool --upload-app` with the same key.
- On a push to main, without secrets: the same archive built with `--no-codesign`, as the other platforms build unsigned there, so a break shows before a release.
- The dev channel uploads nothing.

Until the packet tunnel extension target exists (it waits for the tunnel host's C entry points), the upload carries the app alone; the extension's bundle ID and profile are ready for when it lands.

## What has to exist in the account

1. Bundle ID `com.peakpassvpn.ppvpn`, iOS, with App Groups and Network Extensions enabled. (API: possible.)
2. Bundle ID `com.peakpassvpn.ppvpn.tunnel`, iOS, the same capabilities. (API: possible.)
3. App Group `group.com.peakpassvpn.ppvpn`, assigned to both bundle IDs. (Developer website; the API cannot create app groups.)
4. Apple Distribution certificate from the owner's CSR, exported as `.p12` with a password, stored as two release environment secrets. (Developer website or API with the CSR; the private key stays with the owner.)
5. App Store provisioning profiles for 1 and 2 on certificate 4. (API: possible, once 1–4 exist.)
6. The app record in App Store Connect for bundle ID 1: name, primary language, SKU. (Website only; the API cannot create apps.)
7. A TestFlight internal testing group and its testers.

Decisions for the account owner, needed before the first upload:

- The app's name on the store (it must be free across the App Store).
- The export compliance answer (`ITSAppUsesNonExemptEncryption` in Info.plist): the app is a VPN and uses encryption.
- Who the internal testers are.
