# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[iOS] Switching between simulator and device (or build modes) always triggers "xcodebuild clean build" on Xcode 26+**

*Project description:*
### Steps to reproduce

1. `flutter create --platforms=ios repro_app && cd repro_app`
2. `flutter build ios --simulator --debug`
3. `flutter build ios --debug --no-codesign`
4. `flutter build ios --simulator --debug -v`
5. `flutter build ios --debug --no-codesign -v`

The same thing happens with `flutter run` when alternating between a simulator and a physical device, when switching between debug/profile/release, and after `flutter build ios --config-only`.

### Expected results

Steps 4 and 5 are incremental builds. The Flutter framework headers did not change, so nothing needs to be cleaned.

### Actual results

On Xcode 26+, every switch between simulator and physical device (or between build modes) makes flutter_tools delete `TARGET_BUILD_DIR` and run `xcodebuild clean build`. Nothing is printed about it unless `-v` is used, so it just looks like Xcode is slow.

Results with the counter app from the steps above (Flutter 3.47.7, Xcode 27.1):

| # | Command | `clean build`? | Xcode build |
|---|---|---|---|
| 1 | `--simulator --debug` (first build) | no | 15.4s |
| 2 | `--debug --no-codesign` (first build) | no | 12.0s |
| 3 | `--simulator --debug` | **yes** | 10.5s |
| 4 | `--debug --no-codesign` | **yes** | 8.5s |
| 5 | `--simulator --debug` | **yes** | 10.3s |
| 6 | `--simulator --debug` (same target again) | no | 4.9s |

In a real app with about a dozen Swift Package Manager plugins (including google_mobile_ads), the "Running Xcode build" step goes from about 11s to 32–73s on every switch.

#### Cause

`publicHeadersChanged` in `packages/flutter_tools/lib/src/ios/mac.dart` (added in #177671 for #176462) stores a single fingerprint at `build/ios/framework_public_headers.fingerprint`. `Fingerprinter` keys the checksums by absolute path, and the headers directory comes from `Artifact.flutterFramework` for the current mode and environment:

- `.../engine/ios/Flutter.xcframework/ios-arm64_x86_64-simulator/Flutter.framework/Headers`
- `.../engine/ios/Flutter.xcframework/ios-arm64/Flutter.framework/Headers`
- `.../engine/ios-profile/...`, `.../engine/ios-release/...`

Whenever the path changes, the fingerprint no longer matches, even though the header contents are identical across all four variants (I checked the md5 of every header). The code on `master` is the same.

#### Suggested fix

Keep one fingerprint per environment and mode. This matches how the files that can go stale are laid out: `Flutter.framework` is copied into `build/ios/<Configuration>-<sdk>/`, and the bridging-header PCH lives under `Runner.build/<Configuration>-<sdk>/`.

```diff
--- a/packages/flutter_tools/lib/src/ios/mac.dart
+++ b/packages/flutter_tools/lib/src/ios/mac.dart
@@ -752,9 +752,12 @@ bool publicHeadersChanged({
       .map<String>((FileSystemEntity header) => header.path)
       .toList();
 
+  // The headers live in a different directory for each build mode and environment, and the
+  // fingerprint is keyed by path. Keep a fingerprint per mode and environment so switching
+  // between them (e.g. simulator and physical device) is not mistaken for a header change.
   final String fingerprintPath = fileSystem.path.join(
     buildDirectory,
-    'framework_public_headers.fingerprint',
+    'framework_public_headers_${environmentType.name}_${mode.cliName}.fingerprint',
   );
```

I tested this locally on 3.47.7, with the existing tests updated and one new test added:

- Alternating simulator ⇔ device and debug ⇔ release: no clean and no precompiled-header errors. The Xcode build step stays at 9.5–14s in the real app.
- Changing a header in the cached engine artifacts (to simulate a Flutter upgrade) still triggers a clean on the first build of each environment, and restoring the header triggers it again.

Two notes:

- With build flavors (for example `Debug-dev` and `Debug-prod`, which share a mode), a single shared fingerprint means that after a Flutter upgrade only the first flavor built gets cleaned. That is also true of the current code. Naming the fingerprint after `<Configuration>-<sdk>` instead of mode and environment would cover that case too.
- On Xcode 27.1 I could not reproduce #176462 even without the clean. I appended a line to `FlutterPlugin.h` in the cached engine artifacts and ran plain `xcodebuild` (no `clean`). The build succeeded because Xcode re-ran `SwiftGeneratePch`. The clean may only be needed on Xcode 26.x. I have not tested 26.x.

I can open a PR with the change and tests if this approach looks right.
