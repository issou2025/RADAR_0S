# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Drop flashcards.topic — the topics table is the only source of a topic name**

*Project description:*
#207 gave topics their own table and `flashcards.topic_id` to point at it, and kept `flashcards.topic` alongside as a transitional column. Its two jobs are nearly over. Remove it.

## Why it should not stay

- **Two sources of truth for one fact.** Every write has to update both, for ever. #207 already had to canonicalise the string — a card saved under `environment AND climate` stores the row's `Environment and climate` — purely so the copy could not drift from the original. That is a patch over a duplication, not a feature worth keeping.
- **It only half-delivers #178.** Renaming a topic should be one row: `UPDATE topics SET name = ?`. While the string exists, a rename must *also* rewrite every card's copy, which is exactly the bulk write the table was meant to abolish.
- **The database cannot defend it.** `topic_id` has a foreign key; the string has nothing. A stray `UPDATE flashcards SET topic = 'typo'` is unconstrained and silently puts the two columns into disagreement, where the equivalent mistake on `topic_id` is rejected.
- **It invites new readers.** Every future query that reads `topic` instead of joining is one more thing this ticket has to find. `schema.sql` currently says *"Do not read it here"* — a comment is a poor substitute for the column being gone.

The one argument for keeping it is avoiding a join on the topic pages, and it does not hold: the join is on a primary key, and `get_topics()` needs it anyway to get the canonical name.

## Hard preconditions

**1. Kuantor/ai_agent#67 must be merged *and deployed*.** Not merged — deployed. `cards_db._normalize_row()` finds the topic by sniffing for a column, and with `topic` gone the next candidate that exists is **`pos`**, so Mykola would report every card's part of speech as its category with no error anywhere. This is the entire reason the column outlived #207.

**2. Every card with a topic must already have a `topic_id`.** Check before touching anything:

```bash
python -c "from utils import get_db_connection; c=get_db_connection(); u=c.cursor(); u.execute(\"SELECT COUNT(*) FROM flashcards WHERE topic IS NOT NULL AND topic <> '' AND topic_id IS NULL\"); print('unlinked:', u.fetchone()[0])"
```

It must be `0`. Dropping the column destroys the only copy of a topic name that lives outside `topics`, so any card still holding a string and no id loses its topic permanently.

## What changes

**`utils.py`** — `topic` leaves `FLASHCARD_FIELDS`, which stops `save_flashcard()` writing it. `move_flashcard()` is the only other place that touches the string, in two spots: the `from_topic` it returns for the caller's flash message and vanished-topic check, which becomes a join; and the cheap exact-name "unchanged" check, which can go entirely because the `topic_id` comparison already covers it and is the more correct question. `EDITABLE_FIELDS` is currently `FLASHCARD_FIELDS` minus `topic` — that filter becomes a no-op and should be simplified rather than left looking meaningful.

**`schema.sql`** — the column and `INDEX idx_topic (topic)` come out of the `CREATE TABLE`.

**`apply_schema.py`** — a migration to drop it, which needs **a new kind of step**.

**`applog.py` — nothing.** `_card_fields()` reads `entry.get("topic")`, and `entry` is the in-memory dict built by the parsers and forms, which still carries a topic *name*. The logs keep recording names and should: `topic=7` is unreadable a month later. Worth stating so nobody tidies it away alongside the column.

## The migration needs an inverted step

`apply_schema.py`'s steps are made idempotent by asking whether the object they create already exists. That is exactly backwards for a step whose job is **removal**: "the column exists" would mean *skip*, so the drop would be skipped precisely when there is work to do, and performed only once it had already happened.

So this needs a target whose sense is inverted — a `Removed(Column("flashcards", "topic"))`, or whatever it ends up called — where "already applied" means the object is **gone**. It is the mirror of the `Pending` probe #207 added for the backfill, and like that one it will not be the last of its kind.

## The third repo

`kuantorflow_automation/maintenance/dedup_flashcards.py` reads the column directly:

```python
"SELECT id, word, pos, topic FROM flashcards ORDER BY id"
```

and prints `topic=` for every kept and deleted row. It needs the join, in the usual parallel PR — and it is worth grepping that repo again at implementation time rather than trusting this list, since it also holds the backup and block-user scripts.

## Rollback changes character here

Every deploy so far has been revertible by putting the old code back, because the string was still there and still correct. **After this one it is not.** The column is gone, and a mistake means restoring from a dump.

So this is the deploy that actually needs the backup taken first — unlike #207, where the pre-migration dump was belt-and-braces. Take it, and check it is readable, before running the drop.

## Not part of this

- **#178** (rename a topic). It becomes a one-row update once this lands, which is a reason to do this first, not a reason to fold them together.
- Any change to how a topic name reaches `save_flashcard()`. Callers keep passing names in `entry["topic"]`; only the *column* goes. `_get_or_create_topic()` is unaffected.
- Topic images (#185) or the seeding script (#203).
