## Background

First of all, thanks for maintaining `jellyfin-apiclient-python`!

I would like to discuss the possibility of adding native asynchronous support to this library.

Currently, the library primarily uses synchronous HTTP requests. This works well for traditional scripts and applications, but makes integration into modern asyncio-based applications more difficult.

One particularly relevant use case is **Home Assistant**, which relies heavily on asynchronous I/O. Using synchronous HTTP requests in its event loop can cause blocking operations and negatively affect responsiveness.

Other potential use cases include:
- Asyncio-based applications and services
- FastAPI applications
- Automation and monitoring systems
- Applications managing multiple Jellyfin servers or concurrent requests

## Proposed approach

Rather than replacing the existing synchronous API, I would suggest evaluating an additional asynchronous client while maintaining full backward compatibility.

Ideally, both clients would expose the same API functionality and return equivalent data structures.

For example:

**Synchronous client:**
```python
client = JellyfinClient()
client.authenticate(...)
sessions = client.jellyfin.get_sessions()
```

**Asynchronous client:**
```python
client = AsyncJellyfinClient()
await client.authenticate(...)
sessions = await client.jellyfin.get_sessions()
```

Potential implementation approaches:

1. **Separate async implementation:** Introduce an `AsyncJellyfinClient` using `aiohttp` or `httpx`, while retaining the existing synchronous implementation.
2. **Shared API definitions:** Reuse endpoint definitions, data models, authentication logic and response handling where practical, with separate sync and async transport layers.
3. **Gradual migration:** Start with authentication, sessions and commonly used endpoints, then expand towards feature parity.

## Additional opportunity: WebSocket / Event support

An asynchronous client could also provide a natural foundation for Jellyfin WebSocket connections and event handling.

This could allow applications to react to events such as:
- Playback started / stopped
- Playback progress
- Session changes
- Library updates

This would be particularly useful for Home Assistant, where event-driven updates could reduce the need for frequent polling.
