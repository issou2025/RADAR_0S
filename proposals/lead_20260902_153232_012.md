# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Jawwal Pay mock payment flow before reservation**

*Project description:*
## Problem Statement

`PurchaseScreen` (`flutter/lib/features/queue/purchase_screen.dart`) reserves a bag the instant "ادفع 3 شيكل" is tapped (`_pay()` → `controller.buy()`) — there's no payment step of any kind. The product needs to demo what Jawwal Pay integration will eventually look like (no cash, no other provider — Jawwal Pay is the only viable rail), but the real Jawwal Pay business API isn't confirmed yet (`spec.md` still flags it as an open blocker). This prototype needs a believable mock of that flow: confirm the registered Jawwal Pay number → on-screen OTP (standing in for the SMS a real integration would send, since there's no SMS gateway in this prototype) → code entry → success → *then* the reservation is created, never before.

## Solution

Insert a mock Jawwal Pay flow between the Buy tap and reservation creation: confirm the number (prefilled from `UserModel.jawwalPayNumber`, saved at registration) → on-screen 4-digit code, generated client-side, no real SMS → user types it back → wrong code retries, "resend" re-shows the same code → correct code → success screen → only then does the existing `PurchaseScreen._pay()` reservation logic run (blocker check + `controller.buy()` + navigate to `ConfirmationScreen`, unchanged).

## User Stories

1. As a user who taps "ادفع 3 شيكل" on an available bag, I want to see my Jawwal Pay number (already on file from registration) and confirm it, so that I don't retype it every purchase.
2. As a user in the payment flow, I want to see an on-screen code standing in for the SMS a real integration would send, so the demo is self-contained and provable without a real SMS gateway.
3. As a user, I want to type that code back to confirm payment, so the flow demonstrates the OTP-confirmation step Jawwal Pay's real API is expected to require.
4. As a user who mistypes the code, I want to retry, so a typo doesn't dead-end the flow.
5. As a user who lost the code, I want a "resend" that re-shows the same on-screen code.
6. As a user who enters the correct code, I want to land on a success screen and then immediately get my reservation, so payment feels like the gate in front of "getting the bag," not a disconnected step.
7. As a developer, I want the code-verification logic isolated behind one seam (e.g. `MockJawwalPayService`), so swapping in the real Jawwal Pay API later doesn't require rewriting the payment UI flow.

## Implementation Decisions

- Add `jawwalPayNumber` (nullable `String`) to `DemoUser` (`flutter/lib/features/auth/demo_accounts.dart`) — it currently only carries `phone`/`pin`/`role`/`name`. Populate it in `main.dart`'s `Authenticated` branch from `state.user.jawwalPayNumber` when building `demoUser`.
- New screens under `flutter/lib/features/payment/`: a number-confirmation screen and an OTP screen (number confirm → on-screen 4-digit code + entry field → success). Follow the existing screen conventions (see `RegistrationScreen`, `PhotoCaptureScreen` for the established look: `Scaffold` + `AppBar` + `ConstrainedBox(maxWidth: 480)` + `PrimaryButton`/`SecondaryButton`/`StatusChip` from `core/widgets/`).
- `MockJawwalPayService` (or similar, plain Dart class, no bloc needed — this is local UI-only state, unlike auth): generates a 4-digit code, exposes `verifyCode(entered) -> bool`. Resend re-displays the *same* generated code rather than issuing a new one.
- `PurchaseScreen._pay()` — the existing logic (blocker check, `controller.buy()`, navigate to `ConfirmationScreen`) stays exactly as-is; it just moves to fire *after* the new payment screens report success, not directly from the Buy button. The Buy button now pushes the number-confirm screen instead of calling `_pay()` immediately.
- No real SMS (httpSMS was removed from this repo's docs already — FCM is the only notification channel). No payment persistence — nothing about the mock payment (number, code, wallet) is written to `drift`; only the resulting reservation (already modeled by `Purchase`/`QueueController`) matters.
- Note: `PurchaseScreen`/`QueueController` are still the in-memory mock data layer (TASKS.md's "replace mock data with real drift queries" is separate, pre-existing, unfinished work — do not touch that migration as part of this task, stay on `QueueController`).

## Testing Decisions

- Unit test `MockJawwalPayService`: correct code → verified; wrong code → rejected, still retryable; resend → same code re-displayed (not regenerated).
- Widget test for the screen sequence: number-confirm → OTP screen shows a code → wrong entry shows an error and stays put → correct entry navigates to success.
- This is CI-run work (`flutter analyze` / `flutter test` / `flutter build apk --debug` only, no browser) — keep assertions to widget-tree state and the service's pure logic. Live visual/browser verification of the flow happens in a follow-up online session, not part of this task's Done criteria.
- No golden test needed for the new screens this pass — the existing goldens are already known-flaky in CI font rendering; don't add to that surface now.

- Live UI/browser verification — confirm this renders and flows correctly in a live session, not as part of merging this PR.
