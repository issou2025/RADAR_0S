# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Design: MCP server for the collection (desktop, read-only first release)**

*Project description:*
## Summary

Add a Model Context Protocol (MCP) server to MyMediaScanner so that AI assistants and agents can query, and optionally update, the collection. The first release targets the desktop app only (macOS, Windows, Linux) and is read-only.

## Decisions (2026-11-13)

- **Embedded server.** The app hosts the server, so the app must be running. That is acceptable.
- **Read-only first release.** Write tools are a later phase.
- **Desktop only.** The mobile apps do not need to speak MCP. Mobile is out of scope.
- **The `private` tag hides items from MCP**, as it does in the static export.
- **Started by hand each session.** The server never starts with the app; the user switches it on when it is needed.

Two smaller questions remain open at the end.

## Motivation

The collection is only reachable through the app's own UI, the CSV/JSON export and the static HTML export. An MCP server lets an assistant answer questions and carry out chores against live data, for example:

- "Do I already own this on Blu-ray?" while shopping
- "Who has my copy of *Dune*, and since when?"
- "Which CDs on the Jazz shelf have no FLAC rip yet?"
- "Pick something unwatched under two hours for tonight"
- "Add these ten ISBNs to the wishlist"

## Goals

- Expose the collection to any MCP client over a standard transport
- Reuse the existing use cases and repositories, so behaviour matches the UI
- Off by default, loopback only, read-only
- Items tagged `private` are never visible to a client

## Non-goals

- Mobile (Android, iOS): the server is not started and the Settings section is not shown there
- A general REST API, or access from another machine
- Exposing secrets (API keys, PostgreSQL credentials, TMDB session) or settings
- Driving the UI (Marionette already covers that for debug builds)
- Hard deletes, backup/restore, or sync configuration through MCP

## Architecture

### Options considered

| | Option | For | Against |
|---|---|---|---|
| A | **Server embedded in the running app**, Streamable HTTP (**chosen**) | Reuses use cases and repositories as they are. One process owns the SQLite file. | The app must be running. Stdio-only clients need a bridge. |
| B | Standalone Dart CLI over stdio, opening the SQLite file directly | Works with every client. No app needed. | Two processes writing one database. The data layer depends on Flutter plugins (`path_provider`, `flutter_secure_storage`, `drift_flutter`) and would need extracting. On macOS the database sits in the sandbox container. A CLI built against an older schema could race a migration. |
| C | A plus a thin stdio-to-HTTP bridge | Covers stdio-only clients. | A second artefact to build and ship. |

### Decision: option A, with C as a later add-on if needed

The app hosts the MCP server in-process and serves Streamable HTTP on a loopback port. Tool handlers call the existing domain use cases.

Reasons:

- **One owner of the database.** No second process opens the SQLite file, so there is no locking or migration race.
- **Later writes stay correct.** Repository implementations record `sync_log` entries, apply soft deletes and keep the FTS table current. When write tools arrive, going through them means MCP edits sync to PostgreSQL like any other edit. Option B would have to duplicate that.
- **The UI stays live.** Drift streams already refresh the screens when a row changes, so a later write tool needs no extra UI plumbing.

### Layering

Proposed new top-level folder, so `domain/` stays free of protocol code:

```
lib/mcp/
  server/     → server lifecycle, transport, authentication
  tools/      → one handler per tool; depends on domain use cases only
  mappers/    → domain entity → JSON tool result
lib/presentation/providers/mcp_server_provider.dart  → start/stop, status, settings
lib/presentation/screens/settings/                   → "MCP server" section
```

Not part of the first release. Listed so the first release leaves room for them.

Out of scope for the first version. Candidates later: `mymedia://item/{id}` resources and cover images.

## Security and privacy

- **Off at every launch.** The server is started by hand from a new "MCP server" section in Settings and stops when the app quits. The on/off state is not saved, so a forgotten server is never left listening after a restart.
- **Loopback only** (`127.0.0.1`). There is no option to bind to the LAN.
- **Bearer token required**, generated on first enable, with a "regenerate" action. Requests without it get `401`.
- **Host and Origin validation**, to block DNS-rebinding attacks from a web page.
- **Read-only.** The first release registers no write tools.
- **Private items are hidden.** See below.
- **No secrets and no settings** are reachable through any tool.
- **Borrower details are personal data.** `list_loans` returns the borrower's name only, not contact details.

### Private items

The static export drops every item that carries the private tag (`private` by default, matched case-insensitively). MCP applies the same rule, in one shared filter that every tool passes through:

- List and search tools omit private items
- `get_item` on a private item answers "not found", the same as for an unknown id
- Shelf, series, loan and wishlist results omit private items
- `get_statistics`, `recommend_next` and `random_pick` are computed without private items, so counts and totals cannot reveal them

The tag name is the same one the static export uses, so an item is private in both places or in neither.

## Settings UI

A tonal-container section on the Settings screen, desktop only:

- Start/stop switch and status line (stopped / listening on `http://127.0.0.1:<port>/mcp`). The switch is always off when the app launches
- Port (default fixed, editable, saved between sessions so the client configuration stays valid)
- Token: reveal, copy, regenerate
- "Copy client configuration" button that produces a ready-to-paste JSON snippet

## Testing

- Unit tests per tool handler, with `mocktail` repositories (written test-first)
- Protocol test over an in-memory transport: handshake and tool listing
- Lifecycle test: the server is stopped on a fresh provider container, whatever was running before
- Private-item tests: a private item is absent from every tool's output, including statistics
- HTTP test on loopback: missing token, wrong token, bad `Origin`
- Manual check per desktop platform with a real MCP client; the macOS check must use a release build because of the entitlement
