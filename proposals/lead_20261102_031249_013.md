## Outcome and architectural boundaries
- Native Linux owns the backend/services, dependency preparation, data, sandbox checks and host update mechanism.
- Android/iOS are Flutter clients of an explicitly configured host. They do not install the Linux backend, execute Git updates, or replace native binaries outside platform distribution mechanisms.
- Stable selects an explicitly promoted versioned release. Nightly selects an immutable, identifiable build from an eligible `main` revision after required CI gates. Do not publish a broken build just because the schedule ran.
- Separate application version, build SHA, release channel and protocol/schema compatibility. Display provenance in CLI diagnostics and app About/connection diagnostics.
- Installation/distribution completion is independent of mobile media, background execution, locked-screen calling, push delivery, and provider quality. Those remain under #11 and other applicable roadmap gates.

## Cross-cutting security and operations
- No provider secrets, owner tokens, pairing grants, signing credentials or private user data in build artifacts, URLs, logs, screenshots or issue evidence.
- Off-loopback host access uses authenticated HTTPS and the existing scoped pairing model. Do not expose unauthenticated services or silently disable sandbox/disclosure controls for convenience.
- Preserve user data across installs/upgrades; record migration/backup/restore behavior and refuse incompatible downgrades. Code rollback is not database rollback.
- Publishing is privileged CI work: least-privilege tokens, protected signing material, approved stable promotion, immutable build identity, integrity metadata and auditable release evidence.

## Owner clarification: GitHub-hosted mobile distribution
The owner confirmed that immediate mobile install files should be hosted on the GitHub repository/releases, rather than prioritizing Play/App Store publication. Existing developer/store identities do not make store publication the immediate goal. Android must offer signed APK downloads and an explicit user-confirmed platform installation/update path. Store tracks remain optional future routes.

For iOS, include eligible alternative distribution/sideloading rather than assuming TestFlight is the only non-App-Store path. Do not equate hosting an IPA with universal installability: Apple's regional eligibility, signing/provisioning, notarization and (for authorized Web Distribution) registered-domain requirements still apply. Record the chosen supported route and actual install evidence before calling it complete. Official references: https://support.apple.com/en-us/117767 and https://developer.apple.com/support/web-distribution-eu/ .
