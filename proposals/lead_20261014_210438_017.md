# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Spec: Testing hardening: a trustworthy CI signal, mock policy, isolation and coverage gaps**

*Project description:*
## Problem Statement

Watchdog's test suite is large and mostly sound, but a five-part audit (inventory and quality, value and overkill, web research on 2026 practice for the frontend and for the backend and CI, and CI reliability) found problems that make the green signal less trustworthy than it looks, and a few places where cost and value are out of balance. The full evidence is in the five comments under this issue. The suite itself is not the problem: the tiers, naming and written standard are good, real-Postgres integration with query-count budgets is rarer than typical, and the toolchain is current and mainstream. What is missing is enforcement, a mock policy and a few coverage gaps.

**For a maintainer deciding whether a green CI means "safe to merge"**

- `main` has no branch protection and no rulesets, so the `Check` aggregate is only nominally required. Earlier pull requests merged with `Check` red.
- Path filters let changes merge with relevant jobs skipped. Gates is not triggered by a change that touches only scripts, so those scripts are not linted or typechecked in CI. A package manifest edit in a workspace package outside a short list skips Gates, Unit and Integration. `Check` is skipped, not failed, if file detection fails.
- CI cancels in-progress runs on pushes to `main` as well as on pull requests: in the last 100 push runs on `main`, 17 were cancelled and left that commit with no verdict.
- Failures are hard to debug: CI never records a Playwright trace (the trace setting is "on first retry" while retries are zero), and the coverage comment shows red for integration-tested files because integration and e2e upload no coverage.

**For anyone trusting the tests to catch real bugs**

- Mocks dominate the web tests: 896 `vi.mock(` calls in 304 of 979 test files, 104 of them copies of the same auth-module boilerplate, and the audit estimates about 60% of mocks hit neither a network, database or vendor boundary nor a framework seam. Examples fake the data-fetching hooks themselves, or re-declare query keys inside a mock so that a real key change leaves the test green. This is the characteristic failure mode of agent-written tests: the 2026 research cited in the comments measures agents adding mocks in 36% of their test commits against 26% for humans.
- Mutation testing shows real holes. Real StrykerJS on the custody policy package scored 69.9%, and 29 hand-seeded bugs across three pure slices scored 58.6%. Survivors include swapping "some" for "every" on Evidence ids, Claim text not required, Event entity ids not required, whitespace-only notes accepted, edge operation kinds unrestricted, and no direct test for two assertion helpers.
- Critical behaviour is tested thinly in places: the organization-isolation integration matrix is hand-listed with nothing proving that every router procedure is in it, so a new procedure can ship without anyone attacking it from another organization. The export download and live-update route tests mock the very checks that enforce organization scoping, so scoping on those routes is never proven against real data. The invitation signup flow has only a 21-second end-to-end test. The auth configuration test mocks the auth library and asserts the config it was handed.

**For test isolation**

- Several Vitest projects share workers (`isolate: false`) for speed. The written rule is to restore anything a test changes, but nothing enforces it: no lint rule, no canary, and no shuffled-order run in CI. Two confirmed cases exist today: one component test spies on document and history functions with no restore, and another defines `window.matchMedia` at module scope and never restores it. Shuffled-order runs of the unit, web-unit, property and component projects (19 runs, several seeds and worker counts) found no failures, so these are latent, not active. The history shows the risk is real: ten distinct flake families in CI, eight fixed, the worst failing eight runs over four days.

**For test cost**

- The gate tier (tests that spawn real scripts or exercise lint rules) is 22% of test cases and about 63% of `pnpm test` wall time, and of 34 recent fix commits that touched it, none was a product bug. A handful of its suites are heavy for what they guard.
- The CI "Unit" job is named loosely: it runs unit, web-unit, property and component tests together, and about 28% of its files are component tests rendering React in a DOM. Its test bodies are tiny (369 of 397 unit files run under 50 ms of body); the cost is imports and transforms.
- The written standard has drifted from practice: it says web `*.test.ts` files run in the component project (most run in web-unit), `pnpm test` omits the component tier, the standard bans sleeps and casts but tests contain about 30 real sleeps and about 250 casts, and a large markup snapshot fixture survives only to prove a one-time refactor.

## Solution

Keep the structure and strengthen the enforcement. Five workstreams, each small, none a rewrite:

1. **Make the CI signal enforceable and debuggable.** Protect `main` (with an owner bypass if direct pushes remain the workflow), make `Check` fail when file detection fails, close the path-filter holes, cancel in-progress runs only on pull requests, record traces on failure, and fix the coverage comment noise.
2. **Adopt a mock policy and shrink the debt.** Mock only boundaries (network, database, vendor clients, time, framework seams). Provide shared test doubles for the repeated cases (the auth module, toasts, record builders). Add a shrink-only baseline that stops new internal-module mocks, and convert files as they are touched.
3. **Enforce isolation and probe for order dependence.** A canary and lint checks for unrestored global changes, plus a non-blocking nightly run with shuffled file order, repeats and a printed seed. Fix the two known cases first.
4. **Close the coverage gaps that matter.** A router-enumerating organization-isolation test (every procedure is covered or explicitly allowlisted, and state is unchanged after a denied write), real-data tests for organization scoping on the export and live-update routes, a direct test of the invitation signup flow, and tests for the policy-package survivors that the mutation run found.
5. **Trim the gate tier and correct the standard.** Simplify the heaviest gate suites to pure-function tests, merge the import-ban fixtures, delete the spent snapshot and the redundant config readers, keep the guards that prevented a real regression, move the working-tree-writing test out of the unit tier, convert the process-spawning CLI tests to in-process, and update the written standard and tier table to match reality.

Principles for every change:

- Behaviour-preserving for product code. This spec changes tests, test config and CI, not product behaviour.
- No test or gate is deleted without naming the bug class it covered and where that class is covered now.
- Each change names the measurement that shows it worked (a count, a baseline, a CI result), as in the performance spec.
- The cheapest mechanical enforcer beats a written rule. Agents follow what is enforced.

## Implementation Decisions

Grouped by workstream. File locations are in the audit comments; this list records decisions.

**CI trust**

- Add a ruleset (or branch protection) on `main` that requires the `Check` aggregate, with an owner bypass recorded in the settings doc. This is a decision for the owner (see below).
- Make the aggregate fail, not skip, when file detection does not succeed.
- Align path filters: every job that must run for a script-only change, a root-tooling change or a workspace manifest change runs for it. Extend the existing workflow guard test with each rule so the filters cannot drift.
- Scope in-progress cancellation to pull requests; pushes to `main` always complete.
- Record Playwright traces on failure (or retry once with isolated retries) and upload them on failure.
- Tune the coverage reporting so integration-tested files are not shown as uncovered patch lines, either by uploading a representative integration coverage flag or by changing the patch check to informational for those paths. Decide after looking at what Codecov offers.
- Align Node versions between CI and the nix shell.

**Mock policy and shared doubles**

- Write the policy in the testing standard: allowed to mock a network or vendor client, a database or clock boundary, or a framework seam; not allowed to mock an internal module the code under test owns, a data-fetching hook, or a query key. Prefer Effect layer test doubles over module mocks for Effect services.
- Provide shared doubles for the repeated boilerplate: the auth server module, the toast module and the record fixtures, in the test support packages.
- Add a lint rule or gate that counts internal-module mocks per file against a committed shrink-only baseline, so new ones fail and fixed ones lower the baseline.
- Convert the worst web tests first (those faking the data-fetching hooks or duplicating query keys), as files are touched, not in one sweep.
- Add a pull-request check that reports added mocks and removed assertions as an advisory comment.
- Enforce the existing "no casts in tests" and "no sleeps" rules with shrink-only baselines, converting as files are touched.

**Isolation**

- Fix the two known unrestored changes. Add a canary (a test that asserts a clean global state at the end of each shared-worker file) or lint rules for unrestored spies, global stubs and module-scope global definitions, with a baseline if any exist.
- Add a nightly, non-blocking workflow running each non-database project with shuffled file order, repeats and several seeds, printing the seed on failure.
- Write a flake policy: how a re-run that passes is detected, how a flaky test is quarantined and tracked, and a rule that every distinct flake has an issue. File the one unfixed integration flake.

**Coverage gaps**

- Add a unit-level test that enumerates the router and asserts every procedure is in the organization-isolation matrix or an explicit allowlist with a reason. Extend the matrix assertions to check state is unchanged after a denied write.
- Add real-data integration tests for organization scoping on the export download route and the live-update route, replacing reliance on mocked visibility checks.
- Add direct tests for the invitation signup flow and rewrite the auth configuration test to assert behaviour.
- Turn the mutation survivors in the custody modules into tests, and add the missing direct tests for the two assertion helpers.
- Evaluate an advisory weekly incremental mutation run on the custody modules using a command-runner setup, since the official Vitest runner does not work on this stack. Keep it advisory.

**Gate tier and standard**

- Simplify the baseline-CLI gate suites to pure-function tests, merge the import-ban fixture suites, delete the markup snapshot and the redundant config readers, keep the workflow guard that caught a real regression, and move the probe-writing test to the gate fixtures.
- Convert the process-spawning CLI tests to in-process tests.
- Correct the standard and tier table to match which project runs which files, state what `pnpm test` and the pre-push hook run, and rename the combined CI job to say what it runs.
- Add a short testing ADR with the tier-to-size mapping. Provide shared record builders in the test support packages.

**Evaluate, then decide**

- A small browser-mode project for overlay, focus and drag components, an accessibility check on a few routes, a nightly production-build smoke, and Node alignment are each a spike with a measurement before a commitment.

**Ordering**

CI trust and the two isolation fixes come first, because they are cheap and make every later result trustworthy. The mock policy, shared doubles and baselines come next, then the coverage gaps and the gate-tier trim. The evaluations come last.

**Decisions for the repository owner**

- Whether to protect `main` and keep an owner bypass, given the current direct-push workflow.
- How strict the mock policy is at first (block new internal mocks outright, or warn).
- Whether the nightly shuffle run should open an issue automatically on failure.
- Whether mutation testing stays advisory or ever gates.
- Whether CI moves to Node 24 or the local shell moves to Node 22.
- The Codecov policy for integration-tested files.

## Testing Decisions

A good test here asserts external behaviour through the narrowest public interface and mocks only boundaries. For the meta-tests this spec adds (tests of tests and of CI), assert deterministic facts: a count against a baseline, a set of triggers, a list of procedures, a clean global state. Do not assert wall-clock speed.

Seams, highest first, each used by more than one ticket:

- **The workflow guard test.** It already parses the CI workflow and asserts job conditions and the aggregate. Extend it for every trigger and failure-semantics rule above. Prior art: the existing guard and the bundle-budget gate test.
- **Shrink-only baselines.** One for internal-module mocks, one for casts in tests, one for sleeps, in the style of the existing lint-plugin baselines and the file-size gate.
- **An isolation canary.** A shared-worker end-of-file check for a clean global state, plus the nightly shuffled run as the integration of it.
- **The router enumeration test.** It lists the procedures and compares them with the isolation matrix and an allowlist. Prior art: the existing organization-isolation integration test and the procedure guard lint rule.
- **Behaviour tests for the new coverage.** Real-data integration tests for the export and live-update scoping, direct tests for the invitation flow and the policy helpers, and the mutation survivors as assertions. Prior art: the existing integration suite with private databases and the query-count helpers.

Each ticket shows its before and after number (a mock count, a trigger set, a covered procedure list, a mutation score) in its pull request.

## Out of Scope

- A new testing framework or a wholesale rewrite of existing tests. The audit found the structure sound.
- Gherkin or Cucumber, Pact, Storybook and Chromatic, Cypress, Jest, PGlite, paid flaky-test services, and the unsupervised Playwright Healer agent. The research found no case for them here.
- Wholesale migration of component tests to a browser runner. Only a small evaluated project for overlay, focus and drag components.
- Sharding the unit job or Playwright, larger runners, and a merge queue, until measurements show a need.
- Making mutation testing a blocking gate.
- Replacing the shared test database with a database per worker, unless the integration job nears its timeout.
- Product behaviour changes of any kind.
