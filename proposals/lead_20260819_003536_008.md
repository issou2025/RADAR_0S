# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**Release builds are hand-assembled and not reproducible**

*Project description:*
Getting build 22 to TestFlight took a sequence of steps that exist only in one session's shell history:

- `flutter build ipa` fails at the export step — the App Store profile needs the Associated Domains and Push Notifications capabilities, and the bundle ID has both capabilities but no provisioning profile.
- The working route is `xcodebuild -exportArchive -allowProvisioningUpdates` against **Xcode's signed-in account**. Using the App Store Connect API key instead fails with "Cloud signing permission error": an App Manager key cannot do cloud signing.
- Upload is `xcrun altool --upload-app` with the API key, which *does* work for delivery.
- Beta group, tester, invitation and "What to Test" were all created by hand against the API.

None of that is checked in, so the next build starts from scratch and the next person (or the next session) rediscovers the cloud-signing trap.

## What to do

A `tools/release.sh` — or a Makefile target — that:

1. Archives and exports with the flags that actually work, with a comment saying *why* `-allowProvisioningUpdates` and Xcode's account rather than the API key.
2. Uploads via `altool` with the API key.
3. Waits for `processingState == VALID`.
4. Attaches the build to the internal group and sets the "What to Test" notes from a file in the repo, so release notes are reviewed in a PR rather than typed into a web form.

## Notes worth keeping in the script

- App Apple ID `6802850909`, bundle `dev.osholt.tideandseek`, team `UY4624PH6X`.
- The API key must be App Manager or better; a Developer key cannot upload.
- The build takes about 90 seconds to appear in `/v1/builds` after `UPLOAD SUCCEEDED`, so a poll loop is needed rather than a single check.

Secrets stay out of the repo: issuer and key ID by environment variable, key file from `~/.appstoreconnect/private_keys/`.
