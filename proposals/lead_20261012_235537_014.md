*Project description:*
### App name

photos

### One-line description

Offline-first photo gallery that backs up to the user's own private GitHub repository, with memories, places and people.

### Rationale

**Who it is for:** anyone who wants their photo library to be theirs. Storage is a private GitHub repository the user owns, so there is no storage bill and no lock-in. The app keeps working fully offline and syncs when GitHub is reachable.

**What this repo is: a public Dart (Flutter) app shell.** It holds no feature code. It commits only the three composition inputs:
- a root `composer.json` listing its SDKs: `base_sdk`, `telemetry_sdk`, `auth_sdk`, `users_sdk`, `depot_sdk` (the storage engine) and the photos SDK;
- `.rokct/initiate.py`;
- `.rokct/config/app_type` = `photos`.

All of `lib/` is generated by compose and gitignored. Code that belongs only to this app goes in `custom/`. The features below are built in SDKs that live in the SDK monorepos, not here. The canonical SDK list is the composer template `core/utils/flutter/composer/photos.json` in The-Rokct-Protocol; CI overwrites the committed `composer.json` from it. There is **no Frappe backend**: the user's GitHub repo is the only remote for photos, reached through the GitHub REST API. The phone never runs git.

**Two separate sign-ins:**
- **The app account** comes from `auth_sdk` and `users_sdk`, like every other fleet app. With no backend reachable, registration and login still work offline (auth_sdk's offline users), so the app never blocks on a server.
- **GitHub sign-in** only connects storage, on depot's `/depot/setup` screen.

#### Core: storage on GitHub
- Provided by `depot_sdk` (RokctAI/hardware, `depot/`), shared with the drive app. Sign in with GitHub using the OAuth device flow (no tokens to paste). Create a new private repo from inside the app, or connect an existing one. The repo config is stored in Drift; if the repo is unreachable the app keeps working locally and syncs later.
- **Commits come in batches, not per photo:** one commit for every 20–100 photos plus their thumbnails and index updates, built with the Git Data API (blobs → tree → commit → ref update). The app writes the commit message (e.g. `Backup 37 photos — 17 Sep 2026`).
- Each photo is identified by its **content hash** (SHA-256), not its filename, so two files with the same name never overwrite each other and an exact duplicate is detected before upload.

#### Index: one global index plus per-photo metadata
- A **global index** at the repo root lists every photo with id, date taken, hash, size, repo path, thumbnail path, album/folder, place, people ids and memory groups. It is split by day (e.g. `index/YYYY/MM/DD.json`) behind a small manifest, so "this day in past years" needs only a few files.
- Each photo also gets its own **metadata JSON** with the full detail (EXIF, GPS, camera, face boxes, edits).
- The app builds every screen from the index and never scans image files to draw a list.

#### Gallery: thumbnails first
- Every upload includes a **small thumbnail committed next to the original**.
- The grid is drawn from index rows. Thumbnails are fetched only for the tiles on screen and a little ahead while scrolling. The full photo is fetched only when the user opens it. Recently viewed media is cached locally with a size cap.
- Local and remote photos are merged into one timeline. Each tile shows a badge for its state: on device only, backed up, or remote only.

#### Backup rules
- Watch device folders. When a **new folder appears** (e.g. a messaging app's images folder), ask once: *"Back up photos from <folder>?"* (Back up / Not now) and remember the answer.
- A local photo with no index entry is *unindexed*: index it on the device (date, place, faces), queue it, upload it in the next batch, then clear the queue entry.
- Optional "free up space": remove the local copy once the batch carrying it is confirmed committed.
- A backup status screen shows pending, uploading, done and failed photos.

#### Repo-side automation (GitHub Actions in the user's repo)
- Once the repo is connected, the app **adds workflow files** to it. Prefer thin callers of reusable workflows in `RokctAI/shared-workflows`, so fixes reach every user's repo without the app re-pushing files.
- Those workflows do the heavy lifting on the user's own Actions minutes, with no server of ours:
  - **Import an existing Google Photos library straight into the repo** (server-side, so nothing is downloaded to the phone or a PC first). It writes thumbnails, metadata and index entries as it goes, in batched commits.
  - Index photos that arrived without metadata.
  - Run people recognition on imported photos the phone has never had.
  - Report repo size (see below).
- **Minutes are a budget.** The storage repos are private, and private-repo Actions minutes belong to the user's GitHub **account**, shared by every repo it owns. Extra storage repos created as the data grows add no minutes. Most users are not developers, so depot's repos are likely the only thing spending that allowance. When it runs out, jobs stop until the monthly reset or an upgrade. So every heavy job must be **chunked and resumable**:
  - each run processes a bounded batch, commits it, and records a checkpoint in the repo (e.g. the last imported item);
  - the next run continues from the checkpoint, so running out of minutes pauses work and loses nothing;
  - the app reads the checkpoint and shows progress ("Imported 4,200 of 18,000"). When a job is paused for minutes, it says so in plain words (wait for the monthly reset, or upgrade), with no developer jargon.
- Work that can run on the phone (indexing and people recognition for photos the phone has) stays on the phone and spends no minutes.

#### Memories
- Run locally from the index, never as a daily server job. Candidates are "on this day", "this week N years ago" and trips or events (a cluster of time plus place).
- A **scoring step decides whether anything is worth showing**: date closeness, how many good photos there are, people present, place or event coherence, whether it was already viewed, and how recently that period was surfaced. Nothing above the threshold means nothing is shown. Silence is the default.
- Memories load thumbnails only. The full photo loads on tap.

#### Places, people, duplicates
- **Places:** a map and list from GPS metadata, no AI needed.
- **People:** detect faces, compute an embedding per face, and compare it against a registry of known people (several confirmed embeddings per person) with a confidence threshold. Below the threshold, ask the user instead of assigning. This runs **on the phone** for new local photos and **in Actions** for imported photos; both write `people` ids into the same index, so one registry covers both sources.
- **Duplicates:** an exact match is the same content hash. A near-duplicate (resized or edited copy) is found by perceptual hash. A script is enough; no AI needed.

#### Also in scope for v1
Albums (manual), favourites, archive (hide without deleting), trash with recovery, search by date, place, person or album, screenshots grouped automatically by folder, and videos stored and indexed like photos (poster-frame thumbnail).

#### Later
Edits (crop, adjustments), shared albums, a locked folder, collages and highlights, and search by object or scene from image embeddings.

#### Storage growth
GitHub suggests keeping a repo under about 10 GB, so each storage repo runs an Action that records its **true size, including `.git` and `.github/`**, into the index. When a repo nears the limit the app creates the next repo (`my-photos-2`, `my-photos-3`, …) and new uploads go there. Each repo keeps its own index, the primary repo's manifest lists them all, and the app merges them, so which repo holds a photo is invisible to the user. Moving content between repos is described in the drive app idea and shares the same engine.

**Only the app crosses repos** (decided 2026-10-12, recorded in `depot/CONTRACT.md`, RokctAI/hardware#43). An Action's built-in token reaches only its own repo, and users are never asked to set up a secret or token, so:
- the app creates each new repo and installs its workflows;
- an import that fills its repo writes a note into it (`depot/jobs/<job>.json`: how far it got, `repo_full`) and stops;
- next time the app opens, it reads the note, creates the next repo, copies the note across and the import continues there.

A big import therefore pauses at each full repo until the app is next opened, and the app shows that as progress ("Importing… 12,000 of 40,000"), never as an error.

#### Pricing
Free for the gallery, backup and offline features. A paid unlock for the Google Photos import, which is what does the heavy migration work.

#### Shared engine with the drive app
The storage engine is **`depot_sdk`**, shared by this app and the drive app (RokctAI/hardware#42). It covers sign-in, repo setup, batched commits, the index, versions and the `/depot/setup` screen. Repo sharding and workflow install are still to come. This app configures it with `thumbnails: true` and `suggestedRepoName: my-photos`. The same engine allows a combined photos-and-drive app later.

#### Fleet rules this must satisfy
- This shell tracks zero `lib/` files and never edits `composer.json` as the source of truth. A change to the SDK list goes to the protocol template.
- Feature SDKs import only `base_sdk` (ADR-005). The photos SDK reaches depot through an interface in its own `domain/interface/` plus a host adapter in `templates/`, and opens storage setup by path (`/depot/setup`).
- Layout: `di/` is required. `application/` is split by feature, alongside `infrastructure/repositories/`, `domain/interface/`, and `infrastructure/database/` when the manifest declares Drift tables. Use Remixicon only and `tr_keys` for all UI text.
- Values a GitHub Action must find or act on (date, place, people, hash, repo path) are typed index fields, not hidden in a blob.
- The guided tour runs in demo mode and must never call real GitHub.

**Done for v0:** create an app account (offline is fine), sign in to GitHub, create or connect a repo, choose folders, batched backup with thumbnails and index, a thumbnail-first gallery that works offline, and an "on this day" memory that shows only when it scores above the threshold.
