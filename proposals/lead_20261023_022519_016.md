## Product shape

One desktop application with two deliberate modes:

**Play:** story library, creation using supported original seeds/premises, chat, cancel/retry, load/resume, player sheet, visible history, and model/status controls. This must become a usable local application, not merely a test dashboard or emulator wrapper.

**Story Lab:** opt-in, clearly spoiler-bearing inspection of a selected story/branch/revision. Inspect accepted events, state before/after a turn, player progression, NPC profiles, directed relationships, beliefs versus reality, summaries and their sources, unresolved threads, retrieved context, structured proposals, validation failures and model/runtime metadata. Start with tables/detail views; graph layout is not a first-play gate.

The observer selector is an inspection lens only. Looking as an omniscient developer must never make an NPC omniscient or change a player's permissions.

## Architecture direction (verify through D01)

- Keep the portable Rust engine authoritative for both desktop and Android. Keep Android Kotlin/Compose/JNI; no phone rewrite is required.
- Provisional desktop candidate: Tauri 2 with a TypeScript/React UI calling narrow Rust commands. Compare briefly against Compose Multiplatform Desktop given existing Kotlin UI/JNI work; select one with an ADR, not two production implementations. Framework choice is not pre-approved by this ticket.
- Windows x64 is the proposed first desktop target; confirm actual development OS/hardware in D01. Preserve portable contracts, but claim macOS/Linux support only after running the relevant builds and journeys.
- Reuse `crates/locallore` and extract a small host-neutral session/service module only when necessary. Do not create a speculative forest of empty crates. Proposed desktop paths are `apps/desktop/` and `docs/desktop/`.
- One shared Rust persistence layer owns schema/migrations and accepted state. No TypeScript/Kotlin SQL writers, separate desktop truth store, or SQLite schema controlled by a UI plugin.
- Reuse one inference interface, prompts, context compiler, validators, budgets, and event semantics. A desktop-specific hardware backend may differ from Android, but backend choice does not fork gameplay.
- Production assets and inference are local. Prefer an embedded native runtime, or a managed local worker over bounded stdio if justified. No required hosted API, separate user-managed server, cloud fallback, telemetry, or automatic downloads. Development build tooling is distinct from offline gameplay.

## First end-to-end acceptance story

Use the existing original potion/secret fixture rather than inventing incompatible lore. Spend the last potion helping its intended recipient; try to spend it again; make an unsupported ability claim; inspect the actual event and state diff. After persistence and real inference land, restart and continue in free text. The recipient remembers the help; an unwitnessed NPC does not learn it automatically; private facts never enter that NPC's generation context. Export a snapshot and show the source event for the memory. Later, import the portable archive on Android, compare canonical replay hashes, and continue without duplicating inventory or rewriting history.

Record separately: mechanical correctness, retrieval correctness, narrative use of retrieved facts, prose quality, and measured performance. A nice story is not proof of memory correctness; correct state is not proof of enjoyable prose.
