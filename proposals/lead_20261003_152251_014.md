## Summary
Epic: establish an extensive evaluation and validation setup that runs **only when relevant changes are made**, ensuring future web and Android releases are stable and autonomous.

## Scope

### CI/CD gating (change-based triggering)
- Path-filtered workflows: jobs run only when their relevant code paths change (e.g. `lib/**`, `web/**`, `android/**`, `functions/**`), avoiding wasted runs and flaky signal noise.
- Smoke tests on every affected build.

### Testing layers
- **Smoke tests**: fast, post-build sanity checks for web and Android (app boots, core routes render, auth screen reachable).
- **Playwright (web)**: E2E suite covering core flows — auth, inventory/shopping-list CRUD, transfers, modals, navigation.
- **Flutter integration tests (Android)**: run on Android emulator/device via `flutter test integration_test` and/or Flutter MCP / Android MCP tooling for device-driven verification.
- **Firebase emulator-backed tests**: Firestore rules, auth, and seeding flows against local emulators (extends #123/#124).
- **Unit tests**: targeted unit tests where they are a better fit (models, services, validation logic); the suite should be **mostly integration tests** by default.

### Static analysis & review tooling
- Copilot code review agent
- Qodo (PR review / merge suggestions)
- CodeRabbit (automated review and summaries)
- `flutter analyze`, lint rules, and format checks as required gates
- Generated-code drift detection (extends #122)

### Release stability
- Block release workflows (#145) until the full validation matrix passes for the changed platform(s).
- Artifact validation for web and Android builds; retry/quarantine strategy for flaky tests.

## Acceptance criteria
- [ ] Path-filtered CI that only runs relevant jobs on change
- [ ] Smoke test suites for web and Android
- [ ] Playwright E2E suite for web wired into CI
- [ ] Flutter integration tests for Android wired into CI (emulator/MCP based)
- [ ] Static analysis gates: Copilot, Qodo, CodeRabbit, `flutter analyze`
- [ ] Mostly-integration test suite with unit tests only where they fit better
- [ ] Release workflows gated on validation success

## Cloud testing & release tooling (research findings)
- ⚠️ **Firebase Test Lab is deprecated** (full shutdown Sept 30, 2027; migrate to Google Cloud **Developer Device Platform**). Decision: adopt now + plan migration, or go directly to the alternative.
- **Firebase Test Lab / Developer Device Platform**: run Flutter integration tests on real/virtual devices via `gcloud firebase test android run --type instrumentation` from CI (service-account auth) — 1–2 representative devices per PR, wide matrix nightly/pre-release.
- **Patrol**: extends `integration_test` with native interactions (permission prompts, system dialogs, native WebViews) — needed for camera/barcode scanning flows; compatible with device farms.
- **Firebase App Distribution**: pre-release builds to testers/QA (up to 500 testers, 2 GB artifacts) as a release-gate step.
- **Codemagic** (per #82 deployment advice): Flutter-first CI/CD that also **offers testing** — runs unit/widget/integration tests on its own infrastructure, integrates with **Firebase Test Lab** device farms for cloud device testing, and publishes to Firebase App Distribution / Play Store via `codemagic.yaml`. Candidate to host the release workflow (#145) and cloud device testing.
- **Firebase Crashlytics**: crash/ANR monitoring feeding the autonomous fix loop.
