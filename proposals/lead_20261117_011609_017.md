# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**v0.1.0 — Prepare and verify the first GitHub release**

*Project description:*
## Summary

Prepare SOVTrace for its first formally versioned GitHub release, `v0.1.0`.

The release will identify and document the existing application. It must not introduce new application functionality, change dependencies or establish additional distribution channels.

This issue covers release preparation, documentation, candidate verification and the definition of publication checks.

**Creating the Git tag or publishing the GitHub Release is explicitly out of scope for implementation of this issue.** Both require separate owner authorisation after the preparation PR has merged and the exact release candidate has been verified.

## 1. Objectives

Deliver a reviewable, reproducible release candidate that:

1. Accurately describes the capabilities and limitations of SOVTrace v0.1.0.
2. Removes documentation statements that will become inaccurate when the version is released.
3. Contains concise, manually reviewed release notes.
4. Preserves existing installation, privacy, security and support disclosures.
5. Passes the existing offline and security verification gates.
6. Can be installed and demonstrated from an extracted source archive.
7. Has a defined, fail-closed publication and post-publication verification procedure.
8. Can be published subsequently from an exact, independently reviewed and owner-approved commit.

The first release is a **GitHub source release**, not a PyPI or binary distribution.

## 2. Accepted release policy

The following decisions are fixed for this issue:

| Concern | Decision |
|---|---|
| Release version | `v0.1.0` |
| Python package version | `0.1.0` |
| Publication channel | GitHub Releases only |
| Git tag | Annotated, unsigned |
| Tag target | Exact reviewed and owner-approved commit SHA |
| Tag mutation | No overwriting, moving or force-updating |
| Release classification | Stable, not prerelease |
| Latest-release designation | Mark as latest |
| Release notes | Manually reviewed Markdown file committed to the repository |
| GitHub Release description | Contents of the reviewed Markdown file |
| GitHub-generated source archives | Enabled through ordinary GitHub release behaviour |
| Additional release assets | None |
| PyPI publication | Not authorised |
| Application functionality | No changes |
| Application dependencies | No discretionary changes |
| ADS installation | Out of scope |
| Live-model evaluation | Not required; must not be initiated without separate authorisation |
| Independent review | Mandatory |
| Tag and release publication | Separate explicit owner authorisation required |

These decisions must not be reopened during implementation unless a concrete technical conflict makes compliance impossible.

## 5. Workstream C — Prepare release notes

Create:

`docs/releases/v0.1.0.md`

This file is the authoritative proposed release description. Its contents will subsequently be supplied unchanged as the GitHub Release notes.

Use concise Markdown suitable for direct rendering on GitHub.

### Required contents

#### Overview

Describe SOVTrace as a local Python CLI for supported insurance Schedule of Values spreadsheet queries.

Identify this as the first formally versioned GitHub source release.

#### Capabilities

Accurately describe:

- Supported `.xlsx` ingestion into local SQLite.
- Supported schema concepts and bounded question operations.
- Optional model-assisted schema interpretation and SQL generation.
- Independent validation of generated SQL.
- Read-only, restricted SQLite execution.
- Exact integer micro-USD arithmetic.
- Source-cell evidence retention and reconciliation.
- Resource ceilings and fail-closed behaviour.

Do not imply that the application interprets arbitrary spreadsheet formats or arbitrary natural-language questions.

#### Getting started

State the prerequisites:

- Python 3.12.
- `uv`.
- Extracted source archive or repository checkout.
- Network access for ordinary dependency installation, where necessary.

Include the minimum useful offline demonstration commands:

```sh
uv sync --locked
uv run --locked sovtrace --version
uv run --locked python scripts/demo.py
```

Reference the README for more extensive commands and examples.

Explain that the GitHub-generated source archives contain project source, not preinstalled dependencies or a standalone executable.

#### Offline verification and evaluation

Describe the existing deterministic demonstration and synthetic evaluation.

Use exact fixture, question and test counts only when supported by verification of the release candidate.

Clearly distinguish:

- Deterministic SQL execution and evidence reconciliation.
- Simulated model behaviour and predefined demonstration SQL.
- Synthetic evaluation outcomes.
- Live model interpretation, which is not established by these tests.

Do not claim measured live-model accuracy or guaranteed semantic correctness.

#### Optional model-backed operation

Explain that the existing authenticated workflow requires authorised model access and may incur charges.

Direct users to the README's privacy and data-exposure documentation.

Make clear that workbook headings, questions and semantic schema information may be transmitted to an external model provider, depending on the selected workflow.

Do not claim that all sensitive information remains local or that provider-side retention is necessarily zero.

#### Limitations

Summarise the most important boundaries:

- Limited supported workbook structures and concepts.
- Restricted SQL and question operations.
- Finite resource ceilings rather than unlimited resource-exhaustion protection.
- Source reconciliation does not prove correct interpretation of arbitrary user intent.
- No guarantee of support or maintenance for a particular release.

#### Licence and security

Identify the MIT licence.

Link to `LICENSE` and `SECURITY.md` using links that work from the GitHub Release page, rather than relying on relative Markdown paths that only resolve correctly inside the repository directory.

Explain that confidential vulnerability reports should use the repository's GitHub Private Vulnerability Reporting facility.

### Prohibited claims

Do not describe SOVTrace as:

- Production-ready or production-certified.
- Compatible with arbitrary Excel workbooks.
- A general-purpose natural-language-to-SQL solution.
- Guaranteed to answer every supported-looking question correctly.
- Independently validated for live-model accuracy.
- Fully offline in every operating mode.
- Providing universal security or resource-exhaustion protection.

Do not invent benchmark results, model accuracy measurements or security certifications.

### Release-note consistency

Keep the notes accurate against the candidate source tree.

Avoid embedding a candidate SHA in the committed release notes: the SHA will change when those notes are committed and the PR is merged.

The final SHA belongs in the release authorisation and verification record.

**Deliverable:** A complete proposed `docs/releases/v0.1.0.md`, committed and independently reviewable before publication.

## 6. Workstream D — Verify the release candidate

Reuse existing project verification rather than creating a second release-specific testing framework.

### 6.1 Existing automated checks

The preparation PR must pass the existing offline verification workflow and security verification workflow.

All required jobs must succeed.

Specifically preserve and verify:

- Locked dependency installation.
- Ruff lint and formatting checks.
- Pyright.
- pytest.
- CLI help/version smoke tests.
- Both existing demonstration formats.
- Five-step engineering case-study walkthrough.
- Synthetic offline evaluation.
- Existing secret-scanning controls.
- Existing dependency-audit controls.

Any failure must be investigated and dispositioned.

Do not treat an unavailable external security advisory service as a successful or waived audit.

Do not modify security tooling or weaken existing verification requirements to achieve a green result.

### 6.2 Version and metadata checks

Verify:

- `pyproject.toml` declares `0.1.0`.
- The CLI reports the expected application version.
- Python requirements remain consistent with the documented setup.
- MIT licensing and package licence metadata remain intact.
- The lockfile remains unchanged unless a separately authorised correction is necessary.

No version bump is required.

### 6.3 Extracted-source-archive smoke test

The release must be usable from the source archive that a GitHub user receives.

Before the tag exists, create a temporary source archive from the proposed exact commit using `git archive`, or an equivalent deterministic export of the tracked release tree.

Do not use an uncommitted working directory as a substitute.

Extract the archive into a clean, disposable location without relying on `.git` metadata or the original checkout.

Within that extracted tree:

1. Confirm the expected source files and project metadata are present.
2. Confirm that `LICENSE`, `README.md`, `SECURITY.md` and the release notes are included.
3. Confirm the declared version is `0.1.0`.
4. Install using the committed lockfile and Python 3.12.
5. Confirm the CLI reports `0.1.0`.
6. Run the deterministic text demonstration.
7. Run the JSON demonstration.
8. Run the synthetic offline evaluation.
9. Run the case-study walkthrough.

Use a fresh disposable environment and no model-provider credentials.

The test must not make live model requests.

Record the commands and results.

Do not require a new permanent CI workflow for this smoke test. Reuse existing scripts and tools where possible.

A failure attributable to missing Git metadata, missing source files, broken installation or unexpected archive assumptions is release-blocking.

A separately built wheel or sdist is not required for this source-only release.

### 6.4 Security and content review

Review files added or changed during release preparation for:

- Secrets or credentials.
- Restricted data.
- Unexpected repository or organisation references.
- Unintended source or workbook content.
- Misleading security or privacy claims.

Verify that the release preparation has not introduced new disclosure surfaces.

Use the existing security workflow as the principal automated control.

Do not conduct an unrelated historical investigation without new evidence of a material problem.

**Deliverable:** Reproducible smoke-test instructions and a verification summary attached to the PR.

## 7. Workstream E — Define the controlled publication procedure

Document the exact intended publication procedure in the PR description or a concise release-preparation report.

Do not execute it during this issue.

The procedure must require the following gates.

### Gate 1 — Preparation merged

- The preparation PR has received independent review.
- All material review findings have been resolved.
- The PR has been marked ready to merge.
- The PR has merged into `main`.
- Final `main` CI and security verification have passed.

### Gate 2 — Exact-candidate reconciliation

Immediately before requesting release authorisation:

- Fetch current `main` and tags.
- Confirm the local checkout is clean.
- Identify the full candidate commit SHA.
- Verify that the candidate is the intended current `main` commit.
- Confirm package version `0.1.0`.
- Confirm `v0.1.0` does not exist locally or remotely.
- Confirm no GitHub Release named `v0.1.0` exists.
- Review the exact release-notes content.
- Review any changes since the preparation PR was accepted.
- Confirm the exact candidate's relevant CI and security results are successful.

A changed `main`, unexpected tag, existing release, failed verification or unreviewed source change must stop publication pending reconciliation and renewed approval.

### Gate 3 — Owner approval

Present the owner with:

- Exact release candidate SHA.
- Proposed tag name and type.
- Proposed GitHub Release title and classification.
- Complete release notes.
- Verification evidence.
- Exact proposed publication operations.
- Any residual limitations or unresolved concerns.

Obtain explicit authorisation for the identified SHA and operations.

An approved preparation PR is not sufficient authorisation.

### Gate 4 — Tag creation

After authorisation, create an annotated, unsigned Git tag:

`v0.1.0`

The tag must point to the approved commit.

Do not:

- Automatically tag a moving branch reference.
- Retarget an existing tag.
- Force-push a tag.
- Delete and recreate a tag.
- Substitute another commit without renewed owner approval.

Verify the annotated tag resolves to the approved commit before and after pushing it.

### Gate 5 — GitHub Release publication

Create the GitHub Release with:

- Tag: `v0.1.0`.
- Title: `v0.1.0`.
- Classification: stable, not prerelease.
- Latest-release designation: enabled.
- Release notes: contents of `docs/releases/v0.1.0.md`.
- Uploaded assets: none.

Use GitHub's existing source archive functionality.

When using `gh release create`, specify `--verify-tag` so an absent tag cannot be silently created against an unintended commit.

Do not publish to PyPI or any additional distribution service.

### Gate 6 — Post-publication verification

Independently verify:

1. GitHub displays the release publicly.
2. The release is not marked prerelease.
3. The release is designated latest.
4. The tag is annotated and resolves to the approved SHA.
5. The release notes match the approved file.
6. No unintended binary or package assets were uploaded.
7. The source ZIP and tar archive are anonymously downloadable.
8. The extracted source contents match the tagged release tree.
9. Required documentation and licence files are present.
10. The extracted ZIP supports the minimum offline installation and demonstration.
11. The README and security policy remain truthful after publication.

Check the actual published GitHub archives; a pre-publication `git archive` test alone does not satisfy this final requirement.

If any verification fails, report the observed state and seek owner direction. Do not silently move tags, replace archives or delete published releases.

## 8. Implementation boundaries

### In scope

- Bounded repository and release-state inspection.
- Minimal release-status documentation corrections.
- `docs/releases/v0.1.0.md`.
- Release-specific verification using existing tooling.
- Temporary archive extraction and smoke testing.
- Reproducible verification evidence.
- Documentation of the subsequent publication procedure.
- A preparation PR for independent review.

### Out of scope

- Creating or pushing `v0.1.0`.
- Creating, drafting or publishing a GitHub Release.
- Publishing to PyPI.
- Uploading wheels, sdists or binary assets.
- Adding package-distribution automation.
- Changing application functionality.
- Adding supported workbook or query types.
- Updating runtime or development dependencies.
- Changing the lockfile.
- Installing ADS.
- Running unauthorised live-model evaluations.
- Introducing new model providers.
- Redesigning CI.
- Introducing release orchestration infrastructure.
- Changing licensing or ownership.
- Reopening previously accepted historical investigations without new contradictory evidence.
- Expanding support, compatibility or maintenance promises.

If a necessary fix crosses these boundaries, stop and request a separate decision rather than silently expanding scope.

## 9. Implementation and PR workflow

Implement on a dedicated issue branch from the current public `main`.

The implementation agent should:

1. Perform repository reconciliation.
2. Report genuine conflicts before proceeding.
3. Make the smallest necessary documentation changes.
4. Add the release notes.
5. Run relevant local verification.
6. Perform the extracted-source-archive smoke test.
7. Confirm no unintended dependency or functional changes.
8. Open a draft PR referencing this issue.
9. Include the verification and reconciliation evidence in the PR.
10. Stop before merging, tagging or release publication.

Do not request repeated optional Copilot reviews.

Allow normal repository automation to run. If Copilot reviews automatically, incorporate material findings into the ordinary review process.

The PR requires independent ChatGPT review and resolution of material findings before it can be marked ready to merge.

The implementing agent must not self-authorise final release operations.

## 12. Definition of done

The owner can identify an exact, independently reviewed and verified commit suitable for a subsequent v0.1.0 release decision.

The issue may then be closed as **release preparation complete**.

Actual creation and verification of the `v0.1.0` tag and GitHub Release remain separate owner-controlled operations.
