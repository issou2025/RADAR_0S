# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Autonomy 2/4: plan-level approval with an enforced envelope (one approval per job instead of per call)**

*Project description:*
## Goal

Replace **one approval per write call** with **one approval per plan**. The agent submits a plan: what it intends to do, with which tools, on which elements, within which limits (the *envelope*). The user approves it once in the Pending tab. Every later write call that stays inside the envelope runs without a prompt; anything outside it falls back to today's per-call approval. The safety model is unchanged: destructive tools always need a manual approval, approvals bind to the document, and everything the plan does is recorded against a checkpoint (#98) so it can be reviewed and rolled back.

| Tool | Permission | Purpose |
|---|---|---|
| `revit_plan_submit` | RequiresApproval | Proposes a plan; the approval activates it and creates its checkpoint |
| `revit_plan_status` | ReadOnly | State, counters, remaining budget, violations so far, checkpoint id |
| `revit_plan_close` | ReadOnly (model) | Ends a plan early; returns the final counters and a checkpoint diff summary |
| `revit_plan_use` | bridge-only | Sets or clears the plan id the bridge attaches to every following request |

Depends on #98 (checkpoints, warnings). Needed by #100 (jobs run under a plan).

## Why

`ExternalEventHandler.ExecuteItem` intercepts every `RequiresApproval` tool and parks it in `ApprovalService` (cap 64, 10 minutes). For a 40-step task the user clicks Approve 40 times, or switches Direct Edit on and loses every guardrail. Neither is unattended work. A plan is the middle ground: the user reads one summary, sets the limits, and walks away; the connector enforces the limits mechanically.

## Design

### Plan model (Addin, pure)

```csharp
sealed class PlanEnvelope
{
    string[] Tools;                 // write tool names the plan may run without a prompt (never a DestructiveRequiresManualApproval tool)
    long[] ElementIds;              // explicit allow list, max 20 000; empty = not restricted by id
    string[] Categories;            // allowed categories for touched elements; empty = not restricted by category
    long[] LevelIds;                // optional
    long[] ViewIds;                 // optional: view-specific work (tags, text, detail items) only in these views
    string[] Worksets;              // optional
    bool AllowCreate = true;        // may add elements
    bool AllowModify = true;
    int MaxElementsPerCall = 500;   // distinct touched ids in one call
    int MaxElementsTotal = 2000;    // distinct touched ids over the plan
    int MaxCalls = 100;
    int ExpiresMinutes = 120;       // max 480
    bool Strict = false;            // false: incidental categories (tags, dimensions, wires…) modified as a side effect do not count
}

sealed class Plan
{
    string Id;                      // "plan-" + 6 hex
    string Title;
    string[] Steps;                 // human-readable intent lines, shown to the user, informational
    PlanEnvelope Envelope;
    string ClientName;
    object? DocumentToken; string DocumentTitle; string ModelId;
    string CheckpointId;            // created on activation with Scope = envelope ids/categories
    PlanState State;                // Proposed | Active | Exhausted | Expired | Revoked | Closed
    DateTimeOffset CreatedAt, ActivatedAt, ExpiresAt;
    int Calls;  HashSet<long> Touched;  int Added, Modified, Deleted;
    List<PlanViolation> Violations; // {at, tool, reason, ids[]}
}
```

### Flow

1. Agent calls `revit_plan_submit` with `title`, `steps[]`, `envelope{}`. The tool is `RequiresApproval`, so `ExecuteItem` parks it as usual; `ApprovalSummaryBuilder` renders a multi-line summary (below). In Direct Edit the plan activates immediately (Direct Edit already means "approve everything"; the plan still enforces its limits, which is the point of using one even then).
2. The user approves in the Pending tab. The approved request executes: `PlanService.Activate(plan, doc)` creates the checkpoint through the #98 API (`CheckpointService.Create(doc, scope: envelope ids/categories, title: plan title)`), stores the plan, returns `planId`, `checkpointId`, `expiresAt`, the resolved limits. The agent sees it through `revit_get_approval_status` like any approval.
3. The bridge attaches the plan id to every later request (see "Bridge"). The add-in reads `planId` from `request.Arguments` in `ExecuteItem`.
4. For a `RequiresApproval` tool with a `planId`, `ExecuteItem` runs `PlanService.TryAuthorize(plan, tool, request, uiapp)`:
   - plan `Active`, not expired, same document (`ApprovalContextGuard.IsValid` with the plan's document token — **not** the change stamp; a plan survives its own writes);
   - `tool.Name ∈ Envelope.Tools`; `Calls < MaxCalls`;
   - **pre-check** from the arguments (`PlanArgumentScope.ExtractTargets`): collects the ids the call names (`elementIds`, `circuitIds`, `viewIds`, `sheetIds`, `tagIds`, `textNoteIds`, any `*Id`/`*Ids` key, and `elementId` inside object arrays such as `moves[]`, `changes[]`, `rows[]`, `rotations[]`, `elevations[]`), resolves `useSelection` to the current selection, and reads `category`/`categories`/`limit`. Refuses when a named id is outside `ElementIds` (when set), when a named category is outside `Categories` (when set), when `limit` or the id count exceeds `MaxElementsPerCall`, or when the tool creates elements and `AllowCreate` is false (tool list: `revit_place_*`, `revit_copy_elements`, `revit_create_*`, `revit_duplicate*`, `revit_draw_circuit_arcs`, `revit_create_text_notes`, `revit_place_tags`, `revit_place_dimensions`, `revit_annotate_detail_lines`, `revit_create_sheets_from_table` — keep this in one static table with a unit test that every registered write tool is classified).
   - A refusal does **not** fail the call: it falls through to the normal approval path with `warnings += "Plan <id>: <reason>; this request waits for approval."` so the agent is never blocked harder than today.
5. Authorized call: `ExecuteItem` marks the request approved (`request.IsApproved = true`, so the activity log records it) and runs the tool inside a **`TransactionGroup`** named `Plan <title>: <tool>`:
   - before: `PlanChangeRecorder.Begin(doc)` — a per-call collector fed by the same `DocumentChanged` hook as #98 (added/modified/deleted ids of every transaction committed during this call);
   - run `tool.ExecuteAsync` exactly as today (tools using `RevitTransactionRunner.Run` see `doc.IsModifiable == false` inside a group and open their own `Transaction`, which is correct);
   - after: **post-check** (authoritative) on the recorded ids: netted distinct ids; drop incidental categories unless `Strict` (incidental = OST tags of any kind, Dimensions, Wires, Spot elevations, Room/Space tags, Viewports, Revision clouds, Elevation marks, Section/Callout heads — one static list `PlanIncidentalCategories`); refuse when any id was deleted (plans never auto-approve deletes: `DestructiveRequiresManualApproval` tools are excluded from `Envelope.Tools` at submit time, so a delete here is a side effect the user did not approve), when an added id appears and `AllowCreate` is false, when a modified/added id is outside `ElementIds` (when set) or its category outside `Categories` (when set), or when distinct touched ids exceed `MaxElementsPerCall` or would push the plan over `MaxElementsTotal`;
   - violation → `group.RollBack()`, record `PlanViolation`, return `Status = "plan_envelope_violated"` with the offending ids, categories and the limit, and `Success = false`. No approval fallback here: the call already ran and was undone, the agent must narrow it or ask for a new plan;
   - no violation → `group.Assimilate()` (one Undo entry per authorized call), update counters, `Status` unchanged. When `Touched.Count ≥ MaxElementsTotal` or `Calls ≥ MaxCalls` the plan becomes `Exhausted`; its result carries `warnings += "Plan exhausted"`. Later calls fall back to per-call approval.
   - A tool that throws inside the group: roll the group back, report `transaction_failed` as today.
6. `revit_plan_close` (agent) or **Revoke** (user, Pending tab) ends the plan; both return/show the counters and the `revit_checkpoint_diff` summary. `PanicStop` revokes every plan. Expiry is checked on every authorization and by the UI timer that already refreshes `RecentApprovalOutcomes`.

### What a plan can never do

- Auto-approve a `DestructiveRequiresManualApproval` tool (delete, remove links, rollback). `revit_plan_submit` refuses such names in `Envelope.Tools` with `validation_failed`.
- Act on another document than the one it was approved for.
- Exceed its counters; a single call that would exceed `MaxElementsTotal` is rolled back whole (no partial credit).
- Be created without going through the approval queue in ApprovalRequired mode.

### Approval summary

Add `"revit_plan_submit" => PlanSummary.Build(request)` to `ApprovalSummaryBuilder`. Multi-line (check `PendingApprovalItem` and the DataTemplate in `McpWindow.xaml`; allow `TextWrapping="Wrap"` with a max height and a tooltip holding the full text):

```
PLAN: Tag all sockets on level 2 (12 steps)
Tools: revit_place_tags, revit_set_parameter, revit_move_elements
Scope: 318 listed elements · categories Electrical Fixtures, Electrical Equipment · views: L2 Power plan
Limits: ≤ 500 elements per call, ≤ 2000 in total, ≤ 100 calls, expires in 120 min, may create, may not delete
Steps: 1. Read sockets on level 2 … 12. Verify tags
Everything runs without further prompts inside these limits and is undoable per call; a checkpoint is created for review and rollback.
```

### UI

In the Pending tab, below the pending list, a **Plans** section: `ObservableCollection<PlanItem>` (title, client, state, `Calls/MaxCalls`, `Touched/MaxElementsTotal`, expires in, violations count) with a **Revoke** button and a **Show changes** button that selects the touched elements in Revit (reuse the model page `select` path; #100 replaces it with the report page link when one exists). The Pending tab header counts active plans too: `PENDING (2) · PLANS (1)`.

### Bridge

- `revit_plan_submit`, `revit_plan_status`, `revit_plan_close` as ordinary `[McpServerTool]` methods (submit is not `ReadOnly`).
- `revit_plan_use planId` is bridge-local (no pipe call): stores `_activePlanId` on `RevitPipeClient`; empty clears. `SendAsync` adds `["planId"] = _activePlanId` to the arguments of every request whose tool is not read-only (use the catalog's `ReadOnly` flag so reads are not polluted) when the caller did not pass one. `revit_plan_submit`'s result handler sets `_activePlanId` from the returned `planId` automatically, so the usual flow needs no extra call; `revit_get_approval_status` on the submit's requestId confirms activation.
- `revit_tools_call` passes arguments through unchanged, so a client that calls writes that way still gets the attached id.
- Group: all four in `autonomy` (#98). Server instructions: one sentence — "For several write steps submit one revit_plan_submit with the ids and tools you will use; approved plans run without per-call prompts inside their limits."

### Status codes

`plan_not_found`, `plan_not_active` (with the state), `plan_envelope_violated`, `plan_exhausted` (informational in `warnings`). Add to the `Status` comment in `McpToolResult.cs`.

### Activity log

`LogEntry` gets `PlanId` (string, nullable) and `PlanCheck` (`authorized` | `fallback:<reason>` | `violated`). Plan activation, close, revoke and each violation are logged as entries with tool `revit_plan_*` so an unattended session can be audited from the log alone.

## Acceptance criteria

- One approval activates a plan; writes inside the envelope run with no prompt in ApprovalRequired mode; writes outside it fall back to a prompt with the reason in `warnings`.
- A post-check violation rolls the whole call back (`TransactionGroup.RollBack`), the model is unchanged, the response names the ids and the limit.
- Destructive tools are never auto-approved by a plan, in any mode.
- A plan binds to its document; activating the other document and calling with the plan id falls back to a prompt with `plan_not_active`.
- Counters, exhaustion and expiry behave as specified and are visible in `revit_plan_status` and the Pending tab.
- Every authorized call is one Undo entry in Revit, named after the plan and tool.
- Activity log entries carry `PlanId` and `PlanCheck`.
- Unit tests green, both Revit targets build, benchmark report committed. No new types in `RevitMCP.Core` beyond the two `LogEntry` fields.
