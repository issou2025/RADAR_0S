# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Box bodies: the diagnostics and Measure say why each element stayed a box, by class and reason**

*Project description:*
## What

The export's diagnostics count the bodies it writes as record boxes (`exported.bounding_box_bodies`) and the decisions log lists each as `body_is_record_box`, but neither says why the element's saved mesh was not used. What keeps a box a box has been found by one-off probes on one file each time (RE-385's table for Snowdon Towers Electrical, RE-397's for the BIM4LCA office's railings), and the next decoder to write was chosen by hand from them.

On the office as built, 183 elements are record boxes: 97 `IfcSanitaryTerminal` (median fill 0.20 of the box), 41 `IfcRailing` (0.001), 30 `IfcFurniture` (0.06), 14 `IfcStair` and 1 `IfcCurtainWall` (`box_bodies_vs_ifc.txt`, Measure 42862248369). The reason is known for the railings only.

## Done when

- The diagnostics say, per reason, how many of the boxed elements it holds, from the saved-mesh pass (`saved_meshes::attach_scoped_with_control` already knows each): no saved graphics for the element, an empty mesh, a Tag several entities carry, a partial mesh with the diagnostic kinds that made it partial (digits written as `#`), and the boxes that were never offered a mesh (a release outside 2023 to 2027). Documented in `docs/export-diagnostics.md` and `docs/schemas/export-diagnostics.schema.json`.
- Measure's summary prints those counts across the run, head beside base, next to the box census, so a change that moves boxes says which reason it took them from, and the next decoder is chosen by the count it would clear.
- The per-class table of `box_bodies_vs_ifc.py` and the reasons agree on the total.
