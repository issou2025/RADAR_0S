## Why

The Dart/Flutter adapter (#790, unreleased) has been measured on Windows desktop (`-d windows`), the Android emulator, and (in progress) Chrome. macOS desktop, the iOS simulator and physical iPhones have never been run. v0.26.0 wants to say what works on Apple platforms, with numbers, and the test suite should carry the cases that are green. This ticket is a self-contained brief to run from Claude Code on a Mac (the iMac Pro), in parallel with the Windows-side work on #882 / #876 / #877.

Scope: **measure and record; file what breaks.** Adapter changes found here come back as issues (or a separate PR if trivial), not into the measurement PR.

## 1. Toolchain check first (stop early if the SDK refuses)

- `flutter doctor -v` — record Flutter and Dart versions, Xcode version, CocoaPods, and every red/yellow line verbatim.
- A 2017 iMac Pro may cap the macOS version, and Flutter stable may require a newer Xcode than that macOS allows. If `flutter doctor` says the Xcode is too old: record the verdict, try the newest Flutter release whose Xcode floor the box meets (`fvm` or a second checkout — only if it is a quick install), and otherwise stop with the facts recorded. Do not spend the session fighting Xcode.
- iOS simulator runtime present (`xcodebuild -downloadPlatform iOS` if not), `xcrun simctl list devices available` shows at least one iPhone; `open -a Simulator` once so the first boot is not timed into a measurement.
- Node 22+, pnpm per the repo's `packageManager` pin (`corepack enable`), a clone of `debugmcp/mcp-debugger` on `main`, then `pnpm install` and `npm run build`.

## 2. Existing suites as they are

`flutterDesktopDeviceId()` (`tests/e2e/dart-example-utils.ts`) already returns `macos` on darwin, so the desktop cases run unchanged:

```
pnpm exec vitest run --project e2e tests/e2e/mcp-server-smoke-dart.test.ts tests/e2e/mcp-server-smoke-dart-attach.test.ts tests/e2e/mcp-server-smoke-flutter.test.ts tests/e2e/mcp-server-logpoints.test.ts -t 'Dart|dart|Flutter'
```

Record pass/fail per case and the wall time of the `flutter run -d macos` case (first run of the fresh example is a cold build; run twice). Anything red: proxy log at `sessions/<id>/run-*/proxy-*.log` says why; file it.

## 3. Measurements through the server

Drive `dist/index.js` over stdio the way `tests/e2e/mcp-server-smoke-flutter.test.ts` does (its `waitForPause` helper slices `wait_for_stop` in ≤45 s calls — the MCP client's request cap is 60 s). The example is `examples/dart/flutter_probe` (`prepareFlutterProbe()` generates the platform folders; add `ios` to the `flutter create --platforms` list for this work). Breakpoint markers in `lib/main.dart`: `BP-BUILD`, `BP-INCREMENT`, and `BP-TICK` once the Windows-side PR for #882 lands (a periodic timer that fires on its own — until then use `BP-BUILD`, which fires on launch and on every rebuild).

For each target record: launch → first stop (cold / warm), top frame name, `get_local_variables` and `evaluate_expression counter` shapes, `get_output` lines of note, what `close_debug_session` does to the app and to the process table, and whether the session ends `terminated` without `exited` (the Flutter adapter does on Windows).

1. **macOS desktop**: `start_debugging { scriptPath: lib/main.dart, dapLaunchArgs: { stopOnEntry: false, cwd: <probe dir>, deviceId: "macos" } }` with a breakpoint on the marker line.
2. **iOS simulator**: boot one (`xcrun simctl boot <udid>`), same launch with `deviceId: "<udid>"`. Time the first build separately (it is minutes); then warm.
3. **Attach to an app the simulator is already running**: start it outside the debugger with `flutter run -d <udid> --machine`, read `app.debugPort` → `params.wsUri` from the JSON stream, then `attach_to_process { adapterConfig: { runner: "flutter", deviceId: "<udid>", cwd: <probe dir>, vmServiceUri: <wsUri> } }` with a breakpoint set first. Record whether it reaches `flutter.appStarted` and hits. On the Android emulator the host-forwarded URI does not connect (#882, under measurement on Windows); the simulator has no adb forward, so this answers whether the plain recipe works on iOS. Detach: the app must stay alive.
4. **Physical iPhone** (if one is available: Developer Mode on, trusted, cable first; wireless second): launch and attach as above with its device id. Record signing prompts/steps needed, since they decide whether this is documentable.
5. **Widget test and `integration_test`**: `flutter test` through the test adapter (`runner` auto-detects from the `test/` path) — already covered by the suite on desktop; run `integration_test/` with `deviceId: "<udid>"` on the simulator.
6. **Hot restart / hot reload**: once the Windows-side PRs for #876 merge, `restart_debugging` (DAP `restart` = hot restart) and `hot_reload` on the running `-d macos` and simulator sessions — time to the re-hit. Before they merge, skip this item; do not drive raw DAP for it.
