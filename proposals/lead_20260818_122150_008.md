## Context

Android already has a share-sheet entry point: `SaveWebClipActivity.kt` + `SaveWebClipScreen.kt` + `SecureStorage.kt`. A dialog-style activity, launched via an `ACTION_SEND` intent filter, extracts a shared URL (and optional title), shows a small Compose UI with loading/success/error states, and POSTs `{url, title}` to `$API_BASE_URL/reading-list` with a Bearer token. The token comes from a native `SecureStorage` object (Keystore-encrypted) that reads the same key Flutter's Dart `SecureStorage` factory (`lib/core/platform/secure_storage.dart`) writes on Android, via a MethodChannel — so the native activity and Flutter agree on one physical store.

iOS has none of this: the Dart factory's `_` branch uses `flutter_secure_storage` directly (no native Swift reader), there's no entitlements file for `Runner`, and no mechanism for getting `API_BASE_URL` into compiled iOS code.

Decisions already made:
- Build an iOS-native secure storage shared between Flutter and native code, mirroring Android's shape (not `flutter_secure_storage` + `groupId`).
- macOS is out of scope.
- The POST must survive the extension being dismissed (mirroring Android's process-lifetime `SaveScope`), in scope for this phase.

## Goal

Sharing a URL to Paperdoll from iOS's share sheet adds it to the reading list, with UX equivalent to Android's: a small native dialog, loading → success/error, works only when already logged in (otherwise an "unauthenticated" state, same copy as Android). Lives entirely in a Share Extension, reusing Flutter's existing auth token, no second login. macOS untouched.

## Codebase changes

Mirrors the Android architecture piece for piece, substituting Apple's App Extension mechanism for Android's exported activity.

### Share Extension target

SwiftUI, no Flutter/plugins — entry point, replaces `SaveWebClipActivity`. `NSExtension` activation rule in `Info.plist` matches shared URLs and text.

### URL extraction

Reads the extension's `NSExtensionItem` attachments; prefers a `public.url` provider (what Safari gives), falls back to `public.plain-text` scanned with `NSDataDetector(types: .link)`, same reason Android's `extractUrl()` handles both shapes. Title is best-effort only (no reliable subject-like field on iOS extension items); the server backfills the real title async either way, so this isn't a parity requirement.

### `SecureStorage.swift`

Keychain item (`kSecClassGenericPassword`), mirrors `SecureStorage.kt`. Added to both `Runner` and extension target membership. Dart's `secure_storage.dart` gets an `.iOS` branch (MethodChannel, same shape as `.android`), replacing `flutter_secure_storage` there (that plugin narrows to macOS-only usage).

Needs a **Keychain Sharing** entitlement on both targets so they see one physical item: access group `$(AppIdentifierPrefix)dev.norelease.paperdoll.shared`.

### `API_BASE_URL` delivery

Generated `APIConfig.xcconfig`, included by both targets, populated by a Run Script build phase that runs on *every* build (unlike `Version.xcconfig`, which is CI-only via an `#include?` that's silently absent locally, because local builds don't care about release versioning — this one has to work locally too, since the extension needs to reach the local dev server). Locally the script reads `client/.env` (same file Android's Gradle build reads); in CI, `ci_post_clone.sh` gets extended to emit it from the decoded dart-defines env, using the same `cat > ... <<EOF` pattern it already uses for `Version.xcconfig`.

Caution: xcconfig treats `//` as a comment delimiter, so the URL value needs quoting/escaping.

### Background POST survival

A background `URLSession` upload task (`URLSessionConfiguration.background`, `sharedContainerIdentifier` pointed at an App Groups container). The body is written to a temp file first (background tasks are file-based, no in-memory bodies), then handed to the system daemon (`nsurlsessiond`), so the transfer outlives the extension process — the iOS equivalent of `SaveScope`. `Runner`'s `AppDelegate` implements `handleEventsForBackgroundURLSession` to reconnect and receive the result once the extension is gone, silently, on both success and failure — no local notification, mirroring Android exactly (a save either lands or it silently doesn't once the dialog is dismissed). One shared session with a single fixed identifier (e.g. `dev.norelease.paperdoll.share-upload`) is enough: tasks are fire-and-forget, and the server already tolerates duplicate `{url, title}` POSTs, so no per-share identity tracking is needed.

Needs an **App Groups** entitlement on both targets: `group.dev.norelease.paperdoll` (`group.` prefix is an Apple requirement).

The temp file itself needs cleanup: delete it in the `URLSessionTaskDelegate` completion callback (`didCompleteWithError`, which `Runner` receives after reconnecting) on both success and failure, and sweep the container for leftover files older than a day on `Runner`'s next launch, to catch ones orphaned by a crash before the task delegate ever fired.

### SwiftUI states

Port of `SaveWebClipScreen.kt`'s Loading/Success/Error states and copy verbatim, e.g. "Log in to Paperdoll first, then try sharing again." for unauthenticated. Close is available immediately; closing early doesn't cancel the transfer.

### ATS exception

The extension's own `Info.plist` needs an `NSAppTransportSecurity` debug exception for cleartext to the local dev server. Flutter's own `dart:io` networking bypasses ATS (its own socket stack), which is why `Runner`'s `Info.plist` has no such exception today — but native `URLSession` in the extension is subject to ATS, so this is new, not inherited.

### Version matching

The extension's version (`CFBundleShortVersionString`/`CFBundleVersion`) must match the host app's exactly, or App Store Connect rejects the upload. Today those values reach `Runner` via `Flutter/*.xcconfig` → generated `Version.xcconfig`; a template-created extension target won't inherit that chain automatically.

How: give the extension its own `Debug.xcconfig`/`Release.xcconfig` that `#include?` the same `Version.xcconfig` `Runner` uses (already generated at a fixed path, so no `ci_post_clone.sh` change needed), then point the extension's Info.plist keys at the same build settings it defines — `CFBundleShortVersionString` = `$(FLUTTER_BUILD_NAME)`, `CFBundleVersion` = `$(FLUTTER_BUILD_NUMBER)` — instead of the template default (`$(MARKETING_VERSION)`/`$(CURRENT_PROJECT_VERSION)`). One file stays the single source of truth for both targets' versions.

## Xcode / App Store Connect setup

### Bundle ID and capabilities registration

Register the extension's bundle ID (`dev.norelease.paperdoll.ShareExtension`, nested under the app's own ID as Apple requires) and its capabilities (Keychain Sharing, App Groups) in the Apple Developer portal before the first archive, or automatic signing / the Xcode Cloud TestFlight build can fail.

Caution: Xcode Cloud's managed signing has been known to struggle auto-creating profiles for capabilities added after a workflow's initial setup — safest path is opening the project in Xcode locally with a signed-in Apple ID first (so it provisions the new App ID/App Group/profiles), then letting Xcode Cloud pick up the result.

## Other things to account for

- Background `URLSession` tasks behave differently in the iOS Simulator than on a real device (the simulator doesn't fully suspend/relaunch processes the same way), so verifying "transfer survives extension teardown" needs a physical device.

## Explicitly out of scope

- macOS share extension / any macOS entitlement work.
- No backward-compatibility handling for the auth-token store switch: the app hasn't been released yet, so there's no old Keychain item format to migrate away from or worry about.
- No widget/E2E tests for the extension.
