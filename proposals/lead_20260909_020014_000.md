# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**3010 handling: ARP key evicted before the required reboot, leaving products with a live MSI registration and no way back (see correction in comments re: Defect 1)**

*Project description:*
## Summary

On a machine where `Start-SACPurge` was run, **Revit 2024 was left permanently unremovable and unreinstallable**. Every subsequent uninstall, repair or reinstall fails at `CostFinalize` with `Error 1606`, and the damage is invisible to SAC's own rescan.

Three separate defects combine to produce it. All evidence below is from SAC's own logs plus MSI verbose logs on the affected machine (Windows 11 26200, SAC 2.8.1, PS 5.1).

---

## Defect 1: `Wiping Registry Hive` destroys the root that Autodesk MSIs resolve `INSTALLDIR` from

`Private/`-level hive wipe removes `HKLM\Software\Autodesk` wholesale:

```
[13:30:55] Wiping Registry Hive...
[13:30:56] Removed registry tree: HKEY_CURRENT_USER\Software\Autodesk
[13:30:57] Removed registry tree: HKEY_LOCAL_MACHINE\Software\Autodesk
[13:30:59] Removed registry tree: HKEY_USERS\.DEFAULT\Software\Autodesk
[13:31:00] Removed registry tree: HKEY_USERS\S-1-5-19\Software\Autodesk
```

Autodesk product MSIs resolve their install root at runtime through a custom action, `DIRCA_INSTALLDIR`, which reads `HKLM\SOFTWARE\Autodesk\Revit\<year>\...`. With the hive gone, that CA returns an empty root:

```
MSI (s) Doing action: DIRCA_INSTALLDIR
MSI (s) PROPERTY CHANGE: Adding INSTALLDIR property. Its value is 'Revit 2024\'
...
MSI (s) Note: 1: 1606 2: Revit 2024\
Error 1606.Could not access network location Revit 2024\.
Action ended 19:20:56: CostFinalize. Return value 3.
Action ended 19:20:56: INSTALL. Return value 3.
```

`INSTALLDIR` degrades to the bare relative path `Revit 2024\` with no root, `CostFinalize` cannot resolve it, and the whole transaction returns **1603**. Note `INSTALLDIR32` resolved correctly in the same run (`C:\Program Files (x86)\Autodesk\Revit 2024\`) because it derives from `ProgramFilesFolder` rather than the registry. So the failure is specifically the registry-sourced root.

This makes the product permanently unserviceable by MSI: `/X`, `/f` repair and install-over all fail identically.

**Suggested fix:** if any product's MSI registration will survive the purge, the hive wipe must not remove the per-product `InstallationLocation` roots, or the purge must restore them. Safer: wipe the hive **only** after confirming no MSI product registrations remain that reference it.

## Defect 2: ARP key evicted on exit code `3010`, orphaning a live MSI registration

```
line 1051  [13:16:25] Uninstalling: Revit 2024
line 1152  [13:17:41]   Exit code: 3010 for Revit 2024
line 1153  [13:17:41]   Evicted Add/Remove Programs Key: Revit 2024
```

Compare the healthy path in the same run:

```
line  286  [13:07:46]   Exit code: 0 for Ideate Sticky for Autodesk Revit 2024
line  287  [13:07:46]   Registry key already removed (self-cleaned): Ideate Sticky ...
```

`3010` is `ERROR_SUCCESS_REBOOT_REQUIRED`. The uninstall is **not finished** — deferred operations are queued in `PendingFileRenameOperations` and Windows Installer deliberately retains the product registration until the reboot completes the transaction. Evicting the ARP key at that instant removes the only ARP-visible handle on a product whose MSI registration is still live.

Resulting state, with Revit 2025/2026 as controls on the same machine:

```
                                      UserData  Classes  ARP    LocalPackage
Revit 2024 {7346B4A0-2400-0510-...}   True      True     FALSE  1f6614.msi (on disk)
Revit 2025 {7346B4A0-2500-0510-...}   True      True     True   7bf9b0.msi
Revit 2026 {7346B4A0-2600-0510-...}   True      True     True   9a979f.msi
```

**Suggested fix:** treat `3010` as incomplete. Record it as pending-reboot, do not evict, require the reboot, then re-verify. Eviction should be conditional on the MSI registration actually being gone, never on the exit code alone.

## Defect 3: ARP key evicted on exit code `1603`, hiding a failed uninstall

```
line 1717  [13:23:02]   Exit code: 1603 for Autodesk Steel Connections Core Content for Revit 2024
line 1718  [13:23:02]   Evicted Add/Remove Programs Key: Autodesk Steel Connections ...
line 2243  [13:28:50]   Exit code: 1603 for Autodesk Revit 2024
line 2286  [13:29:16]   Exit code: 1603 for Autodesk Revit 2024.3.6 Update
```

`1603` means the uninstall **failed**. Evicting ARP after a failed uninstall converts a visible, retryable failure into an invisible one.

`Autodesk Revit 2024.3.6 Update` failing this way is the origin of an orphaned patch registration that then returned `1647` on three subsequent install attempts:

```
patch {9CA05B9A-2414-0510-A1B4-FFF7A680FE55}
  UserData\S-1-5-18\Patches\A9B50AC9414201501A4BFF7F6A08EF55   EXISTS
  Classes\Installer\Patches\A9B50AC9414201501A4BFF7F6A08EF55   EXISTS
  LocalPackage C:\WINDOWS\Installer\bc084.msp                  on disk
  linked to                                                    ZERO products
```

**Suggested fix:** never evict on a non-success exit code. Leave the entry so the product stays visible and retryable, and let `AttentionItems.txt` carry the failure.

## Defect 4: post-purge verification is ARP-driven, so it cannot detect this damage

A verification run 11 minutes after the purge reported a clean bill of health over the exact damage the purge had just caused:

```
[13:43:36] Starting uninstallation sequence for Revit *...
[13:43:36] Found 0 component(s) for Purge: 0 primary, 0 update/addon(s), 0 shared.
...
[*] All operations completed successfully with no critical failures.
```

That zero is vacuous. The orphaned Revit 2024 registration was present throughout; it simply has no ARP key, and the scan only reads ARP.

**Suggested fix:** add a residue check that reads the installer hives directly:

```
HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Installer\UserData\S-1-5-18\Products\<squished>
HKLM\SOFTWARE\Classes\Installer\Products\<squished>
HKLM\SOFTWARE\Classes\Installer\Features\<squished>
HKLM\SOFTWARE\Classes\Installer\UpgradeCodes\*
HKLM\SOFTWARE\...\Installer\UserData\S-1-5-18\Patches\<squishedpatch>
HKLM\SOFTWARE\Classes\Installer\Patches\<squishedpatch>
```

Flag two conditions:

1. a product registered in either installer hive with **no** ARP entry;
2. a patch registered globally but linked to **zero** products.

Implementation note, this bit is easy to get wrong: the packed ("squished") product code is **not** a byte-array reversal. Reverse the first 8 hex characters, reverse the next 4, reverse the next 4, then swap each remaining hex pair. Deriving it from `[Guid]::ToByteArray()` yields the correct last 16 characters and the wrong first 16, which silently turns the whole check into a false negative. Verified round trip: `A9B50AC9414201501A4BFF7F6A08EF55` unpacks to `{9CA05B9A-2414-0510-A1B4-FFF7A680FE55}`.

```powershell
function ConvertTo-SquishedGuid {
    param([string]$ProductCode)
    $g = ($ProductCode -replace '[{}\-]', '').ToUpper()
    function Rev { param([string]$S) $c = $S.ToCharArray(); [array]::Reverse($c); -join $c }
    function Swp { param([string]$S) $o = ''; for ($i = 0; $i -lt $S.Length; $i += 2) { $o += $S.Substring($i+1,1) + $S.Substring($i,1) }; $o }
    (Rev $g.Substring(0,8)) + (Rev $g.Substring(8,4)) + (Rev $g.Substring(12,4)) +
    (Swp $g.Substring(16,4)) + (Swp $g.Substring(20,12))
}
```

## Defect 5: no reboot barrier after a `3010`

The run saw `3010` at 13:17:41 and continued uninstalling for a further 15 minutes, declaring `PURGE COMPLETED` at 13:32:05. The reboot happened separately at 13:32:33. Everything in between ran against a machine with an incomplete MSI transaction outstanding.

**Suggested fix:** when any product returns `3010`, end the phase, require a reboot, and resume or verify afterwards.

---

## Defect 6: no `-WhatIf` on destructive commands

`Start-SACCleanup`, `Start-SACPurge` and `Repair-SACODIS` all change state and none declare `SupportsShouldProcess`. `Start-SACScan` is the only preview, takes no parameters, and its help describes launching an interactive menu, which makes it unusable in an automated or remote flow.

**Suggested fix:** declare `SupportsShouldProcess` on the destructive commands, and give `Start-SACScan` the same `-TargetProducts` / `-TargetYears` parameters plus a non-interactive mode.

---

## What worked well

Worth saying, because the diagnosis depended on it:

- `AttentionItems.txt` correctly captured all eight failures with exit codes. The data needed to catch this was recorded; only the eviction logic and the verification were wrong.
- The process-tree supervisor with CPU/memory sampling is a genuinely good way to decide an uninstaller has finished, and it avoids the classic "MSI log has not been written for six minutes so it must be idle" trap.
- Scoping via `-TargetProducts` / `-TargetYears` is the right shape.

## Reproduction

1. On a machine with several Revit versions installed, run `Start-SACPurge -Silent`.
2. Observe any product returning `3010` or `1603` followed by `Evicted Add/Remove Programs Key`.
3. After the run, query `Installer\UserData\S-1-5-18\Products\<squished>` for that product: registration present, ARP entry absent.
4. Attempt `msiexec /X <cached package>` for it. It fails at `CostFinalize` with `Error 1606` and returns `1603`, because `HKLM\Software\Autodesk` was wiped.
