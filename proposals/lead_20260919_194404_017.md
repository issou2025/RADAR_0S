### 2. Exact same identity is not an occupied different participant

Use the current validated profile, opaque own handle and server-retained setup.
A repeated target assignment is eligible only when its mode is `saved`, its handle
resolves to exactly the configured own Player, and it contains no nonblank new name.
Do not infer equivalence from labels, aliases or platform accounts. A same-name new
entry, mixed saved/new fields, unknown handle, forged own binding or different
participant remains rejected by the existing appropriate validation boundary.

Perform this resolution during **Update**, before final canonical creation. A
successful adoption is retained as the same automatic own bundle used by subsequent
review/movement; do not create a second Player or save a new own preference. Repeated
unchanged Update is semantically idempotent. A duplicate own identity at an unrelated
third seat remains a duplicate, not something to clear automatically.

Preserve the existing blank-target placement and server-owned automatic-bundle
movement. Do not normalize arbitrary changed final-Create input back into an old
reviewed roster; exact reviewed values and source checks still govern Create.

For Match's explicitly entered account values, apply a bounded lossless rule only
after establishing that both entries describe this same saved own identity:

| Existing automatic bundle and exact-own target | Resolution |
| --- | --- |
| Neither has an account value | Keep empty |
| Only one has a nonempty value | Retain that explicitly supplied value |
| Both have the same value | Retain it once |
| Two distinct nonempty values | Reject; preserve both for explicit correction |

Use the existing field normalization/validation boundary. An account-only occupied
target without an established participant identity is not permission to adopt it.
Do not copy profile account lists into Match metadata. Different participants never
have their accounts transferred or merged. No hidden fallback to a preferred account.
