# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[Impeller][Vulkan][Android] Pixel 10 (PowerVR DXT): vkDestroyDevice hangs when the last ContextVK reference is released in Dart_ShutdownIsolate after FlutterEngine.destroy(); next engine and HWUI deadlock (ANR)**

*Project description:*
### Steps to reproduce

Seen on a Pixel 10 Pro (PowerVR DXT GPU, Impeller Vulkan backend), Android 17 (`google/blazer/blazer:17/CP3A.261005.005/16271449:user/release-keys`), release build, Flutter 3.49.0-0.1.pre (beta).

Our app's host activity uses a cached `FlutterEngine` (it extends `audio_service`'s `AudioServiceFragmentActivity`). The app draws several widgets with custom fragment shaders (`FragmentProgram.fromAsset`, used through `Paint.shader` and `ShaderMask`, plus some `Picture.toImage` stills), inside `RepaintBoundary`s. The process also runs a foreground/accessibility service, so it outlives the activity.

1. Open the app and let the shader-painted screen render.
2. Swipe the app away from Recents. `audio_service`'s `AudioService.onDestroy` calls `FlutterEngine.destroy()`. The process stays alive (the app's other service keeps it running).
3. Open the app again. A new `FlutterEngine` is created in the same process and the activity is attached to it.

This hangs every time on this device. When the process is started fresh, the app always works.

A smaller repro we have **not verified** yet: an app with a `FragmentShader`-painted widget in a `RepaintBoundary`, hosted by an activity with a cached engine. Call `FlutterEngine.destroy()` while the process stays alive, then create a new engine and attach an activity, on a Pixel 10 (PowerVR DXT, Impeller Vulkan).

### Expected results

The second engine starts and the app renders normally.

### Actual results

The window stays blank and the process gets an ANR ("executing service ..., waited 20000ms"). We captured 4 ANR dropbox entries, and all 4 show the same thread states:

1. **A Dart VM worker thread** (Java-attached, named `Thread-31` / `Thread-29` / `Thread-36` / `Thread-33`) is stuck in `vkDestroyDevice`. In the PowerVR driver this goes `IMG_vkDestroyDevice` → `RGXDestroyGlobalPB` → `DestroyParameterMemory` → `DestroyServerResource` → `BridgeEventObjectWait`, a kernel ioctl wait that never returns. The symbolized Flutter frames show the cause: the old engine's isolate is shut down after `FlutterEngine.destroy()` (`Dart_ShutdownIsolate` → `Isolate::Shutdown` → finalizers). A finalizer drops a Dart `EngineLayer`, which frees its `flutter::Layer` tree. That frees a `DisplayListLayer`'s `DisplayList`, then a `DlRuntimeEffectImpeller` (fragment shader), then an `ImageWrapper` / `TextureVK` sampler input. That last texture resource holds the **last reference to the Impeller Vulkan device**, so `vk::Device::destroy` runs on a Dart worker thread during isolate shutdown, after the old raster thread has gone.
2. **The new engine's raster thread** (`2.raster` / `3.raster`) is blocked on the driver mutex in `IMG_vkCreateDevice`, while it builds `AndroidContextVKImpeller` (`PlatformViewAndroid` `SetupImpellerContext`).
3. **HWUI's `RenderThread`** is blocked on the driver mutex in `IMG_vkDestroyDevice+124`, called from `RenderThread::destroyRenderingContext` (`~VulkanManager`).
4. **The main thread** is blocked in `HardwareRenderer.nCreateProxy` (`RenderProxy::RenderProxy` waits for the RenderThread), called from `ViewRootImpl.setView` in `ActivityThread.handleResumeActivity`. This is the ANR.

So the device teardown that hangs in the driver holds a process-wide PowerVR driver lock, and that blocks both the next Impeller context and HWUI.

Two things probably need fixing, and the first may be a driver bug:
- `vkDestroyDevice` never returns on PowerVR DXT here (it waits forever on a server event in `RGXDestroyGlobalPB`). We think the device is being destroyed on a thread or at a time the driver does not expect. For example, the old engine's queues or surface may already be torn down, or HWUI may be tearing down its own device at the same time.
- The engine side lets a `TextureVK` held by a Dart-retained `EngineLayer` (through a runtime effect's image sampler in a retained `DisplayList`) keep the `ContextVK`/`vk::Device` alive past shell teardown. The device is then destroyed on whichever Dart thread runs the final finalizer. We would expect the context to be torn down deterministically on the raster thread during `Shell` destruction, or these resources to be released before the isolate is shut down.

Possibly related: #194034 (other Pixel 10 PowerVR DXT driver problems), #173589 (PowerVR allowlist/denylist), #191168 (teardown crash in `vkDestroyFramebuffer`), #186186 (FragmentProgram crash on second launch, GLES).
