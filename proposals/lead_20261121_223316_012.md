#### P1 — Real-time channel (needed by F6 Messaging, F8 Polls)

The ROADMAP says "WebSocket", but the frontend architecture rules out a plain one:
**the browser never talks to FastAPI and never holds a JWT**. Every request goes through
same-origin Next.js routes. Decided (2026-11-21): **option A**, Server-Sent Events.

<details><summary>Options considered</summary>

| Option | How | Cost |
|---|---|---|
| **A. SSE proxied through Next.js** ✅ | FastAPI exposes `GET /realtime/stream` (Server-Sent Events). A Next.js route handler opens it server-to-server with the cookie's token and pipes the stream to the browser. The browser *sends* through ordinary POST routes. | Server→client only, which is enough for chat delivery and poll results. Keeps the BFF model intact. Simple to test. |
| B. WebSocket with a one-time ticket | Next.js gets a short-lived ticket (redis, ~30 s, single use) from FastAPI. The browser opens `wss://backend/ws?ticket=…` **directly**. | The backend has to be publicly reachable (ingress, CORS/Origin checks) and a second auth path has to be maintained. |
| C. Polling | The client polls list endpoints every N seconds. | Zero infra. Not "live" enough for chat. |

</details>

**Design**
- **One endpoint for both clients.** `GET /realtime/stream` uses the normal
  `Depends(get_current_user)` with an `Authorization: Bearer` header. The Next.js proxy sends the
  cookie's token, and the **Flutter app connects directly** with its own token. No second auth path.
- **Streams end at token expiry.** The token is checked once, when the stream opens. The backend
  closes the stream at the token's `exp` (at most 15 min), so a revoked or logged-out token cannot
  keep listening. Clients reconnect with a fresh token: the Next.js proxy refreshes through the
  cookie, and Flutter through `POST /user/refresh`.
- **No replay.** There are no `Last-Event-ID` resumes. After a reconnect the client refetches current
  state over REST (latest messages, poll counts). Events are invalidation hints plus a small payload, never the only copy of the data.
- **Fan-out through redis pub/sub** on the existing redis (k8s runs several backend replicas, so
  an in-process broadcast would miss users on other pods). Channels: `user:{id}` (everything aimed at one person:
  messages, notifications) and topics (`poll:{id}`, `conversation:{id}`). The server subscribes on
  the user's behalf and checks membership before subscribing to a topic.
- **Wire format:** `event: <type>` + `data: <json>`, with a `: ping` comment every ~20 s so idle
  proxies (Traefik, the Next.js server, mobile networks) keep the connection open.
- **Infra:** the Next.js route needs `runtime = "nodejs"` and `dynamic = "force-dynamic"`, and must
  pass the body through unbuffered. In k8s, mobile reaches the stream through the existing
  `backend-ingress` (`api.assocore.localhost`). Check that its `api-rate-limit` middleware does not
  throttle reconnects, and that no compression middleware buffers `text/event-stream`.

Deliverables: `core/realtime.py` (`publish(channel, event, payload)` / subscribe helper), the stream
endpoint, heartbeat, close on expiry, tests with fakeredis (publish on one "pod" and receive on another subscriber).

#### P3 — Background jobs

**What actually needs a job.** Fewer features need one than the first draft assumed:

| Need | Job? | Why |
|---|---|---|
| F5: send a newsletter to N recipients | **Durable** | Minutes of work, rate-limited. Must survive a pod restart and never send twice |
| F5: scheduled send, later membership-expiry reminders (F11) | **Durable, at a time** | Runs at `run_at`, possibly days later |
| #193: password-reset mail off the request path | Fire-and-forget | If it is lost, the user just asks again. `BackgroundTasks` runs it *after* the response, which also removes the timing leak |
| F13 low-stock alert | No | One notification after the commit |
| F13 loan due and overdue reminders | Sweeper, daily | Due tomorrow, then overdue (once) |
| F11 Stripe webhook | No | Stripe retries failed webhooks itself for days. We only need idempotency (`stripe_events`) |
| F11: refund every ticket when an event is cancelled | **Durable** | One Stripe call per ticket, retried. Must not be lost if the pod dies halfway through |
| F11: one-off dues renewal reminders | **Durable, at a time** | N days before `valid_until` |
| F6: delete orphaned attachment uploads | Sweeper | Uploads never linked to a message after 24 h |
| GDPR retention purges (P4, F6, F5, …) | Sweeper | One poller per retention rule, running daily |
| F6: notification fan-out in large role channels | Durable | Above 50 members, done out of the request |
| F11: release expired ticket holds | Sweeper | Backup for a missed `checkout.session.expired`: `pending` payments past `expires_at` → `canceled` |
| F8 poll auto-close | No | Computed on read from `closes_at` |
| F10: render, store and email each issued document | **Durable** | The number is assigned in the issuing transaction, then rendering, the Nextcloud upload and the email are retried by the worker. A failure must never lose or reuse a number |

**Why not a redis queue (arq, SAQ, taskiq) or Celery.**
- Redis here **does not persist**: k8s mounts it on an `emptyDir`, and compose has no volume.
  Restarting redis would silently drop every queued newsletter. The auth design already treats
  redis as degradable (`AUTH_REDIS_STRICT=false`), and the job system should not be the exception.
- F5 needs a `newsletter_deliveries` row per recipient anyway, for its stats and to avoid duplicates.
  A broker would keep a second copy of the same state that can drift from the table.
- A broker means another container in compose, k8s and CI to run and monitor. Celery is also
  sync-first, which fits badly with the async SQLAlchemy code.

**Design.** Domain rows are the queue, and one small loop drives them.
- `core/worker.py`: a registry of **pollers**. Each feature registers
  `async def tick(session) -> int` (how many rows it processed). `lifespan` starts one `asyncio`
  task that calls every poller in turn, sleeps `WORKER_INTERVAL_SECONDS` (default 5) when none
  had work, and loops immediately when one did. It stops cleanly on shutdown.
- **Claiming across the 2 backend replicas**: each poller selects a small batch with
  `with_for_update(skip_locked=True)`. MariaDB 10.11 supports `SKIP LOCKED`, and SQLite (tests)
  ignores it, which is fine single-process. It then sets `status='processing', locked_until=now()+lease`,
  commits, works outside the transaction, and marks each row done as soon as that row succeeds.
- **Crash recovery**: a row whose `locked_until` has passed goes back to `pending`. Delivery is
  therefore **at-least-once**: only the one mail being sent at the moment of the crash can go out twice. Exactly-once is not possible over SMTP anyway.
- **Retries**: `attempts` + `last_error` on the row, exponential backoff through `run_at`, and `failed` after
  `max_attempts`.
- **Generic one-off jobs** (scheduled sends, reminders) go in a `jobs(id, kind, payload JSON, run_at,
  status, attempts, locked_until, last_error)` table drained by a poller of its own. Add it only when the first
  scheduled feature arrives. The newsletter's own rows don't need it.
- **Wake-up latency**: polling every 5 s is enough for every case above. If it ever is not, publish a
  "work available" hint on redis (P1's pub/sub) so the loop wakes early. Redis stays an
  optimisation there, and losing it costs only latency.
- CPU-bound work (PDF rendering, xlsx parsing) goes in `asyncio.to_thread`, never directly in the loop.
- `GET /health` reports the worker's last tick time, so a stalled loop is visible.

**When to revisit.** Move to a real queue, with redis made persistent first, if the jobs become
CPU-heavy enough to slow API requests, or if they need to scale independently of the API pods.
Neither is in sight for Steps 2–3.

**Decided**: in-process worker, with at-least-once delivery accepted (one in-flight mail may be sent twice after a crash).
