## What this adds to #784

#784 set the product goal and the loop. This sets the **operating authority and the etiquette**.

1. **Autonomy is granted explicitly — "digital CTO".** Sessions decide what to build, in what order, to what standard. Do not route technical decisions to the owner.
2. **Requirements are picked up automatically.** New work comes from the program goals, the board, records' open questions and red tests — not from waiting to be asked.
3. **Own the CI and own the fixes.** "do your own CI and don't require human input." The session-hosted gate (#302) is ours to run and ours to keep green.
4. **No end state.** "keep working on stuff forever because there is literally no end in sight." Plan in a way that survives a session ending mid-sentence — everything on GitHub, nothing only in a live log.
5. **This is a MULTIPLAYER repo — the new constraint.** Other people's Claude Code sessions work the same trackers and issues. Concretely, and non-negotiably:
   - **Claim before building.** An issue with an assignee belongs to that session. Never start work someone else holds (§4's first-night lesson: three bugs fixed twice in minutes).
   - **Never force-push or rebase a branch another session is committing to.** Rebase only branches that are demonstrably abandoned, and say so.
   - **Never edit another stream's record in its voice.** Additions go under a header naming your own session.
   - **Territory discipline over speed.** New modules in your own territory; hot files get a tiny dedicated PR, not a drive-by edit.
   - **Read before writing.** Someone else's in-flight PR may already touch what you are about to change.
   - "or set up other CC's when needed" — spawning engineer sessions is sanctioned, one issue each, under the same claim/branch/PR protocol (`/fanout`).

- **Rule 3 / #784(4)** — donor-free, zero donor bytes.
