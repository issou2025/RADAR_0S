## 3. Frozen experience specification

The initial page must show a real map, not a splash screen or a compass form. Place two compact rows at the top left of the usable map area, clear of the existing header and safe-area inset. First row: FROM — My location or selected start. Second row: TO — Tap map or selected destination. Keep labels short and ellipsize long values. Maintain usable touch targets, visible focus and accessible names. Preserve dark SCADA styling without ornamental controls. The map should occupy almost all of the screen.

Tapping FROM enables start selection. Tapping the map commits that point and returns to normal browsing. My location is an explicit user choice within the FROM field, requesting GPS only when deliberately selected. Tapping TO enables destination selection and the next intentional map tap commits it. Display distinguishable start and destination markers. A further tap on either field replaces that point. Ordinary map panning and pinching do not alter committed points. Users must be able to leave selection mode without accidentally changing a point.

The default state must not contain coordinate boxes, a pin-name form, a search dialogue, an asset selector, a separate confirmation screen or the old Where are you going panel. Optional place search may later operate within the same fields, but is not a prerequisite. Naming the dropped pin is unnecessary. The default selection must never depend on typing. Keep location permission, Stop and concise navigation status available in a minimal accessible map control or existing location affordance rather than introducing a third selector row or a large panel.

When selecting two fixed points, retain them independently of live measured position. When using My location, distinguish the starting fix from the subsequent moving position. Display accuracy and unavailable/stale state without moving the recorded position onto an assumed route. Do not automatically start location on page load, silently enable tracking or collect personal tracks.

## 4. Architecture and practical reuse

Prefer an additive preview using GridAtlas' existing cartridge and manifest architecture. Do not fork the entire map application or copy a large HTML shell. Use the current approved map renderer and ordinary licensed basemap, with infrastructure-specific layers excluded from the walking preview. The existing map event supplies WGS84 coordinates internally; the human never needs to see or type them. Respect longitude/latitude ordering at every interface.

Inspect these actual paths at the current GridAtlas pin: tools/satnav/line/preview.js (blob f8125829f7b62a8a4798533f6ba47ee4f1a79e52); tools/satnav/line/position-overlay.mjs (ae24435866faf19baa071508d503ea3c0ab7d75d); tools/satnav/line/route-follower.mjs (a0cdb4a6fb808b4b43f87d8bc3a9ac5d20daff8a); tools/satnav/line-browser.py (2b634a3c360769fe70e7875a9d9277bfadd1a0cc). The existing practice harness proves actual browser map taps and exact measured fixes, an eight-metre accuracy circle, clearing a watch and basemap preservation. It is a source of test patterns, not evidence that the new UI works.

Keep the measured GPS marker separate from any selected point or route geometry. Reuse reviewed geodesy and GPS contracts in place when dependency rights and exact pins permit. Do not install private VEDIC packages merely because a catalogue entry exists. Avoid new libraries, backends, keys, telemetry or broad estate scans. Existing geometry is sufficient to demonstrate point selection and straight-line measurement; pedestrian path data is a separate dependency.

The new selector needs a small explicit state model: no selection, selecting FROM, selecting TO, both endpoints available; GPS idle, requesting, usable, uncertain, stale, denied or stopped. Maintain a separate route state: not requested, calculating, available or unavailable. Prevent stale asynchronous responses from overwriting a more recent selection. Release map listeners and location watches on teardown. Preserve committed points when a permission request fails or a selection is abandoned. Document state transitions in tests, not a new architecture report.

## 6. Delivery sequence

Milestone A: an actual GridAtlas map with two compact fields, two selected points and no coordinate entry. Deliver a runnable additive candidate, commit SHA and screenshots. The user can select, replace and distinguish both points and continue interacting with the map. A straight-line measurement may be shown only as a measurement, never as an available pedestrian route.

Milestone B: retain that exact experience and add live measured position and accuracy using explicit GPS permission. A permitted short walk must show movement without changing the destination. Stop must clear the location watch. Publish a reviewable successor through the existing release process, not a replacement of production. Owner feedback may drive another small successor.

Milestone C: calculate and display an ordinary pedestrian route with appropriate access and path evidence. Return a clear unavailable result when the data cannot support routing. Separate route length from direct distance. Route updates must be tied to the current endpoints and must not silently assume a crossing, private access or unsupported off-road passage. The user may test Milestones A and B without waiting for C. Do not describe either of the first two milestones as turn-by-turn navigation.

Deferred: terrain modelling, underground data, transmission-line tracking, infrastructure-specific routing, offline maps, catalogue expansion, ticker improvements and wider engineering tools. These are not deleted; they are simply outside this delivery cohort.

## 7. Acceptance and evidence

FRESH-05 should test actual touch interactions in Chromium and WebKit at phone portrait and landscape dimensions, including narrow widths. Verify exactly two visible selector fields, no default coordinate input, no large blocking panel, readable labels and no overlap with navigation, search or safe-area controls. Test FROM then TO, TO then FROM, replacement, abandoning selection, pinch/pan without changes, invalid map input and basemap switching. Verify an ordinary map location in each test without recording private coordinates.

Mock geolocation must demonstrate no watch before opt-in, at most one active watch, correct fix position and accuracy, denial/retry, stale/poor-fix handling and Stop cleanup. Test a late callback after Stop and a late result after endpoint replacement. Check that personal GPS values are not transmitted by application telemetry or placed in URLs, logs, screenshots or public issue comments. Explain any basemap network requests and data-provider limitations.

For a pedestrian route candidate, use licensed test fixtures and ordinary public walking examples. Test disconnected paths, unsupported access, no path, provider failure and changed endpoints. Never use an illustrative segment as a route oracle. For field acceptance the owner can select two ordinary locations and walk a short known public path; record device, browser, exact candidate, observed behaviour and remaining problems, not precise tracks.

Run repository-local scope lint, relevant browser tests and protected-source comparisons. Preserve atlas/releases, atlas/current.json, STATE.md, homepage, existing public previews, existing MAP/A4/Vicinity behaviour and attribution unless a later owner-approved release explicitly permits a change. Use fresh hosted logs and served-byte verification. Distinguish local test, hosted CI, deployed preview and physical field acceptance. A green maintenance check cannot prove navigation.
