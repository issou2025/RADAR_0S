# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Rename the command: a vetted shortlist, and what a rename costs**

*Project description:*
`agpin` is five characters and says almost nothing. This issue picks the replacement and maps what a rename costs. It renames nothing: the name is wired into the Sigstore identity the installer verifies, into every user's rc file through the guard, and into every profile root through the sessions server registration, so a rename started before the name is settled is worse than none.

## Why this matters

The command is typed several times a day and read by people who have never seen the tool. `agpin` fails on both counts. It is five characters where three or four would do, and it decomposes only for somebody who has already read the README: **ag**ent **p**rofile + p**in**. Nothing about it says "keeps one account per customer apart".

The cheap half is genuinely cheap. `SELF="${0##*/}"` at the top of `bin/agent-profile` derives the name from whatever the script was invoked as, so every message, error, suggested fix and completion function follows the command name for free. Installed under a different name in a throwaway HOME, the tool renames itself completely and correctly:

```
$ tools/install.sh --dev --prefix <throwaway>/bin --name pin --no-server
Installed <throwaway>/bin/pin -> <checkout>/bin/agent-profile

$ pin new brygga
Created profile brygga
Sessions server: on (registered in /Users/alex/.claude-brygga/.claude.json)
Next: pin run brygga   (it will ask you to log in)
```

The expensive half is everything the name is *written into* rather than derived from: 1 471 occurrences across 57 files in this repository, fourteen `AGENT_PROFILE_*` variables in the script and twenty-three across the tree, the registry directory, the share directory, the release tarball, the Python package, the formula, the tap, and — the part that is not ours to change — the rc files and profile roots on machines that already have it installed.

One thing settles the timing. `AGENT_PROFILE_COSIGN_IDENTITY` in `tools/install.sh` is

```
^https://github\.com/mmsge/agent-profile-manager/\.github/workflows/release\.yml@refs/tags/
```

That string is the repository path of the release workflow. Renaming the repository changes the certificate every future release is signed under. GitHub redirects old repository URLs; Sigstore does not. Bundles on existing releases keep the old identity and stay verifiable exactly as they are, but the installer, `tools/update-homebrew-formula.sh` and the README's "Verifying by hand" all have to move in the same release. This is the one step that cannot be undone quietly, and it is why the rename belongs before or with v0.11.0 rather than after it.

Two facts make now unusually cheap, and both were checked rather than assumed:

- **The tap has never been published.** `https://github.com/mmsge/homebrew-agpin` is a 404, and `packaging/homebrew/README.md` still carries "Creating the tap, once" as a step to be done. Nothing public depends on the tap name yet. `README.md` and `docs/INSTALL.md` already tell people to run `brew tap mmsge/agpin`, which is a pre-existing documentation bug either way.
- **v0.11.0 is bumped but not cut.** `bin/agent-profile` says `AGENT_PROFILE_VERSION="0.11.0"` and the generated examples show it; `packaging/homebrew/agpin.rb` still pins v0.10.0, because the formula only catches up after a release is published. So there is no v0.11.0 release, tarball or signature to be inconsistent with yet.

## Recommendation

**Top three, in order: `bolk`, `benk`, `luke`. I would take `bolk`.**

`bolk` is the only candidate that came back clean on every register checked — Homebrew, Debian, macOS, npm, PyPI, GitHub's star-sorted search, and both namespaces — with no homophone hazard and no ambiguity in how it is said or spelled. The derivations read well: `BOLK_REGISTRY`, `~/.config/bolk-profiles`, `~/.local/share/bolk/<version>`, `bolk-<version>.tar.gz`, `class Bolk` in `bolk.rb`, tap `mmsge/bolk`. The old-law sense — a bolk is a self-contained chapter with its own rules — is a better fit for what a profile is than anything else on the list. **One thing to rule out before it is chosen: `bolk` is a name you appear to use already elsewhere, and there is a Norwegian haulier called Bolk AS. Neither is a software collision, but if the name is spoken for in your own world, take `benk` instead.**

`benk` is the fallback and is equally clean; it trades `bolk`'s distinctiveness for being guessable in English, at the cost of looking like a typo for "bench".

Two things worth saying plainly, because they may change the answer:

**No candidate satisfies the "more descriptive" branch.** `bolk`, `benk`, `skap` and `sete` are short words that are easy to say, which is the second branch of the ask. To an English-speaking consultant in London they say strictly *less* than `agpin` does, since `agpin` at least decomposes once you have read the README. The one name that is genuinely more descriptive is `pin` — it is the tool's own vocabulary on every page — and I would not take it: "PIN" reads as personal identification number, which is actively wrong for a tool that spends three paragraphs explaining it never touches a credential, and a three-letter English word on a global `PATH` is the likeliest name here to be taken out from under us later.

**`agpin` is already collision-free.** It is a coined word, which is why it came back clean on every register — a better collision profile than most real words. The change buys one keystroke and sayability, not clarity. That is a real gain for a command typed all day, and it is a smaller gain than it looks against the cost below. Keeping `agpin` is a defensible answer, and the cost map is worth having either way.
