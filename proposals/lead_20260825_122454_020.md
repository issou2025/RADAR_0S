## Problem 1 — normal dispatch responsibility is too broad

Current request shape is approximately:

```text
DISPATCH_REQUEST
  → bridge validation / correlation
  → production current-state acquisition
  → open workflow selection
  → structural closed-workflow conflict screening
  → possibly detailed recovery/consistency reconstruction
  → DISPATCH_DECISION
```

The structural/detailed recovery work exists for a real safety reason, but its placement may make every normal request repeatedly pay historical/recovery cost.

Explore must determine the correct responsibility split among at least these conceptual boundaries:

```text
Bridge / transport
  - request contract
  - exact GitHub comment correlation
  - idempotency / duplicate suppression
  - decision publication

Normal dispatcher
  - authoritative current open-state acquisition
  - WIP/cardinality
  - Change/routing validity
  - deterministic current work selection

Exceptional recovery / consistency validation
  - premature-close contradiction
  - terminal-history/recovery evidence
  - legacy/interrupted workflow reconstruction
```

These are investigation boundaries, not a pre-approved implementation decomposition.

The key question is: **which proof must be recomputed synchronously for every authorization, and which proof can be moved to a narrower exceptional path while preserving an authoritative, complete, current safety predicate?**

## Problem 2 — control-plane runtime rebuilds the application environment

Current bridge uses `uv run` from the repository root even though the dispatch/control-plane modules appear intentionally small and largely stdlib-oriented.

Explore must establish the actual import/dependency graph before choosing a solution. Evaluate at least:

1. plain `setup-python` + `PYTHONPATH=src` + `python -m ...` with no project environment installation;
2. a minimal dedicated runtime dependency group/environment if a small external dependency is genuinely required;
3. a separate package/workspace only if an independently versioned/deployed boundary is demonstrated necessary.

Do **not** create another package, requirements file, or framework merely to make the architecture look separated. Prefer zero/minimal runtime dependencies when the existing code boundary already supports it.

## Safety / design constraints

- Preserve authoritative invocation-local GitHub evidence for authorization-bearing current state.
- Preserve `AUTHORIZE | NO_WORK | FAIL_CLOSED` executable ownership and model non-override.
- Preserve WIP=1 / finish-first and deterministic pre-activation ordering.
- Preserve bounded premature-close recovery and fail closed on contradictory/incomplete provenance.
- Do not use conversation history, previous dispatch output, or stale cache as current authorization evidence.
- Do not solve latency only by lengthening Scheduled Task polling if repository-controlled work can first be made materially narrower.
- Do not introduce lock/lease/heartbeat/retry counters, hidden lifecycle state, a second DAG, or a generic workflow engine.
- Do not reopen #115 terminal-ordering semantics unless current evidence proves an actual regression in that settled invariant.
- Do not absorb #138's repository-wide executable-governance inventory.
