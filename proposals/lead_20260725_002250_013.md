# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**[in_app_purchase] App-facing package unconditionally overrides a registered platform implementation**

*Project description:*

## Summary

`InAppPurchase._getOrCreateInstance()` selects a platform implementation from `defaultTargetPlatform` and assigns it unconditionally, discarding whatever the Dart plugin registrant already installed:

```dart
// packages/in_app_purchase/in_app_purchase/lib/in_app_purchase.dart
static InAppPurchase _getOrCreateInstance() {
  if (_instance != null) {
    return _instance!;
  }

  if (defaultTargetPlatform == TargetPlatform.android) {
    InAppPurchaseAndroidPlatform.registerPlatform();
  } else if (defaultTargetPlatform == TargetPlatform.iOS ||
      defaultTargetPlatform == TargetPlatform.macOS) {
    InAppPurchaseStoreKitPlatform.registerPlatform();
  }

  _instance = InAppPurchase._();
  return _instance!;
}
```

A third-party platform implementation that registers itself the supported way — `dartPluginClass:` in `pubspec.yaml`, which the Flutter tool wires into the generated registrant — is installed correctly at startup and then **silently replaced** the first time application code touches `InAppPurchase.instance`.

The result is not a clean failure. The wrong implementation answers, and calls fail later with `PlatformException(channel-error, ...)` from a method channel that does not exist on that platform, with a stack that points into `in_app_purchase_storekit` rather than anything the app or the third-party package did.

## Evidence

Observed on a custom embedder (watchOS) whose `defaultTargetPlatform` resolves to `TargetPlatform.iOS`, with a federated FFI implementation registered via `dartPluginClass`:

```
defaultTargetPlatform            = TargetPlatform.iOS
InAppPurchasePlatform.instance   = InAppPurchaseWatchos            // after the registrant
<touch InAppPurchase.instance>
InAppPurchasePlatform.instance   = InAppPurchaseStoreKitPlatform   // overridden
```

Every subsequent call fails:

```
PlatformException(channel-error, Unable to establish connection on channel: "[flutter:flutter]")
  #0  _extractReplyValueOrThrow (package:in_app_purchase_storekit/src/sk2_pigeon.g.dart:20:5)
  #1  InAppPurchase2API.canMakePayments (package:in_app_purchase_storekit/src/sk2_pigeon.g.dart:796:41)
```

Observed with `in_app_purchase` 3.2.3 / `in_app_purchase_platform_interface` 1.4.1.

## Why this happens (and why it is reasonable today)

Neither endorsed implementation declares `dartPluginClass`:

```yaml
# in_app_purchase_storekit          # in_app_purchase_android
platforms:                          platforms:
  ios:                                android:
    pluginClass: InAppPurchasePlugin    package: io.flutter.plugins.inapppurchase
    sharedDarwinSource: true            pluginClass: InAppPurchasePlugin
  macos:
    pluginClass: InAppPurchasePlugin
    sharedDarwinSource: true
```

So the hard-coded `registerPlatform()` calls are standing in for Dart-side registration that the endorsed packages do not perform. That is a sensible arrangement for the three supported platforms. The problem is only that the assignment is **unconditional**, so it also overrides implementations that *did* register themselves.

## Impact

This affects any platform implementation that is not one of the three endorsed ones but whose `defaultTargetPlatform` maps to `android`, `iOS`, or `macOS` — i.e. community embedders that present as an existing `TargetPlatform`. The failure is quiet at registration time and only surfaces as a confusing channel error at the first call, in a package the developer never imported.

This is not a request to support watchOS in this repo. The request is that a platform implementation which registers itself should not be silently discarded.

## What working around it currently costs

For completeness, here is what a third-party implementation has to do today to coexist with this. It works, but it is not something an implementation author should have to derive:

```dart
static void registerWith() {
  _preempt();  // read InAppPurchase.instance *first*, so its selection memoises
}

static void _preempt() {
  if (_preempted) return;
  try {
    InAppPurchase.instance;   // runs upstream's one-time selection now
    _preempted = true;
  } on Object {
    // The plugin registrant runs before main() creates the binding, and the
    // selection installs a pigeon handler that needs one — so this throws and
    // memoises nothing. Retry on later event-loop turns (a microtask loop would
    // starve the loop before main() ever runs).
    if (_attempts++ < _maxAttempts) Timer.run(_preempt);
  } finally {
    // The selection assigns its own instance before it can throw, so re-assert.
    InAppPurchasePlatform.instance = MyPlatform();
  }
}
```

The essential trick is that the selection is memoised, so triggering it *before* the app does makes it harmless. Everything else is working around the fact that the override exists at all.

## Possible fixes

**1. Do not overwrite an existing registration** (smallest behaviour change):

```dart
if (!InAppPurchasePlatform.isRegistered) {
  if (defaultTargetPlatform == TargetPlatform.android) {
    InAppPurchaseAndroidPlatform.registerPlatform();
  } else if (defaultTargetPlatform == TargetPlatform.iOS ||
      defaultTargetPlatform == TargetPlatform.macOS) {
    InAppPurchaseStoreKitPlatform.registerPlatform();
  }
}
```

This needs a way to ask whether an instance exists. `InAppPurchasePlatform` currently stores it as:

```dart
static late InAppPurchasePlatform _instance;
```

so reading it before assignment throws `LateInitializationError` and there is no non-throwing probe. A minimal addition to `in_app_purchase_platform_interface` would be needed, e.g.:

```dart
static bool get isRegistered => _isRegistered;
```

set inside the existing `instance` setter. That is additive and does not change existing behaviour.

**2. Have the endorsed implementations declare `dartPluginClass`** and drop the hard-coded selection entirely. Cleaner and more in line with the federated model, but a larger change across three packages.

**3. Documentation only.** If neither is desirable, documenting that `InAppPurchase.instance` always installs an endorsed implementation — so third-party implementations must re-register after the first touch — would at least make the behaviour discoverable. The workaround today is:

```dart
InAppPurchase.instance;               // runs the one-time selection
MyPlatformImpl.registerWith();        // ...then take it back
```

This works reliably because the selection runs only once and every `InAppPurchase` method reads `InAppPurchasePlatform.instance` at call time — but it is not discoverable without reading the source.

Happy to send a PR for option 1 (plus the `isRegistered` addition) if that direction is acceptable.
