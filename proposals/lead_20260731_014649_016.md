# Project Proposal — Python Automation

## Project Understanding
You need assistance with: 
**Automate the release: derive the version bump and changelog from merged PRs**

*Project description:*
## The current process (the baseline this would replace)

Releasing Provx is manual and asserted, not automated. That is stated honestly in
[CONTRIBUTING §3](../blob/main/CONTRIBUTING.md#3-the-contribution-flow) as of #36:

- `make version-set VERSION=x.y.z` writes all five declaration sites at once.
- The required `version-consistency` gate refuses a disagreement between sites, or a
  `pyproject.toml` that regrew a static `version =` instead of delegating via
  `dynamic = ["version"]`.
- `CHANGELOG.md` is written by hand, by the PR author, under `## [Unreleased]`.
- A maintainer cuts a release by moving `[Unreleased]` into a version section, merging,
  and pushing an annotated `vX.Y.Z` tag.
- `release-check` fires on that tag push and fails if the tag disagrees with the version
  the code declares — a **detector, not a gate**, since a pushed tag cannot be blocked.

Nothing reads commit history. There is no release-please config, no commitlint, no publish
workflow.

## What automation would change

Deriving the version bump and the changelog entry from merged PRs, rather than from a
maintainer remembering to run two commands in the right order. release-please and Changesets
are the obvious candidates; neither has been evaluated against this repo's constraints.

## Constraints any solution must meet

1. **One version for the whole product.** Issue #31 established that a single number covers
   the backend, the SDK, the CLI, and the console, and that equality across declaration sites
   is enforced by assertion rather than by file layout. Anything that reintroduces per-package
   versions or a pin matrix is a regression, not an improvement.
2. **It must work where the packages are actually built.** Each Python package has to stay
   buildable from its own directory — the backend image copies `packages/adapters` alone, with
   no `.git` — which is why `hatch-vcs` / `git describe` were rejected for #31. A release tool
   that assumes repo-root context or git metadata inherits that problem.
3. **Determinism (PX-DETERMINISM).** The version a build produces must not depend on where or
   when it was built.
4. **The `version-consistency` gate stays.** Automation replaces the manual bump; it does not
   replace the assertion that catches a partial one.
5. **Air-gapped builds are a supported case**, not an edge one.

## Why this issue exists separately from #34

That is fixed in #36 — the docs now describe the manual process truthfully. This issue is the
