# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Give the home page a visible hierarchy that introduces the person first**

*Project description:*
## Problem Statement

The home page is a flat stack of near-identical rows. A first-time visitor lands, reads one sentence, and then meets twelve links that all look the same weight.

Three specific failures:

**1. The page barely says who Kihyun is.** The **Identity Statement** is a single abstract sentence — "I'm a developer interested in defining problems and solving them." It is true of most developers. Nothing on the page says how he works, what he keeps building, or why the list below is worth scrolling. `CONTEXT.md` gives the Identity Statement a soft ceiling of three sentences; it is currently using one.

**2. The page's central distinction is invisible.** [[adr-0004-open-source-vs-projects]] made **Package** vs **Project** the organising idea of the whole site — build-upon versus use-directly. On screen, both sections render as a `text-sm text-muted-foreground` heading over identical rows. The headings are *quieter and smaller than the content beneath them*, so the structure reads as one undifferentiated list, and nothing anywhere explains what either category means.

**3. A visitor cannot tell what a Project is.** A **Project** row shows a name and nothing else. `flutter_table_plus` self-describes, which is [[adr-0003-minimal-project-card]]'s whole argument — but `Pricly`, `Just Roster`, and `Just Insight` do not. ADR-0003 was written about **Package** cards, and [[adr-0004-open-source-vs-projects]] explicitly left Project metadata undecided. That decision has been deferred long enough to become a hole.

Compounding all three: `main` carries `py-24 sm:py-32`, so on a phone the first viewport is the header, one sentence, and whitespace.

## Solution

Make the home page introduce the person first, then present two clearly distinct bodies of work — without abandoning the restraint the site is built on.

- The **Identity Statement** grows into the three sentences its own constraint already allows: who he is, how he works, what he keeps returning to. It still names no **Ecosystem**, per its documented constraint.
- Each section gains a **section lede** — one English line under the heading saying what the category *is* ("Building blocks other developers install and build on" / "Services you use directly"). This is what makes ADR-0004's distinction legible instead of implied.
- Section headings get real typographic weight, so the page has a visible skeleton: statement → section → rows → section → rows.
- A **Project** gains an optional one-line description. **Package** rows do not change.
- Vertical rhythm is retuned so the first viewport carries the statement *and* the beginning of the first section.

No new colours, no cards, no motion, no third font. [[adr-0002-typography-pretendard-inter]] stands. The page should look like the same site, better organised.

## User Stories

3. As a first-time visitor, I want the Identity Statement to stay short enough to read in one glance, so that "introduce the person" does not become a wall of prose.
4. As a Korean-reading visitor, I want the whole expanded Identity Statement translated, not just its first sentence, so that the **Language Toggle** does not leave me reading a half-Korean paragraph.
5. As a visitor, I want each section to say what kind of thing it lists, so that I understand a **Package** is something I install and a **Project** is something I use.
6. As a visitor, I want section headings to be visually stronger than the rows beneath them, so that I can see the page's structure without reading every row.
7. As a visitor, I want a clear visual break between the two sections, so that I do not read one long list of twelve unrelated names.
8. As a visitor, I want the two sections to remain in a deliberate order, so that the more substantial body of work is met first.
9. As a visitor on a phone, I want the first viewport to contain the statement and the start of the first section, so that I have a reason to scroll.
10. As a visitor, I want a one-line description on each **Project**, so that I know what `Pricly` and `Just Roster` actually are.
11. As a visitor, I want **Package** rows to keep showing only name and **Ecosystem**, so that the 27-row Open Source list does not become 27 lines of padding prose.
12. As a visitor, I want a **Family** row to keep reading as one body of work, so that the hierarchy work does not undo the grouping work.
13. As a visitor, I want the "See all →" link to remain on both sections, so that the full-list pages stay reachable.
14. As a visitor using the **Language Toggle**, I want section ledes and Project descriptions to stay in English, so that toggling does not produce a page half in each language.
15. As a visitor with a screen reader, I want the section heading and its lede to be associated, so that the lede is announced as part of the section rather than as loose text.
16. As a visitor with a screen reader, I want the expanded Identity Statement to carry the right `lang`, so that Korean is pronounced by a Korean speech engine.
17. As a keyboard user, I want every row to remain a single focusable link, so that adding a description does not create two tab stops per Project.
18. As a visitor on a narrow screen, I want a Project's name and description to wrap legibly, so that longer descriptions do not crush the layout.
19. As a visitor in dark mode, I want the new hierarchy to hold, so that the heading/lede/row contrast does not collapse in one theme.
20. As a visitor arriving from search, I want the page's heading structure to be semantically ordered, so that the document outline reflects the visible hierarchy.
21. As Kihyun, I want a Project's description to be optional, so that a self-describing name is not forced to carry invented prose.
22. As Kihyun, I want a soft length limit on Project descriptions, so that the field cannot quietly grow into a paragraph and break the row rhythm.
23. As Kihyun, I want the Identity Statement's ceiling to stay enforced at three sentences, so that "introduce the person" does not license unbounded growth later.
24. As Kihyun, I want the section ledes to live beside the data they describe, so that a future category rename does not leave a stale explanation behind.
25. As Kihyun, I want the **Package** side untouched, so that this work does not silently reverse ADR-0003.
26. As Kihyun, I want the changed rules recorded, so that a later contributor does not "restore" the quiet headings or strip the Project descriptions as inconsistent.
27. As Kihyun, I want `CONTEXT.md` to describe the new surfaces in the project's own vocabulary, so that "section lede" does not get reinvented as "subtitle" or "blurb" next time.
28. As a future contributor, I want the hierarchy expressed in shared list primitives rather than per-page markup, so that `/open-source` and `/projects` inherit it instead of drifting.
29. As a future contributor, I want adding a third section to require no new components, so that the layout is a pattern rather than a one-off arrangement.
30. As a future contributor, I want to know why the Identity Statement still names no Ecosystem, so that the constraint is not read as an oversight and "fixed".

## Implementation Decisions

**The Identity Statement expands within its existing ceiling — no ADR is reversed.**
`CONTEXT.md` already permits up to three sentences; it is using one. Growth to two or three is spending existing headroom, not raising the limit. The constraint that it names no **Ecosystem** stands unchanged: those facts belong to the Open Source list, and the section lede below now does the framing work that tempted people to inline them.

The literal text stays out of the glossary and out of the components — it lives in `src/lib/i18n.ts`, as today.

**The whole Identity Statement stays Translatable Content, in both languages.**
It is already the sole member of **Translatable Content**; expanding it does not add a member and needs no decision under [[adr-0001-language-strategy]]. But every sentence must ship with its Korean counterpart — a partially translated statement is worse than a short one, because the **Language Toggle** would produce a mixed-language paragraph.

**Section ledes are a new surface, and they are English-only.**
Per ADR-0001, the default for any new text is English-only, and this spec does not add a member to **Translatable Content**. The ledes are one line each, drawn from the definitions already written in `CONTEXT.md` ("something another developer installs and builds on top of" / "a standalone service or application that a person uses directly") so the site and the glossary say the same thing in the same words.

The lede text lives beside the data it describes — with the Open Source and Projects modules in `src/lib/`, not inline in `page.tsx` — so a category rename touches one place.

**Hierarchy is typographic, not decorative.**
The section heading becomes visibly stronger than its rows; the lede sits under it in muted small text; the rows keep their current treatment. The section boundary is expressed through spacing and the existing border token, not a new rule, colour, or container. No cards, no background fills, no motion. This is the "minimal, hierarchy only" intervention: nothing is added to the palette or the font stack.

**Heading semantics follow the visible hierarchy.**
Sections are `h2` under the page's `h1`, and the lede is associated with its heading for assistive technology rather than floating as an unattached paragraph.

**Vertical rhythm is retuned so the first viewport earns a scroll.**
The shell's top padding drops from `py-24 sm:py-32` to a value that leaves the statement and the first section heading above the fold on a common phone viewport. Section spacing is rebalanced at the same time so the page does not merely become denser at the top and unchanged below.

**A Project gains an optional single-line description; a Package does not.**
The `Project` type gains an optional description field. This does not reverse [[adr-0003-minimal-project-card]] — that ADR is explicitly scoped to **Package** cards, and [[adr-0004-open-source-vs-projects]] left Project metadata open. The asymmetry is the point and must be recorded: a Package's name is chosen to self-describe and its **Ecosystem** tag supplies context; a Project's name is a product name and supplies none.

The field is **optional** and carries a soft length limit (roughly one short clause, not a sentence with a full stop) so rows keep an even rhythm. Where a Project's name genuinely self-describes, the right move is to omit the description, not to invent one.

**The row primitive carries the description; the page does not.**
The description renders inside the existing single row link, so a Project stays one focusable target. The changed primitives live in the shared list components, so `/projects` picks up the same treatment as the home page without a second implementation. Long descriptions wrap; they never truncate with an ellipsis, since a half-sentence is worse than a wrapped one.

**Package rows, Family rows, and the `HOME_LIMIT` cap are untouched.**
The Open Source list keeps name + **Ecosystem**, a **Family** keeps name + member count, and the cap still counts derived rows. Nothing in this work changes what the Open Source section contains — only how the page around it is organised.

**Documentation.**
`CONTEXT.md` gains a **Section Lede** entry (naming it, so it is not reinvented as "subtitle"/"blurb"), an updated **Identity Statement** entry reflecting its expanded job and unchanged constraints, and an updated **Project** entry noting the optional description. A new ADR records two decisions: that Projects carry descriptions while Packages do not, and that the home page's job is to introduce the person before the catalogue.

## Testing Decisions

**What makes a good test here.** Almost all of this work is presentational, and the repo deliberately does not test rendering — the existing runner is scoped to `src/lib/` for computed behaviour only. Do not introduce a DOM environment, a component testing library, or snapshots to chase coverage of a layout change; a snapshot of markup would fail on every deliberate design tweak and assert nothing about whether the hierarchy reads.

**Prior art.** `src/lib/open-source.test.ts` — fixture-driven unit tests over pure functions, added with the Family work. Follow its shape and its scope discipline.

**What to cover** — only the data-shaped parts:

- Every **Project** with a description satisfies the soft length limit, and the check fails loudly on a violation (same build-time-failure posture as the Family validation rules, which are invisible in the data otherwise).
- A **Project** without a description is valid and renders as a bare name — the optionality is real, not nominal.
- Both languages of the **Identity Statement** have the same sentence count, so a translation cannot silently lag the English by a sentence.
- Existing Open Source tests continue to pass unchanged — if this work needed to touch them, it changed something it was not supposed to.

**Not tested.** Spacing, font weights, heading levels, colour contrast, above-the-fold behaviour, and the wording of any lede or description. These are judged by looking at the page, in both themes and at a phone width, before the work is called done — not by assertions.

## Out of Scope

- **A dedicated `/about` page.** Person-first is served here by expanding the Identity Statement, which already exists and is already translated. A new route brings its own decisions — is it Translatable Content, what does it contain, does the nav change — and those should not ride along inside a hierarchy pass. It is the natural follow-up, not part of this.
- **Descriptions on Package rows.** Explicitly excluded; ADR-0003 stands.
- **Any change to what the Open Source section contains** — the curated order of `packages`, which items surface under the cap, or which **Families** exist. Reordering the catalogue is a separate curation decision.
- **Changing `HOME_LIMIT`.**
- **New colours, gradients, illustration, iconography beyond what exists, animation, or scroll effects.** The chosen intervention is hierarchy only.
- **A third font, or any change to the Pretendard/Inter pairing** ([[adr-0002-typography-pretendard-inter]]).
- **Adding members to Translatable Content.** Section ledes and Project descriptions are English-only.
- **Metadata on Project rows beyond the description** — no kind label, no year, no status, no live/dead indicator.
- **Restructuring the nav, header, or footer**, and any change to the two outbound links.
- **URL-routed localisation** — ADR-0001's rejection stands.
- **Component or visual regression tests.**

## Further Notes

- **The tension to hold onto:** "introduce the person" and "stay minimal" pull against each other, and the Identity Statement's three-sentence ceiling is where that tension is resolved. If the writing wants a fourth sentence, that is the signal to build `/about`, not to raise the ceiling. Say so in the ADR, so the next person meets the argument rather than the limit.
- **Write the Identity Statement last.** The layout work can proceed with the current sentence in place; the prose is the hardest part and benefits from seeing the finished page. It is also the one piece an agent should not finalise alone — it is Kihyun's voice, and a generated "passionate about building things" sentence would be worse than the current one.
- **The ledes should be lifted from `CONTEXT.md`, not written fresh.** The glossary already contains good one-line definitions of **Package** and **Project**. Reusing that wording keeps the site and the domain model from drifting apart, and it is a genuine test of the glossary: if a definition reads badly to a visitor, the definition is the thing to fix.
- **Judge the result at a phone width and in both themes before calling it done.** The failure mode of a hierarchy pass is that it looks correct at desktop width in light mode and collapses elsewhere.
- **Separate bug, not part of this:** `src/components/site-footer.tsx` computes the copyright year with `new Date().getFullYear()` in a statically generated component, so the year is frozen at build time and will read stale until the next deploy. Worth its own issue.
