# Project Proposal — Bim Modeling

## Project Understanding
You need assistance with: 
**Cowork Session Cannot Reach Device Running the Navisworks MCP Server**

*Project description:*
1. During a Cowork session (Claude, running in the cloud) already linked to the user's computer, every call to the device bridge (mcp__remote-devices__*, e.g. get_device_info) failed with: "The device this session is bound to is not connected to the bridge." Meanwhile, on that same computer, Claude Desktop was running normally, a local MCP server named "navisworks" was shown as Running (launched via Python 3.13, script navisworks_mcp_server.py), and the Navisworks file was open with its "MCP Bridge" add-in enabled. As a result, the Cowork session could not proxy through to the locally running navisworks MCP server.

3. Steps to Reproduce: - Open a Navisworks file, enable the "MCP Bridge" add-in.- In Claude Desktop, confirm the "navisworks" local MCP server is Running.
- Open a Cowork session linked to that same computer (scg-sonbh01).
- Ask Claude to connect/check the device inside the Cowork session.

3. Expected Result: The Cowork session connects successfully to the device, and the local navisworks MCP server is proxied through as mcp__remote-devices__navisworks__* tools callable directly from the Cowork session.

4. Actual Result
 Every bridge call returned "The device this session is bound to is not connected to the bridge." The error was consistent across 6 retries over several minutes, including after confirming control permission was granted and the network was normal. No mcp__remote-devices__navisworks__* or mcp__remote-devices__revit-mcp__* tools ever appeared.

>> Questions for the Author:
1. Does "Running" in Claude Desktop guarantee the server is ready to be proxied, or is an extra activation step needed?
2. Could running two local MCP servers at once cause a conflict?
3. Are there logs (client or server-side) that would explain the "not connected" error?
4. Are there specific version or OS permission requirements for the bridge to work reliably?
5. Is this a known issue when combining Cowork with a locally-run MCP server?
