# Project Proposal — Quantity Takeoff

## Project Understanding
You need assistance with: 
**Native mobile app for archaeological and rock art field work**

*Project description:*
A native iOS/Android application for recording in the field - photograph in situ, attach to a context, site or panel, capture position, sync when there is signal.

**Distinct from #307**, which is scoped as a PWA. That difference is not cosmetic: it changes the authentication model, the release process and the cost base. This issue is for the native route; a decision is needed on whether it **replaces** #307 or **follows** it.

## What native buys that a PWA cannot

- **Background and resumable upload.** A dig produces large photos on a poor connection. A PWA uploads only while its tab lives; an app can hand transfers to the OS and resume across restarts.
- **Storage.** A day of RAW or HEIC capture will exceed what browser storage quotas reliably allow. A device offline for a week needs real filesystem access.
- **Camera control** - focus lock, exposure, burst, scale bars, RAW. Rock art recording in particular cares about this.
- **Continuous GPS** without a live tab, plus the device's own accuracy estimate rather than the browser's coarse one.
- **Offline map tiles** - both domains work where there is no signal, and the map is how you find the site again.
- **Hardware** - QR/barcode scanning for context and bag tags is the single biggest transcription-error saver in the field. On newer iPhones, LiDAR opens 3D capture of a panel or a section, which would feed `ahg3DModelPlugin`.

## What it costs, honestly

- **A second codebase**, or a cross-platform framework (React Native / Flutter) with its own failure modes.
- **App store review.** No more "deploy and it is live" - a fix takes days, and a field team can be stuck on a broken version mid-season.
- **Version skew.** Old app versions will hit a changed API. This forces API versioning discipline we do not currently need.
- **Signing, developer accounts, possibly MDM** if devices are institution-owned.
- Neither Wits Archaeology nor RARI has stated a device fleet, so **who owns the phones** is an open question that changes the security model entirely.

## The API is the real architectural consequence

A native app cannot use AtoM's session cookies. It needs a stable, versioned API - which mostly **already exists**:

- **`ahgAPIPlugin` serves `/api/v2`** with `Authorization: Bearer <key>` auth, keys in `ahg_api_key` bound to a user, OpenAPI generation at `/api/v2/openapi`, docs at `/api/v2/docs`, and key revocation.
- `ahgGraphQLPlugin` has a schema builder with mutations, if a graph API suits better.

What is missing for field capture:
1. **Upload and attach endpoints** - post a photo, attach it to a target, with idempotency so a retried upload after a dropped connection does not duplicate.
2. **Per-device keys**, not per-user. A lost phone must be revocable without locking out the archaeologist.
3. **A sync/delta endpoint** so the app can pull the contexts and sites for a dig before going offline.
4. **Reconciliation** for records created in the field against numbers that do not exist in AtoM yet.

## Sensitive location - harder here than in a browser

Everything in #307 applies, and one thing gets worse: **an offline device holds a local copy of site positions**, so a lost or stolen phone becomes a list of rock art locations. That is precisely what `LocalityVisibilityService` exists to prevent.

Minimum requirements:
- Device-local storage encrypted at rest, and remote-wipeable.
- The app receives only what the locality gate allows for that user; an editor-credentialed device is a different risk class from a volunteer's.
- Consider whether the app should hold coordinates at all for gated sectors, or navigate by reference and photograph without recording position.
- ICIP/TK restrictions (`ahgICIPPlugin`) must be settable **at capture**, by the person who was actually there.

## Suggested position

The PWA in #307 and this are not really alternatives. A PWA is far cheaper to build, needs no store, and would prove the data model, the resolver contract and the sync endpoints - all of which a native app then reuses unchanged. The expensive, native-only wins (background upload, storage, barcode, LiDAR) are worth paying for **once the workflow is known to be right**.

So: PWA first as #307 describes, native second against the same API, unless there is a field requirement that makes a browser unusable from day one. Worth asking Wits Archaeology and RARI what devices their teams actually carry before committing either way.

Related: #307 (PWA field capture - shares the API and resolver design), #299 (field-recording plugin), #306 (stratigraphy tooling).
