## Why: one building model for architecture, environmental analysis, and MEP loads

Across both architecture and MEP, teams keep hitting the same wall: you model the building once to run environmental, daylighting, or thermal load simulations, and then rebuild the entire model from scratch in another tool to produce construction documents and schedules — and the two models immediately drift out of sync.

MutinyBIM already has a strong foundation to solve this from **one shared model**, using our **script-first** workflow (`@permitzip/bim-script` + `bim-library` + add-on packs) rather than bolting on dozens of narrow MCP tools. This issue lays out an initial architecture for building-performance and environmental simulation backed by `"EnergyPlus version 26.x" software` (and cleanly extensible to sibling engines like Radiance), so architecture and mechanical contributors can coordinate on the shared kernel pieces before writing code.

## Key technical notes on EnergyPlus

1. **C / Python API vs. `epJSON` model authoring**
   - The EnergyPlus C API (`libenergyplusapi`) and Python API (`pyenergyplus`) are **runtime/co-simulation and property APIs** (state management, standalone psychrometrics/glycol/refrigerant calls, timestep callbacks, sensor/actuator exchange) — *not* model-authoring SDKs.
   - Programmatic model generation works cleanly through **EnergyPlus's native JSON format (`epJSON`)**, validated against the official `Energy+.schema.epJSON` (~859 object types). TypeScript can emit and validate `epJSON` directly (e.g. alongside MIT-licensed libraries like `@idfkit/core` / `@idfkit/schemas`) with no Python dependency required for authoring.

2. **Custom equipment & cut-sheet simulation**
   - Custom air handlers compose cleanly in `epJSON` (`AirLoopHVAC` → outdoor air / economizer → ERV/HRV → cooling coils → heating coils → fan → zone terminals).
   - Real manufacturer cut sheets map directly to EnergyPlus **`Table:Lookup`** (multi-dimensional interpolation over entering wet-bulb × outdoor dry-bulb → total capacity, SHR, EIR, or fan static × CFM) or fitted **`Curve:Biquadratic` / `Curve:Quadratic`** objects.
   - An agent (or engineer) can author a reusable parametric `part` script in `bim-library` that defines a unit's 3D geometry, connectors, clearances, internal coil/fan chain, and cut-sheet performance tables — and even run a lightweight **standalone cut-sheet verification** harness against manufacturer rating points before placing the unit in a building.

3. **Execution: WebAssembly + optional native worker behind one interface**
   - `"EnergyPlus version 26.1.0"` / `26.2.0` software compiles cleanly to **WebAssembly** (e.g., `@idfkit/engine` or an Emscripten build): ~5.7–7.2 MB brotli download, ~0.1 s load, ~1.0–1.3× native speed, agrees with native to `3.5e-9`, single-threaded (no COOP/COEP headers needed), and supports `Sizing:Zone`, `Sizing:System`, Kiva, CondFD, EMS, AirflowNetwork, and SQLite output (`eplusout.sql`).
   - That unlocks **zero-server local/in-browser design-day load calcs, early-stage envelope/daylight/comfort studies, and cut-sheet verification in ~0.5–5 seconds**.
   - Larger multi-zone 8,760-hour annual simulations (or Python Plugin / FMU co-simulation, which WASM omits) can run on a **native worker** behind the exact same async runner contract.

4. **ASHRAE 62.1 / IMC ventilation**
   - EnergyPlus natively calculates ASHRAE 62.1 VRP (`Standard62.1VentilationRateProcedure`, including multi-zone $E_v$, critical zone $Z_{pz}$, and DCV), the 2019 Simplified Procedure, and outputs `Standard62.1Summary`.
   - However, EnergyPlus does **not** ship copyrighted ASHRAE 62.1 / IMC occupancy rate tables ($R_p$, $R_a$, occupant density, exhaust).
   - So `VentilationEngine` should remain the fast, incremental source of truth for space rates and permit tables (and gain the multi-zone $E_v$ calculation directly), exporting each space's $R_p$/$R_a$/$E_z$/occupants straight into `DesignSpecification:OutdoorAir` so loads, DCV, and ventilation schedules stay 100% synced.

5. **License & naming hygiene**
   - EnergyPlus uses a permissive modified BSD-3-Clause license (Apache-2.0 compatible, not copyleft).
   - **Clause (4)** requires referring to the engine as `"EnergyPlus version X" software` when bundled or referenced standalone, and forbids using `"EnergyPlus"`, `"E+"`, or `"e+"` in product or package names without U.S. DOE written consent.
   - Keeping the solver in an **optional add-on pack / runtime adapter** (never in `bim-kernel`) with a neutral package name (e.g. `@permitzip/bim-pack-thermal` or `@permitzip/bim-pack-environmental`) keeps our Apache-2.0 boundary (`eslint/plugins/mutinybim-oss-boundary.mjs`) clean and avoids forcing non-thermal models to download a WASM solver.

## Bedrock Check: shared kernel foundations vs. optional simulation pack

Following the Bedrock rule (**build on the bedrock, never beside it**), **no solver belongs in `bim-kernel`**, and simulation must never run synchronously on edit commits or inside `bim-script-runner`'s locked-down sandbox. Instead, five small, discipline-neutral kernel/library foundations unlock architectural environmental analysis, MEP loads, and owner/GC workflows together:

### 1. Five shared kernel / library foundations

| # | Foundation | Why it belongs in the shared bedrock (cross-discipline) |
| --- | --- | --- |
| 1 | **Site geographic location & climate/design-condition ref** on `SiteElement` (`lat`, `lon`, `elevation`, `timeZone`, weather/climate ref) | **Arch:** sun path, shadows, daylighting, code climate zone · **Mech:** EPW weather & ASHRAE design days · **Civil/Plumb:** rainfall intensity & freeze depth · **Struct:** wind/snow/seismic site hazard · **Elec:** ambient temperature derating |
| 2 | **3D analytical space-boundary & adjacency extractor** (closed exterior/interior wall, floor/slab, roof/ceiling surfaces + window/door sub-surfaces + shading geometry, with outward normals & net areas) | **Arch:** WWR, envelope area, daylight/solar shading, acoustics · **Mech:** watertight thermal surfaces for heat balance · **Fire:** compartmentation boundaries · **GC/Owner:** interior finish vs. exterior facade takeoffs |
| 3 | **Operating schedules & multi-variable performance tables/curves** (`bim-library` / kernel primitives) | **Mech:** occupancy/lighting/plug/setpoint profiles; DX coil, chiller, ERV, fan curves · **Elec:** demand diversity, lighting controls, inverter/transformer curves · **Plumb:** hot-water profiles, booster pump curves · **Fire:** fire pump churn/rated/150% curve · **Owner:** operating energy & utility pro forma |
| 4 | **Composable sub-components on `PartTypeDefinition`** (ordered internal sections / sub-parts) | **Mech:** custom modular AHUs/DOAS/RTUs (OA damper → filter → ERV → coils → fan) · **Elec:** switchboards & MCCs (main + breaker sections + meters) · **Plumb:** packaged pump/heat-exchanger skids · **GC/Owner:** sub-component BOM & pricing |
| 5 | **Async external analysis-runner & result-writeback contract** (`AnalysisRun` fingerprint + off-thread/worker execution) | Keeps edit commits at **0 ms overhead** (only invalidates cached run fingerprints by `changedIds`) and keeps heavy solvers (EnergyPlus WASM/native, Radiance, structural FEA, hydraulic solvers) cleanly outside `bim-kernel`, sync `CALC_POINT`, and `bim-script-runner`. Results write back as ordinary approved edits (`load_point` `basis: "calc"`, lint findings, live schedules & calc sheets). |

### 2. Optional simulation pack on top (zero kernel edits once the 5 points exist)

- **Deterministic `epJSON` compiler** (`EXPORT_TARGET_POINT`) turning MutinyBIM spaces, 3D envelope surfaces, `kernel.material` thermal/optical assemblies, openings, shading, `VentilationEngine` rates, internal heat gains, operating schedules, and custom equipment assemblies into validated `epJSON`.
- **Pluggable solver adapter:** WASM Web Worker for fast local/browser design-day loads, early architectural envelope/daylight/comfort checks, and cut-sheet verification; native worker for large 8,760-hr annual runs.
- **Script-first workflows (`@permitzip/bim-script`):**
  - Agents write and store reusable scripts in `bim-library` to build custom equipment from cut sheets, run load/environmental studies, compare scenarios (glazing SHGC, overhangs/shading, envelope R-values, ERV/DCV, system topologies), validate equipment capacity & unmet hours via `LINT_RULE_POINT`, and populate live permit schedules (`Zone Load Schedule`, `Mechanical Equipment Schedule`, `Ventilation Table`).
