## Context

- **Problem**: #75 shipped a *reactive* capture extension for Idealista — the owner has to already be looking at a listing page and think to click the popup. The owner's actual vision (stated directly) is *guided* browsing: "the app shows me a page with all the places I need to visit one by one... the plugin smartly knows what to capture and sends it to the backend." That guidance layer — a worklist of URLs to visit, with per-URL progress — does not exist anywhere in the repo today. #234 was filed to extend host support to the three WAF/API-blocked REO portals that #75's own design work already promised to route here (Sareb #121/D-026, Altamira #122/D-027, Cimenta2 #136/D-033), but #234's scope is per-portal mapping files only — it doesn't touch the worklist gap either, and no work has started on it.
- **Relationship to #75 and #234**: this issue **extends #75** (reuses its shipped ingest pipeline end-to-end, adds nothing parallel to it) and **proposes superseding #234** — same target portals, same "write a `<site>_mapping.py`" mechanism #234 already scoped correctly, but sequenced against a worklist layer #234 never addressed, and with the two-site-vs-three-site risk split made explicit (see Scope/phasing). Recommend closing #234 in favor of this issue once the owner agrees on scope; not doing that unilaterally here.
- **Worktree**: n/a — this issue is design-only, no branch yet.
- **Scope**: Design (this issue) → owner discussion → owner picks phases → *then* a worktree/phase plan gets written. In scope for the design: worklist data model + seeding strategies, dashboard worklist UI, per-portal mapping additions for Sareb/Altamira/Cimenta2, the Playwright-vs-extension assessment. Out of scope: any code.
- **Constraints**: No automated fetch to any of the three portals, ever (issue #1 §15, unchanged). No CAPTCHA-solving or fingerprint evasion. Single-operator tool — no need for multi-tenant/RBAC in the worklist design.
- **Repo touchpoints** (for the eventual implementation, not touched by this issue): `etl/schema/init.sql` (new `capture_worklist` table), `etl/capture.py` (worklist status correlation), `etl/connectors/{sareb,altamira,cimenta2}.py` + `_mapping.py` (new, following `idealista.py`'s capture-only pattern), `browser-extension/manifest.json`/`background.js` (host list — see §3 for why this might shrink rather than grow), a new dashboard page (`/captura` or similar) + API routes for the worklist.

## What's already built (read this before assuming new plumbing is needed)

`#75`'s pipeline is live, tested, and security-reviewed (Opus review on PR #87 fixed a real unauthenticated-endpoint bug and a stored-XSS bug — both closed). It is **not** Idealista-specific in mechanism, only in configured data:

```
browser-extension/ (Manifest V3, forked from property_web_scraper, MIT — NOTICE.md)
  content-script.js   → captures document.documentElement.outerHTML + url + title,
                          unconditionally, on any http(s) tab (portal-agnostic)
  popup.js            → triggers capture, injects content-script on demand if not
                          already loaded, POSTs to background.js, polls for result
  background.js       → POST {url, html} to ${apiUrl}/api/extension/capture
                          (x-admin-key auth), SUPPORTED_HOSTS gates only the
                          cosmetic badge, not the capture action itself
        ↓
dashboard/app/api/extension/capture/route.ts   → validates (http/https only, size
                                                   cap, admin-key gate), inserts a
                                                   `pending` extension_capture row,
                                                   returns immediately
        ↓ (async — separate Python container, no shared FS/RPC)
etl/capture.py   run_capture_poll_loop (~10s poll, own thread, etl/main.py)
  _connector_for_url()   → hostname-suffix dispatch via _CAPTURE_CONNECTORS dict
  <site>.normalize()     → pure parse, e.g. etl/connectors/idealista.py +
                            idealista_mapping.py (BeautifulSoup + regex, shares
                            extraction.py's first_present() fallback helper with
                            the automated connectors)
        ↓
etl.orchestrator._upsert_canonical_listing()   → the EXACT SAME persistence path
                                                   an automated connector's fetch
                                                   uses — no bypass, dedup/hard-
                                                   filtering apply identically
```

Adding a new capture-supported site today is **already** almost entirely a backend change: one new `<site>.py`/`<site>_mapping.py` pair (capture-only `Connector` subclass, `scope_key()` returns `None`, `discover()`/`fetch_detail()` raise defensively — copy `idealista.py`'s shape) + one line in `etl/capture.py`'s `_CAPTURE_CONNECTORS` dict. This issue's per-portal work (§6) is exactly that, times three.

**What's genuinely missing** is the thing the owner actually asked for: nothing tells the owner *which* URLs to visit. Today the workflow is "stumble onto a supported page, notice the badge, click capture" — there is no list, no progress tracking, no sitemap-seeded queue. That gap, not the capture mechanism, is this issue's real scope.

## Design

### 1. Architecture — reuse, don't parallel-build

No new ingest path. The worklist is a **producer of URLs for the human to open**, sitting entirely upstream of #75's pipeline, which is otherwise untouched. Concretely:

- New table `capture_worklist(id, url, source_portal, status, added_via, note, created_at, matched_capture_id, updated_at)` — `status IN ('pending','captured','failed','skipped')`, `added_via IN ('sitemap','manual','derived')`.
- `etl/capture.py`'s `_process_one` (or a small addition next to it), on a successful capture, does `UPDATE capture_worklist SET status='captured', matched_capture_id=%s WHERE url=%s AND status='pending'` — pure correlation by URL, no extension change required. A capture whose URL isn't in the worklist at all (the owner free-browsed something not on the list) still processes normally; the worklist is a *guide*, not a gate.
- A new dashboard page renders the worklist: counts by status/portal, a table with an "Abrir" link per pending URL (opens in a new tab — the owner still does the actual browsing and still clicks the extension popup themselves; this issue does **not** propose the extension auto-navigating anything, which would reintroduce the automation question this whole design exists to avoid).

### 2. The guided worklist — how URLs get in

Three seeding paths, matching the ask exactly, and the three portals split cleanly across them:

| Portal | Seeding path | Why |
|---|---|---|
| **Cimenta2** | **Sitemap fetch** — `GET https://inmuebles.cimenta2.com/inmuebles/s/sitemap.xml` (and the two child sitemaps it references) on a permissive `robots.txt` (D-033 finding 4). One backend job parses ~3,917 `ga-activo` + ~490 `inv-expediente` URLs into `capture_worklist` with `added_via='sitemap'`. **This is a plain XML fetch to a host that explicitly allows it and returns a boring static file — categorically different from fetching a listing page (which the WAF/shell problem makes pointless anyway) and does not touch the guest RPC D-033 forbids.** Re-run periodically (e.g. weekly) to pick up new/removed assets — `lastmod` in the sitemap makes incremental reseeding cheap. |
| **Sareb / Altamira** | **Manual entry**, at least initially — neither site has ever returned a `robots.txt`, let alone a sitemap (D-026, D-027); there is nothing to fetch. A simple textarea/paste form on the worklist page, one URL per line, `added_via='manual'`. |
| **Sareb / Altamira (later)** | **Derived from prior captures** — once the owner has manually found the search UI and captured a *search-results* page (not just a detail page), the backend can parse that captured HTML for outbound listing-detail links the same way `<site>_mapping.py` parses a detail page for fields, and enqueue them as new `pending` worklist rows, `added_via='derived'`. This is the mechanism that actually earns "worklist," not just "URL list," for the two portals with no sitemap — worth a dedicated mapping concept (a `parse_index_page(html) -> list[str]` function alongside each site's detail-page `normalize()`), scoped as a later phase (§6) since it depends on first knowing what a Sareb/Altamira search page even looks like. |

Progress tracking is per-URL, `pending → captured/failed/skipped`, visible as counts on the worklist page (e.g. "Cimenta2: 3,812/3,917 captured"). No global "job" concept needed — this is human-paced by construction (see §7).

### 3. "Smartly knows what to capture" — already true, tighten one gap

The ask assumes the extension needs per-portal capture logic. **It doesn't, today, by design**: `content-script.js` captures the full rendered DOM unconditionally on every portal; all the portal-specific intelligence — which CSS selector holds the price, which embedded JSON path has the coordinates, which regex extracts the reference code — lives entirely in the Python `<site>_mapping.py` files, dispatched backend-side by hostname. This is *already* "capture rules delivered from the backend without shipping a new extension," in the strongest possible sense: capture itself never varies by portal at all.

One real gap, worth fixing as part of this work: `background.js`'s `SUPPORTED_HOSTS` array is hardcoded and only gates the cosmetic badge (✓ icon) — capture itself works on **any** http(s) tab already, because `popup.js` falls back to `chrome.scripting.executeScript` (covered by the `activeTab`/`scripting` permissions, not `host_permissions`) when the content script isn't pre-injected. So a new portal *can* be captured today with zero extension changes at all; only the confirmatory badge lags. Recommend making `SUPPORTED_HOSTS` backend-driven (a small `GET /api/extension/config` the background worker polls/caches, mirroring `_CAPTURE_CONNECTORS`'s keys) so adding a fourth or fifth portal later is a **pure backend change, no extension version bump, ever** — closing the gap between "the mechanism already supports this" and "the badge/manifest claims it."

**Cimenta2-specific capture caveat** (from the #75 comment thread, worth restating loudly here since it's easy to get wrong): the shell is a Salesforce Lightning SPA — client-side routing, async component population, no `document-ready`-equivalent moment. `content-script.js` currently captures on-message, immediately — for Cimenta2 the human needs to actually wait for the page to visibly finish rendering before opening the popup and clicking capture, or the captured DOM will be an empty shell. Worth a small popup-side nudge (not a hard gate) rather than trusting the human to remember.

**Cimenta2-specific data caveat, non-negotiable**: capture the rendered public fields only (price, surfaces, rooms, address, coordinates, cadastral ref, photos — the ~15 fields D-033 confirms the site itself displays). **Never** call the guest Aura RPC from any backend code, ever, even to "double check" a field — that RPC is the thing D-033 forbids building on, full stop, regardless of which fields are requested from it (D-033 explicitly rejects the "just ask for the narrow public subset" framing). `cimenta2_mapping.py`'s module docstring should restate this as loudly as `idealista.py`'s does its own constraint.

### 4. Normalization + dedup — no new work

Inherited automatically: every worklist-driven capture flows through the identical `_upsert_canonical_listing()` path #75 already wired, so dedup (#16's engine), hard-filtering, and the candidate feed treat a Sareb/Altamira/Cimenta2 capture exactly like a Fotocasa/Milanuncios fetch. Provenance is already the established pattern — `raw_extra={"capture_source": "browser-extension", ...}` (see `idealista.py`) — recommend also stamping `capture_worklist_id` into `raw_extra` when the capture matched a worklist row, purely for "how did this listing get here" auditability, not for any pipeline logic to depend on. The `status="active"`-always honesty rule (`idealista.py`'s own comment: a capture-only connector never revisits a listing, so it can't honestly claim anything but "active" at capture time) generalizes unchanged to all three new connectors.

### 5. The Playwright question — assessed honestly

**Why the extension works where Playwright is blocked**: this project already has a direct, empirical answer, not a hypothesis. D-026's Sareb spike drove real Playwright (1.60, headed *and* headless, default fingerprint, no stealth, no proxy, no CAPTCHA-solving) at `www.sareb.es` and got the identical `403` a plain `curl` got. WAF vendors (Incapsula here, Akamai for Altamira) fingerprint the automation stack itself — `navigator.webdriver`, CDP artifacts, missing plugin/font entropy, request-timing regularity — not just the User-Agent string. A fresh Playwright-launched browser, however "real" the engine, presents exactly those automation tells regardless of how human the resulting requests look at the HTTP layer. A human's own daily-driver browser has none of them: no `navigator.webdriver`, an aged real cookie jar, genuine IP/browsing-history reputation, and — per the PR #224 finding recorded in D-026 — Sareb's 403 is specifically an Incapsula **JS challenge** a real browser resolves invisibly during ordinary use, which is positive, not merely theoretical, evidence the extension path can work there. Altamira's 403 (D-027) is a **static Akamai deny with no challenge at all** — a materially weaker signal that a human's own browsing gets through either, discussed in §6.

**What Playwright *could* do that this design doesn't propose**: drive the owner's own real, already-authenticated Chrome profile via CDP (`--remote-debugging-port`, attaching to a running browser with real history/cookies/extensions rather than launching a fresh throwaway context). This is a meaningfully different technical proposition from the fresh-launch case D-026 already falsified — it's worth naming rather than dismissing by association. Two things make it not the better choice here, both worth being explicit about rather than just asserting:

1. **Technically uncertain, not proven safe.** CDP attachment leaves its own fingerprint surface (the `Runtime.enable`/`Page.enable` protocol handshake, timing characteristics distinguishable from real input events) that some WAF vendors specifically check for — there's no evidence either way for Incapsula/Akamai specifically, and finding out costs a real, deliberate automation attempt against a site this project has committed not to automate.
2. **It reintroduces exactly the ToS/ethics posture problem the extension avoids, even in the case where it technically works.** The owner's own distinction — "I install the plugin, *I* browse one by one, the extension captures what I'm already looking at" — is a *human choosing to visit pages*. A CDP-driven script iterating a worklist and auto-navigating the owner's real browser is automated traffic wearing a human's cookie jar; it is not the same act as the human doing it, even on the same browser binary. D-026/D-027's own "a person's own browsing is a different signal from an automated fetch" framing is about *who initiates each page load*, not just what artifacts the HTTP request carries.

**Verdict**: the extension (human-initiated, one page at a time, guided by the worklist) is the better fit and the one this design proposes. The CDP-attached-real-profile variant is not recommended for implementation, but is worth naming to the owner explicitly as a considered-and-declined alternative, in case they want a one-off, owner-supervised experiment purely to settle the Altamira "does a human even get through" open question (§6) faster than manually clicking around — that would still be the owner doing it personally, at the keyboard, not unattended automation.

### 7. Risks / constraints

- **ToS/legal posture**: unchanged from #75 — private personal use, not resale, the owner's own browsing captured after the fact, no automated request ever reaches any of the three hosts (Cimenta2's sitemap fetch is the one exception, and it's a plain static-file GET to a host whose own `robots.txt` explicitly invites it — not a listing-page or RPC fetch).
- **Auth extension↔backend**: already solved by #75 (`x-admin-key`, `ADMIN_API_KEY`, PR #87's fix) — no new auth surface, the worklist API routes reuse the same admin-key gate as every other write-capable dashboard route.
- **No third-party PII**: unchanged constraint (AGENTS.md, issue #1 §15) — the Cimenta2 caveat in §3 is the sharpest version of this risk in the whole design, since the failure mode there (accidentally pulling from the guest RPC "just this once") is a live temptation, not a hypothetical.
- **Rate/volume is human-paced — a feature, not a bug**: worth stating plainly since it's easy to read a 3,917-row Cimenta2 worklist as implying a fetch-rate problem. It doesn't — the sitemap fetch is one lightweight XML GET; every actual page load is a human clicking "Abrir" and browsing normally, at whatever pace they choose, with no code anywhere driving navigation. The worklist's only job is to remember what's left, not to pace or trigger anything.
