# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**feat(build): support .tpk packaging alongside .wgt**

*Project description:*
### Problem

Auger currently ships only as a signed Tizen web package (`Auger.wgt`) via GitHub Releases, Apps2Samsung, and Tizen Studio sideloading.
A user asked whether Auger can also be distributed as a `.tpk` package to support users who prefer or rely on `.tpk`-based install workflows on Samsung TVs.

### Device

Samsung TV

### Current workaround

Install `Auger.wgt` through Apps2Samsung or sideload `dist/Auger.wgt` with Tizen Studio / `tizen install`.

### Proposed behavior

Evaluate and decide whether Auger should offer a `.tpk` distribution option alongside `Auger.wgt` so users have more than one supported install format for Samsung TVs.

### Alternatives considered

- **Keep `.wgt` only:** Maintain a single `Auger.wgt` artifact and document supported `.wgt` install paths (Apps2Samsung, Tizen Studio / SDB). Lower maintenance cost, but does not cover users specifically asking for a `.tpk`.
- **Separate legacy `.wgt` build (#978):** Addresses older Tizen versions below 8.0, which is orthogonal to `.wgt` vs `.tpk` packaging.

### Technical notes

Auger is a TypeScript/HTML/CSS web app (`app/config.xml`, `scripts/build-wgt.sh`) that plays video through Samsung's native AVPlay (`<object type="application/avplayer">`) and stores credentials in Tizen KeyManager.
Because `.wgt` (Web Widget) and `.tpk` (Native / .NET / Flutter Tizen Package) use different manifests and runtimes, shipping a `.tpk` requires choosing an architecture:

1. **Option A — Thin native `.tpk` wrapper around the existing web app**
   - Package the built web bundle inside a minimal Tizen Native (C/C++) or Tizen .NET WebView shell.
   - **Pros:** Keeps a single UI and `/api/v2` client codebase; lower ongoing drift against `silo-apple` parity.
   - **Cons / risks to verify:**
     - Confirm whether Samsung TV Web APIs (`webapis.avplay`, `webapis.productinfo`, `tizen.keymanager`, TV remote key registration) work inside a `.tpk` WebView or require native-to-JS bridges to Tizen Native multimedia/KeyManager APIs.
     - Adds a second manifest (`tizen-manifest.xml`), package ID, native toolchain in CI, and signing/release path.

2. **Option B — Native `.tpk` rewrite (C/C++, Tizen .NET, or Flutter-Tizen)**
   - Build a dedicated native Tizen TV client targeting `/api/v2` and native AVPlay bindings.
   - **Pros:** First-class native `.tpk` lifecycle, direct native APIs, and potential UI/memory improvements on slower TVs.
   - **Cons:** Full second client to build, test, and maintain alongside `.wgt`; Tizen native `api-version` differences across TV model years can require multiple `.tpk` builds.

3. **Open questions before deciding**
   - Which specific install tool, workflow, or Samsung TV model requires a `.tpk` instead of `Auger.wgt`?
   - Does Apps2Samsung or the requested installer handle `.tpk` re-signing and updates the same way as `.wgt`?
   - Would a `.tpk` coexist with `AugerTv001.Auger` or use a separate package identity?
