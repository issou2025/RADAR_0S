# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Review and modernize the "pyRevit For Teams" deployment guide**

*Project description:*
## Summary

The existing [pyRevit For Teams](<https://pyrevitlabs.notion.site/pyRevit-For-Teams-ddc6c312d6f6488691eed2ec7704fd97>) documentation appears to be outdated and no longer fully reflects the current pyRevit architecture, CLI functionality, installation process, and deployment workflows.

I'd like to propose reviewing and updating this guide, while also considering moving some or all of its technical content into the version-controlled documentation in this repository.

The goal is to provide administrators, BIM managers, IT teams, and pyRevit developers with an accurate, maintainable guide for deploying and managing pyRevit across multiple machines.

## Motivation

The existing guide covers several important topics:

- Installing the pyRevit CLI
- Installing dependencies
- Cloning and distributing pyRevit
- Installing and distributing extensions
- Customizing pyRevit for a team
- Configuring pyRevit
- Attaching pyRevit to Revit installations
- Updating deployments
- Deploying COREUPDATE
- Collecting usage and error data
- Setting up telemetry

However, the project has evolved considerably since this guide was written.

The current repository already contains more detailed documentation for several of these areas, including:

- [Developer Guide](<https://github.com/pyrevitlabs/pyRevit/blob/develop/docs/dev-guide.md>)
- [CI/CD and release flow](<https://github.com/pyrevitlabs/pyRevit/blob/develop/docs/ci-cd.md>)
- [Architecture](<https://github.com/pyrevitlabs/pyRevit/blob/develop/docs/architecture.md>)
- [Extensions](<https://github.com/pyrevitlabs/pyRevit/blob/develop/docs/extensions.md>)
- [Repository organization](<https://github.com/pyrevitlabs/pyRevit/blob/develop/docs/repo-organization.md>)

This creates an opportunity to consolidate documentation, eliminate outdated instructions, and make future maintenance easier.

## Proposed work

### 1\. Review the existing guide

Go through the existing Notion guide and identify:

- Outdated commands, CLI arguments, and workflows.
- Deprecated or superseded functionality.
- Installation and configuration assumptions that are no longer valid.
- Missing information about current deployment options.
- Content that is still useful and should be retained.

### 2\. Identify documentation that belongs in the repository

Consider moving technical documentation into `docs/`, where it can be maintained alongside the implementation.

Potential topics include:

- Enterprise and multi-machine deployment.
- Installation and deployment strategies.
- CLI-based installation and configuration.
- Clone management and distribution.
- Revit version attachment and launch strategies.
- Extension distribution and management.
- Deployment updates and version management.
- Configuration management and environment variables.
- Telemetry deployment and configuration.
- Example PowerShell scripts for automated deployment.

Not all these topics necessarily require separate documents. They could be organized into a dedicated deployment guide with links to existing documentation where appropriate.

### 3\. Establish a clear documentation structure

One possible structure:

`docs/deployment.md` or a dedicated deployment documentation section covering:

1. Introduction and deployment concepts.
2. Choosing an installation and distribution strategy.
3. Installing pyRevit in managed environments.
4. Managing clones and binaries.
5. Configuring pyRevit across machines.
6. Attaching pyRevit to Revit installations.
7. Managing custom and third-party extensions.
8. Updating and maintaining deployments.
9. Telemetry and usage monitoring.
10. Troubleshooting common deployment problems.

The exact structure should be determined after reviewing the existing documentation to avoid unnecessary duplication.

### 4\. Update the Notion guide

Once the technical documentation has been consolidated:

- Update the Notion guide to reflect current deployment recommendations.
- Remove duplicated technical instructions where appropriate.
- Link directly to the relevant GitHub documentation.
- Keep Notion as an accessible introduction and overview if that remains useful.

Alternatively, consider whether the Notion guide should be replaced entirely by the repository documentation.

## Expected outcome

- A reliable, up-to-date deployment guide.
- A clear distinction between individual installation and managed team deployment.
- One authoritative source for technical instructions.
- Less duplicated documentation to maintain.
- Examples and commands that reflect the current CLI and release infrastructure.
- Easier contributions and documentation updates through pull requests.
