## What problem does this solve?

Chronic illness disproportionately affects people who are older, lower-income, or otherwise likely to be running an out-of-date phone rather than this year's flagship — exactly the audience Health Flare exists for. Right now we default to whatever the current Flutter toolchain and our own project config consider "current," which quietly narrows the pool of installable devices every time we bump the SDK. We should default to the newest OS/tooling for development, but *deliberately* choose the lowest OS versions and broadest device set we can reasonably still support, rather than letting the floor drift upward by default.

This started as a narrower ask about the two version-floor settings below, but those are only part of the picture — device compatibility for Play Store/App Store reach also depends on architecture, RAM, screen size/form factor, and what real devices are actually still active in each store's catalog. This issue covers the full audit. Desktop/web (`macos/`, `windows/`, `linux/`, `web/`) are out of scope — CLAUDE.md scopes this app to iOS and Android, and those directories look like unused `flutter create` scaffolding rather than a shipped target; worth confirming and possibly removing in a separate issue, but not part of this audit.

Known gaps already found in-repo:
- **Android** (`android/app/build.gradle.kts`): `minSdk`/`targetSdk` aren't pinned — they fall through to `flutter.minSdkVersion` / `flutter.targetSdkVersion`, i.e. whatever the installed Flutter SDK ships as its default. That floor isn't visible in this repo and can silently rise on a routine `flutter upgrade`.
- **iOS** (`ios/Runner.xcodeproj/project.pbxproj`, all three build configs): `IPHONEOS_DEPLOYMENT_TARGET = 15.0`, explicitly pinned. iOS 15 shipped in 2021 — that already excludes anyone on an iPhone 6s/7-era device stuck on iOS 14 or earlier.

Neither floor is currently justified anywhere in the repo (no comment, no doc), so it's not clear whether these are real dependency constraints or just whatever `flutter create` defaulted to at the time.

## Proposed behavior

**1. OS version floors**
- Determine the actual minimum Android `minSdk` our current dependency set allows (`geolocator`, `isar_community`/`isar_community_flutter_libs`, `image_picker`, `file_picker`, `share_plus`, `url_launcher`, `pdf`, `fl_chart`). Pin `minSdk` explicitly in `android/app/build.gradle.kts` at that floor instead of inheriting `flutter.minSdkVersion`, so the supported floor is visible in-repo and doesn't move on a Flutter upgrade without a deliberate change here. Leave `targetSdk` tracking Flutter's recommended default — Play Store requires a current `targetSdk` for new submissions regardless; this is about how *old* a device can still install the app, not how we build for new ones.
- Re-evaluate iOS `IPHONEOS_DEPLOYMENT_TARGET`. Check whether 15.0 is a real requirement of our dependencies or just the Xcode/Flutter template default, and lower it as far as the toolchain and plugin set allow (App Store submission requirements permitting).

**2. Architecture and device class**
- Confirm we're not silently dropping 32-bit Android (`armeabi-v7a`) support via `abiFilters` or a dependency that's arm64-only — 32-bit devices are still a meaningful slice of the active Play Store install base in budget-device markets.
- Check whether any dependency (Isar's native libs in particular) imposes its own architecture or minimum-RAM floor tighter than the OS version floor.

**3. Screen size / form factor**
- Verify the app isn't accidentally tablet- or phone-only via manifest/`Info.plist` orientation or size-class restrictions, given multi-profile/family use is a stated use case that plausibly includes tablets.

**4. Document and guard the result**
- Document the resulting floors and *why* each is set there (which dependency or API is the binding constraint) — a code comment next to each setting is enough, no separate doc needed.
- Flag it in code review whenever a dependency bump would raise a floor, so it's a deliberate tradeoff rather than a silent regression. `docs/features/developer-experience.feature` may be the right home for a scenario capturing this if the team wants it enforced rather than just documented.
