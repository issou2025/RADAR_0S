## Problem or Use Case

The MCP specification release candidate **2026-07-28** (now past its scheduled date) is the largest revision of the protocol since launch and makes MCP **stateless** ([RC announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)):

- The `initialize`/`initialized` **handshake is removed**.
- The **`Mcp-Session-Id` header is removed** — any request can be routed to any server, so MCP works behind a plain load balancer. Protocol/client version info moves into per-request `_meta` fields.
- The TypeScript v2 SDK has **shipped stable (2026-07-27)** — but as **new split packages**, not a 2.x bump of the current monolith ([SDK announcement](https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/)):
  - `@modelcontextprotocol/client@2.0.0`
  - `@modelcontextprotocol/server@2.0.0`
  - `@modelcontextprotocol/core@2.0.0`
  - The legacy monolith `@modelcontextprotocol/sdk` currently tops out at **1.30.0** (published 2026-07-27) and does not implement the stateless protocol.

OpenClaw currently pins **`@modelcontextprotocol/sdk": "1.30.0"`** (root `package.json`, also in `ui/package.json` alongside `@modelcontextprotocol/ext-apps`). To speak the new spec, OpenClaw needs to migrate onto the split v2 packages — there is no issue currently tracking this.

### OpenClaw's MCP surface area (from a repo-wide grep)

**72 files** import from `@modelcontextprotocol/sdk`; the main touch points:

**Client side:**
- `src/agents/mcp-transport.ts` — transport factory importing `SSEClientTransport` (`client/sse.js`), `StreamableHTTPClientTransport` (`client/streamableHttp.js`), and `FetchLike`/`Transport` types (`shared/transport.js`).
- `src/agents/mcp-stdio-transport.ts` — custom stdio client transport.
- `src/agents/mcp-oauth.ts`, `mcp-oauth-fetch.ts`, `mcp-oauth-provider.ts`, `mcp-oauth-store.ts` — the OAuth stack (v2 also reworks the auth story; `jose`/PKCE now live in the new packages).
- `src/agents/mcp-http-fetch.ts`, `mcp-auth-profile.ts` — header/auth plumbing around the transports.

**Server side (16 files import `@modelcontextprotocol/sdk/server/*`):**
- `src/mcp/tools-stdio-server.ts` — low-level `Server` + `StdioServerTransport` with `CallToolRequestSchema`/`ListToolsRequestSchema`.
- `src/mcp/channel-server.ts`, `channel-server-runtime.ts`, `channel-bridge.ts`, `channel-tools.ts` — channel MCP runtime.
- `src/mcp/openclaw-tools-serve.ts`, `plugin-tools-serve.ts`, `codex-supervision-tools-serve.ts` — tool-serving surfaces.

**Hand-rolled HTTP server:**
- `src/gateway/mcp-http.ts` + `src/gateway/mcp-http.handlers.ts` — the gateway loopback MCP server is a bespoke JSON-RPC implementation, so its handshake/session semantics must be audited directly against the stateless spec (no SDK upgrade will fix it automatically).

**Existing `Mcp-Session-Id` references** (4 files, incl. `extensions/parallel/src/parallel-mcp-search.runtime.ts` and tests) — these encode the session model the new spec removes.

## Proposed Solution

A staged migration, one PR per step:

### Step 1 — Inventory & spike
- Catalog all `@modelcontextprotocol/sdk` import sites and classify them client / server / shared-types.
- Spike one client path (e.g. streamable-HTTP connect + `tools/list` + `tools/call`) against `@modelcontextprotocol/client@2.0.0` to surface the transport/API delta.

### Step 2 — Migrate the MCP client paths
- Move `src/agents/mcp-transport.ts` and the OAuth stack onto `@modelcontextprotocol/client@2.0.0`.
- Remove session-bound assumptions (handshake ordering, `Mcp-Session-Id` handling) from `extensions/parallel` runtime and any client code.
- Keep the legacy `@modelcontextprotocol/sdk@1.x` path available behind config/feature flag if needed, so users on older MCP servers are not broken.

### Step 3 — Migrate the MCP server surfaces
- Move stdio tool servers (`src/mcp/*-serve.ts`, channel server) onto `@modelcontextprotocol/server@2.0.0`.
- Audit the hand-rolled gateway loopback server (`src/gateway/mcp-http*.ts`) against the stateless spec: drop any `initialize` gating / session-id coupling, accept per-request `_meta`.

### Step 4 — Tests & compatibility matrix
- Add a CI leg exercising OpenClaw as client against an `@modelcontextprotocol/server@2.0.0` reference server, and vice versa.
- Keep a 1.x test leg for at least one minor release so existing user-configured MCP servers keep working.

### Step 5 — Docs
- Update `docs/tools/mcp.md` and `docs/cli/mcp.md` with the new transport/config behavior and any migration notes for users running custom MCP servers.

### Acceptance criteria
- [ ] OpenClaw can connect, list tools, and call tools against a stateless (2026-07-28 spec) MCP server over HTTP without `initialize`/`Mcp-Session-Id`.
- [ ] Server surfaces (stdio + gateway loopback) accept stateless clients.
- [ ] CI green against both a 1.x server/client leg and a 2.0 leg.
- [ ] `Mcp-Session-Id` references removed or explicitly gated for legacy compat.
- [ ] Release/migration note added in `docs/`.

## Alternatives Considered

1. **Stay on `@modelcontextprotocol/sdk@1.30.x` indefinitely.** Rejected: 1.x will not speak the stateless protocol, so OpenClaw will stop interoperating with servers that upgrade once the spec goes final — and the v2 stable already shipped.
2. **Fork the monolith SDK and patch in stateless support.** Rejected: upstream v2 is stable in the new split packages; forking creates a permanent maintenance burden.
3. **Wait for the monolith `@modelcontextprotocol/sdk` to reach 2.x.** Risky: the v2 line was deliberately split into `client`/`server`/`core` packages; there is no indication the monolith gets a 2.0.
