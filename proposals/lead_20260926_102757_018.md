## Problem / intent

The non-release hosted surface is spread across four first-party workflows:

- `.github/workflows/ci.yml` — ordinary PR/master merge sufficiency plus explicit exhaustive dispatch;
- `.github/workflows/pr-semver-label.yml` — package-path classification, semver-label/changeset validation and release-branch special cases;
- `.github/workflows/security.yml` — PR/master security checks plus weekly scheduled security work;
- `.github/workflows/consumer-validation.yml` — scheduled and manually/release-invoked installed-consumer validation.

These are not four independent product lifecycles. They are mostly two responsibilities:

1. **merge/admission** for a source change;
2. **recurring maintenance/observation** of the repository and shipped product.

The current hosted split duplicates triggers, checkout/setup, status interpretation and maintainer vocabulary. It also leaves substantial policy directly embedded in YAML—for example the semver admission implementation is a long inline Python program inside the workflow rather than a repository-owned operation that can be tested/invoked directly.

The correction is to contract this surface without recreating release-sized CI on ordinary PRs.

## Intended outcome

Non-release automation has one obvious ordinary path and one obvious recurring path:

- **CI**: ordinary PR/master merge sufficiency, package/semver policy, and explicit exact-head escalation when a claim genuinely needs broader proof.
- **Maintenance**: scheduled installed-consumer observation and periodic security/health work.

GitHub-specific security permissions may justify a small separate wrapper/job if CodeQL or another provider requires it. Such a wrapper must remain thin and must not recreate a second policy/orchestration surface.

Semver/path classification, merge-stage policy and result interpretation live in repository-owned code where they can be exercised without GitHub Actions. Hosted YAML primarily supplies trigger/event data, permissions, runner identity and repository-owned command invocation.

The resulting PR should delete superseded hosted entrypoints rather than keep aliases for familiarity.

## How it fits the larger picture

This is the non-release implementation leaf under #3654.

#3202 already established the semantic boundary: ordinary PRs prove merge sufficiency and broad release-grade proof is explicit. This issue keeps that boundary but makes the hosted expression substantially smaller and easier to reason about.

#3600/#3604 remain the owners of what installed-consumer validation means; this issue changes how that work is hosted/scheduled, not its product/evidence semantics.

## Scope

In scope:

- `ci.yml`, `pr-semver-label.yml`, `security.yml`, and `consumer-validation.yml`;
- move semver admission/path classification out of inline workflow code into an existing or small consolidated repository-owned tool;
- present one stable CI status model for ordinary PR/master work;
- retain explicit exact-head/broad escalation without making it ambient;
- consolidate scheduled consumer/security/health triggers into one coherent maintenance surface where provider constraints permit;
- reduce repeated setup and duplicated trigger/result logic;
- update required-check/ruleset and workflow/static tests accordingly;
- delete retired workflow files/jobs once their responsibilities are carried by the surviving entrypoints.

Out of scope:

- preview/stable release orchestration, owned by the sibling release child and #3652;
- weakening CodeQL, dependency review, secret scanning or other current security claims;
- changing the product semantics of installed-consumer validation;
- introducing a generic CI dispatcher, changed-path scheduler or workflow DSL;
- moving broad release qualification back onto every PR.

## Acceptance criteria

- [ ] Ordinary non-draft PRs have one clear merge-sufficiency hosted entrypoint/status rather than separate CI and semver-policy workflows that maintainers must interpret together.
- [ ] Package-affecting path classification, semver-label/changeset validation and coordinated-release exceptions execute through repository-owned code rather than a large inline Python program in Actions YAML.
- [ ] The semver policy remains directly testable with ordinary repository tests and receives the current PR event/changed-path facts as data, not hidden GitHub-only semantics.
- [ ] #3202 remains true: normal PRs do not unconditionally schedule package builds, exhaustive runtime matrices or support-bearing aggregation.
- [ ] Explicit exact-head escalation remains available and binds its reason and subject; its operation is not duplicated in a second hosted workflow.
- [ ] Scheduled installed-consumer validation and scheduled security/health work are reachable through one coherent maintenance entrypoint/schedule model where no provider trust boundary forbids it.
- [ ] PR/master security checks remain blocking exactly where current policy requires them. If GitHub permission/CodeQL constraints require a distinct workflow identity, it is thin, its reason is documented in the parent disposition, and substantive policy is not duplicated there.
- [ ] Consumer-validation semantics, exact public subject freezing and report ownership from #3600/#3604 are preserved.
- [ ] Required checks/rulesets no longer depend on removed implementation-detail workflow/job names.
- [ ] Superseded `pr-semver-label.yml` and any other no-longer-needed non-release workflow entrypoints are deleted rather than retained as forwarding aliases.
- [ ] Before/after inventory shows a material reduction from the current non-release baseline (4 workflow files and their hosted jobs/YAML), with no equivalent generated Actions graph introduced elsewhere.
- [ ] One narrow package-affecting PR, one non-package PR, one semver-policy failure, one explicit high-risk escalation and one scheduled-maintenance exercise all reach the intended status through the contracted model.
- [ ] Failure localization remains specific: semver, merge proof, security and maintenance failures can be identified without opening a monolithic opaque aggregate.
- [ ] Existing repository-owned test/proof authority remains the owner of evidence sufficiency; the workflow does not add another changed-path/test-selection policy.

## Non-solutions

The following do not close this issue unless explicitly listed in the acceptance criteria:

- merely renaming `pr-semver-label.yml` or calling it from `ci.yml`;
- copying the existing inline semver program into another YAML step;
- combining all checks into one giant shell block whose failures are harder to localize;
- making security advisory because contraction is easier;
- deleting scheduled installed-consumer validation;
- running the full release matrix on every PR;
- adding a new repository-wide CI scheduler or hand-maintained path-to-test registry;
- preserving old workflow files as compatibility shims indefinitely;
- counting reusable-workflow indirection as simplification when the same hosted concepts/jobs remain.

## Final satisfaction

A maintainer looking at a normal PR sees one ordinary CI story: merge sufficiency, including package/semver policy and required security claims, with explicit escalation only when requested.

Recurring installed-product/security observation has one maintenance story.

The hosted surface is smaller because responsibilities were merged into existing owners and repository code, not because the same graph was hidden behind reusable YAML.
