**craft-sheet: should built-in formats 37 to 40 match Excel's reported text?**

*Project description:*
**Published list.** At commit `bf448c194a320f0bce54e6b7f9f0ce6bf97a8831`, the four entries for ids 37 to 40 in `crates/sheet/src/tables.rs`, lines 29 to 32, match the ISO/IEC 29500-1 list reproduced by Microsoft Learn: https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.numberingformat . The `[MS-XLS]` IFmt page refers to ECMA-376 Part 1, section 18.8.30, for built-in number formats: https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/9017e247-7995-4a9c-96e8-950df24735a2 . My Excel test below reports different text for those four ids.

**What Excel reports.** Microsoft Excel, version 16.0 build 20527 (Windows); UI language English (United States), id 1033, install language 1033; Windows culture en-US, region United States; decimal separator `.`, thousands separator `,`. The script at the end of this issue creates a workbook whose cell formats reference built-in ids 37 to 40, with no `numFmts` element in `xl/styles.xml`. A1 to A4 hold 1234.5 and B1 to B4 hold -1234.5. I opened it in Excel and read these properties through automation:

```powershell
$xl = New-Object -ComObject Excel.Application
$wb = $xl.Workbooks.Open((Join-Path (Get-Location).Path "numfmt-in.xlsx"))
$ws = $wb.Worksheets.Item(1)
1..4 | ForEach-Object { $c = $ws.Cells.Item($_,1); "id $(36+$_): [$($c.NumberFormat)] [$($c.NumberFormatLocal)] [$($c.Text)] [$($ws.Cells.Item($_,2).Text)]" }
$wb.Close($false); $xl.Quit()
```

| id | `NumberFormat` and `NumberFormatLocal` (identical) | A (1234.5) shows | B (-1234.5) shows |
|---|---|---|---|
| 37 | `#,##0_);(#,##0)` | `1,235 ` | `(1,235)` |
| 38 | `#,##0_);[Red](#,##0)` | `1,235 ` | `(1,235)` |
| 39 | `#,##0.00_);(#,##0.00)` | `1,234.50 ` | `(1,234.50)` |
| 40 | `#,##0.00_);[Red](#,##0.00)` | `1,234.50 ` | `(1,234.50)` |

The reported positive `Text` values end with a space. In a number-format code, `_)` reserves the width of a closing parenthesis. I tested only English (United States).

**What the library returns for the same file.** `Document::read` then `styles.cell_number_format(i)` for each cell format, with default `Limits`, at the commit above:

```

xf 2: numFmtId 38 -> Some("#,##0 ;[Red](#,##0)")
xf 3: numFmtId 39 -> Some("#,##0.00;(#,##0.00)")
xf 4: numFmtId 40 -> Some("#,##0.00;[Red](#,##0.00)")
```

The same table is used for `.xls`. In Excel I made a new workbook, put 1234.5 in A1, set its number format to `#,##0.00_);(#,##0.00)` (Format Cells, Custom) and saved it as Excel 97-2003. The file has an XF with format id 39 and no FORMAT record for that id, and `craft_xls::read` returns `#,##0.00;(#,##0.00)` for the cell.

**Other source tables (not run on this fixture).** The pinned xlrd and Apache POI tables both use `_)` for ids 37 to 40, matching the format strings reported by my Excel test above. These links are corroborating references; the proposed values come from that test.
- xlrd: https://github.com/python-excel/xlrd/blob/d8302dc39b16c03d643ef1eee89605c2e007ed2b/xlrd/formatting.py#L391-L394
- Apache POI: https://github.com/apache/poi/blob/8d9b40ac4cb62b1c61759c900fb422abfeac4367/poi/src/main/java/org/apache/poi/ss/usermodel/BuiltinFormats.java#L113-L116

**Why I am asking.** For ids 39 and 40, the library's returned code omits the `_)` spacing token reported by Excel. For ids 37 and 38, it has a literal space instead. A caller that renders those returned codes may therefore reserve different space after positive numbers.

**Scope.** The synthetic `.xlsx` example covers all four ids. The separate `.xls` example above covers only id 39.

**The question.** Would you consider using the format strings reported by the Excel test above for these four ids? If you prefer to keep these entries aligned with the published list, would a comment documenting the observed difference be useful?
