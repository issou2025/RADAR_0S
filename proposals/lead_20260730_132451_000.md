# Project Proposal — Dwg To Revit

## Project Understanding
You need assistance with: 
**extraction.py only explodes INSERT one level deep, silently dropping nested block content**

*Project description:*
## Summary

`extraction.py`'s INSERT-handling in `extract_and_normalize_entities` (the `_process_block_entity` helper plus the `for sub_ent in block:` loop in the main iteration) only unpacks **one level** of block nesting:

```python
if etype == "INSERT":
    counts["INSERT"] += 1
    ins_pt = entity.dxf.insert
    ins_s = entity.dxf.get("xscale", 1.0)
    try:
        block = entity.doc.blocks.get(entity.dxf.name)
        if block:
            for sub_ent in block:
                if sub_ent.dxftype() in ("LINE", "CIRCLE", "ARC", "TEXT", "MTEXT"):
                    _process_block_entity(sub_ent, layer, ins_pt.x, ins_pt.y, ins_s)
    except Exception:
        pass
```

There's no recursion when `sub_ent.dxftype() == "INSERT"` — a nested block reference inside another block reference is silently skipped entirely (it doesn't match the `("LINE", "CIRCLE", "ARC", "TEXT", "MTEXT")` whitelist, and nothing recurses into it). `LWPOLYLINE`, `HATCH`, and `SOLID` are also missing from that whitelist even for direct (non-nested) block content, though `SOLID` and `LWPOLYLINE` are handled at the top-level modelspace iteration.

Present since the initial commit (`63b0b68c`, 2026-06-24) — `extraction.py` hasn't been touched by any later commit.

## Impact (concrete case)

Ran `analyze_dxf()` against a real Revit-sourced architectural DXF export (`ORIG_LAYOUT_REF.dxf`, ~50.8k leaf entities across 30 real layers once fully flattened) as part of a DWG-Compare/orienteering workflow. The pipeline only surfaced **7 layers**: `0`, `C-PROP-LINE`, `A-DETL`, `G-ANNO-SYMB`, `G-ANNO-TEXT`, `A-AREA-IDEN`, `A-DETL-HDLN` — missing `A-WALL`, `A-DOOR`, `A-GLAZ`, and every other layer that only appears inside nested Revit-family block instances (which is most of the drawing's real architecture; Revit DXF exports commonly nest 2+ INSERT levels deep: a room/unit block containing door/window/fixture family instances, each themselves an INSERT).

Downstream effects:
- `semantics.rooms` produced 62–85 entries with `area: null, centroid: null` and labels that are just stray digit-only text fragments, not real rooms — because the wall/boundary geometry needed for real loop detection never made it into the topology pass.
- `topology.loops` (1295–1740 entries, truncated) is dominated by hundreds of near-identical micro-loops clustered at one point — consistent with a single repeated non-block-nested fixture symbol (e.g. a directly-placed "WATER/GAS 0.63 m²" annotation loop), not actual rooms.

## Suggested fix

Recurse into nested INSERTs the same way `ezdxf`'s own `Insert.virtual_entities()` does (resolves nested inserts and applies their cumulative transform automatically) — either call `virtual_entities()` directly instead of hand-rolling the transform math in `_process_block_entity`, or make `_process_block_entity`/the main INSERT branch recursive with a depth guard. Also add `LWPOLYLINE`/`HATCH` to the block-content whitelist so wall/room-boundary geometry nested inside blocks isn't dropped either.

## Repro

Any DXF where architectural geometry lives 2+ INSERT levels deep (e.g. any Revit `EXPORTTOAUTOCAD` output with per-unit blocks containing door/window/fixture family instances) will reproduce this — `layers` in the output will be missing every layer that only appears inside a nested (not top-level) block.
