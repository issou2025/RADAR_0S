# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Modernize the Python application with test-backed service boundaries**

*Project description:*
## Problem Statement

The Collective Modding Toolkit application has accumulated Python code that is difficult to change safely. Core application behavior, Windows integration, filesystem mutation, network operations, and Tkinter presentation are tightly coupled; shared utility and global modules are broad dependency hubs; the scanner and overview interfaces contain large methods with mixed responsibilities; and application startup performs work at import time.

The repository has no executable test suite or CI workflow. Ruff and strict Pyright are configured but are not reproducibly installed, the lockfile is stale, formatting and lint checks are not clean, and several high-confidence correctness and lifecycle defects have been identified. The user needs the production application cleaned up according to modern Python practices without breaking existing settings, discovery rules, archive formats, backup behavior, scanner ordering, Tkinter workflows, or the packaged Windows application.

## Solution

Perform a phased, characterization-first modernization of the production Python application and its development tooling.

First establish reproducible quality tooling, an import-safe startup seam, Windows CI, and tests at the highest practical behavioral seams. Then correct demonstrable data-safety, scanner-concurrency, and lifecycle defects under regression tests. Incrementally establish a proper cm_toolkit package for UI-independent models and services while retaining a compatible Tkinter and PyInstaller bootstrap. Replace wildcard imports, separate platform and domain services from widgets, reduce oversized modules and methods, remove proven dead internal code, and tighten enforceable lint and complexity rules.

The cleanup must preserve observable compatibility unless a failing characterization test demonstrates an existing defect and a corrected-behavior test defines the intended result.

## Implementation Decisions

- Production application code, tests, packaging, and development tooling are in scope.
- Experimental work-in-progress code is excluded from all cleanup, formatting, lint, typing, and test requirements in this specification.
- The application remains Windows-only and supports the currently declared Python 3.14 range.
- Tkinter remains the active user-interface framework for this effort.
- A PySide6 migration is not included, but UI-independent boundaries must be suitable for a later alternative interface.
- The cm_toolkit package will be established incrementally rather than preserving the flat layout indefinitely or moving every module in one mass change.
- A small compatibility bootstrap will preserve the existing development and PyInstaller entry points while modules migrate.
- Application startup will be moved into an explicit callable entry point guarded against import-time execution.
- New UI-independent models, protocols, and services will live in dependency-light package modules.
- Existing Tkinter modules will migrate only when their dependencies and tests are ready.
- The core boundary will separate pure policy from Windows filesystem, registry, process, network, dialog, and Tkinter adapters.
- Runtime imports must remain acyclic. Type-only imports must not be converted into runtime imports when doing so would create a cycle.
- Settings schema, validation, persistence, and download-source discovery will become separate responsibilities.
- Existing settings keys and validation behavior are compatibility contracts.
- Settings persistence will use a failure-safe replacement strategy rather than truncating the live file in place.
- Game and mod-manager discovery will return explicit results or errors; the UI adapter will own prompts and process-exit decisions.
- Filesystem compatibility workarounds will move into a dependency-free platform service rather than remain duplicated or coupled to domain models.
- Binary parsing will validate available bytes before unpacking and expose explicit short-read behavior.
- Archive patching will retain its existing magic and version rules and mutate only the documented header location.
- Downgrading will be modeled as a transaction with explicit validation, download, patch, commit, rollback, and cleanup outcomes.
- Patch downloads will be written to temporary files, validated, and atomically promoted only after successful completion.
- Known-good backups will not be removed when decoding reports failure or raises an exception.
- Every worker or processing lifecycle will use terminal success and failure paths that clear processing state.
- Scanner communication will use typed progress, result, completion, and error events instead of an overloaded queue payload.
- Worker threads will not mutate Tkinter widgets. The main thread will consume events and own UI changes.
- Scanner completion must be ordered after final results, and delayed callbacks must tolerate tab destruction or navigation.
- Scanner traversal, overlay ordering, classification, and deduplication will be extracted from widget construction while retaining current results.
- Overview inspection will be separated from rendering; rendering must not create or duplicate domain findings.
- Modal and anchored-pane lifecycle cleanup must preserve grab restoration, stacking, minimize, restore, and close behavior.
- Wildcard imports from shared catalogs and Tkinter will be replaced with explicit imports before broad modules are split.
- Shared global content will be separated into focused metadata, theme, domain-catalog, and UI-copy modules only after consumers are explicit.
- The utility hub will be decomposed into focused platform, filesystem, binary, update, and UI-helper responsibilities.
- Public-looking but repository-unused helpers will be removed only after checking normal imports, reflective access, and packaging inputs.
- Compatibility-sensitive data catalogs and entry points are not dead code merely because direct call sites are not visible.
- Demonstrable behavior defects will be fixed in isolated changes with corrected-behavior regression tests.
- Mechanical formatting and automatic fixes will not be applied broadly before the relevant characterization tests exist.
- Ruff, Pyright, pytest, coverage, and pre-commit will become locked development dependencies alongside the existing Mypy tooling.
- The stale lockfile and redundant or conflicting tool configuration will be corrected.
- Ruff will be clean for production code, the new package, and tests.
- The formatter conflict will be removed.
- Wildcard-import diagnostics will be re-enabled after violations are eliminated.
- Complexity checking will be enabled after the known oversized functions are decomposed.
- Full pydocstyle enforcement remains disabled. Repository policy requires concise docstrings for added or substantially rewritten methods and allows trivial private helpers to remain undocumented.
- Existing accurate comments will be preserved. New comments will explain non-obvious reasons, rollback, cancellation, threading, lifetime, and workarounds.
- Canonical local commands and pre-commit checks will run formatting, lint, Mypy, Pyright, and tests as appropriate.
- Windows GitHub Actions CI will run the canonical checks.
- The cleanup will proceed in phases: tooling and import-safe foundation; compatibility characterization; data-safety and lifecycle fixes; scanner concurrency; package and service extraction; import and shared-module cleanup; GUI simplification; final rule tightening and packaging verification.
- Each phase must leave applicable automated checks green.
- ADR-0001 governs the incremental cm_toolkit package boundary.

## Testing Decisions

- Tests will assert externally observable results, persisted data, emitted events, file mutations, and lifecycle outcomes rather than private helper call sequences.
- Existing behavioral seams will be preferred. New seams will be introduced only where import-time startup, Tkinter ownership, or platform calls prevent direct characterization.
- The highest common seam for core behavior is a UI-independent service invoked through a narrow request/result contract.
- The startup seam is the explicit application entry function; importing application modules must not create windows, perform network checks, or enter a main loop.
- Settings tests will cover missing files, defaults, malformed JSON, non-object JSON, unknown keys, missing keys, value validation, existing key compatibility, successful saves, and failed saves.
- Filesystem and binary tests will cover file and directory predicates, permission failures, encoding detection, checksums, bounded reads, header skips, short reads, endianness, version parsing, and registry return contracts.
- Discovery tests will cover process ancestry, portable and application-data configuration, current directory, registry, manual selection, precedence, cancellation, and invalid paths.
- Archive tests will operate on temporary binary fixtures and assert exact byte-level mutations, classifications, counts, logs, and unchanged content outside the header field.
- Downgrade tests will use temporary directories and fake HTTP and decoder adapters to verify CRC gates, backup names, restore and retention rules, download validation, event ordering, successful commit, false decoder results, exceptions, and rollback.
- Scanner tests will exercise traversal, root-level detection, stage-path ordering, overlay precedence, skip rules, classification, deduplication, and the typed event protocol without a live Tkinter main loop.
- Scanner lifecycle tests will use a controllable scheduler or thin Tk adapter to verify polling, final result ordering, errors, close behavior, and tab-switch behavior.
- UI orchestration tests will remain thin and cover observable tab loading, close protections, modal-grab restoration, pane lifecycle, logging restoration, and update-source branching.
- Main-loop-driven screenshot testing and pixel-level widget assertions are not required.
- Network tests will use fake responses and cover success, non-success status, malformed payloads, timeouts, and connection errors without contacting live services.
- Windows-specific adapter tests will run on Windows CI; pure service tests should remain deterministic and independent of the host registry, process tree, and user files.
- Newly extracted pure core modules require strong branch coverage. No arbitrary repository-wide percentage will be imposed on untouched legacy Tkinter widgets.
- Regression tests must fail against the confirmed scanner identity bug, scanner completion and failure races, downloader terminal-state failures, backup deletion on decoder failure, per-file downgrade-state bug, and processing-state leaks before their fixes are applied.
- The final verification suite will include formatting, Ruff, Mypy, Pyright, pytest with coverage, pre-commit, lockfile validation, and a PyInstaller build check.
- The repository has no existing test prior art. Characterization expectations come from current runtime contracts, application documentation, accepted compatibility decisions, and the audited behavior of production modules.

## Out of Scope

- Experimental work-in-progress modules and prototypes.
- Migrating the active UI from Tkinter to PySide6 or another framework.
- Redesigning the visible application workflow or adding user-facing features.
- Renaming or removing compatibility-sensitive settings keys.
- Changing mod-manager or game-discovery precedence except to correct a demonstrated defect.
- Changing scanner rule catalogs, result ordering, or troubleshooting semantics except to correct a demonstrated defect.
- Changing archive formats, downgrade CRC catalogs, backup naming, or patch semantics except to correct a demonstrated defect.
- Making the application cross-platform.
- Treating internal application modules as a stable third-party library API.
- Requiring comprehensive pixel-level GUI automation.
- Imposing a repository-wide coverage percentage on untouched legacy widgets.
- Enabling the complete pydocstyle rule set.
- Reformatting or linting excluded experimental code.
- Performing the deferred PySide6 migration.
- Creating commits or publishing a pull request as part of this specification.

## Further Notes

The established baseline contains no tests or CI. Mypy passes for production source with the project environment. Ruff currently reports configuration and production findings, Ruff formatting reports multiple production files that would change, Pyright reports unresolved or unknown typing around the patch decoder, and the project lockfile is stale relative to project metadata.

The highest-risk areas are downgrade transactions, archive mutation, scanner worker and UI coordination, settings persistence, game discovery, the broad utility and global dependency hubs, and the oversized scanner and overview interfaces. Data-loss and indefinitely stuck processing states take priority over aesthetic restructuring.

The repository's comment policy is authoritative: accurate comments are never removed as cleanup, substantially rewritten methods receive concise docstrings, and hidden constraints receive WHY comments.

The implementation should preserve unrelated working-tree changes and should not create commits unless separately requested.
