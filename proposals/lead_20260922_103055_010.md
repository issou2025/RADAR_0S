# Project Proposal — Flutter App

## Project Understanding
You need assistance with: 
**ci(release): upload the App Bundle to the Play alpha track from the release workflow**

*Project description:*
## The bundle is built by CI and uploaded by hand

`release.yml` already does everything up to the Play Console door. The release
job builds the App Bundle (`flutter build appbundle --release`), verifies it is
not debug-signed with `keytool -printcert -jarfile`, renames it
`fieldtally-<version>.aab`, and uploads it as the `fieldtally-release-aab`
artifact — on every run, dry or not, and deliberately not attached to the
GitHub Release, because that page is read by people sideloading.

From there it is manual. `docs/release.md`, under *The App Bundle, for the Play
Store*:

> Download it from the run's **Artifacts** section and upload it in the Play
> Console yourself; nothing here talks to Play.

So every release needs someone to fetch a file from a run page, open the
console, create a release, paste notes and roll it out. It works, and it is the
step most likely to be skipped or done a day late — which leaves the GitHub
channel ahead of Play for no reason other than a chore.

## Proposal: one more step in the same job, to the alpha track

The bundle is already in the workspace when the current upload step runs, and
it is already signed with the right key — Play App Signing holds that same
keystore, so the upload key and the app signing key are the same certificate
and nothing about signing changes.

Add a step, after the release is published, that sends `fieldtally-*.aab` to
the Play Developer API. `r0adkll/upload-google-play` is the usual way and takes
exactly what is needed: `serviceAccountJsonPlainText`, `packageName`
(`io.nohzoh.fieldtally`), `releaseFiles`, `track` and `status`. `fastlane
supply` or a direct call to the Android Publisher API would do the same job
with more plumbing.

Gating matters as much as the step itself:

- **Never on a dry run.** A dry run exists to check signing and to produce a
  bundle; it creates no tag and publishes nothing, and that must stay true.
- **Never from a pull request.** `release.yml` is already, deliberately, not
  triggered by `pull_request` or `pull_request_target`, because it holds the
  signing key. A Play credential belongs on exactly the same side of that line.
- Possibly behind its own `workflow_dispatch` input, so a release can still be
  cut without touching Play.

## What is needed outside the repository

A Google Cloud service account with the Android Publisher API enabled, invited
into the Play Console with permission to release to testing tracks, and its
JSON key stored as a repository secret — alongside `ANDROID_KEYSTORE_BASE64`
and the rest, read the same way, and **never committed**. The existing "Check
the signing secrets are present" step is the pattern to copy: fail early and by
name, rather than half-way through.

Nothing about the credential goes in the repository, this issue, or a pull
request.

## Open points

- **Which track.** The ask is alpha (closed testing). `internal` is faster and
  skips review, which may be the better first target while the automation is
  being trusted; that is a call to make, not to assume.
- **`draft` or `completed`.** A draft release still needs a click in the
  console. For a first version that may be exactly the right amount of
  automation — the file arrives, a human decides to roll it out.
- **Release notes.** Play takes per-locale `whatsnew` files.
  `app/assets/changelog.json` is keyed by `versionCode` and already carries
  `en` and `fr` text, so generating `whatsnew/en-US` and `whatsnew/fr-FR` from
  it is straightforward — but it is a second decision, and skipping it just
  means the console shows no notes.
- **`versionCode` monotonicity.** Play refuses a code it has already accepted,
  permanently. The workflow only checks the tag against `app/pubspec.yaml`
  today; nothing compares against what Play has already seen, and a failed
  upload half-way through a release is a worse failure than a refusal up front.
- **Ordering, and what happens when the upload fails.** The tag and the GitHub
  Release are created before this step would run, so a Play failure leaves a
  published release that never reached the store. Either the step tolerates
  that and says so loudly, or the order changes. Re-running is cheap for the
  GitHub side and impossible for a `versionCode` Play has consumed, which
  argues for uploading last and treating a failure as "finish it by hand".
- **The two channels stay in lockstep.** The APK and the AAB come from the same
  run and the same commit, which is what keeps `latest.json` honest for
  sideloaded installs. Nothing here should make it possible to ship one without
  the other.
