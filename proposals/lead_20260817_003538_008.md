# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**New Companion tab (waving, following, voice commands, play, English) + a much richer eye-expression set**

*Project description:*
## Summary

Add a fourth **Companion** tab — a free-play mode where a child and the dog simply spend time
together: the dog waves, listens, plays, follows, and chats in English. It gets eyes like the
other screens.

Separately but in the same area: **the eyes are far too static everywhere they appear.** The
expression vocabulary needs to grow — blink, wink (one eye), a flirty/playful look, a cute
look, a serious look, a plain neutral look, and more.

## Part A — the Companion tab

### Why

The three existing tabs each have a job: `Control` is a joystick, `Word Play` is a lesson,
`Stories` is a narration session. None of them is just *being with the dog*. For a young child
the most natural first thing is not a lesson or a joystick — it is "say hi to the dog, it
waves back". That is the mode that is missing.

### Requirements

1. **New tab** in `RootView`, alongside Control / Word Play / Stories. Same single-BLE-link
   discipline: it shares the one `NaviBLE` and one `SpeechEngine`, and switching into or out of
   it stops motion and releases the mic, exactly like the existing tabs do.
2. **Eyes on screen** — `EyesView`, driven by what is happening in the session (see Part C).
   Landscape should go full-screen eyes, matching how `StoryView` / `LearningView` already
   behave.
3. **Natural interaction, at minimum:**
   - **Waving** — the child waves, the dog waves back. A `wave` skill exists on the firmware
     but is not yet in the app's allow-list (`NaviProtocol.skills`) and has not been confirmed
     on hardware. The companion issue requires **all 16 firmware skills** to be wired up and
     bench tested; the expressive ones (`wave`, `shake_hands`, `finger_heart`, `be_cute`,
     `bow`, `impatient`, `shake`) are exactly this tab's vocabulary.
   - **Listening to voice commands** — reuse `VoiceController`, which already routes both by
     keyword and by AI fallback and already covers stand / sit / lie / wag_tail / dance /
     drive / turn / posture / stop.
   - **Playing together** — short back-and-forth games that need no reading: copy-me, red
     light green light, hide the sound, "do what I say" etc. Each round is: the dog proposes,
     the child acts or speaks, the dog reacts with a movement plus an expression.
   - **Following the child** — see the warning below; treat as a separate, gated deliverable.
4. **English conversation and learning.** Not a drill — talking. The child talks to the dog and
   the dog replies in simple spoken English, weaving in words and phrases. `StoryCompanion`
   already has exactly this shape (LLM in, one short spoken line out, always with a written
   fallback) and `Tutor` / `WordDeck` already hold the teaching content; the companion mode
   should build on those rather than start a fourth parallel implementation.
5. **Every reply moves the robot.** A spoken reply with no movement reads as a speaker, not a
   creature. Reuse the ambient-motion work from the Stories issue rather than duplicating it.
6. **Expressions and movements must keep changing — sameness is the bug.** A companion that
   repeats the same two faces and the same three wiggles is boring within a minute, and a bored
   child stops playing. Concretely, for this tab:
   - the **motion** pool and the **expression** pool are both large, and both are drawn from at
     random with no repeat inside a rolling window (same rule as the Stories issue);
   - **face and body move together** — a wave comes with a bright face, a question with a head
     tilt and curious eyes, a wrong guess with a soft unsure look rather than nothing;
   - reactions to the *same* event vary between occurrences: greeting the child twice should
     not produce an identical performance both times;
   - even with nobody talking, the dog is never inert — it idles with small movements and live
     eyes, so it always looks like it is waiting rather than switched off.

### Follow mode — the robot has no tracking of its own, so the phone does the seeing

Worth being explicit, because it changes who implements what: **the firmware has no follow or
target-tracking mode**. The BLE surface is joystick frames, a few `cmd|` verbs, and
`send_skill` by name — nothing perceptual. So following cannot be "turn on the robot's follow
mode"; the phone riding on the dog's back has to see the person and steer.

**This has already been solved on this exact robot**, in Stephen Sun's `Dogwalk` app
(same dog, same BLE protocol, same phone-on-the-back arrangement — Flutter rather than
SwiftUI). Rather than reinventing it, port the method. The design below is his; the notes are
what matters when reimplementing it here.

**Sensing.** ARKit + Vision on an iPhone with a **LiDAR scanner**, via hand-written
ARKit/Vision code (not a third-party package) — it gives distance in **metres**, a person
detector needing no bundled model, and a real camera pose. On phones without a scanner there
is only an appearance-based floor scan, which is enough for obstacle avoidance but **not
enough to follow** — follow mode requires the depth path. Note ARKit takes the one capture
session iOS allows, so it is chosen when the screen opens, not swapped mid-session.
Porting to this app should be *easier*, not harder: NaviApp is already native Swift, so the
platform-channel layer Dogwalk needed disappears.

**Control law.** A pure function — a camera "look" plus a clock in, a steering command out —
so it is unit-testable with no robot present (his repo tests it against corridors that do not
exist). Key parameters and rules:

| rule | value / behaviour |
| --- | --- |
| Standoff distance | `1.8 m` behind the person |
| Deadband | `0.25 m` — without it the dog surges and stops several times a second |
| Lost the person | **Stop, or turn on the spot. Never travel on a stale bearing.** A follower that keeps walking toward where somebody used to be is a robot heading into an empty room |
| No depth reading | Turn to face them, do **not** walk at them. Following someone you cannot range is walking blind in their direction |
| Obstacle veto | The person is exempt (a person 2 m away looks like a blocked band to a floor scan). **Nothing else is exempt** — the furniture between dog and child still vetoes |
| Drop-off / stairs | **Outranks the person.** A child walking down stairs is a goal bearing pointing over an edge: stop and say so |
| Reacquiring | The person found must be roughly where the last one was, in angle *and* distance. It would rather lose you than follow a stranger — a hallway is full of plausible substitutes |

**Safety mechanisms that must come across with it** (these are what make autonomy acceptable
around a child, and they hold even if every line of app code stops running):

- Every autonomous decision goes out as a **fixed ~0.45 s burst**, never an open-ended
  velocity. If the loop dies — camera wedges, app killed — nothing renews it and the dog stops
  within half a second on the drive timer's own trailing frames.
- **Six neutral trailing frames** end every drive, hold, pose and stop, because a single stop
  frame is a single packet to lose.
- A **~150 ms watchdog** ends autonomy if the camera stops delivering pictures.

**Filming implication:** follow mode needs a LiDAR-equipped iPhone on the dog's back. Confirm
the shoot has one before the storyboard depends on a following shot.

**Still not allowed:** shipping a button that looks autonomous but is really an operator on a
joystick. If the port is not ready, the honest version is a manual drive, labelled as such.

## Part B — filming requirements (a 60-second shoot with a real child)

This work has a deadline shaped by a shoot, not just a release. The film is a single 60-second
piece cut from four interviews (the child, a product teacher, a teacher from an education
partner, an outside developer) over footage of the child and the dog. The child's segments are
the spine of it, so the app has to hold up on camera, take after take, with a child driving it.

### The 60-second structure, and what the app must deliver in each beat

| Time | Beat | What is on screen | What the app must do |
| --- | --- | --- | --- |
| 0–5s | **The First Command** ★child | Child faces the dog: *"Navi, stand up."* The dog stands. The child smiles. Ambient sound and servo noise only — music enters after the stand | The single most robust path in the app. Voice → `stand_up` with no pairing dialog, no permission prompt, no cold-start lag. It must work **first try, every take** |
| 5–12s | **Interaction** | Voice commands, the dog responding, following, expressions | The companion loop of Part A: spoken command → movement + facial reaction. Following is the gated item — see the follow-mode section |
| 12–20s | **From Command to Programming** ★child | Child opens the block editor, picks actions, arranges the order. Child, screen and robot all visible in one frame | Block programming — see the section below. The screen has to be legible on camera while the robot is also in shot |
| 20–29s | **Code Becomes Action** ★child | *"I chose the actions and put them in the order I wanted. Then I pressed run. It did exactly what I made."* The dog performs the actions in sequence; the child watches | **Sequence execution**: run the blocks in the child's exact order, to completion, with at least one unbroken multi-action take that reads on screen as "my program became real movement" |
| 29–37s | **Test and Improve** | First run is not quite what was expected → child changes one block → runs again → second run succeeds | The edit-run loop must be fast and deterministic. This is a *designed* change, not a real malfunction, so the same program must produce the same result both times |
| 37–46s | **Make It Unique** ★child | Child designs, 3D-prints, paints and fits a custom dog head | No app involvement, but the dog must still be operable with the custom head fitted |
| 46–54s | **Open for Growth** | An outside developer does something more advanced while the child watches | Whatever is shown must be real, not a mock-up |
| 54–60s | **A Bigger Journey** | The dog follows the child forward; the child looks back at it; logo | The follow shot. **Depends on the follow-mode item above** — if the perception port is not ready, this beat has to be shot as manual driving, and that has to be known before the shoot day, not on it |

★ = the child performs in this beat.

### Block programming (the 12–29s section)

The programming segment is a third of the film and it has its own hard requirement: **what the
blocks say must be exactly what the robot does.** Program order, action names and the robot's
behaviour have to match, because the camera shows the screen and the robot in the same frame —
any mismatch is visible and makes the whole sequence a lie.

What that needs from this app:

1. **A sequence runner.** Accept an ordered list of actions and execute it in order, to
   completion, without dropping or reordering. This is also what the "play together" games in
   Part A need, so it should be one mechanism, not two.
2. **Action names shown to the child are the actions performed.** The block labelled `wave`
   produces the wave. This is another reason all 16 firmware skills need to be wired up and
   verified (issue #1) — a block set is only as honest as the skills behind it.
3. **Deterministic replay.** Running the same program twice produces the same performance.
   The "no repeat within a rolling window" randomness of Part A applies to *ambient* behaviour
   and must not leak into explicitly programmed sequences.
4. **A fast edit-run loop.** Change one block, run again, see the difference in seconds. The
   29–37s beat is built on this.
5. **Safety lives outside the program.** E-stop, the burst/deadman drive timer and the
   trailing-zero stop must sit in native code *below* the block runtime, so no program —
   whoever wrote it, however it arrived on the device — can disable them. A block program is
   untrusted input to a machine with legs.
6. **Platform note for whoever builds the editor:** App Store rule 2.5.2 forbids downloading
   executable code; the exception is script interpreted by Apple's own WebKit / JavaScriptCore
   without changing the app's stated purpose. So the workable shape is a block editor in an
   in-app WebView that emits a *data* representation of the program, executed by native code —
   not generating and shipping compiled code per child.

Scope note: the block editor may well be its own issue and its own screen. It is written up
here because the shoot depends on it and on this app's sequence execution — split it out if
that is cleaner.

### Production constraints on the app

- **Fixed English command list, agreed in advance.** The child rehearses those exact phrases;
  recognition must be reliable at a child's pitch, volume and distance from the dog. Anything
  outside the list fails gracefully with a friendly "say that again?" — never silence.
- **Every robot action is rehearsable.** Each action used on camera gets dry-run before the
  take, and behaves identically each time. Shots are captured separately (full action / robot
  alone / child's reaction / hands and details) — the app must not require child and robot to
  be perfect in the same continuous take.
- **Recoverable in one tap.** If something fails it fails visibly and recovers immediately. No
  state that needs a force-quit between takes.
- **Filmable screen.** Eyes and state read clearly on camera: adequate contrast, no flicker, no
  debug overlays in the build used for the shoot.
- **Quiet where it matters.** Key sound moments are the child's command, the tap on run, and
  the dog's first movement. The app should not talk over those — no unnecessary UI sounds or
  chatty TTS during the opening command and the run.
- **Battery and thermals.** A shooting day is hours of takes. The app should not be the reason
  a session stops — no runaway camera or mic sessions when a screen is idle.

## Part C — the eyes need a much bigger expression vocabulary

### Current state

`navi-ios/NaviRemote/EyesView.swift`:

- `FaceMood` has **only five** values: `idle`, `listening`, `speaking`, `happy`, `unsure`.
- Blinking exists but is purely automatic and internal (`scheduleBlink`, random interval, with
  an occasional double blink). **Nothing can trigger a blink deliberately.**
- `celebrate()` is the only "expressive" moment, and it is hard-wired to `happy`.
- `EyeStyle` (human / fox / wolf / bear / …) controls *whose* eyes are worn — a different axis
  from expression, and not a substitute for it.

The result: across all three screens the eyes have essentially one look with a slow blink. Over
a multi-minute session with a child that reads as a screensaver.

### Requirements

1. **Add expressions, at least:**
   - `blink` — a deliberate, triggerable blink (both eyes)
   - `wink` — one eye only, left or right
   - a **flirty / playful** look — the "cheeky" one, e.g. a wink plus a curved smiling eye
   - `cute` — big soft round eyes, the melting look
   - `serious` — narrowed, focused, brows lowered
   - `neutral` / plain — the ordinary resting face, distinct from `idle`
   - keep the existing `listening` / `speaking` / `happy` / `unsure`
   - more beyond this list is welcome: sleepy, curious/head-tilt, surprised, sad, proud …
2. **Expressions are triggerable**, not just ambient states — the app can say "wink now" at a
   moment that matters and the eyes do it, then return to the resting state.
3. **Micro-life while resting.** Even with no event, the eyes should drift, re-focus, and blink
   irregularly, and should not repeat the same idle beat over and over — same "no repeat within
   a short window" idea as the motion work.
4. **Applies everywhere eyes appear** — the new Companion tab, plus `StoryView` and
   `LearningView`. Existing call sites keep working: any new expression must be additive, with
   the current five continuing to behave as they do now.
5. **Works with every `EyeStyle`.** An expression must read correctly on a vertical-slit pupil
   (fox, wolf) and a horizontal bar (tortoise, goat), not only on round human eyes.
6. **Eyes and body agree.** A wink should coincide with the matching body movement rather than
   drifting a second behind it; a serious face should not appear over a playful wiggle.

## Open questions

1. Should the Companion tab be a separate mode from `Stories`, or should storytelling
   eventually fold into it? (Proposal: keep them separate for now — different session shapes.)
2. Which of the untested firmware skills read well here — `wave`, `shake`, `shake_hands`,
   `finger_heart`, `be_cute`, `impatient`, `bow`? Every one needs a hardware check before it is
   used on camera.
3. Follow mode: is a LiDAR-equipped iPhone available for the shoot, and is porting the
   perception layer in scope for this milestone or a follow-up?
4. Does the English conversation run through the existing LLM path, and what is the offline /
   no-network fallback during a shoot?

## Acceptance criteria

- [ ] A fourth Companion tab exists and shares the single BLE link and speech engine; switching
      tabs stops motion and releases the mic.
- [ ] Eyes are present in the tab and go full-screen in landscape.
- [ ] The child can greet the dog and get a wave back (assuming the skill passes its bench test).
- [ ] The rehearsed English command list works reliably with a child speaker at filming distance.
- [ ] At least one playable back-and-forth game runs end to end with no reading required.
- [ ] English conversation replies are short, spoken, and always fall back to a written line
      when the network or the model is unavailable.
- [ ] `FaceMood` (or its replacement) covers at least: blink, wink, flirty, cute, serious,
      neutral, plus the existing five.
- [ ] Expressions can be triggered on demand and are used in all three existing eye screens.
- [ ] Idle eyes visibly vary over a two-minute observation and never look frozen.
- [ ] Watching a five-minute companion session, an observer cannot predict the next expression
      or movement, and no face/movement pair repeats back to back. "It got boring" is a valid
      bug report against this issue.
- [ ] Any "follow" affordance either runs the ported perception + control loop with all three
      safety mechanisms (burst drive, trailing zeros, camera watchdog), or is labelled as
      manual driving. Nothing in between ships.
