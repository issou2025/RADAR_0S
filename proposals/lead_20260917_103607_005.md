# Project Proposal — Structural Drawings

## Project Understanding
You need assistance with: 
**Disclose the Gemini voice data flow in the privacy policy and App Privacy answers**

*Project description:*
## Summary

drover 1.0.x shipped an App Privacy questionnaire that answers **"User content — audio: No"**, with the note *"Speech recognition is on-device only"* (`docs/app-store-submission.md`, section "App Privacy questionnaire"). That was true when the only voice feature was dictation through Apple's Speech framework.

The voice assistant on `voice-live` breaks it. It streams microphone audio to Google's Gemini Live API through Firebase AI Logic, and the tool results it sends carry agent context. The moment voice ships in 1.1.0, the declaration and the published privacy policy are both false. This is a **misdeclaration, not a rejection risk** — so it has to land with the release, not after it.

What actually leaves the device during a voice session (verified in `app/lib/src/voice/`):

- 16 kHz PCM microphone audio, streamed live (`voice_transport.dart`).
- Server-side transcription of **both** sides — `inputAudioTranscription` and `outputAudioTranscription` are enabled in `LiveGenerationConfig`.
- The system prompt and the tool declarations (`voice_tools.dart`).
- Tool results (`voice_herd.dart`): agent names/titles/statuses, the text and options of the question a blocked agent is waiting on, the agent's **last reply text** (`lastReply` → `speakable(last.text)`), and the messages the user dictates into a draft.

No Gemini API key lives on the device — the app talks to Firebase AI Logic and App Check gates the endpoint (`docs/voice-live.md`, "Purpose" / "Firebase prerequisites").

Note the sharp edge: the existing policy's "never reach the developer" framing survives literally (Google is a third-party processor, not the developer), but the reader-facing claim does not. The policy lists "Agent transcripts, chat history, and terminal output" and "Commands, prompts, and follow-up messages you send to an agent" under *What Drover does not collect* — a user reading that would not expect their agent's last reply to be sent to Google. Resolve that head-on rather than by lawyering; `docs/app-store-submission.md` already has a "two judgment calls" section for exactly this kind of reasoning.

## Scope

In:

- Update **both** privacy policy pages — `site/privacy/index.md` and `site/ja/privacy/index.md` — to disclose that when the voice assistant is used, microphone audio and the agent context the assistant needs are sent to Google's Gemini service through Firebase AI Logic. Match each page's existing tone and structure; prefer fixing the sections that already exist over bolting on a new one, and keep the two pages saying the same thing (ja is a translation of en and says so in its header).
- Update `docs/app-store-submission.md`:
  - the **audio row** of the App Privacy questionnaire table (line ~219) — it can no longer answer "No" for User content / audio;
  - the *"Speech recognition is on-device only"* note in that row, which contradicts the corrected answer;
  - the store **description** copy in the same file, both locales (see Implementation notes — this is easy to miss);
  - a note that the App Store Connect answers must be **re-submitted for the 1.1.0 release**.

Out (do NOT):

- Do NOT re-answer the questionnaire in App Store Connect. That is a human Console task; this issue only prepares the repo side so the Console answers can be copied from it.
- Do NOT touch any app code. In particular, the 5.1.2(i) consent sheet and the microphone usage string are already in flight in a separate PR.
- Do NOT add `PrivacyInfo.xcprivacy`. drover has none, and whether it needs one is a pre-existing question unrelated to voice.
- Do NOT invent retention periods, deletion guarantees, or storage claims on Google's behalf. Point at Google's privacy documentation, the way the existing **Third parties** entry for Google already does.
- Do NOT restructure or retranslate either privacy page beyond what this disclosure needs.

## Implementation notes

**Base branch is `voice-live`, not `main`.** Open the PR against `voice-live`.

`.github/workflows/site.yml` publishes the site only on pushes to `main` under `site/**`. So this copy landing on `voice-live` does **not** go live until the 1.1.0 merge — which is exactly the desired timing. Do not delay the work out of caution that it would publish early; it cannot.

### The sections that are wrong today

Adding one new section and leaving the rest standing is the failure mode here. Each of these currently contradicts the voice assistant and needs reconciling:

| `site/privacy/index.md` | `site/ja/privacy/index.md` | why it is wrong now |
|---|---|---|
| `## The short version` | `## 要点` | "The only developer-operated service is the **optional push-notification backend**" |
| `## What Drover does not collect` | `## Drover が収集しないもの` | the bullets "Dictated audio", "Agent transcripts, chat history, and terminal output", "Commands, prompts, and follow-up messages you send to an agent" |
| `## Dictation` | `## 音声入力` | "Drover **refuses to start dictation** rather than sending your audio to a server" — still true *of dictation*, but the page now has to distinguish dictation (Apple Speech, on-device) from the voice assistant (Gemini Live) |
| `## Third parties` | `## サードパーティ` | the Google entry is scoped to "the notification-backend data listed above" |

### `docs/app-store-submission.md`

Three places, not one:

- **Line ~219**, the questionnaire table's audio row.
- **The `## Description` → en block, `PRIVACY` paragraph** (line ~119): *"Speech recognition runs entirely on your device — Drover will not fall back to a server."*
- **The `## Description` → ja block, `プライバシー` paragraph** (line ~163): *「音声認識は完全に端末内で処理され、サーバーにフォールバックすることはありません。」*

Both description sentences stay true *of dictation* and become false as a blanket claim once voice ships. This is live App Store listing copy under a `PRIVACY` heading, so it is the most consequential surviving contradiction in the repo. Description text is metadata-only (no new build needed), but it has to be correct before 1.1.0 goes to review.

### Checked and deliberately not in scope

`site/support/index.md` (~line 65) and `site/ja/support/index.md` (~line 40) carry the same on-device claim, but both sit under a **"Dictation will not start" / 「音声入力が始まらない」** troubleshooting heading, so they are already scoped to dictation and remain true. Leave them alone unless the wording reads as a blanket claim to you — if you change them, say so in the PR.

## Acceptance criteria

The change is prose. **There is no test suite for documentation** — `fvm flutter test` covers `app/`, and nothing in the repo asserts on the content of markdown. So the criteria below are observable checks, not a command that proves correctness.

- [ ] Both `site/privacy/index.md` and `site/ja/privacy/index.md` name **Google** (and Gemini / Firebase AI Logic) as a recipient, state **what** is sent (microphone audio, transcripts of both sides, and the agent context: agent names and statuses, the text of a question an agent is blocked on, the agent's last reply, the messages you dictate) and **when** (only while a voice assistant session is running).
- [ ] The two pages say the same thing: every claim added to the en page has a ja counterpart and vice versa, with no statement present in only one.
- [ ] None of the four sections in the table above still contradicts the voice assistant on either page.
- [ ] The audio row of the App Privacy questionnaire table in `docs/app-store-submission.md` no longer claims audio is not collected.
- [ ] No surviving sentence in `docs/app-store-submission.md` contradicts the corrected row. Concretely: `grep -rniE "on.device|entirely on your device|端末内|fall back to a server" docs/app-store-submission.md` returns nothing, or only lines that are explicitly scoped to dictation.
- [ ] `docs/app-store-submission.md` states that the App Privacy answers must be re-submitted in App Store Connect for the 1.1.0 release, and that doing so is a manual Console step.
- [ ] `cd site && npm ci && npm run build` succeeds — this is the only runnable gate, and it checks VitePress frontmatter/markdown validity, not the content. CI runs the same thing: `.github/workflows/site.yml` triggers on `pull_request` for `site/**` with no branch filter, so the PR against `voice-live` will run it. Publishing steps are gated behind `github.event_name != 'pull_request'`.
- [ ] No files under `app/` are touched, and no `PrivacyInfo.xcprivacy` is added.
