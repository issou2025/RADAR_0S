## Finding — `actions-summary` publishes attention and bundle ID without verifying their binding

**Pinned candidate:** `release/0.6.0@6d935ee111e2efab7a5f7d7c8f8d050af8d35567` (unreleased). `src/devostasis/cli.py` blob `6b6cea03a4ddf3317229e47c5c14497fec31f96d`, particularly `_load_members` (~lines 288–301), `actions_summary_text` (~lines 383–423), and `cmd_actions_summary` (~lines 426–441). `src/devostasis/bundle.py` blob `e005237e2f35b812ba02442318bfcdda5f5baffa`.

`cmd_actions_summary(args)` calls `_load_members(args.bundle)`, then `actions_summary_text(parsed)`, and appends the resulting `attention`, `attention-order`, `levels`, `bands`, `gauges` and `bundle-id` to `GITHUB_OUTPUT` (or stdout). `_load_members` loads and JSON-decodes bundle members but never invokes `verify_members` / `verify_dir`. The command therefore exits successfully even if the mutable bundle directory contains **valid JSON with changed, unauthenticated member bytes**. The output includes the untouched manifest's `bundle-id`, which may appear to authenticate a different `demand.json` than that ID actually binds.

The [reusable self-observation workflow](https://github.com/drevendev/Devostasis/blob/6d935ee111e2efab7a5f7d7c8f8d050af8d35567/.github/workflows/observe-self.yml) (blob `7b31ce3583b1f1c4b86c36ee80fb2b04a1b54175`) invokes `devostasis actions-summary --bundle .../latest` immediately after `devostasis run`, then exposes the generated `attention` and `attention-order` as reusable workflow outputs. The normal workflow generates its own bundle, so **no incident or malicious mutation in that workflow is claimed**; this is an input-integrity gap when the CLI is independently given an altered/stale local directory, including consumer integrations that trust its exit status.

### Deterministic evidence from actual checked-in fixture

At this exact release head, `examples/sample-bundle/demand.json` blob `fe4701d7b499f6802adb81d17117f58f5cfdf876` has first `attention_order` item `{"vital_id":"integrity","level":"HIGH"}`. Its manifest blob `1ec79cc7cc940eb24e3ef29f7edb86517374f362` declares `members["demand.json"] = "sha256:38f9170d967c28516dcaf4ca34d77815c0b5589701c076fa1ee176a4f64f0d94"` and `bundle_id=868e4cb6c321a66e14bf6b1dc917cc51ba66ee9535edfb4d5e36ea9045631cd3`.

Modify **only** the local copy of `demand.json` to contain valid JSON with a changed first attention item, for example `{"vital_id":"pulse","level":"MINIMAL"}`, leaving `manifest.json` unchanged. `actions_summary_text` derives `attention = "pulse MINIMAL"` directly from that changed field but `bundle-id` from the untouched manifest; no hash/identity gate intervenes. An actual `devostasis verify --bundle` would reject changed bytes against the manifest's digest.

An isolated, tool-executed JSON/source-predicate check on the exact fetched source and fixture performed **6/6 assertions PASS**: original HIGH integrity, changed MINIMAL pulse, unchanged manifest ID, manifest's recorded demand digest, and absence of verification calls in both `_load_members` and `cmd_actions_summary`. **This is a deterministic source-path demonstration, NOT an execution of the full Python CLI**, tampered-fixture integration test, or a hosted CI result.

### Focused remediation / acceptance

1. Make `actions-summary --bundle` fail closed before writing **any** `GITHUB_STEP_SUMMARY` or `GITHUB_OUTPUT` data unless all relevant bundle members, identity and report/derived commitments pass the existing verifier. Prefer **load members once -> `verify_members(members)` -> parse and render those exact verified bytes**, not `verify_dir` then a second filesystem read (see existing #145's snapshot race). An invalid input should return the repository's established nonzero input/verification exit code with a useful diagnostic, never a positive action output.
2. Add a real CLI regression with a copied `examples/sample-bundle`: valid bundle emits the original `integrity HIGH` and matching ID; a syntactically valid, altered `demand.json` or `snapshot.json` under an unchanged manifest emits **no** workflow outputs and fails nonzero. Test `GITHUB_OUTPUT` and stdout mode, including the no-partial-write property; malformed/missing members fail without a false success.
3. Preserve the published/historical bundle verification semantics and the current pure `actions_summary_text` formatting. Do not invent health ranking, treat UNKNOWN as zero, alter Vital policy/thresholds/contract IDs, or rewrite historic bundles. Confirm read-only adapter and model-free invariants.
4. Check the related `demand --bundle` and `gauges --bundle` reader paths separately before claiming a fully verified consumer CLI surface; their raw-display behavior currently also calls `_load_members`. Keep this Issue's direct acceptance focused on **machine-consumed Actions outputs**.
