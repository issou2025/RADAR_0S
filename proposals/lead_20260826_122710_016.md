# Project Proposal — Unknown

## Project Understanding
You need assistance with: 
**[Bug]: exec blocked by voice confirmation gate in Browser Talk (WebRTC) — read-only commands should not require spoken confirmation**

*Project description:*
## Summary

`exec` tool calls in full realtime Talk mode (Browser Talk via WebRTC, `talk.client.toolCall` path) are blocked by the voice confirmation gate even when exec-policy is `security=full, ask=off`. Read-only shell commands that complete in ~1.4 seconds should not require spoken confirmation. This use case (querying a Google Sheets CRM by name/store while in a live voice conversation) worked previously and is now broken.

## Environment

- Gateway: OpenClaw 2026.7.2-beta.7 (dabe191)
- Client: Chrome browser on iPhone (Browser Talk = client-owned WebRTC)
- exec-policy: `security=full, ask=off` (confirmed via `openclaw exec-policy show`)

## Steps to reproduce

1. Open Control UI in Chrome browser, start a Talk mode session (realtime WebRTC)
2. Say: "Look up Arnold in the connect log"
3. Agent calls exec tool: `python3 interaction_lookup.py --name "Arnold"` (read-only, ~1.4s, hits Google Sheets API)
4. Voice confirmation gate fires — exec is blocked before it can run

## Expected behavior

Read-only exec calls in Talk mode complete without requiring spoken confirmation. The gate documented in `nodes/talk.md` applies to "destructive shell commands" — a read-only lookup should not qualify.

## Actual behavior

Gateway log shows `talk.client.toolCall 112ms` — the exec call routes through the realtime tool call path and the voice confirmation gate intercepts it. The confirmation ID expires before the voice round-trip completes, causing the call to be blocked. Agent in Talk session reports "exec gate blocking it."

## What makes this confusing

Two separate gate systems interact here:

1. **exec approval gate** — governed by `tools.exec.mode` / `openclaw exec-policy`. Ours is `security=full, ask=off`. This gate is **already off** and is NOT the problem.

2. **voice confirmation gate** — fires on `talk.client.toolCall` in the realtime WebRTC path, documented in `nodes/talk.md` line 23: "Voice-originated consult runs require a new, exact spoken confirmation before high-impact actions such as sending messages, controlling nodes, browser/computer actions, service changes, **destructive shell commands**, or publication."

The exec-policy gate being off does not disable the voice confirmation gate on the `talk.client.toolCall` path. Both gates exist independently.

## Key measurements (confirmed live)

- Read-only lookup runtime: **1.435 seconds** (`time python3 interaction_lookup.py --name "Arnold"`)
- Zero writes, zero file mutations, read-only Google Sheets API call
- Well inside any kill ceiling
- exec-policy effective: `security=full, ask=off` (from `openclaw exec-policy show`)
- gateway log: `talk.client.toolCall 112ms` at time of blocked call

## Questions for the team

1. Is it intentional that the voice confirmation gate fires on **all** exec calls in the `talk.client.toolCall` path, including demonstrably read-only commands? The docs say "destructive shell commands" — is there a way to mark a command as read-only/safe to bypass the gate?

2. Was there a version where Browser Talk tool calls routed differently (not through `talk.client.toolCall`) that allowed exec to complete without the voice gate? This worked previously; local release notes only go back to 6.11 so we cannot pinpoint the change.

3. Is `gateway-control-v1` capability (thin-client mode where Gateway owns tool calls) relevant here? If the Gateway owns tool dispatch rather than the client, does the voice confirmation gate still fire on exec?

## Workaround under evaluation

Google Sheets MCP (`sheetsmcp.googleapis.com`) — MCP tools are not exec calls and would bypass the `talk.client.toolCall` exec gate entirely. Setup is non-trivial (new Google Cloud OAuth) but architecturally correct.
