*Project description:*
**After #1691 the default export's peak memory on Revit 2023 to 2027 files is still 1.4 to 4.4 times 0.17.0's; the part #1691 did not move is not the owners' graphs.**

Measure run [42954375538](https://github.com/DrunkOnJava/rvt-rs/actions/runs/42954375538) (#1691's head 8cf93e9c against `main` at 83347260, timed on one runner per file) and run 42949360321 (`main` against v0.17.0). Peak memory, MiB:

| file | v0.17.0 | `main` | #1691 |
|---|---:|---:|---:|
| Snowdon Towers Architectural (2024) | 1,072 | 3,960 | 2,099 |
| BIM4LCA office, concrete, as built | 914 | 2,051 | 1,432 |

| Snowdon Towers Structural (2024) | 259 | 469 | 495 |

#1691 lets go the owners that name nothing (walls) after the first read and meshes them a buffer at a time; that took 20% to 47% off the files whose walls are many. It left `rac_basic` (18.8 MB, 330 boxed elements, 3.0 s) where it was: 875 MiB, 4.4 times 0.17.0's, so most of the remaining growth is something else.

**Where to look.** `RevitFile::inflated_partition` keeps each inflated partition for the handle's lifetime (#266), and reading every boxed element's saved graphics now touches nearly every partition that holds graphics, where doors and windows touched few; the symbols' batches (`BATCH_OBJECT_BUDGET`, 20,000 graph objects) and the owners kept for their symbols (every owner that names a symbol keeps its graph from the first read) are the other holders. Nothing here is measured: the first step is a memory profile of `rac_basic` 2023 by stage (open, owners read, each batch, write), which Measure's timing run can give with a probe that prints the process's peak after each stage.

`--no-saved-meshes` returns 0.17.0's memory. The 0.18.0 notes state this table.
