## Problem

`scripts/check_docs_no_client_data.py` (#429) is correctly reasoned:

> Right layer is **pre-commit** (it has the local config; CI does not, since the config is gitignored).

That holds for files — and it means the guard covers exactly one surface. Every leak measured on 2026-08-06 was outside it:

| Surface | Passes through git? | Guarded |
| --- | --- | --- |
| `docs/*.md` | yes | ✅ pre-commit |
| Issue body | no | ❌ |
| Issue / PR comment | no | ❌ |
| PR description | no | ❌ |

#431's own comment thread carries roughly **278 occurrences** across six terms — more than ten times the ~22 lines in `docs/` it was opened to track.

Two reasons to automate rather than write a rule:

1. **The leak arrives by paste.** Someone runs a report locally and pastes the output to explain what they saw. No discipline survives that reliably.
2. **Agent sessions cannot self-check.** A hosted Claude or Cursor session has no access to `~/.gittan/timelog_projects.json` — local, gitignored, different machine. Agents author much of this repo's issue and PR text, and for that content a server-side check is not the convenient place for a guard, it is the only possible one.

## Acceptance criteria

```gherkin
Scenario: A new issue body containing a client term is flagged
  Given the repository holds the private term list as an Actions secret
  When an issue is opened whose body matches one of those terms
  Then a bot comment names the count and the field it matched in
  And the issue is labelled privacy:review
  And no matched term appears anywhere in the comment or the run log

Scenario: A fork without the secret degrades to skipped, never to a leak
  Given a repository or run with no term list configured
  When the check runs
  Then it exits successfully having checked nothing
  And it says so, so a silent pass is not mistaken for a clean result
```

## Decisions to confirm before implementing

1. **Term list as a repository Actions secret** (`PRIVACY_TERMS`). This is what breaks #429's "CI cannot have the terms" constraint — a secret is not in the tree, not in the diff, and not readable from a fork. Cost: a second copy that goes stale when a project is added.
2. **The check must never echo a match** — count and field name only, never the term, not even partially. Workflow logs on a public repo are public. #431's body is the proof: it printed the terms while claiming to mask them.
3. **Issues first**, then `issue_comment`, then PR bodies. `pull_request_target` carries secrets into a fork-triggered context and must never check out fork code.
4. **Share the matcher** with `check_docs_no_client_data.py` rather than copying it. Two definitions of "what counts as a term" will drift, and the drift gets discovered by a leak.

## Non-goals
