## Executive assessment

The poor ASVS numbers are a mixture of actual assessment defects, inaccurate teaching material, questionable reference answers, and metrics that answer different questions. They are **not a percentage of ASVS compliance, vulnerabilities detected, or requirements correctly verified**.

The most consequential finding is that the **345-record ASVS 5.0.0 catalog is accurate, but the handwritten interpretation surrounding it is not consistently accurate**. Several examples explicitly attribute a different obligation to a real requirement ID. Reference answers repeat some of those mistakes. The system can therefore learn a wrong interpretation and be rewarded for reproducing it.

There are also deterministic paths that turn missing information into a negative applicability decision, bypass semantic review for deferred/unknown-ground claims, or describe unassessed requirements as applicable. These affect trustworthiness independently of the model's capability.

Do not begin by increasing the model size, raising token limits, or optimizing the headline recall. First repair the assessment contract and its reference answers, then repair scoring and exclusions, then measure generation and review against an independently adjudicated corpus.

## 2. Is the standard represented correctly?

### The generated catalog and rosters: yes, at this snapshot

I compared every local record with OWASP's tagged **v5.0.0** release. All 345 IDs, texts, sections, section names, and levels matched. Every generated chapter roster matched the local catalog: 17 of 17. There are 70 L1 requirements, another 183 at L2, and another 92 at L3: cumulative totals **70, 253, 345**.

This rules out a stale 4.x catalog, missing chapter, or transcription error as the primary explanation. It does not validate the prose wrapped around the catalog.

Sources: [official ASVS project](https://owasp.org/www-project-application-security-verification-standard/), [OWASP v5.0.0 release tree](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0/en), [local catalog](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/frameworks/asvs/catalog.json), [catalog loader](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/frameworks/asvs/catalog.py).

**Maintenance gap:** the loader's hard-coded version is not validated against the payload's version, and existing shape/roster checks do not independently prove upstream semantic identity. Add an upstream release manifest/hash and an automated exact comparison, with an explicit reviewed update process. This is a future integrity weakness, not evidence that today's catalog is wrong.

### Level selection is not inherently a fork

`AsvsAnalysis` documentation calls a level-filtered run a fork of ASVS. The standard itself supports choosing a cumulative assurance level and making justified applicability decisions. A restricted tool capability is a limitation of the assessment; selecting L1 or L2 does not by itself fork the standard. Likewise, ASVS level is not the severity of an individual finding. These distinctions should be corrected in product documentation and critic instructions.

Source: [OWASP assessment guidance](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x04-Assessment_and_Certification.md), [local record contract](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/frameworks/asvs/record.py).

### “No passes from prose” is a product boundary, not a universal ASVS rule

Avoiding verified passes from a brief architecture description is sensible. But the rationale overstates the standard when it implies that every requirement always requires source code and the development team. Verification methods depend on the requirement. Actual documentation can satisfy a documentation obligation; configuration and runtime observations can settle other obligations. A sentence asserting that a policy exists is weaker than the policy itself, but both are currently flattened into “prose.”

Represent the available artifact and its evidentiary limits explicitly. Preserve “stated support” without claiming independently verified conformance. Do not equate “this input cannot prove a pass” with “a gap exists.”

## 3. Priority findings

Severity here means impact on the trustworthiness of the ASVS assessment, not an exploitable application vulnerability or ASVS level. **P0** means repair before treating quality numbers as trustworthy; **P1** means substantial assessment error; **P2** means measurement, maintainability, or usability weakness.

### F01 — P0: handwritten exemplars teach different obligations under real IDs

**Confirmed, direct comparison.** All 34 JSON exemplars across 17 lanes were inspected. Examples are appended to the lane prompt after the accurate roster, so these errors reach the agent directly; retrieval does not need to select them.

Examples of clear mismatches:

| ID | What the exemplar teaches | Published subject |
|---|---|---|
| V4.1.1 | Allowed HTTP methods | Correct response Content-Type |
| V6.3.1 | MFA obligation | Defenses against brute force/credential stuffing according to documented policy |
| V7.4.1 | Existence of idle timeout | Invalidation after session termination is triggered |
| V9.2.1 | Issuer/audience checks | Token validity time span |
| V12.2.1 | PostgreSQL connection protection | Client-to-external-service HTTP protection |
| V13.4.1 | Approved secret storage | Exposure of source-control metadata |
| V13.2.1 | Dependency inventory and maintenance | Authentication of backend components |
| V11.4.1 | Key generation/storage/rotation | Approved hashing algorithms |
| V5.2.1 | File content/type validation | File-size bounds |
| V5.3.1 | Browser execution of uploaded content | Server-side execution of untrusted files |
| V10.4.1 | General authorization-code handling | Exact allowlisted redirect-URI matching |
| V15.2.1 | Defensive handling of untrusted input | Dependency remediation timeframes |

### F02 — P0: reference answers contain wrong IDs, unsupported gaps, and source contradictions

**Confirmed examples; some labels require adjudication rather than mechanical correction.** Every ASVS reference and its case source was reviewed. The appendix inventories all 99; an unflagged row is not a certified gold label.

Especially consequential examples:

- **Case 04, V6.2.10:** an API key that never expires/rotates is labeled a gap under a requirement about keeping user passwords valid until compromise or user-requested change, rather than forcing periodic rotation. This is both the wrong credential type and a contrary lesson about rotation.
- **Case 02, V6.3.2:** fleet-wide PSK reuse/rotation is mapped to disabling default user accounts. The source does not establish default accounts.
- **Case 02, V14.2.1:** public firmware readability/integrity is mapped to keeping sensitive data out of URLs.
- **Cases 02 and 10, V12.2.1:** MQTT/MySQL transport concerns are mapped to an HTTP-specific requirement. Real transport concerns do not make the chosen ID correct.
- **Case 01, V6.3.1:** “no MFA” does not prove absence of the required anti-automation defenses. The reference itself says that controls are unstated, yet calls the gap settled.
- **Case 01, V13.3.1:** an environment variable does not prove no secret manager is used; secret managers can inject environment variables.
- **Case 01, V8.2.2:** a shared database account is not proof that the application lacks record-level authorization. It can be a distinct least-privilege concern.
- **Case 05, V13.3.1:** the rationale says it is unclear whether configuration stores contain secrets, while the source explicitly says both hold credentials.
- **Case 05, V12.3.3:** unknown encryption is labeled a prose-established gap; the source explicitly says the diagram does not say whether it is encrypted. Requirement-specific protocol applicability also needs checking.
- **Case 09, V15.3.1:** the source says the delivery file contains only addresses, yet the reference treats the subset question as unstated. Whether addresses are sufficient is a separate question; the existing rationale contradicts the evidence.
- **Case 08, V9.2.4:** a shared signing key does not prove absent audience validation. “Not stated” is a valid question, not proof of a failed check.

Many documentation references say no document “exists” when the evidence only omits it. A `needs-more-prose` status does not repair an assertive false sentence.

**Recommendation:** reopen reference adjudication before using these labels for tuning. Have reviewers assess the actual source, exact requirement, applicability, sufficiency, and acceptable evidence routes separately. Record disagreements and acceptable alternative routes. Treat this as correcting the measuring instrument, not lowering a quality bar.

Source: [ASVS corpus](https://github.com/mstarks01/work-agent/tree/7f0f894ac429e098f3c458558d1cf0c2d5e15469/evals/corpus).

### F03 — P0: applicability scorer counts explicit negatives as expected positives

**Confirmed by source and deterministic checks.** `score_applicability()` builds `expected` from all `ReferenceRequirement` records without filtering `disposition == "not-applicable"`.

Case 04 V9.1.1 and case 05 V17.2.1 are explicitly negative references. Correct not-applicable results are therefore disposition successes but applicability misses. There are **97 positive records and two negatives**, not 99 positives. An otherwise perfect output under those labels cannot receive 99/99 applicability recall while correctly excluding both negatives.

`score_yield()` repeats the all-reference expected-set assumption. It also classifies unlisted rejections as “earned” on sampled reference sets and does not honor the `rules_on_unit()` rejection-cause distinction used by the main applicability scorer. Rejecting a badly filed draft can be counted as destroying a valid requirement.

**Recommendation:** separate positive, negative, and unadjudicated reference sets. Score applicability from actual applicability decisions. Score draft rejection correctness separately from requirement exclusion. Add a regression case where correctly excluding an explicit negative succeeds in every relevant metric.

### F04 — P0: silence is converted into non-applicability by deterministic rules

**Confirmed by code and constructed models.** Presence tests for file handling, self-contained tokens, OAuth/OIDC, and WebRTC can decide a whole chapter. No matching term in a limited model becomes a hard exclusion. Per-requirement tests have the same closed-world assumption. The model does not certify that its feature inventory is complete.

A concrete model description, “A web service creates downloadable PDFs from user-supplied filenames,” caused nine L2 file-handling requirements to be ruled out. Generated filenames and downloads can reach V5.3.2/V5.4.1 without an upload. “Receives documents from customers” also missed the upload vocabulary. Thus this is both a vocabulary defect and an incorrect chapter-wide predicate.

The merge enforces deterministic `ruled_out` decisions even after lane analysis, so the model cannot reliably recover by identifying contrary source evidence.

**Recommendation:** lexical absence should mean “unknown,” not “absent.” Require evidence-backed explicit negatives and a declared completeness boundary for hard exclusions. Attach predicates to requirements and their actual conditional clauses, not one feature to a whole chapter. Keep candidate generation advisory.

Source: [ASVS rules](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/frameworks/asvs/rules.py), [merge graph](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/graph.py).

### F05 — P1: unknown system applicability becomes machine-readable “not applicable”

**Confirmed.** The precondition distinguishes refuted from undecidable, but both can produce a nonempty refusal reason. `_scope_state()` returns `not-applicable` for any nonempty refusal reason.

Direct probe: `_scope_state('V1.2.4', 'Cannot determine whether a web application exists', {})` returns `not-applicable`.

Separately, the precondition treats web-looking flow protocol text as sufficient even if all processes are non-web. A backup using HTTPS can therefore satisfy a gate that extraction guidance says should not be satisfied merely by a backup's HTTPS transport. Substring protocol matching is also broader than a normalized protocol classification.

**Recommendation:** retain precondition state as a typed value through report assembly; distinguish applicability unknown from explicitly out of scope. Specify which application and ownership boundary is being assessed. A web-related protocol somewhere in a mixed model is not a complete scope definition.

### F06 — P1: deferral bypasses validation and loses its explanation

**Confirmed.** `partition_proposals()` routes code/config/people proposals away before full evidence resolution and critic review. The retained deferral is essentially requirement ID plus evidence kind; its rationale, affected scope, and evidence chain are not retained in the public scope entry.

A schema-valid proposal with requirement `99.99` in the authentication lane and a nonexistent evidence reference was accepted by this partition as `{'V6.99.99': 'code'}`. The catalog does not contain that ID. Later catalog-driven scope generation cannot make this into a valid visible requirement decision. This probe demonstrates the validation gap; it is not a live model incidence estimate.

**Recommendation:** validate the ID, selected level, references, applicability reasoning, and evidence route before partitioning. Preserve a typed deferred assessment containing why, what artifact would settle it, and which component/control it concerns. Apply semantic review to deferrals as well as asserted gaps.

### F07 — P1: an unknown ground bypasses the critic without validating relevance

**Confirmed behavior; error frequency unmeasured.** `Claim.settled_by_grounds()` automatically makes a claim `needs-info` when it cites an unknown attribute. Such drafts are removed from the critic's unsettled set.

An unknown fact supports uncertainty; it does not prove that the cited requirement applies, that the fact is relevant, or that the description accurately states the requirement. A wrong-ID or overreaching draft can bypass the very check needed to reject it. Its original assertive text can remain beside a needs-info verdict.

**Recommendation:** mechanically forbid “confirmed” when essential grounds are unknown, but still review applicability, ID meaning, and reasoning. Do not treat an uncertainty marker as semantic approval.

Sources: [claim settlement](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/report.py), [critic flow](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/critic.py).

### F08 — P1: the critic lacks the exact requirement being judged

**Confirmed composition.** `compose_critic_skills()` supplies framework critic guidance and a lane-boundary digest, not the catalog text of each draft's requirement. The critic receives the system model and selected grounds/quotes rather than the complete source evidence corpus.

The final semantic defense must therefore rely on model memory or the draft's own possibly wrong paraphrase. This is especially damaging given F01. Selected quotes prove occurrence, not that omitted nearby text does not contradict the draft.

**Recommendation:** join exact versioned requirement text and applicability conditions to every assessment reviewed; supply retrievable source context and contradicting facts. A requirement-specific review is more useful than merely increasing a global critic's token allowance.

Source: [critic skill composition](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/src/analysis_service/skills.py).

### F09 — P1: claim rejection and requirement non-applicability remain conflated

**Confirmed contract weakness.** `rules_on_unit()` now distinguishes lane and duplicate rejections, a useful correction. But an evidence rejection can still act as a negative applicability ruling. Rejecting an unsupported gap, an invalid inference, or a proposed pass does not establish that the requirement is out of scope.

**Recommendation:** make applicability independent of draft validity and assessment outcome. A rejected statement about an applicable requirement must leave that requirement applicable or unknown, not excluded. Preserve the reason for rejecting the statement.

### F10 — P1: complete scope lists disguise incomplete assessment

**Confirmed.** For catalog requirements with no emitted claim, `_scope_state()` defaults to `applicable` unless deferred or ruled out. The resulting list can be complete even when the agent did not assess those requirements. The scorer intentionally does not treat all these default entries as positive observations, so public scope semantics and scored semantics differ.

**Recommendation:** require one explicit outcome per in-level requirement, including `not-assessed`. Separate “catalog coverage” from “assessment completed.” Never infer that a requirement was considered because a list was filled deterministically.

### F11 — P1: the proposed verdict language does not separate a gap from uncertainty

The record describes `confirmed` as “applies and the input does not show it satisfied,” and `needs-info` as “applies and the input does not settle it.” Those conditions overlap. Shared attacker-oriented instructions further encourage producing findings rather than neutral requirement assessments.

`needs_evidence='prose'` is retained because prose is carried, then stripped during resolution; this alone does not force a needs-info verdict. The evidence route and final gap state can disagree.

**Recommendation:** use independent axes:

| Axis | Required distinction |
|---|---|
| Applicability | Applies / does not apply with reason / unknown |
| Assessment | Supported gap / stated support but unverified / inconclusive / not assessed |
| Evidence | What is present, sufficiency for this obligation, and acceptable next artifacts |
| Review | Accepted reasoning / rejected reasoning, without changing applicability implicitly |

A future verified-pass state should require an explicit verification workflow. It need not be offered by today's prose-only product.

### F12 — P1: sampled references still leak into negative judgments

The current `precision` property correctly returns `None` unless `reference_set == 'exhaustive'`. Preserve that repair. But the module's opening rationale still says a finite catalog makes the reference complement negative; yield still makes related judgments, and “over-applied” suggests an error where the truth is only “not in the reference sample.” `excluded` is complement arithmetic, including silence, rather than verified correct exclusions.

A finite standard does not imply an exhaustive case annotation. Rename unadjudicated outputs accordingly and obtain independent judgments before assigning true-negative or false-positive meaning.

### F13 — P1: corpus breadth and independence are insufficient for the claimed surface

The 11 ASVS cases contain 99 records covering **51 unique requirement IDs** out of 345. All 17 chapters appear, but WebRTC appears only as a negative and OAuth has only one reference. There are no L3 cases. Cases 03 and 07 have no ASVS references. The corpus is sampled and no merged case sittings establish exhaustive annotation.

Counts by expected disposition: 31 needs-code, 26 needs-config, 20 gap-from-prose, 17 needs-more-prose, three needs-people, two not-applicable. Two negatives are far too few to characterize exclusion safety.

Many examples reuse the same payments setting and conceptual habits as the corpus. Exemplar-proximity metadata is helpful but not a substitute for a held-out, independently authored evaluation.

**Recommendation:** add complete feature-present/feature-absent/feature-unknown pairs, protocol-specific transport cases, real positive OAuth and WebRTC cases, L3 coverage, stated-control counterexamples, and adverse evidence contexts. Include a small fully adjudicated application at each selected level before claiming applicability precision. Split tuning cases from held-out cases.

### F14 — P2: extraction metrics omit attributes that control ASVS behavior

`_SCORED_ATTRIBUTES` measures kind, exposure, assets, and reduced states of authentication/encryption/classification. It does not score `interface_kind`, protocol, technology, notes, or the semantic content of stated controls. These drive preconditions, feature tests, and knowledge selection. Exact free-text matching would indeed be wrong; omitting their meaning entirely is also insufficient.

**Recommendation:** evaluate normalized feature facts and whether they preserve downstream applicability decisions. Test that a sparse source remains sparse and that a non-web process stays non-web. Score supported facts, invented facts, lost qualifiers, and contradictions—not merely whether a field is filled or “stated.”

Source: [extraction evaluation](https://github.com/mstarks01/work-agent/blob/7f0f894ac429e098f3c458558d1cf0c2d5e15469/evals/harness/modes.py).

### F15 — P2: evidence validation proves shape and quotation, not entailment

The shared model offers a graph and free-text attributes, not a complete inventory of endpoints, request fields, auth policies, documentation, and verification artifacts. Source/quote checks can establish that words occur; they cannot establish that an inferred control state follows from them. Optional excerpts leave some facts without direct traceability. Raw source details may be lost before the critic sees them.

Do not force every control into a graph node. Add evidence-backed feature/control assertions alongside the graph, each with source location, explicitness, completeness boundary, and contradictory evidence. Make source quotation and entailment separate validation questions.

### F16 — P2: evidence modality labels are too rigid

A single required answer among code/config/people/prose treats implementation-dependent verification paths as mutually exclusive. A response header can be set in application code or infrastructure configuration and verified by observing responses. A document can be attached rather than described. “People” is not the only way to establish a process record.

Route to acceptable artifacts and specific questions rather than a fixed per-requirement modality. Score multiple defensible routes as correct. Avoid improving routing accuracy by hard-coding the corpus's preferences.

### F17 — P2: level and runtime handling create avoidable work and ambiguity

Selected-level catalogs are cumulative and correct, but prompts include full chapter rosters and the record deliberately tolerates some beyond-level claims. A valid catalog ID can therefore be out of the selected assessment scope; the evaluator flags this later. All chapter lanes are constructed even when a selected level or established scope gives a lane little work.

Filter the supplied roster to the selected level and explicitly separate optional higher-level observations. After exclusion semantics are repaired, skip only lanes proven to contain no assessable requirements. Do not optimize away uncertain chapters.

Historical critic truncation is documented in #410. Current larger caps mitigate an identified failure mode but are not evidence that current live runs are complete. Capture per-lane emission completeness, retries, truncation, cost, and terminal job failures in fresh runs.

### F18 — P2: presentation can overstate certainty and hide useful work

Generic confirmed/rejected language obscures the ASVS-specific meanings. Actionable-claim totals omit deferred requirements, while grouped scope counts make it difficult to inspect exact requirements and reasons. Unknown-to-NA conversion amplifies this problem.

Render an expandable row for each selected requirement: exact text/version, applicability, assessment state, evidence, next question, and review reason. Distinguish “no supported gap found” from “no assessment performed.” Make deferrals useful work items, not just counts.

### F19 — P2: aggregate quality can improve by omitting difficult answers/jobs

Disposition accuracy excludes unreached requirements from its judged denominator. Failed live cases are reported separately but do not contribute ordinary case scores. These are legitimate conditional metrics only if paired with coverage and successful-job rate. Neither should be presented alone as overall quality.

Report at least: successful jobs / attempted jobs; explicitly assessed requirements / selected requirements; correct decisions / expected decisions including missing outputs; and conditional accuracy among assessed decisions. Show both per-case and pooled values.

### F20 — P2: narrative guidance contains additional assumptions worth correcting

The knowledge layer includes overgeneralizations such as a login page implying a session cookie, a wildcard CORS origin being inherently a failure, or general transport guidance applying identically across protocol-specific requirements. Login can use other state mechanisms; permissive CORS depends on the resource and credentials; V12 requirements have distinct scopes.

`domains/oauth-oidc.md` says OAuth is neither authentication nor authorization, while its purpose is delegated authorization. The documentation-requirement case moves from omitted documentation to an unwritten allowlist. These are semantic teaching defects even where guardrails elsewhere caution against assumptions.

Review all knowledge prose alongside the exemplars. Preserve helpful prompts to investigate, but do not phrase common architectures or security heuristics as established facts or exact ASVS obligations.

## 4. What to preserve

The repo has useful foundations: versioned IDs, a faithful catalog, reproducible generated rosters, cumulative level selection, framework separation, explicit uncertainty fields, structured evidence references, sampled-reference precision suppression, deterministic instruments separated from live evaluations, and provenance machinery. Recent changes distinguishing duplicate/lane rejections and including deferrals in recall address real problems. The appropriate response is to repair the semantic contracts and their tests, not discard the pipeline.

API authentication, job ownership, failure/deadline handling, execution identity, and CI separation were inspected as supporting paths. They are not evidence that ASVS quality is solved, nor did this audit establish an unrelated exploitable API vulnerability. Do not reinterpret the findings above as a penetration-test result against the service.

## 5. Recommended sequence and acceptance criteria

1. **Freeze quality claims and correct the oracle.** Independently review all 34 exemplars and 99 reference records against exact ASVS 5.0.0 text and sources. Record acceptable alternate evidence paths. Keep old scores labeled with old corpus/scorer identity.
2. **Repair the assessment contract.** Separate applicability, gap/support/unknown, evidence sufficiency, and draft review. Retain explicit unknown and not-assessed states. Acceptance: an empty or sparse input cannot manufacture not-applicable or confirmed-gap decisions.
3. **Repair deterministic exclusions and scoring.** Remove closed-world lexical exclusions; fix explicit-negative denominators, sampled-negative yield, and failure/coverage reporting. Acceptance: explicit negative references are successes, unlisted sampled results are unjudged, and a missing answer never improves the overall success rate.
4. **Repair evidence and review.** Validate every proposal before deferring; carry the explanation; give the reviewer exact requirement text and source context; review unknown-ground claims semantically. Acceptance: invalid IDs/references cannot disappear into a successful deferral; a correct unknown marker cannot legitimize a wrong requirement interpretation.
5. **Build independent evaluation coverage.** Fully adjudicate a small L1/L2/L3 set; expand feature/absence/unknown, OAuth/WebRTC, protocol and source-contradiction cases. Acceptance: labels are source-backed, reviewer disagreements retained, and held-out cases have not been used as examples.
6. **Only then run controlled model/prompt experiments.** Compare unchanged baseline with one intervention at a time, repeated runs, fixed corpus/scorer/provider identities, cost and latency, and per-stage losses. Compare final correctness and useful next-evidence requests—not just trigger recall. A small historical model comparison does not prove model capability is irrelevant.

The ordered applicability/evidence questions proposed in #655 are directionally useful. They do not alone fix wrong requirement meanings, incorrect gold labels, deterministic hard exclusions, or critic bypasses.

| Applicability recall | Explicit positive reference decisions only |
