**parallel-step harness can hang past actual completion (exit 124) despite work finishing successfully**

*Project description:*
## Problem

A generated harness containing a `parallel` step completed all of its actual work (visible in the log: all agent calls returned, including the final orchestrator step's answer text printed in full) but the wrapper shell process did **not exit** within a generous 150-second timeout and had to be killed externally (`timeout 150 bash workflow.sh` → exit 124).

This is a "looks hung forever, but the real work is actually done" failure mode, which is a bad experience for anyone running a generated harness in a script or CI job with a fixed timeout — the workflow reports as failed/timed-out even though it succeeded.

## Reproduction

Workflow: 1 `vars` step, 1 `parallel` step with 4 `agent` critic children, 1 `vars` step reading their output files, 1 final `agent` step merging the results (5 real `opencode run` calls total, ~15-40s of actual model latency based on log timestamps).

```
timeout 150 bash multi_agent_review_loop.sh > run.log 2>&1
echo "exit: $?"   # => 124
```

The log clearly shows the final merge step's `step_finish`/`text` events with the complete correct answer, printed *before* the timeout fired. `ps aux --forest` after the kill showed **no lingering `opencode` or `tee` processes** related to the run — so this does not look like a permanent leak, but rather a transient condition where the wrapper script's own exit was blocked past real completion.

## Suspected root cause

`run_step()` wraps each step's function call in process substitution for logging:

```bash
"$step_name" > >(tee -a "$LOG_FILE") 2> >(tee -a "$LOG_FILE" >&2)
```

When `$step_name` is the `parallel` step's wrapper function, it backgrounds several child functions (`"$child" & pid=$!` per branch) *inside* this redirected context. Each backgrounded child inherits copies of the process-substitution's write-end file descriptors. This is a well-known bash quirk: a `>()`/`<()` process substitution's reader (`tee` here) only sees EOF once *every* process holding a copy of the write end has closed it — including any short-lived grandchild processes spawned by `opencode run` itself (e.g. MCP server subprocesses, plugin processes) that may not close their inherited fds promptly even after the visible parent work is done. The `wait "$pid_..."` calls inside the parallel wrapper only wait for the direct children, not for any of their own descendants that might still be holding the fd.

Not yet root-caused with 100% certainty (would need `strace`/`lsof` captured live during a hang to confirm which specific process held the fd open), but the symptom profile (work done, output printed, no lingering process afterward, still didn't exit) matches this pattern closely.

## Proposed fix (needs deeper investigation first)

Options to explore, roughly in order of invasiveness:
1. Avoid wrapping `parallel`-typed steps in the `tee`/process-substitution logging path at all — log each parallel branch's own output directly to the log file (e.g. via `exec > logfile` inside each branch) instead of relying on process substitution around the outer wrapper function.
2. After each backgrounded branch's `wait`, explicitly close any fds it might still be holding (defensive `exec 1>&- 2>&-` at the end of each branch function) before returning to the parent wrapper.
3. Add a repro test harness with a synthetic long-lived grandchild process (e.g. a background `sleep` spawned by a stub "agent" script) specifically for a `parallel` step, to nail down and regression-test the exact fd-holding culprit before landing a fix.

## Value vs. effort

- Value: high — a workflow that silently reports "timed out" via its own exit code despite having succeeded is a serious trust problem for any CI/automation use of flowsh-generated harnesses that gate on exit code or wall-clock timeout.
