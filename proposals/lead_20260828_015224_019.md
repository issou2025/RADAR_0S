## Problem Statement

Everything the system declines to decide alone ends up waiting for a human, and there is nowhere for that human to go. A caregiver cannot enroll the voices the device must recognise, cannot see why it believes what it believes, cannot correct it when it is wrong, cannot write the reassurance it is supposed to speak, and cannot act on a single queued question.

## Solution

One plain web page, served by the same Python application, where a caregiver enrolls the household, reviews what the device has learned and why, corrects it authoritatively, works through the queue, and writes the words the device says when reassurance is needed.

## User Stories

1. As a caregiver, I want to sign in, so that my mother's private life is not on the open internet.
2. As a caregiver, I want to record my mother's voice, so that the device can tell her apart from everyone else.
3. As a caregiver, I want to record the few people who actually visit, so that what they say can be remembered and a television cannot.
4. As a caregiver, I want to re-record a voice that is not working well, so that a bad sample is fixable without starting over.
5. As a caregiver, I want to add the people who matter before the device has heard anything, so that it is useful on day one.
6. As a caregiver, I want to record how someone is related and where they live, so that my mother can ask the questions she actually asks.
7. As a caregiver, I want to see every value the device holds and where each came from, so that I can tell overheard from entered.
8. As a caregiver, I want to see the sentence that caused a fact, so that I can judge whether to trust it.
9. As a caregiver, I want that sentence still there a week later, so that the audit trail is not shorter than the memory.
10. As a caregiver, I want to see what a value used to be, so that I can spot a change I did not make.
11. As a caregiver, I want my correction to stick permanently, so that overheard speech cannot undo it.
12. As a caregiver, I want one queue holding everything needing a decision, so that there is a single place to look.
13. As a caregiver, I want each queued item to show what would be written and what was said, so that I can decide without guessing.
14. As a caregiver, I want approving an item to perform the write, so that agreeing is a click rather than re-entering it.
15. As a caregiver, I want to pick the right person when the device could not, so that a misheard name reaches the real person.
16. As a caregiver, I want discarding an item to leave nothing behind, so that saying no is free.
17. As a caregiver, I want to see conflicts as conflicts, so that I understand why the device has started hedging.
18. As a caregiver, I want to write the exact words the device says when my mother asks the same thing over and over, so that comfort is in my voice and not a model's.
19. As a caregiver, I want to name the topics that must never be answered plainly, so that a death or a money question is handled the way our family has agreed.
20. As a caregiver, I want to add or cancel an event directly, so that I can correct the schedule without waiting to be overheard.
21. As a caregiver, I want the page usable on a phone, so that I can act on something while I am out.

## Implementation Decisions

**Python-first, no separate toolchain** (ADR-0006). Server-rendered templates with light interactivity, served by the same application on the same deployment. Every control is a form post. No React, no Node build.

**Authentication.** A single caregiver credential per deployment, held in secret storage, establishing a session. Modest by design, but the page holds voice recordings and a vulnerable person's history, so it is not left open.

**Voice enrollment.** Several short samples per household member, each labelled with who it is and whether they are the resident. Enrollment is what makes the speaker signal a positive match against known people rather than a negative one (ADR-0005) — without it the device cannot distinguish a visitor from a television. It is therefore built early rather than with the rest of this page.

**Directory management.** Create and edit entities, set the three fixed properties, add and supersede notes. Values entered here are caregiver-sourced and therefore pinned.

**History and provenance.** Every fact block renders its current value, source, assertion time, the raw phrase, and prior values beneath it. Provenance text is read from the fact block itself, not by looking up the originating utterance, which expires within the hour (ADR-0009).

**Review queue.** One list, all item types (ADR-0010). Each row shows the pending write in readable form and quotes the utterance. Approving replays the held write with any choice the caregiver made — a selected entity, a confirmed value — and, being a caregiver write, pins the result (ADR-0003). Discarding removes the item entirely. Conflict items show current and candidate values side by side.

**Reassurance and policy authoring.** Free-text reassurance per topic, stored and later spoken verbatim, never generated (plan §12). Policy topics carry text used by the write gate as keywords and by the read gate as an embedding, so saving a topic computes and stores its embedding (ADR-0007).

**Event management.** Create, retime and cancel events directly. Cancellation sets the stored flag; planned-versus-past is never stored (ADR-0004).

**Presentation budget.** Legibility only. This page is scored as evidence that feedback capture exists, not as a designed product, and its scope is already wide.

## Testing Decisions

Good tests drive the page over HTTP and assert on resulting state and rendered content, exactly as a caregiver would experience it. No browser automation.

**App seam** (primary), against the emulator with fakes.

Cases: unauthenticated access refused; enrollment storing labelled samples and re-recording replacing one; an entity created here having pinned values; a correction superseding an ambient value and surviving later ambient speech to the contrary; history showing prior values and raw phrases; provenance still rendering after the originating utterance has expired; the queue listing every item type; approving an unresolved-name item with a chosen entity producing the event with that entity attached; approving pinning the result; discarding leaving nothing; a conflict item showing both values and clearing on resolution; saved reassurance text later spoken verbatim by the read path; saving a policy topic computing its embedding; an event cancelled here no longer offered as upcoming.

**Firestore seam.** Embedding storage for policy topics, and provenance surviving real TTL expiry.

**Prior art.** Spec 5 owns the write path this page drives; assertions should go through it rather than around it.

## Out of Scope

Answering residents, policy evaluation and repeat counting belong to spec 6. The room-facing page belongs to spec 8. Multi-caregiver accounts, roles and per-user audit trails are not in this prototype.
